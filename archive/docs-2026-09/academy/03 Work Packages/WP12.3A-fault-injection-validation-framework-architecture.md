# WP 12.3A — Fault Injection & Validation Framework Architecture

## What This Document Is

The design-phase retrospective for the two-Work-Package pair `WP 12.3A`/
`WP 12.3B`, mirroring the two-phase discipline `WP 2.7A`/`WP 2.7B` first
established for the Runtime Host and `WP 4.2`/`WP 4.3` repeated for the
Plugin Manifest and Sample Module: architecture first, implementation
only once every open question is actually settled. Commissioned directly
— not named in `WP11.0B Architecture Roadmap.md`'s own `v0.12.0` §3
table (`WP 12.0A`–`WP 12.2A`) — the identical pattern `WP 11.3A`/`WP
11.3B` and `WP 11.4A`/`WP 11.4B` each already established for
directly-commissioned work inserted outside a predicted roadmap slot.

## 1. Introduction

TempestOS shipped exactly one intentionally-failing module,
`Tempest.Samples.DuplicateNavigationSampleModule` (`WP 5.0B`) — real
code, whose `InitialiseAsync` deliberately registers a duplicate
`NavigationItem.Id` to prove `ModuleLifecycleManager`'s per-module
isolation (ADR-0013) genuinely works. This Work Package's own brief:
remove intentionally-failing modules from the default runtime while
preserving them as first-class diagnostics/fault-injection tools,
explicitly enable-able for validation runs.

## 2. What Was Found

**A genuine, previously-undisclosed defect, not a hypothetical one.**
Traced directly: both real presentation layers (`Tempest.App`'s
`WorkspaceShell`, `Tempest.Desktop`) compose through
`EngineeringWorkspaceComposer.Build()` → an unrestricted
`new TempestHostBuilder()` — a genuine, full-`AppDomain` reflection
scan. Since both reference `Tempest.Samples`,
`DuplicateNavigationSampleModule` was discovered and initialised, and
therefore permanently left `ModuleState.Failed`, on **every real launch
of the shipped application** — confirmed directly:
`tests/Tempest.Desktop.Tests/ModuleLifecycleStabilityTests.cs` already
special-case-excluded this exact module's own Id from every "no module
failed" assertion, with its own doc comment explaining why. TempestOS's
own health-reporting surface, `IDiagnosticsProvider.Modules`
(`Diagnostics Architecture.md`, ADR-0039), therefore never reported a
genuinely healthy platform in real use.

**Simply moving the module to a new, unreferenced project was found
insufficient as the sole mechanism.** `ReflectionFrameworkDiscoveryService`'s
unrestricted overload scans the *whole process's* `AppDomain`, not only
directly-referenced assemblies. The test suite already legitimately
loads every `src/` project into one process; a future unrestricted
`TempestHostBuilder()` call anywhere in that process would silently
resurrect the identical hazard, with no compile-time signal. A second,
explicit, default-excluded discovery-time marker was found necessary as
a genuine architectural decision, not an implementation convenience —
closing this Work Package's own "Introduce a Diagnostics/Fault Injection
registration mechanism" deliverable required both pieces together (see
ADR-0102).

## 3. Architectural Lessons

**"Not referenced" and "not discoverable" are different guarantees, and
only one of them survives a future in-process loader.** This is the
single most consequential finding of this design phase — the same class
of lesson `Sample Module Architecture.md`'s own Testing Strategy section
already drew once, from the opposite direction (`InvalidIdModule`
polluting an unrestricted scan for reasons having nothing to do with
`ClockModule`). A structural boundary (project references) is necessary
but not sufficient wherever a mechanism (reflection-based `AppDomain`
scanning) can cross it silently; a second, explicit, type-level
classification closes the gap a project boundary alone cannot.

**Naming collision avoidance is itself a real design decision, not
bikeshedding.** The Work Package's own brief suggested
`Tempest.Diagnostics`/`Tempest.Samples.Diagnostics` — both would have
introduced a third meaning for "Diagnostics" in a codebase that already
uses it for `IDiagnosticsProvider` (a read-only health-reporting
platform service) and `DiagnosticsSampleModule` (its own living
reference module). `Tempest.Validation` — "Diagnostics observes; this
project proves" — was chosen specifically to keep this glossary-driven
codebase's own cross-referencing discipline intact, confirmed against
`Diagnostics Architecture.md` and `Engineering Glossary.md` directly
before naming anything.

**A marker interface, not a second attribute, for an "is-a" question.**
`ModuleMetadataAttribute` (ADR-0027) was seriously considered as the
template to reuse — it is this codebase's own closest existing precedent
for a discovery-time classification. Rejected on direct comparison:
ADR-0027 solves an instantiation-avoidance problem (read metadata
without constructing); this decision answers a plain "is this type a
fault-injection module, yes or no" question, which `is`/`IsAssignableFrom`
answers more directly, with none of the attribute/reality-drift risk
ADR-0027 itself already discloses as an accepted cost of its own,
different mechanism.

## 4. Key Takeaways

- Two independently-necessary mechanisms, verified apart before being
  combined: project isolation (sufficient for the two real, shipped
  processes) and a default-excluded discovery marker (sufficient
  regardless of what is loaded into a given process). Neither was
  redundant; both were required by direct reasoning about
  `AppDomain`-wide reflection scanning's own actual scope.
- The defect this Work Package fixes was found by tracing the real
  production composition path end to end (`EngineeringWorkspaceComposer`
  → `WorkspaceHost`), not by inspecting the failing module in isolation
  — the same "trace the real path, don't assume" discipline this
  project's own retrospectives have repeatedly credited for finding
  genuine, previously-undisclosed defects (`TD-37`, `WP 10.1B`; the
  `v0.10.0`/`v0.11.0` tag-position defects, `WP 11.1B`/`WP 11.4B`).
- See `WP12.3B Fault Injection & Validation Framework Implementation.md`
  for the realised design, `ADR-0102` for the complete decision record,
  and `Fault Injection & Validation Architecture.md` for the full
  architecture document this retrospective summarises.
