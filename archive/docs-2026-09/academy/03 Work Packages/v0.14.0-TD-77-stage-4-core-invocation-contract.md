# TD-77 Stage 4 — Core Invocation Contract, Proven Against Real Bindings

## 1. Introduction

`1c38cb4`, the third of four `TD-77` stages, adds no production code —
Stage 2 had already built every one of the twelve deliverables Stage 4's
own brief named. What it adds is the proof Stage 2 could not have written
and Stage 3 had only been implicitly relying on: that `ICommandRegistry`
actually carries all 74 real production bindings from an Id and a context
through to a registered handler. A pre-`v0.14.0` engineering-body-of-work
row.

## 2. Purpose

To assert, rather than assume, that the contract Stage 2 built and Stage
3 populated actually holds for every one of the 74 real descriptors —
Stage 2 had proven every rule of the contract against purpose-built
fixture commands, and Stage 3 had proven what the descriptors declare, but
neither had asked whether the registry carries a real binding all the way
through.

## 3. Background

Re-implementing Stage 2's deliverables would have been churn — Stage 3
had already been consuming all of them since `bb22983`. The gap Stage 4
actually closes is the word "against" in its own brief: proving the
contract against Stage 3's binding data, exhaustively, rather than against
fixtures.

## 4. The Problem

A contract proven correct against fixtures, and descriptors declared
correct individually, do not together prove the two agree with each other
at scale — nothing had checked that all 74 real bindings actually reach a
registered handler through the registry's own path, or that `Evaluate`
and `InvokeAsync` agree with each other across every one of them.

## 5. The Design

Every test here enumerates the production registry and holds for all of
it, not a hand-picked sample: 56 bindings build a command without
throwing, from values their own parameters accept (the "a throw out of
`Build` is a defect" invariant, checked exhaustively rather than by
inspection); 56 reach a registered handler through the registry's own
path; 18 report their own reason verbatim from both `Evaluate` and
`InvokeAsync`, identically under every context; 74 agree between
`Evaluate` and `InvokeAsync` across a four-context matrix (296
comparisons, same verdict and same message); 30 validated parameters
refuse a bad value as an outcome, never an exception; 42 prompt-requiring
bindings refuse to run unprompted and treat a decline as Cancelled, not
failure; 14 unattended commands run with no prompt at all. Two `Evaluate`
semantics are deliberately pinned rather than changed: a multi-selection
is Kind-gated on Primary alone, so a mixed-Kind selection passes on its
first entry; and the "one object at a time" gate applies even to bindings
declaring `CommandContextRequirement.None`, so all seven creation
commands are unavailable while two unrelated objects happen to be
selected. Both are pinned by tests documenting them as approved semantics
and carried forward as Stage 5 decision points, deliberately not
"fixed" — fixing either while claiming to implement the contract would be
changing it.

## 6. Alternatives Considered

Re-implementing Stage 2's twelve deliverables as though this stage needed
its own version — explicitly rejected: "Re-implementing it would be
churn, so no production code changes here."

## 7. Why This Solution Was Chosen

Because the honest reading of Stage 4's own brief was that its
deliverables already existed; what remained undone was the proof against
real data, which is what this stage actually supplies.

## 8. Architectural Principles

A contract proven against fixtures and a population proven individually
correct do not together prove the two compose correctly at scale — that
composition needs its own exhaustive proof, over the real registry rather
than a sample of it.

## 9. Benefits

23 new tests. Six mutations of `CommandRegistry` designed, six killed.
Core Debug/Release 3034 passed, Desktop Debug/Release 332 passed, all
with `TreatWarningsAsErrors=true`; governance health check exit 0.

## 10. Trade-offs

Two pinned semantics (Primary-only Kind gating on multi-selection; the
context-`None` gate applying even to selection-independent commands) are
carried forward as decision points rather than resolved — recorded
explicitly as Stage 5's to decide, not silently deferred.

## 11. Common Mistakes

Assuming that because a brief lists deliverables by name, those
deliverables must not yet exist — checking first (and finding Stage 2 had
already built all twelve) avoided writing 700+ lines of redundant
production code.

## 12. Future Evolution

Stage 5 (`e72b933`) is where the two pinned semantics this stage
documents become live decision points the three consuming surfaces
(Ribbon, Palette, Macro Manager) must actually honour.

## 13. Key Takeaways

- Before implementing a stage's named deliverables, check whether an
  earlier stage already built them — re-implementing proven code is
  churn, not progress.
- A contract proven against fixtures needs a separate, exhaustive proof
  against the real production data it is meant to serve.
- Pin a semantic decision explicitly, with a test documenting it as
  approved, rather than silently changing it while claiming only to
  implement the existing contract.
