# Windows Delete-While-Locked Test Fix

## 1. Introduction

`44648ed` fixed a defect its own author had introduced one commit earlier
(`6e38948`): `DeleteAsync_FileLockedByAnotherHandle_ThrowsOrUnlinksAccording
ToThePlatform` read the record back for its post-condition while the
`FileShare.None` handle was still held, so the read failed for its own
reasons rather than the store's, on the one platform where the test runs.
Test-only. A pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To fix the Windows branch of a test that CI itself caught failing in both
configurations, and to disclose, rather than paper over, that the branch
still cannot be executed in this container.

## 3. Background

CI reported: `PersistenceStoreUnavailableException : Failed to READ
collection 'collection', key 'key'. ---- IOException : The process cannot
access the file ... because it is being used by another process.` The
delete assertion itself was right; the check written to run after it was
not, because it tried to read the same locked file the test had
deliberately locked two tests above for `ReadAsync_FileLockedByAnotherHandle`.

## 4. The Problem

A regression test that fails for a reason unrelated to the behaviour it
was written to assert is a false signal — it looks like a defect in
`DeleteAsync`, and the actual defect is in the test's own sequencing.

## 5. The Design

The lock is now scoped to the operation under test in both branches, and
the "a delete that did not happen must never look like one that did"
check runs only after the lock is released. `DeleteAsync` only ever calls
`File.Delete` in this path, so a throw leaves the file untouched and the
read after release must return the original value.

## 6. Alternatives Considered

None recorded beyond the sequencing fix itself — the defect was narrowly
in when the post-condition read ran relative to the lock's lifetime, and
the fix is the direct correction of that ordering.

## 7. Why This Solution Was Chosen

Because it is the minimal, precise correction: nothing about `DeleteAsync`
or the store's locking behaviour changed, only the point in the test at
which the lock is released relative to the assertion that depends on it
being gone.

## 8. Architectural Principles

A regression test's own setup and teardown are part of what it asserts;
a lock held past the point a subsequent read depends on it being released
is a defect in the test, not evidence about the code under test.

## 9. Benefits

Debug and Release both build under `TreatWarningsAsErrors`, 0 warnings, 0
errors. Full unfiltered suite, both configurations: Core 2572/2572,
Desktop 261/261. Governance health check exits 0.

## 10. Trade-offs

Disclosed limitation of the fix itself: the Windows branch still cannot
be executed in this container — it runs as root, so making the collection
directory read-only does not block the unlink, and there is no other way
to make a delete fail on this file system here. The fix was verified by
reading `DeleteAsync`, which is weaker than running it, and this is the
second time this branch has been pushed without local execution — the
first attempt is what made this commit necessary.

## 11. Common Mistakes

Writing a post-condition check that depends on a resource (a file lock)
still being held by an earlier part of the same test, without confirming
the lock's own lifetime actually still covers the check.

## 12. Future Evolution

The disclosed inability to execute the Windows branch locally in this
container remains a standing verification gap for any future change to
this test; CI on the Windows runner remains the only place this branch is
actually exercised.

## 13. Key Takeaways

- A test failure caused by the test's own setup/teardown ordering looks
  identical to a real product defect until traced carefully.
- Disclose a verification limitation (cannot execute a branch locally)
  rather than presenting a read-only review as equivalent to running it.
- The second failure on the same row, from the same root cause (pushing
  without local execution), is a reason to be more careful the next time,
  not less.
