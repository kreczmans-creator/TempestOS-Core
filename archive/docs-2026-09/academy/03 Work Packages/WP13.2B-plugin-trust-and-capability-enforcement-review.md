# WP 13.2B — Plugin Trust & Capability Enforcement Review

## 1. Introduction

The retrospective for `WP 13.2B`, an independent review/verification Work
Package auditing `WP 13.2A` (Plugin Trust & Capability Enforcement
Implementation) before it became a permanent commit — mirroring exactly
the review-before-baseline discipline `WP 13.0B` established for
`WP 13.0A`'s architecture and `WP 13.1B` extended to `WP 13.1A`'s real
production code, applied here one Work Package later to the trust half of
the same plugin platform. Four parallel, genuinely independent audit
sub-agents — Architecture Compliance, Security Review, Verification
Review, Governance Review — each auditing read-only, with fixes applied
centrally to avoid file collisions. `WP 13.2A`'s and `WP 13.2B`'s combined
material was committed together as `25df570` (78 files changed, 6,137
insertions, 114 deletions), the same "commit the reviewed-and-corrected
baseline together" pattern `WP 13.0A`/`WP 13.0B` and `WP 13.1A`/`WP 13.1B`
each already established.

**A note on this document's own provenance.** Unlike `WP 13.0B`/`WP 13.1B`,
this retrospective was not written contemporaneously with `WP 13.2B`
itself. `WP 13.2B` closed with its findings recorded in full only in its
own commit message; it had no Academy retrospective, no `WorkPackages.md`
row of its own, and no `PROJECT_STATUS.md` entry — a gap first surfaced
and disclosed (not backfilled) by `WP 13.3A`, which reconstructed a
`WorkPackages.md` row directly from `25df570` and deliberately declined to
fabricate a full retrospective for a Work Package it had not executed.
`WP 13.3B`'s own Governance Review then explicitly deferred, rather than
silently dropped, the same gap, recommending it as a small dedicated
follow-up. This document is that follow-up. Every fact below is grounded
strictly in `25df570`'s own commit message, `WorkPackages.md`'s own
`WP 13.2B` row, `Technical Debt Register.md`, `WP13.9.0 Engineering
Release Report.md`, or a direct read of real, current source — no
sub-agent report, verdict, or finding beyond what those sources state is
invented or assumed here. Where the record is internally inconsistent,
both readings are recorded and the inconsistency is named (see §10).

Note also that `PROJECT_STATUS.md` still carries no `WP 13.2B` entry of
its own — confirmed directly; its four mentions of `WP 13.2B` all sit
inside other Work Packages' own entries. This retrospective does not
create one; that remains a governance artefact for whichever Work Package
is commissioned to touch that document, and it is named here rather than
left silently unstated.

## 2. Purpose

To perform a genuinely independent second pass over `WP 13.2A`'s trust and
capability enforcement code — the platform's first real privilege boundary
— before it became a permanent baseline, on the established premise that
even careful, contract-driven implementation of an already-audited
architecture benefits from a fresh read by reviewers who authored none of
the material under review.

The narrower framing matters: this was a **defect-fixing pass**, not a
design pass. A finding naming a genuine structural change rather than a
defect was to be disclosed, not fixed — a boundary `WP 13.2B` applied
explicitly, and which determined the disposition of two of its five
findings (§6).

## 3. Background

`WP 13.2A` implemented `ADR-0110`, `ADR-0111`, and `ADR-0112` — the
trust-tier model, the component-principal capability model, and the
detached SHA-256/RSA-PSS signature scheme — closing `TD-09`, `TD-10`, and
`TD-11`, security debt open since `WP 5.0S`/`WP 5.1A`'s own Security
Reviews. That Work Package's own commissioning was explicit that it
implement the three ADRs exactly as ratified, with zero architectural
deviation, and it recorded no new ADR as warranted.

That is precisely the shape of work a second pass is most valuable
against. `WP 13.1B`, one Work Package earlier, had already demonstrated
the point on this same release: two genuine, empirically-confirmed
production bugs in `WP 13.1A`'s dependency-graph and configuration code,
neither of which the implementing pass had caught. `WP 13.2A`'s material
was larger and carried a materially higher blast radius — it introduced
the first code in this platform whose failure mode is privilege escalation
rather than a faulted Host or a dropped plugin.

## 4. The Problem

Per `25df570`'s own commit message and `WorkPackages.md`'s own `WP 13.2B`
row, the audit set out against questions of this shape:

1. **Does `PluginAssemblyLoader.EnforceTrust`'s capability-eligibility
   check actually constrain what a plugin may resolve** — including
   against Host-authority types that happen to be DI-registered under
   their own concrete type for legitimate reasons?
2. **Is a component scope genuinely pushed around every path on which
   plugin-owned code executes**, or only around some of them —
   `EventBus.PublishAsync`'s per-subscriber push and
   `ModuleLifecycleManager`'s per-lifecycle-call push being the
   established shape?
3. **Are First-Party plugins actually exempted from capability checks in
   the way `ADR-0111` and the types' own remarks describe** — skipped
   entirely, not merely satisfied?
4. **Do genuine coverage gaps exist unrelated to any of the above**, in
   code paths a defect-hunting read would not necessarily reach?
5. **Is the governance record accurate** — are `TD-09`/`TD-10`/`TD-11`
   genuinely closed against real code rather than merely cited as closed,
   and does any register carry stale content as a result of this release's
   own activity?

## 5. The Design

**The design here is the design of the review, not of a feature.**
`WP 13.2B` produced findings and corrections; it shipped no new capability
of its own.

**Four parallel, genuinely independent audit sub-agents**, per `25df570`:
Architecture Compliance, Security Review, Verification Review, Governance
Review. Each audited **read-only**; every fix arising from any of them was
applied **centrally**, by the orchestrating pass, specifically to avoid
file collisions between four concurrent reviewers operating over the same
small set of trust-critical files. That central-application discipline is
the structural difference from `WP 13.1B`'s own four-workstream shape, and
it is what makes a single, reconciled regression run meaningful.

**Discipline coverage was chosen against the material, not by rote.**
`WP 13.1B`'s own four workstreams were Code Review, Architecture
Compliance, Verification & Test Audit, and Governance & Documentation
Audit. `WP 13.2B` substitutes a dedicated **Security Review** for the
general Code Review workstream — the correct substitution for a Work
Package whose entire subject is a privilege boundary, and the workstream
that found the Critical finding.

**Every fix was independently re-verified end to end after application.**
Per the commit message, `governance-healthcheck.ps1` was re-run after
*every* fix (7 passed, 1 warned — pre-existing and unrelated — 0 failed),
as were Debug and Release builds (both 0 Warnings, 0 Errors under
`-p:TreatWarningsAsErrors=true`) and the full regression suite in both
configurations (2,473 / 2,473 passing — 2,252 `Tempest.Core.Tests` + 221
`Tempest.Desktop.Tests`). These are the commit message's own figures.

**What the four audits found**, per `25df570`:

**Security Review — one Critical, confirmed privilege escalation.**
`PluginAssemblyLoader.EnforceTrust`'s capability-eligibility check carried
no denylist for Host-authority concrete types. A `VerifiedSigned` — or
`FirstParty` — plugin could request `plugin.services.resolve:*` naming
`Identity.CurrentComponentAccessor` or `Identity.CurrentPrincipalAccessor`,
both dual-registered under their concrete types in `TempestHost`'s own DI
container for legitimate reasons, and receive the exact same singleton
instance the Host itself uses. That let it forge an arbitrary component
principal — including a self-granted `FirstParty` tier marker, confirmed
via live repro — or hijack the ambient, process-wide user principal via
`CurrentPrincipalAccessor.SetCurrent`. **Fixed** by adding a fixed
`NeverEligibleServiceResolveTypes` denylist, checked in *both*
`FindIneligibleCapability` (denying the capability request itself, for
every tier including `FirstParty`) and `HasCompliantConstructor` (defence
in depth against a granted-but-still-denylisted type). Confirmed present
in real, current source by this retrospective's own direct read:
`src/Tempest.Core/Plugins/PluginAssemblyLoader.cs` declares
`NeverEligibleServiceResolveTypes` as a two-member `HashSet<Type>`
(`Identity.CurrentComponentAccessor`, `Identity.CurrentPrincipalAccessor`),
consulted by `IsNeverEligibleServiceResolveTarget` and again inside the
constructor-conformance loop's own per-parameter predicate.

**Architecture Compliance — one blocking deviation, found independently.**
`CommandHandlerTable.DispatchAsync` never pushed a component scope around
handler invocation, unlike `EventBus.PublishAsync`'s per-subscriber push
and `ModuleLifecycleManager`'s per-lifecycle-call push. A plugin-owned
command handler's own internal, capability-gated calls therefore ran under
whichever component was ambient before dispatch rather than under the
handler's own principal — silently skipping enforcement for that entire
re-entry path. **Fixed** by giving `CommandHandlerTable` the same concrete
`Identity.CurrentComponentAccessor` collaborator `EventBus` already takes,
and wrapping handler invocation in a `BeginScope` keyed by the handler's
own recorded owner. Confirmed present in current source:
`CommandHandlerTable.cs` holds an
`Identity.CurrentComponentAccessor? _currentComponentAccessor` field and
dispatches under
`using var scope = owner is not null ? _currentComponentAccessor?.BeginScope(owner) : null;`.

**Security Review — one Medium, confirmed.** `FirstParty`-tier plugins
were never actually exempted from capability checks, despite `ADR-0111`
and the type's own remarks documenting the exemption as "skipped entirely
— not merely satisfied — when the ambient component principal is null or
First-Party": the guard read `if (registrant is not null)` rather than
checking `PluginTrustPermission.IsFirstParty`. **Fixed** identically
across `NavigationService.Register`, `CommandRegistry.RegisterDescriptor`,
`CommandHandlerTable.Register`, and `EventBus.PublishAsync`
(`NavigationService.Unregister` already had this correct). Confirmed
present in current source at `NavigationService.cs` (both `Register` and
`Unregister`), `CommandRegistry.cs`, `CommandHandlerTable.cs`, and
`EventBus.cs` — noting that current source also carries an `IsFirstParty`
guard in `IdentityService.cs`, added by a later Work Package in the
`WP 13.9.x`/`WP 13.10x` chain, not by `WP 13.2B`.

**Verification Review — three targeted regression tests**, for genuine
coverage gaps unrelated to the security findings: `BeginScope` exception
safety, concurrent registration racing, and `TrustDenied` `Detail`-text
distinguishability.

**Governance Review — one drift found and fixed**, and one
re-verification. The `Technical Debt Register`'s own summary counts had
gone stale across three prior Work Packages; that register still carries
the correction's own disclosure marker ("**Disclosed correction
(`WP 13.2B` governance review)**") in its narrative today. This workstream
also independently re-verified `TD-09`/`TD-10`/`TD-11`'s closures against
the real code, not merely against their own citations.

## 6. Alternatives Considered

**Fixing the two lower-severity findings rather than disclosing them.**
Two further findings — both lower-severity and characterised in the commit
message as plausible-not-confirmed — were **disclosed, not fixed**, as
genuinely out of scope for a defect-fixing pass:

- A TOCTOU window between Discovery-time signature verification and
  Loading-time assembly load. Closing it "would require carrying the
  verified hash forward — a structural change, not a defect fix."
- Filename-based (not certificate-attribute-based) first-party trust store
  detection, which requires operator-level filesystem access already and
  is not plugin-exploitable.

Both were formally registered for the first time — by `WP 13.3A`, not by
`WP 13.2B` — as `TD-49` and `TD-50`. Both remain **Open** in
`Technical Debt Register.md` today, each with a recorded rationale for why
it is neither an `ADR-0112` conformance gap nor currently exploitable by a
plugin itself.

**Raising a new ADR.** Considered and rejected: `25df570` records that no
new ADR was required, "confirmed independently by both Architecture
Compliance and Governance Review" — two separate workstreams reaching that
conclusion, not one asserting it. No new Technical Debt was raised by
`WP 13.2B` itself either.

**Broadening the pass into hardening.** Not attempted. Every fix applied
was either a precise correction to a defect `WP 13.2A` itself introduced,
or a regression test proving a fix or closing a coverage gap a sibling
audit had actually named.

## 7. Why This Solution Was Chosen

**A denylist, not a general rule, for the escalation fix.** The escalation
did not arise from a defect in the eligibility logic's own shape — it
arose because two specific Host-authority types are legitimately DI-public.
The minimal, honest correction is therefore an explicit, fixed list of
types ineligible for every tier, rather than a broader heuristic
attempting to infer "Host-authority-ness" from a type's own shape. That
choice is visible in the code: a two-member `HashSet<Type>`, not a
namespace-prefix rule or an attribute scan.

**Checked in two places, deliberately.** `FindIneligibleCapability` denies
the *capability request itself*, so a plugin cannot even be granted the
resolve capability; `HasCompliantConstructor` independently rejects a
denylisted parameter type, so a plugin that somehow held such a grant
still fails constructor conformance. The commit message names the second
check explicitly as "defense in depth" — the correct posture where the
failure mode is a forged principal rather than a faulted plugin.

**The scope-push fix reuses the existing shape rather than inventing one.**
`CommandHandlerTable` was given the identical concrete
`Identity.CurrentComponentAccessor` collaborator `EventBus` already took,
and the identical `BeginScope` wrap — not a new mechanism. That is why the
finding is correctly characterised as a *missed application* of an
established pattern rather than a design gap.

**The First-Party fix is a four-site correction of one predicate**, not a
redesign: `registrant is not null` became
`PluginTrustPermission.IsFirstParty(registrant)`, at exactly the four
sites carrying the wrong predicate, leaving the one site that was already
correct untouched.

## 8. Architectural Principles

- **Host-Owned Collaborators Remain Structurally Unreachable** —
  `WP 13.2A` established this for `PluginTrustStore`,
  `PluginComponentPrincipalRegistry`, and `CurrentComponentAccessor`'s own
  concrete type. The Critical finding is precisely a hole in that
  principle: `ICurrentComponentAccessor`'s deliberate,
  `ADR-0111`-sanctioned DI-public exception carried a concrete-type
  registration alongside it, and `plugin.services.resolve:*` could name
  it. The denylist restores the principle at the one place the exception
  had opened.
- **Fail Closed, Not Fail Open** — the denylist applies to *every* tier,
  with no exception for `FirstParty`, and the code's own remarks say so
  explicitly.
- **Defence in Depth** — the same denylist enforced at two independent
  gates, so neither alone is load-bearing.
- **Zero Behavioural Change for Every Existing Actor** — the First-Party
  exemption fix restores the *documented* behaviour (skip, don't merely
  satisfy) for the actors that already exist, every one of which is
  First-Party.
- **Review Before Baseline** — a genuinely independent pass runs before
  new material becomes permanent, not after.
- **Disclose, Don't Fabricate** — two findings the pass could not honestly
  close within its own brief were named plainly and left open, and the
  Governance workstream's own register correction was recorded as a
  disclosed correction rather than quietly applied.

## 9. Benefits

- **A confirmed, live-reproduced privilege escalation was closed before
  `WP 13.2A`'s trust code ever became a permanent baseline** — the
  strongest single vindication of the review-before-baseline discipline
  this release had produced at that point.
- **An entire enforcement re-entry path was closed.** Without the
  `CommandHandlerTable` scope push, capability enforcement was silently
  absent for every capability-gated call a plugin-owned command handler
  made from inside its own handler body.
- **The documented First-Party exemption became the implemented one.** The
  gap between `ADR-0111`'s stated design and the shipped predicate was
  real, and was closed at all four affected sites.
- **Two independent disciplines each found a genuine blocking defect the
  other did not.** Security Review found the escalation; Architecture
  Compliance found the missing scope push. Neither is a restatement of the
  other.
- **Both fixes have since been independently re-confirmed still present**
  — by `WP13.9.0 Engineering Release Report.md`'s Architecture (A1) and
  Security/Trust (A5) disciplines, each reading real source rather than
  citing this Work Package's own claim, and again by this retrospective's
  own direct read of current source.
- **Governance drift accumulated across three prior Work Packages was
  found and corrected**, and three debt closures were re-verified against
  code rather than accepted on citation.

## 10. Trade-offs

- **`WP 13.2B` left almost no governance footprint of its own.** No
  Academy retrospective, no `WorkPackages.md` row, no `PROJECT_STATUS.md`
  entry — its only trace in governance documentation for some time was a
  single citation inside `Technical Debt Register.md`'s own narrative. Its
  real, substantial findings lived solely in a commit message. `WP 13.3A`
  added the `WorkPackages.md` row; `WP 13.3B`'s Governance Review deferred
  the retrospective; this document closes it. The `PROJECT_STATUS.md`
  entry remains absent, confirmed directly.
- **A disclosed inconsistency in the commit message's own regression-test
  count, recorded here rather than silently resolved.** `25df570` states
  "11 new regression tests added for the three fixed defects (2 theory
  tests x 2 cases + 1 defense-in-depth test for the escalation path; 1
  FirstParty-exemption test in Navigation; 2 in CommandHandlerTable
  including the scope-push proof) plus the Verification Review's 3." Read
  literally, that totals 14; the parenthetical enumeration itself sums to
  8 cases (or 6 methods), so 8 + 3 = 11 is a plausible reconciliation —
  but the message does not say so, and this retrospective does not have
  the four sub-agents' own reports to resolve it. Both readings are
  recorded exactly as the source states them, following the identical
  discipline `WP 13.3B`'s own retrospective applies to that commit's own
  13-versus-15 test-count discrepancy.
- **The denylist is a fixed, hand-maintained list.** Any future
  Host-authority type that becomes DI-public under its own concrete type
  must be added to it deliberately; nothing in the design detects such a
  type automatically.
- **The escalation was closed at the capability-request surface, not at
  the assembly-scanning surface.** `EnforceTrust` still scanned only the
  one manifest-declared assembly — a scoping `ADR-0111` itself specified —
  and `WP 13.9.0`'s own Security/Trust discipline later demonstrated,
  empirically, that a second, wholly undeclared assembly could reach the
  same `CurrentComponentAccessor` singleton through a side channel the
  denylist never sees. That is not a defect in `WP 13.2B`'s fix; it is a
  structural gap at a different join, and it is what the `WP 13.9.1`
  onwards chain went on to close.
- **Four parallel reviewers with centrally applied fixes** avoids file
  collisions but concentrates every correction in one writer's hands — the
  reviewing agents did not verify their own fixes as applied; the
  orchestrating pass re-ran build, regression, and health check after each
  fix instead.

## 11. Common Mistakes

1. **Assuming a DI-public interface registration is the whole exposure.**
   `ICurrentComponentAccessor` is deliberately DI-public per `ADR-0111` —
   but `TempestHost` dual-registers it, once under the interface and once
   under the concrete type (`EventBus` needs the concrete type to call
   `BeginScope`). A `plugin.services.resolve:*` capability naming the
   concrete type is a different exposure from one naming the interface,
   and it was the concrete registration that carried the escalation.
2. **Assuming a scope push present at three call sites is present at the
   fourth.** `EventBus` and `ModuleLifecycleManager` both pushed a
   component scope; `CommandHandlerTable` did not. Nothing about the
   code's own shape made the omission visible — only a reviewer checking
   each plugin-code-execution path individually found it.
3. **Reading `if (registrant is not null)` as equivalent to "is not
   First-Party".** It is not: `PluginTrustPermission.IsFirstParty(null)`
   is `true`, but so is `IsFirstParty` for a genuinely First-Party
   principal. The null check silently subjected First-Party registrants to
   capability checks the ADR says are skipped for them entirely.
4. **Treating "no new ADR required" as a default rather than a
   conclusion.** `WP 13.2B` recorded it as independently confirmed by two
   separate workstreams, not asserted once.
5. **Assuming a Work Package's findings are recorded wherever it landed
   code.** `WP 13.2B`'s were not — they existed only in a commit message
   for several Work Packages, which is exactly why `WP 13.9.0` later
   classified an equivalent gap on `WP 13.3B` as Release Blocking under
   Implementation readiness.

## 12. Future Evolution

- **`TD-49` (Discovery-to-Loading TOCTOU window)** — Open. Closing it
  requires carrying the verified hash forward to the load call site, the
  structural change `WP 13.2B` correctly declined to make within a
  defect-fixing brief. Independently re-assessed against `ADR-0112`'s own
  literal Decision text by `WP 13.9.0`'s Architecture discipline and
  confirmed real, Open, and **not** an ADR violation.
- **`TD-50` (filename-based first-party trust-store detection)** — Open.
  A future Work Package moving first-party detection to a
  certificate-level attribute, if a real need for filename-independent
  detection emerges. Also re-assessed and confirmed non-violating by
  `WP 13.9.0`.
- **The multi-assembly trust boundary.** `WP 13.9.0`'s Security/Trust
  discipline demonstrated that `EnforceTrust`'s single-declared-assembly
  scan let an entirely undeclared assembly reach Module Discovery with
  zero trust checking — reaching, among other things, the very
  `CurrentComponentAccessor` singleton `WP 13.2B`'s denylist exists to
  forbid. `WP 13.9.1` replaced the single-assembly scan with a
  fixed-point, breadth-first `AppDomain`-diff scan; `WP 13.9.2` found that
  fix still incomplete; `WP 13.9.3`, `WP 13.9.4`, and `WP 13.9.6` closed
  the remaining paths, integrated by `WP 13.9.7`. `WP 13.2B`'s own
  denylist survived every one of those passes unchanged.
- **A denylist that maintains itself.** Nothing today detects a newly
  DI-public Host-authority concrete type; adding one to
  `NeverEligibleServiceResolveTypes` remains a deliberate, manual act. No
  Work Package has been commissioned to change that.

## 13. Key Takeaways

- **A review pass over already-audited architecture, implemented by a
  careful implementer, still found a Critical, live-reproduced privilege
  escalation.** `WP 13.2A` implemented three formally ratified,
  independently audited ADRs with zero deviation — and the escalation was
  in the code anyway, because it lived in the interaction between an ADR's
  own sanctioned DI exception and a capability key's own expressiveness,
  not inside any single ADR's own scope.
- **Two disciplines, two different blocking defects, no overlap.** The
  value of running Security Review and Architecture Compliance as
  separate, genuinely independent workstreams is exactly this: neither
  found the other's defect, and a single combined reviewer would
  plausibly have found one and stopped.
- **A defect-fixing brief must be able to say "disclosed, not fixed"
  without embarrassment.** Two real findings were left open with a named
  reason, and both were subsequently registered as formal debt by a later
  Work Package. That is a healthier outcome than either fabricating a fix
  or omitting the finding.
- **Findings recorded only in a commit message are findings the project
  will struggle to act on.** `WP 13.2B` did real, substantial work and
  left almost no governance footprint for it; the cost was paid later, by
  `WP 13.3A`, `WP 13.3B`, `WP 13.9.0`, and this document. The lesson was
  learned again, expensively, when `WP 13.9.0` found the identical shape
  of gap on `WP 13.3B` and classified it Release Blocking.
