## 1. Introduction

This Work Package implements the mechanical, non-trust half of the Plugin
Platform Architecture `WP 13.0A` designed and `ADR-0107`–`ADR-0109`
ratified: inter-plugin dependency declaration and resolution, a
Host-owned Plugin Registry with a read-only diagnostics projection, a
configurable plugins root/manifest convention, and confirmation of the
plugin service-registration boundary — all previously architecture-only,
now real, built, and tested code. It runs on `feature/v0.13.0`, `v0.13.0`
— "Trust & Deployment Hardening" — the release `WP11.0B Architecture
Roadmap.md` §3 predicted would only enter the plan once the Product
Owner committed `v1.0` scope to third-party plugins and/or REST
deployment beyond a trusted local network; that commitment fired at `WP
13.0.0`'s own branch establishment.

`WP 13.0A`'s own Recommendation named this implementation as its own,
separately-scoped successor task: "A future implementation work package…
may implement `PluginDependency`, the extended `PluginManifest`,
`IPluginRegistry`/`PluginRegistry`, the extended `IDiagnosticsProvider`…
not performed by this document, architecture only." `WP 13.0B` was
subsequently commissioned as an independent architecture review instead
(`WP13.0B-plugin-and-trust-isolation-architecture-review-and-baseline.md`),
leaving that implementation task genuinely unassigned until this Work
Package.

Four parallel workstreams delivered this Work Package: Runtime
Implementation (`src/Tempest.Core/Plugins/`), Dependency Injection &
Composition (`src/Tempest.Core/Runtime/TempestHost.cs`,
`src/Tempest.Core/Diagnostics/*.cs`), Verification & Testing (six new
test files plus two extended existing ones, `tests/Tempest.Core.Tests/`),
and Governance & Documentation (this retrospective and its companion
register/Academy updates).

## 2. Purpose

To build the code `ADR-0107`, `ADR-0108`, and `ADR-0109` already,
formally, ratified — and only that code. This Work Package's own brief
draws its boundary from the same document that drew it originally:
`Plugin Platform Architecture.md`'s explicit split between the plugin
*platform's* shape (dependencies, discovery extension, registry,
lifecycle, DI boundaries — this Work Package) and the sibling Trust &
Isolation Architecture's own scope (trust levels, permission/capability
semantics, code-signing verification, the isolation mechanism —
`ADR-0110`–`ADR-0112`, explicitly **not** this Work Package). Building the
trust half without a real, demonstrated need beyond the architecture
phase's own reasoning would be exactly the speculative-design mistake
this project's governing discipline warns against; this Work Package
declines that temptation deliberately, not by oversight.

## 3. Background

`Plugin Manifest Architecture.md` (`WP 4.2`) shipped a single-plugin,
dependency-free discovery/loading pipeline: a manifest describes one
plugin, Plugin Discovery (Phase 3.1) validates it in isolation, Plugin
Loading (Phase 3.2) loads its assembly, and Module Discovery picks up
whatever `IModule` types the loaded assembly contains — with zero
awareness that any of those types arrived via a plugin rather than a
first-party assembly. `TD-06` (fixed plugins root/manifest name),
`FCR-0010` (the same, tracked as a future capability), and the general
absence of inter-plugin dependency or a queryable plugin catalogue were
all left as named, defended non-goals of that document, each times
"a future work package may make this configurable; nothing here
forecloses it."

`WP 13.0A` extended that architecture once the Product Owner's confirmed
third-party plugin commitment (`FCR-0001`) made those non-goals real,
near-term questions: `ADR-0107` (a fixed-point dependency-graph
resolution inside the existing Phase 3.1, extending `ADR-0025`'s failure
classification with categories 12–14), `ADR-0108` (a lifecycle covering
Load/Upgrade/Uninstall as file-system operations, with live in-process
unload reaffirmed — not reversed — as a `v0.13.0` non-goal per `ADR-0015`),
and `ADR-0109` (no new DI container capability for plugins — a plugin
contributes capability through the same `IEventBus`/`INavigationProvider`/
`ICommandRegistry` surfaces any module already has). The sibling Trust &
Isolation Architecture (`ADR-0110`–`ADR-0112`) answers a genuinely
separate question — what a loaded plugin is *trusted* to do — and remains
entirely out of this Work Package's own scope, exactly as `Plugin
Platform Architecture.md`'s own "Explicit boundary with the sibling
Security & Trust workstream" section drew it.

`WP 13.0B`, commissioned next, turned out to be an independent
architecture *review* of `WP 13.0A`, not the implementation the roadmap
originally predicted for that label — disclosed in `WorkPackages.md`,
not silently reconciled. That review closed clean (`governance-healthcheck.ps1`,
7 passed, 1 warned, 0 failed), leaving `WP 13.0A`'s design as a verified,
committed baseline with its own real implementation successor still
unnumbered — until this Work Package.

## 4. The Problem

1. **Does the fixed-point dependency-graph reduction algorithm
   `ADR-0107` specifies actually terminate correctly and isolate exactly
   the right candidates** — a missing dependency, an incompatible
   dependency version, and a circular dependency (including transitive
   chains and cascading exclusion) — without a bespoke cascade mechanism?
2. **Does the Plugin Registry stay structurally unreachable from any
   module**, exactly as `ADR-0017`'s Host-owned-collaborator boundary
   requires, while still projecting read-only through
   `IDiagnosticsProvider.Plugins` (`ADR-0039`'s existing `Func<T>`-accessor
   pattern) for every consumer that needs to observe it?
3. **Do the three new configuration keys
   (`Runtime:Plugins:RootDirectory`/`ManifestFileName`/`Disabled`) close
   `TD-06`/`FCR-0010` without any Host Lifecycle phase change**, consuming
   exactly the seam `ADR-0026` already anticipated rather than opening a
   new one?
4. **Does building this introduce any DI container capability, trust
   enforcement, or capability check** that would trespass on the sibling
   Trust & Isolation Architecture's own, explicitly separate scope?
5. **Does the existing, pre-`v0.13.0` regression suite — 2,255 tests —
   still pass unchanged**, proving this is a purely additive extension of
   an already-shipped pipeline, not a redesign of it?

## 5. The Design

**Dependency graph resolution — a three-phase, repeat-until-stable
loop, not a bespoke cascade.** `PluginManifestDiscoveryService.
ResolveDependencyGraph` runs, per Discovery pass, over the set of
already individually-valid candidate manifests:

1. **Fixed-point removal** (`RemoveCandidatesWithUnmetDependencies`) —
   repeatedly scans the surviving set in deterministic (ordinal
   folder-name) order; any candidate whose declared dependency is absent
   from, or version-incompatible with, the *current* surviving set is
   isolated (`MissingPluginDependencyException`/
   `IncompatiblePluginDependencyVersionException`) and removed. Repeats
   until one full pass removes nothing.
2. **Cycle detection** (`FindAndRemoveCycles`) — a three-colour
   depth-first search over what remains; any candidate still present but
   unreachable by a valid topological order is part of a cycle and is
   isolated (`CircularPluginDependencyException`) — every participating
   plugin, and only those plugins.
3. **Repeat.** Removing a cycle can newly break another candidate's
   previously-satisfied dependency on a removed cycle member, so steps 1
   and 2 repeat, together, until a full pass of each finds nothing left
   to remove.

What survives is handed to `TopologicalSort` — a Kahn's-algorithm pass
using each candidate's own remaining (already-resolved) dependency
count, breaking ties with the same ordinal folder-name order Discovery
already uses. **This is deliberately the entire mechanism** — no separate
cascade-notification step exists; a plugin whose only defect is
depending on a plugin that failed for an unrelated reason is removed
automatically by the very next fixed-point pass, exactly as `ADR-0107`
specified.

**The Plugin Registry — a `Record`/`Entries` split, not one
interface.** `PluginRegistry` implements both `IPluginRegistry` (read,
`Entries`) and `IPluginRegistryRecorder` (write, `Record(entry)`) as one
concrete `sealed class`, but exposes them as two separate interfaces so
that nothing outside `Tempest.Core.Plugins` can ever be handed a
reference capable of mutating it — `TempestHost` holds the concrete
`PluginRegistry`, passes it to `PluginManifestDiscoveryService`/
`PluginAssemblyLoader` typed as `IPluginRegistryRecorder`, and to
`DiagnosticsProvider` typed as `IPluginRegistry`. `PluginFailureLogging`
(shared by both Discovery and Loading, extended in this Work Package to
cover categories 12–14 alongside the existing 1–6) is the single place
that maps a `PluginException` to both its ADR-0025 logging severity and
its `PluginRegistryState` — one switch statement, not two independently
maintained ones.

**Configuration-key wiring and precedence.** `TempestHost.RunAsync`
resolves the plugins root path in a fixed precedence order: the
existing, test-only `_pluginsRootPathOverride` constructor field first
(preserving every pre-existing test's own determinism unchanged), then
`Runtime:Plugins:RootDirectory` from the already-built `IConfiguration`,
then the original `WP 4.2` fixed default
(`Path.Combine(AppContext.BaseDirectory, "Plugins")`). `ManifestFileName`
and `Disabled` follow the identical configuration-or-default shape. All
three keys are resolved immediately after Configuration Built (Phase 2)
and before `PluginRegistry`/`PluginManifestDiscoveryService` are
constructed — no Host Lifecycle phase renumbering, no new phase; the log
lines Discovery/Loading already emit ("Host lifecycle phase completed:
Plugin Discovery"/"…Plugin Loading") are unchanged in wording and
position.

**`DiagnosticsProvider`'s Plugin Registry dependency is a direct
reference, not a `Func<T>` accessor — deliberately, and for a reason
this Work Package confirmed rather than assumed.** `Modules`/
`HostedServices` are supplied as `Func<IModuleLifecycleManager?>`/
`Func<IHostedServiceManager?>` because those two collaborators are
constructed *after* `DiagnosticsProvider` itself (Platform Services
Registered, Phase 6, precedes Module Discovery/Registration/Lifecycle).
`IPluginRegistry`, by contrast, is constructed during Plugin Discovery
(Phase 3.1) — strictly earlier than Phase 6 in `ADR-0026`'s own frozen
phase table — so it is always already available by the time
`DiagnosticsProvider` is built. A deferred accessor here would add a
layer of indirection with no corresponding "not yet constructed" state
to actually guard against; the direct reference says exactly that,
structurally, rather than through a comment.

## 6. Alternatives Considered

None — genuinely. This Work Package implements `ADR-0107`, `ADR-0108`,
and `ADR-0109` exactly as each already, formally, ratified them; no new
design tension requiring a fresh alternative arose during
implementation. Every "should X or Y" question this Work Package's own
code answers was already decided at the architecture stage (`Plugin
Platform Architecture.md`'s own Architectural Questions Evaluated
table) — implementation's task was to build the ratified answer
correctly, not to re-litigate it. This is itself confirmed directly, not
assumed: no sibling workstream's own final report disclosed encountering
a genuine, unanticipated either/or ambiguity the architecture had not
already settled (see §13, Key Takeaways, and this Work Package's own
Governance & Documentation findings).

## 7. Why This Solution Was Chosen

Because there was, in the ordinary sense, only one solution to choose —
the already-Accepted ADRs. The one implementation-level judgment call
genuinely exercised was *how* to structure the dependency-resolution
algorithm's own internals (a single `while (true)` fixed-point loop
calling two extracted, independently testable private methods, rather
than one large inlined method) — a readability/testability choice with
no behavioural alternative, not the kind of decision Engineering
Governance §5 requires an ADR for. The `PluginRegistry`/
`IPluginRegistryRecorder` split, and `DiagnosticsProvider`'s direct
(non-`Func<T>`) reference to it, are both direct, mechanical
applications of already-cited precedent (`ADR-0017`, `ADR-0039`) that
`Plugin Platform Architecture.md` itself already reasoned through in its
own "Why this does not consume one of this work package's three reserved
ADR numbers" section — reused here exactly, not re-argued.

## 8. Architectural Principles

- **Reuse Before Invention** — no new DI container capability was added
  (`ADR-0109`); the Plugin Registry extends the already-shipped
  `IDiagnosticsProvider` (`ADR-0039`) rather than introducing a fifth
  Host-owned collaborator's own dedicated reporting service; a plugin
  contributes capability through `IEventBus`/`INavigationProvider`/
  `ICommandRegistry` — surfaces that already existed for every module.
- **Fail Fast, Isolate, Don't Crash — extended to three new failure
  categories.** `ADR-0025`'s eleven-category table gains categories 12–14
  (missing dependency, incompatible dependency version, circular
  dependency) without weakening its own governing principle: every one of
  the three new categories is isolated, never Host-fatal, mirrored
  exactly by this Work Package's own exception types
  (`MissingPluginDependencyException`, `IncompatiblePluginDependencyVersionException`,
  `CircularPluginDependencyException`, all `sealed`, all deriving
  `PluginException`) and `PluginFailureLogging`'s extended severity
  table.
- **Do Not Redesign Approved Architecture Absent a Genuine Defect** —
  `PluginManifest`'s v1 shape, `Host Lifecycle.md`'s phase table, and
  `IDiagnosticsProvider`'s existing `Modules`/`HostedServices` members are
  all unmodified; every addition in this Work Package is additive to an
  existing type or table, never a redesign of one.
- **Host-Owned Collaborators Remain Structurally Unreachable** —
  `ADR-0017`'s own principle, applied a fourth time: `IPluginRegistry`
  is never added to the `ServiceCollection`; a module can reach it only
  through `IDiagnosticsProvider.Plugins`'s read-only projection.
- **Avoid Speculative Design** — no trust/capability semantics, no
  signature verification, no REST surface, no installer, no hot reload,
  no dynamic unload, no marketplace, no commercial licensing hook was
  built — all eight are named non-goals in `Plugin Platform
  Architecture.md`, confirmed absent from this Work Package's own diff
  directly (`git diff` shows no such code anywhere in the touched files).

## 10. Trade-offs

- **`TD-09`/`TD-10`/`TD-11` are untouched, stated plainly, not
  overclaimed.** This Work Package implements only the mechanical,
  non-trust half of `WP 13.0A`'s design (`ADR-0107`–`ADR-0109`). The
  trust retrofit those three debt items still need
  (`ADR-0110`–`ADR-0112`) remains a genuinely separate, still-unassigned
  future Work Package's task — closing `TD-06`/`FCR-0010` here does not
  move `TD-09`/`TD-10`/`TD-11` an inch closer to resolution.
- **Dependency graph resolution's own runtime cost remains unmeasured**
  beyond the existing regression suite's own small, local candidate
  counts — `Plugin Platform Architecture.md`'s own disclosed assumption
  (Consequences, ADR-0107) is inherited here, not newly proven.
  `src/Plugins/` itself remains empty, so no real-world candidate count
  has ever exercised this algorithm outside test fixtures.
  `Plugin Register.md`'s own "Not Yet Applicable" status is correctly
  unaffected by this Work Package — it implements infrastructure, not a
  real, shipped plugin.
- **Live, in-process plugin unload remains unavailable** — `ADR-0108`'s
  own reserved `Loaded → Unloading → Unloaded` seam is built exactly as
  reserved: nameable, unused, and contingent on the sibling Trust &
  Isolation Architecture's own, still undecided, isolation-mechanism

- **A discrepancy in this Work Package's own file count, disclosed

## 11. Common Mistakes

Two mistakes the Verification & Testing workstream itself found and
corrected while writing its own new tests — both in its own test
assertions, never in production code, disclosed here because a future
reader writing further plugin tests is likely to reach for the identical
wrong assumption first:

1. **Assuming `PluginRegistryEntry.Name`/`Version` reflect the loaded
   module, once a plugin reaches `Loaded` state.** They do not, by
   design: `PluginAssemblyLoader.LoadPlugins` records
   `new PluginRegistryEntry(manifest.Id, manifest.Name, manifest.Version,
   PluginRegistryState.Loaded, null)` — every field sourced from the
   already-validated `PluginManifest`, never from the loaded assembly's
   own reflected `IModule.Name`/`IModule.Version`, which the Plugin
   Registry never inspects at all. A manifest whose declared `Name`/
   `Version` happens to differ from its own assembly's `IModule`
   implementation will report the manifest's values, consistently, for
   every recorded state — not merely `Loaded`.
2. **Assuming every `PluginRegistryEntry.Id` recorded for an isolated
   failure is the plugin's own declared manifest `Id`.** It is, for every
   category that reaches individual validation with a parsed `Id` in
   hand (categories 3–14, including all three of this Work Package's own
   new dependency-resolution categories) — but `PluginFailureLogging.
   RecordIsolatedFailure`'s own `id` mapping falls back to the
   *candidate's folder name* for `InvalidPluginManifestException`
   (category 2), the one category where the manifest failed before its
   own `Id` field could even be parsed (malformed JSON, an unreadable
   file, a missing required field). A test asserting a specific plugin
   Id against a malformed-manifest fixture needs to assert the folder
   name it used to construct that fixture, not a value the manifest
   itself never successfully declared.

## 13. Key Takeaways

- Implementing an already-fully-ratified architecture, with no genuine
  alternative left to weigh, is a real and valuable kind of Work Package
  in its own right — the discipline of confirming zero new ADRs were
  warranted, rather than assuming that conclusion, is itself part of
  what this Work Package's own Governance & Documentation workstream did.
- The fixed-point-reduction-then-cycle-detection algorithm's own
  correctness rests entirely on one property: removing a candidate can
  only ever shrink the surviving set, never grow it, so the
  repeat-until-a-full-pass-changes-nothing loop is guaranteed to
  terminate, and terminates at the unique fixed point regardless of scan
  order — this is why no separate cascade-propagation mechanism was ever
  needed.
- "Architecture only, no code changes" and "the code that architecture
  describes now exists" are two genuinely different, separately
  verifiable claims — `WP 13.0A`'s own retrospective drew this
  distinction for itself once; this Work Package is the event that
  closes the gap that distinction named, for exactly the mechanical,
  non-trust half of the design, and no further.
- A Work Package's own assigned number can itself become a governance
  finding worth disclosing, not merely a label — this Work Package's own
  collision with an unrelated, already-reserved roadmap-predicted `WP
  13.1A` row is recorded here with the same rigour as any other
  finding, not smoothed over because it was inconvenient to discover
  mid-Work-Package.
