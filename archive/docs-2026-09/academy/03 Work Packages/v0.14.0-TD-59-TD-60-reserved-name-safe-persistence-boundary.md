# TD-59 + TD-60 — Reserved-Name-Safe Persistence Boundary; Controlled Malformed-Value Reads

## 1. Introduction

Two defects in `PersistenceStore`, closed together because they share one
boundary: what the store does with a key on the way in (`TD-59`), and what
it does with a value that comes back damaged (`TD-60`). `dc46210` closed
both; `159d862`, five commits later, fixed two of the closure tests
themselves, which had asserted a single file system's behaviour as though
it were universal. This is a pre-`v0.14.0` engineering-body-of-work row —
it carries no `WP` identifier, per the naming decision recorded in this
retrospective set's "architecture audit becomes tracked debt" article.

## 2. Purpose

To make `PersistenceStore` — the substrate every other durable store in
`Tempest.Core` sits on — safe against two classes of input it had never
been tested against: a key that collides with a reserved Win32 device
name, and a value that has been corrupted on disk.

## 3. Background

`PersistenceStore` mapped keys and collections to file names with plain
`Uri.EscapeDataString`, which leaves `CON`, `PRN`, `AUX`, `NUL`,
`COM1`–`COM9`, `LPT1`–`LPT9` (any casing, with or without extension)
untouched. On Windows those writes are routed to devices, and
`File.Exists` then reports them absent — `MaterialCatalog.RegisterAsync
("CON", …)` returned success while the record was never seen again. The
class's own remarks claimed an arbitrary key "can never produce an invalid
or unintended file-system path"; no test had fed the store a hostile name.
Separately, every Desktop state loader and `MacroManager.LoadAsync` threw
a raw `JsonException` on a torn-write-corrupted value, bricking startup
until the file was hand-deleted despite each loader's documented "never an
exception" contract.

## 4. The Problem

A key a caller controls could silently orphan the record it named, on
one platform only, with no error anywhere in the call chain. And a single
poisoned file — a stray `.DS_Store` in a registry directory, one torn
write — could abort a whole listing or brick the composition root, on
every platform.

## 5. The Design

`TD-59`: `EncodeSegment` percent-escapes the first character of a reserved
device stem and any terminal dot; decode stays exactly
`Uri.UnescapeDataString`, so safe names encode unchanged and existing
stores remain valid. Legacy-encoded records stay readable and migrate
forward on write. Reads and deletes match the stored file name exactly —
never a case-variant — and a case-colliding write is refused loudly
instead of silently overwriting; the per-key lock is keyed on the encoded,
case-folded file identity. Writes are temp-file plus atomic-rename.

`TD-60`: corruption now surfaces as each framework's own controlled
exception, never a raw BCL type and never misreported as absence.
`Guid.TryParseExact` with a corruption-naming `MaterialsException` /
`EngineeringDataException` in both index readers; foreign registry files
skipped with a warning; stale index entries read as absent rather than
aborting `ListAsync`; `JsonException` wrapped at every store read; Desktop
loaders and `MacroManager` degrade to documented first-run defaults.

`159d862`, later: two of the new closure tests asserted a POSIX file
system's case-sensitivity as though it were universal, so they reported
`PersistenceStore`'s correct Windows behaviour — refusing a colliding
case-variant write — as a defect. They now assert whichever behaviour the
running file system actually has, decided empirically (write a file, ask
for it back under a different case) rather than from the OS name, because
a Windows volume can be case-sensitive since 1803 and macOS's default
volume is case-insensitive.

## 6. Alternatives Considered

No alternative encoding scheme is recorded in the commit; the fix works at
the one boundary every consumer shares, per the review's own recommended
option, rather than pushing hostile-name handling into each of
`MaterialCatalog`, `RequirementsService` and the rest individually.

## 7. Why This Solution Was Chosen

Because it closes the defect once, at the layer every caller already
depends on, rather than requiring every future store built on
`PersistenceStore` to remember to defend itself. And because corruption
handling that degrades to a documented default is recoverable by a user
who never has to find and delete a file by hand.

## 8. Architectural Principles

A persistence boundary's documented guarantees ("can never produce an
invalid path", "never an exception") are claims about the repository, and
an untested claim is not evidence of a true one. `TD-59`'s hostile-name
matrix and `TD-60`'s corruption tests exist because nothing had checked
either claim before.

## 9. Benefits

A key that happens to spell a reserved device name is no longer a silent
data-loss path on Windows. A single damaged or foreign file can no longer
abort an entire listing or a whole application launch. Both properties are
pinned by tests run against the real file-backed store, not a fake.

## 10. Trade-offs

The Windows-only aspects of `TD-59` — device routing itself,
case-insensitive collision at runtime — cannot be exercised on the Linux
CI host; the tests pin the cross-platform invariants that make those
failures impossible rather than the platform behaviour directly, and that
limit is disclosed rather than papered over. `159d862` disclosed the same
shape a second time: two remaining Linux-only failures were left as a
follow-up rather than folded in, because they are the mirror image of the
same problem — tests asserting Windows behaviour on a Linux runner.

## 11. Common Mistakes

Asserting one file system's behaviour as though it were the only one that
exists — the defect `159d862` fixed in the very tests written to close
`TD-59`. Trusting a documented guarantee ("can never produce an invalid
path") without a test that tries to break it.

## 12. Future Evolution

`TD-31` later builds `IBinaryPersistenceStore` as the byte shape of this
same `PersistenceStore` instance, inheriting the reserved-name encoding,
the per-key lock and the atomic-rename discipline this row established
rather than re-implementing them.

## 13. Key Takeaways

- Fix hostile input at the one boundary every consumer shares, not at
  each consumer.
- A documented guarantee is not evidence until something tries to falsify
  it.
- A cross-platform test that asserts one platform's behaviour will fail
  loudly, eventually, on the other platform — decide the expected
  behaviour empirically, not from the OS name.
