# `WP 10.3A` — Engineering Object Editors

## 1. Introduction

`v0.10.0`'s own seventh Work Package — professional graphical editors
for Engineering Objects across all six disciplines, built as one
generic Object Editor Framework, integrated with the existing
Workspace, Cockpit, and Property Inspector, without redesigning any of
the twelve frozen `WP8.0B` Workspace contracts.

## 2. Purpose

Implementation retrospective, mirroring `WP10.2B`'s own two-part
(Concept Guide, Implementation Retrospective) structure. See
`25-engineering-object-editors.md` for the design narrative; this file
focuses on what was built, files touched, and honest disclosure of
this Work Package's own two genuine findings.

## 3. Background

Commissioned directly after `WP 10.2B` (Docking & Workspace Layouts)
closed with "await Product Owner instruction before `WP 10.3A`." This
Work Package's own controlling instruction named sixteen scope items
and five explicit exclusions, closing with "STOP. Await Product Owner
instruction before `WP 10.3B`."

## 4. The Problem

See `25-engineering-object-editors.md` §4 — the Document Area's own
three-line placeholder, disclosed as future work since `WP 10.0B`,
still unrealised across four subsequent Work Packages.

## 5. The Design

See `25-engineering-object-editors.md` §5. In summary: `ObjectEditorView`
(new, `Tempest.Desktop.Editors`) — one generic engine reading every
real Engineering Object's own uniform `EngineeringObjectBase` facet
set directly (`ADR-0063`), dispatching both of its own two real
editable fields (Name, Content) through Commands
(`RenameObjectAsync`/`ReviseObjectAsync`, `ADR-0096`/`ADR-0097`).
`DocumentAreaView` gained an injectable content-builder constructor
parameter and a `MarkDirty` method — the seam the new editor plugs
into, with zero change to any existing caller's own behaviour.

## 13. Key Takeaways

Sixteen named scope items realised via one generic editor engine, not
six duplicated ones; two real, dispatched editable fields (Name,
Content) across all six disciplines for the first time, honouring
`ADR-0063` throughout; Validation feedback made real for the first
time at the Desktop layer; one precedented, additive `IWorkspaceManager`
extension (`ADR-0097`); zero Engineering Domain changes; zero Runtime
redesign; two genuine, disclosed findings (one test-arithmetic
correction, `TD-40`).

## Architectural Debt Assessment

**One new item**: `TD-40` — closing an Object Editor tab with unsaved,
buffered edits does not prompt for confirmation; `IWorkspaceView.CloseAsync`
always returns `true` today (every concrete View's own `IsDirty` has
been hard-coded `false` since `WP 8.1A`), and this Work Package's own
new, real dirty state is not wired into that close path — a real,
disclosed risk of silent data loss on an accidental tab close,
deliberately not built this Work Package (judged disproportionate
scope for a first implementation). `FCR-0068` (Discipline-Specific
Object Editor Enhancements) also recorded as a Future Capability, not
a defect — deeper per-discipline field editing was always disclosed as
out of this Work Package's own "one generic engine" scope, not an
oversight.

No other new debt. Every pre-existing item (`TD-01`–`TD-39`) reviewed
and confirmed unaffected by this Work Package's own diff.

## Observations

**A genuine, disclosed pre-existing gap closed as a side effect**:
Mechanical was the only discipline of six with no `Revise*Command` at
all — found while designing the Object Editor Framework's own generic
Content field, not by a failing test. Closed by `ReviseMechanicalObjectCommand`,
mirroring the other five disciplines' own identical shape exactly,
restoring symmetry across all six.

**Validation feedback's own honest scoping, re-confirmed**: `PropertyInspectorView`'s
own "Validation" section (`WP 10.2A`) disclosed "no per-object
validation-result read exists anywhere in the Workspace layer" — this
Work Package confirms that disclosure was accurate *for the Property
Facet layer specifically*; the underlying Domain capability
(`IValidatable.ValidateAsync`, `ADR-0075`) always existed, simply never
reachable from any Workspace/Desktop surface until `ObjectEditorView`
reached it directly.
