# WP 13.12.7 — v0.13.0 Tag Push & Release Completion

## 1. Introduction

`WP 13.12.7` pushed the `v0.13.0` tag that `WP 13.12.6` had created
locally, under explicit authorisation, and pushed **only** the tag. The
tag-triggered `.github/workflows/release.yml` run (`32146823154`) then
**failed** at its `Test (Release)` step on a single Desktop test, so
packaging and publication never ran. This Work Package therefore ends
with a valid, pushed, immutable tag and **no** GitHub Release, no
`TempestOS-v0.13.0.zip`, and no engineering-harness asset. It stopped
there deliberately.

## 2. Purpose

To complete the publication step of the Version-Tagging Workflow by
pushing the annotated tag, to observe the resulting workflow run
honestly, and — if that run did not publish — to report the true state
rather than manufacture a release by other means.

## 3. Background

`WP 13.12.6` ran `scripts/new-release.ps1 -Version 0.13.0` without
`-Push`, creating annotated tag object `15aedec` → commit `6089a218`,
verified independently because `TD-42` records that the script's `git
tag` and `git push` calls carry no `$LASTEXITCODE` guard. `6089a218` is
`WP 13.12.5`'s merge commit, and CI on `main` at that exact commit —
run `32145226354` — had returned all four jobs green.

`.github/workflows/release.yml` is `WP 11.1B`'s Version-Tagging Workflow.
It triggers on `push: tags: v*.*.*`, checks out the tag, builds Release
with `-p:TreatWarningsAsErrors=true`, re-runs the full Release suite,
then packages two separate archives — `TempestOS-<tag>.zip`
(Tempest.Desktop, the shipped application) and
`TempestOS-<tag>-engineering-harness.zip` (Tempest.App, the Internal
Engineering Harness, `ADR-0101`, `WP 11.3B`) — resolves the release notes
by directory convention, and publishes via `gh`. Its own inline comment
states the governing rule: a tagged commit that fails its own
re-verification is not published, and per Engineering Governance §7.4 the
corrective action is a new patch version and a new tag, never editing
this one.

## 4. The Problem

Pushing a tag is the point at which a release stops being local. Three
distinct hazards converge on it.

First, `TD-42`: `new-release.ps1`'s `git push origin main` and
`git push origin "v$Version"` are both unguarded, so a rejected push
would still be followed by `RELEASE SUCCESSFUL`. The script's push path
was not used here, but the class of error applies to any push — the
result must be read from the remote, not from the command's silence.

Second, scope. `new-release.ps1 -Push` pushes `main` **and** the tag.
Only the tag was authorised; `origin/main` was already at `6089a218` and
had to stay exactly where it was.

Third — and this is what actually happened — `release.yml` re-tests at
the tag. It is a genuinely independent second verification, on a
GitHub-hosted `windows-2022` runner, not a replay of the CI run that
cleared the release gate. It can disagree with that run, and it did.

## 5. The Design

**Push the tag alone, explicitly.** The tag ref was pushed on its own
rather than through the script's `-Push` path, so `main` could not move
as a side effect.

**Verify against the remote, in three parts.** After the push: the remote
tag object was resolved; its `^{}` peel was resolved; and `origin/main`
was re-read. Both the tag object and its peel resolved to `6089a218`,
and `origin/main` was confirmed **unmoved**. Verifying the peel matters
because an annotated tag's own object SHA (`15aedec`) is not the commit —
checking only the tag object would have proved nothing about which commit
was released.

**Watch the run the push triggered, and read its steps individually.**
Run `32146823154` failed at `Test (Release)`. The step-level detail was
recorded rather than the job-level verdict alone: `Tempest.Core.Tests`
passed **2,341/2,341**; `Tempest.Desktop.Tests` failed **1 of 221**,
namely `ObjectEditorViewTests.Save_RevisedContent_ActuallyAdvancesTheRealRevisionNumber`,
with `Assert.True() Failure`.

**Record the downstream steps as skipped, not as absent.** Because
`Test (Release)` exited non-zero, `Package Release build output`,
`Resolve release notes` and `Publish GitHub Release` were all skipped —
stated in artefact terms: no GitHub Release, no `TempestOS-v0.13.0.zip`,
no engineering-harness asset.

**Stop.** Per the commissioning instruction, the tag was **not** amended,
**not** re-tagged, and the run was **not** retried; no GitHub Release was
created manually. Diagnosis was left to a separate Work Package.

## 6. Alternatives Considered

**Re-run the failed job.** Rejected. A single-test failure on a shared CI
runner is exactly the signature that needs diagnosing, and a green re-run
would have destroyed the timing evidence while publishing a release whose
own gate had failed once. `WP 13.12.8` later depended on that evidence
surviving.

**Delete and re-push the tag after a fix.** Rejected, and barred.
Engineering Governance §7.4 forbids moving or recreating a pushed tag,
and `release.yml`'s own comment names the remedy as a new patch version
and a new tag.

**Publish the GitHub Release manually with `gh release create`.**
Rejected. The workflow's design premise is that a release is not
published until its own Build Gate and Test Gate pass a second,
independent time against the tag itself. Creating the Release by hand
would have satisfied the appearance of that gate while defeating it.

**Push `main` alongside the tag "for tidiness".** Rejected — `origin/main`
was already correct at `6089a218`, and the authorisation covered the tag
only.

## 7. Why This Solution Was Chosen

Because the workflow did exactly what it was built to do. `release.yml`
exists to catch a tagged commit that fails re-verification, and it caught
one. Overriding it — by retry, by retag, or by hand-publishing — would
have converted a working gate into a formality on its first real use. The
correct response to a gate that fires is to stop and investigate, which
is what happened.

## 8. Architectural Principles

- **Push the narrowest ref that satisfies the intent.** Tag only, never
  tag-and-branch by default.
- **Verify a pushed tag by its peel, not its object.** `^{}` is the part
  that names the released commit.
- **A pushed tag is immutable** (Engineering Governance §7.4). Every
  remedy downstream of a bad tag is a *new* tag.
- **An independent second verification is only independent if you accept
  its verdict.** Retrying until green is not verification.
- **Report skipped steps as consequences, not as omissions.** "No zip
  exists" is the fact; "packaging was skipped" is the reason.

## 9. Benefits

`v0.13.0` exists as a real, immutable, remotely-visible tag whose
identity was verified from the remote in both forms — object and peel —
and whose commit is the CI-green `6089a218`. `origin/main` was proven
unmoved, so the push had no collateral effect on the branch.

The failure is captured with enough precision to diagnose without
re-running anything: run id `32146823154`, failing step `Test (Release)`,
`Tempest.Core.Tests` 2,341/2,341 passed, `Tempest.Desktop.Tests` 1 of 221
failed, the exact test name, and the assertion type
(`Assert.True() Failure`). `WP 13.12.8` worked from that record directly.

The release state is unambiguous: tagged, merged, **not published** — a
distinction that later became load-bearing for the `v0.13.0` Release
Register row and for `v0.13.1`'s existence.

## 10. Trade-offs

`v0.13.0` is now permanently a valid tag with no published Release —
an anomalous but honest state that every subsequent register, note, and
status field must describe carefully rather than rounding to "released".

Stopping immediately meant the release was left incomplete at the end of
this Work Package, with no artefacts for anyone to download. That cost
was accepted in exchange for preserving the evidence and honouring §7.4.

The tag also cost something governance noticed at once: the moment it was
pushed, `governance-healthcheck.ps1` began reporting
`[FAIL] Git tag(s) with no Release Register row: v0.13.0` — a real
regression in the health-check baseline caused by this push, later closed
by a separate Work Package.

## 11. Common Mistakes

- **Checking the tag object and calling it verified.** `15aedec` is the
  annotation; `6089a218` is the release. Only the peel proves the latter.
- **Treating a one-test CI failure as noise and hitting re-run.** The
  re-run would very likely have been green — and the diagnosis, which
  turned on comparing two concurrent runs, would have been impossible.
- **Assuming a failed workflow leaves a partial release.** It does not
  here: the publish step is last, so a `Test (Release)` failure yields
  *nothing*, not a half-published release.
- **Using `-Push` when only the tag was authorised.** The script pushes
  `main` first, then the tag.

## 12. Future Evolution

Diagnosis of the failing test was deliberately deferred and became
`WP 13.12.8`, which concluded a genuine intermittent flake rather than a
product defect; the remedy landed separately as a test-only change.
`TD-42`'s unguarded `git push` calls remain open, so any future release
using the script's `-Push` path inherits the same requirement to verify
remote refs by hand. Whether `v0.13.0` should ever be published
retroactively is not decided here — this record establishes only that it
was not, and why the tag itself cannot be reused to do so.

## 13. Key Takeaways

- The second gate is the one that matters; it only counts if you let it
  fail.
- Push exactly one ref when exactly one ref was authorised, then read the
  remote to confirm both what moved and what did not.
- An annotated tag has two SHAs. Verify the one that names a commit.
- "Tagged but not published" is a legitimate, describable release state.
  Recording it accurately is cheaper than pretending otherwise and far
  cheaper than breaking §7.4 to avoid it.
