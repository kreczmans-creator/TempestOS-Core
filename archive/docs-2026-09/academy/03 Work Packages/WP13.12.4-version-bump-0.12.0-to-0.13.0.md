# WP 13.12.4 — VERSION 0.12.0 → 0.13.0

## 1. Introduction

`WP 13.12.4` is the smallest Work Package in `v0.13.0`: it changed one
file, `VERSION`, from `0.12.0` to `0.13.0`, on `feature/v0.13.0`, ahead
of the merge to `main`, and committed that change **alone** as
`30b0f45`.

No `src/` change, no `tests/` change, no tag, no release run, no GitHub
Release. The merge to `main` remained gated on explicit Product
Approval.

## 2. Purpose

To perform the release-time version bump at the moment the release
process requires it, in a form that makes the pre-tag release candidate
identifiable by a **single minimal diff**.

## 3. Background

`WP 13.12.3` had just committed the `v0.13.0` documentation closure as
`f58b475`, deliberately leaving `VERSION` at `0.12.0`. The Engineering
Readiness Review treats `VERSION` and release notes as *release-time*
actions, not evaluated as "ready" before the release branch is about to
close (`Engineering Readiness Review Architecture.md` §2.5) — so the
bump belongs after documentation closure, not before it.

`scripts/new-release.ps1` reads `VERSION` on `main` and refuses to tag
unless its content equals the requested version. That single mechanical
fact fixes the bump's position in the sequence: it has to be on `main`
before tagging, and the only way onto `main` is through the merge, so it
has to land **before** the merge.

## 4. The Problem

A version bump is trivially easy to fold into a neighbouring commit —
into the documentation closure that preceded it, or the merge that
followed. Both are tempting and both are wrong for the same reason: they
destroy the property that makes a release candidate reviewable.

The tagged commit for a release is the one an auditor, a bisect, or a
rollback lands on. If the commit that carries `VERSION 0.13.0` also
carries thirty documentation files, then "what changed to make this a
release candidate?" has no cheap answer.

There is also a byte-level hazard. `VERSION` is read by a script that
compares its *content* to a requested version string. A rewrite that
appends a trailing newline the previous content did not have is an
invisible edit with a mechanical consequence.

## 5. The Design

For a one-line change, the design is not *what* to write — it is **where
the change lives and what shape it keeps**.

**Isolation into its own sequential commit.** `30b0f45` contains the
`VERSION` change and nothing else. The pre-tag release candidate is
therefore a single minimal diff sitting immediately after the
documentation closure, and immediately before the merge. Anyone asking
what makes this tree a `0.13.0` candidate reads one line.

**Position dictated by tooling, not preference.** `new-release.ps1`
reads `VERSION` on `main` and refuses to tag on mismatch. The bump is
therefore placed pre-merge because the release script's own contract
requires it, and that reason is recorded in the commit message rather
than left to be rediscovered.

**Byte-format preservation.** The file was written with **no trailing
newline**, matching the prior content's byte shape exactly. The
comparison is on content; the shape is part of the contract.

**Verification run sequentially, after the bump, not before.** A bump
that changes a file the governance health check reads is only verified
by evidence gathered afterwards.

## 6. Alternatives Considered

**Fold the bump into `f58b475`.** Rejected — it would have put the
release candidate marker inside a large documentation commit, and would
have contradicted that commit's own explicit statement that `VERSION`
remained at `0.12.0`.

**Bump on `main` after the merge.** Rejected — it adds a commit to
`main` after the merge, which means the tag no longer points at the
merge commit whose tree was verified, and the tagged tree is no longer
byte-identical to anything reviewed on the branch.

**Bump as part of the merge commit itself.** Rejected — Engineering
Governance §7.7 requires merges into `main` to be true merge commits
through a pull request, never squash or rebase; a merge commit carrying
its own content edit is not a clean merge and would not have produced
the byte-identical tree `WP 13.12.5` later confirmed.

**Let the release script write `VERSION`.** Not available — the script
*reads* `VERSION` and refuses to tag on mismatch; it is a gate, not a
writer.

## 7. Why This Solution Was Chosen

Because the sequence has exactly one valid position for this change, and
the isolated commit is the only form that keeps that position legible.
The release script's read-and-refuse behaviour makes pre-merge
mandatory; the desire for a reviewable release candidate makes isolation
correct; byte-format preservation makes the mandatory part actually
work.

## 8. Architectural Principles

- **One commit, one reason.** A release-candidate marker shares a commit
  with nothing.
- **Sequence follows tooling contracts.** `new-release.ps1` reads
  `VERSION` on `main`; the bump lands before the merge because of that,
  not by convention.
- **Byte shape is part of a machine-read file's contract.**
- **Verify after the change, never carry evidence forward.**
- **A release-time action happens at release time.** `VERSION` is not
  bumped when the work begins.
- **Zero `src/` and `tests/` changes in a release-mechanics Work
  Package.**

## 9. Benefits

The pre-tag release candidate for `v0.13.0` is one commit with a
one-line diff. `governance-healthcheck.ps1`'s `VERSION` check flipped
from its prior state to reading "`VERSION ('0.13.0')` matches a planned
release folder", confirming the bump agreed with the release folder
structure already in place.

Verification, all run sequentially after the bump and recorded in
`30b0f45`:

- `governance-healthcheck.ps1` — **7 passed, 1 warned** (the
  pre-existing `v0.9.0`/`v0.10.0` informational), **0 failed**, exit 0;
- Debug and Release builds — **0 Warnings / 0 Errors** with
  `-p:TreatWarningsAsErrors=true`;
- full regression — **2,562/2,562** in both configurations
  (`2,341` `Tempest.Core.Tests` + `221` `Tempest.Desktop.Tests`).

Because the commit's tree carried no code change, `WP 13.12.5` was
later able to confirm the merge commit's tree was **byte-identical** to
`30b0f45` — a check that only means something when the candidate commit
is this small.

## 10. Trade-offs

An extra commit in the history for one line. That is the intended cost:
the alternative — a smaller commit count — buys nothing and loses the
single reviewable diff.

The bump also puts the branch briefly into a state where `VERSION`
claims `0.13.0` while the release does not yet exist on `main`. That
window is real, and it is bounded by the merge; the commit message says
plainly that no tag, no release run and no GitHub Release accompanied
it, so the state is documented rather than ambiguous.

## 11. Common Mistakes

- **Rewriting `VERSION` with a tool that appends a trailing newline.**
  The file is compared by content; the prior shape had none, and the
  bump preserved that deliberately.
- **Bumping after the merge.** The release script reads `VERSION` on
  `main` — but a post-merge bump moves the tag target off the verified
  tree.
- **Bundling the bump with documentation.** It hides the release
  candidate and contradicts the documentation commit's own claim about
  `VERSION`.
- **Reusing verification from the preceding commit.** The health check's
  `VERSION` assertion changes *because* of this commit; evidence taken
  before the bump cannot show that.

## 12. Future Evolution

With `VERSION` at `0.13.0` on the feature branch, the remaining
Release Blocking finding was still open: `Build & Test` and `CI Gate`
had never run on `main` at the pre-tag commit
(`Engineering Readiness Review Architecture.md` §2.3). `WP 13.12.5`
took that on — pull request, feature-branch CI, explicit Product
Approval, merge, and real CI on `main`.

The record here is silent on whether the `VERSION` bump should ever be
automated by the release tooling; `new-release.ps1`'s current role is
strictly to read and refuse.

## 13. Key Takeaways

- The smallest commit in a release can be the most load-bearing one.
- Tooling contracts, not habit, decide where a release-mechanics change
  sits in the sequence.
- For machine-read files, the bytes are the interface — a trailing
  newline is a behavioural change.
- Isolation is what lets a later step assert "the merged tree is
  byte-identical to the candidate".
