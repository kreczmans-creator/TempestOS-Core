# WP 16.1A-R1 — Release Path Enforcement

## 1. Introduction

`WP 16.1A-R1` is a `v0.16.0` review board remediation on the integration
line (`feature/v0.16.0`, commit `ac7daa6`) — CI and release-script
configuration plus two documentation corrections, no production code or
test. It closes findings 3, 4, 5 and 8 of the review board's Build, CI &
Release Engineering perspective: `release.yml` never ran the Governance
Health Check at all; `scripts/new-release.ps1` printed a yellow warning
on a non-green CI run and continued past it; `linux-launch-smoke`
accepted a process merely still running at timeout as proof of a
successful launch; and `PHYSICAL_REVIEW.md` asserted two different, and
opposite, facts about Linux launch capability in three different
sections. `TD-45` stays Open — none of this configures GitHub branch
protection, which remains a repository-administrator action.

## 2. Purpose

`WP 16.1A` had made `CI Gate` depend on the Governance Health Check, so
no branch could reach `main` carrying a governance register that had
drifted from source (`TD-45`'s CI-workflow half). The review board's own
Build/CI/Release Engineering perspective asked the next question that
work did not answer: is the *release* path — the workflow that actually
tags and publishes — as strong as the *merge* path that same Work
Package had just hardened? It was not. This Work Package exists to
close that specific gap, not to redo `WP 16.1A`'s own scope.

## 3. Background

`WP 16.1A`'s own brief (`v0.16.0 Release Plan.md` §`WP 16.1A`) was
narrowly scoped to GitHub branch protection and `ci.yml`'s own gate
dependency; `05-release-engineering.md` and `WP11.1B Engineering
Workflow.md` §4 describe the separate hotfix/release-candidate/rollback
procedures that `release.yml` and `scripts/new-release.ps1` actually
execute, and neither of those files was in `WP 16.1A`'s own touched-file
set. `TD-45`'s own register row already distinguished the two halves of
branch-protection enforcement — the CI-workflow half `WP 16.1A` closed,
and the GitHub-settings half that remains a manual, Product-Owner-only
action — but neither that row nor `WP 16.1A`'s own report asked whether
the *tagging* path carried an equivalent gap. It did.

## 4. The Problem

Four distinct gaps, each real and independently verifiable:

1. **`release.yml` never ran the Governance Health Check.** The workflow
   that builds, verifies, and publishes a tag had no step invoking
   `governance-healthcheck.ps1` at all — a tag could be published
   carrying exactly the drift `CI Gate` would have rejected on the way
   to `main`, and with `TD-45`'s GitHub-settings half still
   unconfigured, nothing else stood in the way either.
2. **`scripts/new-release.ps1` degraded a non-green CI run to a
   warning.** It queried `gh run list` and printed a yellow warning on
   failure or absence, then continued regardless — a human who did not
   read the warning could tag and push a commit whose `CI Gate` was red,
   or had never run at all.
3. **`linux-launch-smoke` treated "still running at timeout" as
   success.** Exit code 124/137 — the process had not exited when
   `timeout` fired — was accepted as a pass. That is not evidence of a
   correct launch: a process that deadlocks *after* Avalonia platform
   initialization (a stuck DI resolution, a frozen dispatcher loop) is
   also still running at 25 seconds, and would pass identically to a
   healthy one.
4. **`PHYSICAL_REVIEW.md` contradicted itself.** §1's own table still
   read "Linux cannot currently launch the desktop application" while
   §8 item 1, rewritten by `WP 16.5B`, said the opposite; §9's
   troubleshooting row pointed a reader experiencing a launch failure at
   a section asserting the reverse of their own symptom.

## 5. The Design

**Governance gate on the release path.** `release.yml` now runs the
Governance Health Check as a hard gate, in the same shape as its
existing Build and Test steps — a governance `Fail` now blocks a
publish, not only a merge to `main`.

**`new-release.ps1` requires the literal outcome `success`.** It now
reads the run's own `conclusion` and throws unless it is exactly
`success` — not merely "not `failure`." **This distinction is the
sharpest evidence in this Work Package's own report:** the review board
observed a real run, `33950873014`, complete as **`cancelled`**, not
`failure`, because a later push superseded it under `concurrency:
cancel-in-progress`. A check written as "block on `failure`" would have
let that run through — `cancelled` is neither `failure` nor `success`,
and a two-outcome mental model (pass or fail) does not have a slot for
it. The check as written requires the positive outcome, not merely the
absence of the negative one. A `-SkipCiCheck` switch exists for the one
legitimate case — `gh` cannot reach the run from where the operator is
standing, and they have confirmed the run on GitHub themselves — but it
does not make an un-green commit taggable on its own; it moves the
check off the machine and onto the person, who then owns it, and the
console says so when the switch is used.

**`linux-launch-smoke` requires a positive startup marker, not merely
timeout survival.** The timeout branch now additionally requires
`Host -> Running.` to appear in the captured log. This was **verified
empirically, not assumed from source**: a real `xvfb-run` launch was run
on this branch and its log inspected directly — the marker is
`TempestHost.EnterRunning`'s own log line, appears exactly once, at
`07:03:21.139`, followed by real navigation activity — and only then was
the job's own `grep` run against that captured log to confirm it
matches. The job stays advisory and stays outside `gate`'s own `needs:`
— the review board agreed strengthening what the check proves is a
separate question from whether it should block, and only the first was
in this Work Package's own scope.

**Documentation corrected, not merely reworded.** `PHYSICAL_REVIEW.md`
§1 now states that Linux launches, and — deliberately — that it does so
on weaker evidence than Windows: one local `xvfb-run` launch plus an
advisory, non-required CI job, not a promoted, gating one. §9's
troubleshooting row now states the symptom was `TD-116`, resolved, so
seeing it today is a new defect rather than the known one. A separate,
smaller correction: `PDFtoImage` 4.1.1 was the one version-sensitive pin
in `Tempest.Desktop.csproj` with no rationale comment while every other
pin had one; the new comment records both what it is (not a security
hold — the vulnerability scan is clean) and what it is not (evaluated —
5.x changes the native SkiaSharp/PDFium dependency set, the same class
of change that produced `TD-116`, so it wants its own timeboxed spike,
not a version bump inside a hygiene release).

## 6. Alternatives Considered

**Promote `linux-launch-smoke` to a required check now, alongside
fixing what it actually proves.** Not done — the job has no track
record yet, and no promotion criterion has been set by anyone; the
report names this as an open question rather than deciding it
unilaterally inside a remediation Work Package.

**Write the CI-check as "block on failure," matching the intuitive
mental model of a pass/fail gate.** Rejected directly — this is the
exact formulation the observed `cancelled` run would have defeated. The
report's own account of finding this live, rather than reasoning about
it abstractly, is what makes "require `success`" the only formulation
actually justified by evidence in hand.

## 7. Why This Solution Was Chosen

Each fix targets the specific gap this Work Package's own investigation
found, not a general rewrite of the release tooling. The CI-conclusion
check is written the way it is because a real run was observed
defeating the more intuitive alternative — not because "require
`success`" is abstractly more correct than "block on `failure`," but
because the codebase's own recent history already produced the
counterexample. The `linux-launch-smoke` marker was chosen and verified
against a captured log before being wired into automation, for the same
reason `WP 16.4A` mutation-tested its own new coverage rather than
trusting that it passed: a marker whose match is only ever checked
against its own source, never against a real launch, risks being wrong
in either direction — matching nothing a healthy launch ever produces,
or matching something a broken one produces too.

## 8. Architectural Principles

- **A gate should require the positive outcome it claims, not merely
  the absence of the specific negative outcome it was written against**
  — `cancelled` is neither `success` nor `failure`, and a check modeled
  on the wrong subset of outcomes lets exactly the case that matters
  through silently.
- **A smoke test's positive signal must be evidence of correct
  behaviour, not survival of a timeout** — "still running" and "running
  correctly" are different claims, and `linux-launch-smoke`'s original
  form conflated them.
- **A new automation marker is verified against a real captured
  artifact before it is trusted, not derived from a source-code `grep`
  alone** — the identical evidentiary standard `WP 16.4A` set for test
  coverage, applied here to a CI log assertion.
- **A release-hardening Work Package's own defects, caught by its own
  gate, are disclosed rather than quietly fixed** — see §10.

## 9. Benefits

- The release path is now gated on governance drift exactly as the
  merge path already was — a tag can no longer publish drift `CI Gate`
  would have rejected on the way to `main`.
- The specific, observed hazard (a `cancelled` run reading as
  not-a-failure) is closed with direct evidence behind the fix, not a
  generic hardening.
- `PHYSICAL_REVIEW.md` no longer asserts two opposite facts about the
  same platform capability across three of its own sections.
- `dotnet build -c Release -p:TreatWarningsAsErrors=true` and Debug both
  0 warnings/0 errors; both workflow files parse as valid YAML;
  `new-release.ps1` parses under the PowerShell parser;
  `governance-healthcheck.ps1` 14 passed/2 warned/0 failed, both
  warnings pre-existing and unrelated.

## 10. Trade-offs

**`TD-45` stays Open.** Everything in this Work Package hardens the
paths an engineering session can actually reach. None of it configures
GitHub branch protection itself, which remains `TD-45`'s own stated
closing action and a repository-administrator act — "the gate exists"
is still not "the gate is enforced" until that manual step happens.

**`linux-launch-smoke` stays advisory**, deliberately, meaning Linux
launch capability today still rests on one local capture plus a
non-blocking CI signal, not a required one — a real, disclosed gap in
depth of evidence relative to Windows, named directly in the
`PHYSICAL_REVIEW.md` correction rather than smoothed over.

**A defect in this Work Package's own first attempt was caught by its
own gate, not by review.** The `PDFtoImage` rationale comment initially
contained a literal `--` inside an XML comment, which is illegal and
broke `Tempest.Desktop.csproj` (`MSB4025`); the warnings-as-errors build
failed immediately. The report records this rather than quietly fixing
it and moving on — a release Work Package whose entire subject is
enforcement is stronger evidence for its own thesis when its own
enforcement catches its own mistake, and that only has value if it is
disclosed.

## 11. Common Mistakes

- **Designing a CI-outcome check around "did it fail" rather than "did
  it succeed."** A workflow run has more terminal states than pass and
  fail — `cancelled`, `skipped`, `timed_out` all exist — and a check
  written against the wrong subset of them lets exactly the state that
  matters slip through unnoticed.
- **Treating "the process did not crash and did not hit a definitive
  failure exit code" as proof of correct behaviour for a UI smoke
  test.** A hang after successful platform initialization looks
  identical to a healthy long-running process under a bare timeout
  check.
- **Letting two governance or review documents assert opposite facts
  about the same capability because each was updated by a different
  Work Package that only read its own section.** `PHYSICAL_REVIEW.md`'s
  own §1/§8/§9 contradiction existed because `WP 16.5B` updated §8
  without checking whether §1 or §9 needed the same correction.

## 12. Future Evolution

Promoting `linux-launch-smoke` from advisory to required needs both a
track record this job does not yet have and an explicit promotion
criterion nobody has set — named here as an open question for whoever
next revisits Linux CI coverage, not decided by this Work Package.
`TD-45`'s branch-protection configuration remains the Product Owner's
outstanding action; until it happens, every enforcement layer this
Work Package and `WP 16.1A` together built is still voluntary at the
GitHub-settings level. The `PDFtoImage` 5.x upgrade needs its own
timeboxed spike, given its native dependency-set change is the same
class that produced `TD-116` — explicitly deferred, not forgotten,
by the rationale comment this Work Package added.

## 13. Key Takeaways

- "Block on failure" and "require success" are not the same predicate,
  and the gap between them is exactly where a superseded or cancelled
  run slips through a gate that looks, on a casual read, like it should
  have caught it.
- Verify a new automation marker against a real captured artifact before
  wiring it into a gate — a marker checked only against its own source
  can be wrong in either direction and nothing before production would
  show it.
- A release-hardening Work Package that breaks its own build and is
  caught by its own gate is evidence the gate works; disclosing that
  plainly is stronger engineering communication than treating it as an
  embarrassment to edit away before anyone sees the diff.
- Hardening a merge path and hardening the release path that follows it
  are two different pieces of work — a gate on one gives no assurance
  about the other unless someone deliberately asks whether they match.
