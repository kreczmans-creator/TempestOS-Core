# WP 16.2C — v0.16.0's Own Academy Retrospectives

## 1. Introduction

`WP 16.2C` wrote eleven Academy retrospectives for `v0.16.0`'s own
landed Work Packages, closing half of `TD-127`. It ran as two parallel
branches cut from the same base (`338d8ac`): half A (`4191401`, six
retrospectives — `WP 16.0A`, `16.0B`, `16.1A`, `16.1B`, `16.3A`,
`16.5B`) and half B (`32f75a9`, five — `WP 16.2A`, `16.2B`, `16.3B`,
`16.4A`, `16.5A`), merged within the same minute
(`ee0dc74`/`bdc8643`, both 06:42) and reconciled into the shared
registers at integration (`ac87049`). It has no report of its own —
this retrospective is sourced from its four commits, `v0.16.0
Release Plan.md`, `docs/releases/v0.16.0/WorkPackages.md`'s own row for
it, and the eleven retrospective files it produced.

## 2. Purpose

`WP 16.2B`'s own retrospective (`docs/academy/03 Work Packages/
WP16.2B-academy-retrospective-backfill.md` §12) named the exact gap this
Work Package exists to close, before `WP 16.2C` was ever commissioned:
"closing `v0.16.0` without retrospectives for its own Work Packages
would re-break release DoD item 4 the moment `WP 16.2B` made it true,
because `WP 16.2B`'s own scope, by the plan's own design, excluded this
release's Work Packages." The `v0.16.0` review board raised this
formally as `TD-127` on 2026-09-05, and added `WP 16.2C` to the
programme — it appears in none of the plan's original 13 Work Packages
(`v0.16.0 Engineering Status Report.md` §2, "Added by the review board").
`WorkPackages.md`'s own row states the objective directly: retrospectives
for "`v0.16.0`'s own eleven Work Packages," each following Engineering
Governance §6's thirteen-section template.

## 3. Background

Release-level Definition of Done item 4 ("Academy updated") had been
false since `v0.10.0` until `WP 16.2B` made it true for the first time
in six releases, by backfilling 41 historical retrospectives and 21
register rows. `WP 16.2B`'s own scope, stated in its plan brief and
repeated in its retrospective, was historical work only — it never
touched `v0.16.0`'s own Work Packages, because most of them had not
landed yet when `WP 16.2B` ran. By the time the review board convened,
thirteen Work Packages from the original plan had landed. Nothing in
the plan had scoped anyone to retrospect them, which is precisely the
condition `TD-127`'s own text describes: "Nothing was scoped to write
them."

## 4. The Problem

At the moment `WP 16.2C`'s two branches were cut (`338d8ac`, 06:02:49),
thirteen Work Packages from the original plan were complete, per
`WorkPackages.md`. Two of the thirteen were excluded from `WP 16.2C`'s
own assigned set by design, not by oversight: `WP 16.9.0` (readiness
review, version bump, release notes) had not started at all, so nothing
existed to retrospect; and `WP 16.4B` had merged (`f1a8e33`,
06:42:22) — forty minutes *after* `WP 16.2C`'s branches were cut, and
landing at essentially the same moment `WP 16.2C`'s own two halves
merged (`ee0dc74`/`bdc8643`, 06:42:27–28). `WP 16.2C`'s assigned scope
was therefore fixed to the eleven Work Packages complete at
commissioning time, in a release whose own review board was, at the
same hour, actively spawning additional remediation Work Packages
(`WP 16.1A-R1` at 07:05; `WP 16.4B-R1` at 07:30; `WP 16.4B-R2` at
08:04; `WP 16.5A-R1`, merged 06:42, essentially concurrently with
`WP 16.2C` itself) that no branch — including `WP 16.2C`'s own two — had
been scoped to cover, because none of them existed yet when the
scoping decision was made.

## 5. The Design

**Split by Work Package number range, not by count.** Half A took the
lower-numbered six (`16.0A` through `16.5B`); half B took the
remaining five (`16.2A` through `16.5A`) — the same zero-row-overlap
partition principle `WP 16.2B` used when it split three ways by
release, applied here to a smaller set by number range instead, since a
single release has no release-level boundary to split along.

**Source each retrospective from that Work Package's own primary
evidence**, per each commit message: the Work Package's own report where
one exists, its real commits, `v0.16.0 Release Plan.md` §3's own brief
for it, and the ADRs/`D-0xx`/`TD-nnn` rows it touched. Two disclosed
exceptions, stated inside the retrospectives themselves rather than
silently worked around: `WP 16.3A` produced no report at the time, so
its retrospective is sourced from `ADR-0120` and `State Schema
Versioning Architecture.md` directly, with the missing report itself
recorded as a disclosed deviation; `WP 16.3B` and `WP 16.5A` needed
direct reading of current source and test files beyond their own
reports to verify specific claims.

**Cite `D-021`–`D-026` as Proposed, throughout, without exception** —
both commit messages state this explicitly, and both note the Decision
Register itself still read "Total: 20 entries" at the time of writing,
with no `D-021`+ row — the same discipline every other `v0.16.0` Work
Package retrospective holds to.

**Touch no shared file.** Neither branch edited `Academy Index.md`,
`Academy Register.md`, `Contributor Learning Path.md`, any register,
`PROJECT_STATUS.md`, or `WorkPackages.md` — both commit messages record
running `governance-healthcheck.ps1` locally and getting the expected
failures (new files present, not yet indexed), left unfixed by design,
for the integrator's own pass at merge.

## 6. Alternatives Considered

**One author, sequentially, across all eleven.** Available, and would
have avoided any question of how to partition the set — rejected for
the same reason `WP 16.2B` rejected it at three times this volume: two
authors working a disjoint, non-overlapping split finish in roughly
half the wall-clock time with no coordination cost, because a
by-number-range split has no shared field (unlike `WP 16.2B`'s register
count) that either author's own commit needs to guess at.

**Wait for every in-flight remediation Work Package to land before
scoping the set**, so the retrospective effort could cover everything in
one pass rather than leaving a residual. Not the design actually used,
and — in hindsight, disclosed here rather than only in §10 below — the
choice that would have avoided the exact gap this Work Package's own
existence now demonstrates. It was not available to `WP 16.2C` at
commissioning time: the remediation Work Packages that ended up
uncovered (`WP 16.1A-R1`, `WP 16.4B-R1`, `WP 16.4B-R2`, `WP 16.5A-R1`)
had not yet been raised by the review board when `WP 16.2C`'s scope was
fixed, and `WP 16.4B` itself had not yet merged. A design that waited
for "everything" to land had no defined stopping point available to it
at the time, given a review board actively finding new RED and AMBER
findings in real time.

## 7. Why This Solution Was Chosen

Splitting by number range kept each author's own diff reviewable as
"the retrospectives for this contiguous slice," matching `WP 16.2B`'s
own precedent for the same reason: each retrospective's value depends
on being sourced from that Work Package's own primary evidence, which a
by-range split does not disturb. Fixing scope at commissioning time
rather than waiting indefinitely for the release to fully stabilise was
the only design that let `WP 16.2C` actually complete and land — a
release under active review-board remediation has no natural point at
which "everything is done," and a retrospective effort that waited for
one would never have shipped at all.

## 8. Architectural Principles

- **A retrospective-writing Work Package's own scope is a snapshot of
  the release at commissioning time, not a standing subscription to
  everything the release will eventually contain** — `WP 16.2C`'s eleven
  Work Packages were exactly the set complete when its branches were
  cut; nothing about its own design extended coverage to work that
  landed afterward, including work that landed within the same hour.
- **A parallel documentation split needs a partition with zero
  row-level overlap**, restated from `WP 16.2B`: number-range splitting
  achieved this cleanly for a much smaller set than `WP 16.2B`'s own
  three-way release split needed.
- **Citing decisions as Proposed is a discipline every retrospective in
  this set independently holds to**, verified directly rather than
  assumed: none of the eleven files states or implies `D-021`–`D-026`
  as approved.
- **A retrospective sourced from a missing report should say so inside
  itself**, not silently substitute other evidence and imply a report
  existed — the `WP 16.3A` retrospective's own disclosed deviation is
  the concrete instance.

## 10. Trade-offs — where this Work Package fell short

**`WP 16.2C` wrote eleven retrospectives and left six landed `v0.16.0`
Work Packages without one — `WP 16.4B` itself, and all five Work
Packages the review board added afterward: `WP 16.1A-R1`, `WP 16.4B-R1`,
`WP 16.4B-R2`, `WP 16.5A-R1`, and, with some irony, `WP 16.2C` — this
retrospective's own Work Package.** This is not a hypothetical risk
named for completeness; it is what actually happened, found by the
release's own independent governance audit rather than by this Work
Package disclosing it about itself. `TD-127`'s entire premise was that
closing `v0.16.0` without retrospectives for its own Work Packages would
re-break release DoD item 4 the moment `WP 16.2B` made it true —
`WP 16.2C` closed exactly that risk for the eleven Work Packages
complete when it was commissioned, and, by not extending to what landed
afterward, re-created a narrower version of the same risk it was raised
to close.

**The integration commit's own language overclaims what was actually
achieved.** `ac87049`'s commit message reads: "Academy Index and Academy
Register: eleven links and eleven rows for `v0.16.0`'s own retrospectives
(`WP 16.2C`, **closing `TD-127`**)." Checked directly against the
Technical Debt Register at this retrospective's own base commit: `TD-127`'s
row still reads **Open**, with status text that is unrevised
forward-looking prose from when the row was raised — "`WP 16.2C` writes
the retrospective for each landed `v0.16.0` Work Package" — not a
completion note reflecting what eleven-of-seventeen actually delivered.
The register's own status is correct, for the right underlying reason
(six Work Packages genuinely remain uncovered), but its own text does
not say why it is still Open, and the integrator's commit message
claimed a closure the register itself never recorded. Both facts are
true at once: `WP 16.2C` did real, correctly-sourced work, and the
release's own record briefly overstated what that work had settled.

**Timing explains part of the gap and none of the rest.** `WP 16.4B`
had not merged when `WP 16.2C`'s branches were cut, so its absence from
the original assigned set is not itself a lapse. But `WP 16.4B` had
landed by the time `WP 16.2C`'s own two branches merged, and nothing —
no third branch, no closure pass, no explicit decision to defer —
picked it up before `WP 16.2C` was declared Complete in
`WorkPackages.md`. The four remediation Work Packages raised by the
review board across that same day compound the same gap further, and
none of them had a retrospective scoped for them by anyone, `WP 16.2C`
included, until the present retrospective-writing effort — commissioned
directly by the governance audit that found this exact shortfall —
closes it.

## 11. Common Mistakes

- Treating a fixed-scope assignment, correctly executed, as if it
  discharged an open-ended governance obligation — `WP 16.2C` closing
  its own eleven-item list is real progress on `TD-127`, not the same
  claim as `TD-127` itself being closed, and the two were conflated in
  the integration commit message.
- Declaring a Technical Debt row's underlying condition satisfied in a
  commit message without checking whether the row's own status text
  agrees — `TD-127` still reads Open, for a reason its own prose does
  not state, because nothing revised it after `WP 16.2C` landed.
- Fixing a scope at commissioning time without a defined mechanism for
  picking up work that lands in the same wave, immediately afterward —
  `WP 16.4B` merged minutes before `WP 16.2C`'s own branches did, and no
  design in this Work Package accounted for that adjacency.
- Assuming a retrospective-writing Work Package's own name ("v0.16.0's
  own eleven Work Packages") is a complete description of the release's
  actual Work Package count at the moment the retrospective effort
  concludes, rather than a snapshot frozen at the moment it began.

## 12. Future Evolution

The six-Work-Package gap this retrospective documents is not a
prediction — it is the reason the present retrospective-writing effort
exists at all, commissioned by the `v0.16.0` independent governance
audit's own RED finding against exactly this shortfall. `WP 16.4B-R2`'s
own retrospective and `WP 16.5A-R1`'s own retrospective, alongside this
one, close three of the six; the remaining three (`WP 16.4B`,
`WP 16.4B-R1`, `WP 16.1A-R1`) are being closed in parallel by a sibling
effort. `WP 16.2B`'s own retrospective (§12) already named the standing
governance question this recurrence answers empirically rather than
theoretically: whether Engineering Governance §6 means a retrospective
is owed *within* the Work Package that does the work, or only *before
the release that contains it closes*. This project has now run behind
on that question three times within a single release wave — `WP 16.2C`
itself being commissioned mid-release, immediately followed by four
more remediation Work Packages with no retrospective coverage of their
own, and now this very retrospective documenting the gap it left. A
third recurrence, inside the release that was supposed to have closed
the gap for good, is itself the strongest evidence yet that the
convention needs a decision — most plausibly, that Engineering
Governance §6's existing text ("every work package from this point
forward produces or updates Academy documentation as part of its own
Definition of Done") already answers it, and the actual gap is that
this release's remediation Work Packages did not treat their own
retrospective as part of *their* Definition of Done, deferring it
instead to a separate, later-scoped catch-up effort that then itself
ran out of scope before catching up.

## 13. Key Takeaways

- A Work Package scoped to close a governance gap for a fixed,
  enumerated list closes exactly that list — it does not, by itself,
  close the underlying obligation the list was a snapshot of, and a
  release under active remediation will keep generating new items
  after any such snapshot is taken.
- An integration commit's own prose claiming a Technical Debt row is
  "closing" should be checked against that row's actual status text
  before either is trusted — the two silently disagreed here.
- The safest design for a retrospective-writing Work Package inside an
  active release is to make retrospective-writing part of every other
  Work Package's own Definition of Done, per Engineering Governance §6
  as already written, rather than a separate catch-up pass that will
  itself always be one wave behind whatever remediation the release's
  own review process generates next.
- A retrospective about the Work Package that was supposed to close a
  gap, and did not fully close it, is more useful than one that reports
  only the eleven it did write — the honest account of what was missed
  is the actual lesson a reader of this document needs.
