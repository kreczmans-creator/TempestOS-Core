# WP 11.4A — Release Engineering Corrections

## 1. Introduction

`WP 11.4A` (commits `b7e43ff`/`0670843`) resolves the three
release-engineering defects `WP 11.9.0`'s own Release Publication Report
diagnosed the moment `v0.11.0`'s CI/CD tooling ran on real GitHub-hosted
infrastructure for the first time in this release's history — none a
regression in product code, none discoverable without running on real
infrastructure. Its full account is `docs/releases/v0.11.0/WP11.4A
Release Engineering Corrections.md`. This retrospective is written
retrospectively under `WP 16.2B`, grounded in that report and the two
commits.

## 2. Purpose

Fix exactly the three defects the first real CI execution surfaced,
verify each locally and on real infrastructure independently, and close
out the governance record — no scope beyond those three items.

## 3. Background

`WP 11.9.0` prepared `v0.11.0` for release and its own follow-on
publication step pushed the branch and tag for the first time this
release's history had ever exercised real GitHub-hosted execution. Three
genuine defects surfaced immediately — invisible to every prior local
verification, because none of them could manifest outside a real
GitHub-hosted runner.

## 4. The Problem

**A flaky Desktop test**: `ObjectEditorViewTests.cs`'s
`VerificationResultSection_RecordPass_ActuallyRecordsARealVerificationRecord`
used a fixed `Task.Delay(50)` racing an async status-text update —
confirmed genuinely flaky (the identical commit passed the same test on
a separate CI run). **A path-resolution defect** in
`governance-healthcheck.ps1`: PowerShell's `Join-Path` does not discard
an already-rooted child path, unlike `[System.IO.Path]::Combine` — an
absolute `-SummaryPath` (CI's own `$env:RUNNER_TEMP`-based path) doubled
into `RepoRoot`, tripping the script's own "never write inside the repo"
safety check for the wrong underlying reason. **A checkout conflict** in
`ci.yml`'s `governance-health-check` job: `fetch-tags: true` with no
pinned `ref:` collided with a tag-triggered push's own default checkout
ref, both targeting the same local `refs/tags/<name>` path.

## 5. The Design

The flaky test's fixed delay is replaced with a bounded (2-second) poll
against the real, live status text, re-read from the visual tree on
every iteration — the same final assertion still runs; the test still
genuinely fails if the operation never completes, it no longer fails
because it merely ran slower than an arbitrary guess. The path-resolution
defect is fixed with an `IsPathRooted` guard: an already-rooted path
resolves directly; a relative path still joins against the current
location exactly as before. The checkout conflict is fixed by pinning
`ref: ${{ github.sha }}` — checking out by commit SHA removes the
competing tag-ref write target.

## 6. Alternatives Considered

Increasing the fixed delay (e.g. to 200ms) was implicitly rejected in
favour of a condition-driven poll — a longer fixed delay reduces the
observed flake rate without eliminating the underlying race, and slows
every passing run unconditionally; a poll that exits as soon as the real
condition is met has neither cost.

## 7. Why This Solution Was Chosen

Each fix targets the actual root cause rather than the symptom: a poll
against the real, live condition rather than a longer guess; a rooted-
path guard rather than a workaround avoiding absolute paths in CI;
pinning the checkout ref rather than disabling `fetch-tags` (which
Check 3, `governance-healthcheck.ps1`'s own Release Register check,
genuinely needs).

## 8. Architectural Principles

No production, Domain, or architecture change; no feature work — all
three touched files are test/tooling/CI-configuration only, exactly
matching this Work Package's own explicitly scoped three-item brief.

## 9. Benefits

`Build & Test` and `CI Gate` now genuinely pass on real infrastructure
for the first time in this release's history — independently confirmed
via two separate live runs (a branch push and a disposable,
non-release-pattern tag push, deleted after verification). `TD-44`
(CI never executed on real infrastructure) moves Open → Resolved,
its own precondition now directly confirmed.

## 10. Trade-offs

`Governance Health Check` still reports failure on both real runs after
this Work Package — confirmed benign, not a crash: genuine, pre-existing
governance debt (`WP 11.2A`/`WP 11.9.0`), explicitly outside this Work
Package's own three-item scope. `TD-42`/`TD-43` (both from
`WP 11.9.0`'s own QA findings) remain open, distinct from and not
duplicated by the three new items this Work Package registers
(`TD-46`–`TD-48`).

## 11. Common Mistakes

**Treating a flaky test's own pass on a re-run as confirmation it was
never actually flaky.** This Work Package's own evidence is explicit
that the identical commit passed the same test on a separate CI run
before this fix — a single green run does not disprove a race condition;
the fix here is verified by five further, isolated repetitions plus two
full-suite runs, not by one lucky pass.

## 12. Future Evolution

`WP 11.4B`, immediately following, discovers a fourth, more serious
release-engineering defect during its own pre-merge verification — the
`v0.10.0` tag-position defect `WP 11.1B` had already disclosed, repeated
verbatim in `v0.11.0`'s own tag. This Work Package's own three fixes are
independently reconfirmed still holding by `WP 11.4B`'s own subsequent
real CI runs.

## 13. Key Takeaways

- A defect that only manifests on real, GitHub-hosted infrastructure
  cannot be found by local verification alone, however thorough — this
  Work Package exists precisely because `WP 11.1A`'s own local
  verification could not have caught any of the three items it fixes.
- A fixed delay racing an async condition is not "probably long enough"
  — replace it with a bounded poll against the real condition, which is
  correct by construction rather than by margin.
- A tool's own crash on a specific input shape (an absolute
  `-SummaryPath`) is a defect in the tool, not evidence the input shape
  itself was wrong — CI's own `$env:RUNNER_TEMP`-based path was a
  legitimate use the tool needed to support correctly.
