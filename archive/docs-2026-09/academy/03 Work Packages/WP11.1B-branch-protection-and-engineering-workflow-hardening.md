# WP 11.1B — Branch Protection & Engineering Workflow Hardening

## 1. Introduction

`WP 11.1B` (commit `6966dcf`) defines the complete engineering workflow
surrounding `WP 11.1A`'s CI pipeline: branching strategy, pull request
expectations, merge and release requirements, required CI status checks
(documented, not configured), the version-tagging workflow, a first-ever
hotfix workflow and rollback procedure, and a release-candidate process.
Implementation only in the sense of GitHub configuration and release
tooling — no production code behaviour changed. Its full account is
`docs/academy/06 Engineering Standards/05-release-engineering.md` (cited,
not duplicated) and `docs/releases/v0.11.0/WP11.1B Engineering
Workflow.md`. This retrospective is written retrospectively under
`WP 16.2B`, grounded in that report and commit `6966dcf`.

**Disclosed divergence from `WP11.0B Architecture Roadmap.md`'s own
prediction**: that roadmap scoped `WP 11.1B` as "Governance Currency
Pass & Health-Check Tooling." The Product Owner instead commissioned it
as Branch Protection & Engineering Workflow Hardening — the roadmap's
own predicted scope was, in substance, delivered one Work Package later
by `WP 11.2A`. `WorkPackages.md`'s own Status section names this
directly; it is a "recommendation, not approval" exercised, not a
defect.

## 2. Purpose

Turn `WP 11.1A`'s new machine-verified Build Gate/Test Gate into a
complete, documented process governing how a change actually reaches
`main` and how a release is actually cut — something this project had
never had before.

## 3. Background

Through `v0.10.0`, every merge to `main` was a direct, local `git
merge`/`git push` by Product Approval — no pull request, no branch
protection, no documented hotfix or rollback path existed. `WP 11.1A`'s
CI pipeline gave a pull request's own required status check somewhere to
attach to for the first time; this Work Package writes the process that
depends on it.

## 4. The Problem

A CI pipeline alone does not constitute a workflow — nothing enforced
that a pull request even existed, that merges preserved Work-Package
granularity, or that a release was only cut from `main` after a
CI-verified merge rather than from a feature branch directly. And no
documented procedure existed for the two situations every real project
eventually needs: an urgent post-release fix, and a defect discovered
after a tag is already public.

## 5. The Design

**Branching**: `main` is the only permanent branch; one release branch
per minor version (`feature/vX.Y.0-<slug>`), the exact pattern already
in use since `v0.5.0`; a new `hotfix/vX.Y.Z-<slug>` type. **Pull
requests**: from this Work Package onward, every merge to `main` goes
through one — one PR per release branch (not per Work Package; Work
Packages continue landing as individual commits), using a new
`.github/pull_request_template.md`, merged only as a non-fast-forward
merge commit (never squash/rebase, preserving Work-Package-level commit
history), only on Product Approval's own explicit instruction.
**Required CI status checks and branch protection** are documented in a
recommendation table for a future repository administrator — not
configured, per this Work Package's own explicit constraint.
**Versioning**: `MAJOR.MINOR.PATCH`; MAJOR reserved until `v1.0.0`;
PATCH reused, for the first time as a real convention, for hotfixes
only. **Release-candidate process** (`-rc.N` tags, one deliberate,
named exception to "tag only from `main`" — a candidate by definition
precedes the merge it candidates for). **Hotfix workflow**: branch from
the affected tag, minimal scope, identical gates, PATCH-only bump, and a
mandatory forward-merge step named explicitly because an omitted
forward-merge is, in any project, the single most common way a hotfix
process quietly fails. **Rollback procedure**: a published tag is
immutable; a post-release defect always moves forward via a hotfix,
never a rewritten tag.

**Two genuine pre-existing defects found and fixed** in
`scripts/new-release.ps1`: a stale release-notes path check (`docs/
releases/v$Version.md`, a convention abandoned since `v0.6.0`); missing
`-p:TreatWarningsAsErrors=true` parity with `WP 11.1A`'s own CI check.

**One genuine governance deviation found and disclosed, not silently
corrected**: `v0.10.0`'s own tag resolves to the feature branch's own
pre-merge commit, not to `main` — contradicting Governance §7.1/§7.3 as
literally written. Checked against every other release tag
(`v0.4.0`–`v0.8.0` all correctly resolve to `main`; `v0.9.0`'s own
direct-`main` resolution has an already-disclosed, different reason).
`v0.10.0` is the one genuine, previously-undisclosed instance — and,
despite this explicit warning existing throughout `v0.11.0`'s own
development, `v0.11.0`'s own tag repeated the identical defect (see
`WP 11.4B`).

## 6. Alternatives Considered

A permanent `develop`/`staging` branch was considered and rejected: this
project has never had one, nothing in `WP11.0A`/`WP11.0B`'s own findings
identifies a gap it would close, and adding one would be a genuine
process-architecture change outside this Work Package's own brief.

## 7. Why This Solution Was Chosen

Documenting a recommendation for GitHub repository settings, rather than
configuring them directly, keeps this Work Package's own scope exactly
"infrastructure-as-code in this repository" — a distinction it states
explicitly, and one that matters: configuring a repository setting is an
outward-facing, administrator-scoped action this Work Package's own
brief did not authorise.

## 8. Architectural Principles

No production code, ADR, or architecture document was modified; no
GitHub repository setting was configured. Every job name, file path,
branch pattern, and version convention this document cites was
cross-checked directly against the file that defines it, not assumed —
its own "Verification" section names each check performed.

## 9. Benefits

TempestOS gains its first documented hotfix and rollback procedure, its
first pull-request-gated merge process, and a release-candidate path
`WP11.0B`'s own roadmap had already named `v1.0.0` as an expected user
of. Two real, previously-unexercised script defects are fixed before
either script is ever load-bearing for a real release.

## 10. Trade-offs

The `v0.10.0` tag-position defect is disclosed, not fixed — Governance
§7.4 as it stood at the time did not permit moving a published tag, and
this Work Package does not create the exception that later,
`WP 11.4B`, does. No GitHub repository setting was configured — every
recommendation in §4's table remains discipline-only until a future
administrator acts on it.

## 11. Common Mistakes

**Disclosing a defect class in prose without also closing the loop with
a mechanical check.** This Work Package's own "Evidence & Findings"
explicitly warns future readers about the `v0.10.0` tag-position defect
— and `v0.11.0`'s own tag repeated it anyway, within the same release
cycle, because nothing mechanical verified a new tag's ancestry before
it was created. `WP 11.4B`'s own retrospective covers what happened next
and what preventative action was recommended.

## 12. Future Evolution

Governance §7 item 4 is later amended by `WP 11.4B` to allow a narrow,
one-time, Product-Owner-approved exception for a release-process defect
found before a release branch closes — cross-referenced from this
document's own §10 rather than rewritten here, per Governance §5's
"never delete, mark superseded" convention. `Contributor Learning
Path.md`'s own stale closing pointer — a comparable class of drift —
was found by `WP 11.9.0`'s own Workflow Engineer review and not
corrected until `WP 16.2B`, five releases later.

## 13. Key Takeaways

- A CI pipeline and an engineering workflow are two different
  deliverables — the first makes a claim machine-checkable; the second
  decides when that claim is required, and by whom, before a merge
  happens.
- Naming a defect explicitly in a retrospective's own prose is not the
  same as preventing its recurrence — the identical defect this
  document warned against recurred within the same release.
- A documented-but-unconfigured recommendation (branch protection) is
  real progress over no documentation at all, but it is not yet an
  enforced gate — name that gap plainly rather than let the
  documentation read as though it were already enforced.
