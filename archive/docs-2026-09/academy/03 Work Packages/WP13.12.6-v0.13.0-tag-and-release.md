# WP 13.12.6 — v0.13.0 Tag & Release

## 1. Introduction

`WP 13.12.6` created the `v0.13.0` annotated tag. It ran
`scripts/new-release.ps1 -Version 0.13.0` on `main`, deliberately
**without** the `-Push` switch, so the release-validation pipeline —
branch, tree, `VERSION`, Release Notes, pre-existing-tag, advisory CI,
Release build, Release tests — executed in full and terminated at tag
creation. Nothing was pushed and nothing was published. One deviation
from the intended clean run is disclosed below rather than absorbed.

## 2. Purpose

To convert `WP 13.12.5`'s merged, CI-green `main` into an immutable,
annotated release point, using the project's own release script rather
than a hand-typed `git tag`, and to stop at exactly that boundary so
that publication remained a separate, separately-authorised act.

## 3. Background

`WP 13.12.4` bumped `VERSION` to `0.13.0` in an isolated commit
(`30b0f45`), because `scripts/new-release.ps1` reads `VERSION` on `main`
and refuses to tag unless its content equals the requested version.
`WP 13.12.5` then merged `feature/v0.13.0` into `main` as the true merge
commit `6089a218` (parents `13a6ce3` + `30b0f45`, tree byte-identical to
`30b0f45`), and real CI on `main` at that exact commit — run
`32145226354` — returned all four jobs green, clearing the release's sole
Release Blocking finding under `ADR-0106` §4 for the first time.

`WP 11.1B` built `scripts/new-release.ps1` and
`.github/workflows/release.yml` together as the Version-Tagging Workflow.
`docs/releases/v0.13.0/WorkPackages.md` records that this script had
never been run for a real release; `TD-42` records the same, noting that
every `v0.10.0`/`v0.11.0` tag was created manually. `v0.13.0` is
therefore the script's first genuine execution against a live release.

## 4. The Problem

The script's terminal output cannot be trusted at face value. `TD-42`
records, with an empirical reproduction from `WP 11.9.0`, that
`new-release.ps1`'s `git tag -a "v$Version" -m "TempestOS v$Version"`
call and both its `git push` invocations carry **no `$LASTEXITCODE`
verification**, unlike the script's own `dotnet build` and `dotnet test`
steps, which check it correctly and `throw`. Under this environment's
`$ErrorActionPreference = "Stop"`, a failing unredirected `git` command
does not self-promote to a terminating PowerShell error: `git` writes
`fatal:` to inherited stderr, sets `$LASTEXITCODE` (128, reproduced), and
the script continues straight through to an unconditional
`RELEASE SUCCESSFUL` banner whose body prints `Tag : Created`,
`Build : Passed` and `Tests : Passed` as fixed `Write-Host` lines.
`Tag : Created` is a literal string, not an observation. Any
Work Package that reports "the script said it succeeded" as evidence of a
tag is reporting the script's optimism, not the repository's state.

A second problem was local, not scripted: at checkout, local `main` was
**sixteen commits behind `origin/main`**. Tagging that stale tip would
have produced a `v0.13.0` tag pointing at the wrong commit — one that had
never had CI run against it on `main` — which is precisely the failure
`WP 13.12.1` had graded Release Blocking.

## 5. The Design

**Run the real script, not an equivalent sequence.** The whole point of
`new-release.ps1` is that its preconditions are mechanical and uniform.
Reproducing them by hand would have made this release's tag the
*fourteenth* manually created tag and left `TD-42` still untested against
reality. The script was run as written.

**Withhold `-Push`.** Without the switch, the script performs every gate
and creates the tag, then prints the guidance block about `release.yml`
and exits. Publication therefore required a separate, explicitly
authorised act — which became `WP 13.12.7`.

**Repair the stale checkout by fast-forward only, and prove it first.**
Before moving local `main`, three facts were verified: that local `main`
was a **strict ancestor** of `origin/main`; that there were **zero
local-only commits**; and that the working tree was **clean**. Only then
was the fast-forward taken. A merge, rebase, or reset would each have
produced a tip that was not byte-identical to the CI-verified
`6089a218`.

**Verify the tag independently of the banner.** After the script exited,
the tag was resolved directly against the repository: annotated tag
object `15aedec`, peeling to commit `6089a218` — the exact merge commit
`WP 13.12.5` recorded and the exact commit run `32145226354` had tested.
The banner was treated as decoration.

**Record what the script's advisory CI check actually did.** The `gh`
block is explicitly best-effort — a `gh` failure only prints a yellow
warning and every check below it runs regardless. Here `gh` was present
and resolved run `32145226354` as `completed/success`, agreeing with the
independently established fact rather than substituting for it.

## 6. Alternatives Considered

**Tag manually with `git tag -a`.** Rejected. It would have been the
same act the project has performed for every prior release, and would
have left the script's real-world behaviour unknown for another version —
the precise gap `TD-42` names.

**Fix `TD-42` first, then tag.** Rejected as scope. Adding
`$LASTEXITCODE` guards touches `scripts/`, which was outside this Work
Package's commissioning, and would have made the release's own footprint
larger than the release. Independent verification achieves the same
safety for this one execution without changing the tree; the debt remains
open and disclosed.

**Run with `-Push` in one pass.** Rejected. Pushing a tag triggers
`release.yml`, which builds, tests, packages, and publishes a GitHub
Release. That is an externally visible, effectively irreversible act
under Engineering Governance §7.4, and it deserved its own authorisation
boundary rather than riding on a switch.

**Reset local `main` to `origin/main`.** Rejected in favour of a proven
fast-forward: a `--hard` reset reaches the same SHA but discards any
local-only work silently. The zero-local-commits check is what made the
fast-forward safe, and it was run first, not assumed.

## 7. Why This Solution Was Chosen

Because a release tag is only as good as the commit it names, and a
release script is only as good as the evidence it produces. Running the
script exercised the project's own tooling on its own first real
release; verifying the tag independently ensured that the one known,
registered weakness in that tooling could not silently produce a false
success; and stopping before push kept the irreversible step behind an
explicit decision.

## 8. Architectural Principles

- **Use the project's own tooling for the project's own process.** A
  release run outside the release script proves nothing about the script.
- **Never accept a tool's self-report as evidence of a side effect.**
  Read the repository, not the banner.
- **A known unguarded exit code is a reason to verify, not a reason to
  panic.** `TD-42` did not block the release; it determined *how* the
  release was checked.
- **Irreversible acts get their own boundary.** Tag creation is local and
  recoverable; tag push is neither.
- **Disclose deviations at the point they occur.** A stale checkout
  repaired quietly is a stale checkout nobody can audit.

## 9. Benefits

`v0.13.0` has an annotated tag — object `15aedec`, peel `6089a218` —
whose identity was established by direct inspection rather than by
inference from output text. The commit it names is the one CI ran green
on `main`, so the tag and the release gate agree.

`scripts/new-release.ps1` has now executed against a real release for the
first time since `WP 11.1B` created it, and its preconditions were
observed to hold live: branch `main`, clean tree, `VERSION` matching
`0.13.0`, `docs/releases/v0.13.0/Release Notes.md` present, no
pre-existing `v0.13.0` tag. Its Release build passed 0 Warnings /
0 Errors and its Release tests 2,562/2,562 — both figures as recorded in
`docs/releases/v0.13.0/WorkPackages.md`. The fast-forward deviation is on
the record with the three checks that made it safe, so a future reader
can re-derive the decision rather than trust it.

## 10. Trade-offs

Splitting tag creation from tag push left the repository holding a local
tag `origin` did not have — harmless, but a divergence to remember — and
distributes the release's evidence across two Work Package records.

Running the script rather than hand-tagging meant accepting `TD-42`'s
exposure for the duration of the run. That exposure was mitigated by
verification, not removed: had the tag genuinely failed to create, the
banner would still have claimed success. `TD-42` remains open, so the
next operator inherits the same hazard and must apply the same
discipline.

## 11. Common Mistakes

- **Reading `Tag : Created` as a fact.** It is a hard-coded line printed
  unconditionally after an unguarded `git tag`.
- **Tagging a stale local branch.** Sixteen commits behind, the tip
  looked like a normal `main` and would have produced a plausible,
  wrong tag.
- **Treating the script's `gh` check as a gate.** It is advisory by
  design: a `gh` failure prints a warning and the script proceeds. It
  confirms; it does not authorise.
- **Assuming `-Push` is a convenience.** It is the difference between a
  local, deletable tag and a permanent, workflow-triggering publication.

## 12. Future Evolution

`TD-42`'s recorded remedy is unchanged and still open: add the identical
`$LASTEXITCODE -ne 0` → `throw` guard already used for `dotnet build` and
`dotnet test`, after the `git tag` call and after each `git push` call in
`scripts/new-release.ps1`. Until then, every release must verify the tag
and the remote refs by hand, exactly as this Work Package did. The record
is silent on whether any further hardening of the script's advisory `gh`
check was considered; this retrospective asserts nothing either way.

## 13. Key Takeaways

- A script that says `RELEASE SUCCESSFUL` has told you what it intends,
  not what happened.
- Fast-forward is safe only after you have proved it *is* a
  fast-forward — strict ancestor, zero local commits, clean tree.
- Registered technical debt is most useful the moment you are standing on
  it; `TD-42` shaped this Work Package's verification, and that is what a
  debt register is for.
- Stopping deliberately is a deliverable. A tag that exists locally and
  nowhere else is a decision, not an incomplete step.
