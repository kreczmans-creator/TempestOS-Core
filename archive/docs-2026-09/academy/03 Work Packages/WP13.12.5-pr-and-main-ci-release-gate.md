# WP 13.12.5 — PR & Main-CI Release Gate

## 1. Introduction

`WP 13.12.5` cleared the finding that had held `v0.13.0` at **NOT
READY** through three successive readiness executions: `Build & Test`
and `CI Gate` had never run on `main` at the pre-tag commit
(`Engineering Readiness Review Architecture.md` §2.3).

It did so in two distinct phases separated by a tooling boundary. In the
first, the work **stopped** — `gh` was not installed, no GitHub MCP
integration existed, and the repository is not anonymously readable
(`WebFetch` → HTTP 404) — and reported exactly what remained undone
rather than inventing evidence. In the second, with `gh` 2.97.0
installed and authenticated, it read PR **#1**, recorded its CI, merged
under explicit Product Approval as `6089a218`, and observed real CI on
`main` at that exact commit come back green.

## 2. Purpose

To satisfy §2.3's CI requirement on `main` itself — not on the feature
branch that fed it — and to do so through the approved merge mechanics,
with every step's evidence read from the real system.

## 3. Background

`WP 13.12.1` had adjudicated the classification directly against the
governing text: the never-run `main` CI gate **is** Release Blocking,
because §2.3's blocking condition reads "either job fails, **or has not
actually been run** on `main` at the pre-tag commit".
`WP 13.12.2` and `WP 13.12.3` both closed with the same residual
verdict, describing the finding as structural and unclearable on a
feature branch. `WP 13.12.4` then put `VERSION` at `0.13.0` in an
isolated commit, `30b0f45`, making the branch head a legitimate release
candidate.

Everything remaining sat behind actions a feature branch cannot perform
and a Work Package cannot self-authorise: opening a pull request,
pushing, and merging into `main` — each requiring explicit,
per-occasion Product Approval under Engineering Governance §7.5 and
§7.6, and §7.7 requiring the merge to go through a pull request gated on
`CI Gate`, as a merge commit, never squash or rebase.

## 4. The Problem

The gate could not be observed, let alone cleared, without a channel to
GitHub — and no channel existed. `gh` was absent. There was no GitHub
MCP integration. The repository is private, so `WebFetch` against it
returned HTTP 404, which is indistinguishable from "does not exist" and
therefore useless as evidence either way.

That is precisely the situation in which a report is most tempting to
fabricate: the expected outcome is known, the shape of the evidence is
known, and the only thing missing is the evidence itself. A plausible
CI summary would have been accepted and would have cleared the
release's last blocker on nothing.

The second problem is subtler. Once `gh` was available, **feature-branch
CI was readily observable** — four green jobs on `feature/v0.13.0`. It
looks like the required evidence. It is not: §2.3 requires those jobs on
`main` at the pre-tag commit, and no amount of green on the branch
substitutes.

## 5. The Design

The design here is the **approval-and-verification sequence** — what was
observed, in what order, on whose authority.

**Phase 1 — stop at the boundary and report the boundary.** With no
channel to GitHub, the Work Package did not proceed and did not
approximate. It named the three unavailable routes (`gh` absent, no
GitHub MCP, `WebFetch` → HTTP 404 on a non-anonymously-readable
repository) and reported exactly what remained. A tooling boundary is a
finding, not a gap to paper over.

**Phase 2, step 1 — read the real pull request.** With `gh` 2.97.0
installed and authenticated, PR **#1** was read directly:
`feature/v0.13.0` → `main`, state `MERGEABLE`, `CLEAN`, head `30b0f45`.

**Phase 2, step 2 — record feature-branch CI, and disqualify it in the
same breath.** `Build & Test (Debug)`, `Build & Test (Release)`,
`CI Gate` and `Governance Health Check` all **pass**, on both the push
and the `pull_request` runs. Recorded as fact — and stated plainly that
feature-branch CI does **not** satisfy §2.3.

**Phase 2, step 3 — merge only on explicit Product Approval, with the
mechanics §7.7 requires.** Merged as `6089a218`: a **true merge
commit**, parents `13a6ce3` and `30b0f45`, **no squash, no rebase**, and
its tree **byte-identical** to `30b0f45` — the check `WP 13.12.4`'s
isolation made meaningful.

**Phase 2, step 4 — observe real CI on `main` at that exact commit.**
Run `32145226354`, all four jobs green. This, and only this, is the
evidence §2.3 asks for.

## 6. Alternatives Considered

**Report the expected CI result and move on.** Rejected outright. The
whole value of §2.3 is that it demands an observation; a predicted
observation clears nothing and corrupts the record it is written into.

**Accept feature-branch CI as equivalent.** Rejected — §2.3 names
`main` at the pre-tag commit specifically, and the distinction is not
pedantry: the merge commit's tree is what gets tagged, and it is a
different object from the branch head even when identical in content.

**Squash or rebase the merge to keep `main` linear.** Rejected —
Engineering Governance §7.7 requires a merge commit and forbids both.
Either would also have destroyed the byte-identical-tree check.

**Infer readability from the HTTP 404.** Rejected — a 404 on a private
repository proves nothing about the repository's state. Treating it as
signal would have been inventing evidence by a slower route.

**Proceed to merge without waiting for explicit approval.** Not
available — §7.5 and §7.6 make push and merge per-occasion
authorisations that never carry forward.

## 7. Why This Solution Was Chosen

Because the finding was structural, and structural findings are cleared
by performing the structure, not by arguing about it. The sequence
chosen — real PR, real branch CI recorded honestly and honestly
disqualified, approved merge with mandated mechanics, real `main` CI —
produces exactly the artefact §2.3 names, with each step's evidence
readable by anyone with repository access.

Stopping in phase 1 is what made phase 2 credible. A Work Package that
will report a boundary when it hits one is a Work Package whose green
result means something.

## 8. Architectural Principles

- **A tooling boundary is reported, never approximated.** Absent
  evidence is stated as absent.
- **Evidence must be of the thing the rule names.** `main` at the
  pre-tag commit, not the branch that fed it.
- **Merge mechanics are governance, not preference.** True merge commit,
  no squash, no rebase (§7.7).
- **Hard-to-reverse shared-state actions require explicit,
  per-occasion authorisation** (§7.5, §7.6) — never assumed, never
  carried forward.
- **A private repository's 404 is not information.**
- **Byte-identical trees make merges auditable.**

## 9. Benefits

`v0.13.0`'s **sole §4 Release Blocking finding was cleared for the first
time**. `Build & Test (Debug)`, `Build & Test (Release)`, `CI Gate` and
`Governance Health Check` ran on real, GitHub-hosted infrastructure for
`main` itself at commit `6089a218` — run `32145226354` — and all four
returned green.

The merge is auditable end to end: PR #1 records the head commit,
`6089a218` records both parents, and its tree is byte-identical to
`30b0f45`, so nothing entered `main` that had not been reviewed on the
branch.

The phase-1 report is itself a benefit: the project now has a worked
precedent for a Work Package that halts and says what it could not do,
in the one situation where fabrication would have gone undetected.

## 10. Trade-offs

Clearing the gate required real, irreversible actions — a push and a
merge into `main` — which no amount of prior review can undo. That cost
is inherent: §2.3 cannot be satisfied on a feature branch, so the last
blocker in a release is necessarily cleared by the least reversible
step.

Phase 1 cost a full stop and a resumption. The alternative was a
plausible fiction, so the delay is the cheap option.

Feature-branch CI was recorded even though it satisfies nothing. That
adds a green result to the record that a careless reader could mistake
for the required evidence — mitigated only by the explicit statement,
alongside it, that it does not satisfy §2.3.

## 11. Common Mistakes

- **Treating green feature-branch CI as the §2.3 evidence.** It is the
  most available result and the wrong one.
- **Reading a 404 on a private repository as a fact about the
  repository.**
- **Squashing the release merge.** It breaks §7.7 and destroys the
  tree-identity check.
- **Assuming approval carries forward.** Each push and each merge is its
  own authorisation.
- **Filling a tooling gap with a confident summary.** The gap is the
  finding.

## 12. Future Evolution

The record here ends with the §2.3 gate cleared at `6089a218`. What
followed is recorded elsewhere: `PROJECT_STATUS.md` states that
`v0.13.0` was genuinely tagged (annotated `15aedec` → `6089a218`) and
that its tag-triggered `release.yml` run (`32146823154`) then failed at
`Test (Release)` on one Desktop test, so packaging and publication never
ran — no GitHub Release, no `TempestOS-v0.13.0.zip`, no
engineering-harness asset. `WP 13.12.8` diagnosed that as a genuine
intermittent flake and `WP 13.12.9` remediated it test-only; `v0.13.1`
is the corrected and publishable form. The `v0.13.0` tag is immutable
and stays exactly as cut.

That sequence is worth noting here for one reason: `Build & Test` green
on `main` pre-tag is the gate §2.3 defines, and it is not the same
assurance as a green tag-triggered release pipeline. The record is
silent on whether §2.3 should be extended to cover the latter.

## 13. Key Takeaways

- The right answer to "I cannot observe this" is to say so — especially
  when everyone already expects the answer.
- Evidence has to be of the exact thing the rule names; near-evidence is
  not evidence.
- Merge mechanics carry governance weight: a true merge commit with a
  byte-identical tree is what makes the merge checkable.
- The last blocker in a release tends to be the least reversible one; it
  is cleared under explicit approval, once, deliberately.
