# Governance — The Architecture Audit Becomes Tracked Debt; TD-01's Trigger Fires

## 1. Introduction

`b796b9d` recorded a full-repository architecture and dead-code audit
where debt belongs — the Technical Debt Register — rather than in a
conversation: eleven rows, `TD-105` to `TD-115`, each carrying its own
evidence and its own approved disposition. It also fired `TD-01`'s own
long-recorded revisit trigger, commissioning `WP-C`, and is the last row
of this engineering body of work before the twelve-Work-Package
remediation programme it commissions begins. A pre-`v0.14.0` engineering-
body-of-work row.

## 2. Purpose

To convert an architecture audit's findings into durable, trackable
register rows with named dispositions, and to act on the one finding that
resolved an eleven-release-old open question.

## 3. Background

`TD-01` had been open since `WP 2.6` and deferred twice. Its recorded
revisit trigger was explicit: "the legacy bootstrap code is either
genuinely revived or deliberately deleted." `WP 5.2` had declined to
migrate that code (`D-020`) but never ruled on deleting it — the trigger's
other branch, left untaken. The audit fired the trigger directly:
`LoggingService` is referenced only by `BootstrapService`, itself
referenced by nothing, and the same pattern holds for four further
retired types.

## 4. The Problem

Two problems in one commit. First, eleven real architecture findings with
nowhere durable recorded to live except a conversation, which is
unrecoverable the moment the session ends — precisely the failure mode
`ec81bf6`, earlier in this same engineering body of work, had already
found once (a prior closure report that was never committed and could not
be recovered). Second, a totals paragraph that was already wrong before
this pass: it claimed 92 rows against a direct count of 104, twelve
behind since an earlier point in the branch's history.

## 5. The Design

Eleven rows, `TD-105`–`TD-115`, each with its own evidence and disposition
— for most of them, "deferred, and here is the trigger", not "fix it
now". `TD-01`'s approved disposition is deletion, tracked as `TD-110` and
delivered by `WP-C`, the first Work Package of the twelve-Work-Package
remediation programme this commit commissions. Two sanctioned exceptions
are recorded rather than fixed: `AT-24` (the Duplicate-to-Copy direct
handler invocation, retained unless evidence shows a concrete problem) and
`AT-25` (the `InternalsVisibleTo` in the App assembly). `TD-115` records
three implemented-but-unreachable commands as a capability awaiting
`FCR-0073` — explicitly not dead code, explicitly not for deletion. The
totals paragraph's count is corrected to 115 by direct count; the
Resolved/Open split is deliberately *not* restated, because 48 of the 104
existing rows do not begin with a parseable status token and re-deriving
the split by inspection would be guessing rather than counting — recorded
as outstanding rather than carried forward as a number known to be wrong.

**Naming rule for this backfill.** The 29 rows in this pre-`v0.14.0`
engineering body of work — this one included — carry no `WP` identifier
anywhere in the repository, for the identical reason `WP-Z3` §6 records
for the remediation programme's own work packages: `WP14.x` numbers were
considered and rejected, since inventing them would orphan every existing
cross-reference (commit messages, Technical Debt Register rows, ADRs) that
already names these changes by their real identifiers — a `TD-` number, an
`ADR-` number, or, for `TD-77`'s five-commit migration, a named stage.
Retrospective files for this set are therefore named
`v0.14.0-<anchor>-<kebab-title>.md`, where `<anchor>` is the row's own
identifier when it has one, and a short topic slug when it does not (a CI
fix, a test fix, an audit with no debt-row number of its own). This
mirrors `WP-Z3`'s own precedent exactly, extended to a body of work that
has no `WP-<Letter>` identifiers to reuse either.

## 6. Alternatives Considered

Leaving the audit's findings in the commissioning conversation rather
than committing them as register rows — rejected on the same grounds
`ec81bf6` had already established: an unrecorded finding does not survive
past the session that found it. Inventing `WP14.x` numbers for this
engineering body of work — rejected for the reason stated above, matching
`WP-Z3`'s own rejection of the identical option for its programme.

## 7. Why This Solution Was Chosen

Because a register row with evidence and a named disposition is
recoverable by anyone who reads it later; a conversation is not. And
because reusing each row's own real identifier, rather than inventing a
numbering scheme with no prior existence in the repository, keeps every
existing cross-reference — commit messages, ADRs, the register itself —
pointing at something that still resolves.

## 8. Architectural Principles

A long-open debt row with a two-branch trigger ("revived or deleted")
stays open until somebody actually takes one of the two branches;
declining one branch (`D-020`) is not the same as ruling on the other, and
`TD-01` sat on that exact gap for eleven releases. A total should be
re-derived by direct count rather than carried forward, and a total that
cannot honestly be re-derived (the Resolved/Open split here) should be
disclosed as outstanding rather than guessed at.

## 9. Benefits

`TD-01`, open since `WP 2.6`, finally has an approved disposition and a
Work Package (`WP-C`) to deliver it. Eleven real findings are durable
register rows with evidence rather than a conversation. The totals
paragraph's row count is corrected from a figure twelve behind reality.
Governance health check: 7 passed, 1 pre-existing warn, 0 failed.

## 10. Trade-offs

The Resolved/Open split is deliberately left unreconciled — recorded as
outstanding debt in the paragraph itself rather than resolved by
inspection, since 48 of 104 rows have no parseable status token to count
by. This commit commissions a twelve-Work-Package programme rather than
fixing all eleven findings itself; most of them are deliberately deferred
with a named trigger, not resolved here.

## 11. Common Mistakes

Carrying a register total forward without re-deriving it, which is how
this repository's own totals paragraph drifted twelve rows behind
reality before this pass caught it — the identical mistake `ec81bf6`,
earlier in this same body of work, had already corrected once, recurring
here on a different figure.

## 12. Future Evolution

This commit directly commissions the twelve-Work-Package remediation
programme (`WP-C` through `WP-Z2`) that follows immediately after it in
`docs/releases/v0.14.0/WorkPackages.md` §C — and that programme's own
retrospective gap is what `WP-Z3` later closes, recording in its own §12
the identical backlog (this 29-row engineering body of work, plus
`v0.11.0`) that this retrospective set exists to close.

## 13. Key Takeaways

- A debt row's revisit trigger with two branches is not satisfied by
  ruling on one branch and staying silent on the other — `TD-01` proved
  this by staying open across three separate decisions before the audit
  finally took the deletion branch.
- Commit audit findings to a durable register in the same pass that finds
  them; a conversation is not a record.
- When a body of work has no `WP` identifiers of its own, name its
  retrospectives after the identifiers it does have (`TD-`, `ADR-`, a
  named stage, or a short topic slug) rather than inventing numbers that
  would orphan every existing cross-reference — the same principle
  `WP-Z3` established for the programme this commit commissions, applied
  here to the engineering body of work that preceded it.
