# TD-77 Stage 2 — Core Command Context and Binding Contract

## 1. Introduction

`6e3d6d5` is the first of four `TD-77` stages, adding the Core-only
contract for Id-based command invocation with caller-supplied data: 74
production discipline commands are registered with real, working
handlers, but `CommandDescriptor.CreateDefault` is a parameterless
factory, so none of them can be reached by Id. A pre-`v0.14.0`
engineering-body-of-work row, filed under its own stage identifier
(`TD-77-stage-2`) per the naming rule recorded in this set's
"architecture audit becomes tracked debt" article.

## 2. Purpose

To do exactly the additive extension `Command Framework Architecture.md`
had already anticipated: "extending it to accept caller-supplied
parameters through an Id-based path … is a purely additive change to
`CommandDescriptor` alone."

## 3. Background

`TD-77`'s own register entry states the defect plainly: the Command
Palette is a searchable list, not the contextual command framework the
brief describes — only 22 of 96 registered descriptors set
`CreateDefault`, all in `Tempest.Samples`, so every real discipline
command reports `CommandUnavailable`. This is the same gap the Ribbon
works around with its own three Kind-keyed verbs, addressed here at the
root rather than worked around a third time.

## 4. The Problem

Three surfaces — the Command Palette, the Ribbon's generic path, and the
Macro Manager — were all hollow for one shared reason: nothing in Core
could express "this command needs caller-supplied data" and let a caller
supply it.

## 5. The Design

`CommandContext`/`CommandContextObject` carry the current selection and
nothing else. `CommandContextRequirement` states what a binding declares
it needs. `CommandParameter`/`CommandParameterPrompt` state values to
collect and how to ask. `CommandBinding` maps context plus values to an
`ICommand`. `CommandAvailability` is available, or a user-facing reason.
`CommandInvocation`/`CommandOutcome` record executed, cancelled, or
unavailable — three outcomes, not two, because declining a prompt is not
a failure and must not raise an error. Bindings are hand-written typed
lambdas closing over a command's real constructor — no reflection, no
service location, no attribute scanning, no second registration mechanism
(`ADR-0037`, `ADR-0070`). A context carries a selection and nothing more —
no service provider, no view, no project, no property bag: the audited
absence of any project read across all 74 commands is why no project
field exists.

## 6. Alternatives Considered

Adding `binding` as a second constructor overload — rejected: it proved
ambiguous at named-argument call sites, so `Binding` is an init-only
accessor instead and the constructor stays untouched.

## 7. Why This Solution Was Chosen

Because a hand-written typed binding, rather than reflection or attribute
scanning, keeps the same "no second registration mechanism" property
`ADR-0037`/`ADR-0070` already established for the rest of the command
framework — this extends it rather than adding a parallel path.

## 8. Architectural Principles

Adding `binding` as an optional constructor parameter compiled every call
site unchanged and broke eight plugin tests that emit IL against the
exact seven-parameter constructor signature — not a broken test, but the
canary for a platform that loads plugin assemblies it did not compile
(`ADR-0111`). Binary compatibility with that trust boundary is preserved
by keeping the constructor untouched and adding `Binding` as an init
accessor instead.

## 9. Benefits

Core 2893/2893 in Debug and Release, 0 warnings / 0 errors at
`TreatWarningsAsErrors=true`. 48 new tests. 10 mutations designed, 10
killed. Preserved and asserted: `ICommand`, `ICommandHandler`,
`ICommandDispatcher`, `CommandHandlerTable`, `CommandResult`, every
exception type, `ADR-0111` trust ordering, `CreateDefault`, and
`InvokeAsync(id, ct)` including its exceptions and its documented refusal
to consult `CanExecute`.

## 10. Trade-offs

No descriptor is bound yet, and no surface is changed — that is
deliberately deferred to Stage 3. This stage is Core-only, so it closes
nothing a user can observe on its own.

## 11. Common Mistakes

Adding a new capability as an optional constructor parameter without
checking whether anything outside the codebase emits IL against the exact
constructor signature — plugin assemblies compiled elsewhere do exactly
that, and the eight broken plugin tests were the canary that caught it.

## 12. Future Evolution

Stage 3 (`bb22983`) binds all 74 production descriptors against this
contract; Stage 4 (`1c38cb4`) proves the contract against those real
bindings; Stage 5 (`e72b933`) makes the Palette, Ribbon and Macro Manager
actually consume it.

## 13. Key Takeaways

- An additive extension already anticipated in the architecture document
  should be implemented as that document describes, not redesigned at the
  point of implementation.
- Check whether a new optional member breaks binary compatibility with
  anything that emits IL against a type's exact shape, before assuming
  "optional" means "safe" — plugin assemblies are exactly this kind of
  external consumer.
- Three outcomes, not two: a declined prompt is not a failure, and
  collapsing the distinction would misreport every cancelled command as
  an error.
