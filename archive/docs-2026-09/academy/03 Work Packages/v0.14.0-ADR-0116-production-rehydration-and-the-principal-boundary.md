# Production Rehydration and the Principal Boundary

## 1. Introduction

`671a18b` closed `TD-103` and `TD-104`, implementing `ADR-0116`: two
defects with one shape — the product worked because the sample harness
happened to ship. A pre-`v0.14.0` engineering-body-of-work row; produced
the companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/40-production-rehydration-and-the-
principal-boundary.md`.

## 2. Purpose

To make production rehydration and session-principal resolution work
without any dependency on `Tempest.Samples`, which `TD-75` was already
converging on deleting.

## 3. Background

Twelve engineering Kinds — Risk, Task, Decision, Supplier, Milestone and
the rest — were registered for rehydration only by
`SampleEngineeringObjectRehydrators`, inside `Tempest.Samples`. A build of
TempestOS without the samples could persist one of these and never read
it back. Separately, the desktop shell established no principal at all —
the only callers of `EstablishCurrentPrincipal` in the whole product were
sample modules, during their own initialisation, so a real launch ran as
whichever sample happened to initialise last, or as nobody.

## 4. The Problem

Auditing the first turned up nine more types registered nowhere at all —
Approval, Assumption, EngineeringAction, Hazard, Issue, Review,
Simulation, Test and Verification — each creatable, each silently
discarded on the next launch, the loss recorded as a Warning in a log with
no reader. Found by reflecting over every `EngineeringObjectBase`
implementing `IRehydratable<T>` rather than auditing the registration
list, which can only ever agree with itself.

## 5. The Design (`ADR-0116`)

All 21 canonical Kinds are declared and registered by
`Tempest.App.Workspace.CanonicalObjectKinds` — one more caller of `TD-85`'s
single rehydration boundary, not a second mechanism. They are not
distributed into the discipline registries, because those classes document
their constants as "the Kind this registry can construct" and none of
these can be constructed there.
`SampleEngineeringObjectRehydrators` is deleted; an unknown Kind is now an
Error and a toast in the running shell rather than a silent Warning. The
proof is the absence of a dependency, not the presence of a behaviour:
`Tempest.Samples` is loaded in the test process, so every behavioural
round-trip test would pass just as happily if the product still leaned on
it — `ProductionRegistration_UsesNoTypeFromTempestSamples` asserts the
thing itself. `ISessionPrincipalSource` is the one place the application
decides who is using it: `WorkspaceHost` resolves it at start-up and
publishes it into the accessor every consumer already reads — no username
threaded through call sites, no user field on any engineering object, and
two standing tests assert the absence. The boundary publishes its answer
including null: the first implementation guarded against that, which
reads as ordinary defensive care, and the acceptance test then failed
with a sample module's principal standing in a session that should have
had none — `TD-103` wearing a fix.

## 6. Alternatives Considered

Distributing the twelve/nine rehydrators into the discipline registries —
implicitly rejected: those registries' own documented contracts declare
which Kinds they can construct, and none of these Kinds belong there.

## 7. Why This Solution Was Chosen

Because proving the absence of a dependency requires asserting the
dependency itself, not merely running the behaviour that dependency would
also satisfy — a lesson the row states directly and which the mutation
result (below) confirms was not a theoretical concern.

## 8. Architectural Principles

A boundary that decides "who is using this application" should be exactly
one place, resolved once and read everywhere through one accessor — not
authentication, and two standing tests assert that distinction explicitly.

## 9. Benefits

Core 2748/2748, Desktop 310/310, Debug and Release, 0 warnings, 0 errors.
Seven mutations run, seven killed — Mutation M4 restores the null-guard
and is killed, confirming the guard's removal (publishing the answer
including null) was the correct fix rather than an oversight.

## 10. Trade-offs

`TD-75` stays partially resolved: `Tempest.App` still project-references
`Tempest.Samples`, so sample modules still ship and still show — stated
plainly rather than folded into a closure that would have overstated it.

## 11. Common Mistakes

Auditing a registration *list* to check completeness, which can only ever
agree with itself — the nine additionally-missing Kinds were found only
by reflecting over the types that actually implement `IRehydratable<T>`
and comparing against what is registered, not by re-reading the
registration code.

## 12. Future Evolution

Project Tasks, immediately after, is the first production consumer of
this row's principal boundary for assignment — reading
`ISessionPrincipalSource` rather than any ad hoc identity source.

## 13. Key Takeaways

- When proving an absence, assert the dependency itself; a behavioural
  test passes identically whether or not the dependency is still loaded
  in the test process.
- Audit completeness against the types that actually implement a
  contract, not against a registration list that can only confirm itself.
- A boundary should publish its true answer, including a negative one
  (null); guarding against null "defensively" can silently reintroduce
  the exact defect the boundary exists to prevent.
