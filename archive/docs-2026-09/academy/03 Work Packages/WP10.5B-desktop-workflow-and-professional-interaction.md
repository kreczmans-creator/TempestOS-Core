# `WP 10.5B` — Desktop Workflow & Professional Interaction

## 1. Introduction

`v0.10.0`'s own eleventh Work Package — professional workflow
interactions across `Tempest.Desktop`: a unified, four-dialog Dialog
Framework, real window-geometry persistence with a graceful-shutdown
gate, a real end-to-end object-creation workflow, the Notification
Framework's own first real Desktop consumer, professional error
handling, and real user-facing settings — while changing zero
Engineering Domain, Runtime, or Workspace-contract behaviour.

## 2. Purpose

Implementation retrospective, mirroring `WP10.5A`'s own two-part
(Concept Guide, Implementation Retrospective) structure. See
`29-desktop-workflow-and-professional-interaction.md` for the design
narrative; this file focuses on what was built, files touched, and
honest disclosure of this Work Package's own two genuine findings.

## 3. Background

Commissioned directly after `WP 10.5A` (Workspace Visual Polish &
Engineering User Experience) closed with "await Product Owner
instruction before `WP 10.5B`." This Work Package's own controlling
instruction named an exceptionally broad scope — a full Dialog
Framework (fourteen named dialog kinds), Professional Window Behaviour,
Workspace Workflow, a Notification Framework, User Settings, Recent
Activity, Professional Error Handling, and general User Experience
polish — explicitly requiring any genuine architectural finding to be
documented rather than silently implemented, and explicitly stating the
objective was "to improve how users interact with the application
rather than introducing new engineering capability."

## 4. The Problem

See `29-desktop-workflow-and-professional-interaction.md` §4 — before
this Work Package, exactly one dialog existed (`ConfirmationDialog`,
`WP 10.5A`), no window-geometry persistence existed at all, Delete
executed immediately with zero confirmation anywhere, and a whole-
repository search confirmed `IPlatformNotification` — real, working,
already publishing — had zero consumers anywhere in `Tempest.Desktop`.

## 5. The Design

See `29-desktop-workflow-and-professional-interaction.md` §5. In
summary: `InputDialog`/`MessageDialog` (both new) join
`ConfirmationDialog`/`SettingsDialog` (new) as the complete Dialog
Framework, sharing tokens directly rather than a common base class;
`WindowUiState` (new) persists window geometry with a real
`ClampToVisibleScreen` multi-monitor safety net; `MainWindow.Closing`
is a single, consolidated graceful-shutdown gate (unsaved-work prompt,
then persistence, then real close); `RibbonView.ObjectCreationHandlers`
(new) wires one real, complete, end-to-end Mechanical Create/Duplicate
workflow; `PlatformNotificationToastBridge` (new) gives
`IPlatformNotification` its first real Desktop consumer;
`UserSettings` (new) gives the platform its first real, separate
user-preferences surface. Two genuine defects found and fixed before
commit — see §12.

## 12. Future Evolution

See `29-desktop-workflow-and-professional-interaction.md` §12
(`FCR-0073`–`FCR-0077`).

**Two genuine, disclosed findings, both fixed before commit:**

1. **`ProjectExplorerView`'s own `TextChanged` reliability gap** — a
   real, pre-existing (since `WP 10.2A`) shipped-code issue: the filter
   `TextBox`'s `TextChanged` routed event does not reliably fire for a
   purely programmatic `.Text =` assignment, the identical finding
   `ObjectEditorView` (`WP 10.3A`) already established for its own
   fields. Found while building and testing Recent Searches (clearing
   the filter is a programmatic assignment). Fixed at the real source:
   `_filter` now uses `PropertyChanged`, filtered to
   `TextBox.TextProperty` — a genuine reliability improvement to
   already-shipped filtering code, not merely a test workaround.
2. **A test-precision gap, confirmed by two related discoveries** —
   this Work Package's own new Delete-Confirmation tests initially
   asserted a deleted object becomes unreachable via
   `Repository.FindAsync`; incorrect, since `IDeletable.DeleteAsync` is
   a deliberate, correct, pre-existing soft delete
   (`IsDeleted` flag only). Separately, the generic "first object node
   found" test helper could non-deterministically land on the sample
   data's own root Project object (which genuinely has children, so
   `DeleteAsync` correctly throws), a `TD-27`-class risk. Both fixed:
   the assertion corrected, and a dedicated leaf-node finder added for
   the Delete-specific tests. Production code was always correct in
   both cases — only the tests were wrong.

## 13. Key Takeaways

A near-whole-application "workflow" instruction — fourteen dialog
kinds, a dozen window/workflow behaviours, a full Notification
Framework, User Settings, Recent Activity, Professional Error Handling
— was met with a real, unified four-dialog framework and one genuinely
complete, tested, end-to-end object-creation workflow, rather than a
shallow pass across every named item. Every deliberate scope reduction
(Copy/Move/Export/Import, the other five disciplines' Create/Duplicate,
a startup splash, keyboard-shortcut/Ribbon customisation) is disclosed
directly as new Future Capability Register entries, never silently
narrowed. Two genuine findings — one a real, pre-existing UI reliability
gap in shipped code, one a test-precision correction touching this
Work Package's own new tests — were both found and fixed at their true
source before commit, neither merely disclosed and left open.

## Observations

**The same "found only because a required verification discipline was
followed seriously" pattern this session's own Observations sections
have now named six times (`WP 10.3B`, `WP 10.4A`, `WP 10.5A` twice)
recurs again, and once more crosses a Work Package boundary — this
time forward, not backward.** `ObjectEditorView`'s own `TextChanged`
lesson (`WP 10.3A`) sat unapplied to `ProjectExplorerView`'s own,
structurally identical filter field for two Work Packages' worth of
git history, until this Work Package's own Recent Searches feature
happened to need a programmatic `.Text =` assignment and surfaced the
identical gap independently. A lesson learned once, in one file, does
not automatically propagate to a structurally identical field in
another file — it takes either a deliberate sweep or, as happened here,
a fresh feature that exercises the exact same code path.

**The soft-delete/leaf-node finding is this session's own fourth
recorded instance of `TD-27`'s exact non-determinism risk class**
(`InMemoryEngineeringObjectRepository`'s own unspecified
`ConcurrentDictionary` iteration order), after `WP 10.4A`'s own `TD-32`
test and `WP 10.5A`'s discovery of it. A single, well-understood,
long-disclosed platform characteristic keeps producing new instances of
the same test-authoring mistake across unrelated Work Packages — worth
noting plainly here as a recurring cost, even though each individual
instance remains a correctly-fixed test issue, not a production defect.
