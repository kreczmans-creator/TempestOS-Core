# WP 13.2A — Plugin Trust & Capability Enforcement Implementation

## 1. Introduction

This Work Package implements `ADR-0110`, `ADR-0111`, and `ADR-0112` exactly
as `WP 13.0A` designed and `WP 13.0B` independently verified them —
capability-scoped plugin trust enforcement, a component-principal
capability model built on `ADR-0044`'s existing `IPermissionEvaluator`, and
a detached SHA-256 manifest-and-assembly signature verified at Plugin
Discovery, before any `Assembly.LoadFrom` call. It runs on
`feature/v0.13.0`, `v0.13.0` — "Trust & Deployment Hardening" — directly
following `WP 13.1A`/`WP 13.1B` (the mechanical, non-trust half of the same
plugin platform work, `ADR-0107`–`ADR-0109`), which both left `TD-09`,
`TD-10`, and `TD-11` deliberately untouched, exactly as scoped.

Where `WP 13.1A` built the plugin pipeline's *shape* (dependency
resolution, the Plugin Registry, configuration), this Work Package builds
the plugin pipeline's *trust* — the retrofit `ADR-0044` itself anticipated
when it declined to extend `IPermissionEvaluator` into
`NavigationService.Unregister`, Command/Navigation registration, or plugin
loading back at `WP 6.1`, naming that retrofit as scoped future work.

## 2. Purpose

To build the code `ADR-0110`, `ADR-0111`, and `ADR-0112` already, formally,
ratified — and only that code, with zero architectural deviation. This
Work Package's own commissioning instruction was explicit on that point:
implement the three ADRs as designed; a genuine, unanticipated either/or
ambiguity encountered during implementation would warrant a fresh ADR, but
none was found (see §6, Alternatives Considered).

## 3. Background

`TD-09` ("no isolation boundary exists between a loaded plugin and a
first-party module"), `TD-10` (`NavigationService.Unregister` performs no
ownership check), and `TD-11` (Command/Navigation registration-order
squatting) were each named explicitly as security debt going back to `WP
5.0S`/`WP 5.1A`'s own Security Reviews, and each remained genuinely open
through `v0.11.0` and `v0.12.0` — correctly so, since no real third-party
plugin commitment existed yet to justify building the retrofit ahead of
need (`Security Principles.md` Principle 7). `WP 13.0A` designed the
retrofit in full once that commitment fired; `WP 13.0B` audited that design
and found it sound. `WP 13.1A`/`WP 13.1B` then built and reviewed the
mechanical half of the same architecture package, deliberately leaving the
trust half for this Work Package, its own still-unassigned successor at
the time.

`ADR-0110` decided *where* the isolation boundary lives (capability-scoped,
in-process enforcement — not a separate `AssemblyLoadContext`, which is not
a genuine privilege boundary in modern .NET, and not process separation,
disproportionate to the disclosed threat of vetted, signed, commercial
plugins). `ADR-0111` decided *what the capability model is made of* — a
second, `AsyncLocal<T>`-backed ambient identity axis
(`ICurrentComponentAccessor`, distinct from `ADR-0044`'s user-scoped
`ICurrentPrincipalAccessor`), reusing `Permission`/`IPrincipal`/`IIdentity`/
`IPermissionEvaluator` exactly as they already exist, plus a trust-ordered
registration rule replacing unconditional "first registration wins."
`ADR-0112` decided *how a plugin earns a trust tier* — a detached SHA-256
signature over the manifest (minus its own `Signature` field) and the
assembly bytes, RSA-PSS/SHA-256, verified against a local, flat-file
`TrustedPublishers/` certificate store, entirely within the existing Plugin
Discovery phase boundary `ADR-0026` already established.

## 4. The Problem

1. **Does a plugin's declared `RequestedCapabilities` actually gate what it
   can do**, checked against its assigned trust tier's ceiling at Plugin
   Loading, and does a plugin module's own constructor get reflected over
   for conformance against a fixed always-allowed baseline plus its own
   granted `plugin.services.resolve:*` declarations — closing the
   DI-container-trust half of `TD-09` without a DI resolution interceptor?
2. **Does the new `ICurrentComponentAccessor` correctly answer "which
   component's own code is currently executing," nesting correctly across
   cross-component calls and reverting the instant control returns to the
   plugin's own caller** — the genuinely different question `ADR-0044`'s
   ambient, non-call-chain-scoped `ICurrentPrincipalAccessor` was never
   designed to answer?
3. **Does trust-ordered registration replace unconditional "first wins" at
   every registry `ADR-0111` named** — `NavigationService.Register`/
   `Unregister`, `CommandHandlerTable.Register`,
   `CommandRegistry.RegisterDescriptor` — with zero behavioural change for
   every actor that exists today (every one of them First-Party)?
4. **Does signature verification happen entirely from file bytes, before
   any `Assembly.LoadFrom` call**, correctly distinguishing an honestly
   absent signature (category 16, gated by `Plugins:AllowUnsignedLoad`,
   safe-default-false) from a present-but-broken one (category 15, never
   downgraded to Unsigned-Local)?
5. **Does the existing, pre-`WP 13.2A` regression suite still pass, once
   updated for the one genuinely load-bearing behavioural consequence of
   implementing `ADR-0112` faithfully** — every DI container in this
   codebase requires every constructor parameter type to be independently
   resolvable, so `ICurrentComponentAccessor`/`IPermissionEvaluator` must be
   dual-registered in every test fixture that constructs `NavigationService`/
   `CommandRegistry`/`CommandHandlerTable`/`EventBus` directly, and every
   pre-existing plugin-discovery test fixture whose manifest carries no
   `Signature` field must now explicitly opt into
   `allowUnsignedLoad: true`, or be isolated at category 16 by design?

## 5. The Design

**Trust tier assignment — `PluginManifestDiscoveryService.AssignTrustTier`,
entirely within Phase 3.1.** Once a candidate's fields already parse and
validate, its declared `Signature` (if any) is checked: no field present
resolves to `PluginTrustTier.UnsignedLocal` only if the constructor-supplied
`allowUnsignedLoad` flag is `true`, otherwise it throws
`PluginUnsignedLoadNotAllowedException` (category 16); a present value is
parsed via `PluginSignatureEnvelope.TryParse`, resolved against the
optional `IPluginTrustStore`, and cryptographically checked via
`PluginSignatureVerifier` (RSA-PSS/SHA-256, `SHA-256(canonical manifest
JSON minus Signature) ++ SHA-256(assembly bytes)`) — a parse failure and a
cryptographic verification failure are treated identically, both throwing
`PluginSignatureVerificationFailedException` (category 15), never
downgraded to Unsigned-Local. All of this runs against bytes already on
disk (`File.ReadAllBytes`), never via `Assembly.LoadFrom` — Discovery
remains side-effect-free per `ADR-0026`. `PluginManifest` gained a new,
required trailing constructor parameter, `PluginTrustTier trustTier` — a
manifest never declares its own tier; a plugin that fails either check
never reaches the `PluginManifest` constructor at all, which is why
`PluginTrustTier` itself carries exactly three members (`UnsignedLocal`,
`VerifiedSigned`, `FirstParty`), not four — "Rejected" is a Discovery/
Loading isolation outcome, never a runtime tier a live process observes.

**Capability enforcement — `PluginAssemblyLoader.EnforceTrust`, still
within the existing Plugin Loading try/catch, no new phase.** After a
plugin's assembly successfully loads, two static checks run before it is
ever recorded `Loaded`: every `RequestedCapabilities` entry is checked
against `PluginManifest.TrustTier`'s own ceiling (`UnsignedLocal` is
clamped to a fixed two-key ceiling — `plugin.navigation.register`,
`plugin.commands.register` — regardless of what it requests); every
discovered `IModule` implementer's public constructors are reflected over
for conformance against a fixed always-allowed baseline (`ILogger`,
`IConfigurationProvider`, `IDiagnosticsProvider`) plus the plugin's own
granted `plugin.services.resolve:<FullTypeName>` declarations. Either
failure throws `PluginTrustDeniedException` (category 17) — the assembly
remains loaded in the process (unloading it is not possible, `ADR-0015`),
but the plugin is recorded `PluginRegistryState.TrustDenied`, the sixth
registry state, not `Loaded`, and excluded from the loader's returned list.
A plugin that passes both checks has its component principal
(`PlatformPrincipal`, reusing `IPrincipal`/`IIdentity` directly — no new
principal type, per `ADR-0111`'s own explicit rejection of that
alternative) constructed once and recorded into the optional
`IPluginComponentPrincipalRecorder`, keyed per discovered `IModule` `Type`.

**The component-scope accessor — `ICurrentComponentAccessor`/
`CurrentComponentAccessor`, `AsyncLocal<T>`-backed, mirroring
`ICurrentPrincipalAccessor`'s exact shape.** `TempestHost` constructs one
instance ahead of Plugin Discovery and dual-registers it into the
`ServiceCollection` — once under its own concrete type (`EventBus`'s
constructor needs the concrete type to call `BeginScope`), once under the
interface (`NavigationService`/`CommandRegistry`/`CommandHandlerTable` only
need the read-only `Current` property) — the identical dual-registration
pattern `CurrentPrincipalAccessor` already established. `TempestServiceProvider`
resolves every constructor parameter lazily, at first resolution, not at
`Singleton<>` registration time, so no reordering of any existing
registration line was needed. `ModuleLifecycleManager` gained one new,
optional, fully generic constructor parameter —
`Func<string, IDisposable?>? componentScopeProvider` — carrying no
reference to `Tempest.Core.Plugins`/`Tempest.Core.Identity` at all;
`TempestHost` is the only caller that supplies a non-null closure, looking
up a module Id's owning component principal in
`PluginComponentPrincipalRegistry` and pushing/popping it around each
lifecycle call (`InitialiseAsync`/`StartAsync`/`StopAsync`/`DisposeAsync`),
inside the same `try`/`using` block already responsible for that call, so a
thrown exception still correctly pops the scope before the existing
`catch` logic runs.

**Trust-ordered registration — one additive owner-tracking dictionary per
registry, not a rewrite.** `NavigationService` gained a second,
lock-guarded `Dictionary<string, IPrincipal?>` tracking each item's owning
component principal alongside the existing `_itemsById`, maintained in
lockstep at every mutation. `Register`: a non-null registrant must hold
`plugin.navigation.register` (`RequirePermission`, throwing
`PermissionDeniedException`, uncaught, isolated by
`ModuleLifecycleManager`'s existing per-module isolation exactly like any
other module-thrown exception); a contested Id is resolved by
`PluginTrustPermission.Rank` — a higher-tier registrant evicts and replaces
a lower one, logged loudly at `Warning`, never silently; an equal-or-lower
registrant is rejected exactly as today (`DuplicateNavigationItemException`).
`Unregister`: a `null`/First-Party caller (`PluginTrustPermission.IsFirstParty`)
proceeds unconditionally — the check is *skipped*, not merely satisfied,
for every actor that exists today; a non-first-party caller removing its
own item proceeds; removing someone else's requires the reserved
`navigation.unregister.any` permission, held by no principal this Work
Package's capability-grant logic ever grants, so it always denies — with
one deliberate exception to the "null collaborator reproduces today's
behaviour" rule used everywhere else in this file: if `permissionEvaluator`
itself is unwired (`null`), a mismatched-ownership removal is still denied,
not silently allowed, since resurrecting that gap is exactly `TD-10`. The
identical shape (contested-Id eviction by rank, ownership-checked removal)
is applied to `CommandHandlerTable.Register`/`CommandRegistry.RegisterDescriptor`.
`IEventBus.PublishAsync` gained one `RequirePermission` call against
`plugin.events.publish:<FullTypeName>`, skipped identically for `null`/
First-Party publishers.

## 6. Alternatives Considered

None — genuinely, for the same reason `WP 13.1A` recorded none: this Work
Package implements `ADR-0110`, `ADR-0111`, and `ADR-0112` exactly as each
already, formally, ratified them, and no new design tension requiring a
fresh alternative arose during implementation. Every "should X or Y"
question this Work Package's own code answers was already decided at the
architecture stage and independently re-verified sound by `WP 13.0B`'s own
audit. The one implementation-level judgment genuinely exercised —
resolving the safe-default question for `Plugins:AllowUnsignedLoad` when
the configuration key is absent or fails to parse as a boolean — was not a
fresh either/or the architecture had left open; `ADR-0112`'s own
tier-assignment table already names `false` as the default explicitly. No
sibling workstream disclosed encountering a genuine, unanticipated
ambiguity the architecture had not already settled.

## 7. Why This Solution Was Chosen

Because, as with `WP 13.1A`, there was only one solution to choose — the
already-Accepted ADRs, independently re-verified by `WP 13.0B`'s own audit
before this Work Package began. Two implementation-stage details are worth
naming plainly, both direct, mechanical consequences of the ratified design
rather than new decisions:

**The dual-registration consequence was foreseeable, not a defect.** This
platform's minimal, custom DI container (`ADR-0005`) requires every
constructor parameter type to be independently resolvable — it has no
implicit "resolve the concrete type if the interface isn't registered"
fallback. Once `NavigationService`, `CommandRegistry`, `CommandHandlerTable`,
and `EventBus` each gained new, optional `ICurrentComponentAccessor`/
`IPermissionEvaluator` constructor parameters, every pre-existing test
fixture that constructs one of those four types directly — rather than
through the full `TempestHost` composition root — needed updating to
dual-register `ICurrentComponentAccessor` (interface and concrete type,
mirroring `TempestHost`'s own new registration pattern) alongside
`IPermissionEvaluator`. Twenty-three pre-existing fixtures needed this
update: five direct-construction test files
(`HostedServiceManagerTests.cs`, `CommandDispatcherTests.cs`,
`CommandRegistryTests.cs`, `EventBusTests.cs`,
`NavigationServiceTests.cs`) plus eighteen `Samples/*SampleModuleIntegrationTests.cs`
files that each independently construct a small `ServiceCollection` for
their own module-pipeline integration test. None of the four types'
existing, non-trust constructor parameters changed shape — every new
parameter is optional and trailing, reproducing today's exact behaviour
when unresolved — so no fixture needed anything beyond the two additional
registration lines.

**The `PluginManifestV2FieldsTests.cs` placeholder-signature finding is
this Work Package's own clearest evidence the design closes a real gap, not
merely a test-authoring nuisance.** Two of that file's pre-existing tests
had, since `WP 13.0A`/`WP 13.1A`, asserted a `Signature` field containing a
literal placeholder string (`"base64-looking-opaque-blob=="`) round-tripped
verbatim through `PluginManifestDiscoveryService` — correct at the time,
since `ADR-0112` had not yet been implemented and `Signature` was, as
`ADR-0112`'s own Context section states, "read, not interpreted." Once this
Work Package implements `AssignTrustTier`, a declared `Signature` is
actively parsed as a verification envelope and cryptographically checked —
the placeholder string now correctly fails envelope parsing (category 15)
rather than round-tripping, exactly the behaviour `ADR-0112` specifies. The
fixture was corrected by removing the placeholder `Signature` fragment
entirely (that test's own remaining concern is
`Dependencies`/`RequestedCapabilities`/`Publisher` parsing, not signature
shape, which `PluginSignatureVerifierTests.cs` — a new, dedicated file, 15
test methods — now covers directly) and passing
`allowUnsignedLoad: true` to take the deliberate unsigned path instead.
This is not a defect this Work Package introduced; it is the intended,
disclosed consequence of a field that used to be stored-only becoming
actively verified.

## 8. Architectural Principles

- **Reuse Before Invention** — no new principal type (`PlatformPrincipal`
  reused directly); no new permission type (`Permission`, namespaced
  `plugin.*`); no new NuGet dependency (`System.Security.Cryptography` is
  already part of .NET); `ICurrentComponentAccessor` mirrors
  `ICurrentPrincipalAccessor`'s exact shape rather than inventing a
  differently-structured second axis.
- **Fail Closed, Not Fail Open** — `Plugins:AllowUnsignedLoad` absent or
  unparseable resolves to `false`, the safe default `ADR-0112`'s own
  tier-assignment table names explicitly; a `Signature` that fails to parse
  or fails cryptographic verification is never downgraded to
  Unsigned-Local, treated as tampering, not absence.
- **Fail Fast, Isolate, Don't Crash — extended to two new failure
  categories.** Categories 15–18 all isolate the one affected plugin,
  never the Host; category 17 (trust-tier/constructor-conformance denial)
  is recorded `PluginRegistryState.TrustDenied`, the sixth registry state,
  rather than overloading the general-purpose `Failed`.
- **Zero Behavioural Change for Every Existing Actor** — every new
  permission check is skipped, not merely satisfied, when the ambient
  component principal is `null` or First-Party; every registrant that
  exists today is First-Party, so every existing Navigation/Command
  registration call behaves identically to before this Work Package.
- **Host-Owned Collaborators Remain Structurally Unreachable** —
  `PluginTrustStore`, `PluginComponentPrincipalRegistry`, and
  `CurrentComponentAccessor`'s own concrete type are all Host-constructed;
  none of the three is ever added to the DI `ServiceCollection` as
  DI-public in a way a module could resolve and mutate — mirroring
  `PluginRegistry`'s own established `ADR-0017` boundary.
- **Do Not Redesign Approved Architecture Absent a Genuine Defect** — every
  addition is additive to an existing type or table (`PluginManifest`
  gained one trailing constructor parameter; `PluginRegistryState` gained
  one enum member; `ADR-0025`'s failure table gained categories 15–18);
  nothing already-Accepted was restructured.

## 9. Benefits

- **`TD-09`, `TD-10`, and `TD-11` are genuinely resolved**, not merely
  re-designed — a loaded plugin's capabilities are now checked at Plugin
  Loading against its trust tier, its module constructors are checked
  against a real, reflected conformance rule, `NavigationService.Unregister`
  now performs a real ownership check, and Command/Navigation registration
  now uses trust-tier priority instead of unconditional first-registration-wins.
- **Signature verification is real, working code** — `ADR-0112`'s detached
  SHA-256 scheme, RSA-PSS/SHA-256, verified entirely from file bytes before
  any `Assembly.LoadFrom` call, confirmed directly by
  `PluginSignatureVerifierTests.cs`'s own 15 new test methods.
- **Zero behavioural change to every pre-existing First-Party actor** —
  confirmed directly: every one of the twenty-three updated test fixtures
  needed only additive registration lines, never a changed assertion about
  first-party behaviour.
- **`Plugin Register.md`'s own "Not Yet Applicable" status remains
  correctly unaffected** — `src/Plugins/` remains empty; this Work Package
  implements enforcement infrastructure, not a real shipped plugin.
- **The trust/capability enforcement retrofit `ADR-0044` itself
  anticipated back at `WP 6.1` is now closed**, the last of the three
  deferred retrofit targets that ADR named explicitly.

## 10. Trade-offs

- **Not a hard sandbox, exactly as `ADR-0110` discloses plainly.** A
  sufficiently determined plugin could, in principle, use reflection to
  reach past a `RequirePermission` call site. This Work Package closes the
  ordinary, cooperative API surface `TD-09`/`TD-10`/`TD-11`/`CMD-1`
  actually named — it does not, and was never designed to, defend against
  an actively adversarial assembly willing to bypass its own declared
  trust.
- **No revocation checking.** A compromised publisher key remains trusted
  until an operator manually removes its `.cer` file from
  `TrustedPublishers/` — disclosed explicitly by `ADR-0112`, unchanged by
  this Work Package's own implementation of that design.
- **`Plugins:AllowUnsignedLoad` remains a single, global switch** — an
  operator enabling it for one legitimately-unsigned internal tool permits
  every other unsigned candidate in the Plugins folder to load under the
  same clamped Unsigned-Local ceiling. A per-plugin allow-list remains
  purely additive future work, not attempted here.
- **No real, non-synthetic plugin exercises this enforcement path in
  production** — every test proving this Work Package's own pipeline still
  exercises dynamically-built, in-memory assemblies
  (`DynamicPluginAssemblyBuilder`, extended this Work Package with
  `BuildPluginAssemblyWithConstructorParameters` for the constructor-
  conformance check specifically) and RSA test key pairs
  (`PluginSigningTestHelper`), not a hand-authored, shipped example.
  `src/Plugins/` remains empty.

## 11. Common Mistakes

1. **Assuming a pre-`WP 13.2A` plugin-discovery test fixture with no
   `Signature` field needs no change.** It does, by design: `ADR-0112`'s
   own tier-assignment table isolates an unsigned candidate at category 16
   unless `allowUnsignedLoad: true` is passed explicitly — the
   `PluginManifestDiscoveryService` test constructor's own default
   reproduces today's *safe* default, not today's *permissive* one. A test
   asserting a candidate reaches `Loaded`/a valid `PluginManifest` must now
   pass `allowUnsignedLoad: true` if its fixture manifest carries no
   `Signature`.
2. **Assuming a placeholder `Signature` string can still round-trip
   verbatim through discovery.** It cannot, once `AssignTrustTier` is
   wired in — a `Signature` value is now actively parsed as a JSON
   envelope and cryptographically checked, not merely stored and forwarded.
   A test wanting to exercise `Signature`-adjacent manifest fields without
   exercising verification itself should omit the field and pass
   `allowUnsignedLoad: true`, exactly as `PluginManifestV2FieldsTests.cs`
   was corrected to do (see §7).
3. **Assuming `NavigationService`/`CommandRegistry`/`CommandHandlerTable`/
   `EventBus` can still be constructed directly in a test with only their
   pre-`WP 13.2A` constructor arguments and reach code paths that touch the
   new trust checks.** Every new trust-related constructor parameter is
   optional and defaults to reproducing today's behaviour for a `null`
   collaborator — a fixture that never registers
   `ICurrentComponentAccessor`/`IPermissionEvaluator` and never establishes
   a non-null component scope will simply never exercise the new checks at
   all, which is correct for a test uninterested in trust behaviour, but
   is easy to mistake for "the trust checks aren't wired up."

## 12. Future Evolution

- **A real, non-synthetic signed plugin** — the natural next real-world
  trigger for this Work Package's own machinery, mirroring `WP 13.1A`'s
  identical, still-unmet trigger for the mechanical pipeline: the first
  real, hand-authored, shipped plugin, signed and loaded against a real
  `TrustedPublishers/` entry, not a dynamically-built in-memory assembly
  and a test-generated key pair.
- **Certificate chains, revocation checking, a marketplace, remote trust
  services, a REST API, authentication, authorisation beyond plugin
  capabilities, dynamic trust changes, and live plugin reload** all remain
  exactly as out of scope as `ADR-0110`–`ADR-0112` and this Work Package's
  own commissioning named them — none was implemented, none is a silent
  gap; each remains a genuinely separate, future trigger-gated decision,
  not a default assumed here.
- **A per-plugin `AllowUnsignedLoad` allow-list**, replacing the current
  single global switch, if a real operator need for finer granularity ever
  emerges — `ADR-0112`'s own Consequences section already names this as
  purely additive future work.

## 13. Key Takeaways

- Implementing an already-fully-ratified, independently-audited
  architecture is, once again, a real and valuable kind of Work Package in
  its own right, and one this project has now performed twice in
  succession within the same release (`WP 13.1A` for the mechanical half,
  this Work Package for the trust half) with the identical "zero new ADR
  warranted" outcome both times, confirmed directly rather than assumed.
- A capability model's real implementation cost is rarely in the
  capability-checking logic itself — it is in every pre-existing
  constructor-injection call site the new, optional collaborator now
  touches. Twenty-three test fixtures needing a two-line dual-registration
  update is the direct, foreseeable shape of "every constructor parameter
  must be independently resolvable," not a defect of either the DI
  container or this Work Package's own design.
- A field that used to be "read, not interpreted" becoming actively
  verified is exactly the kind of change that turns a previously-correct
  test fixture into one that now encodes a stale assumption — the
  `PluginManifestV2FieldsTests.cs` placeholder-signature finding is this
  Work Package's own clearest, most concrete evidence that `ADR-0112`'s
  signature verification is real, functioning code, not a shape-only
  extension that happens to compile.
- "Architecture only, no code changes," "the mechanical half is now real,
  built code," and "the trust half is now real, built code" are three
  genuinely separate, separately-verifiable claims this release has now
  made in sequence (`WP 13.0A`, `WP 13.1A`, this Work Package) — each one
  closing the gap its predecessor named, none silently assuming the
  previous claim covered more ground than it actually did.
