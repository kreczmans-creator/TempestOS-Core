# Project Tasks — the First Real Project-Management Surface

## 1. Introduction

`007aec2` gave `EngineeringTask`, `EngineeringAction`, `Milestone` and
`Deliverable` — real, compiled, persistable domain types for several
releases — a workflow, a surface and a place in a project for the first
time, implementing `ADR-0117`. A pre-`v0.14.0` engineering-body-of-work
row; produced the companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/41-project-tasks-and-delivery-
workflow.md`.

## 2. Purpose

To close the Tasks project area, the last one still honestly marked
Declared with genuine domain objects behind it — a workflow to give an
existing model, not a modelling exercise.

## 3. Background

`TaskWorkState` needed a status vocabulary a finished task could reopen
from, which the canonical lifecycle forbids: `Released → Draft` is
correctly barred everywhere else, because a released drawing must not
silently become a draft again, and weakening that rule platform-wide to
serve one family would have been the wrong trade.

## 4. The Problem

A task's status is not the same kind of thing as an engineering object's
lifecycle state, and treating it as one would have either broken the
lifecycle's own protection or made a finished task permanently
unreopenable.

## 5. The Design

`TaskWorkState` implements `IFamilySpecificState` — a contract the
platform had declared and never used — with its own transition table that
permits reopening, mapped onto the canonical lifecycle so anything
reasoning across the domain still gets one answer per Kind. Cancelled
counts as finished, not open: an abandoned task is not outstanding work,
and counting it as such would make every open-task figure slowly become a
lie. Work state, priority, due date and a mutable assignee live on
`EngineeringTask` itself, captured and rehydrated through the production
path `ADR-0116` established. Project membership is the parent chain, for
the third time: documents join transitively (`TD-102`), requirements join
on the allocation link (`TD-102`), tasks join the same way — no
`ProjectId` field added, which would be a third answer to a question the
platform already answers twice. Assignment reads the `ADR-0116` principal
boundary; unassigned stays a first-class state. The surface is an
ordinary `TD-72` panel — no reserved slot — and raises intent while the
shell decides, offering only the moves the transition table actually
permits.

## 6. Alternatives Considered

Weakening the canonical lifecycle's `Released → Draft` prohibition to let
a task be reopened directly — rejected: it would protect released
engineering data less broadly across the whole platform to serve one
family's need.

## 7. Why This Solution Was Chosen

Because `IFamilySpecificState` was already declared for exactly this
shape of problem — a family that needs its own transitions while staying
mapped to one canonical lifecycle for anything that reasons across Kinds
— and using it here is the first real proof the contract works.

## 8. Architectural Principles

A family with genuinely different workflow needs gets its own state
machine mapped onto the canonical lifecycle, rather than either forcing
it into the canonical rules or letting it bypass them entirely.

## 9. Benefits

Core 2773/2773, Desktop 319/319, Debug and Release, 0 warnings, 0 errors.
Thirteen mutations run, thirteen killed. The most useful test result was
a mutation that survived first: making `ChangeWorkStateAsync` skip its
persist call broke nothing, because every assertion read the in-memory
object it had just changed, which cannot distinguish saved from set on
this instance — closed by a test that reads back what the state store
actually holds.

## 10. Trade-offs

`TD-81` is only partially resolved, and the row now lists what remains
item by item: Commercial, Resources, Knowledge, Administration,
Gantt/Timeline and managed Milestone surfaces are untouched. No Gantt, no
scheduling engine, no resource planning, no task dependencies, no
swimlanes.

## 11. Common Mistakes

Asserting only against the in-memory object a mutation just changed,
which cannot distinguish "the change was persisted" from "the change was
merely set on this instance" — the exact gap the surviving mutation here
exposed, fixed by reading back from the actual state store.

## 12. Future Evolution

Project Risks, Issues & Decisions and Project Timeline, both later in
this release, reuse the identical shape this row establishes —
`IFamilySpecificState` mapped onto the canonical lifecycle, membership via
the parent chain, no `ProjectId` field — rather than each inventing its
own pattern.

## 13. Key Takeaways

- A family with different workflow needs than the canonical lifecycle
  should get its own mapped state machine (`IFamilySpecificState`), not a
  weakened canonical rule or a bypass.
- Derive project membership from the domain's existing parent chain for
  every new surface, rather than adding a redundant field each time.
- An assertion against an in-memory object cannot prove persistence — read
  back from the actual store to catch a dropped write.
