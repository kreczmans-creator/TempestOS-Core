# WP 15.1B — v0.15.0 Release Readiness Review

## 1. Introduction

`WP 15.1B` (`32abf64`) is an independent review of
`feature/v0.15.0-release-prep` (`WP 15.1A`, `d2f1fae`) against `main`
(`a417ade`). The full evidentiary account — every re-run build and
test, every register independently re-derived — is its own dedicated
report, not repeated here: `docs/releases/v0.15.0/WP15.1B v0.15.0
Release Readiness Report.md`. This article is written retroactively,
under `WP 16.2B` (`v0.16.0`'s Academy retrospective backfill), for the
same reason `WP 15.1A`'s own retrospective is: Engineering Governance
§6 requires one per Work Package regardless of subject matter.

## 2. Purpose

Independently re-verify `WP 15.1A`'s own deliverable before recommending
`v0.15.0` for tagging — re-run every build, test, and governance check
fresh, and re-derive scope directly from git rather than trusting
`WP 15.1A`'s own count.

## 3. Background

Commissioned as the second, independent reviewing pass this project's
own established convention requires before a release recommendation is
trusted (the `WP 9.9.0` second-pass, `WP 12.9.2` precedent). `WP 15.1A`'s
own report explicitly left tagging, merging, and publication outside its
scope, for a reviewer to approve.

## 4. The Problem

`WP 15.1A`'s own `WorkPackages.md` accounted for only nineteen of the
`v0.14.0..main` range's twenty commits. The missing commit, `b755685`
("WP-Z4 Stage 24: close the v0.14.0 release record"), falls inside the
range because the `v0.14.0` tag points to `026ed7c` (the PR #5 merge
commit) rather than `main`'s own tip at the time the tag object was
created (tagger date 2026-09-03 08:56:07 UTC vs. `b755685`'s own commit
time, 09:32:18 UTC) — a real accuracy defect in a document whose entire
premise is a complete, git-derived inventory.

## 5. The Design

Re-ran `git log --oneline v0.14.0..a417ade` directly (twenty commits,
confirmed) and `git diff --name-only main..feature/v0.15.0-release-prep`
(exactly the fourteen files `WP 15.1A`'s own commit claims — no `src/`,
no `tests/`, no unrelated file). Corrected `WorkPackages.md` in place to
name `b755685` explicitly and explain both why it appears in the range
and why it is properly excluded from `v0.15.0`'s own scope — `v0.14.0`'s
own release-closure work catching up with itself, not new `v0.15.0`
material. Re-ran both builds, all four test/configuration combinations,
and the governance health check fresh rather than carrying forward
`WP 15.1A`'s own claims.

## 6. Alternatives Considered

Silently folding `b755685` into the `v0.15.0` count as an unremarked
twentieth Work Package commit — rejected: it is `v0.14.0`'s own
release-closure work, and disguising that would misrepresent both
releases' own history, the same failure mode `WP 11.5A`'s own
retrospective had already named for a different register.

## 7. Why This Solution Was Chosen

Correcting the gap in place, with the reasoning stated in the document
itself, keeps `WorkPackages.md`'s own "twenty commits, completely
accounted for" claim honest without rewriting `WP 15.1A`'s own report or
commit message — those are left as the historical record of what that
Work Package actually did.

## 8. Architectural Principles

No production code, ADR, or architecture was touched — an independent
readiness review verifies and, where a real documentation gap is found,
corrects the record; it does not design.

## 9. Benefits

`v0.15.0`'s own accounting is now genuinely complete
(1 + 4 + 4 + 7 + 2 + 2 = 20, matching the git-derived total). Every
dimension `WP 15.1A` itself reported — registers, both builds, all four
test/configuration runs, the governance health check, real CI — is
independently re-confirmed rather than merely repeated, including real
CI for the exact reviewed commit (`d2f1fae`, run `33861940494`) rather
than only `main`'s own tip.

## 10. Trade-offs

The remaining open items `WP 15.1A` already disclosed — `v0.11.0`'s
missing retrospectives, `Academy Register.md`'s own deeper per-article
backfill, the unresolved `FCR-0092` origin — were re-confirmed as real
and non-blocking, and deliberately not expanded into this review's own
scope.

## 11. Common Mistakes

**Treating a `git log` range boundary as a work boundary.** `b755685`
lands inside `v0.14.0..main` purely because of when the tag *object*
was created relative to when the commit landed on `main`, not because
of when the work was actually done — a distinction the range's own
literal commit count could not, by itself, reveal.

## 12. Future Evolution

This retrospective was written retroactively, more than a year after
`WP 15.1B` itself, under `WP 16.2B` — the Academy retrospective
backfill Work Package of the `v0.16.0` programme, whose own governing
v1.0 scope decision is `D-021` (proposed, `WP 16.0A`). Per `WP-Z3`'s own
established precedent, a retrospective written after the fact is the
cost of the gap it closes, not a full substitute for one written
alongside the work.

## 13. Key Takeaways

- An independent second pass earns its keep by re-deriving evidence
  directly, not by re-reading the first pass's own report.
- A `git log` commit range and a Work Package's own scope are not the
  same boundary — a tag's creation time relative to `main`'s own tip
  can put an unrelated commit inside an otherwise clean range.
- Correcting a discovered gap in place, with the reasoning left
  visible, is preferable to silently rewriting the document that
  contained it.
