# WP 12.4B — Desktop Command & Event Wiring Implementation

## What This Document Is

The implementation-phase retrospective for `WP 12.4B`, a third
directly-commissioned `v0.12.0` Work Package, on the same branch as
`WP 12.4A` (`feature/v0.12.0-desktop-command-event-wiring`). Realises
`ADR-0104` exactly as approved: consolidates the report-then-refresh
duplication `WP 12.4A` quantified, and closes `WP 12.0B`'s own
architecture review Finding 5 (a two-phase `Attach` pattern used where a
plain delegate would have sufficed). Refactor only — zero public API
changes, zero behavioural changes, verified by characterization tests
written before the refactor and re-run, unchanged, after it.

## 1. Introduction

`WP 12.4A` investigated the Desktop layer's own command/event wiring
after `WP 12.0B`'s decomposition and produced two outputs: `ADR-0104`
(direct delegates by default; typed callback interfaces only at three or
more genuinely bundled callbacks; a Desktop-local Mediator, Command
Dispatcher, and Event Dispatcher each explicitly rejected) and a
quantified finding — a four-statement "report via StatusBar/Toast, then
refresh Explorer/Cockpit" tail repeated 42/25/25/19 times (by individual
statement) across six files, concentrated in
`RibbonObjectActionHandlers` (16 of its own ~29 handlers) and
`WorkspaceViewCoordinator` — named as a real implementation-hygiene
opportunity for a future Work Package, deliberately not designed in full
by `WP 12.4A` itself. This Work Package is that follow-up: implement
`ADR-0104` exactly, add any characterization tests coverage was missing
before touching production code, and leave every public API and every
observable behaviour unchanged.

## 2. What Was Built

### 2.1 Characterization tests, added before any refactor

Three new `[AvaloniaFact]` tests added to
`FeatureCompletionTests.cs`, targeting two real, confirmed-by-direct-search
coverage gaps rather than blanket re-testing of all ~29 Ribbon handlers:

- **`MechanicalCreate_OnARealPart_ActuallyCreatesARealObject`** and
  **`MechanicalDuplicate_OnARealPart_ActuallyCreatesARealCopy`** — the
  entire Mechanical discipline had zero direct Ribbon-handler test
  coverage anywhere in the suite, despite being the two oldest handlers
  in the file (`WP 10.5B`). Dispatches the real `mechanical.create`/
  `mechanical.duplicate` handlers through real `InputDialog`/
  `ConfirmationDialog` interaction (`RaiseEvent(new RoutedEventArgs(Button.ClickEvent))`),
  asserting against the real domain repository.
- **`DocumentsApprove_OnAFreshDraftDocument_IsRejectedByRealValidation_NeverThrows`**
  — the shared `statusHandler` factory (13 of the 16 report-then-refresh
  sites) had only ever been exercised on its success path; its own
  failure branch (report `result.Message`, skip the Explorer/Cockpit
  refresh) had never been tested. Dispatches `documents.approve`
  directly against a fresh Draft document (an invalid Draft→Approved
  transition), asserting no exception is thrown, the document's own
  `LifecycleState` is unchanged, and the StatusBar does not contain the
  success-path text — a genuine, previously-untested code path made
  real.

**One genuine finding during test authoring, disclosed and fixed
directly**: the first version of `MechanicalCreate`'s own assertion
walked the Project Explorer's own tree looking for the newly-created
Part and failed — not a test bug in isolation, but an honest reflection
of `mechanical.create`'s own real, pre-existing scope: it dispatches
`CreateMechanicalObjectCommand("Part", name)` with no `parentId`,
producing a real, valid, but parentless object the tree (rooted at
Projects) never shows. Fixed by asserting against
`EngineeringDomainContext.Repository.ListByKindAsync("Part")` directly —
the authoritative source — rather than by changing the handler's own
behaviour, which was correct and out of this Work Package's scope to
alter. Re-run, all three tests passed against the pre-refactor code
(baseline: `Passed! Failed: 0, Passed: 3, Total: 3`), establishing the
behaviour these tests must continue to prove unchanged once the refactor
lands.

### 2.2 `RibbonObjectActionHandlers` — `ReportAsync` consolidation

All 16 occurrences of the report-then-refresh tail consolidated into one
local function, `ReportAsync(string message, bool succeeded)`, defined
inside the existing constructor and capturing `statusBar`/`toastHost`/
`explorerView`/`cockpitView` — the same constructor parameters every
handler already closed over directly. Each of the 16 call sites reduced
to one line: `await ReportAsync(<message>, result.Succeeded).ConfigureAwait(true);`.
Every handler's own success/failure message text is unchanged, character
for character. `mechanical.create`/`mechanical.duplicate` — the file's
two oldest handlers, `WP 10.5B` — previously computed their own message
twice (once via a duplicated ternary inline, effectively) and were
normalised to compute it once, matching the convention every one of the
other 14 sites already used; this is the only behavioural-shape change
in the whole file, and it changes nothing observable (the computed
string is identical either way).

This is deliberately **not** a typed callback interface: `ADR-0104`
sanctions that pattern only where a single collaborator's own
*constructor* needs three or more genuinely bundled callbacks.
`ReportAsync` adds nothing to `RibbonObjectActionHandlers`'s own
constructor signature at all — it is a private local function, the
"direct delegate... zero new abstraction" default `ADR-0104` names
first, applied at its narrowest: extracting a repeated method body
within one class, never touching how that class is constructed.

### 2.3 `WP 12.0B` Finding 5, closed — `UndoRedoCoordinator`

Previously carried a nullable `CockpitView?` field, assigned once via a
public `AttachCockpitView(CockpitView)` method called by `MainWindow`
after `CockpitView` was constructed — a two-phase-construction pattern
whose only purpose was calling `_cockpitView!.Refresh()` from
`UndoAsync`/`RedoAsync`. Replaced with a plain `Action refreshCockpit`
constructor parameter (5th, alongside the four pre-existing ones);
`AttachCockpitView` removed entirely. `MainWindow` now passes
`refreshCockpit: () => _cockpitView!.Refresh()` at construction —
reusing the exact field-closure lazy-capture pattern the codebase
already established for `_documentArea!` (a closure's own captured-field
read is evaluated at invocation time, not declaration time; safe here
because `_cockpitView` is a `readonly` field always assigned by the time
`UndoAsync`/`RedoAsync` can first run).

### 2.4 `WP 12.0B` Finding 5, closed — `WorkspaceViewCoordinator`

The identical change, applied to the collaborator `WP 12.0B`'s own
review named as the strongest remaining decomposition candidate.
Previously carried `CockpitView` through the same two-phase `Attach`
cycle `DocumentAreaView` still genuinely needs (`Attach(DocumentAreaView, CockpitView)`),
purely so its own 7 internal call sites could reach `_cockpitView!.Refresh()`.
Replaced with the identical `Action refreshCockpit` constructor
parameter (19th, alongside the 18 pre-existing ones); `Attach` narrowed
to `Attach(DocumentAreaView documentArea)` — only one genuine
construction-order cycle remains (`DocumentAreaView` needs this
collaborator's own `BuildDocumentContent`; `TabCloseRequested` needs
`DocumentAreaView` to already exist). All 7 internal `_cockpitView!.Refresh()`
call sites replaced with `_refreshCockpit()`.

**Deliberately not introduced**: a typed callback interface for this
collaborator's own constructor, despite `ADR-0104` naming this exact
class — by its 18-parameter (now 19) constructor — as the motivating
illustration for when the threshold applies. Direct inspection found
only 2 genuinely delegate-shaped constructor parameters existed before
this Work Package (`refreshStatusBar`, `recordHistory`); this Work
Package's own `refreshCockpit` addition brings the count to 3 — but
introducing the interface now, in the same change that adds the third
callback, was assessed as premature: the user's own instruction was
explicit ("introduce them only where they materially reduce constructor
complexity — do not introduce them speculatively"), and a single
class-authoring change is not, on its own, the kind of complexity
pressure the threshold is meant to answer. Left as a legitimate,
named-but-deferred opportunity for a future Work Package, not acted on
here.

### 2.5 `MainWindow.cs` — construction wiring

`UndoRedoCoordinator`'s and `WorkspaceViewCoordinator`'s own constructor
calls both gained `refreshCockpit: () => _cockpitView!.Refresh()`.
`_viewCoordinator.Attach(_documentArea, _cockpitView)` narrowed to
`_viewCoordinator.Attach(_documentArea)`. The
`_undoRedo.AttachCockpitView(_cockpitView)` line — previously the very
last construction step before docking/panel wiring — removed entirely,
since no cycle remains for it to resolve. Surrounding comments updated
to state plainly that only one genuine construction-order cycle
(`DocumentAreaView`) remains, where two existed before.

## 4. Architectural Lessons

**A local function is sometimes the correct answer to "where does this
duplication go," and recognising that requires checking whether the
consuming class's own constructor needs to change at all.** `ADR-0104`'s
own typed-callback-interface threshold answers a *constructor*
complexity question. `ReportAsync`'s duplication was a *method-body*
problem, living entirely inside handlers a single class already owned —
conflating the two would have meant inventing a callback abstraction
that solved a problem it was never asked to solve. Recognising which
kind of duplication is in front of you — statement-level vs.
constructor-parameter-level — determines which of `ADR-0104`'s two
sanctioned mechanisms applies, if either does.

**Closing WP 12.0B's Finding 5 correctly meant checking each
collaborator's own remaining cycle individually, not assuming both
resolved identically.** `UndoRedoCoordinator`'s `CockpitView` dependency
was the *only* thing its two-phase pattern existed for — removing it
left no cycle at all. `WorkspaceViewCoordinator`'s two-phase `Attach`
served two purposes at once (`DocumentAreaView` and `CockpitView`); only
one was genuine. Applying the same delegate substitution required
recognising that `DocumentAreaView`'s own cycle is real (a live
`TabCloseRequested` subscription cannot be satisfied by any delegate —
subscribing requires the object to already exist) while `CockpitView`'s
was not (nothing about `CockpitView` beyond `Refresh()` was ever used).

**A named, motivating example for a future threshold does not obligate
acting on it the moment the threshold is technically reached.** `ADR-0104`
names `WorkspaceViewCoordinator`'s own constructor by number as the
class the typed-callback-interface threshold was written for. This
Work Package's own change brought its genuine delegate-parameter count
from 2 to 3 — the threshold, on paper. Introducing the interface in the
same change that crosses the threshold would have been speculative in
exactly the sense the user's own brief warned against: the threshold
exists to answer *material* constructor complexity pressure, not to be
triggered mechanically the instant a count changes. Deferred, disclosed,
not silently skipped.

## 5. Key Takeaways

- **`ADR-0104` implemented exactly, no deviation, no factual correction
  exposed** — direct delegates used throughout; no typed callback
  interface introduced anywhere (assessed and explicitly deferred for
  `WorkspaceViewCoordinator`, not overlooked); no Desktop mediator,
  Desktop-local command dispatcher, or Desktop-local event dispatcher
  introduced; the platform Command/Event Framework untouched.
- **`WP 12.0B`'s own architecture review Finding 5 is now fully closed**
  in both collaborators it named — `UndoRedoCoordinator` and
  `WorkspaceViewCoordinator` no longer carry a `CockpitView` object
  reference or a two-phase `Attach`/`AttachCockpitView` method; only the
  one genuine `DocumentAreaView` cycle remains.
- **`ADR-0103`'s ownership rules preserved throughout** — every
  collaborator remains `new`-constructed once by `MainWindow`, never
  DI-registered, never referencing a sibling collaborator directly; the
  new `Action` parameters are values passed once at construction, the
  same pattern `ADR-0103` already establishes for `refreshStatusBar`/
  `recordHistory`.
- **Behaviour preservation was proven, not assumed** — the three
  characterization tests added before the refactor pass with identical
  assertions against both the pre- and post-refactor code, and the full
  2,248-test suite regresses cleanly in both Debug and Release.
