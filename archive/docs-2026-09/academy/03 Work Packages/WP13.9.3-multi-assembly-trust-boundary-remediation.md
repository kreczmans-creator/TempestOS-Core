# WP 13.9.3 — Multi-Assembly Trust-Boundary Remediation

## 1. Introduction

`WP 13.9.3` is a security remediation in production code. It closes, in
full, the finding `WP 13.9.2` (`v0.13.0` Readiness Re-Execution) raised
against `WP 13.9.1`'s own multi-assembly trust-boundary fix: that fix's
fixed-point scan diffed the `AppDomain` only around
`Assembly.GetTypes()`/`IsAssignableFrom`, not around the independent CLR
lazy-load trigger a discovered module's own constructor parameter types
represent. It runs on `feature/v0.13.0`, `v0.13.0` — "Trust & Deployment
Hardening"; its `WorkPackages.md` Type column reads `Implementation`.

Its scope is one method. `PluginAssemblyLoader.DiscoverModuleTypes`'s
per-step `AppDomain` diff window was widened to also cover forcing
resolution of every discovered module type's every public constructor's
every parameter's `ParameterType`. `HasCompliantConstructor` itself is
unchanged; only the point at which its own unavoidable reflection side
effects are allowed to fire moved earlier, into a window the scan can see.

Its material was committed as part of the whole chain by `WP 13.9.7`,
commit `d7d19d4` ("WP 13.9.1-13.9.6: Plugin Trust Execution Boundary
Remediation Chain", 35 files, +3,263/−90). Every claim below is grounded
in that commit's own message, this Work Package's own dense
`WorkPackages.md` row, its own retained `PROJECT_STATUS.md` stratum,
`ADR-0111`'s own "Corrected, `WP 13.9.3`" section, and direct reads of
real, current source.

**A note on this document's own provenance.** `WP 13.9.7` recorded an
explicit governance conclusion that `WP 13.9.1`–`WP 13.9.6` "do not
require new Academy retrospective files of their own," checked against
`Academy Index.md`'s own stated maintenance rule and the
`WP 13.2B`/`WP 13.9.1` precedent. This retrospective is written after the
fact and in addition to that conclusion, and is not accompanied by an
`Academy Register.md` or `Academy Index.md` entry — a real
register-currency gap, disclosed here rather than asserted closed.

## 2. Purpose

To close `WP 13.9.2`'s finding **in full** — both variants of it, and the
transitive generalisation of it — without introducing a new isolation
mechanism, without touching `ADR-0110`'s ratified boundary, and without
altering `HasCompliantConstructor`'s own conformance logic.

The distinction between "close the demonstrated PoC" and "close the
finding in full" is the substance of this Work Package. `WP 13.9.2`
demonstrated one hop; `WP 13.9.3` had to make the fixed-point traversal
correct at every hop and prove it, which is why one of its eight committed
tests is a three-assembly transitive chain rather than a repeat of the
demonstration.

## 3. Background

Three Work Packages had already touched this exact boundary:

- **`WP 13.2A`** built plugin trust enforcement to `ADR-0110`–`ADR-0112`
  as designed. `ADR-0111`'s own literal scope was "every discovered
  `IModule` implementer **in the plugin's own assembly**."
- **`WP 13.9.0`**, the first Engineering Readiness Review of `v0.13.0`,
  found and empirically demonstrated the mismatch between that scope and
  Module Discovery's — which, deliberately unchanged per `ADR-0110`, scans
  `AppDomain.CurrentDomain.GetAssemblies()`, every assembly in the
  process. A plugin's declared assembly inheriting a type from an
  undeclared sibling DLL force-loads that sibling as an unavoidable CLR
  side effect of `GetTypes()`; the sibling's own `IModule` implementer is
  never trust-checked, and its ambient component principal is `null`,
  which `PluginTrustPermission.IsFirstParty` treats as First-Party — so
  every dynamic capability check is *skipped*, not satisfied. Verdict:
  `NOT READY`.
- **`WP 13.9.1`** closed that finding by giving `DiscoverModuleTypes` a
  fixed-point, breadth-first `AppDomain`-diff scan mirroring
  `PluginManifestDiscoveryService`'s own dependency-graph idiom: diff the
  `AppDomain`'s assembly set immediately before and after each scan step,
  enqueue only what is newly present as a direct consequence of that step,
  until nothing new appears. Two properties of that design are load-bearing
  and unchanged by this Work Package: an assembly already resident for an
  unrelated reason is excluded **by construction**, and the traversal
  terminates on a visited-assembly `HashSet`.

**`WP 13.9.2`** then re-verified `WP 13.9.1`'s fix against a fresh live
proof-of-concept and found it still incomplete. That finding is this Work
Package's direct commissioning trigger.

## 4. The Problem

`Assembly.GetTypes()` is not the only reflection call in a plugin's own
trust evaluation capable of lazily loading a referenced assembly.

Resolving a constructor parameter's `ParameterType` — which
`HasCompliantConstructor` does for every discovered module type, in a
later, separate pass — is an equally unavoidable CLR load trigger, and it
happens **strictly after `DiscoverModuleTypes` has already returned**. It
is therefore invisible to the before/after diff, by construction: the scan
had closed its fixed point and handed control back before the load ever
occurred.

Two exploit shapes follow, and the second is the more severe:

1. **The direct case.** A plugin module references a type from a second,
   undeclared assembly *only* from a constructor parameter — never from a
   base type. The non-compliant constructor still force-loads the
   referenced assembly. The module itself is correctly denied on
   conformance — but the newly resident assembly's own, separately
   discoverable `IModule` types were never vetted, and Module Discovery,
   deliberately plugin-unaware, will find them.
2. **The alternate-compliant-constructor case.** The same module *also*
   declares an alternate, individually-compliant constructor. Now the
   module is not merely leaking an assembly — it **passes**
   `HasCompliantConstructor` and the plugin is accepted outright.

The critical property making the second case unavoidable rather than
incidental is a fact about the reflection API itself, recorded verbatim in
`ADR-0111`'s own corrected Decision text and in
`PluginAssemblyLoader.cs`'s own inline documentation:
`Type.GetConstructors()` **resolves every returned constructor's own full
parameter signature regardless of declaration order or which one
ultimately proves compliant**. There is no ordering, no short-circuit and
no lazy path that avoids the load. It is not a defect that
`HasCompliantConstructor` could have been coded around — the load is a
consequence of asking the question at all.

That framing is what makes the fix's shape inevitable, and §5 follows
directly from it.

## 5. The Design

**One change, in one method.** `DiscoverModuleTypes`'s fixed-point scan was
widened so that each step's own `AppDomain` diff is taken around forcing
resolution of every discovered module type's every public constructor's
every parameter's `ParameterType`, not only around
`GetTypes()`/`IsAssignableFrom`.

The resolution is forced **unconditionally** — not only for the parameters
`HasCompliantConstructor`'s own short-circuiting `.All()`/early-return
would happen to touch. Confirmed directly in current source, where the
`WP 13.9.3` rationale is recorded inline at the loop: *"force every
discovered type's every public constructor's every parameter's
`ParameterType` to resolve now, inside this scan step — unconditionally,
not only the ones `HasCompliantConstructor`'s own short-circuiting
`.All()`/return would happen to touch — so any assembly this pulls in is
captured by this step's own before/after diff, not invisible to it.
`HasCompliantConstructor` itself remains unchanged; its own reflection
side effects simply have nowhere new left to hide by the time it runs."*

That last clause is the whole design. The fix does not add a check. It
moves *when* an existing, unavoidable side effect is permitted to fire,
from outside the instrumented window to inside it — so any assembly it
pulls in is captured exactly like any other transitively-loaded one, and a
later iteration of the same fixed-point loop discovers and trust-checks
**its** module types too. Generalisation to arbitrary depth is free,
because it is the same loop.

**Explicitly unchanged, and named as unchanged in every source:**
`HasCompliantConstructor` itself; the fixed-point traversal's termination
guarantee (the visited-assembly `HashSet`); the before/after diff's
by-construction exclusion of assemblies already resident for unrelated
reasons; and `ADR-0110`'s isolation boundary — **no new isolation
mechanism, no `AssemblyLoadContext`, no process separation**. This widens
the existing capability-scoped enforcement mechanism's coverage only.

**Tests.** New file
`tests/Tempest.Core.Tests/Plugins/PluginAssemblyLoaderMultiAssemblyTrustTests.cs`,
which this Work Package's own row and `PROJECT_STATUS.md` stratum both
describe as containing **8 tests**, covering four named scenarios:

- the direct case (a non-compliant constructor referencing an external
  assembly, denied, with the secondary module never principaled);
- the alternate-compliant-constructor case — the more severe variant
  `WP 13.9.2` found — asserted still denied, "not silently accepted via
  other overload";
- a three-assembly transitive constructor-parameter chain, with the
  offending module in the *third* assembly, proving the fix generalises
  beyond one hop;
- a benign multi-assembly-with-granted-capability case, proving no
  legitimate plugin regresses.

One new `DynamicPluginAssemblyBuilder.cs` builder method,
`BuildPrimaryPluginAssemblyWithExternalConstructorParameter`.

**A test-count discrepancy in the record, disclosed not resolved.** Three
sources cannot all be read literally at once. `WP 13.9.1`'s
`PROJECT_STATUS.md` stratum states that Work Package created
`PluginAssemblyLoaderMultiAssemblyTrustTests.cs` as "a dedicated
regression suite... 3 tests"; `WP 13.9.3`'s own row calls it a "**New
file**... (8 tests)"; and `WP 13.9.4`'s row states that Work Package added
"new tests in... `PluginAssemblyLoaderMultiAssemblyTrustTests.cs`" as
well. The file as committed at `d7d19d4` contains exactly **8** test
methods, and four of them correspond one-to-one with the four scenarios
`WP 13.9.3`'s own row names. The most consistent reading is that "8 tests"
describes the file's committed state rather than this Work Package's own
additions, and that the file was created by `WP 13.9.1` and extended by
both `WP 13.9.3` and `WP 13.9.4` before any of it was committed — but the
sources do not say so, and this retrospective does not assert it as fact.
No per-Work-Package test count for this file is independently verifiable
from the repository, because the whole chain landed in one commit.

**Documentation.** `ADR-0111` gained a "Corrected, `WP 13.9.3`
Multi-Assembly Trust-Boundary Remediation" Status-section note and
Decision-text amendment — confirmed present in current source. Its
substance: every scan step's own "examining an assembly" now explicitly
means forcing resolution of **both** base-type chains **and** constructor
parameter types, with the `AppDomain` diffed around both, not `GetTypes()`
alone. `Plugin Trust & Isolation Architecture.md`'s Risks section carries
the full before/after account.

## 6. Alternatives Considered

- **Changing `HasCompliantConstructor` to avoid or defer the load.** Not
  taken, and foreclosed by the API rather than by preference:
  `Type.GetConstructors()` resolves every constructor's full parameter
  signature regardless of order or eventual verdict, so there is no
  ordering or short-circuit that avoids the resolution. The record is
  emphatic that `HasCompliantConstructor` is unchanged.
- **Re-scanning the whole `AppDomain` after conformance checking, rather
  than widening the per-step diff.** Not taken. It would have broken the
  property that makes the diff sound — assemblies already resident for
  unrelated reasons are excluded *by construction*, which a
  post-hoc whole-domain scan cannot preserve; and it would have separated
  discovery from the fixed point that guarantees transitive closure.
- **Introducing an `AssemblyLoadContext` or process separation.** Named as
  not taken in all three of this Work Package's own records. `ADR-0110`
  decided that question on its own merits — capability-scoped, in-process
  enforcement, because an `AssemblyLoadContext` is not a genuine privilege
  boundary in modern .NET and process separation is disproportionate to
  the disclosed threat model of vetted, signed, commercial plugins. A
  remediation is not the place to reopen a ratified decision.
- **Closing only the demonstrated one-hop case.** Not taken; the
  three-assembly transitive test exists specifically to prove it was not.

**The record is silent** on whether further alternatives were weighed
inside this Work Package. No Rejected Designs entry was raised by it, and
it produced no standalone report file.

## 7. Why This Solution Was Chosen

**Because the smallest correct fix was a scheduling change, not a logic
change.** The conformance logic was never wrong. The instrumented window
was too narrow. Moving an unavoidable side effect inside the window that
already existed to catch such effects is a strictly smaller intervention
than adding a second mechanism to catch it afterwards — and it inherits
the existing mechanism's correctness argument (fixed-point termination,
by-construction exclusion of pre-resident assemblies) unchanged.

**Because "unconditionally" is the load-bearing word.** Forcing resolution
only where `HasCompliantConstructor` would have looked would have
reproduced the bug in a subtler form: the short-circuiting `.All()` means
which parameters get touched depends on which constructor happens to fail
first, so the set of assemblies pulled into the diff window would vary
with declaration order. Unconditional resolution makes the scan's coverage
a property of the *type*, not of the evaluation order.

**Because the fixed point does the generalisation for free.** Once a
constructor-parameter-loaded assembly is captured by a step's diff, it is
enqueued and scanned like any other, and its own module types'
constructors are resolved inside *their* step's diff. The three-assembly
transitive test is not a separate feature; it is a proof that the existing
loop was the right place to put the change.

**Because `ADR-0111` had to be corrected, not merely satisfied.** The
Decision text asserted a scope ("the plugin's own assembly") the code no
longer implements — and would have been left describing a narrower
boundary than the code enforces. The "Corrected, `WP 13.9.3`" section
brings the ratified text into line with the shipped mechanism, rather than
leaving a reader to infer the difference. This is the second of what
eventually became five such corrections to `ADR-0111`
(`WP 13.9.1`/`WP 13.9.3`/`WP 13.9.4`/`WP 13.9.6`/`WP 13.10B`).

## 8. Architectural Principles

- **Instrument the window, then make sure everything happens inside it.**
  The correct response to "an effect fires where we cannot see it" is to
  move the effect, not to build a second observer.
- **Coverage must not depend on evaluation order.** Unconditional
  resolution over short-circuiting resolution, deliberately.
- **Widen an existing mechanism; do not add a new one.** Recorded
  identically in the commit message, the `WorkPackages.md` row and the
  `PROJECT_STATUS.md` stratum: no new isolation mechanism, no
  `AssemblyLoadContext`, no process separation.
- **`ADR-0110`'s "Module Discovery is plugin-unaware" is a decision to be
  worked with.** Trust enforcement's reach is pulled up to match Module
  Discovery's; Module Discovery is not taught about plugins.
- **A ratified Decision that the code has outgrown gets corrected in
  place, with attribution.** `ADR-0111` carries a named, dated correction
  per remediation rather than a silently rewritten Decision.
- **Prove the generalisation, not just the instance.** A one-hop fix
  verified by a one-hop test is exactly what `WP 13.9.2` had already
  disproved once.

## 9. Benefits

- Both variants `WP 13.9.2` demonstrated are closed, including the severe
  one where the plugin was previously **accepted outright** via an
  alternate compliant constructor.
- The scan now captures both of its own two reflection touchpoints instead
  of one — the completeness argument that was short by one entry is now
  explicitly enumerated in `ADR-0111`'s corrected Decision text, so a
  future reader inherits the enumeration rather than having to rediscover
  it.
- Transitive depth is covered and proven, not assumed: the offending
  module in the three-assembly test sits in the *third* assembly.
- Legitimate multi-assembly plugins are proven not to regress — the benign
  granted-capability case is a committed test, not an assertion.
- `HasCompliantConstructor` is untouched, so the `WP 13.2B`
  `NeverEligibleServiceResolveTypes` denylist and every other conformance
  rule keep their existing, separately-reviewed behaviour and test
  coverage.
- The widened scan became the substrate later Work Packages corrected in
  place rather than replaced: `WP 13.9.4` made it run unconditionally
  before both static trust checks and collect `IHostedService` types;
  `WP 13.10B` extended the same constructor-parameter loop to hosted
  service types; `WP 13.11B` changed how an unresolvable parameter type is
  reported out of it. Four extensions, no replacement.

## 10. Trade-offs

- **The fix does not, by itself, stop a denied plugin's code from
  running.** It ensures the *scan* sees every transitively-loaded
  assembly. `WP 13.9.4` subsequently found — and closed — a separate,
  more severe defect: `PluginTrustDeniedException` never actually
  prevented a denied plugin's already-loaded assembly from being
  rediscovered by Module Discovery and Hosted Service Discovery and fully
  lifecycle-run. `WP 13.9.5` then found a third defect still open in the
  combined boundary. `WP 13.9.3` closes its own finding in full; it does
  not close the boundary.
- **Unconditional resolution costs work that short-circuiting avoided.**
  Every public constructor of every discovered module type now has every
  parameter type resolved during Plugin Loading, whether or not the
  conformance check would have needed it. Justified by correctness; the
  record does not quantify the cost.
- **Forcing a CLR type-load is itself a failure surface.** At this Work
  Package the resolution was unguarded. Later Work Packages record what
  followed: `WP 13.10B` wrapped it (having first placed the `try` one
  level too deep to catch anything, since
  `RuntimeConstructorInfo.GetParameters()` eagerly resolves the signature
  in the loop header), and `WP 13.11B` reworked the resulting denial so it
  records before throwing. None of that is this Work Package's own work,
  and none of it was visible from its own finding.
- **The two mirrored type filters remain duplicated.**
  `PluginAssemblyLoader.IsModuleType` mirrors
  `ReflectionFrameworkDiscoveryService`'s `IsValidModuleType` exactly, run
  independently and earlier — a duplication `ADR-0111` already discloses
  as a risk. This Work Package inherits it and does not address it.
- **Per-Work-Package test attribution is not independently verifiable.**
  The whole chain landed in one commit; the "8 tests" figure and its
  division between `WP 13.9.1`/`WP 13.9.3`/`WP 13.9.4` can only be read
  from prose. See §5.

## 11. Common Mistakes

1. **Believing this Work Package introduced the multi-assembly scan.** It
   did not. `WP 13.9.1` built the fixed-point, breadth-first
   `AppDomain`-diff scan, mirroring `PluginManifestDiscoveryService`'s own
   idiom. `WP 13.9.3` widened *where* the diff is taken.
2. **Believing it changed `HasCompliantConstructor`.** All three sources
   state it is unchanged. Only the point at which its unavoidable side
   effects fire moved.
3. **Assuming a short-circuiting conformance check would have avoided the
   load anyway.** `Type.GetConstructors()` resolves every returned
   constructor's full parameter signature regardless of order or verdict.
   This is why the alternate-compliant-constructor variant exists at all.
4. **Treating the fix as an isolation improvement.** It is a coverage
   improvement to an existing capability-scoped mechanism. `ADR-0110`'s
   boundary — no `AssemblyLoadContext`, no process separation — is
   untouched, and every source says so explicitly.
5. **Reading the three-assembly test as belt-and-braces.** It is the
   proof that the fix lives inside the fixed-point loop and therefore
   generalises; without it, the Work Package would have closed a
   demonstration rather than a finding.
6. **Concluding the trust boundary was sound at this Work Package's
   close.** It was not. `WP 13.9.4` and `WP 13.9.6` each closed further
   distinct defects in the same boundary within the same chain.

## 12. Future Evolution

- **`WP 13.9.4`** — the trust-denial execution boundary, a separate and
  more severe defect found immediately after this one, closed with the
  `IPluginDeniedTypeRecorder`/`IPluginDeniedTypeRegistry` pair and filters
  in `TempestHost`.
- **`WP 13.9.5`/`WP 13.9.6`** — an adversarial review of the combined
  `WP 13.9.3`+`WP 13.9.4` boundary, which found the boundary defensible
  for its own literal claims but surfaced a third distinct bug
  (`ReflectionFrameworkDiscoveryService.CreateDescriptor` calling
  `Activator.CreateInstance` before any filter was consulted), closed by
  `WP 13.9.6`.
- **`WP 13.10B` and `WP 13.11B`** subsequently corrected this very loop
  again — extending it to hosted service types, guarding the type-load,
  and routing an unresolvable-parameter denial through `EnforceTrust` so
  it records before throwing. `ADR-0111` accumulated a further "Corrected"
  section for `WP 13.10B`.
- **The `ADR-0111` duplication risk** — `PluginAssemblyLoader`'s mirrored
  `IsModuleType`/`IsHostedServiceType` filters — remains open and
  disclosed.

## 13. Key Takeaways

- When an unavoidable side effect fires outside your instrumented window,
  move the side effect, not the window's owner. The whole fix is
  scheduling: `HasCompliantConstructor`'s reflection "simply has nowhere
  new left to hide by the time it runs."
- Short-circuiting is a correctness hazard when the *act of asking* has
  side effects. Making resolution unconditional turns scan coverage into
  a property of the type rather than of evaluation order.
- Putting a fix inside an existing fixed-point loop buys transitive
  generalisation for nothing — and the way to prove you got that for free
  is a test at depth three, not a repeat of the reported case at depth
  one.
- A ratified ADR whose Decision text the code has outgrown must be
  corrected with attribution, in place. `ADR-0111` now carries five dated,
  named corrections; a reader can reconstruct exactly which Work Package
  widened which claim, and why.
- Closing a finding in full is not the same as closing a boundary. This
  Work Package did the first, completely, and the chain needed three more
  Work Packages to approach the second.
