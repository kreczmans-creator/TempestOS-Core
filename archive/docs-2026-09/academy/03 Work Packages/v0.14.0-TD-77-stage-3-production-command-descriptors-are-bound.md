# TD-77 Stage 3 — Production Command Descriptors Are Bound

## 1. Introduction

`bb22983`, the second of four `TD-77` stages, binds all 74 production
discipline descriptors against Stage 2's Core contract — declaring what
each command is, instead of leaving a caller to guess from an absence. A
pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To give every real command descriptor either a working binding or an
explicit, named reason it cannot be invoked yet, so nothing falls through
to a generic "isn't available yet" message.

## 3. Background

Stage 2 built the contract; nothing used it yet. 56 of the 74 commands
carry a real binding, a hand-written lambda closing over the same
constructor the handler registered beside it already expects. 18 carry an
explicit reason: 15 need a destination/target object and no object picker
exists (`FCR-0073`); 3 need structured or binary input the platform's
text-only prompt cannot collect.

## 4. The Problem

Two of the 74 commands — `requirements.delete-group` and
`requirements.revise` — were permanently unreachable through the
pre-existing Ribbon dispatch, because its Id-parsing fell through on
"delete-group" not being "delete" and "revise" not being "edit". That is
not a hypothetical risk this stage disclosed; it is a real defect the
binding work found by naming every command's actual requirement.

## 5. The Design

Nothing about the existing surfaces moves — no descriptor gains a
`CreateDefault`, so neither the Command Palette nor the Macro Manager
changes behaviour yet; that is Stage 5. Macro eligibility is not a new
flag: a command can run unattended exactly when it needs neither a value
nor a confirmation, which is what `CommandBinding.RequiresPrompt` already
answers — landing on precisely the audited fourteen (the thirteen status
transitions plus `mechanical.validate-configuration`), since every delete
and duplicate carries a confirmation that keeps it off the list. Kind
scopes are the disciplines' own already-declared constants, never
widened — Calculations excludes the synthetic "CalculationTemplate" Kind
exactly as its existing Rename/Delete/Revise factories already do.
Validation is preserved from both places it already lived: the Ribbon's
own 200-character limit and non-blank rules, and the command constructors
themselves, which throw on a blank name — that second source is not
optional, since a throw out of `Build` is a defect in the binding, so a
constructor that rejects blank input now rejects it as a value first.

## 6. Alternatives Considered

None recorded beyond the binding work itself — each of the 74 commands
had one direct answer (a working binding, or a named unavailability
reason), with no design choice left open once the requirement was stated.

## 7. Why This Solution Was Chosen

Because naming the reason a command cannot be bound, rather than leaving
it to fall through to a generic message, is what a Command Framework
contract should provide — and doing so for all 74 at once, rather than
incrementally, is what let the `requirements.delete-group`/`revise` defect
surface at all.

## 8. Architectural Principles

A command's macro eligibility and its validation rules should derive from
what the command's own contract already declares (`RequiresPrompt`, the
constructor's own blank-name check), not from a second, independently
maintained list that could drift from the first.

## 9. Benefits

118 new tests against the real composition root — the same
`RegisterEngineeringDisciplines` call the console entry point and the
Desktop shell both make — including a source-level guard that a future
descriptor cannot be added with neither a binding nor a reason. Six
mutations designed, six killed.

## 10. Trade-offs

Kind scopes and unavailability reasons are pinned as decisions in this
stage, not as bugs to fix — `Move`/`Copy`/`Link` are disabled with their
declared reasons rather than looking available until a click fails, but
they remain unavailable until `FCR-0073` (an object picker) exists.

## 11. Common Mistakes

Leaving a command's macro eligibility as a separately maintained flag
rather than deriving it from the binding's own `RequiresPrompt` — a
second list invites drift the moment either changes independently.

## 12. Future Evolution

Stage 4 (`1c38cb4`) proves this stage's 74 bindings against the Core
contract exhaustively; Stage 5 (`e72b933`) is what actually makes the
Ribbon, Palette and Macro Manager consume these bindings, at which point
`requirements.delete-group` and `requirements.revise` become reachable
for the first time.

## 13. Key Takeaways

- Requiring every descriptor to declare either a binding or a reason
  surfaces real gaps (two permanently-unreachable commands) that a
  partial pass would have missed.
- Derive a command's eligibility for unattended execution from its own
  declared contract, not a second independently maintained list.
- A validation rule that exists in two places (a UI-layer limit and a
  constructor-level throw) both need to be preserved, since either one
  alone leaves a gap the other was covering.
