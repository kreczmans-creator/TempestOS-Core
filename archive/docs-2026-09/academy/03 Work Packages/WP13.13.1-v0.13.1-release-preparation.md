# WP 13.13.1 — v0.13.1 Release Preparation

## 1. Introduction

`WP 13.13.1` prepares `v0.13.1`, the corrected and publishable form of
`v0.13.0`'s content, on a dedicated branch `release/v0.13.1` cut from
`main` at `ea3fe07`. It bumps `VERSION`, authors the release notes, and
brings the release and governance registers up to date. It touches no
production code, no existing test, and — critically — nothing belonging
to `v0.13.0`.

## 2. Purpose

To make `v0.13.0`'s content publishable without violating tag
immutability. `v0.13.0` was genuinely tagged and merged, but its
tag-triggered `release.yml` run failed before packaging, so no GitHub
Release or asset was ever produced. A new version is the only permitted
remedy.

## 3. Background

`WP 13.12.7` pushed the `v0.13.0` tag; `release.yml` run `32146823154`
failed at `Test (Release)` on a single Desktop test. `WP 13.12.8`
diagnosed it as a genuine intermittent flake — a fixed `Task.Delay(50)`
racing a real disk-write chain, the `TD-46` idiom — and `WP 13.12.9`
remediated it test-only. `WP 13.12.10` recorded `v0.13.0`'s true state in
the Release Register. `WP 13.13.0` then determined the disposition:
leave `v0.13.0` as a valid but unpublished historical tag, and proceed
with `v0.13.1`.

## 4. The Problem

Three constraints intersect, and only one path satisfies all of them.

`Engineering Governance` **§7.4** forbids moving or recreating a pushed
tag. **`WP 11.4B`'s tag-position exception cannot be borrowed**: it is
bounded to a tag's *mechanical position*, never to build or test
evidence, and only before the release branch closes — `main` has already
received the merge. And **rollback-forward does not apply** either: that
procedure presupposes a published Release to mark superseded and a
fallback build to download, neither of which exists.

So the fix cannot be applied to `v0.13.0`, and `v0.13.0` cannot be
re-cut. A new version is the only remaining move — which
`release.yml`'s own inline comment already names: *"the corrective action
is a new patch version and a new tag … never editing this one."*

## 5. The Design

**A dedicated release branch, not a direct push to `main`.** §7.7
requires every merge into `main` to go through a pull request gated on
`CI Gate`; §1.3 forbids implementation directly on `main`. `7449756` and
`ea3fe07` therefore travel into `main` through the `v0.13.1` PR rather
than being pushed straight there — even though `TD-45` means nothing
mechanically prevents the direct push. Availability is not permission.

**Ancestry preserved, not rewritten.** The branch is cut from `ea3fe07`,
so `6089a218` — the exact commit `v0.13.0` tags — remains in ancestry
unchanged. No rebase, no squash, no cherry-pick. The tagged tree is
reachable and intact; only the branch tip differs from it.

**Release notes that do not duplicate.** `v0.13.1`'s notes state the
supersession, preserve the distinction between the immutable historical
tag and the corrected release, describe the one test-determinism change,
and then **point to `v0.13.0`'s own release notes** for the full scope
account rather than restating twenty-eight Work Packages. Duplication
would create two documents to keep in sync, and the older one is not
wrong — only unpublished.

**A fourth Release Register status.** `v0.13.1` is recorded *In
preparation*, alongside `v0.13.0`'s *Tagged and merged — not published*.
Neither is squeezed into "Released", because neither is.

## 6. Alternatives Considered

**Delete and recreate `v0.13.0`.** Rejected — barred by §7.4, and the one
precedent (`WP 11.4B`) is explicitly out of reach here.

**Retry `release.yml` against the existing tag.** Rejected: the tag's tree
still contains the flaky test, so the run would be a coin toss, and
`WP 13.12.7`'s instruction forbade blind retry.

**Fold the correction into `v0.14.0`.** Rejected at Gate 0 by Product
Approval. It would also leave `v0.13.0`'s content permanently
unpublished.

**Push `7449756`/`ea3fe07` straight to `main` first.** Rejected — §7.7
requires a PR gated on CI, and this would have been the project's first
violation of it.

## 7. Why This Solution Was Chosen

Because it is the only option that satisfies tag immutability, the PR
gate, and the requirement that `v0.13.0`'s content actually ship. It also
keeps the historical record honest: `v0.13.0` remains in the register
with a truthful row rather than being quietly erased.

## 8. Architectural Principles

- **Tag immutability is absolute** (§7.4). A failed publish does not
  license re-cutting.
- **An exception is bounded by its own stated scope.** `WP 11.4B` was
  approved for tag position, and is not a general-purpose escape hatch.
- **Discipline over tooling.** With branch protection unenforceable
  (`TD-45`), the PR gate holds only because it is honoured.
- **Do not duplicate a document that is still correct.**
- **Record what is true**, including that a version exists which will
  never be published.

## 9. Benefits

`v0.13.0`'s content becomes publishable without any history rewrite. The
tag stays exactly where it was cut. The register carries both versions
with accurate, distinguishable statuses. And the delta between the
released tree and the tagged one is auditable in a single line: 2 files,
`+35/−5`, zero `src/`.

## 10. Trade-offs

The project now permanently carries a version number that was tagged and
never published — a small, disclosed oddity in the register forever. That
is the cost of tag immutability, and it is the cheaper cost.

`v0.13.1` also sets the project's **first non-zero patch precedent**.
`05-release-engineering.md` defines PATCH as *"a hotfix, and only a
hotfix"*, triggered by *"a confirmed defect in an already-released
version"* — read literally, neither premise fits: the delta contains no
product fix, and `v0.13.0` was never published. The spirit fits
exactly, and the version number was a Product Approval decision (§9), not
an engineering one. Recorded rather than smoothed over.

## 11. Common Mistakes

- **Reaching for a prior exception because it is nearby.** `WP 11.4B`
  looks like the obvious precedent and is the wrong one; its own report
  drew the boundary explicitly.
- **Assuming a failed publish means the release is invalid.**
  `v0.13.0`'s content passed every gate, including real CI on `main` at
  the exact pre-tag commit. Only the publication step failed.
- **Pushing to `main` because nothing stops you.** `TD-45` makes §7.7
  unenforceable; that is a reason to be more careful, not less.

## 12. Future Evolution

The remaining sequence is a PR to `main` gated on `CI Gate`, explicit
Product Approval, merge as a merge commit, real CI on `main` at the
pre-tag commit, then `new-release.ps1 -Version 0.13.1` without `-Push`,
then the tag push under separate approval.

Two items outlive this Work Package: `TD-46`'s fixed-`Task.Delay` idiom
survives in twenty-eight further `Tempest.Desktop.Tests` waits,
deliberately not generalised here; and the Academy retrospective
obligation for `WP 13.12.3`–`WP 13.13.0` remains open, disclosed by this
Work Package rather than absorbed into it.

## 13. Key Takeaways

- A pushed tag is a fact, not a draft. Plan the remedy around it.
- An approved exception is scoped by its own justification — check the
  boundary before reaching for it.
- When two releases exist and only one shipped, the register must be able
  to say so; add a status rather than overload one.
- Cutting the corrected branch from the tagged commit's descendant keeps
  the whole thing auditable in one diff.
