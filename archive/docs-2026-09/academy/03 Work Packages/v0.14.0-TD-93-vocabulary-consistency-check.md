# TD-93 — Vocabulary Consistency Check Scanned Whatever Happened to Be Loaded

## 1. Introduction

`f2600d9` fixed a real defect in `EngineeringVocabularyConsistencyTests`
itself — it reflected over `AppDomain.CurrentDomain.GetAssemblies()`,
which returns whatever the CLR happens to have loaded, not what the test
means to examine — and disclosed, rather than fixed, the deeper `TD-93`
finding the fix exposed. A pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To make the vocabulary-consistency check deterministic and to record,
honestly, the layering reason it cannot cover `Tempest.Samples`.

## 3. Background

Run `33242333283` got the build and Governance Health Check green for the
first time since an earlier commit, then failed one Desktop test in both
configurations. Locally the test failed roughly two runs in five and
never in isolation, because assemblies load lazily at first use — a run
where nothing had yet touched `Tempest.App` examined strictly fewer types
than one where something had, and neither run said which it was.

## 4. The Problem

A check that silently examines less than it claims is worse than no
check: it reports green on the runs that happened to look at less, and
red on the runs that happened to look at more, with nothing distinguishing
the two.

## 5. The Design

The scan now names the three production assemblies it covers —
`Tempest.Core`, `Tempest.App`, `Tempest.Desktop` — and force-loads each
through an anchor type, so its reach is a fact of the test rather than an
accident of ordering. A new guard test fails if that reach ever shrinks,
so the check can no longer pass by having looked at less than it claims.
`Tempest.Samples` is a disclosed exclusion: its thirteen redeclared
vocabulary values (`"calculatedBy"`, the Document and Manufacturing
classifications, and others) are real, but every canonical owner of those
values lives in `Tempest.App`, one layer above the sample assembly, which
references only `Tempest.Core` — a sample module cannot reference the
constant it would need to satisfy `ADR-0105`'s "declared once" rule
without inverting the layering.

## 6. Alternatives Considered

Moving canonical vocabulary into a layer `Tempest.Samples` can see, or
accepting sample-local duplication permanently — both named in the row as
the real fix, and both explicitly deferred as "an `ADR-0105` amendment and
its own Work Package," not something this commit could resolve.

## 7. Why This Solution Was Chosen

Because the check's own scope had never been a fact anyone could verify,
and naming it explicitly — with a guard test that fails if the reach
shrinks — is the minimal fix that makes the check trustworthy without
resolving the underlying layering question, which is a separate, larger
decision.

## 8. Architectural Principles

A check that says what it covers, and is guarded so that claim cannot
silently become false, is worth more than a check that covers more by
accident on some runs and less on others.

## 9. Benefits

Verified non-vacuous by mutation: a rogue constant planted in
`Tempest.Desktop.MainWindow` is reported by name and by canonical owner,
and the test fails. Full unfiltered suite run twice per configuration,
four consecutive full-solution runs: Desktop 260/260 every time.

## 10. Trade-offs

`TD-93` itself stays Open: the real fix — moving canonical vocabulary or
accepting the duplication permanently — is not made here, and the row
says so rather than closing on the strength of a more honest check.

## 11. Common Mistakes

Reflecting over "whatever the runtime has loaded" as a stand-in for "the
assemblies I mean to examine" — the two are the same only by accident of
test execution order, and a check built on that accident will pass and
fail unpredictably depending on what ran before it.

## 12. Future Evolution

The `ADR-0105` amendment this row names as the real fix is not picked up
elsewhere in this engineering body of work; it remains open debt for a
later release to decide.

## 13. Key Takeaways

- A test that scans "whatever is loaded" is scanning an accident of test
  order, not a defined scope.
- Name a check's coverage explicitly and guard the claim with a test, so
  the coverage cannot silently shrink.
- A disclosed exclusion with a stated architectural reason is honest;
  passing intermittently because of load order is not.
