# WP 16.5A — Accessibility Baseline

## 1. Introduction

`WP 16.5A` closed the top four gaps the 2026-08-28 independent
accessibility review found in `TD-65`: real modal behaviour for six
overlays, an `AutomationProperties.Name` pass over a named set of
icon-only buttons and watermark-only inputs, live-region announcement
for the status bar and toasts, and keyboard operability for the Digital
Thread graph. It also consumed the previously-unconsumed `FocusRing`
design tokens, fixed Cockpit health-text contrast on the light theme,
and added the `MainWindow`-level dialog-modality test `TD-83` itself
asked for. Branch `feature/v0.16.0-wp16.5a-accessibility`, cut from
`feature/v0.16.0` at `8b4c394`; commit `60d9966`, merged `494a8a4`.

This retrospective also records what a later, independent pass over the
same shipped code found: the focus ring this Work Package introduced is
invisible on the one button treatment it most needs to be visible on,
and a class of buttons its own scope never named still announces to
assistive technology as a raw .NET type name. Both are verified directly
against the source and test code below, not asserted secondhand.

## 2. Purpose

`TD-65`'s own top-four prioritisation, and `v0.16.0 Release Plan.md`
§"`WP 16.5A`", set the objective: "the dialog family behaves like
dialogs, and a screen reader can name every control." Six named
overlays needed real modal focus trapping; a named set of unnamed
controls needed `AutomationProperties.Name`; every asynchronous
feedback channel needed a live-region setting; the Digital Thread graph
needed keyboard pan/zoom/select; the already-declared `FocusRing`
tokens needed an actual consumer; and Cockpit health text needed to
clear WCAG AA's 4.5:1 floor on the light theme, up from a measured
2.04–3.91:1.

## 3. Background

`TD-65`'s own register text, written from the 2026-08-28 independent
review, is unusually specific: it names six dialogs by class, six
unnamed controls by kind, the graph's own 1.4px hit targets, and the
Cockpit's health-text contrast numerically. This specificity is what
let this Work Package scope itself to "the top four" rather than
attempting a full remediation, and what makes the retrospective's own
honest accounting possible — a register entry this precise makes it
straightforward to check, later, exactly which named items were fixed
and which were not.

## 4. The Problem

Six overlays were `IsVisible`-toggled `Border`s with no focus
trap, no focus restore, and — for `SettingsDialog`/`MacroManagerDialog`
specifically — no Escape handling and no initial focus at all. Every
asynchronous feedback channel was visual-only. The Digital Thread graph
was entirely pointer-only, and its 1.4px relationship line doubled as
its only hit target. The declared `FocusRingBrushKey`/
`FocusRingThickness` tokens existed in `ApplicationPalette`/
`DesignTokens` but were consumed by no style anywhere in the shell —
Avalonia's own `:focus-visible` pseudo-class had nothing painting it.
Cockpit health text used the same four fixed brand hues on both
themes, as low as 2.04:1 on the light theme's white surface.

## 5. The Design

**Modality (item a).** A new static helper, `Views/DialogModality.cs` —
deliberately not a shared base class, per `WP10.5B Architecture
Review.md` §2's own prior rejection of that shape — installs cyclic tab
navigation on each dialog and a capture-on-open/restore-on-close focus
handler keyed to the dialog's own `IsVisible`. `MainWindow` tracks a
modal count across all six overlays and removes the dock from Tab
navigation while any is open, restoring it at zero.
`SettingsDialog`/`MacroManagerDialog` gained Escape handling and initial
focus they previously lacked entirely.

**Naming (item b).** `AutomationProperties.SetName`, plus `ToolTip.SetTip`
where missing, on six specific controls: Toast dismiss, the graph's own
expand/collapse chevron (recomputed every rebuild to reflect the
*next* action, not the last one), the Command Palette query box, the
Macro name box, the graph search box, and the Explorer filter.

**Live regions (item c).** `AutomationProperties.SetLiveSetting`:
`Polite` on the status bar's eight value segments, set once in a
shared factory; `Assertive` on toasts specifically, because a `Polite`
setting risks a transient, auto-dismissing toast being gone before it
is ever announced.

**Graph keyboard operability (item d).** Node borders became
`Focusable` with a deterministic `TabIndex`; `+`/`-` zoom at the same
1.1× factor the pointer wheel already uses; arrow keys pan by a fixed
60px step; Enter/Space selects a focused node and, only for nodes
carrying a chevron, also toggles expansion — deliberately not also
navigating, so a keyboard user is never unexpectedly defocused from the
graph they are exploring. Every relationship line gained an invisible,
8px-wide hit-test twin, rather than thickening the visible 1.4px stroke
itself.

**Focus ring (item e).** `ChromeStyles.Install` now adds a
`:focus-visible` style per button treatment (Flat/Subtle/Primary/
Danger) plus one generic `TemplatedControl` fallback, both painting
`ApplicationPalette.FocusRingBrushKey` at `DesignTokens.FocusRingThickness`.
`FocusVisibleStyleTests.cs` drives a real `Tab` keypress through the
actual headless input pipeline — confirmed necessary, empirically, over
two more direct-seeming alternatives (`Classes.Set` throws;
`Focus(NavigationMethod.Tab)` alone sets `:focus`/`:focus-within` but
not `:focus-visible`) — and asserts the resolved `ContentPresenter.
BorderBrush` equals `BrandPalette.Brush(ApplicationPalette.FocusRingBrushKey)`.

**Contrast (item f).** Four new theme-reactive resource keys,
`HealthText{Healthy,Attention,Blocked,Unknown}BrushKey`, replace
`HealthColors.Resolve`'s fixed brand hues; light values are
hue-preserved and darkened to clear 4.5:1 against `#ffffff`, measured
directly by `HealthColorContrastTests.cs`'s own WCAG relative-luminance
implementation.

**Modality test (item g).** `MainWindowKeyboardModalityTests.cs` opens
each of the six overlays over a real, started `MainWindow`/`WorkspaceHost`,
walks `KeyboardNavigationHandler.GetNext` — confirmed by direct
reflection against the referenced Avalonia assembly to be a real,
public, static API before writing the test — up to 25 steps, and
asserts every stop stays inside the dialog.

## 6. Alternatives Considered

**A shared dialog base class for the modality fix.** Rejected, citing
`WP10.5B Architecture Review.md` §2's own prior decision against that
shape for this dialog family — a static helper applied per dialog keeps
each dialog's own construction independent while still sharing the
actual trap/restore logic.

**A `[Collection]` guard, or Fluent's own theme override, for the
focus ring.** Not directly named in the report, but the design actually
chosen — per-treatment styles winning by class-selector specificity,
plus a generic fallback that does *not* attempt to outrank Fluent's own
built-in `:focus-visible` styling on untreated controls — was checked
empirically against a plain `Button`, a `CheckBox`, and a `TextBox`
before being accepted as correctly scoped rather than silently
incomplete: none of the three show the custom ring, and the report
discloses this as a real, bounded limitation rather than papering over
it.

**Thicken the graph's visible 1.4px relationship line to make it the
hit target.** Rejected in favour of an invisible, wider twin line
sharing the same click handler — preserving the line's own visual
weight while giving it a real, separately-sized hit area.

## 7. Why This Solution Was Chosen

Each of the six items targets exactly the mechanism `TD-65`'s own
review named, verified against Avalonia's actual runtime behaviour
rather than assumed from its documentation — the report's own §2 and §3
describe two places where an initial assumption was checked directly
and found wrong or unconfirmed before being relied on (that
`:focus-visible` could be simulated directly; that the `FocusRing`
brushes might already be swapped between light and dark). That
discipline of checking rather than assuming is exactly what makes the
gap described in §10 below worth taking seriously: the same discipline,
applied one step further, would have caught it.

## 8. Architectural Principles

- **A design token declared but never consumed is not a completed
  feature** — `FocusRingBrushKey`/`FocusRingThickness` existed before
  this Work Package; nothing painted them. Declaring a token is the
  easy half of an accessibility feature; consuming it correctly is the
  half that actually matters to a user.
- **Verify a runtime assumption against the actual framework before
  building a test around it** — the report's own two empirical checks
  (§2, §3) are the right instinct, applied incompletely (see §10).
- **A contrast fix must be measured against the surface a control is
  actually drawn on**, not merely computed as an abstract ratio — the
  Cockpit health-text fix (item f) does this correctly, computing
  against the real resolved `SurfaceBackgroundBrushKey` for each theme.
  The focus-ring fix (item e) does not extend the same discipline to
  its own case — see §10.
- **A named, scoped remaining-inventory list is more valuable than a
  claim of completeness** — §5 of the original report lists six
  specific, disclosed gaps outside this Work Package's own scope. That
  same instinct, applied to the buttons actually built inside this
  Work Package's own scope, would have caught the Ribbon gap this
  retrospective names in §10.

## 9. Benefits

- `TD-83` moved to Resolved: a real `MainWindow`-level dialog-modality
  test now exists, closing the half of that row's own remedy
  `WP 16.4A`'s resize test did not.
- `TD-65` moved to Partially resolved, with its own remaining inventory
  named explicitly rather than left implicit — six concrete gaps
  (`ObjectEditorView`'s calculation input box, `LayoutTabGroupView`'s
  chrome buttons, several sub-floor hit targets, the graph mini-map, and
  drag-and-drop) that this Work Package did not touch and says so.
- Full Desktop suite grew from 412 to 452 tests (+40), all passing, 0
  warnings, 0 errors, both configurations; two real bugs in this Work
  Package's own new code (`MacroManagerDialog`'s list not being
  focusable by construction; a synthetic keypress raised on the wrong
  element for `InputDialog` specifically) were caught by this Work
  Package's own validation pass and fixed before merge — a genuine
  demonstration that the verification step did real work, not merely
  confirmed what was already assumed correct.
- Six dialogs are now genuinely modal, the graph is genuinely
  keyboard-operable, and Cockpit health text genuinely clears 4.5:1 on
  both themes, each independently measured rather than asserted.

## 10. Trade-offs — where this baseline overclaimed, found and verified directly

**The `:focus-visible` ring this Work Package introduced is painted in
`ApplicationPalette.FocusRingBrushKey`, which resolves to the exact same
brush as `BrandPalette.AccentBrushKey` — the Primary button's own
fill — in both themes.** Confirmed directly in
`src/Tempest.Desktop/Theming/ApplicationPalette.cs`: `FocusRingBrushKey`
is registered as `BrandPalette.Indigo600` in the light theme and
`BrandPalette.Cyan500` in dark. `src/Tempest.Desktop/Theming/
BrandPalette.cs` registers `AccentBrushKey` as `Solid(Indigo600)` in
light and `Solid(Cyan500)` in dark — the identical two constants, in the
identical two themes. `ChromeStyles.cs`'s own Primary treatment paints
`Avalonia.Controls.Button.BackgroundProperty` with
`Dyn(BrandPalette.AccentBrushKey)` — the button's own fill. A border
drawn in the same colour as the surface it sits on has a contrast ratio
of 1.00:1 against that surface: the focus ring `WP 16.5A` shipped is
genuinely invisible on the Primary button, in both themes, for exactly
the users the ring exists to serve.

The original report's own §3, "`FocusRing` brush assignment — checked,
not swapped," ran precisely the right check — comparing
`FocusRingBrushKey` against `AccentBrushKey` directly — and found them
matching in both themes. It treated that match as confirmation that an
earlier *suspected* swap had not happened, which is true. It did not
take the next step: asking whether a ring identical to a button's own
accent fill is a ring at all on the one treatment (`Primary`) that
*is* that fill. The check that would have caught this — computing the
ring's own contrast against the surface it is drawn on, exactly as
item f's Cockpit fix does against `SurfaceBackgroundBrushKey` — was
applied to health text and not to the focus ring, in the same Work
Package, by the same author.

**`FocusVisibleStyleTests.cs` cannot catch this, because it never
compares the ring to the surface it is drawn on.** Confirmed directly:
`ButtonTreatments_RealTabKeypress_DrawsTheFocusRing` asserts
`Assert.Equal(focusRing, presenter.BorderBrush)` — that the resolved
brush equals the *token*, for every one of the four treatments,
including Primary. It never asserts anything about that brush's
contrast against `presenter.Background`, which for the Primary
treatment is the identical brush. A test that only checks "the right
token is wired up" cannot distinguish a correctly wired, visible ring
from a correctly wired, invisible one.

**A second, independently-verified gap: Ribbon command buttons carry
no `AutomationProperties.Name` at all, and were never in this Work
Package's own scope to check.** `RibbonView.BuildCommandButton`
(`src/Tempest.Desktop/Views/RibbonView.cs`) sets `ToolTip.SetTip` on
every command button but never calls `AutomationProperties.SetName`.
Each button's `Content` is a `StackPanel` holding an icon and a
`TextBlock` — composite content, not a bare string — which is exactly
the shape Avalonia's default automation peer cannot extract a name
from on its own. This class was not among the six controls item (b)
named, and it does not appear in the original report's own §5
remaining-inventory list either — an omission from the disclosed list,
not merely an unlisted-but-acknowledged gap. Left unremediated, a
screen reader has no principled way to announce a ribbon command
button by its actual command name.

Both gaps are real, both are verified directly against the committed
source and test code rather than inferred from a summary, and both
point at the same underlying miss: a control's automation surface was
built and its wiring was tested, but the test measured "is the
mechanism connected" rather than "does the mechanism actually produce
the accessible experience a user gets." Remediation for both is
tracked on `feature/v0.16.0-a11y-remediation`, which as of this writing
sits at this Work Package's own release-branch tip with no remediation
commits yet applied.

## 11. Common Mistakes

- Confirming a brush-key assignment is *consistent* with a
  convention (accent colour matches theme) without also checking
  whether that same consistency defeats the purpose of the thing being
  styled — a focus ring identical to the surface it decorates is
  "correct" by one check and useless by the one that actually matters.
- Writing a test that asserts a style resolves to the intended *token*
  without also asserting the resolved value differs sufficiently from
  whatever it will be seen against — a token-equality check and a
  contrast check answer different questions, and only one of them
  proves the feature works for a user.
- Applying a rigorous verification method (real WCAG contrast math, in
  this very Work Package) to one item and not to a structurally similar
  one in the same Work Package, without noticing the asymmetry.
- Treating a named remaining-inventory list as complete because it was
  produced by the same source pass that found the items in scope — a
  control outside that pass's own search area (the Ribbon was not among
  the controls item (b) named) can be missed by the same list that
  otherwise looks thorough.

## 12. Future Evolution

The `v0.16.0` review board's own remediation commit (`338d8ac`) has
already begun correcting adjacent governance drift this same release
introduced (the Dependency Injection Register's missing
`IStateMigrationRegistry` row, `TD-121`/`TD-123` through `TD-126`), and
a dedicated remediation branch (`feature/v0.16.0-a11y-remediation`)
exists for accessibility specifically. Neither the focus-ring/Primary-
button collision nor the Ribbon automation-name gap named in §10 above
had a corresponding Technical Debt Register row as of this Work
Package's own base commit — `TD-65`'s own row still reads only the
original report's disclosed remaining inventory. Whoever picks up
`feature/v0.16.0-a11y-remediation` should treat §10 above as a starting
brief: fix the Primary-treatment ring (either a border colour that is
never the treatment's own fill, or an outer/offset ring that reads
against the surrounding surface instead of the button's own background),
extend `FocusVisibleStyleTests` with a real contrast assertion against
`presenter.Background` for every treatment, and give `RibbonView`'s
command buttons real `AutomationProperties.Name`s the same way item (b)
already did for the six controls this Work Package did name.

## 13. Key Takeaways

- A style token wired up correctly is not the same claim as a style
  token producing a visible result — test the second claim, not only
  the first.
- When one item in a Work Package gets a rigorous contrast check,
  every visually similar item in the same Work Package should get the
  same check, or the asymmetry itself becomes the next reviewer's
  finding.
- A remaining-inventory list is only as complete as the search that
  produced it; a control outside that search's own scope can be a real
  gap even when the list otherwise looks careful and honest.
- An accessibility retrospective that reports only the fixes and not
  the defects the fixes themselves introduced or missed is not honest
  enough to teach anything.
