# WP 13.3B — Plugin Platform Integration & End-to-End Validation Review

## What This Document Is

The retrospective for `WP 13.3B`, an independent review/verification Work
Package auditing `WP 13.3A` (Plugin Platform Integration & End-to-End
Validation) before it becomes a real commit — mirroring exactly the
review-before-baseline discipline `WP 13.0B`/`WP 13.1B` each established
for the design/implementation Work Package immediately before them. Four
parallel, genuinely independent audit sub-agents — Architecture &

**A note on this document's own provenance.** Unlike `WP 13.0B`/`WP 13.1B`,
this retrospective was not written contemporaneously with `WP 13.3B`
itself — it is reconstructed here, by `WP 13.9.1` (Governance &

This is the single most-corroborated finding in `WP13.9.0 Engineering

## Root Cause (What the Audit Was Checking For)

`WP 13.3A` closed out the plugin platform's own `v0.13.0` scope: a
governance/documentation workstream running alongside three parallel
technical sub-agents (End-to-End Integration, Fault Injection &
Resilience, Performance & Scalability) that together produced a real
`InvalidPluginManifestException.PluginId` diagnostics fix (closing a
Fault-Injection-found gap where a malformed-manifest failure was keyed by
candidate folder path even when its own `Id` had validated fine) and a
genuine `PluginManifestDiscoveryService.TopologicalSort` O(n²) → reverse-
adjacency-index performance optimization (a full survivor-list rescan per
emission replaced with a reverse-adjacency index, same fixed-point-
removal/three-colour-cycle-detection/Kahn's-sort algorithm shape, ~2.4×
faster at 8,000 synthetic plugins, zero disclosed behaviour change).
`WP 13.3A`'s own commit message states plainly that its centralized
`PluginId` fix needed a correction — "see `WP 13.3B` below for the
correction this needed" — naming, in advance, exactly the kind of
second-pass review this project's own history (`WP 13.0B` catching real
`WP 13.0A` documentation defects; `WP 13.1B` catching two real `WP 13.1A`
production bugs) already establishes is worth performing before new
plugin-platform code becomes permanent.

## What Changed

**Four independent audits, one genuine, empirically-confirmed production
defect found and fixed, plus 13–15 new regression tests and one governance
correction.**

**Architecture & Integration Review** and **Security & Reliability
Review** independently converged on the same genuine, blocking defect in
`WP 13.3A`'s own `InvalidPluginManifestException.PluginId` fix:
`DuplicatePluginIdException` — the platform's only Id-uniqueness check —
fires solely for candidates that pass complete manifest validation; a
manifest failing on any *other* field never reaches it, yet its own
self-declared, uniqueness-unverified `Id` was being used as the recorded
`PluginRegistryEntry.Id`. Since `PluginRegistry` performs no
deduplication of its own, a malformed manifest that never validates could
inject a `Failed` registry entry under the exact `Id` of a genuine,
unrelated, already-`Loaded` plugin — a registry-Id-spoofing defect.
**Fixed**: the declared `Id` is now surfaced only as free text inside
`PluginRegistryEntry.Detail`, never as the structured `Id`, which falls
back to the candidate folder path for this exception type exactly as
before `WP 13.3A` — confirmed directly, by this retrospective's own
independent source read, still present exactly this way in
`PluginFailureLogging.RecordIsolatedFailure`. A dedicated regression test
proves a malformed manifest declaring a healthy plugin's own `Id` can no
longer spoof or duplicate its entry — confirmed directly present,
`PluginPlatformFaultInjectionTests.RunAsync_MalformedManifestDeclaresSameIdAsGenuineLoadedPlugin_DoesNotSpoofOrDuplicateTheGenuineEntry`.

**Architecture & Integration Review** additionally reported verifying the
`TopologicalSort` optimization as a pure, behaviour-preserving performance
change via what its own commit message describes as "a 20,000-trial
differential fuzz harness comparing it against a from-scratch
reimplementation of the pre-optimization algorithm — zero mismatches,
zero nondeterminism" — and confirmed the complete plugin lifecycle
remains deterministic end-to-end. **This specific claim is disclosed here,
not silently repeated as established fact**: `WP13.9.0 Engineering Release
Report.md` (Implementation readiness, Finding F2; independently
corroborated by that report's own Verification-readiness discipline)
searched the current source and the full `git log --all -p` history and
found no such harness anywhere in this repository — only the four
committed, deterministic, fixed-shape equivalence tests, which are real
and do support the underlying preservation conclusion but are
categorically not a 20,000-trial randomized fuzz harness. This
retrospective records the claim exactly as `88e41a2`'s own commit message
states it, and records `WP13.9.0`'s own contrary finding alongside it,
rather than resolving the discrepancy by silently picking one account —
consistent with this project's own "disclose, don't fabricate" discipline,
applied here to a disagreement between two governance documents rather
than to new information this retrospective itself could verify.

**Verification Review** independently re-verified the same performance
claim — confirming the constant-factor win, but correcting an inaccurate
doc comment: the fix does not achieve full O(V+E) Kahn's complexity, since
node selection remains an O(V) scan per emission — a materially larger,
structural fix, correctly out of scope for a narrow performance-only
mandate, and low-impact at the platform's actual plugin-count scale.
Its own commit-message paragraph states this workstream "added 15 further
regression tests: 0/1-plugin boundary coverage, a 3,000-node maximal-
fan-in correctness stress test, discovery-order independence for the
combined-chaos scenario, Detail-text informativeness assertions, and four
behavioral-equivalence tests comparing the optimized `TopologicalSort`
against a naive reference across four dependency shapes." Also flagged
(not fixed, informational) that four distinct signature failure causes —
tampered assembly, tampered manifest, expired certificate, not-yet-valid
certificate — all currently collapse to an identical generic `Detail`
message, distinguishable only by which plugin failed, never by why.

**Governance Review** found and fixed one stale count (`Academy
Register.md`'s own narrative total paragraph, one Work Package behind its
own correctly-updated header), independently re-verified all six ADRs
remain fully implemented, independently re-confirmed `TD-49`/`TD-50` and
`FCR-0085`–`FCR-0088` are all correctly classified and accurately cited,
and explicitly deferred (not silently dropped) the disclosed gap that
`WP 13.2B` itself has no Academy retrospective, recommending it as a
small, dedicated follow-up — a recommendation this very Work Package
(`WP 13.9.1`) does not itself act on, since `WP 13.2B`'s own retrospective
remains outside this Work Package's own commissioned scope (see
`WorkPackages.md`'s own `WP 13.2B` row for that gap's continued status).

**A disclosed internal inconsistency in the commit message's own regression-
test count, recorded here rather than silently resolved.** The commit
message's own closing summary states "13 new regression tests added
across this review (1 for the spoofing fix, 12 from Verification Review's
own audit)" — arithmetically inconsistent with Verification Review's own
paragraph, quoted above, which states 15 tests were added. This
retrospective reports both figures exactly as `88e41a2`'s own commit
message states them, rather than guessing which is correct; resolving the
discrepancy would require access to the four sub-agents' own full reports,
which — per this document's own provenance note, above — this
retrospective does not have.

## Verification

after every fix, reported **7 passed, 1 warned (pre-existing, unrelated),
0 failed**. Debug and Release builds both **0 Warnings, 0 Errors**

2,519 passing** (2,298 `Tempest.Core.Tests` + 221 `Tempest.Desktop.Tests`).

agents, per the commit message. No new Technical Debt beyond what
`WP 13.3A` itself already raised (`TD-49`/`TD-50`).

## Scope Confirmation

Per the commit message, every fix applied was either (a) the registry-Id-
spoofing correction to `WP 13.3A`'s own `InvalidPluginManifestException.PluginId`
fix, a precise, minimal correction to a defect `WP 13.3A` itself
introduced, or (b) a new regression test proving a fix or closing a
genuine, named coverage gap a sibling audit identified. `WP 13.3A`'s and
`WP 13.3B`'s combined material was committed together as `88e41a2` — the
same "commit the reviewed-and-corrected baseline together" pattern
`WP 13.0A`/`WP 13.0B` and `WP 13.1A`/`WP 13.1B` each already established,
here extended for the first time to a Work Package whose own predecessor
(`WP 13.3A`) was itself a Governance & Documentation workstream running
alongside technical sub-agents, not a single implementation pass.
