# WP 12.3B — Fault Injection & Validation Framework Implementation

## What This Document Is

The implementation-phase retrospective realising `WP12.3A Fault
Injection & Validation Framework Architecture.md`'s own design —
mirroring `WP 4.3`'s architecture → implementation pairing for the
Sample Module, and `WP 5.2`'s equivalent for Diagnostics.

## 1. Introduction

Realises `ADR-0102` exactly as designed, with one disclosed addition
found during implementation (see §3): `DuplicateNavigationSampleModule`
moved out of `Tempest.Samples`, renamed `DuplicateNavigationModule`, into
a new project, `Tempest.Validation` (`src/Validation/Tempest.Validation/`,
namespace `Tempest.Validation.FaultInjection`); a new marker interface,
`Tempest.Core.Modules.IFaultInjectionModule`; `ReflectionFrameworkDiscoveryService`
extended with a defaulted `includeFaultInjectionModules` parameter;
`ITempestHostBuilder`/`TempestHostBuilder` extended with one new fluent
method, `EnableFaultInjectionModules()`.

## 2. What Was Achieved

**The actual defect closed, verified directly, not merely asserted.**
`ModuleLifecycleStabilityTests.cs`'s pre-existing special-case exclusion
for this module's Id — the direct evidence `WP 12.3A` traced the defect
through — is **deleted, not updated**: the real `WorkspaceHost`, composed
through the identical production path `Tempest.App` itself uses, now
genuinely reaches `Running` with zero modules in `ModuleState.Failed`.

**Zero behavioural change for any existing, unmodified caller.** Both new
`ReflectionFrameworkDiscoveryService` constructors default
`includeFaultInjectionModules` to `false`; `ITempestHostBuilder`'s one
new method is additive; no `HostState`, Host Lifecycle phase, or failure
category changed. Verified directly: the complete pre-existing test
suite passes unmodified in substance — only the handful of assertions
naming the moved module's own old namespace/Id/module-count were updated
in place, none removed for convenience.

**A real, working, end-to-end validation-run path**, proven by a new
test file (`FaultInjectionModuleDiscoveryTests.cs`, `Tempest.Core.Tests/Modules/`):
a real `TempestHostBuilder`, given a candidate list naming
`DuplicateNavigationModule` directly, discovers zero modules from
`Tempest.Validation` without `.EnableFaultInjectionModules()`, and
discovers + correctly isolates it with that one call added — the exact
shape a future validation-run tool would use.

**Full regression, both configurations, re-verified directly by this
Work Package's own real `dotnet build`/`dotnet test` runs** (not carried
forward from any prior claim): Debug and Release both 0 Warnings/0
Errors; combined suite 2,233/2,233 passing both configurations
(2,031 `Tempest.Core.Tests` + 202 `Tempest.Desktop.Tests`) — net +5 over
this suite's own last recorded total (2,026 → 2,031 in `Tempest.Core.Tests`:
2 new in `FaultInjectionModuleDiscoveryTests.cs`, 3 new in
`ReflectionFrameworkDiscoveryServiceTests.cs`), zero test methods removed.

## 3. Implementation Lessons

**A dependency the architecture phase's own worked example implied but
did not name explicitly, found and resolved during implementation, then
back-filled into ADR-0102 rather than silently absorbed.**
`DuplicateNavigationModule`'s own `InitialiseAsync` needs
`NavigationSampleModule.NavigationItemId` — the specific, real
`NavigationItem.Id` it deliberately collides with. Two options existed:
duplicate that string as a second literal (keeping `Tempest.Validation`'s
own dependency graph to `Tempest.Core` alone), or reference
`Tempest.Samples` directly and use the existing public constant. The
second was chosen and disclosed directly in both `ADR-0102` and this
project's own architecture document, not silently implemented — a
duplicated literal would have been exactly the kind of "two independent
things that must be kept in agreement by hand" risk this codebase's own
conventions (see ADR-0027's own disclosed attribute/instance-property
drift risk) consistently avoid where a direct reference is available at
no real cost. The dependency direction remains downward-only and
introduces no cycle (`Tempest.Samples` does not, and must not, reference
`Tempest.Validation`) — verified directly against every `.csproj`
involved.

**Discovery's own ordinal-Id-sort dependency held without needing its
original hack.** `DuplicateNavigationSampleModule`'s original Id carried
a deliberate `zzz-` prefix solely to sort after `NavigationSampleModule`'s
own Id within `Tempest.Samples`'s shared `tempest.samples.*` namespace.
Moving to `tempest.validation.faultinjection.navigation-duplicate`
removed the need for that hack incidentally, not by design intent:
`"tempest.samples.navigation"` already sorts before
`"tempest.validation...."` ordinally (`s` < `v`), so the same
"successful registration always initialises first" guarantee holds with
a cleaner Id, re-verified directly by the same test
(`DuplicateNavigationId_FailsOnlyTheOffendingModule_TheOriginalRegistrationSurvives`)
that already proved it before the move.

**`IsValidModuleType` moving from `static` to an instance method was the
only real internal shape change** `ReflectionFrameworkDiscoveryService`
needed — it now reads the instance's own `_includeFaultInjectionModules`
field, exactly one new conditional line alongside the pre-existing
interface/abstract/generic checks it already made. No other internal
method, and no public method signature besides the two constructors'
new optional parameter, changed.

## 4. Key Takeaways

- Two additive, independently-testable pieces (a marker interface; one
  new discovery constructor parameter; one new builder method) closed a
  genuine, previously-silent production defect with zero risk to any
  existing, passing test — proven, not assumed, by a full regression run
  both before documentation work began and again after every
  documentation change (this project's own standing "code first,
  verified, then document" discipline).
- A negative test (deleting a special-case exclusion and confirming the
  broader assertion it was written around now holds unconditionally) is
  often the strongest proof that a fix actually works — stronger than
  any number of new, additive tests alone.
- See `ADR-0102` for the complete decision record and `Fault Injection &
  Validation Architecture.md` for the full design this Work Package
  realised unchanged.
