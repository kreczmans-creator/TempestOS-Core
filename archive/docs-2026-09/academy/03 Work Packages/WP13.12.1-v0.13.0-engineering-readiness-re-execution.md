# WP 13.12.1 — v0.13.0 Engineering Readiness Re-Execution

## 1. Introduction

`WP 13.12.1` re-ran the `v0.13.0` Engineering Release Readiness Review
mechanically against the working tree, using `ADR-0106` §4's verdict
derivation and six read-only discipline agents (Architecture,
Implementation, Verification, Governance, Release, Security/Trust). It
changed no file — no code, no documentation. Its entire output is a
verdict and a finding set.

## 2. Purpose

To determine whether `WP 13.12.0`'s Academy backfill had actually cleared
the Release Blocking finding, and to establish the full current finding
set under §4's taxonomy — separately for committed `HEAD` and for the
working tree.

## 3. Background

The prior gate review returned **NOT READY**: Governance readiness
carried a Release Blocking finding (sixteen of twenty-five delivered Work
Packages had no retrospective). `WP 13.12.0` created those sixteen but
left them uncommitted.

## 4. The Problem

Re-running a readiness review against a dirty working tree invites a
specific error: crediting uncommitted evidence as though it had shipped.
`HEAD` and the working tree were materially different states —
9-of-25 retrospectives versus 25-of-25 — and a single verdict covering
both would have been wrong for one of them.

## 5. The Design

**Two states, reported separately.** Every discipline was instructed to
treat the uncommitted `WP 13.12.0` documentation as working-tree evidence
only, to verify both counts itself, and to end with two verdicts — one
for `HEAD`, one for the working tree.

**Mechanical derivation, not judgement.** Each finding was classified
into exactly one of §4's three kinds; category status followed §4's fixed
table; the release verdict followed §4's strict priority order.

**Central adjudication of disputes.** Where disciplines disagreed, the
integrator resolved against the governing text rather than by preference.

**Controlled verification.** Debug and Release builds plus both full
regressions were run centrally, sequentially — not per-agent, and not in
parallel — to avoid multiplying concurrent test processes.

## 6. Alternatives Considered

**Report a single verdict.** Rejected: the two states genuinely differed
on the decisive finding.

**Commit first, then review.** Rejected: it would have made the review
unable to answer whether committing was warranted.

**Accept the disciplines' verdicts as returned.** Rejected — two disputes
required adjudication against the governing text (below).

## 7. Why This Solution Was Chosen

Because the question asked — "is this ready?" — has a different answer
for a commit than for a working tree, and conflating them either credits
work that has not shipped or discards work that exists.

## 8. Architectural Principles

- **Uncommitted evidence is not evidence of a commit's state.**
- **§4 classification is mechanical**, and category/release status are
  consequences of it, never inputs to it.
- **The governing text outranks a reviewer's reading.**
- **A review changes nothing.** Zero files modified.

## 9. Benefits

Both states received an exact, derivable verdict. Two disputed
classifications were resolved against source text rather than left to
narrative. Nineteen Disclosed/Non-Blocking and six Pre-Existing findings
were enumerated with their states, giving `WP 13.12.2` a precise work
list.

## 10. Trade-offs

The review's verdict for both states was **NOT READY**, which can read as
no progress. It was not: the working tree cleared the Academy blocker
entirely, leaving one structural blocker that no branch-local action can
clear.

## 11. Common Mistakes

- **Reading "not run" as "not blocking".** The Verification discipline
  classified the never-run `main` CI gate as Pass-with-observations.
  `docs/architecture/Engineering Readiness Review Architecture.md` §2.3's
  CI row states the blocking condition as "Either job fails, **or has not
  actually been run on `main` at the pre-tag commit**". Adjudicated
  against that discipline: it is Release Blocking.
- **Inflating a missing artefact into a blocker.** The Release discipline
  graded the absent superseding Engineering Release Report Release
  Blocking. §2.4's criterion is "Release Notes cannot be produced
  accurately from the existing record" — they can — and §2.5's blocking
  enumeration does not include a missing report. Adjudicated down to
  Disclosed, Non-Blocking.
- **Assuming a health-check attests to `HEAD`.** `governance-healthcheck.ps1`
  reads the filesystem, so its clean result described the working tree,
  not the commit. The Governance discipline caught this explicitly.

## 12. Future Evolution

`WP 13.12.2` acts on the finding set: committing the backfill, adding the
`WP 13.12.x` records, producing the superseding Engineering Release
Report and the Release Notes, and correcting the documentation drift
enumerated as `DNB-1`, `DNB-2`, `DNB-4`, `DNB-5`, `DNB-7`, `DNB-11`,
`DNB-12`, `DNB-16`.

The remaining Release Blocking finding — CI never run on `main` at the
pre-tag commit — is structural and cannot be cleared on a feature branch.

## 13. Key Takeaways

- When the tree is dirty, a readiness review must answer twice.
- "Has not been run" and "did not fail" are different states, and a
  governing text may treat both as blocking; read it rather than assume.
- Disciplines will disagree; the resolution belongs to the text, not to
  seniority or to the more convenient answer.
- A review that changes nothing is doing its job.
