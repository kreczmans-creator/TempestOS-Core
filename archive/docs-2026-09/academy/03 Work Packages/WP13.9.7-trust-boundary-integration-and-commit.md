# WP 13.9.7 — Trust Boundary Integration & Commit

## 1. Introduction

This Work Package integrated, reconciled, and committed the entire
`WP 13.9.1`–`WP 13.9.6` plugin trust remediation chain as a single commit
on `feature/v0.13.0` — `d7d19d4`, 35 files changed, 3,263 insertions,
90 deletions. It ran as the **sole implementation/integration agent, with
no parallel writers**, immediately after `WP 13.9.6` closed the last of
the four execution-boundary defects `WP 13.9.0`'s Engineering Readiness
Review and its own successor re-verification and adversarial-review passes
had found in the `v0.13.0` plugin trust platform (`ADR-0110`–`ADR-0112`).

It is important to state at the outset what kind of Work Package this is.
`WP 13.9.7` **added no new architecture, no new mechanism, and no new
production behaviour**. Its entire value lies in reconciliation,
independent verification against real source, and the production of one
clean, honest, fully-evidenced commit. The net effect the commit records
is the *chain's* achievement, not this Work Package's: no denied plugin's
code executes at any point from Plugin Discovery through
Module/Hosted-Service Discovery, Registration, and Lifecycle, for any
denial reason, across single- or multi-assembly plugins, for either
`IModule` or `IHostedService`.

The `WorkPackages.md` row for this Work Package classifies it
`Governance/Process`, and that classification is exact.

## 2. Purpose

To convert a working tree containing six Work Packages' worth of
uncommitted, partially-documented remediation into a single committed,
governance-consistent, independently-verified state — and to do so without
trusting the commissioning summary that described it.

Concretely, four obligations:

1. **Verify the changeset directly against real, current source**, not
   against the narrative handed to this Work Package. The `PROJECT_STATUS.md`
   entry records that this meant spot-checking the `PluginAssemblyLoader.cs`,
   `TempestHost.cs`, and `ReflectionFrameworkDiscoveryService.cs` diffs, and
   reading `ADR-0111` and `Plugin Trust & Isolation Architecture.md` in full.
2. **Confirm the governance record describes the final code state**, with
   no "not yet implemented"/"pending"/"to be closed" language surviving for
   this chain's own scope.
3. **Close the one staleness `WP 13.9.5`'s own Governance reviewer had
   flagged as needing to close before commit** — and only that, not a
   wider governance sweep.
4. **Reconcile the release record** — `WorkPackages.md` rows and
   `PROJECT_STATUS.md` strata for six Work Packages that had, until this
   point, existed only as conversational reports to their commissioning
   sessions.

## 3. Background

The `WP 13.9.x` chain is unusual in this project's history for its depth of
recursion. `WP 13.9.0` (Engineering Readiness Review) found four named
findings; `WP 13.9.1` fixed them; `WP 13.9.2` re-executed the review and
found `WP 13.9.1`'s own fix still incomplete; `WP 13.9.3` widened it;
`WP 13.9.4` found and closed a *separate*, more severe defect, and its own
mid-Work-Package Adversarial Review found that closure incomplete in turn
(Hosted Service Registration was a second, unfiltered pipeline);
`WP 13.9.5` — six parallel, read-only reviewers — found a fourth, distinct
defect that three of those reviewers each live-PoC-reproduced
independently; `WP 13.9.6` closed it.

Of those six, only two produced anything a reader could later audit
without this Work Package's intervention. `WP 13.9.2` and `WP 13.9.5` were
verification-only and read-only respectively; each delivered its report
**conversationally, to its own commissioning session**, and saved no
standalone file. `WorkPackages.md`'s own rows for both say so explicitly,
and both rows note that they are retroactive, added by `WP 13.9.7`.

That is the state this Work Package inherited: real, working, verified
code in the working tree; a governance record that could not, on its own,
explain how that code came to be; and one specific, named governance
staleness a prior reviewer had already identified as a commit blocker.

## 4. The Problem

1. **Is the working tree what the commissioning summary says it is?** Six
   Work Packages had written to `src/`, `tests/`, and `docs/` in sequence,
   several of them correcting their own predecessors mid-flight. A summary
   of that sequence is a secondary source. The primary source is the diff.
2. **Do `ADR-0111` and `Plugin Trust & Isolation Architecture.md` describe
   the code that actually exists?** Both had been amended repeatedly — four
   separate "Corrected, `WP 13.9.x`" sections in `ADR-0111`'s case — by four
   different Work Packages, each of which believed it was closing the last
   gap. Aspirational or stale language surviving in either document would
   make the commit's own claims unverifiable.
3. **Which governance registers had drifted, and which had not?** A
   reconciliation pass that corrects everything it touches is
   indistinguishable from scope creep. The obligation was to correct what
   was genuinely stale and leave what was genuinely accurate.
4. **Do `WP 13.9.1`–`WP 13.9.6` require Academy retrospective files of
   their own?** An unexamined answer of "yes" would have added six
   documents; an unexamined "no" would have left a hole. Either needed a
   convention check against this project's own stated rule, not a
   preference.
5. **Does the working tree contain anything the commissioned changeset does
   not account for?** Six sequential writing agents plus this Work
   Package's own edits is exactly the shape in which stray files survive
   into a commit.

## 5. The Design

There is no production design here. What follows is the design of the
**integration discipline** — the only thing this Work Package actually
built.

**Sole integrator, no parallel writers.** `WorkPackages.md`'s own row opens
with this constraint, and `PROJECT_STATUS.md`'s stratum repeats it. Where
`WP 13.9.4` and `WP 13.9.6` had each used parallel reviewers, and
`WP 13.9.5` used six of them, `WP 13.9.7` deliberately used none. The
reason is structural: this Work Package's product is a single atomic
commit, and a commit is not a parallelisable artefact. Every prior stage in
the chain had already supplied the independence; adding more concurrent
writers at the integration step would have introduced exactly the class of
working-tree contamination obligation (5) exists to detect.

**Verification against primary source, not the commissioning summary.**
The discipline recorded in `PROJECT_STATUS.md` is explicit about which
primary sources were consulted: the diffs of the three production files
carrying the chain's load (`PluginAssemblyLoader.cs`, `TempestHost.cs`,
`ReflectionFrameworkDiscoveryService.cs`), and the full text of `ADR-0111`
and `Plugin Trust & Isolation Architecture.md`. The stale-language check
was performed as a repository-wide grep for "not yet implemented"/
"pending"/"to be closed" phrasing across both documents. It returned
exactly one hit — an unrelated Diagnostics recommendation, genuinely still
open, which this chain never touches. It was **left as is**, on the
grounds that a correctly-disclosed open item is not staleness. That
distinction — between a document that is wrong and a document that is
honest about something unfinished — is the whole of the check.

**One governance correction, precisely scoped.** `ADR Register.md`'s
`ADR-0111` Entries-table citation read
`WP 13.0A (architecture)/WP 13.2A (implementation)/WP 13.9.1 (corrected)`.
Three further corrections — `WP 13.9.3`, `WP 13.9.4`, `WP 13.9.6` — had
each landed directly in `ADR-0111`'s own Status and Decision text without
the register's citation field ever being extended to match. This Work
Package corrected it to a six-phase citation, each phase carrying its own
short parenthetical, and confirmed the correction against `ADR-0111`'s own
file: three further "Corrected, `WP 13.9.x`" sections beyond the
`WP 13.9.1` one, present, one per phase. The register's own "Last
Reviewed" narrative gained a matching entry. **111 ADRs unchanged** — every
correction was to an existing ADR's own citation, not a new decision.

**Release-record reconciliation at the established density.** Six dense
`WorkPackages.md` rows (`WP 13.9.1`–`WP 13.9.6`) plus this Work Package's
own, and six matching `PROJECT_STATUS.md` strata prepended. The density
target was not invented: the rows were written to match the `WP 13.2A` and
`WP 13.3B` row precedent, so that a reader arriving at `WorkPackages.md`
cold gets the same depth of account for a chain that produced no reports as
for one that did.

**A convention check, not a preference, on Academy retrospectives.** The
question of whether `WP 13.9.1`–`WP 13.9.6` needed retrospective files was
resolved by direct check against `Academy Index.md`'s own stated
maintenance rule and against the `WP 13.2B`/`WP 13.9.1` precedent — neither
of which had a retrospective at the time, both closed with only a
`WorkPackages.md` row and a `PROJECT_STATUS.md` entry. The conclusion
recorded is that a row plus a status entry already satisfies this project's
actual, established requirement, and that omitting six further documents
was **not scope creep to omit**, but conformance.

**One backfill nonetheless performed.** `WP 13.3B` — an *already-committed*
Work Package (`88e41a2`) — had no Academy retrospective at all. The commit
message records that this changeset includes a new, reconstructed
retrospective for it, plus a `WorkPackages.md` row, correcting stale
governance counts and Status headers at the same time. That work is
attributed in the commit message to `WP 13.9.1`, not to this Work Package;
`WP 13.9.7` carried it into the commit and accounted for it.

**Full verification before staging, and again after every edit.** The
recorded figures:

- `governance-healthcheck.ps1`: **7 passed, 1 warned, 0 failed** — the
  warning pre-existing `v0.9.0`/`v0.10.0` informational, unrelated —
  confirmed **identical before and after every documentation edit**, which
  is the actual claim being made: zero new drift introduced.
- Builds: `dotnet build TempestOS.slnx`, Debug **and** Release, both with
  `-p:TreatWarningsAsErrors=true` — **0 Warnings, 0 Errors**, both
  configurations.
- Full regression: `dotnet test TempestOS.slnx`, Debug and Release, both
  `--no-build` — **2,538/2,538 passing** in both configurations (2,317
  `Tempest.Core.Tests` + 221 `Tempest.Desktop.Tests`).
- Working tree confirmed via `git status --short` **before staging** to
  contain only files accounted for by the commissioned changeset or this
  Work Package's own governance edits.

**Stop at the commit.** Not pushed, not tagged, no release created — per
this Work Package's own explicit instruction, stated in the commit message,
the `WorkPackages.md` row, and the `PROJECT_STATUS.md` stratum alike.

## 6. Alternatives Considered

- **Six separate commits, one per Work Package.** Rejected. The chain is
  not separable into six independently-correct states: `WP 13.9.2` and
  `WP 13.9.5` produced no code at all, and `WP 13.9.1`'s and `WP 13.9.3`'s
  intermediate states are each *known incomplete* — their own successors
  proved it. Committing a state that a later Work Package in the same
  changeset has already demonstrated to be exploitable would put a
  knowingly-broken trust boundary into the branch history as a bisectable
  point. One commit, whose message narrates the full sequence, records the
  same history without ever making the branch pass through it.
- **Trusting the commissioning summary and committing directly.** Rejected
  as the failure mode the whole `WP 13.9.x` chain exists to illustrate:
  four times in six Work Packages, a summary of "this closes the gap" was
  found wanting by someone who went and read the source. Adopting that
  posture at the integration step would have been the one place the chain
  had not yet tested it.
- **A wider governance sweep while the registers were open.** Rejected.
  The `WP 13.9.5` Governance reviewer had named exactly one blocker. The
  grep for stale language found exactly one further candidate and it was
  correctly-disclosed open work. Correcting more than that would have made
  the commit's own diff unreviewable against its stated scope.
- **Writing six Academy retrospectives.** Rejected on the convention check
  described in §5 — not on cost. The rule, the `WP 13.2B` precedent, and
  the `WP 13.9.1` precedent all pointed the same way.
- **Pushing and tagging.** Not this Work Package's call. Explicitly
  out of scope by instruction, and recorded as such in three places.

## 7. Why This Solution Was Chosen

Because the chain's own history had already established, four separate
times, that the expensive failure in this domain is a *claim outrunning its
evidence*. `WP 13.9.1` claimed closure and `WP 13.9.2` disproved it.
`WP 13.9.3` claimed closure and `WP 13.9.4` found a different defect
entirely. `WP 13.9.4`'s first pass claimed closure and its own Adversarial
Review found the Hosted Service pipeline unfiltered. `WP 13.9.5` found the
combined boundary "defensible for its own literal claims" and then
demonstrated a live, Host-fatal bug outside those literal claims.

An integration Work Package that accepted the sixth such claim on its face
would have been, statistically, the least defensible link in the chain. So
the discipline was inverted: read the source, grep the documents, check the
convention, verify the tree, and only then stage. Every one of those steps
is cheap; the chain had already proven that the alternative is not.

The single-commit decision follows from the same reasoning. What the branch
should record is a boundary that closed, together with an honest account of
how many times it was believed closed before it was. A long, sequenced
commit message does that. Six commits, four of which are known-exploitable,
do not.

## 8. Architectural Principles

- **No New Architecture at the Integration Step.** This Work Package
  touched no production file of its own. Every `src/` and `tests/` change in
  `d7d19d4` was authored by `WP 13.9.1`, `WP 13.9.3`, `WP 13.9.4`, or
  `WP 13.9.6`; `WP 13.9.7` verified them and committed them.
- **Primary Sources Over Summaries.** The changeset was verified against
  diffs and document text, not against the narrative describing it — the
  same discipline `Engineering Readiness Review Architecture.md` §5's own
  independence rule applies to reviewers, applied here to an integrator.
- **Correctly-Disclosed Open Work Is Not Staleness.** The one surviving
  "pending"-class phrase found by grep was left untouched because it was
  true. A governance sweep that erases honest disclosure of unfinished work
  makes the record worse, not better.
- **Precisely-Scoped Correction.** One register field corrected — the one a
  prior reviewer had named as a commit blocker — extended from a one-phase
  to a six-phase citation, each phase verified against `ADR-0111`'s own
  file.
- **Convention Checked, Not Assumed.** The Academy-retrospective question
  was answered against `Academy Index.md`'s own stated rule and two named
  precedents, and the answer recorded with its reasoning, so a later reader
  can disagree with the rule rather than guess at the decision.
- **The Commit Message Is Governance.** `d7d19d4`'s message narrates all
  six Work Packages in sequence, names every changed file by category,
  states every verification figure, and cites `ADR-0110`, `ADR-0111`,
  `ADR-0112`, `ADR-0015`, `ADR-0025`, and `ADR-0027` with their exact
  relationship to the change. For `WP 13.9.2` and `WP 13.9.5`, whose only
  other artefacts are retroactive rows, it is a primary source.

## 9. Benefits

- **The `WP 13.9.1`–`WP 13.9.6` chain exists in the repository as one
  reviewable, verified state** — `d7d19d4`, 35 files, +3,263/−90 — rather
  than as an uncommitted working tree plus six conversational reports.
- **Two Work Packages that produced no artefacts of their own are now
  permanently legible.** `WP 13.9.2`'s finding (the `AppDomain` diff never
  covered the constructor-parameter-type lazy-load trigger) and
  `WP 13.9.5`'s finding (`CreateDescriptor` calling `Activator.CreateInstance`
  unconditionally, before the `WP 13.9.4` filter was ever consulted) survive
  in dense `WorkPackages.md` rows and `PROJECT_STATUS.md` strata written
  by this Work Package.
- **`ADR Register.md`'s `ADR-0111` citation now matches `ADR-0111`.** The
  one blocker `WP 13.9.5`'s Governance reviewer named is closed, verified
  against the ADR's own file rather than against the claim that it needed
  closing.
- **The verification claim is a difference, not a snapshot.**
  `governance-healthcheck.ps1` was run before *and* after every
  documentation edit and confirmed identical — which is what actually
  supports "zero new drift", where a single passing run would not.
- **Nothing stray reached the commit.** The `git status --short` check
  before staging is recorded, and the commit's own file list is
  reconcilable against it.
- **The precedent transferred.** `WP 13.10C` explicitly adopted "the same
  integration-and-commit role `WP 13.9.7` established", and `ADR Register.md`
  describes `WP 13.10C`'s own citation extension as "mirroring `WP 13.9.7`'s
  own identical six-phase precedent."

## 10. Trade-offs

- **One commit is one bisection point.** `d7d19d4` changes 35 files across
  production, tests, and governance. A future regression bisected to this
  commit gains no finer granularity from the history itself; the reader must
  use the commit message's own sequenced narrative to localise. This was
  accepted deliberately (§6) because the alternative history contains
  known-exploitable intermediate states.
- **No independent reviewer at the integration step.** Sole integrator, no
  parallel writers, means the final verification pass has no second pair of
  eyes on it. The mitigation is that all six preceding Work Packages carried
  their own independence — `WP 13.9.5` alone used six parallel read-only
  reviewers — and that `WP 13.9.6` was itself verified by mutation testing
  twice, independently, plus a fully independent adversarial review using a
  separate standalone proof-of-concept project. `WP 13.10C` later chose the
  opposite balance for the same role, running four fresh read-only reviewers
  before its own commit.
- **The convention check's conclusion has since been overtaken by
  practice.** `WP 13.9.7` concluded, correctly against the rule as stated at
  the time, that `WP 13.9.1`–`WP 13.9.6` needed no Academy retrospectives.
  Retrospectives for several of them — and this document itself — have since
  been written as an untracked backfill. That does not make the check wrong;
  it makes the rule it checked against something the project subsequently
  chose to exceed.
- **Verification figures are self-reported.** The build, test, and
  healthcheck numbers in `d7d19d4`, `WorkPackages.md`, and
  `PROJECT_STATUS.md` agree exactly with one another (**2,538/2,538**; 7
  passed/1 warned/0 failed), which is internal consistency, not external
  reproduction. Reproducing them requires checking out `d7d19d4` and
  re-running the commands the commit message names.
- **`git status --short` proves the tree, not the intent.** It confirms no
  unaccounted files were staged; it cannot confirm that every accounted file
  was changed for the reason claimed. That confirmation came from the source
  read, and its depth is disclosed as spot-checks of three files plus two
  documents read in full — not a line-by-line audit of all 35.

## 11. Common Mistakes

1. **Reading `d7d19d4` as `WP 13.9.7`'s own work.** It is not. The 35 files
   and +3,263/−90 belong to `WP 13.9.1`/`WP 13.9.3`/`WP 13.9.4`/`WP 13.9.6`;
   `WP 13.9.7` contributed the `ADR Register.md` citation correction, seven
   `WorkPackages.md` rows, six `PROJECT_STATUS.md` strata, and the commit
   itself. The commit message says so in its own final paragraph:
   "governance reconciliation and verification only, no further production
   changes."
2. **Treating a single healthcheck run as evidence of no drift.** The claim
   this Work Package makes is that the result was *identical before and
   after* every documentation edit. Only the pair supports the claim.
3. **Assuming the "no Academy retrospective required" conclusion means
   these Work Packages are undocumented.** They are documented — densely — in
   `WorkPackages.md` rows and `PROJECT_STATUS.md` strata, which is precisely
   what the convention check established as this project's actual
   requirement. The rows for `WP 13.9.2` and `WP 13.9.5` run to several
   hundred words each.
4. **Assuming the chain ended here.** It did not. `WP 13.10A`'s own
   read-only, six-discipline review subsequently found two further,
   genuinely distinct Release-Blocking gaps in the same static enforcement
   mechanism (`TD-51`, `TD-52`), explicitly recorded as **not** variants of
   anything this chain closed. `WP 13.9.7`'s commit closed the execution
   boundary this chain was scoped to; it never claimed the platform was
   finished, and the record does not read as if it did.
5. **Reading a later reopening as a defect in this Work Package's
   verification.** For completeness, and because the same reader is likely
   to encounter both: the successor integration Work Package, `WP 13.10C`,
   characterised `TD-51`'s residual "unresolvable constructor parameter
   type" gap as safely isolated with no crash; `WP 13.11A` later found that
   characterisation false for the `IModule` axis and reopened `TD-51`,
   which `WP 13.11B` then closed. That sequence concerns a denial path
   introduced by `WP 13.9.3` and widened by `WP 13.10B` — it postdates this
   Work Package's own scope and was not visible to it, and none of the
   surviving record suggests otherwise.
6. **Expecting a pushed branch or a tag.** Neither exists from this Work
   Package. "Not pushed, not tagged, no release created" is stated in the
   commit message, the `WorkPackages.md` row, and the `PROJECT_STATUS.md`
   stratum, each time attributed to this Work Package's own explicit
   instruction.

## 12. Future Evolution

- **The role became a pattern.** `WP 13.10C` is described in its own
  `WorkPackages.md` row as "the same integration-and-commit role
  `WP 13.9.7` established for the `WP 13.9.1`–`WP 13.9.6` chain, applied
  here to the `WP 13.10A`/`WP 13.10B` chain". The distinguishing change it
  made was to add four fresh, read-only sub-agents at the integration step —
  directly addressing this Work Package's own disclosed trade-off of having
  no independent reviewer at that point.
- **The chain this commit closed was not the last.** `WP 13.10A`/`WP 13.10B`
  (`TD-51`/`TD-52`, committed `79e453f`), then `WP 13.11A`/`WP 13.11B`
  (`TD-51` reopened and re-closed), then `WP 13.11C` and `WP 13.11D`
  followed. `ADR-0111`'s citation in `ADR Register.md`, which this Work
  Package extended from one phase to six, has since been extended to a
  seventh by `WP 13.10C`. That field is now the load-bearing index of the
  whole trust-boundary correction history, and its growth is the honest
  signal of how many passes this boundary took.
- **The residual gap the successor chain surfaced traces back into this
  chain's own code.** `WP 13.11A` established that the "unresolvable
  constructor parameter type" denial path — pre-existing for the `IModule`
  axis since `WP 13.9.3`, one of the four Work Packages committed here —
  never reaches `RecordDenied`, so `WP 13.9.6`'s own
  `isTypeExcluded: deniedTypeRegistry.IsDenied` filter, also committed here,
  could not exclude the offending type. `WP 13.11B` closed it by making the
  denial path record every type its fixed-point scan discovered before
  throwing, plus a fail-closed reflection guard in
  `ReflectionFrameworkDiscoveryService.CreateDescriptor` as a backstop, and
  recorded that no ADR was added or amended: `ADR-0111`'s Decision text
  already mandated the recording behaviour, so the defect was an
  implementation divergence from an already-correct decision. Nothing in
  that sequence was visible at `d7d19d4`.
- **A repeatable integration checklist is the natural extraction.** The five
  obligations in §4 — verify against source, check the documents describe the
  code, correct exactly the named staleness, reconcile the release record by
  convention, prove the tree before staging — were assembled ad hoc here and
  re-performed at `WP 13.10C`. Neither Work Package promoted them into a
  standing governance document; that remains available, unattempted work.
- **Reproduction of the verification figures remains open.** Nothing in the
  record indicates that `d7d19d4`'s **2,538/2,538** was independently
  re-run by a later Work Package against that exact commit. Later figures
  (2,553, then 2,554) are for later states of the tree.

## 13. Key Takeaways

- **Integration and commit is a real Work Package kind, with real product.**
  Its output is not code. It is a single verified state, a governance record
  that matches it, and a commit message dense enough to serve as the primary
  source for the Work Packages that produced no artefacts of their own.
- **The value is in refusing the summary.** Six Work Packages in this chain
  handed forward a claim of closure; four were subsequently found wanting by
  someone who read the source instead. The integration step was the last
  place that pattern had not been tested, and it was tested by reading
  three production diffs and two governance documents rather than accepting
  a seventh claim.
- **"Identical before and after" is a stronger claim than "passing."** The
  healthcheck evidence in this Work Package is a difference over an edit
  sequence, not a snapshot, and that is what makes "zero new drift" a
  falsifiable statement.
- **Scope discipline in a governance pass is itself a design decision.** One
  register field was corrected because a named reviewer had named it. One
  further "pending"-class phrase was found and deliberately left, because it
  was an honest disclosure of genuinely open work, not drift. Both choices
  are recorded with their reasoning.
- **Committing a chain as one commit is a deliberate history decision, not
  convenience.** Four of this chain's six intermediate states were proven
  exploitable by their own successors. A history that never passes through
  them, but narrates them fully in its message, is more honest than six
  commits that do.
- **Establishing a role is worth more than performing it once.** The most
  durable output of this Work Package is that `WP 13.10C` had a named
  precedent to follow, and improved on it — adding the independent review at
  the integration step that this Work Package disclosed as its own principal
  trade-off.
