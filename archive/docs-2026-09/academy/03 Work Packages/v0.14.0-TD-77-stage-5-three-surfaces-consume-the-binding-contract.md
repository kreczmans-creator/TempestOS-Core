# TD-77 Stage 5 — Three Surfaces Consume the Binding Contract

## 1. Introduction

`e72b933`, the last of four `TD-77` stages this release, makes the Ribbon,
the Command Palette and the Macro Manager stop deciding for themselves
what a command needs and start asking the framework Stages 2–4 built. The
~390-line workaround that stood in for it — `RibbonObjectActionHandlers.cs`
— is deleted rather than bypassed. A pre-`v0.14.0` engineering-body-of-
work row.

## 2. Purpose

To make the 74 real production commands this migration bound actually
reachable from the three surfaces that had each been guessing at command
requirements independently, none of them correctly for every command.

## 3. Background

The Command Palette gated on `CreateDefault`, which no production
discipline command has ever set — so pressing Enter on any of the 74 real
commands reported "unavailable" and did nothing. The Ribbon's own Id-
parsing dispatch had already been shown broken by Stage 3's audit:
`requirements.delete-group` is not "delete" and `requirements.revise` is
not "edit", so both fell through to a generic fallback message and were
permanently unreachable.

## 4. The Problem

Three surfaces, three independent and each-incomplete answers to "what
does this command need" — none of them consulting the one place (the
binding contract) that actually knows.

## 5. The Design

Command Palette: evaluates and invokes against the live selection through
the context-aware path. Unavailable commands stay listed, rendered
genuinely disabled and carrying their own declared reason (`ADR-0070`),
and Enter reports that reason rather than a guess at where else to try.
Declining a prompt reports nothing at all — no toast, no status text, no
history — consistent with Stage 2's three-outcome design (declining is
not a failure). Ribbon: `RibbonObjectActionHandlers.cs` is deleted along
with `ObjectCreationHandlers`, the verb-suffix dispatch branches, the
duplicated eligibility derivation in `RefreshEnablement`, and the generic
fallback message. A click evaluates, then invokes; enablement asks the
same question. Two product decisions are now named explicitly in
`SurfaceCommandPolicy` rather than recovered by parsing an Id:
Rename/Edit open the Object Editor (`ADR-0096`/`ADR-0097`), and Delete
dispatches through `IWorkspaceManager.DeleteObjectAsync`, which is where a
successful delete clears the selection (`TD-58`). Both
`requirements.delete-group` and `requirements.revise`, permanently
unreachable before this stage, now work and are tested. Macro Manager:
eligibility comes from the binding, not `CreateDefault` — a step must
need nobody present, exactly what `CommandBinding.RequiresPrompt` already
answers, landing on the audited fourteen with every delete and duplicate
excluded by its own confirmation. A macro captures the selection at start
and replays it for every step, running with no prompt at all, so a legacy
macro naming a parameterised command fails honestly instead of
interrupting an unattended run with a dialog.

## 6. Alternatives Considered

Bypassing the deleted `RibbonObjectActionHandlers.cs` rather than deleting
it (leaving it as dead code alongside the new path) — rejected implicitly:
the commit deletes it outright, since a workaround left in place beside
its replacement invites the two drifting apart.

## 7. Why This Solution Was Chosen

Because all three surfaces asking the same framework, rather than each
maintaining its own partial answer, is what makes `requirements.delete-
group` and `requirements.revise` reachable at all — no amount of patching
the old Id-parser could have fixed those without eventually re-deriving
the framework this stage now consumes directly.

## 8. Architectural Principles

A behaviour change found along the way is disclosed rather than silently
absorbed: the old closures reported through a local `ReportAsync` —
status bar and toast only — and never raised `ActionCompleted`, so none
of the 31 wired commands was ever written to command history.
Consolidating on one reporting path fixes that, and the commit states the
change plainly rather than letting it pass unremarked.

## 9. Benefits

19 new tests. Five mutations designed, five killed. Core Debug/Release
3043 passed, Desktop Debug/Release 343 passed, all with
`TreatWarningsAsErrors=true`; governance health check exit 0.

## 10. Trade-offs

`RunMacroCommand` gained an optional context so steps can run
context-aware, required by the stage's own macro instruction — no
discipline command or handler, no `ICommandDispatcher`,
`CommandHandlerTable`, `IWorkspaceManager` or Core contract was touched,
keeping this stage's change scoped to the three consuming surfaces alone.

## 11. Common Mistakes

Letting a surface (the Ribbon) maintain its own parsing-based guess at a
command's requirements, drifting from what the command actually declares —
the exact defect that made two real commands permanently unreachable
until this stage asked the framework instead of the Id string.

## 12. Future Evolution

Per the WorkPackages.md notes for this row, `WP-A1`/`WP-A2`, later in the
remediation programme, finish the migration this five-stage sequence
began — closing `TD-105`/`TD-106`/`TD-113` and finding a fourth broken
surface the original audit missed (`MainWindow`'s Macro Manager running
every macro step against no context). `TD-77`'s own register row remains
Open even after this stage, since the parameter-binding/command-context
contract this migration delivers is the mechanism, not the row's own
closure — later Work Packages complete what this five-commit sequence
made possible.

## 13. Key Takeaways

- Three surfaces each maintaining a partial, independent answer to the
  same question will each be wrong in different ways — consolidate on one
  framework that actually knows the answer.
- Delete a superseded workaround outright rather than leaving it beside
  its replacement; a dead path left in place invites the two drifting
  apart.
- Disclose a behaviour change found incidentally (the command-history
  gap) rather than letting it pass as an unremarked side effect of a
  refactor.
