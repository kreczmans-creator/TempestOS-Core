# WP 15.0B — Desktop Productisation Phase 1

## 1. Introduction

`WP 15.0B` covers three commits (`257bac7`, `ee15986`, `0151f35`) merged
via `820d052`, labelled "Desktop Productisation Phase 1" at the time but
carrying no real Work Package number, `WorkPackages.md` row, or Academy
retrospective. Retroactively numbered and retrospected by `WP 15.1A`
(`v0.15.0` Release Preparation) — see §12.

## 2. Purpose

A first-party UX audit of the running application (not source inspection
alone) found navigation dead-ends, static/placeholder data on live
screens, and inconsistent chrome across `Tempest.Desktop`. This phase
closed the P0/P1 findings directly, judged too tightly coupled across
shared files to parallelise safely.

## 3. Background

Follows `WP 15.0A`'s brand recovery. Scope was set by direct application
inspection (screenshots, real interaction under Xvfb), not a pre-existing
backlog document.

## 4. The Problem

Findings, by commit:

- **`257bac7`** — the Object Editor's chrome predated the recovered brand
  theme: raw colours instead of `ChromeStyles`, emoji in place of the
  vector icon set, an unthemed title.
- **`ee15986`** — `ShellHeaderView`'s project chip was inert (no
  navigation); `ProjectExplorerView` lost selection and per-row child
  counts across a reload; `CockpitView` had no Engineering Overview KPI
  card; `ProjectBrowserView` did not open a project it had just created;
  `OutputPanelView` did not colour by severity; `ProjectDocumentsView` had
  no "Open in Engineering" affordance; `MacroManagerDialog` and five
  `Project*View.cs` files predated the recovered brand chrome;
  `MainMenuFactory` used hand-baked shortcut text instead of real
  `InputGesture` binding.
- **`0151f35`** — `MainMenuFactory`'s `InputGesture` wiring was
  incomplete; `DigitalThreadGraphView` still used emoji and untitled
  chrome; `ProjectExplorerView` had no per-row child counts on load, and
  no scroll-to-newly-created-item behaviour (`ICommandRegistry`/
  `ICommandDispatcher`'s `CommandResult` has no structured payload for
  this — a genuine, disclosed architectural gap, worked around at the
  Desktop layer via an Id-diff, not closed).

## 5. The Design

Real fixes against real, running-application findings: `ChromeStyles`/
`TitleFont`/icon-set application across the named views;
`ReturnToProjectAsync` wired to the project chip; selection persistence
and per-row counts via a Kind-keyed lookup already available to
`ProjectExplorerView`; a real KPI card bound to `EngineeringDomainContext`
reads, not placeholder text; auto-open on project creation;
severity-coloured output rows; a real "Open in Engineering" affordance;
`InputGesture` objects replacing hand-baked shortcut strings in
`MainMenuFactory`.

## 6. Alternatives Considered

Parallelising across background agents, as later done for Phase 2 —
rejected here: the shared files this phase touched (chrome styles, the
menu factory, the Explorer) were judged too tightly coupled for
independent agents to edit safely without collision.

## 7. Why This Solution Was Chosen

Direct, sequential implementation against verified, real application
behaviour (screenshots before/after, not just source reading) keeps the
UX findings honest — a placeholder screen that merely *looks* fixed in
source is not the same defect as one confirmed fixed by driving the real
UI.

## 8. Architectural Principles

No Workspace contract, Domain type, or command dispatch mechanism was
changed — every fix operates within `Tempest.Desktop`'s existing View/
Command boundary.

## 9. Benefits

Navigation dead-ends closed; the Cockpit, Explorer, and menu system now
reflect real, live data and real keyboard affordances rather than
placeholders.

## 10. Trade-offs

**Test pass-count figures in `257bac7`/`ee15986`/`0151f35`'s own commit
messages are unreliable and are not repeated as fact here.** Each cites a
Desktop-suite figure with a non-zero failure count (e.g. "373/386") and a
Core-suite figure ("3056/3088, identical 32-failure set") obtained using
what was later found to be a flawed local SDK-substitution technique
(deleting `global.json` rather than editing its SDK version field in
place) — a technique since corrected precisely because it manufactures
exactly this shape of false failure (see `WP 15.1A`'s own Release
Preparation Report, §"Verified," for the full account). The true,
currently-verified baseline for this code — via the corrected technique
and confirmed independently by real GitHub-hosted CI (workflow run
`33777775658`, `820d052`, all four jobs green) — is 0 failures both
configurations.

## 11. Common Mistakes

**Treating a local workaround's side effects as real test failures.**
Deleting `global.json` to dodge an unavailable pinned SDK version also
breaks `DesktopTestHelpers.RepositoryRoot`'s marker-file search,
manufacturing failures that have nothing to do with the code under test.

## 12. Future Evolution

Retrospective written after the fact by `WP 15.1A`, from commit evidence
only — no Stage 1 audit report is preserved in the repository for any of
the three commits. Per `WP-Z3`'s own disclosed convention, fine detail
beyond what the commits themselves record is not reconstructed.

## 13. Key Takeaways

- A UX audit against the *running* application finds defects source
  review alone does not (an inert chip, a screen that never refreshes).
- A local verification workaround can itself be the source of a reported
  failure — verify the workaround before trusting its output.
- Tightly-coupled shared-file changes are a legitimate reason to forgo
  parallelisation, even when it is available.
