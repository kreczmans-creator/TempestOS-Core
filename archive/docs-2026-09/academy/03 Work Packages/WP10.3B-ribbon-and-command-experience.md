# `WP 10.3B` — Ribbon, Toolbar & Command Experience

## 1. Introduction

`v0.10.0`'s own eighth Work Package — a professional command system
for `Tempest.Desktop`: a real, tabbed Engineering Ribbon, a Quick
Access Toolbar, and command discoverability/context-awareness
features, integrated directly with the existing `ICommandRegistry` and
Command Palette, without bypassing `ADR-0070` or building a second
command framework.

## 2. Purpose

Implementation retrospective, mirroring `WP10.3A`'s own two-part
(Concept Guide, Implementation Retrospective) structure. See
`26-ribbon-and-command-experience.md` for the design narrative; this
file focuses on what was built, files touched, and honest disclosure
of this Work Package's own two genuine findings.

## 3. Background

Commissioned directly after `WP 10.3A` (Engineering Object Editors)
closed with "await Product Owner instruction before `WP 10.3B`." This
Work Package's own controlling instruction named fifteen scope items,
five explicit exclusions, and four dispatch-discipline constraints
("integrate directly," "do not duplicate command registration," "do
not bypass `ADR-0070`," "every graphical command shall dispatch the
existing command implementation") — the first `v0.10.0` Work Package
to explicitly *want* a ribbon, reversing every prior Work Package's
own "No ribbon" exclusion.

## 4. The Problem

See `26-ribbon-and-command-experience.md` §4 — no discipline-command-
aware surface existed anywhere in `Tempest.Desktop` beyond the Project
Explorer's own context menu and the Command Palette.

## 5. The Design

See `26-ribbon-and-command-experience.md` §5. In summary: `RibbonView`
(new, `Tempest.Desktop.Views`) — one generic engine, tabbed by
`CommandDescriptor.Category`, grouped/iconed by a deterministic verb-
suffix heuristic, dispatching Delete/Rename/Edit through the real,
already-Kind-keyed `IWorkspaceManager` verbs and honestly reporting
everything else as undispatchable from a button click alone. Two
genuine defects found and fixed before commit — see §12.

## 12. Future Evolution

See `26-ribbon-and-command-experience.md` §12 (`FCR-0069`).

**Two genuine, disclosed findings, both fixed before commit:**

1. **`CommandPaletteOverlay`'s own silent no-op** — pressing `Enter`
   on any real command (every one has `CreateDefault == null`)
   previously closed the palette and did nothing else, with zero
   feedback, since `WP 8.1A`. A pre-existing defect, found while
   designing the Ribbon's own identical case, fixed at its own source.
2. **`RibbonView.Rebuild()`'s own missed initial enablement** — every
   selection-aware button defaulted to enabled regardless of whether a
   real selection existed, until the first external
   `RefreshEnablement()` call. Found by this Work Package's own test
   suite, before any commit, fixed at its own source.

## 13. Key Takeaways

Fifteen named scope items realised via one generic Ribbon engine, zero
new Workspace/Domain/Runtime surface, zero new command framework;
selection-aware dispatch honestly limited to the two verbs that
structurally need no more input than a click, reusing `ADR-0096`/
`ADR-0097` directly; two genuine defects (one pre-existing, one new)
found and fixed before commit, both by direct code discovery/test
failure, not by assumption.

## Architectural Debt Assessment

**No new items.** `FCR-0069` (Real, Authored Per-Command Icons) is
recorded as a Future Capability, not a defect — the deterministic
verb-derived fallback is a genuine, working, disclosed design choice,
not an unfinished implementation. Every pre-existing item
(`TD-01`–`TD-40`) reviewed and confirmed unaffected by this Work
Package's own diff.

## Observations

**A genuine, six-Work-Package-latent defect, only visible once someone
needed to build the identical "cannot dispatch by Id" case honestly.**
`CommandPaletteOverlay.InvokeSelectedAsync`'s own silent no-op existed,
unnoticed, from `WP 8.1A`/`WP 10.0B` through `WP 10.3A` — six real
Work Packages, roughly eighty real commands registered, and not one
of them was ever actually invokable via the Palette's own `Enter` key,
because `CreateDefault` was never set. No prior Work Package's own
test suite caught it, since `CommandPaletteOverlayTests.cs` only ever
tested Open/Close, never a real confirm-and-invoke path. Found here
specifically because this Work Package's own Ribbon needed to answer
the identical "what happens when the user tries to run a command with
no dispatch route" question for itself, and answering it honestly for
the Ribbon exposed the Palette's own silent handling of the same
question.

**`WorkspaceDockPosition.Bottom`, `ReviseMechanicalObjectCommand`, and
now this Palette defect all share a shape**: each is a real capability
gap that sat, compiled and untested against the specific failure
mode, for multiple Work Packages, found only when a *later* Work
Package's own different feature happened to need the identical
capability and built it honestly enough to notice the gap. Named here
as a recurring pattern worth the Academy's own future attention, not
merely coincidence three times over.
