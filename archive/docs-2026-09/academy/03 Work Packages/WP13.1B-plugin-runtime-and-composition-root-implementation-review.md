# WP 13.1B — Plugin Runtime & Composition Root Implementation Review

## What This Document Is

The retrospective for `WP 13.1B`, an independent review/verification Work
Package auditing `WP 13.1A` (Plugin Runtime & Composition Root
Implementation) before it becomes a real commit. On `feature/v0.13.0`,
mirroring exactly the review-before-baseline discipline `WP 13.0B`
established one Work Package earlier for `WP 13.0A`'s own architecture —
applied here, for the first time, to real production code rather than
documentation. Four parallel, genuinely independent audit sub-agents —
Code Review, Architecture Compliance, Verification & Test Audit,
Governance & Documentation Audit — none of which authored any `WP 13.1A`
material, each instructed to assume defects exist until personally
disproven, not to confirm the work is fine by default.

## A Note on This Work Package's Own Number

**By direct instruction, this Work Package claims the `WP 13.1B` label —
not by roadmap prediction, and not without a disclosed collision.**
`docs/releases/v0.13.0/WorkPackages.md`'s own roadmap-predicted table
already carried a `WP 13.1B` row before this Work Package existed: "REST
API Authentication & TLS Implementation," Not started. That is a real,
different, still-uncommissioned Work Package — unrelated to plugins —
and it still needs a number of its own when it is actually commissioned
later. This Work Package (Plugin Runtime & Composition Root
Implementation Review) was assigned `WP 13.1B` directly, the identical
pattern `WP 13.1A` itself disclosed one Work Package earlier for its own
collision with the roadmap's REST API Architecture row. The divergence
is disclosed here plainly, mirroring exactly how `WorkPackages.md`
already discloses both prior instances rather than silently reconciling
any of them.

## Root Cause (What the Audit Was Checking For)

`WP 13.1A` implemented a genuinely hard piece of code — a fixed-point
dependency-graph reduction, three-colour cycle detection, and a Kahn's-
algorithm topological sort, plus a new configuration-precedence chain in
`TempestHost.cs` — the highest-complexity production code this plugin
platform has ever shipped. This project's own history (`WP 12.9.0`'s
same-day Architecture Review Follow-Up catching a real ADR Register
omission; `WP 13.0B` catching real documentation defects in `WP 13.0A`)
establishes that even careful, contract-driven implementation work
benefits from a second, genuinely independent pass before it becomes
permanent. `WP 13.1B` exists to perform that pass for real code, not
merely documentation, for the first time in this release.

## What Changed

**Four independent audits, two genuine, empirically-confirmed production
bugs found and fixed — the first real code defects any review in this
project's `v0.13.0` history has found.**

**Architecture Compliance** — verdict **PASS**, zero blocking findings.
Verified point-by-point against `ADR-0107`/`ADR-0108`/`ADR-0109`: no new
Host Lifecycle phase; all three new failure categories (12–14) isolated
by construction, never Host-fatal; no live-unload capability introduced
anywhere; **`PluginRegistry`/`IPluginRegistry` confirmed never registered
into the DI `ServiceCollection`** (`ADR-0017`/`ADR-0109`'s own boundary,
treated as automatically Blocking had it been violated — it was not); a
full 111-ADR contradiction sweep found no drift. Two non-blocking
observations, both about `ADR-0107`'s own illustrative prose being less
precise than the (correctly implemented) code — not code defects, and
explicitly out of this Work Package's own scope to correct, since the
architecture itself is frozen.

**Code Review** — verdict **FAIL**, two blocking, empirically-confirmed
bugs, both fixed:

1. `PluginManifestDiscoveryService.TopologicalSort`'s
   `remainingDependencyCount` was initialised from raw
   `Dependencies.Count` (including duplicate target declarations) but
   decremented once per distinct target removed — a manifest declaring
   the same dependency `Id` twice (legal, unrejected input) caused that
   candidate's count to never reach zero, silently dropping it from the
   topological sort with **no isolation, no log line, and no registry
   entry** — a direct violation of `ADR-0025`/`ADR-0107`'s own "always
   logged, never silently swallowed" guarantee. Confirmed by direct
   repro before any fix was applied. **Fixed**: the count is now keyed
   on distinct dependency targets (`Dependencies.Select(d => d.Id).Distinct()`),
   matching the decrement logic's own once-per-target semantics exactly.
2. `TempestHost.cs`'s configuration-precedence `??` chain for
   `Runtime:Plugins:RootDirectory`/`ManifestFileName` only substituted on
   `null`, not on an empty or whitespace-only configured value — a
   single blank configuration entry (an empty environment variable, a
   blank JSON field) reached `PluginManifestDiscoveryService`'s own
   `ArgumentException.ThrowIfNullOrWhiteSpace` guard uncaught, **faulting
   the entire Host**, not merely isolating one plugin — confirmed by
   direct repro. **Fixed**: both precedence chains now treat a blank
   configured value as absent, falling back to the next precedence
   level exactly as an omitted key already did.

**Verification & Test Audit** — verdict **FAIL** (qualified), independently
re-ran the full build/test matrix itself and, separately from the Code
Review workstream, converged on the *same two gaps* by judging test
completeness against the real algorithm's edge cases — strong
triangulated evidence both bugs were real, not hypothetical. Also
surfaced and correctly diagnosed a genuinely pre-existing, unrelated
test-isolation flake (`CompositeLogSinkTests.Write_AllSinksThrow_ExceptionNeverPropagatesToTheCaller`,
a `Console.Error`-swapping race with an unrelated test class, confirmed
non-reproducible on two clean isolated/full-suite reruns) — disclosed,
not fixed, since it predates and is unrelated to `WP 13.1A`. Two further
non-blocking observations: `DiagnosticsProviderTests.cs` lacked
dedicated unit-level coverage for the new `Plugins` property and its
constructor's null-guard, breaking that file's own established
per-property convention; `PluginRegistryTests.cs`'s exception-mapping
table covered `RecordIsolatedFailure` but not a consolidated
`SeverityFor` table. Both closed.

**Governance & Documentation Audit** — verdict **PASS**, zero defects.
Independently re-ran `governance-healthcheck.ps1` (7 passed/1 warned/0
failed) and its own full Release regression (2,084/221, matching every
document's claim exactly), fact-checked twenty specific, checkable
claims against the real source (double the required ten), and correctly
declined to flag a genuinely pre-existing, unrelated stale paragraph in
the Technical Debt Register as a finding, per its own scope discipline.

**Every fix applied was a defect `WP 13.1A` itself introduced.** Eight
new regression tests were added closing exactly the gaps found: two
proving the duplicate-dependency fix (a two-plugin case where the
dependent declares its one real dependency twice), two proving the
blank-configuration-value fix (an empty `RootDirectory`, a
whitespace-only `ManifestFileName`, both confirmed to fall back to
default and reach `Running` rather than `Faulted`), and four closing the
`DiagnosticsProviderTests.cs` gap (a null-registry constructor guard,
and three tests mirroring `Modules`/`HostedServices`'s own established
shape for the new `Plugins` property — though, unlike those two,
`Plugins` is a direct reference, not a `Func<T>` accessor, so there is
no "not yet attached" transition to prove, only live reflection of the
registry's current contents).

## Verification

`governance-healthcheck.ps1`, re-run after every fix: **7 passed, 1
warned, 0 failed, exit code 0** — identical shape to `WP 13.1A`'s own
closing baseline. Debug and Release builds both **0 Warnings, 0 Errors**
(`-p:TreatWarningsAsErrors=true`), independently re-run by the
orchestrator after every fix, not assumed from any sub-agent's own
report. Full regression, **both configurations, independently re-run**:
**2,313 / 2,313 passing, 0 failed** (2,092 `Tempest.Core.Tests` + 221
`Tempest.Desktop.Tests`) — 2,305 from `WP 13.1A`'s own closing baseline
plus the 8 new regression tests this Work Package added. No new
Technical Debt introduced — both fixes close genuine, in-scope defects
rather than deferring them; nothing warranted a new debt entry. No ADR
changes required or made — confirmed independently by two of the four
audit workstreams; zero files under `docs/adr/` touched by this Work
Package.

## Scope Confirmation

Code-correctness and test-completeness fixes only, strictly bounded to
defects `WP 13.1A` itself introduced. Every fix applied was either (a) a
precise, minimal correction to the exact line the bug lived on
(`TopologicalSort`'s count initialisation; `TempestHost.cs`'s two
precedence chains), or (b) a new regression test proving a fix or
closing a genuine, named coverage gap a sibling audit identified —
never a new architectural decision, never a broadened scope, never
speculative hardening beyond what was actually found. `TD-09`/`TD-10`/
`TD-11` (trust enforcement) remain exactly as open as `WP 13.1A` left
them — untouched, correctly out of scope. Following this review, `WP
13.1A`'s and `WP 13.1B`'s combined work is committed as a single
reviewed implementation baseline to `feature/v0.13.0` — not pushed, per
this Work Package's own explicit instruction. See `PROJECT_STATUS.md`
and this commit's own message for the exact commit SHA.
