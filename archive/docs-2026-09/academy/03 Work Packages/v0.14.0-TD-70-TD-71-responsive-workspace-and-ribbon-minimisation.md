# TD-70 + TD-71 — Responsive Workspace, Ribbon Minimisation, Drag as a Durable Preference

## 1. Introduction

`e40a3d6` closed `TD-70` and `TD-71`: the desktop workspace gained a real
responsive layout and a minimisable ribbon, and a `GridSplitter` drag
finally updated the preferred width it was supposed to. A pre-`v0.14.0`
engineering-body-of-work row; the technical detail lives in the companion
Academy runtime-architecture article this commit also indexed
(`docs/academy/02 Runtime Architecture/32-responsive-workspace-and-ribbon-
minimisation.md`), which this retrospective complements with the decision
record that article does not carry.

## 2. Purpose

To make the workspace adapt to the space it is given, and to make a panel
resize the user performs by dragging actually persist.

## 3. Background

Both side docks were declared `ColumnDefinition(240, GridUnitType.Pixel)`
— fixed — with only the centre column `Star`, so every pixel a shrinking
window lost came out of the Document Area. At the application's own
`MinWidth` of 960px, the two side panels consumed half the window; the
ribbon held a further fixed 145px with no minimise affordance. Confirmed
categorical by repository-wide search: no `SizeChanged` handler, no
`Bounds` observation, no breakpoint and no compact mode existed anywhere
in `Tempest.Desktop`. Measured empirically on the real `MainWindow` at
seven widths by a headless probe before any change was made. Separately, a
`GridSplitter` drag mutated the `ColumnDefinition` directly and never
called `SetLeftWidth`, so hiding and re-showing a panel after dragging it
silently reverted to the pre-drag width — undetected because the existing
suite drove `SetLeftWidth`, not the drag path itself.

## 4. The Problem

A user who shrank the window lost usable document space disproportionately
and had no way to reclaim it short of resizing the whole window back. A
user who dragged a splitter to a size they wanted lost that choice the
moment they hid and re-showed the panel.

## 5. The Design

`DockingGrid.ApplyResponsiveLayout` observes `Bounds` and fits the docks
into what remains after reserving `MinDocumentAreaWidth` (420px) and
`MinDocumentAreaHeight` (220px): unchanged when they already fit, squeezed
proportionally when they do not, and collapsed to a 32px strip rather than
squeezed below a readable `MinUsablePanelSize` (140px). The user's own
preferred sizes are held separately from the applied widths and restored
in full when the window grows back — a responsive rule must never rewrite
user intent. `RibbonView.SetCollapsed`/`ToggleCollapsed` minimises the
ribbon to its tab strip, persisted via `DesktopPanelUiState.RibbonCollapsed`,
with every tab header kept reachable so no command is lost.
`NotifyLeftPanelResized`/`NotifyRightPanelResized`/`NotifyBottomPanelResized`
now record the dragged size as the new preference.

## 6. Alternatives Considered

None recorded as rejected; the fix follows directly from the measured
gap — no responsive rule existed at all, so the design is the minimal one
that closes it without weakening user intent.

## 7. Why This Solution Was Chosen

Because the clamp preserves the common case exactly: a window that already
fits is unaffected, and only a window that does not fit is squeezed, never
below a readable floor. Preserving the user's preferred size separately
from the applied size is what keeps a responsive rule from quietly
becoming a permanent resize.

## 8. Architectural Principles

A responsive layout rule must be provably distinct from a permanent
resize: it changes what is applied, never what is preferred, and both
must be independently testable.

## 9. Benefits

`ResponsiveWorkspaceTests` adds 12 tests including a seven-width theory;
three mutations run and killed (clamp disabled fails 5, ribbon collapse
no-op fails 2, drag preference removed fails 1). The drag mutation
survived the first version of its own test — which drove `SetLeftWidth`
instead of the column, the wrong path — and only the mutation exposed
that the assertion had been right through the wrong path.

## 10. Trade-offs

Residual compact/icon-only presentation and the 960×600 floor are tracked
separately as `TD-73`, deliberately not folded into this closure.

## 11. Common Mistakes

Driving a test through the API a fix happens to also use (`SetLeftWidth`)
rather than through the real user interaction (a `GridSplitter` drag) —
exactly the gap that let `TD-71` go undetected in the first place, and
that the drag mutation caught a second time in the closure test itself.

## 12. Future Evolution

`TD-72`, later the same release, replaces the fixed three-dock geometry
this row made responsive with a data-driven layout tree, preserving this
row's responsive rule — and, per that row's own closure notes, wiring it
to the window's own resize for the first time, closing a gap `TD-83`
records where the guarantee existed but only tests had ever invoked it.

## 13. Key Takeaways

- Measure the defect empirically (a headless probe at seven widths) before
  writing the fix, so the fix has a target rather than a guess.
- A responsive rule that overwrites user intent is not a responsive rule.
- Drive a regression test through the real interaction path, not through
  whichever API is convenient — the gap between the two is exactly where
  `TD-71` had been hiding.
