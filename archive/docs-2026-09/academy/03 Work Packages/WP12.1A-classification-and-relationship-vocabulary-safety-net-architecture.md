# WP 12.1A — Classification & Relationship Vocabulary Safety Net Architecture

## What This Document Is

The architecture-phase retrospective for `WP 12.1A`, the roadmap-defined
Work Package realising `WP11.0A Platform Architecture Review.md`
Finding `A-6` ("Domain classification/relationship vocabulary is
entirely stringly-typed, by deliberate design, with no compile-time
safety net"). Architecture only — no code; `WP 12.1B`, already named
in `WP11.0B Architecture Roadmap.md` §3, is this Work Package's own
paired implementation successor.

## 1. Introduction

`A-6` was raised, not fixed, by `WP 11.0A`'s own platform-wide review —
recommended "before v1.0," not release-blocking, and deliberately
narrow in its own suggested remedy: "a lightweight, additive safety
net... would preserve `ADR-0073`'s open-string contract while catching
the failure mode this pattern is most exposed to." `WP 12.1A` was
commissioned to investigate that recommendation directly, across every
shipped discipline and layer, rather than assume its shape or scope in
advance — auditing `Tempest.Core`, `Tempest.App`, and `Tempest.Desktop`
for every classification and relationship vocabulary currently in use,
identifying every confirmed instance of duplication or drift, and
designing a canonical model that closes the confirmed gaps without
reopening any of the five prior ADRs that already, deliberately, chose
an open-string vocabulary over a closed or validated one.

## 2. What Was Found

**Five prior ADRs already, independently, settle "should this
vocabulary be a closed type" — every one of them says no, for the
identical extensibility reason.** `ADR-0072` (Kind is an open string,
never a closed type). `ADR-0073` (`RelationshipKind` is open,
unvalidated). `ADR-0076` (`RelationshipCategory` is descriptive
metadata only). `ADR-0088`/`ADR-0091` (Document/Manufacturing
sub-classification is a free-text `Classification` string, a
Workspace-layer `const` catalogue, never a Domain-layer enum) — each
rejecting a closed set because it cannot scale to an extensible,
module-defined object catalogue without becoming a platform-review
bottleneck. None of these five is reopened by this Work Package.

**`ADR-0090` is direct, in-repository evidence that `Classification`-
tagging is not universally the right sub-typing axis.** Verification
deliberately chose `LifecycleState` over `Classification` for
Plan/Activity, reasoning explicitly that a second field for one
distinction would be "never reconciled against each other, a genuine
source of drift `ADR-0088`'s own single-field design does not risk."
This directly shaped the canonical model's own first rule: govern
*where* a chosen value is declared, never *which facet* a discipline
should choose to carry a distinction.

**The confirmed gap is real, and precisely bounded — not "the whole
vocabulary is undisciplined," but "the declare-once discipline that
already, independently, proves itself twice is not applied uniformly."**
Four `Tempest.Core` frameworks (Requirements, Verification,
Calculations, Materials) already declare their own Kind values as
named `public const string` constants. Two Workspace disciplines
(Documents, Manufacturing) already declare their own `Classification`
sub-values the identical way, each under its own ADR (`ADR-0088`,
`ADR-0091`) — but, inconsistently, *within those same two files*,
their own base Kind strings do not receive the same treatment, existing
only inside a `SupportedKinds` array literal. Mechanical declares no
constant for any of its own eight Kinds, at all.

**Quantified, not estimated.** The literal Kind string `"Part"` is
written out at 14 separate sites across 5 different `src/` files
spanning three layers (`Tempest.Samples`, `Tempest.App`,
`Tempest.Desktop`), zero of them referencing a shared constant, because
none exists. `Tempest.Desktop.DigitalThread.DigitalThreadGraphModel`
independently declares `private const string VerifiedByRelationshipKind
= "verifiedBy";` — the identical value and name already declared as
the real, owning constant on `Tempest.Core.Verification.VerificationService`
— a concrete, present instance of the exact drift `A-6`'s own Impact
statement described only in the abstract.

**A real, working, partial safety net for relationship kinds already
exists and already proves the eventual shape works.**
`RelationshipKindCategoryMap` infers a `RelationshipCategory` from 17
named, conventional `RelationshipKind` strings, defaulting
non-blockingly to `Reference` for anything unrecognised — never
throwing, never rejecting a write. The identical defensive shape
appears independently a second and third time in `DocumentCategory.Of`/
`ManufacturingCategory.Of`, each falling back to an honest
`"Uncategorized"` label. `WP8.2A Canonical Object/Relationship
Catalogue.md` already proves the documentation-layer half of the idea
works, and — confirmed directly — has already been kept current past
its own originating Work Package (`calculatedBy`/`manufacturedBy`, both
added later, are both present).

**Digital Thread compatibility confirmed low-risk directly, not by
inference.** `DigitalThreadGraphModel` — the platform's own most
vocabulary-hungry consumer — is fully Kind-agnostic and
`RelationshipKind`-agnostic except for exactly its own two hand-typed
local duplicates, the confirmed defect above. Generalising the
declare-once discipline requires no change to its own generic read
path at all.

## 3. Architectural Lessons

**A platform-wide safety net does not have to be a new mechanism — it
can be the generalisation of a pattern that has already, independently,
proven itself more than once.** `RequirementRelationshipKinds`,
`RelationshipKindCategoryMap`, and `DocumentObjectFactoryRegistry`/
`ManufacturingObjectFactoryRegistry`'s own `Classification` constants
are three separate, already-shipped, already-working instances of the
identical underlying idea (declare a value once, by name; degrade
honestly, never block, for anything unrecognised). The architectural
work here was recognising the convergence and naming it once, platform-
wide — the same "reuse what exists" resolution this project has reached
repeatedly (`ADR-0072`, `ADR-0067`, `ADR-0099`), applied a further
time.

**Finding real, confirmed duplication changes an investigation's own
argument from "this could theoretically drift" to "this has already
drifted."** `A-6`'s own Impact statement was written in the abstract
("a typo... fails at runtime, not compile time"). Finding the actual,
present `VerifiedByRelationshipKind` duplicate — not a hypothetical
one — turned the case for `ADR-0105` from a plausible precaution into
a demonstrated defect with a named fix, the identical evidentiary
standard this project's own ADRs consistently hold themselves to (see,
for one example among many, `ADR-0103`'s own `WorkspaceViewCoordinator`
citation).

**A canonical model can — and, here, must — explicitly decline to
answer a question adjacent to its own.** `ADR-0090`'s own deliberate
choice of `LifecycleState` over `Classification` meant this Work
Package's own model had to be phrased as "govern where a value is
declared," not "always tag sub-types with `Classification`" — a
narrower, more defensible rule that a broader one would have
contradicted a real, already-shipped, already-reasoned decision.

## 4. Key Takeaways

- **`A-6` is now precisely scoped, not merely reconfirmed**: the
  confirmed gap is "declaration discipline is inconsistently applied,"
  not "the vocabulary itself needs redesigning" — five prior ADRs'
  own open-string reasoning is reaffirmed, unmodified, in every case.
- **Two concrete, named defects anchor `WP 12.1B`'s own minimum
  scope**: the `VerifiedByRelationshipKind` cross-layer duplicate, and
  Mechanical's own complete absence of declared Kind constants — real,
  not hypothetical, retrofit targets.
- **`ADR-0105` — new**: every live Kind/`Classification`/
  `RelationshipKind` value is declared exactly once, as a named
  constant, on its owning class; a new governance register
  (Engineering Vocabulary Register) tracks every value platform-wide;
  a single, additive xUnit test catches exact-value collisions and
  register/code drift. None of this validates a value at write time —
  `ADR-0073`/`ADR-0076`/`ADR-0088`/`ADR-0090`/`ADR-0091` are all
  reaffirmed, none amended.
- **Four alternatives evaluated and rejected on real evidence, not
  by inference from an existing ADR alone**: a closed enum (already
  rejected five times, independently); a strongly-typed value object
  (no material benefit over a plain constant, real adoption cost); a
  runtime, DI-resolved registry service (misclassifies a documentation
  concern as a Platform Service, the identical reasoning `ADR-0104`
  just applied to Desktop wiring); a fully free-form metadata model
  (a genuine `IHasMetadata` contract redesign, widening rather than
  narrowing the coordination problem).
