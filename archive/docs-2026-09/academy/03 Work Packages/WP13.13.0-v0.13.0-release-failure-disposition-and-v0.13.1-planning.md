# WP 13.13.0 — v0.13.0 Release Failure Disposition & v0.13.1 Planning

## 1. Introduction

`WP 13.13.0` is **release-engineering analysis only**. It wrote no code,
changed no documentation, produced no commit, and created, moved or
deleted no tag. Its entire deliverable is a reasoned disposition of a
question the preceding two Work Packages had deliberately left open:
`v0.13.0` is tagged, merged, and unpublished — what now?

Its answer, reached from the project's own governance rather than from
first principles, is that `v0.13.0` stays exactly as it is, permanently,
as a valid but unpublished historical tag, and that a `v0.13.1` is the
only conforming route to a published release of the same content.

## 2. Purpose

To determine, before anyone acted, which corrective options this
project's own rules actually permit — and to establish the factual
position (topology, delta, tagged-tree integrity) that any such decision
must rest on.

## 3. Background

`WP 13.12.7` pushed the `v0.13.0` tag; the tag-triggered `release.yml`
run failed at `Test (Release)`, so packaging and publication were
skipped. `WP 13.12.8` diagnosed the cause as a genuine intermittent test
flake matching `TD-46`. `WP 13.12.9` remediated it, test-only.
`WP 13.12.10` recorded the resulting state in the Release Register as
"Tagged and merged to `main` — GitHub Release not published."

That left the tag pointing at a commit whose test suite is now known to
contain a flaky assertion, with a fix sitting two commits later, on
`main`, that the tag cannot see.

## 4. The Problem

The tempting move is obvious and wrong: the fix is trivial, the product
is not defective, and `main` is two commits ahead of a tag that is only
"wrong" by a timing race. Delete the tag, recreate it on `ea3fe07`,
re-run `release.yml`, publish, done.

Three distinct questions had to be answered before anyone could act:

1. **Is the tagged content actually defective?** If `src/` had changed
   since the tag, `v0.13.0`'s tree would not be the release anyone
   intended, and the disposition would be different.
2. **Does any rule in this project permit re-tagging here?** Governance
   §7.4 forbids it in general but carries a narrow, `WP 11.4B`-added
   exception — and `v0.11.0` used it. Does it reach this case?
3. **What is the conforming remedy, and what does taking it cost?**

## 5. The Design

The Work Package's method was verification first, governance second,
recommendation last.

**Verified topology.** `6089a218 → 7449756 → ea3fe07` — linear, **zero
merge commits**. `7449756` is test-only; `ea3fe07` is
documentation-only.

**Verified delta over the tagged tree.** Two files, `+35/−5`, with
**zero `src/` files**. The `v0.13.0` tagged tree is therefore untouched
in every production respect: the release's own content is exactly what
was tagged.

**Governance analysis, from the project's own documents.**

- **§7.4 bars re-tagging.** "A tag, once created and pushed, is not moved
  or recreated; if a mistake is discovered after tagging, a new version
  and a new tag are cut, the old one is never silently altered."
- **`WP 11.4B`'s exception cannot reach this case, on two independent
  grounds.** First, it is bounded to a tag's *mechanical position* —
  `05-release-engineering.md` states it "touches only a tag's own
  mechanical position, never its release content," and never build or
  test evidence. Second, it applies only to a defect found **before
  closure of the release branch**; `v0.13.0`'s branch had closed, the
  merge into `main` having already happened. Either ground alone
  disposes of it.
- **Rollback in this project is always forward.**
  `05-release-engineering.md` is explicit: a defective release found
  after its own branch closes is never un-tagged; the remedy is a
  superseding release.
- **`release.yml` already names the remedy in its own source.** The
  inline comment immediately above the `Test (Release)` step reads: "Per
  Engineering Governance §7.4, a pushed tag is never moved or recreated -
  if this happens, the corrective action is a new patch version and a new
  tag (see 'Rollback Procedure'), never editing this one."

**Two facts recorded as consequences.**

- **`v0.13.1` would be the project's first non-zero patch version.**
  Every tag from `v0.3.0` to `v0.13.0` is `0.Y.0`.
  `05-release-engineering.md` defines PATCH narrowly — "a hotfix, and
  only a hotfix, never a vehicle for new capability" — which the
  test-only and documentation-only delta satisfies.
- **`TD-45` is now demonstrably unenforceable.** Per this Work Package's
  own record, branch protection returns HTTP 403 on this repository plan,
  so §7.7's PR/CI gate is upheld by discipline, not by tooling. `TD-45`
  had until now been disclosed as merely "not configured"; this is a
  stronger finding — it *cannot* be configured here.

**Recommendation.** Leave `v0.13.0` permanently as a valid but
unpublished historical tag.

## 6. Alternatives Considered

**Delete and recreate the `v0.13.0` tag on `ea3fe07`.** Rejected —
barred by §7.4, and unreachable by `WP 11.4B`'s exception on both of the
grounds above. It would also make the tag point at content the release's
own documentation never described.

**Re-run `release.yml` against the existing tag.** Rejected. The tag's
tree still contains the flaky delay, so the re-run would be a coin toss
on the very assertion that failed; and a green re-run would publish a
release whose test suite the project knows to be non-deterministic.

**Publish a GitHub Release manually against `v0.13.0`.** Rejected — it
would fabricate the outcome of a gate that did not pass, defeating the
purpose of having `release.yml` gate publication at all.

**Edit the GitHub Release description to mark it superseded.** Not
applicable: `05-release-engineering.md`'s one narrow rollback exception
permits editing a Release's description, but here **no Release object
exists** — the publish step never ran.

**Leave `v0.13.0` as the latest release indefinitely and defer.**
Rejected — the fix already exists on `main`, and the project would carry
an unpublished head release for no benefit.

**Cut `v0.14.0` instead of `v0.13.1`.** Rejected — a MINOR bump signals
new capability; the delta is two files, test-only and
documentation-only. PATCH is the honest semantic.

## 7. Why This Solution Was Chosen

Because every element of the answer was already written down in this
project, by this project, before the situation arose — §7.4, the
`WP 11.4B` exception and its two boundaries, the forward-rollback rule,
the PATCH definition, and `release.yml`'s own inline comment. The
analysis's contribution was not to invent a policy but to establish that
the existing policy has an unambiguous answer here, and that the
convenient shortcut is barred twice over.

It was also chosen because the verification came first. Had the delta
touched `src/`, the recommendation would necessarily have differed —
"the tagged tree is untouched" is what makes `v0.13.0` a *valid* tag
rather than merely an unpublished one.

## 8. Architectural Principles

- **Immutable tags, forward-only rollback.** A published tag is a fact
  about history, not a mutable pointer.
- **A narrow exception stays narrow.** `WP 11.4B`'s carve-out exists for
  a tag's mechanical position before branch closure; using it for a
  failed test gate would convert a bounded exception into a general
  licence.
- **Verify before you dispose.** Topology and delta first; policy
  reasoning second.
- **Analysis is a legitimate deliverable.** A Work Package that changes
  no file but prevents an irreversible mistake has done real work.
- **Decision authority is not the analyst's.** Per Governance §9,
  version numbering, release timing, tagging and pushing are Product
  Approval's; this Work Package produced a recommendation, not an
  action.

## 9. Benefits

- The irreversible option — deleting a pushed tag — was examined and
  ruled out *before* anyone could take it.
- The factual position is now on record and independently checkable:
  linear topology, zero merges, 2 files `+35/−5`, zero `src/`.
- The `WP 11.4B` exception's boundaries are stated explicitly, which
  matters because `v0.11.0`'s successful use of it is exactly the
  precedent someone would reach for next time.
- `TD-45` moves from "not configured" to "demonstrably unenforceable on
  this repository plan" — a materially different risk statement.
- The route to a publishable release was identified without touching
  anything.

## 10. Trade-offs

- **`v0.13.0` stays permanently unpublished.** The project's headline
  release for "Trust & Deployment Hardening" has a tag and no
  downloadable artefact. That is the cost of tag immutability, and it is
  accepted rather than engineered around.
- **A version number is spent for a two-file delta.** `v0.13.1` exists
  because of a `Task.Delay`, which will look disproportionate to a future
  reader who does not read this record.
- **The project's first non-zero patch version arrives as a process
  correction**, not as the emergency hotfix `05-release-engineering.md`
  envisaged when it defined PATCH.
- **The recommendation binds nobody.** Analysis cannot authorise a
  release; Product Approval must still act.
- **`TD-45` is not closed by this finding**, only sharpened — the PR/CI
  gate remains upheld by discipline.

## 11. Common Mistakes

- Treating "the fix is trivial" as an argument about *policy*. The size
  of a diff has no bearing on whether a tag may be moved.
- Reading `v0.11.0`'s tag correction as a general re-tagging precedent,
  without checking either of the two conditions that made it lawful.
- Assuming a failed release can be salvaged by re-running the workflow —
  the tagged tree, not the workflow, held the defect.
- Publishing a Release by hand to make a gate's outcome look satisfied.
- Confusing rollback's description-edit exception with the `WP 11.4B`
  tag exception; `05-release-engineering.md` states plainly that the two
  are not interchangeable.
- Skipping the retrospective because no file changed. The reasoning *is*
  the artefact.

## 12. Future Evolution

The obvious successor is the release this analysis pointed to, and the
record shows it followed: `WP 13.13.1` cut `release/v0.13.1` from `main`
at `ea3fe07`, bumped `VERSION`, authored `docs/releases/v0.13.1/Release
Notes.md` stating that `v0.13.1` supersedes the unpublished `v0.13.0`,
and added the register row as **In preparation** — with `v0.13.0`
deliberately untouched.

Two items remain open from this analysis. `TD-45`'s HTTP 403 finding
invites either a plan change or a formal acceptance that §7.7 is
discipline-enforced; the record here does not choose. And the remaining
28 fixed delays in `Tempest.Desktop.Tests` (`WP 13.12.9`) remain the
residual risk that could produce this same situation again — a release
whose only defect is its own test suite's timing.

## 13. Key Takeaways

- Establish the facts before invoking the policy; the policy's answer
  often depends on them.
- An exception's conditions are the exception. Strip them and it is a
  new rule.
- The corrective action was already written in `release.yml`'s own
  comment — the project had answered this before it happened.
- A permanently unpublished tag is an acceptable outcome; a rewritten
  one is not.
- A Work Package that changes nothing can still be the most consequential
  one in a release.
