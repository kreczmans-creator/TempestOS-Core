## 12. Future Evolution

See `28-workspace-visual-polish.md` §12 (`FCR-0071`, `FCR-0072`).

**Four genuine, disclosed findings, all fixed before commit:**

1. **`GetResourceObservable`/`Bind` unreliable across attachment** —
   the conventional code-behind `DynamicResource` pattern did not
   reliably re-push a value once a control that subscribed while
   unattached was later attached to a real, shown `Window`. Fixed by
   introducing `ThemeReactiveBrush`, resolving directly against
   `Application.Current` on attach and on theme change instead.
2. **A process-wide static registration guard was actively wrong** —
   `ApplicationPalette.Register`'s own `static bool _registered` guard
   intermittently left a later test's own fresh `Application` instance
   completely unregistered, since Avalonia's headless test host does
   not guarantee one instance per process. Found by a flaking
   `VisualPolishTests` run (reproduced deterministically before the
   fix, zero failures across five re-runs after). Fixed by removing the
   guard — re-registration is harmless.
3. **A test-attribute mistake poisoned unrelated tests** —
   `IconGeometry_EveryEntry_ParsesToARealNonEmptyGeometry` was
   initially `[Fact]`, not `[AvaloniaFact]`; `StreamGeometry.Parse`
   needs a real render context, and the resulting
   `TypeInitializationException` permanently broke `IconGeometry` for
   the rest of the test process. Fixed by correcting the attribute.
4. **A genuine test-precision defect in `WP 10.4A`'s own test**, found
   only because this Work Package re-ran the full suite repeatedly to
   check for flakes — `Recentre_VerificationActivityWithARecordedResult_AddsTheResultAsAVisibleLeafNode`'s
   own assertion matched *any* `"verifiedBy"`-labelled edge rather than
   the specific `Activity→Record` edge `TD-32` names, and could
   intermittently fail depending on `InMemoryEngineeringObjectRepository`'s
   own unspecified iteration order. Fixed by narrowing the assertion.
   `WP10.4A`'s own already-published documents are deliberately left
   untouched — this finding is disclosed here, not backfilled there.

## 13. Key Takeaways

A near-whole-application "polish" instruction was met with a real,
cohesive, tested foundation (theme-reactive brushes, a consistent icon
vocabulary, four reusable feedback controls) applied to the
highest-value surfaces first, honestly disclosing what received lighter
treatment; two long-disclosed Technical Debt items were closed as the
natural, not incidental, consequence of building that foundation; four
genuine defects — two Avalonia-specific binding/lifecycle lessons, one
test-attribute mistake, one prior Work Package's own test-precision
gap — were all found and fixed before commit, none merely disclosed and
left open.

## Observations

**The same "found only because a later Work Package needed to verify
something honestly" pattern this session's own Observations sections
have named three times before (`WP 10.3B`, `WP 10.4A`) recurs a fifth
time, and for the first time points *backward* at a previous Work
Package's own test, not merely a previous Work Package's own production
code.** `WP 10.4A`'s own `TD-32` test carried a real, if narrow,
precision gap for two Work Packages' worth of git history before this
Work Package's own "repeat test execution to identify flakes"
requirement — a genuine, disclosed instruction from the Product
Owner, not a habit this session invented — happened to run the suite
enough times to surface it. A named, required verification discipline
found a real defect a single run would never have caught.

**Two Avalonia-specific lessons (resource-binding-across-attachment,
per-test-run `Application` lifecycle) are now real, reusable platform
knowledge**, captured directly in `ThemeReactiveBrush`'s own code
comments and this retrospective — the next Work Package building a
theme-reactive custom control does not need to rediscover either one.
