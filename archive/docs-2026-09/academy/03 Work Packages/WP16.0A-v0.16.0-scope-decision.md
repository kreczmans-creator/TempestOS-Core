# WP 16.0A — v0.16.0 Scope Decision

## 1. Introduction

`WP 16.0A` (commit `fb8b90c`) is the opening Work Package of `v0.16.0`
and the one every later Work Package in this release cites: six
scope-and-support questions posed by `docs/releases/v1.0.0/v1.0.0
Release Candidate Audit.md` §2, each answered, each written up as a
fully-reasoned Decision Register entry, and each reserved rather than
recorded — `D-021` through `D-026`, numbered by the `WP 7.2B`/`WP 7.2C`
reservation precedent, every one **Proposed — awaiting Product Owner
approval**. Its own full account is `docs/releases/v0.16.0/WP16.0A
v0.16.0 Scope Decision.md`. This retrospective is written under
`WP 16.2C`, sourced from that report, `fb8b90c`, and the repository's own
current state a day after the fact.

## 2. Purpose

Answer, with evidence rather than assumption, the six questions the v1.0
audit found unreconciled — which v1.0 definition governs, what happens
to the Companion branch, whether plugins or non-loopback REST ship in
v1.0, what the v1.0 platform support matrix actually is, and what
becomes of `WP 15.2A`'s orphaned `v0.15.1` folder — so that every
Work Package sequenced after it has a stable scope to build against
instead of three competing v1.0 definitions.

## 3. Background

`v1.0.0 Release Candidate Audit.md` §2 found three unreconciled v1.0
definitions on record and rated closing that ambiguity mandatory before
any v1.0 Work Package could be sequenced. `WP11.0B Architecture
Roadmap.md` §1 ("Definition 2") was the only one that had actually been
scoped and approved; `TD-84`'s 2026-08-28 project-centric decision was a
second, later definition with no formal scope document behind it; a
third existed only as an assumption several Work Packages had begun
citing. Engineering Governance §9 assigns scope, version numbering and
release timing to Product Approval alone — this Work Package's own job
was therefore to prepare the six decisions, not to make them.

## 4. The Problem

Six specific, load-bearing questions had no recorded answer: which v1.0
definition governs (Q1); the Companion mobile branch's disposition
(Q2); whether third-party plugins ship in v1.0 (Q3); whether REST stays
loopback-only and is disabled by default (Q4); the v1.0 platform support
matrix, specifically Linux (Q5); and what to do with `WP 15.2A`'s
`docs/releases/v0.15.1/` folder, which never became a real release
(Q6). Every one of Waves 1–3 in the Release Plan's own execution graph
depends on at least one of these six answers existing.

## 5. The Design

Each question was investigated from source, not carried from the plan:
`git rev-list`/`git diff --stat` against the Companion branch (64
commits behind `main`, a REST-facing surface, its own colliding
`TD-57`/`TD-58` numbering); a direct read of `RestApiHostedService.cs`
confirming no configuration key exists today to disable the REST
listener; a direct read of `Tempest.Desktop.csproj` and `ci.yml`
confirming `TD-116`'s pin and the absence of any macOS CI leg; a direct
`git ls-tree`/`git show` of the `WP 15.2A` branch confirming its own
`docs/releases/v0.15.1/WorkPackages.md` states, in its own words, "Not a
release." Each answer was then written as a complete Decision Register
row — Decision, Source, Type, Why this answer, Consequences, Reversal —
in the register's own exact format, reserved as `D-021`–`D-026`, with
the `When` column left explicitly blank pending an approval date. A new
`Type` value, "Product — scope boundary," was proposed for the five
scope decisions since no existing register `Type` distinguished a
Product Owner scope call from an engineering-tier process decision.

## 6. Alternatives Considered

**Writing the six decisions directly into the Decision Register**, as
if already approved. Rejected outright — the register's own convention
(every existing row a decision already made) would make an unapproved,
Proposed record indistinguishable from a ratified one, and Governance §9
gives Product Approval, not the engineering tier, the authority to make
a scope decision, not merely to draft one.

**Merging or cherry-picking the Companion branch, the `WP 15.2A` branch,
or the audit branch onto this one to resolve the "release plan isn't on
`main`" precondition problem** (see §10). Rejected — which branch
becomes `v0.16.0`'s actual base is itself a Product Approval decision
this Work Package's own brief did not authorise it to make unilaterally.

## 7. Why This Solution Was Chosen

The `WP 7.2B`/`WP 7.2C` reservation pattern — number a record, write it
in the target document's own format, and copy it in verbatim only once
approved — lets six fully-reasoned decisions exist, be cited by number,
and be reviewed as a complete set, without ever asserting they are
already in force. It is the one mechanism available that satisfies both
"the six questions need real answers now" and "only Product Approval may
actually decide."

## 8. Architectural Principles

No production code, test, ADR, register, or `PROJECT_STATUS.md` was
modified — confirmed directly by this Work Package's own `git diff
--stat main`, which shows exactly one file added. A scope-and-support
decision is Product Approval's authority under Governance §9, not an
architectural decision under §5's ADR criteria; none of the six
establishes a code convention or was defended under Technical Review, so
none belongs in `docs/adr/` either. The register's format was followed
exactly, since ratification is meant to be a verbatim copy, not a
rewrite.

## 9. Benefits

Every later `v0.16.0` Work Package gained a single, internally
consistent set of citable answers instead of three competing
definitions — `WP 16.0B`, `WP 16.1B`, `WP 16.3A`, and `WP 16.5B` (this
document's five siblings) all cite `D-021`–`D-026` by number, honestly,
as Proposed. The register itself was left untouched rather than
pre-empted, so a Product Owner reviewing it later sees exactly the
twenty ratified decisions that existed before this Work Package, plus
six clearly-marked proposals sitting beside it in the report — nothing
silently promoted itself to "decided."

## 10. Trade-offs — and the tension this Work Package did not resolve

This Work Package's own closing line reads: **"Stopping here for
Product Owner review; `WP 16.0B` does not begin until the six records
are approved."** That did not happen. `WP 16.0B` began on the very next
commit (`4198289`), on the Product Owner's own later direction, applying
`D-022` and `D-026` while stating plainly, in its own commit message and
report, that both remained Proposed and "ratification pending PR #6."
Every Work Package downstream of it — `16.1A` citing `D-021`; `16.1B`
citing `D-021`; `16.3A` citing `D-021`; `16.5B` implementing `D-025`
directly — did the same: cite the number, state Proposed, proceed. As of
this retrospective, `docs/governance/Architecture/Decision Register.md`
still reads "Total: 20 entries" — `D-021`–`D-026` have never been copied
in. A `TD-124`-class gap of the register's own kind now sits one level
higher: an entire scope decision, cited by six downstream Work Packages
as though load-bearing, has no register row of its own to point to
outside this Work Package's own report.

This is not a failure of `WP 16.0A`'s own execution — it did exactly
what its brief and Governance §9 required, stopped exactly where it said
it would, and every downstream citation is scrupulously honest about the
records still being Proposed. The lesson is upstream of any one Work
Package: a Work Package can correctly refuse to proceed past an
unapproved gate, and a programme can correctly proceed anyway on an
explicit, later Product Owner instruction that overrides that gate — but
when it does, the artefact meant to carry that approval (the Decision
Register itself) does not update itself just because work continued.
Six months of engineering decisions can now rest on six records that
exist only inside one Work Package's own report, cited by number from a
dozen other documents, and never ratified into the one place Governance
§9 designates for a ratified decision to live.

## 11. Common Mistakes

**Treating "the programme proceeded" as equivalent to "the gate was
satisfied."** Every downstream Work Package in this release avoided this
mistake in its own prose — each names `D-0xx` as Proposed, not
approved. The mistake this Work Package's own retrospective flags
instead is structural: nothing in the repository's tooling (not even
`WP 16.1B`'s own sixteen health checks, none of which reads the Decision
Register) would catch a `D-0xx` citation that quietly dropped its
"Proposed" qualifier somewhere downstream. The discipline held here
because every author was careful, not because anything mechanical
enforced it.

## 12. Future Evolution

The six records are ratified — copied verbatim into `docs/governance
/Architecture/Decision Register.md` with a real approval date in the
`When` column — only on explicit Product Owner instruction, per this
Work Package's own "Register rows for ratification (verbatim, on
approval only)" section. Until that happens, any future Work Package
citing `D-021`–`D-026` must continue stating Proposed, exactly as this
one and its five siblings did. Whether Engineering Governance itself
should gain a mechanical check that a `D-0xx` number cited more than
once outside its own originating report is still Proposed after some
threshold — the same class of gap `TD-123` names for three registers
with no machine derivation — is a genuine open question this
retrospective raises but does not answer.

## 13. Key Takeaways

- A reservation pattern (number now, ratify verbatim later) lets a
  scope-boundary question get a complete, citable answer without
  asserting authority the engineering tier does not have — but only if
  every later citation keeps stating the qualifier honestly.
- A Work Package's own explicit stopping condition ("does not begin
  until X is approved") can be overridden by the tier that actually owns
  the gate, on that tier's own later instruction — that is Governance §9
  working as designed, not a violation of it, provided the override is
  explicit and every downstream document discloses it rather than
  quietly treating X as satisfied.
- An unratified decision cited by six later Work Packages accumulates
  real, load-bearing weight in the repository long before it accumulates
  a register row — the citation count is not a substitute for the
  register entry, and a retrospective is the right place to say so
  plainly rather than let the gap go unnoticed until someone asks where
  `D-025` actually lives.
