# WP 12.9.3B — Governance Health Check Consistency Remediation

## What This Document Is

The retrospective for `WP 12.9.3B`, a narrowly-scoped implementation
Work Package that brings `scripts/governance-healthcheck.ps1` into line
with the architecture `WP 12.9.3A` reviewed and approved. On its own
branch, `feature/v0.12.9.3b-governance-health-check-consistency`. This
is an implementation-only remediation of a governance-tool
inconsistency — it does not broaden into CI workflow changes,
repository cleanup, or governance policy changes, per its own
controlling brief.

## Background

Pushing `main` to `origin` for the first time in this release's own
history (`WP 12.9.3`) surfaced a real GitHub Actions
`Governance Health Check` failure that never reproduced locally:

```
[WARN] Release Register matches git tags
       - No git tags available (git missing, -Root is not a git repository,
         or zero 'v*' tags exist) - check skipped
[FAIL] PROJECT_STATUS.md references are valid
       - Version token(s) referenced that match no git tag, the current
         VERSION, or a disclosed exception: v0.3.0, v0.4.0, v0.5.0,
         v0.6.0, v0.7.0, v0.8.0, v0.9.0, v0.10.0
```

`WP 12.9.3A` (architecture/investigation only, no file changed)
established the root cause directly from the script's own source:
`Test-ReleaseRegisterMatchesTags` and `Test-ProjectStatusReferences`
both consume the identical function, `Get-RepoTags`, and both can
receive an empty result for the identical reason — a shallow GitHub
Actions checkout leaves zero local `v*` tag refs, regardless of the
real, tagged release history this repository actually has (nine real
tags, all present in every local clone). Only the first check treats
this as a disclosed environmental limitation (`Warn`, "check skipped").
The second had no equivalent guard and unconditionally treated every
historical version token — `v0.3.0` through `v0.10.0`, every one of
them real and correctly tagged — as unverifiable, producing a false
`Fail`.

`WP 12.9.3A`'s own conclusion: **a checker-architecture inconsistency,
not a repository defect.** `PROJECT_STATUS.md`'s content was never
wrong. The two checks sharing one data source and one failure mode,
but only one of them defensively handling that failure mode, is what
was wrong — and nothing in the code, comments, or design history
defends the asymmetry; the opposite is stated as the intended goal
("deliberately the same exception list Check 3 uses, so the two checks
never disagree").

## Implementation

**Why the fix changes only Check 5.** `Test-ReleaseRegisterMatchesTags`
was already correct — its own precedent (`Warn` on zero tags) is what
this fix extends, not what it changes. `Get-RepoTags` itself is already
correct — the ambiguity between "zero tags legitimately exist" and
"tags exist but this environment can't see them" is a real, disclosed,
accepted limitation of that function (its own comment states this
plainly); teaching it to distinguish the two would require probing the
git object database directly, a materially larger change this Work
Package's own brief explicitly excludes. The one place actually
misbehaving was `Test-ProjectStatusReferences`'s own failure to guard
against the case its sibling check already handled.

**Why path validation intentionally remains active.**
`Test-ProjectStatusReferences` bundles two independent kinds of
evidence into one check result — version-token validation (depends on
tag availability) and path-reference validation (does not, and never
did). Mirroring Check 3's own coarse shape exactly — skip the *entire*
check whenever tags are unavailable — would have silently suppressed
real path-drift detection any time a shallow checkout happened to be
in play, a strictly larger behavioural change than the one actually
needed. The fix instead narrows to precisely the sub-check that
depends on tags:

```powershell
$tagsAvailable = $tags.Count -gt 0

$unknownVersions = if ($tagsAvailable) { ... same logic as before ... } else { @() }

# path-reference validation: unchanged, runs unconditionally

$status = if ($unknownVersions -or $missingPaths) { "Fail" }
          elseif (-not $tagsAvailable) { "Warn" }
          else { "Pass" }
```

When tags are available, behaviour is provably identical to before —
the version-token branch is byte-for-byte the same logic, now guarded
rather than removed. When tags are unavailable, the check degrades to
`Warn` (disclosed, using wording that deliberately echoes Check 3's own
established phrasing) *unless* a real, tag-independent path defect
exists, in which case it still correctly `Fail`s.

## Verification

Four behavioural cases demonstrated directly, three against isolated
fixtures (never the real repository, mirroring `WP 11.2A`'s own
fixture-testing convention):

1. **Tags available** (the real repository, 9 real tags): `[PASS]`,
   identical output to before this change — zero behavioural
   difference confirmed directly.
2. **Tags unavailable, a genuine missing path present** (fixture, not a
   git repository): `[FAIL]` — path validation still catches a real
   defect regardless of tag availability, exactly as required.
3. **Tags unavailable, no path issues** (fixture, not a git
   repository): `[WARN]`, disclosed, no false `Fail` — the defect this
   Work Package exists to close.
4. **Release Register behaviour**: unchanged throughout all three runs
   above — `Get-RepoTags` and `Test-ReleaseRegisterMatchesTags` were
   not touched.

Full Debug+Release regression re-run after the change: 2,255/2,255
passing both configurations, 0 Warnings/0 Errors both — expected, since
this change touches only a PowerShell governance script, no `src/`/
`tests/` file.

## Key Takeaways

1. **Real infrastructure finds real gaps local testing cannot.** This
   inconsistency has existed in the checker's own source since `WP
   11.2A` first wrote `Test-ProjectStatusReferences` — invisible in
   every local run (where tags are always present) and invisible in
   every prior Engineering Readiness Review (each blocked before real
   CI ever actually ran). It took an actual GitHub Actions execution,
   for the first time in this release's history, to surface it — direct
   evidence for exactly the case `ADR-0106`'s own Alternative 3
   rejection already made against relying on local-only or purely
   automated verification.
2. **Matching a precedent's principle is not the same as copying its
   shape.** Check 3's fix (skip the whole check on zero tags) was the
   right answer for a single-purpose check; applying that same coarse
   shape to a check bundling two independent kinds of evidence would
   have introduced a second, larger regression (suppressed path
   validation) while fixing the first. The minimum-change principle
   applies to behaviour, not to literal code shape.
3. **A tightly-scoped brief is easy to satisfy honestly.** Documentation
   updates that had nothing real to report (`Documentation Register.md`
   has no Directory Map row for `scripts/`, out of its own stated
   scope) were disclosed as such rather than padded with a change that
   wasn't needed.
