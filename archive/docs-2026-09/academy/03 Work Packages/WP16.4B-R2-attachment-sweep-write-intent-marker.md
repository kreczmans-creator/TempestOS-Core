# WP 16.4B-R2 — Attachment Sweep Write-Intent Marker

## 1. Introduction

`WP 16.4B-R2` closed the `v0.16.0` review board's first RED finding: the
attachment reconciliation sweep `WP 16.4B` shipped could permanently
delete a live, in-flight attachment's bytes while a user was still
uploading it, with the object's own state left claiming the file
existed. It ran on `feature/v0.16.0-sec-remediation`, cut from
`feature/v0.16.0` at `ac7daa6`, in two rounds: a first commit
(`aa0daaf`) that the review board's second pass proved insufficient, and
a second (`ac562ce`) that corrected it — both merged together as
`c486f27`, with register rows added at integration (`abc9dff`). Scope
widened mid-task, on a second reviewer's independent reproduction, to
an identical write-then-index race in `MaterialCatalogReconciliationService`
and `RequirementsReconciliationService`, and separately closed an AMBER
finding in `ApiRequestHandler`'s `403` response body.

## 2. Purpose

`v0.16.0 Release Plan.md` §`WP 16.4B` specified the fix in advance:
"`TD-67`: a write-intent marker before multi-file writes and a startup
sweep that reports orphans." The implementing stream built the sweep
but not the marker — it substituted a plain two-read comparison instead
— and that substitution is what opened the race the review board found.
This Work Package's purpose was narrow and specific: build the marker
the plan had already specified, and close the race it exists to close,
without touching `ADR-0114` decision 4 (content is written before the
state that names it — unchanged throughout).

## 3. Background

`ADR-0114` decision 4 makes the ordering `content, then state` a
deliberate choice: a crash between the two leaves bytes nothing
references — inert, reclaimable — rather than a state that promises
content the store does not have. `WP 16.4B-3`'s own sweep
(`AttachmentContentReconciliationService`, `docs/releases/v0.16.0/
WP16.4B-3 Durability.md`) closed `TD-97` by comparing every content key
`IAttachmentContentStore` holds against every attachment Id any
persisted `EngineeringObjectState` references, deleting whatever no
state referenced. The Engineering Status Report (§4, R1) records which
order it actually read in: **states first, then content keys** — the
order that makes the race's window *wider*, not narrower, because it
gives the state write the least possible time to land before the sweep
checks for it. `TD-97` had already been marked **Resolved** against
this exact code (`WP 16.4B`, 2026-09-05, Technical Debt Register)
before the race was found — the aggravating detail the review board
itself named.

## 4. The Problem

`EngineeringObjectBase.AttachContentAsync` performs two writes in a
fixed order that cannot be reordered without reopening `ADR-0114`
decision 4: content, then state. A sweep that reads *both* of those
things back is, by construction, reading a snapshot of a two-write
sequence that has no atomic view — there is always some point at which
content exists and state does not yet. The original sweep's states-first
read made this concrete: content lands, the sweep's state read runs
(sees nothing, because the state write has not landed yet), the state
write then lands, and the sweep's content-key read — which already ran
or runs anywhere after — reports an unreferenced key and deletes it. The
state record survives, now naming a hash the store no longer has:
silent, permanent loss, with metadata still claiming the file exists.
The identical write-then-index shape existed, independently, in
`MaterialCatalogReconciliationService` and `RequirementsReconciliationService`
— found by a second reviewer's own reproduction, with a worse practical
consequence there: a fully-registered material's index entry destroyed
while its document survived intact but unfindable, and because
`RegisterAsync`'s own duplicate check reads that same index, a later
registration for the same id would not see a duplicate and would
produce two conflicting documents under one identifier.

## 5. The Design

A third, independent store — `IAttachmentWriteIntentStore`/
`AttachmentWriteIntentStore` (`src/Tempest.Core/EngineeringDomain/
Contracts/IAttachmentWriteIntentStore.cs`, `.../Implementation/
AttachmentWriteIntentStore.cs`) — one record per attachment, keyed by
Id, in its own `EngineeringDomain.AttachmentWriteIntent` collection,
through the same `IPersistenceStore` atomic temp-file-then-rename
discipline every other collection gets for free. `AttachContentAsync`
brackets its two existing writes, **without reordering either of
them**: `MarkAsync` (new) → content write (unchanged) → state write
(unchanged) → `ClearAsync` (new). The sweep gains an optional
`IAttachmentWriteIntentStore?` constructor parameter and reads in a
specific order: **content keys, then markers, then object states** —
skipping any content key still marked, regardless of what the later
state read sees.

**The marker's read position is load-bearing, not cosmetic — and this
is the one fact this retrospective exists to teach.** The attachment's
own lifecycle is `Mark(m) < content(c) < state(s) < Clear(x)`, always,
by construction. Label the sweep's three reads T1 (content, always
first), and whichever order it reads markers/states in as T2 and T3.
With markers sampled **last** (T2 = states, T3 = markers) — the shape
the first round shipped — the interleaving `c < T1 < T2 < s < x < T3`
is fully consistent with that lifecycle: content exists at T1; the
state write has not yet landed by T2, so the attachment still looks
unreferenced; `Clear` then runs; only after that does the marker read
at T3 find nothing marked. Present, unreferenced, unmarked — all three
checks pass, and a now-fully-live attachment is deleted. Reading
content first narrowed the window from the original bug, but did not
close it — it reopened the same defect one read later.

With the marker sampled **between** the two scans (T2 = markers, T3 =
states — the corrected order), the proof runs the other way. For
collection, the attachment must be unmarked at T2. Since `m < c < T1 <
T2`, the mark was already in place before T2 — so "unmarked at T2" can
only mean `Clear` already ran: `x < T2`. But `s < x` always, so `s < x
< T2 < T3` — the state write necessarily completed *strictly before*
the state read at T3, which therefore sees it: referenced, never
collected. There is no interleaving of the sweep's three reads against
`AttachContentAsync`'s four writes that loses live content. This proof
is written into `AttachmentContentReconciliationService.RunAsync`'s own
XML doc, not only into the report.

`MaterialCatalogReconciliationService` and `RequirementsReconciliationService`
have no marker — the fix there is a pure read-order reversal (derived
side first, authoritative side second), which is airtight for their
specific two-write shape by a different, structural argument: the
document write always strictly precedes its own index/registry write
within one uninterrupted async call, and neither service ever
physically removes a document once created. If the derived-side read
observes an entry, the document write that necessarily preceded it has
already landed — so the later authoritative-side read is guaranteed to
still see it.

## 6. Alternatives Considered

**Ship the states-first-then-markers-last order (round 1).** Built,
committed (`aa0daaf`), and rejected by the review board's own second
pass, which proved by the interleaving above that it only narrows the
race rather than closing it. Not a hypothetical rejected at design time
— an actual shipped fix that failed independent review and had to be
reworked in a second commit.

**Reorder the two Attachment reads (content first, states second)
without adding a marker at all**, on the theory that the same structural
argument protecting Materials/Requirements would apply here too.
Rejected on inspection: unlike a document-then-index write, which is a
single continuation of one write path, `AttachContentAsync`'s state
write is a second, unbounded async operation with no guaranteed
"already landed by the time this scan started" relationship to the
content write. A state write can always land after the sweep's state
read, no matter how late that read runs — the reorder alone was never
going to be a closure for this specific three-read shape, which is
exactly why the marker exists.

**A shared, coupled "attachment write-intent configuration" type**
binding `EngineeringDomainContext` (the marking side) and
`AttachmentContentReconciliationService` (the skipping side) together
at the type level, so a future composition could not construct one
without the other. Investigated at the coordinator's own request and
not built: `TempestHost.cs` registers both unconditionally, in one
linear sequence, with no feature flag around either — `grep`-verified
no production call site hand-constructs either type — so today's one
composition root cannot produce a mismatched pair, and every
hypothetical divergence degrades to "the pre-`WP 16.4B-R2` race is
unprotected again," never to something new or worse. Coupling them
would be a larger, more invasive change than this finding's own scope
justified against a risk that does not exist in the current tree.

## 7. Why This Solution Was Chosen

The marker's read position is provably, not merely empirically, correct
— the interleaving proof rules out every possible ordering of the
sweep's three reads against the four writes of `AttachContentAsync`,
rather than resting on "this passed in testing." That is a stronger
claim than the reorder-only fix available to Materials and Requirements
can make for itself, and the difference is disclosed rather than
glossed: Attachments has both the reorder and an independent marker
that would keep closing the race even if a future change altered
`AttachContentAsync`'s own timing assumptions; Materials and
Requirements have only the structural argument, which would need
re-deriving from scratch if either service's write order or delete
policy ever changed.

## 8. Architectural Principles

- **A derived-side marker must be sampled between the derived read and
  the authoritative read, never after both** — sampling it last only
  narrows a race, because the marker itself becomes one more read
  contending for the same undefended gap. This is the general
  principle the round-1 failure teaches, independent of attachments
  specifically.
- **Verify a fix the same way the bug was proven, not by assertion** —
  the corrected order was confirmed by reverting
  `AttachmentContentReconciliationService.RunAsync` to the rejected,
  marker-last order and watching
  `SweepAsync_InterleavedBetweenItsMarkerReadAndItsStateRead_NeverCollectsTheLiveContent`
  fail (content collected, reported `Missing`), then restoring the fix
  and confirming the full 13-test file passes again.
- **A marker that can only ever prevent collection, never cause it, is
  safe under every failure mode by construction** — enumerated directly
  in the report for every crash window (`Mark`-only, `Mark`+content,
  `Mark`+content+state, stale-marker-after-`Clear`-never-runs): none
  loses data, and the worst case degrades to the pre-existing,
  disclosed `TD-97` tolerance for a leaked, uncollected record.
- **A structural proof about today's write order is a real fix, but a
  narrower-scoped one than a runtime marker** — Materials and
  Requirements are protected by an invariant of the code they read
  holding *today*; nothing would catch a regression if a future change
  ever reordered `RegisterAsync`'s writes or introduced a real
  document-deletion path, which is exactly the asymmetry this report
  documents rather than hides.

## 9. Benefits

- The RED finding is closed for all three reconciliation services —
  Attachments (marker plus reorder), Materials and Requirements (reorder,
  proven airtight for their two-read shape) — each verified with a new
  race test built on a `TaskCompletionSource`-driven gate, not a timing
  assumption.
- The AMBER finding in `ApiRequestHandler`'s `403` body is also closed:
  the response no longer names the principal id or required permission
  key, closing a two-round-trip route-table reconstruction the OpenAPI
  route disclosure (`TD-62`) had already been fixed to stop in one
  document. The full detail is preserved in the log
  (`_logger?.Information(...)`, a strict addition), and the pre-existing,
  separately tested decision not to audit-record a denial
  (`HandleAsync_UnauthorizedRequest_RecordsNoAuditEntry`) was checked and
  deliberately left alone rather than silently widened.
- `Tempest.Core.Tests`: baseline 3,185 → 3,192, delta +7 — exactly the
  seven new tests this report adds (four Attachments, one Materials, two
  Requirements) — no other test count moved, confirmed by two full runs
  at each round, identical both times, with `--blame-hang-timeout` to
  catch a hang rather than silently wait one out (which is what caught a
  genuine deadlock in the first version of the test double, described in
  §11).
- Two Technical Debt Register rows raised for genuine, disclosed
  residuals rather than left silently unmentioned (`TD-129`, the
  404-vs-401 route-existence oracle; `TD-130`, no authorization seam on
  any of the three sweeps) — neither fixed here, both correctly scoped
  as out of this finding's own boundary.

## 10. Trade-offs

**This fix is real and provably closes the race it targets — and it is
not the last word on concurrent safety for this same code.** A later
independent review found that the write-intent marker cannot help when
two concurrent mutations on the *same* engineering object race each
other inside `EngineeringObjectStateStore.SaveAsync`
(`src/Tempest.Core/EngineeringDomain/Implementation/
EngineeringObjectStateStore.cs`) — confirmed directly by reading the
method: it is a single, unguarded call to
`_persistenceStore.WriteAsync(StateCollectionName, state.Id.ToString("N"),
JsonSerializer.Serialize(state, StateJsonOptions), cancellationToken)`,
with no lock, no optimistic-concurrency check, and no per-object
serialisation of any kind. Two calls to `SaveAsync` for the same object
Id, racing each other, resolve by last-write-wins at the file-rename
layer — whichever write's rename lands second silently discards
whatever fields the other write changed, with no error and no signal to
either caller. The write-intent marker this Work Package built has
nothing to say about this: it protects the sweep's read against a
half-written attachment, not one `SaveAsync` call against another. That
work is out of this Work Package's own scope and is being carried
separately as `WP 16.4B-R3`. Naming the boundary of what a fix actually
covers, the moment a reviewer finds the next layer down, is worth more
than letting `WP 16.4B-R2`'s own closure read as "the concurrency
problem is solved."

- **Asymmetric protection, disclosed rather than smoothed over.**
  Attachments carries two independent defences (reorder plus marker);
  Materials and Requirements carry one (reorder only, resting on a
  structural invariant of `RegisterAsync`/`CreateAsync` that a future
  change could silently break). A code comment was added to both
  services' `RunAsync` XML doc naming the dependency, so a future writer
  changing either write path trips over the assumption rather than
  reopening the race invisibly.
- **`TD-129` and `TD-130` are named, not fixed** — the 404-vs-401 route
  oracle needs a Product/Security decision before any status code
  changes; an authorization seam on the sweeps was deliberately not
  designed against a caller surface (command, route, scheduled job)
  that does not exist yet, on the reasoning that guessing at a
  permission shape now would be worse than naming the gap for whichever
  Work Package eventually wires one in.
- **`TD-97`'s own register row was never revised to point at this
  fix.** Verified directly against `docs/governance/Quality/Technical
  Debt Register.md` at this Work Package's own integration: the row
  still reads simply "Resolved (`WP 16.4B`, 2026-09-05)," with no
  forward pointer to the race this Work Package found and closed in the
  exact code that row certifies. A reader of `TD-97` alone, without
  independently finding `TD-129`/`TD-130` or this report, would not
  learn that the sweep it describes shipped a data-loss defect one Work
  Package after being marked Resolved.

## 11. Common Mistakes

- Sampling a derived-side marker *after* both of the reads it is meant
  to protect, rather than strictly between them — this looks like a
  strengthening of the original two-read check and is, provably, only a
  narrowing of the same race, one read later.
- Trusting that a fix which passes its own new test is correct, rather
  than reverting to the previous (or a deliberately broken)
  implementation and confirming the test then fails — the corrected
  marker position was verified exactly this way, in both directions.
- Assuming a reorder that closes a race for one service's two-read
  shape (Materials, Requirements) generalises to a three-read shape
  with an unbounded second write (Attachments) — it does not, and the
  report is explicit that the two service families are protected by
  genuinely different mechanisms, not by the same mechanism applied
  with differing rigour.
- Marking a Technical Debt row Resolved against code a sweep has not
  yet been proven safe against, and then never revising that row once a
  defect in the certified code is found and fixed elsewhere in the same
  release.

## 12. Future Evolution

`WP 16.4B-R3` is the direct sequel to this Work Package's own Trade-offs
section (§10): closing the lost-update race inside
`EngineeringObjectStateStore.SaveAsync` when two concurrent mutations
target the same object Id — a defect this report found and disclosed
but explicitly did not fix, because it is a different mechanism (a
missing per-object write lock) than the one this Work Package's own
marker addresses (a sweep observing a half-written attachment).
`v0.16.0 Engineering Status Report.md` §8 also leaves two open questions
this Work Package's own fix does not resolve: whether the write-intent
marker is the right closure at all, or whether `ADR-0114` decision 4's
content-before-state ordering needs revisiting now that a concurrent
*reader* — not only a crash — can observe the window it creates; and
whether asymmetric protection between Attachments (marker-backed) and
Materials/Requirements (structural-only) is an acceptable, permanent
shape or a gap that should eventually be closed the same way. Neither
question is this Work Package's to answer; both are named here so
`WP 16.4B-R3` or whoever picks up either question next does not have to
rediscover them.

## 13. Key Takeaways

- A marker meant to close a race must be sampled *between* the derived
  read and the authoritative read it protects, never after both — the
  position, not merely the marker's existence, is what closes the
  window.
- Verify a corrected fix the same way its bug was proven: revert to the
  broken version and watch the new test fail, not only confirm the fix
  passes.
- A fix that is provably airtight against the race it targets can still
  leave an adjacent, structurally different race untouched — say so
  plainly, and name the follow-up Work Package, rather than let the
  closure read as complete.
- A Technical Debt row marked Resolved against a piece of code is only
  as current as the last time someone checked that code against a new
  finding — a row that is never revised after a defect is found and
  fixed elsewhere silently overstates what "Resolved" means to a reader
  who trusts it alone.
