# WP 13.11A — Plugin Platform Final Hardening Architecture Review

## 1. Introduction

`WP 13.11A` is a **read-only architecture review** — no production code, no
tests, no ADR. It ran on `feature/v0.13.0` after the whole
`WP 13.0A`–`WP 13.10C` plugin-trust chain had landed, across **six parallel
disciplines**: Security/Adversarial, Runtime/Lifecycle Architecture,
API/Compatibility, Verification/Test/RAM, Governance/Documentation, and
UI/UX Dependency. Its commissioning question was single and narrow:
*after everything `v0.13.0` has built, does anything genuinely block WP14
UI/UX from starting?*

It has **no commit of its own**. Its documentation corrections were left
uncommitted in the working tree by its own explicit instruction, and were
carried in by `WP 13.11B`'s commit `8341438` — so the finding and its
closure form a single commit. That is why this retrospective's primary
evidence is `docs/releases/v0.13.0/WorkPackages.md`'s own `WP 13.11A` row
and `PROJECT_STATUS.md`'s retained `WP 13.11A` stratum, rather than a
`git log` entry.

Five of the six disciplines converged clean. The sixth did not.

## 2. Purpose

To determine, by adversarial reading rather than by assumption, whether
the plugin trust boundary as shipped through `WP 13.10C` was actually
sound — and specifically whether any of its own already-disclosed
residual gaps had been characterised more charitably than the code
supports.

The answer, for exactly one of them, was no. `TD-51`'s residual
"unresolvable constructor parameter type" gap had been characterised by
`WP 13.10C` as uniformly safely isolated — no crash. That
characterisation was **false for the `IModule` axis**, and this Work
Package's Security/Adversarial reviewer proved it with a real, minimal
repro built and torn down during the review, then independently
re-confirmed it by direct source read before any document was touched.

## 3. Background

`TD-51` began at `WP 13.10A` as a different defect entirely:
`PluginAssemblyLoader.EnforceTrust`'s static constructor-conformance
check ran only against a plugin's discovered `IModule` types, never its
discovered `IHostedService` types, so an `IHostedService`-only plugin hit
`moduleTypes.Count == 0` and returned before its own hosted service's
constructor was ever inspected. `WP 13.10B` closed that; `WP 13.10C`
independently re-verified it, live proof-of-concept included.

`WP 13.10C`'s own Security/Adversarial reviewer then disclosed a small,
pre-existing residue and deliberately left it unfixed to avoid scope
creep: the "unresolvable constructor parameter type" denial path throws
`PluginTrustDeniedException` directly from inside `DiscoverModuleTypes`,
before `EnforceTrust` ever reaches a `RecordDenied` call site — so that
one denied type is never added to `deniedTypeRegistry` (`WP 13.9.4`'s
execution-boundary registry). `WP 13.10C` reasoned that a second,
independent construction attempt then occurs during Registration and
fails safely for the identical reason: no code execution,
`ModuleState.Failed`/hosted-service equivalent, not a crash.

That reasoning was correct for the `IHostedService` axis. It was never
checked on the `IModule` axis, which does not reach Registration first —
it reaches Module Discovery.

## 4. The Problem

The review carried six questions, one per discipline. Five returned
nothing blocking. The Security/Adversarial question — *is `TD-51`'s
disclosed residue genuinely harmless?* — returned a whole-Host crash.

The traced chain, end to end:

1. `PluginAssemblyLoader.DiscoverModuleTypes`'s denial for this case
   throws from inside the scan.
2. The throw escapes `DiscoverModuleTypes` **before** `EnforceTrust` can
   reach either of its existing `RecordDenied` call sites, so
   `deniedTypeRegistry` stays empty for this one denial reason alone.
3. `TempestHost.cs`'s `WP 13.9.6` Module Discovery crash-prevention
   filter — `isTypeExcluded: deniedTypeRegistry.IsDenied`, wired
   specifically so an unattributed module belonging to a denied plugin is
   never constructed during discovery — therefore has nothing to exclude.
4. `ReflectionFrameworkDiscoveryService.CreateDescriptor`'s
   `type.GetConstructor(Type.EmptyTypes)` call is reached. It is not
   wrapped in any exception handling. Arity-matching against
   `Type.EmptyTypes` resolves **every** public constructor's full
   parameter signature, including overloads irrelevant to the
   parameterless one being asked for — the same eager
   signature-resolution behaviour already established during
   `WP 13.10B`'s own `GetParameters()` investigation.
5. The resulting `TypeLoadException`/`FileNotFoundException` is caught
   nowhere in `TempestHost.ExecuteStartupPhasesAsync`'s call to
   `discovery.DiscoverModules()`, and propagates through
   `TempestHost.RunAsync`'s outer
   `catch (Exception ex) { EnterFaulted(ex); throw; }`.
6. The Host faults and crashes.

Reachable by a single, otherwise-inert `IModule` type — **any trust
tier, zero requested capabilities, no `[ModuleMetadataAttribute]`, any
constructor naming an unresolvable parameter type**, even when a
compliant parameterless constructor also exists on the same type.

This directly contradicts `ADR-0025`'s founding guarantee that a
plugin-scoped failure must never become a platform-wide outage — the
exact guarantee the entire `WP 13` plugin trust chain exists to provide.

The `IHostedService` axis was confirmed genuinely safe from this specific
path: `HostedServiceManager.StartServiceAsync`'s generic `try`/`catch`
isolates the identical underlying failure as `Failed`, not a crash. Only
Module Discovery's independent, plugin-unaware rescan lacked an
equivalent guard.

## 5. The Design

This Work Package's deliverable is a **finding and a recommendation**,
not code. Its design decisions are therefore about grading, scoping and
disclosure.

**Grading.** `TD-51` was moved Resolved → **Reopened**, graded *Release
Blocking for third-party plugin support* — explicitly **not** blocking
`v0.13.0` as currently shipped, since `src/Plugins/` is empty today and
the path is dormant, unreachable without a loaded plugin assembly. That
framing matches this item's own original `WP 13.10A` framing exactly.

**The recommended minimum fix, `WP 13.11B`**, was written as two options:

- **(a)** have `EnforceTrust`'s unresolvable-constructor-parameter-type
  denial path call `RecordDenied` — *"with whatever partial type list
  `DiscoverModuleTypes` had already scanned"* — before throwing, closing
  the root cause so `WP 13.9.6`'s existing filter correctly excludes the
  type;
- **(b)** wrap `CreateDescriptor`'s `type.GetConstructor`/
  `Activator.CreateInstance` path in the same
  `TypeLoadException`/`FileNotFoundException`/`FileLoadException`/
  `BadImageFormatException` guard, isolating the candidate module rather
  than propagating.

Either alone closes the crash; both together match this codebase's
established defence-in-depth convention. **The partial-type-list phrasing
in (a) was wrong, and `WP 13.11B` deliberately did not take it** — see
§10 and §11.

**Two further findings**, both genuinely new, low-severity, non-blocking,
and neither plugin-trust-specific, raised by the same reviewer:

- **`TD-53`** — `HostedServiceManager.StartServiceAsync`'s `catch` block
  classifies a start failure as Host-fatal only if
  `tracked.Instance is ICriticalBackgroundService`. If
  `_serviceProvider.GetService(tracked.ServiceType)` itself throws before
  `tracked.Instance` is ever assigned, that check evaluates against
  `null` and is always `false` — a service that would have been
  `ICriticalBackgroundService` had it constructed successfully is
  silently reclassified as non-critical and merely marked `Failed`,
  undermining `ADR-0021`/`ADR-0029`. Present since `HostedServiceManager`'s
  original implementation; surfaced here because `TD-51`'s reopened
  Module-axis crash is one concrete way to trigger a hosted-service
  construction throw safely.
- **`TD-54`** — `ITempestServiceProvider` is never registered back into
  the `IServiceCollection` it is built from, so a plugin cannot obtain it
  via `plugin.services.resolve:*` and use it to reach
  `CurrentPrincipalAccessor`/`CurrentComponentAccessor` directly,
  bypassing `IdentityService`'s own gate (`TD-52`). Correct today, but
  *incidentally* — a consequence of construction ordering rather than an
  explicit `NeverEligibleServiceResolveTypes` denylist entry, so an
  unrelated future change registering the provider for a legitimate
  reason would silently reopen the path with no test or review signal
  naming it.

**One documentation-accuracy correction, unrelated to the trust
boundary**, made by the Governance/Documentation reviewer and integrated
centrally: `Future Capability Register.md`'s `FCR-0001`/`FCR-0002`
entries had drifted stale since `WP 13.0A` itself, still citing
`WP 13.0B` as "implementation pending" through `WP 13.1A`, `WP 13.2A`,
and `WP 13.3A` — the last of which reconfirmed **Implemented** in the
same register's own narrative without ever correcting the table cells it
contradicted. Corrected to cite `WP 13.2A` as the real implementer, and
`Status: Implemented`.

## 6. Alternatives Considered

- **Fix it here.** Rejected: this Work Package was read-only by its own
  explicit instruction. The finding is recorded, the remediation is
  scoped, and `WP 13.11B` is *recommended* — "not yet scheduled, not
  implemented here". The working tree was left carrying only
  documentation corrections.
- **Option (a) alone, or option (b) alone.** Each was assessed as
  individually sufficient to close the crash. Both were recommended
  together because that matches this codebase's established
  defence-in-depth convention — root cause plus backstop — not because
  either was judged inadequate on its own.
- **Accept `WP 13.10C`'s existing characterisation.** Rejected on
  evidence rather than on style: the characterisation was tested against
  a real repro and found false for one of the two axes.
- **Treat the UI/UX gaps as prerequisite hardening.** Rejected. The
  UI/UX Dependency reviewer found two genuine gaps in the plugin
  platform's own UI-facing surface — no capability-gated Workspace
  view/panel extension point exists yet for a plugin to contribute real
  UI content (only Navigation and Commands, both proven end-to-end today
  via `Tempest.Desktop`), and no plugin-ownership/trust-tier/
  granted-capability projection exists yet on any DI-public diagnostics
  surface a future plugin-management UI would need — but assessed both as
  WP14's own **first-order design scope to build**, not a prerequisite
  hardening gap blocking WP14 from starting.

The record is silent on whether any remediation shape other than (a) and
(b) was weighed and discarded.

## 7. Why This Solution Was Chosen

Because a review that grades its own worst finding by how inconvenient it
would be to act on is not a review. `WP 13.10C` had characterised this
residue uniformly as safely isolated. That statement was made in good
faith and was correct on one axis. The job here was to test it on the
other, and it did not survive contact with a repro.

The decision to **reopen** `TD-51` rather than file a fresh item is
equally deliberate: this is not a new category of defect, it is the same
item, whose Status cell already carried the residue's own disclosure. So
the correction belongs there — as a correction, with the earlier "no
crash" sentence left standing above it and explicitly contradicted rather
than quietly rewritten.

And the decision to stop before commit is the same discipline applied to
this Work Package's own output: a read-only review that commits its own
findings has, in a small way, started implementing them.

## 8. Architectural Principles

- **Disclose, Then Grade — Never Grade to Suit the Schedule.** The
  finding is a mandatory precondition to enabling third-party plugin
  support and explicitly *not* blocking `v0.13.0` as shipped — in
  `ADR-0106` §4 terms, **Disclosed, Non-Blocking for `v0.13.0`** (wording
  normalised by `WP 13.12.2`; this Work Package's own grade said "Release
  Blocking for third-party plugin support", which collides with §4's
  formal term, and the underlying technical classification is
  unchanged). Both halves of that
  sentence are load-bearing and both are stated in the same breath.
- **Adversarial Review Assumes the Prior Review Was Wrong.** Six fresh
  disciplines re-examined already-reviewed, already-closed work. Five
  found nothing blocking. That is the expected shape, and it is exactly
  what makes the sixth credible.
- **Empirical Before Documentary.** The crash was reproduced with a
  real, minimal repro built and torn down during the review, *then*
  independently re-confirmed by direct source read, *before* any document
  was updated.
- **A Plugin-Scoped Failure Must Never Become a Platform Outage
  (`ADR-0025`).** This is the principle the finding is measured against;
  everything else follows from it.
- **Read-Only Means Read-Only.** No `src/`, no `tests/`, no ADR, no
  speculative Work Package file — the remediation is recommended, scoped,
  and left uncommissioned. `ADR Register.md` was correspondingly
  untouched, this Work Package amending no ADR.

## 9. Benefits

- **A genuine Host crash was found before any third-party plugin
  existed** — while `src/Plugins/` is still empty and the path is
  dormant, which is the cheapest possible moment to find it.
- **`WP 13.10C`'s incorrect characterisation is corrected in place**, in
  `TD-51`'s Status cell and in `Plugin Trust & Isolation
  Architecture.md`'s own Status header and Risks section, rather than
  superseded silently.
- **`TD-53` and `TD-54` are now tracked** — two real, low-severity gaps
  no earlier Work Package in the chain had named, one of them predating
  the plugin platform entirely.
- **WP14 received a straight answer.** Zero WP14-blocking findings from
  any of the six disciplines; Runtime/Lifecycle, API/Compatibility,
  Verification/Test/RAM, and Governance/Documentation each converged
  clean independently, with the full regression re-run fresh at
  **2,554/2,554 passing, both configurations**, matching the
  previously-documented figure exactly.
- **The `FCR-0001`/`FCR-0002` staleness is closed** — a drift that had
  survived four consecutive Work Packages, one of which contradicted it
  in its own narrative without correcting the table it contradicted.
- **`governance-healthcheck.ps1` confirmed identical before and after
  every documentation edit** — 7 passed, 1 warned (pre-existing
  `v0.9.0`/`v0.10.0` informational, unrelated), 0 failed.

## 10. Trade-offs

- **The recommendation carried a defect of its own.** Option (a)'s
  *"with whatever partial type list `DiscoverModuleTypes` had already
  scanned"* phrasing describes an abort-mid-traversal shape.
  `WP 13.11B`'s own Security/Adversarial analysis found that shape
  **actively unsafe** — it would have left an assembly already resident
  in the `AppDomain` unscanned and unrecorded while remaining fully
  visible to Module Discovery's deliberately plugin-unaware `AppDomain`
  scan (`ADR-0110`), trading the Host crash for a silent trust bypass.
  `WP 13.11B` implemented a **complete fixed-point scan** instead, and
  `WP 13.11C` later proved that decision non-vacuously with a dedicated
  regression test. A read-only review can name a fix's *root cause*
  correctly and its *shape* dangerously wrongly in the same sentence.
- **A factually wrong supporting claim was introduced here.** Option
  (b)'s "the same guard already used at **three other call sites** in
  this exact codebase" was wrong: `WP 13.11C` established that exactly
  **one** other call site carries that four-exception filter
  (`DiscoverModuleTypes`' own). The claim was inherited verbatim by
  `WP 13.11B` and softened to an unquantified plural rather than
  corrected, and reached four documents and one production comment before
  `WP 13.11C` corrected it in all of them.
- **No commit of its own.** Stopping before commit was this Work
  Package's explicit instruction, and the consequence is that the
  finding's provenance lives in the governance record rather than in
  `git log` — which is precisely why `WorkPackages.md` and
  `PROJECT_STATUS.md` are this retrospective's primary evidence.
- **The debt counts moved the wrong way, correctly.** 52 → 54 tracked
  items; 18 → 17 Resolved; 1 Partially resolved unchanged; 33 → 36 Open.
  A review whose only possible outcome is a smaller Open count is not
  measuring anything.

## 11. Common Mistakes

1. **Assuming a disclosed residue has been reasoned about on every axis
   it touches.** `WP 13.10C`'s "no crash" conclusion was derived from the
   `IHostedService` path, where `StartServiceAsync`'s generic `try`/`catch`
   genuinely isolates the failure. The `IModule` path does not reach
   Registration first — it reaches Module Discovery, deliberately
   plugin-unaware and without an equivalent guard. One axis being safe
   says nothing whatsoever about the other.
2. **Assuming `type.GetConstructor(Type.EmptyTypes)` only inspects the
   parameterless constructor.** It arity-matches across every public
   constructor, resolving each one's full parameter signature — so an
   irrelevant overload naming an unreachable type throws, even when a
   compliant parameterless constructor exists on the same type.
3. **Assuming a crash-prevention filter protects you because it exists.**
   `WP 13.9.6`'s `isTypeExcluded: deniedTypeRegistry.IsDenied` is the
   right filter at the right seam, and it excluded nothing here — because
   the denial path it depends on recorded nothing. A filter is only as
   good as the data feeding it, and "the filter is wired up" is not the
   same claim as "the registry is populated on every denial path".
4. **Writing a fix's implementation shape into a review that cannot test
   it.** The "partial type list" phrasing read like an obvious minimal
   refinement and was neither. A remediation Work Package that had simply
   obeyed it would have shipped a silent trust bypass in place of a
   crash.

## 12. Future Evolution

- **`WP 13.11B`** — commissioned directly from this review's
  recommendation, closing `TD-51` by taking both options and no wider. It
  took (a)'s intent and rejected (a)'s stated shape; see that Work
  Package's own retrospective.
- **`TD-53`** — closed by capturing criticality from the hosted
  service's own declared `Type` (via reflection, before construction is
  attempted) rather than from the constructed `Instance`. Still Open, and
  deliberately untouched by `WP 13.11B`, `WP 13.11C`, and `WP 13.11D`.
- **`TD-54`** — closed by adding `ITempestServiceProvider` (and
  `IServiceCollection`) to `NeverEligibleServiceResolveTypes` explicitly,
  as defence-in-depth matching that denylist's own stated rationale.
  Cheap, no behavioural change today. Still Open.
- **The two UI/UX gaps** — a capability-gated Workspace view/panel
  extension point, and a trust-tier/granted-capability/ownership
  projection on a DI-public diagnostics surface — remain WP14's
  first-order design scope. `WP 13.11D` independently re-confirmed both
  and established that every extension WP14 needs is purely additive to
  contracts already documented as extensible.

## 13. Key Takeaways

- **A review's most valuable output can be the retraction of an earlier
  review's conclusion.** Five of six disciplines found nothing blocking.
  The entire value of this Work Package sits in the sixth, and
  specifically in its refusal to accept a "no crash" characterisation it
  had not personally tested.
- **"Isolated, no crash" is a claim about a specific code path, not about
  a defect.** The same underlying failure was genuinely isolated on one
  axis and genuinely fatal on the other, for reasons that had nothing to
  do with the failure and everything to do with which pipeline reached
  the type first.
- **Name the root cause with confidence and the fix shape with
  humility.** This review got the first exactly right and the second
  dangerously wrong, and both `TD-51`'s Status cell and
  `WorkPackages.md`'s own row say so plainly rather than tidying the
  history.
- **Provenance survives without a commit, if the governance record is
  written to carry it.** This Work Package has no `git log` entry; its
  full account lives in `WorkPackages.md`'s row and `PROJECT_STATUS.md`'s
  retained stratum, and was committed by its successor precisely so that
  the finding and its closure would be inseparable in the history.
