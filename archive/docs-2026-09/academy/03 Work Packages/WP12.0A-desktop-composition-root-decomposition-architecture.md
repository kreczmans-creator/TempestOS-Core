# WP 12.0A — Desktop Composition Root Decomposition Architecture

## What This Document Is

The architecture-phase retrospective for `WP 12.0A`, the roadmap's own
first predicted `v0.12.0` Work Package (`WP11.0B Architecture Roadmap.md`
§3), realising Finding `A-1`. Architecture only — no code; `WP 12.0B`
(not yet started) implements it.

## 1. Introduction

`WP11.0A Platform Architecture Review.md` named `MainWindow.cs` and
`EngineeringCockpit.cs` "composition-root God Objects in the Desktop
layer" and recommended extraction into dedicated collaborator classes,
naming `EngineeringWorkspaceComposer` as existing precedent to extend.
`WP11.0B Architecture Roadmap.md` scoped this as a two-Work-Package pair
(`WP 12.0A` architecture, `WP 12.0B` implementation) and predicted `WP
12.0A` would "likely warrant a new ADR (a genuine structural pattern
decision, Engineering Governance §5)." This Work Package confirms that
prediction and answers it.

## 2. What Was Found

**Finding `A-1`, re-verified directly, unchanged since `WP11.0A`.**
`MainWindow.cs`: still 1,556 lines; its own public constructor still
spans roughly 1,000 lines (89–1082), doing platform-service resolution,
five independent Desktop-local state loads, all docking/panel
construction and wiring, view construction, ~450 lines of per-discipline
Ribbon object-action dispatch handlers (29% of the file, the single
largest extractable block), cross-view coordination, undo/redo, and
window lifecycle. `EngineeringCockpit.cs`: still 1,398 lines — but a
genuinely different shape from `MainWindow`'s: not a large constructor,
a large flat set of computed read-only properties, six Engineering
Disciplines' worth of `Status`/`KpiCards`/`AttentionItems`, each reading
its own discipline's services directly, all inside one class.

**The two files' problems are structurally different, but the same
underlying principle resolves both.** `MainWindow`'s defect is a
composition root doing too much wiring itself; `EngineeringCockpit`'s is
a composition root owning too many disciplines' worth of read-model
logic directly. Both are instances of the identical question — FOUNDATION.md
non-negotiable #2 ("every component has exactly one reason to change")
applied to a Desktop/Workspace-layer object graph rather than a Platform
Service — and both are answered by the same rule set, applied along each
file's own natural seam (feature-area collaborators for `MainWindow`;
per-discipline collaborators for `EngineeringCockpit`).

**No prior document named the rules for this layer.** `ADR-0009` names
the general composition-root principle; `Shell & Composition Framework
Architecture.md` realises it once, at the platform's outermost boundary;
`EngineeringWorkspaceComposer` realises it a second time, one layer down.
Nothing before this Work Package answered "what are the rules one layer
further in, where a single presentation surface's own object graph (not
the platform's) has grown too large" — confirmed by direct search before
designing anything, per this project's own "no duplication" discipline.

## 3. Architectural Lessons

**A pattern can be motivated by one file and still be written to apply
generally, without prescribing that file's own final shape.** The
temptation, given `MainWindow` as the trigger, was to write an ADR titled
around `MainWindow` specifically. Rejected: `ADR-0103` is titled and
written as a platform-wide pattern ("Composition Roots Own
Collaborators"), with `MainWindow`/`EngineeringCockpit` as motivating
evidence in its Context section, not as its Decision. `Desktop
Composition Architecture.md`'s own illustrative collaborator table is
explicitly marked non-binding, deferring the real, final collaborator
boundaries to `WP 12.0B`'s own Implementation Report — the identical
"architecture decides the rule, implementation applies it" separation
`ADR-0027`/`WP 4.4B` already established as this project's own norm.

**The three genuine alternatives were each rejected on this project's
own already-established precedent, not on new reasoning invented for
this decision.** DI-registering extracted collaborators fails `ADR-0023`'s
own layering test. A declarative/reflective Desktop composition
framework fails the identical "no genuine extensibility trigger" test
`ADR-0032` already applied to Navigation. Partial classes fail
`FOUNDATION.md` non-negotiable #2's own "enforced structurally, not by
convention alone" requirement, the identical reasoning `ADR-0017`
already applied to a comparable temptation. Finding that all three
rejections already had a direct precedent in this platform's own history
— rather than needing fresh justification — was itself confirmation this
decision genuinely follows from existing principles rather than
introducing a new one.

**`EngineeringCockpit`'s own decomposition seam was found by reading the
code, not assumed from the file's line count alone.** Line count alone
would have suggested "split it into two or three arbitrary pieces."
Reading the actual structure (six disciplines, each with its own
`Status`/`KpiCards`/`AttentionItems`/private-helper cluster, already
loosely grouped in the file even before extraction) revealed the real
seam: one collaborator per Engineering Discipline, each naturally
belonging in that discipline's own existing namespace alongside its
`*WorkspaceRegistration` — a decomposition that also closes a smaller,
previously-undisclosed inconsistency (a discipline's own Cockpit logic
living physically apart from the rest of that discipline's own code).

## 4. Key Takeaways

- One ADR, two structurally different motivating problems, one
  underlying principle — `ADR-0103` deliberately does not fork into
  "MainWindow rules" and "EngineeringCockpit rules"; both are the same
  decision applied along each file's own natural seam.
- The explicit "never DI-register a collaborator" rule closes a real gap
  this platform's own existing ADRs left implicit: `ADR-0009`/`ADR-0023`
  together imply it, but neither states it as a rule a future
  contributor could check a design against directly. `ADR-0103` states
  it as a direct, reusable test (`ADR-0013`'s own classification
  question, reused verbatim).
- See `ADR-0103` for the complete decision record and `Desktop
  Composition Architecture.md` for the full architecture document this
  retrospective summarises. `WP 12.0B`'s own retrospective will record
  the real, final collaborator boundaries once implementation exists to
  describe.
