# WP 16.1B — Health-Check Extension

## 1. Introduction

`WP 16.1B` (commit `b0a4150`, merged as `3f90078`) grows
`scripts/governance-healthcheck.ps1` from `WP 11.2A`'s original eight
checks to sixteen, adding eight checks that each derive their expected
state directly from `src/` or from a register's own internal arithmetic
— never from another register's say-so — and closes `TD-43` (the
script's top-level catch naming only a generic label, never the specific
check or exception). Its full account, including complete
induced-failure evidence for all eight new checks, is `docs/releases/
v0.16.0/WP16.1B Health-Check Extension Report.md`. This retrospective is
written under `WP 16.2C`, sourced from that report and `b0a4150`.

## 2. Purpose

Give `TD-57`'s six named registers (Interface, Exception, DI, Namespace,
Platform Services, Validation) a mechanical check so the drift `WP
16.2A` had to re-derive by hand, once, cannot recur silently the same
way a second time.

## 3. Background

`WP 16.2A`, immediately prior in the same wave, re-derived six
governance registers directly from source after finding them drifted.
That re-derivation was necessarily a one-time, human act — nothing
checked whether it stayed true the moment the next commit landed. `WP
16.1B` was sequenced directly after it specifically so the new checks
would have a currently-accurate baseline to compare against, per the
Release Plan's own dependency note ("otherwise the new checks fail
immediately, correctly").

## 4. The Problem

Three of `TD-57`'s six named registers (Interface, Exception, Namespace)
are mechanically derivable straight from `src/Tempest.Core/` — a
`public interface` grep, an `Exception`-derived-class scan, a
`namespace` declaration scan — yet nothing did so automatically. Two
more governance artefacts (the Technical Debt Register's own summary
line, the Future Capability Register's own stated range) carry internal
arithmetic nothing checked against their own rows. The Governance Index's
stated ADR count, the Academy Register's Work Package coverage, and the
Documentation Register's own `03 Work Packages/` row count were each
similarly un-verified against the directories they describe.

## 5. The Design

Eight new check functions, each following `WP 11.2A`'s own established
shape (`New-CheckResult`, one function per check, ASCII-only console and
`-SummaryPath` output): Interface Register vs. `public interface`
declarations; Exception Register vs. classes deriving from `Exception`;
Namespace Register vs. `namespace` declarations across its own declared
scope, plus an advisory per-namespace file-count check; Technical Debt
Register's summary line vs. its own row count; Future Capability
Register's highest `FCR-nnnn` vs. its stated range, plus an advisory
staleness check; Governance Index's ADR count vs. `docs/adr/`; Academy
Register coverage of every `03 Work Packages/` file (row-presence a hard
`Fail`, the header's own retrospective count a deliberate, temporary
`Warn`); and the Documentation Register's own `03 Work Packages/` row
count against the same directory (also a deliberate, temporary `Warn`).
`TD-43` closes by having the top-level `catch` name the specific check's
own declared name and the thrown exception's runtime type and message,
proven by an actual induced `throw` inserted into one check function,
observed, and reverted. Every one of the eight new checks was proven
non-vacuous the `WP 11.2A` way: run clean, break the real governance
document on purpose, observe the exact `Fail`/`Warn` text, restore with
`git checkout --`, run clean again — full transcripts for all eight
checks and `TD-43` are in the report.

## 6. Alternatives Considered

**Adding checks for the Decision, Risk, and Validation registers with
the same rigour.** Rejected for this Work Package's own declared scope —
those registers are prose-heavy and cannot be mechanically re-derived
from source the way Interface/Exception/Namespace can; the Release Plan
itself named this as explicitly out of scope, leaving only a staleness-
date pattern (demonstrated on the Future Capability Register) as the
cheap partial check available today. `TD-123`, raised later by the
`v0.16.0` review board, records this same boundary as a still-open gap
for the DI, Platform Services, and Validation registers specifically.

**Silently narrowing a check's own severity to `Warn` to avoid a red
run the first time it executes for real.** Rejected explicitly, in the
report's own words: only the two staleness items disclosed in advance
(the Academy Register header count and the Documentation Register row
count, both known-stale pending `WP 16.2B`'s backfill) were treated as
temporary `Warn`s. Everything else this Work Package found stale is
reported as a hard `Fail`.

## 7. Why This Solution Was Chosen

Deriving each new check directly from `src/` or from a register's own
internal count, rather than cross-checking one register against another,
is the only design that actually closes `TD-57`'s root cause — a check
that compared two registers to each other could go stale in lockstep
with both and never notice.

## 8. Architectural Principles

Tooling only — `scripts/governance-healthcheck.ps1` and one Academy
standards document changed; `.github/workflows/ci.yml` was not touched,
since every new check runs against the same checkout the existing
`governance-health-check` job already performs. No register was edited
by this Work Package itself, per its own declared file ownership
(`docs/governance/**` belongs to `WP 16.2A`'s wave).

## 9. Benefits

The health check grows from eight checks to sixteen, all deterministic,
all proven non-vacuous by an actual induced failure rather than by
inspection. `TD-43` closes: a crashing check now names itself and its
own exception in the `Fail` result instead of one indistinguishable
generic label.

## 10. Trade-offs — two brand-new checks, two real findings, on their very first run

**Final run: 16 checks, 11 Pass, 3 Warn, 2 Fail, exit code 1 — and
neither `Fail` is a defect in the new checks.** Both are genuine,
previously-undisclosed governance-register defects the new checks found
against the real, merged `feature/v0.16.0` tree, on the very first time
either check ran for real. This Work Package's own report calls this out
explicitly rather than treating it as an inconvenience to smooth away —
exactly the `WP 11.2A` precedent of disclosing real drift a tool's first
run finds, not narrowing the tool until it passes.

**Finding 1 is the more interesting of the two.** The register's own
documented "Source of Truth" command for the Namespace Register is
`grep -rhoP "^namespace \K[\w.]+" src/...` — anchored at line start.
`src/Tempest.Core/Models/ProjectModel.cs` opens with a UTF-8 byte-order
mark (`EF BB BF`) before its `namespace Tempest.Core.Models;`
declaration, confirmed directly with `od -An -tx1` on the file's first
three bytes. That BOM sits between the true start of the line and the
literal text `namespace`, so the register's own anchored `grep` pattern
silently never matches this one file — not an error in the pattern, a
genuine blind spot in what "line start" means once an invisible
three-byte marker sits in front of it. `WP 16.2A`'s own full
re-derivation, built on that identical `grep`, therefore filed
`ProjectModel.cs` under the register's `*(no namespace declared — global
namespace)*` row instead of recognising it as the first real member of a
namespace with no row of its own. This Work Package's own check uses
PowerShell's `Get-Content -Raw`, which strips a leading BOM
automatically — not a different rule, only a different tool's own
default encoding handling, and it is `Get-Content -Raw` that sees what
the file actually declares. A register whose own documented derivation
command has a blind spot that a different tool's default behaviour
happens not to share is precisely the kind of fact only a second,
independently-implemented derivation can surface — reading the register
harder would never have found it; deriving the same fact a second way,
differently, did.

**Finding 2 is a different lesson: a merge, not an arithmetic error.**
The Technical Debt Register's summary line (39 Resolved, 72 Open) was
authored by `WP 16.2A` on its own branch, before `WP 16.5B`'s own
`TD-116` resolution — a parallel, independent branch — was merged into
the same integration branch. Git's own three-way merge correctly
combined both branches' row edits (`TD-116`'s Status cell now genuinely
reads Resolved), but a merge cannot re-run prose arithmetic that one
side had already written against a tree the other side's change had not
yet touched — so the summary line still states the pre-merge count
(`git merge-base --is-ancestor` confirms the two commits are on
independent branches, neither an ancestor of the other). A governance
register's own internal count can drift not because anyone made a
mistake, but purely as a structural consequence of two Work Packages
correctly running in parallel and later being merged — a class of drift
no single Work Package's own diligence can prevent, only a check run
after the merge can catch.

**The disclosed consequence.** `WP 16.1A`, immediately before this Work
Package in the same wave, made the governance check's exit code a
required `CI Gate` input. Until one of these two findings is corrected,
`CI Gate` will not go green on any branch built on this repository's
current governance-document state — named here as the intended, not
accidental, effect of `FCR-0005` finally having a required, blocking
gate behind it, the exact situation `WP 11.2A`'s own original design
deliberately deferred.

## 11. Common Mistakes

**Trusting a register's own documented "Source of Truth" command as
authoritative without an independent second derivation.** `WP 16.2A`'s
re-derivation was careful, thorough, and used exactly the command the
register itself specifies — and still missed `ProjectModel.cs`, because
the command itself has a blind spot no amount of care applying it
correctly would surface. The lesson is not that `WP 16.2A` was careless;
it is that a single derivation method, however diligently applied,
cannot catch a defect in the method itself — only a second,
independently-built check can.

## 12. Future Evolution

Both findings are handed to the integrator as exact one-line fixes,
neither corrected here per this Work Package's own file ownership — see
the report's "Findings for the Integrator" section for the precise
register edits each needs. `TD-123` (raised by the `v0.16.0` review
board) records that the DI, Platform Services, and Validation registers
`TD-57` also named remain undetected by any mechanical check — the next
natural extension of this Work Package's own pattern. `TD-124` records a
related, adjacent gap this Work Package's own Check 12 cannot close on
its own: a single Technical Debt row whose Status cell was never updated
is invisible to a summary-vs-rows check, since the row is
self-consistent by construction — `TD-120` itself sat stale this exact
way through two subsequent register passes before the review board
caught it directly.

## 13. Key Takeaways

- A governance register's own documented derivation command can itself
  have a blind spot — a BOM defeating a line-anchored `grep` here — that
  only shows up when a second tool, with different default behaviour,
  derives the same fact independently. Trusting the documented command
  is not the same as verifying it.
- A brand-new check's very first real run against a mature, merged tree
  will likely find genuine drift, sometimes for a structural reason (two
  correct parallel branches, merged) rather than anyone's mistake —
  disclosing both real findings as hard `Fail`s, rather than quietly
  reclassifying either as `Warn` to get a clean run, is what makes a
  health check trustworthy rather than merely reassuring.
- Making an advisory check a required gate input (`WP 16.1A`, the
  Work Package immediately before this one) and then immediately finding
  two things that check now blocks on is not a coincidence to be
  smoothed over — it is the predictable, intended cost of finally
  enforcing a control that had real drift sitting behind it the whole
  time.
