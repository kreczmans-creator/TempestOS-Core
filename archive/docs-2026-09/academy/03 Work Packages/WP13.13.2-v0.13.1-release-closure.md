# WP 13.13.2 — v0.13.1 Release Closure

## 1. Introduction

`WP 13.13.2` (`194b067`, merged as `00f7f39`) corrected the release
records once `v0.13.1` was genuinely published. It changed two files and
**zero** `src/` and `tests/` files, created no tag, amended no tag, and
retried no release. It was the last Work Package of the `v0.13.x` train.

This retrospective was written later, by `WP-Z4`, from committed evidence
— see §12.

## 2. Purpose

To make the Release Register and `PROJECT_STATUS.md` describe the release
that had actually happened, and to close the `v0.13.x` train explicitly
rather than by implication.

## 3. Background

`v0.13.1` existed because `v0.13.0`'s tag-triggered `release.yml` run had
failed at its `Test (Release)` step, so packaging and publication never
ran. `WP 13.13.1` prepared the corrected, publishable form. By the time
this Work Package began, `v0.13.1` had been merged, tagged and published —
but the records still described it as it had been mid-flight.

## 4. The Problem

The Release Register's `v0.13.1` row still read *"In preparation — release
branch cut, not yet tagged, merged, or published"*. That became false the
moment the release completed, and a register that describes a shipped
release as unshipped is worse than one that is merely behind: a reader
checking whether `v0.13.1` is available gets a wrong answer from the
document whose job is to answer exactly that.

## 5. The Design

Documentation only, and evidence-first.

The Release Register's `v0.13.1` row moved from *In preparation* to
**Released, published, merged to `main`**, carrying the evidence rather
than the claim: merge commit `6eca5fde` on `main` (parents `6089a218` +
`9707fe7f`, a true merge commit from PR #2 under explicit Product
Approval, no squash, no rebase, tree byte-identical to the branch tip);
annotated tag `b647e2c` → `6eca5fde`, **verified locally and against the
remote peel rather than from the release script's own success banner
(`TD-42`)**; real CI on `main` at that exact pre-tag commit all green (run
`32157115399`); `release.yml` run `32158618270` succeeded end to end and
published the GitHub Release at 2026-08-18T16:14:42Z with both required
assets — `TempestOS-v0.13.1.zip` and
`TempestOS-v0.13.1-engineering-harness.zip` — **each confirmed directly
via `gh release view`, not inferred from workflow success**.

The totals line moved 11 → 12 confirmed released, and `Last Reviewed` was
advanced. `PROJECT_STATUS.md` gained a closure block recording the
`v0.13.x` train as CLOSED and the `WP14` handover position.

**`v0.13.0` was left untouched.** Its row is unchanged and its tag remains
immutable at `6089a218` — tagged and merged but never published, because
its own `release.yml` run failed before packaging. Superseded in content,
never in tag, per Engineering Governance §7.4.

## 6. Alternatives Considered

**Retry `release.yml` against the `v0.13.0` tag.** Rejected by §7.4: a
published tag is immutable, and re-running a release against it is not a
correction but a rewrite. `v0.13.1` exists precisely so that this was
never necessary.

**Amend the `v0.13.0` row to describe it as superseded-and-replaced.**
Rejected — it is superseded in content, not in tag, and the row already
says so accurately.

**Take the release script's success banner as evidence.** Rejected under
`TD-42`, which records exactly that failure mode. The tag was verified
against the remote peel and the assets against `gh release view`.

## 7. Why This Solution Was Chosen

Because a release record is an evidentiary document. Every claim in the
amended row cites something independently checkable — a commit SHA, a
parent pair, a workflow run number, a publication timestamp, an asset
name — rather than asserting that the release happened.

## 8. Architectural Principles

Engineering Governance §7.4 (a published tag is immutable; a mistake found
after tagging produces a new version, never a silently altered old one)
governed what could and could not be touched. `TD-42`'s rule — verify the
artefact, not the tool's report of the artefact — governed how each claim
was established.

## 9. Benefits

The Release Register answers "is `v0.13.1` available?" correctly, with
evidence. The `v0.13.0`/`v0.13.1` relationship is recorded honestly:
superseded in content, immutable in tag. And the `v0.13.x` train has an
explicit closure point rather than trailing off.

## 10. Trade-offs

None material. The Work Package was scoped to two files and took nothing
else on — which is why it could be verified line by line.

## 11. Common Mistakes

**Trusting a success banner.** `TD-42` exists because a script reporting
success is not the same as the artefact existing.

**Letting a status field outlive its truth.** "In preparation" was correct
when written and false a day later, and nothing but a deliberate closure
pass changes that.

**Touching the previous tag while closing the current one.** `v0.13.0`'s
row and tag were deliberately left exactly as they were.

## 12. Future Evolution

This Work Package's own closure statement recorded *"38 delivered
`v0.13.x` Work Packages, 38/38 Academy retrospectives, zero missing and
zero duplicates"* — and it did not have one itself. The gap was found by
`WP-Z4`'s release-preparation audit, which observed that this Work Package
sits inside `v0.14.0`'s commit range (it was merged to `main` *after* the
`v0.13.1` tag) and therefore ships first under `v0.14.0`. It is included
in `v0.14.0`'s `WorkPackages.md` and this retrospective was written there,
from the commit message, the Release Register row and the
`PROJECT_STATUS.md` block it produced.

**Stated limitation:** this article is reconstructed from committed
evidence only. Where a contemporaneous retrospective would have recorded
reasoning that was never written down, this one records what the
repository can support and no more.

## 13. Key Takeaways

- A release record is evidence, not narrative. Cite the SHA, the run
  number, the asset name.
- Verify the artefact, never the tool's claim about it (`TD-42`).
- A closure pass is itself a Work Package, and §6 applies to it — a Work
  Package that certifies retrospective completeness is not exempt from
  needing one.
- Work merged after a tag ships under the *next* release, and belongs in
  that release's accounting.
