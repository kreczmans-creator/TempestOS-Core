# WP 13.9.0 — `v0.13.0` Engineering Readiness Review

## 1. Introduction

The retrospective for `WP 13.9.0`, the **first execution of the permanent
Engineering Readiness Review (ERR)** `ADR-0106` defines, applied to
`v0.13.0` at `feature/v0.13.0`'s then-HEAD commit
`88e41a2a48d1f89ea085b4817ee41b3ac0262a06`. Six independent discipline
reviews — Chief Architect, Principal Software Engineer, joint QA
Lead/Workflow Engineer, Technical Author, a disclosed additional
Security/Trust discipline, and Product Manager — each performed **before
seeing the others' conclusions**, reconciled into a single Programme
Review and one report.

**This is a review Work Package, not an implementation one.** It produced
findings, classifications, and a verdict — no feature, no fix. Its entire
commit, `0b8726f`, is two files: `PROJECT_STATUS.md` (+38/−1) and the new
`docs/releases/v0.13.0/WP13.9.0 Engineering Release Report.md` (+572),
609 insertions against one deletion. Nothing under `src/` or `tests/` was
touched.

**Its verdict was `NOT READY`.** Four of six categories independently
reached Not Ready via largely non-overlapping evidence. The commit message
closes plainly: "Not tagged. Not pushed. No GitHub Release created."

**A note on this document's own provenance.** `WP 13.9.0` was genuinely
completed but was, for a period, the only completed `v0.13.0` Work Package
with no row in `WorkPackages.md`'s delivered table — a gap disclosed and
corrected by `WP 13.11D` rather than left silently absent. It did receive a
`PROJECT_STATUS.md` entry of its own at the time. This retrospective is
grounded strictly in `0b8726f`'s own commit message, the Engineering
Release Report it produced, `WorkPackages.md`'s own `WP 13.9.0` row, and
`PROJECT_STATUS.md` — plus direct checks of repository state where a claim
is checkable today (§12).

## 2. Purpose

To answer one question objectively, from fresh evidence: **is `v0.13.0`
ready to release?** — and to answer it by `ADR-0106`'s own fixed
procedure rather than by narrative judgement, producing one of exactly
four permitted verdicts derived from a strict-priority table.

A second, equally explicit purpose: to answer it *without fixing anything*.
This execution's commissioned brief was deliberately narrower than prior
sign-offs' own precedent — `WP 11.9.0`'s Part C had made small in-review
corrections, which `Engineering Readiness Review Architecture.md` §5
expressly permits for "small, genuinely narrow corrections (a stale
register figure, a missing cross-reference)". `WP 13.9.0` declined that
latitude entirely: **review, classify, report, stop.**

## 3. Background

`ADR-0106` and `docs/architecture/Engineering Readiness Review
Architecture.md` establish the ERR as a permanent gate, defining **five**
readiness categories — Architecture, Implementation, Verification,
Governance, Release — executed by the six-discipline Programme Review
structure proven at `WP 10.9A`/`WP 11.9.0` and re-executed at
`WP 12.9.0`/`WP 12.9.2`. §4 of that document supplies a blocking taxonomy
(Release Blocking; Disclosed, Non-Blocking; Pre-Existing, Unaffected) and
a strict-priority derivation table; §6 supplies exactly four verdicts —
`NOT READY`, `ACCEPT WITH OBSERVATIONS`, `CERTIFIED WITH ACCEPTED
TECHNICAL DEBT`, `CERTIFIED`.

Two prior precedents shaped this execution. `v0.11.0`'s own review found
`TD-42`/`TD-43` precisely because a QA Lead did not defer to a Workflow
Engineer's "looks fine" — the independence-before-reconciliation rationale
`ADR-0106` cites for itself. `v0.12.0`'s `WP 12.9.0` found a single-category
`NOT READY` on a CI gap where `main` itself, though unpushed, at least
already held the release's commits.

`v0.13.0`'s own substantive content is a plugin trust/capability/signature
enforcement platform (`ADR-0107`–`ADR-0112`) delivered across seven
commits — `WP 13.0.0` through `WP 13.3B` — none of which had been merged
or pushed when this review ran.

## 4. The Problem

1. **Is each of `ADR-0106`'s five categories genuinely ready** — assessed
   against its own evidence table, from fresh evidence, not from any prior
   Work Package's own report?
2. **Does a five-category model suffice for a release whose entire content
   is a security platform?** — and if it does not, how is the extension
   made without silently deviating from a ratified ADR?
3. **Are the prior Work Packages' own claims true?** Seven commits of
   self-reported completion existed; none had been independently checked
   from source at release scope.
4. **Has real CI ever run against this release?**
5. **Does the shipped trust boundary actually hold** against an adversarial
   read by a reviewer who did not build it?

## 5. The Design

**The design here is the design of the review.** No software was
designed, built, or changed.

**Six independent discipline reviews, mapped onto six readiness
categories.** Five are `ADR-0106`'s canonical categories; the sixth,
**Security/Trust**, was an explicit, **disclosed** commission for this
release specifically. The report is careful about that addition's status:
`ADR-0106`'s own "Future Considerations" section anticipates exactly this
case ("If a future release finds the six-discipline structure genuinely
insufficient... that is itself Technical Review material... a candidate
for revising this ADR directly, not a silent deviation from it"), and the
report classifies the extension as "a deliberate, disclosed methodology
extension for this specific release — not a silent deviation from the
standard model, and not evidence the canonical five-category model itself
needs revising (that judgement is Product Approval's own, informed by this
report, not asserted here)."

**Independence before reconciliation, per §5.** Each discipline reached its
own conclusion before seeing any other's. Reconciliation happened once, in
Part B, as a distinct step — not as a running consensus.

**Fresh evidence, not inherited claims.** "Every claim in every
discipline's own report was independently re-verified from source this
Work Package... no prior Work Package's own report (`WP13.0A` through
`WP13.3B`) was assumed correct without a fresh check."

**Shared evidence gathered once, centrally.** Debug/Release builds
(0 Warnings/0 Errors both configurations), the full regression suite
(2,519/2,519 both configurations — 2,298 `Tempest.Core.Tests` + 221
`Tempest.Desktop.Tests`), and `governance-healthcheck.ps1` (7 passed,
1 warned, 0 failed) were run once, fresh, by the orchestrating review at
that exact commit and cited by the disciplines that needed them, rather
than re-run six times. The Governance discipline nonetheless re-ran the
health check itself and reported an exact match.

**Read-only by construction.** Part C ("Corrections Made Within This Work
Package") reads, in full: **None.** The report records that `git status`
confirmed no file under `src/`, `tests/`, or any pre-existing governance
document was touched by any of the six discipline agents.

### What the six disciplines found

**A1 — Chief Architect (Architecture readiness): Pass, with
observations.** Zero Release Blocking; four Disclosed, Non-Blocking. ADR
Register versus `docs/adr/` an exact 111/111 match, independently
recounted; every `ADR-0107`–`ADR-0112` Decision confirmed honoured by
direct source read — including specific re-confirmation that `WP 13.2B`'s
`NeverEligibleServiceResolveTypes` denylist and `WP 13.3B`'s
registry-Id-spoofing fix both remain genuinely present;
`git diff v0.12.0..HEAD --stat -- "*.csproj"` empty, so zero
project-reference changes across the entire release. Findings: `Plugin
Platform Architecture.md` absent from `Architecture Document Register.md`
(register file count stale at 25 against a real 26); `TD-49` and `TD-50`
each re-assessed against `ADR-0112`'s literal Decision text and confirmed
real, Open, and **not** ADR violations; and `WP 13.3B` having no
`WorkPackages.md` row, Academy retrospective, or `PROJECT_STATUS.md`
entry — classified here as adjacent to, not inside, Architecture's own
§2.1 evidence table.

**A2 — Principal Software Engineer (Implementation readiness): Not
Ready.** Three Release Blocking findings.
- **F1** — `WP 13.3B` is in an undocumented governance state.
  Implementation's own §2.2 evidence table names this blocking verbatim:
  "Any Work Package is in an undocumented or ambiguous state."
- **F2** — `88e41a2`'s own commit message claims a "20,000-trial
  differential fuzz harness comparing it against a from-scratch
  reimplementation... zero mismatches, zero nondeterminism". An exhaustive
  search of current source and full `git log --all -p` history found no
  such harness, ever, anywhere — only four committed, deterministic,
  fixed-shape equivalence tests, real and supportive of the underlying
  conclusion but categorically not a randomised 20,000-trial harness.
- **F3** — `PluginManifest`'s public constructor grew from 6 to 11
  parameters, the five new ones all **required**, no defaults; 30+ test
  call sites needed updating. Verbatim one of `ADR-0106`'s own three named
  Release-Blocking examples ("an undocumented public API break"). The
  report records mitigating context (`PluginManifest` is constructed
  exclusively by the Host-owned `PluginManifestDiscoveryService`;
  `src/Plugins/` is empty, so no external consumer is harmed today) and
  states explicitly that this does not change the classification, "which
  is by a finding's own nature, not its current blast radius, per
  `ADR-0106`'s own explicit rule."
Two further Disclosed, Non-Blocking findings: the abstraction-level
inconsistency across the trust-retrofit constructors (`CommandHandlerTable`/
`EventBus` take the concrete `CurrentComponentAccessor`; `NavigationService`/
`CommandRegistry` take the interface — already disclosed in `WP 13.2A`'s own
commit message), and `IDiagnosticsProvider` gaining a new interface member
(`Plugins`).

**A3 — QA Lead / Workflow Engineer (Verification readiness): Not Ready.**
One Release Blocking finding, described in the report as "the single most
consequential evidence in this review": real, GitHub-hosted CI has **never
run** against any commit of this release. Not unknown — structurally
impossible: `feature/v0.13.0` has no upstream, does not exist on `origin`
at all, and `git log main..feature/v0.13.0` showed seven commits, none
merged. `.github/workflows/ci.yml`/`release.yml` were confirmed present,
unmodified since `v0.11.0`, and would execute correctly once pushed — the
gap is purely that they have never been given the chance. `gh` was
confirmed unavailable in the environment. One Disclosed, Non-Blocking
finding independently corroborating A2's F2: the same fuzz harness
searched for and not found.

**A4 — Technical Author (Governance readiness): Pass, with observations.**
Zero Release Blocking; five Disclosed, Non-Blocking, all newly surfaced by
this review: `WP 13.3B` undisclosed anywhere in governance documentation
(the mirror image of `WP 13.2B`'s own gap — except `WP 13.2B`'s **is**
disclosed and `WP 13.3B`'s is not); `Architecture Document Register.md`
untouched by any `v0.13.0` Work Package; both plugin architecture
documents still carrying `WP 13.0A`-era "nothing implemented yet" Status
headers, now false; `Documentation Register.md`'s retrospective count
stale at 107 against a real 112; and `PROJECT_STATUS.md`'s own "Current
Release"/"Current Work Package"/"Current Development Branch" sections
frozen at `v0.11.0`/`WP 11.3B` content, contradicting that same document's
own preamble.

**A5 — Security/Trust (the disclosed, additional sixth category): Not
Ready.** One Release Blocking finding, newly found, empirically
demonstrated, and not previously tracked anywhere — not in the ADRs' own
Negative Consequences, not `TD-49`/`TD-50`, not `Plugin Trust & Isolation
Architecture.md`'s Risks section. `PluginAssemblyLoader.EnforceTrust`
scans only the one manifest-declared assembly's own types (`ADR-0111`'s
literal scope), while Module Discovery
(`ReflectionFrameworkDiscoveryService`, deliberately left "completely
unchanged" per `ADR-0110`) scans `AppDomain.CurrentDomain.GetAssemblies()`.
A live proof-of-concept built against that commit's actual compiled
`Tempest.Core.dll` — a real, run, reproducible demonstration, not a
hypothetical reading — showed a plugin's one declared assembly (`AsmA.dll`,
zero requested capabilities, the *lowest* `UnsignedLocal` tier) inheriting
a type from a second, wholly undeclared `AsmB.dll` in the same folder;
resolving the base-type chain during `EnforceTrust`'s own `GetTypes()`
call loads `AsmB` as an unavoidable CLR side effect, whose
`EvilModule : IModule` is never trust-checked, capability-checked, or
constructor-conformance-checked, yet is discovered and activated as an
ordinary module. Because no principal was recorded for it, its ambient
component principal is `null` — and `PluginTrustPermission.IsFirstParty(null)`
is `true`, so **every** dynamic capability check across `NavigationService`/
`CommandHandlerTable`/`CommandRegistry`/`EventBus` is skipped rather than
merely satisfied, and its constructor freely receives the real, mutable
`CurrentComponentAccessor` singleton — precisely the type `WP 13.2B`'s
denylist exists to forbid for every tier. The report distinguishes this
categorically from `ADR-0110`'s disclosed "not a hard sandbox" caveat and
from `TD-49`/`TD-50`, characterising it as "a structural blind spot at the
join between `ADR-0110`'s own 'Module Discovery unchanged' decision and
`ADR-0111`'s own 'the plugin's own assembly' scope — not a coding defect
inside `EnforceTrust` itself, which does exactly what its governing ADR
describes."

**A6 — Product Manager (Release readiness): Not Ready.** One Release
Blocking finding, derived independently from this discipline's own
branch/repository-state evidence gathered for its own separate purpose,
before it had any access to A3's report — and landing on the identical
underlying fact. `VERSION` (`0.12.0`, correctly unbumped) and `Release
Notes.md`'s absence were both confirmed correctly deferred, release-time
actions rather than findings. `TD-06`/`FCR-0010`, `TD-09`/`TD-10`/`TD-11`
were independently re-confirmed Resolved against real code; `TD-49`/`TD-50`
and `FCR-0085`–`FCR-0088` were each confirmed Disclosed, Non-Blocking. The
never-pursued REST-deployment half of the roadmap's own trigger condition
was assessed as a legitimate, repeatedly disclosed scope narrowing, not a
defect.

### The reconciliation

**No contradiction was found between any two of the six reports.** Three
convergences are recorded, each reached via independent evidence paths:
the branch/CI gap (A3, A6); the `WP 13.3B` documentation gap, found
independently by **four** of six disciplines; and the unsubstantiated fuzz
harness claim, specifically verified and disproven by two disciplines and
"passed over uncritically in narrative summary" by a third (A4) — named
explicitly in the report as a small, direct illustration of why the
independence discipline exists.

The `WP 13.3B` gap received two different classifications — A1
Disclosed-Non-Blocking (Architecture's §2.1 table has no
Work-Package-documentation blocking criterion), A2 Release-Blocking
(Implementation's §2.2 table names it verbatim). The report states this
is "**not a contradiction to resolve**" but two categories correctly
applying their own differently-scoped criteria to one fact.

Applying §4's derivation table literally: four of six categories Not
Ready, and row 1 fires — **verdict `NOT READY`**, with rows 2–4 never
reached. The Reconciled Definition of Done scored five of twelve items
fully satisfied, four (`#1`, `#3`, `#4`, `#7`) carrying real findings, and
one (`#6`) Architecture-clean but surfacing a genuine gap through the
disclosed sixth category.

## 6. Alternatives Considered

**Folding trust into the canonical five categories.** The alternative to
commissioning a sixth discipline was to assess the trust platform under
Architecture and Implementation readiness. The report does not claim this
would have failed — but the outcome is instructive: Architecture readiness
independently scored **Pass** on every dimension it checked, and the
trust-boundary bypass surfaced only under a discipline whose entire brief
was adversarial security. The extension was made **disclosed**, and the
report is explicit that its own existence "is not itself evidence the
canonical model needs revising; that judgement belongs to Product
Approval, informed by this report."

**Resolving A1 and A2's differing classifications of the same fact into
one.** Rejected deliberately. §2's own design derives each category's
status "solely... from the findings raised against it", so Implementation's
Release-Blocking classification governs Implementation's status and is not
overridden by Architecture's narrower framing.

**Making small in-review corrections, per `WP 11.9.0`'s Part C
precedent.** Permitted by §5 and declined by explicit brief. Five real,
newly-surfaced documentation-currency gaps sat directly in front of a
Technical Author who could have fixed several in minutes, and none was
touched.

**Prescribing the Security/Trust fix.** Declined explicitly: the report
"does not recommend a re-execution timeline or prescribe the
Security/Trust fix's own shape — that judgement belongs to the
Architecture tier, informed by A5's own full evidence."

**Issuing any other verdict.** Not reachable. §4's table is strict
priority, first match wins; one Not Ready category already resolves it,
and four independently-derived ones make the case, in the report's own
words, "not a marginal or contestable case."

## 7. Why This Solution Was Chosen

**Because objectivity had to survive four Not Ready findings.** The
strongest argument for a mechanical derivation table is a review whose
result is unwelcome. Every step from finding to verdict here is
traceable: a finding is classified into one of three kinds, a category's
status follows from its findings, and the verdict follows from the
categories by strict priority. The only judgement exercised anywhere is
the classification of an individual finding.

**Because independence is what produced non-overlapping evidence.** Four
Not Ready categories reached "via largely disjoint evidence
(branch/CI mechanics; API/documentation diff auditing; a live security
proof-of-concept; independent branch-state re-derivation)". A single
reviewer, or six reviewers reading each other's drafts, would very
plausibly have produced one finding and a consensus.

**Because a proof-of-concept beats a code reading.** A5's finding was
demonstrated against the real compiled binary. That is why it was
actionable immediately, and why the remediation chain that followed never
had to argue about whether the gap was real.

**Because the "no fixes" brief protects the evidence.** A review that
fixes as it goes cannot cleanly report what it found; the state it
assessed no longer exists. Part C's "None", backed by a `git status`
check, keeps the report a faithful description of commit `88e41a2`.

## 8. Architectural Principles

- **Independence Before Reconciliation** — six disciplines, no discipline
  sees another's conclusions until Part B. `ADR-0106`'s own rationale, and
  the `TD-42`/`TD-43` precedent that earned it.
- **Fresh Evidence, Not Inherited Claims** — no prior Work Package's
  report assumed correct. The fuzz-harness finding exists solely because
  two disciplines set out to verify a claim rather than repeat it.
- **Classification by a Finding's Own Nature, Not Its Blast Radius** —
  `ADR-0106`'s explicit rule, applied to F3 even though no external
  consumer is harmed today.
- **Strict-Priority Derivation, Not Narrative Judgement** — the verdict
  falls out of a table; rows 2–4 were never evaluated.
- **Disclose, Don't Fabricate** — the sixth category is disclosed as an
  extension rather than presented as standard; the ADR-revision question
  is named and left to the correct tier.
- **Tier Separation** — "the Programme Review recommends, it never
  decides; Product Approval alone issues a verdict." The report states
  plainly that it "does not authorise any push, merge, or code change."
- **Review, Classify, Report, Stop** — the execution boundary, held
  absolutely.

## 9. Benefits

- **A genuine, exploitable, previously-untracked trust-boundary bypass was
  found before it reached `main`** — empirically demonstrated against the
  actual shipped binary, at the lowest trust tier, requesting zero
  capabilities, via entirely ordinary multi-assembly plugin packaging.
- **The six-discipline structure demonstrably outperformed any single
  pass.** The report names the fuzz-harness claim explicitly as the
  illustration: two disciplines verified it and found it did not hold; a
  third repeated it uncritically in narrative summary. Reconciling six
  independent passes caught what one would not have.
- **Four independent evidence paths, one conclusion.** The branch/CI gap
  was reached twice from disjoint evidence; the `WP 13.3B` gap four times.
- **An unsubstantiated verification-rigor claim was caught in this
  project's own commit history.** A governance record that asserts more
  rigor than it can evidence is a specific, correctable failure mode, and
  it was corrected.
- **`ADR-0106`'s taxonomy proved it could return an unwelcome verdict
  cleanly.** `NOT READY` had never been used before this execution; the
  ERR Architecture document lists it as "the case this taxonomy exists to
  make unambiguous."
- **The whole `WP 13.9.x` → `WP 13.11x` hardening chain descends from
  this review.** `WorkPackages.md`'s own `WP 13.9.0` row characterises it
  as "the release-readiness review that opened the `WP 13.9.x` hardening
  chain."

## 10. Trade-offs

- **Nothing was fixed.** Every finding — a live security bypass among them
  — was left open at the end of this Work Package, by design. That is
  correct for the brief, and it means the review's value is entirely
  contingent on the remediation Work Packages that follow it.
- **The sixth discipline is a per-release extension, not a ratified
  model.** `ADR-0106` still defines five categories. Whether the canonical
  model should change is explicitly deferred to Product Approval, and this
  retrospective records no evidence that it has been.
- **All build, test, and health-check evidence is local.** 2,519/2,519
  passing in both configurations is a genuine result and a local one — the
  very fact A3 and A6 flagged as blocking.
- **Shared evidence gathered once trades six-way redundancy for
  efficiency.** Only the Governance discipline independently re-ran the
  health check; the build/regression figures were centrally gathered and
  spot-confirmed rather than re-run per discipline.
- **A Work Package auditing governance completeness left an incomplete
  governance footprint of its own.** `WP 13.9.0` had no
  `WorkPackages.md` row for a considerable period — the only completed
  `v0.13.0` Work Package missing from that table — a gap disclosed and
  corrected by `WP 13.11D`. `WP 13.11D` also records rejecting a fourth
  reported defect on inspection: `WP 13.9.0`'s `Not started` cell in the
  roadmap-*predicted* table is correct and deliberately unchanged, because
  that table is a frozen branch-cut snapshot the document itself states is
  never re-derived.

## 11. Common Mistakes

1. **Treating two categories' different classifications of one fact as a
   contradiction.** A1 and A2 classified the identical `WP 13.3B` gap
   differently and both were correct — each applied its own category's own
   evidence table. Forcing a single classification would break §2's own
   derivation design.
2. **Assuming "CI is configured" means "CI has run".** The workflows were
   present, unmodified, and correct; they had simply never executed
   against any commit of this release. A3 distinguishes "unknown" from
   "genuinely has not happened, and structurally could not have."
3. **Reading a mitigating context as a downgrade.** F3's blast radius is
   nil today, and it is still Release Blocking, because `ADR-0106`
   classifies by a finding's nature.
4. **Repeating a prior commit message's verification claim as
   established fact.** A4 did exactly this in narrative summary while A2
   and A3 disproved it. The lesson is named in the report itself.
5. **Assuming a security finding is closed because a fix landed.**
   `WP 13.9.1` closed A5's bypass; `WP 13.9.2` re-tested it against a
   fresh live proof-of-concept and found the fix still incomplete. Three
   further Work Packages followed.
6. **Reading `IsFirstParty(null) == true` as a defect.** It is deliberate
   — every actor that exists today is First-Party, and `WP 13.11D` later
   confirmed it is why first-party UI is not accidentally blocked. A5's
   finding is that an *untrusted* module reached that `null` state, not
   that the predicate is wrong.

never by `WP 13.9.0` itself:**

  `WP 13.9.1`" note. `WP 13.9.2` then re-verified against a fresh live

  `AppDomain` only around `GetTypes()`/`IsAssignableFrom`, not around a

- **A2 F2 (the fuzz harness)** — closed by `WP 13.9.1`, which replaced the

- **A4 Finding 5 — still open.** `PROJECT_STATUS.md`'s "Current

**A fresh ERR execution is required to re-derive an updated verdict**;
`WP 13.9.1`'s own record states this is not assumed by any remediation

**Whether `ADR-0106` itself should adopt a Security/Trust category** — or
a general mechanism for per-release discipline extensions — remains an
open question this review deliberately declined to answer.

## 13. Key Takeaways

- **A review that fixes nothing can still be the most consequential Work
  Package in a release.** `WP 13.9.0` touched two documents and changed no
  code, and everything from `WP 13.9.1` to `WP 13.11D` exists because of
  what it found.
- **Independence is not a formality; it is the mechanism.** Four of six
  disciplines found the same governance gap without coordination; two
  found the same CI fact from disjoint evidence; two disproved a claim a
  third had repeated. None of that is reachable from a single reviewer or
  a consensus process.
- **A live proof-of-concept converts an argument into a fact.** A5's
  finding was never disputed by any subsequent Work Package — it was
  remediated, re-tested, found incomplete, and remediated again, because
  the demonstration left nothing to debate.
- **Extending a ratified process is safe when it is disclosed and its
  status is stated.** The sixth category was commissioned openly, labelled
  as an extension throughout, and explicitly denied the authority to imply
  that `ADR-0106` should change.
- **A verdict vocabulary earns its keep the first time it must say
  something unwelcome.** `NOT READY` had never been used; the taxonomy
  produced it mechanically, from four independently derived categories,
  with no room for a softer wording to be invented in its place.
