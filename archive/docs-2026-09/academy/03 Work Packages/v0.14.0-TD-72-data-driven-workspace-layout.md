# TD-72 — Data-Driven Workspace Layout Replacing the Compile-Time Docking Grid

## 1. Introduction

`76a520b` replaced `DockingGrid`'s compile-time five-column, three-row
`Grid` with `WorkspaceLayoutTree`, an immutable tree of arbitrarily nested
splits and tab groups plus floating windows, implementing `ADR-0095` — a
number reserved for exactly this question on 2026-08-05 and left unwritten
until now. `6e38948` closed the row for real with a running-application
verification pass that found one surviving mutation the closure itself had
missed. A pre-`v0.14.0` engineering-body-of-work row; produced the
companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/36-workspace-layout-and-docking.md`.

## 2. Purpose

To make drag-to-dock, tabbed panel groups, arbitrary splitting, panel
reordering and floating panels possible at all — none of which the
compile-time grid could express, because panels were assigned to a dock
once at composition time and could never move.

## 3. Background

`DockingGrid` was a compile-time 5-column × 3-row `Grid`;
`SetLeftPanel`/`SetRightPanel`/`SetBottomPanel` assigned panels once.
`WorkspaceDockPosition` had no `Floating` member. Exactly one `Window`
subclass existed, so multi-monitor engineering work was not supported —
the `Screens` API was used only to validate a restored window position.
The missing capabilities were missing from the vocabulary, not from the
implementation: there were three places a panel could be and all three
were occupied, so "drag this panel there" had no *there*.

## 4. The Problem

A brief and five mock-ups describing drag-to-dock, tabbed groups,
arbitrary splits and floating multi-monitor panels, against a shell whose
model had no representation for any of them.

## 5. The Design (`ADR-0095`)

The abstraction is replaced, not decorated:
`WorkspaceLayoutTree` — `LayoutSplitNode(Orientation, Children, Weights)`
or `LayoutTabGroupNode(PanelIds, SelectedIndex)`, the only leaf — plus
`FloatingLayoutWindow[]` and `PanelPresentation(IsPinned, IsCollapsed)`.
A lone docked panel is a tab group of one, which makes "drop a panel onto
another to tab them" the ordinary insert rather than a special case. Every
operation (`Dock`, `DockToEdge`, `Float`, `MoveFloating`, `Remove`,
`SelectPanel`, `SetWeights`, `SetPinned`, `SetCollapsed`) is a pure
function returning a new normalised tree, so no half-applied drag can
exist. Sizing is proportional, never pixels. Normalisation collapses
one-child splits and nested splits sharing their parent's orientation, the
debris repeated dock/undock would otherwise leave. The document area is a
panel like any other — a future surface registers one
`WorkspacePanelDescriptor` and gains docking, tabbing, splitting,
floating, collapse, auto-hide and persistence with no change to the
model, the renderer or the drag logic; `DigitalThreadGraphView`'s own
recorded reason for not being a panel ("exactly three physical dock
slots, all already occupied") no longer exists. Rendering is a total
function from tree to visual tree. Persistence is a versioned,
hand-written DTO through `ISettingsProvider`, deliberately not the
engineering persistence authority (`TD-85`) — session state, not domain
data — reading total: malformed, foreign or unrecognised data degrades to
a fallback rather than an exception. `WorkspaceLayoutMigration` preserves
existing user preferences as exact fractions rather than renormalised
weights — a test written as the user's own question found that
substituting the weight and renormalising gave 23.8% where 25% was
recorded. `TD-70`'s responsive rule is preserved, now expressed against
the tree rather than three named docks. `DockingGrid`, `PanelHostControl`
and `PredefinedLayouts` were deleted with their tests, their guarantees
re-proven against the new host.

`6e38948`'s closure verification ran the real shell, found no surviving
reference to the deleted types anywhere but historical prose, and traced
all nine required capabilities to production wiring rather than test-only
entry points. Six mutations were run against the closure claims and one —
deleting the host's own `SizeChanged` subscription — survived, leaving all
260 Desktop tests green: `TD-83`'s own smell had been reintroduced one
level up, because every responsive test called `ApplyResponsiveLayout`
directly and nothing proved the rule was wired at all. Closed with a test
that drives a real layout pass and never names the method, so the mutant
could not hide behind the method name; the mutant then died.

## 6. Alternatives Considered

Decorating the existing three-dock geometry to add drag-to-dock and
tabbing incrementally — implicitly rejected: the commit states the
abstraction is "replaced, not decorated" because the missing capabilities
had no representation to decorate onto.

## 7. Why This Solution Was Chosen

Because every capability the brief and mock-ups required was expressible
in one model — a tree of splits and tab groups plus floating windows —
rather than requiring a separate mechanism per capability.

## 8. Architectural Principles

`ADR-0095` establishes that the workspace layout is a data-driven tree,
not a compile-time arrangement — a total, pure, testable model with the
renderer as a total function over it, so drag-to-dock, tabbing, splitting
and floating are properties of the model rather than separate mechanisms
bolted onto a fixed grid.

## 9. Benefits

119 tests (81 model/geometry/serialisation/preset/migration with no UI, 38
renderer and controller); eleven mutations run and all eleven killed — one
survived first time and exposed a real coverage gap (nothing exercised a
split reducing to a single child), closed with three tests before it
died. `TD-70` and `TD-71`'s guarantees, ribbon minimisation, and existing
user preferences all preserved through the replacement rather than
restarted.

## 10. Trade-offs

Disclosed, all new: `TD-90` (focus across a re-render), `TD-91` (the
edge-based projection is lossy for tabbed and floating panels), `TD-92`
(no live drag preview adorner) — re-checked against the source at closure
and confirmed still accurate. `TD-94`, found incidentally during closure
verification, was a case-sensitivity defect in `PluginTrustStore`
unrelated to docking, fixed in the same commit because it was one of the
two remaining "environment" test failures the closure pass had to account
for honestly rather than wave through.

## 11. Common Mistakes

Carrying two failing tests forward as "pre-existing environment cases"
without checking both are actually environment-dependent — one of the two
`6e38948` inherited was a real cross-platform defect (`TD-94`), not an
environment artefact, and only checking rather than assuming caught it.
Writing a responsive test that calls the implementation method directly
rather than driving a real layout pass — which is exactly how `TD-83`'s
smell survived inside the very work package written to close it.

## 12. Future Evolution

`TD-80`'s document and drawing viewer, later this release, is delivered as
"an ordinary `TD-72` panel" with no per-panel code of its own — the direct
payoff of this row's "document area is a panel like any other" decision.

## 13. Key Takeaways

- When several capabilities are all "missing from the vocabulary" rather
  than merely unimplemented, replace the abstraction rather than
  decorating it.
- A closure claim needs a mutation run against the closure's own claims,
  not just the feature's own tests — the surviving `SizeChanged` mutation
  found a gap the feature tests had all missed.
- Do not assume a carried-forward "pre-existing environment failure" is
  actually environment-dependent; check each one, because one of two here
  was a real defect.
