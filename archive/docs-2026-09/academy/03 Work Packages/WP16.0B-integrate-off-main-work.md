# WP 16.0B — Integrate Off-`main` Work

## 1. Introduction

`WP 16.0B` (commits `1e44daf`, `4198289`; merged as `a4f891b`) brings
`WP 15.2A`'s finished, off-`main` fix onto `feature/v0.16.0` and applies
two of `WP 16.0A`'s six reserved decisions — `D-026` (fold the orphaned
`docs/releases/v0.15.1/` folder into `v0.16.0`) and `D-022` (defer the
Companion branch to v1.1) — as the boundaries this Work Package's own
scope stays inside. Its full account is `docs/releases/v0.16.0/WP16.0B
Integration Report.md`. This retrospective is written under `WP 16.2C`,
sourced from that report and both commits.

## 2. Purpose

Make `main`'s eventual successor state the only place `WP 15.2A`'s
finished work lives, close the phantom `v0.15.1` release folder the
Release Plan's own Q6 identified, and record the Companion branch's
disposition without touching a line of Companion code.

## 3. Background

`WP 15.2A` (`TD-120`, Desktop test suite persistence-root cleanup) had
already merged cleanly and passed CI on its own branch,
`feature/wp15.2a-td120-persistence-root-cleanup`, but had never reached
`main` or any release branch — its own `docs/releases/v0.15.1/` folder
was, in its own words, "Not a release," with no tag and no Release
Register row. Separately, the Companion mobile application
(`claude/tempestos-companion-mobile-ubznt3`) sat 64 commits behind
`main` with an open `TD-82` ("merge or formally reject") and an `FCR-0092`
citation the Future Capability Register did not resolve.

## 4. The Problem

Two pieces of finished-but-unlanded work needed a disposition before any
later Work Package could safely assume a stable `v0.16.0` base: a real
folder that looked like a release but was not one, and a branch that
looked abandoned but was not formally rejected. Neither could be
resolved by code alone — both are the "Product — scope boundary" and
"Sequencing" decisions `WP 16.0A` had already drafted, `D-022` and
`D-026`.

## 5. The Design

The `WP 15.2A` branch merged non-fast-forward (`1e44daf`); its
Implementation Report moved into `docs/releases/v0.16.0/` with a
"Location" note, and the `v0.15.1` folder's own `WorkPackages.md` —
which itself stated "Not a release" — was deleted, applying `D-026`
literally. Every reference the health check's own literal path checks
read was repointed in the same commit so Checks 4 and 5 stayed green
rather than breaking on a moved file: `Documentation Register.md`'s
`v0.15.1` row became the `docs/releases/v0.16.0/` row, `PROJECT_STATUS.md`
was updated, and the `WP 15.2A` retrospective's own Related Documents
list was corrected. `TD-82` moved to "Deferred to v1.1 per `D-022`
(Proposed)"; the Companion branch itself was left untouched — not
merged, not deleted — and `FCR-0092` was recorded as a Companion-scoped
number sitting outside the Future Capability Register's own
`FCR-0001`–`FCR-0088` range, with no new entry added for it.

## 6. Alternatives Considered

**Leaving the `v0.15.1` folder in place and simply adding a
cross-reference note to `v0.16.0`.** Rejected — a folder shaped exactly
like a release, with no tag and no Release Register row, is the precise
phantom-release pattern the health check and `TD-57` exist to prevent;
leaving it in place would have kept the ambiguity `D-026` was written to
resolve rather than closing it.

**Formally rejecting the Companion branch outright, deleting it.**
Rejected — that is not what `D-022` decided; the branch is retained,
deferred to v1.1, not discarded, and this Work Package's own scope is
explicitly to apply the decision as recorded, not to relitigate it.

## 7. Why This Solution Was Chosen

Repointing every literal path reference in the same commit that performs
the move keeps the health check's own before/after state consistent —
a check that reads a specific path literally has no way to know a
document moved unless something tells it, and doing so as a separate,
later commit would have left `v0.16.0` in a briefly-broken state for no
reason.

## 8. Architectural Principles

No production code of this Work Package's own authorship was
introduced; the test-infrastructure change it carries is `WP 15.2A`'s,
brought in unmodified by the merge. Two register/status edits and one
folder move do not meet Governance §5's ADR criteria — neither
establishes a code convention nor resolves a genuine technical
alternative.

## 9. Benefits

`TD-120` closes on `main`'s own eventual line rather than sitting
finished-but-stranded on a feature branch. The Companion branch's status
moves from an ambiguous, disclosed-but-unresolved `TD-82` to an
explicit, dated deferral, still fully reversible per `D-022`'s own
Reversal clause. `Tempest.Desktop.Tests` verified 412/412 in Release,
locally, on the merged tree.

## 10. Trade-offs — decided while still Proposed

**Both decisions this Work Package applies are, as of this writing,
still `Proposed — awaiting Product Owner approval`.** `WP 16.0A`'s own
report states explicitly that `WP 16.0B` "does not begin until the six
records are approved." This Work Package began anyway, on later,
explicit Product Owner direction, and it says so in every place that
matters: the report's own header line ("both Proposed... ratification
pending PR #6"), the commit message, and the `TD-82` status text itself.
It also **deleted a folder** — `docs/releases/v0.15.1/` — on the
strength of a decision that has no register row yet. If `D-026` were
ever rejected rather than approved, undoing this Work Package means
recreating a deleted folder from git history, not merely reverting a
line of prose. This Work Package's own honesty about the decisions'
status is exemplary; the underlying exposure — irreversible-by-default
action (a `git rm` of a folder) taken on a Proposed decision — is real
regardless, and is the same exposure `WP 16.0A`'s retrospective names at
the programme level.

This report was itself written after the fact, at `WP 16.2B`'s own
closure — a disclosed departure from the normal sequence (report,
then retrospective) worth naming rather than smoothing over, since it
means this Work Package's evidentiary trail briefly existed only in two
commit messages before its own report caught up.

## 11. Common Mistakes

**Assuming "the decision is Proposed" and "the action is reversible" are
the same statement.** They are not. This Work Package discloses the
first honestly throughout; it does not claim the second, and a future
reader should not assume it either — reversing `D-026` after this Work
Package requires restoring a deleted folder from history, not flipping a
flag.

## 12. Future Evolution

Two disclosures were handed forward rather than fixed here, per this
Work Package's own declared scope: the Core test suite's own leftover
temp-directory pattern (65 `tempest-project-*` roots per full run, four
fixture factories with no disposal) and `SampleSeparationTests`'
environment-dependent failure in any checkout carrying extra git
worktrees — both closed by `WP 16.4A`, later the same release. `D-022`
and `D-026` are ratified — or not — only when `D-021`–`D-026` as a set
are; see `WP 16.0A`'s own retrospective for the state of that
ratification as of this writing.

## 13. Key Takeaways

- Repointing every literal path a health check reads, in the same commit
  that moves the file, is what keeps a governance script's before/after
  state honest — a separate, later repoint invites a real, if brief, red
  check for no benefit.
- A decision recorded as Proposed can be *acted on* under explicit,
  later authority without ever becoming *approved* — but an irreversible
  action (deleting a folder) taken on that basis carries a different,
  larger cost if the decision is ever reversed than a reversible one
  would, and that asymmetry is worth naming even when the disclosure
  itself is impeccable.
- A report written after its own Work Package's commits, at a later
  Work Package's closure, is a genuine, disclosed departure from the
  normal sequence — naming it plainly is more useful to a future reader
  than letting the report's own date quietly imply it was contemporaneous.
