# WP 11.3A — Presentation Strategy Review & Platform Consolidation

## 1. Introduction

`WP 11.3A` (commit `4c46ff8`) finally commissions the Desktop & Console
Presentation Strategy Decision `WP11.0A` finding `A-2` first named —
after being predicted for two roadmap slots (`WP 11.1B`, then
`WP 11.2A`) without landing under either. Review only — no code, ADR, or
architecture modified, no repository restructuring performed. Its full
account is `docs/releases/v0.11.0/WP11.3A Presentation Strategy
Review.md`. This retrospective is written retrospectively under
`WP 16.2B`, grounded in that report and commit `4c46ff8`.

## 2. Purpose

Answer, with direct source evidence rather than assumption, whether
`Tempest.App` and `Tempest.Desktop` are genuinely two competing
presentation stacks, and if not, what the real shape of the duplication
is and what to do about it.

## 3. Background

`WP 11.0A` had described "two independently maintained, full
presentation stacks" as though `Tempest.App` and `Tempest.Desktop` were
symmetric competitors. No Work Package had yet investigated whether that
framing was accurate.

## 4. The Problem

`Tempest.App`'s own `Program.cs` still boots a full, hand-rolled console
renderer end to end; `Tempest.Desktop`'s own `Program.cs` boots the
Avalonia GUI. Nothing in the repository stated whether the console shell
remained a real, supported product surface or was effectively a
legacy/test harness that happened to still run — a question that
doubles the presentation-layer maintenance surface for every future
Engineering Discipline feature until it is answered.

## 5. The Design

Direct source review finds a shape more specific than `WP11.0A`'s own
framing: `Tempest.App` bundles two structurally distinct things — a
shared Workspace domain/business layer `Tempest.Desktop` genuinely
depends on and could not function without, and a console-*presentation*
layer `Tempest.Desktop` has zero code-level dependency on (every match
for `WorkspaceShell`/`TempestShell` inside `Tempest.Desktop` is a
doc-comment design-precedent citation, never a `using`, field, or
constructor call — verified directly by `grep`).

Within that console layer, two classes carry two genuinely different
real statuses: `TempestShell` has been completely unreachable from any
running entry point for three full releases (`ADR-0068`, `WP 8.1A`,
`v0.8.0`) — provably dead code, zero risk to retire. `WorkspaceShell` is
`Tempest.App`'s real, live entry point today, with genuine, demonstrated
ongoing value as a fast, no-Avalonia-startup-cost harness for smoke-
testing the Runtime Host and all six Engineering Disciplines.

**Six findings** (`F1`–`F6`) support this: `F1` `TempestShell` is
provably dead, safe to retire at zero risk. `F2` `README.md` — the
repository's own highest-visibility document — describes an
architecture roughly six releases stale and never mentions
`Tempest.Desktop` at all. `F3` the one code-comment claim asserting a
formal "Desktop is primary" decision (attributed to `WP 10.0B`) is
**Unverified** — a direct search of all six `WP 10.0B` deliverable
documents and the rest of the repository for the phrases it uses returns
zero matches anywhere else. `F4` the release process (`WP 11.1A`/
`WP 11.1B`, this same release) already treats the two presentation
layers as symmetric, co-equal shipped products, contradicting `F3`'s own
positioning. `F5` no dedicated engineering investment has gone into the
console rendering layer since `WP 10.0B`; sixteen dedicated Work
Packages (`WP 10.0A`–`WP 10.9A`) built `Tempest.Desktop`-only
capability in the same period — the Product Owner's own actual Work
Package allocation already answers "which is primary," independent of
`F3`'s unverifiable comment. `F6` `WorkspaceShell` has real, demonstrated
harness value, already relied on for a real audit elsewhere in the
Academy — retiring it too, on no evidence of harm, would be the opposite
of this project's own "act only on demonstrated need" discipline.

**Recommendation (Option 3, Differentiated Disposition, scored 21/25
against three alternatives)**: retire `TempestShell` at zero risk;
formally ratify `Tempest.App`/`WorkspaceShell` as TempestOS's Internal
Engineering Harness, not a shipped product, via a new ADR; correct
`README.md`/`Contributor Learning Path.md`; correct release-artifact
packaging. A five-stage, minimum-disruption implementation roadmap is
sequenced but not executed here — that is `WP 11.3B`'s job.

## 6. Alternatives Considered

Retiring both console shells entirely (Option 1) was rejected — it would
remove a working, demonstrably-used asset (`F6`) on no evidence of harm.
Doing nothing (Option 2) was rejected — it leaves `F2`/`F3`/`F4`'s real
inconsistencies uncorrected indefinitely. Promoting the console to a
fully co-equal, actively developed second product (Option 4) was
rejected — it contradicts `F5`'s own actual allocation evidence and
doubles ongoing feature-delivery cost with no demonstrated business
need.

## 7. Why This Solution Was Chosen

The differentiated option is the only one that matches every finding
directly rather than trading one against another: dead code is removed
(risk-free), live-but-secondary code is correctly labelled (not
destroyed), and documentation is corrected to match what the Product
Owner's own Work Package allocation already, in practice, decided.

## 8. Architectural Principles

No production code, ADR, or architecture document was modified; no
repository restructuring was performed — review only, per this Work
Package's own explicit constraint. Neither `ADR-0068` nor `ADR-0092` is
edited even though `ADR-0092`'s own text is found imprecise on direct
comparison — Engineering Governance §5 does not permit rewriting an
ADR's own body, so a fresh, accurate ADR is recommended instead of
amending either (realised by `WP 11.3B` as `ADR-0101`).

## 9. Benefits

A commissioned decision finally exists where none did through two prior
predicted slots. The recommendation requires no change to any Workspace
contract, Platform Service, or Engineering Domain type — every
dependency `F1`/`F6` traced terminates entirely within the presentation
layer, meaning the fix is genuinely low-risk.

## 10. Trade-offs

`F3`'s own claim is reported Unverified, not false — a real,
plausible-but-untranscribed Product Owner instruction is not ruled out,
only shown to be currently unsubstantiated anywhere else in the
repository. This is itself named as a governance gap (treating an
unverified source-code comment as a settled product decision) rather
than resolved by assumption in either direction.

## 11. Common Mistakes

**Accepting a prior review's own framing without re-verifying it against
source.** `WP11.0A`'s "two independently maintained, full presentation
stacks" reads as a symmetric competition; direct review found the real
duplication confined entirely to the console-rendering slice, not the
shared domain layer — a materially different, and materially cheaper to
resolve, situation.

## 12. Future Evolution

`WP 11.3B` executes Stages 1–4 of this review's own roadmap directly —
retiring `TempestShell`, authoring `ADR-0101`, correcting `README.md`
and `Contributor Learning Path.md`, and correcting release-artifact
packaging. Stage 5 (further trimming `WorkspaceShell`'s own coverage)
remains explicitly deferred, not executed by any later Work Package this
retrospective's own sources disclose.

## 13. Key Takeaways

- Re-verify a prior review's own framing against direct source before
  building on it — the real shape of a problem is sometimes narrower
  than its first description.
- A source-code comment asserting a product decision is not itself
  evidence the decision was ever formally made — check the rest of the
  repository for corroboration before treating it as settled.
- A project's own actual Work Package allocation is real evidence of its
  real priorities, independent of what any single document claims.
