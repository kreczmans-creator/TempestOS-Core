# Project Risks, Issues & Decisions — the Governance Families Get a Surface

## 1. Introduction

`45d8a99` gave Risk, Hazard, Issue and Decision — real, durable,
rehydratable domain types since `WP 8.2C` — a workflow, ownership and a
surface for the first time: nothing had previously raised one, scored one,
owned one or closed one. A pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To close the Risks area, the last project area still marked Declared with
genuine governance domain objects behind it.

## 3. Background

The brief asks for status, priority and ownership "where the existing
model supports it", and the honest answer, checked directly, was:
nowhere. `Issue` had no status, no priority and no owner; `Risk` had
Likelihood and Severity as immutable strings and nothing else; `Decision`
had an immutable Rationale. Surfacing only what existed would have
produced a Risks area where a risk cannot be closed and an issue cannot be
triaged — the exact defect class `TD-102` was raised to fix, recurring
here as a designed absence rather than a false claim.

## 4. The Problem

A disclosed judgement call rather than a defect: the domain model as it
stood could not support a working Risks area without extension, and a
minimal surface over an unextended model would itself have been another
capability claiming more than it delivered.

## 5. The Design

The three types are extended minimally, in the shape `ADR-0117`'s Tasks
work established: mutable state on the real object, captured through
`CaptureTypeState`, read back by tolerant rehydration constructors,
persisted by the same mutate-then-persist path — no parallel models, no
`ProjectId`, no new persistence mechanism. Each family gets its own status
vocabulary rather than borrowing the document lifecycle, mapped onto it
through `IFamilySpecificState`. The distinctions are the point: an
Accepted risk is still live — the team decided to carry it, not that it
went away, and collapsing that into Closed would quietly drop exactly the
risks a reviewer most needs to see. A Resolved issue still counts as open,
because a fix nobody has confirmed is still somebody's problem. A
Superseded decision is the one genuinely terminal state across all
three — bringing one back would rewrite what the project decided and
when. Priority is shared, not duplicated: `TaskPriority` became
`WorkPriority` (17 usages across 5 files), since `ADR-0105` says one
canonical declaring class per value and a second four-value enum would let
"High" drift between task and issue for no reason a user could see.
Membership is `ProjectMembership` transitively, for the fourth time.
Assumption is deliberately not surfaced — it has no workflow, only a
standing-or-invalidated state, and inventing one would be designing a
capability nobody asked for; `FCR-0056` records that decision rather than
leaving it looking forgotten.

## 6. Alternatives Considered

Surfacing only the fields the existing model already had — rejected
explicitly: it would have produced a Risks area that looked implemented
and could not actually close a risk or triage an issue, the same
"claims a capability it does not have" defect `TD-102` exists to name.

## 7. Why This Solution Was Chosen

Because the minimal extension needed was small and reused an existing
contract (`IFamilySpecificState`) rather than inventing a new mechanism,
and because sharing `WorkPriority` rather than duplicating it keeps
"High" meaning one thing across every family that uses it.

## 8. Architectural Principles

Distinct status vocabularies per family, mapped onto one canonical
lifecycle, preserve real distinctions (Accepted-but-live, Resolved-but-
open, Superseded-but-terminal) that a single shared vocabulary would
flatten and quietly misreport.

## 9. Benefits

Eight mutations run, eight killed. Core 2828/2828; the whole solution
compiles with 0 warnings and 0 errors. Five new Desktop acceptance
journeys pass through the real `MainWindow` across a genuine relaunch.
Two of the new tests failed first time and both were worth having: one
found a real defect (an issue's originating risk was read by filtering
outgoing relationships for a link pointing at itself, which can never
match, since `GetRelationshipsAsync` returns outgoing edges only); the
other was the test's own wrong premise.

## 10. Trade-offs

Disclosed: this container's disk allowance could not hold the Desktop
test build by the end of the run, so the full Desktop suite and both
Debug-configuration suites were verified by CI rather than locally.
`TD-81` stays Partially resolved, now listing what is genuinely left:
Commercial, Resources, Knowledge, Administration, Gantt/Timeline and
managed Milestone surfaces.

## 11. Common Mistakes

Filtering a type's own outgoing relationships for a link pointing back at
itself, when the read method only ever returns outgoing edges — a
structurally impossible match that silently reported "no originating
risk" for every issue until a new test caught it.

## 12. Future Evolution

Project Timeline, later this release, reuses the same
`IFamilySpecificState`-mapped-onto-canonical-lifecycle shape this row and
`ADR-0117`'s Tasks work both establish, rather than inventing its own
pattern a third time.

## 13. Key Takeaways

- A minimal capability that cannot actually complete its own workflow
  (close a risk, triage an issue) is the same defect class as a
  descriptor claiming an unbuilt surface — extend the model rather than
  ship a hollow one.
- Distinct per-family status vocabularies, mapped onto one canonical
  lifecycle, preserve distinctions a shared vocabulary would flatten.
- The most useful test result came from a mutation that survived because
  a later persisting call re-captured and masked an earlier omission —
  keep restart tests and persistence tests separate for exactly this
  reason.
