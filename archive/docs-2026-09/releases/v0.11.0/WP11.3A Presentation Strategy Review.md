## Executive Summary

The evidence does not support the question as originally framed. `WP
11.0A` described "two independently maintained, full presentation
stacks" as if `Tempest.App` and `Tempest.Desktop` were symmetric
competitors. Direct source review finds a different, more specific
shape: **`Tempest.App` contains two structurally distinct things bundled
in one project** — a shared Workspace domain/business layer that
`Tempest.Desktop` genuinely depends on and could not function without,
and a console *presentation* layer that `Tempest.Desktop` has **zero**
code-level dependency on. Within that console presentation layer, one
class (`TempestShell`) has been **completely unreachable from a running
application for three full releases** (`ADR-0068`, `WP 8.1A`, `v0.8.0`)
and another (`WorkspaceShell`) is `Tempest.App`'s real, live entry point
today, doing real, demonstrated work as a lightweight harness.

The strategic decision this Work Package was commissioned to make has,
in substance, **already been made** — by `WP 10.0B`, which made
`Tempest.Desktop` the "primary launch target" and the console "retained
for diagnostics/testing," per that code's own doc comment. What has
never happened is: verifying that claim against the documentation record
(it does not appear in any of `WP 10.0B`'s own six deliverable
documents — see Finding F3), formally ratifying it anywhere a future
contributor would find it, or reconciling the rest of the repository
(most visibly `README.md`) to match it.

**Recommendation:** retire `TempestShell` (zero risk — see Finding F1);
formally ratify `Tempest.App`/`WorkspaceShell` as TempestOS's Internal
Engineering Harness, not a shipped product, via a real, citable decision
this time; correct the documentation and release-packaging
inconsistencies that decision's own absence has allowed to accumulate.
No architectural disruption is required — see Implementation Roadmap.

## Current-State Architecture

### The Dependency Graph (Verified)

```
Tempest.Core (platform)
      ▲
      │ references
Tempest.App
      │  ├─ Composition/EngineeringWorkspaceComposer.cs   ─┐
      │  ├─ Workspace/  (WorkspaceManager, 6 disciplines'  │  SHARED — Tempest.Desktop
      │  │   Commands/NodeProviders/FactoryRegistries/      │  depends on all of this
      │  │   PropertyFacetProviders, IWorkspaceManager,     │
      │  │   IWorkspace, etc.)                              ┘
      │  ├─ Workspace/WorkspaceShell.cs   (console renderer)  ─┐  CONSOLE-ONLY —
      │  └─ Shell/TempestShell.cs, IPage.cs,                   │  zero Tempest.Desktop
      │      PlaceholderPage.cs            (older console      │  reference, confirmed
      │      shell, pre-Workspace)                              ┘  by direct grep
      ▲
      │ references
Tempest.Desktop  (Avalonia GUI — MainWindow, Views/, Editors/,
                  Docking/, DigitalThread/, Theming/, ...)
```

**Verified directly, not inferred:** `grep -rl "WorkspaceShell\b" src/Tempest.Desktop`
and `grep -rl "TempestShell\b" src/Tempest.Desktop` both return matches —
but every single one is inside an XML doc `<remarks>` comment citing the
console shell as a design-precedent reference (*"mirrors `TempestShell`'s
own `StartAsync`/... shape"*), never an actual `using`, field, or
constructor call. `Tempest.Desktop` builds and runs with zero executable
dependency on either console-presentation class. The dependency graph
therefore has a clean seam exactly where a decision needs one: the
*shared* Workspace layer, and the *console-presentation* layer, already
live in different files with no code-level entanglement between the
latter and `Tempest.Desktop`.

`ADR-0092` (`WP 10.0A`, `v0.10.0`), the one ADR that formally addresses
the console/desktop question, states in its own Decision §4: *"`TempestShell`
(console) is not removed or deprecated by this decision... `TempestShell`
remains available and untouched, exactly as it has been additive rather
than replaced since `v0.8.0`."* This is imprecise on direct comparison
against `ADR-0068`: `TempestShell` was not "additive... since `v0.8.0`"
— `ADR-0068`, dated the same release, is the very decision that made it
*unreachable* from `v0.8.0` onward. `ADR-0092` appears to use
"`TempestShell`" as informal shorthand for "the console surface
generally" rather than the specific, already-orphaned class it names —
an imprecision in the one ADR meant to settle this question, not a
contradiction requiring an ADR correction (Governance §5 does not permit
rewriting an ADR's own body; see Implementation Roadmap for how to
handle this without amending `ADR-0092` itself).

### `Tempest.Desktop`

51 source files, 10,200 lines. The Avalonia 11.2.3 (`ADR-0094`) desktop
GUI: `MainWindow`, per-discipline `ObjectEditorView`, `ProjectExplorerView`,
`RibbonView`, docking (`DockingGrid`/`PanelHostControl`), the Digital
Thread graph, theming, Command Palette, Undo/Redo, Macros — the full
`v0.10.0` feature set, built across 16 Work Packages (`WP 10.0A`–
`WP 10.9A`). Its own dedicated test suite, `Tempest.Desktop.Tests`, uses
Avalonia's real headless rendering backend against real controls: 28
files, 6,105 lines, 202 real tests (confirmed by an actual `dotnet test`
run during `WP 11.1A`'s own verification).

### Startup Flow (Both, Traced Directly)

**`Tempest.App`** (`Program.cs`): `EngineeringWorkspaceComposer.Build()`
→ `WorkspaceShell.StartAsync()` (starts the Runtime Host) →
`EngineeringWorkspaceComposer.RegisterEngineeringDisciplines()` (all six
disciplines, host must already be running) → `WorkspaceShell.RunInputLoopAsync()`
(console read/render loop) → `WorkspaceShell.StopAsync()`.

**`Tempest.Desktop`** (`Program.cs` → `App.cs` → `WorkspaceHost.cs` →
`MainWindow`): identical composer call
(`EngineeringWorkspaceComposer.Build()`/`RegisterEngineeringDisciplines()`),
confirmed by direct read of `WorkspaceHost.cs` and its own doc comments
citing this as deliberate ("so both presentation layers register the
identical sequence... rather than risking two, independently maintained
copies drifting apart" — `EngineeringWorkspaceComposer.cs`'s own
`<summary>`), then constructs `MainWindow` and runs Avalonia's own
classic desktop lifetime loop instead of a console read loop.

**This is the one part of the architecture already correctly
consolidated.** `EngineeringWorkspaceComposer` exists specifically
because `WP 10.0B` extracted it from `Tempest.App`'s own `Program.cs` to
prevent exactly the domain-wiring duplication a naive two-presentation-
layer design would produce. Confirmed: no duplicated Host-construction,
discipline-registration, or Domain-service-resolution code exists
anywhere in this repository. The duplication this Work Package was
commissioned to assess exists **only** at the rendering layer, not the
domain layer — an important, evidence-based correction to `WP11.0A`'s
own framing.

## Findings

**F1 — `TempestShell` is provably dead code, safe to retire at zero
risk.** Unreachable from any running entry point since `ADR-0068`
(`v0.8.0`); zero executable references anywhere; its own 463-line test
suite exists solely to test that a manually-constructed instance of an
otherwise-unreachable class still behaves correctly, not to protect any
real, running path. Retiring it changes no observable behaviour of
either shipped presentation layer.

**F2 — `README.md`, the repository's own highest-visibility document,
describes an architecture roughly six releases stale, and never mentions
`Tempest.Desktop` at all.** Direct quote: *"`Tempest.App/` — A console
front end — still the legacy bootstrap/project-management app; does not
yet run through `TempestHost`"* — this describes the pre-`v0.5.0`
bootstrap-era `Tempest.App` (`BootstrapService`/`ProjectService`), superseded
first by `TempestShell` (`WP 5.0D`) and then by `WorkspaceShell`
(`WP 8.1A`). The `src/` tree diagram omits `Tempest.Desktop/` and
`Templates/`; the `tests/` tree diagram omits `Tempest.Desktop.Tests/`
entirely; the **only** run instruction given anywhere in the file is
`dotnet run --project src/Tempest.App/Tempest.App.csproj` — the console.
A new contributor reading this file today, exactly as directed by its
own opening sentence, would not learn that a desktop application exists
at all, let alone that it is the primary product. `docs/academy/
Contributor Learning Path.md` — the document `README.md` itself sends
new contributors to next — shows the identical pattern: it describes
`TempestShell` as *"`Tempest.App`'s own composition root"* and does not
mention `Tempest.Desktop`.

**F3 — The one claim asserting a formal "Desktop is primary" decision is
unverifiable against this project's own documentation record.**
`Tempest.Desktop/Program.cs`'s own doc comment states: *"`Tempest.Desktop`
is now the primary launch target for TempestOS (`WP 10.0B`'s own
explicit "replace the console application as the primary launch target"
instruction); the console `Tempest.App`/`TempestShell` remains, retained
for diagnostics/testing per that same instruction's own explicit
exception."* A direct search of all six `WP 10.0B` deliverable documents
(`Implementation Report`, `Architecture Review`, `Engineering Review`,
`Security Review`, `Systems Engineering Review`, `Technical Debt
Review`) and the entire remaining `docs/` tree and `PROJECT_STATUS.md`
for the phrases *"primary launch target"* and *"replace the console
application"* returns **zero matches** anywhere outside this one code
comment. This does not mean the claim is false — a Product Owner
instruction given informally and acted on, but never transcribed into a
retrospective, is plausible in this project's own history — but it means
the claim is currently **Unverified**, not **Verified**, per this
project's own Governance Philosophy discipline, and it is the *only*
place in the repository asserting this positioning as settled. Treating
an unverified source-code comment as the platform's actual, standing
product decision is itself a governance gap.

**F4 — The release process (this session's own prior work,
`WP 11.1A`/`WP 11.1B`) treats the two presentation layers as symmetric,
co-equal shipped products** — `.github/workflows/ci.yml`'s Release
build-artifact step and `.github/workflows/release.yml`'s GitHub Release
packaging both stage `Tempest.App` and `Tempest.Desktop` identically,
side by side, with no distinguishing label. This directly contradicts
the "Desktop primary, console diagnostic" positioning `F3` names — an
inconsistency this Work Package's own predecessors introduced
unknowingly, before this review existed to catch it.

**F5 — No evidence of ongoing dedicated investment in the console
presentation layer since it stopped being the primary surface.** Every
Work Package that has touched `src/Tempest.App/Workspace/` since
`WP 10.0B` has done so to extend the *shared* domain layer (a new
discipline's commands, node providers, property facets — code
`Tempest.Desktop` equally consumes), never to advance `WorkspaceShell`'s
own console rendering. `Tempest.Desktop`, by contrast, received sixteen
dedicated Work Packages (`WP 10.0A`–`WP 10.9A`) building out console-
unreachable capability (Docking, the Digital Thread graph, Ribbon,
Object Editors, Macros, Undo/Redo). This is the clearest evidence this
review found that the two surfaces are not competing for engineering
priority in practice, whatever the documentation says — the Product
Owner's own actual allocation of Work Packages already answers the
"which one is primary" question, independent of `F3`'s unverifiable
comment.

**F6 — `WorkspaceShell` has genuine, demonstrated ongoing value as a
harness, not merely inertia.** It is the fastest way to smoke-test that
the Runtime Host, the Workspace domain layer, and all six Engineering
Disciplines compose and start correctly — no Avalonia startup cost, no
windowing system, directly scriptable, directly redirectable
(`TextWriter`/`TextReader`, already exploited by its own 46-test suite).
This is not a speculative benefit: `docs/academy/02 Runtime Architecture/
31-commercial-user-experience-and-application-completion.md`'s own text
(quoted above, `dotnet run` process-launch verification) shows this
exact pattern already being relied on for a real audit. Retiring
`WorkspaceShell` outright, not only `TempestShell`, would remove a
working, low-cost, demonstrably-used asset without any evidence of harm
from keeping it — the same "do not act without demonstrated need" test
this project applies everywhere else, applied here in the direction of
*not* removing something that works.

|---|---|
| **1. Retire both console shells entirely** | Delete `Shell/` and `Workspace/WorkspaceShell.cs`; `Tempest.App` becomes a class library exposing only the shared Workspace domain layer, no executable presentation of its own. |

| **3. Differentiated disposition** *(recommended)* | Retire `TempestShell` only (F1, zero risk). ## Recommendation

**Adopt Option 3 — Differentiated Disposition.**

1. **Retire `TempestShell`, `IPage`, `PlaceholderPage`, and
   `TempestShellTests.cs`.** Proven dead (`F1`); zero risk; a real,
   immediate reduction in both source and CI cost with no product
   impact whatsoever.
2. **Formally classify `Tempest.App`/`WorkspaceShell` as TempestOS's
   Internal Engineering Harness** — explicitly **not** a shipped
   product, mirroring the informal positioning `F3` already gestures at
   but cannot currently substantiate. This is a genuine, disclosed
   architectural/product-positioning decision meeting Engineering
   Governance §5's ADR criteria (it resolves real, previously-
   ambiguous reasoning about a standing platform surface) — recommended
   as a new ADR, not a further code comment, so the next contributor
   who asks this same question finds an answer instead of researching
   it from source the way this Work Package had to.
3. **`Tempest.Desktop` remains the sole shipped, primary product
   surface** — already true in practice (`F5`); this recommendation
   makes it true on paper as well.
4. **Correct `README.md` and `Contributor Learning Path.md`** to
   describe the actual, current architecture — both presentation
   layers, correctly labelled, with `Tempest.Desktop` as the documented
   way to run the product and `Tempest.App`/`WorkspaceShell` documented
   as the internal harness it now formally is.
5. **Correct the release-artifact packaging** (`ci.yml`, `release.yml`)
   to stop presenting `Tempest.App` as a co-equal shipped deliverable
   alongside `Tempest.Desktop`.

This recommendation requires **no change to any Workspace contract,
Platform Service, or Engineering Domain type** — every dependency `F1`
and `F6` traced terminates entirely within the presentation layer.

  the console/desktop product positioning — `ADR-0068`/`ADR-0092` are
  **not** edited (Governance §5), only cross-referenced.

  `TempestShell` itself (Stage 2). Net reduction in both source and CI
  time, testing code with zero live path today.

  unchanged. It continues validating a real, live surface; only the

  obligation.

- No change to `Tempest.Core.Tests`'s own Workspace-domain-layer tests
