# WP 11.0B — v1.0 Architecture Roadmap & Release Planning

**Type.** Planning only. No production code, ADR, or architecture was
modified to produce this document.
**Branch.** `feature/v0.11.0-v1-architecture`, cut from `main` at the
`v0.10.0` tag.
**Input.** `docs/releases/v0.11.0/WP11.0A Platform Architecture Review.md`
(ten findings: `A-1`–`A-9`, `R-1`), cross-checked against the pre-existing
Technical Debt Register, Future Capability Register, and `PROJECT_STATUS.md`'s
own "Next Planned Work Package" candidate list.
**Purpose.** Turn `WP 11.0A`'s findings into a scoped, sequenced,
estimated engineering roadmap from `v0.11.0` to the first public `v1.0.0`,
in this project's own Work Package / WBS format.

## 1. Recommended Definition of "TempestOS v1.0"

**v1.0.0 is a commercially credible, single-user (or small-trusted-team),
locally-trusted desktop engineering platform**, covering the six
Engineering Disciplines already shipped through `v0.10.0` (Mechanical,
Requirements, Calculations, Verification, Documents, Manufacturing),
running on:

- A CI-verified build (every merge to `main` gated by an automated build
  and full test run — currently absent, `R-1`).
- A decomposed, single-responsibility Desktop composition root — not the
  current 1,556-line `MainWindow`/1,398-line `EngineeringCockpit`
  concentration of risk (`A-1`).
- One deliberately-chosen, documented presentation surface, or an
  explicit, costed decision to maintain two (`A-2`).
- A compile-time safety net around the classification/relationship
  vocabulary that now underpins all six disciplines (`A-6`).
- An internally-consistent governance suite, with the recurring
  register-staleness pattern (`A-5`/`FCR-0005`) closed by tooling rather
  than caught by the seventh manual audit in a row.

**Explicitly out of `v1.0` scope, by recommendation:** third-party plugin
support (`FCR-0002`) and REST API exposure beyond a trusted local
network (`FCR-0003`/`FCR-0004`). Both remain correctly gated on a real
trigger that has not fired — building either now would be building ahead
of demonstrated need, the same discipline `WP7.2A Recommended
Programme.md` already applied to this exact material (see §4). If the
Product Owner instead commits `v1.0` to either capability, §5 names the
conditional release (`v0.13.0`) that closes the corresponding trust gap
first.

This definition does not add new Engineering Discipline breadth beyond
what `v0.10.0` already shipped — that is a product-scope decision outside
this review's evidence base, not an architectural one, and is
deliberately left to the Product Owner rather than assumed here.

## 4. Review of the Existing Roadmap — Reprioritisation & Merging

**`Product Roadmap.md` is stale and should be refreshed, not
reprioritised.** Its own "Last Reviewed" is `WP 7.2A` (2026-07-30) — it
still describes Phase 5 (Engineering Modules) as "sequencing
recommended, not yet scoped," despite six disciplines having since
shipped through `v0.9.0`/`v0.10.0`. This roadmap does not rewrite that
document (outside this Work Package's own deliverables) but recommends
`WP 11.1B` fold in the one-paragraph correction as part of its
governance-currency pass, and recommends the phase list gain a new
entry: **Phase 5.5 — v1.0 Readiness (Platform Hardening & Release
Engineering)**, sitting between Phase 5 (Engineering Modules, now
substantially delivered) and Phase 6 (Professional Features) — exactly
where the Work Packages in §3 belong.

**This roadmap is the direct continuation of "Programme F," not a new
initiative — merge, don't duplicate.** `WP7.2A Recommended Programme.md`
(`v0.7.0`) identified and deliberately deferred a "Platform Hardening"
programme covering `FCR-0001` (plugin/registration trust retrofit),
`FCR-0003`/`FCR-0004` (REST auth/TLS), and `FCR-0005` (governance
health-check tooling) — deferred correctly, on the grounds that none of
their triggers had fired and building them ahead of need would violate
Security Principle 7. That reasoning **still holds** for `FCR-0001`/
`FCR-0003`/`FCR-0004` today (§2, above) and this roadmap does not
override it. It **no longer holds** for `FCR-0005`:

- `WP7.2A`'s own text already named this pattern as recurring (raised to
  **High** priority by `WP 7.1F`, reconfirmed by `WP 7.4.0`).
- `PROJECT_STATUS.md`'s "Next Planned Work Package" section (written at
  `v0.10.0`'s close, before `WP11.0A` began) already counted **six**
  independent recurrences and named `FCR-0005` as a live `WP 11.0`
  candidate.
- `WP11.0A` independently found a **seventh** — the Governance Index's
  own stale "39 ADRs" claim (actual count: 99) — without having read
  either of the paragraphs above first.

Seven independent, unrelated discoveries of the identical failure mode
is no longer "no real, demonstrated need." **This roadmap reprioritises
`FCR-0005` from perpetually-deferred to `WP 11.1B`**, folded together
with the mechanical fix `A-5` already requires, rather than opening a
separate Work Package for each. No other existing Future Capability or
Technical Debt item is reprioritised ahead of its own registered
trigger — `FCR-0001`/`FCR-0002`/`FCR-0003`/`FCR-0004` keep the exact
gating `WP7.2A` and the registers themselves already assign them.

**No merging of already-scheduled Work Packages is recommended.** The
`v0.11.0`–`v1.0.0` Work Packages in §3 are additive to the existing
numbering scheme; none renumbers or replaces a prior release's Work
Package.

**Other existing "Next Planned Work Package" candidates are
acknowledged, not absorbed.** `TD-38`, `TD-41`, the Command
Palette/Macro `CreateDefault` gap, `FCR-0073` (Copy/Move
destination-picker), and `FCR-0056` (Governance & Risk Workspace) are
all real, already-tracked candidates — none traces to a `WP11.0A`
finding, so none is scoped into this roadmap. They remain available for
the Product Owner to interleave with §3's Work Packages at their own
discretion, per this project's standing "each requires its own
Architecture, Planning, and Contract Review phase before a Work Package
number is assigned" discipline (`Product Roadmap.md`, Non-Commitments).

## 6. Recommended Release Sequence

```
v0.10.0 (shipped)
   │
   ▼
v0.11.0 — Release Engineering & Architecture Governance
   WP 11.0A (review, complete) → WP 11.0B (this roadmap)
   → WP 11.1A (CI/CD) ∥ WP 11.1B (governance tooling) ∥ WP 11.2A (presentation decision)
   → WP 11.9.0 (release prep)
   │
   ▼
v0.12.0 — Desktop Composition & Domain Vocabulary Hardening
   WP 12.0A → WP 12.0B (composer decomposition)
   WP 12.1A → WP 12.1B (vocabulary safety net)          [parallel with above]
   WP 12.2A (execute WP 11.2A's decision)
   → WP 12.9.0 (release prep)
   │
   ▼
[CONDITIONAL] v0.13.0 — Trust & Deployment Hardening
   Only if WP 11.2A commits v1.0 to third-party plugins and/or
   non-local REST deployment.
   WP 13.0A → WP 13.0B (plugin trust)
   WP 13.1A → WP 13.1B (REST auth/TLS)                  [parallel with above]
   → WP 13.9.0 (release prep)
   │
   ▼
v1.0.0 — General Availability
   WP RC.0A (full release-readiness re-certification)
   → Product Approval → tag v1.0.0
```

**Recommended path (per §1's definition): `v0.11.0` → `v0.12.0` →
`v1.0.0`**, three releases, skipping `v0.13.0` entirely. **Fallback path,
if `v1.0` scope expands:** `v0.11.0` → `v0.12.0` → `v0.13.0` → `v1.0.0`,
four releases. Which path applies is decided once, by `WP 11.2A`/the
Product Owner, not re-litigated at each subsequent Work Package.

## 7. What This Roadmap Deliberately Does Not Do

- Does not modify any ADR, any production source file, or any existing
  architecture document.
- Does not re-scope the full Technical Debt Register or Future
  Capability Register — only the items a `WP11.0A` finding or a direct,
  evidenced reprioritisation case (`FCR-0005`, §4) touches.
- Does not commit to calendar dates — this project's own release
  cadence has no recorded velocity to extrapolate from, and inventing
  one would violate this project's own "prefer evidence over
  speculation" discipline.
- Does not assume the Product Owner's `v1.0` scope decision (§1, §5) —
  it names the decision, the Work Package that makes it (`WP 11.2A`),
  and both resulting paths, without pre-empting either.
