# WP 11.0A — Platform Architecture & Code Quality Review

**Role.** TempestOS Principal Software Architect (independent review).
**Scope.** The complete codebase as of the `v0.10.0` tag / `main` HEAD
(`57601eb`) — `Tempest.Core`, `Tempest.App`, `Tempest.Desktop`,
`Tempest.Samples`, `Tempest.Templates`, both test projects, and the
governance/architecture documentation suite that describes them.
**Method.** Independent, evidence-based review: direct reading of source
(600 `.cs` files, ~66,000 lines across `src/`; ~243 test files, ~42,600
lines across `tests/`), direct verification of dependency direction via
`.csproj` references and `using` graphs, direct file/line counts, and
cross-checking the platform's own governance claims (Technical Debt
Register, Risk Register, Repository Maturity Report, Governance Index)
against what the repository actually contains, rather than accepting
those claims at face value. Not a line-by-line audit of every file — a
targeted review of every major subsystem plus deep inspection of the
files most likely to carry risk (largest files, composition roots,
concurrency-sensitive code, plugin/security boundaries).
**Constraint.** No code was modified. This document is the sole
deliverable of `WP 11.0A`.

---

## Executive Summary

TempestOS is an unusually disciplined codebase for its size. Four release
cycles of platform work (`v0.7.0`–`v0.10.0`) added a full Engineering
Domain model, six real engineering disciplines, and — in `v0.10.0` — a
complete Avalonia desktop application, without the core platform
(`Tempest.Core.Runtime`, `DependencyInjection`, `Events`, `Commands`,
`Modules`) needing to change shape. That is real evidence the original
layering decisions (`ADR-0023`'s four-layer platform model, `ADR-0033`'s
Shell-above-Host boundary) were correctly chosen, not merely convenient
for their first use — this review independently confirmed the dependency
direction claim empirically (zero references from `Tempest.Core` into
`Tempest.App` or `Tempest.Desktop`; zero from `Tempest.App` into
`Tempest.Desktop`) rather than accepting it on the documentation's word.

The engineering discipline evident in the platform core — a small,
comprehensible custom DI container, correct concurrency handling in the
Event Bus, a thin and consistent Command Dispatcher, near-total absence of
service-locator leakage into business logic, a test suite (1,934 test
methods) that genuinely avoids mocking frameworks in favour of real
collaborators — is production-grade. ADR compliance, spot-checked against
several of the highest-risk decisions (event/command failure isolation,
DI-public vs. Host-owned service boundaries, dependency direction), holds
in the code, not only in the documents describing it.

Three things stand between this platform and a confident `v1.0`, none of
them in the platform core: **(1)** there is no CI/CD automation anywhere
in the repository — every "all tests passing, 0 warnings" claim in 100+
Work Package retrospectives is a manually-run, self-reported assertion,
never independently verified by a machine; **(2)** the newest and most
user-facing layer, `Tempest.Desktop`, already shows the composition-root
God Object pattern the platform core has otherwise avoided
(`MainWindow.cs` at 1,556 lines / 35 fields, `EngineeringCockpit.cs` at
1,398 lines); **(3)** the product now ships two independently maintained,
full presentation stacks — a hand-rolled console shell and the Avalonia
desktop GUI — with no documented decision about whether the console shell
remains a real product surface or should be retired now that the GUI
exists. None of these three are architectural flaws in the platform's
foundations; all three are real, and all three compound with every future
Work Package until addressed.

A fourth, quieter risk is process rather than code: the governance and
documentation discipline this project is proud of (and largely earns) has
grown to a scale where it is starting to work against itself — table
cells and doc-comments running tens of thousands of tokens of narrative
history make the governance suite harder to actually use for its own
stated purpose, and this review found a concrete instance of exactly the
staleness that discipline is meant to prevent (the Governance Index's own
ADR count is stale by 60 entries).

**Overall verdict: architecturally sound, engineering-disciplined, not
yet release-engineered.** The code is ready to keep building on. The
release process is not yet ready to ship it with confidence at the cadence
a `v1.0` commitment implies.

## Architecture Review

### Layering, Assembly Boundaries, Dependency Direction

**Verified, not merely documented.** `Tempest.Core.csproj` carries no
`ProjectReference` to anything (only a `FrameworkReference` to
`Microsoft.AspNetCore.App`, confined to `Tempest.Core.Api` per
`ADR-0049`). `Tempest.App.csproj` references only `Tempest.Core` and
`Tempest.Samples`. `Tempest.Desktop.csproj` references only
`Tempest.App`. A direct `using`-graph search confirms this holds in
practice, not only in project files: zero files in `Tempest.Core`
reference `Tempest.App` or `Tempest.Desktop`; zero files in `Tempest.App`
reference `Tempest.Desktop`. The four-layer model (`ADR-0023`: Modules →
Platform APIs → Platform Services → Runtime Host, with Shell/Desktop
layered above all four per `ADR-0033`) is real in the code, and it has
now absorbed a GUI framework, six engineering disciplines, and a REST API
without the core needing to bend.

**Discovery/Registration/Lifecycle are correctly kept out of the DI
container.** `ADR-0017`'s decision — that `IFrameworkDiscoveryService`,
`IRuntimeModuleManager`, and `IModuleLifecycleManager` are constructed
directly by `TempestHost` and never registered into the
`ServiceCollection` — is a real, enforced boundary: no module can
constructor-inject its way back into the machinery orchestrating it. This
is exactly the kind of boundary that is easy to state and easy to
accidentally violate under feature pressure; it has not been violated
here.

**Service-locator usage is confined to genuine composition roots.** Every
`.GetService(typeof(...))` call in the codebase resolves at a legitimate
boundary — `Program.cs`/`WorkspaceManager.StartAsync`/`MainWindow`'s
constructor pulling platform services out of `ITempestHost.Services` once,
`ModuleLifecycleManager`/`HostedServiceManager` resolving the specific
instances they are responsible for orchestrating. None was found inside
ordinary business logic reaching back into a container it shouldn't know
about. This is the correct realization of `ADR-0006`'s constructor-
injection-only rule.

### Namespace Organisation

Clean and legible: `Tempest.Core`'s ~35 top-level namespaces map
one-to-one onto platform concerns (`DependencyInjection`, `Events`,
`Commands`, `Modules`, `Plugins`, `Runtime`, `Hosting`, `BackgroundServices`,
`EngineeringDomain`, per-discipline namespaces, etc.), with the
`Runtime`-vs-`Hosting` distinction (`ADR-0016`: "Runtime = platform,
Hosting = environment") a good example of a naming decision that
resolved genuine ambiguity rather than papering over it. No namespace was
found straddling two architectural layers.

### SOLID Adherence

Strong in the platform core, weaker at the presentation edge:

- **SRP** holds cleanly in `Tempest.Core` — `TempestServiceProvider`,
  `EventBus`, `CommandDispatcher`, `CommandHandlerTable` are each a few
  dozen to ~150 lines and do exactly one thing. It does **not** hold in
  `Tempest.Desktop.MainWindow` (composition root + view construction +
  undo/redo stack + command history + layout-preset management + status
  bar + flyout management, all in one 1,556-line sealed class) or in
  `Tempest.App.Workspace.EngineeringCockpit` (1,398 lines). See Finding
  A-1.
- **OCP** is honoured deliberately at the domain-model level: the
  facet-composition contracts (`ADR-0075`) and the single generic
  relationship interface (`ADR-0076`) let six engineering disciplines be
  added without modifying existing contracts — real, demonstrated
  extensibility, not a promise. See Finding A-6 for the trade-off this
  buys.
- **DIP** is correctly realized throughout the platform core — every
  platform service is consumed through an interface, resolved via
  constructor injection; the one deliberate exception (Discovery/
  Registration/Lifecycle, above) is a considered, disclosed exclusion,
  not an oversight.
- **ISP** is respected in the Engineering Domain's facet-interface design
  (`IHasParent`, `IHasBomLine`, etc., composed per kind rather than one
  fat interface).

### ADR Compliance

Spot-checked directly against code, not merely against the ADR's own
prose, for the highest-risk decisions:

- **ADR-0028** (Event Bus dispatch/failure model) — confirmed exactly:
  `EventBus.PublishAsync` snapshots subscribers under lock, dispatches
  outside it, isolates every subscriber exception except
  `OperationCanceledException`, which propagates.
- **ADR-0038** (Command dispatch failure model) — confirmed: unlike the
  Event Bus, `CommandDispatcher.DispatchAsync` logs and *rethrows* a
  handler exception rather than isolating it — the correct, deliberately
  different failure model for a one-caller-one-handler command versus a
  many-subscriber event, and the code matches the documented distinction
  precisely.
- **ADR-0017 / ADR-0034** (Host-owned vs. DI-public boundary) — confirmed
  via the service-locator audit above.
- **ADR-0023 / ADR-0033** (layering, Shell-above-Host) — confirmed via
  the dependency-direction audit above.

No ADR violation was found in the areas sampled. This is a meaningfully
positive signal given the volume of decisions (99 ADRs) this platform is
tracking — but it is a sample, not exhaustive coverage of all 99.

### Command Framework

Well-scoped and consistent: `CommandDispatcher` is a thin wrapper over
`CommandHandlerTable`, with a documented, deliberate failure model
(rethrow, not isolate — commands are point-to-point, not broadcast).
The framework is DI-public per `ADR-0036`. Two disclosed, still-open gaps
are real and independently confirmed, not overstated by the project's own
Technical Debt Register: `TD-11` (registration-order "squatting" — a
plugin whose module Id sorts earlier can claim a well-known command Id
before its intended owner) and the related permission-enforcement gap
(`TD-09`/`TD-10`) — the enforcement mechanism (`IPermissionEvaluator`,
`ADR-0044`) exists but has not been wired into command/navigation
registration. See Finding A-3.

### Event Framework

The strongest-engineered subsystem reviewed. Concurrency handling is
correct and economical (single lock, snapshot-then-dispatch, no deadlock
risk on re-entrant publish from within a handler — independently traced
through the code, not merely trusted from the doc comment describing it).
The three disclosed exclusions (no automatic unsubscription, strong
subscriber references, no polymorphic dispatch) are genuine, low-cost
trade-offs for a single-process, first-party-consumer event bus, not
defects.

### Runtime Host

`TempestHost` (704 lines) correctly stays within its documented
"deliberately thin" mandate — it orchestrates six independently-tested
services in a fixed sequence rather than reimplementing any of them.
Sequential, single-threaded startup/shutdown is a defensible choice at
current scale and is honestly justified (Deterministic Systems principle)
rather than left unexplained. The startup-race class of bug this
sequencing model is most exposed to (a Workspace read occurring before
module initialization has actually finished, `TD-26`) was found,
correctly root-caused, and fixed at its true source (`WorkspaceManager`
now waits on `IDiagnosticsProvider.HostState == HostState.Running`) rather
than patched at each symptom site — a good example of this project's
engineering discipline actually holding under a real defect, not only in
greenfield design.

### Plugin Architecture

Structurally sound, security-incomplete. `PluginManifestDiscoveryService`
and `PluginAssemblyLoader` correctly isolate per-plugin failures (a
malformed manifest or unloadable assembly is logged and excluded, never
brought down the whole discovery pass — `ADR-0025`'s failure
classification is real in the code). The unresolved gap is trust, not
discovery: `PluginAssemblyLoader.LoadOne` loads a plugin assembly via
`Assembly.LoadFrom` into the default `AssemblyLoadContext` — a loaded
plugin receives the same DI-container trust as first-party code, cannot
be unloaded, and no `IPermissionEvaluator` check exists anywhere on the
plugin-load or module-registration path despite the mechanism existing
since `WP 6.1`. This is honestly disclosed as `TD-09` and currently low-
impact only because the plugin catalogue is empty (zero real third-party
plugins exist). See Finding A-3.

### Desktop Architecture

`Tempest.Desktop` (`ADR-0094`, Avalonia, `v0.10.0`) is the newest and
least mature layer, as its version history would predict, and it shows.
The pure-code-UI decision (no `.axaml`, every view built in C#) is a
reasonable, disclosed trade-off for keeping one build pipeline rather
than two — but combined with `MainWindow` also being the layer's
composition root, it has produced the platform's largest and least
cohesive class. `ObjectEditorView.cs` (941 lines) and
`ProjectExplorerView.cs` (738 lines) show the same growth pattern one
tier down. The theming approach (`ThemeReactiveBrush`/
`ApplicationPalette`, per the Technical Debt Register's own `TD-39`-class
entries) has already needed the same fixed-brush-instead-of-theme-
reactive-brush bug found and repaired five separate times across five
different Work Packages — a real, recurring defect class, not a one-off,
suggesting the underlying pattern (a brush must opt in to being theme-
reactive, rather than defaulting to it) is easy to get wrong by
omission. See Finding A-1 and A-7.

## Engineering Domain Review

### Code Quality

Consistently high in the platform core; good-to-uneven at the UI edge.
Exception design is disciplined: only **one** blanket `catch (Exception)`
exists in the entire `src/` tree; everywhere else, exception handling is
typed and deliberate. Nullable-reference-type escape hatches (`null!`,
`#pragma warning disable`) appear in only 3 files, 7 occurrences total,
across ~66,000 lines — a genuinely low rate. No mutable static state was
found. No commented-out code or inline `TODO`/`FIXME`/`HACK` markers
exist anywhere in `src/` — this project tracks debt in its governance
register instead of scattering markers through the code, and that
discipline has actually held (zero markers found, not merely low).

The recurring weakness is size and cohesion at the composition-root/view
layer — see Finding A-1.

### Test Quality

Strong. 1,934 test methods across 177 files (`tests/`, ~42,600 lines —
nearly two-thirds the size of `src/` itself). No mocking framework
(Moq, NSubstitute, FakeItEasy) is referenced anywhere in the solution;
test doubles found are hand-written, purpose-built fakes (e.g.
`RecordingHandler<TEvent>`) that exercise real collaborator contracts
rather than asserting against mock call verification — the "prefer real
implementations over mocks" convention this project documents is
genuinely followed, independently confirmed by absence-of-dependency, not
by the project's own claim. No `[Skip]`/`Skip =` markers were found —
no test is silently disabled. `Tempest.Desktop.Tests` uses Avalonia's real
headless rendering backend rather than a UI mock, a materially stronger
choice than the common alternative.

The gap is not test *quality* but test *assurance*: see the CI finding
below — a large, well-written suite that nothing but a human running it
locally actually gates on.

### Technical Debt

The Technical Debt Register (41 tracked items as of the last entry read)
is a genuinely useful artifact — each entry has a since-date, an owning
Work Package, a revisit trigger, and an honest Open/Resolved/Partially-
Resolved status, and this review's own spot-checks (`TD-09`, `TD-26`,
`TD-39`) confirmed the register's characterization of each matches what
the code actually does. The debt itself is mostly well-chosen deferral —
narrow, disclosed, genuinely low-cost-to-leave-alone items (no Temperature
unit conversion, no calculation cancellation token, etc.) rather than
accumulated shortcuts.

The register's biggest problem is not its content but its *format*: see
Finding A-5.

### Maintainability

High in `Tempest.Core`, where every subsystem reviewed was small enough
to hold in working memory and the ADR trail makes *why* traceable.
Declining at the presentation edge, where `MainWindow`/`EngineeringCockpit`
-scale files mean a contributor touching one more feature is now editing
an already-1,500-line file rather than a small, focused one. The
project's own Work Package cadence (roughly one feature per WP, each
retrospective auditing its own diff against every existing Technical Debt
item) is a real maintainability asset — it is also the mechanism by which
`MainWindow.cs` grew to its current size one "additive, non-breaking"
change at a time, since no single Work Package's own diff ever looked
large enough on its own to trigger a decomposition.

### Extensibility

Demonstrated, not merely designed-for. The facet-interface/generic-
relationship domain model (`ADR-0075`/`ADR-0076`) has now absorbed six
engineering disciplines without a contract change — real evidence of
correct abstraction. The Module/Plugin/Hosted-Service pipelines have each
been proven against at least one genuinely independent consumer beyond
their own first implementation. The cost side of this extensibility is
Finding A-6 (stringly-typed classification/relationship vocabulary) —
real, working, but leaning entirely on convention and code review rather
than the type system to keep six-and-growing disciplines' tags coherent.

## Release Readiness for v1.0

TempestOS is **feature- and architecture-ready** to keep extending toward
`v1.0`. It is **not yet release-engineered** for the confidence a `v1.0`
commitment implies:

- **No CI/CD pipeline exists anywhere in this repository** — no
  `.github/workflows`, no build-server configuration of any kind, only a
  single, manually-invoked `scripts/new-release.ps1` that checks branch
  and clean-tree state before tagging. Every "N/N tests passing, 0
  Warnings/0 Errors" claim that appears in every one of the 100+ Work
  Package retrospectives this review read is a self-reported, locally-run
  assertion — real and almost certainly accurate given everything else
  observed about this project's honesty discipline, but currently
  unverifiable by anyone who did not personally run the build. This is
  the single highest-leverage gap standing between this codebase and a
  confident `v1.0` — see Finding R-1.
- **License/security posture is disclosed, not resolved, for anything
  beyond local/first-party use** — `TD-13`/`TD-14` (no real REST API
  authentication beyond a trusted header, no TLS) and `TD-16` (no license
  file signature verification) are all honestly named and all currently
  mitigated by scope (loopback-only binding, no untrusted distribution
  channel). Whether these need to close before `v1.0` depends entirely on
  whether `v1.0` intends to expose the REST API or license file beyond a
  fully-trusted local boundary — a product decision this review cannot
  make, but one worth making explicitly rather than by default.
- **The plugin trust gap (`TD-09`) and the dual-presentation-stack
  question (Finding A-2)** both hinge on the same unanswered question:
  what is TempestOS's `v1.0` product surface? A single-user desktop
  application with an empty plugin catalogue can safely ship with both
  gaps open. A platform advertising third-party extensibility or a
  supported console mode cannot.

None of the architecture reviewed would need to change to close any of
these gaps — that is itself a positive signal about how the platform was
built.

## Findings

Ordered by severity. Each finding names whether it should be resolved
**before v1.0** or is safe to **defer to v1.x**.

### Critical

None found.

### High

**A-1. Composition-root God Objects in the Desktop layer.**
*Evidence:* `MainWindow.cs` — 1,556 lines, 35 fields, one `sealed class`
combining service resolution (10+ `GetService` calls in the constructor),
view construction, undo/redo stack, command history, layout-preset
management, flyout/auto-hide handling, and status-bar refresh.
`EngineeringCockpit.cs` — 1,398 lines, similarly multi-responsibility.
*Impact:* Every new Desktop capability is now, by construction, a change
to an already-huge file — this concentrates merge risk, makes unit
testing an individual responsibility (e.g. undo/redo) harder than it
needs to be, and is the direct mechanism behind the recurring `TD-39`-
class theming bugs (fixed five separate times) — a class this size is
harder to review for "did I miss a spot" than several small ones would
be.
*Recommendation:* Extract composition/service-resolution into a
dedicated composer (the project already has this pattern —
`EngineeringWorkspaceComposer` — precedent exists to extend it or add a
sibling for Desktop-specific wiring). Extract Undo/Redo, Command History,
and Layout-preset management into their own collaborator classes
`MainWindow` delegates to rather than implements.
*Disposition:* **Before v1.0** — the file will only keep growing at the
current one-feature-per-Work-Package cadence, and it is currently the
single largest source file in the platform by a wide margin (nearly 3×
the next-largest `Tempest.Core` file).

**A-2. Two independently maintained presentation stacks, with no
documented product decision about the console shell's future.**
*Evidence:* `src/Tempest.App/Program.cs` still boots a full, hand-rolled
console renderer (`WorkspaceShell`, `TempestShell`) end to end;
`src/Tempest.Desktop/Program.cs` boots the Avalonia GUI. Both share
`EngineeringWorkspaceComposer` for platform composition but each
independently re-implements rendering, input handling, and per-discipline
presentation logic on top of it.
*Impact:* Every future Engineering Discipline feature now has two
plausible places it needs to land (or an explicit, currently-undocumented
decision that it only needs one). This roughly doubles the presentation-
layer maintenance surface for a two-person-scale project's worth of
Work Package cadence, and nothing in the reviewed documentation states
whether the console shell remains a supported product surface after the
`v0.10.0` Desktop release, or is now effectively a legacy/test harness
that happens to still run.
*Recommendation:* Make the decision explicit. Either formally retire the
console shell as a shipped product surface (demoting it to a dev/test
harness, documented as such) or commit to maintaining both, with the
added cost named plainly in governance the way this project names every
other trade-off.
*Disposition:* **Before v1.0** — this is a cheap decision to make now and
an expensive one to have made implicitly by the time a third UI
consumer's worth of features has landed in both places.

**R-1. No CI/CD automation exists.**
*Evidence:* No `.github/workflows`, no build-server configuration
anywhere in the repository; `scripts/new-release.ps1` is the only
automation, and it validates branch/clean-tree state, not build/test
success. Every test-pass and warning-count claim across 100+ retrospective
documents is self-reported from a local run.
*Impact:* Nothing currently prevents a regression from being merged to
`main` with a broken build or a failing test, other than the discipline
of whoever is running the Work Package — a discipline this review found
to be genuinely strong, but which a `v1.0` commitment should not need to
rely on trust alone to verify.
*Recommendation:* Stand up a minimal CI pipeline (build + full test suite
+ warnings-as-errors, matching the "0 Warnings/0 Errors" bar this project
already holds itself to manually) gating merges to `main`, before making
any external `v1.0` release promise.
*Disposition:* **Before v1.0.**

### Medium

**A-3. Plugin/Command/Navigation trust boundary is unenforced.**
*Evidence:* `PluginAssemblyLoader.LoadOne` uses `Assembly.LoadFrom` into
the default `AssemblyLoadContext` (no isolation, no unload capability);
no `IPermissionEvaluator` call exists on the plugin-load, module-
registration, command-registration, or navigation-registration path
despite the mechanism existing since `WP 6.1` (self-disclosed as `TD-09`/
`TD-10`/`TD-11`, independently confirmed by direct code inspection).
*Impact:* Currently low — the plugin catalogue is empty. Becomes real the
moment a first third-party plugin ships, at which point a plugin has
full, unenforced DI-container trust and can squat a well-known command or
navigation Id ahead of its intended owner.
*Recommendation:* If third-party plugin support is on the `v1.0` roadmap,
wire `IPermissionEvaluator` into the plugin-load and registration paths
before advertising it. If `v1.0` remains first-party-modules-only, this
is safe to defer, but should be named as a blocking prerequisite for
*any* future third-party plugin announcement.
*Disposition:* **Before v1.0** only if third-party plugins are promised
at `v1.0`; otherwise **defer to v1.x**.

**A-4. `TD-13`/`TD-14`/`TD-16` — no real REST API authentication, no TLS,
no license file signature verification.**
*Evidence:* Independently confirmed via `Tempest.Core.Api` and
`Tempest.Core.Licensing` inspection; all three are honestly disclosed in
the Technical Debt Register with the same "mitigated by scope, not fixed"
framing.
*Impact:* None today (loopback-only binding, no untrusted distribution
channel for license files). Becomes real the moment either surface is
exposed beyond a fully-trusted local boundary.
*Recommendation:* Treat as a named prerequisite for any deployment
scenario beyond local/trusted use — do not let it become an implicit gap
discovered at deployment time.
*Disposition:* **Defer to v1.x**, contingent on deployment scope — flag
explicitly if `v1.0`'s scope changes to include network- or distribution-
exposed use.

**A-6. Domain classification/relationship vocabulary is entirely
stringly-typed, by deliberate design, with no compile-time safety net.**
*Evidence:* `ADR-0073`/`ADR-0076`/`ADR-0088`/`ADR-0091` each independently
choose open string tags (`Classification`, relationship kind) over typed
alternatives, to avoid a combinatorial explosion of per-discipline
concrete types. Confirmed as real and working across six disciplines.
*Impact:* A typo in a classification or relationship-kind string fails at
runtime, not compile time, and is discoverable only via the
`RelationshipKindCategoryMap`/registries or a full-text search — the
coordination cost of "know the right string" is currently carried
entirely by convention and Work Package code review, with no enforced
catalogue.
*Recommendation:* A lightweight, additive safety net — e.g. per-
discipline `internal static class` string-constant catalogues, or a
build-time check validating classification/relationship strings against
the live registries — would preserve `ADR-0073`'s open-string contract
while catching the failure mode this pattern is most exposed to.
*Disposition:* **Recommend before v1.0** given how central this pattern
now is to every discipline (nine planned, six shipped) — not release-
blocking on its own.

**A-7. DI container has no cached/compiled construction path.**
*Evidence:* `TempestServiceProvider.Construct` calls
`implementationType.GetConstructors()` and reflective `.Invoke(...)` on
every resolution, with no delegate caching.
*Impact:* Negligible today (mostly-singleton, startup-time resolution).
Latent risk if a future Work Package leans on Transient-heavy, per-
command or per-request resolution (the REST API and Command Framework
are plausible future consumers of exactly that shape).
*Recommendation:* No action needed absent a measured problem — matches
this project's own "no measured problem yet" disclosure pattern used
elsewhere (`TD-12`/`TD-20`).
*Disposition:* **Defer to v1.x** — explicitly a watch item, not a fix-now
item.

**A-5. Governance/documentation verbosity has become a structural
maintenance cost.**
*Evidence:* The Technical Debt Register's own "Last Reviewed" cell for
a single row is one unbroken paragraph spanning the register's entire
multi-month history (tens of thousands of tokens); XML doc `<remarks>`
blocks on ordinary sample-module classes routinely run 40-60 lines
narrating Work Package cross-references rather than describing the API;
`PROJECT_STATUS.md` is 338 KB and includes multi-paragraph essays
adjudicating Work Package *numbering* history. A concrete consequence:
`docs/governance/Governance Index.md` states "all 39 Architecture
Decision Records" — the actual count, verified directly against
`docs/adr/`, is 99 (the linked `ADR Register.md` sub-document itself is
current and correct; the index's own summary text is not).
*Impact:* Every future change pays a rising documentation tax; the volume
itself works against the governance suite's own stated purpose ("find
where X is tracked without knowing which category it lives in first"),
and — as the ADR-count drift shows — makes exactly the kind of staleness
this discipline exists to prevent more likely, not less, because
correctly updating a 30,000-token narrative cell is much harder than
updating a fact.
*Recommendation:* Cap narrative history in register cells and doc-comment
`<remarks>` blocks — link to a changelog/retrospective rather than
inlining its full text on every review. Fix the Governance Index's ADR
count as a trivial, immediate example.
*Disposition:* **Recommend before v1.0** (or at minimum an explicit
governance decision to accept the compounding cost) — this is a process
finding, not a code defect, but it will only get more expensive to
unwind the longer it continues.

### Low

**A-8. Per-resolution Information-level logging in the DI container.**
*Evidence:* `TempestServiceProvider.GetService` logs "Resolving service
X" / "Resolved service X -> Y" at `Information` level on every single
call, unconditionally when a logger is attached.
*Impact:* Log-noise and minor overhead; drowns out genuinely actionable
Information/Warning entries as resolution volume grows.
*Recommendation:* Move per-resolution success logging to Debug/Trace;
reserve Information/Warning for failures.
*Disposition:* **Defer to v1.x** — cheap to fix whenever the file is next
touched.

**A-9. `ADR-0095` is missing from the sequence (`ADR-0094` → `ADR-0096`).**
*Evidence:* Direct file enumeration of `docs/adr/`.

## Architectural Strengths (Summary)

For balance, restated plainly: the platform core is genuinely
well-built. Empirically verified downward-only dependency direction; a
DI container small enough to read in full and reason about, with
deterministic construction and full resolution-chain error reporting; an
Event Bus with textbook-correct concurrent snapshot-then-dispatch
semantics; a Command Framework with a documented and honoured failure
model distinct from the Event Bus's; a domain model that has absorbed six
engineering disciplines without a contract change; a test suite that
avoids mock-based brittleness by actual policy, not aspiration; near-zero
blanket exception handling and near-zero nullable-safety escape hatches
across 66,000 lines; and a Technical Debt Register whose entries, spot-
checked against the code, say what they claim to say. The gaps found in
this review sit at the edges — the newest UI layer, the release pipeline,
the trust boundary around a currently-empty plugin catalogue — not in the
foundation everything else is built on.

## Overall Engineering Assessment

**Architecturally sound. Engineering-disciplined. Not yet release-
engineered for v1.0.** TempestOS's platform core would pass a rigorous
architecture review at a considerably larger organization. Its newest
layer (`Tempest.Desktop`) is carrying the normal growing pains of a
young, fast-moving UI codebase and should be decomposed before it sets
the pattern for everything built on top of it. Its release process is the
weakest link relative to everything else reviewed — a codebase this
carefully engineered deserves a build pipeline that verifies its own
claims by machine, not narrative alone. None of the findings in this
review require revisiting a foundational decision; all of them are the
ordinary, addressable cost of a platform that has grown quickly and
mostly well.
