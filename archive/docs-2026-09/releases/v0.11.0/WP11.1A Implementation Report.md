## What Was Built

`.github/workflows/ci.yml` — TempestOS's first CI pipeline. One workflow,
two jobs:

- **`build-and-test`** — a `fail-fast: false` matrix over
  `configuration: [Debug, Release]`. Each leg: checks out the commit;
  installs the exact .NET SDK named in `global.json` via
  `actions/setup-dotnet`'s `global-json-file` input; restores; builds
  `src/TempestOS.slnx` for its own configuration with
  `-p:TreatWarningsAsErrors=true`; runs the complete test suite
  (`dotnet test` against the same solution) with TRX output; publishes a
  Markdown build/test summary to the run's Job Summary; uploads the build
  log and TRX results as artifacts (always, even on failure); and, for
  the Release leg only, uploads the built `Tempest.App`/`Tempest.Desktop`
  output as a downloadable artifact.
- **`gate`** — depends on the matrix, fails if either leg did not
  succeed. One named status check for future branch-protection rules to
  require, rather than needing to enumerate both matrix legs.

Triggers: `push`, `pull_request`, `workflow_dispatch` — every one
requested, none narrowed by a path filter or branch filter.

Two small, disclosed supporting changes: `.gitignore` gained one new
pattern (`build-*.log`, the log file the workflow's Build step writes,
harmless if reproduced locally); `Directory.Build.props` was **not**
touched — `TreatWarningsAsErrors` remains `false` there, so a local
`dotnet build` behaves exactly as it always has. The stricter check is a
CI-invocation-only override, not a production build-configuration change.

## Design Decisions and Rationale

| Decision | Rationale |
|---|---|
| Runner pinned to `windows-2022`, not `windows-latest` | Matches this project's own house style of pinning every version exactly (`global.json`'s SDK version, every `PackageReference`) — an unannounced runner-image change should not silently change CI behaviour. |
| SDK installed via `global-json-file: global.json`, not a hand-typed version | Single source of truth already established by this repository; a second, independently-typed SDK version in the workflow would be exactly the kind of drift `WP11.0A` finding `A-5` flagged elsewhere. |
| `TreatWarningsAsErrors=true` at the CI build step only | Verified safe first (see Verification, below) rather than assumed; makes the "0 Warnings" claim every retrospective has always made machine-enforced without changing local build behaviour. |
| Matrix (`Debug`, `Release`) rather than one configuration | The brief requires both configurations built; running the full test suite against both (rather than one) directly operationalises this project's own recurring retrospective claim, "Debug and Release both clean" — previously asserted, now checked. |
| `fail-fast: false` | A failure in one configuration should never suppress the other's own result — both are independently informative. |
| No third-party marketplace actions | Only official, first-party GitHub actions (`actions/checkout`, `actions/setup-dotnet`, `actions/upload-artifact`) are used. Build/test summaries are produced by a small, inline, fully-auditable PowerShell script writing directly to `$GITHUB_STEP_SUMMARY`, rather than a third-party test-reporting action — this keeps the pipeline's supply-chain surface minimal and consistent with this project's own security-conscious posture (`ADR-0044`, the Threat Model, the Security Roadmap). |
| Exit-code checks are explicit (`if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }`) after every `dotnet` invocation | PowerShell pipeline exit-code propagation through `2>&1`/`Tee-Object` is a documented sharp edge; an explicit check is deterministic and does not depend on it. The build/test summary step's own warning/error counts are a diagnostic aid only — the exit-code check is the actual, authoritative gate, so a parsing edge case in the summary can never mask a real failure. |
| Release build output published as an artifact; Debug output is not | The Release artifact is a smoke-testable build of the exact commit — genuinely useful. Publishing the Debug build too would double artifact storage for no verification benefit. |
| No branch-protection rule configured | Configuring repository branch-protection settings is a GitHub repository-administration action, outside this Work Package's own scope (infrastructure-as-code in this repository, not repository settings). The `gate` job exists specifically so that becomes a one-line addition whenever the Product Owner chooses to require it. |

## Verification

Direct local reproduction of every command the workflow issues, run
before the workflow was finalised — not simulated, not assumed:

### 1. Debug build

```
$ dotnet build src/TempestOS.slnx -c Debug --no-restore
Build succeeded.
    0 Warning(s)
    0 Error(s)
```

Re-verified with the exact CI-invocation flag added:

```
$ dotnet build src/TempestOS.slnx -c Debug --no-restore -p:TreatWarningsAsErrors=true
Build succeeded.
    0 Warning(s)
    0 Error(s)
```

### 2. Release build

```
$ dotnet build src/TempestOS.slnx -c Release --no-restore
Build succeeded.
    0 Warning(s)
    0 Error(s)
```

### 3. Complete test suite

```
$ dotnet test src/TempestOS.slnx -c Release --no-build --logger "console;verbosity=normal"
Tempest.Core.Tests:    Total tests: 2064   Passed: 2064   Failed: 0
Tempest.Desktop.Tests: Total tests: 202    Passed: 202    Failed: 0
```

Combined: **2,266 / 2,266 passing** — matching the count this project's
own most recent retrospectives (`WP 10.8A` onward) independently
reported. `Tempest.Desktop.Tests` (Avalonia headless UI tests) ran and
passed directly on Windows with no display attached beyond the ordinary
CI session — confirms the pipeline's own runner choice (`windows-2022`)
does not need `Xvfb` or any other display-virtualisation workaround an
`ubuntu-latest` runner would.

Total wall-clock for one full test pass: ~8 minutes (`Tempest.Core.Tests`
~2.2 min, `Tempest.Desktop.Tests` ~5.9 min — the dominant cost, real
Avalonia UI construction per test, not I/O). Both matrix legs run this
in parallel on separate runners, so the workflow's own wall-clock cost is
one leg's time, not both summed.

### 4. Failure reporting

Not exercised against a real failure in this Work Package (the tree
builds and tests cleanly throughout — introducing a deliberate,
temporary regression to prove the negative was judged unnecessary risk
against "no production code behaviour shall change"). Correctness of the
failure path instead rests on:

- `dotnet build`/`dotnet test` returning a non-zero exit code on any
  compile error, promoted warning, or failing test — standard,
  well-documented CLI behaviour, not something this workflow reimplements.
- Each step's own explicit `if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }`
  check, which propagates that exit code to the step, and from there to
  the job, and from there (via `gate`) to the one status check a future
  branch-protection rule would require.
- The summary/artifact-upload steps' `if: always()` guard, confirmed by
  direct reading of GitHub Actions' own documented step-condition
  semantics (an `always()` step runs regardless of a prior step's
  outcome within the same job) — so a failing run still produces a
  summary and artifacts to diagnose from.

**Disclosed, not glossed over: this is `Inferred`, not `Verified`,
against a real GitHub-hosted failure.** The Product Owner should treat
the first genuinely failing run as this pipeline's own real proof, the
same "prefer evidence over speculation" discipline this project applies
everywhere else.

### 5. Passes from a clean checkout

Every command above was run against `feature/v0.11.0-v1-architecture` at
the exact commit this Work Package's own changes were built on top of —
a real local build/test/restore cycle, from source, not a cached or
partial one (`dotnet restore` was run explicitly before either build).
This reproduces every step the workflow itself performs, in the same
order, with the same flags.

**What was not, and could not be, verified in this environment:**
this sandboxed working environment has no GitHub Actions runner and no
`gh` CLI available, and pushing this branch to trigger a real,
GitHub-hosted run was judged an outward-facing action outside this Work
Package's own "await review" closing instruction. The workflow's actual
execution on a real `windows-2022` GitHub-hosted runner — including
`actions/setup-dotnet`'s own network-dependent SDK install and
`actions/upload-artifact`'s own upload behaviour — remains **Unknown**
until the branch is actually pushed. Every command it runs has been
directly, locally verified to succeed with the exact flags the workflow
uses; the GitHub Actions execution environment itself has not. This is
named plainly, per this project's own Verified/Inferred/Unknown
discipline, rather than presented as fully proven.
