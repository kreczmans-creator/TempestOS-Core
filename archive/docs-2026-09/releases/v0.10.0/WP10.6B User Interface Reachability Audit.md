# WP 10.6B — User Interface Reachability Audit

## Purpose

A pure audit — no implementation changes. For every feature
implemented from `WP 10.0B` onward (through `WP 10.6A`/`WP 10.5C`,
the most recent), this document records whether it exists in code, is
reachable through the running UI, is actually instantiated at runtime,
is wired to a real command/handler, and is genuinely end-to-end
functional — or is a disclosed placeholder or dead code. A companion
document, `WP10.6B Prioritised Defect List.md`, lists every genuine gap
found, ranked, with evidence.

## 0. Methodology, Disclosed Honestly

This environment has no screenshot tool and no accessibility-tree
inspector — the same constraint disclosed in `WP10.5C Runtime UX
Traceability Matrix.md`, unchanged. "Verify manually" is honoured here
by the same two-part evidence discipline that document established,
extended one level deeper for this audit's own seven explicit
questions:

1. **A fresh real process launch** (`dotnet run`, this session,
   8-second window) — log evidence re-captured, not reused from a
   prior Work Package's own run, to confirm nothing has regressed
   since `WP 10.5C`.
2. **Direct, re-derived source tracing** for every claim — "exists in
   code" (a `grep`/file read), "reachable" (a real entry point added to
   the real shown `Window`'s own tree), "instantiated" (a real
   constructor call on a live code path, not merely a type
   declaration), "command wired" (a real dispatch call reaching
   `ICommandDispatcher`/`ICommandRegistry`/`IWorkspaceManager`), "end-
   to-end functional" (the dispatch reaches a real handler that
   mutates real state, confirmed either by direct handler inspection or
   by an existing, real, passing test that proves it).
3. **Where a headless `[AvaloniaFact]` test already exercises the exact
   path in question**, that test's own pass is cited directly as "end-
   to-end functional" evidence — a real, attached, rendered control
   tree, not a mock.

**Status vocabulary** used throughout the matrix:

| Symbol | Meaning |
|---|---|
| ✅ Live | Exists, reachable, instantiated, wired, end-to-end functional. |
| ⚠ Live (Partial) | Reachable and functional for some real cases; an honest, disclosed fallback for the rest — never a silent failure. |
| 🟡 Placeholder (Disclosed) | Reachable; shows an honest "not available"/"needs more input" message; no real dispatch occurs. |
| 🔵 Foundation Only (Disclosed) | Exists, correctly wired end-to-end at the infrastructure level; zero real production caller currently exercises it (no UI reaches it yet). |
| ❌ Unreachable | Exists in code, correctly wired once reached, but no real UI path reaches it — a genuine defect. |
| ⬛ Dead Code | Exists in code; never referenced, instantiated, or reachable from anywhone in production — a genuine defect. |

## 5. Ribbon — Command Dispatch, By Verb (the Audit's Own Central Finding)

This is where "reachable" and "end-to-end functional" diverge sharply
enough to warrant its own section — see `WP10.6B Prioritised Defect
List.md` item 1 for the full write-up. Every verb below is **visually
present, correctly grouped, and shown enabled whenever any object is
selected** (`RibbonView.RefreshEnablement`'s own `_ => true` default
for every verb except rename/edit/delete) — but clicking most of them
produces only a status message, never a real command dispatch.

| Verb (all six disciplines unless noted) | Reachable? | Instantiated? | Command wired? | E2E functional? | Status |
|---|---|---|---|---|---|
| Delete | Yes | Yes | Yes (`IWorkspaceManager.DeleteObjectAsync`) | Yes | ✅ Live |
| Rename | Yes | Yes | Yes (opens real Object Editor) | Yes | ✅ Live |
| Edit / Revise | Yes | Yes | Yes (opens real Object Editor) | Yes | ✅ Live |
| Create — **Mechanical only** | Yes | Yes | Yes (`CreateMechanicalObjectCommand`) | Yes | ✅ Live |
| Duplicate — **Mechanical only** | Yes | Yes | Yes (`DuplicateMechanicalObjectCommand`) | Yes | ✅ Live |
| Create — other 5 disciplines | Yes (button visible, enabled) | N/A | No | No — honest status message only | 🟡 Placeholder (Disclosed, `FCR-0075`) |
| Duplicate — other 5 disciplines | Yes | N/A | No | No | 🟡 Placeholder (Disclosed, `FCR-0075`) |
| Move, Copy — all 6 disciplines | Yes | N/A | No | No | 🟡 Placeholder (Disclosed, `FCR-0073`) |
| Lock, Unlock, Request Review, Approve, Archive, Release, Set Status — all 6 disciplines | Yes | N/A | No | No | 🟡 Placeholder (**not previously quantified this precisely — see Defect List item 1**) |
| Execute, Recalculate (Calculations) | Yes | N/A | No | No | 🟡 Placeholder |
| Record Result, Record Inspection Result (Verification/Manufacturing) | Yes | N/A | No | No | 🟡 Placeholder |
| Attach, Link (Documents) | Yes | N/A | No | No | 🟡 Placeholder |

| Compare Baselines, Validate Configuration, Set BOM Line (Mechanical) | Yes | N/A | No | No | 🟡 Placeholder |

**Confirmed via direct code trace**: `RibbonView.OnCommandButtonClickAsync`
has exactly four real dispatch branches (delete; rename/edit; a
`CreateDefault is not null` branch that — confirmed by `grep
"createDefault:"` across all six `*WorkspaceRegistration.cs` files,
zero matches — never fires for any real discipline command; and
`ObjectCreationHandlers`, containing exactly two entries,
`mechanical.create`/`mechanical.duplicate`). Every other verb, for
every discipline, falls through to the final, honest line: `'{descriptor.DisplayName}'
needs a selected target or additional input this ribbon does not yet
collect...`. Every one of these buttons is nonetheless shown fully
enabled (not greyed out) whenever any object is selected — a real,
if honestly-messaged, discoverability gap.

## 16. Summary

**Zero ❌ Unreachable and zero ⬛ Dead Code findings among the
application's real, shipped, user-facing surfaces** — every menu item,
Ribbon button, panel, and dialog traces to a real, wired control,
matching `WP10.5C Runtime UX Traceability Matrix.md`'s own conclusion
extended to `WP 10.6A`/`WP 10.5C`'s own newer surfaces. **One large,
precisely-quantified `🟡 Placeholder` surface** — the Ribbon's own
Lifecycle command group and every non-Mechanical Create/Duplicate/Move/
Copy verb, all shown fully enabled, none dispatching a real command —
is this audit's own sharpest, newest finding; see `WP10.6B Prioritised
Defect List.md` item 1 for the full write-up and evidence. One genuine
❌-adjacent finding — **no UI anywhere can change an object's lifecycle
state** (§10) — is the same root cause as item 1, called out
separately because it affects the Object Editor and Property Inspector
too, not only the Ribbon.
