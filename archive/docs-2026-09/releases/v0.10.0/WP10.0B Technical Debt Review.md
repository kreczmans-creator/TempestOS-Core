# WP 10.0B — Technical Debt Review

## Purpose

The required, dedicated Technical Debt Review this Work Package's own
controlling instruction names explicitly (distinct from the
"Technical Debt Assessment" title every prior real-discipline Work
Package used) — a full accounting of every debt item this Work Package
touches, resolves, or adds, plus independent re-confirmation of items
it does not.

## 1. `TD-26` — Reconfirmed Open, Its Own Predicted Consequence Now Directly Observed

`TD-26` (`WP 9.0A`): `WorkspaceManager.StartAsync` returns once
Platform Services are resolvable, not once Runtime Host module
Discovery/Initialise has finished. Its own "Revisit trigger" field
named, verbatim, exactly the class of consumer this Work Package is:
"a scripted, automation-driven, or latency-sensitive Workspace
consumer where a stale first read would be user-visible or
consequential." `tests/Tempest.Desktop.Tests` is precisely that
consumer — a `SwitchAreaAsync` call issued immediately after
`WorkspaceManager.StartAsync` returns intermittently failed with
`NavigationItemNotFoundException` before `WP10.0B Implementation
Report.md` §6.6's own mitigation (`WorkspaceHost`'s bounded poll) was
added.

**Disposition: remains Open, not resolved by this Work Package.** The
root cause (`WorkspaceManager.StartAsync`'s own readiness contract)
is unchanged — fixing it belongs to a future Work Package that touches
`WorkspaceManager` directly, outside this Work Package's own "no
contract redesign" scope. **Priority reconsideration recommended**: this
is now the *second* independent consumer (after `WP 9.0A`'s own
disclosure) to hit this exact defect's real consequences, not merely
name it as a theoretical risk — the evidentiary bar for prioritising a
real fix is now materially stronger.

## 2. New Item — `ProjectExplorer`/`PropertyInspector` Non-Deterministic Panel Ids Broke Cross-Restart Persistence — Found and Fixed

A genuine, pre-existing defect (present, unmodified, on the `v0.9.0`
tag — confirmed by direct code inspection of the shipped
`ProjectExplorer.cs`/`PropertyInspector.cs`, both unchanged since
`WP 8.1A`/`WP 8.1B`) — `Id` was generated via `Guid.NewGuid()` per
instance, meaning `ADR-0064`'s own session persistence design could
**never** correctly restore a panel's own placement across a genuine
process restart, only appear to work within a single process's own
save/load cycle. Found by `WP10.0B`'s own
`PersistentLayouts_HidingAPanelAndRestarting_RestoresTheSameLayout`
test — the first test in this project's history to construct two
genuinely independent `WorkspaceManager` instances against the same
persisted session state. **Fixed in place** (`WP10.0B Implementation
Report.md` §4, §6.5): both panels' own `Id` is now a fixed, well-known
`Guid` constant. Registered here as a Technical Debt item with
disposition **Resolved by `WP 10.0B`**, rather than silently omitted,
because it was genuinely present in already-shipped, tagged `v0.9.0`
code — mirroring `TD-26`'s own precedent of registering a pre-existing,
confirmed-shipped defect even though this Work Package closes it
immediately rather than leaving it open.

## 3. New Item — Desktop Persistence Store Location Is Launch-Context-Dependent

Disclosed directly by `WP10.0B Security Review.md` §6:
`PersistenceStore.DefaultRootPath` ("`persistence-data`") resolves
relative to the process's current working directory, not a fixed,
per-user profile location. A console tool's own working directory is
predictable (wherever the user's shell was); a graphical application's
own working directory, launched from a shortcut or file manager, is
not. **Disposition: Open, disclosed, not fixed** — the underlying
persistence mechanism is `ADR-0064`'s own unchanged design, and
changing its root-path resolution strategy is a decision for whichever
future Work Package owns `Tempest.Core.Persistence` directly, not this
one's own "no contract redesign" scope. No data-correctness
consequence today — worst case is session state persisting to an
unexpected (but still discoverable, still functional) location.

## 4. Item Reviewed, Not Newly Affected — `TD-32`

`TD-32` (`VerificationRecordReader`'s own ungated relationship read,
`WP 9.3A`) was flagged by `WP10.0A Security Review.md` §3 as a
future concern for the eventual graph-based Object Relationship View.
This Work Package's own scope does not include that graph view
(`WP10.0B Implementation Report.md` §5) — `TD-32` is therefore
unaffected by this Work Package, reconfirmed still Open, no action
required here.
