# WP 10.1A — Technical Debt Review

## Purpose

The required, dedicated Technical Debt Review this Work Package's own
controlling instruction names explicitly — a full accounting of the one
significant new finding this Work Package made, plus reconfirmation of
items it touches without changing.

## 1. New Item — Four Sample Modules Fail `InitialiseAsync` Against Their Own Literal Id

**The most significant finding of this Work Package.** Diagnosing an
incomplete `WP 10.0B`-era `TD-26` mitigation (`WP10.1A Implementation
Report.md` §4.1) via `IDiagnosticsProvider.Modules`, this Work Package
found four `Tempest.Samples` modules genuinely fail their own
`InitialiseAsync`, each against a duplicate-registration error
targeting a literal Id string that appears **nowhere else** in the
entire `Tempest.Samples` project (confirmed by direct, whole-project
`grep`):

| Module | Error |
|---|---|
| `tempest.samples.engineeringdomain` | "A material is already registered with Id 'SAMPLE-MAT-001'." |
| `tempest.samples.materials` | "A material is already registered with Id 'sample.fictional-test-alloy'." |
| `tempest.samples.requirements` | "A requirement is already registered under identifier 'SAMPLE-REQ-001'." |
| `tempest.samples.requirementsworkspace` | "A requirement is already registered under identifier 'REQ-STR-001'." |

**Confirmed, not merely observed once:**

- Reproducible on the very first `WorkspaceHost` construction in a
  fresh process (ruling out "leftover state from an earlier host in the
  same test process" — independently re-confirmed, `WP10.1A Engineering
  Review.md` §4).
- No retry mechanism exists anywhere in `IModuleLifecycleManager`
  (confirmed by direct source search) — ruling out "the module's own
  `InitialiseAsync` runs twice via an automatic retry."
- Each failing module's own colliding Id appears in **exactly one**
  source file — its own — ruling out "two different modules
  coincidentally chose the same literal Id."
- `Discovered`/`tempest.samples.navigation.zzz-duplicate`'s own failure
  ("A navigation item with ID 'tempest.samples.navigation.home' is
  already registered") is a **separate, deliberately-named** module
  (its own Id literally contains "duplicate") — this review treats it
  as an intentional demonstration of module failure isolation
  (`FOUNDATION.md` non-negotiable #4), not part of this same finding.

**Root cause not fully diagnosed within this Work Package's own scope.**
The most plausible remaining explanation — that each failing module's
own `InitialiseAsync` is, for some reason, invoked more than once
against the same running `EngineeringDomainContext`/`IMaterialCatalog`/
`IRequirementsService` singleton — was not confirmed at the mechanism
level (whether via Module Discovery finding a type twice, or some other
cause). This is deliberately not chased further here: diagnosing
`IModuleLifecycleManager`/Discovery's own internal behaviour is outside
a Cockpit-implementation Work Package's own proportionate scope,
exactly as `TD-26` itself was disclosed, not fixed, by `WP 9.0A`.

**Consequence, disclosed precisely:** `EngineeringDomainSampleModule`'s
own failure occurs before any Risk/Task/Milestone/Deliverable/Supplier/
PurchaseItem object is constructed (confirmed by statement order,
`WP10.1A Security Review.md` §5) — so none of those six sample object
types exist in *any* Workspace host today, console or desktop, and have
not since whichever Work Package introduced this defect (not
determined). `RiskSummary`/`UpcomingMilestones`/`OpenTaskCount`
(`WP 10.1A`'s own new Cockpit reads) are directly, honestly affected —
each correctly reports an empty/zero result today, proven correct by
this Work Package's own tests (`WP10.1A Implementation Report.md` §5).

**Disposition: Open, disclosed, not fixed.** Recommended next step: a
dedicated Runtime Host/Module Discovery Work Package (the same
candidate `TD-26` already recommends) should first determine whether
`InitialiseAsync` is genuinely being invoked twice per affected module,
and if so, why — before attempting any fix to
`EngineeringDomainSampleModule`/`MaterialsSampleModule`/
`RequirementsSampleModule`/`RequirementsWorkspaceSampleModule`
themselves, since fixing the symptom (renaming Ids) without
understanding the mechanism could mask a genuine, deeper defect.

## 2. `TD-26` — Reconfirmed Open, Mitigation Strategy Upgraded

`TD-26` itself (`WorkspaceManager.StartAsync` returning before Module
Initialisation completes) remains Open, unchanged at its own source.
`Tempest.Desktop`'s own mitigation (`WorkspaceHost.StartAsync`) was
upgraded from `WP 10.0B`'s own six-item-specific poll to a poll against
`IDiagnosticsProvider.HostState == HostState.Running` — a strictly more
general, authoritative signal (`WP10.1A Architecture Review.md` §2),
which is precisely how this Work Package's own finding (§1) was
discovered in the first place: the new signal correctly does *not*
mask the four permanently-failed modules the way the old six-item
check accidentally did.

## 3. Items Reviewed, Not Newly Affected

`TD-32` (`VerificationRecordReader`'s own ungated relationship read)
and `TD-35`/`TD-36` (`WP 10.0B`'s own findings — well-known panel Ids,
Settings persistence store location) are all reconfirmed unaffected by
this Work Package's own scope; none is touched by any file this Work
Package modifies.
