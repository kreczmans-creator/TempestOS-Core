# WP 10.2A — Engineering Review

## Purpose

An independent, direct-source verification of every claim
`WP10.2A Implementation Report.md` makes — not a summary of it.

## 1. `ADR-0096` — Verified Directly

Re-read `IWorkspaceManager.cs`/`WorkspaceManager.cs` independently of the
Implementation Report's own description. Confirmed: all five new members
(`RegisterRenameFactory`, `RegisterDeleteFactory`, `CanRename`,
`CanDelete`, `RenameObjectAsync`, `DeleteObjectAsync`) are genuinely
additive — every pre-existing member's own signature is byte-for-byte
unchanged. Confirmed `DispatchObjectCommandAsync`'s own use of
`CommandHandlerTable.DispatchAsync(ICommand, CancellationToken)` is the
identical, unmodified method `CommandRegistry.InvokeAsync` already calls
internally (`grep` against `CommandRegistry.cs` confirms the same call
shape) — genuinely no new dispatch mechanism, no reflection, introduced.

Traced all six discipline registration files directly: `Mechanical`,
`Calculations` (excluding the synthetic `"CalculationTemplate"` Kind,
confirmed correct by re-reading `EngineeringObjectFactory`'s own
`FindAsync`-based handler logic — a `CalculationTemplate` genuinely
cannot resolve there), `Documents`, `Verification`, `Manufacturing`
(confirmed `"WorkInstruction"`/`"Inspection"` correctly reuse Documents'/
Verification's own already-registered command types, not new ones), and
`Requirements` (confirmed no `Rename*Command` exists anywhere under
`src/Tempest.App/Workspace/Requirements/` by direct `find`, corroborating
the disclosed absence).

## 2. Project Explorer — Verified Directly

Read `ProjectExplorerView.cs` end to end. Confirmed the filter's own
`FilterNode` recursion correctly keeps an ancestor visible when only a
descendant matches (traced the `matchingChildren`/`selfMatches` branch
logic by hand against three constructed cases: root matches, leaf
matches, neither matches). Confirmed the inline-rename editor commits
only when the new name is non-empty and actually different, and cancels
cleanly on `Escape` without ever calling `RenameObjectAsync`. Confirmed
the drag/drop `Drop` handler is a genuine no-op (`e.DragEffects =
DragDropEffects.None`, no state mutation) — matches its own documented
"preparation architecture" scope exactly, not partially implemented and
silently failing.

## 3. Property Inspector — Verified Directly

**Genuine defect found and fixed during this Review, before sign-off:**
the Lifecycle section's own first implementation identified
status/lifecycle-shaped facets correctly, but never removed them from
the per-`FacetKind` loop afterward — the same fact appeared twice, once
under Lifecycle and once under its own original group (e.g.
`DisciplineSpecific`). Fixed in place: `Refresh()` now computes the
Lifecycle set once (`ExtractLifecycleFacets`), and the per-group loop
iterates only the *remaining* facets (`facets.Except(lifecycleFacets)`),
via `PropertyFacet`'s own record value-equality. Proven by a new,
dedicated regression test
(`PropertyInspectorView_LifecycleShapedFacet_IsShownOnlyOnce_NotDuplicatedWithItsOwnOriginalGroup`,
using a new internal test hook, `CountRenderedRowsWithFacetName`, that
walks the real rendered visual tree rather than trusting the model
alone) — not merely a corrected assumption, a proven fix.

Confirmed the editable Name field is gated correctly:
`isDisplayNameField && _currentKind is not null && _manager.CanRename(_currentKind)`
— a selection of a non-renamable Kind (e.g. `"Requirement"`) genuinely
renders read-only text, verified by direct trace against
`WorkspaceModernisationTests.ProjectExplorer_CanRename_IsFalseForRequirementKind_HonestlyDisclosedAbsence`.

## 4. Document Area / Status Bar — Verified Directly

Confirmed `SelectNextTab`/`SelectPreviousTab`'s own modulo arithmetic

against divide-by-zero). Confirmed every `StatusBarView` segment reads a
real value at call time (`IDiagnosticsProvider.HostState`/`.Modules`
freshly, `WorkspaceManager.StatusBar.StatusText` freshly) — no cached or
stale field retained across calls.
