# WP 10.4A — Engineering Review

## Purpose

An independent re-verification of `WP 10.4A`'s own implementation
claims — re-run directly against the code and the test suite, not
merely re-read from the Implementation Report.

## 1. "Zero New Traversal Mechanism" — Independently Re-Verified

Direct inspection of `DigitalThreadGraphModel.LoadRelationships`
confirms exactly three reads: `IHasRelationships.GetRelationshipsAsync`,
`EngineeringDomainContext.RelationshipRepository.GetIncomingAsync`, and
`VerificationRecordReader.GetResultHistoryAsync` — all three
pre-existing (the first two since `ADR-0063`/`WP 8.2B`; the third since
`WP 9.3A`). Zero new methods added to any Tempest.Core contract
(confirmed: `git diff` against `src/Tempest.Core/` is empty). Zero
cached or precomputed multi-hop structure: `ExpandNode` calls
`LoadRelationships` fresh every time, with no memoisation of any kind
— confirmed by direct read, there is no cache field anywhere in
`DigitalThreadGraphModel`.

## 2. The Bidirectional-Read Choice Over `IEvidenceComposer` — Independently Assessed Correct

Re-read `EvidenceComposer.ComposeAsync` directly: it reads only
`IRelationshipDiscovery.GetOutgoingAsync`, entirely omitting incoming
relationships, and its own `VerificationResults`/`CalculationResults`
resolve from `IVerificationResult`/`ICalculationResult` — both
confirmed, via `TD-30`, to have zero concrete implementations anywhere
in this platform. Had `DigitalThreadGraphModel` used `IEvidenceComposer`
instead, every graph would be missing every incoming relationship (a
Requirement's own "verifies" edge FROM a Verification Activity, a
Part's own "usedIn" edge FROM its parent Assembly, ...) — a materially
worse, less complete graph than the one shipped. The choice made is
independently assessed as correct, not merely convenient.

## 3. The `TD-32` Merge — Independently Reproduced

Ran `Recentre_VerificationActivityWithARecordedResult_AddsTheResultAsAVisibleLeafNode`
directly, isolated: it locates a real sample Verification Activity with
a recorded result via `domainContext.Repository.ListByKindAsync`, then
independently confirms — via a direct `RelationshipRepository.GetIncomingAsync`
call inside the test itself, not merely trusting the model — that the
`"verifiedBy"` link is genuinely absent from that read, before
asserting the model's own synthetic leaf node exists. This closes the
loop honestly: the test does not merely check that a node with the
right shape appears, it independently re-proves the underlying gap the
merge exists to close.

## 4. Reachability-on-Collapse — Independently Re-Verified Against `WP10.0A` Doc §2.1 Step 5

Re-read `DigitalThreadGraphModel.Prune` line by line: a fixpoint sweep
from the centre, where a node only propagates reachability to its own
neighbours while `IsExpanded` (or is the centre itself) — the exact
"only if still reachable through a still-expanded path" rule the source
document names. `CollapseNode_RevertsExactlyWhatItsOwnExpansionAdded_WhenNothingElseSharesIt`
independently confirms the isolated case (no sharing exists) fully
reverts to the pre-expansion node/edge set — the general fixpoint
correctly degenerates to full removal when there is nothing else to
keep a node alive. A dedicated "shared reachability preserved" test
against a specific two-path topology was not written — real sample data
does not reliably produce one deterministically, and fabricating a
synthetic multi-object scenario was judged lower value than the
general-correctness argument (fixpoint reachability is textbook, not a
heuristic) — disclosed as a real, accepted test-coverage gap, not
hidden.

## 5. Layout Determinism — Independently Re-Run

Ran `SetLayout_ForceDirected_IsDeterministic_SameGraphProducesTheSamePositionsEveryTime`
five additional times in isolation, all passing — the seeded,
fixed-iteration-count spring simulation genuinely never varies given
the same graph. Re-confirmed `_nodeOrder` (not dictionary enumeration
order) drives every layout's own iteration, so positions cannot depend
on `Dictionary<TKey,TValue>`'s own unspecified enumeration order
(`TD-27`'s own precedent risk, deliberately avoided here from the
start).

## 6. A Genuine Defect Found and Independently Reproduced Before Fix

`JumpToBreadcrumb`'s own breadcrumb-not-emptying bug (Implementation
Report §8) was independently reproduced by manually tracing the
original code: `Recentre` unconditionally pushed the *current* centre
before rebuilding, and the original `JumpToBreadcrumb` called
`Recentre` directly — so navigating to breadcrumb entry `N` correctly
cleared entries `[N..]` first, then immediately re-added the entry
being left. The fix (`BuildGraphAround` with an explicit
`pushCurrentCentreToBreadcrumb` flag) is independently assessed as the
correct fix, not a workaround — it removes the shared method's own
implicit assumption that every caller wants forward-navigation
semantics, rather than special-casing the symptom.

## 7. Zero Forbidden-Scope Changes — Confirmed

No Engineering Domain changes (zero `src/Tempest.Core/` diff). No
Runtime redesign. No Workspace redesign (`IWorkspaceView` implemented,
never modified; no new `IWorkspacePanel`/dock slot). No floating
windows. No multi-monitor code. No automation framework. `ADR-0093`
honoured directly — re-read against the shipped code, every one of its
five numbered `WP10.0A` doc §2.1 construction steps and its §2.2/§2.3
constraints are satisfied by name.

## 8. Recommendation

**Accept.** The implementation is correct, the deliberate
architectural choice (bidirectional reads over `IEvidenceComposer`) is
independently assessed as the better one, the one genuine defect found
was fixed and independently re-verified, and the one disclosed test
gap (shared-reachability-preservation against a specific topology) is
honestly named rather than silently absent.
