# WP 10.5A — Architecture Review

## Purpose

Assesses `WP 10.5A`'s own architectural decisions — including the
explicit instruction that any genuine architectural finding be
documented through an ADR rather than silently implemented — and
independently confirms whether that condition was actually met.

## 1. "No ADR Was Required" — Independently Assessed Correct

Re-examined every real design decision this Work Package made against
Engineering Governance §5's own ADR-creation criteria:

- **Theme-reactive brush infrastructure** (`ApplicationPalette`/
  `ThemeReactiveBrush`) — a new Desktop-local presentation mechanism,
  but not a new *architectural* decision in the sense §5 means: it
  introduces no new contract, no new cross-layer boundary, and is fully
  reversible/replaceable without affecting any other layer. Comparable
  in kind to `DesignTokens` (`WP 10.2A`) and `IconRegistry` (`WP 10.0B`),
  neither of which received an ADR either.
- **Four new controls** (`ToastHost`/`BusyOverlay`/`ConfirmationDialog`/
  `EmptyStateView`) — ordinary, additive `Tempest.Desktop` classes, the
  same category as `RibbonView`/`ObjectEditorView`/`DigitalThreadGraphView`
  in every prior recent Work Package, none of which received an ADR for
  their own introduction either.
- **`TD-39`/`TD-40` closures** — bug fixes against already-disclosed,
  already-registered debt items, not new decisions.

No genuine architectural requirement — a new Tempest.Core contract, a
new cross-layer boundary, or a reversal of an existing ADR — was
discovered during implementation. This assessment is independently
reached, not merely copied from the Implementation Report's own claim.

## 2. Document Tab vs. Dock Slot — Not Revisited, Correctly

`WP 10.4A`'s own decision (Digital Thread graph as a Document tab, not
a new dock slot) is unchanged and unrevisited here — this Work Package
touched `DigitalThreadGraphView` only for its own hardcoded-colour
regression, never its own tab-vs-panel architecture. Confirmed no
scope creep into re-litigating an already-settled prior decision.

## 3. `ThemeReactiveBrush` as a New Shared Primitive — Assessed Sound

Rather than repeating the `Application.Current.TryGetResource` +
`AttachedToVisualTree`/`ActualThemeVariantChanged` pattern at each of
the (eventually eight) call sites, it was factored into one shared,
internal helper immediately after the second genuine failure (§4 of the
Engineering Review) — assessed as the correct level of abstraction:
small enough to stay a static helper (no DI registration, no new
Platform Service), general enough that every future theme-reactive
control can reuse it without rediscovering the same two findings.

## 4. `SeverityColors` as a Fourth Colour-Language Mapping — Assessed Consistent, Not Redundant

`HealthColors` (Engineering health), `CategoryColors` (relationship
category, `WP 10.4A`), `LifecycleColors` (lifecycle state, `WP 10.4A`),
and now `SeverityColors` (general UI feedback severity) are four
genuinely distinct classifications, confirmed by direct comparison of
each one's own enum — no overlap, no redundant reimplementation of an
existing mapping under a new name. `ObjectEditorView`'s own reuse of
`LifecycleColors` (rather than inventing a fifth, ad hoc status colour
scheme) is assessed as the correct, consistency-preserving choice.

## 5. `IWorkspaceView`/`IWorkspacePanel` Untouched — Independently Confirmed

`DocumentAreaView.IsMarkedDirty` reads this class's own already-private
`_extraDirtyFlags` field — no contract member added, no interface
touched. `EmptyStateView` is a plain `UserControl`, never registered as
an `IWorkspacePanel`. Both re-confirmed by direct read.

## 6. Recommendation

**Accept.** The explicit "document via ADR, do not silently implement"
condition this instruction names was correctly evaluated and correctly
found not to apply — every real decision this Work Package made is
Desktop-local, additive, reversible, and consistent with this
platform's own established pattern for introducing new presentation-
layer infrastructure without an ADR.
