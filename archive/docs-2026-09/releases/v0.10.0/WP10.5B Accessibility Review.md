# WP 10.5B — Accessibility Review

## Purpose

This platform's own second dedicated Accessibility Review (`WP 10.5A`
was the first) — assesses keyboard navigation, focus, and window/
scaling behaviour for every new `WP 10.5B` surface, disclosing what was
verified directly versus what remains inherited/unverified.

## 1. Keyboard Navigation — Verified for Every New Dialog

`InputDialog` (Enter confirms, Escape cancels — real `KeyDown`
handling, confirmed by test), `MessageDialog`/`SettingsDialog`/
`ConfirmationDialog` all use ordinary `Button` controls reachable via
Tab and activatable via Enter/Space through Avalonia's own default
handling, unmodified. No new custom input handler bypasses standard
keyboard reachability anywhere in this Work Package's own new code.

## 2. Focus on Dialog Open — Real, Verified for `InputDialog`

`InputDialog.PromptAsync` calls `_input.Focus()` and `_input.SelectAll()`
— a user can start typing immediately without an extra Tab press, and
existing text (a Rename-style pre-filled value) is pre-selected for
easy full replacement. `MessageDialog`/`ConfirmationDialog`/
`SettingsDialog` do not explicitly move focus on open — disclosed
directly as a real, minor gap: Avalonia's own default tab order still
makes every control reachable, but the first Tab press is required
before any control is focused, one keystroke more than `InputDialog`'s
own explicit focus.

## 3. Multi-Monitor / Window Restoration — Honestly Re-Scoped From `WP 10.5A`'s Own Disclosure

`WP10.5A Accessibility Review.md` §6 disclosed no physical High-DPI/
multi-monitor rig exists in this environment. This Work Package closes
part of that gap for window *position* specifically:
`WindowUiState.ClampToVisibleScreen` is real, tested code (not merely
inherited trust) — verified directly against a real, constructed
`Window` (headless `Screens` reports empty, exercising the graceful
"no screen info available, leave unchanged" fallback path; the
in-bounds/out-of-bounds branch logic itself is verified by direct code
reading, not a live multi-monitor render, since no such render is
possible in this environment). High-DPI *rendering* itself remains the
identical inherited, unverified trust boundary `WP 10.5A` already
disclosed — unchanged by this Work Package.

## 4. Delete Confirmation — a Real Accessibility/Safety Win

A destructive action (Delete) that previously executed on a single
click/keypress with zero confirmation now requires a second, deliberate
action — a genuine improvement for any user prone to mis-clicks or
mis-keys (a real accessibility concern, not only a UX one), independent
of `UserSettings.ConfirmBeforeDelete`'s own default (`true`).

## 5. Colour Contrast — No New Colours Introduced

Every new dialog reuses `SeverityColors`/`ApplicationPalette` exactly
as already reviewed and disclosed in `WP10.5A Accessibility Review.md`
§4 — no new colour value was added this Work Package, so no new
contrast pairing needs independent re-assessment.

## 6. Colour Is Never the Only Signal — Verified Directly

`MessageDialog`'s own severity glyph (`SeverityColors.Glyph`) is always
paired with its own colour and the dialog's own title/message text —
re-confirmed directly, no colour-only indicator was introduced.

## 7. Recommendation

**Accept**, with §2's own minor, disclosed focus-on-open gap
(`MessageDialog`/`ConfirmationDialog`/`SettingsDialog`) and §3's own
continued High-DPI-rendering trust boundary named directly as real,
low-severity, honestly-disclosed limitations, not defects blocking
acceptance.
