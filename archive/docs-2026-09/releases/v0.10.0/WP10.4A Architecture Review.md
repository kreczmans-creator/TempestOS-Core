# WP 10.4A — Architecture Review

## Purpose

An independent assessment of `WP 10.4A`'s own architectural decisions
— where this Work Package chose one design over a plausible
alternative, is that choice sound, and does it honour every frozen
contract and every prior ADR it touches.

## 1. `IWorkspaceView`, Not a New `IWorkspacePanel` — Assessed Sound

`WP10.0A Digital Thread & Relationship Visualisation.md` §3 itself
describes the graph as "two independently dockable panels" alongside
the Property Inspector — architecture-stage language, written before
`WP 10.2B`'s own concrete `DockingGrid` fixed the platform at exactly
three physical dock slots (Left/Right/Bottom), all already occupied.
Adding a fourth slot is a real, if modest, Workspace docking change —
squarely inside this Work Package's own "No Workspace redesign"
constraint. Implementing `IWorkspaceView` directly instead — a Document
Area tab, exactly like every discipline's own object view — reuses
100% already-built tab infrastructure (open/focus/dedupe/close) with
zero docking-framework change. Assessed as the correct reconciliation
of an earlier architecture document against a later, more restrictive
instruction, not a silent scope reduction — disclosed directly in the
Implementation Report §3.

**One direct consequence, handled correctly**: since
`DigitalThreadGraphView` is simultaneously its own `IWorkspaceView` and
its own rendered `Control` — unlike every other Kind, where
`ObjectEditorView.TryCreate(view.ObjectId, view.ObjectKind, ...)` builds
content *from* the view — `MainWindow.BuildDocumentContent` needed
exactly one new, generic first branch (`if (view is Control
alreadyBuilt) return alreadyBuilt;`). This is assessed as the right
level of genericity: it does not special-case the Digital Thread graph
by name, so any future self-rendering `IWorkspaceView` gets the
identical treatment for free.

## 2. Bidirectional `RelationshipRepository` Reads Over `IEvidenceComposer` — Assessed Sound

Full comparison, independently re-derived:

| | `IEvidenceComposer`/`IEvidence` | Reused bidirectional pair |
|---|---|---|
| Direction | Outgoing only | Outgoing + incoming |
| Verification/Calculation enrichment | Present in shape, structurally empty in practice (`TD-30`) | N/A — handled separately, correctly, via `VerificationRecordReader` |
| Precedent | New to the Workspace/Desktop layer | Already proven, already tested (`ObjectEditorView`, `WP 10.3A`) |
| Per-discipline special-casing | None (generic) | None (generic) |
| `ADR-0093` wording fit | Names `GetEvidenceAsync` for Requirements specifically; other disciplines' own "composed read" in `WP10.0A`'s own table is discipline-specific (`CalculationRecordReader`/`VerificationRecordReader`/`EngineeringDomainContext` reads), not uniformly `GetEvidenceAsync` | Matches the *spirit* — "no new read is added for any discipline," generic over Kind — more faithfully than a Requirements-specific method reused platform-wide would |

Assessed as the better choice on every axis except literal-name
matching to `ADR-0093`'s own Requirements-specific example — and the
ADR's own broader "no new read... generic over Kind" principle is
better served by the choice made, not worse.

## 3. Per-Contract/Per-Layer Compatibility

`IWorkspaceView` — implemented, unmodified. `EngineeringDomainContext`
— consumed, unmodified. `IconRegistry`/`DesignTokens` — consumed,
unmodified. `HealthColors` — deliberately *not* reused for lifecycle
status (it is keyed on the coarser `EngineeringHealthStatus`); a new,
narrowly-scoped `LifecycleColors` was added instead, correctly avoiding
a type mismatch rather than forcing an ill-fitting reuse.

## 4. The `TD-32` Merge — Correct Layer

`VerificationRecordReader.GetResultHistoryAsync` is called from
`DigitalThreadGraphModel.LoadRelationships`, gated on
`target.Kind == "VerificationActivity"` — the identical Kind-keyed
generic dispatch principle `ADR-0067` already established, applied
here for the first time to *which extra read to run*, not merely
*which command handler to invoke*. Assessed as a correct, minimal,
precedented extension of an existing pattern, not a new one.

## 5. Layout Algorithms — Assessed Real, Not Decorative

All three (`Hierarchical`, `Engineering`, `ForceDirected`) operate on
the same `_nodeOrder`/`_edges` data with no UI dependency — genuinely
pure functions of graph structure, independently testable (Engineering
Review §5), not merely three different static arrangements presented
as if algorithmic.

## 6. Defect Fix — Correct Layer

The `JumpToBreadcrumb` fix (Implementation Report §8) was made in the
model, not papered over in the view — `BuildGraphAround`'s explicit
`pushCurrentCentreToBreadcrumb` parameter fixes the actual shared
method's own ambiguous contract, rather than having the View
conditionally clear the breadcrumb after calling a still-ambiguous
`Recentre`. Assessed as the architecturally correct fix location.

## 7. Recommendation

**Accept.** Both major, disclosed architectural decisions (Document tab
over new dock slot; bidirectional reads over `IEvidenceComposer`) are
independently assessed as sound, well-reasoned, and correctly weighed
against the instruction's own explicit constraints — not merely the
path of least resistance.
