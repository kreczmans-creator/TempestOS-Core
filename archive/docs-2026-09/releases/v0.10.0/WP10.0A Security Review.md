# WP 10.0A — Security Review

## Purpose

An independent security review of the `WP 10.0A` UX architecture
package — whether the graphical desktop paradigm shift (`ADR-0092`),
the graph-based Object Relationship View (`ADR-0093`), and every other
named capability preserve this platform's existing permission model,
and whether any genuinely new attack surface or data-exposure risk is
introduced at the architecture level. Architecture-only review — no
code exists yet for this Work Package to test directly; every finding
below is a design-level assessment, to be re-verified against real
code by the first implementation Work Package's own dedicated Security
Review, exactly as this project's own established pattern requires
(`WP 9.0A` onward, each real-discipline Work Package's own dedicated
review).

## 1. Scope Reviewed

The same nine documents `WP10.0A Engineering Review.md` §1 names, from
a security rather than correctness perspective.

## 2. Permission Model — Preserved, No Bypass Introduced

Every read this Work Package's own documents name is an *existing*
service method, already subject to whatever permission gate that
method already enforces (`ADR-0061` and each framework's own
permission-checking layer, unchanged). This review confirms, by
re-reading `WP10.0A UX Architecture Document.md` and its companions in
full, that no document proposes a new read path that bypasses an
existing gate:

- **Object Relationship View / graph expansion** (`ADR-0093`) calls the
  identical `GetEvidenceAsync`-shaped method a flat list would have
  called — expanding a node is not a new capability, only a repeated
  invocation of an already-gated read. A principal without permission
  to view a given object's relationships is denied identically whether
  the panel renders a list or a graph.
- **Command Palette** (`WP10.0A Interaction Specification.md` §2)
  dispatches through the existing `ICommandDispatcher`, unchanged — the
  same authorization path every context-menu-invoked command already
  goes through. The Command Palette's own filtering (applicability by
  Kind/lifecycle state) is a *usability* filter, not a security
  boundary — this review confirms the documents never describe it as
  one, avoiding the mistake of presenting a UI-level filter as a
  substitute for the Command Framework's own actual authorization
  check.
- **Object Editors** (`WP10.0A UX Architecture Document.md` §8) commit
  only through existing Commands — a principal who can open an object's
  editor tab but lacks permission to invoke the relevant Rename/Revise/
  SetStatus command is rejected at dispatch time, identically to today.
  Presentation-local "dirty" draft state (§8) is held only in memory,
  never written to `ISettingsProvider` or any other persistence — this
  review confirms no document proposes persisting unsaved draft
  content, which would otherwise create a new at-rest data-exposure
  surface for content a principal never actually had permission to
  commit.

## 3. Finding: `TD-32`'s Own Consequences Now Extend to the Graph View

**Disclosed, not newly introduced by this Work Package.** `TD-32`
(`WP 9.3A`) recorded that `VerificationRecordReader` reads
`IEngineeringDocumentStore.GetReferencesAsync` directly rather than the
permission-gated `IVerificationService.GetVerificationHistoryAsync`, to
work around `RecordAsync`'s own raw-store-only linking. `WP10.0A
Digital Thread & Relationship Visualisation.md` §4 names
`VerificationRecordReader` as the Verification discipline's own
composed-read source for the new graph view — meaning a Verification
node expanded inside the Object Relationship View inherits `TD-32`'s
own already-disclosed ungated-read characteristic, at a new, more
visually prominent surface than the flat list it replaces. This is not
a new vulnerability this Work Package introduces; it is an existing,
already-registered one now reachable from one additional screen. **This
review recommends `TD-32`'s own disposition be reconsidered — not
necessarily fixed, but its own Technical Debt Register entry
cross-referenced from `WP10.0A Digital Thread & Relationship
Visualisation.md`** — when the first implementation Work Package for
this graph view begins, since the graph's own greater visibility raises
the practical cost of leaving it unaddressed, even though the
underlying data-correctness argument `TD-32` itself made (no
functional gap, only a permission-gate bypass) is unchanged.

## 4. Finding: Multi-Monitor Introduces a Genuine New Physical-Exposure Consideration

**Named here for the first time in this project's history.** A
single-window terminal application has one, bounded, physically
private display surface. A multi-monitor desktop application
(`WP10.0A UX Architecture Document.md` §15) can place a panel — an
Object Editor showing draft, unsaved engineering content; a Property
Inspector showing a Requirement's own sensitive statement — on a
secondary monitor that may be more visible to a shared or public space
than the primary. This is a **physical/procedural** security
consideration, not a code-level one, and this review does not treat it
as blocking this architecture-only Work Package. It is recorded here so
the eventual Contract Review Work Package (`ADR-0095`) inherits the
finding rather than rediscovering it: no panel-placement contract
extension should assume every monitor is equally trusted, and a future
implementation Work Package should consider whether a "always keep on
primary monitor" per-panel setting is worth naming as a real
requirement, not merely a nice-to-have.

## 5. Finding: Notification Framework Integration Is a Deferred, Named Risk

`WP10.0A UX Architecture Document.md` §10 explicitly defers concrete
`INotificationService` integration to a future implementation Work
Package. This review flags, for that future Work Package specifically:
a Notification tray that surfaces event content (e.g., "Requirement
REQ-0142 status changed to Approved") must apply the identical
permission gate the underlying object itself is subject to — a
notification is a second read path for the same data, and a naive
implementation could leak an object's existence or state to a principal
who could not otherwise see it. **Not a finding against this Work
Package's own content** (which names the requirement but explicitly
does not design the integration) — recorded so the eventual
implementation Work Package's own Security Review inherits this
question directly rather than starting from zero.

## 6. Finding: Theme/Iconography/Colour — No Security Implication

Reviewed and confirmed clean: `WP10.0A Visual Design System.md`
describes presentation-only concerns (colour, icon, density) with no
data-handling behaviour of their own. The one item worth naming
explicitly: §4's own "colour is never the only signal" accessibility
constraint is also, secondarily, a security-adjacent good practice
(an engineer who cannot distinguish `Released` from `Draft` by colour
alone, due to colour blindness or a monochrome secondary monitor per
§4 above, must not be led to make an incorrect trust decision about an
object's own approval state) — noted as a positive design choice, not
a finding requiring remediation.

## 7. Verdict

**No release-blocking or Work-Package-blocking security finding.**
Two genuine risks are surfaced for the first time (§3, an existing
debt item's exposure widening; §4, a new physical-exposure
consideration) and one integration point is flagged for the future
Work Package that will actually build it (§5) — none originates in
this Work Package's own content, and none requires this
architecture-only Work Package to change anything it has produced.
Recommended: cross-reference `TD-32` from `WP10.0A Digital Thread &
Relationship Visualisation.md` (§3, actionable now, documentation-only)
and carry §4/§5 forward into the relevant future Work Packages'
own controlling instructions.
