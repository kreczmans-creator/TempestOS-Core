# WP 10.0A — Screen Catalogue

## Purpose

Every screen and surface the next-generation Workspace presents,
catalogued with its own data sources (always an existing service or
contract, never a new one) and its own state variants. Expands
`WP10.0A UX Architecture Document.md`; mirrors and supersedes-in-effect
`WP8.0C Screen Catalogue.md`'s own pre-implementation catalogue, now
grounded in six real Engineering Disciplines instead of a plan for
zero.

## 1. Application Start-Up Experience

`Tempest.App` launches directly into the Workspace (`ADR-0068`,
unchanged) — no separate splash screen is specified; a graphical
desktop application's own OS-level window creation is the only
"start-up" surface, followed immediately by the Engineering Cockpit
(§2) as the default landing screen (`ADR-0069`, unchanged). If no
`Project` exists yet, the Cockpit renders its own genuine empty state
(§17), never a fabricated placeholder project.

## 2. Home Screen / Engineering Cockpit

Data source: `EngineeringCockpit` (`WP 8.1C`, extended through
`WP 9.5A`) — six disciplines' worth of real `CockpitKpiCard`/
`CockpitAttentionItem`/`CockpitActionItem` reads, `RecentProjects`,
`ContinueWhereILeftOff`. Presentation: a responsive KPI card grid
(§11, Visual Design System §4/§6), an Attention Items list, an Open
Actions list, a Recent Projects rail. **States:** populated (the
common case, six discipline cards plus overview); genuinely empty (no
`Project` exists — a real empty state, §17, not a mocked one); partial
(some disciplines have live data, others honestly show
`EngineeringHealthStatus.Unknown`, exactly as `EngineeringCockpit`'s
own XML documentation already discloses for a discipline with zero
live objects).

## 3. Workspace Shell (Main Window Layout)

Full detail: `WP10.0A UX Architecture Document.md` §3, `WP10.0A
Wireframe Sketches.md` §2. Five persistent regions (Command Bar,
Toolbar, Project Explorer, Document Area, Property Inspector/Object
Relationship View, Status Bar), plus the Notifications tray as a
transient overlay (§16). Data source: `WorkspaceShell`/
`IWorkspaceLayout`/`WorkspacePanelPlacement` (unchanged).

## 4. Project Explorer

Full detail: `WP10.0A UX Architecture Document.md` §5. Data source:
`ProjectExplorer` + six registered `IProjectExplorerNodeProvider`
implementations. **States:** populated tree (per-discipline category
nodes — Product Structure, Requirements Groups/Collections,
Calculations, Verification-by-Method, Documents-by-Classification,
Manufacturing-by-Category, mirroring each provider's own already-
implemented grouping); filtered (`FilterAsync`, live-narrowing as the
engineer types, §12 pointer, `WP10.0A Interaction Specification.md`
§3); empty per-category (a discipline with zero live objects shows its
own category node collapsed with a genuine "No items yet" leaf, never
hidden entirely — the category itself remains discoverable).

## 5. Docking / Panel Arrangement Behaviour

Full detail: `WP10.0A UX Architecture Document.md` §4. Data source:
`IWorkspaceLayout.PanelPlacements`. **States:** default layout
(`IWorkspaceLayout.ResetToDefault()`, unchanged); user-rearranged
(persisted, §13); panel collapsed (position retained, `IsVisible =
false`); panel resized (live `Size` update on drag, committed to
`ISettingsProvider` on release, mirroring `ADR-0064`'s existing
persistence path).

## 6. Property Inspector

Full detail: `WP10.0A UX Architecture Document.md` §6. Data source:
`IPropertyFacetProvider` for the selected object's own `Kind`. **States:**
populated (grouped facets: Identity/Lifecycle/Discipline-Specific/
Relationships); no selection (a genuine empty state, §17 — "Select an
object to inspect it," never a stale prior object's data left showing);
multi-selection (`ISelectionService.SelectedItems`, `WP 9.1A`) — shows
only facets common to every selected object's own `Kind`, or an
explicit "N objects selected, no common facets" state when the
selection spans incompatible Kinds — a genuinely new state this Work
Package names, since `WP8.0C`'s own pre-implementation catalogue
predates multi-selection (`ADR-0085`) entirely.

## 7. Object Relationship View

Full detail: `WP10.0A Digital Thread & Relationship Visualisation.md`.
Data source: `GetEvidenceAsync`/`GetRelationshipsAsync` (and each
sibling framework's own equivalent), composed progressively per
`ADR-0093`. **States:** single-object graph (the selected object as
centre node, one hop of direct relationships as edges); expanded graph
(two or more hops, built through repeated in-place expansion); no
relationships (a genuine empty state, §17 — an object with zero
`DocumentReference`/verification links, honestly shown, exactly as the
Documents discipline's own External Reference sample object already
demonstrates for the existing flat-list panel, `WP 9.4A`).

## 8. Command Palette

Full detail: `WP10.0A Interaction Specification.md` §2. Data source:
`ICommandRegistry.GetDescriptors()` (`ADR-0070`, unchanged — the
Command Palette's own status as "a first-class global entry point" is
reaffirmed, not redesigned). **States:** empty query (recently-used
commands, if any — a genuine "no recent commands yet" state on first
use); filtered query (fuzzy/substring match over `CommandDescriptor`
labels, categories); zero matches (an explicit "No matching commands"
state, never a silently empty list indistinguishable from "still
loading").

## 9. Object Editors

Full detail: `WP10.0A UX Architecture Document.md` §8. Data source: the
same `IWorkspaceView` each discipline already registers, rendered
editable. **States:** clean (matches last-committed read); dirty
(presentation-local draft differs, dirty-state tab indicator, §10);
invalid (a field fails discipline-specific validation before a Command
is even dispatched — presentation-local, never a fabricated service
error); command-rejected (the dispatched Command fails — an invalid
lifecycle transition, for instance — surfaced as an inline error, §19,
never a silent no-op, exactly as `WP8.0A Workspace Architecture
Document.md` §2 Journey 4 already requires).

## 10. Tabbed Document Area

Full detail: `WP10.0A UX Architecture Document.md` §9. Data source:
`WorkspaceStateDto.OpenViewIds`. **States:** single project (tabs in
open order, unchanged from `WP8.0A`); multi-project (tabs grouped by
owning `Project`, §14 in the master document); overflow (tab strip
exceeds available width — a real state this Work Package names for the
first time, §9 in the master document).

## 11. Status Bar

Full detail: `WP10.0A UX Architecture Document.md` §11. Data source:
`WorkspaceStatusBar` (current selection, lifecycle status,
`IDiagnosticsProvider`). Unchanged data; segmented graphical
presentation only.

## 12. Toolbar

Full detail: `WP10.0A UX Architecture Document.md` §11. Data source:
`ICommandRegistry`, filtered to whatever inclusion mechanism a future
implementation Work Package defines (§17, deferred). Deliberately
minimal — named here so it is not silently assumed to duplicate the
Command Palette's own full command surface.

## 13. Search

Full detail: `WP10.0A Interaction Specification.md` §3. Data source:
`ProjectExplorer.FilterAsync` (Project Explorer scope) and
`ICommandRegistry.GetDescriptors()` (Command Palette scope) — the same
two existing mechanisms, presented consistently. **No new search
service is introduced anywhere in this catalogue.**

## 14. Context Menus

Full detail: `WP10.0A Interaction Specification.md` §4. Data source:
`ICommandRegistry`, filtered by the selected object's `Kind` and
current lifecycle state — unchanged from `WP8.0A UI Architecture.md`
§4.

## 15. Notifications

Full detail: `WP10.0A UX Architecture Document.md` §10. Data source:
the existing Notification Framework (`WP 6.2`), read-only, presentation
integration deferred (§17). **States:** empty tray; unread badge count;
transient toast (a new notification arriving while the Workspace is in
focus) — the toast/tray split is named here as a UX requirement; the
underlying delivery mechanism is unchanged and pre-existing.

## 16. Attention / Action Centre

Data source: `EngineeringCockpit.AttentionItems`/`OpenActions` (six
discipline entries plus base-platform entries, unchanged). Distinct
from Notifications (§15) — Attention Items are derived, computed
Cockpit state (e.g. "3 Requirements awaiting review"); Notifications
are discrete, timestamped events from the Notification Framework.
Conflating the two was a risk this Work Package explicitly disclaims,
naming the distinction here so no future implementation Work Package
merges them by accident.

## 17. Empty States

A genuine empty state — never a mocked placeholder — is required
wherever this catalogue names one above (§2, §4, §6, §7, §8, §15). The
governing principle, stated once here rather than per-screen: **an
empty state names what is missing and, where a Command exists to fill
it, offers that Command directly** (e.g., the Cockpit's own empty
state, no `Project` exists, offers "Create Project" if such a Command
is registered — never a generic "nothing here" message with no path
forward). This mirrors `EngineeringCockpit`'s own existing documented
discipline of honest, disclosed placeholder-vs-real distinction (its
own XML documentation, `WP 8.1C` onward), extended from a data-honesty
principle into a presentation-design one.

## 18. Loading States

Every read this catalogue names is already asynchronous
(`Task`/`Task<T>`-returning throughout `Tempest.Core`) — a loading
state is required wherever a read has not yet completed. **No
skeleton-screen or spinner design is fixed here** (an implementation-
phase visual choice); the requirement named is only that no screen ever
shows a stale or default-constructed value indistinguishable from real
data while a read is in flight — the same "never silently wrong"
discipline `FOUNDATION.md` requires of the platform generally, applied
to presentation loading states specifically for the first time.

## 19. Error Presentation

Three distinct error categories, named separately because each has a
different correct presentation, mirroring `WP8.0A Workspace
Architecture Document.md` §2 Journey 4's own existing "surfaced as a
command failure, not a silent no-op" principle, generalised:

1. **Command rejection** (an invalid lifecycle transition, a failed
   validation rule) — an inline, contextual error at the point of the
   failed action (a field, a button), never a modal interrupting the
   entire Workspace.
2. **Read failure** (a service call throws — a permission gate denies
   access, `ADR-0061`, or a genuine platform fault) — an inline error
   in the specific panel that attempted the read; every *other* panel
   remains functional, mirroring `FOUNDATION.md`'s own module/
   platform-service failure-isolation principle applied to presentation
   panels for the first time.
3. **Platform-level fault** (the Runtime Host itself degrades) — the
   one case warranting a Workspace-wide banner, mirroring
   `IDiagnosticsProvider`'s own existing Host-lifecycle-state read,
   already surfaced in the Status Bar (§11) and now escalated
   visually when the state itself is degraded.

## 20. First-Run Experience

Identical to §1/§2's own empty-state path — no dedicated onboarding
flow is designed in this Work Package's own first iteration; a
genuinely empty Cockpit *is* the first-run experience, consistent with
`VISION.md`'s own "do not build ahead of a demonstrated need" principle
applied here: no evidence exists yet that a first-run population needs
more than an honest empty state with a clear path to "Create Project."
