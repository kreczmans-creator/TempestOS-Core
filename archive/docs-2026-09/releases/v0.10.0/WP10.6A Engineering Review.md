# WP 10.6A — Engineering Review

## Purpose

An independent technical review of `WP 10.6A`'s own real implementation
— re-verifying the Implementation Report's own central claims directly
against the running code, not merely trusting its own prose.

## 1. "Only `Tempest.Samples` Commands Are `CreateDefault`-Eligible" — Independently Re-Verified

Re-ran `grep -rn "createDefault:\|CreateDefault:" src --include=*.cs`
this review's own way, independently, excluding `obj/`/`bin/` build
output. Every match resolves to a file under `src/Samples/
Tempest.Samples/`, plus exactly one new match this Work Package itself
introduced — `src/Tempest.Core/Macros/MacroManager.cs`, which is the
macro-registration mechanism itself (each macro's own descriptor is
necessarily `CreateDefault`-eligible so it can be invoked by Id), not a
discipline command. Confirmed zero matches under any of the six real
Engineering discipline registration files
(`Mechanical`/`Requirements`/`Calculations`/`Documents`/`Verification`/
`ManufacturingWorkspaceRegistration.cs`). This is the load-bearing fact
`ADR-0099`'s own disclosed macro-step-eligibility limitation rests on
— independently re-derived, not assumed from the Implementation
Report's own claim.

## 2. Rename Undo/Redo — Independently Traced Through the Real Dispatch Path

Read `ObjectEditorView.OnSaveAsync`'s own diff directly: `oldName` is
captured from `_originalName` *before* `RenameObjectAsync` is awaited,
and `UndoableActionRecorded` is raised only after `result.Succeeded` is
confirmed true — a failed Rename never records a broken Undo entry.
Independently re-ran `ProductivityExperienceTests.
RenameObjectAsync_UndoAndRedo_ActuallyRenamesTheRealObjectBackAndForth`
in isolation (`dotnet test --filter`) against a fresh
`WorkspaceHost`/`InMemoryEngineeringObjectRepository` — confirmed
passing, and confirmed by direct read that the assertion checks the
real object's own `DisplayName` via `Repository.FindAsync` after each
of `UndoAsync`/`RedoAsync`, not a cached or assumed value.

## 3. `RunMacroCommandHandler`'s Own Stale-Descriptor Failure — Independently Reproduced

Read `MacroManager.DeleteAsync` directly: it removes the macro from
`_macrosById` but never touches `_registeredDescriptorIds` or calls any
`ICommandRegistry` removal method (there is none — confirmed by
independently re-reading `ICommandRegistry.cs` in full, finding no
unregister/remove member of any kind). Traced `RunMacroCommandHandler.
HandleAsync` directly: `_macroManager.FindAsync` correctly returns
`null` for a deleted macro's own Id, and the handler returns
`CommandResult.Failure` rather than letting a `NullReferenceException`
propagate. `MacroManagerTests.
DeleteAsync_RemovesFromListAsync_ButLeavesTheStaleDescriptorFailingGracefully`
re-run in isolation, confirmed passing, confirmed asserting exactly
this behaviour (not merely "does not throw").

## 4. `InputBindingRouter`'s Own Isolation — Independently Reproduced

Read `InputBindingRouter.RouteAsync` directly: wrapped in a full
`try`/`catch (Exception ex)`, logging and returning rather than
rethrowing — confirmed this covers both a bad Command Id (`InvokeAsync`
throwing `CommandNotFoundException`) and a handler that itself throws.
`InputBindingRouterTests.
ARequestForAnUnknownCommandId_IsIsolated_NeverThrowsBackIntoTheProvider`
re-run in isolation, confirmed passing — `Record.Exception` around the
synchronous `SimulatePress` call correctly returns `null`, confirming
the exception truly never reaches the calling provider's own code
(the async `RouteAsync` itself running detached, `async void`, is the
one place in this Work Package's own new code using that pattern —
independently confirmed deliberate and necessary: an event handler
cannot return a `Task` a caller could `await`, and the alternative,
blocking the raising provider's own thread until dispatch completes,
would defeat the entire "input source doesn't block on command
execution" design intent).

## 5. `MacroManagerDialog`'s Own Real Save Flow — Independently Traced

Read `MacroManagerDialog.SaveMacroAsync`/`AddStep` directly: `AddStep`
appends the selected `_availableDescriptors[...].Id` (a real
`CommandDescriptor.Id`, not a display label) to `_draftSteps`, and
`SaveMacroAsync` passes that exact list to `IMacroManager.CreateAsync`
— no transformation, no display-text parsing in between. Confirmed the
Available Commands list is rebuilt fresh from
`ICommandRegistry.Items.Where(d => d.CreateDefault is not null)` every
time `OpenEditor` runs, not cached from dialog construction — a macro
created after the dialog was first shown, adding a new eligible
command, would be picked up correctly (though no such scenario is
directly tested — a minor, disclosed test-coverage gap, not a
correctness defect: the code path is identical to the
already-tested initial-open case).

## 6. Thread-Safety — `MacroManager`/`InputBindingRouter`

Both use a private `lock (_gate)`/`object _gate` guard around their own
mutable state (`_macrosById`/`_registeredDescriptorIds` in
`MacroManager`; `_providers`/`_handlersByProvider` in
`InputBindingRouter`) — mirroring `CommandRegistry`'s own identical,
already-established locking discipline exactly. No new concurrency
primitive introduced; no `async` work happens while a lock is held in
either type (confirmed by direct read — `SaveAsync`/`InvokeAsync` calls
always occur outside the `lock` block).

## 7. Conclusion

Every independently re-verified claim in the Implementation Report held
up against the real code and a real, isolated test run: the
`CreateDefault`-eligibility limitation is real and total, Rename
Undo/Redo genuinely mutates and restores the real object, a deleted
macro's own stale descriptor genuinely fails gracefully rather than
throwing, and `InputBindingRouter`'s own isolation genuinely prevents a
bad request from reaching the raising provider. One minor, disclosed
test-coverage gap noted (§5) — not a correctness defect, not requiring
a Technical Debt entry.
