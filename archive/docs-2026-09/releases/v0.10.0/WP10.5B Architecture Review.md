# WP 10.5B — Architecture Review

## Purpose

Assesses `WP 10.5B`'s own architectural decisions — including this
instruction's own explicit requirement that any genuine architectural
finding be documented through an ADR rather than silently implemented
— and independently confirms whether that condition was actually met.

## 1. "No ADR Was Required" — Independently Assessed Correct

Every real decision this Work Package made was checked directly
against Engineering Governance §5's own ADR-creation criteria:

- **The Dialog Framework** (`InputDialog`/`MessageDialog`/`SettingsDialog`)
  — new, additive `Tempest.Desktop` classes, the identical category as
  `ConfirmationDialog`/`ToastHost`/`BusyOverlay`/`EmptyStateView`
  (`WP 10.5A`), none of which received an ADR.
- **`WindowUiState`/`UserSettings`** — new sibling classes to the
  already-established `DesktopPanelUiState`/`ThemeService` pattern
  (`ISettingsProvider`, one JSON blob per Settings key) — an
  application of an already-decided pattern a further time, not a new
  decision (mirrors `WP 10.4A`'s own identical "reusing an established
  pattern is not itself a new decision" reasoning).
- **`PlatformNotificationToastBridge`** — subscribes to the
  already-existing `IEventBus`/`IEventHandler<T>` mechanism (`WP 5.x`),
  introducing no new eventing infrastructure of its own.
- **The real Create/Duplicate dispatch** — reuses
  `ICommandDispatcher.DispatchAsync` directly, the platform's own
  already-established, unmodified mutation path (`ADR-0063`).

No genuine architectural requirement — a new `Tempest.Core` contract, a
new cross-layer boundary, or a reversal of an existing ADR — was
discovered during implementation.

## 2. Four Dialogs, No Shared Base Class — Assessed Correct

`ConfirmationDialog`/`InputDialog`/`MessageDialog`/`SettingsDialog`
share styling via tokens/resource keys, not inheritance. Re-examined
directly: each dialog's own layout is genuinely different enough
(one text field vs. title/message/OK vs. title/message/two-buttons vs.
a full preferences form) that a shared base class would need either a
lowest-common-denominator shape (losing real structure) or a complex
templated-content mechanism (new complexity for four call sites) —
assessed as correctly avoided; "a common framework with consistent
styling and behaviour" is satisfied by the shared tokens, not requiring
a shared type hierarchy.

## 3. `ObjectCreationHandlers` as a Generic `Id → Func<Task>` Map — Assessed Sound

Rather than special-casing `"mechanical.create"`/`"mechanical.duplicate"`
directly inside `RibbonView.OnCommandButtonClickAsync`, the dispatch
was factored into an externally-populated dictionary — assessed as the
correct level of indirection: `RibbonView` itself needs zero per-
discipline knowledge (mirrors its own established "one generic engine"
principle, `WP 10.3B`), and `MainWindow` (which already owns
`InputDialog`/`ConfirmationDialog`/`ICommandDispatcher`) is the correct
layer to own the actual per-command flow.

## 4. The Soft-Delete Test Fix — Correct Layer

The fix (§10 of the Implementation Report) corrected the *test's own
assertion*, not the production `IDeletable.DeleteAsync` — independently
assessed as the right call: the production soft-delete behaviour is
correct, intentional, audit-preserving design, unrelated to this Work
Package's own scope; the test's own incorrect assumption was the actual
defect.

## 5. `MainWindow.Closing`'s Own Async Pattern — Assessed Correct

The "cancel synchronously, do the real work, close programmatically"
pattern is independently verified as the textbook-correct approach for
an async operation gating a synchronous, non-awaitable event — Avalonia
does not await `Closing`'s own handler, so any path that does not
synchronously set `e.Cancel = true` before its first `await` would let
the close proceed before the save/confirmation completes. Re-read the
implementation directly: every code path sets `Cancel = true`
unconditionally first, confirmed correct.

## 6. Recommendation

**Accept.** The explicit "document via ADR, do not silently implement"
condition was correctly evaluated and correctly found not to apply;
every real design decision (no shared dialog base class, a generic
handler map, reusing the existing `ISettingsProvider`/`IEventBus`
patterns) is independently assessed as sound and consistent with this
platform's own established conventions.
