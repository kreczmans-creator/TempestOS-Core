# WP 10.1B — Runtime Host & Module Discovery Hardening — Implementation Report

## Purpose

The complete implementation record for `WP 10.1B` — investigating and
resolving `TD-26` and `TD-37`, hardening the Runtime Host/Module
Discovery/Lifecycle/Dependency Injection/Sample Module/Diagnostics
pipeline, and guaranteeing deterministic discovery, registration, and
initialisation with no duplicate registrations, correct module
isolation, and stable startup/shutdown/restart. Root-cause investigation
is recorded separately and in full: `WP10.1B Root Cause Analysis.md` —
read it first; every fix below follows directly from a finding recorded
there.

## 1. `TD-26` Fixed at Its Own Source

`src/Tempest.App/Workspace/WorkspaceManager.cs`'s own `WaitForServicesAsync`
now waits for two conditions, not one:

1. `ITempestHost.Services` is resolvable (unchanged, the original check).
2. `IDiagnosticsProvider.HostState == HostState.Running` — the Runtime
   Host's own authoritative "every module has finished
   `InitialiseAsync`/`StartAsync`" signal, resolved through the newly-
   available `Services` from step 1.

A `ThrowIfHostRunFaulted()` guard prevents an infinite wait if the
Runtime Host faults before ever reaching `Running` (a critical hosted
service failure, `ADR-0021`/`ADR-0029`) — the fault is observed via the
same `Task` `StartAsync` already holds a reference to
(`_hostRunTask`) and rethrown immediately, rather than spinning forever
waiting for a state transition that will now never happen.

**Consequence:** every `IWorkspaceManager.StartAsync` caller — console,
desktop, or any future presentation layer — now receives the same
"platform is genuinely, fully ready" guarantee without its own
workaround. `Tempest.Desktop`'s own now-redundant mitigation
(`WorkspaceHost.WaitForHostRunningAsync`, introduced `WP 10.0B`,
strengthened `WP 10.1A`) was removed outright, not kept as
defence-in-depth — a second, independent "is it really ready" check one
layer up would silently mask any future regression at the true source,
which is precisely the class of gap this Work Package exists to close.

## 2. `TD-37` Fixed — Idempotent Sample-Module Seeding

Each of the four affected modules
(`src/Samples/Tempest.Samples/MaterialsSampleModule.cs`,
`EngineeringDomainSampleModule.cs`, `RequirementsSampleModule.cs`,
`RequirementsWorkspaceSampleModule.cs`) now checks, at the very start of
its own `InitialiseAsync`, whether its own fixed literal identifier is
already durably registered (`IMaterialCatalog.FindAsync`/
`IRequirementsService.FindByIdentifierAsync`) — the same durable signal
`WP10.1B Root Cause Analysis.md` §2.2 identified as the true collision
point. If already present, the module treats it as its own prior work,
not a collision:

| Module | On collision, skips | Still (re-)registers |
|---|---|---|
| `MaterialsSampleModule` | Register + revise | Both commands |
| `EngineeringDomainSampleModule` | The entire sixteen-object graph (not just the Material step — see `WP10.1B Root Cause Analysis.md` §2.3 for why partial duplication would otherwise continue) | The graph-summary command |
| `RequirementsSampleModule` | Create/revise/status/group/collection/allocate/verify | Commands, report definition, export adapter |
| `RequirementsWorkspaceSampleModule` | The entire ten-Requirement, four-Group sequence | *(nothing further this module registers outside the sequence)* |

Commands, report definitions, and export adapters are always
(re-)registered on every launch regardless of which branch ran — all
three are in-memory only (`ICommandRegistry`/`IReportingService`/
`ImportService`) and never survive a restart on their own, unlike the
durably-persisted domain data they operate over.

**Disclosed, honest trade-off:** on the idempotent-skip branch, a
module's own `Sample*Id`/`AllSample*Ids` properties are left at their
unset defaults (`null`/empty) rather than fabricated or recovered — no
lookup-by-business-identifier capability exists on
`IEngineeringObjectRepository` to recover an earlier run's own object
Ids (see `WP10.1B Root Cause Analysis.md` §2.3), and
`RequirementsSampleModule`'s own `SampleGroupId`/`SampleCollectionId`
have no equivalent `FindByNameAsync` to recover either. Nothing in
`Tempest.App`/`Tempest.Desktop` depends on these properties being
populated on a restart — confirmed by direct search (only
`GetSampleEngineeringDomainGraphSummaryCommandHandler` and this Work
Package's own new tests read them, and the former already, correctly,
reports "not finished initialising" rather than fabricating a count
when they are unset).

## 3. Test Isolation — `Tempest.Desktop.Tests`

`WorkspaceHost` gained an optional constructor parameter,
`persistenceRootPathOverride` (default `null`, leaving the real
application's own behaviour completely unchanged), and
`EngineeringWorkspaceComposer.Build` gained an optional
`configurationSources` parameter for the same reason — both additive,
both defaulted, neither touched by the console entry point
(`src/Tempest.App/Program.cs`) or the real `Tempest.Desktop.App`.

`WorkspacePersistenceCollection.NewIsolatedPersistenceRootPath()`
(`tests/Tempest.Desktop.Tests/WorkspacePersistenceCollection.cs`) returns
a fresh, `Guid`-suffixed temporary directory. Every `new WorkspaceHost()`
call site in the assembly (17 call sites across four existing test
files) now passes a path from this method — one fresh call per
independent test, except the two tests that deliberately construct two
sequential hosts to prove cross-restart session persistence (`ADR-0064`,
`TD-35`), which call it once and share the result between both hosts,
exactly mirroring `Tempest.Core.Tests`' own `TempDirectory`-per-test
pattern, established since `WP 7.3A`, only now extended to this second
test assembly.

## 4. `EngineeringCockpitTests` — From Honest-Empty to Real, Stable Data

`WP 10.1A`'s own three `TD-37`-affected assertions
(`RiskSummary`/`UpcomingMilestones`/`OpenTaskCount`) were rewritten from
asserting the disclosed honest-empty state to asserting the real,
now-stably-seeded sample data — the direct, concrete demonstration of
this Work Package's own "Ensure all Cockpit cards receive stable live
data after successful module initialisation" requirement:

| Member | `WP 10.1A` assertion | `WP 10.1B` assertion |
|---|---|---|
| `RiskSummary` | `"0 open (no live Risk/Hazard recorded yet)."` | `"1 open — 1 Medium."` |
| `UpcomingMilestones` | `Empty` | Contains `"Sample Milestone"` |
| `OpenTaskCount` | `0` | `1` |

No change was made to `EngineeringCockpit.cs` itself — every one of
these three members was already correctly implemented, `WP 10.1A`;
their own honest-empty output was always a faithful reflection of a
platform-level defect one layer below them, exactly as `WP 10.1A`'s own
disclosure said. Fixing the defect, not the Cockpit, is what changed
their output.
