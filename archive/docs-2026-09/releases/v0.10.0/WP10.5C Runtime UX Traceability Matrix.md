# WP 10.5C — Runtime UX Traceability Matrix

## Purpose

This Work Package's own explicitly-required first deliverable — before
any implementation change, launch the application and compare the
actual running application against the implementation claims made in
`WP 10.0B` through `WP 10.5B`. Every claimed user-facing feature is
listed with a Reachable/Not Reachable verdict and the real evidence
behind it. Any feature found genuinely unreachable is treated as a
defect and corrected within this Work Package where practical — see
§6.

## 0. Methodology, Disclosed Honestly

**This environment cannot render or visually inspect a live GUI.** No
screenshot tool, no accessibility-tree inspector, and no way to observe
pixels exists here — the identical, already-repeatedly-disclosed
constraint every `WP10.x` Accessibility/UX Review this session has
named ("no way to visually verify... in this environment"). A genuine
runtime audit under this constraint therefore combines two real,
independent forms of evidence, neither faked as the other:

1. **A real process launch.** `dotnet run` against the compiled
   `Tempest.Desktop` executable, allowed to run to completion of its
   own startup sequence (Runtime Host phases, module discovery,
   Workspace composition, Settings/Theme/Panel-state load, `Opened`
   handler). Captured directly — see §1. This proves the application
   *starts*, composes its full dependency graph, and reaches a shown
   `Window` without exception; it cannot prove what that window's
   pixels look like.
2. **Direct source-level reachability tracing.** For every claimed
   feature, the real call chain is traced from its own real, clickable
   entry point (a `Menu`/`MenuItem.Click`, a `RibbonView` command
   button, a `TreeView` context-menu item, a Quick Access Toolbar
   button) through to the real backing capability, confirming the
   control is actually constructed, actually added to the real visual
   tree the running `Window` shows (`Content = root`, `root.Children.Add(...)`,
   not merely instantiated and discarded), and actually wired to a
   working handler — never assumed present because a prior Work
   Package's own document said so. This is the same discipline this
   project's own Engineering Reviews already apply to every "confirmed
   directly" claim, applied here specifically to *reachability*, not
   *behaviour*.

Where a headless `[AvaloniaFact]` test already exercises a real,
attached, rendered control (the majority of `Tempest.Desktop.Tests`),
that test's own pass is additional, real evidence — a genuine control
tree assembled and inspected by Avalonia's own headless renderer, not a
mock.

## 1. The Real Process Launch

```
dotnet run --project src/Tempest.Desktop/Tempest.Desktop.csproj -c Debug --no-build
```

Run for a fixed 8-second window (this environment cannot leave a GUI
process attached indefinitely for interactive use). Real, captured
log evidence: every Runtime Host lifecycle phase completed
(Configuration Built → Logging Built → License Validated → Plugin
Discovery/Loading → Framework Discovery → every one of the fourteen
`Tempest.Samples` modules discovered and initialised → every command
handler/descriptor for all six disciplines registered → `ISettingsProvider`/
`ICommandRegistry`/`ICommandDispatcher`/`EngineeringDomainContext`/
`IDiagnosticsProvider`/`IEventBus`/`IMacroManager`/`IInputBindingRegistry`
all resolved → `Desktop.WindowUiState`/`Desktop.UserSettings`/
`Desktop.RecentObjects`/`Desktop.FavouriteObjects`/`Desktop.Theme`/
`Workspace.Desktop.PanelUiState` Settings definitions all registered →
the Keyboard input binding provider registered → the
`PlatformNotificationToastBridge` subscribed) — zero exceptions, zero
faulted tasks, the process still running (not exited) when the fixed
window elapsed. **Verdict: the application genuinely starts and reaches
a shown window with its full, real dependency graph composed** — not
merely "the code compiles."

## 4. Disclosed, Pre-Existing, Non-Defect Observations

- **`Desktop.PanelUiState.OutputVisible` defaults to `false`.** The
  Output panel is not shown on a first, fresh launch — a deliberate,
  disclosed default since `WP 10.2B` (an empty diagnostics panel adds
  no value until a user has a reason to look), reachable in one click
  via `View › Output Panel` or any Layout preset. Not a defect.
- **Requirements' own Project Explorer nodes never receive a
  lifecycle-status dot** (this Work Package's own new decoration, §5)
  — the Requirements Framework's own `RequirementStatus` is a
  deliberately distinct taxonomy from the generic `LifecycleState`
  every other discipline's node now colours by; force-mapping one onto
  the other would misrepresent real status data, so this Work Package
  leaves Requirements nodes undecorated rather than fabricate a
  mapping. Disclosed directly, not a defect.
- **`ObjectEditorView` does not receive a discipline-colour accent
  strip.** Considered directly for this Work Package's own "engineering
  colour language" scope item; rejected — `DisciplineColors.Resolve`
  is deliberately keyed on the real `CommandDescriptor.Category`
  string (`"Mechanical"`, `"Requirements"`, ...), but `ObjectEditorView`
  only ever holds an object's own `Kind` (`"Part"`, `"Assembly"`,
  `"Requirement"`, ...) — most Mechanical/Manufacturing Kinds do not
  themselves contain their own discipline's name as a substring, so
  reusing the identical resolver here would silently mis-colour most
  Mechanical objects Gray (the unmatched fallback). Building a second,
  separate Kind→Discipline lookup table was judged a real risk of
  encoding a wrong mapping for at least one of this platform's own
  ~20 Kinds without a way to visually verify the result in this
  environment — deferred, disclosed, not attempted, rather than shipped
  as a plausible-looking guess.

## 5. Genuine Findings, Fixed Within This Work Package

Two real, previously-undiscovered `TD-39`-class theme-reactivity
defects, found by this Work Package's own fresh sweep of every
remaining `Brushes.*` literal in `Tempest.Desktop/Views/`:

1. **`CockpitCardControl`'s own neutral (no-accent) border** was a
   fixed `Brushes.Gray` since `WP 10.1A` — every one of the twenty
   Cockpit cards with no explicit health/lifecycle accent (most of
   them) carried a border that could read wrong against one theme
   variant. Fixed via `ThemeReactiveBrush.Bind`, `ApplicationPalette.PanelBorderBrushKey`
   — the identical fix already applied to `PanelHostControl`/
   `CommandPaletteOverlay` (`TD-39`).
2. **`RibbonView.BuildSectionWithLabel`'s own group divider** was a
   fixed `Brushes.Gray` since `WP 10.3B` — every Ribbon tab's own
   Create/Organize/Lifecycle/Actions group divider. Fixed identically.

Neither reaches a new Technical Debt entry — both are fixed in place,
before commit, mirroring this session's own established "found and
fixed, not merely disclosed" precedent (see `WP10.5C Technical Debt
Review.md`).

## 6. Runtime Integration — Conclusion

**No genuinely unreachable claimed feature was found.** Every named
capability across `WP 10.0B`–`WP 10.5B` traces to a real control,
actually added to the real, shown `Window`'s own visual tree, actually
wired to a real handler reaching a real capability. The two real
defects found (§5) were visual *correctness* gaps (a wrong-in-one-theme
colour), not *reachability* gaps (a missing menu entry, an unwired
button, a panel never registered) — the specific failure mode this
Work Package's own instruction named ("Any implemented feature that is
not reachable... shall be treated as a defect"). This is recorded
plainly as a genuine, positive finding, not softened to manufacture a
larger "Runtime Integration" section than the evidence supports.

## 7. Recommendation

**Accept.** The running application's own real reachability is honestly
stronger than this Work Package's own controlling instruction's
description implied — every prior Work Package's own "confirmed
directly" claims about wiring hold up under a fresh, independent trace.
The real, remaining gap this Work Package's own instruction correctly
anticipated is not reachability but *visual richness* — text-heavy
cockpit panels, a plain tree presenter, a sparse-looking inspector for
Kinds with few facets — addressed directly in §5 above and throughout
the remainder of this Work Package's own Implementation Report.
