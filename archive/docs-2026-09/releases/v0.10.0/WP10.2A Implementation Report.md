# WP 10.2A — Workspace Modernisation — Implementation Report

## Purpose

The complete implementation record for `WP 10.2A` — transforming
`Tempest.Desktop`'s own working-but-minimal `WP 10.0B`/`WP 10.1A` UI into
a modern, professional engineering application shell, while preserving
every existing Engineering capability unchanged.

## 0. Scope Discipline

- **No Engineering Domain redesign** — zero files touched under
  `src/Tempest.Core/EngineeringDomain/`.
- **No Runtime redesign** — zero files touched under
  `src/Tempest.Core/Runtime/`, `Modules/`, or `Diagnostics/`.
- **No Workspace contract redesign unless genuinely required** — one
  genuine, disclosed exception: `IWorkspaceManager` gained five new,
  additive members (`ADR-0096`) to realise real object Rename/Delete
  dispatch — see §1, below, for the full justification. Every other
  Workspace contract (`IWorkspace`, `IProjectExplorer`,
  `IPropertyInspector`, `IWorkspaceView`, `IWorkspaceLayout`, etc.) is
  unchanged.
- **Not implemented, by explicit instruction**: floating windows, a
  docking framework beyond the existing five-column `DockingGrid`
  (`WP 10.0B`, unchanged), multi-monitor support, a ribbon, the Digital
  Thread graph. None were attempted.

## 1. The Real Gap This Work Package Found and Closed

Reading every discipline's own composition-root registration file
directly (`MechanicalWorkspaceRegistration.cs` and its five siblings)
surfaced a genuine, pre-existing, disclosed-since-`WP 9.0A` platform
gap: every discipline already had a real, tested, `IWorkspaceCommand`
-shaped `Rename*Command`/`Delete*Command` pair, registered against
`ICommandDispatcher` — but **no interactive surface, console or
desktop, had ever dispatched one against an arbitrary selected
object**. `MechanicalWorkspaceRegistration`'s own `WP 9.0A` remarks say
so explicitly: `createDefault` is deliberately omitted from every such
descriptor, "dispatched with real data... by a caller that already has
it (**a future context-menu action**)." This Work Package's own
"inline rename"/"editable controls where appropriate" requirements are
exactly that caller.

**`ADR-0096`** records the fix: `IWorkspaceManager` gains
`RegisterRenameFactory`/`RegisterDeleteFactory`/`CanRename`/`CanDelete`/
`RenameObjectAsync`/`DeleteObjectAsync` — additive only, mirroring
`RegisterFacetProvider`'s own `ADR-0082` shape and precedent exactly.
Dispatch reuses the existing, unmodified `CommandHandlerTable.DispatchAsync(ICommand, ...)`
primitive — the same runtime-type-keyed lookup `ICommandRegistry.InvokeAsync`
already uses internally. No new command class was written: every
factory constructs a command type that already compiled, was already
tested, and already had a registered handler before this Work Package.

All six discipline registration classes were updated to register their
own real Rename/Delete factories. Two disciplines are honestly
incomplete, disclosed, not fabricated: Requirements' three Kinds
(Requirement/RequirementGroup/RequirementCollection) register Delete
only — no `Rename*Command` exists for this discipline (a Requirement's
own mutable field is its `Statement`, mutated via
`ReviseRequirementCommand`, not an `IRenamable`/`DisplayName` concept);
Calculations' synthetic `"CalculationTemplate"` Kind registers neither
— it is never an `EngineeringDomainContext.Repository` object, so both
handlers would always fail against it.

## 2. Project Explorer

`ProjectExplorerView` (`src/Tempest.Desktop/Views/ProjectExplorerView.cs`)
rewritten:

| Requirement | Implementation |
|---|---|
| Professional tree presentation | Existing icon+text `TreeView`, now themed via `DesignTokens` |
| Expand/collapse | `TreeView`'s own built-in behaviour, unchanged |
| Engineering icons | `IconRegistry` (`WP 10.0B`), unchanged, reused |
| Context menus | Real: Open/Rename/Delete, each dispatching through `ADR-0096`; `Rename`/`Delete` honestly disabled (`IsEnabled = manager.CanRename/CanDelete(kind)`) when no factory is registered |
| Multi-select | `TreeView.SelectionMode = SelectionMode.Multiple` |
| Inline rename | `F2` or context menu swaps the selected node's own label for a real `TextBox`; `Enter`/focus-loss commits via `RenameObjectAsync`, `Escape` cancels |
| Drag/drop preparation architecture | Real drag begins with real `(Id)` payload; `DragOver` gives real Move-cursor feedback only over a genuine Object node; `Drop` is a documented, deliberate no-op — see §6 (Trade-offs) |
| Filtering | A `TextBox` filters the already-loaded tree client-side (title substring match, ancestors of a matching descendant kept visible) — no re-query, so this stays responsive regardless of `IProjectExplorer` latency |
| Breadcrumbs | A clickable path bar, derived from each node's own new `Parent` back-reference, tracking the current selection |
| Selection highlighting | `TreeView`'s own built-in selection visuals (Fluent theme), unchanged |

## 3. Property Inspector

`PropertyInspectorView` rewritten around real `Avalonia.Controls.Expander`
sections, one per `PropertyFacetKind` group (Identity/Revision/
Provenance/DisciplineSpecific/Relationship, relabelled "Relationships" —
this Work Package's own real relationship summary), plus two new,
honestly-scoped sections:

- **Lifecycle summary**: no dedicated `PropertyFacetKind.Lifecycle`
  exists in this platform's own frozen facet taxonomy (`WP 9.0A`,
  unchanged) — a real, disclosed presentation-layer extraction instead:
  any already-present facet whose own `Name` contains `"Status"`/
  `"Lifecycle"` is pulled into its own distinguished section, never
  duplicated, never fabricated; honestly omitted when none exists for
  the selected Kind.
- **Validation summary**: an honest, disclosed placeholder — no
  per-object validation-result read exists anywhere in the Workspace
  layer today (`IValidationRuleSet`/`IReferenceIntegrityChecker`
  operate at Domain-object-graph scope, not a single selected object's
  own summary). Mirrors `EngineeringCockpit`'s own "disclose, never
  fabricate" discipline, applied to the Property Inspector for the
  first time.

**Genuine defect found and fixed during Engineering Review**: the
Lifecycle section's own first implementation identified status/lifecycle
-shaped facets correctly but never removed them from their own original
`PropertyFacetKind` group, so each appeared twice. Fixed before any
commit — `Refresh()` now excludes the extracted Lifecycle set from the
per-group loop (`Except`, via `PropertyFacet`'s own record equality) —
proven by a dedicated regression test walking the real rendered visual
tree (`WP10.2A Engineering Review.md` §3).

**Editable controls where appropriate**: the Identity group's own
`"Name"` facet becomes a real, working `TextBox` — committing on
`Enter`/focus-loss via `IWorkspaceManager.RenameObjectAsync` — only when
`CanRename` reports the selected Kind supports it; every other facet
remains read-only text, since no generic per-facet mutation capability
exists beyond rename, and this View never fabricates one.

## 4. Document Area

`DocumentAreaView` gained pinned tabs (📌 toggle button; pinned tabs
sort before unpinned ones, immediately after the permanent Home tab,
and lose their close glyph while pinned — the identical convention
every mainstream desktop tab strip follows) and active-tab highlighting
(the selected tab's own header text is bolded, beyond whatever the
Fluent theme already applies — never colour alone, matching this
platform's own Engineering Colour Language discipline). `SelectNextTab`/
`SelectPreviousTab` (wrapping) back `Ctrl+Tab`/`Ctrl+Shift+Tab`; a new
`ActiveClosableViewId` property backs `Ctrl+W`.

**"Empty workspace experience"**: disclosed, not separately built — the
permanent Home tab (the Engineering Cockpit, `WP 10.1A`, `ADR-0069`)
already *is* that experience, realised one Work Package earlier; the
Document Area is never genuinely empty. **"Loading placeholders where
appropriate"**: disclosed, not built — `ShowTab` is only ever called
with an already-fully-constructed `IWorkspaceView`; no code path in
this platform opens a tab before its own content is ready, so a loading
placeholder would never actually be shown.

## 5. Status Bar

Replaced entirely: `StatusBarView` is now six independently-updatable
segments — Current Project, Selected Object, Active Workspace, Host
State, Diagnostics, Notifications — each separated by a hairline
divider. Every segment is backed by a real read:

| Segment | Source |
|---|---|
| Current Project | Honest, disclosed placeholder — this platform has no formal "current project" concept (a single running Workspace over one seeded object graph); always "No project," never a guessed value |
| Selected Object | `WorkspaceManager.StatusBar.StatusText` (`WP 10.0B`, unchanged) |
| Active Workspace | The current `INavigationService` area's own title, tracked at every switch point |
| Host State | `IDiagnosticsProvider.HostState`, read fresh on every refresh |
| Diagnostics | A live count of `ModuleState.Failed` modules from `IDiagnosticsProvider.Modules` |
| Notifications | Honest, disclosed placeholder — `INotificationDispatcher` is real, but no Workspace-layer bridge into a per-session count exists yet; always 0, mirroring `EngineeringCockpit.OverdueActions`'s own identical discipline |

## 6. Navigation

`KeyboardShortcuts` extended from one binding to five:
`Ctrl+K` (Command Palette, unchanged), `Ctrl+Tab`/`Ctrl+Shift+Tab`
(document switching), `Ctrl+W` (close active document), `Ctrl+F` (focus
the Explorer filter). Tree-level: `F2` (rename), `Delete`, `Enter`
(open). Every bound action remains also reachable from a visible
control (menu, button, or context menu) — `WP10.0A UX Architecture
Document.md` §11's own "convenience, never capability" rule, upheld a
second Work Package running.

## 7. Workspace Visual Design

`Tempest.Desktop/Theming/DesignTokens.cs` (new) — a single, shared
source of spacing constants (4px base unit), typography sizes/weights,
and a minimum control size (28px, the Accessibility "minimum control
sizes" requirement, applied, not merely documented). `PanelHostControl`
(the Panel Header requirement) now draws from it, plus a real hairline
separator beneath each header. No new theming *mechanism* — Avalonia's
own `Application.Current`/`ThemeVariant` (`WP 10.0B`, `ADR-0094`) remain
the only theme engine; full light/dark compatibility is inherited
automatically, confirmed by direct review (`WP10.2A UX Review.md` §3),
not re-implemented.

## 8. Accessibility

- **Keyboard access**: every new interactive affordance (filter box,
  breadcrumb buttons, context menu, pin button, tab shortcuts) is a
  standard Avalonia control, reachable by `Tab`/arrow keys/`Enter` by
  default — none suppress the platform's own built-in keyboard
  handling.
- **Focus visibility**: the Fluent theme's own default focus-ring
  rendering is never overridden or hidden anywhere in this Work
  Package's own changes.
- **Screen scaling**: Avalonia's own DPI virtualisation is unaffected —
  every new size in this Work Package is expressed in device-independent
  units (the pre-existing convention), never a hardcoded physical pixel
  assumption.
- **Minimum control sizes**: `DesignTokens.MinControlSize` (28px) is
  applied to every new/modified interactive control (tree, filter box,
  toolbar buttons, navigation buttons, panel header buttons) — a real,
  applied floor, not merely a documented target.

## 9. Performance

- **No measurable startup regression**: no new eager work was added to
  `App.OnFrameworkInitializationCompleted`/`WorkspaceHost.StartAsync`;
  every new capability (filtering, breadcrumbs, pinning) is
  presentation-layer-only and constructed lazily, on first use.
- **Responsive tree expansion**: unchanged — `TreeView`'s own built-in
  virtualised expand/collapse.
- **Responsive property updates**: unchanged synchronous `Refresh()`.
- **Responsive document switching**: `Ctrl+Tab`/`Ctrl+Shift+Tab` are
  O(1) index arithmetic over an already-in-memory `TabControl.Items`
  collection — no I/O, no re-query.

Full measurement methodology and results: `WP10.2A Performance
Review.md`.

## 12. Summary

Every named area (Project Explorer, Property Inspector, Document Area,
Status Bar, Navigation, Visual Design, Accessibility, Performance) was
addressed with real, working code — never decorative UI. The one
genuine platform gap this Work Package's own scope required closing
(no interactive surface could dispatch a real, per-object mutating
command) was found, root-caused to its own precedented origin
(`WP 9.0A`'s own explicit anticipation), and closed with the smallest,
most consistent contract extension available (`ADR-0096`). Every
honestly-incomplete capability (Requirements rename, the empty
workspace/loading-placeholder items, Current Project/Notifications)
is disclosed, not fabricated, each with a concrete, named reason.
