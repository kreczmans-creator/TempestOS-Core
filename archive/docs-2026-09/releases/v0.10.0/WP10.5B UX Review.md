# WP 10.5B — UX Review

## Purpose

Assesses `WP 10.5B`'s own new/changed surfaces directly against real,
running controls for clarity, consistency, and genuine professional
interaction quality.

## 1. Delete Confirmation Wording — Consequence-Led, Consistent With `TD-40`'s Own Precedent

"Delete the selected {Kind}? This cannot be undone." mirrors
`ConfirmationDialog`'s own established "Discard unsaved changes?"
wording pattern (`WP 10.5A`) — leads with the irreversible consequence,
names the real Kind (never a generic "this item"), and labels the
primary button with the actual verb ("Delete"), never a generic "OK."
Assessed as consistent, scannable, and honest about the soft-delete
reality (§4 of the Implementation Report) without over-explaining it in
the dialog itself — a user does not need to know "soft delete" exists
to correctly understand "this cannot be undone" from the Workspace's
own perspective (the object leaves every live view/tree/count).

## 2. The Create/Duplicate Flow — Assessed a Real, Coherent First Step

Clicking "Create" now genuinely creates a real Part with a real name,
appearing in the Project Explorer moments later — the ProjectExplorer's
own empty-state guidance ("Create one from the Ribbon to get started,"
`WP 10.5A`) is now literally true for the first time. Duplicate's own
single-confirmation flow (no name prompt) is assessed as the right
interaction for its own simpler need — asking for a name the user did
not ask to provide would be friction without benefit.

## 3. `TaskScheduler.UnobservedTaskException` — Correctly Scoped, Not Oversold

The Implementation Report's own §6 and this Work Package's own
`ShowUnexpectedErrorAsync` doc comment both explicitly disclose that
this is *not* a global crash handler — a genuinely fatal
`AppDomain.UnhandledException` is not caught. Assessed as the right UX
honesty: a "Professional Error Handling" feature that silently implied
broader crash protection than it actually provides would be worse than
naming the real, narrower scope directly.

## 4. Settings Dialog — Real, Minimal, Honestly Scoped

Three real preferences (Theme, Toast duration, Confirm-before-delete),
laid out in three labelled sections. Assessed as appropriately minimal
for a first, real Preferences surface — no placeholder rows for
capabilities that do not exist yet (no keyboard-shortcut remapping UI,
since no remapping capability exists to configure), consistent with
this platform's own "never fabricate a control for a capability that
isn't real" discipline.

## 5. Recent Searches — the Flyout Button Assessed Discoverable Enough, Not Perfectly

The "🕐" button sits directly beside the filter box — reachable,
visually distinct from the filter itself, but relies on the user
recognising the clock glyph as "recent" without a text label (space-
constrained next to the filter). Disclosed as a real, minor,
accepted trade-off, not a defect — a tooltip ("Recent searches") is
present for anyone who hovers.

## 6. Disclosed UX Trade-offs

- No visual distinction between a Toast triggered by a local action
  (Save/Delete) and one triggered by a background `IPlatformNotification`
  — both use the identical `ToastNotification` styling. A future Work
  Package could add a small "background" badge; not attempted here.
- The window-restore centring (off-screen recovery) has no transition
  animation — the window simply appears at the corrected position, an
  intentionally simple, always-correct behaviour over a more polished
  but unverified animated recovery.
- `SettingsDialog`'s own Theme change applies immediately on Save
  (via `ThemeService.ToggleAsync`), not previewed live while the
  dialog is still open — a real, disclosed simplification.

## 7. Recommendation

**Accept**, with every named trade-off in §6 disclosed directly as a
real, accepted decision, not a hidden gap.
