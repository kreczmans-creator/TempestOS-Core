# WP 10.2B — Engineering Review

## Purpose

An independent technical review of `WP 10.2B`'s own real implementation
— whether every claim in `WP10.2B Implementation Report.md` is
genuinely true against the real diff, whether the "already real before
this Work Package" claims (§1 there) hold up under direct re-check,
and whether the one disclosed finding (`TD-39`) is correctly diagnosed.

## 1. "Already Real Before This Work Package" — Independently Re-Verified

Directly re-read `WorkspaceState.SaveAsync`/`LoadAsync`
(`src/Tempest.App/Workspace/WorkspaceState.cs`) and
`IWorkspaceLayout.ResetToDefault`
(`src/Tempest.App/Workspace/IWorkspaceLayout.cs`,
`WorkspaceLayout.cs`) directly, not taken on the Implementation
Report's own word. Both confirmed genuinely already implemented,
unmodified by this Work Package's own diff — `git status`/`git diff`
shows neither file touched. The Implementation Report's own claim that
"Saved workspace layouts"/"Restore previous layout on startup"/
"Persistent panel visibility"/"Persistent splitter positions" pre-date
this Work Package is accurate, not a convenient excuse to skip work —
this Work Package's own genuinely new contribution for "Reset workspace
layout" specifically is the real, reachable `View → Layout → Reset
Layout` menu item (`MainWindow.cs`, `ResetLayout` private method),
confirmed present and confirmed to call `ResetToDefault()` directly.

## 2. `DockingGrid`'s Bottom Row — Verified Directly

Read `src/Tempest.Desktop/Docking/DockingGrid.cs` in full. `RowDefinitions`
correctly declares three rows (`Star`/`Auto`/`Pixel(0)`); the bottom
`GridSplitter` correctly spans all five columns
(`Grid.SetColumnSpan(_bottomSplitter, ColumnCount)`); `SetBottomPanel`
correctly places its own content with `Grid.SetColumnSpan(content,
ColumnCount)` too, so the Output panel genuinely spans the full window
width beneath Left/Centre/Right, not merely beneath the centre column.
`SetLeftCollapsed`/`SetRightCollapsed`/`SetBottomCollapsed` all
correctly no-op while the corresponding panel is hidden (`if
(IsLeftVisible) SetLeftVisible(true);`) — confirmed by
`Collapse_IsANoOp_WhileThePanelIsAlreadyHidden`
(`DockingGridTests.cs`), which this review re-ran independently and
confirmed passing.

## 3. `OutputPanelView` — Honest-Scope Claim Verified

Read `src/Tempest.Desktop/Views/OutputPanelView.cs` in full, then
cross-checked `Tempest.Core.Logging.ILogSink`
(`src/Tempest.Core/Logging/ILogSink.cs`) directly — confirmed
`void Write(LogEntry entry)` is the interface's own only member, with
no read-back/history API anywhere in `Tempest.Core.Logging`, and no
other type in `Tempest.Core` buffers written entries for later replay.
The Implementation Report's own claim — "a live module/hosted-service
status stream, not a captured log-history feed... adding one would be
a Runtime change" — is independently confirmed accurate, not merely
asserted. `IDiagnosticsProvider.Modules`/`HostedServices` are both
already-real, already-live reads (`WP 10.2A` precedent,
`StatusBarView.SetDiagnostics`); `OutputPanelView.Refresh` calls
neither with any caching layer of its own, confirmed by direct read —
every refresh is a fresh read, never a stale snapshot.

## 4. `TD-39` — Correctly Diagnosed, Correctly Scoped

Read `PanelHostControl.cs`'s own `Background = Avalonia.Media.Brushes.White;`
assignment directly, and `CommandPaletteOverlay.cs`'s own
`Background = Avalonia.Media.Brushes.Black;` (unmodified, `WP 10.0B`)
alongside it. Both confirmed genuinely fixed, non-`DynamicResource`
brushes — the finding is real, not manufactured to pad the Technical
Debt Register. Confirmed **cosmetic-only**, not a functional defect:
`PanelHostControl`'s normal docked-mode rendering was never affected
(no overlap exists there), and the flyout's own open/close/restore
mechanics (`DockingGridTests.cs`'s own `ShowFlyout`/`HideFlyout` tests)
are fully correct regardless of background colour — the finding is
purely visual, confirmed by direct code inspection, not by running the
application in Dark theme (this review notes that as a real, disclosed
limitation of its own verification method — no visual/screenshot
comparison was performed, consistent with this platform's own
established headless-test-only verification discipline since `WP
10.0B`).

## 5. Auto-Hide Flyout — Not a Floating Window, Confirmed

Independently re-read `DockingGrid.ShowFlyout`/`HideFlyout`. Confirmed:
no `Avalonia.Controls.Window`, `Popup`, or `OverlayLayer` construction
anywhere in either method — the flyout is realised entirely via
`Grid.SetColumn`/`SetRow`/`SetColumnSpan`/`SetRowSpan`/`HorizontalAlignment`/
`VerticalAlignment`/`Width`/`Height`/`ZIndex` on the **same,
already-parented** `PanelHostControl`, which remains a child of the
same `DockingGrid` throughout. This satisfies "No floating windows"
literally, not merely in spirit — confirmed by direct inspection of
every `new` expression in both methods (none constructs a second
top-level surface).

independently re-verified true against the real diff and the real,
re-run test suite. One genuine, correctly-scoped, cosmetic-only
