# WP 10.0A — Visual Design System

## Purpose

Theme architecture, iconography strategy, engineering colour language,
information hierarchy, and visual density — the presentation vocabulary
every screen in `WP10.0A Screen Catalogue.md` draws from. Intent and
architecture only, per `ADR-0092`: no concrete colour value, font, or
icon asset is fixed here — those are implementation-phase choices made
once a concrete UI framework (`ADR-0094`, reserved) is selected.

## 1. Theme Architecture

**Principle, not palette.** This Work Package specifies that theming
is **data-driven, not hard-coded per screen** — every screen in `WP10.0A
Screen Catalogue.md` reads its own colours, spacing, and typography
from one theme definition, never inlines a literal value. This directly
generalises `WP8.0A UI Architecture.md` §3.3's own "no View introduces
its own query, cache, or index" principle to styling: no View owns its
own private colour or spacing value either.

Two themes are named as required (Light, Dark) — a genuinely new
requirement `ADR-0066`'s own terminal paradigm never needed to consider
(a terminal inherits its colours from the user's own terminal emulator
settings; a desktop application owns its own). **No theme-switching
mechanism, storage location, or default is designed here** — this
follows the same persistence pattern already established (`ADR-0064`,
`ISettingsProvider`), named as the correct mechanism to reuse, not
redesigned.

**Zero new Platform Service.** Theme data is a Settings value, exactly
like panel layout (§UX Architecture Document §13) — no new
"Theming Service" is introduced.

## 2. Iconography Strategy

**One icon per `Kind`, resolved by a Kind-keyed lookup — mirroring
`ADR-0067`'s own registration pattern exactly, applied to icons
instead of Views/Explorer nodes.** Every Domain `Kind` string already
in use (`"Part"`, `"Assembly"`, `"Requirement"`, `"CalculationRecord"`,
`"VerificationActivity"`/`"Test"`/`"Inspection"`, `"Document"`/
`"Drawing"`/`"CadModel"`, `"ManufacturingOperation"`/
`"WorkInstruction"`) maps to exactly one icon, consistently across
every screen that shows it (Project Explorer, Object Editor tab, Cockpit
KPI card, Command Palette result, Object Relationship View node) —
**never a different icon in two places for the same `Kind`.**

**No new contract.** This lookup is presentation-layer-only, keyed by
the same `Kind` string every discipline already carries on its own
`IEngineeringDocument`/`ProjectExplorerNode` — no `Tempest.Core` or
Workspace contract change, mirroring `ADR-0067`'s own reasoning that a
string-keyed registry needs no new abstraction to add a new
registrant. A future Engineering Discipline Module registering a new
`Kind` (Journey 5, `WP10.0A Navigation & Workflow Diagrams.md` §6)
supplies its own icon at registration time, exactly as it already
supplies its own `IWorkspaceViewFactory`.

**No concrete icon set chosen here** — an implementation-phase asset
decision, deferred alongside `ADR-0094`.

## 3. Explorer and Editor Density

Building directly on iconography (§2): every Project Explorer row, and
every Object Editor's own header, presents Kind icon + lifecycle colour
chip (§4) + label as one consistent unit — the same three-element
composition, reused everywhere an object is represented, rather than a
bespoke layout per screen. This is the concrete mechanism Journey 8
(`WP10.0A Navigation & Workflow Diagrams.md` §9) depends on.

## 4. Engineering Colour Language

**One colour per `EngineeringHealthStatus`/lifecycle state value,
applied uniformly.** `EngineeringHealthStatus` (`Healthy`/`Unknown`,
extended per-discipline) and `LifecycleState` (`Draft`/`InReview`/
`Approved`/`Released`/`Archived`) already form closed, existing
vocabularies — this Work Package specifies that each value maps to
exactly one colour, used identically in Cockpit KPI cards, Project
Explorer lifecycle chips, Object Editor headers, and context-menu
availability cues (a greyed-out "Approve" for an object already
`Released`, for instance). **No colour values are chosen here** — the
mapping's own existence and its "one value, one colour, everywhere" rule
is the architecture decision; the specific hex/theme-token values are
implementation-phase, deferred alongside `ADR-0094`.

**A deliberate constraint, named explicitly:** colour is never the
*only* signal for a state — every colour-coded element also carries a
text label or icon distinction (§2), so the design remains legible
without relying on colour perception alone. This is stated here as a
requirement this Work Package holds itself to, not deferred to a future
accessibility review.

## 5. Information Hierarchy

Three fixed levels, applied consistently across every screen this Work
Package catalogues:

1. **Primary** — the selected/open object's own identity and lifecycle
   state (largest, most prominent — the Object Editor's own header, the
   Cockpit's own KPI card headline number).
2. **Secondary** — discipline-specific facts and relationships (the
   Property Inspector's own grouped facets, §UX Architecture Document
   §6; the Object Relationship View's own neighbour nodes).
3. **Tertiary** — provenance, timestamps, and diagnostic detail (revision
   history entries, the Status Bar's own Diagnostics summary) — present,
   discoverable, never competing visually with Primary or Secondary.

This hierarchy is the direct visual expression of `WP8.0A Workspace
Architecture Document.md` §6's own existing facet model (Identity/
Revision History/Provenance/Relationships plus discipline-specific
facets) — this Work Package does not invent a new categorisation, only
gives the existing one a consistent visual weighting.

## 6. Visual Density

**Two density modes named, not designed in full**: Comfortable (default)
and Compact — a genuinely new consideration a graphical desktop
application must make that a terminal's own fixed character grid never
needed to (a terminal has exactly one density). Comfortable favours
readability for an engineer inspecting one or two objects; Compact
favours the Project Explorer's own dense, multi-discipline tree (§Screen
Catalogue §4) when many objects must be scannable at once. **No default
switching heuristic or persisted preference mechanism is designed
here** — named as a real requirement, deferred to implementation,
reusing the same `ISettingsProvider` persistence pattern (§1) once
designed.
