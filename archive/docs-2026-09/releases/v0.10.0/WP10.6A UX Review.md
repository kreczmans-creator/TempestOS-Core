# WP 10.6A — UX Review

## Purpose

The required, dedicated UX Review — verifying this Work Package's own
new interactions (Undo/Redo, Recent/Favourite Objects, Command History,
Background Tasks, Macros, keyboard binding) genuinely follow this
platform's own established interaction conventions, are each reachable
without needing to know an undocumented gesture, and honestly disclose
where a convenience affordance has no backing capability.

## 1. Undo/Redo — Standard Convention, Real Feedback

`Ctrl+Z`/`Ctrl+Y` match the platform-standard Windows convention (never
`Cmd+Z`/`Cmd+Shift+Z`, since this is a Windows-first Avalonia
application, matching every other existing shortcut's own `Ctrl`-based
convention, `KeyboardShortcuts.cs`, unchanged pattern). Two Quick Access
Toolbar buttons (`↶ Undo`/`↷ Redo`) give the identical capability a
mouse-only user needs — mirroring `WP10.0A UX Architecture Document.md`
§11's own "convenience, never capability" rule: every keyboard-only
action here is also reachable from a visible button. Button
enablement/tooltip is live (`RefreshUndoRedoButtons`, called after
every Record/Undo/Redo), so a disabled Undo button honestly signals
"nothing to undo" rather than a dead click; the tooltip names exactly
what would be undone/redone (`"Undo: Rename to 'X'"`), never a generic
label.

## 2. Recent/Favourite Objects — Mirrors an Existing, Already-Accepted Pattern Exactly

Both new flyout buttons (`🕓`/`⭐`) sit directly beside the existing
`🕐` Recent Searches button in `ProjectExplorerView`'s own filter row —
the identical flyout-button shape (`ShowRecentObjectsFlyout`/
`ShowFavouritesFlyout` mirror `ShowRecentSearchesFlyout` byte-for-byte
in structure), so a user who has already learned Recent Searches'
own interaction gains the two new ones for free, with zero new
interaction pattern to learn. Both honestly show "No recent objects
yet."/"No favourite objects yet." when empty, rather than an empty list
with no explanation.

## 3. Toggle Favourite — Discoverable From Two Places, Consistent Label

The Project Explorer context menu's own new "Add to Favourites"/"Remove
from Favourites" item reflects live state (never a generic "Toggle") —
a user reading the menu already knows what clicking it will do, without
needing to check a separate flyout first. `Ctrl+D` gives the identical
capability to the current selection without opening a menu at all — the
same "keyboard shortcut for an already-visible action" pattern Undo/Redo
uses.

## 4. Command History / Background Tasks — Reused Real Estate, Not a New Surface to Learn

Both new sections live inside the already-existing, already-docked
Output panel (`OutputPanelView`), alongside "Modules"/"Hosted Services"
— a user who already knows where to look for platform status finds
both new sections in the identical place, rather than a new panel to
discover, position, or learn to open. Genuinely live: both refresh
automatically at every point `RefreshStatusBar` already runs, plus
their own dedicated `Changed`-driven refresh points (Undo/Redo,
Macro completion) — never a stale, manually-refreshed view.

## 5. Macros — A Real, If Deliberately Minimal, Two-Screen Flow

`MacroManagerDialog` opens directly from a new "🧩 Macros" Quick Access
Toolbar button (the identical toolbar row every other cross-cutting
action — Command Palette, Theme, Reset Layout, View Relationships —
already lives in). Browse (list + Run/Delete/New) and Editor (name +
two-list step builder) are two clearly separated screens, never one
crowded form — "New Macro..." swaps the panel, "Cancel"/"Save Macro"
swap it back, mirroring `SettingsDialog`'s own established
single-purpose-panel convention. Honest disclosure built directly into
the UI, not just the docs: the Available Commands list shows *only*
what is genuinely usable as a macro step (`CreateDefault`-eligible) —
a user is never shown a step they could pick that would then silently
fail to run.

## 6. Keyboard Input Binding — Honestly, Deliberately Invisible This Work Package

`KeyboardCommandBindingProvider` ships with zero default bindings and
no discoverable UI — a deliberate, disclosed choice (`AT-23`), not an
oversight to be found by a confused user. Nothing in the shipped UI
references it (no "Configure Shortcuts..." menu item pointing at an
empty screen) — the mechanism exists for a future Work Package to
surface, not half-exposed today.

## 7. Consistency With Established Feedback Conventions

Every new completed action (Undo/Redo, Toggle Favourite, Macro run)
uses the identical Status Bar text + `ToastHost` Success/Error severity
pattern every existing action already uses (`MainWindow`'s own
established `_statusBar.SetText`/`_toastHost.Show` pairing) — no new
feedback mechanism introduced, no inconsistent severity mapping (a
failed Undo/Redo/Macro correctly shows `FeedbackSeverity.Error`,
verified directly against `UndoAsync`/`RedoAsync`/the macro `runMacro`
delegate's own `result.Succeeded` branch).

## 8. Disclosed Gaps

- No visual indication in the Ribbon/QAT of *which* object a pending
  Undo would affect beyond the tooltip text — acceptable at this Work
  Package's own two-action-type breadth, would need reconsideration if
  Undo coverage broadens (`FCR-0078`).
- `MacroManagerDialog`'s own step list shows raw `CommandDescriptor.Id`
  strings in the Steps column (`"1. mechanical.create"`) rather than
  each step's own `DisplayName` — a minor, disclosed readability gap,
  not fixed this Work Package (the Available Commands list itself does
  show `DisplayName`, so the information exists, just not carried
  through to the Steps list's own rendering).
- No confirmation prompt before deleting a macro — mirrors this
  platform's own pre-`WP 10.5B` Delete behaviour for every other object
  type before `ConfirmDeleteAsync` was introduced; a real, disclosed
  gap, not wired to the existing Delete Confirmation gate this Work
  Package's own time budget did not extend to macros.

## 9. Conclusion

Every new interaction reuses an existing, already-accepted TempestOS
convention — the Recent Searches flyout shape, the Output panel's own
column layout, `SettingsDialog`'s own panel-swap pattern, the Status
Bar/Toast feedback pairing — rather than introducing a new pattern a
user would need to learn from scratch. Two minor, disclosed UX gaps
found (§8); neither blocks real, productive use of any of the six new
capabilities.
