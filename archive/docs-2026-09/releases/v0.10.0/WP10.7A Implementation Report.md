# WP 10.7A — Feature Completion — Implementation Report

## Context

`WP 10.6D` (Feature Completion Audit) produced a prioritised list of
placeholder behaviour found in the running application — Ribbon
lifecycle/organize buttons that dead-ended into a permanent honest
degraded message across five of six disciplines; five discipline-specific
Object Editor sections named as future work since `WP 10.3A` but never
built; two Cockpit KPI cards hardcoded to a placeholder despite real
backing data existing; a Project Explorer drag/drop mechanism that was
"real drag, real visual feedback, `Drop` is a documented no-op." This
Work Package closes every one of those items that can genuinely be
closed using only already-existing, already-registered services and
commands — no new `ICommand`/`IWorkspaceCommand`, no new Domain contract,
no new member on any of `IWorkspaceManager`/`ICommandDispatcher`/
`ICommandRegistry`. A small number of WP10.6D items turned out, on direct
investigation, to need genuine new architecture to close for real; those
are named explicitly below as out of scope, not silently dropped.

Per this Work Package's own controlling instruction ("Using WP10.6D
only... Verify every completed feature interactively. STOP"), scope is
strictly the WP10.6D-audited items — no accompanying full Engineering/
Architecture/Security/Systems review cycle was requested, matching
`WP 10.6C`'s own identical precedent for a narrowly-scoped wiring Work
Package.

## Part 1 — Ribbon Lifecycle/Organize Dispatch

Extended `RibbonView.ObjectCreationHandlers` (the existing, empty-by-
default `Dictionary<string, Func<Task>>` seam `MainWindow` already
populated for `"mechanical.create"`/`"mechanical.duplicate"`) with real
handlers for:

- **Status transitions** (Approve/Archive/Lock/Unlock/Request-Review/
  Release) for Calculations, Documents, Verification, Manufacturing —
  all four share `Set{X}StatusCommand(Guid, string, LifecycleState)`,
  dispatched via one shared `statusHandler` factory. Requirements' own
  `SetRequirementStatusCommand(Guid, RequirementStatus)` has a genuinely
  different shape (a different enum, no `targetKind` parameter) — its
  own dedicated handler, collecting the target status via a validated
  `InputDialog` prompt (no status-picker control exists anywhere in this
  platform).
- **Duplicate** for Calculations/Documents/Verification/Manufacturing
  (a shared handler factory, mirroring Mechanical's own) and
  Requirements (its own handler — `DuplicateRequirementCommand`'s own
  `newIdentifier` is required, not optional, unlike every other
  discipline).
- **Create** for Calculations/Documents/Manufacturing (each defaults
  every optional constructor parameter beyond name, mirroring
  Mechanical's own "defaults to the most common Kind" precedent),
  Verification (`SubjectId` is the current selection's own Id — "Create
  Verification Activity" genuinely means "verify what I have selected"),
  and Requirements (all three real Create commands — Requirement, Group,
  Collection — each its own Ribbon entry with its own descriptor).

## Part 2 — Real Drag-and-Drop Reparenting

`ProjectExplorerView` gained a new public event, `ObjectMoveRequested`
(mirroring the shape of its own existing `ObjectSelected`/`ObjectOpened`/
`ToggleFavouriteRequested`), raised from `OnTreeDrop` — previously a
two-line no-op. The drop target is resolved via `FindAncestorOfType
<TreeViewItem>` from the routed event's own source; dropping on empty
tree space means "move to root" (`null` parent), matching every
`Move*Command`'s own nullable `newParentId` shape. Guards against
dropping an object onto itself or its own descendant (an honest
`ActionCompleted` message, never a crash or a silently-accepted
structural loop).

`MainWindow` subscribes once, mapping `Kind` to the correct discipline's
own already-registered `Move*Command` and dispatching it directly via
`ICommandDispatcher` — this View never references the dispatcher itself,
matching `ToggleFavouriteRequested`'s own "raise intent, owner
dispatches" precedent. `IWorkspaceManager` was not extended — no
`RegisterMoveFactory`/`MoveObjectAsync` member was added, deliberately,
to stay inside "no new architecture."

## Part 3 — Five New Object Editor Sections

`ObjectEditorView` gained a new `ICommandDispatcher` constructor
parameter (threaded from `MainWindow`'s own already-resolved instance)
plus two new optional parameters (`IRequirementsService?`,
`CalculationTemplateRegistry?`). Five new `Expander` sections were added
to `BuildLayout`, each collapsed-and-hidden (`IsVisible = false`) until
`PopulateFrom`'s own gate matches the real target — a C# `is` type-check
against the real object (the identical idiom `PopulateLifecycle`/
`PopulateRelationships`/`PopulateValidation` already use) for BOM/
Attachments/Record-Result, or an `_objectKind` string check for
Requirements Owner/Priority and Calculations Execute, since those two
need a service the object graph itself does not expose:

- **Mechanical BOM** (`IHasBomLine`) — Quantity/UOM/Find#/Item#/Ref
  Designator, dispatches `SetBomLineCommand`.
- **Requirements Owner/Priority** — reads via `IRequirementsService.
  FindAsync` (a genuinely different read path from `target`, see §5),
  dispatches `SetRequirementOwnerCommand`/`SetRequirementPriorityCommand`.
- **Calculations Execute/Recalculate** — required plumbing:
  `CalculationTemplateRegistry` (already constructed by
  `CalculationsWorkspaceRegistration.Register`) was previously discarded
  by `EngineeringWorkspaceComposer.RegisterEngineeringDisciplines`
  (`void` return) — now returned, captured by `WorkspaceHost.
  CalculationTemplates`, and threaded through. Whether to show
  "Execute" or "Recalculate" is read from the object's own real
  `calculatedBy` relationship (the identical read `PopulateRelationships`
  already performs).
- **Verification Record Result** (`IVerificationActivity`) — Pass/Fail/
  Conditional buttons + a Method field, dispatches
  `RecordVerificationResultCommand`.
- **Documents Attachments** (`IHasAttachments`) — lists already-attached
  metadata via `GetAttachmentsAsync`, an Attach mini-form dispatches
  `AttachDocumentCommand`. No file-picker affordance — `Attachment`
  carries descriptive metadata only (`TD-31`, unchanged).

## Part 4 — Cockpit KPI Cards

`EngineeringCockpit.KpiCards`'s own "Risks" entry now reads
`LiveRisks.Count` (the identical read `RiskSummary` already uses) instead
of a hardcoded `IsPlaceholder: true`. "Review" now sums each discipline's
own already-computed in-review count (`RequirementsInReviewCount`,
`CalculationsInReviewCount` — two small properties promoted from
previously-inline closures — plus the already-named
`OutstandingDocumentReviews`); Verification/Manufacturing have no
equivalent single named count exposed publicly today, honestly not
included rather than approximated.

`CockpitView`'s "Favourite Projects" card now reads the real, already-
shipped, Desktop-layer `FavouriteObjectsState` (`WP 10.6A`) filtered to
Kind `"Project"`, rather than a fixed message — `EngineeringCockpit.
FavouriteProjects` itself (the App-layer member) is unchanged, still
always empty, since `Tempest.App` cannot reach a Desktop-layer service
without inverting the project's own layering; the two remain genuinely
distinct concepts, as `FavouriteObjectsState`'s own remarks already
disclose.

## Explicitly Out of Scope, Disclosed

- **Command Palette / Macro `CreateDefault` gap** — `CommandDescriptor`
  has no mechanism to pass "the current selection" through to a command
  construction; closing this needs a genuine new `CommandDescriptor`/
  `ICommandRegistry` member. Left as-is.
- **Cockpit "Overdue Actions"** — `ITask`/`IAction` have no due-date
  field anywhere in the Domain. Left as the existing honest placeholder.
- **Ribbon Copy** (as a button) — needs a destination-parent picker; no
  such dialog exists. Falls through to the existing honest degraded
  message, unchanged (`FCR-0073`).
- **Materials discipline** — never reachable at all; out of scope (a new
  discipline, not a completion of an existing placeholder).

## Genuine Findings During Implementation

1. **`TD-41` (new, disclosed)** — `ObjectEditorView.TryCreate` never
   resolves a real Requirement via `EngineeringDomainContext.Repository`
   — a genuine, pre-existing gap since `WP 10.3A`, not caused by this
   Work Package, found while testing the new Requirements Owner/Priority
   section. The section is correctly implemented but currently
   unreachable specifically through the Object Editor for Requirements;
   the identical capability remains genuinely reachable via the Ribbon's
   own `"requirements.set-owner"`/`"requirements.set-priority"` handlers
   (Part 1), which dispatch independently of `ObjectEditorView`. See the
   Technical Debt Register.
2. **Found and fixed in place, before any commit, not registered as
   debt** — every one of the five new Object Editor sections had its own
   success/failure status message immediately overwritten by the
   `Refresh()` call that reported it (`Refresh()` re-runs `PopulateFrom`,
   which unconditionally clears each section's own status text) —
   reordered (`Refresh()` first, message set after) in all five.
