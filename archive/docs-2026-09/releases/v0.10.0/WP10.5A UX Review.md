# WP 10.5A — UX Review

## Purpose

Assesses `WP 10.5A`'s own new/changed surfaces directly against real,
running controls for clarity, consistency, and genuine professional
polish — never a mock-up.

## 1. Toasts Complement, Never Replace, the Status Bar — Assessed Correct

Every `ActionCompleted` message now renders in two places: the Status
Bar (persistent, low-key, already established since `WP 10.0B`) and a
Toast (transient, more visually prominent, ~4.5s auto-dismiss). This is
assessed as the right pairing — a user who is watching the Status Bar
loses nothing; a user who is not gets a real, hard-to-miss confirmation
for the same event, without a second, divergent message ever being
possible (both come from the identical string).

## 2. Toast Auto-Dismiss Duration — Assessed Reasonable, Disclosed as Untuned

4.5 seconds was chosen as a reasonable default (long enough to read a
short confirmation, short enough not to accumulate), not derived from
any user testing — disclosed directly as a first, sensible guess, not
a measured optimum.

## 3. `ConfirmationDialog`'s Wording — Assessed Clear, Consequence-Led

"Discard unsaved changes?" / "This tab has unsaved edits. Closing it
now will discard them permanently." leads with the consequence
(permanent discard), not the mechanism (closing a tab) — the correct
ordering for a destructive-action prompt; the default/primary button is
labelled with the actual verb ("Discard"), never a generic "OK," so a
user scanning quickly cannot mistake which button does what.

## 4. `EmptyStateView`'s Two Project Explorer Messages — Assessed Genuinely Distinct, Not Generic

"Nothing here yet. This area has no objects yet. Create one from the
Ribbon to get started." (genuinely empty) is assessed as meaningfully
different from "No matches. No items match "{query}". Try a different
search term, or clear the filter." (filter mismatch) — a user hitting
either one gets guidance specific to *why* the panel is empty, never
the same generic sentence for two different real situations.

## 5. Icon Consistency — Assessed a Real, Visible Improvement, Correctly Scoped

Every Kind glyph now renders in one consistent, monochrome, theme-
correct style rather than a mix of full-colour emoji and monochrome
symbols — assessed as a genuine visual-consistency win, most noticeable
in the Project Explorer tree (where many Kinds appear together) and the
Ribbon (icon-above-label Create buttons). The `IconGeometry` vector set
is currently invisible to an end user browsing the app normally (it is
only used inside the new controls' own interactive chrome, none of
which render a Close/Check/Chevron glyph via `IconGeometry` yet in this
Work Package's own actual wiring — the toast close button still uses
"✕" text) — disclosed directly: `IconGeometry` exists and is tested,
but is not yet visibly consumed anywhere. A real, honest gap, not a
claimed-but-undelivered feature (the four glyphs are real, parse
correctly, and are ready for a follow-up Work Package to actually wire
in).

## 6. Disclosed UX Trade-offs

- Toast stacking has no maximum count — a burst of rapid actions could
  stack several toasts bottom-right. No cap was added; disclosed as
  untested against a high-frequency burst scenario.
- The Busy Overlay covers the entire window (root Grid), not just the
  Project Explorer panel it is currently wired to — a real, disclosed
  scope decision (simpler, and the one wired action — area switch —
  genuinely affects the whole Workspace's own content), not a mistake.
- No first-run tutorial/tour introduces the new Toast/Confirmation
  behaviour — a user simply encounters it the first time they trigger
  it.

## 7. Recommendation

**Accept**, with §5's own honest disclosure (a built, tested, but not
yet visibly wired vector icon set) and §6's trade-offs named directly,
not treated as hidden gaps.
