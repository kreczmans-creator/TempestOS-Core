# WP 10.0B — Engineering Review

## Purpose

An independent technical review of `WP 10.0B`'s own real implementation
— whether every scope constraint is genuinely honoured, whether every
"Demonstrate" requirement is genuinely proven rather than merely
asserted, and whether the four found defects (`WP10.0B Implementation
Report.md` §6) were fixed correctly and minimally.

## 1. "No Engineering Functionality Changes" — Verified

Direct `git status` re-check confirms zero files touched under
`src/Tempest.Core/EngineeringDomain/`, `src/Tempest.Core/Calculations/`,
`.Verification/`, `.Requirements/`, or any of the six discipline
namespaces under `src/Tempest.App/Workspace/` (Mechanical, Requirements,
Calculations, Documents, Verification, Manufacturing). `tests/Tempest.Core.Tests`
own 2026/2026-passing result, unchanged in count and content, is direct
empirical proof — not merely a file-count assertion — that no
discipline's own observable behaviour regressed.

## 2. "Must All Load Without Behavioural Change" — Verified, Structurally

This review specifically checked whether the claim is backed by a
structural guarantee or only a point-in-time test result. It is
structural: `Program.cs` (console) and `WorkspaceHost` (`Tempest.Desktop`)
both call the identical `EngineeringWorkspaceComposer.Build()`/
`.RegisterEngineeringDisciplines(...)` methods — the same object code,
not two independently authored copies. A future change to discipline
registration order or parameters can only be made once, in one place,
for both presentation layers — the strongest form of "unchanged
behaviour" this review could ask for, confirmed by direct read of
`EngineeringWorkspaceComposer.cs` line by line against the pre-`WP
10.0B` `Program.cs` it was extracted from (byte-for-byte identical
registration sequence, reordered into two methods only).

## 3. "No Workspace Contract Redesign" — Verified

Every one of the twelve `WP 8.0B` Workspace contracts, plus the two
additive members `WP 9.0A`/`WP 9.1A` already added
(`IPropertyFacetProvider`, `ISelectionService.ToggleSelectionAsync`),
was independently re-read against `Tempest.Desktop`'s own usage. None
is touched. The two changes this Work Package does make in
`Tempest.App.Workspace` (`InternalsVisibleTo`, well-known panel Ids)
are re-confirmed here, independently, to be exactly what `WP10.0B
Implementation Report.md` §4 claims: an assembly-visibility attribute
and a property-initializer value change, neither altering any
interface member's own signature.

## 4. The Four Found-and-Fixed Defects — Independently Re-Verified

**Finding F1 (`ThemeService.Apply` thread safety):** re-read directly.
The fix (`Dispatcher.UIThread.CheckAccess()`/`Invoke`) is the correct,
idiomatic Avalonia pattern for a method that may be called from either
thread — confirmed against `ThemeServiceTests`'s own two tests, both
passing, one of which (`LoadAsync_OnAFreshHost_...`) specifically
exercises the exact post-await, off-UI-thread call path that
originally failed.

**Finding F2 (well-known panel Ids):** re-read directly. This review
independently confirms the root-cause reasoning in `WP10.0B
Implementation Report.md` §6.5 is correct: `WorkspaceState.LoadAsync`
(unchanged, `WP 8.1A`) unconditionally replaces `Layout` with
`new WorkspaceLayout(dto.PanelPlacements)` on a successful load, with
no reconciliation against the *current* instance's own panel Ids —
meaning any panel whose own `Id` is not stable across a real restart
was **never** correctly restorable, not merely rarely. This review
independently confirms this defect pre-dates `WP 10.0B` (present on
the `v0.9.0` tag, `git worktree`-comparable to `TD-26`'s own
established verification method) and was invisible until a test
genuinely modelled two independent processes — which no prior test,
across `v0.8.0` and `v0.9.0` combined, ever did.

**Finding F3 (`TD-26` live reproduction):** re-verified against the
existing `TD-26` register entry (`docs/governance/Quality/Technical
Debt Register.md`) — its own "Revisit trigger" field reads, verbatim,
"Any future Work Package building a scripted, automation-driven, or
latency-sensitive Workspace consumer where a stale first read would be
user-visible or consequential." `Tempest.Desktop`'s own headless test
suite is precisely that consumer. This review confirms the mitigation
(`WorkspaceHost`'s own bounded poll) is scoped correctly — it does not
attempt to fix `WorkspaceManager` itself (out of this Work Package's
own scope, and `TD-26` remains a legitimate, tracked, cross-cutting
concern any future Work Package touching `WorkspaceManager` should
address at the source).

**Finding F4 (`ThemeServiceTests`'s own non-idempotent second test):**
re-read directly, and re-run: this review independently re-executed
`dotnet test src/TempestOS.slnx` (the full, combined solution) four
consecutive times without cleaning `persistence-data` between runs —
0 failures each time, confirming the fix in `WP10.0B Implementation
Report.md` §6.3 is genuine, not a symptom merely masked once. This
finding is a test-quality defect, not a production one — this review
confirms it is correctly *not* registered against
`Tempest.Desktop`/`Tempest.App.Workspace` in the Technical Debt
Register (`WP10.0B Technical Debt Review.md` §5 lists only the two
genuine production-adjacent items, `TD-35`/`TD-36`, correctly omitting
this one).

## 5. "Demonstrate" List — Verified as Real Tests, Not Assertions

Cross-checked `WP10.0B Implementation Report.md` §8's own table
directly against `tests/Tempest.Desktop.Tests/`: every named test
exists, is `[AvaloniaFact]`-attributed (a real Avalonia runtime, not a
mock), and was independently re-run by this review (`dotnet test`,
three consecutive invocations) — 10/10 passing each time, zero
flakes observed.

## 6. Code Quality Observations

- `DockingGrid`'s own `NotifyLeftPanelResized`/`NotifyRightPanelResized`
  being `public` (not `internal`) is a deliberate, disclosed choice to
  let a test drive the same notification path a real
  `GridSplitter.DragCompleted` would, without needing
  `InternalsVisibleTo` or reflection — this review agrees this is
  cleaner than the alternative (a third assembly-visibility grant) and
  does not weaken the class's own encapsulation in any way a caller
  outside a test could misuse (calling it merely re-raises an event
  from already-current state; it mutates nothing).
- `ProjectExplorerView`'s own eager, full-depth tree load (§WP10.0B
  Implementation Report.md §5) is confirmed appropriate at this
  project's own current sample-data scale (single/low-digit hundreds
  of nodes across six disciplines) — this review recommends revisiting
  it specifically if a future Work Package's own sample data grows by
  an order of magnitude, not before.

## 7. Verdict

**No release-blocking or Work-Package-blocking finding.** All four
found defects were genuine, disclosed, minimally and correctly fixed,
each independently re-verified against real, passing tests rather than
accepted on the Implementation Report's own say-so. Scope discipline
(`WP10.0B Implementation Report.md` §0) is fully honoured.
