# WP 10.2B — UX Review

## Purpose

An independent UX review of the Docking &amp; Workspace Layouts
implementation — whether Collapse and Auto-Hide are genuinely
distinguishable to a user, whether the three predefined layouts are
coherent, sensible presets rather than arbitrary values, and whether
the deliberate click-to-dismiss interaction model is a defensible
choice.

## 1. Collapse vs. Auto-Hide — Verified Distinguishable

Both mechanisms share one visual affordance (the thin
`CollapsedStripSize` strip) by deliberate design (`WP10.2B
Implementation Report.md` §3–4) — reviewed directly for whether this
creates user confusion. Findings:

- **Header iconography differs.** The Collapse button
  (`◀`/`▶`/`▼`/`▲`, direction-hinted per dock edge) is only present
  while pinned (`PanelHostControl.ApplyVisualState`:
  `_collapseButton.IsVisible = _pinned`) — a user in Auto-Hide mode
  never sees a Collapse button that would behave differently than
  expected.
- **Pin icon (📌/📍) is the sole Auto-Hide affordance**, always visible,
  giving a persistent visual cue of which mode governs the current
  strip.
- **Behavioural difference is consistent with the icon difference**:
  Collapse's own strip always expands in place (§3, Implementation
  Report); Auto-Hide's own strip always opens a temporary flyout —
  never inconsistent within a single session, confirmed by
  `PanelHostControlTests.StripButtonClick_WhilePinned_...`/
  `WhileUnpinned_...`.

**Assessed as genuinely distinguishable**, not merely internally
consistent code with an ambiguous surface.

## 2. Predefined Layouts — Coherence Review

| Preset | Rationale, Independently Assessed |
|---|---|
| Engineering | Balanced Explorer/Inspector, Output hidden — the default working posture for active engineering authorship, where the Output panel's own diagnostic content is rarely needed |
| Review | Narrower Explorer (less tree-browsing expected during review), wider Inspector (more facet detail visible while reviewing an object), Output visible (platform health relevant while reviewing) — each choice traces to a real reviewing behaviour, not an arbitrary size delta |
| Documentation | Widest Explorer (browsing a document tree is the primary activity), Inspector Auto-Hidden (reclaims width for the Document Area, remains one click away) — the only preset that exercises Auto-Hide by default, a deliberate showcase of the mechanism in its own natural use case |

Each preset's own three-panel combination is internally coherent with
a named user activity, not an arbitrary permutation of the available
sizes — assessed as a genuine, useful set of three, not merely
"three different numbers to satisfy the word 'multiple'."

## 3. Auto-Hide Interaction Model — Click-to-Dismiss, Assessed

The deliberate choice (click-the-strip-to-open, click-the-Document-Area
-away-or-`Escape`-to-close, never hover-to-peek) is reviewed against
the alternative directly:

**In favour of click-to-dismiss (the choice made):** deterministic —
no dwell-timer tuning, no accidental-flicker risk on pointer transit;
keyboard-accessible from the first release (`Escape`), where
hover-to-peek would need a second, separate keyboard affordance built
later; directly, deterministically testable headlessly (every
`DockingGridTests.ShowFlyout_*`/`PanelHostControlTests.StripButtonClick_*`
test is a real, deterministic click simulation, not a timing-dependent
hover simulation).

**Trade-off, disclosed honestly:** a hover-to-peek flyout (as VS
Code/Visual Studio both default to) is one fewer click for a
frequent, brief "just let me glance at this" interaction. This
Work Package's own model costs one extra click (open) and one extra
click-or-keypress (close) versus hover, for every single peek.

**Assessed**: a defensible, disclosed trade-off for a first
implementation, not an oversight — recorded as its own item in
`WP10.2B Implementation Report.md`'s own disclosure, with hover-to-peek
nameable as a future enhancement if real usage demonstrates the extra
clicks are a genuine friction point (no Future Capability entry raised
for it specifically — no real, demonstrated need exists yet, mirroring
this platform's own "disclosed, not fixed absent a real need" pattern
used throughout the Technical Debt Register).

## 4. Direction-Hinting Iconography — Verified Correct

`PanelHostControl.CollapseGlyph`/`ExpandGlyph` correctly vary by
`IWorkspacePanel.DockPosition` — Left points `◀`/`▶`, Right points
`▶`/`◀` (mirrored, correctly, since collapsing left means "collapse
toward the left edge"), Bottom points `▼`/`▲`. Independently verified
by direct read against each of the three real dock positions — no
copy-paste of a single glyph pair across all three.

## 5. Disclosed UX Trade-offs

- **`TD-39`** (fixed-brush overlay background, not theme-variant-
  aware) — a real, if minor, UX rough edge in Dark theme specifically
  for the Auto-Hide flyout; already disclosed, `FCR-0067` raised.
- **Click-away scope** — dismissing an open flyout via click-away only
  fires on a pointer press landing on the Document Area itself, not on
  the toolbar/menu/status bar; `Escape` covers the gap for keyboard
  users, but a mouse user clicking the toolbar while a flyout is open
  will find it still open. A minor, disclosed limitation, not a
  blocking defect (the strip itself, or a second `Escape`/click on the
  Document Area, always closes it).

## 6. Recommendation

**Sound.** Collapse and Auto-Hide are genuinely, not merely
internally, distinguishable; the three predefined layouts are coherent
against named real activities, not arbitrary; the click-to-dismiss
interaction model is a defensible, disclosed trade-off for this first
implementation, not an oversight. Two minor, disclosed UX rough edges
(`TD-39`; click-away scope), neither release-blocking.
