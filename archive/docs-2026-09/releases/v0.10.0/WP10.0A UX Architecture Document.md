# WP 10.0A — User Experience Architecture Document

## Purpose

The complete architecture for TempestOS's next-generation user
experience — the master reference for Programme 10 ("User Experience &
Desktop Application," `v0.10.0`). Architecture and specification only;
**no implementation, no code, no contract changes**. This document
covers UX philosophy, the desktop paradigm decision, overall
application layout, the multi-panel workspace, and Workspace-state
topics directly; `WP10.0A Screen Catalogue.md`, `WP10.0A Wireframe
Sketches.md`, `WP10.0A Interaction Specification.md`, `WP10.0A
Navigation & Workflow Diagrams.md`, `WP10.0A Visual Design System.md`,
and `WP10.0A Digital Thread & Relationship Visualisation.md` each go
deeper into one area named below (§13, Summary of Companion
Deliverables).

## 0. Where This Sits, and a Disclosed Continuity

This is not a green-field UX design. It is the direct, disclosed
continuation of `WP8.0A Workspace Architecture Document.md`, `WP8.0B
Workspace Contracts.md`, and `WP8.0C UX Specification.md` — the
Engineering Workspace those three Work Packages designed and specified
*before* any Engineering Discipline existed to populate it. Six real
disciplines now exist (`Tempest.App.Workspace.Mechanical`/
`.Requirements`/`.Calculations`/`.Verification`/`.Documents`/
`.Manufacturing`, `v0.9.0`, `WP 9.0A`–`WP 9.5A`), each already exercising
every Workspace contract `WP 8.0B` froze: `IWorkspaceView`,
`IWorkspacePanel`, `IWorkspaceLayout`, `IProjectExplorer`,
`IPropertyInspector`, `IPropertyFacetProvider`, `IProjectExplorerNodeProvider`,
`IWorkspaceCommand`, `ISelectionService`, `INavigationService`. This
Work Package designs the next generation of *presentation* over that
same, already-proven contract layer — it does not redesign the
contracts themselves, and confirms directly (§4, §12) that none of
them needs to change to support everything named below.

**The one genuine paradigm change this Work Package makes**, disclosed
prominently rather than buried in an ADR cross-reference: `ADR-0066`
(`WP 8.0B`) decided the Workspace's presentation would be a terminal
interface, not a graphical desktop framework, and named its own
reversal condition — a real, demonstrated need for a graphical
experience. The Product Owner's own Programme 10 commissioning, titled
"User Experience & **Desktop Application**" and naming multi-monitor
behaviour, theme architecture, and iconography as explicit required
topics, is that demonstrated need. `ADR-0092` formally supersedes
`ADR-0066` on this basis (full reasoning there, not repeated here);
`ADR-0093` separately supersedes `ADR-0065`, moving Digital Thread/
Object Relationship visualisation from a flat list to a progressively-
expandable graph (§12, `WP10.0A Digital Thread & Relationship
Visualisation.md`). Every other prior Workspace ADR (`ADR-0062`,
`ADR-0063`, `ADR-0064`, `ADR-0067`, `ADR-0068`, `ADR-0069`, `ADR-0070`,
`ADR-0071`) is reaffirmed, unchanged, by this Work Package — each was
already presentation-technology-agnostic, and remains correct under a
graphical desktop paradigm exactly as it was under a terminal one
(§14, ADR Summary).

## 1. UX Philosophy

This Work Package inherits `WP8.0A Workspace Architecture Document.md`
§1's own five philosophy points in full — none is reversed, each is
extended:

1. **The Workspace remains additive, not a replacement of the
   platform's own architecture.** Zero new Platform Service, zero new
   storage mechanism, zero new authorization model, and now confirmed:
   zero new Workspace *contract* either (§4).
2. **Every engineering object remains explorable in place.** The
   desktop paradigm strengthens this rather than weakening it — a
   graphical canvas has more room to show an object's Properties, its
   Digital Thread, and its editor simultaneously than a terminal's own
   character grid ever could (§7, §12).
3. **Reads remain direct; writes remain commands.** No exception is
   introduced anywhere in this Work Package's own scope, including
   Object Editors (§9) — editing a field is presentation-local state
   until a Command commits it, never a direct service mutation.
4. **The Workspace still does not know what an Engineering Discipline
   Module is.** Every screen this Work Package catalogues (`WP10.0A
   Screen Catalogue.md`) is composed from `INavigationProvider`/
   `ICommandRegistry`/Kind-keyed registration (`ADR-0067`), exactly as
   today — a graphical renderer changes nothing about this.
5. **Disclose, don't invent.** Every open question this document names
   (§15, Deliberately Out of Scope) says so explicitly, mirroring
   `WP8.0A`'s own discipline exactly.

**One new principle, added by this Work Package:** **6. A richer
presentation surface is not a licence to duplicate data.** `WP8.0A UI
Architecture.md` §3.3's "no View introduces its own query, cache, or
index" principle governs every new screen this Work Package specifies,
including the graph-based Object Relationship View (§12) — more pixels
available to render does not mean more data is fetched or cached
ahead of what a View actually displays at any given moment.

## 2. User Journeys, Extended

`WP8.0A Workspace Architecture Document.md` §2 named five journeys
against a Workspace that did not yet exist. All five remain valid and
are now exercised daily against six real disciplines. This Work
Package adds three more, each exercising a capability that either did
not exist (multi-project, object relationship graph) or was not
achievable (true multi-panel arrangement across monitors) before this
Work Package's own decisions:

6. **Work across two projects side by side.** An engineer with two
   `Project` objects open (`EngineeringDomainContext`, `WP 9.0A`)
   arranges one project's Document Area tabs on one monitor and the
   second project's on another, comparing a Requirement in one against
   a Calculation Record in the other — never possible under `ADR-0066`'s
   own single-terminal-window paradigm (§10, §11).
7. **Trace a relationship chain three hops deep, visually.** From an
   open Requirement, the engineer opens its Object Relationship View,
   sees its direct verification and reference links as a graph, and
   expands two further nodes in place — without losing the requirement's
   own position as the graph's centre, and without leaving the current
   tab (`ADR-0093`, `WP10.0A Digital Thread & Relationship
   Visualisation.md`).
8. **Recognise Verification objects by colour and icon alone, across
   every discipline.** An engineer scanning a densely populated Project
   Explorer tree distinguishes a `Test` from an `Inspection` from a
   `Requirement` in `Draft` from one `Released`, at a glance, before
   reading a single label — a capability a terminal's own constrained
   glyph set could approximate but never deliver at the fidelity this
   journey requires (`WP10.0A Visual Design System.md`).

## 3. Overall Application Layout

Full detail and wireframe: `WP10.0A Screen Catalogue.md` §2-3,
`WP10.0A Wireframe Sketches.md` §2.

The five-region model `WP8.0A Workspace Architecture Document.md` §3
established — Command Bar (top), Project Explorer (left dock), Document
Area (centre, tabbed), Properties/Digital Thread panel (right dock),
Status Bar (bottom) — is retained in full as the **default** layout.
What changes under a graphical paradigm is what surrounds it:

- A **Toolbar row** beneath the Command Bar, present but deliberately
  minimal (§10, Toolbar Philosophy) — the Command Bar remains the
  primary command surface; the toolbar surfaces only the small,
  stable set of actions worth one-click, icon-only access.
- The **Properties/Digital Thread panel** splits into two independently
  dockable panels for the first time — **Property Inspector** and
  **Object Relationship View** — rather than one panel with an internal
  mode switch, now that a graphical desktop application has genuine
  room for both simultaneously (§7, §12; a terminal's own screen real
  estate never justified this split).
- A reserved region for **Notifications** (§8), presented as a
  transient overlay/tray rather than a permanent sixth docked region —
  named explicitly so it is not silently conflated with the Status
  Bar's own always-visible summary line (§9).

## 4. Multi-Panel Workspace, Docking, and Resizable Panels

Full detail: `WP10.0A Screen Catalogue.md` §4, `WP10.0A Interaction
Specification.md` §1.

**Zero contract change.** `IWorkspaceLayout`, `WorkspacePanelPlacement`,
and `WorkspaceDockPosition` (`WP 8.0B`) already express exactly what a
graphical desktop docking model needs for docked panels: a position
(`Left`/`Right`/`Bottom`), a size (`double`, "deliberately unitless...
for example, a column count in a terminal" — now interpreted as
device-independent pixels, a documentation-only reinterpretation, not a
signature change), and visibility. Every docked-panel behaviour this
Work Package specifies — resize by drag, collapse, reopen at the same
size, independent visibility per panel — is already representable by
this existing contract, confirmed by direct re-read.

**One genuine gap, named and deferred, not designed here:**
`WorkspaceDockPosition` has "deliberately no `Floating` value" (its own
XML documentation, `WP 8.0B`) — undocking a panel into its own
top-level window, and placing that window on a specific monitor (§11),
both require a real contract extension. **Reserved as `ADR-0095`**, a
Contract Review Work Package's own question, named here (mirroring
`ADR-0066`'s own original treatment of what became `ADR-0092`) and
explicitly not designed under this Work Package's own "no contract
changes" instruction.

**Panels remain independently resizable and closable**, exactly as
`WP8.0A UI Architecture.md` §2 already specified — this Work Package
changes nothing about that behaviour, only the fidelity at which it is
rendered (pixel-precise drag vs. a terminal's own coarser column-based
resize).

## 5. Project Explorer Evolution

Full detail: `WP10.0A Screen Catalogue.md` §5, `WP10.0A Visual Design
System.md` §3.

`IProjectExplorer`/`ProjectExplorer`/`IProjectExplorerNodeProvider`
(`WP 8.0B`/`WP 8.1B`) are unchanged. What evolves is presentation
density and legibility, now that six real disciplines populate the
tree simultaneously (`MechanicalProductStructureNodeProvider`,
`RequirementsNodeProvider`, `CalculationsNodeProvider`,
`VerificationActivityNodeProvider`, `DocumentsNodeProvider`,
`ManufacturingNodeProvider` — six registered `IProjectExplorerNodeProvider`
implementations today, confirmed by direct read of `Program.cs`):

- **Kind-keyed iconography** (`WP10.0A Visual Design System.md` §2)
  gives every node a distinct glyph by `Kind`, not only by discipline
  area — a `Part` reads differently from an `Assembly`; a `Test`
  differently from an `Inspection`, even though both are
  `VerificationActivity`-Kind-family objects.
  `ProjectExplorerNodeType`/`ProjectExplorerNode` (`WP 8.1B`) already
  carry everything an icon-resolution layer needs (`Kind`, node type) —
  zero contract change.
- **Lifecycle-state colour coding** (`WP10.0A Visual Design System.md`
  §4) — `Draft`/`InReview`/`Approved`/`Released`/`Archived` each render
  in a fixed colour from the Engineering colour language, consistently
  across every discipline's own tree nodes, Cockpit KPI cards (§8), and
  object editors (§9).
- **Denser, multi-column presentation** where a terminal's own
  single-line-per-node layout previously forced truncation — a
  graphical row can show a node's label, Kind icon, lifecycle colour
  chip, and a compact revision indicator together, using
  `ProjectExplorerNode`'s own already-exposed fields, none of which
  needs to change.
- `ProjectExplorer.FilterAsync` (`WP 8.1B`) — the same generic search
  mechanism every discipline already inherits for free — is unchanged
  and remains the Project Explorer's own filter/search backbone (§12
  pointer; full detail `WP10.0A Interaction Specification.md` §3).

## 6. Property Inspector Evolution

Full detail: `WP10.0A Screen Catalogue.md` §6, `WP10.0A Wireframe
Sketches.md` §3.

`IPropertyInspector`/`PropertyInspector`/`IPropertyFacetProvider`/
`PropertyFacet`/`PropertyFacetKind` are unchanged. Every one of six
real `IPropertyFacetProvider` implementations already composes its own
facets from `PropertyFacetKind`'s existing closed vocabulary
(confirmed by direct read: `MechanicalPropertyFacetProvider`,
`RequirementsPropertyFacetProvider`, `CalculationsPropertyFacetProvider`,
`VerificationActivityPropertyFacetProvider`,
`DocumentsPropertyFacetProvider`,
`ManufacturingOperationPropertyFacetProvider` — the last two Kind-family
providers reused directly by Manufacturing for `"Inspection"`/
`"WorkInstruction"`, `WP 9.5A`, a fact this document reconfirms rather
than repeats). What evolves is presentation only: facets render as a
structured, grouped panel (Identity / Lifecycle / Discipline-Specific /
Relationships, a fixed four-group ordering applied uniformly across
every Kind) rather than a terminal's own flat key-value list, using
exactly the same `PropertyFacet` data each provider already returns.

**Now formally split from the Object Relationship View** (§3, §12) —
the Property Inspector shows facts *about* the selected object; the
Object Relationship View shows what it is *connected to*. `WP8.0A`'s
own combined "Properties/Digital Thread panel" framing is retired in
favour of this split, disclosed here as a presentation reorganisation,
not a contract change — both panels read from the identical services
they always have.

## 7. Engineering Cockpit Evolution

Full detail: `WP10.0A Screen Catalogue.md` §2, `WP10.0A Visual Design
System.md` §4.

`EngineeringCockpit` (`WP 8.1C`, extended by every real-discipline Work
Package since) is unchanged at the data layer — `CockpitKpiCard`,
`CockpitAttentionItem`, `CockpitActionItem`, `EngineeringHealthStatus`,
and all six disciplines' own KPI card sets remain exactly as
implemented. This Work Package specifies the Cockpit's **next**
graphical presentation: KPI cards render as real visual cards (a
coloured status chip per `EngineeringHealthStatus`, not a text label),
arranged in a responsive grid that reflows across monitor widths (§11)
rather than a terminal's own fixed-column layout; Attention Items and
Open Actions render as a scannable, iconified list rather than a
numbered text menu. No new Cockpit member is added by this Work
Package — `ManufacturingStatus` (`WP 9.5A`) remains the most recently
added, and this Work Package touches zero Cockpit source.

## 8. Object Editors

Full detail: `WP10.0A Screen Catalogue.md` §9, `WP10.0A Wireframe
Sketches.md` §3.

**A genuinely new named surface, resolved here as an editable View, not
a new contract.** `WP8.0A UI Architecture.md` §3.1 already defined a
View as rendering "exactly one engineering object" — an Object Editor
is that same View, made field-editable, still bound by `WP8.0A`'s own
"reads direct, writes via Commands" principle (§1, Point 3; reaffirmed
§1 above). Editing a field updates presentation-local state only (an
in-memory draft, never written anywhere); committing (explicit "Save,"
or a field-level blur-to-commit where a discipline's own Command is
narrow enough — e.g. `RenameRequirementObjectCommand`-shaped) dispatches
the exact same `IWorkspaceCommand`/`ICommandDispatcher` path every
discipline's own Rename/Revise/SetStatus commands already use. **Zero
new contract**: no `IWorkspaceEditor` interface is introduced:
`IWorkspaceView` already suffices, distinguished only by whether the
View's own concrete implementation renders its fields as read-only text
or as editable controls — an implementation-phase choice, not an
architecture one.

An Object Editor tab shows a **dirty-state indicator** (an asterisk or
equivalent glyph on its own tab, §10) whenever presentation-local draft
state differs from the last-committed read — itself presentation-only
state, never persisted, discarded on tab close exactly as `WP8.0A UI
Architecture.md` §5's own "current object data... not cached" row
already establishes.

## 9. Tabbed Document System

Full detail: `WP10.0A Screen Catalogue.md` §3, `WP10.0A Interaction
Specification.md` §5.

The Document Area remains "always present and always tabbed... the one
region that cannot be closed" (`WP8.0A Workspace Architecture
Document.md` §7), unchanged. Two refinements, both presentation-only:

- **Tab grouping by Project** (§11, Multi-Project Workflow) — when more
  than one `Project` is open, tabs visually cluster by owning project,
  never interleaved arbitrarily, so an engineer working across two
  projects can tell at a glance which tab belongs to which.
- **Tab overflow** — a graphical desktop application's own tab strip
  can grow wide enough to need overflow handling (a scrollable strip, or
  an overflow menu) in a way `TempestShell`'s own single-page-at-a-time
  model never needed to consider. Named here as a real UX requirement;
  the specific overflow mechanism is an implementation-phase choice.

`WorkspaceStateDto.OpenViewIds` (`WP 8.1A`) already persists exactly
"which objects, in what order" (`WP8.0A UI Architecture.md` §5) —
unchanged, sufficient for both refinements above without any schema
change.

## 10. Notifications

Full detail: `WP10.0A Screen Catalogue.md` §16, `WP10.0A Wireframe
Sketches.md` §6.

**Named here for the first time as a Workspace-level UX surface** — no
prior Workspace architecture document specified one; `WP 6.2`'s own
Notification Framework (`Tempest.Core`, Platform Service) exists today
with zero Workspace-level presentation consumer. This Work Package
specifies, at the architecture level only, that the Workspace's own
Notification tray is a **read-only presentation of the existing
Notification Framework** — no new Platform Service, no new delivery
mechanism, mirroring exactly how every other Workspace surface in this
document composes an existing service rather than inventing one. Full
integration (which `INotificationService` methods a future
implementation Work Package calls) is explicitly deferred to that
future Work Package — this document names the requirement and the
composition pattern to follow, not a finished contract-level design.

## 11. Status Bar and Toolbar Philosophy

Full detail: `WP10.0A Screen Catalogue.md` §11, §15.

`WorkspaceStatusBar` (`WP 8.1A`) is unchanged — current selection,
lifecycle status, and Diagnostics remain its own three data sources.
Presentation only changes: a graphical Status Bar renders these as a
segmented row (selection breadcrumb | lifecycle colour chip |
Diagnostics summary icon) rather than a terminal's own concatenated
text line.

**Toolbar philosophy, stated as a principle, not a fixed toolbar
design:** the toolbar is a *convenience*, never a *capability* — every
action available from the toolbar is already reachable from the
Command Bar/Command Palette (§12 pointer) and, where applicable, a
context menu (§12 pointer). No action is ever toolbar-only. This
mirrors `WP8.0A Workspace Architecture Document.md` §1 Point 4's own
"Workspace does not know what a Discipline Module is" principle applied
to the toolbar specifically: a discipline module registering a new
`CommandDescriptor` (`ADR-0067`) becomes toolbar-eligible automatically
under whatever inclusion rule a future implementation Work Package
sets (e.g. a `CommandDescriptor.IsPinnedToToolbar`-shaped flag,
explicitly not designed here — a contract question, deferred).

## 13. Session Persistence

`ADR-0064` (`WP 8.0A`) — Workspace layout/session state is persisted via
`ISettingsProvider`, no new persistence mechanism — is unchanged and
reaffirmed. `WorkspaceStateDto` (`PanelPlacements`, `OpenViewIds`,
`LastSelection`) already carries everything a graphical desktop session
needs to restore: panel arrangement, open tabs, last selection. **One
genuine future extension, named not designed:** multi-monitor placement
(§11) will eventually need each panel's own placement to additionally
record *which monitor* — a field addition to `WorkspacePanelPlacement`,
folded into the same `ADR-0095` Contract Review this document already
reserves for the Floating dock position (§4), not a second, separate
contract question.

## 14. Multi-Project Workflow

`EngineeringCockpit.RecentProjects` (`WP 9.0A`) and `Project`'s own
existing Domain representation already support more than one `Project`
existing in the underlying data. What has never been specified is
whether the **Workspace** supports more than one open *simultaneously*
— today's Workspace, and every prior architecture document, is
implicitly single-project-at-a-time. This Work Package specifies: **a
graphical desktop application supports multiple open Projects
simultaneously**, each with its own Project Explorer root and its own
cluster of Document Area tabs (§9), switchable via the Command Bar's
own global navigation (§3) without closing the other. This is a
genuinely new capability relative to every prior Workspace document —
disclosed as such, not presented as an existing behaviour this Work
Package merely writes down. It requires no new contract:
`IWorkspaceContext`/`ISelectionService` are already scoped per-caller,
not process-global singletons, confirmed by direct read — multiple
concurrent contexts are already representable, only never previously
specified as a supported *user-facing* arrangement.

## 15. Multi-Monitor Behaviour

At the architecture level, multi-monitor behaviour is two capabilities,
named separately because they carry different implementation cost:

1. **Panel arrangement spanning monitor width** — a single
   application window, wide enough to span multiple monitors, laying
   out its own docked panels across that combined width. This requires
   **no contract change** — `WorkspacePanelPlacement.Size` already
   accommodates any width.
2. **Independent top-level windows per panel, placed on distinct
   monitors** — this is the same capability §4 already named and
   deferred to `ADR-0095` (the `Floating` dock position). This Work
   Package does not design it twice; §4 is the canonical reference.

## 18. Deliberately Out of Scope

- **No implementation, no code, no contract changes** — this Work
  Package's own explicit constraint, honoured throughout; every
  capability named above is confirmed representable by existing
  contracts, or explicitly deferred with a reserved ADR number where it
  is not.
- **No concrete UI framework decision** (§17, `ADR-0094` reserved).
- **No floating/undocked panel or multi-monitor placement contract
  design** (§4, §15, `ADR-0095` reserved).
- **No Notification Framework integration design** (§10) — the
  requirement and composition pattern are named; the concrete
  `INotificationService` call sites are deferred.
- **No toolbar pinning contract design** (§11) — the principle is
  named; the mechanism is deferred.
- **No changes to any existing Platform Service, Engineering Core, or
  Workspace contract** — reconfirmed directly, by name, throughout this
  document, not merely asserted once at the top.
