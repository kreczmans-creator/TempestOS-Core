# WP 10.0B — Architecture Review

## Purpose

An independent architecture review of `Tempest.Desktop`'s own real
structure against `WP10.0A`'s own architecture, `FOUNDATION.md`'s
non-negotiables, and the two disclosed changes to `Tempest.App.Workspace`.

## 1. Conformance to `WP10.0A`'s Own Predictions

`WP10.0A Architecture Review.md` §5 (Risk 2) named this exact moment:
"this review recommends the first implementation Work Package
explicitly re-confirm 'zero contract change' empirically once real
rendering code exists, rather than treating this package's own
prediction as already proven." This review confirms that
re-confirmation happened, and passed — `WP10.0B Engineering Review.md`
§3 independently re-verified every Workspace contract unchanged
against real, running `Tempest.Desktop` code, not merely against the
prior architecture documents' own prose.

`WP10.0A UX Architecture Document.md` §4's own reserved question,
`ADR-0095` (floating/multi-monitor contract extension), is correctly
**not** touched — `DockingGrid` supports exactly Left/Right (the two
positions `WorkspaceDockPosition` actually has), never simulating a
`Floating` capability the contract does not yet offer.

## 2. `EngineeringWorkspaceComposer` — The Correct Composition-Root Shape

This review independently assessed whether extracting shared
composition logic was the right structural choice, rather than each
presentation layer duplicating it. It is: `FOUNDATION.md`'s own
non-negotiable #2 ("every component has exactly one reason to change")
applies directly here — before this Work Package, the *only* code that
could add, remove, or reorder a discipline's registration was
`Program.cs`'s own top-level statements; a second presentation layer
duplicating that sequence would have created a *second* reason to
change the same fact, exactly the shape non-negotiable #2 exists to
prevent. `EngineeringWorkspaceComposer` restores "one reason to
change" by making both presentation layers depend on the same single
source.

## 3. `WorkspaceHost` as a Genuine Composition Root, Not a God Object

Reviewed against `ADR-0033`'s own composition-root precedent
(`TempestShell`): `WorkspaceHost` owns exactly the `ITempestHost`/
`WorkspaceManager` lifecycle and nothing else — it does not know about
`MainWindow`, Avalonia, or any View. `MainWindow` depends on
`WorkspaceHost`; `WorkspaceHost` has no dependency in the reverse
direction. This one-directional dependency is confirmed by direct
read of `using` directives across both files — `WorkspaceHost.cs`
imports no Avalonia namespace at all, meaning the entire Workspace
composition sequence remains genuinely independent of any UI
framework, exactly mirroring `ADR-0092`'s own central claim that the
Workspace layer stays rendering-agnostic.

## 5. Architectural Risk Assessment

**Risk 1 — `TD-26`'s own mitigation lives in the wrong layer, long-term.**
`WorkspaceHost`'s own bounded poll (`WP10.0B Implementation Report.md`
§6.6) is a correct, minimal, disclosed mitigation for *this* Work
Package's own scope — but it means the actual fix (making
`WorkspaceManager.StartAsync` itself await module initialisation, or
exposing a real "fully ready" signal) still does not exist anywhere in
the platform. Every *future* consumer of `WorkspaceManager` — not only
`Tempest.Desktop` — remains exposed to `TD-26`'s own root cause. This
review recommends `TD-26`'s own priority be reconsidered now that a
second, independent consumer (this Work Package) has hit its
consequences directly (`WP10.0B Technical Debt Review.md`).

**Risk 2 — No `.axaml` markup is a deliberate, disclosed, but real
constraint on future maintainability.** Pure-C# UI construction avoids
a second build pipeline today, but as `Tempest.Desktop` grows (richer
Object Editors, the graph-based Relationship View), C#-constructed
visual trees become markedly harder to read and modify than XAML at
scale. This review does not treat this as wrong for this Work
Package's own first-iteration scope, but flags it as a decision a
future implementation Work Package should revisit deliberately, not
inherit by default.

**Risk 3 — First-ever GUI dependency, now real.** Already named by
`ADR-0092`/`ADR-0094`; this review adds no new information, only
confirms the cost is now paid, not merely anticipated.

## 6. Verdict

**Sound.** `WP10.0A`'s own architecture survives contact with real
implementation without a single contract change, confirmed
independently rather than trusted. The one structural risk worth
carrying forward (`TD-26`'s own layer-of-fix question) is named
plainly, not buried.
