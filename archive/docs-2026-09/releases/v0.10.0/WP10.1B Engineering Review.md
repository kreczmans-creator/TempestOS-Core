# WP 10.1B — Engineering Review

## Purpose

An independent, direct-source verification of every claim
`WP10.1B Implementation Report.md`/`WP10.1B Root Cause Analysis.md`
make — not a summary of them.

## 1. `TD-26` Fix — Verified Directly

Re-read `src/Tempest.App/Workspace/WorkspaceManager.cs`'s own
`WaitForServicesAsync` against `TempestHost.cs`'s own phase ordering,
independently of the Implementation Report's own description. Confirmed:
`_services` is assigned inside `ExecuteStartupPhasesAsync` strictly
before `ModuleLifecycleManager.InitialiseAllAsync`/`StartAllAsync` are
awaited, and `EnterRunning()` (setting `HostState.Running`) is called
only after `ExecuteStartupPhasesAsync` returns without throwing — i.e.
only after both of those complete. `WaitForServicesAsync`'s new second
loop therefore genuinely cannot return before Module Initialisation and
Start both finish. The `ThrowIfHostRunFaulted()` guard was traced
against `TempestHost.RunAsync`'s own `catch` blocks: a fault during
`ExecuteStartupPhasesAsync` completes `_runCompletion`'s underlying task
with a fault (via `finally { _runCompletion.TrySetResult(); }` — note:
`TrySetResult`, not `TrySetException`, so the *`_hostRunTask`* returned
by `RunAsync` itself carries the fault via its own `catch`/`throw`, not
`_runCompletion`) — confirmed `_hostRunTask.IsCompleted` correctly
becomes `true` with a faulted `Task` in this case, so
`task.GetAwaiter().GetResult()` correctly rethrows rather than hanging.

## 2. `TD-37` Fix — Verified Directly

Read all four modified sample modules end to end, not only the diffed
hunks. Confirmed for each: the idempotency check precedes every durable
write the module performs (no partial work occurs before the check),
and the check itself queries the exact same durable index the module's
own first write would otherwise collide against (`FindAsync`/
`FindByIdentifierAsync` against the identical `materialId`/`Identifier`
literal each module's own `RegisterAsync`/`CreateAsync` call uses) — not
a proxy or a different identifier. `EngineeringDomainSampleModule`'s
extracted `RegisterGraphSummaryCommand()` was confirmed reachable from
both branches (skip and full-seed), and confirmed to register
identically either way — no behavioural drift between the two paths
beyond the documented, disclosed Id-property difference.

## 3. Test Isolation — Verified Directly

Confirmed, by direct `grep`, that all 17 pre-existing `new WorkspaceHost()`
call sites across `CommandPaletteOverlayTests.cs`, `EngineeringCockpitTests.cs`,
`ThemeServiceTests.cs`, and `WorkspaceIntegrationTests.cs` were updated —
none left passing no argument (which would silently fall back to the
real, shared, working-directory-relative store and reintroduce exactly
the collision this Work Package fixes). Confirmed the two paired-host
tests (`ThemeServiceTests.LoadAsync_OnAFreshHost_ReadsThePreviouslyPersistedChoiceBack`,
`WorkspaceIntegrationTests.PersistentLayouts_HidingAPanelAndRestarting_RestoresTheSameLayout`)
each compute their own isolated path exactly once and pass the same
value to both hosts — the one case where sharing state within a test is
correct and intended (`ADR-0064`/`TD-35`), not a regression of the
isolation fix.

## 4. `TD-38` — Confirmed a Genuine, Separate, New Finding

Independently re-read `EngineeringObjectFactory<T>.CreateAsync`
(`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectFactory.cs`)
directly: confirmed it performs no uniqueness check of any kind against
the `businessId`/display-identifier argument its callers pass — every
call unconditionally creates a fresh document with a new `Guid`. Cross-
checked `MechanicalProductStructureSampleModule` (not itself one of the
four `TD-37`-affected modules) to confirm the same pattern reproduces
there too, independent of Materials'/Requirements' own separate
uniqueness enforcement. Confirmed `IEngineeringObjectRepository`'s own
XML documentation states it is in-memory-only, unchanged since `WP
8.2C`. `TD-38` is correctly scoped: fixing it would require an
Engineering Domain change (uniqueness enforcement or durable-store
rehydration), explicitly out of this Work Package's own stated scope —
disclosure, not a fix, is the correct action here, mirroring this
project's own established "disclose, don't necessarily fix everything
found" precedent (`TD-26` itself is the exact precedent this mirrors).

## 5. Regression Coverage — Verified Directly

Read every new test's own assertions, not merely its name.
`ModuleLifecycleStabilityTests.AssertNoFailedModules` was confirmed to
both (a) assert `HostState.Running` and (b) individually assert each of
the four previously-affected modules is `ModuleState.Running` by name —
a materially stronger proof than merely "the failed-module list is
empty," which could pass vacuously if `Modules` were unexpectedly
empty. Confirmed `IntentionallyFailingModuleId`'s exclusion is
correctly scoped to only that one, permanently-failing, by-design
module — not a blanket exclusion that could hide a genuine new failure
elsewhere.

## 6. Zero Engineering Domain Changes — Confirmed

`git diff --stat` against this Work Package's own full change set,
independently re-run: zero files under `src/Tempest.Core/EngineeringDomain/`
appear. Every change lives in `Tempest.App.Workspace`, `Tempest.Desktop`,
`Tempest.App.Composition`, `Tempest.Samples`, or test projects.

## 7. Recommendation

**Sound, complete.** Both named items (`TD-26`, `TD-37`) genuinely
root-caused, not merely mitigated a second time; both fixes verified
directly against source, not trusted from the Implementation Report's
own description; the one new finding (`TD-38`) correctly, proportionately
scoped and disclosed rather than either ignored or over-reached into
forbidden Engineering Domain territory.
