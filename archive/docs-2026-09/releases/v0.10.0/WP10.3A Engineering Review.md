# WP 10.3A — Engineering Review

## Purpose

An independent technical review of `WP 10.3A`'s own real implementation
— whether the Object Editor Framework's own claims are genuinely true
against the real diff and the real, re-run test suite, whether `ADR-0063`
is genuinely honoured throughout, and whether `ADR-0097` is correctly
scoped.

## 1. `ADR-0063` — Independently Re-Verified, Not Merely Asserted

Read `ObjectEditorView.cs` in full, line by line, checking every call
against a real Domain object for whether it reads or mutates. Confirmed:
every direct call (`Content`/`Status`/`History`/`GetRelationshipsAsync`/
`ValidateAsync`) is a read-only member, confirmed by cross-reading each
interface directly (`Facets.cs`, `Validation.cs`) — none has a mutating
side effect. Both actual mutations (`OnSaveAsync`) go exclusively
through `IWorkspaceManager.RenameObjectAsync`/`ReviseObjectAsync`, both
of which dispatch through `CommandHandlerTable.DispatchAsync`,
confirmed by direct re-read of `WorkspaceManager.cs`. **Zero direct
calls to `IHasRevisions.ReviseAsync`, `IHasLifecycle.TransitionAsync`,
or `IHasRelationships.LinkAsync` exist anywhere in this Work Package's
own diff** — confirmed by a direct `grep` across every new/modified
file.

## 2. `TryCreate`'s Own Null-Return Behaviour — Verified Correct

Re-read `ObjectEditorView.TryCreate` directly: `domainContext.Repository.FindAsync(objectId)`
returning `null` is the sole condition for returning `null`. Cross-checked
against `CalculationsWorkspaceRegistration`'s own synthetic
`"CalculationTemplate"` Kind (confirmed never an `EngineeringDomainContext.Repository`
object, per that class's own remarks, unmodified) and
`SampleWorkspaceViewFactory`'s own fixed sample content (confirmed
unrelated to `EngineeringDomainContext` entirely) — both correctly fall
through to `DocumentAreaView.BuildDefaultBody`, confirmed by
`ObjectEditorViewTests.TryCreate_NonExistentObjectId_ReturnsNull`, re-run
by this review and confirmed passing.

## 3. Six Disciplines, One Engine — Verified, Not Overstated

Confirmed by direct re-read of all six `*WorkspaceRegistration.cs`
files: every real Kind (Mechanical's own product-structure Kinds,
Requirement, Calculation/CalculationSet, VerificationActivity,
Document/Drawing/CadModel, ManufacturingOperation, plus
WorkInstruction/Inspection) already resolves via
`EngineeringDomainContext.Repository`, confirmed by the same
`EngineeringObjectBase`/`ADR-0075` composition every real Kind class
already inherits from — none needed a Desktop-side per-Kind
registration to work with `ObjectEditorView`, confirmed by the complete
absence of any Kind-keyed registry in `Tempest.Desktop/Editors/`.

## 4. `ADR-0097` — Correctly Scoped, Not Over-Reaching

Re-read `IWorkspaceManager.cs`'s own diff directly: exactly three new
members (`RegisterReviseFactory`/`CanRevise`/`ReviseObjectAsync`), zero
existing members touched. Confirmed the exact same
`Dictionary<string,T>`/`TryAdd`/`DuplicateWorkspaceRegistrationException`
shape `RegisterRenameFactory` already established, byte-for-byte
structurally identical in `WorkspaceManager.cs`. Confirmed
`ReviseMechanicalObjectCommand`/`ReviseMechanicalObjectCommandHandler`
are structurally identical to `ReviseCalculationCommand`/its own
handler, differing only in namespace and the one, correctly-scoped
addition (Mechanical's own missing sixth command).

## 5. Dirty-State — Distinct From `IWorkspaceView.IsDirty`, Confirmed Not Confused

Re-read `ObjectEditorView.IsDirty`'s own doc comment and
`DocumentAreaView.MarkDirty`'s own implementation directly — confirmed
the tab header combines both sources (`_extraDirtyFlags.Contains(view.Id)
|| view.IsDirty`), never silently replacing the frozen contract member's
own semantics. Confirmed by direct read that no concrete `IWorkspaceView`
implementation was touched — `MechanicalWorkspaceView.IsDirty` (and its
five siblings) still unconditionally return `false`, unmodified.

## 6. One Genuine, Disclosed Test-Arithmetic Finding

`MechanicalWorkspaceIntegrationTests.CommandRegistry_ListsAllNineMechanicalCommands`
failed on first full-suite run after this Work Package's own change
(`Expected: 9, Actual: 10`) — independently confirmed to be the direct,
correct consequence of this Work Package's own new
`"mechanical.edit"` `CommandDescriptor`, not a genuine defect. Fixed in
place (renamed, count corrected to 10), re-run, confirmed passing. The
other five disciplines' own identical hardcoded-count tests (Requirements
18, Calculations 14, Documents 11, Verification 11, Manufacturing 10)
were independently re-checked and confirmed unaffected — none of the
five needed a new `CommandDescriptor` this Work Package, since each
already had its own `"...edit"`/`"...revise"` descriptor from its own
original Work Package.

## 7. Zero Forbidden-Scope Changes — Confirmed

Direct `git diff --stat` review against the controlling instruction's
own five named exclusions: no Runtime redesign (zero
`src/Tempest.Core/Runtime/` files); no Workspace redesign (twelve
frozen contracts unmodified, one precedented additive extension only);
no ribbon; no floating windows (`ObjectEditorView` is an ordinary
`UserControl`, hosted inside the existing `DocumentAreaView` tab strip
— no `new Window(...)` anywhere in the diff); no Digital Thread graph
(the Relationship summary is a flat list, confirmed by direct read of
`PopulateRelationships` — no node-link/graph data structure of any
kind).

## 8. Recommendation

**Sound, complete.** `ADR-0063` independently re-verified honoured
throughout, not merely claimed; the "one engine, six disciplines"
design independently confirmed to need zero per-Kind Desktop
registration; `ADR-0097` correctly, minimally scoped; the one
pre-existing test failure correctly diagnosed as an expected
consequence, fixed, and disclosed, not silently patched over.
