# WP 10.1B — Runtime Host & Module Discovery Hardening — Root Cause Analysis

## Purpose

`WP 10.1B`'s own controlling instruction opens: "Investigate and resolve:
`TD-26`, `TD-37`. Determine the true root cause(s)." This document is
that investigation record — read first, before `WP10.1B Implementation
Report.md`, since every fix that report describes follows directly from
a finding recorded here.

Both items were reconfirmed, not re-diagnosed from nothing: `TD-26` was
already precisely described (`docs/governance/Quality/Technical Debt
Register.md`, added `WP 9.0A`); `TD-37`'s own register entry already
ruled out two of three candidate explanations (cross-test contamination,
a retry mechanism) and left one open ("most plausibly that each affected
module's own `InitialiseAsync` is somehow invoked more than once against
the same running singleton service — unconfirmed"). That remaining
candidate is examined first, below, and rejected.

## 1. `TD-26` — Confirmed Root Cause

**`WorkspaceManager.StartAsync`'s own `WaitForServicesAsync` returned as
soon as `ITempestHost.Services` became non-null** —
`src/Tempest.App/Workspace/WorkspaceManager.cs`, unchanged since `WP
9.0A`. Reading `TempestHost.ExecuteStartupPhasesAsync`
(`src/Tempest.Core/Runtime/TempestHost.cs`) directly confirms the exact
phase ordering already named in the register:

```
...
services.AddDiscoveredModules(...)
ITempestServiceProvider serviceProvider = new TempestServiceProvider(...)
_services = serviceProvider;                     // <- Services becomes non-null HERE
logger.Information("... Dependency Injection Built.");
...
var lifecycleManager = new ModuleLifecycleManager(...)
await lifecycleManager.InitialiseAllAsync(...)    // <- every module's InitialiseAsync runs AFTER
await lifecycleManager.StartAllAsync(...)
logger.Information("... Module Initialisation.");
```

`ITempestHost.Services` is set during Phase 6 ("Platform Services
Registered"); Module Initialisation is Phase 7. A caller that returns as
soon as `Services` is non-null can therefore observe the Workspace
mid-Phase-7 — before any module's own `NavigationItem` registration or
Engineering Domain seeding has run. This is precisely `TD-26`'s own
description; nothing new was found here beyond confirming it directly
against the current source, unmodified since first disclosed.

**Root cause: a caller-side readiness check keyed on the wrong signal**
(`Services != null`, a Phase-6 event) **instead of the Runtime Host's
own authoritative "every module has finished initialising and starting"
signal** (`IDiagnosticsProvider.HostState == HostState.Running`, set only
after Phase 7 completes — `TempestHost.cs`'s own `EnterRunning()`, called
only once `ExecuteStartupPhasesAsync` returns without throwing). `WP
10.0B` and `WP 10.1A` each independently rediscovered this same gap and
mitigated it one layer up, in `Tempest.Desktop`'s own `WorkspaceHost`,
using exactly that authoritative signal — proving the fix, without ever
applying it at `WorkspaceManager`'s own source. See `WP10.1B
Implementation Report.md` §1 for the fix now applied there directly.

## 2. `TD-37` — Investigation

### 2.1 Ruling out double-invocation

`TD-37`'s own register entry left one candidate open: `InitialiseAsync`
somehow invoked twice per affected module. `ModuleLifecycleManager`
(`src/Tempest.Core/Modules/ModuleLifecycleManager.cs`) was re-read line
by line:

- `InitialiseAllAsync` iterates `_orderedModules` — a `List<TrackedModule>`
  snapshotted once, at construction, from `IRuntimeModuleManager.GetAll()`
  — exactly once per module.
- `TransitionAsync` requires `tracked.State == ModuleState.Registered`
  before it will call `InitialiseAsync`; the first successful call moves
  state to `Initialising` then `Initialised`, and a second call against
  the same `ModuleLifecycleManager` instance would throw
  `InvalidModuleLifecycleTransitionException` immediately, never
  reaching `InitialiseAsync` a second time.
- `RunBatchAsync`'s own per-module `catch (Exception)` swallows exactly
  that kind of "not eligible for this phase" exception and moves on —
  it does not retry.

**Confirmed: no double-invocation exists anywhere in the module
pipeline.** `TD-37`'s own remaining candidate is rejected. The true root
cause lies elsewhere — outside `IModuleLifecycleManager`/
`RuntimeModuleManager` entirely, both of which were re-confirmed fully
deterministic, single-pass, and correct.

### 2.2 The actual mechanism — durable, cross-launch persistence

Reading `MaterialCatalog.RegisterAsync`
(`src/Tempest.Core/Materials/MaterialCatalog.cs`) shows the real
mechanism directly:

```csharp
if (await ReadDocumentIdAsync(materialId, cancellationToken) is not null)
    throw new DuplicateMaterialException(materialId);
...
await _persistenceStore.WriteAsync(IndexCollectionName, materialId, document.Id.ToString("N"), ...);
```

`IMaterialCatalog`'s own `materialId` index (`ADR-0055`) — and
`IRequirementsService`'s own `Identifier` index (`ADR-0058`), confirmed
by the identical shape — are both built directly on
`IPersistenceStore`, which is a real, file-backed, durable store
(`src/Tempest.Core/Persistence/PersistenceStore.cs`), not an in-memory
one. Its root path (`PersistenceStore.DefaultRootPath = "persistence-data"`)
is resolved once, at construction, relative to the process's own
working directory, and defaults unconfigured everywhere `WP 10.1B`
checked: the console `Program.cs`, `Tempest.Desktop`'s own
`WorkspaceHost`, and (critically) every `Tempest.Desktop.Tests` fixture
before this Work Package.

**Direct file-system evidence** (found before any fix was written):

```
tests/Tempest.Desktop.Tests/bin/Debug/net10.0/persistence-data/Materials.Index/SAMPLE-MAT-001
tests/Tempest.Desktop.Tests/bin/Debug/net10.0/persistence-data/Materials.Index/sample.fictional-test-alloy
tests/Tempest.Desktop.Tests/bin/Debug/net10.0/persistence-data/Requirements.Index/SAMPLE-REQ-001
tests/Tempest.Desktop.Tests/bin/Debug/net10.0/persistence-data/Requirements.Index/REQ-STR-001 ... REQ-STR-006
tests/Tempest.Desktop.Tests/bin/Debug/net10.0/persistence-data/Requirements.Index/REQ-AV-001 ... REQ-AV-999
```

Every one of these files already existed, on disk, in the test
project's own build output directory, **before the affected module ever
ran a second time in this investigation** — left there by an earlier
test run. The test project's own working directory is reused, unmodified,
run after run, exactly like a real user's own application launch
directory: `dotnet test`/the desktop application both resolve
`persistence-data` relative to wherever the process starts, and neither
this test project nor the real application ever cleans it between runs.

**Root cause, confirmed:** `MaterialsSampleModule`, `EngineeringDomainSampleModule`,
`RequirementsSampleModule`, and `RequirementsWorkspaceSampleModule` each
register one or more fixed, literal business identifiers
(`"SAMPLE-MAT-001"`, `"SAMPLE-REQ-001"`, `"REQ-STR-001"`, etc.) against a
Platform Service that durably, correctly enforces uniqueness for that
identifier across the store's own entire lifetime — which, by design
(`ADR-0041`), spans every process launched from the same working
directory, not just the current process. The very first successful
launch from a given working directory durably writes that identifier;
every subsequent launch's sample-module seeding then collides with its
own prior work and fails loudly. This is not a Runtime Host defect, not
a Module Discovery defect, not a double-invocation, and not a genuine
cross-module identifier collision (each identifier is unique to its own
module, confirmed `WP 10.1A`) — it is **sample/demonstration data,
carrying literal fixed identifiers, seeded against a real, durable store
that was never reset between runs**, exposed the moment any consumer
launched the same host twice from the same directory (a scenario no
Workspace test exercised before `Tempest.Desktop`'s own headless test
suite existed).

### 2.3 A second, related, non-crashing finding

`EngineeringDomainSampleModule` builds five objects (`Portfolio`,
`Programme`, `Project`, `Assembly`, `SubAssembly`) through
`EngineeringObjectFactory<T>` **before** reaching the Material
registration that crashes. `EngineeringObjectFactory<T>` was read
directly and confirmed to enforce **no** business-identifier uniqueness
of its own — each `CreateAsync` call always creates a fresh document
with a new `Guid`, regardless of whether its own literal
`"SAMPLE-PORT-001"`-style identifier already exists elsewhere. The same
pattern was confirmed in `MechanicalProductStructureSampleModule`. This
means every sample module built directly on `EngineeringObjectFactory<T>`
(not routed through Materials'/Requirements' own separate, durable
uniqueness indices) silently creates a **duplicate** object graph, with
the same displayed identifier text, on every restart — never crashing,
but never idempotent either. Registered as new Technical Debt item
`TD-38` (`docs/governance/Quality/Technical Debt Register.md`), disclosed
and explicitly **not** fixed in this Work Package — see §4, below, for
why.

A further, related, purely architectural observation, confirmed while
tracing this: `IEngineeringObjectRepository`/`IEngineeringRelationshipRepository`
(`Tempest.Core.EngineeringDomain`) are documented, by their own XML
comments, as **in-memory only** — "never a replacement for
`IEngineeringDocumentStore`, which remains the sole source of durable...
truth." No rehydration step reads the durable document store back into
this in-memory index on startup. This is confirmed to be `WP 8.2C`'s own
original, deliberate scope decision (not a regression), but it is the
direct reason `TD-38`'s own silently-duplicated objects are strictly
*invisible* to a Workspace read the moment the process that created them
exits — not merely duplicated, but orphaned. Recorded as part of
`TD-38`'s own disclosure; a genuine Engineering Domain rehydration
capability is explicitly out of this Work Package's own "No Engineering
Domain changes" scope.

## 3. Why the standard test suite never caught this

Every `Tempest.Core.Tests` fixture that builds a real module pipeline
(`RequirementsSampleModuleIntegrationTests.BuildPipeline` and its
siblings) has, since `WP 7.3A`, passed a fresh `TempDirectory` per test
via `PersistenceStore.RootPathConfigurationKey` — genuine isolation,
established early and consistently applied. `Tempest.Desktop.Tests`
never adopted the same pattern: every `WorkspaceHost` constructed by
`WP 10.0B`/`WP 10.1A` used the framework default, unconfigured, sharing
one real, durable `persistence-data` folder across every test in the
assembly, across every run of that assembly, indefinitely. The first
`Tempest.Desktop.Tests` run after `WP 10.1A` introduced sample-data-reading
Cockpit tests was, in effect, the first time this platform's own test
suite exercised a second real launch against already-durable state — and
it did so by accident, as a side effect of shared test infrastructure,
not by design.

## 4. Disposition

| Item | Disposition |
|---|---|
| `TD-26` | **Fixed at its own source** — `WorkspaceManager.StartAsync` (`WP10.1B Implementation Report.md` §1). |
| `TD-37` | **Fixed** — idempotent seeding in the four affected `Tempest.Samples` modules, plus genuine test isolation in `Tempest.Desktop.Tests` (`WP10.1B Implementation Report.md` §2–§3). |
| `TD-38` (new) | **Disclosed, not fixed.** Fixing it correctly means one of: (a) a real business-identifier uniqueness capability on `EngineeringObjectFactory<T>`/`EngineeringObjectBase` — an Engineering Domain change, explicitly out of this Work Package's own scope; or (b) a durable-store rehydration capability for `IEngineeringObjectRepository` — the same. Both are named as candidates for a future, dedicated Engineering Domain Work Package, not attempted here. |
| In-memory-only `IEngineeringObjectRepository` | **Disclosed as context for `TD-38`**, not a new, separately-tracked item — it is `WP 8.2C`'s own original, deliberate, unchanged scope decision, not a defect. |

No Engineering Domain file was touched to reach any of the above — every
fix lives in `Tempest.App.Workspace`, `Tempest.Desktop`, or
`Tempest.Samples`, consistent with this Work Package's own explicit
scope constraints.
