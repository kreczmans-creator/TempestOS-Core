# WP 10.0A — Navigation & Workflow Diagrams

## Purpose

Full Navigation Model detail and step-by-step diagrams for all eight
user journeys named across this Work Package (`WP10.0A UX Architecture
Document.md` §2). Mirrors and extends `WP8.0A Navigation
Specification.md` and `WP8.0A User Workflow Diagrams.md`.

## 1. Navigation Model

Two tiers, unchanged from `WP8.0A Workspace Architecture Document.md`
§4: **global navigation** (`INavigationProvider.Items`, top-level areas
— Home, Requirements, Calculations, Verification, Documents,
Manufacturing, Mechanical, Settings) and the **Project Explorer**
(per-area hierarchical tree, §Screen Catalogue §4). This Work Package
adds one navigational concept, made possible only by the desktop
paradigm (`ADR-0092`): **the Command Bar's own global navigation now
also switches between open Projects** (§14 in the master document) —
previously an implicit single-project assumption, now an explicit
third navigational dimension (Area × Project × open Document tab)
layered on the same two pre-existing tiers, not a fourth new mechanism.

## 2. Journey 1 — Browse and Inspect a Requirement (retained, unchanged)

```
Cockpit → Project Explorer → expand "Requirements" →
select a Requirement → Property Inspector shows statement/status/
revision history.  Zero writes, zero commands.
```

Identical to `WP8.0A Workspace Architecture Document.md` §2, Journey 1
— now exercised against `RequirementsNodeProvider`'s own real tree
(`WP 9.1A`) rather than a planned one.

## 3. Journey 2 — Trace the Digital Thread (retained, re-grounded)

```
Open Requirement tab → open Object Relationship View (right dock) →
see verifiedBy/references edges as graph nodes →
click "expand" on the linked Calculation Record node →
graph adds that Calculation's own direct relationships →
click the Calculation node itself → opens in a new Document Area tab,
alongside the Requirement, never replacing it.
```

Re-grounded in `ADR-0093`'s own graph rendering (§Digital Thread &
Relationship Visualisation companion document) rather than
`WP8.0A`'s own flat list — the underlying data path
(`GetEvidenceAsync`) is identical.

## 4. Journey 3 — Revise a Requirement (retained, unchanged)

```
Open Requirement tab (Object Editor, §UX Architecture Document §8) →
edit statement field → tab shows dirty-state indicator →
invoke "Revise Requirement" (Command Palette or Save button) →
ICommandDispatcher dispatches ReviseRequirementCommand-shaped command →
tab returns to clean state on success, or shows inline error (§Screen
Catalogue §19) on rejection.
```

## 5. Journey 4 — Change Lifecycle Status (retained, unchanged)

```
Select Requirement in Draft/Reviewed status → right-click →
context menu shows "Approve" (filtered by RequirementStatusTransitions'
own valid-transition table) → invoke →
success: lifecycle colour chip updates in place, across every open
view of that object (Property Inspector, Project Explorer node,
Cockpit KPI) simultaneously, since all read the same live service state
→ invalid transition: inline error, never a silent no-op.
```

## 6. Journey 5 — Discover What a Module Contributes (retained, unchanged)

```
A future Engineering Discipline Module registers a NavigationItem,
CommandDescriptor(s), an IWorkspaceViewFactory, and an
IProjectExplorerNodeProvider (ADR-0067) → Workspace presents all four
automatically, zero Workspace code change, exactly as every one of the
six real disciplines already does today.
```

## 7. Journey 6 — Work Across Two Projects Side by Side (new)

```
Cockpit → Recent Projects → open "Wing Root Rib Redesign" (Project A) →
Project Explorer roots on Project A → open Spar Web Plate tab →
Cockpit → Recent Projects → open "Landing Gear Overhaul" (Project B),
without closing Project A →
Command Bar's own Project switcher (§1) now lists both →
Document Area tabs visually cluster: [Project A: Spar Web Plate ×] |
[Project B: (none open yet)] →
open Bearing Load Capacity Calculation from Project B →
tabs now read [Project A: Spar Web Plate ×] | [Project B: Bearing Load
Capacity ×] → engineer arranges Project A's tab cluster on one monitor,
Project B's on another (§UX Architecture Document §15) →
compares both simultaneously.
```

Exercises `WP10.0A UX Architecture Document.md` §14 (Multi-Project
Workflow) and §15 (Multi-Monitor Behaviour) together — the first
journey in this project's own history that requires both.

## 8. Journey 7 — Trace a Relationship Chain Three Hops Deep (new)

```
Open Requirement REQ-0142 → Object Relationship View shows centre node
+ one hop (verifiedBy Test-0091, references Spar Web Plate) →
expand Spar Web Plate node → graph adds its own direct relationships
(verifiedBy Beam Bending Stress Calculation) →
expand Beam Bending Stress Calculation node → graph adds
basedOnCalculation Bearing Load Capacity →
engineer now sees three hops from REQ-0142 to Bearing Load Capacity in
one screen, built entirely from three separate one-hop reads
(ADR-0093), zero server-side transitive query.
```

## 9. Journey 8 — Recognise Objects by Colour and Icon Alone (new)

```
Project Explorer, densely populated tree spanning all six disciplines →
engineer scans without reading labels →
Kind icon distinguishes Part from Assembly from Requirement from Test →
lifecycle colour chip distinguishes Draft (grey) from InReview (amber)
from Approved (blue) from Released (green) from Archived (muted),
applied identically in the tree, the Cockpit KPI cards, and every
Object Editor's own lifecycle indicator →
engineer locates every Released Drawing in the tree in seconds, without
opening a single node.
```

Exercises `WP10.0A Visual Design System.md` §2 (Iconography) and §4
(Engineering Colour Language) directly — named here as the journey
those two sections exist to satisfy.
