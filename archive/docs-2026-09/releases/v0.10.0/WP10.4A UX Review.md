# WP 10.4A — UX Review

## Purpose

Assesses `WP 10.4A`'s own graphical presentation directly against a
real, running control — never a mock-up — for clarity, discoverability,
and consistency with the rest of the Workspace's own visual language.

## 1. Single-Click vs. Double-Click — Assessed Unambiguous

Single click opens the Object Editor tab (a familiar, low-commitment
action — "tell me more about this"); double click re-centres the graph
itself (a higher-commitment, structural action — "make this the new
focus"). This mirrors a convention already familiar from graph-
exploration tools generally (Visio, yEd, Neo4j Bloom), and gives each
of the instruction's two named, distinct scope items ("Click-to-open
object editor," "Double-click navigation") its own unambiguous gesture,
rather than overloading one click count for both. Assessed as
discoverable without documentation, though a first-run tooltip/hint is
disclosed future work (§5).

## 2. Filtering Hides Edges, Not Nodes — Assessed the Correct Default

Toggling a `RelationshipCategory` off in the legend removes only that
category's own edges and labels; every node stays put. Assessed
correct: a node popping in and out of existence based on an unrelated
filter toggle would be more disorienting than a temporarily
edge-less node — the graph's own overall shape stays legible and
predictable across filter changes.

## 3. The Legend Doubling as the Filter Control — Assessed Efficient, Slightly Dense

Combining "what does this colour mean" with "hide this category" in
one panel avoids a second, redundant filter UI — one clear win. The
panel does render all 17 `RelationshipCategory` values plus all 8
`LifecycleState` values unconditionally (never scoped down to only
categories present in the current graph), which is visually denser
than strictly necessary for a small graph. Disclosed as a real,
accepted trade-off (§5), not a defect — a legend that changes its own
row count as the graph changes shape was judged more confusing than a
fixed, complete key.

## 4. Verification-Record Leaf Nodes — Assessed Honest, Not Broken-Looking

A synthetic Verification-record leaf node has no expand toggle, cannot
be clicked to open an editor, and cannot be double-clicked to
re-centre — every one of these is a deliberate absence (Implementation
Report §5), not a bug. Because the node still renders with a real icon,
a real display name (`{Outcome} — {Method}`), and participates fully in
selection/search/highlighting, it does not read as broken — it reads
as a different, correctly-differentiated *kind* of node (no toggle
chevron is visually absent, not present-but-disabled, avoiding a
"why won't this button work" moment).

## 5. Disclosed UX Trade-offs

- No first-run onboarding/tooltip walkthrough for the
  click/double-click distinction — the instruction's own "No automation
  framework" and general scope pressure kept this out; a real, named
  gap, not silently absent.
- The legend shows the complete, fixed category/status vocabulary
  rather than only what the current graph contains — denser, but
  stable across expansion/collapse.
- Edge labels (`RelationshipKind` text) can visually overlap on a dense
  hierarchical layout with many same-row neighbours — no label
  collision-avoidance algorithm was implemented (`WP10.0A` doc §5's own
  disclosed "no automatic pruning/clustering" limitation, extended here
  to label placement specifically).
- The mini-map's own click-to-pan is a real, working affordance but has
  no dedicated visual affordance (cursor change, hover highlight)
  signalling it is clickable — a minor, disclosed polish gap.

## 6. Recommendation

**Accept**, with the disclosed trade-offs in §5 named as real,
low-severity future polish items, not defects requiring rework before
sign-off.
