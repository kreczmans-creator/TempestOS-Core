## What was decided

`ADR-0120 — Durable State Carries a Schema Version, and Migrations Apply
Only on Read` (Accepted at Technical Review, 2026-09-04), realised in
detail by `docs/architecture/State Schema Versioning Architecture.md`:

1. **`EngineeringObjectState` gains an integer `SchemaVersion`.** An
   absent version normalises **explicitly** to `1` in code, not via a
   serialiser default — so a record written by a `v0.15.0` build is
   read as v1 by construction rather than by accident of framework
   behaviour.
2. **Migrations are an ordered chain, applied on read only.** A common
   chain runs first, then the chain registered for the record's own
   `Kind` (`IStateMigration`, `IStateMigrationRegistry`). Never on
   write: `EngineeringObjectBase.CaptureState()` always stamps the
   current version from live in-memory fields, so a write is by
   definition current and a write-side migration would be dead code.
3. **Enums serialise as strings** from here on. The built-in
   `JsonStringEnumConverter` still reads previously-written numeric
   values, which closes `TD-87`'s concretely named failure — a
   `LifecycleState` reordering silently reinterpreting a persisted
   status — with **no migration required at all**. This is the part of
   the decision that does the most work for the least machinery.
4. **A record whose version cannot be bridged is logged and skipped**,
   extending rather than duplicating the `TD-60` discipline
   `EngineeringObjectStateStore.Deserialise` already applies to
   malformed JSON. An unrecoverable record must never abort startup.
5. **A golden corpus of v1 records is committed** and must load after
   every future version bump.
6. **`SettingsDocument<T>` joins the same scheme** through its own
   `ISettingsMigration<TDocument>` seam. The release plan asked this
   Work Package to *decide* whether it should, recommending yes; the
   decision recorded is yes, on the grounds that a second, divergent
   versioning mechanism for the same problem is the more expensive
   outcome.

## What was deliberately not done

- **No code.** The seam, the registry and the store changes are
  `WP 16.3B`'s, and were held back so the design could be reviewed on
  its merits rather than through a diff. `WP 16.3B` was subsequently
  rejected twice at Technical Review before it landed — evidence that
  separating the two was the right call, since both rejections were
  about implementation fidelity to this document, not about the design.
- **`TD-87` was not marked Resolved.** Closing a debt on a design is
  the drift this release exists to end.
- **Attachment content records** were considered and left on the
  existing `ADR-0114` ordering. The ADR records why rather than
  silently omitting them.
