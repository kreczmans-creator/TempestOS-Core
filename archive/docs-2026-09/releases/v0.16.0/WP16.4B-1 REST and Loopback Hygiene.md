## What changed

### Item 1 — D-024: the REST listener is off by default

`src/Tempest.Core/Api/RestApiHostedService.cs`:

- New public const `EnabledConfigurationKey = "Runtime:RestApi:Enabled"`,
  documented in the same style as the existing `PortConfigurationKey`/
  `DefaultPort`.
- `StartAsync` now reads that key **before constructing any ASP.NET
  Core object** — no `WebApplication.CreateSlimBuilder()`, no
  `builder.Build()`, no `UseUrls`, no port binding — and returns early,
  logging at Information (naming the key), when the gate is not
  satisfied.
- The gate itself: `_configuration.TryGetValue(EnabledConfigurationKey,
  out var raw) && bool.TryParse(raw, out var parsed) && parsed`. This is
  the exact convention already used in this codebase for a fail-closed
  configuration boolean — `TempestHost.cs`'s own
  `Plugins:AllowUnsignedLoad` read (`ADR-0112`) uses the identical
  `TryGetValue` + `bool.TryParse` + `&&` shape. Absent, empty, or
  unparseable (`"1"`, `"yes"`, `"on"` are **not** accepted — only what
  `bool.TryParse` itself accepts, case-insensitively: `"true"`/`"false"`)
  all resolve to disabled, matching the existing precedent's own
  documented "fail closed" rationale.
- `BoundPort` stays `null` when disabled (never assigned before the
  early return).
- `StopAsync` was already safe when `_app` is `null` (unconditional
  guard, pre-existing) — verified, not changed.
- Class-level `<remarks>` and the `EnabledConfigurationKey` doc comment
  both cite `D-024` explicitly as **Proposed, awaiting Product Owner
  approval** — never as decided.

### Item 2 — TD-62: the OpenAPI route requires identity + permission

`src/Tempest.Core/Api/ApiRequestHandler.cs`:

- Extracted the identity-resolution + permission-check + audit-record
  block that `HandleAsync` already had into a new private
  `AuthorizeAsync(method, path, identityHeaderValue, requiredPermission,
  cancellationToken)`, returning `ApiResponse?` — `null` means
  "proceed", a non-null `ApiResponse` is the 401/403 to send back.
  `HandleAsync` now calls it instead of inlining the checks a second
  time.
- Added `HandleOpenApiDocumentAsync(path, identityHeaderValue,
  cancellationToken)`, a new public entry point that runs the OpenAPI
  document through the identical `AuthorizeAsync` path (same identity
  resolution, same `IPermissionEvaluator.HasPermission` call, same
  `IAuditRecorder.RecordAsync` call, same `Log` helper) before calling
  `OpenApiDocumentGenerator.Generate` and returning `200`.
- Added `public static readonly Permission OpenApiDocumentPermission =
  new("api.openapi.read")` — see "Permission chosen" below.

`src/Tempest.Core/Api/RestApiHostedService.cs`:

- `InvokeOpenApiAsync` no longer calls `OpenApiDocumentGenerator.Generate`
  directly. It now extracts the identity header exactly like `InvokeAsync`
  does, calls `_requestHandler.HandleOpenApiDocumentAsync`, and writes
  back whatever `ApiResponse` comes out — `application/json` content type
  only on `200`, `text/plain` otherwise (matching the error-body content
  type every other route already uses). No second, parallel
  identity/permission check exists anywhere in this file any more.

**Permission chosen: `api.openapi.read`.** I looked at every permission
key already defined in the codebase
(`grep -rn "new Permission("`/`"PermissionKey ="` across `src/`): every
one of them is either sample-module-scoped (`reporting.generate`,
`sample.read`, `licensing.check-capability`, `exportimport.export`/
`import`, `requirements.read`) or a `plugin.*` capability key
(`PluginCapability`) with a completely different purpose. None of them
is a Core-level, platform-shaped permission a real deployment would use
to gate "read the API's own route map." The one existing precedent for
a **Core**-defined, non-sample, non-plugin permission is
`Audit.AuditQuery.QueryPermission = new Permission("audit.query")` —
I followed that precedent exactly: a new, dedicated
`ApiRequestHandler.OpenApiDocumentPermission = new("api.openapi.read")`,
defined on the type that enforces it, documented with the reasoning
above directly in its XML doc comment. This is a new permission
constant, not a reuse of an existing one — I am flagging that
explicitly per your instructions, since no existing key fit.

**Status codes.** An unauthenticated caller hitting `OpenApiPath` now
gets **401** — the exact code `ApiRequestHandler.HandleAsync` returns
for an unauthenticated command-route caller (`AuthorizeAsync`'s
`string.IsNullOrWhiteSpace(identityHeaderValue)` branch, shared by both
paths). A caller with an identity but not the permission gets **403**,
again via the same shared path. Verified directly by test, not just by
code inspection (see Validation).

**Audit.** The OpenAPI document is now audited identically to a command
request: `AuthorizeAsync` calls `_auditRecorder.RecordAsync` with the
same `RequestAuditAction` ("api.request") and the same `Detail` shape
(`Method`, `Path`, `CallerIdentityDetailKey`) before either path
proceeds — there is no separate audit action for the document.

## What did not change, and why

- **`AT-10` (no request-parameter binding), `TD-13` (no authentication),
  `TD-14` (no TLS), `TD-16` (unsigned licence file), `FCR-0003`/`FCR-0004`
  all stay open, exactly as `D-024` confirms them.** Nothing in this
  stream adds real authentication, TLS, or parameter binding — the
  identity header is still a trusted, unverified claim
  (`ApiRequestHandler`'s own pre-existing remarks, only reworded to say
  "when enabled" instead of "by default"). `TD-62`'s fix is exactly what
  the Technical Debt Register's own row proposes ("gate behind the same
  identity + permission pipeline as every command route") — the
  alternative it also floats, a per-caller document listing only routes
  the caller's own permissions reach, was **not** built: that would be
  a second, larger design (the document's shape now depends on the
  caller) and `D-024`/the Release Plan both describe closing `TD-62`
  as gating the existing document, not reshaping it.
- **`docs/architecture/Platform Service Map.md`, `docs/adr/ADR-0049-*.md`,
  and historical release notes (`v0.14.0 Release Notes.md`, academy
  docs) still say the listener "binds to the loopback address only by
  default."** These are real, now-stale statements, but every one of
  them falls outside "Documentation you own" for this stream — I did
  not touch them. Flagging this as a genuine gap for the integrator:
  `Platform Service Map.md` line ~1228 in particular reads as a current
  architectural fact and will mislead a reader until it is corrected.
- **`TD-62`'s Technical Debt Register row is not marked Resolved.** Per
  your instruction, that register edit belongs to the integrator.
- **The Decision Register and `WorkPackages.md` are untouched** — both
  are explicitly off-limits to this stream.
- **No new permission-granting mechanism, role, or default grant was
  added for `api.openapi.read`.** No existing identity/role is granted
  it by default; every test that needs an authorized call grants it
  explicitly through the same `Identity:Roles:*:Permissions` /
  `Identity:Principals:*:Roles` configuration mechanism the other
  sample integration tests already use. Whether any real operator
  identity should hold this permission by default is a Product/Identity
  design question, not something this stream decided.
