## 2. Focus-visible — what actually resolves, measured, not assumed

Two things about `:focus-visible` were confirmed empirically before
relying on them (both contradicted an initial assumption):

- **Simulating it directly fails.** `Classes.Set(":focus-visible", true)`
  throws `ArgumentException` ("may only be added by the control itself"),
  and calling `control.Focus(NavigationMethod.Tab)` directly is *not*
  enough either — it sets `:focus`/`:focus-within` but not
  `:focus-visible` (Avalonia tracks the last real input device
  separately from the navigation method argument). `FocusVisibleStyleTests`
  instead drives a real `Tab` keypress through the actual headless input
  pipeline (`HeadlessWindowExtensions.KeyPressQwerty`) — the only thing
  that genuinely sets it.
- **The generic `TemplatedControl` fallback does not outrank Fluent's own
  built-in `:focus-visible` styling.** Tried empirically against a plain
  unclassed `Button`, a `CheckBox`, and a `TextBox`: none show the custom
  ring. Fluent's own `ControlTheme` for each already declares its own
  `:focus-visible` treatment, at a selector specificity a generically-
  scoped external `Style` does not outrank — the four per-treatment
  `ChromeStyles` button styles (Flat/Subtle/Primary/Danger) only win
  because `.Class(styleClass)` makes their own selector more specific
  than Fluent's. The generic fallback is real, correctly wired (verified
  structurally — the `Style` object, its selector, and both setters, in
  `FocusVisibleStyleTests`), and will reach a future custom
  `TemplatedControl` this shell adds with no competing theme of its own;
  it does **not** additionally ring every existing Fluent-templated
  control that lacks one of the four named treatments. Disclosed here
  rather than left as an untested assumption.

## 3. `FocusRing` brush assignment — checked, not swapped

The prior analysis flagged a suspicion that `ApplicationPalette`'s
Light/Dark `FocusRingBrushKey` values might be swapped relative to
`BrandPalette`'s own accent convention. Checked directly against
`BrandPalette.AccentBrushKey`'s own registration
(`BrandPalette.cs`, `Register`):

| Theme | `BrandPalette.AccentBrushKey` | `ApplicationPalette.FocusRingBrushKey` (before this WP, unchanged) |
|---|---|---|
| Light | `Indigo600` (`#1c2d97`) | `Indigo600` |
| Dark | `Cyan500` (`#40a2ce`) | `Cyan500` |

They match exactly — cyan on dark (the brand's home ground), indigo on
paper (the brand's documented light-theme accent), the identical
convention `BrandPalette`'s own class remarks state ("one cyan
interactive accent... indigo the accent of the paper (light) theme").
**No change made** — the suspicion did not hold up; left exactly as
found, and now finally consumed by `ChromeStyles`'s own `:focus-visible`
styles (§1.e).

## 4. Cockpit health text — measured contrast

Computed by `HealthColorContrastTests.cs` (the real WCAG 2.1 §1.4.3
relative-luminance formula, against the real resolved
`BrandPalette.SurfaceBackgroundBrushKey` for each theme — `#ffffff`
light, `#111527`/`Navy700` dark) — reproduced here for the record:

| Status | Light (was) | Light hex (new) | Light ratio (new) | Dark hex | Dark ratio |
|---|---|---|---|---|---|
| Healthy | 2.54:1 (`Green500` `#12b981`) | `#0a7a53` | **5.36:1** | `#12b981` (unchanged) | **7.14:1** |
| Attention | 2.04:1 (`Amber500` `#f5a524`) | `#996208` | **5.12:1** | `#f5a524` (unchanged) | **8.87:1** |
| Blocked | 3.91:1 (`Red500` `#e5484d`) | `#d92b31` | **4.84:1** | `#e5484d` (unchanged) | **4.62:1** |
| Unknown | 3.72:1 (`Slate500` `#82848e`) | `#6f7179` | **4.87:1** | `#82848e` (unchanged) | **4.86:1** |

Every cell is ≥ 4.5:1 (WCAG AA, normal-weight body text). The dark
values needed no change — the review's own 2.1:1 finding was a
light-theme-only defect (the Cockpit's light surface is `#ffffff`
directly; its dark surface, `Navy700`, is dark enough that the identical
brand hues already clear the floor with real margin).

- No existing test was weakened, skipped, or deleted.

**Two real bugs this validation pass itself found and fixed** (both in this Work Package's own new code, caught before merge, not shipped):

1. `MacroManagerDialog._macroList` (a `ListBox`) was never `Focusable` by construction — confirmed by direct reflection that `ListBox`'s own class-level default is `Focusable = false` (only Fluent's theme turns it on, once a template is applied, too late for `ShowAsync`'s own deterministic initial-focus call). Fixed by setting `Focusable = true` explicitly on construction, mirroring the same fact-check discipline the rest of this report applies to Avalonia's own API surface.
2. Three of the six per-dialog focus-restore tests, and the `MainWindowKeyboardModalityTests` close step, initially raised a synthetic `KeyEventArgs` on the wrong element for `InputDialog` specifically (its own Escape handling lives on its inner `TextBox`, unlike the other five dialogs, which handle it on the dialog root) — a test-authoring bug, not a production one; fixed by raising on the actually-focused element (matching what a real keypress bubbles from) rather than the dialog root.
