# WP 16.4A-R1 — Test Strength Remediation

**Type.** Implementation (tests only). No production code, ADR, or
register edit — see "What did not change, and why".
**Branch.** `feature/v0.16.0-test-strength`, cut from `feature/v0.16.0`
at `9771273`.
**Closes.** Five findings from an independent test-strength review of the
v0.16.0 branch, each proven by mutation (the production fix reverted, the
guarding test run, and observed to pass anyway):

| # | Severity | Test | Defect |
|---|---|---|---|
| 1 | RED | `MaterialCatalogReconciliationServiceTests.SweepAsync_InterleavedWithAnInFlightRegistration_NeverMakesTheMaterialUnfindable` | Blind, name-keyed gate never exercised the race against the sweep's pre-fix read order. |
| 2 | RED | `RequirementsReconciliationServiceTests` — two identical race tests | Same blind gate, duplicated. |
| 3 | AMBER | `AsyncKeyedLockTests.Releaser_DoubleDisposedConcurrently_ReleasesExactlyOnce` | A single `Barrier(2)` race detects the reverted double-dispose guard in ~0.45% of runs. |
| 4 | AMBER | `GoldenCorpusTests.AssertEveryFieldSurvived` | `Metadata`, most of `BomLine`, per-entry `History`, and `Attachments.ContentType` were never compared — the "every field" docstring was false. |
| 5 | YELLOW | Every `TaskCompletionSource`-gated test in the suite | No gate had a bounded wait; CI had no `--blame-hang` collector — a seam that stops being reached hangs silently for the full 30-minute job timeout. |

**Cites.** `docs/releases/v0.16.0/WP16.4B-R2 Attachment Sweep
Write-Intent Marker.md` (the `SecondReadPausingGate` pattern findings 1–2
generalise, and the read-order fix findings 1–2 guard); `docs/releases/
v0.16.0/WP16.4A Test Determinism Report.md` (this project's own
mutation-testing discipline, applied here to gates rather than timing);
`tests/Tempest.Core.Tests/Navigation/NavigationServiceTrustTests.cs`

## What changed

### Findings 1–2 — order-agnostic race gates (Materials, Requirements)

Added `tests/Tempest.Core.Tests/Persistence/OrderAgnosticGatedListKeysPersistenceStore.cs`
— a single shared `IPersistenceStore` wrapper, constructed with the small
set of collection names one race test cares about, that pauses
`ListKeysAsync` on whichever of those names is the **second** call to
arrive, by order of arrival, never by name. Chose a shared class over a
third and fourth copy of the same private fake: the two existing copies
in `MaterialCatalogReconciliationServiceTests.cs` and
`RequirementsReconciliationServiceTests.cs` were already byte-for-byte
identical (the latter's own comment said so), so the duplication this
finding's fix would otherwise add a third and fourth copy of is exactly
the kind `WP16.4B-R2`'s `SecondReadPausingGate` was introduced to avoid
elsewhere. Placed under `Persistence/` (not `EngineeringDomain/`, which
the concurrently-editing sibling agent owns for this branch) since both
Materials and Requirements test namespaces already reference across
folders in this project (e.g. `PersistenceStoreTests.cs` already imports
`Tempest.Core.Tests.EngineeringDomain`/`.Plugins`) — this is that same,
already-established convention, not a new one.

Unlike `AttachmentContentReconciliationServiceTests`'s
`SecondReadPausingGate` (which counts every call and needs no name
filter, because its own two reads are the only two the sweep under test
ever makes), Materials' and Requirements' sweeps read more collections
than the two collections one race test is exercising — Requirements
reads four collections per run, not two. The shared gate is therefore
parameterised on a **watched set** of collection names: only calls
against those names are counted, and the second one *among the watched
set* pauses, regardless of which of the watched names it turns out to be.
An unrelated registry's own read passes straight through uncounted.

- `MaterialCatalogReconciliationServiceTests`: watched set = `{IndexCollectionName, DocumentsCollectionName}`.
- `RequirementsReconciliationServiceTests`, Requirement race: watched set = `{IdentifierIndexCollectionName, DocumentsCollectionName}`.
- `RequirementsReconciliationServiceTests`, Collection race: watched set = `{CollectionRegistryCollectionName, DocumentsCollectionName}`.

Both test files' own private `GatedListKeysPersistenceStore` classes were
deleted and their three call sites repointed at the shared gate; no other
test in either file changed.

### Finding 3 — looped double-dispose race

`AsyncKeyedLockTests.Releaser_DoubleDisposedConcurrently_ReleasesExactlyOnce`
now loops the same `Barrier(2)` race 2,000 times inside the one test
(fresh `AsyncKeyedLock`, fresh `Barrier` each iteration), bounded purely
by iteration count — the same looped-real-thread-race idiom
`NavigationServiceTrustTests.Register_ConcurrentRegistrantsForSameId_HighestTierAlwaysEndsUpSoleOwner`
already uses in this suite. See "Validation" for the arithmetic behind
2,000 and the measured detection rate.

### Finding 4 — the golden corpus's missing fields

`GoldenCorpusTests.AssertEveryFieldSurvived` now also compares, when the
fixture carries them:

- **`Metadata`** — `Category`, `Discipline`, `Owner`, `Classification`,
  `Notes`, and `Tags` (against `TagsOrEmpty`). This was the finding's
  named gap: two fixtures (`assembly-with-parent.json`) carry real,
  non-null values here, and nothing compared them.
- **`BomLine`**'s remaining fields — `UnitOfMeasure`, `FindNumber`,
  `ItemNumber`, `ReferenceDesignator` (previously only `Quantity` was
  checked).
- **`History`**'s per-entry fields — `From`, `To`, `ActorPrincipalId`,
  `OccurredAt`, `ApprovalId` (previously only the array's *length* was
  checked, so a transition's own content could be corrupted silently).
- **`Attachments[].ContentType`** (previously `Id`, `FileName`,
  `SizeInBytes`, `ContentHash` were checked but not this field).

`SchemaVersion`, `Id`, `Kind`, `Identifier`, `DisplayName`, `IsDeleted`,
`ParentId`, `Status`, and `TypeState` were already asserted and are
unchanged.

### Finding 5 — bounded gates and a CI hang collector

Every `TaskCompletionSource`-based gate await this branch could touch
without colliding with the sibling agent (see "What did not change, and
why") now has a 10-second `.WaitAsync(TimeSpan)` bound:

- `OrderAgnosticGatedListKeysPersistenceStore` (new file) — both the
  internal pause and the three test-side `await gated.ReachedGate` call
  sites in Materials/Requirements.
- `AsyncKeyedLockTests` — the two `firstAcquired`/`releaseFirst` gate
  pairs.
- `Runtime/HostTestFixtures.cs`'s `BlockingModuleGate` — both
  `WaitUntilEnteredAsync` and `EnterAndWaitForReleaseAsync`; its three
  callers in `TempestHostTests.cs` needed no change, since the timeout
  now lives inside the gate method itself.

`.github/workflows/ci.yml`'s `Test (${{ matrix.configuration }})` step
now passes `--blame-hang --blame-hang-timeout 5m` — comfortably above
this suite's real run time (currently well under a minute) and
comfortably below the job's own 30-minute `timeout-minutes`, so a genuine
hang is caught, named, and given a hang dump long before the job would
otherwise be silently killed.

## What did not change, and why

- **`AttachmentContentReconciliationServiceTests.cs`'s own gates
  (`GatedObjectStateStore`, `SecondReadPausingGate`) are not
  timeout-wrapped.** That file lives under
  `tests/Tempest.Core.Tests/EngineeringDomain/`, which a sibling agent is
  concurrently editing on its own worktree; this branch's own scope
  instruction was to touch only `SchemaVersioning/GoldenCorpusTests.cs`
  within that folder. Left alone deliberately, not missed — a follow-up
  pass after both branches merge should apply the identical
  `.WaitAsync(TimeSpan.FromSeconds(10))` bound there.
- **No production file carries any change.** Findings 1, 2, 3, and 4 each
  required a temporary production-side mutation to prove the fixed test
  actually fails against broken code (see "Validation"); every one of
  those mutations was reverted with `git checkout --` immediately after
  the failing run was captured, confirmed restored byte-for-byte, and
  never committed. `git status` at every commit on this branch shows only
  test files, the one new shared test-support file, this report, and
  `.github/workflows/ci.yml`.
- **No ADR or register file changed** (`docs/governance/**`,
  `PROJECT_STATUS.md`, `WorkPackages.md`, `docs/adr/**`) — out of scope
  for this Work Package per its own instruction; the integrator's own
  register pass is expected to record this report's existence, as prior
  `WP 16.4B-R*` reports note the same deferral.
- **`MaterialCatalogReconciliationServiceTests`/`RequirementsReconciliationServiceTests`'s
  documentation comments were updated in place**, not left describing the
  old, blind gate — a stale comment claiming order-independence a reader
  could not verify from the code would be exactly the kind of
  documentation-ahead-of-reality drift this project's own review
  discipline exists to catch.

### Finding 3 — looped double-dispose race

**Iteration-count arithmetic.** The review measured the single-shot
race's detection probability at 9/2,000 = 0.45% (`p = 0.0045`). Treating
each of `N` looped iterations as an independent Bernoulli trial, the
probability of catching the bug at least once is `1 - (1-p)^N`. Solving
`1 - (1-0.0045)^N ≥ 0.99` gives `N ≥ ln(0.01)/ln(0.9955) ≈ 1021`. `N =
2,000` — the same order of magnitude as the reviewer's own probe,
comfortably above that threshold — gives `1 - (0.9955)^2000 ≈ 1 - e^-9 ≈
99.99%` detection probability, while the whole looped test runs in
**78ms** measured locally (well under a second; no wall-clock waits,
bounded purely by iteration count).

**Mutation:** reverted `Releaser.Dispose()` in `AsyncKeyedLock.cs` from
the `Interlocked.Exchange`-guarded field to a plain, non-atomic `bool
_disposed` guard.

**Measured detection rate:** 10 separate full runs of the looped test
against the reverted guard — **10/10 failed** (100% in this sample,
consistent with the ~99.99% predicted rate). One representative failure:

```
Failed Tempest.Core.Tests.Concurrency.AsyncKeyedLockTests
  .Releaser_DoubleDisposedConcurrently_ReleasesExactlyOnce
  Assert.Empty() Failure: Collection was not empty
Collection: [System.Threading.SemaphoreFullException: Adding the
specified count to the semaphore would cause it to exceed its maximum
count.
   at System.Threading.SemaphoreSlim.Release(Int32 releaseCount)
   at Tempest.Core.Concurrency.AsyncKeyedLock.Releaser.Dispose()
```

Runs completed in 30–44ms each — the loop exits on the first violation
via the thrown assertion, so a detecting run does not pay for all 2,000
iterations.

**After (real, fixed code):**

```
Passed! - Failed: 0, Passed: 1, Skipped: 0, Total: 1, Duration: 44 ms
```
