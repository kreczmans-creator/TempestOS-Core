## What changed

### 1. BLOCKER — invisible keyboard focus ring on every Primary/Danger-treatment button

`src/Tempest.Desktop/Theming/ChromeStyles.cs` drew every treatment's
`:focus-visible` ring from the one generic `ApplicationPalette.FocusRingBrushKey`.
`Primary`'s own rest fill is `BrandPalette.AccentBrushKey`, which resolves
to the *identical* colour as `FocusRingBrushKey` in both themes (measured
**1.00:1** — a keyboard user tabbing to Save/Continue/Enter Engineering
saw no ring at all). Checking `Danger` as asked: its `:pointerover` fill
(`DangerBrushKey`) also failed the generic ring's 3:1 floor once also
focused (measured **2.33:1** light, **1.36:1** dark).

Fix: `Primary` now draws its `:focus-visible` ring in
`BrandPalette.OnAccentBrushKey` — its own foreground colour, so it is
guaranteed to contrast with its own fill (measured ≥ 4.60:1 against every
Primary fill state in both themes — see the Validation table). `Danger`
keeps the generic ring at rest (never reported broken there — its rest
fill is transparent) and gains a second, more specific style —
`.tempest-danger:pointerover:focus-visible` — that also switches to
`OnAccentBrushKey` exactly when hovered. **Real finding this fix
surfaced about the codebase's own styling engine, disclosed in a code
comment:** two `Style`s in the same `Styles` collection that both match
are not resolved by selector specificity (an extra pseudo-class does not
win) — they resolve by *addition order*, last-added wins. The two Danger
rules are therefore added rest-then-hover, deliberately, and this was
confirmed directly by writing the fix the "obvious" specificity-first way
first, watching the new test fail, and re-ordering.

**Test fixed to actually catch this.** `tests/Tempest.Desktop.Tests/FocusVisibleStyleTests.cs`'s
existing test asserted only `presenter.BorderBrush == focusRing` — updated
to resolve the *expected* ring per treatment (`Primary` now expects
`OnAccentBrushKey`) so it does not regress silently. A new theory test,
`ButtonTreatments_FocusRing_DiffersFromAndContrastsWithEveryOpaqueFillItBorders`,
covers all 4 treatments × 2 themes (8 cases): drives a real Tab keypress
and then a real pointer hover (both via the actual headless input
pipeline), resolves the presenter's real `BorderBrush`/`Background`, and
— wherever the background is a genuine, fully-opaque solid fill (a
translucent wash or `Brushes.Transparent` is skipped, with the reasoning
in a comment, since that lets the real page background show through) —
computes the actual WCAG ratio and asserts ≥ 3:1 and non-equality.
**Verified as a real regression test**: reverted `ChromeStyles.cs` alone
to the pre-fix source (the `BrandPalette.cs` colour fixes from finding #6
already applied on top of it) and confirmed all 4 new theory cases fail:
Primary at 1.00:1 in both themes — matching the review board's own number
exactly, since `AccentBrushKey` is untouched by this round; Danger at
2.26:1 light / 1.36:1 dark — dark matches the review board's own 1.36:1
exactly (`Red500` untouched), light differs slightly from the board's own
2.33:1 only because that isolated revert measured against this round's
*already*-nudged `DangerBrushKey` (`#cf353b`, not the original `#d03a3f`)
— restoring the fix returns both to passing.

Each theme is exercised via `Window.RequestedThemeVariant` (a per-window,
local override) rather than toggling the shared
`Application.Current.RequestedThemeVariant` — `VisualPolishTests.cs`
already disclosed that live toggle-and-reread as flaky under this
project's own parallel test execution, and this avoids it entirely.

### 2. Ribbon command buttons announced as "Avalonia.Controls.StackPanel"

`src/Tempest.Desktop/Views/RibbonView.cs`, `BuildCommandButton`: every
command's `Button.Content` is a `StackPanel` (icon + `TextBlock`) with no
`ToString` override, so `ContentControlAutomationPeer.GetNameCore()`'s
own fallback (`Owner.Content?.ToString()`) resolved to the literal type
name. Fixed with one `AutomationProperties.SetName(button,
descriptor.DisplayName)` call, right where the button is built.

### 3. Same defect on the Digital Thread graph's "Reset View" button

`src/Tempest.Desktop/DigitalThread/DigitalThreadGraphView.cs`: identical
shape (`StackPanel` content, no name). One
`AutomationProperties.SetName(resetZoomButton, "Reset View")` call —
in the same file `WP 16.5A` explicitly claimed to have audited for
automation names.

### 4. `DocumentViewerView` — glyph-only names, mouse-only panning

`src/Tempest.Desktop/Viewing/DocumentViewerView.cs`:

- `ToolbarButton`'s four glyph buttons (`"‹"`, `"›"`, `"−"`, `"+"`) had
  only a `ToolTip`; the accessible name resolved to the bare glyph
  character. Fixed at the shared `ToolbarButton` factory itself — every
  caller already passes the real, descriptive name as `tooltip`
  ("Previous page", "Next page", "Zoom out", "Zoom in", "Fit the whole
  page in the view", "Show the page at its actual size"), so one
  `AutomationProperties.SetName(button, tooltip)` call fixes all six
  toolbar buttons uniformly, not just the four named in the finding.
- Panning was `OnPointerPressed`/`OnPointerMoved`/`OnPointerReleased`
  only, with no `KeyDown` handler anywhere in the class. Added
  `OnViewerKeyDown`, attached at the root (`this`) exactly like
  `DigitalThreadGraphView.OnGraphKeyDown` — arrow keys call the existing
  public `PanBy(double, double)`, a new `KeyboardPanStep = 40` constant,
  `e.Handled = true`. Direction follows `OnPointerMoved`'s own documented
  convention ("drag right, see what was to the left"): `Right`/`Down`
  pass a *positive* delta (reveal further right/below), `Left`/`Up`
  negative — the same direction a scrollbar user already expects. No new
  focus target was added: the fix relies on the toolbar buttons already
  being real tab stops, and the `KeyDown` bubbles from whichever one is
  focused, matching the graph's own "fires regardless of which node
  holds focus" shape.

### 5. Status bar "Hint" segment — Polite live region driven by mouse hover

`src/Tempest.Desktop/Views/RibbonView.cs` wires `PointerEntered`/`PointerExited`
on **every** ribbon button to `_setHint(...)`, which sets `StatusBarView`'s
`_hint.Text`. The shared `Value()` factory applied `AutomationLiveSetting.Polite`
uniformly to all eight segments.

Read every segment's own call sites before deciding.
`SetProject`/`SetLocation`/`SetArea`/`SetDiagnostics`/`SetNotifications`
and `SetText` (the "Selected object" segment — also reused for one-off
action-outcome messages, e.g. `ActionOutcomeReporter`,
`WorkspaceViewCoordinator`) are each driven only by a real, discrete
navigation/backend/action event, never by hover. `SetHint` has exactly
two kinds of caller: `RibbonView`'s own hover wiring (the noise this
finding is about) *and* `WorkspaceLayoutPresetCoordinator`'s two genuine,
discrete "Grid layout applied."/"Layout reset to the default arrangement."
messages. `AutomationLiveSetting` is per-control, not per-update, so
there is no way to keep the layout-preset messages `Polite` while
silencing the hover spam without a structural change (a second,
`Polite` segment for genuine hint-style status, or the coordinator
routing through `SetText` instead) — out of this finding's own scope. Turning
`Hint` off is therefore a real, disclosed trade-off: the two layout-preset
messages stop being announced too. Given the finding's own severity
(constant noise on every ribbon hover, on top of the button's own name,
versus two rare messages that are also visible on screen), Off is the
right call for this round; a follow-up giving `WorkspaceLayoutPresetCoordinator`
its own announced route is a reasonable enhancement, not something this
finding requires. Fix: `Value()` gained an `announceChanges` parameter
(default `true`); `_hint = Value(announceChanges: false)` is the only
call site that passes `false`. `AutomationLiveSetting` is left unset for
`Hint` rather than explicitly set to `Off` — confirmed directly that
Avalonia's own unset default *is* `Off`, so omitting the property is the
more honest "this is not a live region" than declaring it.

**Kept `Polite` on:** Current project, Location, Selected object, Active
area, Host state, Diagnostics, Notifications — all seven change only on a
real, discrete event, never on hover.

The existing test that asserted the bug as if it were correct behaviour
(`AccessibilityAutomationTests.StatusBarView_EverySegmentValue_CarriesAPoliteLiveSetting`,
asserting all eight segments `Polite`) is replaced by
`StatusBarView_SevenSegmentValues_CarryAPoliteLiveSetting_ButHintDoesNot`,
which asserts the seven stay `Polite` and `Hint` resolves to `Off`.

### 6. Three measured contrast failures

See the Validation section below for the full before/after table. All
three are the same "hue-preserved, darken/lighten for the real floor"
treatment `WP 16.5A` already applied to the four `HealthText*` keys:

- `BrandPalette.FaintTextBrushKey` (light): `Slate500` (`#82848e`) →
  `#696b75`. `grep`ped every consumer first (`StatusBarView`,
  `GlobalNavigationRail`, `RibbonView`, `PageHeading`, `CockpitView`,
  `ProjectExplorerView`, `LayoutTabGroupView`, `CockpitCardControl`) —
  all real text/caption use, never decoration. The dark value (also
  `Slate500`) is untouched; it already clears 4.5:1 on both dark surfaces
  this key is drawn on.
- `BrandPalette.Cyan600` (dark's `AccentPressBrushKey`): `#2b7fa5` →
  `#2c82a9`. Also used, unrelated to text contrast, as one swatch in
  `DigitalThreadGraphView.CategoryColors`' 17-colour relationship-category
  palette — a decorative, categorical use with no contrast floor, and the
  nudge is imperceptible there. The light theme's own press fill
  (`#16247a`) is untouched — already ≥ 4.5:1.
- `BrandPalette.DangerBrushKey` (light): `#d03a3f` → `#cf353b`. Also used
  as the `Danger` treatment's own rest border/text colour and the status
  bar's diagnostics-failed dot (`StatusBarView.SetDiagnostics`) — a
  decorative dot, no floor; the rest-state text use is *improved* by this
  change (measured below), not put at risk. The dark theme's own
  `Red500` is untouched — already ≥ 4.5:1 for the same pairing.

New test file `tests/Tempest.Desktop.Tests/ContrastRemediationTests.cs`,
following `HealthColorContrastTests.cs`'s own established pattern exactly
(the identical WCAG relative-luminance/contrast-ratio formula, computed
from the real registered `BrandPalette` resources via the explicit-theme
`BrandPalette.Brush(key, ThemeVariant)` overload — never a live
`Application.Current.RequestedThemeVariant` toggle, for the same
disclosed-flakiness reason as finding #1's test): one theory test per
pair, both themes, 6 cases total. **Verified as real regression tests**:
reverted to the pre-fix `BrandPalette.cs` and confirmed all three
failures reproduce the review board's own measured numbers exactly
(3.72:1, 4.46:1, 4.42:1), then restored the fix.

## What did not change, and why

- **Digital Thread graph edge (relationship) keyboard selection — a real,
  disclosed gap, deliberately not touched.** `line.PointerPressed`/
  `hitTestLine.PointerPressed` (`DigitalThreadGraphView`) are the only way
  to select an edge; `OnGraphKeyDown` has no case for it, and node
  `Tab`/arrow-key focus never reaches an edge at all. Fixing this needs a
  focus model for edges that does not exist today (edges are `Line`/hit-test
  overlay pairs, not `Focusable` elements the way node `Border`s are) —
  a design decision, not a defect fix, and explicitly out of this Work
  Package's scope per its own brief. Left exactly as found; see the
  Technical Debt Register row proposed below.
- **`TD-65`'s other named residuals** (`Editors/ObjectEditorView`
  watermark, Docking chrome buttons, non-button focus-visible precedence
  — all listed in `WP16.5A Accessibility Baseline Report.md`'s own
  "Remaining inventory") are untouched. None of the six findings handed
  to this Work Package named them, and fixing them here would be the
  general sweep this brief explicitly rules out.
- **The light Danger treatment's own rest-state text on the Sunken
  surface** (`DangerBrushKey` as the button's own border/foreground,
  against `SunkenBackgroundBrushKey`) measures 4.37:1 even after this
  round's nudge — still under 4.5:1 (it was 4.23:1 before). Not one of
  the six findings. `grep`ping every `ChromeStyles.Danger` use: two of
  the three call sites are confirmed on `ApplicationPalette.PanelBackgroundBrushKey`
  (`ConfirmationDialog`, `MacroManagerDialog`, both `: Border` with their
  own explicit `Background` binding — Paper000 in light, the same colour
  `SurfaceBackgroundBrushKey` resolves to); the third
  (`ObjectEditorView`'s Fail Verification button) sets no background of
  its own and was not traced further up its own host chain to a
  confirmed final surface, so it is not asserted as safe with the same
  confidence — flagged here either way rather than silently left for a
  future placement to trip over.
- `TD-65` stays **Partially resolved** — its "Digital Thread"
  keyboard-operability clause still excludes edges, and this round's own
  fixes are additional narrowing, not closure. This report does not
  change the register; the integrator applies the recommended row below.
