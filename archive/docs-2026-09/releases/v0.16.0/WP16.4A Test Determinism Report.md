## 1. `TD-34` — `CompositeLogSink`'s injected error writer

**Root cause.** `CompositeLogSink.Write`'s per-sink failure handler wrote
directly to the static, process-wide `Console.Error`
(`src/Tempest.Core/Logging/CompositeLogSink.cs:84`, pre-fix). Two test
classes redirected that same stream (`Console.SetError`/`Console.SetOut`)
without joining `[Collection("Console output capture")]`, the collection
every other Console-redirecting class in the suite already serialises
against — so both could race a concurrently-running `CompositeLogSinkTests`
under xUnit's default cross-class parallelism.

**Re-derivation, not assumption (grep, this worktree, pre-fix):**
`grep -rln "Console\.SetOut\|Console\.SetError" tests/Tempest.Core.Tests/`
found 55 files. Cross-checking each against
`grep -n "^\[Collection\|^public.*class"` found exactly one **class**
outside the collection: `LoggerTests` (`Console.SetError` at its private
`CaptureConsoleError` helper). `ConsoleLogSinkTests` already carried the
collection tag, confirming it — the fact sheet's claim that it was
"already fixed" before this Work Package started, contradicting an
earlier draft of the same claim, was verified true by direct read.
`CompositeLogSinkTests` itself doesn't appear in that grep at all
pre-fix-adjacent, because its own `Console.Error.WriteLine` call happens
inside `src/`, not in the test file — the race was between
`CompositeLogSinkTests`'s *assertions* (which never touched `Console` at
all, only observed the effect of `CompositeLogSink.Write`'s internal
write) and `LoggerTests`/`ConsoleLogSinkTests` redirecting the same
static stream underneath it.

**Change.**
- `CompositeLogSink` gains an additive constructor overload
  `CompositeLogSink(IEnumerable<ILogSink> sinks, TextWriter? errorWriter = null)`
  (default parameter, so every existing one-argument call site keeps
  compiling and behaving identically — defaults to `Console.Error`,
  captured once at construction). `Write` now writes to the instance's
  own `_errorWriter` field instead of re-reading the static
  `Console.Error` on every failing write.
- **Verified no `src/` call site needed updating**:
  `grep -rn "new CompositeLogSink(" src/` returns zero matches —
  `CompositeLogSink` is not yet constructed anywhere in `src/`.
- `CompositeLogSinkTests` rewritten: every throwing-sink test now injects
  a private `StringWriter` and asserts the failure message actually
  landed there (`Assert.Contains(nameof(ThrowingLogSink), reported)`,
  `Assert.Contains("Simulated sink failure.", reported)`) — a positive
  assertion, replacing the old "did not throw" check, which is
  necessary-but-not-sufficient (a swallowed silent failure would also
  pass it). A fourth test asserts nothing is written when every sink
  succeeds. The class no longer touches `Console` at all — not "joined
  the collection", genuinely removed the dependency, which is the fix
  the register's own remedy column named as the complete one.
- `LoggerTests` gains `[Collection("Console output capture")]`.

**Proof.**
- Re-derived post-fix: the same grep/cross-check shows **every** class
  touching `Console.SetOut`/`Console.SetError` in `Tempest.Core.Tests`
  now carries the collection tag (command and full per-file listing were
  run and inspected directly, not sampled).
- `dotnet test --filter "FullyQualifiedName~Logging"` (Debug):
  59/59 passed, 0 failed, on the finished rewrite.
- Full Core suite: 3,090/3,090 across 3 Release runs (§8).

## 2. `TD-119` — the one retained fixed wait

**Investigation.** Removed `await Task.Delay(50)` at
`tests/Tempest.Desktop.Tests/WorkflowInteractionTests.cs:335`
(`RibbonDelete_ConfirmationDeclined_DoesNotDeleteTheRealObject`) and ran
the test in a loop:
`for i in $(seq 1 20); do dotnet test ... --filter "FullyQualifiedName~RibbonDelete_ConfirmationDeclined_DoesNotDeleteTheRealObject"; done`
(Release, `--no-build`) — **20/20 passed**, 0 failures.

**Why it is safe, confirmed by reading, not guessed:**
`RibbonView.DeleteAsync` (`src/Tempest.Desktop/Views/RibbonView.cs`):
when `ConfirmDeleteAsync` declines, the method does
`if (ConfirmDeleteAsync is { } confirm && !await confirm(message)...) return;`
with a bare `return` — no event, no signal. The test's own
`ConfirmDeleteAsync = _ => Task.FromResult(false)` hands back an
**already-completed** task, so the `await` inside `DeleteAsync` never
yields to the dispatcher (an `await` on an already-completed awaiter
resumes synchronously rather than posting a continuation) — the entire
click-handler chain (`Button.Click` → `OnCommandButtonClickAsync` →
`DeleteAsync` → the bare `return`) completes on the same call stack
`deleteButton.RaiseEvent(...)` is on. There is nothing left running after
`RaiseEvent` returns, so there was never anything to wait for.

**Change.** The delay is removed permanently. A comment at the call site
explains the synchronous-completion reasoning above and cites
`RibbonView.cs` and `TD-119` by name, so a future reader does not have to
re-derive it.

**Further verification.** Rebuilt with the comment in place and ran the
same test 10 more times (Release, `--no-build`): 10/10. **Total: 30/30,
0 failures**, across two separate build/loop passes.

**Proposed TD-119 disposition (register edit deferred to `WP 16.2A` per
instruction — text below is this report's own proposal, not yet applied
to the register):**

> **Resolved, `WP 16.4A`.** The sole remaining fixed wait
> (`WorkflowInteractionTests.cs:335`, `Task.Delay(50)`) is removed. 30/30
> clean runs with it removed (20 before, 10 after, the explanatory
> comment added between the two passes) — 0 failures, 0 flakes. Root
> cause of safety, confirmed by reading `RibbonView.DeleteAsync`: the
> declined path's `await confirm(message)` resolves against an
> already-completed `Task.FromResult(false)` and therefore never yields;
> the bare `return` that follows executes synchronously within
> `RaiseEvent`'s own call, so nothing is still running once `RaiseEvent`
> returns and there is nothing to wait for or join. 51 of this row's own
> original 52 fixed waits were already converted by `WP-Z4`; this Work
> Package closes the 52nd and last one — 0 fixed waits remain.

## 3. `TD-83` — `MainWindow`-level resize

**Root cause.** `WorkspaceLayoutHostTests` (`TD-70`/`TD-72`) drives the
responsive rule directly against `WorkspaceLayoutHost`; `ResponsiveWorkspaceTests`
constructs a real `MainWindow` but never resizes it. No test exercised a
real `MainWindow.Width`/`Height` change through a real headless layout
pass — the exact gap `TD-83`'s own register text names.

**Change.** New file `tests/Tempest.Desktop.Tests/MainWindowResizeTests.cs`,
in `[Collection("Tempest.Desktop WorkspaceHost persistence")]`:
- Builds a real `WorkspaceHost` (isolated root via
  `WorkspacePersistenceCollection.NewIsolatedPersistenceRootPath()`), a
  real `new MainWindow(host)`, shows it under the headless platform.
- Waits for `MainWindow`'s own async `Opened` handler (theme load, layout
  restore, area selection) via a bounded, condition-based poll — the
  `TD-46`/`WP 11.4A` pattern (deadline 2s, `Dispatcher.UIThread.RunJobs()`
  + a real `Measure`/`Arrange` pass each iteration, `await Task.Delay(10)`
  between), matching the established `LayOutAsync`/`RenderUntilAsync`
  idiom in `ProjectTaskAcceptanceTests.cs`.
- Resizes by setting `window.Width`/`Height` then running a real
  `Measure`/`Arrange` pass (never calling
  `WorkspaceLayoutHost.ApplyResponsiveLayout` or `MainWindow`'s own
  `SizeChanged` handler directly) at three widths: **1920, 1280, and 960**
  (requested ~900; `MainWindow` declares `MinWidth = 960` in its own
  constructor and the real window honours it — discovered empirically,
  the test targets the actual narrowest width the product ever lays out
  at rather than an unreachable number).
- At each width asserts, from the real arranged bounds: the shell's
  compact threshold (`GlobalNavigationRail.IsCompact`, wired through
  `MainWindow`'s own `SizeChanged` at `DesignTokens.CompactShellWidth` =

  at 960px the document pane is never squeezed below its floor). The
  ribbon is set collapsed once, before any resize, and asserted still
  collapsed after every resize, proving the resize path does not leak
  into that unrelated, separately-persisted axis.

**Mutation-tested, not merely passing:**

  resize helper (keeping the `Measure`/`Arrange` calls) still passed —
  correctly: it proved `Measure`/`Arrange` is what drives layout under
  headless, not the property assignment alone, matching the documented
  warning in `WorkspaceLayoutHostTests`'s own remarks ("driving the
  Window's Width instead does nothing here"). Reverted (test file
  restored from the committed backup, confirmed byte-identical via
  `git diff`).
- The real discriminating mutation: commenting out
  `_navigationRail.SetCompact(compact);` inside `MainWindow`'s own
  `SizeChanged` handler (`src/Tempest.Desktop/MainWindow.cs`) — rebuilt,
  reran the test: **failed** (`Assert.Equal() Failure: Expected: True,

  `git diff src/Tempest.Desktop/MainWindow.cs` empty before proceeding.
  This is the proof the test would fail if `MainWindow`'s own resize
  wiring regressed, not just when a test-side helper is broken.

## 4. Core-side temp-directory leak (`ProjectGovernanceTests`, `ProjectTaskTests`,
`ProjectMilestoneTests`, `ProjectAreaRegisterTests`)

Not a Technical Debt Register row of its own — the register's `TD-120`
names only the Desktop-side leak, already Resolved by `WP 15.2A`. This is
the same defect shape on the Core side, found and fixed under this Work
Package's own "test determinism" remit because an unbounded per-run
`/tmp` leak is exactly the kind of environment-dependent failure mode
(disk exhaustion) `TD-120`'s own register text already documented for the
Desktop suite.

**Root cause, re-derived directly:** each of the four files' own
`Fixture.CreateAsync()` builds a fresh
`Path.Combine(Path.GetTempPath(), "tempest-project-{name}-" + Guid.NewGuid())`
root and never deletes it. Call-site counts, re-grepped:
`ProjectTaskTests.cs` 20, `ProjectMilestoneTests.cs` 17,
`ProjectAreaRegisterTests.cs` 12, `ProjectGovernanceTests.cs` 16 —
**65 total**, matching the fact sheet exactly.

**Design decision — per-test `IDisposable`, not a shared
`[CollectionDefinition]`.** The Desktop precedent
(`WorkspacePersistenceCollection`, `TD-120`) groups every
`WorkspaceHost`-building class into one xUnit collection so one
`ICollectionFixture` can delete a shared root once, after everything
finishes — but xUnit never runs two classes from the same collection in
parallel, and today these four classes are each their own default
collection, running concurrently with each other. Grouping them would
serialise four classes that do not need to be serialised (nothing about
their own fixtures is process-wide shared state — each already builds a
fully isolated `PersistenceStore` root). Chosen instead: each of the four
classes implements `IDisposable`; xUnit constructs a fresh instance per
`[Fact]`/`[Theory]` (not per class), so `Dispose()` runs once per test —
exactly matching fixture-creation granularity. A private
`CreateFixtureAsync(...)` wrapper on each class creates the fixture,
records `fixture.Root`, and returns it; every one of the 65 call sites
was mechanically repointed at that wrapper (`sed`, then hand-verified —
see the recursion bug caught and fixed below). `Dispose()` deletes every
root the instance recorded, swallowing `IOException`/
`UnauthorizedAccessException` so a locked file cannot mask the test's own
real result as a cleanup failure. This preserves the four classes'
existing cross-class parallelism, which the Desktop precedent's own
`[CollectionDefinition]` approach would not have.

**Shared parent for identifiability.** New file
`tests/Tempest.Core.Tests/Projects/ProjectFixtureRoot.cs`: a static
`RootPath` (`Path.GetTempPath()/tempestos-core-tests-{guid}/`, one per
process) and `NewIsolatedRoot(prefix)` nesting each fixture's own root
beneath it — every one of the four `Fixture.CreateAsync()` methods now
calls this instead of building its own `Path.Combine` directly. A
best-effort `AppDomain.ProcessExit` hook removes the (by then normally
empty) shared parent too, catching what per-test disposal could not
(a killed process, a `Dispose` itself throwing) without ever masking a
real test failure.

**Caught during implementation, disclosed rather than silently fixed:**
the mechanical `sed` replacement of `Fixture.CreateAsync(` →
`CreateFixtureAsync(` in each file also rewrote the one call *inside*
`CreateFixtureAsync`'s own body, producing infinite recursion
(`CreateFixtureAsync` calling itself). Caught immediately by the first
build/test pass in each file (a `StackOverflowException` would have
crashed the test host); manually corrected back to
`XxxFixture.CreateAsync(...)` in all four wrapper bodies before
proceeding.

**Proof — proves the root is removed, not just asserts it should be:**
new test `ProjectGovernanceTests.DisposingThisTestInstance_DeletesTheFixturesOwnPersistenceRoot`
creates a fixture, performs a real write (`CreateProjectAsync`, forcing
`PersistenceStore`'s lazy `Directory.CreateDirectory` — the store does
not create its root until first write, confirmed by reading
`PersistenceStore.cs`), asserts the root **exists**, calls `Dispose()`
directly, asserts the root **no longer exists**.

**Empirical count, this worktree, `/tmp` cleared first:**

| Point | `tempestos-core-tests-*` (this fix's own prefix) |
|---|---|
| Before any run | 0 |
| After 1 full Core suite run (3,090 tests, Release) | 0 |
| After 2 full Core suite runs | 0 |
| After 3 full Core suite runs | 0 |

Legacy-named `tempest-project-*` directories were also observed on this
shared machine during validation (0 after run 1, 64 after run 2) — traced
to **other concurrent agent sessions on the same host** running their own
unfixed worktrees in parallel (`ps aux` showed live `dotnet test`
processes under `.claude/worktrees/agent-a172bf39fa11d2de8`,
`agent-a764f202068d91463`, none of them this branch), confirmed by the
fact that every one of those leftover directories used the *old*,
un-nested naming scheme (`tempest-project-areas-*` directly under `/tmp`),
never the new `tempestos-core-tests-{guid}/*` nesting this fix produces —
i.e. zero of *this fix's own* directories were ever found left behind.
Noted here rather than omitted because a misleading "leftover count" was
briefly visible mid-validation and the actual cause matters more than the
number.

## 5. `SampleSeparationTests` — environment dependency on extra worktrees

**Root cause, confirmed by reading, not the fact sheet alone.**
`FindRepositoryRoot()` walks up from `AppContext.BaseDirectory` looking
for `global.json` — in *this* worktree that resolves to this worktree's
own root (`.../worktrees/agent-ac8d8e4918fb13f03/global.json`), which has
no nested `.claude/worktrees` of its own, so
`TheSampleAssembly_IsDeletable_NothingOutsideItDeclaresItAsADependency`
**passes here today, trivially** — there is nothing to trip over. The
failure mode described in the fact sheet occurs when the same test runs
from a checkout that *does* have sibling git worktrees under
`.claude/worktrees/**` (each a full nested checkout, complete with its
own `tests/**/*.csproj` referencing `Tempest.Samples`) — `Directory.EnumerateFiles(root, "*.csproj", SearchOption.AllDirectories)`
has no way to prune those directories from the walk, so the enumeration
returns project files that belong to a nested checkout, not to the tree
under test.

**This worktree's own git-operation sandboxing prevented reproducing the
failure directly** (Bash refuses `cd` into the shared checkout
`/home/user/TempestOS-Core` for git operations from an isolated worktree
agent) — worked around by **constructing the failure locally**: created
`.claude/worktrees/fake-nested/tests/Fake.Tests/Fake.Tests.csproj`
(inside this worktree, which itself has no `.claude` directory to begin
with) referencing `Tempest.Samples`, then ran the **original**,
`SearchOption.AllDirectories`-based test against it —
**reproduced the exact failure**: `Assert.Equal()` diff showing the fake
project's path as an unexpected extra holder. Confirms the fact sheet's
claim directly rather than by inference.

**Change.** New private helper `EnumerateProjectFiles(root)` — a manual
stack-based directory walk that prunes any directory whose name starts
with `.` (catches `.git`, `.claude`, `.vs`, any other dot-directory) or
equals `bin`/`obj`, rather than filtering the flat result afterward
(`SearchOption.AllDirectories` gives no pruning hook). Both call sites in
the file (`NoProjectUnderSrc_ReferencesTheSampleAssembly_ExceptTheSampleAssemblyItself`
and `TheSampleAssembly_IsDeletable_NothingOutsideItDeclaresItAsADependency`)
now use it; existing `.Where` filters (the `obj` substring check, the
`src/Samples` exclusion) are left in place — assertion semantics
unchanged, redundant-but-harmless.

**Proof.**
- Rebuilt with the fix in place against the same fake nested worktree:
  **passed** — the fake directory is correctly pruned.
- Reverted to the original `SearchOption.AllDirectories` code (fix
  temporarily backed out) with the fake directory still present: **failed**
  again, identically — confirms the fix, not an unrelated change, is what
  closes the gap.
- Restored the fix, deleted the fake directory
  (`rm -rf .claude` — this worktree's own tree, confirmed via
  `git status` showing no tracked-file changes from the deletion): full
  `SampleSeparationTests` class, 25/25 passed.
- Full Core suite: 3,090/3,090 across 3 Release runs (§8), `.claude`
  absent throughout.

## 6. `LifecycleTestLog` — thread safety

**Root cause.** `internal static class LifecycleTestLog` held a bare,
reassignable `List<string> _entries` with no lock and no
`[Collection]` guard. Confirmed single-consumer by grep: only
`ModuleLifecycleManagerTests.cs` calls `LifecycleTestLog.Reset()`/
`.Record()`/`.Entries` — `HostTestFixtures.cs` and
`HostedServiceFixtures.cs` only *mention* it in a comment as the naming
precedent for their own, separate logs.

**Chosen fix — lock, not a `[Collection]` guard (smaller, and strictly
stronger).** `ModuleLifecycleManager`'s own invocation of lifecycle
methods is a `foreach`, not a parallel fan-out (confirmed by reading
`ModuleLifecycleManager.cs`), so no concurrent write has ever actually
raced inside a single test. A `[Collection]` tag on the sole consumer
class would guard only against whatever else joined that same named
collection in the future — nothing does today, so it would be a
no-op label. A `lock` around `Reset`/`Record`/`Entries` (returning a
defensive `ToList()` snapshot under the lock) closes the hazard
unconditionally, for any future consumer, without depending on anyone
remembering to join a collection. Smallest correct, and the more durable
guarantee.

**Proof.** `dotnet test --filter "FullyQualifiedName~ModuleLifecycleManagerTests"`
(Debug, `--no-build`): 15/15 passed. Included in the full Core suite:
3,090/3,090 across 3 Release runs (§8).

### 1. Root cause and fix

Confirmed exactly as the prior analysis stated:
`tests/Tempest.Desktop.Tests/TestAppBuilder.cs` built its `AppBuilder` with
`.UseHeadless(new AvaloniaHeadlessPlatformOptions())` and no Skia, so
`Avalonia.Media.Imaging.Bitmap` decodes ran through the headless
platform's own stub decoder rather than a real codec.

`TD-100`'s own register row (`docs/governance/Quality/Technical Debt
Register.md`) states the fix directly: *"Closing it needs a
rendering-capable test host, not a change to the viewer."* That is the
constraint this change satisfies exactly — every line touched is under
`tests/Tempest.Desktop.Tests/`, and `src/Tempest.Desktop/Viewing/
DocumentPageSources.cs` (`ImageDocumentPageSource`) is untouched, because
the register's own note is correct: the viewer's decode call was never
the problem, the test host feeding it a stub decoder was.

The mechanism, confirmed by decompiling `Avalonia.Headless` 11.3.20 with
`ilspycmd` (no source browsing available offline) rather than assumed
from documentation:

- `AvaloniaHeadlessPlatformExtensions.UseHeadless` reads
  `AvaloniaHeadlessPlatformOptions.UseHeadlessDrawing`. When `true` (its
  constructor default), it calls
  `UseRenderingSubsystem(HeadlessPlatformRenderInterface.Initialize,
  "Headless")` — the stub. When `false`, it skips that call entirely and
  leaves whichever rendering subsystem was already registered in place.
- `SkiaApplicationExtensions.UseSkia()` (from the newly-added
  `Avalonia.Skia` 11.3.20 package) registers the real Skia rendering
  subsystem the same way: `UseRenderingSubsystem(() =>
  SkiaPlatform.Initialize(...), "Skia")`.

So the fix is `.UseSkia()` called **before** `.UseHeadless(new
AvaloniaHeadlessPlatformOptions { UseHeadlessDrawing = false })` — Skia
registers the rendering subsystem, and the headless platform, told not to
overwrite it, leaves it in place. Windows still run with no real display
attached (the headless windowing subsystem is unchanged); only image
decode/draw now goes through a real codec. `Avalonia.Skia` was pinned to
`11.3.20`, identical to the existing `Avalonia.Headless.XUnit` reference,
per this branch's own file boundary.

`Tempest.Desktop.Tests.Tempest.Desktop.Tests.csproj` gained the one
package reference; no other project file changed.

**Verified:** a temporary run of `DocumentPageSourceTests.ImageDecoding
IsReal()`'s own probe (the 4x3 fixture PNG, decoded and checked for its

### 4. Narrower per-session design — investigated, not needed

The instruction asked for a fallback if enabling Skia globally
destabilised the suite or slowed it by more than ~50%. Neither happened
(§3), so the fallback was not built — but its feasibility was checked
directly rather than assumed, by decompiling `Avalonia.Headless.XUnit`
11.3.20:

- `[assembly: AvaloniaTestApplication(typeof(TestAppBuilder))]` is backed
  by `AvaloniaTestApplicationAttribute`, declared
  `[AttributeUsage(AttributeTargets.Assembly, AllowMultiple = false)]` —
  exactly one `AppBuilder` entry point per test **assembly**, not per
  class or per collection.
- The framework it activates, `AvaloniaTestFrameworkAttribute`
  (`AvaloniaTestFramework` / `AvaloniaTestAssemblyRunner`), replaces the
  xUnit test framework for the whole assembly and is itself
  `[AttributeUsage(AttributeTargets.Assembly, AllowMultiple = false)]`.

So `Avalonia.Headless` 11.3.20 has no supported per-test-session or
per-collection override of the `AppBuilder` — every `[AvaloniaFact]` in
one assembly runs against the one `BuildAvaloniaApp()` that assembly
declares. A narrower design would need a **second test assembly** (a new
`.csproj`), which this branch's own file boundary forbids alongside being
disproportionate to a 40% duration increase with zero destabilisation.

**Recommendation.** Keep the assembly-wide Skia enablement as implemented
in §1. If a future Work Package needs the stub's faster, drawing-free
runs back for some other reason, the correct unit for that split is a
second `Tempest.Desktop.*.Tests` project, not an in-assembly toggle.
