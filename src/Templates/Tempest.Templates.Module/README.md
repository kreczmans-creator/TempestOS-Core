# Your New TempestOS Module

This project was generated by the TempestOS module template
(`dotnet new tempest-module`). It compiles as-is and is already shaped
exactly as `docs/academy/02 Runtime Architecture/03-building-a-module.md`
("Building a Module") describes — but it isn't wired into the platform
yet. Two steps remain:

## 1. Add it to the solution

From the repository root:

```
dotnet sln src/TempestOS.slnx add path/to/YourModule/YourModule.csproj
```

## 2. Make it discoverable

A module is only discovered once something references its assembly and
that assembly is loaded into the running process. The simplest path,
used by every real module in this repository today, is an ordinary
project reference from `Tempest.App` (or from a test project, to prove
it in isolation first) — see `Tempest.Samples.ClockModule` for the
living reference example every other module in this codebase is proven
against.

Packaging your module as a **plugin** instead (loaded from
`Plugins/<name>/` via a manifest, with no project reference from
`Tempest.App` at all) is also supported — see
`docs/architecture/Plugin Manifest Architecture.md` and
`docs/academy/02 Runtime Architecture/07-plugin-architecture.md` if
that fits your module better.

## Customising further

- The generated class already carries `[ModuleMetadataAttribute]`, so
  its constructor is free to request any DI-public platform service —
  add a parameter and assign it to a field, exactly as `ClockModule`
  does with `IEventBus`.
- Override only the lifecycle methods (`InitialiseAsync`, `StartAsync`,
  `StopAsync`, `DisposeAsync`) your module actually needs — every one is
  `virtual` and defaults to a no-op.
- If your module doesn't live as a sibling of `Tempest.Samples` under
  `src/Samples/`, adjust the `ProjectReference` path in the generated
  `.csproj` to point at the real location of `Tempest.Core.csproj`.
