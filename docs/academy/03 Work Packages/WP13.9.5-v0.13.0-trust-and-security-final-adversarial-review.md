# WP 13.9.5 — `v0.13.0` Trust & Security Final Adversarial Review

## 1. Introduction

This Work Package is a **review**. It produced no production code, no
test, and no ADR of its own. Its entire deliverable is a judgment,
delivered adversarially: after `WP 13.9.1`, `WP 13.9.2`, `WP 13.9.3`, and
`WP 13.9.4` had each in turn found and closed a trust-boundary gap in the
`v0.13.0` plugin trust platform, is the boundary those four Work Packages
collectively claim to have closed actually closed?

It ran on `feature/v0.13.0`, immediately after `WP 13.9.4` (Trust-Denial
Execution Boundary Remediation) and immediately before `WP 13.9.6` (Module
Discovery Trust Boundary Remediation), which it directly commissioned. Per
`docs/releases/v0.13.0/WorkPackages.md`'s own `WP 13.9.5` row, the review
was performed by **six parallel, read-only reviewers (Security,
Architecture, Runtime/Lifecycle, Verification, Governance, Adversarial),
each performed before seeing the others' conclusions**. Its answer was not
a clean bill of health: the boundary was found "defensible for its own
literal claims," and three of the six reviewers each independently
reproduced, with a live proof-of-concept, a further, distinct, genuine
code-execution defect that none of the preceding four Work Packages had
looked for.

**A note on this document's own provenance.** This retrospective was not
written contemporaneously with `WP 13.9.5`. The Work Package itself
produced no standalone report file — its own row records that "its report
was delivered conversationally to the commissioning session, not saved as
a standalone file," and that the row itself is retroactive, added later by
`WP 13.9.7`. `WP 13.9.7` further confirmed, by direct convention check
against `Academy Index.md`'s own stated maintenance rule and the
`WP 13.2B`/`WP 13.9.1` precedent, that `WP 13.9.1`–`WP 13.9.6` did not
require Academy retrospective files of their own. This document does not
overturn that finding; it supplements the record, and every fact below is
grounded strictly in `d7d19d4`'s own commit message, this Work Package's
own `WorkPackages.md` row, its retained `PROJECT_STATUS.md` stratum,
`ADR-0111`'s own "Corrected, `WP 13.9.6`" section, `docs/security/Plugin
Trust & Isolation Architecture.md`'s own Risks entry, and — where a claim
is checkable from code alone — direct reads of real, current source. What
could not be corroborated beyond the record's own statement is named
explicitly in the Observations section, not smoothed over. This is the
same "disclose, don't fabricate" handling
`WP13.3B-plugin-platform-integration-and-end-to-end-validation-review.md`
established for a reconstructed retrospective.

## 2. Purpose

To determine, adversarially and independently, whether the `v0.13.0`
plugin trust platform's execution boundary was genuinely closed before it
became a permanent commit — not whether each preceding Work Package had
done what it said it did (each had), but whether what they collectively
did was **enough**.

The distinction matters, and is the reason this Work Package exists at
all. `WP 13.9.1` closed `WP 13.9.0`'s four named findings and nothing
broader, exactly as scoped. `WP 13.9.2` then re-verified `WP 13.9.1`'s own
fix and found it incomplete. `WP 13.9.3` closed what `WP 13.9.2` found.
`WP 13.9.4` found a separate, more severe defect entirely — and its own
Adversarial Review found `WP 13.9.4`'s own first pass incomplete,
broadening it mid-Work-Package. A chain in which every verification pass
finds the previous pass incomplete is a chain with no natural stopping
point. `WP 13.9.5`'s purpose was to be that stopping point, or to prove it
had not yet been reached.

It was explicitly read-only. It produced no code changes of its own, by
design — a reviewer that fixes what it finds is no longer an independent
reviewer of the thing it fixed.

## 3. Background

The chain this review was auditing, in sequence, per `d7d19d4`'s own
commit message:

- **`WP 13.9.0`** — the `v0.13.0` Engineering Readiness Review, which
  named four findings in the plugin trust platform.
- **`WP 13.9.1`** — Readiness Remediation, closing those four findings
  only. `PluginAssemblyLoader.DiscoverModuleTypes` gained a fixed-point,
  breadth-first `AppDomain`-diff scan following every assembly entering
  the process as a direct or transitive consequence of examining a
  plugin's own declared assembly, closing a bypass where a second,
  undeclared assembly reached via base-type inheritance could contribute
  an `IModule` implementer with zero trust checking.
- **`WP 13.9.2`** — Readiness Re-Execution, verification only. Found that
  scan still incomplete: it diffed the `AppDomain` only around
  `Assembly.GetTypes()`/`IsAssignableFrom`, not around the independent CLR
  lazy-load trigger a discovered module's own constructor parameter types
  represent.
- **`WP 13.9.3`** — Multi-Assembly Trust-Boundary Remediation, widening
  the scan so each step's own `AppDomain` diff also covers forcing
  resolution of every discovered module type's every public constructor's
  every parameter's `ParameterType`.
- **`WP 13.9.4`** — Trust-Denial Execution Boundary Remediation, closing a
  separate and more severe defect: `PluginTrustDeniedException` never
  actually prevented a denied plugin's already-loaded assembly (`ADR-0015`:
  load cannot be undone) from being separately rediscovered by Module
  Discovery and Hosted Service Discovery — both deliberately
  plugin-unaware per `ADR-0110` — and fully lifecycle-run, since a denied
  module's ambient component principal is `null` and `null` is treated as
  First-Party. Closed via a Host-owned `PluginDeniedTypeRegistry` plus
  filters at Module Registration and Hosted Service Registration.

The architectural facts the review had to hold simultaneously: `ADR-0110`
decides that the isolation boundary is capability-scoped and in-process,
and that the Module and Hosted Service pipelines are deliberately
plugin-unaware; `ADR-0015` decides that a Host is single-use and an
assembly load cannot be undone; `ADR-0027` establishes the declarative
module metadata convention, under which a module carrying
`[ModuleMetadataAttribute]` is never instantiated by discovery, and one
without it is instantiated purely to read its `Id`/`Name`/`Version` — a
convention dating to `WP 5.3`, written long before any third-party plugin
existed, and never previously a security concern because every module was
first-party by construction.

## 4. The Problem

The review had to answer questions a passing test suite structurally
cannot:

1. **Is `WP 13.9.4`'s "excluded before `RuntimeModuleManager.Register`
   ever sees it" the right boundary at all** — or is there code execution
   belonging to a denied plugin that happens *earlier* in the Host
   lifecycle than Registration?
2. **Does the pipeline's own phase ordering hide an execution site?**
   Plugin Loading populates the denied-type registry; Module Discovery
   runs next; Module Registration, where both `WP 13.9.4` filters live,
   runs after that. Anything a denied plugin's code does during the middle
   phase is outside both filters by construction.
3. **Do the preceding Work Packages' claims survive an adversary who is
   not looking for the defect they fixed?** Each of `WP 13.9.1`–`WP 13.9.4`
   was scoped to the finding that commissioned it. A scoped fix verified
   only against its own scope proves nothing about the axis nobody asked
   about.
4. **Is the governance record true?** A trust boundary whose ADR, security
   architecture, and registers describe a state the code does not actually
   hold is a boundary nobody can safely reason about afterwards.

## 5. The Design

This section describes **the review's own design** — its disciplines, its
independence rules, and its evidential standard — because that is this
Work Package's only deliverable.

**Six disciplines, run in parallel, each blind to the others.** Per its
own `WorkPackages.md` row: Security, Architecture, Runtime/Lifecycle,
Verification, Governance, and Adversarial, "each performed before seeing
the others' conclusions, per `Engineering Readiness Review Architecture.md`
§5's own independence discipline." That §5 states the rule plainly: each
reviewer performs their own review **before** seeing the others'
conclusions — "the deliberate, already-proven discipline that found
`TD-42`/`TD-43` at `v0.11.0`: a QA Lead who deferred to a Workflow
Engineer's own 'looks fine' would not have independently exercised the
release-tooling scripts against real fixtures."

*Disclosed precisely*: §5's own named six are role titles — Chief
Architect, Principal Engineer, Workflow Engineer, QA Lead, Technical
Author, Product Manager — not the six discipline names `WP 13.9.5` used.
The citation in the record is to §5's **independence discipline**, which
`WP 13.9.5` applied to a differently-named, engineering-tier roster; it is
not a claim that this Work Package executed a release-level Engineering
Readiness Review. `WP 13.9.5` is not an ERR, has no §6-vocabulary verdict
recorded anywhere in the governance record, and made no release decision.

**Read-only, absolutely.** Its row records "This Work Package produced no
code changes of its own — a read-only review." The consequence is
deliberate: a finding could only be closed by commissioning a successor
Work Package, which is exactly what happened (`WP 13.9.6`). The reviewer
that finds a defect never becomes the author of its fix, so the fix gets
its own fresh, independent adversarial review rather than a
self-assessment.

**A live proof-of-concept as the evidential standard, not an argument.**
The three convergent findings are recorded not as "a reviewer believed"
but as reproductions: `ADR-0111`'s own corrected section describes "a live
proof-of-concept (independently found and confirmed three separate times —
`WP 13.9.5`'s own Runtime/Lifecycle, Security, and Adversarial reviewers,
each with a compiled reproduction against the unmodified pipeline)." A
compiled reproduction against unmodified code is falsifiable in a way a
code-reading opinion is not.

**The adversarial stance.** The presumption is that defects exist until
personally disproven — the same instruction `WP 13.3B` gave its own four
audit sub-agents ("assume defects exist until personally disproven, not to
confirm the work is fine by default"). This is what makes the review's
partial clearance meaningful: "the combined `WP 13.9.3`+`WP 13.9.4`
boundary defensible for its own literal claims" is a narrow statement, and
was deliberately written narrowly.

**Governance in scope, alongside code.** One of the six disciplines was
Governance, and it produced a finding of its own: a staleness in `ADR
Register.md`'s own `ADR-0111` citation, flagged as needing to close before
commit. Per `Engineering Readiness Review Architecture.md` §5, "small,
genuinely narrow corrections (a stale register figure, a missing
cross-reference) found during the review may be corrected within the same
sign-off Work Package" — but this Work Package was instructed read-only,
so the correction was carried forward and executed by `WP 13.9.7` instead.

## 6. Alternatives Considered

The record does not document a menu of review shapes that `WP 13.9.5`
itself weighed and rejected; it documents the shape it ran. What the wider
record *does* establish is that the project had already rejected three
alternative sign-off shapes, in `Engineering Readiness Review
Architecture.md`'s own Alternatives Considered section — continuing an
informal per-release checklist, a single-reviewer sign-off, and a purely
automated gate — in favour of the multi-discipline, independence-first
shape `WP 13.9.5` applied here at the Work Package tier.

One alternative is visible in the record by elimination rather than by
deliberation: **trusting `WP 13.9.4`'s own internal Adversarial Review and
committing the chain without a further pass.** That was not taken, and the
record shows why it would have been unsafe — `WP 13.9.4`'s own Adversarial
Review had found `WP 13.9.4`'s first pass incomplete and broadened it
mid-Work-Package, which demonstrates a review internal to a Work Package
catching an in-scope gap, not an out-of-scope one. The defect `WP 13.9.5`
found sat on an axis `WP 13.9.4` had no reason to examine.

The record is silent on whether a smaller review (fewer disciplines, or a
single security reviewer) was considered and rejected for this specific
Work Package. It is recorded as silent here rather than filled in.

## 7. Why This Solution Was Chosen

The review's shape is justified by its own result, and the justification
is unusually concrete.

**Convergence is the evidence.** Three of six reviewers — Runtime/Lifecycle,
Security, and Adversarial — each *separately* reproduced the same defect,
each with their own compiled proof-of-concept, none having seen the
others' conclusions. Independent convergence on a single finding is the
one thing a serial review cannot produce: a second reviewer who has
already read the first's report is no longer independent evidence of
anything. This is the same signal `WP 13.3B`'s own record prizes, where
two of four independent audits converged on one genuine
registry-Id-spoofing defect, and the same one `WP 13.9.0`'s
most-corroborated finding carried, found by four of six disciplines.

**Independence also produced the split verdict.** A less disciplined
review, presented with a boundary four preceding Work Packages had just
hardened and whose tests all passed, would plausibly have converged on
"clean." The recorded finding is deliberately two-part: defensible for its
literal claims, *and* carrying a further, distinct, live-reproduced
defect. Both halves are true simultaneously, and only a review willing to
state both would have recorded them that way.

**The finding itself.** Per its own row and `ADR-0111`'s corrected
section, the three reviewers found that
`ReflectionFrameworkDiscoveryService.CreateDescriptor`'s own
metadata-reading convention (`ADR-0027`) called `Activator.CreateInstance`
for any `IModule` candidate type lacking `[ModuleMetadataAttribute]`,
unconditionally, during Module Discovery — which runs strictly before the
`WP 13.9.4` Module Registration filter is ever consulted — so a denied
plugin's unattributed module constructor **genuinely executed**: real,
verified code execution. A more severe variant was also confirmed: a
denied, unattributed module with no public parameterless constructor hits
`CreateDescriptor`'s own `ModuleDiscoveryException` guard, uncaught inside
the Discovery loop — Host-fatal, crashing `RunAsync` entirely, "a
denial-of-service any plugin author could trigger deliberately, requiring
no constructor trickery beyond a bare capability-ceiling denial."
`docs/security/Plugin Trust & Isolation Architecture.md` adds the detail
that makes it worse: "`Plugins:AllowUnsignedLoad` is irrelevant to either:
capability-ceiling denial alone is a sufficient precondition."

Both halves of that finding are checkable from real source today, and were
verified directly for this retrospective. `CreateDescriptor` still
contains exactly the `Activator.CreateInstance(type)` call and the
`ModuleDiscoveryException` guard the finding describes — now reached only
after the predicate `WP 13.9.6` added; and
`src/Tempest.Core/BackgroundServices/HostedServiceDiscoveryService.cs`
contains no `Activator`, `CreateInstance`, or `GetConstructor` call at
all, corroborating the record's claim that the hosted-service pipeline
needed no equivalent fix.

## 8. Architectural Principles

- **Independence Before Convergence** — six reviewers, each blind to the
  others until their own conclusion was formed. Convergence is only
  evidence if it was not coordinated.
- **Assume Defects Exist Until Personally Disproven** — the adversarial
  stance `WP 13.3B` established for audit sub-agents, applied here to a
  boundary four Work Packages had just claimed to close.
- **A Live Proof-of-Concept, Not an Argument** — each of the three
  convergent findings is recorded as a compiled reproduction against the
  unmodified pipeline, not as a reading of the code.
- **A Reviewer Does Not Fix What It Reviews** — read-only by instruction;
  the finding commissioned `WP 13.9.6`, which then earned its own fresh,
  independent adversarial review rather than a self-assessment.
- **Narrow Claims, Stated Narrowly** — "defensible for its own literal
  claims" is not "correct," and the record says exactly the former.
- **Governance Is In Scope for a Security Review** — a stale register
  citation is a real finding, raised here and closed by `WP 13.9.7`, not
  quietly left for someone to notice later.

## 9. Benefits

- **A real, live-reproduced code-execution defect was found before the
  chain became a permanent commit** — a denied plugin's constructor
  running inside the Host process is precisely the outcome the whole
  `ADR-0110`/`ADR-0111` trust boundary exists to prevent, and it survived
  four preceding remediation Work Packages untouched.
- **A Host-fatal denial-of-service variant was found with it** — worse in
  effect than the quiet execution, trivially triggerable, and requiring no
  unsigned-load misconfiguration to reach.
- **The defect was found on an axis nobody had been asked to examine.**
  Every preceding Work Package in the chain was scoped to its own
  commissioning finding; this one was scoped to the boundary as a whole.
- **The boundary's genuinely closed parts were confirmed genuinely
  closed**, which is what made `WP 13.9.6` a small, targeted fix rather
  than a redesign.
- **A governance staleness was surfaced with a named owner and a
  deadline** ("needing to close before commit"), and did in fact close, in
  `WP 13.9.7`.

## 10. Trade-offs

- **It fixed nothing.** A read-only review's finding is inert until a
  successor Work Package is commissioned and run. The chain grew by two
  further Work Packages (`WP 13.9.6`, `WP 13.9.7`) as a direct result.
- **Six parallel reviewers is expensive for a partial clearance.** Three
  of the six converged on the finding; the record does not state what the
  other three concluded beyond the boundary being defensible for its own
  literal claims, and no per-discipline report survives to say.
- **No standalone report file exists.** Its report was delivered
  conversationally to the commissioning session. The durable record is
  therefore `d7d19d4`'s commit message, one `WorkPackages.md` row, one
  retained `PROJECT_STATUS.md` stratum, and the `ADR-0111`/security-architecture
  narratives — dense, but second-hand, and all authored by `WP 13.9.7`
  rather than by the reviewers themselves.
- **"Final" was not final.** The Work Package is titled a *Final*
  Adversarial Review, and `ADR-0111` records `WP 13.9.6` as believed to be
  "the third and … final correction." `WP 13.10A` and `WP 13.11A` each
  subsequently found further, genuinely distinct gaps in the same
  boundary. The title described an intent, not an outcome.

## 11. Common Mistakes

1. **Reading "defensible for its own literal claims" as "correct."** It is
   the narrowest possible clearance: the claims each preceding Work
   Package made are true as written. It says nothing about the claims
   nobody made.
2. **Assuming a Registration-time filter covers Discovery-time
   execution.** `WP 13.9.4`'s filters are correct and load-bearing; they
   simply run after the phase in which the defect executed. Phase
   ordering, not filter logic, was the gap.
3. **Assuming a metadata-reading convention is passive.** `ADR-0027`'s
   fallback path calls `Activator.CreateInstance`. "Discovery" reads as a
   passive scan and was not one — a convention entirely safe while every
   module was first-party by construction (`WP 5.3`) became a trust
   boundary the moment third-party denial existed.
4. **Assuming a green suite is evidence of a closed boundary.** Every test
   passed throughout. The defect required a compiled reproduction built
   specifically to look for constructor execution — which is why the
   `WP 13.9.6` fix landed with `ConstructorExecutionProbe`, permanent test
   infrastructure that observes execution directly rather than inferring
   it from registration state.
5. **Treating a review as finished when the code review is clean.** The
   Governance discipline's staleness finding was real, was carried, and
   was closed by `WP 13.9.7`. A review that reports only on code leaves
   that class of defect to be found by nobody.

## 12. Future Evolution

- **The chain continued past this review.** `WP 13.10A` found `TD-51` and
  `TD-52` — both live-PoC-confirmed, and, per its own row, "neither a
  variant of anything the `WP 13.9.1`–`WP 13.9.6` remediation chain
  closed" — on a discovery axis (`IHostedService`-only plugins, and
  `IIdentityService.EstablishCurrentPrincipal`) this review did not
  examine. `WP 13.11A` then reopened `TD-51` after finding `WP 13.10C`'s
  own characterisation of a residual gap false for the `IModule` axis.
- **The review shape itself became reusable.** `WP 13.10C` is recorded as
  "the same integration-and-commit role `WP 13.9.7` established," and
  `ADR-0111` describes `WP 13.10C`'s four fresh, read-only reviewers as
  "mirroring `WP 13.9.6`'s" own arrangement — the parallel, independent,
  read-only shape used here propagated forward through the release.
- **The structural question this review implicitly raises** — how many
  independent adversarial passes a trust boundary needs before it can be
  declared closed — is not answered anywhere in the record. What the
  record shows instead is empirical: at `v0.13.0`, successive adversarial
  passes (`WP 13.9.0`, `WP 13.9.2`, `WP 13.9.5`, `WP 13.10A`, `WP 13.11A`)
  each found something the previous had not, until `WP 13.11D` returned no
  blocker across all six of its disciplines.

## 13. Key Takeaways

- A review that finds nothing and a review that finds everything are both
  suspicious. This one found a *specific* thing, on an axis outside every
  preceding Work Package's scope, and cleared the rest with a deliberately
  narrow phrase — which is what a genuine adversarial review's output
  actually looks like.
- **Independent convergence is the strongest evidence a review can
  produce.** Three reviewers reaching the same defect via three separate
  compiled reproductions, none having read the others, is qualitatively
  different from one reviewer's finding being agreed with.
- **Phase ordering is a trust boundary.** Every filter in the world is
  irrelevant to code that runs before it. "Where in the lifecycle does the
  adversary's code first get to execute?" is a different, and more useful,
  question than "what does the filter check?"
- **A convention that was safe for years can become a vulnerability
  without changing one line.** `ADR-0027`'s `Activator.CreateInstance`
  fallback did not change; the threat model around it did, when
  third-party plugin denial became real. Reviews of new trust boundaries
  must re-examine old, unmodified, previously uninteresting code.
- **Read-only is a discipline, not a limitation.** By refusing to fix what
  it found, this Work Package guaranteed the fix would be reviewed by
  someone other than its author — and `WP 13.9.6`'s own fresh, independent
  adversarial review is a direct consequence of that refusal.

## Observations

- **What is directly checkable from real source, and was verified for this
  retrospective**: `ReflectionFrameworkDiscoveryService.CreateDescriptor`
  still contains the `Activator.CreateInstance(type)` call and the
  `ModuleDiscoveryException`-throwing guard for a type with no public
  parameterless constructor, exactly as the finding describes;
  `src/Tempest.Core/BackgroundServices/HostedServiceDiscoveryService.cs`
  contains no `Activator`/`CreateInstance`/`GetConstructor` call at all,
  corroborating the record's claim that the hosted-service pipeline needed
  no equivalent fix; `d7d19d4` is a 35-file, `+3263/-90` commit.
- **What could not be corroborated beyond the record's own statement**:
  the number, naming, and parallelism of the six reviewers; that each
  worked before seeing the others' conclusions; that exactly three
  (Runtime/Lifecycle, Security, Adversarial) reproduced the finding
  independently; and the existence of the three compiled proofs-of-concept.
  No per-discipline report, proof-of-concept project, or review artefact
  from `WP 13.9.5` exists in the repository — its report was conversational
  by its own record, and the proofs-of-concept were built against the
  unmodified pipeline and not retained. These are recorded here as the
  record's own claims, attributed, not as independently verified fact.
- **A precise discrepancy, disclosed**: the `WorkPackages.md` row cites
  `Engineering Readiness Review Architecture.md` §5 for the independence
  discipline. §5's own six named disciplines are role titles (Chief
  Architect, Principal Engineer, Workflow Engineer, QA Lead, Technical
  Author, Product Manager), which are not the six this Work Package used.
  The citation is to the independence rule, not the roster; both sources
  are recorded here rather than reconciled by assumption.
- **No verdict, no Technical Debt item.** The record contains no
  §6-vocabulary verdict for `WP 13.9.5`, and no `TD-` item was raised or
  closed by it — its finding was closed directly by `WP 13.9.6` inside the
  same uncommitted changeset, and never needed to become tracked debt.
  `TD-51`/`TD-52` were raised later, by `WP 13.10A`.
- **This document is not cited by `Academy Index.md` or `Academy
  Register.md`.** This retrospective's own commissioning restricted it to
  creating this file and its two siblings; those registers were
  deliberately not modified, and their reconciliation remains outstanding.
