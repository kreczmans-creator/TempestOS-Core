# WP 13.11B — TD-51 Trust-Denial Crash Remediation

## 1. Introduction

`WP 13.11B` is a **production implementation** Work Package — the only
one in the `WP 13.11x` chain that changes `src/`. It closes the single
Release-blocking finding `WP 13.11A` raised: `TD-51`, reopened, the
"unresolvable constructor parameter type" residual gap that genuinely
crashes the whole Host on the `IModule` axis.

Commit **`8341438`**, 10 files, **+1060/-17**: two production files
(`PluginAssemblyLoader.cs`, `ReflectionFrameworkDiscoveryService.cs`),
three test files, and five governance documents. Four parallel sub-agents
— Security/Adversarial, Runtime/Lifecycle, Verification/Test,
Governance/Documentation — with the three analysis disciplines strictly
read-only and every production and documentation edit integrated
centrally, one owner per file.

The commit also carries `WP 13.11A`'s own documentation corrections,
which stopped before commit by that Work Package's explicit instruction.
The finding and its closure are therefore a single commit by design.

## 2. Purpose

To take `WP 13.11A`'s recommended minimum fix — **both** of its options,
and no wider — and close the root cause rather than the symptom.

The remit was explicitly minimal: no architectural change beyond existing
seams, no new ADR unless a genuine either/or ambiguity emerged, no
opportunistic hardening of adjacent items. `TD-53` and `TD-54` were left
tracked and untouched throughout, and one genuine consequence discovered
during the work (`TD-55`) was disclosed and tracked rather than fixed,
precisely because closing it needs architectural change.

## 3. Background

`WP 13.11A` traced the crash end to end and graded it *Release Blocking
for third-party plugin support*, not blocking `v0.13.0` as shipped
(`src/Plugins/` is empty; the path is dormant). It recommended:

- **(a)** have the unresolvable-constructor-parameter-type denial path
  call `RecordDenied` before throwing — *"with whatever partial type list
  `DiscoverModuleTypes` had already scanned"* — so `WP 13.9.6`'s
  `isTypeExcluded: deniedTypeRegistry.IsDenied` filter genuinely excludes
  the offending type;
- **(b)** wrap `ReflectionFrameworkDiscoveryService.CreateDescriptor`'s
  reflection path in the same four-exception CLR type-load guard,
  isolating the candidate rather than propagating.

Both were implemented. **(a)'s stated *shape* was not** — see §5 and §7,
because that divergence is the single most consequential decision this
Work Package made.

## 4. The Problem

Precisely, from `PluginAssemblyLoader.cs` and
`ReflectionFrameworkDiscoveryService.cs` as they stood at `79e453f`:

1. `DiscoverModuleTypes`'s `WP 13.9.3` pre-resolution loop forces every
   discovered type's every constructor parameter to resolve inside the
   scan's own diff window. When `constructor.GetParameters()` throws
   `TypeLoadException`/`FileNotFoundException`/`FileLoadException`/
   `BadImageFormatException`, the `catch` converted it to a
   `PluginTrustDeniedException` and **threw immediately, from inside the
   scan**.
2. That throw escaped `DiscoverModuleTypes` before `EnforceTrust` could
   reach either existing `RecordDenied` call site, so `deniedTypeRegistry`
   stayed empty for this one denial reason.
3. `TempestHost.cs`'s `WP 13.9.6` Module Discovery filter therefore
   excluded nothing.
4. `CreateDescriptor`'s unguarded `type.GetConstructor(Type.EmptyTypes)`
   — itself a genuine CLR type-load, arity-matching across every public
   constructor's full parameter signature — rethrew the identical failure
   uncaught.
5. It propagated through `TempestHost.RunAsync`'s outer
   `catch (Exception ex) { EnterFaulted(ex); throw; }`, faulting the whole
   Host.

Two independent defects, then, not one: a **recording** defect at the
loader, and a **guard** defect at Module Discovery. Either alone closes
the crash. Both were closed.

There was also a third problem the recommendation did not see. Aborting
the scan mid-traversal — the shape (a) literally described — skips the
per-step before/after `AppDomain` diff, leaving any assembly the plugin
had *already* pulled into the `AppDomain` unscanned and unrecorded, yet
fully visible to Module Discovery's deliberately plugin-unaware
`AppDomain` scan (`ADR-0110`).

## 5. The Design

**(a) The root cause — a denial that is surfaced, not thrown.**

`DiscoverModuleTypes` gained a new `out PluginTrustDeniedException?`
parameter. The `catch` no longer throws; it records the denial and
continues:

```
unresolvableConstructorDenial ??= new PluginTrustDeniedException(
    pluginId,
    $"Module or hosted service type '{moduleType.FullName}' declares a constructor " +
    $"parameter whose type could not be resolved ('{ex.GetType().Name}': {ex.Message}).");

break;
```

The `??=` keeps the **first** offending type, so the thrown message is
byte-identical to the one the immediate throw produced. The `break`
leaves that type's remaining constructors uninspected — the plugin is
already condemned, and every later constructor of a condemned type is
irrelevant — while the enclosing loops carry on, so the per-step
before/after `AppDomain` diff still executes and the fixed point still
closes.

`EnforceTrust` then handles it as a first-class denial path, at the same
seam as the other two, **placed first**:

```
if (unresolvableConstructorDenial is not null)
{
    RecordDenied(moduleTypes, hostedServiceTypes);

    throw unresolvableConstructorDenial;
}
```

First, deliberately, for two reasons: it preserves the message precedence
the in-scan throw already had (this denial reason has always won when a
plugin triggers more than one), and it keeps the offending type away from
`HasCompliantConstructor` below, whose own `GetConstructors()`/
`GetParameters()` calls are unguarded and would rethrow the identical
uncaught CLR type-load failure.

`RecordDenied` is unchanged — it records every discovered `IModule` and
`BackgroundServices.IHostedService` type via `IPluginDeniedTypeRecorder`
(`WP 13.9.4`). After this change, `DiscoverModuleTypes` contains **no
`throw` at all**.

**Deliberately a complete fixed-point scan, not the partial type list.**
This Work Package's own Security/Adversarial analysis found the
partial-list shape actively unsafe. Aborting the traversal leaves an
assembly already resident in the `AppDomain` — enqueued but not yet
dequeued, or pulled in earlier in the same step — unscanned and
unrecorded, while remaining fully visible to Module Discovery's
plugin-unaware `AppDomain` scan (`ADR-0110`). A well-formed module among
those (attributed, parameterless constructor) would then have been
registered and lifecycle-run with a `null`, and therefore
First-Party-treated (`PluginTrustPermission.IsFirstParty`), ambient
component principal — **trading the Host crash for a silent trust
bypass: strictly worse, and not fail-closed.**

**(b) The backstop.** `ReflectionFrameworkDiscoveryService.DiscoverModules`
now wraps its `CreateDescriptor` call in the narrow four-exception CLR
type-load guard:

```
catch (Exception ex) when (ex is TypeLoadException or FileNotFoundException or FileLoadException or BadImageFormatException)
```

The candidate is excluded and logged at `Warning` — never a crash, never
a silent inclusion. The class gains **no plugin awareness** (`ADR-0110`):
this is a reflection guard, not a trust decision. It is deliberately
narrow — `ModuleDiscoveryException` derives from none of the four, so the
long-standing `WP 5.3` "no parameterless constructor and no
`[ModuleMetadataAttribute]`" guidance and every `ValidateMetadata`
failure still propagate unchanged, and `DuplicateModuleIdException` is
thrown outside the guarded block entirely.

**No ADR added or amended.** `ADR-0111`'s Decision text already mandates
the recording behaviour (a) restores, verbatim — *"every `Type` this scan
discovered for it, whether an `IModule` implementer or a
`BackgroundServices.IHostedService` implementer, is recorded denied
(`IPluginDeniedTypeRecorder`, `WP 13.9.4`)"*. The defect was an
implementation divergence from an already-correct decision, not a
decision requiring revision; re-confirmed by direct read of that Decision
section before any documentation was written. `ADR Register.md`
accordingly untouched, its `Last Reviewed` still correctly citing
`WP 13.10C`.

**No public API change and no new dependency.** Every touched member is
`private`, except the `internal DiscoverModules(IEnumerable<Type>)` test
seam, whose signature is unchanged.

**Seven permanent regression tests**, across three files:

- `PluginAssemblyLoaderMultiAssemblyTrustTests.cs` (four) —
  `..._ModuleAxis_RecordsDeniedModuleType`,
  `..._HostedServiceAxis_RecordsDeniedHostedServiceType`,
  `..._RecordedTypeIsExcludedByModuleDiscoveryPredicate`, and
  `LoadPlugins_LegitimatePluginWithCompliantConstructor_IsNeverRecordedDenied_AndStillDiscoversNormally`
  — both discovery axes, the recorded-type-is-actually-excluded boundary,
  and the legitimate-plugin no-overreach direction.
- A new `ModuleDiscoveryUnresolvableConstructorTests.cs` (two) — the
  guard, and its narrowness
  (`..._TypeWithNoParameterlessConstructorAndNoMetadataAttribute_StillThrowsActionableModuleDiscoveryException`).
- `TempestHostPluginTrustTests.cs` (one) — end to end:
  `RunAsync_UnresolvableConstructorParameterModulePlugin_IsRecordedTrustDenied_HostStaysRunning_ModuleNeverRegistered`.

**Non-vacuousness confirmed by reverting each half independently.** With
`RecordDenied` reverted, the three recording tests fail; with the
discovery guard reverted, the guard test fails on the raw reflection
exception; with **both** reverted, the end-to-end Host test reproduces
`WP 13.11A`'s crash exactly — `Assert.Equal() Failure: Expected: Running,
Actual: Faulted`. Both production files were then restored and confirmed
byte-identical to their fixed versions.

## 6. Alternatives Considered

- **The partial type list, exactly as recommended.** Rejected on
  security grounds — the central design decision of this Work Package.
  It would have satisfied the letter of `WP 13.11A`'s recommendation and
  shipped a silent trust bypass in place of a crash.
- **Merely adding a `RecordDenied` call to the existing throw.** The same
  rejection, stated more sharply: it closes the recording defect without
  closing the traversal defect, so types already resident in the
  `AppDomain` remain undiscovered by the scan and visible to Module
  Discovery.
- **Option (b) alone.** Sufficient to stop the crash, and insufficient as
  a fix: it treats the symptom at Module Discovery while leaving
  `deniedTypeRegistry` empty for this denial reason, so the
  execution-boundary registry stays wrong. Root cause first, backstop
  second.
- **Giving `ReflectionFrameworkDiscoveryService` plugin awareness.**
  Rejected against `ADR-0110`, which makes that class deliberately
  plugin-unaware. The guard added is a reflection guard, not a trust
  decision, and the class references no `Tempest.Core.Plugins` type.
- **Raising a new ADR.** Rejected: `ADR-0111`'s Decision already
  mandated the restored behaviour verbatim, so there was no either/or
  ambiguity for an ADR to resolve.
- **Fixing `TD-55` in the same Work Package.** Rejected as out of remit —
  closing it needs per-plugin denial scoping, an architectural change to
  `WP 13.9.4`'s registry shape. Disclosed and tracked instead.

## 7. Why This Solution Was Chosen

Because a remediation Work Package's obligation is to the *finding*, not
to the *wording of the recommendation*. `WP 13.11A` correctly identified
that the denial must be recorded before it is thrown. Its parenthetical
about a partial type list was an implementation guess made by a review
that could not run the code, and this Work Package's own adversarial
analysis found that guess actively harmful.

Deviating had to be earned, and it was: the divergence is stated
explicitly in the commit message, in `TD-51`'s Status cell, in
`WorkPackages.md`, in `PROJECT_STATUS.md`, and in a long in-source
comment at the `catch` block itself — including the reasoning about the
`AppDomain`-resident assembly and the `IsFirstParty` consequence.

Placing the new denial check **first** in `EnforceTrust` is the second
earned decision: it is not stylistic ordering, it is the only ordering
that keeps a type known to have unresolvable constructor parameters away
from `HasCompliantConstructor`'s unguarded reflection.

## 8. Architectural Principles

- **Fix the Root Cause, Then Add the Backstop.** (a) restores the
  recording `ADR-0111` already mandated; (b) ensures Module Discovery
  cannot fault the Host over an unreadable candidate whatever produced
  it. Neither substitutes for the other.
- **Fail Closed, Never Fail Open.** The whole rationale for rejecting the
  partial-list shape: a Host crash is a bad outcome, and a silently
  first-party-treated plugin module is a worse one.
- **Do Not Widen a Class's Awareness to Fix a Failure It Merely
  Observes.** `ReflectionFrameworkDiscoveryService` stays plugin-unaware
  per `ADR-0110`; it gained a reflection guard, not a trust decision.
- **Deliberately Narrow Guards.** Four CLR type-load exceptions and no
  more, so `ModuleDiscoveryException`, `DuplicateModuleIdException`,
  `ValidateMetadata` failures and the `WP 5.3` actionable guidance all
  still propagate — a guard that swallows genuine defects is worse than
  no guard.
- **An Implementation Divergence From a Correct Decision Is a Defect, Not
  a New Decision.** `ADR-0111` was right; the code had drifted from it.
  No ADR was added or amended.
- **Prove Non-Vacuity by Reversion.** Every half of the fix was reverted
  independently and the predicted, targeted failures observed — including
  reproducing the original crash end to end.
- **Disclose the Consequence You Created.** `TD-55` was found by this
  Work Package's own adversarial review of its own fix, and recorded
  rather than accepted silently.

## 9. Benefits

- **`TD-51` moved Reopened → Resolved.** The Host no longer crashes on
  the `IModule` axis, and `ADR-0025`'s founding guarantee — a
  plugin-scoped failure never becomes a platform-wide outage — is
  restored on this path.
- **`deniedTypeRegistry` is now correct on all three denial paths.**
  `DiscoverModuleTypes` contains no `throw` at all, so `RecordDenied`
  provably precedes every denial `EnforceTrust` surfaces —
  independently confirmed by `WP 13.11C`.
- **Denied `IModule` *and* `IHostedService` types are excluded from
  Discovery, Registration, and Lifecycle**, including a single type
  implementing both — also independently confirmed by `WP 13.11C`.
- **Module Discovery can no longer fault the Host over an unreadable
  candidate**, from any source, plugin or first-party.
- **Seven permanent regression tests** where the scenario had previously
  been proven only by throwaway proof-of-concept code, covering both
  axes and both directions.
- **Measured, not assumed, test cost**: no parallelism increase (every
  new test joins the existing `"Console output capture"` serialisation
  collection, mandatory because these tests load real assemblies and
  `DiscoverModuleTypes` diffs the process-global `AppDomain`), no
  processes spawned, six collectible reflection-only load contexts
  created and unloaded, and roughly 7 small dynamic assemblies
  permanently resident in the default, non-unloadable
  `AssemblyLoadContext` (`ADR-0015`) — under ~2 MB, against 141 such
  existing calls already in the suite.
- **Verification**: Debug and Release builds both 0 Warnings / 0 Errors
  (`-p:TreatWarningsAsErrors=true`); full regression **2,561/2,561 both
  configurations** (2,554 documented baseline + 7 new);
  `governance-healthcheck.ps1` 7 passed, 1 warned (pre-existing), 0
  failed, re-run fresh after every edit.

## 10. Trade-offs

- **`TD-55` is a genuine consequence of this fix, and it is Open.**
  `RecordDenied` records every type a denied plugin's transitive scan
  reached, and `PluginDeniedTypeRegistry` is keyed on `Type` identity
  alone with no plugin attribution — so one plugin's denial can suppress
  another assembly's module types. The hazard has been **latent since
  `WP 13.9.4`** on the two existing denial paths; this fix makes it newly
  **reachable** on the third, which previously recorded nothing at all.
  Fail-closed in direction (a type is wrongly excluded, never wrongly
  included), dormant today, and `Tempest.Samples` is provably unaffected
  by *composition ordering* rather than by design —
  `WorkspaceManager`'s constructor force-loads it before `RunAsync` is
  ever called, so it is always inside the scan's `before` snapshot. That
  is a property of App composition, not of the loader, which is exactly
  why it is tracked. Closing it needs per-plugin denial scoping, beyond
  this Work Package's remit. (`WP 13.11C` later extended `TD-55` with a
  complementary **under**-recording half that is *not* fail-closed.)
- **The security-critical half of the fix shipped with no regression
  coverage.** The completed-fixed-point-scan decision — the part its
  rationale argued at greatest length — could be reverted to the unsafe
  partial-list shape with all 2,561 tests still green. `WP 13.11C` found
  this and closed it. This is the single most important trade-off in this
  Work Package's record: an argument written at length in five documents
  and one source comment was, at commit time, unenforced by anything
  executable.
- **A factually wrong inherited claim was softened, not corrected.**
  `WP 13.11A`'s "guard already used at three other call sites" became an
  unquantified plural here rather than being checked. Exactly one other
  call site carries that four-exception filter; `WP 13.11C` corrected it
  in four documents and one production comment.
- **`ADR-0013`'s "Discovery throws → `Faulted`" clause is narrowed** for
  four CLR type-load classes, and the guard is per-*candidate* and also
  covers first-party candidates — so a first-party module with a missing
  dependency assembly now disappears with a `Warning` rather than
  faulting loudly. `WP 13.11C` reviewed this and found no ADR amendment
  required, disclosing the residue in `Plugin Trust & Isolation
  Architecture.md`.
- **Two documentation-only corrections from the post-implementation
  adversarial review** were applied: a stray deleted `/// </summary>` tag
  in a test helper's doc comment (invisible to the build, since
  `GenerateDocumentationFile` is `false`), and an incomplete `<exception>`
  element on `EnforceTrust`, now that this denial is raised there rather
  than inside `DiscoverModuleTypes`.

## 11. Common Mistakes

1. **Implementing a review's recommended *shape* rather than its
   recommended *outcome*.** Option (a) said "with whatever partial type
   list `DiscoverModuleTypes` had already scanned". Doing exactly that
   would have satisfied the recommendation, closed the crash, and opened
   a silent trust bypass. Read the recommendation for its intent, then
   attack the shape adversarially before writing it.
2. **Assuming an early `throw` from inside a scan is free.** It skipped
   the per-step `AppDomain` diff, which is what makes an
   already-force-loaded assembly discoverable. The throw's cost was not
   the exception — it was the traversal it cut short.
3. **Assuming `break` inside nested loops does what the comment says.**
   It exits only the per-constructor loop here; the enclosing loops
   continue and the fixed point still closes. `WP 13.11C` independently
   verified precisely this, along with termination being bounded by the
   finite `AppDomain` assembly set.
4. **Assuming a long, careful rationale is the same as coverage.** The
   completed-fixed-point-scan decision was argued at length in the commit
   message, `TD-51`, `WorkPackages.md`, `PROJECT_STATUS.md`, the
   architecture document, and an in-source comment — and could be
   reverted with the entire suite green. Prose does not fail a build.
5. **Assuming a widened `RecordDenied` is purely a safety improvement.**
   Recording more types is fail-closed in direction and still has a blast
   radius: `TD-55` is exactly that blast radius, made reachable by this
   fix on a path that previously recorded nothing.

## 12. Future Evolution

- **`WP 13.11C`** — the review of this Work Package, which found the
  missing coverage for the completed-scan decision, closed it with one
  new test and one new `DynamicPluginAssemblyBuilder` helper, and
  corrected the "three other call sites" claim. It also extended `TD-55`.
- **`TD-55`** — closed only by per-plugin denial scoping: recording per
  plugin, and excluding a type only for the plugin that actually owns it.
  Both the over-recording half disclosed here and the under-recording
  half `WP 13.11C` added close together, or not at all.
- **`TD-53` and `TD-54`** — deliberately untouched here and still Open
  through `WP 13.11D`; neither is a variant of `TD-51`, and neither is
  naturally or directly implicated by this fix.
- **A real, non-synthetic signed plugin** remains the trigger that would
  make any of these paths non-dormant. `src/Plugins/` still contains only
  `README.md`.

## 13. Key Takeaways

- **The most valuable thing this Work Package did was disobey half of its
  own brief, with evidence.** Taking `WP 13.11A`'s recommendation
  literally would have closed a crash and opened a silent trust bypass.
  Deviating from a recommendation is legitimate exactly when the
  deviation is argued, disclosed in every place the recommendation was
  recorded, and later provable.
- **"Provable" is doing real work in that sentence.** At commit time the
  argument was prose. `WP 13.11C` converted it into a demonstrated fact
  with a dedicated test — and found that until then, the unsafe shape
  would have passed the entire 2,561-test suite.
- **Recording a denial and throwing it are different acts, and their
  order is the whole defect.** Surfacing the exception through an `out`
  parameter so the caller can record *then* throw is a small mechanical
  change that restores an `ADR-0111` guarantee the code had silently
  diverged from.
- **A minimal remit is a discipline, not a limitation.** `TD-53`,
  `TD-54`, and the newly-found `TD-55` were all left tracked. The
  alternative — fixing what was convenient while a Release-blocking crash
  was open — is how a remediation becomes unreviewable.
