# xUnit2029 Build Failure and the Vacuous Assertion Behind It

## 1. Introduction

`562a563` fixed a build failure CI run 76 reported on the author's own new
acceptance test, and then found the fixed assertion had been vacuous all
along. A pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To fix the flagged analyzer pattern, and to check what the corrected
assertion actually proves once its form is fixed.

## 3. Background

`Assert.Empty(collection.Where(predicate))` is the `xUnit2029`-flagged way
of writing an absence check; CI applies `TreatWarningsAsErrors` at its
build step, so an analyzer warning there is a hard failure. This was
visible locally the whole time: `Directory.Build.props` sets
`TreatWarningsAsErrors=false` locally and CI sets it true, so the warning
had been present in a local build the author had read the count of and
not chased.

## 4. The Problem

A new test breaking an existing convention, not a product defect — but
correcting the assertion's *form* first required checking what the
assertion actually meant, because mutation-testing the rewritten form
showed it surviving a mutation that made the Risks area render a
`DeclaredCapabilityView` it should not have.

## 5. The Design

Passing `-p:TreatWarningsAsErrors=true` locally reproduces the gate
exactly; the fix is demonstrably the thing that fixed it, since
re-introducing the old form fails the build again. The repository was
swept for the same anti-pattern: four other `Assert.Empty` uses take the
shape `Assert.Empty(x.OfType<T>())`, which genuinely asserts zero elements
of a type rather than absence, and are deliberately left alone. The
assertion itself is then rewritten, not merely reformatted: it now asserts
the Risks tab's own content is a `ProjectRisksView`, and that no card
appears within that subtree — targeted at the tab rather than the window
deliberately, since the project workspace builds every area's content up
front and a window-wide assertion would wrongly flag the cards that
genuinely-Declared areas legitimately show.

## 6. Alternatives Considered

Suppressing or configuring the analyzer to accept the flagged form —
explicitly rejected: "the analyzer is not weakened, suppressed or
configured."

## 7. Why This Solution Was Chosen

Because correcting the assertion's syntax alone would have left a
vacuous check in place; mutation-testing the corrected form is what
revealed the predicate could never fail for any reachable state, and
fixing that was the actual point of the exercise.

## 8. Architectural Principles

A build-time analyzer warning caught locally and not chased is exactly
the gap between "I saw a warning" and "I confirmed it does not matter" —
the local/CI `TreatWarningsAsErrors` mismatch means only CI enforces the
difference, so a local pass is not sufficient evidence.

## 9. Benefits

Two mutations run, two killed: the area rendering a card alongside the
surface, and the descriptor reverted to Declared — both survived the
previous, vacuous version of the assertion. Core 2828/2828, Desktop
329/329, Debug and Release, 0 warnings, 0 errors, with
`TreatWarningsAsErrors=true`.

## 10. Trade-offs

None recorded beyond the narrow scope: this fixes one test's form and its
underlying vacuity, not a systemic pattern beyond the four correctly-shaped
uses the sweep confirmed were fine as written.

## 11. Common Mistakes

Reading a local warning count without chasing whether any individual
warning matters, when the local build configuration (`TreatWarnings
AsErrors=false`) is deliberately more permissive than CI's. Correcting an
analyzer-flagged assertion's syntax without checking whether the
corrected form is actually testing anything — the predicate here asked
whether a card had a `ProjectRisksView` ancestor, and `ProjectRisksView`
never constructs one, so the check could not fail for any reachable
state.

## 12. Future Evolution

No further instances of the vacuous-predicate pattern were found in the
sweep beyond this one test; the four correctly-shaped `Assert.Empty
(x.OfType<T>())` uses remain as the intended form for that kind of check.

## 13. Key Takeaways

- A local build's warning tolerance can differ from CI's; do not treat a
  local pass as proof a warning is harmless.
- Fixing an analyzer-flagged assertion's syntax is not the same as
  confirming the assertion tests something — mutation-test the corrected
  form to check.
- Target an assertion at the specific subtree the behaviour concerns
  (the tab) rather than the whole window, when siblings legitimately
  contain the pattern being checked for elsewhere.
