# WP 10.0A — User Experience Architecture

## What This Document Is

The whole-review Academy retrospective for `WP 10.0A`, mirroring
`WP8.0A-engineering-workspace-architecture.md`'s own format exactly —
an architecture-only Work Package retrospective, no implementation
section beyond an explicit disclosure that none occurred.

## Introduction

`WP 10.0A` opens Programme 10 ("User Experience & Desktop
Application," `v0.10.0`) on a new branch, `feature/v0.10.0-user-experience`,
cut from `main` at the point the `v0.9.0` release was pushed. It is the
eleventh Work Package this project has performed at the architecture-
or-specification-only level (after `WP 7.0A`/`7.0B`/`7.2A`/`7.2B`,
`WP 8.0A`/`8.0C`, and others), and the first to formally supersede a
prior Architecture Decision Record — in fact, two, in the same Work
Package.

## Architectural Lessons

**A rendering-agnostic contract pays its full cost back exactly once,
at the moment a rendering paradigm actually changes — not before, and
not gradually.** `WP 8.0B`'s own decision to keep every Workspace
contract free of pixel/window/graphics concepts looked, for a full
release cycle (`v0.9.0`, six real disciplines), like a decision that
cost nothing and delivered nothing extra either — until this Work
Package needed to change the entire presentation paradigm and found
zero contract needed to move. This is a genuinely new kind of evidence
for an architectural principle this project has held since
`FOUNDATION.md` was first written: some investments are invisible until
the one moment they are tested, and this project now has a concrete,
dated example of exactly that.

**A named reversal condition is what makes superseding a decision
possible without looking arbitrary.** `ADR-0066` did not merely make a
choice — it named, in writing, exactly what evidence would justify
reversing it. When that evidence arrived (a Product Owner Programme
titled "Desktop Application"), `ADR-0092` could point to it directly
rather than re-litigating the original decision's own soundness. This
retrospective recommends every future ADR that makes a genuinely
close-call decision consider naming its own reversal condition
explicitly, following `ADR-0066`'s own precedent, now proven valuable
in practice rather than only in theory.

**Partial supersession is a real, useful pattern, not a fallback.**
`ADR-0093` did not fully discard `ADR-0065` — it carried forward the
piece of that decision the new evidence said nothing about (no new
traversal mechanism) while changing only the piece the new evidence
actually addressed (rendering shape). `WP10.0A Architecture Review.md`
§3 confirms this was the architecturally correct scope, not an
oversized reversal. Future supersessions should default to asking "what
part of the old decision does the new evidence actually invalidate?"
rather than assuming a supersession means discarding the whole thing.

## Repository Maturity

This is the fourth architecture-only Work Package in a row across two
Programme boundaries (`WP 9.8B`, `WP 9.9.0` First Pass, `WP 9.9.0`
Second Pass, `WP 9.9.1`, now `WP 10.0A`) to leave `src/`/`tests/`
completely untouched, each independently confirmed by direct `git
status` check rather than merely asserted — a discipline this project
now applies as routinely to a brand-new Programme's opening Work
Package as to a release-closing one. The ADR supersession mechanism,
specified in `Engineering Governance.md` §5 since this project's early
history but never once exercised across 91 prior ADRs, is now proven
to work exactly as written, on the first two attempts, independently
re-verified correct by a dedicated Architecture Review rather than
only by the issuing Work Package's own say-so.

## Recommendations for the Next Work Package

1. **Resolve `ADR-0094`** (concrete cross-platform .NET desktop UI
   framework) as early as possible in the next Work Package — nearly
   every other reserved question in this package's own scope (test
   strategy, concrete visual tokens) depends on knowing what framework
   category is chosen.
2. **Consider `ADR-0095`** (floating/multi-monitor panel contract
   extension) as a Contract Review Work Package in its own right,
   mirroring exactly how `WP 8.0B` picked up `ADR-0066`/`ADR-0067` from
   `WP 8.0A`'s own reserved list.
3. **Design a graphical-presentation test strategy explicitly** before
   any Workspace rendering code is written — `WP10.0A Architecture
   Review.md` §5 (Risk 2) names this as the one prediction in this
   package ("zero contract change") that must be empirically
   re-confirmed once real code exists, and a test strategy is the
   mechanism that confirmation runs through.
4. **Cross-reference `TD-32` from the new graph view's own
   implementation**, per `WP10.0A Security Review.md` §3 — already
   done at the documentation level (`WP10.0A Digital Thread &
   Relationship Visualisation.md` §4); the next Work Package should
   revisit `TD-32`'s own disposition once the graph view is real, not
   only documented.

## Key Takeaways

Two supersessions, executed correctly on the first attempt, are worth
more to this project's own governance maturity than either decision
alone — they prove the mechanism this project's own standards have
described since its early history actually survives contact with a
real use case. A contract designed to outlive its own rendering
technology is not a hedge against uncertainty; it is what makes
changing your mind about the rendering technology safe. Naming a
reversal condition when you make a decision is what lets you reverse
it later without it looking like you never believed in it the first
time.
