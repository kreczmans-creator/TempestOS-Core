# WP 12.4A — Desktop Command & Event Wiring Architecture

## What This Document Is

The architecture-phase retrospective for `WP 12.4A`, a second
directly-commissioned `v0.12.0` Work Package (following `WP 12.3A`/`WP
12.3B`'s own precedent), reviewing the Desktop layer's own command,
event, and UI-wiring architecture as it stands after `WP 12.0B`'s
`MainWindow`/`EngineeringCockpit` decomposition, and formally evaluating
how Desktop collaborators should communicate going forward. Architecture
only — no code; no `WP 12.4B` has been commissioned to act on its
findings.

## 1. Introduction

`WP 12.0B` decomposed two 1,000+-line composition roots into eighteen
smaller, single-purpose files. That decomposition was itself reviewed
(a read-only architecture/code review, recorded in the `WP12.0B`
retrospective) and approved with ten findings, none blocking except one
(since closed). Two of those ten — `WorkspaceViewCoordinator`'s own
multi-responsibility shape (Finding 4) and the two-phase-`Attach`
pattern applied where a delegate would have sufficed (Finding 5) —
were about wiring specifically, not the composition-root/collaborator
shape itself. `WP 12.4A` was commissioned to take a second, dedicated
pass at exactly that question, in two stages: first, an investigation
of what wiring exists today and what it costs (duplication, disposal
discipline); second — the stage this document's own final form
reflects — a forward-looking design brief asking whether Desktop
communication should keep using direct delegates, or one of five named
alternatives, evaluated formally rather than assumed settled by
precedent.

**Disclosed naming correction.** This Work Package's scope was
initially requested under the label `WP 12.1A` — already the roadmap's
own name for a different, unrelated item ("Classification & Relationship
Vocabulary Safety Net Architecture," `WP11.0B Architecture Roadmap.md`
§3, Finding `A-6`). Corrected to `WP 12.4A` before any document was
written, mirroring `WP 12.3A`/`WP 12.3B`'s own precedent for a
directly-commissioned Work Package inserted outside the roadmap's own
predicted numbering — recorded here plainly, the same discipline this
project's own governance registers already apply to every comparable
numbering question.

## 2. What Was Found

**Command ownership is not one mechanism but four — all pre-existing,
all individually already governed by their own ADR, none redundant.**
`ICommandRegistry`/`ICommandDispatcher` (`ADR-0036`–`0038`), `RibbonView.ObjectCreationHandlers`
(a UI-input-collection layer over already-registered commands, not a
second registration mechanism), `KeyboardShortcuts` (a small, fixed,
hardcoded set of non-Command Framework UI actions), and
`KeyboardCommandBindingProvider`/`IInputBindingProvider` (`ADR-0100`).
`WP 12.0B` did not create this four-way split — it already existed,
spread across `WP 10.0B`–`WP 10.6A`'s own separate decisions, simply
easier to see now that each has its own collaborator instead of sharing
one file.

**Zero event unsubscription, zero `IDisposable`, anywhere in `Tempest.Desktop`
— confirmed by direct, exhaustive search, not sampling.** Every one of
25 events wired with `+=` is never explicitly torn down. Investigated
directly rather than flagged reflexively: found *safe today*, because
exactly one `MainWindow` (and, transitively, exactly one instance of
every collaborator) is ever constructed per process — `ADR-0103`'s own
"Ownership and lifetime" section already establishes a collaborator's
lifetime as exactly its composition root's own, and no code path in
this codebase constructs a second one while a first one's subscriptions
are still live. Recorded as a disclosed design characteristic, with one
open question (does any handler fire mid-shutdown-race) named directly
rather than silently assumed away.

**Real, measured duplication: a four-statement "report, then refresh"
tail, counted, not estimated.** `StatusBar.SetText` (42 occurrences),
`ToastHost.Show` (25), `ProjectExplorerView.LoadAsync` (25),
`CockpitView.Refresh` (19) — concentrated overwhelmingly in
`RibbonObjectActionHandlers` (the single largest, most mechanical
`WP 12.0B` extraction, ~29 handlers each independently repeating the
identical tail) and, to a lesser but still real degree, in
`WorkspaceViewCoordinator`. Real evidence for the Objective's own
"duplicated event wiring" concern, not a subjective impression.

**Six candidate communication mechanisms, evaluated on their own
individual merits — three genuinely new rejections follow.** Direct
delegates, typed callback interfaces, a Desktop-local Mediator, a
Desktop-local Command Dispatcher, a Desktop-local Event Dispatcher, and
reuse of the existing platform Command/Event Framework were each
evaluated for advantages, disadvantages, layering impact, ownership,
lifetime, and testing implications (`Desktop Command & Event Wiring
Architecture.md` §"Candidate Communication Mechanisms — Full
Evaluation"). Direct delegates (the status quo) and typed callback
interfaces (accepted narrowly, at three or more bundled callbacks) were
retained. The Mediator, a second Command Dispatcher, and a second Event
Dispatcher were each rejected on their own individual merits — not
merely inferred from `ADR-0103`'s more general "delegate over reference"
rule, the way `WP 12.4A`'s own first-pass investigation had left the
question. This evaluation is recorded formally in **`ADR-0104`**.

## 3. Architectural Lessons

**A decomposition that is architecturally correct can still leave real
duplication behind, and finding it requires a second pass with a
different question in mind.** `WP 12.0B`'s own code review checked "does
each collaborator have one reason to change" and "does any collaborator
reference a sibling" — both real, both answered correctly — but did not
count how many times an *identical sequence of calls* was repeated
*within* collaborators that individually passed both tests.
`RibbonObjectActionHandlers` is architecturally sound (one reason to
change, `ADR-0103`-compliant, sanctioned by its own illustrative table)
and still contains the codebase's single largest concentration of
literal duplication — the two questions are genuinely independent, and
answering the first does not answer the second.

**"Four command mechanisms" sounds like a smell until each is traced to
its own, separately-justified ADR.** The instinct on first finding four
different ways a Desktop action reaches a result is to suspect
accidental sprawl. Tracing each to `ADR-0070`, `ADR-0096`/`0097`,
`ADR-0098`, `ADR-0099`, `ADR-0100` in turn showed each answers a
genuinely different question, decided independently, at a different
Work Package, for a different reason — the multiplicity is a symptom of
this platform's own incremental, ADR-per-decision history working
correctly, not of duplicated effort.

**A rule that already follows *implicitly* from an existing ADR can
still be worth recording *explicitly*, as its own ADR, when the question
is one a future contributor will plausibly ask again.** `WP 12.4A`'s own
first pass concluded `ADR-0103` already answered the "how should Desktop
collaborators communicate" question, and stopped there. Revisiting that
conclusion under this Work Package's own more specific brief — naming
five concrete alternatives and asking for each one's own merits, not
only whether `ADR-0103` technically covers it — found a genuine
difference: `ADR-0103` forecloses reflective/declarative *composition*
generally; it does not, on its own text, evaluate a non-reflective,
compile-time Mediator, a second Command Dispatcher, or a second Event
Dispatcher on their own individual terms. Each was evaluated and
rejected on real, mechanism-specific grounds (testability regression,
duplicated registration confusion, platform-service misclassification)
— reasoning genuinely new to this Work Package, not restated from
`ADR-0103`, which is exactly what distinguishes "this is already
governed" from "this is worth its own citable answer." `ADR-0104` is
the result. This is the opposite lesson from `WP 12.4A`'s own first
pass, and both are true: sometimes an existing ADR fully answers a new
question (the duplication and disposal findings, still true, still
`ADR-0103`-governed); sometimes a question that *sounds* like it should
already be answered turns out to need its own, freshly-reasoned record.
Telling the two apart requires doing the specific evaluation, not
inferring from how similar the question sounds to one already decided.

## 4. Key Takeaways

- Command ownership across the Desktop layer is a four-mechanism model,
  each already ADR-governed, now documented together in one place for
  the first time — no change recommended to any of the four.
- The duplicated "report, then refresh" tail (42/25/25/19 occurrences)
  remains this Work Package's own central *implementation-hygiene*
  finding — real, counted, and left as an open implementation-stage
  question for a future `WP 12.4B`, deliberately not designed in full
  here; `ADR-0104` governs how any consolidation communicates, not
  whether or how it happens.
- `WorkspaceViewCoordinator` remains the strongest decomposition
  candidate, unchanged from `WP 12.0B`'s own Finding 4 — re-confirmed,
  not rediscovered, and directly addressable by `ADR-0104`'s own typed-
  callback-interface threshold (its 18-parameter constructor is the
  named, motivating example for when that threshold applies).
- **`ADR-0104` — new**: direct delegates remain the default; typed
  callback interfaces are sanctioned narrowly, at three or more bundled
  callbacks; a Desktop-local Mediator, Command Dispatcher, and Event
  Dispatcher are each explicitly rejected as Desktop composition
  mechanisms, closing three concrete future temptations by name rather
  than by inference. `ADR-0103` itself needed no amendment — `ADR-0104`
  applies its principles more specifically, the identical boundary
  discipline `ADR-0103` itself already used against `ADR-0009`.
