# WP 13.9.2 — `v0.13.0` Readiness Re-Execution

## 1. Introduction

`WP 13.9.2` is the re-execution Work Package of the `v0.13.0`
`WP 13.9.x` chain — commissioned to independently re-verify what
`WP 13.9.1` (`v0.13.0` Readiness Remediation) had just done to close
`WP 13.9.0`'s Engineering Readiness Review findings, rather than accept
that remediation's own account of itself. It runs on `feature/v0.13.0`,
`v0.13.0` — "Trust & Deployment Hardening".

**It is verification only.** Its own `WorkPackages.md` row and its own
`PROJECT_STATUS.md` stratum both state, in the same terms, that it
produced no code, no documentation and no Academy artefact of its own, and
that **zero `src/`, `tests/` or `docs/` files were touched by this Work
Package itself**. Its `WorkPackages.md` Type column reads `Verification
only`. Its own row in that table is retroactive, added later by
`WP 13.9.7`.

It found `WP 13.9.1`'s headline security fix **still incomplete**, and
that finding is the direct commissioning trigger for `WP 13.9.3`.

Every claim below is grounded in `d7d19d4`'s own commit message ("WP
13.9.1-13.9.6: Plugin Trust Execution Boundary Remediation Chain", the
commit that eventually carried the whole chain's material, 35 files,
+3,263/−90), this Work Package's own `WorkPackages.md` row, its own
`PROJECT_STATUS.md` stratum, and direct reads of real source where a claim
is checkable from code. Where the record is silent, that silence is stated
rather than filled.

**A note on this document's own provenance.** `WP 13.9.7` recorded an
explicit governance conclusion that `WP 13.9.1`–`WP 13.9.6` "do not
require new Academy retrospective files of their own," checked against
`Academy Index.md`'s own stated maintenance rule and the
`WP 13.2B`/`WP 13.9.1` precedent. This retrospective is written after the
fact and in addition to that conclusion; it is not accompanied by an
`Academy Register.md` or `Academy Index.md` entry, and that
register-currency gap is disclosed here rather than asserted closed. The
same disclose-the-provenance discipline was established by the `WP 13.3B`
retrospective, itself reconstructed after the fact.

## 2. Purpose

To re-execute readiness verification against `WP 13.9.1`'s remediated
state, independently, from fresh evidence — and specifically to determine
whether the multi-assembly trust-boundary bypass `WP 13.9.0`'s
Security/Trust discipline had empirically demonstrated was genuinely,
completely closed.

`WP 13.9.1` had deliberately declined to answer that question about
itself. Its own record states the boundary explicitly: "**`WP 13.9.0`'s
own verdict is not rewritten by this Work Package** — a fresh Engineering
Readiness Review is required to re-derive an updated verdict, not assumed
here." `WP 13.9.2` exists to be that independent second opinion.

## 3. Background

`WP 13.9.0` — the first execution of the permanent Engineering Readiness
Review `ADR-0106` defines, applied to `v0.13.0` at HEAD `88e41a2` —
returned **`NOT READY`**, with four of six disciplines independently
reaching Not Ready. One of those four was a **disclosed, additional sixth
category, Security/Trust**, commissioned specifically for this release
because `v0.13.0`'s entire substantive content is the new plugin trust
platform. Its single Release Blocking finding was a live, run,
reproducible proof-of-concept built against the commit's actual compiled
`Tempest.Core.dll`: a plugin's one manifest-declared assembly, at the
lowest trust tier requesting zero capabilities, inheriting a type from a
second, wholly undeclared assembly in the same folder — the second
assembly's own `IModule` implementer receiving zero trust checking of any
kind and being activated as an ordinary module by the deliberately
plugin-unaware Module Discovery pass (`ADR-0110`).

`WP 13.9.1` closed that finding, per its own record, by giving
`PluginAssemblyLoader.DiscoverModuleTypes` a fixed-point, breadth-first
`AppDomain`-diff scan — mirroring the dependency-graph idiom
`PluginManifestDiscoveryService` already used — following every assembly
entering the process as a direct or transitive consequence of examining a
plugin's declared assembly, and applying the existing, unchanged
constructor-conformance check to every `IModule` type found across all of
them. It committed the earliest scenarios of
`PluginAssemblyLoaderMultiAssemblyTrustTests.cs` as a base-type-inheritance
reproduction of `WP 13.9.0`'s exact PoC, confirmed denied.

That is the state `WP 13.9.2` was pointed at.

## 4. The Problem

**A fix verified only by its own author is an unverified fix.** More
precisely, in this case: `WP 13.9.1`'s fix was verified against the *one
proof-of-concept that had already been written* — a base-type-inheritance
smuggle. A regression test that reproduces yesterday's exploit and
confirms it is now denied proves exactly that, and nothing about the class
of exploit it belongs to.

The underlying question `WP 13.9.1`'s fix implicitly answers is: *which
reflection calls, during a plugin's own trust evaluation, can cause the
CLR to lazily load a further assembly?* The fix's `AppDomain` diff is only
as complete as the answer to that question. `WP 13.9.1` diffed around
`Assembly.GetTypes()`/`IsAssignableFrom` — the touchpoint that resolves a
discovered type's own base-type chain, i.e. precisely the mechanism the
one known PoC used.

The problem `WP 13.9.2` had to solve was therefore methodological before
it was technical: re-derive the *class* of the finding from first
principles rather than re-running the *instance* of it, and do so without
touching anything, so that whatever it found remained a finding rather
than becoming a half-applied fix.

## 5. The Design

This Work Package's own design is a method, not an artefact. Per its
`WorkPackages.md` row and `PROJECT_STATUS.md` stratum:

- **Re-verified `WP 13.9.1`'s own multi-assembly fix directly against a
  fresh live proof-of-concept** — not against `WP 13.9.1`'s committed
  regression tests, and not by reading its diff. A new PoC, independently
  constructed.
- **Found the fix still incomplete.** `DiscoverModuleTypes`'s fixed-point
  scan diffed the `AppDomain` only around
  `Assembly.GetTypes()`/`IsAssignableFrom`, **not** around the independent
  CLR lazy-load trigger a discovered module's own constructor parameter
  types represent — `ConstructorInfo.GetParameters()` /
  `ParameterInfo.ParameterType`. That resolution happens in a later,
  separate pass (`HasCompliantConstructor`), strictly after
  `DiscoverModuleTypes` has already returned, and is therefore invisible
  to the diff.
- **Demonstrated the consequence, in two variants.** The proof-of-concept
  showed a second, wholly undeclared assembly reachable **only** through a
  non-compliant constructor's own parameter type — never through any base
  type — again reaching Module Discovery with zero trust checking. And
  the more severe variant: where the same module *also* exposes an
  alternate, individually-compliant constructor, so the module is not even
  rejected on its own conformance check, and the plugin loads outright.
- **Changed nothing.** Zero `src/`, `tests/`, `docs/` files touched.
- **Commissioned a successor.** The finding is the direct commissioning
  trigger for `WP 13.9.3` (Multi-Assembly Trust-Boundary Remediation).

The second variant is the sharper of the two, and the reason it matters is
a property of the reflection API rather than of the plugin: as
`ADR-0111`'s later "Corrected, `WP 13.9.3`" section records,
`Type.GetConstructors()` resolves every returned constructor's full
parameter signature **regardless of declaration order or which one
ultimately proves compliant**. The undeclared assembly is force-loaded
whether or not the offending constructor is the one that decides the
verdict — so this was never a lazy, incidentally-avoidable effect that a
short-circuiting conformance check might have skipped.

**What the record does not contain.** No Engineering Release Report was
produced by this Work Package — unlike `WP 13.9.0`, which produced
`WP13.9.0 Engineering Release Report.md`, and unlike `WP 12.9.2`, the
closest structural precedent, which produced `WP12.9.2 Engineering Release
Report.md`. `WP 13.9.2`'s report was delivered conversationally to its
commissioning session and is not preserved as a file. **The record is
therefore silent** on whether `WP 13.9.2` re-executed all five canonical
`ADR-0106` categories plus the disclosed Security/Trust extension, on how
many disciplines or reviewers it used, and on whether it mechanically
re-derived a release verdict at all. No verdict is recorded for it
anywhere in `WorkPackages.md`, `PROJECT_STATUS.md` or `d7d19d4`'s commit
message. Its durably recorded output is exactly one finding.

## 6. Alternatives Considered

**The record is silent** on alternatives weighed inside this Work Package.
It produced no report file, raised no Rejected Designs entry, and its
`WorkPackages.md` row and `PROJECT_STATUS.md` stratum record method and
finding only. What can be stated is what it demonstrably declined to do,
each of which was a genuinely available option:

- **Accepting `WP 13.9.1`'s committed regression suite as sufficient
  evidence.** `PluginAssemblyLoaderMultiAssemblyTrustTests.cs` already
  reproduced `WP 13.9.0`'s PoC end-to-end and confirmed it denied. Taking
  that as closure would have been defensible on its face and would have
  missed the finding entirely.
- **Fixing what it found.** It did not: zero files touched, finding
  handed to a separately-commissioned successor. `WP 13.9.0`'s own Part C
  ("Corrections Made Within This Work Package: **None**") had established
  exactly this discipline one Work Package earlier, and `WP 13.9.2`
  continued it.
- **Reading the diff instead of running an exploit.** It built a fresh
  live proof-of-concept. `WP 13.9.0`'s Security/Trust discipline had set
  that precedent explicitly — "not a hypothetical reading of the code — a
  real, run, reproducible demonstration."

## 7. Why This Solution Was Chosen

**Because the re-execution was commissioned by the remediation's own
disclosure.** `WP 13.9.1` did not merely permit a re-check; its record
names one as *required* before any verdict could move. `WP 13.9.2` is the
discharge of a stated obligation, not a discretionary second look.

**Because verifying a class of defect requires a new exploit, not the old
one.** The distinction between "the demonstrated bypass no longer works"
and "no bypass of this kind works" is the entire value this Work Package
delivered. A fresh PoC targeting a *different* CLR lazy-load trigger is
the only method that could have separated those two claims, and it did.

**Because finding-and-stopping keeps the finding intact.** Had
`WP 13.9.2` widened the diff window itself, the fix and its verification
would again share an author, and the chain would have been back where
`WP 13.9.1` left it. Handing the finding to `WP 13.9.3` preserved the
separation. That separation kept paying: `WP 13.9.5`, a later, fully
independent adversarial review of the combined `WP 13.9.3`+`WP 13.9.4`
boundary, found a further distinct bug that three of its own reviewers
each separately live-PoC-reproduced.

**Because touching nothing is a design decision.** "Zero `src`/`tests`/`docs`
files touched" is recorded in both of this Work Package's own durable
records, in those words. It is what makes the finding independently
attributable and the successor independently reviewable.

## 8. Architectural Principles

- **Independent verification means fresh evidence, not a second reading of
  the same evidence.** `WP 13.9.0`'s Part B is explicit that its
  independent-before-reconciliation discipline exists because not every
  pass at an identical fact reaches identical rigour; `WP 13.9.2` applies
  the same principle across Work Packages rather than across disciplines.
- **Review, classify, report, stop.** Inherited directly from
  `WP 13.9.0`'s own explicit commission and preserved unchanged.
- **A remediation does not certify itself.** The structural reason this
  Work Package exists.
- **Prove it against a running system.** A trust-boundary claim is
  verified by an exploit that fails, not by a diff that looks right.
- **Enumerate the mechanism, not the instance.** The finding is not "the
  fix missed a case"; it is "the fix's own completeness argument rested on
  an incomplete enumeration of the CLR's lazy-load triggers."

## 9. Benefits

- A genuine, exploitable trust-boundary gap was found **before** it
  reached `main` — and before the release it belonged to was ever pushed,
  tagged or merged.
- The finding was materially more severe than the one it succeeded, in a
  way the earlier PoC could not have surfaced: the
  alternate-compliant-constructor variant means the plugin is not merely
  leaking a second assembly past the scan, it is **accepted outright**,
  its own conformance check passing.
- The chain's separation of concerns was established as a repeatable
  pattern — remediate, re-verify independently, remediate again — and was
  exercised three more times (`WP 13.9.3`, `WP 13.9.5`, `WP 13.9.6`)
  within the same chain.
- The finding is precisely enough stated that `WP 13.9.3`'s remedy is
  directly checkable against it: widen the same per-step diff window to
  cover constructor `ParameterType` resolution. Confirmed present in
  current source — `DiscoverModuleTypes` forces every discovered type's
  every public constructor's every parameter's `ParameterType` to resolve
  inside the same before/after diff window, with the `WP 13.9.3` rationale
  recorded inline.

## 10. Trade-offs

- **No durable report.** The single largest cost. Everything this Work
  Package examined *besides* the one finding is unrecoverable: the
  breadth of the re-execution, its reviewer structure, whether it produced
  a verdict, and what it checked and found clean. Three dense secondary
  records exist; none is a first-person account.
- **A verification-only Work Package leaves the defect live for the
  duration.** Between `WP 13.9.2`'s finding and `WP 13.9.3`'s fix, the gap
  was known and open. Justified here by the branch never having been
  pushed or merged, and by `src/Plugins/` remaining empty — no real
  third-party plugin existed to exploit it — but it is a real interval,
  not a nominal one.
- **Its own `WorkPackages.md` row is retroactive**, added by `WP 13.9.7`
  rather than written at the time. The row is dense and specific, but it
  is a reconstruction from the chain's integration point, not a
  contemporaneous record.
- **It re-verified one finding of `WP 13.9.0`'s four.** The
  API/`PluginManifest`, verification-harness and `WP 13.9.3`-documentation
  remediations are not mentioned in this Work Package's own record at all;
  whether it re-checked them is not stated either way.

## 11. Common Mistakes

1. **Reading `WP 13.9.2` as a full Engineering Readiness Review
   re-execution on the `WP 12.9.2` model.** `WP 12.9.2` produced a
   complete six-discipline `WP12.9.2 Engineering Release Report.md` and a
   mechanically-derived verdict. `WP 13.9.2` produced neither, and the
   record is silent on its breadth. Its title is `Readiness Re-Execution`;
   its durable output is one finding.
2. **Crediting `WP 13.9.2` with the constructor-parameter fix.** It found
   the gap and touched nothing. The fix — widening each scan step's
   `AppDomain` diff around every discovered type's every public
   constructor's every parameter's `ParameterType` — is `WP 13.9.3`'s,
   along with the eight tests and the `ADR-0111` "Corrected, `WP 13.9.3`"
   section.
3. **Assuming the alternate-compliant-constructor variant is a corner
   case.** It is the more severe of the two, precisely because the plugin
   *passes* its own conformance check. A reviewer looking only for
   "denied plugin still leaks an assembly" will not find it.
4. **Assuming a regression test proving yesterday's exploit is denied
   demonstrates the boundary is sound.** That is the exact reasoning
   `WP 13.9.2` disproved, one Work Package after it was made.
5. **Treating "zero files touched" as "nothing happened."** It is the
   Work Package's most consequential property and the reason its finding
   survived intact to be independently remediated.

## 12. Future Evolution

- **`WP 13.9.3`**, commissioned directly by this finding, closed it in
  full — and was itself subsequently reviewed by `WP 13.9.5`, which found
  a further, distinct defect in the combined boundary.
- **The CI/branch-push/merge gap** that produced two of `WP 13.9.0`'s four
  Not Ready categories is not addressed by this Work Package and is not
  mentioned in its record. `d7d19d4` itself states "Not pushed, not
  tagged, no release created."
- **No `v0.13.0` verdict is re-derived here.** At this Work Package's
  close, `WP 13.9.0`'s `NOT READY` remained the release's standing
  recorded verdict, unrewritten — exactly as `WP 13.9.1` said it would
  until a fresh review re-derived one.
- **A durable report file for verification-only Work Packages** is the
  obvious structural improvement this Work Package's own record argues
  for. `WP 12.9.2` and `WP 13.9.0` both produced one; `WP 13.9.2` and
  `WP 13.9.5` both did not, and both lost detail permanently as a result.

## 13. Key Takeaways

- Re-running the exploit you already have proves the patch, not the
  boundary. `WP 13.9.2`'s entire value came from writing a *different*
  exploit against the *same* claim.
- A completeness argument is only as good as its enumeration. The
  `AppDomain`-diff approach was right; the list of reflection calls that
  can trigger a CLR assembly load was short by one entry, and one entry
  was enough for a working bypass — including a variant where the plugin
  is accepted outright rather than merely leaking.
- Finding and stopping is a complete deliverable. Zero files touched,
  one finding, one successor commissioned — and the finding survived
  into `WP 13.9.3`'s remedy and `ADR-0111`'s own corrected Decision text
  precisely because nobody half-fixed it on the way past.
- The value of separating remediation from verification compounds. This
  chain ran that separation four times and each pass found something the
  previous one had missed — a pattern that only exists because the first
  remediation (`WP 13.9.1`) declined to certify itself.
- Verification-only Work Packages need durable reports too. Everything
  `WP 13.9.2` examined other than its single finding is now unrecoverable,
  and this retrospective can only record that the record is silent.
