# WP 16.3B — Durable State Schema Versioning: Implementation

## 1. Introduction

`WP 16.3B` implemented `ADR-0120` exactly: `EngineeringObjectState`
gained a `SchemaVersion` field, every enum reachable from that record
now serialises as its member name rather than its numeric value, an
ordered per-Kind-plus-common migration chain applies once on read, a
seven-file golden corpus of genuine pre-`ADR-0120` records is committed
as a permanent regression check, and a real-host restart test proves an
unversioned record rehydrates identically to before. It closed `TD-87`.
Branch `feature/v0.16.0-wp16.3b-schema-versioning`, cut from
`feature/v0.16.0` at `8b4c394` — the commit landing `WP 16.3A`'s
architecture and `ADR-0120` itself.

This Work Package is worth studying less for what it built than for how
it got there: three commits, and the first two were each rejected at
Technical Review before the third one merged.

## 2. Purpose

`ADR-0120`'s own stated purpose is that v1.0 data can be read by v1.1 —
a record written by an older build must not be silently misinterpreted
by a newer one, and a record a newer build genuinely cannot bridge must
fail loudly (a logged, skipped record) rather than silently (a
misread field, a reinterpreted enum). `TD-87` named the two concrete
risks this closes: a versionless schema degrading a broken record
honestly today, and a numeric `LifecycleState` that would silently
reinterpret every persisted status the moment the enum was ever
reordered.

## 3. Background

`ADR-0113` made `EngineeringObjectState` durable and named, in its own
Consequences, exactly what it did not do: "versionless today... a real
migration story is disclosed debt (`TD-87`)." `WP 16.3A`, one wave
earlier on this same release, turned that disclosed debt into an
accepted architecture — `ADR-0120`, and `docs/architecture/State Schema
Versioning Architecture.md` — with a `SchemaVersion` field, a
common-then-Kind-specific migration chain, string-valued enums, and a
golden corpus as its acceptance criteria. `WP 16.3B`'s own job was to
realise that architecture exactly, not to redesign it.

## 4. The Problem

The architecture document specified the mechanism; implementing it
correctly required getting several independent things right at once —
a migration loop that actually terminates at the right version, a way
for a test to drive that loop past the platform's own fixed
`CurrentSchemaVersion = 1` without changing production behaviour, and
a `TempestServiceProvider`-shaped container that has no notion of a
constructor parameter's default value, so every optional dependency an
object takes must already be satisfiable by a real container
registration. Getting any one of these wrong would not necessarily fail
a test today — `CurrentSchemaVersion` stays `1` this release, so a
"stuck record" bug in the ahead-of-version gate has no live record to
trigger it yet. That is exactly what makes this class of defect
dangerous: it can pass every test in the release that introduces it and
still be silently wrong for the release that first needs it.

## 5. The Design — as it stood after three commits and two Technical Review rounds

**`EngineeringObjectState`** gained `SchemaVersion` as its first
positional component. **`EngineeringObjectStateStore.Deserialise`**
now: normalises an absent or non-positive `SchemaVersion` to `1`;
rejects a record ahead of the store's own target as unbridgeable (a
record from a newer build); inside a `try`/`catch` that treats a
throwing migration as stuck, repeatedly finds and applies the migration
whose `FromVersion` matches the record's current version — the common
chain first, then that Kind's own, per `ADR-0120` Decision 2 — forcing
the result's `SchemaVersion` to `FromVersion + 1` regardless of what the
migration itself returns, until the record reaches target; and, the
line that exists only because of Technical Review Round 1, checks
**after** the loop whether the record actually reached target and, if
not, logs a `Warning` naming the record's Id, Kind, stuck version and
target version, and returns `null`.

**`TargetSchemaVersion`** is a public, read-only property, defaulting
to `CurrentSchemaVersion` (fixed at `1` this release) but overridable —
after Round 2's correction, **only** through a second, `internal`
four-parameter constructor, invisible to the DI container and reachable
only from `Tempest.Core.Tests` via the pre-existing
`InternalsVisibleTo("Tempest.Core.Tests")` declaration, itself verified
present in `AssemblyInfo.cs` before being relied on rather than assumed.

**`IStateMigration`/`IStateMigrationRegistry`** give every Kind, plus a
common chain, an ordered place to register a `FromVersion`-keyed
migration; none exist yet, because `CurrentSchemaVersion` stays `1` this
release — `WP 16.3B` "ships the mechanism, not a version bump," in the
architecture document's own words. A seven-file golden corpus of
genuine pre-`ADR-0120` records, generated by a throwaway test calling
the unmodified `SaveAsync` before any production file in this Work
Package's diff was touched, is loaded through the real read path on
every test run — standing regression coverage that a future schema bump
cannot silently break. A real-host `RestartProofTests` overwrites a
freshly-created object's own persisted record with the exact
pre-`ADR-0120` byte shape and proves a second, independent host
rehydrates it identically.

## 6. Alternatives Considered — including the two Technical Review rejected the mid-stream

**Let the "ahead" gate stand in for "stuck" (Round 1's own first
attempt).** The first commit (`2e3ec8e`) gated only whether a record's
version was ahead of `CurrentSchemaVersion` *before* the migration
loop, and let the loop's own natural exit — no matching migration found
— stand in for "this record is stuck." Technical Review Round 1
rejected this directly: a record at `SchemaVersion 1`, read by a future
build whose `CurrentSchemaVersion` has moved to `2` with no `1 → 2`
migration registered, would pass the "ahead" check (`1` is not `> 2`),
the loop would find nothing and exit immediately, and the record would
be returned **unmigrated, at `1` — silently misinterpreted as
current**, exactly the "no migration path to the store's current
version" case `ADR-0120` Decision 5 names and this design failed to
catch. Because `CurrentSchemaVersion` is still `1` this release, no
test could have caught this by accident — the bug was invisible until
someone actually needed a version bump. Fixed in the same round
(`2225d2e`) by adding the post-loop check described in §5.

**A container-wide `int?` registration to reach the new
`targetSchemaVersion` parameter (Round 1's own delivered fix, rejected
at Round 2).** To let a test exercise the post-loop check without
changing production's fixed `CurrentSchemaVersion`, the first fix added
a fourth, `int?` constructor parameter to
`EngineeringObjectStateStore` and satisfied it in `TempestHost.cs` and
the Samples integration test with
`services.AddInstance(typeof(int?), (object)(int?)EngineeringObjectStateStore.CurrentSchemaVersion)`.
Technical Review Round 2 rejected this correctly: registering
`Nullable<Int32>` itself as a container-wide service to satisfy one
constructor's one parameter would silently collide with **any other**
type in the platform that ever declared its own unrelated `int?`
constructor parameter — every one of them would receive
`CurrentSchemaVersion` too, whether or not that was ever intended. It
also papered over a real, disclosed gap rather than working within it:
`TempestServiceProvider` has no default-parameter-value support at
all — every constructor parameter resolves through the same registry
regardless of its C# default — and that gap is `TD-69`'s own second
defect class, `WP 16.4B`'s to fix, not something to work around a
second time inside `WP 16.3B`.

**The chosen fix — an `internal` second constructor, invisible to the
container by construction.** `TempestServiceProvider.Construct` calls
`implementationType.GetConstructors()` with no arguments, which returns
*public instance* constructors only, and requires exactly one. Giving
`EngineeringObjectStateStore` back its original, unchanged-in-shape
public constructor and adding a second, `internal` one that only
`Tempest.Core.Tests` can see (via the assembly's own pre-existing
`InternalsVisibleTo`) uses the container's own stated construction rule
against the problem, rather than fighting it with a registration that
would reach every unrelated `int?` parameter in the platform.
`TempestHost.cs` needed **no change at all** to keep constructing the
store with its own default target, because the restored public
constructor's shape is exactly what it already satisfied.

**Move `RestartProofTests` to `Tempest.Desktop.Tests`, since it drives a
`WorkspaceManager` host (Round 1's second required change, resolved
without relocation).** Rejected in favour of keeping it in
`Tempest.Core.Tests`: that assembly already references `Tempest.App`
and already builds real `TempestHostBuilder`/`WorkspaceManager` hosts
directly in existing tests, so no boundary was actually being crossed —
only a manual validation needed to become a committed one, which it now
is.

## 7. Why This Solution Was Chosen

Each of the two rejected designs failed for a reason specific to what
it was trying to satisfy cheaply. The first tried to make "ahead of
current" answer a question only "did the loop actually finish"
correctly answers, and a fixed `CurrentSchemaVersion = 1` this release
meant nothing exercised the gap until Technical Review reasoned about
the future case directly rather than waiting for a test to fail. The
second tried to reach a test-only construction path through the
platform's single, general-purpose container, and traded a narrow,
contained hack (one test seam) for a platform-wide hazard (any future
`int?` parameter, anywhere, silently colliding). The chosen design —
one public constructor unchanged in shape, one `internal` constructor
reachable only by the test assembly the container never sees — resolves
the tension by using the container's own documented behaviour
(`GetConstructors()` returns public constructors only) as the seam,
rather than asking the container to make an exception for one type.

## 8. Architectural Principles

- **A gate that checks a precondition before a loop is not the same as
  a gate that checks the postcondition after it** — the loop's own
  natural termination is not a substitute for verifying it terminated
  where it needed to.
- **A container-wide registration by primitive type is a platform-wide
  hazard, not a local convenience** — `services.AddInstance(typeof(int?), ...)`
  reaches every constructor with that parameter type, not only the one
  it was written for.
- **Work within a documented container constraint rather than around
  it** — `TempestServiceProvider`'s "exactly one public constructor"
  rule is exactly the seam that makes an `internal` test-only
  constructor invisible to it, for free.
- **A gap the container genuinely has (no default-parameter-value
  support, `TD-69`) is not this Work Package's to fix a second time** —
  naming it and handing it to the Work Package that owns it is the
  correct response to discovering it mid-implementation.
- **A decision "specifically challenged and defended under Technical
  Review" is itself ADR-worthy**, per Engineering Governance §5's own
  fifth criterion — see §12 below for where this Work Package's own
  record does not follow that rule.

## 9. Benefits

- `TD-87` is Resolved: a `SchemaVersion` stamp, string-valued enums, and
  a real migration chain replace a versionless schema that could only
  degrade a broken record honestly, never migrate one.
- The stuck-record gate correctly distinguishes three cases — ahead of
  target (a newer build's record), no path to target (a missing
  migration), and a migration that throws — logging each with the
  record's Id, Kind, and stuck version, rather than conflating them.
- A seven-file golden corpus and a real-host restart test are permanent,
  committed regression checks against every future schema bump, not
  one-time manual validations.
- 34 new tests; the full Core suite (3,122) and full Desktop suite (412)
  pass unchanged, in both Debug and Release, 0 warnings, 0 errors.

## 10. Trade-offs

- **The migration mechanism ships with nothing to migrate.**
  `CurrentSchemaVersion` stays `1` this release, so the entire chain —
  correct as it is — is exercised only by tests using the `internal`
  constructor's explicit `targetSchemaVersion`, not by any real record
  in production yet. The design's correctness rests on tests deliberately
  constructing the future scenario, not on having observed it happen.
- **`SettingsDocument<TDocument>`'s schema-version detection is
  reflection-based, not an interface constraint** — a runtime,
  duck-typed check for a declared `SchemaVersion` property, chosen
  specifically because a compile-time constraint would have forced
  every one of the six real consumers to change their DTO's declared
  type, breaking the architecture document's own "no change beyond an
  optional constructor parameter" promise.
- **`EngineeringRehydrationResult` was not extended with a "stuck"
  field**, even though the architecture document's own test-list entry
  implies one — the ADR's Decision 5 Consequences say the distinction
  belongs "in the log line a caller reads," not in a result field, and
  the implementation follows the ADR's own text over the architecture
  document's looser description. `IsComplete` still reads `true` for a
  batch containing only a store-level-stuck record — a pre-existing gap,
  unchanged by this Work Package, disclosed rather than silently left.
- **Discipline `RegisterStateMigrations` methods were not added
  anywhere** — the concrete registries the architecture document names
  live in `src/Tempest.App/`, outside this Work Package's file
  boundary, and no Kind has a migration to register yet. Ceremony with
  no behaviour behind it was deliberately not added.

## 11. Common Mistakes

- Letting a loop's own natural termination stand in for verifying it
  terminated in the right place — the exact defect Technical Review
  Round 1 caught.
- Reaching for a container-wide registration by primitive type to
  satisfy one constructor's one parameter, rather than checking whether
  the container's own construction rule already provides a narrower
  seam.
- Fixing a foundational container gap (no default-parameter-value
  support) piecemeal, inside the Work Package that happens to trip over
  it, rather than naming it and handing it to whoever owns that layer.
- Trusting an architecture document's own pseudocode or inline comments
  over the ADR's actual Decision text when the two disagree — the
  migration-ordering comment ("Kind-specific first, then common")
  directly contradicted `ADR-0120` Decision 2's own prose ("common
  chain first"); the implementation followed the ADR, and the
  architecture document's comment was corrected to match it, not the
  reverse.

## 12. Future Evolution

**A real gap in this Work Package's own record, found while writing
this retrospective and disclosed rather than silently left implicit:**
Engineering Governance §5 states that "the decision was specifically
challenged and defended under Technical Review — the outcome of that
review, whichever way it concluded, is itself ADR-worthy." Round 2's
decision — reject a container-wide `int?` registration in favour of a
public/internal constructor split as the pattern for reaching a
test-only construction parameter around a container with no
default-parameter-value support — meets that criterion on its face: it
was specifically challenged, it was defended, and the outcome
establishes a convention (`TD-69`'s container gap will recur for any
future optional-parameter-for-tests-only need) future Work Packages may
plausibly want to follow. No ADR exists for it; a direct search of
`docs/adr/` for this pattern found none. Whether this rises to the
level Engineering Governance §5 actually intends, or is better read as
an implementation-detail resolution local to one class, is a judgement
call this retrospective does not settle — but the absence is real and
worth a future Work Package's attention rather than being quietly
assumed settled.

`WP 16.4B` inherits `TD-69`'s second defect class directly: the
container's own lack of default-parameter-value support, named here as
the reason the `int?` hack was hazardous rather than merely inelegant,
is explicitly not fixed by this Work Package and is handed to `WP 16.4B`
to address at the platform level.

## 13. Key Takeaways

- A loop's exit condition and a gate's success condition are not
  automatically the same thing — check the postcondition explicitly.
- A container-wide registration keyed by a primitive type is never as
  narrow as the one call site it was written for.
- When a platform container has a documented construction rule (here,
  "exactly one public constructor"), that rule is often the cheapest
  and safest seam for a test-only alternate path — narrower than any
  registration-based workaround.
- Two rounds of Technical Review rejection on the same Work Package is
  not a sign of a badly-run Work Package; it is Technical Review
  working exactly as intended, and the record of what each round caught
  is more valuable to the next reader than a version history with the
  rejected attempts silently squashed away.
- A decision Technical Review specifically challenged and defended is
  itself a candidate for an ADR, per Engineering Governance §5 — check
  before assuming a merged fix closes that obligation.
