# TD-75 — The Product No Longer Ships Inside Its Own Demo Harness

## 1. Introduction

Two commits close `TD-75`. `a5795bd` (phase 1) moves the product's own
content out of `Tempest.Samples` and cuts the `Tempest.App` →
`Tempest.Samples` project reference. `fdd2a2a` (phase 2) removes the
sample-supporting wiring phase 1 deliberately left, deleting the last
edge keeping the sample harness undeletable. A pre-`v0.14.0` engineering-
body-of-work row.

## 2. Purpose

To stop the shipped desktop application from depending on
`Tempest.App.Workspace.Samples`-declared content, once the Product Gap
Reconciliation audit had shown removing the reference outright would
delete real product navigation and calculations, not demos.

## 3. Background

`ADR-0101` classifies `Tempest.App` as an internal engineering harness,
yet the shipped desktop application was built on it, with `Tempest.Desktop`
→ `Tempest.App` → `Tempest.Samples` meaning all 33 fictional sample
modules initialised in a real launch and a "Sample" ribbon tab and
"Sample Objects" explorer area were visible to end users.

## 4. The Problem

The six discipline explorer modules that give the Engineering Workspace
its navigation identity, and the entire engineering calculation catalogue
(Bolt Shear Capacity, Beam Bending Stress, Bearing Load Capacity, Pressure
Vessel Wall Thickness, Material Selection Margin), were declared inside
the sample assembly — real product content misfiled, not demo content
disguised as product content.

## 5. The Design

Phase 1: the six `*WorkspaceExplorerModule` types move to
`Tempest.App.Workspace.<Discipline>`, beside the registration that
attaches each real node provider to its area, with navigation ids kept
unchanged deliberately — renaming one would silently detach a discipline's
node provider from its own area. The five engineering calculations move
to `Tempest.Core.Calculations` rather than to the Calculations discipline,
since they depend on nothing but the calculation framework and units — a
catalogue of engineering knowledge belongs beside the framework that
executes it, and staying reachable from the sample harness (which
references only `Tempest.Core`) lets the samples continue demonstrating
them. The trivial arithmetic stand-in stays behind, being a genuine
demonstration. The `ProjectReference` is cut, and the composition root's
forced sample-assembly load moves into a `ModuleInitializer` in each test
project, since a test rig asking for test data is not a product depending
on demo content.

Phase 2: the composition root's dead sample-explorer registration is
removed (measured before removal: it registered a navigation area no
production run had reached since phase 1). `Tempest.App.Workspace.Samples`
— the fictional Longeron/Frame/Bracket tree — moves to
`Tempest.Core.Tests`, since it implements `Tempest.App` Workspace
abstractions the sample assembly (references only `Tempest.Core`) cannot
see. `Tempest.Validation`'s reference to `Tempest.Samples`, for one
navigation-id constant to collide with, is replaced with a collision
against whatever `INavigationProvider.Items` already holds — needing no
constant and testing a better invariant, since it now fails whichever
module it is paired with rather than the one sample module it was written
against.

## 6. Alternatives Considered

Deleting the `ProjectReference` in one step without first moving the
misfiled content — ruled out directly by the Product Gap Reconciliation
audit's own measurement (70 compile errors).

## 7. Why This Solution Was Chosen

Because a content move followed by a dependency cut is the honest shape
of the actual problem: severity unchanged, sequence corrected.

## 8. Architectural Principles

A layer boundary (`Tempest.App` is an internal harness, per `ADR-0101`)
should be enforced by what actually compiles without the dependency, not
by a project reference that happens to be unused at the moment someone
checks — phase 1's own mutation found this the hard way (see §11).

## 9. Benefits

Phase 1: proven by running the real composition root with no
`Tempest.Samples.dll` on disk — Discovery reports "6 module(s) found",
exactly the six discipline areas, zero fictional modules; the shipped
`Tempest.Desktop` output contains only `Tempest.App.dll`,
`Tempest.Core.dll` and `Tempest.Desktop.dll`; the sample module count
falls 33 to 27. Phase 2: proven by deleting `src/Samples` outright and
building Core, App, Desktop, Validation and Templates with 0 warnings, 0
errors — the property the boundary exists for, asserted directly as a
solution-wide `csproj` check rather than a text search.

## 10. Trade-offs

Phase 1 deliberately left the sample-supporting wiring behind and said
so — the composition root's dead registration, the sample explorer's
production-assembly code, and `Tempest.Validation`'s dependency — closed
only by phase 2. `TD-75` stays open between the two commits, honestly.

## 11. Common Mistakes

Asserting a boundary by checking `Assembly.GetReferencedAssemblies()` —
phase 2's mutation testing found this passes even with a raw
`<Reference Include="Tempest.Samples"/>` in a project file, because that
compiler-level API lists only references the compiler actually emitted,
and an unused reference emits none. The assertion now parses the
declared `ProjectReference`/`Reference` includes across every `csproj`
directly — the thing that actually declares the dependency. The same
lesson recurs from phase 1: restoring the cut `ProjectReference` did not
fail the phase-1 separation test either, for the identical reason.

## 12. Future Evolution

`41a171a` and `e57f1aa`, immediately after, fix two stale documentation
pointers this move itself created — the Academy guide and
`PROJECT_STATUS.md` both still named the pre-move namespace.

## 13. Key Takeaways

- When proving a dependency boundary is enforced, assert against the
  declared project references directly — a runtime reflection API like
  `GetReferencedAssemblies()` only sees what the compiler actually
  emitted, which an unused reference does not.
- A misfiled-content problem and a packaging-chore problem require
  different fixes in a different order; measure before assuming which one
  you have.
- The same assertion mistake (proving an absence with a test that does
  not actually prove it) recurred across two commits on this row — worth
  noting explicitly rather than treating each as isolated.
