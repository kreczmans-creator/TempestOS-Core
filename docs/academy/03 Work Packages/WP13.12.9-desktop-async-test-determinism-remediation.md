# WP 13.12.9 — Desktop Async Test Determinism Remediation

## 1. Introduction

`WP 13.12.9` replaced a single fixed `Task.Delay(50)` in
`tests/Tempest.Desktop.Tests/ObjectEditorViewTests.cs` with the bounded,
condition-based poll that `TD-46` had already established — in the very
same file — for a sibling test. It is a **test-only** change: one method,
one file, `+28/−2` (`7449756`). Zero `src/` files were touched, no
production behaviour changed, and no test framework configuration was
altered.

It exists because that one assertion failed once, on real infrastructure,
at the worst possible moment: `WP 13.12.7`'s tag-triggered `release.yml`
run against the `v0.13.0` commit.

## 2. Purpose

To make `ObjectEditorViewTests.Save_RevisedContent_ActuallyAdvancesTheRealRevisionNumber`
wait for the condition it actually cares about, rather than race a guess
against a real disk-write chain — while leaving the test's *failure*
semantics exactly as they were, so a genuine regression still fails, and
still fails clearly.

## 3. Background

`WP 13.12.7` pushed the `v0.13.0` tag under explicit authorisation. The
tag-triggered `release.yml` run (`32146823154`) failed at its
`Test (Release)` step: `Tempest.Core.Tests` passed 2,341/2,341, and
`Tempest.Desktop.Tests` failed 1 of 221 — this exact test, with an
`Assert.True() Failure`. `Package Release build output`, `Resolve release
notes` and `Publish GitHub Release` were consequently all skipped.

`WP 13.12.8` then investigated with four parallel read-only agents
(test/source, concurrency/isolation, CI/release-environment,
verification/reproduction) and converged on one verdict: **a genuine
intermittent test flake, not a product defect.**

Its decisive environmental evidence: the tag push triggered `ci.yml`
*and* `release.yml` on the identical SHA, the same `windows-2022` runner
image and the same minute, with character-identical `dotnet test`
invocations — `ci.yml` passed, `release.yml` failed, and the failing run
was roughly 51% slower end to end. `TD-34` was explicitly excluded
(different assembly, separate process, and the assertion reads a revision
number, never console text).

`WP 13.12.9` is the remediation `WP 13.12.8`'s diagnosis called for.

## 4. The Problem

The mechanism, as `WP 13.12.8` established it against real source:

- The Save button's click handler is an **`async void`** subscriber. The
  test raises `Button.ClickEvent` and gets back nothing awaitable — there
  is no task for the test to observe.
- The revise path performs **real disk I/O**:
  `EngineeringDocumentStore.ReviseAsync` does one read plus two
  `File.WriteAllTextAsync` writes under an `AsyncKeyedLock`, continuing
  on the thread pool via `ConfigureAwait(false)`.

A fixed `Task.Delay(50)` against that chain is therefore a **race, not a
wait**. On a quiet local machine it wins; on a loaded, shared GitHub
Actions runner it need not. Worse, the original code read the repository
exactly **once**, after the guess — so a slow write did not merely delay
the observation, it guaranteed a stale one.

`TD-46` records the identical idiom, in the identical file, already
convicted and fixed once — for
`VerificationResultSection_RecordPass_ActuallyRecordsARealVerificationRecord`,
under `WP 11.4A`. That remedy was never generalised. This test was the
second occurrence of a failure mode the project had already named.

**What could not be shown.** `WP 13.12.8` attempted local reproduction
and failed: 15/15 isolated, 2/2 full suite, and 8/8 even with the delay
set to `0`. The diagnosis therefore rests on source analysis, the
`TD-46` precedent, and the CI timing evidence — not on a local repro.
The commit message records this explicitly rather than overstating the
case.

## 5. The Design

The fix is small and entirely local to one method:

- Delete `await Task.Delay(50)`.
- Declare `IEngineeringObject? reread = null` and a deadline of
  `DateTime.UtcNow.AddSeconds(2)`.
- Loop until the deadline: `reread = await
  domainContext.Repository.FindAsync(target.Id)`; break when `reread is
  not null && reread.CurrentRevisionNumber > originalRevision`; otherwise
  `await Task.Delay(10)`.
- Leave both original assertions **unchanged** —
  `Assert.True(reread!.CurrentRevisionNumber > originalRevision)` and the
  content equality check.

Three properties matter here, and each is deliberate:

**Re-read every iteration, not once after a guess.** The bug was not only
the duration; it was observing a single sample at an arbitrary instant.

**A deadline, not an unbounded wait.** Two seconds is generous relative
to a two-write file operation and still bounded, so a genuinely broken
revise path fails the suite rather than hanging it.

**Assertions untouched.** The loop only decides *when* to assert. If the
revision genuinely never advances, the same assertion fails with the same
message it always would. The change removes a false-failure mode without
weakening a true one.

The inline comment added with the fix names the `async void` handler, the
real disk I/O, the `TD-46` precedent, and the specific `WP 13.12.7`
release run that made this concrete — so the next reader does not have to
re-derive any of it.

## 6. Alternatives Considered

**Generalise the fix to all 28 remaining fixed `Task.Delay` waits in
`Tempest.Desktop.Tests`.** Rejected for this Work Package. It is a much
larger, unverified diff at a moment when the release record needed a
minimal, fully-verified one; and each remaining delay would need its own
condition identified, not a mechanical substitution.

**Change xUnit or Avalonia parallelism configuration.** Rejected and
explicitly recorded as untouched: no `xunit.runner.json`, no
`.runsettings`, no `CollectionBehavior`, `maxParallelThreads` or
`DisableParallelization` change. The failure was a race against I/O
completion, not a collision between tests — reducing parallelism would
have masked timing rather than fixed the observation.

**Lengthen the delay (50 ms → 500 ms, say).** Rejected. It buys margin
against the same defective mechanism and makes the next failure rarer
and harder to diagnose, not impossible.

**Expose an awaitable seam on the Save handler.** Rejected here as
out of scope — it is a `src/` change, and this Work Package's whole
premise was that the product is not defective.

**Quarantine or skip the test.** Rejected — it asserts something real
(that saving actually advances the persisted revision number), and the
failure was in the waiting, not the asserting.

## 7. Why This Solution Was Chosen

Because the project had already answered this question once. `TD-46`
named the mechanism, `WP 11.4A` implemented the remedy, and the remedy
worked. Re-applying a precedent that the codebase itself established —
in the same file, for the same idiom — needs no new decision, no ADR, and
no novel design.

The scope was held to one method because the release record needed a
change whose effect could be stated exactly: 2 files, `+35/−5`
combined across `WP 13.12.9` and `WP 13.12.10`, zero `src/`. A
28-delay sweep would have made the release delta unmeasurable at the
precise moment measurability was the point.

## 8. Architectural Principles

- **Wait for the condition, never for the clock.** A test that sleeps is
  asserting about elapsed time; a test that polls is asserting about
  state.
- **Bounded, not unbounded.** Determinism must not be bought with a
  hang.
- **A precedent already in the codebase outranks a fresh design.**
  Engineering Governance §8.4 ranks established codebase convention
  above general principle; `TD-46`'s poll idiom is exactly that.
- **Scope discipline is evidence discipline.** A minimal diff is what
  makes "the tagged tree is untouched" a checkable claim.
- **Disclose what was not shown.** The absent local repro is recorded in
  the commit message, not glossed.

## 9. Benefits

- The single assertion that blocked `v0.13.0`'s publication no longer
  fails for a reason unrelated to what it tests.
- Failure semantics are preserved exactly — no assertion was relaxed,
  removed, or made conditional.
- The inline comment leaves a durable, in-place account of the
  mechanism, the precedent, and the real run that exposed it.
- The change is trivially reviewable: one method, one file.

## 10. Trade-offs

- **28 fixed delays remain.** The same latent failure mode still exists
  elsewhere in `Tempest.Desktop.Tests`. This is a known, disclosed
  residue, not an oversight.
- **The poll costs up to 2 s on a genuine failure** where the old code
  cost 50 ms — a real but small price for not failing spuriously.
- **The diagnosis rests on inference.** Without a local repro, the fix
  cannot be proved to address the exact instance that failed in CI; it
  is proved to address the mechanism `WP 13.12.8` identified.
- **Verification cannot demonstrate absence of flakiness**, only
  repeated success: target test 20/20 Release; Desktop suite 221/221
  Release ×2; Debug and Release builds 0 Warnings / 0 Errors; full
  regression 2,562/2,562 in both configurations.

## 11. Common Mistakes

- Treating a passing local run as proof a flake is gone — it was never
  reproducible locally.
- Substituting a longer delay for a condition.
- Reading state once after waiting, instead of re-reading while waiting.
- Turning parallelism down to make a timing bug disappear.
- Widening scope mid-Work-Package because "the other 28 are the same
  bug" — they may be, and that is a separate, separately-verified piece
  of work.
- Silently omitting an unrelated failing check. `governance-healthcheck`
  failed at commit time on an out-of-scope item — the `v0.13.0` tag
  having no Release Register row, caused by `WP 13.12.7`'s tag push, not
  by this change. It was recorded in the commit message and left for
  separate release-state work (`WP 13.12.10`), not quietly fixed and not
  quietly dropped.

## 12. Future Evolution

The remaining 28 fixed delays in `Tempest.Desktop.Tests` are the obvious
next candidate, each converted to a condition it can actually observe
rather than mechanically wrapped in a loop. A shared bounded-poll helper
would make that sweep smaller and more uniform than 28 hand-written
loops; the record is silent on whether one has been proposed.

The deeper fix — giving the Save path an awaitable test seam so no poll
is needed at all — remains a `src/` change and was out of this Work
Package's scope. Nothing in this Work Package's record commits the
project to it.

## 13. Key Takeaways

- A fixed `Task.Delay` before an assertion is a race, not a wait.
- The second occurrence of a named failure mode is a signal that the
  first fix was not generalised — record that rather than rediscover it.
- Re-read while polling; a single late read is still a stale read.
- Preserving a test's failure semantics is part of fixing its flakiness.
- Report the out-of-scope check you broke nothing in but that is
  nonetheless red.
