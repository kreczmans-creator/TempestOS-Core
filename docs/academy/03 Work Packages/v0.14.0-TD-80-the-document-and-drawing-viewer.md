# TD-80 — The Document and Drawing Viewer

## 1. Introduction

`0faf6ab` delivered `TD-80`'s document and drawing viewer, implementing
`ADR-0115`. `3f68376`, a closure follow-up, found and fixed four
user-visible defects a real Skia-driven harness caught that the headless
test suite structurally could not see — one of them fatal (no Open
button). A pre-`v0.14.0` engineering-body-of-work row; produced the
companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/38-document-and-drawing-viewer.md`.

## 2. Purpose

To let a user open a drawing in TempestOS at all. Mock-ups 2 and 3 both
centre on a viewer (zoom, pan, fit, rotate, markup, annotations); before
`TD-31`, attachments carried no bytes, so there was nothing to view even
in principle.

## 3. Background

A search across `Tempest.Desktop` for image, PDF, DWG, SVG or bitmap
rendering returned nothing; `ZoomBy`/`PanBy` existed only in the Digital
Thread graph. The design turned on one question: what "render" is allowed
to mean. A pure-managed approach — extract a PDF's text and lay it out at
recorded positions — would have passed for specifications and procedures
and been indistinguishable from working right up until someone opened an
engineering drawing, whose content is vector paths and whose text
extraction yields only the title block.

## 4. The Problem

No image, PDF or bitmap rendering existed anywhere in the product, and
the obvious pure-managed shortcut would have shipped something that
looked like a viewer and failed at the one document type the mock-ups
were actually about.

## 5. The Design (`ADR-0115`)

PDFium rasterises for real — verified with a five-line probe before a
line of viewer code was written: a PDF containing one red stroked
rectangle rendered 3,516 non-white pixels, first pixel at (24,24) in R255
G36 B36. `IDocumentPageSource` is the format seam — page count, page size,
`RenderPage(index, scale)` — with pages rasterised at the *current* zoom
rather than once and stretched, which is the whole reason a vector format
is worth rasterising on demand. Three sources implement it (PDF, raster
image, text); the viewer knows nothing about any format. `DocumentViewport`
and `DocumentViewSession` are pure immutable values in `Tempest.App` with
no rendering type in them, so zoom, pan, fit, resize and page-turn rules
run with no UI in the process — `TD-72`'s discipline, for the same
reason. Format is decided by magic bytes first, declared content type
second, because renaming rather than converting is a thing people do.
`Missing`, `Corrupt` and `Unsupported` are three distinct on-screen
states: telling a user their intact file is damaged would be a false
accusation about their data. The viewer is an ordinary `TD-72` panel — it
tabs, splits, floats and persists with no code of its own for any of it,
and opening a document never navigates.

`3f68376`'s follow-up: a throwaway Skia harness drove the real
`MainWindow` and wrote PNGs, because the Desktop suite runs headless with
`UseHeadlessDrawing` on, so `CaptureRenderedFrame` throws and every green
test had asserted control state, never actually looked. Found: no Open
button reachable from a running application (the shell subscribed after
the editor's rows were already built, so a freshly opened object's row
never got one — every test had called the launcher directly, verifying
the destination and never the door); a closed viewer tab could never be
re-opened (the launcher's map was never reconciled against the layout
tree); disabled-but-visible toolbar controls on `Missing`/`Corrupt`/
`Unsupported` that could do nothing; and a page of a different size
rendered stretched into the previous page's shape, because
`WithContentSize` had been correct since the first commit and the view
never called it.

## 6. Alternatives Considered

The pure-managed text-extraction viewer — rejected explicitly and by
name, on the grounds that it serves specifications and fails at the exact
drawing content the mock-ups centre on.

## 7. Why This Solution Was Chosen

Because a viewer that only ever renders what a document's structured text
happens to contain would pass every test built against text-shaped
documents and fail the moment it met the vector content it exists to
show.

## 8. Architectural Principles

Geometry and view-state rules belong in a pure, UI-free model — the same
principle `TD-72`'s layout tree established, reapplied here to zoom, pan
and page navigation. A rendered frame is evidence a control-state
assertion is not; a headless test suite structurally cannot see one, and
`3f68376`'s harness exists because of that gap specifically.

## 9. Benefits

77 tests, eight mutations run, eight killed (fit stops fitting, pan stops
clamping, zoom ignores its anchor, page navigation stops clamping, the
renderer ignores the zoom, corrupt reported as missing, unsupported
reported as corrupt, the detector trusts the label over the bytes).
`3f68376` adds four regression tests, one per real-application defect,
each mutation-tested: reverting any one fix fails exactly its own test and
nothing else.

## 10. Trade-offs

`TD-80` is closed for the scope delivered, not for the row's original
text: markup, annotation and rotation are carried as `TD-98` rather than
absorbed into a closure that would overstate what was built. Also
disclosed: `TD-99` (DWG/SVG report Unsupported honestly), `TD-100` (image
decoding unverified by the headless suite — the headless platform's own
image decoder is a stub that decodes any bytes to 1×1), `TD-101` (no
tiled rendering, bounded today by a hard raster-edge cap).

## 11. Common Mistakes

Trusting a green headless test suite as proof a feature works when the
suite's own rendering platform cannot capture a rendered frame — every
one of the four defects `3f68376` found was invisible to control-state
assertions and visible only to a harness that actually looked at pixels.

## 12. Future Evolution

`TD-102`, shortly after, finds the identical defect class one layer up —
a descriptor and a surface disagreeing with nothing checking — in the
Project Workspace's Documents and Requirements areas, which route through
this row's viewer via the same `AttachmentViewerLauncher`.

## 13. Key Takeaways

- Verify a rendering claim with a real render before writing the feature
  around it — the five-line PDFium probe here, done first.
- A headless test suite's own limitations (no captured frame) are a gap
  in what "green" can mean, not proof of correctness.
- Closing a row against the scope actually delivered, rather than against
  its original text, is more honest than a closure that silently expands
  to cover what was left out.
