# WP 16.1A — Enforce the Release Gate

## 1. Introduction

`WP 16.1A` (commit `6338330`, merged as `836b2dd`) makes `CI Gate`
depend on the `Governance Health Check` job, so a governance `Fail`
turns the merge gate red instead of sitting beside it as an informational
job summary — the mechanical half of a control `FCR-0005` named as
"machine-detectable but not machine-enforced" since `WP 11.2A` shipped
it, deliberately advisory, four Work Packages earlier. Its full account
is `docs/releases/v0.16.0/WP16.1A Enforce the Release Gate.md`. This
retrospective is written under `WP 16.2C`, sourced from that report and
`6338330`.

## 2. Purpose

Close `TD-45`: make the documented release workflow (`WP11.1B
Engineering Workflow.md` §4) the mechanically enforced one, not merely
the one everybody is trusted to follow.

## 3. Background

`WP 11.2A` shipped the governance health check advisory on purpose — its
own first run found real, pre-existing Academy Index drift, and making
the check required immediately would have failed every future push for a
backlog that Work Package's own scope did not include clearing.
`TD-45` has stood open since branch protection was first documented,
`WP 11.1B`, as "recommended — not configured." Every release since,
including `v0.15.0`, still had to backfill governance drift the check
would have caught days earlier had it been required.

## 4. The Problem

`TD-45` names two distinct halves: whether `CI Gate` itself requires the
governance check to pass, and whether GitHub's own branch-protection
setting on `main` requires `CI Gate` at all before a merge is even
possible through the UI. Neither existed. A governance `Fail` was
visible in the Job Summary and nowhere else — a reviewer could merge
straight past it without ever seeing red.

## 5. The Design

One change to `.github/workflows/ci.yml`'s `gate` job: `needs:
build-and-test` becomes `needs: [build-and-test, governance-health-check]`,
and the gate step now fails, naming which, if either input did not
succeed. `governance-health-check` itself is untouched — it still runs
with `if: always()` so the report is produced even on a red build; what
changed is that its result is now *consumed* by the gate rather than
merely reported next to it. The second half — the actual GitHub
branch-protection rule on `main` — cannot be set from an engineering
session at all: no branch-protection endpoint exists in this session's
GitHub MCP toolset, and `gh` is not installed. That half is handed to
the Product Owner as an exact settings table (required PR review,
required status checks naming `CI Gate`, no force-push, no linear-history
requirement since the project merges via merge commits, administrators
included) with a five-minute verification procedure: push a
deliberately-broken commit to a throwaway branch and confirm the Merge
button stays disabled.

## 6. Alternatives Considered

**Retitling `WP11.1B Engineering Workflow.md` §4 from "Recommended — Not
Configured" to "Configured" now**, on the strength of the workflow-side
change alone. Rejected explicitly — the GitHub setting does not exist
yet, and retitling the document ahead of that reality would be exactly
the kind of documentation-ahead-of-reality drift this entire release is
meant to end.

**Closing `TD-45` outright** on the basis of the workflow half landing.
Rejected for the identical reason — the row's own text names the GitHub
configuration as the closing action, and half of it remains genuinely
undone.

## 7. Why This Solution Was Chosen

Making the workflow-side dependency explicit costs one line and is
immediately, mechanically true the moment it merges; the branch-protection
setting is an outward-facing, administrator-scoped GitHub action no
engineering session can perform on its own authority, so splitting the
control into its machine-checkable half (done here) and its
human-administered half (documented, handed off, not simulated) is the
only honest way to represent what actually changed.

## 8. Architectural Principles

CI configuration only — no production code, test, ADR, or register
touched. `.github/workflows/ci.yml` is valid YAML, confirmed by local
parsing, and the change is exercised by this branch's own CI run.

## 9. Benefits

A governance `Fail` is now structurally incapable of being invisible at
merge time on any branch where `CI Gate` runs — the workflow-side half
of `TD-45` is done, verifiable by reading the job graph, not merely
asserted. `FCR-0005`'s own four-Work-Package-old caveat ("not yet a
required check") is finally closed on the CI side.

## 10. Trade-offs — half a control, and what shipping half of it actually means

**`TD-45` stays Open.** This Work Package closes exactly the half it can
close from inside an engineering session and is explicit that the other
half — the actual repository setting — is a human, one-time,
administrator action nothing here can perform or fake evidence for. This
is worth sitting with rather than glossing: a *documented* required
check and a *configured* required check are not the same guarantee.
Until a repository administrator actually visits Settings → Branches and
saves the rule, `CI Gate`'s new dependency on the governance check is
real inside the workflow file but enforces nothing at the point that
matters most — the Merge button in a pull request. A contributor with
write access could still merge a red `CI Gate` run through the UI today,
exactly as before this Work Package, because nothing yet tells GitHub
that check is required. Half a control shipped honestly, and disclosed
as half, is real progress over the status quo — the workflow no longer
merely *hopes* a reviewer notices a governance failure — but it is not
the same thing as the gate being enforced, and this document says so
rather than letting "CI Gate now depends on the governance check" read
as though the release gate were already closed.

**A second, sharper consequence, disclosed by `WP 16.1B` rather than
this Work Package:** the moment the governance check's exit code becomes
a required `CI Gate` input, any pre-existing register drift turns the
gate red on every branch built on that state — which is exactly what
happened one Work Package later, when `WP 16.1B`'s own new checks found
two genuine, previously-undisclosed register defects. This Work Package
made that consequence possible; it is the intended effect of finally
having a required, blocking gate behind `FCR-0005`, not an accident, but
it means this Work Package's own "done" is entangled with whatever state
the governance registers happen to be in on any given branch.

## 11. Common Mistakes

**Treating "the workflow file says it's required" as equivalent to "it
is enforced."** This Work Package deliberately avoids that mistake in
its own prose — retitling nothing, closing nothing prematurely — but the
mistake is easy enough for a later reader to make by skimming the commit
title alone ("CI Gate now requires the Governance Health Check") without
reading past it to the branch-protection half that is still missing.

## 12. Future Evolution

`TD-45` closes only once a repository administrator confirms the
GitHub branch-protection rule and records the two demonstration run IDs
this Work Package's own report specifies (a broken-test PR staying
unmergeable; a governance-`Fail` PR staying unmergeable once this
change's `CI Gate` dependency is live). `WP11.1B Engineering Workflow.md`
§4's title changes from "Recommended — Not Configured" to "Configured,"
with a date, at that same moment — not before.

## 13. Key Takeaways

- A control with a machine half and a human-administered half is not
  done when the machine half lands — naming exactly which half shipped,
  rather than letting the whole control read as closed, is the honest
  version of "partial progress."
- Making an existing advisory check load-bearing is itself a real design
  decision with a real consequence: every pre-existing drift the check
  already tolerated becomes a hard blocker the instant the dependency is
  wired in, and that consequence lands on whoever's branch happens to
  carry the drift at the time, not necessarily on the Work Package that
  wired the gate.
- Some actions genuinely cannot be simulated or worked around from
  inside an engineering session — a GitHub repository setting is one of
  them — and the correct response is an exact, actionable handoff with a
  verification procedure attached, not a substitute or a workaround that
  only looks equivalent.
