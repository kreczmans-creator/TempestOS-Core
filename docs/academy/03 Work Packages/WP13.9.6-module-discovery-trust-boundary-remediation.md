# WP 13.9.6 — Module Discovery Trust Boundary Remediation

## 1. Introduction

`WP 13.9.6` is a production-code security remediation and the final
engineering link in the `WP 13.9.1`–`WP 13.9.6` trust execution boundary
chain, committed with the whole chain as `d7d19d4` by `WP 13.9.7`.

It closed the gap `WP 13.9.5`'s own final adversarial review had just
found: `WP 13.9.4`'s registration-time filters were correct, but they act
at *Registration* — and an unattributed module type belonging to a denied
plugin was already being **constructed** during *Discovery*, strictly
before either filter was ever consulted.

This retrospective was not written contemporaneously. It is reconstructed
by `WP 13.12.0` (v0.13.0 Academy Retrospective Completion) from
`d7d19d4`'s own commit message, this Work Package's own row in
`docs/releases/v0.13.0/WorkPackages.md`, `PROJECT_STATUS.md`'s retained
strata, `ADR-0111`'s "Corrected, `WP 13.9.6`" section, and direct reads of
the real, current source — including
`ReflectionFrameworkDiscoveryService.cs`'s own class remarks, which
document this change in place. Where the record is silent, this document
says so.

## 2. Purpose

To stop a denied plugin's module type being instantiated by Module
Discovery itself, without giving Module Discovery any knowledge that
plugins exist.

## 3. Background

`ADR-0027` allows a module to declare its metadata via
`ModuleMetadataAttribute`, in which case Discovery reads the attribute
and never constructs the type. A module *without* that attribute falls
back to Discovery's original behaviour, unchanged since the framework's
early releases: instantiate the type via its public parameterless
constructor purely to read its `Id`/`Name`/`Version`, then discard the
instance.

`WP 13.9.4` had, two Work Packages earlier, built the denied-type
registry and wired two filters in `TempestHost` — at Module Registration
and Hosted Service Registration. Those filters are consulted only *after*
Module Discovery has already returned its descriptors.

## 4. The Problem

Per this Work Package's own row and the class remarks it added: an
unattributed `IModule` type belonging to a plugin already denied trust
was still constructed via `Activator.CreateInstance` inside
`CreateDescriptor`, during Module Discovery, strictly before the
`WP 13.9.4` Registration filter was ever reached.

That is a genuine, live constructor execution of a denied plugin's own
code. Two distinct failure modes followed, and this Work Package's own
mutation testing reproduced both exactly:

- **Quiet execution** — the denied plugin's constructor body simply ran.
- **A `Faulted` Host** — if that same type also lacked a public
  parameterless constructor, `CreateDescriptor` threw an uncaught
  `ModuleDiscoveryException` that faulted the whole Host.

The `WP 13.9.4` boundary could not reach this: it is keyed on
descriptors, and the construction happens while those descriptors are
still being produced.

## 5. The Design

**One optional constructor parameter, and nothing else in the discovery
service.** `ReflectionFrameworkDiscoveryService` gained
`Func<Type, bool>? isTypeExcluded = null`, consulted inside its existing
candidate-scanning loop immediately after the existing `IsValidModuleType`
check and strictly before `CreateDescriptor` is ever called. `TempestHost`
supplies `deniedTypeRegistry.IsDenied` — the same, unmodified `WP 13.9.4`
registry, already fully populated by Plugin Loading before Module
Discovery runs.

Three properties make this the minimum viable shape:

- It **defaults to `null`**, meaning never-excluded, so every existing
  caller and test is behaviourally unchanged.
- The predicate is **generic**. `Tempest.Core.Modules` gains no reference
  to `Tempest.Core.Plugins`, preserving `ADR-0110`'s deliberate
  plugin-unawareness at the type-reference level exactly as the
  `WP 13.9.4` filter already did.
- It **reuses the existing registry unmodified** — no new state, no
  second source of truth about who was denied.

**The process design was itself deliberate**: four parallel Round-1
read-only reviewers converged on one design, then a single implementation
agent, then a fresh, independent adversarial review.

**New test infrastructure**, per the row: `ConstructorExecutionProbe.cs`
— a new file providing a GUID-keyed, thread-safe static invocation
counter that an emitted plugin module's own IL calls into, so a test can
prove whether `Activator.CreateInstance` genuinely ran for that exact
type; one new `DynamicPluginAssemblyBuilder` method,
`BuildUnattributedPluginModuleWithConstructorProbe`; one new
`ModuleFixtures.cs` fixture, `ConstructorTrackingModule`; and new tests in
`ReflectionFrameworkDiscoveryServiceTests.cs` (2) and
`TempestHostPluginTrustTests.cs` (7).

## 6. Alternatives Considered

The record does not enumerate a formal alternatives list. What the design
declined is visible and consistent with the release's standing decisions:
making Discovery plugin-aware (rejected — it would contradict `ADR-0110`,
and the generic predicate achieves the same exclusion without it), and
moving the trust filter earlier by restructuring the Host's phase order
(not taken — the registry was already populated before Discovery, so no
reordering was required).

## 7. Why This Solution Was Chosen

Because it closes a live code-execution path with one optional,
generically-typed parameter and no behavioural change to any existing
caller.

The alternative shapes all cost more and buy nothing: a plugin-aware
discovery service breaks an ADR; a second registry duplicates state; a
phase reordering churns the Host lifecycle for a problem that was purely
one of *when the existing data is consulted*.

## 8. Architectural Principles

- **`ADR-0110` — plugin-unawareness preserved at the type-reference
  level.** A `Func<Type,bool>` is not a plugin reference.
- **`ADR-0027` — the attribute path is untouched.** A module carrying
  `ModuleMetadataAttribute` was never constructed by Discovery and still
  is not.
- **Default to no behaviour change.** An optional parameter defaulting to
  `null` means every pre-existing caller is provably unaffected.
- **One source of truth.** The `WP 13.9.4` registry is reused, not
  mirrored.
- **Defence in depth retained.** The `WP 13.9.4` Registration filter was
  deliberately left in place.

## 9. Benefits

A denied plugin's module constructor no longer runs at all. The
Host-faulting variant — an uncaught `ModuleDiscoveryException` from a
denied type lacking a parameterless constructor — is closed with it. And
because the predicate is consulted before `CreateDescriptor`, the fix is
independent of *why* the plugin was denied.

`ADR-0111` gained a "Corrected, `WP 13.9.6` Module Discovery Trust
Boundary Remediation" section — the third and, per this Work Package's own
adversarial review, final correction closing the "isolates the whole
plugin" execution boundary the Decision first stated.

## 10. Trade-offs

The exclusion is a predicate supplied by the caller, so the discovery
service cannot itself guarantee it is wired. Correctness depends on
`TempestHost` passing `deniedTypeRegistry.IsDenied` — which it does, at
the single production construction site, but an embedder constructing the
service directly gets the `null` default and no exclusion. That residual
is what later made `WP 13.11B`'s fail-closed reflection guard worth
adding at the same boundary for a different failure class.

The `WP 13.9.4` Registration filter is now partly redundant for the
module pipeline. It was deliberately retained as harmless defence in
depth, and remains fully load-bearing for Hosted Service Registration.

## 11. Common Mistakes

- **Filtering after the work has already happened.** `WP 13.9.4`'s filter
  was correct and still too late — Discovery had already constructed the
  type. The lesson generalises: a boundary must sit before the first
  side effect, not before the first *use of the result*.
- **Assuming symmetric pipelines need symmetric fixes.** Hosted Service
  Discovery was confirmed to need no equivalent change, because
  `HostedServiceDiscoveryService` never instantiates a candidate at all.
  The row records this explicitly rather than applying a reflexive
  matching fix.
- **Trusting a guard without proving it fires.** This Work Package
  verified non-vacuousness by mutation testing — temporarily disabling
  the guard reproduced both the quiet-execution and the `Faulted`-crash
  failure modes exactly.

## 12. Future Evolution

`WP 13.9.7` integrated and committed this Work Package with the rest of
the chain. `WP 13.10A`–`WP 13.10C` then hardened a different axis
(hosted-service constructor conformance and identity, `TD-51`/`TD-52`).

The same `isTypeExcluded` seam this Work Package introduced later proved
load-bearing again: `WP 13.11B`'s remediation of the reopened `TD-51`
depended on the denied-type registry actually containing the offending
type, precisely so this predicate would exclude it — and added a narrow
fail-closed reflection guard around `CreateDescriptor` for the case where
metadata cannot be read at all.

## 13. Key Takeaways

- Put the trust check before the first side effect, not before the first
  use of the result.
- A generic `Func<Type,bool>` can carry a trust decision across an
  architectural boundary without carrying the trust *vocabulary* with it.
- An optional parameter defaulting to inert behaviour makes "no existing
  caller changed" provable rather than argued.
- Mutation testing — disabling the guard and confirming the original
  failures return — is what separates a real regression test from a
  decorative one.
