# WP 16.2B — Academy Retrospective Backfill

## 1. Introduction

`WP 16.2B` wrote 41 new Academy retrospectives, backfilled 21 more
`Academy Register.md` rows for files that already existed on disk
without one, corrected a stale `Contributor Learning Path.md` closing
pointer that had been wrong since `v0.5.0`, and made release-level
Definition of Done item 4 ("Academy updated") true for the first time
since `v0.10.0`. It ran as three parallel branches from
`feature/v0.16.0` at `8b4c394` —
`feature/v0.16.0-wp16.2b-retros-v0.11.0` (`b7ceada`),
`feature/v0.16.0-wp16.2b-retros-v0.15.0` (`17cad3f`), and
`feature/v0.16.0-wp16.2b-retros-v0.14.0` (`214bc76`) — merged in that
order, plus a closure commit (`9843b63`) reconciling the counts none of
the three could touch without colliding with the other two.

## 2. Purpose

Close the retrospective gap that `WP 11.9.0`, `WP 12.3A`/`12.3B`,
`WP-Z3` §12, `WP 11.5A` §10 and `WP 15.1A` had each, independently,
already disclosed: this project had been running one release behind on
its own Academy Maintenance obligation (Engineering Governance §6) for
its entire history. `v0.16.0 Release Plan.md` states the objective
directly — "release DoD item 4 is true for the first time since
`v0.10.0`" — and names the acceptance test: `Academy Index.md`'s own
check passes, and zero Work Packages in any `WorkPackages.md` lack a
retrospective, verified by a one-off script whose output is in the
report.

## 3. Background

The gap had a specific shape. `v0.11.0`'s ten Work Packages
(`WP 11.0A` through `WP 11.9.0`) had reports but no retrospectives.
`WP 15.1A`/`WP 15.1B` were the same. And `docs/releases/v0.14.0/
WorkPackages.md`'s own second table — the pre-`v0.14.0` engineering body
of work, unnumbered because it predates this project's Work Package
numbering convention — had never been retrospected at all, despite
`WP-Z3` having already established, one release earlier, the precedent
for writing retrospectives for unnumbered historical work. Separately,
21 retrospectives already existed on disk (`WP 9.3A`, `9.4A`, `9.5A`,
`9.8B`, `9.9.0` twice, `10.0A`, `10.0B`, `10.1A`, `10.1B`, `10.2A`,
`12.9.1`, `12.9.2`, `13.0.0`, `13.0.0A`, `11.5A`, `15.0A`–`15.0D`,
`15.2A`) with no corresponding `Academy Register.md` row — a gap the
register itself could not reveal, because nothing had ever diffed the
register's own table against the folder's actual contents.

## 4. The Problem

The volume made the ordinary single-author retrospective process
impractical: the plan itself calls the effort "M–L (volume, not
difficulty)" and explicitly authorises splitting it "across parallel
authors by release." Three authors writing into the same
`docs/academy/**` tree, on separate branches cut from the same base,
creates a specific and unavoidable collision: every one of them would
naturally want to write the true, final count into `Academy Register.md`'s
own `## 03 Work Packages (N retrospectives)` header and "Last Reviewed"
narrative — but no author, working alone on their own slice, can know
what that final total is, because it depends on what the other two
slices add. Any author who wrote a number would be guessing at a moving
target the other two branches were simultaneously moving.

A second, more mundane problem surfaced during execution: two of the
three parallel authors could not invoke PowerShell directly from their
own worktrees — a sandbox guard neither expected going in — which meant
neither could run `scripts/governance-healthcheck.ps1` itself to
self-verify Check 2 (the Academy Index link check) before handing off
their branch.

## 5. The Design

**Split by release, not by count or by author-convenience.** Each of
the three branches owns a self-contained set with no row-level overlap:
`v0.11.0`'s ten Work Packages, `WP 15.1A`/`15.1B`, and the `v0.14.0`
pre-programme's 29 rows. Because the sets are disjoint by construction,
the only genuinely shared resource is `Academy Register.md`'s own
summary line and count header — everything else (the retrospective
files themselves, each Work Package's own register row) can be written
independently without a merge conflict.

**Leave the shared summary for a closure commit, merged last.** Rather
than have any of the three branches guess at or reserve the final
count, each branch's own commit adds its own rows to the register table
without touching the header narrative; the closure commit, applied
after all three branches are merged, re-derives the true final count
(142 → 206 files, by direct `ls`/`wc -l`) and writes it once. This is
the same principle `WP 16.2A` applies to registers generally — re-derive
from the merged tree, never carry forward a number computed before the
merge — applied specifically to the one field three independent authors
could not have gotten right on their own.

**A naming rule for the 29 unnumbered `v0.14.0` rows, decided once and
applied consistently.** `WP-Z3` §6 had already rejected inventing
`WP14.x` numbers for work that carries no such identifier anywhere in
the repository. This Work Package extends that precedent: the 29 files
are named `v0.14.0-<anchor>-<kebab-title>.md`, where `<anchor>` is the
row's own identifier when it has one (`TD-59-TD-60`, `TD-84`,
`ADR-0116`, `TD-77-stage-2`) and a short topic slug otherwise — stated
explicitly inside the retrospective for the row that commissioned
`WP-Z3` in the first place.

**Where PowerShell was unavailable, verify by an independent method
rather than skip verification.** One of the two blocked authors
reimplemented Check 2's own algorithm (diff every `Academy Index.md`
link against the files that actually exist) in Python; the other used a
shell wrapper. The real script was still run — by the integrator,
against the fully merged tree, in every case cited in the report — so
no branch's own verification claim substitutes for the authoritative
check; it only gives that branch's own author independent evidence
before handoff.

## 6. Alternatives Considered

**One author, sequentially, working through all 41 retrospectives.**
Rejected by the plan itself as disproportionate to the task's own
nature ("volume, not difficulty") — three authors working in parallel
on disjoint sets finishes in roughly a third of the wall-clock time
with no loss of quality, provided the one genuinely shared resource is
handled by a closure step rather than by hopeful coordination between
branches that cannot see each other's work in progress.

**Have each branch write its own guess at the final register count and
let the last merge simply overwrite the others.** Rejected implicitly
by the design actually used — a "last merge wins" approach to a shared
summary line is exactly the kind of collision the split-by-release
design was built to avoid, and it would silently discard whichever
branch's own supporting narrative merged first.

**Skip PowerShell verification for the two blocked authors and rely on
the integrator's run alone.** Rejected in practice by both blocked
authors, who chose to reimplement the check rather than submit unverified
work — a reasonable response to a sandbox limitation neither branch
could fix itself, though it means two different reimplementations of
the same check now exist nowhere in the permanent record, only in this
retrospective's own account of what happened.

## 7. Why This Solution Was Chosen

Splitting by release rather than by row count keeps every author's own
diff reviewable as "the retrospectives for this one release," which
matters for a task whose entire value depends on each retrospective
being sourced from that release's own primary evidence rather than
copied from a template. Deferring the shared count to a closure commit
is the only design that does not require three simultaneous authors to
coordinate on a number that does not exist until all three are done —
it converts an impossible coordination problem into a trivial one-step
reconciliation performed once, by whoever merges last.

## 8. Architectural Principles

- **A shared, derivable summary field should never be written by a
  branch that cannot see the other branches it will be merged with** —
  defer it to a closure step over the merged tree, exactly as
  `WP 16.2A` re-derives registers from source rather than trusting an
  earlier pass.
- **A naming convention decided once and stated inside the material it
  governs** (the `v0.14.0-<anchor>-<title>.md` rule, recorded in the
  retrospective for the row that commissioned `WP-Z3`) survives better
  than a convention only described in a report nobody reads before
  authoring the next file.
- **A blocked verification tool is a reason to find an independent way
  to verify, not a reason to skip verification** — both blocked authors
  chose reimplementation over submission-without-proof.
- **Parallel work on one shared document needs a partition with zero
  row-level overlap**; splitting by release achieved this cleanly,
  where splitting by, say, alphabetical Work Package number would not
  have (the `v0.14.0` and `v0.11.0` sets would have interleaved).

## 9. Benefits

- 41 new retrospectives; `docs/academy/03 Work Packages/` grew from 165
  to 206 files, every one linked from `Academy Index.md` (Check 2: 280
  files / 373 links, 0 orphans, 0 broken, at the merged tree).
- 21 backfill rows close a register gap that existed silently — files
  present on disk with no register row are invisible to anyone auditing
  the register alone, and this closes that specific blind spot.
- `Contributor Learning Path.md`'s closing pointer, stale since
  `v0.5.0` through eleven releases, now correctly names
  `docs/releases/v0.16.0/WorkPackages.md`.
- Release-level Definition of Done item 4 is true for the first time
  since `v0.10.0` — the precondition `TD-127` (below) depends on to be
  worth anything at all.

## 10. Trade-offs

- **The 29-row `v0.14.0` naming convention is a compromise, not a full
  solution.** Files with no `WP` identifier anywhere in the repository
  are harder to find by number and easier to find only by the topic
  slug or `TD`/`ADR` anchor the naming rule uses — a deliberate cost
  accepted because inventing numbers the repository itself never used
  would be worse.
- **Two independent, uncommitted reimplementations of Check 2's own
  algorithm** (one in Python, one as a shell wrapper) were used for
  self-verification and then discarded — real engineering effort spent
  on tooling that leaves no trace in the permanent record, because the
  sandbox limitation that necessitated them was itself out of scope to
  fix.
- **This Work Package's own scope explicitly excludes rewriting
  existing retrospectives** — the 21 backfilled register rows point at
  files whose own quality was never re-reviewed as part of this pass,
  only registered.

## 11. Common Mistakes

- Letting the last-merged branch silently overwrite a shared summary
  field instead of deferring it to a dedicated closure step — this
  looks like it "just works" until two branches' own guesses disagree
  and the later merge quietly wins by accident of ordering, not by
  correctness.
- Inventing a numbering scheme for historical work that never had one,
  rather than reusing an existing precedent (`WP-Z3`'s own prior
  rejection of invented `WP14.x` numbers) — consistency with prior
  Academy decisions matters more than internal tidiness.
- Treating a sandbox tooling limitation as a reason to skip
  verification rather than a reason to verify by another method.
- Assuming a file present on disk implies a register row for it — the
  21-row backfill exists precisely because that assumption had gone
  unchecked for several releases.

## 12. Future Evolution

`TD-127`, raised by the `v0.16.0` review board on 2026-09-05, is the
direct sequel to this Work Package's own existence: closing `v0.16.0`
without retrospectives for its own Work Packages would re-break release
DoD item 4 the moment `WP 16.2B` made it true, because `WP 16.2B`'s own
scope, by the plan's own design, excluded this release's Work Packages.
`WP 16.2C` (this retrospective's own Work Package, split across two
parallel worktrees for the same reason `WP 16.2B` itself was split
three ways) is that closure. `TD-127` also names a standing governance
question this Work Package's own history raises but does not answer:
whether Engineering Governance §6 means a retrospective is owed *within*
the Work Package that does the work, or only *before the release that
contains it closes*. This project has now run behind on that question
twice — once before `v0.10.0`, prompting `WP 16.2B` itself, and again
within `v0.16.0`, prompting `TD-127` — which is itself evidence that
the convention needs a decision, not a third repetition.

## 13. Key Takeaways

- A number that depends on the outcome of parallel, disjoint work
  cannot be written correctly by any one participant in that work — it
  needs a closure step over the merged result.
- Split parallel documentation work along a boundary with zero
  row-level overlap; release boundaries did this cleanly here.
- A sandbox or tooling limitation blocking the authoritative
  verification script is a reason to verify independently, not a
  reason to skip verification and hope the integrator catches it.
- Closing a long-standing gap (retrospectives since `v0.10.0`) does not
  retire the underlying convention question — it can recur within the
  very release that closed it, as `TD-127` shows.
