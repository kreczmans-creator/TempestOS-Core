# WP 16.3A — Durable State Schema Versioning Architecture

## 1. Introduction

`WP 16.3A` (commit `a80e95d`, merged as `8b4c394`, "Technical Review:
accepted") produces `ADR-0120` and `docs/architecture/State Schema
Versioning Architecture.md`: the decision, and the design built from it,
that gives `EngineeringObjectState` an integer `SchemaVersion` and a
per-Kind, read-path-only migration chain, closing the concrete risk
`TD-87` names — a `LifecycleState` reorder silently reinterpreting a
persisted status as a different, valid-looking one. **This Work Package
has no standalone Work Package report of the kind every one of its five
siblings in this release produced.** Its evidence is the ADR and the
architecture document themselves, plus commit `a80e95d`. This
retrospective is written under `WP 16.2C`, sourced directly from those
two documents and that commit — not from any intermediate summary,
because none exists.

## 2. Purpose

Decide how `EngineeringObjectState` (and, where the same shape actually
applies, `SettingsDocument<T>`) carries a schema version and migrates
old records on read, so that `WP 16.3B`'s implementation has an
architecture to build exactly rather than a set of choices to make while
coding.

## 3. Background

`ADR-0113` made `EngineeringObjectState` durable and disclosed, in its
own Consequences, that the record it introduced is versionless: an
unreadable record already degrades safely (`TD-60`'s established
discipline — `EngineeringObjectStateStore.Deserialise` catches
`JsonException` and returns `null` rather than aborting), but a record
that parses correctly and means something *different* because its shape
changed underneath it is not handled at all. `ADR-0114` repeated the
identical disclosure a second time when it added `ContentHash`,
deliberately additive specifically so it would not need a version. Two
ADRs in a row had now built around the gap rather than into it before
this Work Package finally closed it.

## 4. The Problem

`LifecycleState` is an eight-member `enum` with no explicit numeric
values, serialised today by `JsonSerializer.Serialize(state)` with no
converter — meaning `Status` and every `History[].From`/`To` persist as
the enum's ordinal position. Reordering that enum's members would make
every persisted status and every recorded transition silently
reinterpret as a different, valid-looking value: not a `JsonException`,
not a skipped record, a *wrong* one, indistinguishable from a correct
one until an engineer notices their released part reads as cancelled.
Because `EngineeringObjectBase.PersistStateAsync` always calls
`CaptureState()`, which always builds a fresh record from live in-memory
fields, migration is structurally only ever a read-path problem — there
is no code path that writes an old shape on purpose.

## 5. The Design

`EngineeringObjectState` gains `SchemaVersion` as its first component;
absent normalises explicitly to `1` via one `if` inside the store's own
read path, deliberately not relying on a serialiser default for a
missing constructor argument. Migrations are an ordered chain per Kind
(`IStateMigration`, with `Kind`, `FromVersion`, and a `Migrate` method),
collected by an `IStateMigrationRegistry` and applied repeatedly inside
`EngineeringObjectStateStore`'s existing read path — after JSON
deserialisation, after the version normalisation, before the record ever
reaches a caller — so both existing callers (`FindAsync`, `ListAsync`)
inherit migration for free with no signature change. Attachment content
(`EngineeringObjectAttachmentState`) gets no independent `SchemaVersion`
of its own: it is nested inside its parent's own JSON document with no
independent read path, so a Kind's own migration is the correct and only
place to rewrite it. Enums serialise as strings from this point
forward via a shared `JsonStringEnumConverter`; because that converter
reads both a name and a number, this one change closes `TD-87`'s
concretely named risk with **no migration required at all** — a record
written before this ADR, still holding a numeric `Status`, deserialises
identically to one written after. A record whose version cannot be
bridged is logged and skipped, extending — not duplicating — the
`TD-60` discipline `Deserialise` already applies to malformed JSON.
`SettingsDocument<T>` joins the same scheme for its six DTO-shaped
consumers; its three list-shaped consumers (`MacroDto`,
`FavouriteObjectEntry`, `RecentObjectEntry`) explicitly do not, because
each is a bare JSON array on disk today and wrapping one in an envelope
to carry a `SchemaVersion` would change the wire shape every installed
copy of TempestOS already holds for those three keys — a materially
larger, riskier change this ADR declines to make against a need that
does not yet exist.

## 6. Alternatives Considered

Five alternatives are recorded in `ADR-0120` itself, each rejected on a
specific, stated ground: a schema-registry service resolved through DI
(rejected — one concrete store already owns exactly one collection; a
separate service would be unnecessary indirection, the same shape
`ADR-0104` already rejected one layer down); versioning at the
`IPersistenceStore` collection level, a `.v2` collection per breaking
change (rejected — it would force an eager, whole-store startup
migration pass, reintroducing the exact cost `TD-88` already discloses
as undesirable); a version-keyed DTO hierarchy
(`V1EngineeringObjectState`, `V2EngineeringObjectState`, ...) (rejected —
heavier than an ordered list of one-argument functions, for a shape
nothing in the platform ever round-trips through code); migrating on
write instead of read (rejected — `TD-86` already discloses unbatched
per-mutation writes, so tying schema currency to how often an object
happens to be touched buys nothing an untouched object still needs
read-time migration to handle); a single global `SchemaVersion` for
every Kind rather than per-Kind chains (rejected — it would force every
Kind's migration to move in lock-step even when only one Kind's fields
changed, the opposite of `ADR-0113`'s own "each type owns its own
persistence" decision applied one level up); and wrapping the three
list-shaped `SettingsDocument<T>` consumers in an envelope now, for
uniformity (rejected — the identical building-ahead-of-demonstrated-need
reasoning `D-023` already applies to the plugin platform, on the
identical ground).

## 7. Why This Solution Was Chosen

An ordered function `EngineeringObjectState → EngineeringObjectState`,
one per version step, composes cleanly (version 1 to 4 is three
single-step migrations applied in sequence, each independently
testable) and needs no parallel type hierarchy for a shape the platform
never constructs directly — the version-keyed alternative was rejected
for exactly the complexity this shape avoids. Enum-as-string is listed
in `TD-87`'s own closing note as "cheap, do it first," and this ADR
follows that: it closes the one concretely named risk immediately, with
no migration machinery required to do so, before the heavier per-Kind
chain mechanism is even needed for a real breaking change.

## 8. Architectural Principles

This is the ADR-eligible decision itself, meeting Governance §5 on at
least three independent grounds: it was not the only reasonable choice
(five genuine alternatives seriously considered and rejected, per §6
above); it establishes a convention future Work Packages are expected to
follow (any future breaking change to `EngineeringObjectState` or a
DTO-shaped `SettingsDocument<T>` lands in this seam, not a new one); and
it resolves an explicit tension the Release Plan itself named
("`SettingsDocument<T>` joins the same scheme" was recommended without
qualification, and this ADR's own text says so directly: "the actual
code has two seams, not one, and only one of them is the seam
`EngineeringObjectState` uses" — following the recommendation where it
matches, naming rather than papering over where it does not).

## 9. Benefits

The one risk `TD-87` names concretely closes with no migration required
at all, because the chosen converter reads both representations. A
genuine future breaking change now has a real, ordered, testable seam to
land in instead of the prior choice between "make it additive forever"
or "silently lose or misread old records." `IStateMigrationRegistry` is
an optional collaborator, mirroring `ADR-0113`'s own
`EngineeringDomainContext.ObjectStateStore` pattern, so every existing
hand-assembled test context keeps working unchanged with no migration
chain supplied.

## 10. Trade-offs — and the deviation this retrospective does not smooth over

**This Work Package produced no standalone report.** Every one of its
five siblings in this release — `WP 16.0A`, `WP 16.0B`, `WP 16.1A`,
`WP 16.1B`, `WP 16.5B` — has its own report under `docs/releases/
v0.16.0/`. `WP 16.3A` does not. The `v0.16.0` review board flagged this
gap directly: an architecture-phase Work Package that produces an ADR
and an architecture document, and nothing else, still departs from this
project's own established convention (every Work Package from `WP 2.1`
onward produces a completion report meeting Governance §4's nine-item
floor — summary, files touched, architectural decisions and reasoning,
test results, build results, assumptions, observations, documentation
summary). `ADR-0120` and the architecture document are excellent,
detailed, and traceable to source line numbers throughout — but neither
is a substitute for a report that states, in one place, what was built,
what was tested, and what assumptions were made. This retrospective is
sourced entirely from the ADR and the architecture document because
that is all the primary evidence there is; it does not manufacture a
report's worth of detail (test counts, build results) that was never
recorded anywhere, and it says so here rather than presenting the ADR's
own citations as if they were a completion report's.

**A second, related cost**: `ADR-0120` and the architecture document
both describe `WP 16.3B` as "not yet started" and "implementation is
`WP 16.3B`'s" respectively, at the time they were written — accurate
then, and this retrospective does not update those documents to say
otherwise (per Governance §5's own "never delete, mark superseded"
convention, that correction belongs to whichever document tracks
`WP 16.3B`'s own status, not to this one).

## 11. Common Mistakes

**Treating "this Work Package produced excellent design documents" as
equivalent to "this Work Package met the Definition of Done."**
`ADR-0120` is unusually rigorous even by this project's own standard —
five alternatives considered, six numbered decision points, an explicit
acknowledgment of where the Release Plan's own recommendation did not
match the actual code. None of that substitutes for the completion
report Governance §4 requires of every Work Package, and this
retrospective's own job is to say that plainly rather than let the
ADR's quality imply the deviation did not happen.

## 12. Future Evolution

`WP 16.3B` (commits `2e3ec8e`, `2225d2e`, `67e7ce3`, merged as `7220c0b`)
implements this architecture and closes `TD-87`; its own retrospective
is `WP 16.2C`'s sibling document under a separate Work Package number
and covers the implementation's own test evidence, which this
retrospective — sourced only from the architecture-phase documents — does
not claim. If a genuine breaking change reaches a `TypeState` field
before `WP 16.3B` lands, `ADR-0120`'s own Future Considerations section
already names the interim discipline: keep the field additive, the same
pattern `ADR-0114`'s `ContentHash` already used. If one of the three
list-shaped `SettingsDocument<T>` documents ever needs a breaking
change, the Work Package that needs it decides the envelope question on
that document's own concrete requirement, not by retrofitting this ADR's
mechanism onto a shape it was not designed for.

## 13. Key Takeaways

- A single write-path change (enums as strings, via a converter that
  reads both old and new representations) can close a concretely named
  risk with zero migration machinery required — the heavier, general
  mechanism this ADR builds is for the *next* breaking change, not this
  one.
- An architecture Work Package that produces a rigorous ADR and design
  document is not automatically exempt from Governance §4's own report
  requirement — the two serve different purposes (a decision's reasoning
  versus a Work Package's own accounting of what it built and verified),
  and one being excellent does not make the other's absence a non-event.
- Recommending a design pattern ("same seam") in a release plan, and
  then finding on inspection that the actual code has two seams and only
  one matches, is exactly the kind of tension worth naming in the
  decision record itself rather than forcing the recommendation to fit —
  `ADR-0120` does this directly, and it is a model worth repeating.
