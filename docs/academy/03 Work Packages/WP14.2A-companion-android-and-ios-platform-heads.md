# WP 14.2A — Companion Android & iOS Platform Heads

## 1. Introduction

`WP 14.2A` gave the Companion its real mobile form: `Tempest.Companion`
became the shared single-view application library (the official Avalonia
cross-platform shape), with four thin heads — the phone-frame
`Tempest.Companion.Desktop` (in the gating solution),
`Tempest.Companion.Android`, and `Tempest.Companion.iOS` (in a new,
deliberately separate `Tempest.Companion.Mobile.slnx`, built by the
dispatch-only `mobile-heads.yml` workflow) — carrying the brand pack's
launcher icons. One new ADR (`ADR-0116`) settles where heads live
relative to the CI gate; `TD-57` moves Open → Partially resolved. The
gating solution and complete test suite are unchanged and green.

## 2. Purpose

Close `TD-57`'s structural half: make the Companion genuinely
installable mobile software, without gating the platform's CI on
toolchains its environments cannot hold.

## 3. Background

`ADR-0113` shipped the Companion as a single executable that was both
the app and its own desktop host, with heads anticipated
("`ISingleViewApplicationLifetime`-ready") and their absence recorded
honestly as `TD-57` — the `WP 14.0A` environment could not obtain the
.NET mobile workloads. This Work Package's environment could install the
**Android** workload (NuGet-delivered) and a JDK, but not the Android
SDK itself (its distribution hosts are unreachable under the network
policy), and the **iOS** workload does not exist for Linux hosts at all.

## 4. The Problem

Three constraints to reconcile honestly: the single-project shape
structurally cannot grow heads (`NETSDK1150`: a self-contained mobile
executable cannot reference another executable — hit directly on the
first build attempt); the gating solution must stay buildable in
workload-free environments (`NETSDK1147` otherwise fails every restore);
and whatever ships must be validated exactly as far as the environment
allows, with the gap stated — not "it should work".

## 5. The Design

- **The template shape.** `Tempest.Companion` drops `OutputType` and
  becomes the shared library holding everything — `App`, every view,
  service, theme, and asset. `Tempest.Companion.Desktop` takes the moved
  `Program.cs` (phone-frame window; joins `TempestOS.slnx` so the gate
  still builds a runnable Companion). The Android head is one
  `MainActivity : AvaloniaMainActivity<App>` plus launcher identity
  (label, the pack's icon as a drawable, an AppCompat `DayNight`
  activity theme with the navy-800 first-frame window background); the
  iOS head is the template `Program`/`AppDelegate :
  AvaloniaAppDelegate<App>` plus `Info.plist` and an `AppIcon` asset set
  (the pack's icon, flattened opaque at 1024² per Apple's rules). Heads
  contribute bootstrap only — a head that grows logic is a defect
  (`ADR-0116`).
- **Solution/CI boundary (`ADR-0116`).** Mobile heads live in
  `src/Tempest.Companion.Mobile.slnx`, outside the gating solution;
  `.github/workflows/mobile-heads.yml` (manual dispatch, non-gating)
  builds Android on `windows-2022` (runner image ships an Android SDK)
  and iOS on `macos-15` against the simulator RID (no signing needed),
  uploading the artefacts. `ci.yml` and the CI Gate are untouched.
- **Validation to the environment's edge.** Android: full NuGet restore,
  then a Roslyn compile of the head's source against the workload's own
  reference assemblies (`Microsoft.Android.Ref.36`, the AndroidX
  bindings, `Avalonia.Android`) — clean; the toolchain build stops only
  at `XA5300` (no Android SDK). iOS: authored to the official template;
  no compile possible on this host; validated by the workflow's macOS
  job on first dispatch. All of this is stated in `ADR-0116` and
  `TD-57`, which stays **Partially resolved** until that dispatch is
  green and the apps are observed running.

## 6. Alternatives Considered

Recorded in `ADR-0116`: heads inside the gating solution with workload
installs in `ci.yml` (rejected — iOS cannot build on the gate's Windows
runners at all, and every contributor restore would demand workloads);
conditional solution membership (rejected — not a thing, and per-project
conditions make restore environment-dependent); an auto-triggered mobile
workflow (rejected for now — its first run could not be validated from
here, and an unvalidated auto-red on every push is noise; promotion is a
one-line change once dispatched green); `ReferenceOutputAssembly`
tricks to dodge `NETSDK1150` (rejected — adopt the ecosystem shape
instead of fighting the toolchain).

## 7. Why This Solution Was Chosen

Every piece is the boring, ecosystem-standard answer: the Avalonia
template's own library/heads split, the runner images' own toolchains,
the simulator RID that needs no signing secret, and a workflow that
cannot redden the gate. The only invention is the honesty machinery —
compile-to-the-edge validation and a debt entry that names exactly what
remains.

## 8. Architectural Principles

Heads are bootstrap, never behaviour; the gate never depends on a
toolchain the environment cannot hold; validation claims match evidence
exactly (restore-proven, reference-compile-proven, template-mirrored —
three different confidence levels, each labelled); debt is retired by
observation, not by authoring.

## 9. Benefits

The Companion is now packageable for the devices it was designed for;
the shared library means the mobile heads inherit all 69 Companion tests
and the entire brand system with zero duplication; the gating solution
gained a cleaner shape (app library + explicit desktop head); and future
heads — the `FCR-0091` wall display included — now have a socket.

## 10. Trade-offs

Mobile breakage is caught at dispatch time, not push time (`ADR-0116`'s
accepted cost); the iOS head is unvalidated until the first macOS run;
launcher iconography is the pack's static icon (no adaptive-icon
foreground/background split yet — a polish item for the first on-device
pass).

## 11. Common Mistakes

Referencing an executable from a mobile head and discovering
`NETSDK1150` late (split library-first); using a plain
`@android:style` Activity theme with `AvaloniaMainActivity` — it derives
from `AppCompatActivity` and **crashes at launch** without a
`Theme.AppCompat` family theme (this Work Package's reference-assembly
compile surfaced the dependency; the theme was fixed before it ever ran);
gating CI on workloads it cannot install; and shipping an auto-triggered
workflow whose first run nobody has ever executed.

## 12. Future Evolution

Dispatch `mobile-heads.yml` and take `TD-57` to Resolved on green +
observation; promote the workflow to path-triggered once trusted; add an
Android adaptive icon and iOS launch-screen branding on the first
on-device polish pass; real device deployment (signing, distribution)
is deliberately unscoped until a real need is named — and off-box
connectivity remains gated on `FCR-0003`/`FCR-0004` (`TD-58`)
regardless of installability.

## 13. Key Takeaways

"The environment can't build it" never means "author it blind": restore
graphs, reference assemblies, and template fidelity give three graded
rungs of real evidence below a full toolchain — and stating which rung
each artefact reached is what keeps an unbuildable target honest. The
CI gate's job is to be reproducible everywhere the team works;
capability that isn't goes beside the gate, never inside it.

## Observations

- `dotnet workload install android` succeeds on this Linux host purely
  from NuGet — it is only the Android *SDK* (Google-hosted) that the
  network policy blocks. Recorded here because the distinction decides
  what any future constrained environment can validate.
- The two pre-existing Linux-environment Core test failures reproduce
  unchanged (baseline-identical; green on Windows CI).
