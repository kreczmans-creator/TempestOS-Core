# WP 14.2.1 — CI Pipeline Remediation

## 1. Introduction

`WP 14.2.1` is a remediation Work Package: it fixes the reason this
repository's required `CI Gate` had been red on every recent run, on the
`v0.14.0` feature branch *and* on `main`. The investigation began from
the Product Owner's observation that there had been "lots of failures on
Git build/test actions", and every one of those failures turned out to
have nothing to do with the code. Committed as one change to
`.github/workflows/ci.yml` and `.github/workflows/mobile-heads.yml`,
plus `ADR-0117`, two new Technical Debt entries, and a correction to the
Academy's own CI article. Zero `src/` and zero `tests/` files changed.

## 2. Purpose

Make the gate state a true fact about the commit, remove the condition
that had been making it lie, and leave the next real failure able to
explain itself.

## 3. Background

`WP 11.1A` built this repository's first CI pipeline expressly so that
"0 Warnings/0 Errors, N/N tests passing" would stop being a manually
self-reported claim (`WP11.0A` finding R-1). `WP 11.2A` added the
governance health-check as a third, deliberately non-gating job. The
shape has been stable since: a two-leg `build-and-test` matrix, a
`governance-health-check` job, and a `gate` job that branch protection
requires and that decides by reading `needs.build-and-test.result`.

## 4. The Problem

A GitHub Actions job's conclusion folds in **every** step it ran. So
`build-and-test.result` never meant "the build and the tests passed" —
it meant "the build, the tests, **and every artefact upload** passed".

That distinction became load-bearing between 2026-08-28 and 2026-08-29,
when the account's Actions artifact storage quota was exhausted:

```
##[error]Failed to CreateArtifact: Artifact storage quota has been hit.
{ "code": "permission_denied", "msg": "insufficient usage to create artifact" }
```

Across runs `33150525673`, `33151166016` (three attempts),
`33212508984` and `33241023711` the shape is identical: `Restore` ✅,
`Build` ✅, `Test` ✅, `Publish build & test summary` ✅,
`Governance Health Check` ✅ — then `Upload build log` ❌ and
`Upload test results` ❌ on quota, so the job failed and the gate failed.

Two observations settle the diagnosis. The failures reached `main`: run
`33241023711` failed at commit `00f7f394`, an unchanged commit that had
passed as run `32170250522` eleven days earlier. And the storage was
being eaten by the pipeline itself — the Release leg uploaded
`Tempest.Desktop`'s and `Tempest.App`'s whole build output on *every push
to every branch* at 14-day retention, about 50 MB a push, for trees that
are a convenience copy and never the release mechanism.

Investigating also exposed a second, quieter defect. Run `33241023711`'s
Release leg reported a genuine `Test (Release)` failure — one test of
2,341 — and it could not be identified. The TRX naming it had failed to
upload, and the console log sat far outside the run-log API's own tail
window. A pipeline whose stated purpose is machine-verified truth could
count a failure it could not name.

## 5. The Design

- **`ADR-0117`: verification decides the gate; diagnostics never do.**
  Every artefact upload in both workflows takes
  `continue-on-error: true`. Build and test are untouched, and
  `TreatWarningsAsErrors` stays. A failed upload is still a red step —
  it simply no longer votes on whether the commit is sound.
- **Remove the cause, not just the symptom.** Build-output artefacts are
  now published from `main` and tags only, at 7-day retention, so
  feature-branch pushes stop consuming ~50 MB apiece.
- **Make failures self-identifying.** The summary step already parsed the
  TRX for counts; it now also emits every failed test's name, message and
  stack, to both the Job Summary and the console. It needs no storage
  quota and no artefact retention, so it works in exactly the conditions
  that break artefacts — which is the whole point.
- **Harden `mobile-heads.yml`** (authored in `WP 14.2A` and never once
  executed, so every assumption in it was a liability): both uploads lose
  `if-no-files-found: error`, the Android glob widens from a guessed
  `*Signed.apk` to any `.apk`/`.aab`, and both become non-fatal.
- **Disclose what was not fixed.** `TD-59` records the intermittent
  Release-configuration test — real, proven non-deterministic, and
  deliberately *not* retried, quarantined or made tolerant. `TD-60`
  records the Node 20 action deprecation the runners warn about on every
  run.

## 6. Alternatives Considered

Recorded in full in `ADR-0117`: re-running until the quota window cleared
(tried — run `33151166016` reached attempt 3 — and structurally unable to
work); deleting the uploads entirely (fixes the gate by destroying the
diagnostics `WP 11.1A` deliberately added); having `gate` inspect
step-level outcomes (GitHub exposes none to a downstream job); detecting
quota state in-workflow (a workflow cannot know its own billing state);
and reducing retention alone (slows the accumulation without addressing
that the artefacts have no consumer on a feature branch).

The one alternative worth naming here because it was *never* on the
table: making the failing test pass by retrying or skipping it. The
brief's own standing rule — and Engineering Governance §3 — forbid
weakening a test to reach green, and `TD-59` exists precisely so that
the failure stays visible until it is fixed at its source.

## 7. Why This Solution Was Chosen

Because the gate had stopped being evidence. Everything else follows
from restoring that one property: a gate that a billing counter can
redden is not reporting on the code, and a pipeline that can count a
failure it cannot name is not reporting on it either.

## 8. Architectural Principles

Verification and diagnostics are different categories of step, and only
one of them decides. Fix the cause, not the symptom. Never weaken a test
to reach green. Disclose what you did not fix, with the evidence, rather
than leaving it implied. And prefer the mechanism that works under the
failure conditions you actually observed — the Job Summary survives
exactly the outage that removed the artefacts.

## 9. Benefits

The required gate now states a true fact about the commit, on every
branch and on `main`. The recurring storage cause is removed rather than
tolerated. The next Release-configuration failure will name itself from
the run page alone, with no artefact, no download and no local
reproduction — which is what `TD-59` needs in order ever to be closed.
And two `if-no-files-found: error` traps are gone from a workflow that
had never been run.

## 10. Trade-offs

A genuinely broken upload is easier to overlook now, being amber rather
than fatal. Build-output artefacts are no longer available from
feature-branch runs. Neither costs anything a working gate does not
repay. Storage already consumed is not released by this change: GitHub
recalculates usage on its own cycle, so the first runs after this commit
may still show amber upload steps — the difference is that they will be
amber against a **green gate**.

## 11. Common Mistakes

Believing a green local run means green CI — three Work Packages'
completion reports in this train stated the suite passed locally, which
was true, while the actual GitHub Actions runs for those very commits
were red for an entirely different reason nobody had looked at. Reading
a job's conclusion as though it meant its headline steps. Re-running a
red pipeline without first reading *which step* failed. Letting a
diagnostic artefact become load-bearing for a verdict. Writing a
workflow that has never executed and treating its globs as facts. And
the one to avoid hardest: reaching for a retry when a test fails
intermittently, instead of making the failure describe itself.

## 12. Future Evolution

`TD-59` closes when the next Release-configuration failure names the
test and it is fixed at its own source — deliberately not before.
`TD-60` closes when each action is bumped to a release that natively
targets the current Node runtime, in an environment able to verify which
tags exist. If mobile heads ever become release-critical,
`mobile-heads.yml` graduates from dispatch-only to path-triggered
(`ADR-0116`), at which point its uploads deserve the same review this
Work Package gave the gating pipeline's.

## 13. Key Takeaways

A gate is a claim, and a claim is only as good as what it is actually
measuring. This one had been measuring "did the build, the tests, and
the diagnostics all succeed" while telling everyone it measured the
first two — so an exhausted storage quota, a fact about billing, was
able to say something false about the code, on `main`, at a commit that
had already passed. The fix was not to make the pipeline more tolerant
but to make it more precise: verification decides, diagnostics inform,
and the failure that could not be named now names itself.

## Observations

- The intermittent failure recorded as `TD-59` is the same class as
  `TD-46` and the same class that failed `v0.13.0`'s own tag-triggered
  `release.yml` at `Test (Release)`. `release.yml` runs its own test
  step, so `TD-59` is a live risk to the next release, not only to CI.
- `release.yml` was reviewed in this Work Package and deliberately left
  unchanged: it publishes GitHub Release assets rather than Actions
  artefacts, so the storage fault cannot reach it, and its test step
  *should* remain able to stop a release.
- Run `33129951166` shows as `cancelled` rather than failed: that is
  `ci.yml`'s own `concurrency` group with `cancel-in-progress`,
  superseding an in-flight run. Benign, and not part of this defect.
