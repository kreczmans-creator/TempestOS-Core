# WP 13.9.4 — Trust-Denial Execution Boundary Remediation

## 1. Introduction

`WP 13.9.4` is a production-code security remediation, the fourth link in
the `WP 13.9.1`–`WP 13.9.6` trust execution boundary chain, committed —
together with the whole chain — as `d7d19d4` by `WP 13.9.7`'s own
sole-integrator pass.

It closed a defect materially more severe than the multi-assembly scan
gap `WP 13.9.3` had just fixed: trust denial did not actually stop a
denied plugin's code from running. Denying a plugin excluded it from
`PluginAssemblyLoader.LoadPlugins`'s own returned list and recorded it
`PluginRegistryState.TrustDenied` rather than `Loaded` — and there the
isolation stopped. Nothing prevented the same assembly's types being
independently rediscovered, registered, and lifecycle-run through
pipelines that were, by deliberate design, entirely unaware that plugins
exist.

This retrospective was not written contemporaneously. It is reconstructed
by `WP 13.12.0` (v0.13.0 Academy Retrospective Completion) from
`d7d19d4`'s own commit message, this Work Package's own row in
`docs/releases/v0.13.0/WorkPackages.md`, `PROJECT_STATUS.md`'s retained
`WP 13.9.7` stratum, `ADR-0111`'s own "Corrected, `WP 13.9.4`" section,
and direct reads of the real, current source it produced. Every claim
below is grounded in one of those; where the record is silent, this
document says so rather than filling the gap.

## 2. Purpose

To make trust denial mean what `ADR-0111`'s Decision already claimed it
meant — that a denied plugin is isolated from execution, not merely from
one method's return value — by recording every `Type` a denied plugin's
own scan discovered, and filtering those types out at the two points
where they would otherwise enter the running platform.

## 3. Background

`WP 13.2A` introduced trust denial. `PluginTrustDeniedException`
(category 17) isolated a plugin whose manifest requested a capability
outside its tier's ceiling, or whose discovered `IModule` types had no
compliant public constructor.

Two prior facts made that isolation weaker than it appeared. First,
`Assembly.LoadFrom` runs *before* the trust checks — and `ADR-0015`
states plainly that an assembly load cannot be undone. A denied plugin's
assembly therefore remains resident in the process regardless of the
denial. Second, Module Discovery
(`ReflectionFrameworkDiscoveryService`) and Hosted Service Discovery
(`HostedServiceDiscoveryService`) are deliberately plugin-unaware per
`ADR-0110` — they scan `AppDomain.CurrentDomain` and know nothing of
manifests, tiers, or denials.

`WP 13.9.3` had, immediately before this Work Package, closed a related
but distinct gap in the *scanning* of a plugin's own transitively-loaded
assemblies. `WP 13.9.4` addresses what happens *after* a denial decision
has already been correctly reached.

## 4. The Problem

Per this Work Package's own `WorkPackages.md` row: `PluginTrustDeniedException`
isolated a denied plugin only from `LoadPlugins`'s own returned list and
from `PluginRegistryState.Loaded` — nothing stopped the plugin's
already-loaded assembly from being separately, redundantly rediscovered
by Module Discovery and Hosted Service Discovery and fully lifecycle-run.

The consequence was not merely that denied code ran. It ran with
*first-party authority*. A denied module's ambient component principal is
always `null`, and `PluginTrustPermission.IsFirstParty` treats `null` as
first-party — so a denied plugin's module, rediscovered through the
plugin-unaware pipeline, would pass every capability gate by skipping it
entirely.

Two properties of the defect made it worse than a single-scenario bug.
It was **true of every denial reason**, not only the multi-assembly case
`WP 13.9.3` had just closed. And it was **true since `WP 13.2A` first
introduced trust denial** — the mechanism had never actually enforced
what its own ADR text asserted.

## 5. The Design

Three new files, one reordering, and two filters — deliberately no new
phase, no new isolation mechanism, and no plugin awareness anywhere it
did not already exist.

**A Host-owned denied-type registry**, mirroring
`PluginComponentPrincipalRegistry`'s own already-established read/write
split exactly:
`src/Tempest.Core/Plugins/IPluginDeniedTypeRecorder.cs` (the write side,
used only from within `Tempest.Core.Plugins`),
`IPluginDeniedTypeRegistry.cs` (the read side, observed only by
`TempestHost`), and `PluginDeniedTypeRegistry.cs` implementing both. It
is constructed and held directly by `TempestHost`, never added to the
`ServiceCollection`, and never resolvable by a module or plugin —
`ADR-0017`'s boundary, applied identically to the principal registry that
preceded it.

**`EnforceTrust` reordered** in `PluginAssemblyLoader.cs` so
`DiscoverModuleTypes` runs unconditionally before *either* static trust
check — not merely ahead of the constructor-conformance check as before.
The row states the reason precisely: a capability-ceiling denial
previously threw before `DiscoverModuleTypes` had ever run, so nothing
anywhere learned which types belonged to that plugin, leaving no data a
downstream filter could key on for that denial reason.

**Two filters, entirely within `TempestHost.cs`'s own orchestration** —
at Module Registration and at Hosted Service Registration. Neither
`ReflectionFrameworkDiscoveryService`, `RuntimeModuleManager`,
`ModuleLifecycleManager`, `HostedServiceDiscoveryService`, nor
`IHostedServiceManager` gained any trust awareness; the filters live
exactly where plugin-relevant data was already being threaded through
otherwise generic machinery.

**The mid-Work-Package broadening.** This Work Package's own Adversarial
Review found its first pass — Module Registration only — itself
incomplete *before the Work Package concluded*. Module Registration and
Hosted Service Registration are two wholly independent pipelines, and a
single `Type` implementing both `IModule` and `IHostedService` could
still reach `StartAsync` unfiltered through the second. The scope was
broadened mid-Work-Package to cover both, which is why the interfaces are
named `IPluginDeniedTypeRecorder`/`IPluginDeniedTypeRegistry` rather than
`...ModuleType...`: one registry, keyed on `Type` alone, covers both
pipelines from a single recording pass.

## 6. Alternatives Considered

The record does not enumerate a formal alternatives list for this Work
Package. Two alternatives are, however, visible in what the design
deliberately did *not* do, and both are consistent with decisions already
taken elsewhere in the release.

**Unloading the denied assembly** was not available: `ADR-0015` states
the load cannot be undone, and `ADR-0110` had already rejected a separate
`AssemblyLoadContext` as the isolation mechanism on direct technical
grounds. **Making the discovery services plugin-aware** was not taken
either — it would have contradicted `ADR-0110`'s deliberate
plugin-unawareness, and the chosen design keeps that property intact by
placing the filters in `TempestHost`'s orchestration instead.

## 7. Why This Solution Was Chosen

Because it closes the boundary at the narrowest point that actually works
while leaving every architectural commitment already made in this release
untouched.

The registry is Host-owned and DI-invisible, so it cannot itself become a
capability a plugin resolves. The filters live in orchestration code that
already threads plugin-relevant data, so no generic component learns what
a plugin is. And recording *every* discovered type — rather than only the
one type that triggered the denial — matches the semantics the denial
actually has: the whole plugin is isolated, so every type reachable from
its own scan must be excluded.

## 8. Architectural Principles

- **`ADR-0110` — deliberate plugin-unawareness preserved.** The trust
  decision stays in `PluginAssemblyLoader`; the exclusion is applied by
  `TempestHost`. No discovery, registration, or lifecycle component gains
  a reference to `Tempest.Core.Plugins`.
- **`ADR-0017` — Host-owned collaborators stay out of DI.** The registry
  is never registered, mirroring `PluginComponentPrincipalRegistry`.
- **`ADR-0015` — a load cannot be undone.** The design works *with* that
  constraint rather than attempting to defeat it.
- **`ADR-0025` — plugin-scoped failures stay plugin-scoped.** Denial
  isolates one plugin; it never faults the Host.
- **Read/write split.** Nothing outside `Tempest.Core.Plugins` is ever
  handed a reference capable of mutating the registry.

## 9. Benefits

Trust denial became an execution boundary rather than a bookkeeping
outcome. Both discovery pipelines are covered by one recording pass. A
type implementing both `IModule` and `IHostedService` — the case the
mid-Work-Package review caught — is excluded from both. And the fix
generalises across every denial reason, because the reordering guarantees
the type set is known before any denial is raised.

## 10. Trade-offs

The registry is keyed on `Type` identity alone, with no notion of which
plugin caused a recording. That is what makes one recording pass cover
both pipelines, and it is also the root of a limitation later registered
as `TD-55` by `WP 13.11B` and extended by `WP 13.11C`: one plugin's
denial can suppress another assembly's module types, and an assembly
already resident when a plugin is scanned is never attributed to it. That
consequence was not identified at the time of this Work Package; it is
recorded here because it is a direct property of this design, not to
imply it was known.

The `WP 13.9.4` filters also proved insufficient on their own. They act
at *Registration*; `WP 13.9.5` found that an unattributed module type
belonging to a denied plugin was still being constructed during
*Discovery*, before either filter was consulted — closed two Work
Packages later by `WP 13.9.6`.

## 11. Common Mistakes

- **Believing an exception isolates execution.** Throwing
  `PluginTrustDeniedException` changed a return value and a registry
  state; it did not stop code running. The gap survived from `WP 13.2A`
  precisely because the denial *looked* complete.
- **Closing one pipeline and assuming the other is symmetric.** The first
  pass covered Module Registration only. Hosted Service Registration is
  wholly independent, and a dual-interface type slipped through it. The
  Work Package's own Adversarial Review caught this before commit.
- **Deferring data collection until it is needed.** The original ordering
  ran `DiscoverModuleTypes` only when the constructor check required it,
  which meant a capability denial had no type set to record. Collecting
  unconditionally is what made the fix work for every denial reason.

## 12. Future Evolution

`WP 13.9.5` reviewed this boundary and found the Discovery-time gap that
`WP 13.9.6` then closed with the `isTypeExcluded` predicate — reusing
this Work Package's own registry, unmodified. `ADR-0111` gained a
"Corrected, `WP 13.9.4` Trust-Denial Execution Boundary Remediation"
section, because the Decision's own original text had asserted that
denial "isolates the whole plugin before Module Discovery ever sees it".

Later, `TD-55` named the `Type`-keyed attribution limitation described in
§10; closing it requires per-plugin denial scoping, which is an
architectural change to this registry's own shape and remains open.

## 13. Key Takeaways

- Trust denial must be enforced where execution actually begins, not
  where the decision is made.
- Two independent discovery pipelines need two filters, and a single type
  can belong to both.
- Collect the evidence a boundary needs *before* any branch that might
  skip collecting it.
- An adversarial review inside the same Work Package caught a genuine
  incompleteness before it ever became a commit — the review-before-commit
  discipline this release applies repeatedly.
