# WP 13.11D — v0.13.0 Plugin Platform Exit Review

## 1. Introduction

`WP 13.11D` is a read-only exit review of the complete `v0.13.0` plugin
platform through `WP 13.11C`, across six fresh sub-agents:
Security/Adversarial, Architecture/Runtime, API/Compatibility,
Verification/Test and RAM-concurrency, Governance/Documentation, and WP14
UI/UX Dependency. Committed as `dea1b34` (4 files, +207/−10).

Its scope was deliberately narrow — one question only: **does anything
genuinely prevent starting WP14 UI/UX?** All six disciplines returned no
blocker, and the platform was declared **READY FOR WP14**. It changed
**zero** `src/` and `tests/` files: it implemented nothing, fixed
nothing, and created no ADR or speculative Work Package.

## 2. Purpose

To decide whether the plugin platform was in a state WP14 could safely
build on — not whether it was perfect — and to record honestly anything
found along the way, blocking or otherwise.

## 3. Background

`v0.13.0` had by this point run a long remediation chain:
`WP 13.9.1`–`WP 13.9.6` (execution boundary), `WP 13.10A`–`WP 13.10C`
(hosted service and identity, `TD-51`/`TD-52`), and
`WP 13.11A`–`WP 13.11C` (the reopened `TD-51`, its remediation, and that
remediation's own review). Each link had been reviewed, but no single
pass had asked whether the *whole* was fit to build UI on.

## 4. The Problem

Exit reviews fail in two opposite ways. They rubber-stamp — declaring
readiness because each prior Work Package said it was fine — or they
inflate, treating every open item as a reason to stop. The blocking
taxonomy in `docs/architecture/Engineering Readiness Review Architecture.md`
§4 exists precisely to remove that judgement from narrative discretion,
and this review's task was to apply it honestly in both directions.

## 5. The Design

Six independent disciplines, each given one category and the same firm
instruction: distinguish a genuine blocker from non-blocking tracked debt,
do not inflate, do not soften, and end with an unambiguous one-line
verdict. All six were read-only; every finding was independently
re-confirmed against real source centrally before anything was written.

Specific things verified rather than assumed: that `TD-51` remained
closed — all four elements of the `WP 13.11B` mechanism intact; that
`TD-52` remained closed; that `TD-55` was correctly classified, with an
escalation attempted from both of its halves and failed; that no public
API, dependency, or ADR regression existed anywhere in `v0.13.0`; and
that multi-assembly behaviour was sound.

## 6. Alternatives Considered

**Reviewing only the last change.** Rejected — the question was about the
platform's fitness as a foundation, not about `WP 13.11C`'s correctness,
which `WP 13.11C` itself had already established.

**Treating every open `TD` as a blocker.** Rejected as the inflation
failure mode §4 exists to prevent: an Open register status is explicitly
orthogonal to the blocking taxonomy.

**Fixing what was found.** Rejected by the Work Package's own read-only
instruction. `TD-56` was found and deliberately left unfixed, with its
minimum follow-up defined but not performed.

## 7. Why This Solution Was Chosen

Because "can WP14 start?" is a different question from "is this
finished?", and conflating them either blocks work that could safely
proceed or ships a foundation with an unexamined hole. Six narrow
mandates, each with a forced verdict, made the answer derivable rather
than negotiated.

## 8. Architectural Principles

- **Classification precedes conclusion.** A finding's kind is a property
  of the finding, never of the release's desired status.
- **Read-only means read-only.** Finding a genuine trust gap did not
  license fixing it inside a review.
- **Disclose, don't defer silently.** `TD-56` was registered immediately,
  with its exploitability analysis and its minimum follow-up.
- **Greenfield is not a blocker.** The absence of a plugin-facing UI
  extension point is WP14's scope to build, not a prerequisite it is
  missing.

## 9. Benefits

The platform received an unambiguous readiness verdict backed by six
independent checks. The plugin-facing UI dependency was stated plainly:
a plugin can contribute Navigation items and Commands — both
capability-gated and proven end-to-end — but **cannot contribute any
renderable UI content at all**, `NavigationItem` carrying no rendering
concern by explicit design and the real UI seams living in `Tempest.App`,
which plugin projects structurally cannot reference. First-party UI was
confirmed *not* accidentally blocked by the new capability gates.

And one genuine trust gap was caught before it could reach WP14 unnoticed.

## 10. Trade-offs

The most consequential finding was recorded as debt rather than fixed,
which leaves the platform shipping with a known fail-open path. That was
the correct call for a read-only review — but it means `TD-56`'s closure
depends on a future Work Package being commissioned, not on this one.

## 11. Common Mistakes

- **Assuming a scoped hook covers construction.** `ADR-0111`'s component
  scope was wired around each *lifecycle method*, which is exactly what
  its own wording describes — and construction was never in scope on
  either axis. Both `ModuleLifecycleManager` and `HostedServiceManager`
  create the instance *before* opening the scope, so plugin code runs
  during construction with a `null` ambient principal, which every
  capability gate treats as genuine first-party at the top trust rank.
  This became **`TD-56`**.
- **Writing a probe that cannot observe the gap.** No prior review caught
  `TD-56` because the existing `AmbientPrincipalCaptureProbe` records
  inside `StartAsync` — which *is* correctly scoped — so it passed
  regardless. A probe placed one step later than the risk proves nothing
  about the risk.
- **Reusing a governing term informally.** This Work Package graded
  `TD-56` "Release Blocking for third-party plugin support", which
  collides with §4's formal term. The underlying technical classification
  is unchanged; the correct reading for this release is **"Disclosed,
  Non-Blocking for `v0.13.0`; mandatory precondition to enabling
  third-party plugin support"**, and the same collision exists in
  `TD-51`'s historical wording.

## 12. Future Evolution

`TD-56`'s minimum follow-up is defined: move the component scope to
enclose construction on both axes — the scope key is available before
construction on each — which is a statement-ordering change within
`ADR-0111`'s existing hook rather than a new seam, paired with coverage
that probes the constructor rather than only `StartAsync`. It is graded
**Disclosed, Non-Blocking for `v0.13.0`; mandatory precondition to
enabling third-party plugin support**: dormant (`src/Plugins/` holds only
`README.md`), unreachable below `VerifiedSigned` (that tier's ceiling
admits no `plugin.services.resolve:*` key at all), causing no crash, and
orthogonal to UI work.

`TD-34` was also extended, recording a live intermittent Release-run
failure observed during this release and naming its untracked sibling
hazard.

## 13. Key Takeaways

- An exit review's job is to answer one question, not to re-audit
  everything; six narrow mandates beat one broad one.
- The gap a long remediation chain misses is usually the one every
  existing probe sits just past.
- Finding a real trust gap during a read-only review is a reason to
  register it precisely — not a licence to start fixing.
- Reusing a formally-defined governance term informally creates a
  contradiction a future reader will have to litigate; say what the
  taxonomy says, or say something else entirely.
