# WP 15.0A — Desktop Shell Brand Recovery & Windows Startup Crash Fix

## 1. Introduction

`WP 15.0A` covers two commits merged directly to `main` immediately after
the `v0.14.0` tag, under the author's own ad hoc `WP-Z4 Stage 27`/`Stage
28` labels: `cd68077` (Desktop shell brand recovery) via merge `6c25a1f`,
and `91cdbff` (the Windows startup crash fix) via merge `e21be67`. Neither
carried a real Work Package number, a `WorkPackages.md` row, a TD entry,
or an Academy retrospective at the time. This retrospective, and the
`WP 15.0x` numbering, were both assigned retroactively by `WP 15.1A`
(`v0.15.0` Release Preparation) — see §12.

## 2. Purpose

To bring `Tempest.Desktop`'s visual chrome into alignment with the
`Tempest.Companion` brand, and to fix a real, severe defect: the Desktop
application crashed on startup on Windows.

## 3. Background

Phase 1 of a post-`v0.14.0` UI audit found no unmerged `Tempest.Desktop`
UI work on any branch or worktree; the only recoverable brand work was
`Tempest.Companion`'s own alignment (`WP 14.1A`,
`origin/claude/tempestos-companion-mobile-ubznt3`) — verbatim mark/lockup
geometry, the Chakra Petch/Space Mono type faces, and the brand asset
set. `FCR-0092` is cited in the shell's own commit message and in
`docs/design/Tempest Engineering Design System Reference.md` as the
finding this closes. **Verified defect in this citation, disclosed here,
not fixed**: `FCR-0092` does not exist in this repository's own `Future
Capability Register.md` (`FCR-0001`–`FCR-0088`, confirmed by direct
count). `Tempest.Companion` is described in the same design-system
document as living "on its own branch" — the most likely explanation
(**Inferred**, not confirmed: the Companion branch was not reviewed by
this Work Package) is that `FCR-0092` belongs to the Companion's own,
separately-numbered capability sequence, cited here without translation.
Not a release blocker; a cross-reference this register does not resolve.

## 4. The Problem

Two independent problems, one commit each:

1. **Brand drift.** `Tempest.Desktop`'s theme, icon set and chrome had
   not been realigned with the Companion's own design-system reference.
2. **A real startup crash on Windows.** `WorkspaceLayoutController.
   RestoreAsync` awaited a Core settings read with `ConfigureAwait(false)`
   and then called `Load(tree)` directly. Once that read genuinely
   completes asynchronously — reliably the case on Windows — the
   continuation resumes on a thread-pool thread, and `Load` synchronously
   drives the visual tree (`Adopt` → `Host.Update` → `HideFlyout` →
   `Visual.IsVisible`). Every `AvaloniaObject` read there calls
   `Dispatcher.VerifyAccess`, throwing `"Call from invalid thread"` off
   the UI thread. The one caller awaited this from the `async void
   Window.Opened` handler, so the throw was unhandled and killed the
   process moments after the window appeared.

## 5. The Design

**Brand recovery** (`cd68077`): `BrandPalette` (tokens + theme-reactive
semantic keys, dark-first instrument/paper), `TempestTheme` (Fluent
`ColorPaletteResources` for both variants, squared corners, type scale,
selection, inputs, focus ring), `ChromeStyles` (flat/subtle/primary/
danger button treatments), `DesignTokens` realigned (type roles,
tracking, radii, shell geometry), `Branding/` (verbatim mark/lockup
geometry transcription), `Icons/IconGeometry` (the monochrome vector set
replacing colour emoji), `Assets/` (brand PNGs, app icon, `.ico`;
Chakra Petch/Space Mono under OFL; Inter via `Avalonia.Fonts.Inter`).
59 files, +3,863/−652.

**Crash fix** (`91cdbff`): `ConfigureAwait(false)` is kept — the Core
call has no UI affinity and should not pay for a context capture. The
tree is now built off the UI thread (`DropUnknownPanels` touches no UI
state) and only `Load` is marshalled, using the same `CheckAccess`/
`Invoke` shape `ThemeService` already established for this exact class of
problem.

## 6. Alternatives Considered

Reinventing the brand chrome from the design brief directly, rather than
recovering the Companion's own verbatim assets — rejected: the Companion
had already solved brand alignment once, and re-deriving it independently
risked a second, divergent interpretation of the same mark.

For the crash: marshalling the entire `RestoreAsync` continuation back to
the UI thread at its call site, rather than only `Load` — rejected as
broader than the actual defect; `DropUnknownPanels` has no UI affinity
and does not need it.

## 7. Why This Solution Was Chosen

The brand chrome already existed, tested and shipped, in the Companion;
recovering it is lower-risk than re-designing it. The crash fix follows
`ThemeService`'s own already-established `CheckAccess`/`Invoke` idiom
rather than introducing a second pattern for the same problem class.

## 8. Architectural Principles

UI-thread affinity is a Desktop-local concern; `Tempest.App`/`Tempest.
Core` remain dispatcher-free, unchanged by this fix — the same boundary
`ADR-0119` (`WP-Z2`, `TD-117`) later formalised for `UndoRedoStack`.

## 9. Benefits

The Desktop application launches and runs on Windows without crashing;
the shell now carries the intended brand identity rather than a
placeholder theme.

## 10. Trade-offs

**A stated evidence limitation** (per `WP-Z3`'s own precedent, §12,
below): no Stage 1 audit report for either commit exists in the
repository — this retrospective is derived from the commits' own
messages and diffs, not from a preserved investigation record.

## 11. Common Mistakes

**Awaiting with `ConfigureAwait(false)` and then touching UI state
directly in the continuation.** The `false` is correct for the awaited
call; the mistake is assuming the *caller's* thread, not the callee's
configuration, controls where execution resumes.

## 13. Key Takeaways

- A verbatim asset recovery from a sibling product is lower-risk than a
  re-derivation, provided the sibling's own work is itself verified.
- `ConfigureAwait(false)` describes the *awaited call's* continuation
  behaviour, not a blanket exemption from UI-thread rules downstream.
- An FCR citation that does not resolve in this repository's own register
  is worth disclosing even when it is not this Work Package's to fix.
