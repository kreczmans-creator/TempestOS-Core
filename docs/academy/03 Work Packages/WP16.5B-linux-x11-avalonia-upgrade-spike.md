# WP 16.5B — Linux/X11 Avalonia Upgrade Spike

## 1. Introduction

`WP 16.5B` (commit `309c15d`, merged as `1fc6954`) is a timebox-bounded,
one-day spike against `TD-116` — the Linux/X11 `TypeLoadException` that
kept `Tempest.Desktop` from launching at all under X11 — with a
documented fallback if the timebox ran out before a fix was found:
state the platform-support matrix honestly instead of forcing a fix.
The spike succeeded: Avalonia `11.2.3` → `11.3.20`, `Tmds.DBus.Protocol`
`0.94.2` → `0.21.3`, a clean 0-warning/0-error build, both full test
suites green, and a real `xvfb-run` launch that starts, initialises
every service, and runs until deliberately terminated. Its full account,
with verbatim reproduction and verification transcripts, is `docs/
releases/v0.16.0/WP16.5B Linux Launch Spike Report.md`. This
retrospective is written under `WP 16.2C`, sourced from that report,
`309c15d`, and the Technical Debt Register's `TD-116` row as re-derived
by the `v0.16.0` review board on 2026-09-05.

## 2. Purpose

Spend exactly one day finding out which of `TD-116`'s two competing
remedies actually works — revert the deliberate `Tmds.DBus.Protocol`
security pin, or find a newer Avalonia that binds against a patched
version — and turn the debt from "open, undecided" into a closed,
evidenced answer either way.

## 3. Background

`TD-116` was a deliberate, documented trade: `Tempest.Desktop.csproj`
pinned `Tmds.DBus.Protocol` to `0.94.2` to remediate advisory
`GHSA-xrw6-gwf8-vvr9`, but `0.94.2` no longer presents the type
`Avalonia.FreeDesktop 11.2.3`'s own `X11DBusImeHelper.DetectAndRegister()`
binds against — a `System.TypeLoadException` thrown during platform
initialisation, before any window exists, on Linux/X11 only. Windows and
macOS were unaffected because neither initialises the FreeDesktop/X11
path, and the entire `Tempest.Desktop.Tests` suite passed regardless
because `Avalonia.Headless` never initialises X11 either — which is
precisely why nothing in the repository had noticed until the debt was
found by direct, deliberate reproduction.

## 4. The Problem

Two remedies traded against each other with no clear winner recorded:
revert the security pin (restoring the crash's precondition on the
advisory the pin was meant to close) or find a version of
`Tmds.DBus.Protocol` that is both patched and binary-compatible with
`Avalonia.FreeDesktop`'s compiled IL, which binds by member layout, not
by semantic version. `D-025` (Proposed, `WP 16.0A`) made the v1.0
platform matrix's Linux clause depend directly on this spike's outcome.

## 5. The Design

The crash was reproduced first, verbatim, exactly as `TD-116` describes,
before any fix was attempted — the same `System.TypeLoadException` on
`Tmds.DBus.Protocol.Connection`, `SIGABRT`, exit 134. Research into the
NuGet nuspecs and osv.dev found that `0.21.3` and `0.92.0+` are both
listed as fixed for the advisory but sit on two different API lines:
`0.21.3` backports the fix onto the pre-rewrite `0.2x` line —
the same member layout the code already binds against — while `0.92.0+`
belongs to a rewritten `0.9x` line. `0.94.2` (the pre-upgrade pin) was
patched but on the wrong line, which is `TD-116` in one sentence;
`0.21.3` is patched and on the right one. Avalonia was upgraded to
`11.3.20` (the newest 11.x whose `Avalonia.FreeDesktop` raised its own
floor to `Tmds.DBus.Protocol >= 0.21.3`) across all four Avalonia
packages plus the test project's `Avalonia.Headless.XUnit` reference,
and `Tmds.DBus.Protocol` was repinned to `0.21.3` directly, with the
full reasoning recorded in the `.csproj`'s own comment next to the pin.

## 6. Alternatives Considered

**Reverting the `Tmds.DBus.Protocol` pin to `0.20.0`** (the pre-`TD-116`
version). Rejected — this is the remedy that reopens `GHSA-xrw6-gwf8-vvr9`,
the exact risk the pin exists to close; the spike's own job was to find
whether the *other* remedy worked before accepting that trade.

**Migrating `ProjectExplorerView`'s drag/drop to Avalonia 11.3's new
`DataTransfer`/`DataFormat<T>`/`DoDragDropAsync` API** immediately, once
the upgrade surfaced it as an obsolete-API compile break. Rejected within
this Work Package's own scope — `DataFormat<T>` has no built-in `Guid`
format for the id this code drags, so adopting the new API means
designing a custom serializer and rewriting every read/write site, which
is a real redesign, not the "small, obvious edit" a one-day timebox
against `TD-116` specifically is scoped for. The old API is deprecated,
not removed, and remains fully functional; the four call sites were
narrowly suppressed (`#pragma warning disable CS0618`) with a comment
naming the reason, no behaviour change, and the migration is disclosed
as new, real debt for a future Work Package.

## 7. Why This Solution Was Chosen

`0.21.3` is the lowest version that is simultaneously patched against
the advisory and binary-compatible with `Avalonia.FreeDesktop`'s current
build — the direct, minimal pin that closes the debt without also
requiring a rewrite of `Avalonia.FreeDesktop` itself or accepting the
advisory's risk again.

## 8. Architectural Principles

A one-day timebox with an explicit, pre-declared fallback (state the
matrix instead of fixing it) is itself the risk-management design this
Work Package embodies — the timebox was met with a genuine fix rather
than the fallback, but the fallback's existence is what made starting
the spike a bounded, acceptable risk rather than an open-ended one. No
ADR was produced; a dependency-version pin chosen for binary
compatibility, with the full reasoning recorded directly in the
`.csproj`'s own comment, does not meet Governance §5's bar for a
separate architecture record.

## 9. Benefits

`TD-116` moved to Resolved. `PHYSICAL_REVIEW.md` §8 and the platform
support matrix now state Linux as launching rather than unsupported.
One genuine, unrelated Avalonia 11.3 headless-layout behaviour
difference was found and fixed along the way — a test asserting
`Visual.Bounds` immediately after `Measure`/`Arrange` observed a
zero-sized rectangle because part of the layout pass is now queued onto
the dispatcher under 11.3; fixed with the repository's own established
`Dispatcher.UIThread.RunJobs()` drain, already used in two other test
files, with no assertion weakened.

## 10. Trade-offs — what one `xvfb-run` launch does and does not prove

**The entire positive verdict rests on one local, `Xvfb`-based launch.**
The report is explicit about this rather than letting the green result
read as more than it is: `Xvfb` is a virtual framebuffer, not a real
X11 or Wayland desktop session, and no real X11/Wayland or macOS run was
performed at all — the report's own §9 states this outright as
something deliberately not done, within scope. A `linux-launch-smoke`
CI job was added to `ci.yml`, but it is **advisory** — deliberately not
added to `gate`'s `needs:` list — specifically because it "has not yet
accumulated a track record of real CI runs" at the moment it was
written. That caveat has since hardened into something worse than
merely "not yet accumulated": **GitHub Actions on this account has been
unable to obtain a runner since 2026-09-04 22:34 UTC**, confirmed
independently by `WP 16.0B`'s own disclosure of the identical outage on
a different push. The advisory job that was meant to start accumulating
real CI evidence has instead accumulated none at all — not because it
failed, but because it has not run. The `v0.16.0` review board's own
2026-09-05 re-derivation of the `TD-116` row makes exactly this
correction: it hedges the row's own claim to match the report precisely
and marks the `D-025` citation Proposed, specifically because an earlier
reading of this Work Package's result risked overstating it. **What this
evidence does establish**: the code path that crashed under X11
initialisation now completes a full startup and shutdown cycle,
including 60 DI registrations, module discovery, and binding a REST
listener, with no exception anywhere in its output. **What it does not
establish**: that a real X11 session, a Wayland compositor, or any CI
runner behaves identically — those remain unverified, by the report's
own account, not by omission this retrospective is adding after the
fact.

**A second, smaller but genuinely disclosed finding**: the process did
not end promptly on a plain `SIGTERM` in testing — the launch harness
had to escalate to `SIGKILL` after a ten-second grace period to get a
deterministic exit code at all. The report suspects, but did not
root-cause within the timebox, that this involves the ASP.NET Core
generic host's own shutdown handling rather than anything `TD-116`'s fix
touched — disclosed as a real, open question for a future Work Package
rather than quietly worked around by the CI job's own choice to treat
both exit codes as success.

## 11. Common Mistakes

**Reading "the spike succeeded" as "Linux is now as verified as
Windows."** The report itself never claims this, and the review board's
own later correction to the `TD-116` row exists specifically because an
earlier statement of the result had drifted toward that stronger
reading. A single local `xvfb-run` launch and zero real CI runs behind
an advisory smoke job is real, valuable evidence that the crash is
fixed — it is not the same evidentiary weight as `windows-2022`'s own
CI-verified leg, and treating the two as equivalent would be exactly the
kind of documentation-ahead-of-reality drift this release exists to end.

## 12. Future Evolution

`linux-launch-smoke` is a candidate for promotion into `gate`'s required
checks once it has actually accumulated a track record of real CI
runs — which cannot happen while this account's runners remain
unavailable, a condition entirely outside this Work Package's control.
The `ProjectExplorerView` drag/drop migration to Avalonia 11.3's new
`DataTransfer` API is disclosed, real debt for whichever Work Package
next touches that view or performs a general Avalonia API-currency
pass. The `SIGTERM`-does-not-end-the-process behaviour is worth its own
investigation if TempestOS is ever daemonised or run under a process
manager expecting a clean shutdown on Linux.

## 13. Key Takeaways

- A timeboxed spike with an explicit, pre-declared, acceptable fallback
  is what makes starting it a bounded risk — and it is worth recording,
  after the fact, exactly how close the actual outcome sat to that
  fallback rather than only celebrating that the harder path succeeded.
- A dependency crash that a security pin caused is not always fixed by
  reverting the pin — the two versions marked "fixed" for the same
  advisory can sit on incompatible API lines, and the real fix is the
  one that is both patched and binary-compatible with what already binds
  against it.
- Advisory CI jobs exist to accumulate a track record before being
  trusted as a gate — and a track record cannot accumulate while the
  runners themselves are unavailable, which means this Work Package's
  own promotion path is currently blocked by something no engineering
  decision can fix, not by anything left undone in the spike itself.
