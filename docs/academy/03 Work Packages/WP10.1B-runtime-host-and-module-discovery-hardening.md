# `WP 10.1B` — Runtime Host & Module Discovery Hardening

## 1. Introduction

`v0.10.0`'s fourth Work Package — the first this release to be a pure
hardening/root-cause pass rather than a new discipline or new UI
surface, commissioned specifically to investigate and resolve `TD-26`
and `TD-37`.

## 2. Purpose

To determine the true root cause of two previously-disclosed, previously-
only-mitigated Technical Debt items, fix each at its own actual source,
and guarantee deterministic module discovery/registration/initialisation,
no duplicate registrations, correct module isolation, and stable
startup/shutdown/restart — directly, with named tests, not by assertion.

## 3. Background

`TD-26` (`WP 9.0A`) and `TD-37` (`WP 10.1A`) had each already been
mitigated once, in `Tempest.Desktop`, without ever being fixed at their
own true source or, for `TD-37`, fully root-caused at all. This Work
Package's own controlling instruction named both explicitly and asked
for genuine resolution, not a third mitigation.

## 4. The Problem

Read real source, not the register's own prior descriptions alone;
determine whether `TD-37`'s own remaining candidate explanation
(double-invocation) held up; find the actual mechanism if it did not;
fix both items at their true owning layer; prove the fix with tests
that would have failed before it.

## 5. The Design

`WorkspaceManager.StartAsync` now waits for
`IDiagnosticsProvider.HostState == HostState.Running`, not merely
`Services != null` — `TD-26` fixed at its own source for the first
time. `TD-37`'s double-invocation candidate was directly disproved by
re-reading `ModuleLifecycleManager`; the real mechanism — durable,
cross-launch persistence colliding with fixed, literal sample-module
identifiers — was found via direct file-system evidence in the test
project's own build output. Each of the four affected
`Tempest.Samples` modules now checks first and skips idempotently;
`Tempest.Desktop.Tests` gained genuine per-test persistence isolation,
mirroring `Tempest.Core.Tests`' own established pattern.

## 6. Alternatives Considered

See `22-runtime-host-restart-stability.md` §6 — re-mitigating `TD-26` a
third time; changing `PersistenceStore`'s own production default root
path; fixing `TD-37` inside `EngineeringObjectFactory<T>` (an
Engineering Domain change, out of scope). All rejected in favour of the
narrower, correctly-scoped fixes actually applied.

## 7. Why This Solution Was Chosen

Both fixes needed to satisfy "No Engineering Domain changes / No
Workspace contract redesign / No UX redesign" simultaneously with
"determine the true root cause." Fixing at the actual owning layer
(`WorkspaceManager`, `Tempest.Samples`) was the only approach
satisfying every constraint at once.

## 8. Architectural Principles

A mitigated symptom is not a resolved cause; durable-by-design
persistence has real consequences for code that assumes an empty
store; idempotency, not fragility, is the correct contract for seed
data; scope boundaries survive even a visible, nearby, cheaper-looking
fix (`TD-38`).

## 10. Trade-offs

On the idempotent-skip branch, a sample module's own `Sample*Id`
properties are left honestly unset rather than recovered from the
durable store — no lookup-by-business-identifier capability exists to
recover them, and building one was judged disproportionate. `TD-38`
remains open by deliberate scope boundary, not oversight.

## 11. Common Mistakes

Treating a working mitigation as evidence the underlying cause is
understood; assuming a "module fails initialisation" symptom must live
inside the module pipeline itself, rather than one layer below in how a
Platform Service's own durable constraint interacts with data that
assumed it wouldn't exist yet; fixing a visible, related defect found
mid-investigation without checking it falls inside the current Work
Package's own scope.

## 12. Future Evolution

A dedicated Engineering Domain Work Package could resolve `TD-38`
directly. `WP 10.2A` is the next named candidate per this Work
Package's own closing instruction.

## 13. Key Takeaways

"Determine the true root cause" is a real, distinct instruction from
"mitigate again" — honouring it required reading real source end to
end, empirically ruling candidate explanations out (not merely judging
them plausible or implausible), and placing each fix at its true
owning layer even when a nearby, related finding tempted scope creep.

## Architectural Debt Assessment

One new, genuine, disclosed finding: `TD-38` —
`EngineeringObjectFactory<T>` enforces no business-identifier
uniqueness of its own, so sample modules built directly on it (not
routed through Materials'/Requirements' own separate durable indices)
silently duplicate their own object graph on every restart, invisible
to any Workspace read once their own process exits
(`IEngineeringObjectRepository` is in-memory-only, `WP 8.2C`'s own
original, unchanged scope decision). Not fixed here — both candidate
resolutions are genuine Engineering Domain changes, explicitly out of
this Work Package's own scope. `TD-26` and `TD-37` both fully resolved,
not merely reconfirmed a further time.

## Observations

- **A register entry that already rules out two explanations is doing
  real work — trust it, and finish the third.** `TD-37`'s own prior
  disclosure had already eliminated cross-test contamination and a
  retry mechanism; this Work Package only needed to rule out the one
  remaining candidate (double-invocation) and then look further, not
  start from nothing.
- **Direct file-system evidence settles a root-cause question that
  code-reading alone leaves ambiguous.** Finding `SAMPLE-MAT-001`
  already present on disk, before triggering any deliberate second
  launch, was the single piece of evidence that turned "most plausibly
  invoked twice" into a confirmed, different, and correctly-fixed root
  cause.
- **The same investigation that resolves one item can — and should —
  surface a new one, disclosed and correctly scoped, rather than
  either ignored or absorbed into the current fix.** `TD-38` is exactly
  that: found for free while fixing `TD-37`, registered honestly,
  deliberately left for a Work Package whose scope actually permits
  fixing it.
