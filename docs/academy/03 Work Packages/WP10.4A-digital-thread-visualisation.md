# `WP 10.4A` — Digital Thread Visualisation

## 1. Introduction

`v0.10.0`'s own ninth Work Package — a graphical Digital Thread viewer
over the existing Engineering Domain: an interactive, progressively-
expandable node-link graph realising `ADR-0093`, built entirely as a
presentation layer over already-existing, already-permitted reads.

## 2. Purpose

Implementation retrospective, mirroring `WP10.3A`/`WP10.3B`'s own
two-part (Concept Guide, Implementation Retrospective) structure. See
`27-digital-thread-visualisation.md` for the design narrative; this
file focuses on what was built, files touched, and honest disclosure of
this Work Package's own genuine finding.

## 3. Background

Commissioned directly after `WP 10.3B` (Ribbon, Toolbar & Command
Experience) closed with "await Product Owner instruction before
`WP 10.4A`." This Work Package's own controlling instruction named
nineteen scope items and named `ADR-0093` directly ("Honour
`ADR-0093`") — the first `v0.10.0` Work Package to explicitly want a
Digital Thread graph, reversing every prior Work Package's own
"No Digital Thread graph" exclusion (`WP 10.2A`, `WP 10.2B`, `WP 10.3A`,
`WP 10.3B`), the identical "genuine, disclosed reversal" pattern
`WP 10.3B`'s own ribbon already established for "No ribbon" one release
earlier — except here a governing ADR (`ADR-0093`) already existed
before this Work Package began, authored specifically during
`WP 10.0A` to authorise exactly this graph once built.

## 4. The Problem

See `27-digital-thread-visualisation.md` §4 — `ObjectEditorView`'s own
flat Relationship summary (`WP 10.3A`) is correct and honest, but a
Digital Thread genuinely is a graph; following a chain of relationships
across several hops meant repeatedly re-opening a new editor tab at
every step.

## 5. The Design

See `27-digital-thread-visualisation.md` §5. In summary:
`DigitalThreadGraphModel` (new, `Tempest.Desktop.DigitalThread`) — a
pure, Avalonia-free graph state/algorithm class over the identical
bidirectional relationship read `ObjectEditorView` already established,
with a dedicated `TD-32` merge for Verification results;
`DigitalThreadGraphView` (new, same namespace) — a `UserControl` that
is also directly its own `IWorkspaceView`, rendered as a Document Area
tab, never a new dock slot. One genuine defect found and fixed before
commit — see §12.

**One genuine, disclosed finding, fixed before commit:**

1. **`DigitalThreadGraphModel.JumpToBreadcrumb`'s own breadcrumb-not-
   emptying bug** — the original implementation cleared the target
   breadcrumb entries, then called the same `Recentre` path forward
   navigation uses, which unconditionally re-pushed the centre being
   left — so jumping back to an earlier centre never actually emptied
   the trail. Found by this Work Package's own test suite
   (`JumpToBreadcrumb_ReturnsToThePriorCentre_TruncatesForwardHistory`),
   before any commit, fixed by splitting the shared rebuild logic into
   `BuildGraphAround` with an explicit
   `pushCurrentCentreToBreadcrumb` flag.

**A second, disclosed, pre-existing gap found in the process, not
introduced here**: independently re-proving the `TD-32` merge (Security
Review §3) required confirming, directly, that `ObjectEditorView`'s own
Relationship summary (`WP 10.3A`) shares the identical "verifiedBy"
blind spot — a genuine, previously-undisclosed fact about already-
shipped code, found only because this Work Package needed to prove its
own merge was solving a real, current gap, not a stale one.

## 13. Key Takeaways

Nineteen named scope items realised via two new, small, layered classes
(a pure model, a rendered view), zero new Workspace/Domain/Runtime
surface, zero new traversal mechanism; the deliberate choice to reuse
`ObjectEditorView`'s own bidirectional relationship read over
`IEvidenceComposer` proved, independently, to be the more complete
choice, not merely the more convenient one; one genuine defect found
and fixed before commit, plus a second, pre-existing gap disclosed as a
byproduct of proving the fix for the first was real.

## Architectural Debt Assessment

## Observations

**A rendering-layer Work Package can still close the loop on a
data-layer disclosure two releases old.** `WP10.0A`'s own architecture
document, written at the start of this release, explicitly predicted
that `TD-32`'s disposition would need revisiting "when a future
implementation Work Package actually builds this graph view" — and
named the exact trigger condition precisely enough that, five Work
Packages later, this one could act on it directly, without
re-discovering the underlying gap from scratch. A well-written, disclosed
trade-off with a named revisit trigger remains useful arbitrarily far
into the future, not just at the moment it was written.

**The same "found only because a later Work Package needed the
identical case honestly" pattern `WP 10.3B`'s own Observations section
named recurs a fourth time.** `WorkspaceDockPosition.Bottom`,
`ReviseMechanicalObjectCommand`, `CommandPaletteOverlay`'s silent
no-op, and now `ObjectEditorView`'s own shared `TD-32` blind spot all
share the identical shape: a real gap that sat, compiled and
untested against the specific failure mode, until a later Work
Package's own different feature needed to answer the same question
honestly for itself.
