# WP 15.2A — Desktop Test Suite Persistence Root Cleanup

## 1. Introduction

`WP 15.2A` closes `TD-120`: the Desktop test suite creates a fresh,
isolated persistence-store directory per test and never deletes any of
them, so a machine running the suite repeatedly fills its own disk.
Identified as the correct next Work Package by independently inspecting
the repository at `main` (`5165e3f`, `v0.15.0` released and published) —
not assumed from any prior roadmap.

## 2. Purpose

Stop the Desktop test suite from accumulating one leftover directory per
test, forever, without weakening the test isolation `TD-37` (`WP 10.1B`)
established that isolation for in the first place.

## 3. Background

`TD-120` was found and disclosed by `WP-Z4` Stage 13 (2026-09-02) during
`v0.14.0`'s own release verification: running the Desktop suite six
times over exhausted the container's disk, and the third repetition
failed en masse with `No space left on device` — a genuinely misleading
failure mode, since it looked like a correctness regression and was
actually starvation. `WP-Z4` deliberately left it open, its own scope
being documentation only. It stayed open through `v0.15.0`.

## 4. The Problem

`WorkspacePersistenceCollection.NewIsolatedPersistenceRootPath()`
returns a fresh path directly under the OS temp folder, once per test —
correctly, since a shared path would let test *N* observe test
*N-1*'s already-seeded data within the same run. Nothing ever deleted
any of them. Re-confirmed empirically at the start of this Work Package,
not merely read from the register: this session's own `/tmp` already
held 6,786 such directories from prior runs.

A second, adjacent gap surfaced while implementing the fix:
`ResponsiveWorkspaceTests` builds three real `WorkspaceHost` instances
via the same method but carried no `[Collection(...)]` attribute at
all — the only one of 40+ call sites that didn't. It ran in its own
unserialised collection, exposed to the same process-wide
headless-dispatcher hazard the collection exists to prevent, and its own
three directories would not have been covered by any collection-scoped
cleanup.

## 5. The Design

Every isolated root now lives under one shared, per-process parent
directory (`WorkspacePersistenceCollection.RunRootPath`, generated once
when the class loads). A new `PersistenceRootCleanupFixture`, wired to
the "Tempest.Desktop WorkspaceHost persistence" collection via xUnit's
own `ICollectionFixture<T>`, deletes that entire parent directory once,
in its own `Dispose()` — which xUnit calls only after every test in the
collection has finished, the same point at which no test could still be
using its own subdirectory. `ResponsiveWorkspaceTests` joined the
collection, closing both gaps with one change.

The actual recursive-delete mechanism is factored into a small, directly
testable static helper (`TestTempDirectoryCleanup.
TryDeleteDirectoryRecursively`) so it can be proven against a throwaway
directory a test creates and owns itself — deleting the real, live
`RunRootPath` to prove the mechanism works would risk deleting a
directory a concurrently running test still needs.

## 6. Alternatives Considered

**Per-test cleanup** (each test deletes its own root in a `finally`
block or `IDisposable`) — rejected: would require touching every one of
40+ call sites individually, a far larger and riskier change for the
same outcome, and does not by itself resolve `ResponsiveWorkspaceTests`'
own missing serialisation.

**Special-casing failed tests to keep their own directory for
diagnosis** — rejected: xUnit v2 collection fixtures have no visibility
into individual test outcomes, and an ordinary assertion failure already
carries its own message and stack trace, so it does not need its
directory preserved to be diagnosable.

## 7. Why This Solution Was Chosen

A collection fixture is the one lifetime that is guaranteed to run after
every test in the collection has finished and never before — exactly the
guarantee this fix needs, using a mechanism xUnit already provides
rather than inventing new test-lifecycle machinery.

## 8. Architectural Principles

Test infrastructure only. No production (`src/`) file was touched, no
public contract changed, no ADR required — a test suite's own cleanup
discipline is not a platform architectural decision.

## 9. Benefits

A machine running the suite many times over — exactly what release
verification requires — no longer accumulates disk usage across runs.
The one situation that still leaves a directory behind (a crash, a
disk-exhaustion kill, a forced interrupt before normal teardown runs) is
also the one situation a real post-mortem would want evidence for, which
the design serves without tracking pass/fail state at all.
`ResponsiveWorkspaceTests` is no longer exposed to unserialised
parallel execution against process-wide Avalonia dispatcher state.

## 10. Trade-offs

This fix prevents new accumulation; it does not retroactively clean the
6,786 stray directories this session's own prior runs already left
behind — a one-time environment cleanup, disclosed rather than silently
left implied as done.

## 11. Common Mistakes

**Assuming a static helper method's own call sites are uniform without
checking.** Forty-plus files called `NewIsolatedPersistenceRootPath()`
consistently with the collection attribute; the one exception was found
only by checking every call site directly (`grep`, not sampling), not by
assuming consistency from the pattern's own popularity.

## 12. Future Evolution

Whether `Tempest.Core.Tests` has an analogous leftover-directory pattern
of its own is genuinely Unknown — `TD-120` named the Desktop suite
specifically, and `Tempest.Core.Tests` already gives every host
construction a fresh, isolated root per `WP 7.3A`'s own precedent, but
this Work Package did not independently re-verify that suite for a
cleanup gap of its own. Recorded here as a real, disclosed candidate for
a future Work Package, not investigated further within this one's own
bounded scope.

## 13. Key Takeaways

- A collection fixture's `Dispose()` lifetime — guaranteed to run after,
  never before, every test in the collection — is the right tool for
  "clean up once the whole group is done," not a per-test `finally`.
- Factor a destructive operation (recursive delete) into something a
  test can exercise against a throwaway target, never against the real,
  live resource other concurrent tests depend on.
- Checking every call site of a shared helper directly, not sampling a
  representative few, is how a real outlier gets found.
