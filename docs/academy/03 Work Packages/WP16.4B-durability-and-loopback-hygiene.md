# WP 16.4B — Durability & Loopback Hygiene

## 1. Introduction

`WP 16.4B` closed five Technical Debt rows across three parallel
streams, all cut from `feature/v0.16.0` at `9606d21`: `WP 16.4B-1`
(`feature/v0.16.0-wp16.4b-rest`, `d2f2de3`) gated the OpenAPI document
route behind identity and permission (`TD-62`) and put the REST
listener off by default (`D-024`, Proposed); `WP 16.4B-2`
(`feature/v0.16.0-wp16.4b-platform`, `486a662`) closed a keyed-lock
leak (`TD-68`) and two latent DI container defects (`TD-69`);
`WP 16.4B-3` (`feature/v0.16.0-wp16.4b-durability`, `bdba379`, plus a
follow-up correction at `8fff32a`) closed `TD-97` in full and `TD-67`
partially. An integration commit (`3489c12`) wired the three new
reconciliation services into `TempestHost` — they had landed as
constructible types with no registration, which would have left
`TD-67`'s own "no reconcile path exists" complaint exactly as open as
it started — and the whole line merged at `f1a8e33`.

This retrospective also records what the three streams' own reports
could not: `WP 16.4B` shipped a data-loss defect. The attachment
reconciliation sweep this Work Package built could permanently delete a
file while a user was in the middle of attaching it, while the object's
own metadata went on claiming the file existed — and `TD-97` was marked
**Resolved** against exactly that code. The `v0.16.0` review board found
it; `WP 16.4B-R2`, a separate remediation Work Package outside this
retrospective's own scope, closed it. A retrospective for the Work
Package that shipped the release's most serious defect would not be
honest if it treated that defect as someone else's story.

## 2. Purpose

`v0.16.0 Release Plan.md` §`WP 16.4B` states the objective directly:
"the 'no consequence yet realised' items stop relying on there being no
users." Concretely, the plan's own acceptance line asked for, among
other things, "`TD-67`: a write-intent marker before multi-file writes
and a startup sweep that reports orphans" and "`TD-97`: attachment
content is released when its last referencing object is deleted, plus
the same sweep." Under `D-024` (Proposed), the REST listener's default
state and the OpenAPI document's own authorization were folded into the
same Work Package because both are "no consequence yet realised" items
in the identical sense — a loopback-only listener with no real users
yet, rather than a durable-state defect with no real users yet.

## 3. Background

Five defects, from two independent 2026-08-28 reviews (persistence;
architecture; security), each already fully characterized in the
Technical Debt Register before this Work Package began:

- **`TD-67`** named five separate defect shapes under one row: crash-window
  write ordering in `EngineeringDocumentStore.CreateAsync`; a
  document-then-index ordering in `MaterialCatalog.RegisterAsync`/
  `RequirementsService.Create*` with no reconcile path; a partial
  evidence graph in `VerificationService.RecordAsync`; `MoveToGroupAsync`/
  `MoveGroupAsync` allegedly appending `GroupedUnder` references without
  removing prior ones; and `MoveGroupAsync` checking neither parent Kind
  nor ancestry cycles.
- **`TD-97`** — nothing collected orphaned attachment content: deleting
  an engineering object left its attachments' bytes in the store, and a
  crash between the content write and the metadata write left a record
  nothing referenced.
- **`TD-68`** — `AsyncKeyedLock.GetOrAdd` created one `SemaphoreSlim` per
  key and nothing ever removed an entry; five independent call sites
  leaked one semaphore per distinct key for process life, and the
  double-dispose guard was a plain `bool`, not `Interlocked`.
- **`TD-69`** — the DI container's `ServiceCollection.Add`/`AddInstance`
  silently overwrote an existing registration for the same service type
  (last-wins, no exception, no log), and `TempestServiceProvider.Construct`
  resolved every constructor parameter unconditionally, never honouring
  `ParameterInfo.HasDefaultValue`.
- **`TD-62`** — the REST API's OpenAPI document route disclosed the
  complete route→required-permission map to any unauthenticated loopback
  caller, with `RestApiHostedServiceTests` locking the unauthenticated
  `200` in as intended behaviour.

## 4. The Problem

Each stream's own root-cause work went beyond the register's own
one-line description. `WP 16.4B-1` audited every permission key already
defined in `src/` before minting `api.openapi.read` and found none of
the existing keys — all sample-module-scoped or `plugin.*` capability
keys — fit a Core-level, platform-shaped permission; the one precedent,
`Audit.AuditQuery.QueryPermission`, is what it followed.

`WP 16.4B-2`'s `TD-68` fix required naming the exact TOCTOU window a
naive refcounted rewrite would still have: between one thread deciding a
key's count has reached zero and actually removing the entry, a second
thread's `GetOrAdd` can observe the same about-to-be-removed entry and
start waiting on a semaphore the first thread is about to dispose out
from under it. Its `TD-69` audit went further than the register asked —
a whole-tree, hand-traced search of every `Add`/`AddInstance`/`Singleton`/
`Transient` call site (roughly 330 of them) found exactly **one**
legitimate replace-semantics case in the entire codebase, and it was a
unit test that had codified the last-wins defect as a feature
(`Add_SameServiceTypeTwice_LastRegistrationWins`, testing `IGreeter`).
It also found a second, real, previously-silent defect the fix's own
strictness exposed: eight `Samples` integration test fixtures each
registered `IPermissionEvaluator` twice, the first registration
silently dead under the old last-wins semantics.

`WP 16.4B-3`'s `TD-67` investigation is where this Work Package's most
important judgement call sits. Item 3 of the register's own five —
`MoveToGroupAsync`/`MoveGroupAsync` "append new `GroupedUnder`
references without removing prior ones" — was investigated directly
against the code rather than accepted on the register's own word, and
found **stale**. `RequirementDto.GroupId` and `RequirementGroupDto.ParentGroupId`
are each that record's own live, current value, not resolved from the
relationship graph — a disclosed `WP 9.1A` correction, made specifically
to stop the ambiguity the register's own claim describes. `IRequirementsService.cs`
lines 96 and 106 call the `GroupedUnder` link "permanent" in the
contract itself; `RequirementsLifecycleExtensionsTests.MoveToGroupAsync_ASecondTime_PreservesTheOriginalGroupedUnderLinkAsHistory`
was already passing and already asserted the invariant explicitly; and
`EngineeringDomain.EngineeringObjectBase.MoveAsync` already ships the
identical design platform-wide. "Fixing" this would have reintroduced a
bug `WP 9.1A` had already closed. The stream did not resolve the
conflict itself — it corrected the register's own text (commit
`8fff32a`) and referred the disagreement to Technical Review, exactly as
its own governing instructions require for a comparable ADR conflict.

## 5. The Design

**`TD-62`.** `ApiRequestHandler`'s identity-resolution + permission-check
+ audit block was extracted into a shared `AuthorizeAsync`, and a new
`HandleOpenApiDocumentAsync` runs the OpenAPI document through the
identical path before generating it — the same `401`/`403` a
command-route caller gets, guarded by the new `api.openapi.read`
permission. `D-024`'s `Runtime:RestApi:Enabled` gate is read before any
ASP.NET Core object is constructed, following the exact
`TryGetValue`/`bool.TryParse`/`&&` fail-closed idiom `TempestHost.cs`'s
own `Plugins:AllowUnsignedLoad` read already established.

**`TD-68`.** Each key's `SemaphoreSlim` now sits behind a private
reference-counted `Entry`, removed from the dictionary and disposed the
instant its count returns to zero. The TOCTOU window above is closed by
a `lock (entry)` held across both the refcount mutation and the
dictionary removal — a losing `GetOrAdd` can never rediscover a retired
entry, at worst retrying once against a guaranteed-fresh one. A second,
unnamed leak (a cancelled `WaitAsync` after `AcquireAsync` had already
reserved the entry) was found and closed in the same change. The
double-dispose guard became `Interlocked.Exchange`.

**`TD-69`.** `Add`/`AddInstance` gained a trailing `allowReplace = false`
parameter; the default throws `DuplicateServiceRegistrationException` on
a colliding registration. The new exception is **not** hung off the
existing `ServiceResolutionException` — that type's own doc comment
scopes it to resolution-time failures against an already-built provider,
a different lifecycle phase from registration-time. A new base,
`ServiceRegistrationException`, mirrors the existing
`ModuleDiscoveryException`/`ModuleRegistrationException` split. Every
one of the ~330 audited call sites was reconciled: the one legitimate
case rewritten to assert the new throw plus a dedicated `allowReplace:
true` test; the eight latent duplicates fixed by deleting the
now-redundant line, confirmed a no-op on test outcomes by full re-run.
`TempestServiceProvider.Construct` falls back to a parameter's own
declared default only when its type has no registration at all **and**
the parameter itself declares one — a strict narrowing, not a general
swallow.

**`TD-67`.** `EngineeringDocumentStore.CreateAsync` now writes revision 1
before the document record, the exact inversion `ReviseAsync` already
used — safe because the document's own Id is minted locally before
either write. Two new reconciliation services,
`IRequirementsReconciliationService` and
`IMaterialCatalogReconciliationService`, give the two document-then-index
pairs the register named an explicit, operator-invoked `DetectAsync`/
`SweepAsync` — never automatic, never wired to a startup path or any
other caller. `MoveGroupAsync` gained both a parent-Kind check and a new
`RequirementGroupCycleException`-guarded ancestry-cycle check, mirroring
`EngineeringObjectBase.GuardAgainstCircularParentAsync`'s own algorithm.
The document-then-index ordering itself could not be cheaply inverted
the way `CreateAsync`'s could — `MaterialCatalog.RegisterAsync`/
`RequirementsService.Create*` obtain their own Id *from*
`IEngineeringDocumentStore.CreateAsync`, so there is nothing to index
beforehand without changing that interface's own contract — so the
sweep is a disclosed mitigation, not a fix, for that item.
`VerificationService.RecordAsync`'s partial evidence graph was judged,
on time and scope grounds, not to warrant a fourth reconciliation
service, and is disclosed as genuinely still open.

**`TD-97`.** `EngineeringObjectBase.DeleteAsync` now releases an object's
attachment content once its deletion is durable — after, never before,
preserving `ADR-0114` decision 4's own crash-safety direction unchanged.
A third reconciliation service, `IAttachmentContentReconciliationService`,
compares the content store's own keys against every attachment Id any
persisted `EngineeringObjectState` references (live or soft-deleted
alike) and, on sweep, collects what nothing references.

**The substitution.** The Release Plan's own acceptance line for `TD-67`
reads "a write-intent marker before multi-file writes and a startup
sweep that reports orphans." `WP 16.4B-3`'s own report discloses,
explicitly, that it built something different: "a direct index-vs-document
comparison, with no new persisted marker of any kind, and an explicit,
operator-invoked sweep rather than a startup one," stating that its own
"controlling instructions specify a different, simpler design instead...
and I followed those instructions, which are more specific than the
Release Plan's own paragraph." The disclosure is genuine — it is written
plainly, under "Out of scope, named rather than silently left," not
buried. But the substitution is not a neutral implementation choice: per
the `v0.16.0` Engineering Status Report's own account of the RED finding
this Work Package shipped, "the implementing stream substituted a plain
comparison, and that substitution is what opened the race." A disclosed
deviation from an approved plan's own acceptance criterion is not the
same thing as a deviation whose safety consequence was also evaluated
before it shipped — see §10, below.

## 6. Alternatives Considered

**One merged reconciliation service instead of three.** `WP 16.4B-3`'s
own governing instructions explicitly invited merging the `TD-67` and
`TD-97` sweeps. Rejected: `RequirementDto`/`RequirementGroupDto`/
`RequirementCollectionDto` and `MaterialSpecificationDto` are `internal`
to their own namespaces, and every existing service in this pattern
depends only downward into `EngineeringData`/`Persistence`, never
upward across sibling disciplines. A single merged service spanning
Requirements, Materials, and `EngineeringDomain` would have inverted
that layering.

**A per-caller, permission-filtered OpenAPI document, rather than gating
the existing one.** The Technical Debt Register's own row floated this
as an alternative to gating. Not built — it is a materially larger
design (the document's own shape would depend on the caller) than
`D-024`/the Release Plan describe for closing `TD-62`.

**Hanging `DuplicateServiceRegistrationException` off `ServiceResolutionException`
directly**, rather than a new `ServiceRegistrationException` base.
Considered and rejected as semantically wrong against that type's own
stated scope — see §5.

**Building the write-intent marker the plan actually specified.** This
is the alternative that was not taken, and its absence is the direct
cause of §10's finding. A marker-based design was available, named, and
approved at the plan level; the implementing stream substituted a
simpler mechanism on the strength of narrower, more specific
instructions it received during the work, without an accompanying
safety re-analysis of what the substitution gave up.

## 7. Why This Solution Was Chosen

Where this Work Package investigated a register's own claim against the
actual code rather than trusting it — `TD-67` item 3's stale
"append-without-removing" premise — the judgement was sound: a
deliberately reviewed, already-tested design (`WP 9.1A`) was not
overwritten to satisfy a debt row that had not kept up with it, and the
disagreement was routed to Technical Review rather than resolved
unilaterally by whichever side happened to be doing the work that week.
That is the correct instinct this Work Package's own governing
instructions call for.

Where this Work Package substituted a simpler mechanism for the one the
approved plan specified — the `TD-67`/`TD-97` write-intent marker — the
same instinct did not hold. The substitution was disclosed as a scope
note, not evaluated as a safety question. Both are documented in this
Work Package's own reports; only one of them was actually safe.

## 8. Architectural Principles

- **Verify a register's own root-cause claim by reading the actual code
  path, not by trusting its prose** — `TD-67` item 3's stale premise,
  and `TD-69`'s full call-site audit finding one legitimate case among
  ~330, are both concrete instances.
- **An automated repair facility that touches a user's own data is
  something a person decides to run, never something that runs while
  they are not looking** — every one of the three reconciliation
  services is explicit `DetectAsync`/`SweepAsync` with no startup hook
  or scheduled path, stated identically across all three.
- **A conflict between a register's own text and the code's already-
  reviewed, already-tested design is referred to Technical Review, not
  resolved unilaterally by whoever is touching the code that week** —
  the `TD-67` item 3 disposition.
- **A disclosed deviation from an approved plan's own acceptance
  criterion still needs its safety consequence evaluated before it
  ships, not only its scope difference named** — the principle this
  Work Package's own `TD-67`/`TD-97` substitution violated, named here
  because the Work Package's own reports do not name it this way.

## 9. Benefits

- `TD-62`, `TD-68`, `TD-69`, `TD-97` all Resolved; `TD-67` Partially
  resolved — three of its five named defects closed, one corrected as
  not a defect, one (`VerificationService.RecordAsync`) genuinely still
  open and disclosed.
- `TD-68`'s stress test (40 tasks × 50 iterations over 4 keys) is
  interleaving-independent by construction, bounded entirely by fixed
  loop counts rather than wall-clock waits — it cannot flake by machine
  speed, the identical bar `WP 16.4A` established for this release.
- `TD-69`'s audit turned up and fixed a real, previously-silent defect
  (eight duplicate `IPermissionEvaluator` registrations) that last-wins
  semantics had been hiding, not merely a theoretical hazard.
- Full-suite Core results across the three streams: `WP 16.4B-1` 3,133/3,133;
  `WP 16.4B-2` 3,135/3,135 (baseline 3,124, delta fully reconciled);
  `WP 16.4B-3` 3,161/3,161 (baseline 3,124, +37 new tests, zero
  pre-existing tests touched). All local only — see §10.

## 10. Trade-offs — the data-loss defect this Work Package shipped

**What happened.** `AttachmentContentReconciliationService`'s original
sweep read object states, then content keys, and deleted any content key
nothing referenced. `EngineeringObjectBase.AttachContentAsync` writes
content, then object state — `ADR-0114` decision 4, deliberate, and
correctly left unchanged by this Work Package. A sweep running between
those two writes saw content with nothing yet referencing it, and
deleted it; the state write then landed anyway, recording an attachment
whose content hash pointed at bytes that no longer existed. This is
**silent, permanent data loss**, with the object's own metadata
continuing to claim the file was there. Reading states first, as the
original code did, made the window *wider* than reading content first
would have — the state read has less time to observe a write still in
flight the earlier it runs.

**`TD-97` was marked Resolved against this exact code.** The register
row this Work Package itself wrote states the sweep "compares the
content store's own keys against every attachment Id any persisted
`EngineeringObjectState` references" with no caveat that the two reads
were unsynchronized against a live writer. The three reconciliation
services' own report frames every sweep in this Work Package as a
mitigation for a crash window — none of the three streams' reports
evaluate what a sweep run *concurrently with a live write*, not only
after a crash, can do.

**Two independent review perspectives found it.** The security
perspective found the attachment race directly; the persistence
perspective reproduced it independently and found the identical race
shape in the `MaterialCatalogReconciliationService` sweep this Work
Package also built, with a worse practical consequence — a
fully-registered material's index entry deleted, document intact but
unfindable, and because `RegisterAsync`'s own duplicate check reads that
same index, a later registration for the same identifier would not see
a collision, producing two conflicting documents under one identifier.

**It was fixed by a different Work Package.** `WP 16.4B-R2` — not in
this retrospective's own scope, and not authored by any of the three
`WP 16.4B` streams — closed it with a durable write-intent marker
(`Mark → content → state → Clear`) plus a read-order reversal across all
three sweeps this Work Package built. `WP 16.4B-R2`'s own first attempt
was itself rejected at a second review round for sampling the marker
*after* the state read rather than between the two scans, which only
narrowed the race rather than closing it — the correct fix needed a
formal interleaving proof, not an intuition about read order. That
history belongs to `WP 16.4B-R2`'s own retrospective, not this one; it
is named here only so a reader of this Work Package's own account is
not left thinking the defect was simple to close once found.

**What is still genuinely open, not settled by any fix to date.** The
`v0.16.0` Engineering Status Report's own §8 records, as an open
question for external architectural review, whether the write-intent
marker is the right closure at all — or whether `ADR-0114` decision 4's
own content-before-state ordering needs revisiting now that a
**concurrent reader**, not only a crash, can observe the window; that
ADR's own reasoning predates the existence of any sweep. The same
report notes the Materials and Requirements sweeps carry no independent
runtime marker at all, relying entirely on a structural proof about
today's write order that would need to be re-derived the moment either
service's own create path changes shape. Neither of these is resolved
as of this Work Package's own record, and this retrospective does not
claim otherwise — no report available to it describes a further fix
covering, specifically, two concurrent mutations against the same
object beyond the crash-and-single-attach interleavings `WP 16.4B-R2`'s
own tests exercise.

## 11. Common Mistakes

- **Substituting a simpler mechanism for one the approved plan
  specifically named, and disclosing the substitution as a scope note
  rather than evaluating what it gave up.** The write-intent marker
  existed in the plan precisely because a crash window and a concurrent
  sweep are the same shape of hazard; the substitution removed the one
  piece of the design that closed the concurrent case.
- **Marking a Technical Debt row Resolved against code that had not
  been reasoned about under concurrent access**, only under a crash. A
  sweep that runs while other writers are active is exactly as much "in
  production" as one that only ever runs after a restart.
- **Treating three sibling streams' own reports as sufficient without a
  fourth pass asking what happens when two of them run at once** — the
  race this Work Package shipped only exists at the seam between
  `AttachContentAsync` (untouched by any of the three streams) and the
  new sweep (`WP 16.4B-3`); no single stream's own review would have
  caught it in isolation.

## 12. Future Evolution

`VerificationService.RecordAsync`'s partial evidence graph remains open
— `WP 16.4B-3`'s own report names the pattern (enumerate documents of a
Kind via `IPersistenceStore.ListKeysAsync`, check the subject's own
back-reference) as proven three times over and a small addition for
whichever Work Package next touches this area. `CreateGroupAsync`'s own
missing parent-Kind check — the identical gap `MoveGroupAsync` had
before this Work Package — is named, not fixed. The `MoveToGroupAsync`/
`MoveGroupAsync` conflict between the register's text and the `WP 9.1A`
design is referred to Technical Review and not yet settled at this
retrospective's own writing. None of the three reconciliation services
is wired to any command, CLI, or scheduled surface; `TD-130` records
that whichever Work Package wires one owns adding its authorization seam
at the same time. The Engineering Status Report's own open question
about whether `ADR-0114` decision 4 needs revisiting given a concurrent
reader — not only a crash — can now observe the window this Work
Package's own sweep introduced is unresolved and squarely this area's
to answer next.

## 13. Key Takeaways

- A disclosed deviation from an approved plan's own acceptance line is
  not automatically a safe deviation — the safety property a design
  element exists to provide has to be re-derived for the substitute, not
  assumed preserved because the substitute is "simpler."
- Marking a debt row Resolved is a claim about the code's behaviour
  under every condition the original defect described, including
  concurrent access, not only the crash scenario a fix happened to be
  tested against.
- Refusing to "fix" a register's own claim once direct evidence shows it
  stale, and referring the resulting conflict to Technical Review rather
  than resolving it unilaterally, is exactly the behaviour a review
  board should reward — this Work Package did both the thing worth
  praising and the thing that produced the release's most serious
  defect, in the same three streams, days apart.
- A Work Package built from independently-scoped parallel streams still
  produces one shared, honest account — a defect at the seam between two
  streams is invisible to any single stream's own retrospective and has
  to be told from the Work Package's own vantage point instead.
