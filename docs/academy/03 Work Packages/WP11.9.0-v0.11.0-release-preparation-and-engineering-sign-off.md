# WP 11.9.0 — `v0.11.0` Release Preparation & Engineering Sign-Off

## 1. Introduction

`WP 11.9.0` (commit `fda4172`, tagging `v0.11.0`) is `v0.11.0`'s closing
sign-off, executed as the TempestOS Engineering Programme: six
independent disciplines — Chief Architect, Principal Software Engineer,
Workflow Engineer, QA Lead, Technical Author, Product Manager — each
performing an independent review before any document was corrected,
reconciled into a single Programme Review. Its full account is
`docs/releases/v0.11.0/WP11.9.0 Engineering Release Report.md` and
`docs/releases/v0.11.0/Release Notes.md` (the narrative record, created
by this Work Package — it did not exist before). This retrospective is
written retrospectively under `WP 16.2B`, grounded in those two
documents, `WorkPackages.md`'s own row, and commit `fda4172`.

**Verdict: ACCEPT WITH OBSERVATIONS.** Every hard gate (build, test,
architecture, regression) passed cleanly on independent re-verification.
Six governance-documentation gaps and two genuine release-tooling
defects were found during this sign-off itself, all corrected or
formally registered within it, none left silently absorbed. One depth
gap against the prior release's own sign-off precedent — no mouse-driven
interactive UI verification — is disclosed explicitly, not narrowed to
look equivalent.

## 2. Purpose

Answer, from fresh evidence independently reproduced during this Work
Package itself, whether `v0.11.0` is ready to release — by
`ADR-0106`'s later-formalised standard applied here in substance for the
first time as a six-discipline Programme Review, the same rigor
`WP10.9A` set as this project's own prior sign-off precedent.

## 3. Background

`v0.11.0` shipped eight Work Packages spanning architecture review,
roadmap planning, CI/CD, engineering workflow, governance automation,
and presentation-strategy resolution — zero new Engineering Discipline,
zero new product feature. Nothing in that scope had yet been
independently re-verified end to end from a clean build under this same
Work Package's own review.

## 4. The Problem

Every prior Work Package's own report made its own claims; none had been
cross-checked against the others by an independent reviewer with no
sight of the prior conclusions, and no discipline's own finding had been
reconciled against the rest before this release could credibly be called
ready.

## 5. The Design

**Six independent discipline reviews (Part A), reconciled without
prior sight of each other's conclusions**: Chief Architect (Pass —
`ADR-0101` honoured, zero executable-code changes anywhere outside the
disclosed `TempestShell` deletion, independently re-derived from
`git diff v0.10.0..HEAD`, 49 files, +5194/−951); Principal Software
Engineer (Pass — full clean rebuild, both configurations, 0 Warnings/0
Errors; 2228/2228 tests; both `WorkspaceShell` and `Tempest.Desktop`
launched and verified directly; a disclosed depth gap — no
mouse-driven UI click-through, no automation tool available this
session, named plainly rather than presented as equivalent to
`WP10.9A`'s own ten-point precedent); Workflow Engineer (net positive,
"designed, not yet operative" — finds `scripts/governance-healthcheck.ps1`
itself undiscoverable via the documented onboarding path, and a new
defect: `Contributor Learning Path.md`'s own closing section still
points to `docs/releases/v0.5.0/WorkPackages.md`, six releases stale,
missed by `WP 11.3B`'s own edit pass to the same file); QA Lead (Pass
with conditions — test-count drop of 38 exactly reconciled; two new
tooling defects found by actually running the scripts, `TD-42`/`TD-43`,
neither exercised by how this release is actually being tagged); Technical
Author (documentation updated within scope; five governance registers
found stale and corrected, one an outright factual error —
`Future Capability Register.md`'s own `FCR-0005` entry still read
"Identified, not started" despite having shipped; Academy retrospective
coverage found absent for all seven prior Work Packages — assessed
non-blocking per this project's own `v0.10.0`-era precedent for a
comparable finding, recommended as an immediate `v0.12.0` fast-follow);
Product Manager (Pass — judged correctly as release-engineering/
governance infrastructure, not a feature release; recommends `WP 12.0A`
next).

**Part B — Programme Review reconciliation**: no discipline's factual
findings contradicted another's; the reconciliation required was one of
emphasis and disposition. The Technical Author's own initially
near-blocking closeout language ("cannot be tagged until…") is
reconciled in favour of Pass, on the same grounds `WP10.9A` used for a
comparable gap-finding — a real, disclosed gap is not automatically a
release blocker if named honestly and does not compromise a hard gate.

**Part C — corrections made within this Work Package**: `FCR-0005`
corrected to Implemented; `TD-42`–`TD-45` newly registered (41 → 45
total; 34 → 38 Open); `Academy Register.md`, `Documentation
Register.md`, `Release Register.md` all corrected/backfilled;
`Release Notes.md` created. **Not corrected, disclosed instead**: the
`Contributor Learning Path.md` stale pointer; the undiscoverable
health-check tool; the seven missing Academy retrospectives; the two
new tooling defects' own code fixes (registered, not applied — a code
fix inside a "Verification only" Work Package would repeat the
"undisclosed drift" pattern this whole release exists to prevent).

**Part D — reconciled Definition of Done**: eleven of twelve items fully
satisfied; item 4 (Academy) partially satisfied, disclosed non-blocking;
item 8 (UX) correctly not applicable to this release's own scope.

## 6. Alternatives Considered

Fabricating four retrospective articles to close the Academy Definition
of Done item outright, within this "Verification only" Work Package's
own scope, was implicitly rejected in favour of disclosing the gap and
recommending a dedicated fast-follow — matching this project's own
`v0.10.0`-era precedent for the identical class of finding, rather than
inventing coverage under time pressure at the point of sign-off.

## 7. Why This Solution Was Chosen

Independent, before-reconciliation review by six separate disciplines
catches disagreements a single reviewer's own report cannot surface —
Architecture and QA both independently flagged real findings not yet
formally registered; Workflow Engineer and Technical Author both
independently found governance/documentation currency gaps from
different surfaces (onboarding discoverability vs. register staleness),
the same underlying root cause seen from two angles neither discipline
alone would necessarily have connected.

## 8. Architectural Principles

No production code, ADR, or architecture was modified beyond the
governance-register corrections named in Part C — this is a review and
correction pass, not an implementation Work Package. `ADR-0101`
reconfirmed honoured directly by the Chief Architect's own independent
re-derivation, not carried forward from `WP 11.3B`'s own prior claim.

## 9. Benefits

`v0.11.0` receives a defensible release decision grounded in six
independently reproduced reviews rather than a single self-report. Five
governance registers are current for the first time in this release's
history. The Product Manager's own review names a concrete cost
avoided: entering `v0.12.0`'s own largest planned refactor
(`WP 12.0B`) without a CI gate, a documented process, or automated
governance checking would repeat exactly the failure classes this
release found and closed.

## 10. Trade-offs

The disclosed depth gap (no mouse-driven UI verification) is real, not
merely disclosed as a formality — assessed low-risk given the Chief
Architect's own independent confirmation that zero UI-rendering code
changed anywhere this release, but it is a genuine narrowing of
verification depth against the prior release's own precedent, named
plainly rather than smoothed over. **No git commit or tag was created by
this Work Package itself** — per this project's own standing discipline,
Product Approval's decision is sought explicitly, separately, never
assumed from a Programme Review's own recommendation.

## 11. Common Mistakes

**Letting an alarming-sounding draft finding stand as the release's own
final verdict without reconciliation.** The Technical Author's own draft
closeout initially read as near-blocking; reconciled in Part B in favour
of Pass once its own three named conditions were confirmed satisfied by
the report itself — the same resolution `WP10.9A` reached for its own
comparable finding. An unreconciled alarming draft, left standing, would
have misrepresented the release's own actual readiness.

## 12. Future Evolution

The `Contributor Learning Path.md` stale-pointer defect this Work
Package's own Workflow Engineer discipline found is not corrected until
`WP 16.2B`, five releases later — the identical gap this retrospective
itself is part of backfilling. `TD-42`/`TD-43` (the two tooling defects
this Work Package registered but did not fix) are outside this
retrospective's own sourced evidence to confirm as closed. `WP 12.0A`
(Desktop Composition Root Decomposition Architecture), this Work
Package's own recommended next step, follows directly per the roadmap.

## 13. Key Takeaways

- Six independent reviews, performed before any of them sees the
  others' conclusions, catch disagreements and blind spots a single
  reviewer cannot — the Programme Review's own reconciliation step is
  where that value is actually realised, not merely in running six
  reviews.
- A disclosed, non-blocking gap against precedent (no mouse-driven UI
  check) is honest release engineering; silently narrowing the scope to
  read as equivalent to a prior, deeper precedent would not be.
- A finding disclosed as "recommended immediate fast-follow" needs an
  actual fast-follow — this Work Package's own Academy and
  `Contributor Learning Path.md` findings both took five releases to
  close.
