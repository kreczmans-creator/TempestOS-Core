# WP 15.1A — v0.15.0 Release Preparation & Governance Closure

## 1. Introduction

`WP 15.1A` (`d2f1fae`, on `feature/v0.15.0-release-prep`, cut from `main`
at `a417ade`) formalised twenty commits that had already landed on
`main` since the `v0.14.0` tag into a real, numbered release. The full
evidentiary account — every `git log`/`git diff` derivation, every
register correction, every Verified/Inferred/Unknown finding — is its
own dedicated report, not repeated here: `docs/releases/v0.15.0/
WP15.1A v0.15.0 Release Preparation Report.md`. This article is written
retroactively, under `WP 16.2B` (`v0.16.0`'s Academy retrospective
backfill), because Engineering Governance §6 requires one per Work
Package regardless of subject matter — a release-preparation Work
Package is not exempt from the Academy obligation it itself partly
exists to restore.

## 2. Purpose

Turn twenty undocumented commits into a real release: derive their
scope entirely from git evidence, retroactively number and retrospect
the five distinct pieces of work found in the range, bump `VERSION`,
reconcile the Technical Debt and Future Capability Registers, and
recommend whether `v0.15.0` is ready for tagging.

## 3. Background

Commissioned as the correct next Work Package following a full
current-programme audit, which found no `"WP15.x"` programme, no
`docs/releases/v0.15.0/` folder, and twenty undocumented commits
already on `main` since the `v0.14.0` tag — `VERSION` itself still read
`0.14.0` while `main`'s own tree had moved well past what that tag
described.

## 4. The Problem

No commit in the `v0.14.0..a417ade` range carried a `WP 15.` or
`WP15.` reference, a `WorkPackages.md` row, a Technical Debt entry, or
an Academy retrospective. Five distinct pieces of work needed
identifying and numbering from commit evidence alone, with no commit
left unaccounted for and none assigned to more than one Work Package.

## 5. The Design

Every fact was derived directly from `git log`/`git diff` against the
working tree, never carried forward from a prior summary. The four
Desktop-related pieces were numbered `WP 15.0A`–`D`; `WP 11.5A` kept
its own already-independently-numbered, out-of-sequence slot. All five
retrospectives were written from commit evidence, disclosing where that
evidence is thinner than a contemporaneous account would have been
(`WP-Z3`'s own established precedent for this exact situation).
`TD-121`/`TD-122` were added for two real, already-fixed defects that
had never been registered; the Future Capability Register was reviewed
for the first time since `v0.13.0` (`WP 13.11A`).

## 6. Alternatives Considered

Deferring the twenty commits' own accounting to whatever release came
next, rather than closing the gap now — rejected: the backlog would
only grow, and Release DoD item 4 (an Academy retrospective per Work
Package) would stay unmet for an increasingly stale, uninvestigated
range.

## 7. Why This Solution Was Chosen

Deriving scope entirely from git evidence — never from memory, a
commit message's own claim, or a prior report — is the only way to
retroactively number work honestly. `WP 11.5A` had already modelled
this exact discipline for a smaller correction; this Work Package
applied it at release scale.

## 8. Architectural Principles

No ADR, architecture, or production/test file was touched — a
release-preparation Work Package changes what the repository *says*
about itself and its own `VERSION`, not what it *is*.

## 9. Benefits

`v0.15.0` now exists as a real, numbered release folder with a
`WorkPackages.md` deriving every entry from evidence; `VERSION` matches
`main`'s own actual state; two real, already-fixed production defects
(the Windows startup crash, the Ribbon scrollbar) are now tracked in
the Technical Debt Register as `TD-121`/`TD-122` instead of untracked.

## 10. Trade-offs

Seven findings were disclosed rather than silently absorbed into a
falsely-complete account. The most consequential for what came after:
Finding 7 — `docs/governance/Documentation/Academy Register.md` was not
backfilled with entries for the five new retrospectives this Work
Package added, despite that register's own stated Review Frequency
("in practice, every Work Package"). That is the specific gap `WP
16.2B`, the Work Package that produced this retrospective, closes.

## 11. Common Mistakes

**Trusting a commit message's own embedded test-pass-count as fact.**
Finding 2 discovered that three `WP 15.0B` commits embed figures (e.g.
"373/386 passing") obtained via a flawed local SDK-substitution
technique — deleting `global.json` to work around an unavailable
pinned SDK version, which also breaks a test helper's own repository-
root search, manufacturing failures unrelated to the code under test.
The true, currently-verified baseline (0 failures, both configurations,
every commit in the range) was confirmed independently only by real,
GitHub-hosted CI — not by re-trusting the historical local number.

## 12. Future Evolution

This retrospective was written retroactively, more than a year after
`WP 15.1A` itself, under `WP 16.2B` — the Academy retrospective
backfill Work Package of the `v0.16.0` programme, whose own governing
v1.0 scope decision is `D-021` (proposed, `WP 16.0A`). Per `WP-Z3`'s own
established precedent for this exact situation: a retrospective written
after the fact rather than alongside the work is the cost of the gap,
and it is not fully recoverable by closing it. Fine detail beyond what
the source report and commit itself record is genuinely absent, not
reconstructed.

## 13. Key Takeaways

- Deriving a retroactive Work Package's scope entirely from `git log`/
  `git diff` evidence, never a prior summary, is what makes the
  numbering trustworthy.
- A release-preparation Work Package still owes the Academy its own
  retrospective — the obligation is not implicitly satisfied by the
  retrospectives it commissions for the work it formalises.
- Disclosing a scope limitation as deliberately not fixed (Finding 5,
  Finding 7) is a legitimate, complete resolution when closing it is
  itself a separate, later undertaking.
