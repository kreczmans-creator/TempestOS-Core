# WP 13.9.1 — `v0.13.0` Readiness Remediation

## 1. Introduction

`WP 13.9.1` is the first remediation Work Package of the `v0.13.0`
`WP 13.9.x` hardening chain — the pass commissioned to close the four
named findings `WP 13.9.0`'s Engineering Readiness Review raised against
`feature/v0.13.0`, and nothing broader. It runs on `feature/v0.13.0`,
`v0.13.0` — "Trust & Deployment Hardening" — directly following
`WP 13.9.0`, whose own verdict was `NOT READY` with four of six
disciplines independently reaching Not Ready.

Its material was not committed on its own. It was integrated and committed
as part of the whole `WP 13.9.1`–`WP 13.9.6` chain by `WP 13.9.7`, commit
`d7d19d4` ("WP 13.9.1-13.9.6: Plugin Trust Execution Boundary Remediation
Chain", 35 files, +3,263/−90). Every claim below is grounded in that
commit's own message, this Work Package's own row in
`docs/releases/v0.13.0/WorkPackages.md`, its own retained stratum in
`PROJECT_STATUS.md`, `docs/releases/v0.13.0/WP13.9.0 Engineering Release
Report.md`, and — where checkable from code alone — direct reads of real,
current source. Where those sources disagree with each other, the
disagreement is recorded rather than resolved away.

**A note on this document's own provenance.** `WP 13.9.7`, the integrating
Work Package, recorded an explicit governance conclusion that
`WP 13.9.1`–`WP 13.9.6` "do not require new Academy retrospective files of
their own," checked against `Academy Index.md`'s own stated maintenance
rule and the `WP 13.2B`/`WP 13.9.1` precedent (neither of which has an
Academy retrospective) — a `WorkPackages.md` row plus a
`PROJECT_STATUS.md` entry being, per that conclusion, this project's
actual established requirement for a Work Package of this shape. This
retrospective is therefore written after the fact — and, as
`WP 13.12.0` subsequently established, **in satisfaction of an obligation
that was genuinely outstanding all along**, not merely in addition to a
sound conclusion. That governance conclusion was wrong: `Academy Index.md`
states no such maintenance rule, Engineering Governance §6 requires a
retrospective for every Work Package unconditionally, and the cited
`WP 13.2B`/`WP 13.9.1` "precedent" was the gap itself being used to
justify its own continuation. This document is accompanied by matching
`Academy Register.md` and `Academy Index.md` entries, added by
`WP 13.12.0` in the same pass. The `WP 13.3B` retrospective — reconstructed by this
very Work Package — established the same disclose-the-provenance
discipline for exactly this situation.

## 2. Purpose

To close `WP 13.9.0`'s four named findings, each one, exactly and only —
not to re-derive `WP 13.9.0`'s verdict, not to widen scope into adjacent
defects, and not to declare the release ready. Per this Work Package's own
`WorkPackages.md` row and `PROJECT_STATUS.md` stratum, both state the
boundary in identical terms: **`WP 13.9.0`'s own verdict is not rewritten
by this Work Package** — the CI/branch-push/merge gap (Verification and
Release readiness) remains entirely unaddressed, out of this Work
Package's own engineering scope, and a fresh Engineering Readiness Review
is required to re-derive an updated verdict rather than assume one.

That self-imposed limit is the defining feature of this Work Package. It
is what made `WP 13.9.2` — the re-execution — a necessary, separate,
independently-commissioned successor rather than a formality, and it is
why `WP 13.9.1` closed with a report to its commissioning conversation
rather than a new Engineering Release Report of its own.

## 3. Background

`WP 13.9.0` was the first execution of the permanent Engineering Readiness
Review `ADR-0106` defines, applied to `v0.13.0` at `feature/v0.13.0` HEAD
`88e41a2`. It ran the canonical five-category model (Architecture,
Implementation, Verification, Governance, Release) plus a **disclosed,
additional sixth category, Security/Trust**, specific to this release,
whose entire substantive content is the new plugin trust platform
(`ADR-0107`–`ADR-0112`). Six independent discipline reviews, each
performed before seeing the others' conclusions.

**Verdict: `NOT READY`.** Four of six categories independently reached Not
Ready, via largely non-overlapping evidence:

- **Verification** — real, GitHub-hosted CI had never run against any
  commit of this release; `feature/v0.13.0` has no upstream, does not
  exist on `origin`, and none of its seven commits had ever merged into
  `main`.
- **Release** — independently re-derived the identical branch/CI fact from
  its own evidence.
- **Implementation** — three Release Blocking findings: `F1`, `WP 13.3B`
  (the real, substantive HEAD commit `88e41a2`) had no `WorkPackages.md`
  row, no Academy retrospective and no `PROJECT_STATUS.md` entry; `F2`,
  that same commit's message claimed a "20,000-trial differential fuzz
  harness" that an exhaustive search of current source and full
  `git log --all -p` history found nowhere in the repository, ever; `F3`,
  `PluginManifest`'s public constructor grew from 6 to 11 parameters, the
  five new ones all **required** — verbatim one of `ADR-0106`'s own three
  literally-named Release-Blocking examples.
- **Security/Trust** (the disclosed sixth category) — a genuine,
  empirically-demonstrated, previously-untracked trust-boundary bypass:
  `PluginAssemblyLoader.EnforceTrust` scanned only the one
  manifest-declared assembly (`ADR-0111`'s own literal scope, "every
  discovered `IModule` implementer **in the plugin's own assembly**"),
  while Module Discovery — deliberately left "completely unchanged" per
  `ADR-0110`'s own Decision text — scans
  `AppDomain.CurrentDomain.GetAssemblies()`, every assembly present in the
  process by any means.

Architecture and Governance readiness both scored Pass, with observations
— nine further Disclosed, Non-Blocking findings between them, none
Release Blocking. `WP 13.9.0` corrected nothing: its Part C records
"**None**", by explicit commission — review, classify, report, stop.

`WP 13.9.1` is the Work Package that picks those findings up.

## 4. The Problem

Four problems, of four genuinely different kinds, handed to one Work
Package by one review — and the review's own report is explicit that they
are not variations on a theme:

1. **A live security bypass in production trust code.** `WP 13.9.0`'s
   Security/Trust discipline built a live proof-of-concept against the
   commit's actual compiled `Tempest.Core.dll` — not a reading of the
   code, a run demonstration. A plugin's one manifest-declared assembly
   (`AsmA.dll`, requesting zero capabilities, at `UnsignedLocal`, the
   *lowest* trust tier) inherits a type from a second, wholly undeclared
   assembly (`AsmB.dll`) sitting in the same plugin folder — an entirely
   ordinary plugin-with-a-dependency-DLL layout. Resolving `AsmA`'s own
   base-type chain during `EnforceTrust`'s own `assembly.GetTypes()` call
   loads `AsmB.dll` into the `AppDomain` as an unavoidable CLR side
   effect. `AsmB`'s own `EvilModule : IModule` is never seen by
   `EnforceTrust` — never trust-checked, never capability-checked, never
   constructor-conformance-checked — yet is discovered and activated as an
   ordinary module by the correctly plugin-unaware Module Discovery pass.
   Because no principal was ever recorded for it, its ambient component
   principal is `null`, and `PluginTrustPermission.IsFirstParty(null)` is
   `true`, so every dynamic capability check is *skipped*, not merely
   satisfied.
2. **An undisclosed public API break.** `PluginManifest`'s constructor
   gained five new required parameters this release with no ADR or Work
   Package row disclosing it — while every other public constructor the
   release touched added only optional, trailing, defaulted parameters.
3. **A verification claim with no artefact behind it.** `WP 13.3B`'s own
   commit message asserted a 20,000-trial differential fuzz harness that
   did not exist. `WP 13.9.0`'s Part B names this explicitly as a small,
   direct illustration of why its independent-before-reconciliation
   discipline exists: two disciplines set out to verify the claim and
   found it did not hold; a third cited it uncritically in narrative
   summary.
4. **A Work Package in an undocumented governance state.** `WP 13.3B` —
   real, substantive, already committed as `88e41a2` — was invisible to
   `WorkPackages.md`, to the Academy, and to `PROJECT_STATUS.md`. This is
   the single most-corroborated finding in the entire report, found
   independently by **four of six disciplines**.

The problem behind the four problems is scope discipline. A remediation
pass handed a security bypass is under continuous pressure to keep pulling
the thread; a remediation pass handed governance staleness is under
continuous pressure to tidy adjacent staleness it did not find. `WP
13.9.0`'s findings define the boundary, and the Work Package's own
commissioning made staying inside it a first-class requirement.

## 5. The Design

Four parallel sub-agents — Security, Implementation/API, Verification/Test,
and Governance & Documentation — one per finding, each stopped before
commit and not merged by this Work Package itself. Per the commit message
and `WorkPackages.md` row, the four remediations were:

**Priority 1 — Security.** `PluginAssemblyLoader.DiscoverModuleTypes`
gained a fixed-point, breadth-first `AppDomain`-diff scan, following every
assembly that enters the process as a direct or transitive consequence of
examining a plugin's own declared assembly, applying the existing,
unchanged constructor-conformance check to every discovered `IModule` type
across all of them. The idiom was not invented: it is the same
dependency-graph resolution shape `PluginManifestDiscoveryService` already
used. Its structural properties are worth naming precisely, because both
survive every later correction in the chain — an assembly already resident
in the `AppDomain` for an unrelated reason before this plugin's scan began
is correctly out of scope, excluded by the before/after diff *by
construction*, and the traversal terminates on a visited-assembly
`HashSet`. **No `AssemblyLoadContext`, no process separation, no new
isolation mechanism** — `ADR-0110`/`ADR-0111`'s boundary is widened in
scope, not weakened. `ADR-0111` gained a "Corrected, `WP 13.9.1` Security
Remediation" Status-section note and Decision-text amendment; the section
is present in `docs/adr/ADR-0111-plugin-trust-capability-model-extends-ipermissionevaluator-via-component-principal.md`
today, confirmed directly.

**Priority 2 — API.** `PluginManifest`'s break was resolved
**asymmetrically, not simply reverted**. `TrustTier` stays required;
`Dependencies`/`RequestedCapabilities`/`Publisher`/`Signature` were
restored to optional, defaulted, trailing parameters, matching every other
constructor the release touched. All six `new PluginManifest(` call sites
(`PluginManifestDiscoveryService` plus five test files) were updated. The
asymmetry is documented as a formal rejection, `RD-0065`, in
`docs/architecture/Rejected Designs.md` — see §6.

**Priority 3 — Verification.** The unsubstantiated fuzz-harness claim was
replaced with a real one:
`TopologicalSort_RandomizedTrials_MatchesNaiveFullRescanReference` in
`PluginPlatformPerformanceTests.cs`, **10,000 seeded trials** (seed
`20130`), each trial a freshly-random acyclic dependency graph checked
against `NaiveFullRescanTopologicalSort`'s own independent
reimplementation. `PROJECT_STATUS.md` records ~1.9s measured runtime. Note
the number: the fix is a *smaller*, real harness, not a matching 20,000 —
the response to an inflated claim was a substantiated one, not a claim
resized to fit.

**Priority 4 — Governance.** `WP 13.3B` was backfilled with a full
13-section Academy retrospective
(`WP13.3B-plugin-platform-integration-and-end-to-end-validation-review.md`,
new file in `d7d19d4`) and a `WorkPackages.md` row.
`Architecture Document Register.md` and `Documentation Register.md` counts
were corrected; `Plugin Platform Architecture.md` and `Plugin Trust &
Isolation Architecture.md` had stale `WP 13.0A`-era "architecture
only"/design-pending Status headers corrected to reflect real
implementation and review.

**Test-harness collateral, disclosed rather than hidden.** The new scan
introduced a test-harness-only `AppDomain` race with no real-world
counterpart — Plugin Loading is single-threaded, sequential Host startup
in production. It was serialised by adding
`[Collection("Console output capture")]` to four further real-assembly-loading
test classes (`PluginAssemblyLoaderTests`,
`PluginAssemblyLoaderEnforceTrustTests`, `PluginSignatureVerifierTests`,
`PluginTrustTierAssignmentTests`).

**Verification, this Work Package's own figures.** Full regression re-run
fresh after all four fixes: **2,524/2,524 passing**, both configurations
(2,303 `Tempest.Core.Tests` + 221 `Tempest.Desktop.Tests`), against
`WP 13.9.0`'s own baseline of 2,519/2,519 (2,298 + 221).
`governance-healthcheck.ps1`: 7 passed, 1 warned (pre-existing,
unrelated), 0 failed.

## 6. Alternatives Considered

- **Reverting `PluginManifest`'s constructor wholesale** — restoring all
  five new parameters to optional and defaulted. Rejected as `RD-0065`,
  a formal Rejected Designs entry recorded by this Work Package:
  `TrustTier` is a security-critical field with no safe implicit default.
  Even defaulting it to the most restrictive tier
  (`PluginTrustTier.UnsignedLocal`) is a live footgun — a caller who
  forgets to pass `trustTier` would silently construct a manifest
  carrying *some* trust grant rather than fail to compile. `RD-0065`
  explicitly grounds this in the `AssemblyPath` precedent (a required,
  Discovery-computed field, a deliberate `WP 13.2A` design choice rather
  than an oversight) and applies `ADR-0106`'s own explicit rule that a
  classification follows a design's nature, not its current blast radius —
  the reasoning would hold identically even if third-party plugin authors
  already depended on the constructor.
- **Building a 20,000-trial harness to match the original claim.** Not
  taken. A real, committed, re-runnable 10,000-trial harness with a named
  seed substantiates the underlying equivalence conclusion; matching an
  arbitrary number from a message that never had an artefact behind it
  would have dignified the number rather than the verification.
- **Introducing an `AssemblyLoadContext` or process separation to close
  the multi-assembly bypass.** Not taken, and named as not taken in the
  commit message, the `WorkPackages.md` row and the `PROJECT_STATUS.md`
  stratum alike. `ADR-0110` already decided this question on its own
  merits; a remediation pass is not the place to reopen a ratified
  isolation-boundary decision.
- **Correcting `WP 13.9.0`'s verdict in light of the fixes.** Explicitly
  declined — see §2 and §7.

**The record is silent** on whether any further alternative was weighed
inside the four sub-agents' own deliberations. `WP 13.9.1` produced no
standalone report; its full account went to its commissioning conversation
and is not preserved as a file. `RD-0065` is the only alternative this
Work Package durably recorded as a formal rejection.

## 7. Why This Solution Was Chosen

**Because the findings, not the fixer, defined the scope.** Each of the
four priorities maps one-to-one onto a named `WP 13.9.0` finding. The
`WorkPackages.md` row states the constraint in its opening clause: "closes
`WP13.9.0`'s four named findings only, nothing broader." The CI/branch-push/merge
gap that produced two of the four Not Ready categories was left
untouched, correctly — it is a release-mechanics problem, not an
engineering one, and no amount of code remediation moves it.

**Because a remediation pass must not grade its own work.** This is the
single most consequential design decision in the Work Package, and the
chain that followed vindicated it twice over. `WP 13.9.1` declined to
re-derive a verdict; `WP 13.9.2` was commissioned to re-execute the review
independently; and `WP 13.9.2` found the Priority 1 security fix **still
incomplete** — the `AppDomain` diff was taken only around
`Assembly.GetTypes()`/`IsAssignableFrom`, not around the independent CLR
lazy-load trigger a discovered module's own constructor parameter types
represent. Had `WP 13.9.1` closed its own findings and declared itself
done, that gap would have shipped. The `WP 13.9.5` review later found a
third distinct bug the combined `WP 13.9.3`+`WP 13.9.4` boundary still
left open. The self-imposed "I do not get to say I succeeded" limit is
what made a chain possible at all.

**Because mirroring an existing idiom beats inventing one.** The
fixed-point breadth-first `AppDomain` diff was lifted from
`PluginManifestDiscoveryService`'s own dependency-graph resolution rather
than designed fresh. A reviewer auditing the fix has a working, already-reviewed
reference implementation to compare against, and the termination argument
was already made once.

**Because asymmetric is the honest answer to an asymmetric problem.** Four
of the five new `PluginManifest` parameters genuinely have safe defaults;
one genuinely does not. A uniform answer would have been tidier and wrong
in one of five cases — and that one case is the security-critical one.

## 8. Architectural Principles

- **Fail closed, and prefer a compile error to a silent grant.** `RD-0065`
  is this principle applied to a constructor signature: the required
  parameter forces a deliberate choice at every call site rather than
  quietly conferring a trust tier on the forgetful.
- **Widen an existing mechanism's coverage; do not add a new mechanism.**
  The Priority 1 fix changes what the existing capability-scoped
  enforcement scans, not how enforcement works. `ADR-0110`'s boundary is
  untouched.
- **`ADR-0110`'s "Module Discovery is deliberately plugin-unaware" is a
  decision, not an accident.** The fix pulls trust enforcement's coverage
  up to match Module Discovery's reach rather than teaching Module
  Discovery about plugins — the finding is a structural blind spot at the
  join between two ADRs, not a coding defect inside `EnforceTrust`, which
  did exactly what its governing ADR described.
- **A review's findings bound its remediation.** Scope is inherited from
  the review, not negotiated by the remediator.
- **Disclose, don't fabricate.** The Work Package that replaced a
  fabricated verification claim also wrote the retrospective disclosing
  that the claim had been fabricated, in `WP 13.3B`'s own reconstructed
  retrospective, naming the discrepancy in that document rather than
  quietly correcting the record around it.
- **A register is part of the artefact.** `Architecture Document
  Register.md`, `Documentation Register.md`, and the Academy each carry
  their own currency obligation; a real, substantive Work Package invisible
  to all three is a genuine defect, not a paperwork nicety.

## 9. Benefits

- The `WP 13.9.0` Security/Trust proof-of-concept no longer reproduces:
  the earliest scenarios in the new file
  `PluginAssemblyLoaderMultiAssemblyTrustTests.cs` are a
  base-type-inheritance reproduction of that exact PoC, confirmed denied,
  alongside confirmation that legitimate multi-assembly plugins still
  load.
- The undisclosed public API break is closed *and* the one genuinely
  required parameter is now durably justified, in a citable Rejected
  Designs entry, rather than left as an undocumented sharp edge.
- A verification claim that existed only in prose became a committed,
  seeded, re-runnable test any engineer can execute.
- `WP 13.3B` moved from an undocumented governance state to a full
  13-section Academy retrospective plus a `WorkPackages.md` row — closing
  the single finding four of six disciplines independently raised.
- The multi-assembly scan idiom this Work Package introduced became the
  substrate every later remediation in the chain corrected in place:
  `WP 13.9.3` widened its diff window, `WP 13.9.4` made it run
  unconditionally and collect `IHostedService` types too, `WP 13.10B` and
  `WP 13.11B` corrected it further still. That it was extended four times
  rather than replaced is evidence the shape was right even where the
  coverage was not.

## 10. Trade-offs

- **The Priority 1 fix was incomplete, and the record says so.** `WP
  13.9.2` found the diff window too narrow within the same chain. This is
  disclosed here as this Work Package's own most significant limitation,
  not attributed to a successor's cleverness. The `AppDomain`-diff
  approach is sound; the enumeration of which reflection calls can
  lazily load an assembly was not exhaustive at this point.
- **Four parallel sub-agents, none merged by this Work Package.** Each
  stopped before commit; integration was deferred to `WP 13.9.7`. That
  keeps a remediation pass from also owning integration risk, at the cost
  of a long-lived uncommitted working tree across six Work Packages.
- **A test-harness-only `AppDomain` race was introduced and worked
  around, not eliminated.** Four test classes now carry
  `[Collection("Console output capture")]` purely to serialise them. The
  real-world counterpart genuinely does not exist — production Plugin
  Loading is single-threaded — but the test suite pays a serialisation
  cost for a production property it cannot itself assert.
- **No Engineering Release Report of its own.** `WP 13.9.1`'s full account
  lives in its commissioning conversation. Its durable record is the
  `WorkPackages.md` row, the `PROJECT_STATUS.md` stratum, and `d7d19d4`'s
  own commit message — dense, but three sources rather than one, and none
  of them a first-person account of the four sub-agents' own working.
- **The register-currency work this Work Package performed did not extend
  to itself.** It corrected `Architecture Document Register.md` and
  `Documentation Register.md` counts, and closed the Academy gap for
  `WP 13.3B` — while `WP 13.9.1` itself was subsequently determined by
  `WP 13.9.7` not to need an Academy entry at all. This document exists
  outside that determination; see §1.

## 11. Common Mistakes

1. **Reading "Readiness Remediation" as documentation-only work.** It is
   not. This Work Package's own `WorkPackages.md` Type column reads
   `Implementation/Governance`, and its Priority 1 changed real production
   trust code in `PluginAssemblyLoader.cs`. The governance half is one of
   four priorities, not the whole.
2. **Assuming closing a review's findings makes the release ready.** It
   does not, and this Work Package says so twice in its own record. Two of
   `WP 13.9.0`'s four Not Ready categories (Verification and Release) were
   never in scope here and remained entirely open at its close.
3. **Attributing the finished multi-assembly trust boundary to this Work
   Package.** The boundary shipped in `d7d19d4` is the product of
   `WP 13.9.1` (the scan), `WP 13.9.3` (the constructor-parameter diff
   window), `WP 13.9.4` (unconditional scan, denied-type recording,
   `IHostedService`) and `WP 13.9.6` (the Module Discovery filter), with
   later corrections again in `WP 13.10B` and `WP 13.11B`. `WP 13.9.1`
   contributed the first, deliberately-narrow version.
4. **Assuming `PluginManifest`'s constructor was reverted.** Four
   parameters were made optional; `trustTier` was not, deliberately, and
   `RD-0065` exists precisely so that decision is not mistaken for an
   oversight a future engineer should "finish".
5. **Treating the 10,000-trial harness as a downgrade from 20,000.** The
   20,000 never existed. The comparison is between a claim and a test, not
   between two tests.

## 12. Future Evolution

- **A fresh Engineering Readiness Review** to re-derive a verdict — named
  as required by this Work Package's own record, and delivered as
  `WP 13.9.2`, which found further work rather than clearance.
- **The CI/branch-push/merge gap** (`WP 13.9.0`'s Verification and Release
  Not Ready categories) remains open at this Work Package's close: real,
  GitHub-hosted CI has never run against a commit of this release,
  `feature/v0.13.0` has no upstream, and nothing has merged to `main`.
  `d7d19d4` itself states "Not pushed, not tagged, no release created."
- **Register currency for the `WP 13.9.x` chain itself.** `WP 13.9.7`
  extended `ADR Register.md`'s `ADR-0111` citation to six phases and added
  the six `WorkPackages.md` rows, and concluded no Academy files were
  needed. This document, and its three siblings, sit outside that
  conclusion and outside the Academy registers.

## 13. Key Takeaways

- A remediation Work Package that declines to grade its own work is worth
  more than one that closes its findings and declares victory. `WP 13.9.1`
  refused to re-derive `WP 13.9.0`'s verdict; `WP 13.9.2` then found its
  own headline security fix incomplete. The refusal is what caught it.
- "Fix the four named findings, nothing broader" is a real, defensible
  scope for a Work Package — including when one of the four is a live
  security bypass whose thread visibly keeps going. The thread was pulled,
  by four further Work Packages, each separately commissioned and
  separately reviewed.
- An asymmetric problem deserves an asymmetric fix, durably justified.
  Four of five constructor parameters had safe defaults and one did not;
  `RD-0065` exists so nobody later "finishes the job" by defaulting the
  one that must not be defaulted.
- Enumerating *every* way a reflection API can lazily load an assembly is
  the hard part of a multi-assembly trust scan — not the fixed-point
  traversal, which was borrowed from an existing, working idiom and never
  needed correcting. Each later correction in this chain widened the same
  scan's coverage; none replaced its shape.
- A fabricated verification claim is a governance defect *and* an
  engineering one, and it took a review specifically setting out to check
  it to find it. `WP 13.9.0`'s Part B names the discipline that passed
  over the same claim uncritically. `WP 13.9.1`'s answer was to build the
  real thing and disclose the discrepancy in the retrospective it wrote
  for the offending Work Package.
