# Academy Guide — Sample Explorer Content's New Home

## 1. Introduction

`41a171a` corrected a stale pointer in the Engineering Workspace Academy
guide, left behind by `TD-75` phase 2's move of the Project Explorer's
fixed fictional tree out of `Tempest.App` and into the test project. A
pre-`v0.14.0` engineering-body-of-work row; documentation-only.

## 2. Purpose

To stop the guide sending a reader looking for code that is no longer
where the guide says it is.

## 3. Background

`TD-75` phase 2 (`fdd2a2a`) moved
`Tempest.App.Workspace.Samples` — the Longeron/Frame/Bracket sample tree —
into `Tempest.Core.Tests`, since it implements `Tempest.App` Workspace
abstractions the sample assembly cannot see and `WorkspaceShellTests` was
the only thing that had ever driven it. The Engineering Workspace guide
still named the old namespace.

## 4. The Problem

A reader following the `WP 8.1B`/`WP 8.1C` narrative would go looking for
code that is no longer at the path the guide describes.

## 5. The Design

The `WP 8.1B`/`WP 8.1C` narrative is left as it was — it describes what
those Work Packages did at the time, and that has not changed — with only
a current-location note added, so the history stays accurate and the
pointer stops being wrong.

## 6. Alternatives Considered

Rewriting the historical narrative to describe the code's current
location as though it had always been there — rejected implicitly: the
commit deliberately keeps the original narrative and adds a pointer,
rather than rewriting history to match the present.

## 7. Why This Solution Was Chosen

Because a Work Package retrospective and guide should describe what
happened at the time truthfully; a current-location note is the correct
way to keep a reader oriented without falsifying the historical record.

## 8. Architectural Principles

Historical documentation (what a Work Package did) and live documentation
(where the code is now) are different kinds of claim, and a move should
correct the second without rewriting the first.

## 9. Benefits

A reader following the guide is pointed at code that actually exists.

## 10. Trade-offs

The implementation reports, the Academy Register and `ADR-0071` keep the
old paths deliberately — they are records of their own moment, not live
documentation, and `ADR-0071`'s decision itself is untouched by the move.

## 11. Common Mistakes

Moving code without checking whether any documentation names its old
location — a mistake `e57f1aa`, the very next commit on this list, found a
second instance of in `PROJECT_STATUS.md`.

## 12. Future Evolution

`e57f1aa`, immediately after, fixes the second stale pointer the same
move produced — both found by something that checks (the governance
health check, in that case) rather than by re-reading.

## 13. Key Takeaways

- A code move should be checked against every documentation reference to
  its old location, not just the ones the mover happens to remember.
- Distinguish historical narrative (what happened) from a live pointer
  (where things are now) — correct the second without rewriting the
  first.
- The same move can leave more than one stale pointer; find all of them
  rather than stopping at the first.
