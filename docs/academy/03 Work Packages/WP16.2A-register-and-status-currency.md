# WP 16.2A — Register and Status Currency

## 1. Introduction

`WP 16.2A` re-derived, directly from source, every number seven
governance registers had been carrying — some for as long as eleven
releases — and cut `PROJECT_STATUS.md` from 565,445 bytes (9,068 lines)
to 11,036 bytes, moving everything below `## READY FOR WP14 UI/UX`
verbatim into a new archive file. It closed `TD-57`, the standing
finding that this project's own governance registers had drifted from
the source tree they claim to describe. Branch
`feature/v0.16.0-wp16.2a-register-currency`, cut from
`feature/v0.16.0` at `8b4c394`; landed as `40e267d`, merged `c2c89ac`.

No `src/` or `tests/` file was touched — this is a documentation and
governance Work Package, and its own report opens by saying so and
backing it with `git status`/`git diff --stat`.

## 2. Purpose

Every count in every touched register was to match a fresh
`ls`/`grep` re-derivation, recorded in the report; `governance-
healthcheck.ps1` clean; `PROJECT_STATUS.md` under 60 KB
(`v0.16.0 Release Plan.md` §"`WP 16.2A`"). The deeper purpose, stated
in the plan's own objective, was that every governance artefact
describe the repository at `v0.15.0`, and that `PROJECT_STATUS.md`
stop carrying eight releases' worth of "this field is stale"
corrections layered on top of each other.

## 3. Background

The registers this Work Package re-derived had not been touched by a
source-driven pass in a long time. The Interface Register stated 174
interfaces against a real count of 188. The Exception Register hedged
with "at least 55" against a real 84. The Validation Register still
named `VERSION 0.4.0` and 552 tests, eleven releases stale. The
Feature Register held 27 rows covering only `v0.5.0`. The Release
Register's own `v0.15.0` row still read "in preparation" after
`v0.15.0` had shipped. And `PROJECT_STATUS.md` itself had grown to
9,068 lines by accretion — every release adding a correction on top of
the last one instead of anyone re-deriving the document from scratch.
An earlier fact-finding pass had already flagged most of this drift;
this Work Package's own job was to fix it, not merely re-confirm the
earlier pass's numbers.

## 4. The Problem

Two distinct problems, not one. First, the ordinary problem of stale
governance data: numbers written once and never re-checked drift
further from the truth every release, and nobody can tell how far
without redoing the derivation. Second, a subtler problem the
fact-finding pass itself created: **that pass was run at an earlier
base commit**, and by the time this Work Package actually re-derived
the Exception Register against its own base (`8b4c3948`), the register's
true gap had grown from the fact-finding pass's own stated 27 missing
rows to 29 — two more exception types had been added to the tree in the
interval. Trusting an earlier count, however carefully derived, is
itself a source of staleness the moment any time passes between
deriving it and applying it.

`PROJECT_STATUS.md`'s own problem was different in kind: not incorrect
content so much as an ever-growing document nobody could keep current,
because keeping 9,068 lines synchronised with a live repository is not
a task anyone will actually do release after release.

## 5. The Design

**Every number was re-derived from source at this Work Package's own
base commit, not carried forward from the fact-finding pass.** Each
derivation command and its output are recorded in the report's own
Derivations Appendix — `grep -rEn '^\s*public interface \w+' src/
Tempest.Core --include=*.cs | wc -l` for interfaces, an equivalent
exception-class pattern, a `Singleton`/`AddInstance`/`AddDiscovered`
count against `TempestHost.cs` for Dependency Injection, a
per-namespace `grep`/`sort -u` pass for the Namespace Register, and so
on through Platform Services, Validation, the Feature Register, the
Release Register, and Repository Metrics.

Where a derivation surfaced a contradiction, the report states it as a
contradiction rather than silently overwriting the old number: the
Exception Register's 29-versus-27 gap is called out by name as "one
material contradiction of the fact-finding pass, found by re-deriving
at this Work Package's own base rather than the earlier one."

**`PROJECT_STATUS.md` was split, not merely trimmed.** Everything from
`## READY FOR WP14 UI/UX` onward (8,045 lines) was moved verbatim into
`docs/governance/Documentation/PROJECT_STATUS Archive (v0.5.0–v0.15.0).md`,
confirmed byte-identical against the original by `diff` with no output,
and the live file was rewritten as a short, current, re-derived
document 11,036 bytes long — under the plan's own 60 KB ceiling with
considerable margin. Nothing was deleted; every retained correction the
old file carried survives in the archive.

## 6. Alternatives Considered

**Trust the fact-finding pass's own numbers and apply them directly.**
Rejected once the Exception Register's own re-derivation disagreed with
it by two rows. A number derived at an earlier commit is a claim about
that earlier commit, not about this Work Package's own base — treating
it as current would have re-introduced exactly the staleness this Work
Package existed to remove.

**Delete `PROJECT_STATUS.md`'s historical sections outright, rather
than archive them.** Rejected — the plan's own scope explicitly forbids
rewriting history: "the archive keeps every retained correction." A
document that has been accumulating corrected knowledge for eight
releases is itself a historical record; the fix for its unwieldy size
is to relocate the history, not erase it.

**Extend this Work Package's own itemised scope to also correct the
Rejected Designs Register (45 vs. the source log's real 65) and
`Architecture Document Register.md`'s uncorroborated count.** Rejected.
Both were found during this Work Package's own derivation work but sat
outside its named registers; both are disclosed as residuals rather
than silently fixed (§6, items 5 and 6 of the report) or silently
ignored.

## 7. Why This Solution Was Chosen

Re-deriving from source at this Work Package's own base, rather than
trusting a prior pass, is the only design that actually closes `TD-57`
— a register whose numbers are correct today but were copied from
yesterday's derivation is still, structurally, a register whose
correctness depends on nobody having touched the source in between.
Archiving rather than deleting `PROJECT_STATUS.md`'s history satisfies
the plan's own explicit constraint and costs nothing: an archive file
nobody reads day to day is exactly as available to history as an
oversized live document nobody reads either, and considerably cheaper
to keep current.

## 8. Architectural Principles

- **A register is only as current as its own last re-derivation, never
  as current as the derivation it was copied from.** This is the
  precise lesson the Exception Register's 27-versus-29 gap teaches:
  even a careful, recent derivation goes stale the moment the source
  tree moves again.
- **Disclose a contradiction found while fixing something else, rather
  than quietly reconciling it.** The report names the fact-finding
  pass's own undercount explicitly instead of just writing 29 and
  moving on.
- **Splitting a document that has grown unmaintainable is safer than
  deleting from it**, provided the split preserves everything and the
  preservation is verified (the `diff`-confirmed byte-identical
  archive), not merely asserted.
- **Scope discipline extends to what is disclosed, not fixed.** Finding
  the Rejected Designs Register's own 45-vs-65 gap while deriving
  Repository Metrics did not obligate this Work Package to fix it —
  only to say so, in both the register and `Governance Index.md`,
  rather than let a second stale count survive undetected because
  fixing the first one made it visible.

## 9. Benefits

- Seven governance registers, the Feature Register, the Release
  Register, `Repository Metrics Register.md`, and `Product Roadmap.md`
  now match the repository at `v0.15.0`, each with a re-run derivation
  command any future reader can repeat.
- `PROJECT_STATUS.md` fell from 565,445 to 11,036 bytes — a 98% cut —
  while every retained correction it carried since `v0.5.0` survives,
  verified byte-identical, in the new archive.
- `TD-57` is Resolved and `TD-45` gains a pointer to `WP 16.1A`'s own
  report rather than continuing to describe a fix that had already
  landed elsewhere.
- The Exception Register correction (84, not "at least 55") and the
  Feature Register's extension from 27 rows covering one release to
  101 rows covering ten give the next Work Package that needs an
  accurate count something it can actually rely on.

## 10. Trade-offs

**What made the 554 KB deletion from `PROJECT_STATUS.md` safe was that
it was not a deletion at all — it was a verified move.** The archive
was diffed against the excised body and found byte-identical before
the live file was rewritten; had that diff shown any divergence, the
archive would not have been a safe substitute and the cut would have
been destructive. A `wc -c`/`wc -l` check alone, without the
byte-identical diff, would have made the same operation dangerous: it
would confirm the live file shrank, not that nothing was lost.

- Two residuals were disclosed, not fixed, because they fell outside
  this Work Package's own itemised registers:
  `docs/architecture/Platform Service Map.md` was not updated for the
  three new Platform Services rows, and the Rejected Designs Register's
  own 45-vs-65 gap (found while deriving Repository Metrics) was
  recorded but not corrected.
- `Architecture Document Register.md`'s own count (31) was not
  independently re-verified — explicitly outside this Work Package's
  scope, and `Governance Index.md`'s citation of it is therefore
  unchanged and unverified by this pass.
- The condensation applied to the Feature Register's nine new release
  sections (one row per major capability, rather than one row per Work
  Package) is a disclosed simplification for releases with many small
  Work Packages — a real loss of granularity, chosen deliberately over
  either omitting the releases entirely or bloating the register with
  dozens of small rows.

## 11. Common Mistakes

- Treating an earlier fact-finding pass's numbers as ground truth
  merely because they were carefully derived once — a re-derivation at
  a later base is the only thing that actually answers "is this true
  now."
- Deleting a large stale document instead of archiving it, on the
  reasoning that "it's all superseded anyway" — the archive here still
  needed a verification step (the `diff`) before the deletion could be
  trusted as lossless.
- Fixing a register whose staleness happens to be visible while
  leaving an equally stale sibling register untouched because nobody
  happened to look at it this time — the Rejected Designs Register and
  `Architecture Document Register.md` residuals are exactly this risk,
  disclosed rather than repeated.
- Silently widening scope to "just also fix" an adjacent stale register
  found mid-derivation, rather than disclosing it and leaving it for
  the Work Package that actually owns it.

## 12. Future Evolution

The two disclosed residuals — `Platform Service Map.md`'s missing
detail sections for the three new Platform Services, and the Rejected
Designs Register's 45-vs-65 gap — were both later picked up by the
`v0.16.0` review board and given their own Technical Debt rows,
`TD-126` and `TD-125` respectively, exactly the outcome disclosure is
supposed to produce: a residual that is recorded rather than silently
dropped gets its own tracked follow-up instead of being rediscovered
from nothing.

The review board also found a further recurrence of `TD-57`'s own
failure mode one Work Package later: `WP 16.3B` added
`IStateMigrationRegistry` to `TempestHost.cs`'s Phase 6 registration
block without a matching Dependency Injection Register row, and the
board's own remediation commit (`338d8ac`) corrected the DI Register's
totals from 55 statements / 50 named rows to 56 / 51. This is not a
failure of this Work Package's own derivation — its numbers were
correct against the tree it measured — but it is the clearest possible
demonstration of why re-deriving from the current source, every time,
rather than trusting a prior pass's count, is the only design that
actually holds: the review board's own new row, `TD-123`, names the
underlying gap directly — the Dependency Injection, Platform Services
and Validation registers have no machine check deriving them the way
`scripts/governance-healthcheck.ps1` already derives the Interface,
Exception and Namespace registers, so a register can go stale again the
very next Work Package and nothing catches it automatically.

## 13. Key Takeaways

- Re-derive from source at your own base commit; a number inherited
  from an earlier pass is a claim about that pass's base, not yours.
- A large document can be cut safely only when the cut is verified
  lossless, not merely smaller.
- Disclosing a residual that falls outside your own scope is what lets
  the next Work Package or reviewer find and close it — the Rejected
  Designs and Platform Service Map gaps this Work Package disclosed
  both became tracked debt rows within one review cycle.
- A register with no automated derivation check will drift again the
  moment a later Work Package touches the source it describes, exactly
  as `WP 16.3B` demonstrated one commit later.
