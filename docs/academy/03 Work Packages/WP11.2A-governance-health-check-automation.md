# WP 11.2A — Governance Health-Check Automation

## 1. Introduction

`WP 11.2A` (commit `14e24e6`) delivers `scripts/governance-healthcheck.ps1`
— TempestOS's first automated governance validation tool, closing
`FCR-0005` after `WP11.0B`'s roadmap reprioritised it (see that
retrospective's §5) following its own **seventh** independent
recurrence. A standalone, read-only PowerShell script with no production
project dependency, eight checks, Pass/Warn/Fail each. Its own account
in depth is `docs/academy/06 Engineering Standards/
06-governance-automation.md` (cited, not duplicated here) and
`docs/releases/v0.11.0/WP11.2A Governance Health-Check Tool.md`. This
retrospective is written retrospectively under `WP 16.2B`, grounded in
that report and commit `14e24e6`.

**Disclosed divergence, mirrored from `WP 11.1B`'s own retrospective**:
`WP11.0B`'s roadmap predicted this scope for `WP 11.1B`'s own slot; it
landed here instead, one Work Package later, under a different number —
named directly by `WorkPackages.md`'s own Status section as the
roadmap's own "recommendation, not approval" distinction exercised.

## 2. Purpose

Give the governance suite's own recurring staleness problem — caught
seven separate times by chance, never before by tooling — a mechanical
check, so an eighth recurrence is caught by a script rather than by
luck.

## 3. Background

`WP7.2A Recommended Programme.md` (`v0.7.0`) first identified this
pattern and correctly deferred `FCR-0005` — no real trigger had fired
yet. `WP 11.0A`'s own independent finding (the Governance Index's stale
"39 ADRs" claim against an actual 99) became the seventh, without having
read either of the prior six disclosures first — the evidence bar
`WP11.0B`'s roadmap required before reprioritising anything.

## 4. The Problem

Every prior catch of this drift pattern was a human noticing it by
chance during an unrelated Work Package. Nothing in the repository
checked, on demand or automatically, whether the ADR Register matched
`docs/adr/`, whether the Academy Index's own links actually resolved, or
whether `PROJECT_STATUS.md`'s own path references pointed anywhere real.

## 5. The Design

Eight checks, in a fixed order, each independently Pass/Warn/Fail: ADR
Register vs. `docs/adr/`; Academy Index vs. `docs/academy/` articles;
Release Register vs. git tags; Documentation Register path references;
`PROJECT_STATUS.md` references; `VERSION` vs. a planned release folder;
release-folder mandatory documentation; Governance Index orphans. A
crashing check reports as `Fail`, never a silent skip. `-RepoRoot` is a
parameter (never hard-coded), making the tool testable against an
isolated fixture without ever touching the tracked repository —
exactly the mechanism its own failure-detection demonstration depends
on. `WorkPackages.md` absence is `Warn`, never `Fail`, for a shipped
release — confirmed directly against `v0.9.0`/`v0.10.0`, both real,
fully-governed releases genuinely lacking the file, before writing the
rule. Not yet wired into the required `CI Gate` — a deliberate decision,
not an oversight (see §7).

**Three genuine tool defects found and fixed while building it**: a
crash on a multi-line-wrapped inline path reference (this project's own
prose hard-wraps, so a genuine path routinely straddles a line break);
an unhandled crash when git is available but the target is not a git
repository (found by actually running the negative case, not by
inspection); an empty "warned" count whenever exactly one check
produced a `Warn` (`(Where-Object {...}).Count` on a single-item result
returns `$null` in PowerShell, not `1` — found by reading the tool's own
output, not by code review).

**The tool's first real run against this repository, after all three
fixes, found genuine, real drift** — not fabricated to demonstrate
value: the Academy Index's own "Work Package Walkthroughs" section
stopped at `WP 7.3A`, roughly fifty real retrospectives unlinked (the
exact gap `WP 16.2B`, five releases later, is backfilling for `v0.11.0`
itself); three directories the Documentation Register described as
existing but git could not track because they were empty. Both
disclosed, neither fixed within this Work Package's own scope.

## 6. Alternatives Considered

A new .NET console project was considered and rejected in favour of
PowerShell — no new build-step dependency for the very pipeline meant to
verify builds, and consistency with `scripts/new-release.ps1`'s already
established tooling language.

## 7. Why This Solution Was Chosen

Wiring the check into CI's Job Summary (visible on every run) without
making it a required, blocking `gate` check is a considered decision:
the tool's own first run found real, pre-existing drift that predates
this Work Package. Making `governance-health-check` required today would
fail every future push immediately for a backlog this Work Package's own
scope — "implement the tool" — does not include clearing. Promoting it
is named as the natural next step once a follow-up closes the disclosed
drift, not deferred indefinitely or silently.

## 8. Architectural Principles

No production code, ADR, or architecture document was modified; no
GitHub repository setting was configured. A validation script choosing
what to check is process tooling, not a platform architectural decision
meeting Engineering Governance §5's criteria.

## 9. Benefits

TempestOS gains its first automated governance check, immediately
proven against the real repository (three genuine tool defects fixed,
two genuine real findings surfaced). `WP 11.3B`, later the same release,
re-runs this exact tool post-change and confirms the ADR Register check
correctly reports 100/100 automatically — no tool change required to
pick up `ADR-0101`.

## 10. Trade-offs

The tool's own free-text path extraction is deliberately scoped, not
exhaustive — disclosed directly as a real limitation (governance prose
contains many bare, context-relative filename mentions this tool
correctly cannot resolve without guessing). Its ~50-link Academy Index
gap and its untracked-directory findings were both left open by this
Work Package's own explicit scope boundary — "implement the tool," not
"fix everything it finds."

## 11. Common Mistakes

**Fixing a validation tool's own first real findings under the same Work
Package that built the tool.** This Work Package deliberately does not
do that — backfilling fifty links accurately is a substantial, separate
undertaking, and folding it into "implement the tool" would repeat
exactly the kind of scope creep this project's own discipline exists to
prevent. The finding was disclosed and left for a dedicated Work Package
— which did not actually happen until `WP 16.2B`, five releases later.

## 12. Future Evolution

`WP 11.3B` re-runs this tool as part of its own verification, confirming
it self-updates correctly. `WP 11.4A` fixes a real defect in this
script's own `-SummaryPath` resolution, found on the first real
GitHub-hosted CI execution. `WP 12.9.1` (`v0.12.0`) is the Work Package
that finally closes the Academy Index gap this tool first surfaced —
adding 58 entries at once, per that Work Package's own Academy Index
entry — though the `v0.11.0`-specific ten retrospectives this tool's own
Check 2 was still missing were not among them, closed only now, by
`WP 16.2B`.

## 13. Key Takeaways

- Test a validation tool against its own negative cases (an isolated,
  deliberately broken fixture), never only against the real repository —
  two of this tool's own three fixed defects were found exactly that
  way.
- A tool's first real run against a mature repository will likely find
  real, pre-existing drift — disclosing it, without fixing it under the
  same Work Package that built the detector, is a legitimate, complete
  resolution, provided the disclosure is followed up.
- A disclosed-but-deferred finding needs an actual follow-up Work
  Package eventually, or the gap simply persists — this tool's own
  Academy Index finding took five releases to close.
