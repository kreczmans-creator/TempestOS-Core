# WP 11.4B — Merge to Main & Release Process Correction

## 1. Introduction

`WP 11.4B` (commits `9196aa6`/`b203aef`) merges
`feature/v0.11.0-v1-architecture` into `main` and closes `v0.11.0` — but
first discovers, during its own required pre-merge verification, that
`v0.11.0`'s own tag repeats, verbatim, the `v0.10.0` tag-position defect
`WP 11.1B` had already disclosed and warned against. Written as a
genuine engineering Non-Conformance Report / Corrective and Preventive
Action (NCR/CAPA) record. Its full account is `docs/releases/v0.11.0/
WP11.4B Release Process Correction Report.md`. This retrospective is
written retrospectively under `WP 16.2B`, grounded in that report and
the two commits.

## 2. Purpose

Document a release-process defect — not a product, architecture, or code
defect — found before `v0.11.0`'s own release branch closed; the
one-time, Product-Owner-approved governance exception under which it was
corrected; the corrective sequence executed; and independent
verification of every claim.

## 3. Background

`v0.11.0` was tagged (`WP 11.9.0`) directly against
`feature/v0.11.0-v1-architecture`'s own tip commit, before any merge to
`main` existed — mirroring `v0.10.0`'s own tag-creation *mechanics*
without cross-checking that `v0.10.0`'s underlying *sequence* was itself
the defect `WP11.1B Engineering Workflow.md` had already, in the same
release, disclosed.

## 4. The Problem

`WP 11.4B`'s own required pre-merge verification — checking where the
tag actually resolved relative to `main` before performing the merge,
not assumed correct because it had already been created — found
`git merge-base --is-ancestor v0.11.0 main` returned false. Governance
§7 items 1 and 3 (a release is cut only from `main`; Build Gate/Test
Gate must pass on `main` itself, immediately before tagging) were both,
as a direct consequence, unsatisfied at the moment `v0.11.0` was tagged
— identically to `v0.10.0`. Per the task's own explicit instruction at
the time ("stop and report, do not correct"), no further repository
action was taken until the finding was reported and the Product Owner
had explicitly reviewed and authorised a correction.

## 5. The Design

**Root cause**: a precedent was copied at the wrong level of
abstraction — `WP 11.9.0`'s own tag-creation step reproduced `v0.10.0`'s
tag *format* correctly but did not re-derive *when* a tag should be
created from Governance §7 itself. The two facts (the `v0.10.0`
disclosure, and the governance rule it reinforced) both already existed
in the repository at the moment of action; the error was a missing
cross-check between an available fact and an action about to be taken,
not a missing fact. No mechanical gate existed to catch it — branch
protection was not yet configured, and nothing verified a new tag's
ancestry before or after it was pushed.

**Governance exception**: per explicit Product Owner authorisation,
Governance §7 item 4's absolute "a tag, once created and pushed, is not
moved or recreated" is qualified by a narrow, explicitly-scoped
exception — a documented release-process defect identified *before*
closure of the release branch, requiring explicit Product Owner
approval, a documented Release Process Correction Report, and complete
traceability. Explicitly bounded: applies only to a defect in the tag's
own mechanical *position*, never to content, build, or test evidence;
applies only before the release branch closes (`v0.10.0`'s own case,
found after its branch had long closed, is explicitly, textually **not**
reopened — it remains permanent, disclosed history).

**Corrective action, each step independently verified before the
next**: outstanding commits pushed; local and remote `v0.11.0` tag
deleted; `main` checked out and merged with the feature branch
(`--no-ff`, clean, no conflicts) → merge commit `4b1fb16`; Build
Gate/Test Gate re-verified **on `main` itself**, immediately before
tagging — Governance §7.3 satisfied as literally written, for the first
time this release; a new annotated tag created on the merge commit,
reusing the original annotation verbatim (captured before deletion via
`git for-each-ref`) — the tag's own text is therefore byte-identical to
what Product Approval originally reviewed, only its target commit
changed; `main` and the corrected tag both pushed.

## 6. Alternatives Considered

Leaving the tag's mechanical position uncorrected and disclosing it
permanently, mirroring `v0.10.0`'s own precedent, was implicitly the
default absent Product Owner authorisation — rejected here specifically
because the defect was caught *before* the release branch closed, the
one condition under which `v0.10.0`'s own precedent does not apply and a
correction genuinely does not rewrite already-relied-upon history.

## 7. Why This Solution Was Chosen

The distinction the exception draws — a defect in the tag's own
mechanical position, found before closure, versus a defect in the
release's own content, found after — is not cosmetic: a release branch
that has already closed has, by definition, already had its own tag
durably referenced for however long it has been closed; `v0.11.0`'s own
correction was executed within the same working session the defect was
created in, before the branch that produced it had merged anywhere.

## 8. Architectural Principles

No production, Domain, or architecture change was made — the only
production-adjacent files touched were three governance documents
(wording only: `Engineering Governance.md` §7, `WP11.1B Engineering
Workflow.md` §10, `05-release-engineering.md`) and the routine
documentation updates named in `WorkPackages.md`'s own entry.

## 9. Benefits

`main` is now the authoritative development baseline for the first time
this release — the entire ten-commit `feature/v0.11.0-v1-architecture`
history merged via a genuine, non-fast-forward merge commit. `Build &
Test`/`CI Gate` both genuinely pass on real infrastructure for both the
`main` push and the corrected tag push — four consecutive real CI runs
(two from `WP 11.4A`, two here) showing the identical, correct pattern.
`release.yml` independently rebuilt, retested, and republished a fresh,
correctly-tagged, non-draft GitHub Release.

## 10. Trade-offs

**A residual, disclosed, unresolved artifact**: deleting the original
tag orphaned its associated GitHub Release object into a draft
(discovered directly, not assumed — an initial `GET` for the tag
returned HTTP 404 before this was understood) at a synthetic
`untagged-...` URL; `release.yml`'s own re-run created an entirely new
Release object rather than reattaching it. The orphaned draft (`id
368605775`) still exists, not deleted — cleaning it up was outside this
Work Package's own explicitly authorised sequence, and deleting a GitHub
Release, even a draft, is named as an outward-facing action deferred to
a separate, explicit instruction rather than taken unilaterally.

## 11. Common Mistakes

**Copying a precedent's own command shape without re-deriving whether
the precedent itself was correct.** This is, by the report's own
account, the direct root cause: `v0.10.0`'s tag-creation sequence was
mirrored as a template at the moment `v0.11.0` was tagged, without
cross-checking the very document (`WP11.1B`, written earlier in this
same release) that had already established the precedent was itself
defective.

## 12. Future Evolution

`WP 11.4B`'s own §11 "Preventative Action" recommends a tag-ancestry
check be added to `scripts/governance-healthcheck.ps1` — converting the
check that caught this defect from a human/agent-remembered
cross-reference into a mechanical one, named as a concrete `v0.12.0`
candidate. Whether that check was actually added is outside this
retrospective's own sourced evidence (`v0.12.0`'s own retrospectives are
out of `WP 16.2B`'s scope) to confirm.

## 13. Key Takeaways

- A precedent's own command *shape* and its underlying *correctness* are
  two different things — copying the first without re-checking the
  second is exactly how this defect recurred within the same release
  that had already disclosed it once.
- "The tag exists, is annotated, is pushed, and a Release was published
  from it" is a different claim from "the tag is correctly positioned" —
  this defect occurred precisely because the former was verified while
  the latter was not, and the two are easy to conflate when every
  visible signal looks like success.
- A governance rule's own absolute wording ("never moved") can still
  need a narrow, explicit, disclosed, Product-Owner-approved exception —
  the exception itself, written down with its own bounds, is what keeps
  it from becoming a silent precedent for the next defect.
