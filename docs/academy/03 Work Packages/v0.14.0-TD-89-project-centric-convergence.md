# TD-89 — Project-Centric Convergence: One Definition of Project Membership

## 1. Introduction

`cd26b8f` corrected a too-strong reading of `TD-84`'s own product decision:
Engineering had been made reachable only from an open project, and the
authoritative model has two branches — projects as primary organisational
context, and standalone calculation sets as a first-class workflow
requiring none. A pre-`v0.14.0` engineering-body-of-work row; produced the
companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/35-project-centric-convergence.md`.

## 2. Purpose

To fix three related defects the Product Spine left: standalone
engineering work had no route; project membership was answered by direct
children only, so a two-level product structure looked almost empty; and
the shell showed only the three modules the platform could serve, making
the product look smaller than designed.

## 3. Background

`ShellLocation.ProjectId` had been treated as an absence to special-case
around rather than as the scope value it actually is. `ProjectMembership`
did not exist yet — contents were resolved from direct children only, so a
Part inside an Assembly inside a Project was not counted as being in the
project.

## 4. The Problem

An engineer checking a bolt should not have to invent a project first, and
`TD-84`'s enforcement made them do exactly that. Separately, the normal
product structure — several levels deep — made every project look nearly
empty, because membership stopped at the first level.

## 5. The Design

`ShellLocation.ProjectId` *is* the engineering scope: non-null means
inside that project, null on `ShellArea.Engineering` means standalone —
restating the load-bearing invariant rather than weakening it: a location
that claims a project must agree with `IProjectContext`; a location that
claims none cannot disagree with anything.
`GoToStandaloneEngineeringAsync` deliberately does not close the open
project, because standalone is a different scope, not a reason to discard
the one the user is in. `IEngineeringScope` is the real derived state the
Engineering Workspace reads, computed from navigation state and the live
graph, never cached and never inferred by a view. `ProjectMembership`
walks the durable `IHasParent` chain (durable since `TD-85`) upward:
reach a Project and you belong to it, reach nothing and you are
standalone — no `ProjectId` field added to the domain; both
`IProjectDirectory.ListProjectContentsAsync` and the engineering scope
resolve through the same function, so the platform has one answer to
"what is in this project". `ShellAreas`/`ProjectAreas` declare the
product's designed module and area sets and which have a capability
behind them, as application state a test asserts rather than a caption a
view renders — reversing the earlier choice to omit unbuilt modules, since
omitting them made the product look smaller than designed and faking them
would have been worse. `DeclaredCapabilityView` gives anything unbuilt a
real, navigable, project-aware surface naming what is missing and the
debt tracking it.

## 6. Alternatives Considered

None recorded as separately rejected beyond the reversal of the earlier
"omit unbuilt modules" choice, which the row explicitly states was worse
than declaring them honestly with `DeclaredCapabilityView`.

## 7. Why This Solution Was Chosen

Because scope as a value, rather than an absence handled by a switch,
meant standalone engineering needed no special case in the navigator — it
falls out of the same `ProjectId` field the project-scoped path already
used.

## 8. Architectural Principles

One definition of project membership, derived from the domain's own
`IHasParent` chain rather than duplicated as a stored field on each type
that needs to answer "am I in this project" — the principle this row
states once and every later surface in the release reuses without
re-deciding it.

## 9. Benefits

Five mandatory journeys through the real `MainWindow` (new project;
existing project with a real calculation and validation; standalone
calculation with no project, surviving a reopen; context restoration
across a restart; a full navigation circuit), plus 17 integration tests
and 3 docking-seam tests; six mutations run and killed, including "make
Engineering require a project again", which fails the standalone journey
specifically. Two tests that encoded the superseded rule were inverted
and strengthened, never deleted.

## 10. Trade-offs

`TD-72`'s full Option-C docking, `TD-79`/`TD-81`/`FCR-0056`/`TD-76` (the
declared-but-unbuilt modules and areas) and `TD-80` (the drawing viewer)
remain under this grouping, deliberately not built here — this row
verifies and pins the seam they will use rather than building them.

## 11. Common Mistakes

Enforcing a product rule ("project-centric") more strongly than the
product decision actually intended, and only discovering the gap when a
real workflow (a standalone bolt check) had nowhere to go.

## 12. Future Evolution

The Tasks, Risks/Issues/Decisions, and Timeline surfaces later in this
release each reuse `ProjectMembership`'s transitive parent-chain
definition rather than inventing a `ProjectId` field of their own — the
same convergence this row establishes, repeated by design each time.

## 13. Key Takeaways

- A strict reading of a product decision can be more literal than the
  decision intended; check against the real workflows before enforcing it.
- Scope expressed as a nullable value, rather than a boolean plus a
  special case, removes the special case entirely.
- Derive membership from the domain's existing structure rather than
  adding a redundant field — and reuse that derivation everywhere the
  question is asked.
