# WP 13.0A — Plugin & Registration Trust Isolation Architecture

## 1. Introduction

`v0.13.0` — "Trust & Deployment Hardening" — is TempestOS's first
conditional release: `WP11.0B Architecture Roadmap.md` §3 stated it would
"only enter the plan if `WP 11.2A` / the Product Owner commits `v1.0`
scope to third-party plugins and/or REST deployment beyond a trusted
local network. Otherwise… this release is skipped entirely." Neither
trigger had fired as of `v0.12.0`'s own close — `src/Plugins/` remained
empty (`WP 12.9.1`'s own tracked marker `README.md`), and no `v0.12.0`
Work Package touched REST API scope. The Product Owner has now explicitly
committed both, confirmed directly at `WP 13.0.0`'s own branch
establishment, firing the condition and commissioning `feature/v0.13.0`.
`WP 13.0A` is the roadmap's own first predicted item on that branch
(`docs/releases/v0.13.0/WorkPackages.md`): "Plugin & Registration Trust
Isolation Architecture (`A-3`/`FCR-0001`)."

This retrospective covers two composed architecture documents, produced
by parallel sibling workstreams and integrated into one coherent package:
`docs/architecture/Plugin Platform Architecture.md` (dependency graph
resolution, a new Host-owned `IPluginRegistry`, plugin lifecycle, DI
service-registration boundaries — `ADR-0107`, `ADR-0108`, `ADR-0109`) and
`docs/security/Plugin Trust & Isolation Architecture.md` (a four-tier
trust model, a capability model extending `IPermissionEvaluator`, a
detached signature scheme, and the isolation-boundary decision —
`ADR-0110`, `ADR-0111`, `ADR-0112`) — six new ADRs in total, and nineteen
new Rejected Designs entries (`RD-0046`–`RD-0064`).

## 2. Purpose

To design, before any code changes, the answer to the question three
already-shipped platform services have carried as open, explicitly
disclosed debt since `v0.6.0`: what is a loaded plugin — and,
inseparably, a plugin-sourced module's own registration — actually
*trusted to do*, once its assembly is resident in the process and its
DI-container access is identical to a first-party module's. `WP 6.1`
(Permissions & Identity) built the single enforcement mechanism
(`IPermissionEvaluator`/`ADR-0044`) this design applies, deliberately
declining to retrofit it into plugin loading itself — this Work Package
is the "future, explicitly-scoped Work Package" that decision named. A
second, equally real purpose, carried by the sibling Plugin Platform
workstream: answer the shape questions `Plugin Manifest Architecture.md`
deliberately left as non-goals (dependencies between plugins, a queryable
catalogue, upgrade/uninstall, configurable conventions) now that a real
trigger exists to answer them responsibly, without which the trust design
would have had nowhere to attach its own manifest fields.

## 3. Background

Three technical debt items, one root architectural gap, have carried the
identical revisit trigger since their own disclosure:

- **`TD-09`** — no isolation boundary exists between a loaded plugin and
  a first-party module; a plugin gets identical DI-container trust once
  its assembly loads (`Technical Debt Register.md`, disclosed `WP 5.0S`,
  scope widened `WP 5.1A` to also cover the Command Framework's own
  registration path).
- **`TD-10`** — `NavigationService.Unregister` performs no ownership
  check; any caller can unregister any other component's navigation item
  by Id (disclosed `WP 5.0S`, Finding `NAV-1`).
- **`TD-11`** — Command/Navigation registration-order squatting: "first
  registration wins" rejects a later duplicate but never establishes the
  first registrant was the well-known Id's intended owner; because
  `ModuleLifecycleManager` initialises modules in ascending-Id order, a
  plugin-loaded module whose Id sorts earlier can legitimately claim a
  well-known Id before its real, first-party owner registers — entirely
  within the registry's own stated rules (disclosed `WP 5.1A`, Finding
  `CMD-1`).

`WP 6.1` built `IPermissionEvaluator` (`ADR-0044`) as the platform's
single authorization enforcement point, explicitly *not* retrofitting it
into any of the three call sites above — a deliberate scope boundary, not
an oversight, recorded in `ADR-0044` itself: "a future, explicitly-scoped
Work Package can close each by adding one `RequirePermission` call at the
relevant point… without inventing a new authorization mechanism first."

`docs/governance/Future Capability Register.md`'s `FCR-0001` ("Plugin &
Registration Trust Isolation Retrofit") merges these three debt items
with `Security Roadmap.md` items 1, 2, and 10 into one capability —
explicitly recorded as one root cause, three affected surfaces, not three
unrelated gaps (Governing Rule 4). `Security Roadmap.md` item 1 names the
concrete shape of this Work Package's own brief: evaluate and decide
among a separate `AssemblyLoadContext` per plugin, a manifest-declared
enforced capability/permission scope, code-signing verification before
load, or some combination — "a dedicated Architecture Work Package," with
its own ADR and a genuinely considered rejected alternative, "not a quiet
code change." Item 10 explicitly pairs the Command/Navigation Id
ownership question with item 1's own isolation-boundary work, "since both
share the same root precondition and the same future Architecture Work
Package is the natural place to resolve them together" — the basis for
this single Work Package covering both `TD-09` and `TD-11` together, not
as separate efforts.

Separately, `Plugin Manifest Architecture.md` (`WP 4.2`) left a distinct
set of non-goals unaddressed: inter-plugin dependencies, package
management/upgrade, a queryable plugin catalogue, and configurable
plugins-root/manifest-name conventions (`TD-06`) — each explicitly, "a
real, plausible future need — none has enough real understanding behind
it yet to design responsibly." The same Product Owner commitment that
fired `FCR-0001`'s trigger also makes these real, near-term questions,
covered by this Work Package's sibling Plugin Platform workstream.

## 4. The Problem

1. **What isolation mechanism actually closes `TD-09`** — a separate
   `AssemblyLoadContext` per plugin, a manifest-declared enforced
   capability/permission scope consumed via `IPermissionEvaluator`,
   code-signing verification before load, or some combination — and why,
   evaluated against real alternatives rather than assumed?
2. **How does `NavigationService.Unregister` (`TD-10`) determine
   ownership** without redesigning `NavigationService`'s already-shipped
   `v0.5.0` public contract?
3. **What ownership/priority/reservation model closes `TD-11`** for
   Command and Navigation Id registration, given `ModuleLifecycleManager`'s
   existing ascending-Id initialisation order is itself approved, shipped
   architecture not up for redesign?
4. **Does this design require changing any already-shipped, approved
   public interface** (`IModule`, `PluginManifest`, `INavigationService`,
   `ICommandRegistry`, `IPermissionEvaluator`) — and if so, is that
   change additive, per this project's own "do not redesign approved
   architecture absent a genuine defect" discipline?
5. **What must be decided, formally, via ADR, before implementation (`WP
   13.0B`) begins** — mirroring exactly how `WP 4.2`'s own architecture
   phase preceded `WP 4.2`'s own implementation?
6. **What does a plugin depend on, and how is that resolved** without a
   new Host Lifecycle phase — a question `Plugin Manifest Architecture.md`
   explicitly declined to answer in `v0.4.0`?
7. **What is a plugin, once loaded, actually observable as** — is there
   any queryable record of what was attempted and what happened, or does
   that information exist only in the log?
8. **How does a plugin get upgraded or removed**, given `ADR-0015`
   already establishes the Host itself cannot be restarted in-process?

## 5. The Design

Two composed documents, each owning a distinct half of the same problem
and explicitly cross-referencing the other rather than duplicating it.

**`Plugin Platform Architecture.md` (`ADR-0107`–`ADR-0109`) designs the
plugin platform's *shape*.** `PluginManifest` gains a v2 set of fields,
every one optional and additive — a v1-shaped manifest remains fully
valid: `Dependencies` (`IReadOnlyList<PluginDependency>`, each an `Id`,
`MinimumVersion`, optional `MaximumVersion`), and three fields whose
*shape* only this document fixes, with semantics deferred entirely to the
sibling document — `RequestedCapabilities` (`IReadOnlyList<string>`,
opaque, unvalidated), `Publisher` (`string?`, free text, unverified), and
`Signature` (`string?`, an opaque encoded blob). Dependency resolution
happens entirely within the existing Plugin Discovery phase (3.1, no new
phase) via a fixed-point reduction over the individually-valid candidate
set, followed by a topological sort determining Plugin Loading's own load
order — a missing dependency, an incompatible dependency version, or
membership in a cycle isolates exactly the affected plugin(s), extending
`ADR-0025`'s table with three new categories (12–14), never Host-fatal. A
new Host-owned collaborator, `IPluginRegistry`/`PluginRegistry`, records a
`PluginRegistryEntry` (`Id`, `Name`, `Version`, `PluginRegistryState`,
`Detail`) for every candidate this run attempted — **never DI-public**,
mirroring `IRuntimeModuleManager`'s own `ADR-0017` boundary exactly — and
is projected read-only through one new property on the already-shipped
`IDiagnosticsProvider` (`WP 5.2`, `ADR-0039`): `Plugins`, reusing the
identical `Func<T>`-accessor pattern already established for
`Modules`/`HostedServices`, not a new service. Plugin lifecycle (`ADR-0108`)
covers Load (unchanged from `WP 4.2`), Upgrade, and Uninstall as
file-system operations taking effect on the *next* process start — a
direct consequence of `ADR-0015`, since Plugin Discovery carries no memory
across runs — with **live, in-process unload explicitly, formally
declared a non-goal for `v0.13.0`**, reserving but not building a
`Loaded → Unloading → Unloaded` state-machine seam a future per-plugin
isolation mechanism could someday use. Service registration (`ADR-0109`)
introduces no new DI container capability at all: a plugin's `IModule` is
constructor-injected exactly as any discovered module's is (`ADR-0027`),
and a plugin contributes capability to the rest of the platform only
through the same DI-public, imperative surfaces every module already has
— `IEventBus`, `INavigationProvider`, `ICommandRegistry` — called during
its own Module Initialisation step, never through a plugin-specific
registration API or raw `IServiceCollection` access. The plugins root
directory and manifest file name, fixed since `WP 4.2` (`TD-06`), become
configurable (`Runtime:Plugins:RootDirectory`/`ManifestFileName`/
`Disabled`), exercising a seam `ADR-0026` already anticipated rather than
opening a new one — closing `FCR-0010`/`TD-06`.

**`Plugin Trust & Isolation Architecture.md` (`ADR-0110`–`ADR-0112`)
designs the trust *semantics* layered onto that shape.** A **four-tier
trust model** — First-Party (compiled-in, or signed against TempestOS's
own publisher certificate; unrestricted, not subject to any capability
check — the guarantee that this design changes nothing observable for any
actor that exists today), Verified-Signed (signed against any other
trust-store certificate; granted exactly what `RequestedCapabilities`
declares), Unsigned-Local (no signature; loads only if
`Plugins:AllowUnsignedLoad` is explicitly `true`, default `false`;
capability grants clamped to a fixed, low ceiling —
`plugin.navigation.register`/`plugin.commands.register` only, regardless
of what is requested), and Untrusted (a signature present but failing
verification — never loads, never silently downgraded to Unsigned-Local)
— assigned exactly once, at Plugin Loading, immutable for the process
run. A **capability model** reusing `Permission`/`IPermissionEvaluator`
directly (`ADR-0044`, not a parallel mechanism): a closed set of
`plugin.*`-namespaced keys (`plugin.navigation.register`,
`plugin.commands.register`, `plugin.di.register`,
`plugin.events.publish:<Type>`, `plugin.services.resolve:<Type>`),
enforced two ways — **statically**, at Plugin Loading: a capability
eligibility check against the assigned tier's ceiling, and a
constructor-conformance check reflecting over the plugin's own `IModule`
types independently, *before* Module Discovery ever runs, rejecting any
constructor parameter type outside the fixed baseline
(`ILogger`/`IConfigurationProvider`/`IDiagnosticsProvider`) plus the
plugin's own granted `plugin.services.resolve:*` declarations — the
concrete mechanism that closes the "resolve a given service" half of
`TD-09`, with zero change to `TempestServiceProvider`'s resolution logic,
Module Discovery, Registration, or Lifecycle; and **dynamically**, at the
call site: one `IPermissionEvaluator.RequirePermission` call added to
`NavigationService.Register`/`Unregister`, the Command Framework's
registration path, and `IEventBus.PublishAsync`, skipped entirely — not
merely satisfied — when the ambient component principal is `null`/
First-Party, so every actor that exists today observes zero behavioural
change. A new, second identity axis, `ICurrentComponentAccessor`
(`IPrincipal? Current { get; }`, `AsyncLocal<T>`-backed, scoped via
`IDisposable BeginScope(...)` around every Host re-entry into plugin-owned
code — `InitialiseAsync`/`StartAsync`/`StopAsync`/`DisposeAsync`, an event
subscriber invocation, a command handler invocation), answers "which
loaded component's own code is currently executing" — distinct from
`ICurrentPrincipalAccessor`'s existing ambient *user*-principal axis, and
precisely the layered, request/call-scoped accessor `ADR-0044` itself
anticipated as its own future extension, not a revision of it. A
**detached, hash-based signature** (`ADR-0112`) — `SHA-256` over the
canonical manifest JSON (minus `Signature` itself) concatenated with
`SHA-256` of the declared assembly's raw bytes, signed with `RSA-PSS`/
`SHA-256`, verified using .NET's own `System.Security.Cryptography`
primitives (zero new dependency) — entirely at Plugin Discovery (Phase
3.1), before any `Assembly.LoadFrom` call, against a flat-file
`TrustedPublishers/` certificate store (mirroring the plugins-root
convention's own "fixed now, configurable later" precedent). No network
call, no CRL/OCSP check. Finally, the **isolation-boundary decision**
(`ADR-0110`): **capability scoping, entirely in-process — not a separate
`AssemblyLoadContext`, not process separation** — stated with an explicit,
disclosed limit (not a hard sandbox; does not defend against an actively
adversarial assembly using reflection to bypass its own declared trust)
and an explicit consequence stated plainly for the sibling document: **this
does not enable per-plugin unload**; `ADR-0108`'s own reserved lifecycle
seam stays reserved, unused, under this design.

**The trust-ordered registration rule directly closes `TD-10` and
`TD-11`/`CMD-1`.** Applied identically to `NavigationService.Register`/
`Unregister` and the Command Framework's registration path. Ownership
(`TD-10`): the registry captures the caller's component principal
out-of-band at `Register`, with no change to `NavigationItem`'s or
`CommandDescriptor`'s own public shape; `Unregister` rejects a caller
whose own component principal does not match the recorded owner, via a
reserved override permission held only by First-Party by construction.
Priority (`TD-11`/`CMD-1`): "first registration wins" becomes "first
registration wins **among registrants of the same trust tier**" —
unchanged for every registrant that exists today, all First-Party — with
a higher-trust-tier registration always evicting and replacing a
lower-tier one regardless of order, logged loudly at Warning, never
silently, rather than rejected as an ordinary duplicate.

Four new `PluginRegistryState`/failure categories tie both documents
together: a sixth `PluginRegistryState.TrustDenied` value (`Plugin
Platform Architecture.md`'s own enum, explicitly reserved for and named by
the sibling document, not invented speculatively) records `ADR-0112`
categories 15–17 (signature fails to verify; unsigned and not allowed; a
requested capability or constructor parameter outside the tier's
ceiling); category 18 (a *running* plugin attempts a capability-gated
operation it was not granted) has no registry state at all, since it
occurs long after Plugin Loading has finished. All four are Isolated,
never Host-fatal, continuing `ADR-0025`'s own "isolate failure, not
trust" discipline extended, for the first time, to a genuine trust
violation rather than only a crash.

## 6. Alternatives Considered

Recorded in full, per-ADR, in each of the six new ADRs; the two most
consequential are worth restating here because each was seriously
considered, not merely listed for completeness.

**A separate `AssemblyLoadContext` (ALC) per plugin** — the Security
Roadmap's own first-named option, and a real, available .NET mechanism.
Rejected as the *trust* boundary specifically, for one concrete, decisive
reason: `AssemblyLoadContext` is not a security boundary in modern .NET.
Code Access Security and AppDomain-based sandboxing were removed entirely
from .NET Core; an ALC governs assembly *identity and unload*, not
*privilege*. A plugin loaded into its own ALC still runs with the full
process's own OS privileges, can still call any public API of any type
loaded anywhere in the process (the exact fact `ADR-0026` already depends
on — `AppDomain.CurrentDomain.GetAssemblies()` already returns assemblies
across every ALC in a single-AppDomain .NET Core process), and can still
hold and use any DI-resolved service reference it was ever given. Its one
genuine benefit — enabling unload — is explicitly a non-goal both this
document and the already-implemented Plugin Manifest Architecture share;
building it now for a benefit this release does not use is exactly the
"security theatre ahead of a real need" `Security Principles.md`
Principle 7 warns against.

**Separate OS process per plugin, with IPC to the Host** — the only
mechanism in modern .NET providing a *genuine* privilege boundary.
Seriously considered, rejected as disproportionate to the actual,
disclosed threat: the trigger that opened this Work Package is a Product
Owner commitment to *vetted, signed, commercial* third-party plugins, not
a marketplace accepting anonymous, actively adversarial publishers.
Process isolation would also require redesigning DI resolution, event
dispatch, and every module constructor-injection point across an IPC
boundary — an order of magnitude larger than this Work Package's own
brief. Revisit trigger: TempestOS is ever asked to run genuinely
adversarial, unvetted third-party code rather than signed, accountable
commercial plugins.

**Code-signing alone, with no capability scoping**, and, separately, **a
manifest-declared capability scope alone, with no signing** — each
seriously considered as the cheaper, single-mechanism option, and each
rejected as an incomplete answer on its own: signing without capability
scoping says nothing about what a legitimately-signed plugin may then do
once loaded; capability scoping without signing makes "the manifest
declares X capabilities" an unverifiable, self-asserted claim with no
accountability behind it. The two solve different problems (*who* vs.
*what*) and are complementary, not substitutable — the chosen design
adopts both.

The remaining decisions — Host-fatal circular dependency (`RD-0046`,
rejected), a dedicated cascade-notification step for transitive
dependency failure (`RD-0047`, rejected), soft/optional plugin
dependencies (`RD-0048`, rejected), automatic restart/backoff for a
failed-after-loading plugin (`RD-0050`, rejected, mirroring `RD-0029`'s
identical reasoning), a dedicated `IPluginDiagnosticsProvider` instead of
extending `IDiagnosticsProvider` (`RD-0051`, rejected), making
`IPluginRegistry` itself DI-public (`RD-0052`, rejected, mirroring
`ADR-0017` directly), and a restricted plugin-scoped `IServiceCollection`
registration API (rejected in `ADR-0109` on ordering grounds — plugin code
does not run until Module Initialisation, after the container is already
built and frozen, `RD-0043`) — are each recorded in full in their owning
ADR and in the Rejected Designs Log (`RD-0046`–`RD-0064`), not repeated
here.

## 7. Why This Solution Was Chosen

Every non-obvious decision in both documents traces back to the same
sentence `Plugin Manifest Architecture.md` established: "the Manifest
describes; the Runtime decides." The trust design extends it one step
further rather than replacing it — the Manifest now also describes what a
plugin *wants* to do (`RequestedCapabilities`) and *who signed it*
(`Signature`), still inert data, interpreted nowhere inside the manifest
itself; the Runtime still makes every consequential decision (which tier,
which capabilities are actually granted, whether a call is permitted)
through the platform's one existing enforcement point, `IPermissionEvaluator`
(`ADR-0044`), rather than a second, parallel authorization mechanism.
Choosing capability-scoped, in-process enforcement over `AssemblyLoadContext`
or process separation is the identical "Reuse Before Invention" reasoning
`Plugin Manifest Architecture.md` already applied to `ModuleDescriptor`
and `IFrameworkDiscoveryService`: apply the platform's own existing
authorization mechanism to a new principal kind, rather than build a
second, structurally different trust mechanism just because the *actor*
(a plugin) is new, even though the *question* (is this action permitted)
is not. The Plugin Platform half of the design was chosen by the same
test `Plugin Manifest Architecture.md` originally applied to every
manifest field: challenge each candidate capability (dependencies, a
registry, configurable conventions) against a real, current consumer —
the confirmed third-party plugin commitment — rather than speculating
ahead of it, exactly the discipline that excluded `Author`/`Description`/
an entry-point-type field from the original `v0.4.0` manifest.

## 8. Architectural Principles

- **The Manifest describes; the Runtime decides** — extended, not
  replaced: the Manifest now also describes trust-relevant intent
  (`RequestedCapabilities`, `Publisher`, `Signature`); every consequential
  decision remains the Runtime's alone.
- **Reuse Before Invention, applied to authorization** — the capability
  model is `Permission`/`IPermissionEvaluator` (`ADR-0044`) directly,
  namespaced under `plugin.*`, not a second, parallel authorization
  mechanism invented because the actor is new. The Plugin Registry
  extends `IDiagnosticsProvider` (`ADR-0039`) rather than introducing a
  new service, for the identical reason.
- **Fail Closed** — an unsigned plugin loads only if an operator has
  explicitly set `Plugins:AllowUnsignedLoad` to `true`; default `false`.
  Mirrors `ADR-0043`'s identical fail-closed precedent for an
  unrecognised identity.
- **Fail Fast** — signature verification and capability eligibility are
  both checked at Plugin Discovery/Loading, before any plugin code
  executes, not discovered awkwardly later via a capability-gated call
  failing at an arbitrary point in the plugin's running life.
- **Avoid Speculative Design** — a DI resolution interceptor, wildcard
  capability keys, automated quarantine, ALC-based unload, and online
  CA/CRL checking are all named, explicit non-goals with their own
  revisit triggers, not built ahead of real, demonstrated need.
- **Do Not Redesign Approved Architecture Absent a Genuine Defect** —
  `NavigationService`'s and `ICommandRegistry`'s own public shapes are
  unmodified; ownership and priority are captured out-of-band, not by
  changing `NavigationItem`'s or `CommandDescriptor`'s own public fields.

## 9. Benefits

- A complete, ADR-ratified design exists for all three previously-open
  debt items before any code changes — the same benefit `WP 4.2A`/`4.2B`/
  `4.2C` produced ahead of `WP 4.2`'s own implementation, now produced for
  the trust retrofit `ADR-0044` explicitly deferred.
- **`TD-09`/`TD-10`/`TD-11` move from "mechanism exists, not yet applied"
  to "design resolved, retrofit remains open until `WP 13.0B`."** This is
  design resolution, not implementation — stated plainly here, not
  overclaimed; see Trade-offs, below, and §11.
- **Zero behavioural change for every actor that exists today.** Every
  first-party module — the only kind that has ever run — is First-Party
  tier by construction, not subject to any capability check; every
  dynamic enforcement call is skipped entirely, not merely satisfied,
  when the caller is `null`/First-Party.
- **No new runtime dependency.** Dependency graph resolution is pure
  computation over already-validated manifests; signature verification
  uses .NET's own `System.Security.Cryptography` primitives — consistent
  with `ADR-0005`'s reuse-first mandate.
- Six ADRs are now named and scoped precisely (`ADR-0107`–`ADR-0112`)
  rather than left to be decided ad hoc, under time pressure, during
  implementation — mirroring exactly the discipline `WP 4.2`'s own
  architecture phase established for this same document once before.
- `TD-06`/`FCR-0010` (configurable plugins root/manifest name) is closed
  at the design level as a direct side effect of this Work Package's own
  brief, not a separately-scoped effort.

## 10. Trade-offs

- **This is documentation only** — nothing here is enforced by a
  compiler, test, or running code yet. `WP 13.0A` wrote zero
  implementation code, confirmed directly (`git status` shows only
  documentation changes on this branch for this Work Package's own
  commits).
- **This is not a hard sandbox**, disclosed plainly, not overclaimed. A
  sufficiently determined plugin could, in principle, use reflection
  in-process to reach past a `RequirePermission` call site. This design
  closes the *ordinary, cooperative* API surface — exactly what `TD-09`/
  `TD-10`/`TD-11`/`CMD-1` describe — not an actively adversarial assembly
  willing to bypass its own declared trust; that requires OS-process
  isolation, explicitly out of scope, with its own named revisit trigger.
- **`Plugins:AllowUnsignedLoad` is a single, global switch, not
  per-plugin.** An operator enabling it for one legitimately unsigned
  internal tool also permits every other unsigned candidate in the
  Plugins folder to load, under the same clamped ceiling. Accepted for
  v1; a per-plugin allow-list is purely additive if finer granularity is
  ever needed.
- **The construction-time conformance check duplicates, independently, a
  kind of type-scanning Module Discovery also performs** — a real, if
  narrow, future maintenance hazard if the two scans diverge. `WP 13.0B`
  is explicitly asked to share the underlying logic with
  `IFrameworkDiscoveryService` where practical, rather than maintaining
  two independent implementations.
- **No trust-tier promotion or demotion at runtime** — a plugin fix
  requires a new process run, exactly as a plugin code fix already does
  today (`Plugin Manifest Architecture.md`'s own Risk, unchanged).
- **Live, in-process plugin unload remains unavailable** — a defended,
  explicit non-goal for `v0.13.0`, not an oversight; `ADR-0108`'s own
  reserved lifecycle seam stays reserved, unused, since the chosen
  isolation mechanism (capability scoping, not a collectible
  `AssemblyLoadContext`) does not make it usable.

## 11. Common Mistakes

Two mistakes are most worth naming, one avoided by this Work Package and
one worth guarding against in whatever reads this retrospective next.

**Avoided: assuming `AssemblyLoadContext` is a security boundary because
it sounds like isolation.** It governs assembly identity and unload in
modern .NET, not privilege. Reaching for an ALC to solve `TD-09` would
have closed nothing while adding real implementation complexity
(collectible-context lifetime management, type-identity-across-context
hazards) — recognising *why* it does not fit the actual problem, not
merely that an alternative technically exists, is what both new
architecture documents spend real space demonstrating rather than
asserting.

**To guard against: assuming this Work Package's own architecture phase
already resolved `TD-09`/`TD-10`/`TD-11`**, because it was the Work
Package their own revisit trigger named. It designed the resolution in
full, ADR-ratified and ready; it built none of it. `WP 13.0B` is where the
actual `RequirePermission` calls, the signature verification code, and
the trust-tier assignment logic get written — the identical distinction
`WP 6.1`'s own retrospective already drew for itself when it built
`IPermissionEvaluator` without retrofitting it anywhere, and worth
re-drawing here rather than letting "the trigger fired" and "the debt
closed" collapse into the same event.

## 12. Future Evolution

- **`WP 13.0B`** — the implementation Work Package this entire design
  anticipates: `PluginDependency`, the extended `PluginManifest`,
  `IPluginRegistry`/`PluginRegistry`, the extended `IDiagnosticsProvider`,
  `ICurrentComponentAccessor`, the signature verification pipeline, and
  the `RequirePermission` retrofit into `NavigationService`/the Command
  Framework/`IEventBus` — none of it performed by this Work Package,
  architecture only, exactly as `Plugin Manifest Architecture.md` was
  itself architecture-only ahead of `WP 4.2`. **Correction, found by `WP
  13.0B`'s own independent Documentation Audit**: this bullet's own prior
  wording claimed the corresponding `Host Lifecycle.md`/`Failure
  Behaviour.md` updates were "none of it performed by this Work Package"
  — false, and self-contradicting this retrospective's own §Architectural
  Debt Assessment/Observations below, which correctly list both as
  already integrated. What `WP 13.0A` performed was the **prose**
  extension of both documents (the "Extended, `WP 13.0A`" blocks
  describing the new Phase 3.1/3.2 behaviour and failure categories
  12–18) — real, already-merged architecture content, not a remaining
  task. What `WP 13.0B` still owes both documents is the **code** those
  extended descriptions describe (the actual dependency-graph/signature/
  capability logic inside `PluginManifestDiscoveryService`/
  `PluginAssemblyLoader`/`TempestHost`) — a code change, not a further
  documentation pass. Corrected here rather than left standing.
- **A DI resolution interceptor** checking every individual `GetService`
  call against a plugin's declared capabilities, beyond the
  construction-time reflection check this design already performs.
  Revisit trigger: real evidence, from `WP 13.0B`'s own implementation or
  a real plugin, that constructor-time gating alone is insufficient.
- **Wildcard/glob capability keys** (e.g. `plugin.events.publish:*`).
  Revisit trigger: a real plugin needing broad, dynamic event-type
  coverage makes an exact-key manifest genuinely unworkable, not merely
  verbose.
- **Automated quarantine/disable-on-repeated-violation.** Revisit
  trigger: real evidence of a plugin repeatedly attempting denied
  operations in a way that itself becomes a problem.
- **Real per-plugin unload.** Revisit trigger: a future, separate
  decision adopts a collectible `AssemblyLoadContext` (or equivalent)
  specifically for that purpose — this Work Package does not make that
  decision and does not unlock it as a side effect of trust enforcement.
- **Online CA/CRL/OCSP revocation checking.** Revisit trigger: `Security
  Roadmap.md` item 7 (API and networking exposure) fires.
- **A runtime-mutable trust store or capability administration UI.**
  Revisit trigger: the same trigger `ADR-0043` names for its own eventual
  reconsideration — a genuine multi-user/administered deployment
  scenario.
- **`RD-0009`'s platform-version-ceiling rejection is reaffirmed, not
  reversed.** A commitment to build toward third-party plugins is not the
  same fact as "real plugins and real version history exist" —
  `src/Plugins/` remains empty, verified directly during this Work
  Package. Revisit trigger, now nameable concretely for the first time:
  the first real plugin (first- or third-party) ships, and is upgraded at
  least once.
- **A real, non-synthetic plugin** — `Plugin Manifest Architecture.md`'s
  own §12 already named this as outstanding; still open after this Work
  Package, unchanged.
- **Future Commercial Plugin Support (`FCR-0025`)** — `Plugin Platform
  Architecture.md` records a structural observation (`ILicenseValidator`
  already runs ahead of Plugin Discovery in the phase table) without
  designing licensing-gated plugin loading; revisit trigger: `FCR-0025`
  becoming a real, scheduled need.

## 13. Key Takeaways

1. "The Manifest describes; the Runtime decides" extends cleanly to trust
   without becoming a different sentence — the Manifest now also
   describes what a plugin wants to do and who signed it, and the Runtime
   still makes every consequential decision through the platform's one
   existing enforcement point, not a second one.
2. A mechanism that sounds like isolation (`AssemblyLoadContext`) is not
   automatically a security boundary — verify what a candidate mechanism
   actually governs (assembly identity/unload) against what the problem
   actually requires (privilege) before adopting it, rather than reaching
   for the first available API with a plausible-sounding name.
3. Firing a long-disclosed revisit trigger (`TD-09`/`TD-10`/`TD-11`,
   `Security Roadmap.md` items 1/2/10) and actually closing the debt are
   two different events. This Work Package designed the resolution in
   full and ADR-ratified it; it built none of it. `TD-09`/`TD-10`/`TD-11`
   move from "mechanism exists, not yet applied" to "design resolved,
   retrofit remains open until `WP 13.0B`" — not further than that, and
   stating the boundary plainly is what keeps this retrospective, and the
   `Future Evolution` sections it updates elsewhere, honest rather than
   quietly overclaiming.
4. Signing and capability scoping answer different questions (*who* vs.
   *what*) and are complementary, not substitutable — a design adopting
   only one leaves the other question completely open, however
   sophisticated the one it does answer.
5. Two parallel architecture workstreams composing cleanly — the Plugin
   Platform document defining a field's *shape* and explicitly deferring
   its *semantics* to the sibling Trust & Isolation document, which then
   adopts that exact shape without renegotiation — is only possible
   because each stated its own boundary with the other in writing, before
   either was finished, not discovered informally at integration time.
