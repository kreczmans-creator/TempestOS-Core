# TD-84 — The Product Spine: Module → Project → Workspace as Persisted State

## 1. Introduction

`37788a0` implemented the 2026-08-28 product decision that TempestOS is a
project-centric engineering operating environment — `TempestOS → Module →
Project → Workspace → Engineering Object → Evidence` — connecting an
engineering platform that already worked to a shell that had never existed.
A pre-`v0.14.0` engineering-body-of-work row; the technical detail lives in
the companion Academy runtime-architecture article this commit also
indexed (`docs/academy/02 Runtime Architecture/33-the-product-spine.md`),
which this retrospective complements with the decision record.

## 2. Purpose

To close `TD-84`, a grouping row recording that four apparently
independent gaps — no global navigation, no project context, no
per-discipline engineering surfaces, no Tasks/Commercial/Resources/
Knowledge/Admin modules — were not four features but four symptoms of one
missing layer: the Product Shell / Project Context layer. The row was
recorded as a group deliberately, so it would never be worked as
unrelated tickets, which would have produced a projects screen, a
navigation rail, a project dashboard and some engineering links with no
relationship between them.

## 3. Background

The engineering platform underneath was already correct and untouched by
this work; the gap was entirely in what connected a user to it. Every
Kind, calculation, requirement and relationship the six disciplines had
built since `WP 8.2C` already worked. Nothing in the product let a user
reach a project, see it as the current context, or have that context
agree with where they were navigating.

## 4. The Problem

A brief describing a project-centric platform, and a shell that could not
answer "what project is open" because nothing could set that answer.

## 5. The Design

`IProjectDirectory`/`ProjectDirectory` — a project *is* an `IProject`
engineering object, created through the same `EngineeringObjectFactory`
every discipline uses, so it arrives with lifecycle, relationships,
revisions, traceability and audit already working, rather than through a
second, parallel project model. The pre-platform `ProjectModel`/
`ProjectService`/`IProjectRepository` cluster was investigated and
deliberately not reused: it constructed its own repository in its
constructor, bypassing `IPersistenceStore`, audit, revisions and
lifecycle entirely. `IProjectContext`/`ProjectContext` holds the current
project as real application state — open/switch/close/refresh, an
`IEventBus` event, persisted by Id only, never by name or status, which
would create a second, drifting source of truth. `IShellNavigator`/
`ShellLocation` makes navigation one immutable value (`ShellArea`,
`ProjectId`, `ProjectArea`), enforcing the invariant that a project-scoped
location and the current project can never disagree — `OpenProjectAsync`
opens the context first, so a failed open cannot leave the shell pointing
into a project that was never opened. The Desktop shell —
`GlobalNavigationRail`, `ProjectBrowserView`, `ProjectWorkspaceView`, a
single module host rendering whatever the navigator reports, and a Status
Bar that finally shows the real current project — is built on top.

`TD-85` surfaced from this row's own Definition-of-Done journey, which
failed at "close and reopen TempestOS" until a real durability boundary
was confronted: the engineering object graph is in-memory by design
(`ADR-0077`), so documents persisted but the objects reconstructed over
them did not. This pass's own fix was a workaround, not the boundary fix:
a durable `Projects.Index`, following `MaterialCatalog`'s own approved
pattern (`ADR-0055`) for the identical reason, with the live object still
authoritative when it exists. `TD-85` later removed that index outright
once the real boundary was fixed.

## 6. Alternatives Considered

Reusing the pre-platform `ProjectModel`/`ProjectService` cluster —
rejected on inspection: it bypassed every durability and audit guarantee
the platform's real engineering objects already had, for no benefit
beyond avoiding new code.

## 7. Why This Solution Was Chosen

Because a project that is not a real engineering object would have been a
second product model living beside the first one, disagreeing with it in
ways nobody could predict in advance. Making a project *be* an
`IProject` object means every guarantee the platform already gives every
other engineering object — lifecycle, relationships, audit — comes free.

## 8. Architectural Principles

`D-021` (Proposed, `WP 16.0A`) later ratifies the 2026-08-28 project-centric
decision this row implements as the governing v1.x roadmap direction,
distinct from the v1.0 scope definition itself — this row is the moment
that decision became running code.

## 9. Benefits

32 tests, including the full Definition-of-Done acceptance journey through
the real `MainWindow`, and the three commissioned engineering traces
(Project→Component→Material→Calculation→Validation→Result;
Project→Requirement→Verification→Evidence; Project→Drawing/Document→
Engineering Object). Four mutations run and killed, including the durable
index itself, which fails the acceptance journey and not merely a unit
test.

## 10. Trade-offs

Engineering was reachable only from an open project — a faithful but
too-strong reading of "project-centric" — later superseded by `TD-89`,
which makes standalone calculation sets and quick calculations a
first-class workflow requiring no project. The durable `Projects.Index`
this row added was itself a disclosed workaround, later removed by
`TD-85`.

## 11. Common Mistakes

Treating four related gaps as four independent tickets, which the row's
own grouping was written to prevent, because that shape of fix produces
disconnected screens rather than one coherent shell.

## 12. Future Evolution

`TD-85` (durable object state, closing the workaround this row's own
journey forced), `TD-89` (standalone engineering, undoing the
too-strong reading), and the later Tasks/Risks/Timeline surfaces all
build directly on the spine this row establishes — each is recorded as
"remaining under this grouping" in the Technical Debt Register rather
than as a separate architectural decision.

## 13. Key Takeaways

- Four gaps that share one missing layer should be grouped and worked as
  one, not split into unrelated tickets that would each half-solve the
  real problem.
- A project should be a real engineering object with the platform's
  existing guarantees, not a second model beside it.
- The Definition-of-Done acceptance journey is what surfaced `TD-85` — a
  real end-to-end test found the boundary a unit-level pass would have
  missed.
