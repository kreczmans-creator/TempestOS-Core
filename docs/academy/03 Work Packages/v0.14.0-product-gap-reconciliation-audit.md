# Product Gap Reconciliation Audit: Findings and Standing Evidence

## 1. Introduction

`187180a` is an evidence-based audit of the tree against the mock-ups,
architecture and registers — no feature work. Two things were found stale
and both were corrected; nothing else was changed, and no status was
moved to make a count agree. A pre-`v0.14.0` engineering-body-of-work
row.

## 2. Purpose

To check the registers' claims against the repository rather than assume
them current, and to leave a standing test behind rather than a one-time
finding.

## 3. Background

`TD-102`, shortly before, had found the exact defect class this audit
generalises: a descriptor and a surface disagreeing with nothing checking.
This row asks whether that same shape of gap exists anywhere else.

## 4. The Problem

`TD-75`'s own text described a packaging problem — `Tempest.App`
references `Tempest.Samples`, so demo modules ship — but measuring it by
actually removing the `ProjectReference` and building left 70 errors
across three files, because real product content (all six discipline
explorer areas' `NavigationItemId`s, and the entire engineering
calculation catalogue) was declared inside the sample assembly. Deleting
the reference as written would have removed the Engineering Workspace's
navigation and the product's calculations, not the demos. Separately, the
shell's Tasks module descriptor still stated, in shipped UI text, that
"no task surface, assignment workflow or board has been built" — false
since the project Tasks area shipped.

## 5. The Design

`TD-75` is re-scoped rather than re-closed: its severity is unchanged, but
the shape is now recorded honestly — a content move followed by the layer
split, not the split alone — because a packaging chore and misfiled
product content belong in very different places in a queue. The Tasks
descriptor is corrected to describe what is genuinely missing (a
cross-project view over tasks), Availability left `Declared`, since that
cross-project module really is unbuilt. `ProductGapReconciliationAuditTests`
drives every declared area through the real shell and asserts the
descriptor matches what renders — Implemented areas must not draw a
`DeclaredCapabilityView` and must name no tracking debt, Declared areas
must draw one and must name what tracks them, one level up for shell
modules too — reading the descriptor tables at run time, so an area added
later is covered without anyone remembering to add a test for it.

## 6. Alternatives Considered

Leaving `TD-75`'s original text as the scope and simply removing the
`ProjectReference` — the audit's own measurement (70 compile errors) rules
this out directly; it is not a viable alternative once measured.

## 7. Why This Solution Was Chosen

Because a standing, run-time-driven test that reads the descriptor tables
themselves catches every future instance of this defect class without
anyone needing to remember to re-audit — three mutations run and three
killed, including the `TD-102` defect re-introduced deliberately to prove
the new test catches it.

## 8. Architectural Principles

A register's claim about the repository should be periodically checked
against the repository, not merely trusted forward from when it was
written — and the check, once written, should be a standing test rather
than a one-time manual pass.

## 9. Benefits

Six new tests; two failed first time and both were the test's own
precondition rather than a product defect (Project Explorer root nodes
scoped to the selected navigation area; `NavigationService` not resolvable
by its concrete type) — corrected rather than asserted around. Confirmed
accurate and left alone: `TD-73`, `TD-74`, `TD-76`, `TD-77`, `TD-83`,
`TD-84` already carry correct "remaining" clauses; `TD-82` has zero
Companion implementation; `TD-78` brand colours are absent; `TD-98`–
`TD-101` match the viewer as built; `FCR-0054` is correctly Implemented.
Register counts unchanged at 104 tracked.

## 10. Trade-offs

The audit re-scopes `TD-75` rather than closing it — the row stays open,
now honestly described, and the actual content-move work is deferred to
the two phases that follow (`a5795bd`, `fdd2a2a`).

## 11. Common Mistakes

Reading a debt row's own description as the current scope of the problem
without measuring it against the repository — `TD-75`'s text had
described a packaging problem for some time, and only actually attempting
the removal revealed it was a product-content-placement problem instead.

## 12. Future Evolution

`a5795bd` and `fdd2a2a`, immediately after, are the two phases this
audit's re-scoping makes possible — moving the misfiled product content
first, then removing the now-genuinely-unused sample dependency.

## 13. Key Takeaways

- Measure a debt row's described scope against the repository before
  planning the fix — a description can be stale even when the row itself
  looks current.
- Leave a standing, run-time-driven test behind an audit finding rather
  than relying on the next person to re-run the audit by hand.
- Confirming existing rows are still accurate is itself worth recording —
  an audit that finds "these are fine" is not wasted if it says so
  explicitly rather than silently.
