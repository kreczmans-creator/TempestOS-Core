# WP 13.0.0 — v0.13.0 Branch Establishment

## What This Document Is

The retrospective for `WP 13.0.0`, which created `feature/v0.13.0` —
the sole integration branch for TempestOS's next release, "Trust &
Deployment Hardening" — and initialised its release-planning documents.
Process/governance only; no production code, no ADR.

## Two Real Conflicts Found and Resolved Before Proceeding

**`VERSION` format.** The brief specified `VERSION → 0.13.0-dev`.
Confirmed directly, this format breaks `governance-healthcheck.ps1`:
`Test-ProjectStatusReferences` strips only a `-rc.\d+$` suffix before
casting to `[version]`, so `[version]"0.13.0-dev"` throws a genuine
cast exception. It also has no precedent in this project's own
documented versioning policy (`WP11.1B Engineering Workflow.md` §7 —
`MAJOR.MINOR.PATCH` or `-rc.N` only). Directly observed precedent
throughout this entire engagement: `VERSION` stayed `0.11.0` for the
*entire* development of `v0.12.0`, bumped only at the final pre-tag
commit. Raised to the Product Owner rather than silently worked
around; resolved: `VERSION` stays `0.12.0`.

**`v0.13.0`'s own scope.** `WP11.0B Architecture Roadmap.md` §3 marks
`v0.13.0` "Trust & Deployment Hardening" explicitly *conditional* —
"only enters the plan if the Product Owner commits `v1.0` scope to
third-party plugins and/or REST deployment beyond a trusted local
network. Otherwise… this release is skipped entirely." No evidence the
trigger had fired existed anywhere in this engagement (`src/Plugins/`
confirmed still empty as recently as `WP 12.9.1`; no `v0.12.0` Work
Package touched REST API scope). Raised rather than assumed; the
Product Owner confirmed the commitment is being made now, as this Work
Package's own commissioning.

## What Was Built

- `feature/v0.13.0`, cut directly from the `v0.12.0` tag (`13a6ce3`),
  not from `main` or any working branch — verified six independent
  ways by the Architecture Agent (below): tag dereference, merge-base
  against both the tag and `main`, direct parent inspection of the
  branch's own sole new commit. All six byte-identical.
- Branch discipline, stricter than every prior release's own
  multiple-parallel-branch convention: `feature/v0.13.0` is the sole
  integration branch for every `v0.13.0` Work Package; commit directly
  to it; never rebase, never squash; merge commits only when
  integrating back to `main` at this release's own close.
- `docs/releases/v0.13.0/WorkPackages.md`, seeded from `WP11.0B
  Architecture Roadmap.md` §3's own predicted table — Work Package
  IDs, Scope, and Type columns reproduced verbatim; Status updated from
  `Conditional` to `Not started` now that the trigger has fired.
- `PROJECT_STATUS.md` updated — both this branch's own establishment
  and `v0.12.0`'s own final release completion (tag, GitHub Release),
  which no prior Work Package had actually recorded.

## Three Parallel Verification Agents

Per this Work Package's own explicit instruction, spawned in parallel
once the substantive setup work was complete (git branch/commit
operations are inherently stateful and sequential; independent
verification of the *result* parallelises safely, mirroring this
project's own six-discipline Programme Review pattern applied via real
subagents for the first time):

- **Architecture Agent** — verified branch point: **Pass**, six
  independently-derived commit SHAs all identical to `13a6ce3`.
- **Repository Agent** — verified clean working tree, branch state,
  tags, `VERSION` consistency: **Pass** on all four, with two
  informational notes (nine stale prior-release feature branches
  left un-deleted; `WorkPackages.md` doesn't mention `VERSION` at all
  — silent, not contradictory).
- **Governance Agent** — audited the new release documentation against
  its own cited sources: **Pass**, with one real, minor finding — the
  Work Package table was described as "reproduced below verbatim"
  despite the Status column being deliberately edited. Fixed same
  session, second sequential commit (`a43a197`), never amended.

## One Finding Disclosed, Not Fixed Here

`governance-healthcheck.ps1` reported `[FAIL] Release Register matches
git tags` — the `v0.12.0` tag had no row in `docs/governance/Delivery/Release
Register.md`. Independently confirmed by the Governance Agent to
predate this Work Package (`git show 13a6ce3:...` — already missing at
the exact commit the tag points to). Correctly out of this Work
Package's own scope (concerns `v0.12.0`'s own release record, not
`v0.13.0`); closed by the next Work Package, `WP 13.0.0A`.
