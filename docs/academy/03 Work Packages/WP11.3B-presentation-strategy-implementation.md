# WP 11.3B — Presentation Strategy Implementation

## 1. Introduction

`WP 11.3B` (commit `acc2832`) executes the approved, low-risk portion
(Stages 1–4) of `WP11.3A`'s own five-stage roadmap: retires
`TempestShell`/`IPage`/`PlaceholderPage` as production code, authors
`ADR-0101` formally classifying `Tempest.App`/`WorkspaceShell` as
TempestOS's Internal Engineering Harness, corrects repository
documentation, and corrects release-artifact packaging. Its full account
is `docs/releases/v0.11.0/WP11.3B Presentation Strategy
Implementation.md`. This retrospective is written retrospectively under
`WP 16.2B`, grounded in that report, `ADR-0101`, and commit `acc2832`.

## 2. Purpose

Execute `WP11.3A`'s own approved recommendation exactly, with no
behavioural change to `Tempest.Desktop`, no architectural redesign, and
no change outside that review's own approved plan.

## 3. Background

`WP11.3A` found `TempestShell` provably dead (unreachable since
`ADR-0068`, three releases) and recommended retiring it while formally
ratifying `WorkspaceShell` as an internal harness rather than a shipped
product — a five-stage roadmap, Stage 5 explicitly deferred pending
demonstrated need.

## 4. The Problem

The dead code, the missing formal ratification, and the stale
documentation `WP11.3A` found were all still present — a review's own
recommendation is not itself a fix.

## 5. The Design

**Retirement**: `git rm` on `TempestShell.cs`, `IPage.cs`,
`PlaceholderPage.cs`, and their two test files — history preserved, not
deleted from the repository's own past. Eight files' worth of
doc-comment references to `TempestShell` as a design precedent were
corrected rather than left dangling; a direct sweep confirmed zero
remaining references anywhere in source or tests.

**`ADR-0101`** — "`Tempest.App`/`WorkspaceShell` Is TempestOS's Internal
Engineering Harness, Not a Shipped Product" — cites `ADR-0068` and
`ADR-0092` directly; neither is modified, per `WP11.3A`'s own explicit
instruction and Engineering Governance §5. Registered in the ADR
Register, 99 → 100.

**Documentation**: `README.md`'s architecture diagram and build
instructions now include `Tempest.Desktop`; `Tempest.App` is correctly
described as the Internal Engineering Harness rather than the
pre-`v0.5.0` "legacy bootstrap... does not yet run through `TempestHost`"
description that had been stale since before `v0.5.0`.
`Contributor Learning Path.md`'s own `TempestShell` reading-order entry
now discloses its retirement and points to `ADR-0101`/`Tempest.Desktop`
instead of presenting a retired class as `Tempest.App`'s composition
root without qualification. `Platform Service Map.md` and `Shell &
Composition Framework Architecture.md` corrected. Three governance
registers (Namespace, Test, Architectural Dependency) narrowly
corrected — each already independently, disclosedly stale for unrelated
reasons predating this Work Package; the correction here is disclosed as
narrow, not a full re-derivation.

**Release engineering**: `ci.yml`/`release.yml`'s prior symmetric,
bundled packaging is replaced with two separate, clearly-named
artifacts — `tempestos-desktop-release` (the shipped application) and
`tempestos-engineering-harness` (`Tempest.App`, explicitly labelled).

**Unsupported historical claim removed**: `Tempest.Desktop/Program.cs`'s
own doc comment previously asserted a specific `WP 10.0B` instruction
`WP11.3A`'s own search could not find anywhere else in the repository
— corrected to state the now-formally-ratified `ADR-0101` position
directly, with an explicit note that the prior wording was found
unverifiable.

## 6. Alternatives Considered

Executing `WP11.3A`'s Stage 5 (further trimming `WorkspaceShell`'s own
test coverage or feature scope) alongside Stages 1–4 was considered and
rejected — that review explicitly recommended against it absent a
demonstrated cost problem, and none exists.

## 7. Why This Solution Was Chosen

Executing exactly the approved plan, in the sequence that review's own
roadmap specified (documentation before code removal, so a reader
following the corrected `README.md` never finds a dangling reference to
a just-retired class), keeps the implementation traceable directly back
to a reviewed, approved recommendation rather than introducing new
judgment calls mid-execution.

## 8. Architectural Principles

`ADR-0068` and `ADR-0092` are cited by `ADR-0101`, neither modified — the
correct handling of an ADR found imprecise on direct comparison
(`WP11.3A`'s own finding) without Engineering Governance §5 permitting a
rewrite. Zero behavioural change to `Tempest.Desktop` — every edit inside
`src/Tempest.Desktop/` was a doc-comment correction, confirmed by the
full headless test suite passing unchanged (202/202, before and after).

## 9. Benefits

`scripts/governance-healthcheck.ps1` (`WP 11.2A`), re-run post-change,
now correctly reports the ADR Register check as 100/100 automatically —
no tool change required to pick up `ADR-0101`, direct evidence that Work
Package's own tool genuinely self-updates. Release artifacts are now
correctly, distinctly labelled — a real user or automation consuming a
future GitHub Release can no longer mistake `Tempest.App`'s build for
the shipped product.

## 10. Trade-offs

Test count drops from 2,266 to 2,228 (−38) — exactly reconciled against
the two removed test files' own raw source (`TempestShellTests.cs` 29
cases, `PlaceholderPageTests.cs` 9 cases), independently confirmed, not
a regression. No full re-derivation of the three touched governance
registers was performed — each remained disclosedly stale for reasons
predating this Work Package; only the specific rows this change touched
were corrected.

## 11. Common Mistakes

**Assuming a review's own five-stage roadmap must be executed in full,
immediately.** This Work Package deliberately executes only the
approved, low-risk four stages and leaves Stage 5 explicitly deferred —
matching the review's own recommendation rather than treating "the
review named five stages" as an obligation to complete all five now.

## 12. Future Evolution

`WP 12.2A` (`v0.12.0`), the roadmap's own predicted next step for this
thread, discovers its own scope was already delivered here, one release
early — direct evidence the presentation-strategy question this Work
Package closed genuinely stayed closed. `Contributor Learning Path.md`
received a real, substantive edit here (the `TempestShell` entry) but
not the closing-pointer fix a different, independent finding
(`WP 11.9.0`'s own Workflow Engineer review) surfaced in the same
release — that fix did not land until `WP 16.2B`, five releases later.

## 13. Key Takeaways

- Execute a review's own approved recommendation exactly, including its
  own explicit deferrals — a review naming five stages does not obligate
  the implementing Work Package to complete all five immediately.
- A test-count drop is not itself a regression signal — reconcile it
  directly against the removed files' own raw source before reporting
  it, not merely against the delta.
- Re-running a prior Work Package's own validation tool after a change
  is real evidence that tool self-updates correctly — a stronger claim
  than simply asserting the change is complete.
