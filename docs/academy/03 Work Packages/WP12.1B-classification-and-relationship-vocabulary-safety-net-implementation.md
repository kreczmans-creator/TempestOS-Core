# WP 12.1B — Classification & Relationship Vocabulary Safety Net Implementation

## What This Document Is

The implementation-phase retrospective for `WP 12.1B`, realising
`ADR-0105`/`Classification & Relationship Vocabulary Safety Net
Architecture.md` exactly as approved. Implements the architecture only
— does not revisit or extend the decision. On the same branch as
`WP 12.1A` (`feature/v0.12.0-classification-relationship-vocabulary-safety-net`).

## 1. Introduction

`WP 12.1A` audited every Kind/`Classification`/`RelationshipKind`
vocabulary this platform uses, confirmed the gap `WP11.0A` Finding
`A-6` named was real but precisely bounded, and produced `ADR-0105`:
every live vocabulary value declared exactly once, as a named constant,
on its owning class; a new Engineering Vocabulary Register tracking
every value platform-wide; an additive, non-blocking consistency test.
A follow-up architecture review then closed two findings — the
Architecture Document Register's own arithmetic, and Component 3's own
proposed test location (moved to `Tempest.Desktop.Tests`, the only
project able to reflect across all three layers). `WP 12.1B` is the
implementation this whole chain of work has been building toward:
apply `ADR-0105` for real, against real code, with real characterization
tests proving nothing observable changed.

## 2. What Was Built

### 2.1 Declaration discipline — every FactoryRegistry retrofitted

`MechanicalObjectFactoryRegistry` (the discipline `WP 12.1A` found with
the largest, most conspicuous gap — zero declared Kind constants across
all eight Kinds) now declares `Project`/`Assembly`/`SubAssembly`/`Part`/
`Component`/`Configuration`/`Baseline`/`Release` as named constants,
used internally throughout its own `SupportedKinds` array, switch
labels, and `EngineeringObjectFactory<T>` constructor arguments — the
exact three-times-repeated-per-Kind duplication `WP 12.1A`'s own
investigation quantified, now collapsed to one declaration per value.

`DocumentObjectFactoryRegistry` and `ManufacturingObjectFactoryRegistry`
— already disciplined about their own `Classification` sub-values
(`ADR-0088`/`ADR-0091`) — now also declare their own base Kinds
(`Document`/`Drawing`/`CadModel`; `ManufacturingOperation`/
`WorkInstruction`/`Inspection`, the latter three named with a `Kind`
suffix to avoid colliding with their own identically-named Domain
types already used unqualified throughout each file) as named
constants, closing the one gap that remained inside otherwise-compliant
files. `CalculationObjectFactoryRegistry` gains `CalculationKind`/
`CalculationSetKind`, the smaller, comparable gap `WP 12.1A` found
there.

### 2.2 The confirmed duplicate, closed

`Tempest.Desktop.DigitalThread.DigitalThreadGraphModel` previously
declared three private local constants
(`VerificationActivityKind`/`VerificationRecordKind`/
`VerifiedByRelationshipKind`) independently duplicating values already
canonically owned elsewhere. All three now reference the real owning
constants directly —
`VerificationActivityFactoryRegistry.SupportedKind`,
`VerificationService.VerificationRecordDocumentKind`,
`VerificationService.VerifiedByRelationshipKind` — closing the single
clearest, most concrete piece of evidence `WP 12.1A`'s own
investigation found that `A-6`'s concern was real, not speculative.

### 2.3 Engineering Vocabulary Register — created and populated

`docs/governance/Engineering/Engineering Vocabulary Register.md`, new:
46 declared values (23 Kind, 12 `Classification`, 11 `RelationshipKind`)
across 11 declaring classes, populated from a full, direct repository
scan — every value cross-checked against a real `CreateAsync`/
`LinkAsync` call site, never assumed. Seven further conventional
`RelationshipKind` values (`manufacturedBy`, `documentedBy`, `blocks`,
`relatedTo`, `supersedes`, `duplicates`, `approvedBy`) are listed too,
honestly marked **Undeclared** — used only by convention today, with no
canonical owning class — rather than silently omitted, matching this
platform's own established "Uncategorized"/honest-disclosure
convention. **One genuine, pre-existing dual-ownership case found and
disclosed, not treated as a defect**: `references` is independently,
legitimately declared by both `RequirementRelationshipKinds` and
`VerificationService` for a genuinely shared, conventional meaning
neither discipline exclusively owns — recorded explicitly with its own
footnote, mirroring `ADR-0073`'s own already-accepted "vocabulary
drift" risk, and named by exception in the consistency test rather than
silently causing a false failure.

### 2.4 Component 3 — the consistency test

`EngineeringVocabularyConsistencyTests` (`Tempest.Desktop.Tests`, new),
per the corrected `WP 12.1A` architecture — placed here specifically
because `Tempest.Core.Tests` cannot reference `Tempest.Desktop` and so
could never reflect over `DigitalThreadGraphModel`, confirmed directly
against both `.csproj` files. Four tests:

1. **Register/code drift** — every registered (Value, Declaring Class)
   pair still exists in code with the exact recorded value.
2. **Cross-owner duplication** — no two declaring classes state the
   identical (Vocabulary, Value) pair, except the one disclosed
   `references` exception.
3. **Register self-consistency** — the register itself never lists the
   same declaring class/field with two different values.
4. **Rogue-duplicate scan** — reflects every type in `Tempest.Core`/
   `Tempest.App`/`Tempest.Samples`/`Tempest.Desktop` (public *and*
   private `const string` fields, since the confirmed
   `DigitalThreadGraphModel` duplicates were `private`) for any class
   *not* already the registered owner redeclaring a registered value —
   the general form of the exact defect this Work Package found and
   fixed, now caught automatically for any future instance, in any
   class, not only ones the register already happens to name.

**Verified to actually work, not merely assumed**: a rogue duplicate
(`private const string SanityCheckRogueDuplicate = "verifiedBy";`) was
deliberately, temporarily reintroduced into `DigitalThreadGraphModel`
mid-implementation — the consistency test failed immediately, with a
precise, actionable message naming both the offending class and the
real owner. Reverted immediately after confirming the failure; the
test suite was clean again before implementation continued.

### 2.5 Characterization tests added before refactoring

`MechanicalCommandsTests.Create_SupportedKindWithoutParent_Succeeds`
gained three new `[InlineData]` cases (`Configuration`/`Baseline`/
`Release`) — a real, confirmed-by-direct-search gap: these three Kinds
had never been exercised via the real `CreateMechanicalObjectCommand`/
`MechanicalObjectFactoryRegistry` path anywhere in the test suite
(private test helpers elsewhere in the same file constructed them by
bypassing the registry entirely, for unrelated Baseline-comparison
tests). Run and passing against the unrefactored registry first
(34/34), establishing the validated baseline this Work Package's own
declaration-discipline refactor had to preserve. Documents/
Manufacturing/Calculations' own registries already had full,
direct `[Theory]`/`[InlineData]` coverage of every one of their own
Kinds — confirmed by direct re-derivation, not assumed from `WP 12.1A`'s
own earlier, less precise grep-based estimate (which had missed
`[InlineData]`-driven theory tests entirely on a first pass).
`DigitalThreadGraphModel`'s own `VerificationActivity`-expand path
already had real, direct coverage
(`Recentre_VerificationActivityWithARecordedResult_AddsTheResultAsAVisibleLeafNode`)
— no new test needed there, only confirmed as the correct baseline.

## 4. Architectural Lessons

**A "minimum scope" named in an architecture document is a floor, not a
ceiling — a controlling instruction can commission the fuller retrofit
explicitly, and doing so is not scope creep.** `WP 12.1A`'s own
Migration Strategy named only two defects as `WP 12.1B`'s own required
minimum (Mechanical's gap; the `VerifiedByRelationshipKind` duplicate),
explicitly disclosing the remaining, smaller gaps (Documents'/
Manufacturing's own base Kinds; Calculations' own Workspace gap) as
"real, disclosed, future work, not required." This Work Package's own
controlling instruction commissioned that fuller retrofit directly —
closing all of it in the same change was a legitimate expansion of an
explicitly-named future option, not a deviation from the architecture's
own decision.

**A coverage estimate produced by grepping for literal strings can
silently miss a `[Theory]`/`[InlineData]`-driven test entirely.**
`WP 12.1A`'s own investigation, searching for `CreateMechanicalObjectCommand("Kind"`
literally, concluded several Mechanical Kinds looked untested — a real
test existed, but its own Kind arguments were theory parameters, not
inline literals, invisible to that specific grep pattern. Re-deriving
coverage directly against the real test file, method by method, found
the true picture: four of eight Kinds already covered, a smaller,
more precisely bounded gap (`Configuration`/`Baseline`/`Release`) than
the earlier estimate implied. Grep is a starting point for a coverage
claim, never the final word.

**A blanket "flag every duplicate value" rule needs a real, disclosed
exception list the moment it meets real code — and finding that
exception is itself evidence the underlying architecture was sound.**
Implementing Component 3's own duplicate-declaration check literally
would have failed immediately, on a pre-existing, legitimate situation
(`references`, independently owned by two disciplines for a genuinely
shared meaning) that `ADR-0073` had already, explicitly accepted as a
disclosed cost of this platform's own extensibility model. Finding this
before shipping the test — rather than after it produced a confusing,
spurious first failure — confirmed the underlying architecture
(`ADR-0105`'s own "coordination aid, never a gate") was right to leave
room for disclosed exceptions, and gave this Work Package a concrete
opportunity to demonstrate that discipline rather than merely assert
it.

## 5. Key Takeaways

- **`ADR-0105` implemented exactly** — every value declared once, on
  its owning class; the Engineering Vocabulary Register created and
  populated; the consistency test added, in the corrected location; no
  write-time validation, no runtime registry, no enum, no value object
  introduced anywhere.
- **Both `WP 12.1A`-confirmed defects closed, plus every further
  confirmed gap** — Mechanical's own eight Kinds; the `DigitalThreadGraphModel`
  triple duplicate (`VerificationActivityKind`/`VerificationRecordKind`/
  `VerifiedByRelationshipKind`, one more than the single defect
  originally named, found while directly reading the file); Documents'/
  Manufacturing's own base Kinds; Calculations' own Workspace Kinds —
  every live vocabulary value in this platform now has exactly one
  canonical declaration.
- **The consistency test's own effectiveness was verified directly, not
  assumed** — a real, temporary rogue duplicate was introduced and
  confirmed to fail the test with a precise, actionable message, then
  reverted, before this Work Package considered Component 3 complete.
- **Behaviour preservation proven, not merely claimed** — characterization
  tests written and passing against the unrefactored code first, then
  re-run unchanged against the refactored code; full 2,255-test
  regression clean in both Debug and Release.

## 6. Addendum — Architecture Review Follow-Up (2026-08-12, documentation only)

A read-only architecture/code review of this Work Package found two
non-blocking documentation findings, no implementation defects, verdict
"Approved with documentation follow-up." Both are closed here,
documentation only — `ADR-0105` not reopened, zero `src/`/`tests/`
files touched:

- **Declaring-class count corrected.** §2.3, above, originally stated
  the declaring-class count as 12. Re-derived directly
  from the Engineering Vocabulary Register's own three Entries tables
  (manual enumeration, cross-checked by an automated extraction), the
  true count is **11** — the original figure double-counted
  `VerificationService`, which appears once in the Kind table and three
  times in the RelationshipKind table but is one class. All 46
  individual values and their declaring classes were themselves already
  correct; this is a narrative-arithmetic correction only. The same
  "12" figure, propagated from the register's own "Last Reviewed"
  field, was also corrected in `Engineering Vocabulary Register.md`,
  `PROJECT_STATUS.md`, `docs/releases/v0.12.0/WorkPackages.md`,
  `Documentation Register.md`, `Academy Register.md`, and `ADR
  Register.md` — confirmed by repository-wide search that no occurrence
  remains.
- **Component 3 documentation broadened.** `Classification &
  Relationship Vocabulary Safety Net Architecture.md`'s own Component 3
  section named only two of the four checks `EngineeringVocabularyConsistencyTests`
  actually implements (register drift; cross-class duplication). The
  implementation is, and always was, strictly more protective than
  described — never less — but the architecture document is now updated
  to name all four: register drift detection, duplicate canonical-owner
  detection, register self-consistency, and a rogue-duplicate vocabulary
  scan across assemblies.
