# WP 12.0B — Desktop Composition Root Decomposition Implementation

## What This Document Is

The implementation-phase retrospective for `WP 12.0B`, closing
`WP11.0A Platform Architecture Review.md` Finding `A-1` in full. A full
concept guide already exists separately (`docs/architecture/Desktop
Composition Architecture.md`), so this file focuses on the
implementation narrative: the real, final collaborator boundaries this
Work Package found (differing in a few disclosed places from `WP
12.0A`'s own explicitly non-binding illustrative sketch), the two
genuine construction-order cycles found and resolved, and what
regression proved.

## 1. Introduction

`WP 12.0A` designed `ADR-0103` ("Composition Roots Own Collaborators")
as a general, platform-wide pattern and left `MainWindow`/
`EngineeringCockpit`'s own real, final collaborator boundaries as this
Work Package's own job — its own illustrative table was explicit that
"implementation finds a better cut" is expected, not a deviation. This
Work Package implements the pattern against both files exactly, under a
tight, explicit scope: refactor only, zero public API changes, zero
behavioural changes, zero new Platform Services, zero new DI
registrations, no `partial class`.

## 2. What Was Built

**`MainWindow.cs`: 1,556 → 544 lines; its own constructor: ~1,000 →
~370 lines.** Nine collaborators, all in a new `Tempest.Desktop.Composition`
namespace: `DesktopCompositionRoot` (Platform Service resolution, mirrors
`EngineeringWorkspaceComposer`'s own shape), `DesktopSessionState` (the
five independent synchronous state loads), `WorkspaceDockingComposer`
(panel construction/resize/hide/collapse/pin/flyout wiring),
`RibbonObjectActionHandlers` (the ~450-line, ~29%-of-file per-discipline
Create/Duplicate/status-transition population — the single largest,
most mechanical extraction, moved verbatim), `WorkspaceViewCoordinator`
(Explorer/Inspector/Document-Area cross-view wiring, `ToggleFavourite`,
dirty-aware document close), `UndoRedoCoordinator` (the stack, its two
buttons, `Undo`/`RedoAsync`), `MainMenuFactory`/`QuickAccessToolbarFactory`
(stateless static build functions — `ADR-0103`'s own rule 5 names this
shape directly: "a stateless static factory... a composition root does
not force every collaborator into one identical shape"), and
`WorkspaceLayoutPresetCoordinator` (the three named presets, `Apply`/
`Reset`). `MainWindow` itself retains only what `ADR-0103` names as
irreducibly a composition root's own job: root visual-tree assembly, the
`Opened`/`Closing` lifecycle handlers, keyboard-shortcut registration,
and the genuinely cross-collaborator bridges no single collaborator can
own (Ribbon's own `ActionCompleted`/`CategorySelected`, the Engineering
Cockpit's own construction).

**`EngineeringCockpit.cs`: 1,398 → 575 lines.** Six per-discipline
read-model collaborators (Mechanical/Requirements/Calculations/
Documents/Verification/Manufacturing), each in its own existing
`Tempest.App.Workspace.{Discipline}` namespace alongside that
discipline's own `*WorkspaceRegistration` — exactly `WP 12.0A`'s own
predicted seam. `EngineeringCockpit` itself becomes the composition
root: constructs all six with `new`, delegates every single-discipline
member to them directly, and retains the genuinely cross-discipline
aggregation (`Health`, `HealthScoreDisplay`, `KpiCards`, `AttentionItems`,
`OpenActions`, `BlockedItems`) and the Governance & Risk family
(Decisions/Risks/Milestones/Tasks) — neither is owned by any one of the
six named disciplines, so both stay on the root, per `ADR-0103`'s own
Composition-root Responsibility #4 ("wires the genuinely
cross-collaborator bridges that have no single natural owner... this
wiring is the composition root's own, irreducible job"). A shared,
stateless `CockpitFormatting` helper (`FormatCoverage`/`PercentOf`,
extracted from the cockpit's own prior private statics) is deliberately
not itself called a collaborator — never constructed, no state, no
composition root owns it.

## 3. What Was Found — Two Genuine Construction-Order Cycles, Both Resolved the Same Way

**`DocumentAreaView` needs `WorkspaceViewCoordinator`'s own
`BuildDocumentContent` to be constructed; `WorkspaceViewCoordinator`
needs `DocumentAreaView` (for `ShowTab`/`RemoveTab`) to do its own job.**
`CockpitView` needs `WorkspaceViewCoordinator`'s own `NavigateToObject`
(the Favourite Projects card's open-callback); `WorkspaceViewCoordinator`
needs `CockpitView` (for `Refresh()`) in nearly every one of its own
event handlers. Both are real cycles, not extraction mistakes — the
pre-decomposition source already had the identical shape, resolved with
a two-phase sequencing its own constructor remarks named directly: "a
local function's own captured-field flow state is evaluated at its own
declaration point, not its own later invocation point" — a field is
read lazily, via the null-forgiving operator, inside a closure that is
only ever invoked after the constructor has fully returned. This Work
Package moved that identical resolution one collaborator boundary out:
`WorkspaceViewCoordinator.Attach(documentArea, cockpitView)` is called
once, immediately after both are constructed; every constructor-time
event handler that needs either reads it through a nullable field with
`!`, exactly mirroring the original. `UndoRedoCoordinator` has the
identical `CockpitView` cycle for its own `UndoAsync`/`RedoAsync`,
resolved the same way via `AttachCockpitView`. Neither is a new pattern
— both are the one the source already used, applied at a new seam.

**A cross-collaborator sibling-reference risk, found and resolved before
it became real.** `ADR-0103` states plainly: "a collaborator never
depends on a sibling collaborator directly... an event, a callback
delegate, or a value passed once at construction — never a direct field
or constructor reference between two collaborators." Two real near-misses:
`WorkspaceLayoutPresetCoordinator.Apply`/`Reset` both need to close any
open Auto-Hide flyout first — the naive extraction would have given it a
direct `WorkspaceDockingComposer` reference; instead it takes an
`Action closeFlyout` delegate, wired once by `MainWindow`. The Digital
Thread graph's own per-root-object open-tab map
(`_openGraphViewsByRootId`) is written by `QuickAccessToolbarFactory`'s
own graph button and read by `WorkspaceViewCoordinator`'s own document-close
cleanup — genuinely cross-collaborator state with no single natural
owner (`ADR-0103`'s own Composition-root Responsibility #4 again), so it
stays a plain `Dictionary` `MainWindow` owns and passes to both, never a
reference from one collaborator to the other. `UndoRedoCoordinator`'s
own button-enablement refresh is fully reactive, subscribed once to the
already-existing `IUndoRedoStack.Changed` event — this actually
*simplified* the extraction versus the original source, which called an
explicit `RefreshUndoRedoButtons()` from four separate call sites; none
of those call sites need to know `UndoRedoCoordinator` exists at all now.

## 4. Architectural Lessons

**Passing a plain UI control or pre-existing session-state object to two
collaborators is not a sibling-collaborator violation.** `ADR-0103`'s
"never a direct reference between two collaborators" rule is about the
nine (six) named `Tempest.Desktop.Composition`/per-discipline
collaborators referencing *each other* — not about ordinary shared
dependencies like `StatusBarView`, `IUndoRedoStack`, or
`EngineeringDomainContext` flowing into several of them, the identical
way a Platform Service flows into several Platform Services' own
consumers. Recognising this distinction early avoided a much more
convoluted, purely-delegate-based design that the ADR's own text does
not actually require.

**A construction-order cycle is a genuine signal to check for a real
architectural problem, not just an implementation inconvenience —
and in both cases here, it wasn't one.** Each cycle was checked directly
against `ADR-0103`'s own rules before reaching for the two-phase
`Attach` resolution: neither collaborator needs the other at
construction time, only at first invocation, and neither is a sibling
referencing a sibling — a genuinely acceptable existing pattern, not a
design smell being papered over.

**`RibbonObjectActionHandlers`, the largest and most mechanical
extraction, was also the lowest-risk one — moved verbatim, not
rewritten.** Every one of its ~29 handler closures was transcribed
directly from the read source with only parameter-name substitution
(`_statusBar` → `statusBar`, etc.), never re-derived from what the
behaviour "should" be. `FeatureCompletionTests.cs`'s own pre-existing
direct tests of the two shared factories (`statusHandler`/
`duplicateHandler`) and several individually-dedicated handlers gave
strong existing regression coverage for this exact class of risk.

## 5. Regression

12 new characterization tests added before their own respective
extractions, both real, confirmed-by-direct-search coverage gaps: 5
`EngineeringCockpit` tests (`AttentionItems`/`OpenActions` fixed
concatenation order and conditional entries, three per-discipline KPI
card sets, Mechanical reads, cross-cutting Workspace reads — all had
zero prior direct test coverage), run and passing against the
*unrefactored* source first to establish a validated baseline, then
again after the collaborator extraction (17/17, both passes). 7
`MainWindow` tests (`MainWindowCompositionTests.cs` — Menu System
View/Layout/Document menus and Quick Access Toolbar Reset Layout/View
Relationships/Undo-Redo reactivity/Macros; no existing test had ever
constructed the Menu System or clicked a Quick Access Toolbar button).
Full Debug+Release regression, both configurations, run twice (once
immediately after each file's own extraction, once as the closing
gate): **2,245/2,245 passing, 0 Warnings/0 Errors** (2,031
`Tempest.Core.Tests` + 214 `Tempest.Desktop.Tests`, up from the 2,233
baseline `WP 12.3B` last recorded — 12 net new tests, zero regressions).

## 6. Key Takeaways

- `ADR-0103`'s own illustrative, non-binding table held up well:
  `MainWindow`'s nine realised collaborators match its own nine
  predicted ones by name and responsibility exactly; `EngineeringCockpit`'s
  six match its own predicted "one collaborator per Engineering
  Discipline" seam exactly. The one real implementation-stage judgement
  — where genuinely cross-collaborator aggregation logic stays on the
  composition root rather than inventing a seventh/tenth collaborator —
  was explicitly anticipated by `ADR-0103`'s own Composition-root
  Responsibility #4, not an improvisation outside it.
- Two construction-order cycles, one already-established resolution
  (two-phase `Attach`, moved from field-level to collaborator-level) —
  confirms `ADR-0103`'s own claim that this pattern introduces no new
  precedent for synchronous composition-root construction-time work.
- `ADR-0103` needed no factual correction — every rule it states held up
  against real, adversarial extraction pressure (two genuine cycles, one
  genuine near-miss sibling reference), not just the motivating
  evidence it was written from.

## 7. Governance Follow-Up — Architecture Review Finding 3

A read-only architecture/code review of this Work Package, run against
`ADR-0103`, `Desktop Composition Architecture.md`, `FOUNDATION.md`,
`ADR-0009`, `ADR-0017`, and `ADR-0023`, found ten findings — nine
non-blocking (documentation staleness, test-comment accuracy, and
cohesion/coupling refinement observations, tracked for future work) and
one, **Finding 3**, requiring closure before this Work Package could be
considered fully closed: `Desktop Composition Architecture.md`'s own
"Documentation Impact" section (written `WP 12.0A`) had stated
`Namespace Register.md` was "`WP 12.0B`'s own obligation, once real
collaborator types exist to record" — real collaborator types now
exist, but that register's own declared **Scope** has never covered
`src/Tempest.Desktop/` at all, for any namespace, at any prior Work
Package. The original implementation silently left this unreconciled —
a real gap against `FOUNDATION.md`'s own transparency discipline
("the willingness to document a contradiction honestly rather than
resolve it silently").

**Resolution, this same Work Package's own governance follow-up.** Two
options were weighed: extend `Namespace Register.md`'s own declared
Scope to cover `src/Tempest.Desktop/` and add a row for the new
`Tempest.Desktop.Composition` namespace, or disclose the gap explicitly
and reconcile every document that referenced it. The first was rejected
— `Tempest.Desktop.Composition` is one of *nine* `Tempest.Desktop`
namespaces (`Docking`, `Editors`, `History`, `Input`, `Tasks`,
`Theming`, `Views`, `DigitalThread`, plus the root namespace itself),
none of which this register has ever tracked; adding a row for only the
newest one would not close the real gap, only mask one piece of it
inconsistently — the identical class of half-measure this project's own
governance discipline has consistently rejected elsewhere. Disclosure
was chosen instead: `Namespace Register.md` itself now states this
exclusion explicitly in its own **Scope** field and records the full
reasoning in a new `WP 12.0B` (follow-up) "Last Reviewed" entry,
including a separately-disclosed, related finding — the six
`Tempest.App.Workspace.*` discipline namespaces this Work Package added
files to are themselves part of an older, larger, previously-undisclosed
gap (`src/Tempest.App/` is in scope, but no `Tempest.App.Workspace` row
of any kind has ever existed in this register, predating `WP 12.0B`
entirely). `Desktop Composition Architecture.md`'s own now-inaccurate
sentence was corrected in place, not silently left standing, and
`docs/releases/v0.12.0/WorkPackages.md`'s own `WP 12.0B` row was updated
to match — all three documents, plus this retrospective, now agree.
