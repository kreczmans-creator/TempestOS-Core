# WP 12.2A — Presentation Strategy Execution Architecture

## What This Document Is

The architecture-phase retrospective for `WP 12.2A`, the roadmap-defined
`v0.12.0` Work Package (`docs/releases/v0.12.0/WorkPackages.md`,
originally scoped by `WP11.0B Architecture Roadmap.md` §3 as
"Presentation Strategy Execution (realises `WP 11.2A`'s decision)").
Architecture only — no code, no ADR unless genuinely justified, no
implementation. On its own new branch
(`feature/v0.12.0-presentation-strategy-execution`).

This Work Package's scope is not reinterpreted, renamed, or replaced
anywhere in what follows. What changed is the finding: systematic
discovery, performed before any solution was proposed (per this
project's own standing engineering process), establishes that the
scope named — executing `WP 11.2A`'s presentation-strategy decision —
has already been delivered, in full, by a different Work Package pair,
before `v0.12.0` even branched. That finding is documented here
explicitly, per this Work Package's own controlling instruction,
rather than re-deciding or re-implementing anything already settled.

### 1.3 What `WP 11.3A`/`WP 11.3B` actually decided and did

Read in full: `docs/releases/v0.11.0/WP11.3A Presentation Strategy
Review.md` (review) and `docs/releases/v0.11.0/WorkPackages.md`'s own
`WP 11.3B` row (implementation).

`WP 11.3A` (Review only, Complete) found `WP11.0A`'s "two independently
maintained, full presentation stacks" framing imprecise: the real shape
is a shared Workspace domain layer `Tempest.Desktop` genuinely depends
on, plus a console *presentation* layer it has zero code dependency on.
Within that console layer, `TempestShell` was provably dead code
(unreachable since `ADR-0068`, `v0.8.0`, three releases); `WorkspaceShell`
was live, real, and doing genuine harness work. Recommended (Option 3,
scored 21/25 against three alternatives, informal 1–5 Engineering Trade
Study) a five-stage, minimum-disruption roadmap:

1. Correct `README.md`/`Contributor Learning Path.md`.
2. Retire `TempestShell`/`IPage`/`PlaceholderPage`/`TempestShellTests.cs`.
3. Author a new ADR formally classifying `Tempest.App`/`WorkspaceShell`
   as TempestOS's Internal Engineering Harness, not a shipped product.
4. Correct `ci.yml`/`release.yml` release-artifact packaging.
5. *(deferred, not recommended now)* Any further trimming of
   `WorkspaceShell`'s own test coverage or feature scope, only if a
   real, demonstrated cost problem emerges — explicitly not scoped.

`WP 11.3B` (Implementation, Complete) "executes `WP11.3A`'s own approved
Stages 1–4" — Stage 5 deliberately excluded, exactly as recommended.

## 2. Phase B — Architectural Analysis

### 2.1 Does `WP 12.2A` have any remaining scope?

**No.** `WP 12.2A`'s entire named scope — "execute `WP 11.2A`'s
decision" — presupposes an unexecuted decision. There is none: the
decision was made (`ADR-0101`) and four of its own five recommended
stages were executed (`WP 11.3B`), independently re-verified as
genuinely complete in §1.4 above, not merely claimed. The fifth stage
was not silently dropped — it was explicitly evaluated, explicitly
rejected *for now*, and formally logged as accepted Product Debt at
`v0.11.0`'s own release sign-off, with an explicit, named trigger
condition ("a real, demonstrated cost problem") that this Work
Package's own direct search confirms has still not occurred.

### 2.2 Alternatives considered for disposing of this finding

| Option | Assessment |
|---|---|
| **1. Execute Stage 5 now** (trim `WorkspaceShell`'s test coverage/feature scope) | **Rejected.** `WP11.3A`'s own review explicitly recommended against this absent a demonstrated cost problem; none has emerged (§1.4). Doing it speculatively here would violate this project's own repeatedly-applied "act only on demonstrated need" discipline (the same standard `WP11.3A` itself applied when it declined to recommend Option 4, "Promote the console," on identical grounds) and would silently expand `WP 12.2A`'s own scope beyond what the roadmap named, which this Work Package's own controlling instruction forbids. |
| **2. Re-run the presentation-strategy investigation from scratch**, treating `WP11.3A`/`WP11.3B` as if they had not happened | **Rejected.** Every material claim was independently re-verified directly against live source (§1.4), not merely trusted; none was found stale or incorrect. Redoing already-sound, already-implemented work would contradict this Work Package's own explicit instruction ("if existing implementation already satisfies part of the Work Package, document that explicitly rather than recreating it") and this project's own established "reuse what exists" discipline. |
| **3. Formally close `WP 12.2A` as delivered by `WP 11.3A`/`WP 11.3B`**, disclosed and dated, with zero remaining scope | **Adopted.** Directly precedented by this exact document's own sibling case (`WP 11.1B`/`WP 11.2A` renumbering, §1.2) — the identical situation (a roadmap-predicted Work Package's scope delivered under a different number) already has an established, working disposition pattern in this project's own governance. |
| **4. Leave `WP 12.2A`'s Status silently as "Not started"** | **Rejected.** Misrepresents `v0.12.0`'s true completion state ahead of `WP 12.9.0`'s own Release Preparation & Engineering Sign-Off; this project's own Governance Philosophy requires disclosing findings, not leaving a stale, inaccurate status line for a later Work Package to trip over. |

### 2.3 Is a new ADR required?

**No.** Engineering Governance §5's own ADR-creation criteria — "a
genuine, evaluated either/or choice with a rationale needing to be
recorded" — is not met here. No new architectural decision is being
made; `ADR-0101` already stands, unmodified, as the presentation
strategy decision, and this Work Package neither reverses, amends, nor
extends it (Governance §5 does not permit rewriting an ADR's own body,
the same constraint `WP11.3A` itself cited when it chose not to amend
`ADR-0068`/`ADR-0092`). This is a pure discovery-and-disposition
finding — the same "zero new ADRs added, reviewed directly against
Governance §5's own criteria" pattern the ADR Register's own history
already uses repeatedly for Work Packages that investigate and confirm,
rather than decide (for example, `WP 10.1B`, `WP 10.4A`, `WP 10.5A`–
`WP 10.5C`, all cited in `ADR Register.md`'s own "Last Reviewed" chain).

### 2.4 Is a new or updated architecture document required?

**No.** `docs/architecture/Shell & Composition Framework Architecture.md`
already carries the correct, current state — its own "Update, `WP
11.3B` (`ADR-0101`)" addendum, independently re-verified in §1.4,
already documents `TempestShell`'s retirement and the Internal
Engineering Harness classification accurately. Authoring a second
architecture document to describe a state the first already describes
correctly would create a duplicate source of truth this project's own
"one canonical declaration" discipline (`ADR-0105`, the immediately
preceding Work Package's own governing principle) exists specifically
to avoid.

## 5. Key Takeaways

- **Discovery before solution finds real, existing implementation
  more often than it finds a genuine gap** — this Work Package's own
  controlling instruction anticipated exactly this outcome ("if
  existing implementation already satisfies part of the Work Package,
  document that explicitly rather than recreating it"), and that is
  precisely what direct investigation found here.
- **A roadmap-predicted Work Package's scope can be delivered under a
  different number without ever becoming untracked** — this project's
  own governance already has a working disposition pattern for exactly
  this case (`WP 11.1B`/`WP 11.2A`'s own renumbering row), applied here
  a second time for `WP 12.2A`/`WP 11.3A`/`WP 11.3B`.
- **A deliberately deferred stage is not silently-abandoned scope** —
  Stage 5's own disclosure trail (`WP11.3A`'s own recommendation →
  `WP11.3B`'s own explicit "Stages 1–4" scoping → `WP11.9.0`'s own
  formal "Product Debt... deferred by design" sign-off entry) is a
  complete, three-Work-Package chain of honest disclosure, not a gap
  this Work Package needed to close.
- **"Do not assume an ADR is required" is a genuine test, not a
  formality** — this Work Package's own Phase B (§2.3) applied
  Engineering Governance §5's own criteria honestly and concluded no
  new ADR is justified, the correct outcome when no new either/or
  choice actually exists to record.
