# WP 13.11C — TD-51 Remediation Review & Trust-Boundary Verification

## 1. Introduction

`WP 13.11C` is a review Work Package. It audited `WP 13.11B`'s
remediation of the reopened `TD-51` against `ADR-0110`/`ADR-0111` and the
real implementation, using four fresh sub-agents — Security/Adversarial,
Runtime/Lifecycle, Verification/Test, Governance/Documentation — with the
three analysis disciplines strictly read-only and every revert experiment
and edit performed centrally. Committed as `c0f3a19` (8 files, +498/−17).

It found the production fix clean on every axis it was asked to prove,
and it found one thing that mattered a great deal: **the most
security-critical decision in `WP 13.11B` had no regression coverage
whatsoever.**

## 2. Purpose

To verify that `WP 13.11B` actually closed `TD-51`, that it did so
without introducing a regression, and — per its own explicit test
discipline — to prove each defence non-vacuously by reverting it and
observing the corresponding failure appear.

## 3. Background

`WP 13.11A` had reopened `TD-51`: an unresolvable constructor-parameter
type in a plugin crashed the whole Host on the `IModule` axis.
`PluginAssemblyLoader.DiscoverModuleTypes` threw from inside its own scan,
before `EnforceTrust` could reach `RecordDenied`, so the denied-type
registry stayed empty, so `WP 13.9.6`'s `isTypeExcluded` filter had
nothing to exclude, so
`ReflectionFrameworkDiscoveryService.CreateDescriptor`'s unguarded
`type.GetConstructor(Type.EmptyTypes)` rethrew it uncaught.

`WP 13.11B` closed it with two defences: the denial is now surfaced to
`EnforceTrust` through an `out PluginTrustDeniedException?` parameter so
`RecordDenied` runs before the throw, and the scan is allowed to run to
its **completed fixed point** (`??=` plus `break`) rather than aborting;
separately, `DiscoverModules` gained a narrow four-exception CLR
type-load guard around `CreateDescriptor`.

Critically, `WP 13.11B` **deliberately declined** `WP 13.11A`'s own
recommended "partial type list" shape, on the grounds that aborting the
scan would strand an already-resident assembly — trading a Host crash for
a silent trust bypass.

## 4. The Problem

Reverting the completed-fixed-point semantics to `WP 13.11A`'s
partial-list shape left **all 2,561 tests green**.

The reason is mechanical: every existing unresolvable-parameter test
deliberately places its secondary assembly in a directory the default
`AssemblyLoadContext` can never probe, precisely so the parameter type is
genuinely unresolvable. No assembly therefore ever becomes resident
mid-scan, and the partial list and the fixed-point list are byte-identical.

So the decision `WP 13.11B` argued for at greatest length — the one
standing between a contained crash and a silent first-party trust bypass
— was protected by nothing. A future "simplification" back to the unsafe
shape would have passed the entire suite.

A second, smaller problem: the claim that the four-exception guard was
"already used at three other call sites in this exact codebase",
inherited verbatim from `WP 13.11A` and softened rather than corrected by
`WP 13.11B`, is factually wrong. Exactly **one** other site carries that
filter; `LoadOne`'s neighbouring guard is a different three-exception
filter that omits `TypeLoadException` and adds `IOException`.

## 5. The Design

**The review design.** Four fresh sub-agents, three read-only, one
question each, with all mutation of the tree performed centrally by the
integrator so no agent could disturb another's evidence.

**The test design — the substantive output.** Closing the coverage gap
required a shape no existing fixture produced: a plugin exercising *both*
transitive-load mechanisms at once.

- An **unreachable tertiary** assembly supplies the constructor parameter
  type that cannot be resolved.
- A **reachable secondary** assembly, deliberately saved *alongside* the
  primary so directory probing genuinely finds it, carries a well-formed
  `InertModule` with a fully baseline-compliant constructor.
- The **primary** declares an anchor type deriving from the secondary's
  base type — so `Assembly.GetTypes()`'s base-type-chain resolution pulls
  the secondary into the `AppDomain` *during* the scan step, after that
  step's `before` snapshot — and a module whose sole constructor takes
  the unresolvable tertiary type, tripping the denial *mid-step*, before
  the step's own before/after diff is reached.

Under the partial-list shape the scan returns there and then: the diff
never runs, the secondary is never enqueued, and its well-formed module
is never recorded denied — yet it is resident and fully visible to Module
Discovery's plugin-unaware `AppDomain` scan. Under the completed scan,
the diff runs, the secondary is enqueued, and `RecordDenied` covers it.

This required one new `DynamicPluginAssemblyBuilder` helper — a merge of
the two existing single-mechanism builders, resolving both external types
through one temporary collectible `AssemblyLoadContext`.

## 6. Alternatives Considered

**Accept the gap and record it as debt.** Rejected: the review brief's
own test discipline required each defence be proven non-vacuously, and
that was impossible for this one without a test.

**Put the unresolvable constructor on the secondary's module instead.**
Rejected on analysis — the secondary's module is added to
`allModuleTypes` before its own constructor loop runs, so the partial
list would still contain it and the test would be vacuous.

**Reshape the production code to make it easier to test.** Rejected: the
production code was found correct on every axis, and a review Work
Package that rewrites the implementation it is auditing is no longer a
review.

## 7. Why This Solution Was Chosen

Because the missing artefact was evidence, not code. The fix was right;
what was absent was proof that it was right *for the reason its author
gave*. Adding one test that fails under exactly the reverted decision —
and passes with it — converts an argued rationale into a demonstrated
one, and pins the decision against future well-intentioned simplification.

## 8. Architectural Principles

- **Non-vacuity is a property you prove, not assume.** A test that passes
  with and without the fix protects nothing.
- **Review does not rewrite.** No production behaviour was changed; the
  only `src/` edit was a comment correcting a false factual claim.
- **Disclose, don't fabricate.** The wrong "three other call sites" claim
  was corrected in every document that repeated it, with attribution,
  rather than quietly softened.
- **Test the decision, not just the outcome.** Two defences were already
  covered; the third — a *design choice* rather than a code path — was
  not, and needed a fixture built specifically to distinguish it.

## 9. Benefits

The completed-fixed-point decision now has a dedicated regression test
that fails on its own load-bearing assertion when the decision is
reverted. `WP 13.11B`'s trust-bypass argument became a demonstrated
result. A factually wrong claim was removed from four documents and one
production comment. And all three defences were individually proven:
reverting `RecordDenied` fails four tests; reverting the discovery guard
fails exactly one; reverting the completed-scan semantics fails exactly
the new test; reverting the first two together reproduces `TD-51`'s Host
crash end-to-end (`Expected: Running, Actual: Faulted`).

## 10. Trade-offs

The new fixture is the most intricate in the plugin suite — three
assemblies, two link mechanisms, and an ordering dependency on when the
`before` snapshot is taken relative to `GetTypes()`. That intricacy is
inherent to the behaviour being distinguished, but it raises the cost of
understanding the test for a future maintainer, which is why its own
remarks document the mechanism at length.

It also adds one permanently-resident dynamic assembly to the default,
non-unloadable `AssemblyLoadContext` (`ADR-0015`), against a suite
baseline already in the low thousands — immaterial, and measured rather
than assumed.

## 11. Common Mistakes

- **Mistaking a green suite for coverage.** 2,561 passing tests said
  nothing about the decision under review.
- **Building the fixture so the mechanism cannot fire.** The first
  version of the new test failed *with the fix in place* — a
  `SingleOrDefault` matched two same-named assemblies because the
  builder's collectible context unloads asynchronously. It briefly looked
  as though `WP 13.11B`'s central claim was false, and it invalidated a
  revert result that had to be redone. The fix was to resolve explicitly
  through `AssemblyLoadContext.Default`.
- **Softening an inherited claim instead of checking it.** `WP 13.11B`
  converted "three other call sites" into an unquantified plural rather
  than counting. The count was one.

## 12. Future Evolution

`WP 13.11D` then performed the `v0.13.0` exit review and declared the
platform ready for WP14. This Work Package also observed a live
intermittent Release-run failure — 2,561/2,562, then 2,562/2,562 on an
immediate re-run of identical binaries — and extended `TD-34` to record
it and to name an untracked sibling hazard:
`tests/Tempest.Core.Tests/Logging/ConsoleLogSinkTests.cs` redirects
process-global `Console.Out` while sitting outside the collection that
serialises the other classes doing the same. Adding that one class to the
collection is the smallest available mitigation; it was deliberately not
applied here, this Work Package being a review.

## 13. Key Takeaways

- The most-argued design decision in a change is the one most worth
  testing, and the one most likely to have no test.
- Reverting each defence individually is the only reliable way to learn
  what a suite actually protects.
- A test that fails for an incidental reason is worse than no test — it
  masquerades as evidence.
- Correcting a false claim you previously repeated costs a paragraph;
  leaving it costs the next reader's trust in the whole record.
