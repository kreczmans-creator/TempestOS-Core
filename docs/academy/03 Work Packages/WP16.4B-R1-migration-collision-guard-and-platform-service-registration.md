# WP 16.4B-R1 — Migration Collision Guard and Platform Service Registration

## 1. Introduction

`WP 16.4B-R1` is a `v0.16.0` review board remediation, not a
Release-Plan Work Package — it exists because the Architecture
perspective found two problems in the integrated tree that no planned
Work Package had scoped. Branch `feature/v0.16.0-arch-remediation`, cut
from `feature/v0.16.0` at `ac7daa6`; commit `4f31591`, merged at
`c35ae95`. It closes two independently-verified review board findings —
a silent migration-collision hazard in `StateMigrationRegistry`, and
three Platform Services (`WP 16.4B`'s own three reconciliation
services) with no Platform Services Register or Platform Service Map
entry — and, in doing the second, closes `TD-126` in full.

## 2. Purpose

Neither finding has a Release Plan brief to cite, because neither
existed at plan time. The first is a defect the plan's own `WP 16.3A`/
`WP 16.3B` (`ADR-0120`, durable state schema versioning) did not
introduce deliberately but also never guarded against. The second is
Engineering Governance §6's own standing obligation — "any work package
that adds... a platform service's responsibility... updates that
service's entry as part of the same work package's Definition of Done,
never as a separate, later pass" — which `WP 16.4B` did not meet for
the three services it added. This Work Package's purpose is to close
both gaps and to close `TD-126`, a residual `WP 16.2A` had already
disclosed once and the review board re-raised.

## 3. Background

`ADR-0120` gives every durable `EngineeringObjectState` a `SchemaVersion`
and an ordered, per-Kind migration chain applied only on read.
`StateMigrationRegistry.Register` is the entry point that builds that
chain: a plain dictionary keyed by `(chain, FromVersion)`, with `Find`
preferring a common (Kind-less) migration over any Kind-specific one at
the same version — `ADR-0120` Decision 2, stated and unchanged by this
Work Package. `TD-126` — `docs/architecture/Platform Service Map.md`
having register rows but no detail sections for three `v0.14.0`
services — was a residual `WP 16.2A` recorded as outside its own
`docs/governance/**` ownership rather than fixed; the review board
re-raised it on 2026-09-05 alongside the new finding that `WP 16.4B`'s
own three reconciliation services had no entry in either document at
all, despite the Platform Services Register's own Coverage Status still
claiming "35 of 35 known Platform Services."

## 4. The Problem

`StateMigrationRegistry.Register`'s original body was `chain[migration.FromVersion]
= migration` — a plain, unconditional assignment. Two collisions were
possible and both were silently allowed: **same-chain duplicate**
(registering a second migration for the identical `(chain, FromVersion)`
pair — two common migrations at the same version, or two migrations for
the same Kind at the same version), where the second silently overwrote
the first; and **cross-chain collision** (registering a common migration
and a Kind-specific migration at the *same* `FromVersion`), where
whichever one lost — regardless of registration order, since `Find`
always prefers the common chain — would simply never run, while the
record's own `SchemaVersion` still advanced to `FromVersion + 1` and
looked fully migrated. This is precisely the "parses correctly but means
something different" failure `ADR-0120` exists to prevent, and it is
the identical defect *shape* — a dictionary assignment that silently
replaces an existing entry — `ADR-0122` had just closed for the DI
container's own `ServiceCollection.Add`/`AddInstance` (`TD-69`,
`WP 16.4B`), in a file one directory over, one Work Package earlier in
the same release.

There was also a test that had codified the hazard as a feature:
`WhenBothACommonAndAKindSpecificMigrationTargetTheSameVersion_TheCommonOneRunsFirst`
asserted the Kind-specific migration never running and the record still
advancing — the exact shape `RestApiHostedServiceTests`' pre-`WP 16.4B`
unauthenticated-`200` assertion had for `TD-62`.

## 5. The Design

`Register` now throws on both collision shapes: `DuplicateStateMigrationException`
for the same-chain case, `ConflictingStateMigrationException` for the
cross-chain case — checked in both directions explicitly (registering a
common migration scans every existing Kind chain at that `FromVersion`;
registering a Kind-specific migration checks the common chain), because
a guard that only caught one order would read as complete while still
allowing the other. Both are new sealed `EngineeringDomainException`
subtypes, mirroring `DuplicateRehydratorRegistrationException`'s own
shape in `EngineeringObjectRehydrator.cs`, one file up in the same
namespace — not a new exception root, and not `StateMigrationRegistry`
hanging its new failures off some unrelated existing type. `Find`'s own
ordering — common chain first — is untouched; this fix removes the
*ambiguous* registration state that made that ordering destructive, not
the ordering itself.

**No `allowReplace` escape hatch was added — a deliberate, disclosed
divergence from its own sibling fix.** `TD-69`'s `IServiceCollection.Add`
needed one because roughly 330 real call sites across the codebase
depended on the old last-wins behaviour continuing to compile and, in
one case, actually relied on being able to replace a registration
deliberately. Here, a repository-wide search for
`IStateMigrationRegistry`/`StateMigrationRegistry` usage outside this
file, `StateMigration.cs`, and `TempestHost.cs`'s own empty-registry
registration found **zero real migrations registered anywhere in
`src/`** — `CurrentSchemaVersion` is `1`. Nothing depends on replacing a
migration once registered, so an escape hatch was judged to exist for a
hazard that would only reopen the one just closed, and was not added.

For the second finding: three new rows in the Platform Services
Register (Requirements Reconciliation, Material Catalog Reconciliation,
Attachment Content Reconciliation), Coverage Status corrected to 38 of
38; and, in `docs/architecture/Platform Service Map.md`, an "At a
Glance" row plus a full Responsibility/Key types/Dependencies/Consumers/
Lifecycle/ADR-reference/Academy-reference section for each of the three
— every one stating prominently that nothing invokes the service, so a
reader a year from now does not mistake the absence of a caller for
dead code. `TD-126` was closed in the same pass: the three `v0.14.0`
services it actually named (Plugin Trust & Capability Enforcement,
Engineering Object Durability & Rehydration, Attachment Content Store)
all gained complete detail sections, and — found only while doing this
— none of the three had an "At a Glance" row either, so those were
added too.

## 6. Alternatives Considered

**Hang the two new exceptions off an existing base**, the way `TD-69`'s
fix considered and rejected reusing `ServiceResolutionException`. Not
seriously considered here — `DuplicateRehydratorRegistrationException`
was an exact, same-file-family precedent already established for
registration-time collisions in this exact subsystem, and following it
required no new judgement call.

**Add an `allowReplace` opt-in, mirroring `TD-69`.** Available, and
explicitly considered — the report frames it as "a considered 'no,' not
an oversight." Rejected on the evidence that zero real migrations exist
to need replacing, not on principle; the report itself invites being
argued out of it if a real need surfaces.

**Fold the `WP 10.6A` Platform Service Map gap into this pass.** Found
while adding the six new detail sections — `User Command Macros` and
`External Controller / Input Binding` are also missing both an "At a
Glance" row and a detail section, a pre-existing gap distinct from
`TD-126`. Left disclosed, not fixed: folding an unrelated gap into this
change would have blurred what this Work Package's own commit actually
closes.

## 7. Why This Solution Was Chosen

The migration-collision fix follows an idiom this codebase had already
established twice in the same release (`TD-69`'s DI guard;
`DuplicateRehydratorRegistrationException`'s own precedent), so the
*shape* of the fix required no new design. The harder decision — whether
to add the same `allowReplace` escape hatch its sibling fix needed — was
made on the strength of a direct audit rather than by pattern-matching
the sibling's own answer: `TD-69` needed the hatch because real code
depended on replace semantics; this fix's own audit found no such
dependency, so adding one anyway would have reopened, for no proven
need, the exact hazard the guard exists to close.

## 8. Architectural Principles

- **A defect shape found and closed once should prompt a search for the
  same shape elsewhere, not just a fix at the one site a reviewer
  happened to name.** The migration registry's own silent-overwrite
  hazard existed, unclosed, one file away from `TD-69`'s identical fix
  for the entire duration of that Work Package — nothing about `TD-69`'s
  own scope required noticing it, and nothing did.
- **An escape hatch is a decision made on evidence of real need, not
  granted symmetrically because a sibling fix needed one.** This
  Work Package's own audit — zero real migrations registered anywhere —
  is what justifies withholding `allowReplace` here, not a general
  preference for stricter APIs.
- **A Platform Service's Register and Map entry is part of the
  introducing Work Package's own Definition of Done, never a later
  pass** — Engineering Governance §6's own text, and the gap this Work
  Package exists to close for `WP 16.4B`'s three services is a direct
  instance of that rule not being followed the first time.

## 9. Benefits

- `TD-126` closed in full, with detail sections and "At a Glance" rows
  for six services total (three new, three residual).
- Two new, precisely-scoped exception types with five regression tests,
  including the one that matters: a Kind-specific migration registered
  after a same-`FromVersion` common one, and the reverse order, both
  throw — a guard proven in both directions, not just the order a first
  pass happened to test.
- The pre-existing regression test that asserted the hazard as correct
  behaviour was removed and replaced with one asserting the real
  invariant end to end (common at version 1, that Kind's own later
  migration at version 2, walked 1 → 2 → 3 correctly).
- While re-deriving the Exception Register's own Distribution-by-Root-
  Category table for its own two new rows, a pre-existing arithmetic
  drift from the `WP 16.4B` integration was found and corrected in the
  same pass (Dependency Injection 4 → 6, Requirements 5 → 6) — disclosed
  in the table's own text, not silently absorbed.
- `pwsh -File scripts/governance-healthcheck.ps1`: the Exception
  Register check, failing before this Work Package (89 declared, 87
  register rows), now passes (89 declared, 89 rows). 14 passed, 2
  warned, 0 failed, of 16 checks — both warnings pre-existing and
  unrelated.
- `dotnet test tests/Tempest.Core.Tests -c Release` — 3,189/3,189
  (baseline 3,185; net +4 — one defect-asserting test removed, five new
  tests added).

## 10. Trade-offs

**The report closes with an explicit "No ADR" line, for a decision this
Work Package's own governing standard arguably required one for.**
Engineering Governance §5 requires an ADR when a decision "was not the
only reasonable choice available, and at least one genuine alternative
was seriously considered and rejected," or when it "establishes a
convention future work packages are expected to follow." The
`allowReplace` omission meets both readings on its own report's own
words: `allowReplace: true` was a real, considered alternative — its
own sibling `TD-69` fix chose it for the identical defect shape — and
rejected here specifically; and the choice sets the pattern the next
person adding a migration, or the next person closing a similar
collision hazard elsewhere, will look to. This retrospective did not
find an ADR filed for this decision anywhere in `docs/adr/` at the time
of writing, and does not assert one exists — only that the report's own
"No ADR" line, read against §5's own stated criteria, is a live
governance question this Work Package leaves open rather than one it
answers. Whether it should be treated as ADR-worthy, and by whom, is
recorded here as unresolved, not settled by this retrospective.

**No runtime backstop if a future migration path ever needs to replace a
registration.** The decision is correct against today's evidence (zero
real migrations); it is not evidence-proof against tomorrow's. The
report's own text says as much.

**The `WP 10.6A` Platform Service Map gap remains open**, found and
named but explicitly not folded into this Work Package's own scope.

## 11. Common Mistakes

- **Closing one instance of a recurring defect shape without a
  repository-wide sweep for the same shape.** `TD-69`'s own fix did not
  ask "where else does this codebase do a plain dictionary assignment
  that silently replaces an existing entry" — this Work Package exists
  because a reviewer, not a mechanical check, asked that question one
  Work Package later.
- **Adding a Platform Service without its Register and Map entry, on
  the theory that documentation can follow later.** `WP 16.4B` shipped
  three real, DI-registered services with neither — Governance §6 names
  this exact failure mode as the one it exists to prevent, and it
  happened anyway, one Work Package after the rule was restated.
- **Closing a Work Package with "No ADR" without checking the decision
  against §5's own stated criteria first**, rather than after an
  external reviewer asks. This report's own governance framing does not
  show that check having happened.

## 12. Future Evolution

The `WP 10.6A` Platform Service Map gap (`User Command Macros`,
`External Controller / Input Binding`) is named, not fixed, and is a
natural next-Work-Package item distinct from `TD-126`. The
`v0.16.0` Engineering Status Report's own open question 4 — whether
`allowReplace` is the right escape hatch for the DI container at all,
given the `TD-69` audit found zero legitimate replacers among ~330 call
sites — sits directly beside this Work Package's own opposite answer
for migrations (no escape hatch, because zero legitimate replacers)
without either document connecting the two; a future governance pass
could usefully ask whether the codebase wants one consistent answer to
"does a silent-overwrite guard need an opt-in" rather than two
independently-reasoned ones. Whether the `allowReplace` omission here
needed an ADR at the time it was made, per §5, is recorded above as
unresolved and is this area's own to settle.

## 13. Key Takeaways

- A defect shape closed once in one file is not closed everywhere it
  appears — the same silent-overwrite pattern existed unguarded one
  directory over for the length of the Work Package that fixed its
  sibling, and nothing about that Work Package's own scope would have
  surfaced it.
- Withholding an escape hatch on the strength of a direct usage audit
  (zero real migrations exist to need one) is a legitimate, defensible
  engineering call — but a legitimate call that meets an ADR Creation
  Rule's own stated criteria still needs the ADR at the time it is made,
  not only if and when an external reviewer asks for one.
- Engineering Governance §6's Platform Service Map/Register obligation
  is stated as part of the *introducing* Work Package's own Definition
  of Done for a reason: a remediation Work Package existing to add the
  documentation a prior one skipped is exactly the "separate, later
  pass" the rule was written to prevent.
