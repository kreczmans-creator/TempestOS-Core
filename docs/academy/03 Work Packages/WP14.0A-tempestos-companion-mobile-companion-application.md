# WP 14.0A — TempestOS Companion: Mobile Companion Application

## 1. Introduction

`WP 14.0A` built TempestOS Companion — the platform's first non-desktop
client: a separate-process Avalonia single-view mobile application for
awareness, triage, and controlled quick actions — together with the REST
API evolution it needs (a late-bound query-and-action surface), in one
architecture-through-validation sweep. It is the first Work Package of
the `v0.14.0` train (in preparation) and the first concrete step on
`FCR-0023` (Offline/Mobile), which `Product Roadmap.md` had parked in
Phase 8 and this Work Package's commissioning brief explicitly pulled
forward. Three ADRs (`ADR-0113`–`ADR-0115`), three new projects
(`Tempest.Companion`, `Tempest.Companion.Contracts`,
`Tempest.Companion.Tests`), additive changes to `Tempest.Core.Api` and
`Tempest.App`, and 75 new tests (23 API-surface, 52 Companion) shipped
together; the complete pre-existing suite passes unchanged in Debug and
Release.

## 2. Purpose

Give TempestOS a genuine mobile operational window — "what is happening
right now, what needs my attention, what can I safely deal with from my
phone?" — without creating a second platform: no competing architecture,
no shadow domain model, no parallel identity system, no second source of
truth.

## 3. Background

Through `v0.13.1` every presentation surface composed the Engineering
Workspace in-process: the Avalonia desktop (`ADR-0092`/`ADR-0094`) and
the console harness (`ADR-0101`), both through
`EngineeringWorkspaceComposer`. The REST API (`WP 6.3`) existed but was
a route-to-zero-argument-command trigger with plain-text responses —
structurally unable to serve data to any remote client. The Engineering
Cockpit (`ADR-0069`, `WP 10.1A`) already computed exactly the awareness
model a mobile client needs; nothing could reach it from outside the
process.

## 4. The Problem

Four problems had to be solved together, and honestly:

1. **No read path over the wire** — `CommandResult` has no payload; no
   route could return JSON at all.
2. **A route-registration ordering trap** — Kestrel snapshots routes at
   hosted-service start (Phase 8.1), but the Workspace read models the
   Companion needs exist only *after* the Host starts.
3. **A commissioning brief describing things that do not exist** — an
   "offline dashboard implementation", invoice/contract business
   management, and "established" brand assets, none of which appear
   anywhere in code or governance. Reconnaissance had to establish this
   before design, and the resolution had to be recorded, not improvised.
4. **An environment that cannot build mobile heads** — .NET mobile
   workloads and the Android SDK were unobtainable under the build
   environment's network policy.

## 5. The Design

- **`ADR-0113`**: the Companion is a separate OS process — Avalonia
  11.2.3, the desktop's own pure-C# view authoring and headless test
  strategy, a single-view shell (`ISingleViewApplicationLifetime`-ready)
  shipped today behind a phone-frame desktop head. It references only
  `Tempest.Companion.Contracts` — the dependency-free wire contract both
  sides share — never `Tempest.Core`/`Tempest.App`.
- **`ADR-0114`**: `Tempest.Core.Api` gains `IApiQueryRegistry` —
  `MapQuery` (GET → JSON produced by a registered delegate) and
  `MapAction` (POST → body bound to an existing typed command,
  dispatched through the unmodified Command Framework) — served through
  one catch-all fallback resolved per request, which is what makes
  post-start registration by the Workspace composition root legal.
  `ADR-0063`'s reads-read/mutations-dispatch rule, applied at the API
  boundary; the pipeline (identity → permission → audit → error map) is
  `ApiRequestHandler`'s, extended by exactly one case (binding fault →
  400).
- **Server-side registration in the shared composer**:
  `CompanionApiRegistration` is called from
  `RegisterEngineeringDisciplines`, so console and desktop serve the
  identical Companion API with zero presentation-layer changes
  (`ADR-0071`'s rule). `CompanionQueryService` projects the *same*
  `EngineeringCockpit` read models the desktop renders into DTOs — one
  authoritative read model, three surfaces.
- **`ADR-0115`**: offline is read-only snapshot caching with four
  disclosed freshness states (Live/Cached/Stale/Unavailable), 401/403
  never served from cache, and **no offline write queue** (`AT-24`) —
  the platform has no sync semantics to build one on honestly.
- **Mobile UX**: cockpit-first five-tab shell (Cockpit / Projects /
  Attention / Activity / More), the Command Palette as a global entry
  point (`ADR-0070`), 44dp touch floors, and a mandatory per-page state
  machine (loading / freshness banner / honest empty / error with
  Retry) enforced by the `CompanionPage` base class.
- **Brand realisation**: the first concrete TempestOS visual identity —
  Royal Blue `#1E2F97` / Electric Blue `#00AEEF` / Purple `#6C2BD9`
  used semantically, Chakra Petch + Inter + Space Mono, and the
  six-blade shutter/iris mark as code-drawn `StreamGeometry` — exactly
  the implementation phase `WP10.0A Visual Design System.md` deferred
  values to.

## 6. Alternatives Considered

Recorded in full in the ADRs; the majors: .NET MAUI and a browser/PWA
client (both rejected — second UI stack; `ADR-0094` precedent); shipping
Android/iOS heads now (rejected — unbuildable in this environment,
`TD-57`); extending `CommandResult` with a payload (rejected — inverts
`ADR-0063` platform-wide); a discovered module mapping Companion routes
(rejected — would activate in every test host and still could not reach
post-start read models); an offline write queue and a local SQLite
mirror (both rejected — a second source of truth on the least trusted
device, `ADR-0115`).

## 7. Why This Solution Was Chosen

Every choice reduces to one discipline: reuse the platform's own
established answer wherever one exists. Avalonia and C#-constructed
views because the desktop proved them; reads-vs-mutations at the API
because `ADR-0063` already settled it in-process; composition-root
registration because `ADR-0071` already settled who registers;
`X-Identity-Id` + `IPermissionEvaluator` because inventing client auth
would fake security the platform deliberately does not claim
(`TD-13`/`TD-14`); honest freshness disclosure because the Cockpit's own
placeholder discipline (`IsPlaceholder`, "no due-date field exists")
already set the truth-in-UI bar.

## 8. Architectural Principles

One source of truth for the wire shape (the contracts assembly); domain
≠ API representation ≠ presentation model, each named; dependencies flow
downward only — the Companion sits entirely above the API boundary;
mutations dispatch through the Command Framework without exception;
fail closed (unconfigured identity → 403; refused caller → no cache);
disclose, never fabricate (placeholders survive onto the wire; absent
domains become FCR entries, not fake data).

## 9. Benefits

A genuinely useful mobile window into a running TempestOS, today, over
loopback/tunnel; a reusable JSON query surface any future client (the
`FCR-0091` display, richer desktop remoting) consumes for free; the
platform's first concrete visual identity; and a Companion test suite
whose integration layer runs the production client against a real Host
and real Kestrel — no permanent mocks anywhere.

## 10. Trade-offs

No Android/iOS heads yet (`TD-57`); off-box production reach gated on
`FCR-0003`/`FCR-0004` (`TD-58`); no offline writes (`AT-24`); no
business-management surface because no such domain exists (`FCR-0089`);
notifications are poll-based and Host-session-bounded (`FCR-0090`);
project drill-down renders the list DTO it was opened with rather than a
dedicated per-project query (a disclosed thinness, future FCR scope if a
need is named).

## 11. Common Mistakes

The traps this Work Package specifically avoided, for the next
contributor: assuming a brief's described artefacts exist (verify by
grep before designing against them); registering API routes before the
Host starts and wondering why Kestrel never serves them (the snapshot
ordering in §4.2 — use the late-bound surface); "fixing" mobile
connectivity by widening the loopback bind (that is the `TD-13`
vulnerability, weaponised); queueing offline writes without server
idempotency (silent divergence from the system of record); and letting a
body-binding action grow into a generic mutator (whitelist the Kinds the
discipline's command actually owns).

## 12. Future Evolution

`TD-57` (platform heads) is the natural next Companion Work Package once
an environment with mobile workloads exists; `FCR-0090` (push
notifications) and `FCR-0091` (the display client) both build directly
on `ADR-0114`'s surface; `FCR-0089` (business awareness) needs a domain
decision before any UI; real off-box deployment is exactly
`FCR-0003` + `FCR-0004`, after which `TD-58` closes and the security
review's findings 3–4 (at-rest encryption, rate limiting) become due.
When any of these land, update this section per §6's own rule.

## 13. Key Takeaways

A companion app is an architecture exercise, not a UI exercise: the hard
work was the boundary (what crosses the wire, who registers it, when),
and the platform's existing decisions answered almost every question if
read carefully. Honesty scales down to a phone screen — placeholder
disclosure, freshness states, and fail-closed authorization are what
make a small screen trustworthy. And a brief is input, not evidence:
reconnaissance before design turned three phantom concepts into three
governed future capabilities instead of three fabrications.

## Observations

- The two pre-existing Linux-environment test failures
  (`PluginTrustStoreTests.Constructor_TempestOSCerFileNameIsCaseInsensitive_StillFlaggedFirstParty`,
  `PersistenceStoreTests.DeleteAsync_FileLockedByAnotherHandle_…`)
  reproduce identically before and after this Work Package on the
  Linux build host used here (case-sensitive filesystem; advisory file
  locking) and pass on the pinned `windows-2022` CI runners. Pre-existing
  environmental characteristics, not regressions; unfixed as outside
  scope.
- `PROJECT_STATUS.md`'s own guidance ("keep it short — this is a
  dashboard") remains unfollowed by the file at 511 KB; noted, not
  addressed.
- The local build host could not satisfy `global.json`'s 10.0.302 pin
  (SDK unobtainable under network policy); validation ran on SDK
  10.0.111 via a version-named symlink, with the pin untouched. CI's
  `setup-dotnet` honours the pin as before.
