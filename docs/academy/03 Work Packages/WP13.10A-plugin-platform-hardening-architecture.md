# WP 13.10A — Plugin Platform Hardening Architecture

## 1. Introduction

This Work Package is a **read-only architecture/security hardening review**
of the complete `v0.13.0` plugin platform — every Work Package from
`WP 13.0A` through `WP 13.9.7` — conducted across six parallel disciplines
(Plugin Runtime Architecture, Security/Trust, Lifecycle/Composition,
API/Compatibility, Verification/Testability, Governance/Documentation),
with **no implementation of any kind**. It runs on `feature/v0.13.0`,
`v0.13.0` — "Trust & Deployment Hardening" — immediately after
`WP 13.9.7` committed the `WP 13.9.1`–`WP 13.9.6` remediation chain.

It found and formally registered two new, genuinely distinct
Release-Blocking findings — `TD-51` and `TD-52` — both confirmed against
the current, committed code with a live proof-of-concept, and **neither a
variant of anything the `WP 13.9.1`–`WP 13.9.6` chain had closed**. Both
findings are in `ADR-0111`'s own enforcement mechanism: the machinery the
whole `WP 13` trust chain exists to provide.

The Work Package produced no standalone report file — its findings were
delivered directly, in-session, to the commissioning conversation, and
recorded in the governance registers. It directly commissioned
`WP 13.10B` (the implementation), which `WP 13.10C` (the independent
review and integration) then committed, as `79e453f`.

## 2. Purpose

To answer one question honestly: after six consecutive rounds of
adversarial remediation (`WP 13.9.1`–`WP 13.9.6`) and a formal integration
pass (`WP 13.9.7`), **does the plugin trust boundary actually hold** — and
if not, exactly where, proven by real, executed code rather than by
reading.

The remit was explicitly read-only. Nothing in `src/` or `tests/` was
touched. The only permitted outputs were governance-register entries and a
direct in-session report — the deliberate separation of *finding* from
*fixing* that this project's own remediation-chain convention
(`WP 13.9.x`, `WP 13.2B`, `WP 13.3B`) had already established.

## 3. Background

`ADR-0110` decided *where* the plugin isolation boundary lives
(capability-scoped, in-process — not a separate `AssemblyLoadContext`,
which is not a genuine privilege boundary in modern .NET, and not process
separation). `ADR-0111` decided *what the capability model is made of* — a
second, ambient component-identity axis (`ICurrentComponentAccessor`)
reusing `ADR-0044`'s existing `Permission`/`IPrincipal`/`IPermissionEvaluator`
directly, enforced **statically at Plugin Loading** (capability-ceiling
check plus constructor conformance) and **dynamically at each call site**
(`IPermissionEvaluator.RequirePermission`). `ADR-0112` decided how a plugin
earns a trust tier. `WP 13.2A` implemented all three;
`WP 13.2B`/`WP 13.3A`/`WP 13.3B` reviewed and validated them end-to-end.

`WP 13.9.0` then opened an engineering-readiness review that produced the
`WP 13.9.1`–`WP 13.9.6` remediation chain — multi-assembly scanning
(`WP 13.9.3`), trust-denial enforcement at the execution boundary
(`WP 13.9.4`), Module Discovery closure (`WP 13.9.6`) — each of which
amended `ADR-0111` with a "Corrected" note rather than raising a fresh
ADR. `WP 13.9.6`'s own independent Adversarial Review, mutation-tested
against the real suite plus a standalone proof-of-concept, believed itself
to be "the third and, ... final correction closing the 'isolates the whole
plugin' execution boundary" (`ADR-0111`, prior text, since amended).

That belief is the background this Work Package tested. Every one of those
six rounds had scoped "the plugin trust boundary" as **coextensive with
the `IModule` pipeline**; none had asked whether the same static
enforcement applies uniformly to *every* way a plugin's own code can be
discovered, constructed, or granted ambient identity.

## 4. The Problem

The review's six disciplines each carried their own question. Two produced
registered findings.

1. **Security/Trust — does the static enforcement cover every discovery
   axis?** `PluginAssemblyLoader.EnforceTrust` discovers both `moduleTypes`
   and `hostedServiceTypes` (`DiscoverModuleTypes` returns the first and
   emits the second via an `out` parameter). The capability-ceiling check
   applies to the manifest, so it is axis-independent. But
   `HasCompliantConstructor` — and, with it, the
   `NeverEligibleServiceResolveTypes` denylist that blocks
   `Identity.CurrentComponentAccessor`/`Identity.CurrentPrincipalAccessor`
   from constructor injection — was invoked against `moduleTypes` only.
2. **Security/Trust — does the dynamic enforcement cover every path to the
   ambient-identity write surface?** `NeverEligibleServiceResolveTypes`
   names two *concrete* types. It says nothing about an ordinary,
   DI-public **interface** that internally reaches the same surface.
3. **Lifecycle/Composition — does a legitimately-passing plugin's hosted
   service actually run under its own component principal?**
   `ModuleLifecycleManager` had carried a `componentScopeProvider` hook
   since `WP 13.2A`; `HostedServiceManager` had no equivalent seam of any
   kind.
4. **Plugin Runtime Architecture, API/Compatibility,
   Verification/Testability, Governance/Documentation** — the remaining
   four disciplines. The record attributes neither registered finding to
   any of these four, and records no separate finding from them.

The two findings, as registered:

**`TD-51`.** `HasCompliantConstructor` and the
`NeverEligibleServiceResolveTypes` denylist were invoked only against a
plugin's discovered `IModule` types, never its discovered `IHostedService`
types. An `IHostedService`-only plugin assembly (zero `IModule` types) hit
`moduleTypes.Count == 0` and returned immediately after the
trivially-satisfied, empty capability-ceiling check — **its hosted
service's constructor was never inspected at all**. Live-PoC confirmed: an
`UnsignedLocal` manifest requesting zero capabilities, one `IHostedService`
type whose sole constructor took the concrete, denylisted
`Identity.CurrentComponentAccessor` — accepted, not denied. Compounded by
`HostedServiceManager` having no `componentScopeProvider`-equivalent hook,
so even a *legitimately-passing* plugin's hosted service ran with a `null`
ambient component principal — and `PluginTrustPermission.IsFirstParty(null)`
is `true`, so every dynamic capability check downstream was silently
skipped for it too.

**`TD-52`.** `IIdentityService.EstablishCurrentPrincipal` called
`ICurrentPrincipalAccessor.SetCurrent` directly, and `IIdentityService` is
an ordinary, DI-public, un-denylisted interface every sample module already
legitimately depends on. A plugin declaring
`plugin.services.resolve:Tempest.Core.Identity.IIdentityService` — an
innocuous-looking capability request — passed `EnforceTrust` cleanly, then
could call `EstablishCurrentPrincipal` for **any** configured identity at
runtime, with no ownership check. Because `ICurrentPrincipalAccessor` is
deliberately *not* call-chain-scoped (`ADR-0044`), the effect persisted
ambiently for every later, unrelated caller in the process. Live-PoC
confirmed.

`ADR-0111`'s own Decision text was the root of the first: it named only a
discovered `IModule` implementer as the constructor-conformance check's
subject, and `EnforceTrust` implemented that literal scope **faithfully**.
The code was not diverging from the architecture — the architecture was
narrower than the boundary it claimed to draw.

## 5. The Design

This is a review Work Package; its "design" is the review's own.

**Six parallel, read-only disciplines.** Plugin Runtime Architecture,
Security/Trust, Lifecycle/Composition, API/Compatibility,
Verification/Testability, Governance/Documentation. Parallel rather than
sequential, so that no discipline inherits another's framing — the exact
property that made the `IHostedService` axis visible at all, since the
prior six remediation rounds had each inherited the `IModule` framing from
their predecessor.

**A live proof-of-concept as the evidential standard, not a reading.**
Both registered findings were demonstrated against the current, committed
code by building a real plugin scenario and observing the actual outcome —
the `UnsignedLocal`, zero-capability, `IHostedService`-only manifest taking
the denylisted concrete accessor and being *accepted*; the
`plugin.services.resolve:...IIdentityService` manifest passing
`EnforceTrust` and reaching `EstablishCurrentPrincipal`. A finding that
could not be executed was not registered.

**Independent corroboration before registration.** `TD-51` was found by
the Security/Trust and Lifecycle/Composition reviewers *independently*,
each with its own proof-of-concept, from two different starting questions
("is the static check axis-complete?" and "does a hosted service get a
component scope?") that converge on the same defect.

**Classification, stated precisely.** Both findings were graded **Release
Blocking for third-party plugin support only**. `v0.13.0`'s
already-shipped, already-signed first-party modules are unaffected —
`src/Plugins/` is empty, so neither path is reachable in the product as it
actually ships — and WP14 UI/UX work is untouched, since it does not go
near the plugin trust boundary. This is a narrower and more honest grade
than a blanket "Release Blocking", and it is the grade `TD-51` retained
through every subsequent reopening.

**Remediation shape assessed, not designed.** Both findings were judged
closable via **existing mechanisms** — no new isolation mechanism, no
`AssemblyLoadContext`, no process separation, and **no new ADR**, only a
"Corrected" note on `ADR-0111`, the amendment pattern `WP 13.9.1`,
`WP 13.9.3`, `WP 13.9.4`, and `WP 13.9.6` had each already used. Both
reviewing disciplines reached that assessment independently.

**Governance registration as the only durable output.**
`Technical Debt Register.md` gained `TD-51` and `TD-52` (50 → 52 tracked
items). `Plugin Trust & Isolation Architecture.md`'s Status header and
Risks section gained a "Found, `WP 13.10A`" entry, explicitly marked
**NOT YET CLOSED** — a deliberate, temporary, self-flagging state that
`WP 13.10C` later had to correct, and did.

## 6. Alternatives Considered

- **Trust `WP 13.9.7`'s clean exit and start WP14.** The prior chain had
  exited clean, with `ADR-0111` recording its final correction as final.
  Rejected: "clean under the questions previously asked" is not "clean";
  the whole value of a fresh, parallel review is that it does not inherit
  the previous round's scope.
- **A single-reviewer pass rather than six parallel disciplines.**
  Rejected: `TD-51` was found independently by two disciplines approaching
  from opposite directions. A single reviewer following one thread would
  plausibly have found one half of it — the missing constructor check, or
  the missing scope hook — without recognising that the two compound.
- **Fix the findings in-flight, in this same Work Package.** Rejected by
  the commissioning remit: this Work Package is read-only. Separating
  finding from fixing preserves the independence of the later review
  (`WP 13.10C`) — a reviewer who has already written the fix cannot
  credibly re-verify it.
- **Raise a new ADR for hosted-service trust enforcement.** Rejected on
  the assessment of both reviewing disciplines: nothing here is a new
  decision. `ADR-0111` already decided that a plugin's discovered types
  are constructor-checked and that a plugin's code runs under its own
  component principal; the Decision text merely named one discovery axis
  where it should have named two. That is a **correction**, and this
  project has an established precedent for correcting an ADR in place
  rather than superseding it.
- **Introduce a real isolation mechanism (`AssemblyLoadContext`, process
  separation) now that a second escape path had been found.** Rejected:
  `ADR-0110` had already weighed and declined both, and neither finding is
  evidence against that decision — both are gaps in the *coverage* of the
  chosen mechanism, not evidence that the mechanism is the wrong one.
- **Grade both findings blanket Release Blocking.** Rejected as
  overstatement: with `src/Plugins/` empty, neither path is reachable by
  anything `v0.13.0` actually ships.

## 7. Why This Solution Was Chosen

A parallel, multi-discipline, read-only review with a live-execution
evidential standard was chosen because the failure mode being hunted was
**inherited framing**, not missing diligence. Six previous rounds of
genuinely rigorous adversarial review had each been rigorous *within* the
`IModule` frame. No amount of additional depth inside that frame would
have surfaced an axis the frame never named. Breadth across independent
disciplines, each free to define its own scope, is the mechanism that
breaks a shared blind spot; depth is not.

The live-proof-of-concept standard was chosen because `TD-51`'s first half
reads, on inspection, like a plausible-but-arguable concern ("is an
`IHostedService`-only plugin even a real shape?") and its second half reads
like a defensive nicety ("does a hosted service really need a component
scope?"). Executed, they are neither: the plugin loads, is accepted, and
runs holding the exact concrete type the denylist exists to keep out of
plugin hands. Execution converted two arguable readings into one
registered, gradeable, Release-Blocking finding.

Registration-only output was chosen because finding and fixing are
different kinds of work with different failure modes, and this project had
already established that separation as its convention.

## 8. Architectural Principles

- **Do Not Redesign Approved Architecture Absent a Genuine Defect** — both
  findings were assessed as closable within `ADR-0110`/`ADR-0111`'s
  existing mechanisms; no new ADR, no new isolation mechanism, and no new
  principal or permission type was proposed.
- **Evidence Over Assertion** — nothing was registered that had not been
  executed. Both `TD-51` and `TD-52` carry "Live-PoC confirmed,
  `WP 13.10A`" in their own register entries.
- **Independent Corroboration** — `TD-51` was reached twice, independently,
  by two disciplines with different starting questions, before it was
  written down.
- **Grade Honestly, Including Downwards** — "Release Blocking for
  third-party plugin support only", not "Release Blocking"; the
  distinction is load-bearing and was preserved by every later Work
  Package that touched these items.
- **Disclose In Progress, Not Only On Completion** — the Risks entry was
  written as "Found, `WP 13.10A` — **NOT YET CLOSED**", so the security
  architecture document was never silently wrong about its own state, even
  for the window between finding and fixing.
- **Separation of Finding From Fixing** — a read-only reviewer keeps the
  later independent review honest.

## 9. Benefits

- **Two genuine, live-confirmed escape paths in the trust platform's own
  enforcement were found before any third-party plugin existed** — while
  `src/Plugins/` is still empty and the cost of closure is a handful of
  additive changes, not a compatibility break.
- **`ADR-0111`'s Decision text was shown to be narrower than the boundary
  it claims** — a documentation-level defect with a code-level consequence,
  which is exactly the class of defect a code-only review does not find,
  because the code faithfully implements the narrow text.
- **The "third and final correction" claim in `ADR-0111` was falsified by
  evidence rather than left to age into a false statement of record.**
- **The remediation shape was settled before implementation began** —
  existing mechanisms, no new ADR, a "Corrected" note on `ADR-0111` — so
  `WP 13.10B` began with an agreed scope rather than an open architectural
  question.
- **The parallel-discipline pattern was validated on a platform that had
  already survived six sequential adversarial rounds**, which is the
  strongest available evidence that the two review shapes are
  complementary rather than redundant.

## 10. Trade-offs

- **A read-only review leaves the platform knowingly broken for a window.**
  Between this Work Package and `WP 13.10C`'s commit, the trust boundary
  had two documented, live-confirmed holes, and the governance record said
  so in plain text. This is the correct trade — the alternative is an
  unreviewed fix — but it is a real one.
- **Six parallel disciplines cost more than one reviewer**, and four of the
  six produced no registered finding. That is not waste — a discipline that
  looks and finds nothing has produced a negative result — but the cost is
  paid up front, before anyone knows which two disciplines will pay.
- **No standalone report file was produced.** Findings were delivered
  in-session and captured in the registers only. Everything durable
  survives in `TD-51`/`TD-52` and the Risks entry, but the review's own
  full reasoning across all six disciplines does not exist as a document.
- **The review's own conclusions were not themselves independently
  re-verified at the time.** `WP 13.10C` re-verified the *fix*;
  `WP 13.11A` later re-examined one of `WP 13.10C`'s characterisations and
  found it partly false (see §12). A review's findings are evidence, not
  proof, and this chain demonstrates it.
- **Registering a finding is not fixing it.** `TD-51` and `TD-52` sat Open
  in the register between this Work Package and `WP 13.10C`'s commit.

## 11. Common Mistakes

1. **Assuming "the plugin trust boundary" means "the `IModule`
   pipeline".** This is the precise assumption six previous remediation
   rounds each inherited. A plugin's code reaches the process along at
   least two discovery axes — `IModule` and
   `BackgroundServices.IHostedService` — and enforcement that covers one is
   not enforcement.
2. **Assuming a denylist of concrete types covers the interfaces that
   reach the same surface.** `NeverEligibleServiceResolveTypes` names
   `CurrentComponentAccessor` and `CurrentPrincipalAccessor` by type.
   `IIdentityService` is neither, is DI-public, is legitimately depended on
   by sample modules — and reaches `SetCurrent` directly. A type-name
   denylist is a static, closed enumeration; the set of interfaces that can
   reach a write surface is not.
3. **Assuming a check that returns early on an empty collection is safe.**
   `if (moduleTypes.Count == 0) return;` looks like a harmless
   nothing-to-do guard. For an `IHostedService`-only assembly it was the
   entire enforcement bypass.
4. **Assuming a `null` ambient principal is a neutral default.** It is not:
   `PluginTrustPermission.IsFirstParty(null)` is `true`. Absence of an
   established component scope is not "no trust decision" — it is "maximum
   trust", by design, so that first-party callers skip the gates. Any code
   path that fails to establish a scope therefore fails *open*, for that
   specific reason.
5. **Assuming a previous review's "final" is final.** `ADR-0111` said the
   `WP 13.9.6` correction was the third and final one, on the strength of a
   mutation-tested adversarial review plus an independent proof-of-concept.
   It was a completely honest claim about a scope that turned out to be
   narrower than the boundary.

## 12. Future Evolution

- **`TD-52` remained closed** after `WP 13.10B`/`WP 13.10C`. A separate,
  later item — `TD-56`, raised read-only by `WP 13.11D` and deliberately
  not fixed there — records that a plugin's own *constructor* executes
  outside its component scope on both axes (the scope is pushed after the
  instance is created), so within the constructor window
  `IdentityService.EstablishCurrentPrincipal`'s gate, along with every
  other capability gate, is skipped for a `VerifiedSigned` or `FirstParty`
  plugin. That is registered as a new item against the scope-establishment
  mechanism, **not** as a reopening of `TD-52`.
- **`TD-51` was subsequently reopened.** `WP 13.11A`'s Final Hardening
  Architecture Review re-examined the residual "unresolvable constructor
  parameter type" gap that `WP 13.10C` had disclosed and characterised as
  safely isolated, found that characterisation false for the `IModule`
  axis, and moved `TD-51` Resolved → **Reopened** (still Release Blocking
  for third-party plugin support only, exactly as graded here).
  `WP 13.11B` then closed it again; `WP 13.11C` reviewed that closure and
  applied one factual correction to the register text; `WP 13.11D`
  confirmed against real source that it remains closed. None of that was
  known to, or knowable by, this Work Package.
- **Two further, non-plugin-specific items** were raised by the same
  `WP 13.11A` reviewer — `TD-53` (`HostedServiceManager.StartServiceAsync`'s
  critical-service failure classification) and `TD-54`
  (`ITempestServiceProvider`'s DI-escape closure being correct only
  incidentally, not as an explicit denylist entry) — both low-severity and
  non-blocking, neither a variant of `TD-51`/`TD-52`.
- **The governance sign-off `WP 13.10C` later called for** — explicit
  approval before any third-party publisher is granted
  `plugin.identity.establish` — remains outstanding future governance work,
  not code.
- **A real, non-synthetic signed plugin** remains the unmet trigger for all
  of this machinery, exactly as it was at `WP 13.2A`. Every
  proof-of-concept behind these findings used a dynamically-built,
  in-memory assembly.

## 13. Key Takeaways

- **Six sequential rounds of rigorous adversarial review closed six real
  gaps and left two, because all six inherited the same frame.** The fix
  for inherited framing is parallel independent disciplines, not another
  round of the same review, however deep.
- **A faithfully-implemented architecture can still be an insecure one.**
  `EnforceTrust` did precisely what `ADR-0111` said. The defect lived in
  the Decision text, one noun wide: "a discovered `IModule` implementer"
  where the boundary required "a discovered `IModule` or `IHostedService`
  implementer". Reviewing code against its own ADR would have found
  nothing.
- **Execute the finding.** Both findings read as arguable on inspection and
  are unarguable once run. "Live-PoC confirmed" is the difference between a
  register entry that gets fixed and one that gets debated.
- **A `null` that means "trusted" is a trapdoor under every code path that
  can fail to set it.** `IsFirstParty(null) == true` is the right design
  for first-party callers and is, simultaneously, the mechanism by which a
  missing scope hook silently granted a plugin's hosted service full
  first-party authority.
- **"Final" is a claim about the questions asked so far.** `ADR-0111`'s own
  "third and final correction" was honest, evidenced, and wrong — and the
  review that falsified it was itself later falsified, in part, by
  `WP 13.11A`. The record's value is that each of those turns is written
  down.
