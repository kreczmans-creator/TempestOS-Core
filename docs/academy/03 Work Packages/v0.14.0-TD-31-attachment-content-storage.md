# TD-31 — Attachment Content Is Durable Bytes This Platform Holds

## 1. Introduction

`3715aa8` closed `TD-31`, implementing `ADR-0114`: attachments gained a
real byte-storage path, `IBinaryPersistenceStore`, the byte shape of the
same `PersistenceStore` `TD-59` had already hardened. A pre-`v0.14.0`
engineering-body-of-work row; produced the companion Academy runtime-
architecture article
`docs/academy/02 Runtime Architecture/37-attachment-content-storage.md`.

## 2. Purpose

To give the Document Viewer (`TD-80`) something to open: `IAttachment` had
carried `FileName`, `ContentType` and `SizeInBytes` since `WP 8.2C` and
never the bytes.

## 3. Background

`FCR-0054` had left the design question open in three parts: local
filesystem storage, a blob-storage abstraction, or an external DMS
integration. All three were bigger than the answer actually needed:
`PersistenceStore` is already a file store — one file per record under a
configured root — so storing bytes in it is not a new capability, it is
the capability it already has reached through a different door.

## 4. The Problem

An attached file was a description of a file, never the file. A user
could see that a drawing had been attached and never see the drawing
itself.

## 5. The Design (`ADR-0114`)

`IBinaryPersistenceStore` is the byte shape of the *same*
`PersistenceStore` class, instance and root: it shares `GetFilePath`,
`LockKey`, `ResolveReadablePath`, `ExistsWithExactName` and the write-to-
temporary-then-rename outright, so `TD-59`'s reserved-device-name-safe
naming, its legacy migration, the per-key lock and the atomic replacement
are inherited rather than re-implemented. `IAttachmentContentStore` writes
one record per attachment, keyed by the attachment's own Id, in its own
collection — the same relationship to the substrate
`EngineeringObjectStateStore` has (`ADR-0113`), one level down. Metadata
describes content; it does not assert it: `IAttachment` gained
`ContentHash` (SHA-256, or null when this platform holds no content), and
`AttachContentAsync` derives both size and hash from the bytes it stores
rather than accepting them from the caller, so metadata cannot describe a
file the store does not hold. The split earns its keep at startup: object
state carries name, type, size and hash and not one byte of the file, so
rehydrating a whole graph loads no attachment content and a 40 MB drawing
is read only when opened. Content is written before metadata, deliberately
— a crash between the two leaves unreferenced bytes rather than an
attachment promising content that was never stored. A read verifies what
it returns: `Available` with the bytes, `Missing`, or `Corrupt` with no
bytes at all, and neither throws (`TD-60`'s discipline).

## 6. Alternatives Considered

Base64 into the text store — rejected on arithmetic (a third again the
size, plus an encode/decode of the entire file on every read and write)
and because fidelity should not depend on a round-trip the content never
asked for. Storing a path or URL — rejected because that is precisely
`TD-31`'s own defect description. Content-addressed keys — rejected for
now: they deduplicate for free and turn deletion into reference counting,
but there is no attachment-deletion path yet to make that trade against.

## 7. Why This Solution Was Chosen

Because it reuses a capability `PersistenceStore` already has rather than
building a second storage mechanism, and because writing content before
metadata makes the failure mode of a crash mid-write harmless bytes rather
than a lying record.

## 8. Architectural Principles

Metadata should describe verified content, never assert unverified
content — size and hash are derived from what was actually written, never
accepted from a caller's claim.

## 9. Benefits

47 tests, deliberately including payloads a text-oriented store would
mangle silently: NUL bytes mid-stream, `0x1A`, bare CR and bare LF,
invalid-UTF-8 sequences, and `0xFF`/`0xFE` leading bytes, in structurally
real files (a PDF, a PNG with real CRCs, a ZIP/`.docx` container, a JPEG,
a BOM'd CSV). Seven mutations run, seven killed — the instructive one
recorded metadata but never stored the bytes, and every Core test still
passed; only the restart journey caught it, because only the restart
journey asks the store for something it did not just put in memory.

## 10. Trade-offs

Disclosed residual debt, all new: `TD-95` (content stored per attachment,
not deduplicated), `TD-96` (whole-file reads, no streaming), `TD-97` (no
orphaned-content collection). No content-type enforcement, deliberately —
a store that guesses at file types eventually refuses a legitimate one.
The viewer itself is deliberately not built here; `TD-31` is the storage
boundary, rendering is `TD-80`.

## 11. Common Mistakes

Testing only well-formed text-like payloads for a binary store — a store
that decoded bytes as text, stopped at a NUL, normalised a line ending, or
round-tripped through UTF-8 would pass every test built on `byte[64]` of
arbitrary data and lose every real file.

## 12. Future Evolution

`TD-80`, immediately after, builds the Document Viewer directly on this
row's storage boundary — the viewer's own design turns on what "render"
is allowed to mean, but it has bytes to render only because this row
exists.

## 13. Key Takeaways

- Reuse an existing capability reached through a new interface rather
  than building a second storage mechanism for the same underlying need.
- Derive metadata (size, hash) from verified bytes, never accept it as a
  caller's claim.
- Test a binary store with payloads specifically chosen to break a
  text-shaped assumption — the mutation that survived every well-formed
  test here was caught only by the restart journey.
