# WP 13.3A — Plugin Platform Integration & End-to-End Validation

## 1. Introduction

This Work Package is the plugin platform's own closing integration and
validation pass for `v0.13.0` — the final Work Package before this
release's own `WP 13.9.0` Release Preparation & Engineering Sign-Off. It
runs on `feature/v0.13.0`, directly following `WP 13.0A`/`WP 13.0B`
(architecture and its independent review), `WP 13.1A`/`WP 13.1B`
(mechanical implementation and its independent review), and `WP 13.2A`/
`WP 13.2B` (trust implementation and its independent review) — six Work
Packages that together took the plugin platform from a named,
architecture-only gap to real, tested, reviewed, working code implementing
`ADR-0107` through `ADR-0112`.

Four parallel sub-agents were commissioned together: three technical
verification workstreams — **End-to-End Integration**, **Fault Injection &
Resilience**, and **Performance & Scalability** — each adding new test
coverage under `src/`/`tests/`, and this **Governance & Documentation**
workstream, scoped strictly to `docs/`/`PROJECT_STATUS.md`, running
independently of the other three and explicitly forbidden from touching
their files.

## 2. Purpose

To close out the plugin platform's `v0.13.0` scope with a genuine,
independently-verified confirmation — not a restated claim — that
`ADR-0107`–`ADR-0112` are fully implemented with zero remaining gaps; that
every plugin-related Technical Debt and Future Capability entry correctly
reflects the platform's real, current state; and that the Academy,
release, and status documentation for this six-Work-Package programme is
complete and internally consistent before `WP 13.9.0`'s own release
sign-off begins.

## 3. Background

`WP 13.0A` designed the plugin trust and capability model; `WP 13.0B`
independently audited that design before baseline. `WP 13.1A` implemented
the mechanical, non-trust half (`ADR-0107`–`ADR-0109`: dependency-graph
resolution, the Plugin Registry, configurable conventions); `WP 13.1B`
independently reviewed it, finding and fixing two genuine production bugs.
`WP 13.2A` implemented the trust half (`ADR-0110`–`ADR-0112`: capability
enforcement, the component-principal model, detached-signature
verification), closing `TD-09`/`TD-10`/`TD-11`; `WP 13.2B` independently
reviewed it, finding and fixing one Critical privilege-escalation defect,
one Blocking architecture-compliance gap, and one Medium enforcement
defect — and disclosing, without fixing, two further findings judged
genuinely out of scope for a defect-fixing review: a TOCTOU window between
Discovery-time signature verification and Loading-time `Assembly.LoadFrom`
(no hash carried forward, no re-verification immediately before load), and
filename-based (not certificate-attribute-based) first-party trust-store
detection.

This Work Package exists because six Work Packages of architecture,
implementation, and per-implementation review — however each individually
verified — have never been checked together, end to end, as one coherent
platform, nor has any Work Package yet independently re-verified, against
real current code rather than any predecessor's own self-reported claim,
that all six ADRs are genuinely, fully implemented with nothing quietly
left undone.

## 4. The Problem

1. **Are `ADR-0107`–`ADR-0112` genuinely, fully implemented**, verified
   directly against real, current source — not against `WP 13.1A`'s,
   `WP 13.1B`'s, `WP 13.2A`'s, or `WP 13.2B`'s own prior claims — with zero
   remaining gap in any decision either ADR makes?
2. **Do `WP 13.2B`'s own two disclosed-but-unfixed findings** (the TOCTOU
   window; filename-based first-party detection) **represent an ADR
   conformance gap**, or are they scoped as acceptable by the ADRs' own
   text — and, either way, are they tracked anywhere in this project's
   governance registers, or does this Work Package need to raise them for
   the first time?
3. **Does the Technical Debt Register correctly reflect the platform's
   real, current state** — are `TD-09`/`TD-10`/`TD-11` still genuinely
   Resolved (re-verified against code, not citation), and does any other
   still-open plugin-related debt item now close as a genuine consequence
   of this integration/validation pass?
4. **Does the Future Capability Register correctly track every
   plugin-platform capability the ADRs explicitly defer** — certificate-
   chain validation, revocation checking, a marketplace, hot/live
   reload/unload — each named as out of scope by `ADR-0108`/`ADR-0110`/
   `ADR-0112` and by `WP 13.2A`'s own Future Evolution section, but never
   before given its own roadmap-facing entry?
5. **Is the six-Work-Package plugin programme's own Academy trail
   complete and internally consistent** before `WP 13.9.0`'s own release
   sign-off — one closing retrospective, the Academy Index/Register
   correctly listing it, and `WorkPackages.md`/`PROJECT_STATUS.md`
   correctly recording this Work Package's own place in the sequence?

## 5. The Design

**Independent, clause-by-clause ADR re-verification, not a citation
audit.** Each of the six ADRs' own Decision section was read in full and
checked directly against the real, current implementation file it governs
— `PluginTrustStore.cs`, `PluginAssemblyLoader.cs`,
`PluginManifestDiscoveryService.cs`, `NavigationService.cs`,
`CommandRegistry.cs`, `CommandHandlerTable.cs`, `EventBus.cs` — rather
than trusting any prior Work Package's own "implemented exactly as
designed" claim. Confirmed directly: dependency-graph resolution
(`ResolveDependencyGraph`, `PluginDependency`, categories 12–14,
`PluginRegistryState.DependencyUnmet`) for `ADR-0107`; no live-unload
mechanism anywhere in the codebase, matching `ADR-0108`'s own named
non-goal; no `IServiceCollection` access granted to any module for
`ADR-0109`; capability-scoped enforcement with no `AssemblyLoadContext`
or process boundary for `ADR-0110`; the component-principal model
(`ICurrentComponentAccessor`, trust-tier-ordered eviction, the `WP 13.2B`
FirstParty-exemption fix) for `ADR-0111`; and detached-signature
verification entirely at Plugin Discovery, before any `Assembly.LoadFrom`
call, for `ADR-0112`.

**The two `WP 13.2B`-disclosed findings, checked against the ADRs' own
literal text, not against an assumed stronger guarantee.** `ADR-0112`'s
own Decision text reads: signature verification is "checked entirely
during Plugin Discovery, before any assembly is loaded" — literally true
of the real code (`PluginManifestDiscoveryService` verifies from
`File.ReadAllBytes`, strictly before `PluginAssemblyLoader.LoadOne`'s own
`Assembly.LoadFrom` call) and never promises re-verification *at* the load
call site itself. The TOCTOU window is real, disclosed engineering debt —
not a broken ADR promise. `ADR-0112`'s own trust-store description names
only "a fixed, always-present entry," never committing to attribute-based
detection; `PluginTrustStore`'s own filename convention
(`FirstPartyCertificateFileName`) is a valid implementation of that text,
self-disclosed directly in the class's own remarks since `WP 13.2A`. Both
findings were confirmed, by direct source re-read, to still be present in
real code exactly as `WP 13.2B` described them — and confirmed absent from
every governance register searched (`Technical Debt Register.md`,
`Future Capability Register.md`) before this Work Package. Registered as
`TD-49`/`TD-50`.

**Future Capability Register gap search — the four out-of-scope
capabilities the ADRs themselves name.** `ADR-0112`'s Negative
consequences names certificate-chain validation, revocation checking, and
a per-plugin `AllowUnsignedLoad` allow-list; `ADR-0108`/`ADR-0110` name
hot/live reload and in-process unload (the reserved, unused
`Loaded → Unloading → Unloaded` seam) and process-separated isolation for
an open marketplace. `WP 13.2A`'s own Future Evolution section names all
five again, in narrative form, but none had ever been given a formal
`FCR-NNNN` entry. Four new entries raised (`FCR-0085`–`FCR-0088`),
following the register's own "merge duplicates, cite every source" rule —
`FCR-0085` combines certificate-chain validation and revocation checking,
since `ADR-0112` treats both as one Negative-consequences gap rather than
two independent ones.

## 6. Alternatives Considered

**Treating the TOCTOU window and filename-based detection as ADR
non-conformance, requiring a fix rather than a debt entry.** Considered
directly, per this Work Package's own commissioning instruction to check
whether either ADR "actually promises stronger guarantees than what's
implemented." Rejected, on the textual grounds detailed in §5 — both ADRs'
own Decision text is satisfied literally by the real, current
implementation; treating either as a broken promise would misdescribe a
real, disclosed engineering limitation as an ADR violation, precisely the
conflation this project's own Technical Debt Register "Governing
Distinction" section (debt vs. accepted trade-off) exists to prevent.

**Fixing the TOCTOU window directly, as part of this Work Package's own
governance pass, rather than merely registering it.** Considered, since
the fix is conceptually simple to describe (carry the Discovery-time hash
forward, re-verify before `Assembly.LoadFrom`). Rejected outright — this
Work Package's own explicit scope is `docs/`/`PROJECT_STATUS.md` only; the
fix is a real, non-trivial change to `PluginManifestDiscoveryService`'s
public shape and `PluginAssemblyLoader`'s own call site, squarely `src/`
work reserved for a future, properly-scoped implementation Work Package,
and touching it here would collide with the three parallel technical
sub-agents' own concurrent work in the same files.

**Closing a broader set of Technical Debt Register items as a side effect
of this pass**, beyond re-confirming `TD-09`/`TD-10`/`TD-11`. Considered —
several older, non-plugin debt items remain Open. Rejected: this Work
Package's own scope is the plugin platform specifically; closing an
unrelated item without the same direct-code-verification rigour applied
here would be exactly the "citation without verification" failure mode
this Work Package's own commissioning instruction warns against.

## 7. Why This Solution Was Chosen

Because the commissioning instruction was explicit and the six prior Work
Packages' own record made the right method self-evident: re-verify against
real code, not against what a prior retrospective already claimed. Every
one of `WP 13.1B`'s and `WP 13.2B`'s own reviews found real, genuine
defects that careful implementation work alone had not caught — the
identical lesson applies one level up, to whether an entire six-Work-
Package programme's own governance trail is accurate, not only whether any
one Work Package's own diff was correct in isolation. `WP 13.2B`'s own
commit message already did the hard part of naming two genuine,
plausible-not-confirmed findings honestly rather than either fixing them
under time pressure or silently dropping them — this Work Package's own
contribution is closing the loop those findings were left open by: giving
them a permanent home in the Technical Debt Register rather than letting
them live only in a commit message a future reader might never think to
search git history for.

## 8. Architectural Principles

- **Verify Against Code, Not Citation** — every ADR conformance claim in
  this retrospective is backed by a direct file/line reference read fresh
  during this Work Package, not by repeating a prior Work Package's own
  "implemented exactly as designed" sentence.
- **Debt vs. Accepted Trade-off, Kept Distinct** — the TOCTOU window and
  filename-based detection are registered as genuine, disclosed
  engineering debt (Technical Debt Register), not misfiled as an ADR
  violation or silently folded into an "accepted trade-off" that would
  understate their own real, if low, severity.
- **Disclose, Don't Fabricate** — this Work Package's own "what the three
  parallel technical sub-agents validated" section (§12) reports only
  what this Governance & Documentation workstream could independently
  verify by the time its own report was written; it does not invent test
  counts or findings belonging to sub-agents running concurrently, whose
  own results were not yet available.
- **Reuse Before Invention** — every new register entry
  (`TD-49`/`TD-50`, `FCR-0085`–`FCR-0088`) reuses each register's own
  existing severity/category/field conventions exactly, matched against
  several existing entries before writing, rather than introducing a new
  format.
- **Merge Duplicates** — `FCR-0085` combines certificate-chain validation
  and revocation checking into one entry, mirroring the Future Capability
  Register's own explicit "merge duplicates" governing rule rather than
  raising two entries for what `ADR-0112` itself treats as one gap.

- **All six plugin ADRs independently re-confirmed fully implemented**,
  with zero remaining gap, by a workstream that did not author any of the
  six ADRs or any of their prior implementations — the first time this
  release's own plugin programme has been checked end to end rather than
  Work-Package-by-Work-Package.
- **Two real, previously-uncaptured findings now have a permanent,
  discoverable home** (`TD-49`/`TD-50`) instead of living only inside a
  commit message — closing exactly the kind of drift this project's own
  Technical Debt Register exists to prevent.
- **Four previously-untracked, ADR-deferred future capabilities are now
  roadmap-visible** (`FCR-0085`–`FCR-0088`), each traceable directly to
  the ADR clause and Work Package that named it out of scope, so a future
  planning pass does not need to re-derive them from ADR prose.
- **A stale ADR Register citation gap, unrelated to this Work Package's
  own primary brief, was found and fixed in passing** — `ADR-0107`/
  `ADR-0108`/`ADR-0109`'s own Originating Work Package field had never
  been updated to cite `WP 13.1A`'s own implementation, unlike the
  sibling `ADR-0110`–`ADR-0112` citation `WP 13.2A` correctly fixed.

## 10. Trade-offs

- **This retrospective's own §12 (What the Three Parallel Technical
  Sub-Agents Validated) is written from ADRs, existing code, and this
  Work Package's own independent verification alone** — the three
  parallel technical sub-agents (End-to-End Integration, Fault Injection
  & Resilience, Performance & Scalability) were still running at the time
  this document was written, per this Work Package's own explicit
  instruction to proceed without waiting on their results. No specific
  test count, pass/fail verdict, or finding belonging to any of the three
  is stated here unless independently confirmed by this workstream itself
  — see §12's own explicit disclosure and the closing report to the
  orchestrator for the recommended follow-up pass.
- **Neither `TD-49` nor `TD-50` was fixed, only registered** — both
  remain genuinely Open, exactly as `WP 13.2B` itself judged them: real,
  disclosed, low-probability-of-exploitation debt, not defects this
  Work Package's own `docs/`-only scope could or should have fixed.
- **A pre-existing, unrelated documentation gap was found but not
  backfilled**: `WP 13.2B` (Plugin Trust & Capability Enforcement Review)
  has no Academy retrospective file, no `WorkPackages.md` row, and no
  `PROJECT_STATUS.md` entry of its own — its only trace in this project's
  governance documentation, before this Work Package, was one citation
  inside the Technical Debt Register's own `Last Reviewed` narrative.
  Disclosed here plainly, not fabricated a retrospective to fill — this
  Work Package did not execute `WP 13.2B` and has access only to its own
  commit message, not its own four sub-agents' full reports, so
  reconstructing a genuine 13-section retrospective for it would risk
  inventing detail rather than reporting it. Recommended as its own,
  separate, small follow-up task.

## 11. Common Mistakes

1. **Assuming a prior Work Package's own "implemented exactly as
   designed" claim is sufficient evidence.** It is not, for a closing
   integration pass specifically — `WP 13.1B`'s and `WP 13.2B`'s own
   reviews each found real defects careful implementation work alone
   missed; this Work Package's own value is in re-deriving conformance
   from source, not in repeating a citation.
2. **Treating a disclosed-but-unfixed finding from a commit message as
   either already tracked or safe to leave untracked.** Neither is
   automatically true — `TD-49`/`TD-50` existed only in `WP 13.2B`'s own
   commit message until this Work Package searched both governance
   registers directly and confirmed neither had a formal entry.
3. **Conflating an ADR's own literal Decision text with an assumed,
   stronger, unwritten guarantee.** `ADR-0112` never promises
   re-verification at Loading, only "before any assembly is loaded" —
   reading the disclosed TOCTOU window as an ADR violation would be a
   misreading of the ADR's own words, not a real conformance gap.
4. **Fabricating specific test counts or findings for a parallel
   sub-agent's own still-running work.** This Work Package's own §12
   deliberately states only what could be independently verified by this
   workstream, and names the follow-up pass explicitly rather than
   guessing at the other three sub-agents' own eventual results.

## 12. What the Three Parallel Technical Sub-Agents Validated

**This section reflects what this Governance & Documentation workstream
could independently verify by reading ADRs and real, current code alone —
not the End-to-End Integration, Fault Injection & Resilience, or
Performance & Scalability sub-agents' own final reports, which were not
yet available when this document was written**, per this Work Package's
own explicit instruction to proceed in parallel without waiting on them.

From independent code inspection, this workstream confirmed the
*structural* prerequisites each of the three technical workstreams would
need to validate against are genuinely present in real code: a full,
dependency-ordered Plugin Discovery→Loading pipeline (`ADR-0026`/
`ADR-0107`) with eighteen distinct, individually-isolated failure
categories (`ADR-0025` categories 1–11, `ADR-0107` categories 12–14,
`ADR-0112` categories 15–18) for fault injection to exercise; a real,
working trust-tier/capability/signature enforcement chain (`ADR-0110`–
`ADR-0112`) for end-to-end integration to exercise across Discovery,
Loading, and every registration call site; and a fixed-point dependency-
graph reduction plus reflection-based constructor conformance check
(`PluginAssemblyLoader.EnforceTrust`) whose own runtime cost `ADR-0107`'s
own Negative consequences already discloses as "not expected to be
observable at any realistic plugin count, not measured, disclosed as an
assumption rather than a proven bound" — the exact assumption a
Performance & Scalability pass would be expected to test.

**This section is explicitly incomplete and requires a follow-up pass**
once the three parallel sub-agents' own results land — see this Work
Package's own closing report to the orchestrator for that recommendation
stated directly, not only here.

## 13. Key Takeaways

- A six-Work-Package programme's own final integration/validation pass is
  a genuinely different kind of verification from any single Work
  Package's own implementation-or-review cycle — it re-derives conformance
  from source across the *whole* programme, not one Work Package's own
  diff, and is where a citation gap spanning multiple Work Packages
  (`ADR-0107`–`ADR-0109`'s stale Originating Work Package field) is
  exactly the kind of drift most likely to surface.
- A disclosed-but-unfixed finding in a commit message is not the same
  thing as a tracked debt item — the two are easy to conflate, and the
  gap between them (a real finding with no discoverable home outside git
  history) is itself a small governance risk this Work Package's own
  `TD-49`/`TD-50` entries close.
- Distinguishing "the ADR doesn't promise this" from "the implementation
  has a real, disclosed limitation" matters — collapsing the two either
  overstates a genuine gap as a broken architectural promise, or
  understates a genuine debt item as fully conformant. Both `TD-49` and
  `TD-50` needed this distinction applied carefully, not assumed either
  way.
- Running a documentation/governance workstream genuinely in parallel
  with concurrent technical workstreams — rather than waiting for their
  results — is real, valid work when scoped honestly: independently
  verifiable claims (ADR conformance, register accuracy, Academy
  completeness) can and should be finished now; claims that depend on
  another workstream's own unfinished output must be named as pending,
  not guessed at.
