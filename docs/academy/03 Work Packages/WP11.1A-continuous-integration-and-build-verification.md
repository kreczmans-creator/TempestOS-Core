# WP 11.1A — Continuous Integration & Build Verification

## 1. Introduction

`WP 11.1A` (commit `4006541`) builds TempestOS's first CI pipeline,
`.github/workflows/ci.yml`, closing `WP11.0A Platform Architecture
Review.md` finding `R-1` — no build/test automation existed anywhere in
the repository, and every "0 Warnings, N/N tests passing" claim in over
100 prior retrospectives was self-reported, never machine-verified. This
retrospective is the Academy article this Work Package's own report
already forward-referenced (`04-continuous-integration.md`, produced by
this same Work Package, covers CI philosophy and pipeline design in
depth and is cited here rather than duplicated); it is written
retrospectively under `WP 16.2B`, grounded in `WP11.1A Implementation
Report.md`, `WorkPackages.md`'s own row, and commit `4006541`.

## 2. Purpose

Give every future "0 Warnings, 0 Errors, N/N tests passing" claim a
machine-verifiable source, without changing what a local `dotnet build`
does today.

## 3. Background

`WP 11.0A` empirically confirmed a genuinely sound platform core but
found no CI/CD automation anywhere — `scripts/new-release.ps1` was the
only automation in the repository, and it validated branch/clean-tree
state, not build/test success. `WP 11.0B` scoped closing this gap as
`v0.11.0`'s own single Must-Complete-Before-`v1.0` item with no
dependency, sequenced to run alongside `WP 11.1B`/`WP 11.2A`.

## 4. The Problem

A platform this disciplined deserved a build pipeline that verifies its
own claims by machine — not narrative alone, as `WP11.0A`'s own closing
assessment put it. Nothing in the repository prevented a regression from
merging with a broken build or a failing test other than the personal
discipline of whoever ran the last Work Package.

## 5. The Design

One workflow, two jobs. `build-and-test` is a `fail-fast: false` matrix
over `Debug`/`Release`: installs the exact SDK named in `global.json`,
restores, builds `src/TempestOS.slnx` with
`-p:TreatWarningsAsErrors=true` (a CI-invocation-only override —
`Directory.Build.props` stays unchanged, so a local build behaves
exactly as before), runs the complete test suite with TRX output,
publishes a build/test summary, and uploads logs/results as artifacts
always, even on failure. `gate` depends on both matrix legs and gives a
future branch-protection rule one named required check instead of two.
Triggers: push, pull request, manual dispatch — every one requested,
none narrowed. Only official, first-party GitHub Actions are used
(`checkout`, `setup-dotnet`, `upload-artifact`); the build/test summary
is a small, inline, fully-auditable PowerShell script, not a third-party
reporting action — keeping the pipeline's own supply-chain surface
minimal.

Every command the workflow issues was reproduced locally, command for
command, before being finalised: Debug and Release both 0 Warnings/0
Errors, both with and without `-p:TreatWarningsAsErrors=true`; the
complete suite 2,266/2,266 passing (2,064 `Tempest.Core.Tests` + 202
`Tempest.Desktop.Tests`, real Avalonia headless UI, confirmed runnable
without display virtualisation on `windows-2022`).

## 6. Alternatives Considered

A third-party test-reporting action for the build/test summary was
considered and rejected in favour of a small, inline, auditable
PowerShell script — consistent with this project's own
security-conscious posture and minimising the pipeline's supply-chain
surface. `windows-latest` was rejected in favour of pinning
`windows-2022` exactly, matching this project's own house style of
pinning every version (the SDK, every `PackageReference`) rather than
letting a runner-image change silently alter CI behaviour.

## 7. Why This Solution Was Chosen

Verify before asserting, applied to the CI pipeline's own design, not
only to what it checks: `TreatWarningsAsErrors=true` at the CI step was
proven safe locally, with the flag, before being adopted — not assumed
safe because the local build was already clean without it. The matrix
directly operationalises the recurring retrospective claim ("Debug and
Release both clean") this project had always asserted but never
checked.

## 8. Architectural Principles

No production code, ADR, or architecture document was modified.
Zero `.cs` files touched; `Directory.Build.props`'s
`TreatWarningsAsErrors` remains `false` for every local build — the one
CI-only override exists solely inside the workflow's own build
invocation. No ADR was written: a CI pipeline choosing how to verify
already-existing standards is process tooling, not a platform
architectural decision meeting Engineering Governance §5's criteria.

## 9. Benefits

Every future release's Build Gate and Test Gate (Engineering Governance
§2) are now machine-verified rather than trusted from a self-report.
The `gate` job gives a future branch-protection rule exactly one named
check to require. `WP11.0B`'s own roadmap already named this pipeline as
a hard dependency for `WP 12.0B` (the largest single implementation Work
Package in the roadmap) — the platform's largest planned refactor is
CI-gated from the moment it begins.

## 10. Trade-offs

Actual GitHub-hosted execution was disclosed as `Unknown`/unverified —
no runner was available in this sandboxed environment, and pushing the
branch was judged outside this Work Package's own "await review" scope.
Every command was verified locally with the exact flags the workflow
uses; the GitHub Actions execution environment itself was not — named
plainly as `Inferred`, not `Verified`, rather than presented as fully
proven. No branch-protection rule was configured — a GitHub
repository-administration action, outside this Work Package's own
infrastructure-as-code scope; the `gate` job exists specifically to make
that a one-line future addition.

## 11. Common Mistakes

**Treating a locally-reproduced command sequence as equivalent to a real
CI run.** This Work Package's own report is explicit that local
verification and GitHub-hosted execution are two different claims with
two different confidence levels — the first real push (`WP 11.9.0`, and
the corrections it triggered, `WP 11.4A`) is what actually settled the
second.

## 12. Future Evolution

The first real GitHub-hosted push (during `WP 11.9.0`'s own release
sequence) found genuine defects this local verification could not have
caught — see `WP 11.4A`'s retrospective, which fixed exactly what the
first real CI execution surfaced. Cross-platform (Linux/macOS) CI
remains explicitly out of scope here, named directly in the new Academy
article as a real, disclosed gap rather than a silently assumed one.

## 13. Key Takeaways

- A CI pipeline's own claims (e.g. "0 Warnings under
  `TreatWarningsAsErrors`") should be verified locally before being
  adopted, not assumed from the existing unflagged build being clean.
- Local reproduction of every command a workflow issues is real evidence
  the workflow will work — it is not the same evidence as a real
  GitHub-hosted run, and both this report and the Work Package that
  followed it (`WP 11.4A`) treat that distinction as load-bearing.
- A pipeline that only gives one named required check (`gate`, not two
  matrix legs) is easier for a future branch-protection rule to depend
  on correctly.
