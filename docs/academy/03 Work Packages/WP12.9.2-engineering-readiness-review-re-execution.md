# WP 12.9.2 — Engineering Readiness Review Re-Execution

## What This Document Is

The retrospective for `WP 12.9.2`, commissioned to re-execute the
complete Engineering Readiness Review (`ADR-0106`) against `main`
after `WP 12.9.1` remediated the two governance findings the first
execution (`WP 12.9.0`, embedded in commit `fb76ce8`) disclosed. This
is a release-readiness assessment only — no implementation work beyond
what a genuinely discovered blocking issue required. The full,
six-discipline evidence base lives in `WP12.9.2 Engineering Release
Report.md`; this document is the narrative account of how that report
came to be, in the same format every other Work Package's retrospective
uses.

## Controlling Brief

Re-derive every Phase A item independently — "do not rely on previous
reports." Execute the five-category ERR exactly as `ADR-0106` and
`Engineering Readiness Review Architecture.md` define it, deriving the
verdict mechanically. Do not modify production code, tests, or the
governance model itself unless a genuine blocking defect is
independently discovered. If the verdict allows proceeding, stop and
await explicit instruction before tagging.

## What This Work Package Found

**The repository was not in the state the controlling brief assumed.**
"The current repository state after `WP 12.9.1`" implicitly assumes
`WP 12.9.1`'s own remediation is part of the repository's real history.
It was not: every file `WP 12.9.1` changed sat as an uncommitted
working-tree diff, never committed, never merged. Phase A's own
"repository cleanliness" item is not a formality — a working tree with
real, undiscarded, uncommitted governance fixes fails it directly, and
no meaningful release-readiness verdict can be reached for "the state
after `WP 12.9.1`" while that state exists only on disk. With explicit
confirmation, this Work Package committed those changes to `main`
locally (`955badb`) — no push — before evaluating anything else.

**That commit immediately reproduced the identical class of finding
`WP 12.9.0`'s own first execution closed on.** `main` had been `0
ahead/0 behind origin/main` when this review began (`fb76ce8`, already
pushed). Committing `WP 12.9.1` put `main` one commit ahead of
`origin/main` again — mechanically, certainly, real GitHub-hosted CI
cannot have run against a commit that has never been pushed. This is
not a new kind of finding; it is `WP 12.9.0`'s own A4 finding recurring
for the same underlying, structural reason (a real repository-state
change, correctly not also pushed without separate authorisation),
against a different commit.

**A related evidentiary question the controlling brief anticipated —
"do not assume CI success, use actual evidence" — was genuinely
unanswerable from this session alone.** No `gh` CLI, and `WebFetch`
returns `404` against this private repository's API and web UI both.
The Product Owner offered to supply `fb76ce8`'s own real CI outcome
directly — not used in the final verdict, since `fb76ce8` stopped being
`main`'s tip the moment `WP 12.9.1` was committed; whatever it achieved
is evidence about a commit that will not be tagged, not the one that
would be. Disclosed in full in the Engineering Release Report's own
Part G, so the evidence gap is visible rather than silently
sidestepped.

**Two further, narrow documentation staleness items** — `Release
Notes.md` still described "Ten Work Packages" and still listed both
governance findings as open; `PROJECT_STATUS.md`'s own "Last Updated"
field still described `WP 12.9.0`'s own verdict as current — both
corrected within this same Work Package, per `Engineering Readiness
Review Architecture.md` §5's own allowance for genuinely narrow
corrections, and both disclosed in Part C of the Engineering Release
Report rather than silently folded in.

**One further, pre-existing inconsistency found and corrected**:
`docs/releases/v0.12.0/WorkPackages.md`'s own `WP 12.9.0` row still
read "execution not yet commissioned" and "no verdict is rendered…
here," even though `WP 12.9.0`'s own actual delivered scope — the same
Work Package, the same commit — had gone on to execute the first real
ERR and render a `NOT READY` verdict. The row simply was never updated
after that scope expansion happened. Corrected in place, disclosed as
a pre-existing gap this Work Package found, not introduced.

## Verdict

**`NOT READY`** — mechanically derived, `ADR-0106` §4 row 1: Verification
readiness carries one Release Blocking finding (real CI not run against
`main`'s current tip, `955badb`, because it has not been pushed).
Architecture, Implementation, Governance, and Release readiness are all
clean **Pass** — Governance readiness improves from `WP 12.9.0`'s own
"Pass, with observations" to a clean Pass, both prior findings closed.

**Recommendation**: push `main`, confirm `Build & Test`/`CI Gate` both
pass on the real run against `955badb`, then this review is expected to
become `CERTIFIED` — not a lesser verdict, since zero Disclosed-
Non-Blocking or Pre-Existing-Unaffected findings remain anywhere in
this execution. No tag, GitHub release, or push authorised or proposed
by this Work Package — verdict `NOT READY` independently prohibits
proceeding regardless.

## Key Takeaways

1. **A model correctly resists being executed against wishful state.**
   The controlling brief's own framing ("the current repository state
   after `WP 12.9.1`") assumed a fact — that remediation was committed
   — that was not yet true. Discovering and correcting that first,
   rather than reviewing the working tree as if it were history, is
   what made the rest of this review meaningful.
2. **The identical finding recurring is not a failure of the model —
   it is the model working.** Committing real change and correctly not
   pushing it without separate authorisation necessarily reproduces the
   "not yet on real CI" finding every time, by design; that repetition
   is `ADR-0106`'s own tier separation (Engineering Governance §7.5)
   functioning exactly as intended, not a defect in this Work Package.
3. **An evidence gap this session could not close was disclosed, not
   guessed around.** Offered evidence for a commit that had already
   stopped being relevant was named and set aside with its own
   reasoning, rather than either silently used or silently ignored.
4. **The pattern from `WP 12.9.0` holds across a second, independent
   execution.** Two consecutive real exercises of the corrected
   `ADR-0106` model have each found exactly one blocking finding,
   cleanly traced to its own root cause, with no ambiguity about which
   of the four verdicts applies — the same kind of unprompted
   convergence that justified formalising the model as permanent in
   the first place.
