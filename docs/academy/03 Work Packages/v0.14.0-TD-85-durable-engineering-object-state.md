# TD-85 — Durable Engineering Object State, Per-Type Rehydration, Removal of Projects.Index

## 1. Introduction

`e752368` fixed the real boundary `TD-84`'s own restart journey had
exposed and worked around: engineering documents persisted, but the
objects reconstructed over them did not. `fa01c63`, a closure audit, found
and fixed one material defect the work itself had created —
`IHasRevisions.ReviseAsync` dropping lifecycle state and history on a
revision. A pre-`v0.14.0` engineering-body-of-work row; produced
`ADR-0113` and the companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/34-engineering-object-rehydration.md`.

## 2. Purpose

To make the engineering object graph durable at its real source, not at
the one caller (`Projects.Index`) that had been worked around.

## 3. Background

`TempestHost` registers in-memory `IEngineeringObjectRepository`/
`IEngineeringRelationshipRepository` (`ADR-0077`). Documents persisted;
the reconstructed objects over them did not survive a restart. The obvious
fix — a Kind-to-constructor map over the discipline factory registries —
could never have worked, for two independent reasons: those registries
live in `Tempest.App`, explicitly "never a Domain-layer registry
contract"; and, decisively, `EngineeringObjectFactory<T>.CreateAsync`
persisted only the document (Kind, created-at, prose). The constructor
arguments such a map would need had never been written to disk at all.
State had to become durable before any rehydration mechanism could exist.

## 4. The Problem

A relaunched TempestOS silently started a new object graph over the
user's still-persisted work — every identifier, lifecycle state,
relationship, revision and BOM line reconstructed from nothing.

## 5. The Design (`ADR-0113`)

`EngineeringObjectState` — the one canonical model's own serialisation,
never a second model — written through `IEngineeringObjectStateStore` into
the same `IPersistenceStore` the document store already uses
(`ADR-0053`), at creation and after every state-changing mutation, with
no save step. `CaptureTypeState` + `IRehydratable<TSelf>.Rehydrate` give
each of 30 concrete canonical types both directions of its own
persistence, keyed by `nameof`, with no central switch over Kind and a
compile error if a type cannot rebuild itself. `IEngineeringObjectRehydrator
Registry` lives in the Domain layer, populated by each Kind's own
declaring class using the constant it already owns (`ADR-0105`) — 29
Kinds, every Kind with a live write path. `EngineeringObjectRehydration
Service`, run by the shared composition root in both desktop and console
entry points, reconstructs objects, restores lifecycle/history/parent/
deletion/BOM/attachments, reattaches self-factories, rebuilds the
relationship index from durable `DocumentReference`s, and never overwrites
an object already live in the process. `DocumentReference` gained optional
`CreatedByPrincipalId`/`CreatedAt` so a rebuilt relationship is not
credited to whoever is signed in at startup — null for pre-existing links,
honestly absent rather than fabricated. `Projects.Index` was removed
outright — collection, DTO, read/write paths, `IPersistenceStore`
dependency — leaving one object model and one persistence authority.

`fa01c63`'s closure audit found `IHasRevisions.ReviseAsync` copied only a
hand-picked subset of state (rename, parent, delete, BOM line, added by
`WP 9.0B` for its own scope) rather than the whole object, so a revised
object silently reverted to `Draft` with no history. Cosmetic while state
was in-memory (discarded at restart anyway); `TD-85` made it durable, so
the revised instance's next mutation persisted the reset, destroying a
recorded lifecycle state and its transition history on disk. Fixed by
`revised.RestoreState(CaptureState())`, the same pair rehydration already
uses, so `CaptureState`/`RestoreState` became the single definition of an
object's state shared by persistence, rehydration and revision.

## 6. Alternatives Considered

A Kind-to-constructor map over the discipline factory registries —
rejected on two independent grounds: it would invert the layering
(registries live in `Tempest.App`, not Domain), and the state it would
need to construct from had never been persisted in the first place.

## 7. Why This Solution Was Chosen

Because the alternative — leaving each type to build its own ad hoc
recovery path — would have produced 29 different answers to "what does
this object need to come back". A single canonical state model, captured
and restored the same way everywhere, gives one answer.

## 8. Architectural Principles

`ADR-0113` establishes the pattern this row's later siblings all build on:
one canonical state model, one persistence authority, per-type
self-rehydration through a Kind-keyed registry rather than a central
switch. `TD-31`'s attachment content store later takes the identical
relationship to the substrate, one level down.

## 9. Benefits

An 18-step acceptance journey through the real `MainWindow` across three
application lifetimes, plus 24 focused tests over the real persistent
stores; the Product Spine's own restart tests now run through real
rehydration instead of an index. Thirteen mutations run, thirteen killed.
The closure audit's four regression tests brought the total to fifteen
mutations run, fifteen killed, with no test weakened or deleted.

## 10. Trade-offs

The closure audit found `ReviseAsync`'s partial-copy defect only because
`TD-85` made an existing silent bug durable — a defect that was harmless
while state was in-memory became a real data-loss path the moment
persistence was added. Disclosed residual debt, all new: `TD-86` (write
batching), `TD-87` (state schema versioning), `TD-88` (lazy rehydration).

## 11. Common Mistakes

Assuming an obvious-looking fix (a Kind-to-constructor map) will work
without checking whether the data it would need actually exists on disk —
it did not, because the factory that created objects had never persisted
their constructor arguments.

## 12. Future Evolution

`TD-87` — state schema versioning — is picked up directly by `WP 16.3A`/
`WP 16.3B` in this release, giving `EngineeringObjectState` and attachment
records a `SchemaVersion` and an ordered migration chain, closing the
row this work disclosed rather than resolved.

## 13. Key Takeaways

- Before designing a rehydration mechanism, confirm the data it needs was
  ever persisted — an elegant-looking map over existing registries had
  nothing to construct from.
- A partial state-copy that is harmless in memory becomes a real defect
  the moment the state it half-copies is made durable.
- One canonical `CaptureState`/`RestoreState` pair shared by persistence,
  rehydration and revision means a field added to it cannot be honoured
  by one copy path and forgotten by another.
