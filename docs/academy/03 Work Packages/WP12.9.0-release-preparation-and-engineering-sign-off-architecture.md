# WP 12.9.0 — Release Preparation & Engineering Sign-Off Architecture

## What This Document Is

The architecture-phase retrospective for `WP 12.9.0`, the final
roadmap-defined Work Package before the `v0.12.0` release. On its own
new branch (`feature/v0.12.0-release-preparation-and-signoff`).
Architecture only — designs the permanent TempestOS Engineering
Readiness Review (ERR); does not execute it against `v0.12.0`, does not
tag, does not begin release engineering.

## 1. Introduction

Every TempestOS release since `v0.6.0` has undergone a release-readiness
review before tagging, but no standing document has ever defined *how*
— what evidence, in what categories, against what criteria. `WP 10.9A`
and `WP 11.9.0` each independently converged on a six-discipline
Programme Review (Chief Architect, Principal Software Engineer,
Workflow Engineer, QA Lead, Technical Author, Product Manager) and a
12-item Definition of Done, `WP 11.9.0` explicitly reusing `WP 10.9A`'s
own shape as "the standard applied." This Work Package's own brief:
design the permanent model this convergence has already earned, not a
third ad hoc checklist.

## 3. Phase B — Engineering Readiness Review Architecture

Designed in full in `docs/architecture/Engineering Readiness Review
Architecture.md`. Five categories — Architecture, Implementation,
Verification, Governance, Release readiness — each independently
reviewed by a named discipline, each with defined required evidence,
pass criteria, and blocking conditions. A single category assessed Not
Ready is sufficient to prevent Product Approval from proceeding.

**Two genuinely new pieces**, neither existing in either prior
sign-off: a **blocking taxonomy** (Release Blocking / Disclosed
Non-Blocking / Pre-Existing Unaffected — no prior review ever wrote
down what makes a finding block a release, each judged it narratively)
and a **fixed, four-value verdict vocabulary** (`CERTIFIED`;
`CERTIFIED WITH ACCEPTED TECHNICAL DEBT`; `ACCEPT WITH OBSERVATIONS`;
`NOT READY`), replacing six releases' worth of independently-worded
free text. The proven six-discipline Programme Review structure is
retained unchanged — formalised, not replaced — since `WP 11.9.0`'s
own `TD-42`/`TD-43` finding is direct, concrete evidence independent,
un-reconciled review catches real defects a single reviewer or a pure
automation gate would not (both evaluated and rejected as alternatives,
§4 below).

The release's own existing 12-item Definition of Done (`WP 10.9A`/`WP
11.9.0`'s own shape) is preserved exactly, re-grouped under the five
categories — every one of the twelve items maps cleanly to exactly one
category with no item needing to be dropped or reworded, itself
evidence the five-category structure genuinely fits what this
project's own two prior sign-offs already proved necessary.

## 4. Decision Evaluation

**A new ADR is required** — `ADR-0106`. Engineering Governance §5's own
criteria are met on two grounds: this decision establishes a convention
every future release is expected to follow, and three genuine
alternatives were seriously evaluated and rejected, each on
project-specific evidence rather than abstract preference:

1. **Continue the ad hoc checklist** — rejected, the named problem this
   Work Package exists to solve.
2. **A single-reviewer sign-off** — rejected; `WP 11.9.0`'s own
   independently-found `TD-42`/`TD-43` is direct counter-evidence.
3. **A purely automated gate** — rejected;
   `governance-healthcheck.ps1` evaluates one of five categories well
   and cannot substitute for the architectural/product judgement the
   other four require, which Engineering Governance §9 reserves for
   specific human tiers.
4. **The five-category ERR, six-discipline Programme Review** —
   adopted; formalises what is proven, adds only the taxonomy and
   verdict vocabulary that were genuinely missing.

No existing ADR governs release sign-off criteria specifically —
`ADR-0009`/`ADR-0017`/`ADR-0023` govern architectural layering and
composition, not process; Engineering Governance §7 states the
approval *principle* but is not itself an ADR. `ADR-0106` is the first
ADR whose subject is the sign-off process itself.

## 5. Architecture

Full specification in the architecture document; summarised here per
this repository's own established retrospective shape:

- **Responsibilities/ownership**: the ERR owns *evaluating* release
  readiness; it does not own tagging, pushing, or the underlying
  Build/Test/Technical Review gates, all unchanged.
- **Layering/dependencies**: purely a process/documentation layer over
  existing gates — no code, no new Platform Service, no new dependency
  of any kind.
- **Lifecycle**: exercised exactly once per release, at its close,
  immediately before Product Approval's own tagging decision.
- **Interaction model**: six independent reviews → Programme Review
  reconciliation → Engineering Release Report → Product Approval's own
  explicit, per-occasion verdict — Engineering Governance §9's own tier
  separation applied unchanged, one level more specifically.
- **Verification strategy**: every piece of evidence a future ERR
  gathers must be freshly re-derived at that time, never carried
  forward from an architecture-phase estimate — this Work Package's
  own Phase A (§2, above) is itself the worked example of that
  discipline, not merely a stated rule.
- **Testing/governance impact**: none to code or tests (architecture
  only); `ADR Register.md`, `Architecture Document Register.md`,
  `Academy Register.md`, `Documentation Register.md` each updated to
  record this Work Package's own two new documents, all counts
  re-derived directly.

## 7. Key Takeaways

- **Convergence without a written rule is evidence, not a
  substitute, for the rule.** Two independent sign-offs choosing the
  same shape unprompted is exactly the signal that shape deserves to
  be named permanently — waiting for a third coincidence would have
  been the wrong lesson to draw from the first two.
- **A blocking taxonomy that was never written down was still being
  applied, informally, every time** — formalising it did not invent a
  new judgement; it made an existing, already-exercised judgement
  legible to whoever performs it next.
- **The strongest argument against a single-reviewer or automated-only
  gate was this project's own history, not a hypothetical.**
  `TD-42`/`TD-43` are not abstract risks the multi-discipline structure
  might prevent — they are defects it already did prevent, once,
  concretely.
- **An architecture-only Work Package can still perform a real,
  evidentiary repository assessment** without crossing into release
  engineering — the distinction is whether a verdict is rendered
  (release engineering) or only evidence is gathered and a model is
  designed (architecture) — the same discipline `WP 12.2A` applied one
  Work Package earlier, generalised here to a much larger assessment.

## 8. Addendum — Architecture Review Follow-Up (2026-08-12, same day, documentation only)

A read-only architecture review of this Work Package, performed before
any commit, found two blocking findings, no non-blocking findings
otherwise material — both closed here, documentation only:

- **Finding 1 — the ADR Register's own Entries table was never updated.**
  This Work Package's first pass correctly updated `ADR Register.md`'s
  own narrative "Last Reviewed" and "Related ADRs" fields but never
  added `ADR-0106`'s own row to the register's real, structural source
  of truth, its `## Entries` table. Caught by the review's own direct
  `governance-healthcheck.ps1` run: `[FAIL] ADR Register matches
  docs/adr/ (105 files, 104 register rows)`. Re-derived independently,
  not merely patched: a full bijection check between every file under
  `docs/adr/` and every row in the Entries table confirmed `ADR-0106`
  was the *sole* discrepancy — all other 104 rows already matched their
  files exactly, one-to-one. `ADR-0106`'s own row added, immediately
  after `ADR-0105`'s; `governance-healthcheck.ps1` re-run after the fix
  reports `[PASS]` (105 files, 105 register rows).
- **Finding 2 — the blocking taxonomy, category status, and verdict
  vocabulary were mutually contradictory.** Category status (§2 of the
  architecture document) held that *any* disclosed, non-blocking
  finding moves a category from **Pass** to **Pass, with observations**
  — yet the verdict `CERTIFIED WITH ACCEPTED TECHNICAL DEBT` was
  defined as requiring simultaneously "every category Pass" *and*
  "Disclosed-Non-Blocking findings exist," a condition that, given the
  category-status rule, could never actually hold: the verdict was an
  unreachable, empty set as originally written. Closed with the
  minimum architectural change that produces a complete, internally
  consistent model — no new mechanism, no new taxonomy category, no
  new verdict: §4 (Blocking taxonomy) now states, once, the complete,
  exclusive derivation from finding kind → category status → release
  verdict, as a strict priority order (any category Not Ready →
  `NOT READY`; else any Disclosed, Non-Blocking finding anywhere →
  `ACCEPT WITH OBSERVATIONS`; else any Pre-Existing, Unaffected finding
  anywhere → `CERTIFIED WITH ACCEPTED TECHNICAL DEBT`; else, no finding
  of any kind anywhere → `CERTIFIED`); §2 and §6 both now cite this one
  table rather than each restating their own version of it, closing the
  duplication that let the two drift apart from each other in the
  first place. `ADR-0106`'s own Decision section corrected to match,
  disclosed via its own Status-section note, since the ADR had not yet
  been committed. Verified: all four verdicts are now reachable (each
  row's own condition is independently satisfiable), mutually exclusive
  (a strict priority order fires exactly one row), and objectively
  derivable (the only judgement anywhere is classifying a finding into
  one of §4's three kinds — never a second, separate judgement about a
  category or the release as a whole).

**Scope discipline.** Neither finding required touching the five
readiness categories' own evidence tables, the six-discipline process,
the Repository Investigation, or any of the three taxonomy kinds
themselves — all unchanged from the original design, exactly the
"minimum architectural change" the follow-up's own brief required. No
`src/`/`tests/` file was touched (none had been, at either pass). No
commit, merge, or tag was performed at either pass.
