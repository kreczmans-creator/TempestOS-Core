# WP 16.5A-R1 — Accessibility Remediation

## 1. Introduction

`WP 16.5A-R1` remediated six accessibility findings the `v0.16.0` review
board raised against `WP 16.5A`'s own shipped baseline, on
`feature/v0.16.0-a11y-remediation`, cut from `feature/v0.16.0` at
`338d8ac`. Two commits — `2178e5a` (the six fixes) and its merge
(`4ddf9ff`), both landing at 06:41–06:42, essentially concurrently with
`WP 16.2C`'s own two branches merging the same minute. The most severe
of the six was a BLOCKER: the keyboard focus ring `WP 16.5A` introduced
was invisible on the shell's own Primary-treatment button — the single
most common call-to-action a keyboard user would tab to — in both
themes, and the test written to prove the ring worked could not
structurally have caught it.

## 2. Purpose

`v0.16.0 Engineering Status Report.md` records this Work Package as
closing findings "raised `TD-128`" and remediating "six accessibility
findings against `16.5A`'s baseline, incl. the invisible focus ring."
The findings were not discovered independently twice: `WP 16.2C`'s own
retrospective for `WP 16.5A` (`docs/academy/03 Work Packages/
WP16.5A-accessibility-baseline.md` §10, committed `32f75a9` at
06:18:24) had already recorded the identical focus-ring and Ribbon
automation-name defects, found by direct source reading, and named
`feature/v0.16.0-a11y-remediation` explicitly as the branch that would
need to fix them — this Work Package is that branch, landing within
twenty-five minutes of that retrospective being committed. This Work
Package's purpose was to close exactly the six findings the review
board handed it, narrowing `TD-65` further without attempting the
general accessibility sweep its own brief explicitly ruled out.

## 3. Background

`WP 16.5A`'s own baseline (`docs/releases/v0.16.0/WP16.5A Accessibility
Baseline Report.md`) introduced `:focus-visible` styling across every
button treatment, drawing every treatment's ring from one generic token,
`ApplicationPalette.FocusRingBrushKey`. That report's own §3 explicitly
checked whether `FocusRingBrushKey` had been accidentally swapped with
another token and confirmed it matched the intended assignment in both
themes — a real check, correctly run, that answered a different
question than the one that mattered: `BrandPalette.AccentBrushKey`, the
Primary treatment's own rest fill, resolves to the *identical* colour as
`FocusRingBrushKey` in both themes (`Indigo600` in light, `Cyan500` in
dark) by design, because Primary's ring was always meant to use the
brand accent. A ring painted in a colour identical to the surface it
sits on has a contrast ratio of 1.00:1 against that surface — invisible,
regardless of how correctly the token itself was wired.

## 4. The Problem

Six findings, verified directly against the shipped `src/Tempest.Desktop/`
tree:

1. **BLOCKER.** `ChromeStyles.cs`'s Primary treatment draws its
   `:focus-visible` ring in `FocusRingBrushKey`, identical to its own
   `:rest` fill (`AccentBrushKey`) — measured 1.00:1 in both themes.
   `Danger`'s `:pointerover` fill also failed the generic ring's 3:1
   floor once focused (2.33:1 light, 1.36:1 dark).
2. Ribbon command buttons (`RibbonView.BuildCommandButton`) render
   `Button.Content` as a `StackPanel` (icon + `TextBlock`) with no
   `ToString` override, so `ContentControlAutomationPeer.GetNameCore()`'s
   fallback resolves to the literal type name — a screen reader
   announces "Avalonia.Controls.StackPanel," not the command.
3. The identical shape on `DigitalThreadGraphView`'s "Reset View"
   button, in the same file `WP 16.5A` explicitly claimed to have
   audited for automation names.
4. `DocumentViewerView`'s four glyph-only toolbar buttons had a tooltip
   but no accessible name, and the whole view had no keyboard panning at
   all — mouse drag only.
5. `StatusBarView`'s "Hint" segment was wired `Polite` uniformly with
   seven other segments that change only on discrete events, but `Hint`
   itself fires on every ribbon-button pointer hover — constant
   announcement noise a screen-reader user would have to tolerate on top
   of the button's own name.
6. Three measured contrast failures below WCAG floors:
   `FaintTextBrushKey` (light, on two surfaces), `Cyan600` (dark
   accent-press), `DangerBrushKey` (light).

## 5. The Design

**Finding 1, Primary treatment.** The ring now draws in
`BrandPalette.OnAccentBrushKey` — Primary's own *foreground* colour —
which is guaranteed to contrast with Primary's own fill by construction,
since a treatment's foreground and background tokens are chosen to
contrast with each other for text legibility in the first place; no
independent colour pairing had to be measured and hoped to stay correct
under future palette edits. Measured ≥ 4.60:1 against every Primary fill
state (`:rest`, `:pointerover`, `:pressed`) in both themes.

**Finding 1, Danger treatment, and a real framework finding.** `Danger`
keeps the generic ring at rest (never reported broken — its rest fill
is transparent) and gains a second, more specific style,
`.tempest-danger:pointerover:focus-visible`, switching to
`OnAccentBrushKey` exactly when hovered. **Writing this the "obvious"
way — trusting selector specificity, with the more specific pseudo-class
combination expected to win — failed**: the fix was written, its own new
test run against it, and the test failed. Avalonia resolves two
`Style`s in the same `Styles` collection that both match **by addition
order, not by selector specificity** — an extra pseudo-class in a
selector does not make it win against a less specific one added later.
The two Danger rules are added rest-then-hover, deliberately, once this
was understood, and the discovery is recorded directly in a code
comment at the point it matters, not only in this report.

**Finding 1, test.** The existing `FocusVisibleStyleTests.cs` asserted
only `presenter.BorderBrush == focusRing` — that the right *token* was
wired up, never that the resolved colour contrasted with anything. It
was rewritten to resolve the *expected* ring per treatment and extended
with `ButtonTreatments_FocusRing_DiffersFromAndContrastsWithEveryOpaqueFillItBorders`
— 4 treatments × 2 themes, driving a real Tab keypress and a real
pointer hover through the actual headless input pipeline, resolving the
presenter's real `BorderBrush`/`Background`, and computing the actual
WCAG contrast ratio against every genuinely opaque fill state (a
translucent wash or `Brushes.Transparent` is skipped, so the real page
background can show through, with the reasoning in a comment).

**Findings 2–4.** `AutomationProperties.SetName` calls added at each
build site: the Ribbon command button, the graph's Reset View button,
and — at the shared `ToolbarButton` factory itself, so all six
`DocumentViewerView` toolbar buttons are fixed uniformly rather than
only the four the finding named — every caller's already-descriptive
`tooltip` string reused as the accessible name. Keyboard panning added
as `OnViewerKeyDown`, attached at the view's own root exactly like
`DigitalThreadGraphView.OnGraphKeyDown`, calling the existing public
`PanBy(double, double)` with a new 40px step, direction matching the
view's own documented pointer-drag convention.

**Finding 5.** `StatusBarView`'s shared `Value()` segment factory gained
an `announceChanges` parameter (default `true`); only `Hint`'s own call
site passes `false`. `AutomationLiveSetting` is left *unset* for `Hint`
rather than explicitly declared `Off` — confirmed directly that
Avalonia's own unset default already is `Off`, so omitting the property
is the more honest statement of "this is not a live region" than
declaring it redundantly. The seven genuinely discrete segments are
untouched.

**Finding 6.** Three brush values nudged using the identical
hue-preserved darken/lighten treatment `WP 16.5A` already applied to
`HealthText*` — every consumer of each key `grep`ped first to confirm
the change is safe everywhere it is used (text/caption use in every
case but one, where the nudge is to a decorative, non-text swatch in a
17-colour categorical palette, imperceptible there).

## 6. Alternatives Considered

**Fix the Danger `:focus-visible:pointerover` ring with a single,
maximally specific selector, trusting CSS-style specificity resolution.**
Tried first, as the "obvious" approach — rejected the moment its own new
test failed, and replaced by explicit addition-order sequencing once
Avalonia's actual resolution rule was understood. Recorded here and in
the code itself, because the same mistake is available to any future
contributor who assumes Avalonia's `Styles` collection behaves like a
CSS cascade.

**Declare `AutomationLiveSetting.Off` explicitly on `Hint`, rather than
leaving it unset.** Considered and rejected in favour of leaving it
unset, once Avalonia's own default was confirmed directly to already be
`Off` — an explicit `Off` would have been redundant and, more
importantly, would have implied a considered choice about the value
rather than simply the absence of a live-region designation, which is
the more accurate statement of what changed.

**Fix the light Danger-on-Sunken text contrast failure (4.37:1,
discovered incidentally while validating finding 6) as part of this
round**, since the machinery to measure and fix it was already in hand.
Rejected: it was not one of the six findings handed to this Work
Package, its live placement could not be traced with the same
confidence as the other pairs (one of its three call sites sets no
background of its own and was not traced further up its host chain to a
confirmed surface), and fixing unlisted defects opportunistically is the
general sweep this brief explicitly rules out. Disclosed instead, with
the reasoning for not fixing it stated plainly.

## 7. Why This Solution Was Chosen

Drawing Primary's ring from its own foreground token (`OnAccentBrushKey`)
rather than picking a new, independently-chosen colour for the ring
means the contrast guarantee holds by the same design logic that already
guarantees Primary's own text is legible against its own fill — one
fewer independently-verified colour pairing to keep correct as the
palette evolves, rather than one more. Verifying the addition-order fix
by watching the specificity-first version fail is what actually
converts "the framework resolves same-selector styles unusually" from a
hunch into a confirmed, transferable fact about Avalonia, recorded where
the next contributor styling a pseudo-class combination will need it.

## 8. Architectural Principles

- **A style token wired up correctly is not the same claim as that
  token producing a visible result** — `FocusVisibleStyleTests.cs`'s
  original assertion (`BorderBrush == focusRing`) proved the first claim
  and was silent on the second, which is the one a keyboard user
  actually depends on.
- **Avalonia resolves same-selector-matching styles within one `Styles`
  collection by addition order, not by selector specificity** — a real,
  transferable fact about the framework, discovered by writing the
  intuitively "more specific" fix, watching it fail its own test, and
  re-deriving the actual rule empirically rather than from documentation
  assumed by analogy to CSS.
- **When one item in a Work Package receives a rigorous contrast check,
  every visually similar item in the same Work Package should receive
  the same check** — `WP 16.5A`'s own retrospective (§10) named this
  exact asymmetry (WCAG math applied to health text, not to the focus
  ring, by the same author in the same Work Package); this remediation
  applies the same rigour uniformly across all four treatments and both
  themes rather than repeating the asymmetry at a different item.
- **Verify a regression test by reverting the fix it targets, not only
  by observing it pass** — every one of the four regression-relevant new
  test groups in this Work Package was checked against the pre-fix
  source and confirmed to fail, matching the review board's own measured
  numbers, before being reconfirmed passing.

## 9. Benefits

- All six review-board findings closed, each with contrast numbers or
  automation-name assertions computed against real, resolved Avalonia
  values rather than against a static table — 21 new tests, `Tempest.
  Desktop.Tests` 453 → 474, 0 regressions.
- `TD-128` raised for the one genuine gap this Work Package's own brief
  explicitly did not cover (the Digital Thread graph's edge/relationship
  keyboard-selection gap) rather than silently left undisclosed —
  correctly scoped as a design decision (a real focus model for
  non-`Focusable` edge lines), not a defect fix this round could absorb.
- The Ribbon automation-name gap and the invisible Primary focus ring —
  both found independently by `WP 16.2C`'s own retrospective for
  `WP 16.5A`, written within the same hour — are the two most severe of
  the six findings this Work Package closes, closing the loop between a
  retrospective disclosing a defect and a remediation Work Package
  fixing the same defect within the same release wave.
- `TD-65` stays correctly **Partially resolved** rather than being
  pushed to Resolved on work this round did not do — the Digital Thread
  edge gap and the baseline's other previously-disclosed residuals
  (Editors watermark, Docking chrome buttons, non-button focus-visible
  precedence) are explicitly named as untouched, not implied closed by
  omission.

## 10. Trade-offs — what six findings closed does not mean

**The Digital Thread graph's relationship (edge) lines remain
keyboard-unreachable — a real, disclosed gap, deliberately not
touched.** Edges are `Line`/hit-test overlay pairs today, not
`Focusable` elements the way node `Border`s are; fixing this needs a
focus model that does not exist, which is a design decision outside
this Work Package's own six-finding brief. Recorded as `TD-128` rather
than left implicit.

**The light Danger-on-Sunken text pairing still fails WCAG (4.37:1
against a 4.5:1 floor) after this round's own nudge (it was 4.23:1
before)** — not one of the six findings, and not fixed, because its live
placement could not be traced to a confirmed surface with the same
confidence as the pairs that were fixed. Flagged rather than silently
left for a future placement to trip over.

**Turning off the Hint live region silences two genuine messages, not
only noise.** `SetHint` has exactly two kinds of caller: the Ribbon's
own hover wiring (the finding) and `WorkspaceLayoutPresetCoordinator`'s
two discrete, real status messages ("Grid layout applied.", "Layout
reset to the default arrangement."). `AutomationLiveSetting` is
per-control, not per-update, so there is no way to keep the two
layout-preset messages `Polite` while silencing hover spam without a
structural change (a second `Polite` segment, or routing those two
messages through `SetText` instead) — out of this finding's own scope,
and disclosed as a real, accepted cost rather than an unqualified win.

**Two registers now disagree about what this Work Package changed,
verified directly at this retrospective's own base commit.**
`docs/governance/Documentation/Academy Register.md`'s own `WP 16.5A` row
already reads "both remediated by `WP 16.5A-R1`" — updated at some point
after this Work Package landed. `docs/governance/Quality/Technical Debt
Register.md`'s own `TD-65` row was **not** updated the same way: it
still points only at `WP16.5A Accessibility Baseline Report.md`'s
"Remaining inventory," with no mention of `WP 16.5A-R1` at all, even
though `TD-65` is the exact row this Work Package's own six findings
narrow. `TD-128` was added as a new row (as this Work Package's own
report recommended), but the pre-existing `TD-65` row was left
unrevised. Neither register is wrong about anything it states — but a
reader of `TD-65` alone would not learn that two of the defects its own
baseline shipped were found and fixed one Work Package later.

**Per this retrospective's own scope boundary, `WP16.5A-accessibility-
baseline.md`'s own Future Evolution section (§12) is not updated
here.** That section explicitly named this Work Package's own branch,
`feature/v0.16.0-a11y-remediation`, as a "starting brief" and stated, as
of its own writing, that no remediation commits had yet been applied —
both now stale, since this Work Package is exactly that remediation.
Engineering Governance §6 requires a Future Evolution section that
predicted a change to be updated, not left stale, the moment that
change happens. This retrospective's own author boundary is limited to
three named files and does not include editing an existing retrospective
outside that set — the update is named here explicitly so it is not
lost, and is reported as an outstanding item rather than silently
performed outside scope or silently skipped.

## 11. Common Mistakes

- Checking that a brush-key assignment is internally consistent with a
  convention (Primary's ring uses the brand accent, as intended) without
  separately asking whether that same consistency defeats the purpose of
  the thing being styled — a focus ring identical to the fill it
  decorates is "correctly wired" and useless at the same time.
- Assuming CSS-style selector specificity governs which of two matching
  styles wins in an Avalonia `Styles` collection — it does not; addition
  order does, and the "obviously more specific" fix failed its own test
  as a direct result of this wrong assumption.
- Writing a style-resolution test that asserts a token equality
  (`BorderBrush == focusRing`) without also asserting the resolved
  colour's relationship to whatever it is drawn against — the two
  questions are different, and only the second one proves the feature
  works for a user.
- Updating one register's own row to reflect a remediation Work Package
  (`Academy Register.md`'s `WP 16.5A` row) while leaving a second
  register's directly relevant row (`TD-65`) unrevised — both describe
  the same code; only one now says what happened to it.

## 12. Future Evolution

`TD-128` (Digital Thread edge keyboard selection) and the light
Danger-on-Sunken contrast failure (4.37:1) are both real, disclosed, and
unfixed — either is a reasonable next accessibility remediation target,
and neither was in this Work Package's own six-finding scope. `TD-65`'s
own register row should be revisited to record what this Work Package
actually changed, the same way `Academy Register.md`'s own `WP 16.5A`
row already was — that revision was outside this retrospective's own
authoring boundary and is named here so it is not lost. `WP16.5A-
accessibility-baseline.md`'s own Future Evolution section (§12) named
this Work Package as its own predicted sequel and should, per
Engineering Governance §6, be revisited now that the prediction has come
true — also outside this retrospective's own three-file boundary, and
also named here rather than silently left for whoever next touches that
file to rediscover independently.

## 13. Key Takeaways

- A style token wired up correctly is not the same claim as a style
  token producing a visible result — test the second claim directly,
  against the real surface it is drawn on, not only the first.
- Do not assume a UI framework's same-selector style resolution follows
  CSS specificity rules; verify empirically, by watching the "obvious"
  fix fail its own test, before trusting an assumption borrowed from a
  different styling model.
- When a remediation Work Package updates one register to reflect what
  it changed, check whether every other register describing the same
  code needs the identical update — updating one and not the other
  leaves the record internally inconsistent.
- A Future Evolution section that correctly predicted this exact
  remediation should be revisited once the prediction comes true, per
  Engineering Governance §6 — naming that obligation explicitly, even
  when it falls outside the current author's own scope, is more honest
  than letting it go unmentioned.
