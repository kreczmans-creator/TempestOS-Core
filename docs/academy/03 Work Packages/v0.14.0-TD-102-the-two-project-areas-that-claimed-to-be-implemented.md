# TD-102 — The Two Project Areas That Claimed to Be Implemented Now Are

## 1. Introduction

`4bd6140` closed `TD-102`: the Project Workspace's Documents and
Requirements areas were declared `NavigationAvailability.Implemented` and
rendered `DeclaredCapabilityView` — a glyph, a title, a paragraph of
prose, and no content — with no "Not yet implemented" badge, because that
badge shows only for `Declared` areas. A pre-`v0.14.0` engineering-body-
of-work row; produced the companion Academy runtime-architecture article
`docs/academy/02 Runtime Architecture/39-project-documents-and-requirements.md`.

## 2. Purpose

To close a gap where the descriptor table, the governance registers and
the surface itself all agreed a capability existed, and it did not — found
by the 2026-08-29 post-`TD-80` product gap reassessment, which read
`ProjectWorkspaceView.BuildAreaContent` and found `Overview` was the only
area with content of its own.

## 3. Background

This is the same defect class `TD-80`'s own closure follow-up had just
found one layer down (a surface claiming a capability it lacked, with
nothing checking); here it recurs at the project-area descriptor level.

## 4. The Problem

Two of nine project areas claimed to be built and were not, with no
visible signal distinguishing them from the seven genuinely `Declared`
areas that honestly showed what was missing.

## 5. The Design

`ProjectDocumentRegister` lists the project's documents and drawings
through `ProjectMembership` transitively, so a drawing on a Part inside a
Sub-Assembly inside an Assembly is a project document — a direct-
children-only rule would find almost nothing in a real product structure.
Each file opens in the `TD-80` viewer through the same
`AttachmentViewerLauncher` the object editor uses. `ProjectRequirement
Register` lists requirements allocated into the project and reports the
declared status and the recorded verification outcome side by side,
because they can disagree and a reviewer needs to see it — the latest
verification wins, not the worst ever recorded. A requirement is not an
engineering object, so `ProjectMembership` cannot reach one directly; the
join is instead the allocation link the platform already records, and an
unallocated requirement belongs to no project — stated as the honest
consequence rather than engineered around, with the empty state saying so.

One new gap found and disclosed rather than patched: `GetEvidenceAsync`
is permission-gated, and the desktop shell establishes no principal, so
what a session may read depended on which sample module happened to
initialise last. Membership now joins on the ungated relationship read;
where verification genuinely cannot be read, the state is `Unknown`, kept
distinct from `NotVerified` — recorded as `TD-103`.

## 6. Alternatives Considered

A `ProjectId` field on the requirements model — implicitly rejected: the
join uses the allocation link the platform already records rather than
adding a second, competing answer to a question the platform can already
answer.

## 7. Why This Solution Was Chosen

Because `DeclaredCapabilityView`'s own badge logic already distinguished
`Declared` from `Implemented`; the fix is to make the descriptor tell the
truth rather than to change what the badge means.

## 8. Architectural Principles

A descriptor's claim and the surface's actual content must be checked
against each other, not merely declared consistently by whoever wrote
each — this is exactly the audit `187180a`'s later `ProductGapReconciliation
AuditTests` makes standing rather than one-time.

## 9. Benefits

12 register tests and 11 acceptance tests, every acceptance test driven
project → area → document/requirement → action through the real
`MainWindow`. Five mutations, five killed: membership reduced to direct
children, project isolation removed from the requirement join, a file-less
document dropped, the earliest verification preferred over the latest,
and the Documents area's Open button unwired.

## 10. Trade-offs

`TD-103` (the permission-gating principal-boundary gap) is disclosed
rather than fixed here; the fix belongs with the Administration module,
per the commit's own statement, not with this row's document/requirement
surfaces.

## 11. Common Mistakes

Marking a descriptor `Implemented` on the strength of a glyph, a title and
prose rendering without content behind it — the same shape of overclaim
`TD-80`'s closure had just caught one layer down, recurring here at the
area-descriptor level.

## 12. Future Evolution

`187180a`, the Product Gap Reconciliation audit later in this release,
generalises the fix into a standing test —
`ProductGapReconciliationAuditTests` — that drives every declared area
through the real shell and asserts the descriptor matches what renders,
rather than relying on this row's own manual find.

## 13. Key Takeaways

- A descriptor claiming "Implemented" needs the same scrutiny as any
  other claim in the repository — check it against what actually renders.
- Join through the domain relationship the platform already records
  (allocation, parent chain) rather than adding a redundant field.
- Distinguish "cannot see what was recorded" from "nothing was recorded"
  — collapsing the two states makes a surface state something false about
  a user's own data.
