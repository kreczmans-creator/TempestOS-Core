# WP 13.10C — Plugin Trust Hardening Review & Integration

## 1. Introduction

This Work Package independently re-verified, reconciled, and committed the
`WP 13.10A`/`WP 13.10B` plugin trust hardening chain as a single commit on
`feature/v0.13.0` — `79e453f`, 18 files changed, 1,782 insertions, 31
deletions. Its own `WorkPackages.md` row describes it exactly: "the same
integration-and-commit role `WP 13.9.7` established for the `WP 13.9.1`–
`WP 13.9.6` chain, applied here to the `WP 13.10A`/`WP 13.10B` chain."

As with its precedent, this is an **integration and review** Work Package.
It added no new architecture, no new isolation mechanism, no new ADR, and —
with one deliberate, narrowly-scoped exception noted throughout — no new
production behaviour. Its value lies in independent re-verification against
real source, in establishing that the fix under review was **non-vacuous**,
in reconciling the governance record, and in producing one clean commit.

The one exception is worth naming immediately, because it is the clearest
demonstration of why a review step is not ceremonial: this review found
that the twice-found, twice-fixed Host-crash regression `WP 13.10B` had
closed mid-implementation had **only ever been proven fixed via throwaway
proof-of-concept code**, never a permanent regression test. `WP 13.10C`
wrote that test itself.

`WorkPackages.md` classifies this Work Package `Governance/Process`.

## 2. Purpose

To determine — independently, against real, current source, and not against
the commissioning summary — whether `WP 13.10B` had genuinely closed
`TD-51` and `TD-52`; whether the closure was non-vacuous; whether anything
had regressed; whether the governance record described the resulting code
state; and, if all of that held, to commit it.

The four workstreams recorded in `PROJECT_STATUS.md` and `WorkPackages.md`
were run as **four fresh, read-only sub-agents**:

1. **Security/Adversarial** — is `TD-51`/`TD-52` genuinely closed, and can
   it be reopened by an adversary who reads the fix?
2. **Architecture/API** — is there a public API break, an unintended ADR
   change, or a dependency change?
3. **Verification/Test + RAM/Concurrency** — is the test coverage
   permanent and non-vacuous, and did anything about the suite's
   parallelism or memory configuration change?
4. **Governance/Documentation** — does the record match the code?

Each carried its own live proof-of-concept, per `TD-51`'s and `TD-52`'s own
Origin cells.

## 3. Background

`WP 13.9.7` had committed the `WP 13.9.1`–`WP 13.9.6` execution-boundary
chain (`d7d19d4`) and closed the boundary that chain was scoped to.
`WP 13.10A` then ran a read-only, six-discipline architecture and hardening
review across the *complete* `v0.13.0` plugin platform (`WP 13.0A`–
`WP 13.9.7`) and found two further Release-Blocking gaps, both live-PoC
confirmed, and — the register is explicit on this — **neither a variant of
anything the `WP 13.9.1`–`WP 13.9.6` chain closed**:

- **`TD-51`** — `PluginAssemblyLoader.EnforceTrust`'s static
  constructor-conformance check, `HasCompliantConstructor`, and with it the
  `NeverEligibleServiceResolveTypes` denylist, was invoked only against a
  plugin's discovered `IModule` types, never its `IHostedService` types. An
  `IHostedService`-only plugin hit `moduleTypes.Count == 0` and returned
  immediately after a trivially-satisfied, empty capability-ceiling check —
  its hosted service's constructor was never inspected at all. Compounded by
  `HostedServiceManager` having no `componentScopeProvider`-equivalent hook,
  unlike `ModuleLifecycleManager`, so even a legitimately-passing plugin's
  hosted service ran with a `null`, First-Party-treated ambient component
  principal. Introduced at `WP 13.2A`; `WP 13.9.4` extended
  `hostedServiceTypes` *recording* for the denial path but never the
  *conformance check itself*.
- **`TD-52`** — `IIdentityService.EstablishCurrentPrincipal` called
  `ICurrentPrincipalAccessor.SetCurrent` directly, and `IIdentityService` is
  an ordinary, DI-public, un-denylisted interface. A plugin declaring
  `plugin.services.resolve:Tempest.Core.Identity.IIdentityService` passed
  `EnforceTrust` cleanly, then could call `EstablishCurrentPrincipal` for any
  configured identity at runtime, with no ownership check — and because
  `ICurrentPrincipalAccessor` is deliberately not call-chain-scoped
  (`ADR-0044`), the effect persisted ambiently for the process.

`WP 13.10B` closed both, via strict per-file ownership across three parallel
production agents plus central integration. Its own independent Adversarial
Security review then found a **compounding regression introduced
mid-implementation**: `DiscoverModuleTypes`'s `WP 13.9.3` pre-resolution
loop iterated `moduleTypes` only, so once `HasCompliantConstructor` was
extended to `hostedServiceTypes`, an `IHostedService`-only plugin with a
genuinely unresolvable constructor-parameter type reached
`HasCompliantConstructor`'s own unguarded `GetParameters()` call as the
*first* resolution attempt for that type — throwing uncaught out of
`LoadPlugins` and `TempestHost.RunAsync` entirely. A Host-wide crash,
strictly worse than `TD-51`'s original gap. It was found **twice,
independently**, and the first attempted fix placed its `try`/`catch` one
level too deep — around the per-parameter body rather than `GetParameters()`
itself, which eagerly resolves every parameter's signature the moment it is
called — and never caught anything for its own documented scenario.

`WP 13.10B` did not commit. That was left to this Work Package.

## 4. The Problem

1. **Are `TD-51` and `TD-52` genuinely closed against real, current
   source?** Both had live proofs of concept demonstrating the gap. The
   question is whether the same proofs now fail.
2. **Is the closure non-vacuous?** A test that passes both with and without
   the fix proves nothing. Given that this chain's own implementation Work
   Package had already shipped one fix that "never actually caught anything
   for its own documented scenario," this was not a theoretical concern.
3. **Is the coverage permanent?** A regression proven fixed only by
   throwaway proof-of-concept code is a regression with no guard against its
   own return.
4. **Did anything else move?** Public API surface, ADRs, dependencies — and
   specifically, given this session's own repeatedly-observed "Test host
   process crashed" incidents, had `WP 13.10B` changed anything about
   test-suite parallelism or RAM configuration?
5. **Does the governance record match?** `Plugin Trust & Isolation
   Architecture.md` still carried a "Found, `WP 13.10A` — NOT YET CLOSED"
   Risks entry. `ADR-0111` carried a "third and final correction" claim from
   `WP 13.9.6` that was, by this point, superseded. `Technical Debt
   Register.md`'s `Total` line had last been incremented at `WP 13.3A` and
   had never been updated for `TD-51`/`TD-52`.

## 5. The Design

Again, no production design. What follows is the design of the **review and
integration discipline**.

**Four fresh, read-only sub-agents.** This is the deliberate divergence
from `WP 13.9.7`, which ran as sole integrator with no reviewers at all.
The four disciplines (Security/Adversarial, Architecture/API,
Verification/Test + RAM/Concurrency, Governance/Documentation) each
re-verified `WP 13.10B`'s fix **directly against real, current source, not
the commissioning summary alone**, and each carried its own live proof of
concept. All four converged clean on `TD-51`/`TD-52` themselves.

**Central integration, no parallel writers.** The reviewers are read-only.
Every edit — the new test, the register corrections, the ADR amendments, the
row and stratum additions — was made centrally, preserving the property
`WP 13.9.7` established: one writer at the integration step, one commit.

**Non-vacuousness established by revert-and-restore.** This is the
methodological core. `TD-51`'s and `TD-52`'s Origin cells record it
identically: "non-vacuousness confirmed by reverting the fix and observing
the targeted tests genuinely fail, then restoring." It was performed on the
two most load-bearing tests, **independently by two separate reviewers**.
For the new permanent test this Work Package wrote, the record is more
specific still: reverted, **observed to fail with the exact uncaught
`FileNotFoundException`**, restored. A test that fails for the wrong reason
when reverted is nearly as uninformative as one that does not fail at all;
naming the exception is what closes that.

**One permanent-coverage gap found and closed directly.** The
Verification/RAM reviewer established that the twice-found Host-crash
regression had only ever been proven fixed via throwaway proof-of-concept
code, across two independent `WP 13.10B` reviewers, and never by a permanent
regression test. This Work Package wrote
`LoadPlugins_FirstHostedServiceOnlyPluginHasUnresolvableConstructorParameterType_IsolatesFailure_SecondLegitimatePluginStillLoads`
— a name that is itself the specification: the first plugin's failure is
isolated, and the second, legitimate plugin still loads. This is the one net
new permanent test, and accounts for the regression count moving from
`WP 13.10B`'s 2,553 to this Work Package's **2,554**.

**Two items disclosed, deliberately not fixed.** Scope discipline at the
integration step means finding things and *not* fixing them, with the
reasoning recorded:

- A small, low-severity, **pre-existing** (not `WP 13.10B`-introduced) gap:
  the "unresolvable constructor parameter type" denial path throws
  `PluginTrustDeniedException` directly from inside `DiscoverModuleTypes`,
  before `EnforceTrust` ever reaches a `RecordDenied` call site — so that
  one specific type is never added to `deniedTypeRegistry`. This review
  characterised the consequence as a second, independent construction
  attempt during Registration, safely failing for the identical reason: **no
  code execution, a `Failed` state, not a crash.** Confirmed pre-existing
  since `WP 13.9.3` for the `IModule` axis; `WP 13.10B` merely widened its
  reach. §11 and §12 return to this characterisation, which was
  subsequently found to be wrong on one axis.
- A **governance-only note, not a code defect**: `plugin.identity.establish`
  is grantable to any trust tier above `UnsignedLocal` — including
  `VerifiedSigned`, not only `FirstParty` — and `EstablishCurrentPrincipal`
  accepts an arbitrary `identityId` with no ownership check **by design**
  (`ADR-0043`, no authentication). Granting this one capability to a signed
  third-party publisher is effectively full ambient-identity impersonation
  power, including impersonating a configured administrator identity: a
  materially broader blast radius than every other v1 capability. Inherent
  to the capability's necessary semantics; warrants explicit governance
  sign-off before any third-party publisher is actually granted it.

**An open session question resolved rather than left hanging.** The
Verification/RAM reviewer **definitively confirmed no test-suite
parallelism or RAM configuration was changed at all** — every new
real-assembly-loading test correctly reuses the pre-existing
`[Collection("Console output capture")]` convention — and independently
traced the session's repeated "Test host process crashed" pattern to
**external, concurrent multi-agent process contention**, a session-workflow
artefact, not a test-suite design defect. Recording a negative finding with
its actual cause is what stops it resurfacing as folklore.

**Governance reconciliation.** `TD-51`/`TD-52` moved **Open → Resolved** in
`Technical Debt Register.md`, each entry's Status field extended to disclose
the mid-`WP 13.10B` regression and both further items in full, mirroring
`TD-49`'s established "disclose the full discovery history" convention; the
register's own stale `Total` line — last incremented at `WP 13.3A`, never
updated for `WP 13.10A`'s addition of `TD-51`/`TD-52` — corrected to **52
tracked items: 18 Resolved, 1 Partially resolved, 33 Open**. `Plugin Trust &
Isolation Architecture.md`'s "Found, `WP 13.10A` — NOT YET CLOSED" Risks
entry corrected to "Closed, `WP 13.10B`", with the regression and both
disclosed items recorded there too, and its Status-header narrative
corrected to match — **including the now-superseded "third and final
correction" claim in `ADR-0111`**. `ADR-0111` gained a "Corrected,
`WP 13.10B`" Status-section note and matching Decision-text amendment (the
static check's stated scope extended to `IHostedService`; the "Dynamic, at
each call site" list extended to `IIdentityService.EstablishCurrentPrincipal`)
plus a `Related Documents` extension citing `TD-51`/`TD-52` — **not a new
ADR**, per both `WP 13.10A` reviewing disciplines' independent assessment —
and `ADR Register.md`'s `ADR-0111` citation was extended to a **seventh
phase**, "mirroring `WP 13.9.7`'s own identical six-phase precedent", 111
ADRs unchanged. Three `WorkPackages.md` rows and a matching
`PROJECT_STATUS.md` stratum were added. Two convention checks were run and
both recorded negative: none of the three Work Packages requires a new
Academy retrospective, per `Academy Index.md`'s own maintenance rule and the
`WP 13.2B`/`WP 13.9.1`–`WP 13.9.6` precedent; and `Security Roadmap.md`
items 1/2/10 require no update, matching the precedent the `WP 13.9.1`–
`WP 13.9.6` integration already set.

**Verification, independently re-run fresh after every correction.**
`governance-healthcheck.ps1`: **7 passed, 1 pre-existing informational
warning, 0 failed**, confirmed identical before and after every
documentation edit. Debug and Release builds both **0 Warnings, 0 Errors**
with `-p:TreatWarningsAsErrors=true`. Full regression both configurations:
**2,554/2,554 passing** (2,333 `Tempest.Core.Tests` + 221
`Tempest.Desktop.Tests`). Working tree confirmed via `git status --short`
before staging. Not pushed, not tagged, no release created.

## 6. Alternatives Considered

- **Accepting `WP 13.10B`'s own two independent reviews as sufficient.**
  Rejected. Those reviews were internal to the implementation Work Package
  and had, between them, already shipped one fix that caught nothing. The
  specific thing four fresh reviewers found — that a twice-fixed Host crash
  had no permanent test — is precisely the class of gap an implementation's
  own review is least likely to see, having watched the crash reproduced
  twice and reasonably concluded it was well understood.
- **Sole integrator with no reviewers, exactly as `WP 13.9.7`.** Rejected,
  and the divergence is the point. `WP 13.9.7`'s disclosed principal
  trade-off was that its verification pass had no second pair of eyes; this
  chain had a mid-implementation regression strictly worse than the defect
  being fixed, which raised the cost of an unreviewed integration above the
  cost of four review passes.
- **Fixing the disclosed `RecordDenied` gap here.** Rejected, explicitly, to
  avoid scope creep beyond this review's own remit — it was assessed
  pre-existing since `WP 13.9.3` and, on this review's own analysis, safely
  isolated. §11 and §12 record what happened to that assessment.
- **Raising the `plugin.identity.establish` blast-radius note as a code
  defect.** Rejected. `EstablishCurrentPrincipal`'s lack of an ownership
  check is `ADR-0043`'s design, not an implementation error, and
  re-litigating a ratified ADR inside a review-and-commit Work Package is
  exactly the architectural drift this WP kind exists to avoid. Recorded as
  a governance sign-off requirement in `TD-52`'s Status cell instead.
- **A new ADR for the `IHostedService` scope extension and the identity
  gate.** Rejected on both `WP 13.10A` reviewing disciplines' independent
  assessment: both changes sit within `ADR-0111`'s existing scope and were
  handled by the amendment pattern `WP 13.9.1`/`WP 13.9.3`/`WP 13.9.4`/
  `WP 13.9.6` each already used.
- **Treating the "Test host process crashed" incidents as a test-suite
  defect and re-tuning parallelism.** Rejected on evidence: no parallelism
  or RAM configuration had changed, and the cause was traced externally.
  Re-tuning a suite to accommodate an artefact of how the session itself was
  run would be a permanent change made for a transient reason.

## 7. Why This Solution Was Chosen

Because the chain's own evidence set the bar. `WP 13.10B` was not a
careless Work Package — it used strict per-file ownership across parallel
agents, sequenced its test-writing agents to avoid a shared-builder-file
conflict, and ran two independent reviews of its own. It nonetheless
introduced a Host-wide crash worse than the defect it was fixing, needed two
independent discoveries to see it, and needed two attempts to fix it. A
chain with that history does not get committed on the strength of its own
summary.

The four-discipline split follows the shape of what could still be wrong.
Security/Adversarial for whether the gap is truly gone; Architecture/API for
whether closing it broke something else; Verification for whether the proof
is real and permanent; Governance for whether the record is honest. Each was
read-only, each carried a live proof of concept, and the two most
load-bearing revert-and-restore checks were performed by two *separate*
reviewers — so the non-vacuousness claim does not rest on a single agent's
account of its own work.

The decision to fix exactly one thing and disclose two is the same scope
discipline `WP 13.9.7` applied to governance staleness, applied here to code:
the missing permanent test was a direct, in-remit consequence of what this
review was chartered to verify — that the fix is genuinely proven — and the
other two were not.

## 8. Architectural Principles

- **No New Architecture at the Integration Step.** No new isolation
  mechanism, no `AssemblyLoadContext`, no process separation, no new ADR.
  Every production change in `79e453f` was authored by `WP 13.10B`; this
  Work Package added one test file's worth of permanent coverage and the
  governance record.
- **Independent Re-verification Against Primary Source.** Four fresh
  reviewers, read-only, each against real current source rather than the
  commissioning summary — the same discipline `Engineering Readiness Review
  Architecture.md` §5 applies to reviewers, here applied to the closure of a
  fix rather than to the code being fixed.
- **A Fix Is Not Closed Until Its Proof Is Permanent.** The distinction
  between "reproduced fixed by a proof of concept" and "guarded by a
  committed regression test" is the difference between knowing a bug is gone
  today and knowing it cannot return. This Work Package treated the former
  as an open finding.
- **Non-vacuousness Is Demonstrated, Not Asserted.** Revert, observe the
  targeted test genuinely fail — with the exact expected exception, where
  the record names it — restore. Performed independently by two reviewers on
  the two most load-bearing tests.
- **Disclose, Don't Fix, Outside the Remit.** Two findings were recorded in
  full and deliberately left: one pre-existing code gap, one governance
  sign-off requirement. Both carry their reasoning and their own register
  Status cells.
- **Record Negative Findings With Their Cause.** "No parallelism or RAM
  configuration changed; the crashes were external multi-agent process
  contention" is a more useful record than silence, and prevents a
  session artefact hardening into a believed test-suite defect.
- **Amend the Existing Decision Where the Decision Still Holds.**
  `ADR-0111`'s Decision text already described the enforcement model; what
  was wrong was its stated scope. Extending it — and extending its register
  citation to a seventh phase — is honest amendment, not a new decision.

## 9. Benefits

- **`TD-51` and `TD-52` moved Open → Resolved with independent, non-vacuous
  evidence.** Both register entries record that the exact `WP 13.10A`
  proof-of-concept scenarios now behave correctly: the `UnsignedLocal`,
  zero-capability, `IHostedService`-only manifest whose constructor took the
  denylisted concrete `CurrentComponentAccessor` is now denied at category
  17, exactly like a non-compliant `IModule` type always was; a plugin
  declaring `plugin.services.resolve:...IIdentityService` now additionally
  requires an explicit `plugin.identity.establish` grant.
- **A twice-fixed Host crash now has a permanent guard**, its
  non-vacuousness independently confirmed against the exact uncaught
  `FileNotFoundException`.
- **Zero behavioural change for every existing first-party caller**, per
  `TD-52`'s Status cell — the new `EstablishCurrentPrincipal` gate is
  *skipped entirely*, not merely satisfied, when the ambient component
  principal is `null` or First-Party.
- **`HostedServiceManager` gained the component-scope hook it had always
  lacked**, mirroring `ModuleLifecycleManager`'s established `ADR-0111`
  hook, keyed by `Type` since a hosted service carries no string `Id` —
  verified by an `AmbientPrincipalCaptureProbe`-based regression test.
- **The governance record now matches the code.** "NOT YET CLOSED" corrected
  to "Closed"; a superseded "third and final correction" claim corrected; a
  `Total` line stale since `WP 13.3A` corrected to 52 tracked items.
- **An open operational question was closed with evidence**, not deferred:
  the test-host crashes were external contention.
- **A governance risk was surfaced before it could be granted** — the
  `plugin.identity.establish` blast-radius note sits in `TD-52`'s Status
  cell before any third-party publisher can request it.
- **The integration role now has two instances and a visible improvement
  between them** — `WP 13.9.7` established it; this Work Package added
  independent review at the integration step.

## 10. Trade-offs

- **Four reviewers converging clean is not proof of absence.** All four
  converged clean on `TD-51`/`TD-52`, and `WP 13.11A` subsequently found a
  genuine Release-Blocking defect in a residual gap this very review had
  examined and characterised (§11). Convergence establishes that four
  independent examinations found nothing; it does not establish that there
  was nothing.
- **The one disclosed-not-fixed code item was characterised incorrectly for
  one axis.** This is the record's most instructive single fact and is
  treated at length in §11 and §12.
- **One commit, 18 files.** Same bisection trade-off `WP 13.9.7` accepted,
  for the same reason: `WP 13.10B`'s intermediate states include one that
  crashes the Host, and a history that never passes through it is more
  honest than one that does.
- **Verification figures are internally consistent, not externally
  reproduced.** **2,554/2,554** appears identically in the commit message,
  the `WorkPackages.md` row, and the `PROJECT_STATUS.md` stratum. Note
  that `WP 13.10B`'s own row records **2,553/2,553** — the difference is
  exactly the one net new permanent test this Work Package added, and the
  two figures are consistent rather than contradictory.
- **A governance sign-off requirement is not a control.** The
  `plugin.identity.establish` note records that explicit sign-off is
  warranted before granting the capability to a third-party publisher.
  Nothing in the code enforces that; it is a register entry relying on a
  human reading it at the right moment.
- **The convention check said no Academy retrospective was required.** This
  document, and the `WP 13.10A`/`WP 13.10B` retrospectives alongside it,
  are later backfills that exceed the rule the check verified.

## 11. Common Mistakes

1. **Reading `79e453f` as `WP 13.10C`'s own engineering.** It is not. The
   production changes — `PluginAssemblyLoader.cs`, `HostedServiceManager.cs`,
   `TempestHost.cs`, `PluginCapability.cs`, `IdentityService.cs` — are
   `WP 13.10B`'s. This Work Package contributed one permanent test, the
   governance reconciliation, and the commit.
2. **Treating "all four reviewers converged clean" as a stronger claim than
   it is.** It means four independent examinations found nothing on the
   axes they examined. §10 and the next item show why that is not the same
   as correctness.
3. **The characterisation that was subsequently found false — and how to
   read it.** This Work Package disclosed the residual "unresolvable
   constructor parameter type" gap (the type never reaching `RecordDenied`,
   hence never entering `deniedTypeRegistry`) and characterised its
   consequence **uniformly** as safely isolated: a second, independent
   construction attempt during Registration, failing for the identical
   reason, **no code execution, a `Failed` state, not a crash**. That was
   this review's honest, recorded conclusion at the time, and it was
   deliberately disclosed rather than fixed, on scope-discipline grounds.

   `WP 13.11A`'s own Security/Adversarial reviewer later re-examined that
   characterisation and found it **accurate for the `IHostedService` axis
   and false for the `IModule` axis**. `HostedServiceManager.StartServiceAsync`'s
   generic `try`/`catch` genuinely isolates the failure; Module Discovery's
   independent, deliberately plugin-unaware rescan has no equivalent guard.
   Because the type never enters `deniedTypeRegistry`, `TempestHost.cs`'s own
   `WP 13.9.6` filter (`isTypeExcluded: deniedTypeRegistry.IsDenied`) never
   excludes it; `ReflectionFrameworkDiscoveryService.CreateDescriptor`'s
   unguarded `type.GetConstructor(Type.EmptyTypes)` then throws an uncaught
   `TypeLoadException`/`FileNotFoundException`, which propagates through
   `TempestHost.RunAsync`'s outer `catch` to a genuine Host crash —
   reachable by a single, otherwise-inert `IModule` type, any trust tier,
   zero requested capabilities. `WP 13.11A` reopened `TD-51` (Resolved →
   Reopened; graded at the time "Release Blocking for third-party plugin
   support" — in `ADR-0106` §4 terms **Disclosed, Non-Blocking for
   `v0.13.0`; mandatory precondition to enabling third-party plugin
   support**, normalised by `WP 13.12.2`) and confirmed
   it empirically with a real, minimal repro built and torn down during the
   review. `WP 13.11B` then closed it, and `TD-51`'s Status cell today reads
   "**Resolved, `WP 13.11B`; previously Reopened `WP 13.11A`, and before
   that Resolved `WP 13.10B`, independently re-verified `WP 13.10C`.**"

   The mistake to avoid is reading this as either (a) a concealment — it was
   not; the gap was disclosed, in writing, in three places, by this Work
   Package's own reviewer, which is precisely why `WP 13.11A` had something
   to re-examine — or (b) a mere clerical correction. It was a wrong
   inference from a correct observation. The observation (the type never
   reaches `RecordDenied`) was right. The inference (therefore the
   consequence is a redundant, safe second construction attempt) held on one
   axis and did not hold on the other, because the two axes have different
   downstream guards. **Nothing in the record suggests `WP 13.10C` had the
   evidence to know this**; `WP 13.11A` reached it by tracing the gap
   end to end, through `TempestHost.cs` and into
   `ReflectionFrameworkDiscoveryService`, which is a longer trace than
   "disclosed, out of remit" invited.
4. **Assuming a disclosed-not-fixed item is a low-priority item.** This one
   was disclosed as low-severity and was, on one axis, Release Blocking. The
   durable lesson is that a *characterisation* attached to a disclosure
   deserves the same non-vacuousness discipline this Work Package applied to
   the fix it was reviewing — a disclosure asserting "not a crash" is a
   claim, and claims in this chain have a demonstrated habit of needing
   testing.
5. **Assuming the mid-`WP 13.10B` regression is `TD-51` itself.** It is
   not. `TD-51` is the missing `IHostedService` conformance check. The
   Host-crash regression was introduced by extending that check, found twice
   independently, fixed twice, and only given a permanent test here.
6. **Assuming the `plugin.identity.establish` note is a defect report.** It
   is explicitly not: "inherent to the capability's own necessary semantics,
   not a code defect requiring a fix, but warrants explicit governance
   sign-off."
7. **Expecting a push or a tag.** None. Not pushed, not tagged, no release
   created — as with `WP 13.9.7`.

## 12. Future Evolution

- **`TD-51`'s full arc is now a four-Work-Package record**, and its Status
  cell carries every phase rather than only the latest: found `WP 13.10A`,
  fixed `WP 13.10B`, independently re-verified `WP 13.10C`, reopened
  `WP 13.11A`, closed `WP 13.11B`. That the register preserves the reopening
  in place, rather than overwriting it, is what makes this Work Package's
  own superseded characterisation legible to a later reader at all.
- **`WP 13.11B` closed the root cause this Work Package disclosed and left.**
  It implemented both of `WP 13.11A`'s recommended options: (a)
  `PluginAssemblyLoader.DiscoverModuleTypes`'s unresolvable-constructor-
  parameter-type failure no longer throws from inside the scan, but is
  surfaced to `EnforceTrust` through a new `out PluginTrustDeniedException?`
  parameter which records every discovered `IModule` and `IHostedService`
  type via `RecordDenied` **before** throwing — with the fixed-point scan
  allowed to run to completion rather than aborting mid-traversal, because

## 13. Key Takeaways

- **An integration Work Package earns its place by finding what the
  implementation's own reviews could not.** `WP 13.10B` had two independent
  reviews and still shipped a twice-fixed Host crash with no permanent test.
  Four fresh reviewers found that in a pass whose stated purpose was merely
  to confirm the fix.
- **"Proven fixed" and "guarded against return" are different claims.** A
  throwaway proof of concept establishes the first. Only a committed test
  establishes the second, and treating the gap between them as a genuine
  finding is what this review contributed to the code.
- **Non-vacuousness is the review's real product.** Revert, watch the
  targeted test fail — with the exact expected exception — restore; done
  independently by two reviewers on the two most load-bearing tests. Without
  it, "the tests pass" is compatible with the fix doing nothing, which this
  chain had already demonstrated once.
- **A characterisation attached to a disclosure is a claim, and claims need
  testing too.** This Work Package's own "safely isolated, no crash" was a
  reasonable inference from a correct observation, disclosed in good faith
  and in full — and was false for the `IModule` axis, as `WP 13.11A`
  established by tracing the same gap two layers further downstream. The
  discipline the record recommends is to extend the same evidential standard
  to what you decline to fix as to what you verify.
- **Disclosing a gap you decline to fix is what makes it fixable later.**
  `WP 13.11A` did not discover this gap; it re-examined a disclosure this
  Work Package had written down, in three places, with enough technical
  detail to be re-traced. A silent decision not to fix would have left
  nothing to re-examine.
- **Scope discipline cuts both ways at the integration step.** One thing was
  fixed because it was directly in remit — the missing permanent test — and
  two were disclosed and left because they were not. Both decisions are
  recorded with reasoning, which is what allows a later reader to judge
  them, and one of them to be judged wrong.
- **The role improved between instances.** `WP 13.9.7` established
  sole-integrator integration-and-commit and disclosed its lack of
  independent review as its principal trade-off. `WP 13.10C` kept the single
  writer and added four read-only reviewers. That is what a governance
  precedent is for.
