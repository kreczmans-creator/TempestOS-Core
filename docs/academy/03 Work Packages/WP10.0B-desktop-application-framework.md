# WP 10.0B — Desktop Application Framework — Implementation

## 1. Introduction

`WP 10.0B` is Programme 10's own second Work Package — the first real
implementation Work Package of `v0.10.0`, following `WP 10.0A`'s own
architecture-and-specification-only opening. It builds
`Tempest.Desktop`, TempestOS's first graphical desktop application,
over the exact same Engineering Workspace six real disciplines already
populate.

## 2. Purpose

To realise `WP10.0A UX Architecture Document.md`'s own design as real,
running, tested code — resolving `ADR-0094` (concrete framework
selection) and building every named implementation item (Application
bootstrap through Window lifecycle) over the unchanged Workspace
contract layer.

## 3. Background

See `20-desktop-application-framework.md` for the full concept guide —
this document is this Work Package's own implementation narrative and
retrospective specifically.

## 4. The Problem

Build a second, structurally different presentation layer
(`Tempest.Desktop`) alongside the existing console one (`Tempest.App`/
`TempestShell`), loading the identical six Engineering Disciplines,
without touching any Workspace contract, without any engineering
functionality change, and with every "Demonstrate" requirement proven
as real, automated, passing tests.

## Architectural Debt Assessment

Four genuine, disclosed implementation-time findings, each caught by
a real, failing `Avalonia.Headless.XUnit` test before any commit — the
identical discipline `WP 9.1A` first established for this project:

1. **`ThemeService.Apply` threw on a non-UI thread** — fixed via
   `Dispatcher.UIThread.CheckAccess()`/`Invoke`. Not registered as
   Technical Debt (never part of a commit or tagged release).
2. **`ProjectExplorer.Id`/`PropertyInspector.Id` non-determinism broke
   cross-restart session persistence** — a genuine, pre-existing
   defect confirmed present, unmodified, in the shipped `v0.9.0` tag.
   Fixed in place; registered as a new Technical Debt item with
   disposition **Resolved by `WP 10.0B`** (see `WP10.0B Technical Debt
   Review.md` §2), mirroring `TD-26`'s own precedent of registering a
   pre-existing, confirmed-shipped defect even when closed
   immediately.
3. **`TD-26` itself, directly reproduced** — `WorkspaceManager.StartAsync`
   returning before Runtime Host module Discovery/Initialise completes,
   named at `WP 9.0A` but never before directly, reproducibly hit by
   any test. Mitigated (not fixed at the source) entirely within
   `Tempest.Desktop` — `TD-26` itself remains Open, its own priority
   reconsideration recommended (`WP10.0B Technical Debt Review.md`
   §1).

One further, disclosed, non-blocking finding: the file-based Settings
persistence store resolves relative to the process's own current
working directory, a genuinely new consideration for a graphical
application launched from outside a terminal — registered as a new,
Open Technical Debt item (`WP10.0B Technical Debt Review.md` §3).

## Observations

- **A second presentation layer is the strongest possible test of "the
  contract is rendering-agnostic."** This project asserted that claim
  at `WP 8.0B` and reaffirmed it at `WP 10.0A`; only this Work
  Package's own real code actually tested it, and it held.
- **Cross-process testing finds defects single-process testing
  structurally cannot.** Both `TD-26`'s own live reproduction and the
  panel-Id defect required constructing two genuinely independent
  `WorkspaceManager`/`ITempestHost` instances in the same test — a
  test shape this project had never once used before this Work
  Package, despite 2026 existing tests.
- **Shared composition roots are worth extracting the moment a second
  consumer appears**, not before (`FCR`-style "do not build ahead of
  evidence" applied to internal refactoring, not only external
  capability).
