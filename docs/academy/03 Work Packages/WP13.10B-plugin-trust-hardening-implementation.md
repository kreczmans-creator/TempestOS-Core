# WP 13.10B — Plugin Trust Hardening Implementation

## 1. Introduction

This Work Package is the **production implementation** that closes both of
`WP 13.10A`'s findings in full — `TD-51` (the static constructor-conformance
check and the `NeverEligibleServiceResolveTypes` denylist never covering a
plugin's `IHostedService` types, compounded by `HostedServiceManager` having
no component-scope seam at all) and `TD-52`
(`IIdentityService.EstablishCurrentPrincipal` reaching the ambient-identity
write surface ungated). It runs on `feature/v0.13.0`, directly commissioned
by `WP 13.10A`, and is itself reviewed and committed by `WP 13.10C`.

Five production files changed: `Plugins/PluginAssemblyLoader.cs`,
`BackgroundServices/HostedServiceManager.cs`,
`Identity/IdentityService.cs`, `Plugins/PluginCapability.cs`, and
`Runtime/TempestHost.cs`. No new isolation mechanism, no
`AssemblyLoadContext`, no process separation, and **no new ADR** — only a
"Corrected, `WP 13.10B`" note and Decision-text amendment on `ADR-0111`,
exactly the shape both of `WP 13.10A`'s reviewing disciplines had
independently assessed as sufficient.

**This Work Package's own independent Adversarial Security review found and
fixed a compounding regression, mid-implementation, before any commit** — a
Host-wide crash strictly worse than the gap `TD-51` was closing. It is
disclosed here in full because it is the most instructive thing this Work
Package produced.

This Work Package **did not commit**. `WP 13.10C` reviewed, corrected one
test-coverage gap, and committed the whole as `79e453f`.

## 2. Purpose

To close `TD-51` and `TD-52` using mechanisms that already exist in this
codebase, with zero behavioural change for every actor that exists today —
all of which are First-Party — and with no widening of scope beyond the two
registered findings.

The design constraint was explicit and inherited from `WP 13.10A`: each fix
must be a **coverage extension of an existing mechanism**, not a new
mechanism. `HasCompliantConstructor` already existed and was correct — it
was simply not being called on one of the two discovery axes.
`ModuleLifecycleManager` already had a `componentScopeProvider` hook —
`HostedServiceManager` simply had none. `NavigationService.Register`
already had a dynamic `IPermissionEvaluator.RequirePermission` gate —
`EstablishCurrentPrincipal` simply had none. Three gaps, three existing
patterns to copy.

## 3. Background

`ADR-0111` (`WP 13.2A`) established two enforcement halves. **Static, at
Plugin Loading:** every requested capability key is checked against the
plugin's trust tier's ceiling (`ADR-0112`), and every constructor parameter
type on a discovered implementer is reflected over for conformance against
a fixed always-allowed baseline (`ILogger`, `IConfigurationProvider`,
`IDiagnosticsProvider`) plus the plugin's own granted
`plugin.services.resolve:<FullTypeName>` entries, with two concrete
Host-authority types — `Identity.CurrentComponentAccessor` and
`Identity.CurrentPrincipalAccessor` — never eligible at any tier
(`NeverEligibleServiceResolveTypes`, a `WP 13.2B` security-review finding).
**Dynamic, at each call site:** `NavigationService.Register`/`Unregister`,
the Command Framework's registration path, and `IEventBus.PublishAsync`
each carry one `RequirePermission(componentPrincipal, permission)` call,
skipped — not merely satisfied — when the ambient component principal is
`null` or First-Party.

`WP 13.9.3` had earlier added a fixed-point, breadth-first multi-assembly
scan to `DiscoverModuleTypes`, with a **pre-resolution loop** that forces
every discovered type's every public constructor's every parameter's
`ParameterType` to resolve *inside* the scan's own before/after `AppDomain`
diff window — so that an assembly pulled in only by a constructor
parameter's signature is discovered by the scan rather than sneaking in
later. That loop iterated `moduleTypes` only. It is the single most
important piece of prior context for §7 of this retrospective.

`WP 13.10A` then found both gaps this Work Package closes, live-PoC
confirmed, and graded them, at the time, "Release Blocking for
third-party plugin support only" — in `ADR-0106` §4 terms **Disclosed,
Non-Blocking for `v0.13.0`; mandatory precondition to enabling
third-party plugin support** (wording normalised by `WP 13.12.2`; the
underlying technical classification is unchanged).

## 4. The Problem

1. **Extend the static check to the second discovery axis without changing
   the check itself.** `HasCompliantConstructor` is correct; it was called
   on the wrong set. `EnforceTrust` also returned early on
   `moduleTypes.Count == 0`, and recorded the plugin's component principal
   for `moduleTypes` only — so an `IHostedService`-only plugin was
   unchecked *and* unrecorded.
2. **Give `HostedServiceManager` a component-scope seam it has never
   had — without giving it any plugin awareness.** `HostedServiceManager`
   lives in `Tempest.Core.BackgroundServices` and carries no reference to
   `Tempest.Core.Plugins` or `Tempest.Core.Identity` at all. Whatever seam
   it gains must stay generic. It also has no `Id` concept: a hosted
   service is identified by its own `Type`, unlike a module, which carries
   a string `Id` and a descriptor.
3. **Gate `EstablishCurrentPrincipal` without breaking the genuine
   first-party login/session flow.** Every existing caller of
   `EstablishCurrentPrincipal` is first-party and must observe *zero*
   behavioural change — not "a check that passes", but no check at all.
4. **Add one capability key to a v1 key set that is closed.**
   `plugin.identity.establish` must be additive, recognised by the
   loader's own key validation, and correctly absent from
   `UnsignedLocalCapabilityCeiling` so the lowest tier can never request
   it.
5. **Change nothing else.** Five files, two findings, no scope creep — the
   condition under which `WP 13.10C`'s independent review can be a review
   of a bounded change rather than an audit of a release.

## 5. The Design

**`PluginAssemblyLoader.EnforceTrust` — axis-complete static enforcement.**
The non-compliant-type search became
`moduleTypes.Concat(hostedServiceTypes).FirstOrDefault(type => !HasCompliantConstructor(type, manifest))`;
`HasCompliantConstructor` itself is unchanged, and so, therefore, is the
`NeverEligibleServiceResolveTypes` denylist it applies. The denial message
widened from "Module type ..." to "Module or hosted service type ...". The
early return became `if (moduleTypes.Count == 0 && hostedServiceTypes.Count == 0)`,
and the component-principal recording loop became
`foreach (var type in moduleTypes.Concat(hostedServiceTypes))
_componentPrincipalRecorder?.Record(type, principal);` — so a hosted
service type is now *both* checked and recorded. This is a four-line change
in shape and the whole of `TD-51`'s first half.

**`PluginCapability.IdentityEstablish` — one additive key.**
`public const string IdentityEstablish = "plugin.identity.establish";`,
documented in that type's own capability table, and added to
`PluginAssemblyLoader`'s recognised-key predicate alongside `Navigation`,
`Commands`, `DiRegister`, and the two prefixed families
(`plugin.events.publish:`, `plugin.services.resolve:`). It is deliberately
**not** added to `UnsignedLocalCapabilityCeiling`, which remains exactly
`{ PluginCapability.Navigation, PluginCapability.Commands }` — so an
`UnsignedLocal` plugin requesting it is denied by the existing
capability-ceiling check (`FindIneligibleCapability`) before any dynamic
gate is ever reached.

**`HostedServiceManager` — a generic, plugin-unaware component-scope
hook.** A new fourth constructor parameter,
`Func<Type, IDisposable?>? componentScopeProvider = null`, optional and
trailing, so every existing caller compiles and behaves identically. Given
a hosted service's own concrete `Type` — keyed by `Type` precisely because
a hosted service has no string `Id`, unlike `ModuleLifecycleManager`'s own
`Id`-keyed hook — it may return a disposable scope token. It is invoked as
`using var scope = _componentScopeProvider?.Invoke(tracked.ServiceType);`
**inside the existing `try` block** in both `StartServiceAsync` and
`StopServiceAsync`, immediately before `StartAsync`/`StopAsync`. Placement
inside the `try` is load-bearing: the `using` block's implicit `finally`
pops the scope before this class's existing `catch` logic runs, so a
hosted service that throws still leaves the ambient principal correctly
restored. The class gains no reference to `Tempest.Core.Plugins` or
`Tempest.Core.Identity`.

**`TempestHost` — the one real, non-null provider.** A closure keyed by
`Type`, reading the same collaborators `ModuleLifecycleManager`'s own hook
already uses:

```
Func<Type, IDisposable?> hostedServiceComponentScopeProvider = serviceType =>
{
    var principal = componentPrincipalRegistry.GetPrincipalFor(serviceType);
    return principal is not null ? currentComponentAccessor.BeginScope(principal) : null;
};
```

No `moduleId`-to-descriptor lookup step is needed, unlike the module-side
provider. `null` is returned for a genuine first-party hosted service, and
for a plugin's hosted service whose types never passed trust enforcement —
identically to the module case. This is `TD-51`'s second half, and it only
works because the recording loop above now records hosted-service types
into `componentPrincipalRegistry` at all.

**`IdentityService.EstablishCurrentPrincipal` — the dynamic gate.** Two
new optional trailing constructor parameters,
`ICurrentComponentAccessor? currentComponentAccessor = null` and
`IPermissionEvaluator? permissionEvaluator = null`, both defaulting to
`null` and both reproducing today's exact unconditional behaviour when
unresolved. The gate itself mirrors `NavigationService.Register`'s
established pattern exactly:

```
var registrant = _currentComponentAccessor?.Current;

if (!Plugins.PluginTrustPermission.IsFirstParty(registrant))
    _permissionEvaluator?.RequirePermission(registrant!, new Permission(Plugins.PluginCapability.IdentityEstablish));
```

`IsFirstParty(null)` is `true`, so a `null` accessor and a `null` current
component are treated identically, and the check is **skipped** — not
merely satisfied — for every first-party caller. A failing check throws
`PermissionDeniedException`, propagating uncaught.

**`ADR-0111` amendment, not a new ADR.** The Decision's static-enforcement
text was widened from "a discovered `IModule` implementer" to "a discovered
`IModule` or `BackgroundServices.IHostedService` implementer"; the
"Dynamic, at each call site" list gained
`IIdentityService.EstablishCurrentPrincipal`; a "Corrected, `WP 13.10B`"
Status-section note records the whole account, including the correction of
the now-superseded "third and final correction" claim. `WP 13.10C`
finalised and committed these edits.

**Execution shape.** Strict per-file ownership across three parallel
production agents — `PluginAssemblyLoader.cs`; `HostedServiceManager.cs`;
`IdentityService.cs` with `PluginCapability.cs` — with `TempestHost.cs`
integrated centrally, then three test-writing agents, deliberately
sequenced rather than parallelised to avoid a conflict on the shared
`DynamicPluginAssemblyBuilder.cs` fixture file. Two independent reviews
followed: an Adversarial Security review and an Architecture/API review.

## 6. Alternatives Considered

- **Give `HostedServiceManager` plugin awareness directly** — let it
  consult `IPluginComponentPrincipalRegistry` itself. Rejected: it would
  put a `Tempest.Core.Plugins` reference into
  `Tempest.Core.BackgroundServices`, which `ADR-0110`'s boundary
  deliberately keeps plugin-unaware, and it would diverge from
  `ModuleLifecycleManager`'s already-ratified generic-hook shape.
- **Key the hosted-service hook by string `Id`, matching
  `ModuleLifecycleManager` exactly.** Rejected: a hosted service has no
  `Id`; inventing one for symmetry would have added a concept to
  `BackgroundServices` purely to make two hooks look alike.
- **Add `IIdentityService` to `NeverEligibleServiceResolveTypes` instead of
  gating the method.** Rejected: `IIdentityService` is a legitimate,
  DI-public dependency that sample modules already take. Denylisting it
  would break honest consumers to stop one method, and would leave the
  method itself ungated for any other route to it. The denylist exists for
  concrete Host-authority types; the correct tool for a public method is a
  call-site gate.
- **Reuse an existing capability key rather than adding a sixth.**
  Rejected: no existing key means "may reassign the ambient process-wide
  principal", and overloading one would make the grant unauditable.
  `PluginCapability`'s own remarks already anticipate purely additive keys.
- **Make the two new `IdentityService` constructor parameters required.**
  Rejected: every DI container in this codebase requires every constructor
  parameter type to be independently resolvable, and `WP 13.2A`'s own
  retrospective records twenty-three fixtures needing update the last time
  this pattern was introduced. Optional and trailing, defaulting to
  today's behaviour, is the established convention here.
- **Guard only the `IHostedService` axis in the pre-resolution loop**, once
  the crash regression (§7) was found. Rejected: the `IModule` axis needed
  the identical guard, and a per-axis asymmetry is precisely the class of
  defect `TD-51` itself was. Both collections are iterated uniformly.
- **Fix the residual `RecordDenied` gap the crash fix exposed.** Deferred,
  not rejected — see §10 and §12. `WP 13.10C` disclosed it deliberately
  unfixed; `WP 13.11B` later closed it.

## 7. Why This Solution Was Chosen

Every one of the three fixes is a copy of a pattern already ratified,
already implemented, and already reviewed elsewhere in this same codebase.
That was the point. `WP 13.10A` had assessed both findings as closable
without new architecture, and the fastest way to make that assessment true
rather than aspirational is to write code that a reviewer can check by
diffing it against its own established sibling — `HasCompliantConstructor`
against itself on a second collection, `HostedServiceManager`'s hook
against `ModuleLifecycleManager`'s hook, `EstablishCurrentPrincipal`'s gate
against `NavigationService.Register`'s gate.

**The compounding regression, in full — the most important thing this Work
Package learned.** `DiscoverModuleTypes`' `WP 13.9.3` pre-resolution loop
originally iterated `currentModuleTypes` only. Once `HasCompliantConstructor`
was extended to also check `hostedServiceTypes`, an `IHostedService`-only
plugin whose constructor named a genuinely unresolvable parameter type
reached `HasCompliantConstructor`'s own `GetParameters()` call as the
**first** resolution attempt for that type — with no exception handling
anywhere in reach. `HasCompliantConstructor` throws nothing itself, and the
thrown `TypeLoadException`/`FileNotFoundException` is not a
`PluginException`, so `LoadPlugins`' own `catch (PluginException)` never
saw it. It propagated out of `LoadPlugins` and out of
`TempestHost.RunAsync` entirely: **a Host-wide crash, strictly worse than
the gap `TD-51` was closing**, and a direct violation of `ADR-0025`'s
guarantee that a plugin-scoped failure never becomes a platform-wide
outage.

It was found **twice, independently**. An `IModule`-only version of the
pre-resolution fix had already landed when a second reviewer reproduced the
identical gap for hosted services. And a **first attempted fix was wrong**:
it placed its `try`/`catch` one level too deep — around the per-parameter
loop body (`_ = parameter.ParameterType`) rather than around
`constructor.GetParameters()` itself. `RuntimeConstructorInfo.GetParameters()`
eagerly resolves every parameter's own signature the moment it is called,
so the exception is thrown from the loop *header*, and a `catch` inside the
body never fired for its own documented scenario. That was confirmed live
and corrected before landing.

The final shape iterates
`currentModuleTypes.Concat(currentHostedServiceTypes)` uniformly, wraps
`constructor.GetParameters()` itself, and converts
`TypeLoadException`/`FileNotFoundException`/`FileLoadException`/
`BadImageFormatException` into a `PluginTrustDeniedException` — isolating
the one plugin exactly like any other trust-check failure. It also
completes `WP 13.9.3`'s own original intent for the hosted-service axis:
forcing a hosted service's constructor-parameter types to resolve inside
the scan's diff window is what lets the scan discover a secondary assembly
reachable only through a hosted service's constructor signature.

The lesson is not "we made a mistake and fixed it". It is that **widening
the reach of a static check widens the reach of every side effect that
check performs** — and reflection's side effects are type loads, which
throw.

## 8. Architectural Principles

- **Reuse Before Invention** — three fixes, three existing patterns
  copied; no new principal type, no new permission type, no new exception
  type, no new dependency, no new ADR.
- **Zero Behavioural Change for Every Existing Actor** — every new
  constructor parameter is optional and trailing and reproduces today's
  behaviour when `null`; the `EstablishCurrentPrincipal` check is skipped,
  not satisfied, for `null`/First-Party ambient principals.
- **Fail Fast, Isolate, Don't Crash** — the crash regression was closed by
  converting an uncaught reflection exception into a
  `PluginTrustDeniedException`, the existing category-17 isolation path,
  rather than by suppressing it.
- **Host-Owned Collaborators Remain Structurally Unreachable** — the
  component-scope closure is constructed in `TempestHost` and captured;
  `HostedServiceManager` never sees `componentPrincipalRegistry` or
  `currentComponentAccessor`, only an opaque `Func<Type, IDisposable?>`.
- **Boundaries Stay Where the ADR Put Them** — `BackgroundServices` gains
  no plugin or identity awareness; `ADR-0110`'s plugin-unaware discovery
  boundary is untouched.
- **Correct the ADR in Place When the Decision Was Right and the Text Was
  Narrow** — a "Corrected" note, matching the pattern `WP 13.9.1`,
  `WP 13.9.3`, `WP 13.9.4`, and `WP 13.9.6` each set.
- **Disclose the Full Discovery History, Including Your Own Mistakes** —
  the regression, its double discovery, and the mis-placed first fix are
  recorded in `TD-51`'s Status cell, the Risks entry, `ADR-0111`'s
  correction note, the source comments, and the commit message.

## 10. Trade-offs

- **The residual `RecordDenied` gap was knowingly left open.** The
  "unresolvable constructor parameter type" denial path throws
  `PluginTrustDeniedException` from *inside* `DiscoverModuleTypes`, before
  `EnforceTrust` reaches either `RecordDenied` call site, so that specific
  type never enters `deniedTypeRegistry`. `WP 13.10C` disclosed this and
  deliberately did not fix it, characterising it as safely isolated by a
  second, independent construction attempt during Registration. That
  characterisation was later shown to be false for the `IModule` axis (see
  §12) — but at the time it was assessed as a low-severity,
  pre-existing-since-`WP 13.9.3` inefficiency that this Work Package merely
  widened the reach of.
- **`plugin.identity.establish` has a materially broader blast radius than
  every other v1 capability.** `EstablishCurrentPrincipal` accepts an
  arbitrary `identityId` with no ownership check **by design** (`ADR-0043`,
  no authentication), and the key is grantable to any tier above
  `UnsignedLocal` — including `VerifiedSigned`, not only `FirstParty`.
  Granting it to a signed third-party publisher is effectively full
  ambient-identity impersonation. `WP 13.10C` disclosed this as a
  governance note, not a code defect.
- **Two more optional constructor parameters on `IdentityService`, and one
  more on `HostedServiceManager`.** Binary-breaking, source-compatible.
  Acceptable here only because nothing in `v0.13.0` is packaged for
  external consumption — a fact `WP 13.11D` later re-confirmed across the
  whole release.
- **Every proof remains synthetic.** `src/Plugins/` is still empty; every
  test exercises dynamically-built, in-memory assemblies via
  `DynamicPluginAssemblyBuilder`.
- **The gate is still cooperative, not a sandbox** — unchanged from
  `ADR-0110`'s plainly-disclosed position. A reflective plugin willing to
  bypass its own declared trust is not defended against, and was never
  meant to be.

## 11. Common Mistakes

1. **Assuming that widening a static check's *input set* is a pure
   change.** It is not, when the check performs reflection. Extending
   `HasCompliantConstructor` to a second collection moved the first type
   load for those types to a call site with no exception handling — and
   turned a denied-plugin outcome into a Host crash. **Widening a check
   widens its side effects.**
2. **Placing a `try`/`catch` around the loop body when the loop *header*
   is what throws.** `constructor.GetParameters()` eagerly resolves every
   parameter's signature at the moment of the call, so
   `foreach (var parameter in constructor.GetParameters()) { try { ... } }`
   never catches an unresolvable parameter type. The first attempted fix
   made exactly this error and caught nothing for its own documented
   scenario.
3. **Assuming a `catch (PluginException)` upstream will contain a
   reflection failure.** `TypeLoadException`, `FileNotFoundException`,
   `FileLoadException`, and `BadImageFormatException` derive from none of
   this codebase's plugin exception types — so `LoadPlugins`' own handler
   does not see them, and they leave `TempestHost.RunAsync`.
4. **Assuming the component-scope hook can be invoked outside the existing
   `try`.** It must be inside, so the `using` block's implicit `finally`
   pops the scope *before* `HostedServiceManager`'s existing `catch` logic
   runs. Outside it, a throwing hosted service would leave the ambient
   principal established.
5. **Assuming `HostedServiceManager` should look up the plugin registry
   itself.** It must not — it has no plugin or identity awareness, and the
   hook is deliberately a `Func<Type, IDisposable?>` so that the only
   component that knows about plugins is `TempestHost`.
6. **Assuming the new capability key needed a ceiling entry.** It needed
   the opposite: deliberate *absence* from `UnsignedLocalCapabilityCeiling`
   is what makes it un-requestable at the lowest tier.
7. **Assuming a gate that is "satisfied" for first-party callers is the
   same as one that is skipped.** It is not — a satisfied check requires a
   resolvable `IPermissionEvaluator` and a non-null principal in every test
   fixture and every first-party flow. The established pattern here skips
   entirely on `IsFirstParty(registrant)`.

## 12. Future Evolution

- **`TD-51` was subsequently reopened, then closed again — this Work
  Package could not have known.** `WP 13.11A` re-examined the residual
  `RecordDenied` gap that `WP 13.10C` characterised as safely isolated,
  and found that characterisation **false for the `IModule` axis**: because
  the offending type never enters `deniedTypeRegistry`, `WP 13.9.6`'s own
  `isTypeExcluded: deniedTypeRegistry.IsDenied` Module Discovery filter
  never excludes it, and
  `ReflectionFrameworkDiscoveryService.CreateDescriptor`'s unguarded
  `type.GetConstructor(Type.EmptyTypes)` call then throws uncaught through
  `RunAsync` — a genuine Host crash reachable by a single, otherwise-inert
  `IModule` type at any trust tier with zero requested capabilities.
  `TD-51` moved Resolved → **Reopened**. The `IHostedService` axis was
  confirmed genuinely safe from that specific path, because
  `HostedServiceManager.StartServiceAsync`'s own generic `try`/`catch`
  isolates it.
- **`WP 13.11B` closed `TD-51` again**, by surfacing the
  unresolvable-constructor-parameter failure to `EnforceTrust` through a
  new `out PluginTrustDeniedException?` seam that records every discovered
  type via `RecordDenied` before throwing, allowing the fixed-point scan to
  run to completion, and by adding the same four-exception guard around
  `CreateDescriptor`. `WP 13.11C` reviewed that closure and corrected one
  factual claim in the register; `WP 13.11D` confirmed against real source
  that it remains closed.
- **`TD-52` remained closed.** A separate later item, `TD-56` (`WP 13.11D`,
  read-only, deliberately unfixed), records that a plugin's own
  *constructor* runs outside its component scope on both axes, so within
  that window this Work Package's `EstablishCurrentPrincipal` gate — along
  with every other capability gate — is skipped for a `VerifiedSigned` or
  `FirstParty` plugin. That is a defect of the scope-establishment
  mechanism, registered as its own item, not a reopening of `TD-52`.
- **Explicit governance sign-off before granting `plugin.identity.establish`
  to any third-party publisher** remains outstanding, as `WP 13.10C`
  disclosed.
- **A real, non-synthetic signed plugin** remains the unmet trigger for the
  whole mechanism, exactly as at `WP 13.2A`.

## 13. Key Takeaways

- **Extending a reflection-based check to a new set of types is a change to
  where type loads first happen, not just to what gets checked.** This is
  the whole regression in one sentence, and it generalises well beyond this
  codebase.
- **Reflection APIs resolve more eagerly than their call shape suggests.**
  `GetParameters()` resolves every parameter's signature when called, so
  the exception surfaces from the `foreach` header, not the body. A
  `try`/`catch` that looks correctly placed can catch nothing at all — and
  will pass review unless someone runs the scenario.
- **"Found independently twice" is a property worth engineering for.** The
  hosted-service half of this regression was reproduced by a second
  reviewer after the `IModule`-only fix had already landed. Parallel
  independent review is what turned a half-fix into a whole one.
- **The safest fix is the one a reviewer can verify by diffing it against
  its own sibling.** Three fixes, three existing patterns copied verbatim
  in shape — which is exactly why `WP 13.10C`'s four independent reviewers
  could converge cleanly on a bounded change.
- **A fix that closes a gap can widen a different, pre-existing one.**
  Extending the constructor check widened the reach of the `RecordDenied`
  gap from one discovery axis to two. It was disclosed rather than
  silently accepted — and the disclosure is precisely what let `WP 13.11A`
  find the crash that disclosure's own severity assessment had understated.
