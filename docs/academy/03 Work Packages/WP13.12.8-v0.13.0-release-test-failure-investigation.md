# WP 13.12.8 — v0.13.0 Release Test Failure Investigation

## 1. Introduction

`WP 13.12.8` investigated the single test failure that stopped
`WP 13.12.7`'s tag-triggered `release.yml` run (`32146823154`) at its
`Test (Release)` step. It is a **read-only investigation**: four parallel
read-only agents, no fix, no commit, no `src/` or `tests/` change. Its
verdict is that the failure is a **genuine intermittent test flake, not a
product defect** — and it discloses, rather than hides, that the flake
could not be reproduced locally.

## 2. Purpose

To establish, from evidence rather than plausibility, whether
`ObjectEditorViewTests.Save_RevisedContent_ActuallyAdvancesTheRealRevisionNumber`
failing with `Assert.True() Failure` on the `v0.13.0` tag indicated a
real defect in the revise path — which would have made `v0.13.0`'s
content unshippable — or a defect in the test's own waiting strategy,
which would not.

## 3. Background

`WP 13.12.7` pushed the `v0.13.0` tag (`15aedec` → `6089a218`) and
recorded the resulting failure precisely: `Tempest.Core.Tests` passed
2,341/2,341; `Tempest.Desktop.Tests` failed 1 of 221. `Package Release
build output`, `Resolve release notes` and `Publish GitHub Release` were
all skipped, so nothing was published.

The same commit had already passed CI on `main` (`32145226354`, all four
jobs green), and `WP 13.12.1`'s and `WP 13.12.4`'s local full regressions
had both returned 2,562/2,562 in Debug and Release — so the failing test
had a long record of passing on identical code.

`TD-46` is the project's existing precedent for exactly this shape of
failure: `ObjectEditorViewTests.cs`'s
`VerificationResultSection_RecordPass_ActuallyRecordsARealVerificationRecord`
used a fixed `Task.Delay(50)` to wait for an async update, was reliable
locally, and lost its race on a loaded GitHub Actions Windows runner on
its first-ever real execution there. It was confirmed flaky, not a
regression, on the grounds that the identical commit passed the same test
on a separate, concurrent CI run — and was resolved in `WP 11.4A` by a
bounded poll against live state.

## 4. The Problem

A test failure at a release gate has two readings with opposite
consequences. If the revise path is genuinely broken, `v0.13.0`'s content
must not ship. If the test's wait is broken, the content is fine and only
the harness needs correcting. Guessing in either direction is the failure
mode: declaring a flake to unblock a release is how real defects ship,
and declaring a defect on one red run is how correct releases get
abandoned.

The complication is that the obvious tie-breaker was unavailable — the
failure would not reproduce locally, so no amount of local re-running
could settle it. The verdict had to come from source analysis,
environment evidence and precedent, and had to say so.

## 5. The Design

This Work Package's design is the design of the investigation itself, not
of any change.

**Four parallel read-only agents, on separate questions.** Test/source;
concurrency and isolation; CI and release environment; verification and
reproduction. Each read only, none permitted to edit, so no agent's
conclusion could contaminate the tree the next agent read.

**Agent 1 — test and source.** Establish what the test actually waits
for. `src/Tempest.Desktop/Editors/ObjectEditorView.cs:199` subscribes the
Save button as `_saveButton.Click += async (_, _) => await
OnSaveAsync().ConfigureAwait(true);` — an `async void`-shaped click
subscriber whose task the test cannot observe. The test raises
`Button.ClickEvent` and then, at the time of the failure, waited a fixed
`Task.Delay(50)` before re-reading the repository once. Meanwhile
`EngineeringDocumentStore.ReviseAsync`
(`src/Tempest.Core/EngineeringData/EngineeringDocumentStore.cs:128`)
performs **real disk I/O**: it acquires an `AsyncKeyedLock` on the
document id, does one read (`ReadDocumentAsync`), then two writes
(`WriteRevisionAsync`, then `WriteDocumentAsync`), each ultimately
`File.WriteAllTextAsync` (`src/Tempest.Core/Persistence/PersistenceStore.cs:113`),
every step `ConfigureAwait(false)` and therefore continuing on the thread
pool. A fixed 50 ms delay is a **race against that chain, not a wait for
it**.

**Agent 2 — concurrency and isolation.** Rule in or out the project's
known cross-test interference. `TD-34` was **explicitly excluded**: it
concerns `CompositeLogSinkTests` in `Tempest.Core.Tests`, a different
assembly running in a separate process, and its mechanism is a
process-global `Console.Out`/`Console.Error` redirection race — whereas
this assertion reads a revision number and never touches console text.

**Agent 3 — CI and release environment.** The decisive evidence. Pushing
the tag triggered **two** workflows on the **same SHA** — `ci.yml` and
`release.yml` — on the same `windows-2022` image and in the same minute.
`ci.yml` **passed**; `release.yml` **failed**. The `dotnet test`
invocations were character-identical, and the failing run was roughly
**51% slower** end to end. Same code, same image, same minute, opposite
outcomes, the loser being the slower: a timing signature, not a
deterministic defect.

**Agent 4 — verification and reproduction.** Attempt to reproduce, and
report the attempt truthfully whatever it showed. It **failed to
reproduce**: 15/15 passes in isolation, 2/2 in the full suite, and 8/8
even with the delay set to `0`. That last result is the strongest form of
the negative — the mechanism could not be forced even by removing the
wait entirely on this hardware.

**Convergence, then precedent.** The four lines were reconciled centrally
against `TD-46`, which matches **exactly**: same file, same idiom, same
"quiet locally, red under CI load" behaviour, same class of assertion —
and already convicted and fixed once, for a sibling test, by a remedy
that was never generalised to this method.

## 6. Alternatives Considered

**Re-run the release workflow and see.** Rejected. A green re-run would
have removed the failure without explaining it, and would have destroyed
the concurrent-run comparison that made the diagnosis possible.

**Declare a product defect and halt on the revise path.** Rejected on
evidence. `Tempest.Core.Tests` passed 2,341/2,341 in the very same
failing run — including the store's own coverage — and the concurrent
`ci.yml` run passed the failing Desktop test itself on identical
binaries. A genuine defect in `ReviseAsync` would not be selective by
runner minute.

**Fix the test as part of this Work Package.** Rejected by the
commissioning instruction: this was read-only. Diagnosis and remediation
were kept in separate Work Packages so the finding could be reviewed on
its own merits rather than arriving pre-implemented.

**Blame `TD-34`.** Rejected, and rejected explicitly rather than by
silence — it is the project's best-known flake and would have been the
convenient answer. Different assembly, separate process, wrong mechanism.

**Increase the delay to 200 ms and move on.** Rejected as the same defect
with a larger constant; `TD-46`'s remedy exists precisely because a
bigger guess is still a guess.

**Suppress the verdict pending a local repro.** Rejected. Reproduction is
evidence when it succeeds; its absence on a quiet, single-tenant machine
is weak counter-evidence against a load-dependent race, and waiting
indefinitely would have left the release undiagnosed.

## 7. Why This Solution Was Chosen

Because the question was decidable without reproducing the failure, and
the decisive evidence was already sitting in the run history. Two
workflows on one SHA, one image, one minute, with identical commands and
opposite results, is a controlled experiment the tag push happened to run
for free. Source analysis explained *how* a race was possible; the
concurrent runs proved that timing, not code, separated pass from fail;
`TD-46` supplied a matching, already-adjudicated precedent in the same
file. Parallel read-only agents were used so those four independent lines
were developed without any one of them steering the others.

## 8. Architectural Principles

- **An investigation is read-only until its verdict is reviewed.** Fixing
  while diagnosing hides which evidence actually mattered.
- **A fixed delay is not a synchronisation primitive.** Wait on the
  condition; bound the wait.
- **Prefer natural experiments already present in the evidence.** The
  same-SHA concurrent runs beat any local rerun.
- **Exclude the familiar suspect explicitly.** `TD-34` was named and
  ruled out, so nobody has to re-litigate it.
- **A failed reproduction is a result, and it is reported.** Confidence
  is stated at the level the evidence supports, never above it.
- **Precedent in the same file is evidence.** `TD-46` was not an analogy;
  it was the same idiom, previously convicted.

## 9. Benefits

The release's blocking question was answered definitively: `v0.13.0`'s
**product code is not implicated**. That let the project move to a
narrow, test-only correction rather than reopening the revise path, and
it kept the tagged tree's `src/` content credible.

The failure now has a mechanism, not a label. The `async void` click
subscriber, the unobservable task, the `AsyncKeyedLock`, the two
`File.WriteAllTextAsync` writes and the `ConfigureAwait(false)`
continuations are each named with a location, so the diagnosis can be
checked rather than believed — an account carried directly into the
remediating change's own comment and commit message. `TD-46`'s scope is
now understood as under-applied: a remedy adopted for one test in a file
that contains the same idiom elsewhere.

## 10. Trade-offs

The verdict rests on source analysis, environment comparison and
precedent — **not** on a reproduction. That is a genuinely weaker
foundation than a caught repro, and this Work Package says so rather than
implying otherwise. If a future failure of the same test proves
deterministic under some condition not tested here, the conclusion must
be revisited. Read-only discipline also meant the flake remained live in
the suite throughout, so any Work Package verifying in between could have
hit it.

Four parallel agents cost more than one investigation, and three of the
four lines of enquiry were confirmatory rather than decisive. That
redundancy is what made the exclusion of `TD-34` and the failed
reproduction trustworthy instead of convenient.

## 11. Common Mistakes

- **Concluding "flake" because a re-run went green.** Green on re-run is
  consistent with a flake *and* with a load-dependent real defect; it
  discriminates nothing on its own.
- **Reaching for the project's famous flake.** `TD-34` is the wrong
  assembly, the wrong process, and the wrong mechanism here.
- **Reading a failed local repro as disproof.** The mechanism is
  load-dependent by hypothesis; a quiet machine is where it is *expected*
  to pass, which is exactly what 15/15, 2/2 and 8/8 showed.
- **Waiting on an `async void` handler by sleeping.** The task is
  unobservable by construction; no constant is correct.
- **Fixing one instance of an idiom and not recording the rest.**
  `TD-46`'s remedy sat one screen away from the failing method for two
  releases.

## 12. Future Evolution

Remediation was left to a separate Work Package, which replaced the fixed
delay with the bounded, condition-based wait `TD-46` had already
established for the sibling test in the same file; the current text of
`tests/Tempest.Desktop.Tests/ObjectEditorViewTests.cs` reflects that
change and carries the diagnosis inline. The broader question this
investigation opens — the remaining fixed waits in
`Tempest.Desktop.Tests` sharing the idiom — was deliberately not answered
here, and the remediation that followed was deliberately not generalised.
Whether to sweep them is an open decision, not an omission.

## 13. Key Takeaways

- The best evidence for a timing bug is often two runs you already have,
  not a run you are about to force.
- Say what you could not reproduce. A verdict with a disclosed weakness
  is worth more than a confident one with a hidden gap.
- Name the suspect you ruled out, and why — otherwise the next
  investigator starts from zero.
- A remedy adopted once in a file is a claim about the whole idiom in
  that file; leaving siblings untouched is a decision that should be
  recorded, and here it was not, until this failure recorded it.
- Read-only means read-only. The value of this Work Package is that its
  conclusion could be reviewed before anything moved.
