# Project Timeline — Milestones, Deliverables, and the Work Behind Each Date

## 1. Introduction

`f9fd9e0` gave `Milestone` and `Deliverable` — real, durable, rehydratable
domain types since `WP 8.2C` — a surface for the first time: measured
directly, there was not a single construction of either type in `src/`
outside the sample harness, which no longer ships (`TD-75`). A
pre-`v0.14.0` engineering-body-of-work row.

## 2. Purpose

To close the Timeline project area, tracked by `TD-81`, by listing
milestones in date order with the deliverables and contributing tasks
against each.

## 3. Background

Tasks have been able to `contributeTo` a Milestone or Deliverable since
the Project Tasks work package. Work reaches a milestone by either of two
routes and the register keeps the difference: a task `contributesTo` a
Milestone or a Deliverable directly, or reaches a Milestone indirectly
through a Deliverable that already knows its own `MilestoneId` — a read
rather than a second link.

## 4. The Problem

The Timeline area was Declared and tracked; nothing in the product ever
created a milestone and no surface ever showed one, despite the domain
model already supporting both.

## 5. The Design

A deliverable is parented to its milestone, not to the project — the
structure this creates is transitively a project deliverable, because it
is the structure the domain holds rather than a presentation-only
grouping; no `ProjectId` was added, for the fifth time this release. The
restraint is the load-bearing decision: the brief asked for the state and
date information the model already supports, so no domain change was
made. `Milestone` keeps its immutable `TargetDate` and the canonical
lifecycle; there is no "achieved" state to read, so the register does not
invent one — it states only what is knowable: the date has passed; work
against it is or is not outstanding; nothing was ever linked to it — and
keeps "past with outstanding work" distinct from "past with nothing
linked", because those are different failures a review needs to tell
apart. Creation is included, because without it the surface would be
empty forever, the hollow-capability defect class `TD-102` was raised to
close; rescheduling is not, since `TargetDate` has no setter and the
absence is disclosed rather than faked. Dates are typed and parsed exactly
as `yyyy-MM-dd` in the invariant culture, because a date a project commits
to must mean the same thing on every machine that opens the file.

## 6. Alternatives Considered

Inventing an "achieved" state for a milestone the domain model does not
support — rejected explicitly: "there is no 'achieved' state to read, so
the register does not invent one."

## 7. Why This Solution Was Chosen

Because the restraint (no domain change, no invented state, no
rescheduling) is what keeps the surface honest about what the model
actually knows, rather than presenting inferred or fabricated
information as recorded fact.

## 8. Architectural Principles

A surface should state only what its underlying model can actually know,
distinguishing "past and unresolved" from "past and never engaged with"
rather than collapsing both into a single, less informative signal.

## 9. Benefits

Six mutations run, six killed: indirect contributions dropped, project
isolation removed, the two past-date states collapsed together, finished
work still counted as open, chronological ordering replaced by name order,
and the descriptor reverted to Declared. All 20 new tests passed first
time. Core 2845/2845, Desktop 332/332, Debug and Release, 0 warnings, 0
errors, with `TreatWarningsAsErrors=true`.

## 10. Trade-offs

Explicitly not built: no Gantt, no time axis, no scheduling engine, no
dependency graph, no critical path, no rollup of dates from tasks to
milestones. `TD-81` stays Partially resolved: Commercial, Resources,
Knowledge, Administration and Gantt/scheduling proper remain.

## 11. Common Mistakes

Inferring a milestone's "achieved" status from date-plus-linked-work
signals the domain does not actually track — the row deliberately avoids
this by stating only the three facts the model can support (date passed;
outstanding work exists or does not; anything was ever linked or was
not).

## 12. Future Evolution

`ProjectArea.Timeline` moves to Implemented and drops its `TD-81`
reference, leaving Reports and Settings as the only project areas still
Declared — the next candidates for this same treatment in a future
release.

## 13. Key Takeaways

- Do not invent a state the underlying domain model has no field to
  support, even when a surface would be more satisfying with it.
- Distinguish "past with nothing engaged" from "past with something still
  unresolved" — collapsing them loses information a reviewer needs.
- Parse committed dates in a fixed, invariant format — a date a project
  commits to must read identically regardless of the machine opening it.
