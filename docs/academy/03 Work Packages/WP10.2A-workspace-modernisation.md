# `WP 10.2A` — Workspace Modernisation

## 1. Introduction

`v0.10.0`'s fifth Work Package — the first UI-focused implementation
pass since `WP 10.1A`, and the first to require a genuine, disclosed
Workspace contract extension (`ADR-0096`) purely to deliver its own
explicitly-required capabilities honestly.

## 2. Purpose

To transform `Tempest.Desktop`'s own working-but-minimal shell into a
modern, professional engineering application UI across six named areas
(Project Explorer, Property Inspector, Document Area, Status Bar,
Navigation, Visual Design), plus Accessibility and Performance, while
preserving every existing Engineering capability unchanged.

## 3. Background

`WP 10.0B` delivered a real, working, but visually and functionally
minimal shell; `WP 10.1A` gave it a real, live-data Cockpit. Neither
Work Package built context menus, filtering, breadcrumbs, collapsible
sections, or a multi-segment Status Bar — all six real disciplines'
own `Rename*Command`/`Delete*Command` pairs had compiled and been
tested since their own Work Packages, but no interactive surface had
ever dispatched one against an arbitrary selected object.

## 4. The Problem

Deliver "inline rename" and "editable controls where appropriate" as
real, working capabilities — not decorative UI — while honouring "No
Workspace contract redesign unless genuinely required."

## 5. The Design

`IWorkspaceManager` gained five new, additive members (`ADR-0096`),
mirroring `RegisterFacetProvider`'s own `ADR-0082` shape; every
discipline's own already-existing Rename/Delete command became a
registered factory, reusing `CommandHandlerTable`'s own existing
runtime-type-keyed dispatch. Around that real dispatch path: a
filterable, breadcrumbed, multi-select Project Explorer with a real
context menu and inline rename; a collapsible, sectioned Property
Inspector with a real editable Name field and two new, honestly-scoped
summary sections; pinned, actively-highlighted Document Area tabs; a
six-segment Status Bar; five keyboard shortcuts; a shared
`DesignTokens` spacing/typography system.

## 6. Alternatives Considered

See `23-workspace-modernisation.md` §6 — decorative rename/delete UI;
a generic untyped dispatch method; exposing `CommandHandlerTable`
directly to `Tempest.Desktop`. All rejected in favour of the narrower,
precedented extension actually applied.

## 7. Why This Solution Was Chosen

Satisfied every constraint at once: genuinely required, minimally
scoped (five additive members), and precedented (`ADR-0082`'s own
pattern, applied a second time).

## 8. Architectural Principles

A "future context-menu action" named four Work Packages ago is still a
real requirement when the time comes; "never fabricate" applies to
interactive affordances, not only displayed data; a second use of an
extensibility pattern confirms it as this platform's own general idiom
rather than a one-off.

## 10. Trade-offs

Drag/drop is prepared, not implemented — reparenting needs a second,
larger, not-yet-uniform contract decision this Work Package's own
proportionate scope did not justify. Two disciplines are honestly
incomplete (Requirements' rename, Calculations' synthetic Kind).
"Current Project"/Notifications remain honest Status Bar placeholders.

## 11. Common Mistakes

Treating "modernise the UI" as purely visual, missing that two required
capabilities cannot be delivered honestly without real dispatch;
building a second, parallel dispatch mechanism instead of reusing the
proven one; extracting facets into a new summary section without
removing them from their own original group — a real defect this Work
Package's own Engineering Review found and fixed before sign-off.

## 12. Future Evolution

A uniform `Move*Command` shape across all six disciplines would let a
future Work Package complete drag/drop into real reparenting.
`ADR-0095` (floating/multi-monitor panels) remains the next reserved
contract question, explicitly out of this Work Package's own "Do NOT
implement" list.

## 13. Key Takeaways

A UI modernisation Work Package that takes its own "never fabricate"
discipline seriously will sometimes need a small, real capability
extension underneath the visual work — the correct response is to
scope it as narrowly and precedentedly as the actual requirement
demands, not to avoid it or over-build it.

## Architectural Debt Assessment

No new Technical Debt item registered. One genuine, low-severity
implementation defect (Property Inspector Lifecycle-section
duplication) was found by this Work Package's own Engineering Review
and fixed in place, before any commit, proven by a dedicated regression
test — never reaching a state that would have warranted a Technical
Debt entry. Two disciplines' own honestly-incomplete Rename/Delete
coverage (Requirements, Calculations' synthetic Kind) are documented
directly in `ADR-0096` and the Implementation Report, not registered
separately — both are permanent, correct, disclosed absences (no
`Rename*Command` exists for Requirements by design; `"CalculationTemplate"`
is never a Domain object by design), not defects with a future fix
trigger.

## Observations

- **A doc comment written four Work Packages earlier ("a future
  context-menu action") turned out to be an accurate, actionable
  specification, not merely a note.** `WP 9.0A`'s own disclosed
  `createDefault`-omission comment named exactly the extension this
  Work Package built — reading existing code's own remarks carefully
  before designing anything new surfaced the correct, minimal solution
  directly.
- **The same "never fabricate" discipline that shapes what data a
  Cockpit shows also shapes what a UI control is allowed to do.** An
  editable-looking text box with no real dispatch behind it is the
  interactive equivalent of a fabricated placeholder number — this
  Work Package treated it as such, and built the real dispatch path
  rather than deferring it.
- **A Review that traces claims against real source, not the
  Implementation Report's own description, finds real defects.** The
  Property Inspector duplication was caught only because the
  Engineering Review re-derived the control flow by hand rather than
  trusting the Implementation Report's own "never duplicated" claim —
  worth repeating as a standing discipline, not a one-off diligence.
