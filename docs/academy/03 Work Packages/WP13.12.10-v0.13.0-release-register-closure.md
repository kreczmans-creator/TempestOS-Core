# WP 13.12.10 — v0.13.0 Release Register Closure

## 1. Introduction

`WP 13.12.10` added the `v0.13.0` row to
`docs/governance/Delivery/Release Register.md`. It is a
**documentation-only** Work Package: one file, `+7/−3` (`ea3fe07`), zero
`src/` and zero `tests/` files changed, no tag created, amended or
repointed, `VERSION` unchanged at `0.13.0`, and `Release Notes.md`
untouched.

Its whole difficulty lies in a single wording decision: what status the
row should carry for a version that was genuinely tagged and genuinely
merged, but never published.

## 2. Purpose

To close the governance health-check failure that `WP 13.12.7`'s tag push
opened, and to do so with a row that states what is true rather than one
that merely satisfies the checker.

## 3. Background

`governance-healthcheck.ps1` cross-references real git tags against the
Release Register's Entries table. The moment `WP 13.12.7` pushed
`v0.13.0`, it reported:

```
[FAIL] Release Register matches git tags (11 tags, 12 register versions)
       - Git tag(s) with no Release Register row: v0.13.0
```

This is the same check that first surfaced `v0.12.0`'s own omission
during `WP 13.0.0`, closed by `WP 13.0.0A`'s Release Register
Reconciliation — the register has a documented history of going stale
across releases, which is precisely why `FCR-0005`'s health-check tooling
exists.

`WP 13.12.9` had already declined to fix this: it recorded the failure in
its commit message as an unrelated, out-of-scope item and left it for
separate release-state work. This Work Package is that work.

## 4. The Problem

The checker's demand is trivial — add a row. The genuine problem is that
every prior status the register carries is wrong for this case.

`v0.11.0` and `v0.12.0` are recorded as **"Released, published, merged to
`main`"**. `v0.13.0` is not that. Per the commit record, the
tag-triggered `release.yml` run `32146823154` failed at its
`Test (Release)` step, so `Package Release build output`, `Resolve
release notes` and `Publish GitHub Release` were all **skipped** — no
GitHub Release object, no `TempestOS-v0.13.0.zip`, no engineering-harness
asset exists for this version.

Nor is it "In progress — not yet tagged", the status `WP 11.9.0`
introduced for `v0.11.0`: the tag exists, is annotated, is pushed, and
resolves to a real merge commit on `main`.

So the register faced a version that is simultaneously *more* complete
than its "in progress" category and *less* complete than its "released"
one — and a totals line whose only counter was "confirmed released."

## 5. The Design

**A new, honestly-named status.** The row reads **"Tagged and merged to
`main`, 2026-08-18 — GitHub Release not published."** The distinction is
load-bearing, not cosmetic: anyone reading the register to find a
downloadable `v0.13.0` artefact must learn from the row itself that none
exists.

**A totals line that adds a category rather than inflating a count.**
12 → 13 versions referenced, decomposed as: 11 confirmed released, 1
tagged and merged but not published (`v0.13.0`), 1 Unknown (`v0.2.0`).
The "confirmed released" figure is deliberately left at 11.

**A row that records what is genuinely verifiable.** Per the commit
message: annotated tag object `15aedec` resolving to `6089a218`, verified
locally and against the remote's own `refs/tags/v0.13.0^{}` peel; a real
merge commit (parents `13a6ce3` + `30b0f45`) created under explicit
Product Approval with no squash and no rebase, its tree byte-identical to
branch tip `30b0f45`; and all four GitHub Actions jobs green on `main` at
that exact pre-tag commit (run `32145226354`) — the
`Engineering Readiness Review Architecture.md` §2.3 verification
satisfied for the first time this release.

**A row that also records the failure and its diagnosis.** It cites
`WP 13.12.8`'s finding of a genuine intermittent flake matching the
`TD-46` idiom, and `WP 13.12.9`'s test-only remediation — so the reason
publication did not happen is inside the register, not only in a commit
message.

**`Last Reviewed` prepended, never overwritten.** The register's
established chain convention is followed: the new `WP 13.12.10` entry is
prepended and `WP 13.0.0A`'s demoted to "Previously reviewed," preserving
the whole review lineage back to `v0.6.0`.

## 6. Alternatives Considered

**Record it as "Released, published, merged to `main`" like its
predecessors.** Rejected outright. It would have made the register state
something false about an artefact's existence, in exactly the field a
reader consults to find that artefact.

**Leave the row out and suppress or waive the health-check failure.**
Rejected — the check is the tooling `FCR-0005` exists to provide, and
teaching the project to route around it would forfeit the very
capability that caught `v0.12.0`'s omission.

**Retry `release.yml`, or re-tag, so the row could honestly say
"published."** Rejected and out of scope: Engineering Governance §7.4
forbids moving or recreating a pushed tag, and this Work Package touched
no tag and created no Release. The disposition of that question was left
to `WP 13.13.0`.

**Reuse the "In progress" status `WP 11.9.0` introduced.** Rejected — it
understates the position. The tag is real and merged; only publication is
missing.

**Increment "confirmed released" to 12 and footnote the caveat.**
Rejected — a totals line is read at a glance far more often than its
footnote.

## 7. Why This Solution Was Chosen

Because a register's value is entirely in its accuracy, and the cheapest
way to destroy it is to let a status label mean "the checker passed"
rather than "this is what happened." A new category costs one line of
prose; a wrong label costs the register's credibility on every future
read.

It also preserves the release's own measurability. Documentation-only,
one file, `+7/−3`, no historical row rewritten — so the combined delta
over the `v0.13.0` tagged tree remains something `WP 13.13.0` could state
exactly.

## 8. Architectural Principles

- **A register records what happened, not what would be tidy.**
- **Add a category before overloading an existing one.** Statuses are a
  vocabulary; stretching one to cover a genuinely new case makes every
  prior use ambiguous.
- **Never rewrite history to satisfy a checker.** No prior row was
  touched.
- **Append to the review chain, do not replace it** — the `Last
  Reviewed` lineage is itself evidence of how often this register has
  drifted.
- **Governance tooling is a signal to answer, not an obstacle to
  silence.**

## 9. Benefits

- `governance-healthcheck.ps1` restored to its pre-tag-push baseline: 7
  passed, 1 warned (the pre-existing `v0.9.0`/`v0.10.0` informational
  warning), 0 failed, exit 0.
- The register now carries the release's full factual position —
  tag object, resolved commit, merge parents, the green pre-tag CI run,
  and the failed `release.yml` run — in one place.
- A reader looking for a `v0.13.0` download learns immediately that none
  exists, and why.
- The precedent for future partial releases is set and named.

## 10. Trade-offs

- **The register now carries three status vocabularies** (released,
  in progress, tagged-but-unpublished, plus `v0.2.0`'s Unknown). More
  expressive, but no longer a two-valued field.
- **The row is long.** It carries diagnosis and CI-run identifiers, which
  is dense to read but is the reason it does not depend on a commit
  message surviving.
- **The health-check pass is now a weaker signal** than it looks: it
  confirms every tag has a row, not that every tag is published.
- **A documentation-only fix cannot make `v0.13.0` publishable.** The
  underlying release state was left untouched, deliberately, for
  `WP 13.13.0` to dispose of.

## 11. Common Mistakes

- Writing the status the checker will accept rather than the status that
  is true.
- Silently rewriting a historical row while "already in the file."
- Overwriting `Last Reviewed` instead of prepending to it, losing the
  drift history the field exists to expose.
- Bumping a totals count without deciding which sub-count it belongs to.
- Bundling the release-disposition decision into the register update —
  they are different authorities, and §9 does not let the engineering
  tier settle the second.

## 12. Future Evolution

If `v0.13.1` is ever cut and published, `v0.13.0`'s row stays exactly as
written — an immutable historical record of a tag that was valid and
never published — and the new release gets its own row. The record shows
this is precisely what followed: `WP 13.13.1` added `v0.13.1` as a
fourth category, **In preparation**, and left `v0.13.0`'s row untouched.

The health check could plausibly be extended to verify that a row marked
"published" corresponds to an actual GitHub Release, closing the gap this
Work Package's own status distinction had to close by hand. The record is
silent on whether such an extension has been proposed.

## 13. Key Takeaways

- A status label is an interface; widening its meaning silently breaks
  every reader.
- Making a checker green is the by-product of a correct record, never the
  goal.
- Prepend review history; never overwrite it.
- Documentation-only changes still deserve a stated, checkable footprint
  — one file, `+7/−3`, zero `src/`, zero `tests/`.
