# WP 15.0D — Ribbon Responsive Scrollbar Fix

## 1. Introduction

`WP 15.0D` covers `0451369` (merged `d9488b2`), the last of `Tempest.
Desktop`'s known post-`v0.14.0` UI defects: the Ribbon's horizontal
scrollbar never rendered at compact window widths (~1000px), even though
its command groups genuinely overflowed. Retroactively numbered and
retrospected by `WP 15.1A`.

## 2. Purpose

Close the one defect `WP 15.0C`'s own Ribbon/Property Inspector work left
open: at a narrow enough width that a discipline's command groups
genuinely overflow, nothing told the user scrolling was even possible.

## 3. Background

The initial diagnosis (a layout-chain width-propagation problem from
`MainWindow` → `topStack` → Ribbon) was investigated and disproven:
headless diagnostics showed the Ribbon's `ScrollViewer` already correctly
received bounded width and correctly computed `Extent > Viewport` before
any fix.

## 4. The Problem

**Root cause, found only after several disproven hypotheses**: a
`ScrollViewer`'s `Auto` horizontal scrollbar only ever occupies room its
own final arranged size already has *slack* for — it never grows itself
purely to make room for its own scrollbar. The Ribbon's horizontal
`ScrollViewer` sits inside a vertical `StackPanel` sized to its own
content, so nothing ever gave it more height than the button rows alone
need. At a width narrow enough that a discipline's command groups
genuinely overflowed, `Auto` correctly determined a scrollbar was needed
but had nowhere to draw it — the groups past that width were clipped in
total silence.

Disproven along the way: `AllowAutoHide`/`ScrollBarVisibility.Visible`
(no effect on the underlying starvation); a `DockPanel` in place of the
outer `StackPanel` (reverted — did not fix it, since `StackPanel` already
gives its stacking-direction child unbounded height in measure, so height
starvation was never a `StackPanel`-vs-`DockPanel` question). A stale
build of the diagnostic launcher (a `ProjectReference` caching gap) cost
two further iterations by making working fixes look like no-ops.

## 5. The Design

Reserve one scrollbar's worth of height on the Ribbon's `ScrollViewer`,
read once after the first real layout pass from the button row's own
measured height (window-width-independent) plus `DesignTokens.SpaceXl` —
an existing spacing token, not a new magic number — via a one-shot
`LayoutUpdated` handler.

## 6. Alternatives Considered

A hardcoded total height for the `ScrollViewer` — rejected: wastes space
at normal width where nothing overflows, and does not track content that
grows or shrinks.

## 7. Why This Solution Was Chosen

Content-driven and window-width-independent: costs nothing when no
scrollbar is ever needed, and is exactly what lets `Auto` show one the
moment it is.

## 8. Architectural Principles

No Ribbon restructuring, no hardcoded width, normal-width layout and
compact-mode nav-rail/header behaviour both explicitly preserved and
verified unchanged.

## 9. Benefits

The Ribbon's overflow affordance is now visible exactly when content
overflows, in both themes, at the width it was originally reported
missing from.

## 10. Trade-offs

None disclosed beyond the investigation cost already covered in §4.

## 11. Common Mistakes

**Trusting a rebuilt `ProjectReference` without checking output
timestamps.** `dotnet build --incremental`'s default behaviour can leave
a stale referenced assembly in a throwaway launcher's own output
directory, silently invalidating a diagnostic session's results.

## 12. Future Evolution

Unlike `WP 15.0A`–`C`, this Work Package's own commit message already
records real verification detail in full (root cause, disproven
hypotheses, Xvfb evidence, both themes, both widths) — this retrospective
is a faithful compression of that record, not a reconstruction from a
thinner trace. Retroactively numbered and indexed by `WP 15.1A`.

## 13. Key Takeaways

- `Auto` scrollbar visibility never grows its own container to make room
  for itself — a starvation bug in this shape needs an explicit
  reservation, not a visibility-mode change.
- Disproving a plausible hypothesis with a real headless diagnostic is
  progress, even when the fix itself comes later.
- Verify a diagnostic tool's own build freshness before trusting a
  negative result from it.
