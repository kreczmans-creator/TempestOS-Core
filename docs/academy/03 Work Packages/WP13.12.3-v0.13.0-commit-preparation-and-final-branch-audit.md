# WP 13.12.3 — v0.13.0 Commit Preparation & Final Branch Audit

## 1. Introduction

`WP 13.12.3` audited the `v0.13.0` documentation closure before it was
allowed to become history. `WP 13.12.0`–`WP 13.12.2` had left a large
uncommitted documentation set in the working tree; this Work Package ran
**six read-only audits** across it — Architecture/ADR, Security/Trust,
Implementation/API, Verification (test discipline), Governance/
Documentation, and Release/branch readiness — resolved what they found,
and committed the result as `f58b475`.

It changed no `src/` and no `tests/` file, left `VERSION` at `0.12.0`,
and pushed, tagged, merged and released nothing.

## 2. Purpose

To make the commit of a three-Work-Package documentation pass an audited
event rather than an act of faith — and, specifically, to answer one
governance question before the commit rather than after it: did
`WP 13.12.2`'s amendment of `ADR-0110` require architectural approval?

## 3. Background

`WP 13.12.0` closed the Academy-completeness Release Blocking finding by
writing sixteen missing retrospectives. `WP 13.12.1` re-ran the
Engineering Readiness Review mechanically under `ADR-0106` §4.
`WP 13.12.2` produced the superseding Engineering Release Report and the
Release Notes, and corrected a named set of documentation-drift
findings — including striking `ADR-0110`'s Consequences bullet asserting
that Module Discovery, Registration and Lifecycle were "completely
unchanged", false since `WP 13.9.6`.

None of that had been committed. All three passes had written into the
same working tree, and the third had corrected registers whose
arithmetic the first two had moved.

## 4. The Problem

A documentation pass that corrects other documents' figures is itself a
producer of figures — and therefore a producer of defects. The set
awaiting commit contained counts, deltas, tallies and baselines that had
been computed at different moments against different tree states, with
nothing having checked them against the tree they would actually be
committed alongside.

Second, `ADR-0110` had been amended in place. Engineering Governance §5
governs when an ADR is *required*; the repository's practice for
amending an existing one is carried by precedent rather than by an
explicit rule, so the question of whether the amendment needed
architectural approval had a real answer that had to be found, not
assumed.

## 5. The Design

The design here is the design **of the audit** — six disciplines, all
read-only, each with its own evidence and its own verdict.

**Read-only by construction.** No audit was permitted to edit. Findings
were reported as findings; every resolution was applied afterwards,
centrally, so an auditor could never quietly repair what it was meant to
report.

**Six disciplines, not one sweep.** Architecture/ADR owned the
`ADR-0110` approval question. Security/Trust checked the trust-boundary
claims. Implementation/API checked assertions about code against the
code. Verification owned the test-discipline evidence. Governance/
Documentation owned register arithmetic. Release/branch readiness owned
what the branch could and could not clear. Splitting them meant a defect
had to survive a discipline that was specifically looking for its kind.

**Adjudicate the ADR question against the governing text and the
strongest available precedent.** The amendment altered `ADR-0110`'s
**Consequences** only; its **Decision** text was untouched. The
`ADR-0111` precedent was found to be *stronger still*: three of that
ADR's five in-file corrections had altered **Decision** text, and none
had been pre-approved. On that basis, the amendment was determined
**not** to require architectural approval.

**Resolve before commit, not after.** Three of the six audits returned
**FAIL**. Every defect they named was fixed in the working tree and the
whole set committed as one, so the committed record never contained a
known-wrong figure.

**Name what is deliberately not tidied.** Pre-existing debt inside the
audited files was recorded as preserved, not silently corrected.

## 6. Alternatives Considered

**Commit first, audit the commit.** Rejected — the defects were in
figures a reader would take as authoritative. Committing them would have
put wrong counts into the permanent record and required a second
correcting commit to undo, which is exactly the pattern `WP 13.12.0` had
just spent sixteen retrospectives unwinding.

**Let the auditors fix what they find.** Rejected — an auditor with
write access has an incentive to under-report, and six concurrent
writers over one working tree reintroduces the same-file collision risk
`WP 13.12.2` had deliberately designed out.

**Treat the `ADR-0110` amendment as requiring approval, to be safe.**
Rejected as false caution. Manufacturing an approval requirement that
the governing text does not impose, and that the `ADR-0111` precedent
positively contradicts, would set a convention future Work Packages
would inherit without anyone having decided it.

**Fix the surrounding pre-existing debt while in the files.** Rejected —
the same instruction and the same principle `WP 13.12.2` applied: a
release whose footprint absorbs unrelated historical debt cannot be
measured.

## 7. Why This Solution Was Chosen

Because the defects were real and self-inflicted. All **eight** were
introduced by the documentation pass itself, per the `WorkPackages.md`
row and `f58b475`'s own message:

- a wrong test baseline — `2,290` corrected to the true `2,255`, net
  `+307`;
- wrong Academy deltas — `104` → `132` and `169` → `197`, not the
  HEAD-time `113`/`178`;
- "Ten further Work Packages" introducing a list of **seventeen**;
- a false `Ownership Matrix` claim that `ICurrentComponentAccessor` is
  registered as interface only — it is registered under **both**
  concrete type and interface (`TempestHost.cs:520-521`);
- stale Academy Register arithmetic — `114/129` → `117/132`;
- a stale `Documentation Register` count — `113` → `132`;
- an Engineering Release Report Definition-of-Done tally reading "Eleven
  satisfied" against a twelve-row table containing ten;
- an unexplained "19 Disclosed" against Part B's 28, restated as
  deduplicated.

Alongside these, `Plugin Manifest Architecture.md`'s three surviving
"Unchanged" rows — the very document `ADR-0110`'s struck bullet had
cited — were corrected, and the release name aligned to the established
**"Trust & Deployment Hardening"**.

## 8. Architectural Principles

- **Auditors do not hold the pen.** Read-only findings, central
  resolution.
- **A precedent is evidence, and the stronger precedent wins.**
  `ADR-0111`'s unapproved *Decision*-text corrections outrank a
  Consequences-only amendment.
- **Never commit a figure you have not recomputed against the tree you
  are committing.**
- **Disclose deliberate non-action.** Preserved debt is listed by name.
- **Test serialisation is a correctness property.** The audit confirmed
  no parallelism increase, no `xunit.runner.json`, no
  `CollectionBehavior`, no `maxParallelThreads`, and 64 guarded classes
  unchanged.
- **A documentation Work Package touches no code.**

## 9. Benefits

The committed `v0.13.0` documentation record is internally consistent:
its test baseline, Academy deltas, register arithmetic, Ownership Matrix
claim, DoD tally and disclosure count all agree with the tree they
describe. The `ADR-0110` amendment carries a recorded, reasoned
determination rather than an implicit one.

Verification recorded with the commit: Debug and Release builds
**0 Warnings / 0 Errors**; full regression **2,562/2,562** in both
configurations; `governance-healthcheck.ps1` **7 passed, 1 warned**
(pre-existing), **0 failed**; Academy **28/28**, verified 0 missing and
0 duplicates.

## 10. Trade-offs

Six audits over one uncommitted set is expensive for a change that adds
no code, and it delayed the commit. The counterweight is that eight
defects were caught in the working tree, where fixing them costs one
edit, rather than in history, where fixing them costs a commit and an
explanation.

Determining that no architectural approval was needed relies on
precedent rather than an explicit written rule. That determination is
recorded with its reasoning so a future reader can disagree on the
evidence; the record is silent on whether the rule itself should be
written down.

## 11. Common Mistakes

- **Trusting a figure because the pass that produced it was careful.**
  The baseline, deltas, arithmetic and tallies were all produced by a
  deliberate, well-run documentation pass — and all were wrong.
- **Computing a delta at HEAD-time and reporting it at commit-time.**
  The `113`/`178` values were true when taken and false when written.
- **Reading a registration site partially.** `ICurrentComponentAccessor`
  is registered twice; a search that stopped at the first hit produced a
  confident false claim.
- **Assuming an in-file ADR amendment needs approval because it feels
  like it should.** The governing text and the `ADR-0111` precedent both
  say otherwise.

## 12. Future Evolution

The verdict remained **NOT READY** on one Release Blocking finding:
`Build & Test` and `CI Gate` have never run on `main` at a pre-tag
commit (`Engineering Readiness Review Architecture.md` §2.3). That
finding is structural and unclearable on a feature branch. Absent it,
§4's derivation reaches row 2 — **ACCEPT WITH OBSERVATIONS**. Clearing
it is `WP 13.12.4`'s `VERSION` bump followed by `WP 13.12.5`'s PR,
green `main` CI, and merge.

Preserved deliberately, not tidied: `Feature Register.md` and
`Traceability Matrix.md` staleness since `WP 5.3`; the Academy
Register's 15-row deficit; `TD-42`, `TD-43`, `TD-45`; the
`v0.9.0`/`v0.10.0` health-check warning; and the frozen roadmap table's
rows.

## 13. Key Takeaways

- The pass that corrects other people's numbers will produce its own;
  audit it before it becomes history.
- Auditors that can edit will report less than auditors that cannot.
- A governance question with a determinate answer should be answered
  from the text and the precedent, not resolved by adding ceremony.
- Splitting an audit into disciplines is what makes a defect have to get
  past someone who was looking for it.
