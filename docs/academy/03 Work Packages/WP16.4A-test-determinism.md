# WP 16.4A — Test Determinism

## 1. Introduction

`WP 16.4A` closed four Technical Debt rows in two parts. Part 1
(`1dbb8ab`) gave `CompositeLogSink` an injected error writer (`TD-34`),
removed the one remaining fixed `Task.Delay` wait in
`Tempest.Desktop.Tests` (`TD-119`), added real `MainWindow`-level
resize coverage (`TD-83`), and along the way fixed a Core-side
temp-directory leak that was `TD-120`'s own defect shape recurring on
the other side of the codebase, plus an environment dependency in
`SampleSeparationTests` that a nested git worktree could silently
break. Part 2 (`30f5cb2`) gave the Desktop test host a real Skia
rendering subsystem so image decoding is genuinely verified (`TD-100`).
Branch `feature/v0.16.0-wp16.4a-test-determinism`, then
`feature/v0.16.0-wp16.4a-td100-image-decode`, both cut from
`feature/v0.16.0`.

## 2. Purpose

`v0.16.0 Release Plan.md` states this Work Package's own objective
verbatim: "three consecutive clean full-suite runs, both configurations,
are routine rather than lucky." Under `D-021` (Proposed), a v1.0
release candidate needs a test suite whose full-run result does not
depend on execution order, wall-clock timing, or the machine it happens
to run on — the property every item in this Work Package removes one
instance of.

## 3. Background

Four named debts, each a distinct mechanism. `TD-34`:
`CompositeLogSink.Write`'s per-sink failure handler wrote directly to
the static, process-wide `Console.Error`, racing any concurrently-run
test class that redirected the same stream without joining the
`"Console output capture"` collection every other such class already
used — a flake this project's own narrative record had disclosed since
`WP 6.3` and only actually captured once, in `WP 9.9.0`'s own
verification pass. `TD-119`: the last of an original 52 fixed
`Task.Delay` waits in `Tempest.Desktop.Tests`, the other 51 already
converted by `WP-Z4`. `TD-83`: no test drove a real window resize
through `MainWindow` itself — only `WorkspaceLayoutHostTests` against
`WorkspaceLayoutHost` directly. `TD-100`: the headless Avalonia
platform's own stub image decoder reported every image as 1×1 and
accepted non-image bytes as valid, so no test had ever actually proven
image decoding worked.

## 4. The Problem

Each item's root cause required confirmation by reading, not inference
from the register's own prose. `TD-34`'s register text estimated
"fifty-odd" guarded classes; a direct `grep`/cross-check at this Work
Package's own base found exactly one unguarded class,
`LoggerTests` — the fact sheet's own claim that `ConsoleLogSinkTests`
was "already fixed" was verified true by direct read, not assumed.
`TD-119`'s safety required reading `RibbonView.DeleteAsync` directly:
the declined-delete path's `await confirm(message)` resolves against an
already-completed `Task.FromResult(false)`, so it never yields, and the
entire handler chain completes synchronously inside `RaiseEvent` itself
— there was never anything running after `RaiseEvent` returned for a
fixed delay to wait for. `TD-100`'s fix required decompiling
`Avalonia.Headless` 11.3.20 with `ilspycmd`, because no source browsing
was available offline, to confirm that `UseHeadlessDrawing = false`
actually leaves whichever rendering subsystem was already registered in
place rather than overwriting it with the stub.

A fifth, unregistered problem surfaced during this Work Package's own
work rather than from any prior disclosure: `SampleSeparationTests`'
`FindRepositoryRoot()`/`EnumerateProjectFiles` walk had no way to prune
a nested git worktree's own `.claude/worktrees/**` checkouts from its
`SearchOption.AllDirectories` enumeration — invisible in this worktree
(which has no nested worktrees of its own) but reproducible by
deliberately constructing one, which this Work Package did, to prove
both the failure and the fix against a real, if synthetic, instance of
the defect.

## 5. The Design

**`TD-34`.** `CompositeLogSink` gained an additive constructor overload
taking an optional `TextWriter? errorWriter`, defaulting to
`Console.Error` captured once at construction, so every existing
one-argument call site keeps compiling and behaving identically — a
`grep` confirmed zero `src/` call sites needed updating, since
`CompositeLogSink` is not yet constructed anywhere in `src/`.
`CompositeLogSinkTests` was rewritten to inject a private `StringWriter`
and assert the failure message actually landed there — a positive
assertion, replacing an "it did not throw" check that a silently
swallowed failure would also have passed. `LoggerTests` joined the
`"Console output capture"` collection.

**`TD-119`.** The delay was removed permanently, with a comment at the
call site naming `RibbonView.cs`'s synchronous-completion mechanism and
`TD-119` itself, verified across 30 consecutive runs (20 before the
comment, 10 after) with zero failures.

**`TD-83`.** A new `MainWindowResizeTests.cs` builds a real
`WorkspaceHost` and a real `MainWindow`, resizes it at three widths —
1920, 1280, and the product's own real `MinWidth = 960` (discovered
empirically; the plan's requested ~900 is below what `MainWindow`
itself ever lays out at) — and asserts, from real arranged bounds, both
the shell's compact threshold and the docking layout's `TD-70` floor.
The test was **mutation-tested, not merely passed**: commenting out
`_navigationRail.SetCompact(compact)` inside `MainWindow`'s own
`SizeChanged` handler made it fail exactly at the 960px assertion,
confirmed and reverted.

**Core-side temp-directory leak.** Four test classes each implement
`IDisposable`, deleting their own isolated persistence root once per
`[Fact]`/`[Theory]` — chosen over the Desktop precedent's shared
`[CollectionDefinition]` specifically because these four classes run
concurrently with each other today and grouping them into one
collection would have serialised four classes that do not need it. A
mechanical `sed` rewrite of the 65 call sites caught and fixed its own
recursion bug (a call inside the new wrapper's own body rewritten to
call itself) before it could reach a committed state.

**`SampleSeparationTests`.** A manual, stack-based directory walk
prunes any dot-directory or `bin`/`obj` before it can be enumerated —
proven against a deliberately constructed fake nested worktree that
reproduced the original failure, then passed once the fix was applied,
then failed again once the fix was temporarily reverted, isolating the
fix as the actual cause rather than an incidental change.

**`TD-100`.** `TestAppBuilder.cs` now calls `.UseSkia()` before
`.UseHeadless(new AvaloniaHeadlessPlatformOptions { UseHeadlessDrawing = false })` —
Skia registers the real rendering subsystem first, and the headless
platform, told not to overwrite it, leaves it in place. Two tests lost
their stub-detecting conditional branches entirely:
`AnImage_IsASinglePage_AtItsOwnPixelSize` now asserts the real 4×3 pixel
size and that all twelve pixels read back non-white, unconditionally;
`BytesThatAreNotAnImage_AreReportedAsUndecodable` now asserts
`DocumentRenderException` unconditionally.

## 6. Alternatives Considered

**Generalise `TD-34`'s fix by joining `CompositeLogSinkTests` to the
existing collection, rather than injecting a writer.** Available and
smaller, but rejected: the register's own remedy column asked for the
dependency to be removed, not merely serialised around, and a joined
collection would still leave `CompositeLogSink` itself dependent on the
static stream for any future consumer that forgot to join.

**Lengthen `TD-119`'s delay instead of removing it, or generalise the
fix to a shared bounded-poll helper.** Neither was pursued — the delay
was proven to protect nothing (the handler completes before `RaiseEvent`
returns), so lengthening it would only have made a no-op wait slower.

**A second, narrower test assembly for `TD-100`'s Skia change, rather
than enabling it assembly-wide.** Investigated directly by decompiling
`Avalonia.Headless.XUnit` and confirming its `AppBuilder`
entry-point attribute is assembly-scoped with no per-collection
override available. The measured cost — a ~40% suite duration
increase, under the ~50% threshold the governing instruction set as the
trigger for a narrower design — did not justify the `.csproj` addition
a second assembly would require, itself outside this Work Package's own
file boundary.

**Fix `TD-100` inside this Work Package's original scope, rather than
deferring it.** The Release Plan's own acceptance line names `TD-100`
alongside `TD-34` and `TD-83` for Part 1. Part 1 explicitly deferred it:
item 7 of its own governing instruction forbade any `.csproj` edit, and
`WP 16.5B` was bumping Avalonia versions concurrently — a
rendering-capable host is exactly the kind of change that would have
collided with an in-flight version bump. This is a disclosed deviation
from the plan's own acceptance line, resolved by a Part 2 branch cut
after `WP 16.5B`'s own merge rather than silently reconciled inside
Part 1.

## 7. Why This Solution Was Chosen

Each fix targets the actual dependency a test had on something
environment-specific — a static stream, a fixed clock duration, a stub
decoder, an unbounded directory walk — rather than a symptom of it.
Removing `CompositeLogSink`'s dependency on `Console.Error` entirely is
stronger than serialising around it, because it also protects every
future consumer that forgets to join the collection. Mutation-testing
`TD-83`'s new test, rather than trusting that it passed, is what turns
"a test exists" into "a test that would actually catch the regression
it claims to guard against."

## 8. Architectural Principles

- **A test suite whose full-run result depends on machine, timing, or
  order is untrustworthy in the same way a suite that fails at random
  is** — `TD-100`'s own framing makes this explicit: a stub decoder that
  passes the same way every time, for a reason unrelated to the code
  under test, is exactly as untrustworthy under `D-021`'s "routine
  rather than lucky" bar as a flake, only silent instead of loud.
- **Prove a fix would catch the regression it claims to guard against,
  not merely that it currently passes** — mutation-testing `TD-83`'s new
  test is the concrete instance of this principle in this Work Package.
- **Verify a root-cause claim by reading the actual code path, not by
  trusting the register's own prose** — the `TD-34` guarded-class count
  and the `TD-119` synchronous-completion argument were both confirmed
  this way, and both corrected a detail the existing record had
  slightly wrong.
- **Reconstruct a failure deliberately when the real environment cannot
  reproduce it**, rather than leave a fix unverified — the fake nested
  worktree built to reproduce `SampleSeparationTests`' own failure mode
  is this Work Package's clearest instance.

## 9. Benefits

- `TD-34`, `TD-83`, `TD-100`, and `TD-119` are all Resolved in the
  Technical Debt Register.
- Three consecutive clean full-suite runs, Release configuration: Core
  3,090/3,090 three times, Desktop 413/413 three times (Part 1); Desktop
  413/413 three times again after Part 2's Skia change, with the same
  pass count, confirming the rendering change altered no test's
  pass/fail outcome.
- A Core-side temp-directory leak, not itself a named register row,
  found and closed under this Work Package's own "test determinism"
  remit before it could accumulate the way `TD-120`'s Desktop-side
  sibling already had.
- `SampleSeparationTests`' own environment dependency on the absence of
  nested worktrees is closed — a real hazard for exactly the kind of
  multi-agent, multi-worktree development this repository now runs.

## 10. Trade-offs — what "determinism, verified locally" is and is not worth

**The Release Plan's own acceptance line asked for the full suite run
five times in CI, in both configurations, on a temporary matrix.** This
Work Package delivered three consecutive clean local runs, Release
configuration only (Debug was built clean but not run three times, by
its own governing instruction's scope). The report discloses this
directly, in its own words: the CI matrix "is CI work this local
session cannot perform without pushing, which this Work Package's own
instruction forbids... left for whoever opens the PR from this branch."
This is not a minor omission — GitHub Actions on this account has been
unable to obtain a runner at all since 2026-09-04 22:34 UTC (`WP 16.0B`'s
own Integration Report discloses the same outage independently), so no
Work Package on this branch has been able to satisfy a CI-run
acceptance criterion literally since that time, and none of them can
until the outage resolves. `docs/releases/v0.16.0/WorkPackages.md`'s own
row for `WP 16.4A` reads simply "**Complete**" — with the resolved
`TD-34`/`TD-83`/`TD-100`/`TD-119` named, but no caveat that the plan's
own five-run CI matrix was never executed, on this branch or any other,
because there has been no CI to execute it on.

Three clean local runs are real evidence against a specific, narrow
class of nondeterminism — the mechanisms this Work Package's own fixes
actually address (a shared static stream, a fixed-duration race, a
stub decoder, an unbounded directory walk). They are not evidence
against nondeterminism that only manifests on a shared, loaded CI
runner under real parallel load — which is precisely the failure mode
`WP 13.12.9`'s own retrospective already documents for this exact test
suite: a flake that reproduced zero times in 25 local attempts and
still failed a real tag-triggered release run. "Determinism, verified
locally" is worth exactly what its own verification method can
observe, and no more; the CI matrix this Work Package could not run
existed specifically to observe what local runs cannot.

- `TD-100`'s fix costs the Desktop suite roughly 40% more wall-clock
  time — a real, measured, and disclosed price for verifying image
  decoding is real rather than assumed.
- The generic per-test `IDisposable` pattern chosen for the Core-side
  temp-directory leak is a second, independent cleanup mechanism from
  `WP 15.2A`'s own `[CollectionDefinition]` pattern for the Desktop
  side — a deliberate, disclosed divergence rather than reused code,
  because the two sets of test classes have genuinely different
  parallelism needs.

## 11. Common Mistakes

- Treating three clean local runs as proof a flake mechanism is fully
  closed, when the specific evidence the release plan itself asked for
  (a five-run CI matrix, both configurations) was never obtained, for a
  reason outside this Work Package's control.
- Writing a `WorkPackages.md` status of "Complete" without a pointer to
  the CI-unavailability caveat the Work Package's own report discloses
  in detail — a reader of the summary row alone would not learn that
  the acceptance criterion's own strongest evidence was never gathered.
- Trusting a register's own descriptive prose ("fifty-odd" guarded
  classes) as a precise count rather than re-deriving it directly.
- Assuming a passing test proves a fix works, rather than
  mutation-testing it to confirm it would fail if the fix regressed.

## 12. Future Evolution

The GitHub Actions runner outage this Work Package's own local-only
verification had to work around is not this Work Package's to resolve,
and nothing in this Work Package's own record commits any later one to
resolving it either — it is an account-level infrastructure condition,
disclosed here and in `WP 16.0B`'s Integration Report, that any
Work Package on this branch attempting a CI-gated acceptance criterion
will need to account for until it lifts. `WP 16.4B` inherits `TD-69`'s
container-level default-parameter-value gap directly from `WP 16.3B`'s
own disclosure, not from this Work Package, but the two Work Packages'
shared release wave means both land expecting the same container
limitation to be fixed once, properly, rather than worked around twice.

## 13. Key Takeaways

- Local verification and CI verification prove different things; a
  Work Package that can only obtain the first should say so plainly in
  its own status line, not only in its report's own fine print.
- A test that mutation-tests its own claim (deliberately breaking the
  production code and confirming the test then fails) is worth more
  than one that has only ever been observed to pass.
- Reconstruct a failure deliberately, with a synthetic instance if the
  real environment cannot reproduce it, rather than leave a fix's
  effect unverified.
- An infrastructure outage that blocks one Work Package's acceptance
  criterion will block every subsequent Work Package's identical
  criterion until it is disclosed as a standing condition, not
  rediscovered fresh each time.

## Closure addendum — the acceptance evidence was obtained (2026-09-05)

The retrospective above is left as written, because its lesson is about
working honestly under an evidence gap and that lesson does not survive
being edited after the gap closed. The gap has since closed, and the
record needs the outcome as well as the lesson.

The repository was made public, which restored hosted-runner minutes. The
candidate was frozen on a branch of its own — `release/v0.16.0-rc` at
`d7d3f3b` — because the workflow's `concurrency` group is
`ci-<workflow>-<ref>` with `cancel-in-progress: true`: runs sharing a ref
cancel each other. Dispatched on the working branch, each release-
documentation commit would have killed the run in flight, which is
exactly what runs 192, 193 and 194 each did to their predecessor. The
five-run matrix then ran and passed **five for five**: runs 195, 197, 199,
201 and 202, all `workflow_dispatch`, all on that one SHA, every job green
in each — `Build & Test (Release)`, `Build & Test (Debug)`,
`Governance Health Check`, `CI Gate`, and the advisory
`Linux Launch Smoke`. No retries, no re-run of a failed job. Evidence
table: `WP16.9.0 Engineering Release Report.md` §4.1.

Two things worth keeping from how it ended:

- **The reviewer who refused 16/16 local runs was right.** Not because
  the local runs found anything — they did not, and the CI matrix did not
  either. Being right about evidence is not the same as being right about
  the outcome, and the discipline only means something when the evidence
  eventually agrees with you.
- **Once runners returned, the obstacle was not flakiness — it was the
  pipeline's own cancellation rule.** Three consecutive runs (192, 193,
  194) were cancelled by the next push rather than failing on their
  merits, and `new-release.ps1` correctly refuses to treat `cancelled` as
  green. Giving the candidate a dedicated ref is what made five
  *consecutive* runs obtainable at all — a technique this release had to
  discover, and the thing to reach for first next time a release needs
  repeated runs on one immutable commit.
