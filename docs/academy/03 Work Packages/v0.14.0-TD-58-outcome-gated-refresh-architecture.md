# TD-58 — Outcome-Gated Refresh Architecture

## 1. Introduction

`6135c7f` closed `TD-58` by giving every Desktop `View`'s `ActionCompleted`
event an `ActionOutcome` (`Succeeded`, `WorkspaceChanged`) instead of a bare
success flag, so a subscriber can finally tell "the command ran" apart
from "the workspace actually changed" — and stop rebuilding surfaces that
did not need it. A pre-`v0.14.0` engineering-body-of-work row; see the
naming rule stated in this set's "architecture audit becomes tracked
debt" article.

## 2. Purpose

To stop redundant Desktop rebuilds: every `RibbonView` command click tore
down and rebuilt the entire ribbon tab tree just to update a five-item
"Recently Used" row, and every `ActionCompleted` fan-out reloaded the full
Project Explorer and rebuilt the full Cockpit unconditionally — including
for pure refusals and failed commands, always with a Success-severity
toast.

## 3. Background

The defect was not one bug but a pattern repeated across every subscriber
of a Desktop-wide event: `MainWindow`'s ribbon handler, the
`WorkspaceViewCoordinator` explorer/inspector/editor handlers, the
`UndoRedoCoordinator`, and the Command Palette all treated "a command
completed" as "the workspace changed", because the event carried nothing
that could tell them otherwise. The Cockpit's "Favourite Projects" open
double-rebuilt all cards through two parallel paths. Mutating flows that
*should* have refreshed did not: macro runs and palette-invoked commands
refreshed no Explorer; a deleted object stayed selected with Delete/Rename
still enabled; `BackgroundTaskRunner.Changed` and the platform-notification
toast bridge had no live subscriber at all.

## 4. The Problem

A refusal ("needs a selected object first") or a failed command toasted as
a success and triggered the same full rebuild as a real mutation, while
several genuinely mutating paths triggered none. The UI was doing the most
expensive possible thing on every click, in the wrong direction as often
as the right one.

## 5. The Design

Every `ActionCompleted` event now carries an `ActionOutcome`: subscribers
report severity honestly and refresh dependents only when the workspace
actually changed. `RecordRecent` updates the per-tab "Recently Used" row
in place, so tab instances and keyboard focus survive a click that used to
rebuild the whole tree, with a single enablement pass instead of two. The
favourite-open inline `Refresh()` was removed, since the navigate path
already refreshes. `WorkspaceManager.DeleteObjectAsync` clears a deleted
current selection, so every delete surface converges on one place instead
of each remembering to do it. Macro and palette successes now reload
Explorer and Cockpit. `BackgroundTaskRunner.Changed` drives the Output
panel. The toast bridge is subscribed on `INotificationDispatcher` — the
channel producers actually publish through — with UI-thread marshalling.

## 6. Alternatives Considered

None recorded beyond the shape delivered; the fix follows directly from
naming the missing distinction (outcome versus completion) rather than
proposing a different rebuild strategy.

## 7. Why This Solution Was Chosen

Because the actual defect was a missing piece of information, not a wrong
algorithm. Every consumer already knew what to do with "did the workspace
change" — none of them had ever been told the answer.

## 8. Architectural Principles

A Desktop-wide event contract should carry enough information for every
subscriber to make its own correct decision, rather than each subscriber
guessing from the event's mere occurrence.

## 9. Benefits

No more full-ribbon rebuild for a five-item row update; no more
Success-toasted refusals; no more stale selection surviving a delete; the
Cockpit and Explorer actually refresh after a macro run or a palette
command, which they did not before.

## 10. Trade-offs

Remaining refresh-architecture debt — an O(everything) Cockpit rebuild
internally, and editor-tab staleness on external mutation — is deliberately
not folded into this closure and is tracked separately as `TD-66`.

## 11. Common Mistakes

Treating "a command completed" and "the workspace changed" as the same
fact, which is what every one of the affected subscribers had been doing
independently, in slightly different ways, none of them correct.

## 12. Future Evolution

`WP-D1`, in the later remediation programme, consolidates the pattern this
row establishes — status-bar/toast/history/gated-refresh — into one
implementation, `ActionOutcomeReporter`, rather than the seven hand-written
copies this row's convention still allowed.

## 13. Key Takeaways

- A shared event that only says "it happened" forces every subscriber to
  assume the worst (or the best) case identically and usually wrongly.
- Fixing the same defect in seven places at once is a sign the defect is
  in the contract, not in the seven places.
- Consolidation into one implementation is a later, separate decision
  (`WP-D1`) — this row establishes the convention, not the single
  implementation of it.
