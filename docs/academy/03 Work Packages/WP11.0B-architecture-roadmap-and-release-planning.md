# WP 11.0B — v1.0 Architecture Roadmap & Release Planning

## 1. Introduction

`WP 11.0B` (commit `e8cbec9`, joint with `WP 11.0A`) turns `WP 11.0A`'s
ten findings into a scoped, sequenced, estimated engineering roadmap
from `v0.11.0` to a first public `v1.0.0`, in this project's own
Work Package/WBS format. Planning only — no code, ADR, or architecture
was modified. Its sole deliverable is `docs/releases/v0.11.0/WP11.0B
Architecture Roadmap.md`.

This retrospective is written retrospectively under `WP 16.2B`, grounded
strictly in that document and in `WorkPackages.md`'s own `WP 11.0B` row.

## 2. Purpose

Decide what "`v1.0`" means for TempestOS, categorise `WP 11.0A`'s ten
findings against that definition, and sequence the resulting Work
Packages across releases — without inventing calendar dates this
project has no velocity data to justify.

## 3. Background

`WP 11.0A` found zero Critical issues but three real gaps standing
between the platform and a confident `v1.0`: no CI/CD, a
composition-root growth problem in the newest UI layer, and an
undecided question about whether the console shell remains a real
product surface. This roadmap is also the direct continuation of
"Programme F" — a Platform Hardening programme `WP7.2A Recommended
Programme.md` (`v0.7.0`) had already identified and deliberately
deferred, correctly, because none of its triggers (plugin trust,
REST auth, governance tooling) had fired yet.

## 4. The Problem

Without an explicit `v1.0` scope definition, every subsequent roadmap
decision has nothing to be judged against. Without categorising
`WP 11.0A`'s findings by that definition, there is no principled way to
decide what belongs in `v0.11.0` versus `v0.12.0` versus indefinitely
deferred. And one specific item — `FCR-0005`, governance health-check
tooling — had already been deferred correctly six times by `WP7.2A`'s
own "no demonstrated need yet" discipline; this roadmap had to decide,
with real evidence, whether a seventh recurrence changed that.

## 5. The Design

**Definition of `v1.0`** ("Definition 2"): a commercially credible,
single-user or small-trusted-team, locally-trusted desktop engineering
platform covering the six shipped Engineering Disciplines, explicitly
excluding third-party plugin support and REST exposure beyond a trusted
local network. This definition does not add new discipline breadth
beyond what `v0.10.0` already shipped — deliberately left to the
Product Owner, not assumed here.

**Finding categorisation**: `R-1` (CI/CD) and `A-2` (presentation
strategy) and the `A-5` mechanical fix are Must Complete Before `v1.0`;
`A-1` (composition-root decomposition) and the `A-6` vocabulary safety
net are Strongly Recommended; `A-3`/`A-4` (plugin trust, REST auth/TLS)
are Post-`v1.0` Technical Debt, gated on a real trigger that has not
fired; `A-7`/`A-8`/`A-9` are low-priority watch items.

**The `FCR-0005` reprioritisation**: `WP7.2A`'s own text already named
this pattern (governance/documentation drift) as recurring, raised to
High priority by `WP 7.1F`, reconfirmed by `WP 7.4.0`;
`PROJECT_STATUS.md` had already counted six recurrences before this
review began; `WP 11.0A` independently found a seventh (the stale
Governance Index ADR count) without having read either prior note.
Seven independent discoveries of the identical failure mode moved
`FCR-0005` from perpetually-deferred to `WP 11.1B` (later delivered, in
substance, by `WP 11.2A` — see that retrospective). No other Future
Capability or Technical Debt item was reprioritised ahead of its own
registered trigger.

**Recommended sequence**: `v0.11.0` (Release Engineering & Architecture
Governance) → `v0.12.0` (Desktop Composition & Domain Vocabulary
Hardening) → `v1.0.0`, three releases, skipping a conditional `v0.13.0`
(Trust & Deployment Hardening) entirely unless the Product Owner commits
`v1.0` scope to third-party plugins or non-local REST — a fallback path
this roadmap also names explicitly.

## 6. Alternatives Considered

Reprioritising every other deferred Future Capability alongside
`FCR-0005` was considered and rejected — `TD-38`, `TD-41`, `FCR-0073`,
`FCR-0056` are all real, already-tracked candidates, but none traces to
a `WP 11.0A` finding or a comparable seven-recurrence evidence base;
absorbing them here would violate the same "no demonstrated need"
discipline this roadmap otherwise applies consistently.

## 7. Why This Solution Was Chosen

Evidence-gated reprioritisation, applied consistently in both
directions: `FCR-0005` moves forward because seven independent
recurrences is real, demonstrated need; `FCR-0001`/`FCR-0003`/`FCR-0004`
stay deferred because their own triggers (a real plugin author, a real
non-local deployment need) still have not fired. The roadmap does not
treat "this would be useful eventually" as sufficient — it requires the
same evidentiary bar this project already applies via Security
Principle 7 everywhere else.

## 8. Architectural Principles

No ADR, production file, or architecture document was modified —
planning is not architecture. The roadmap explicitly notes none of
`WP 11.0A`'s ten findings requires revisiting a foundational decision;
every Work Package it scopes is additive.

## 9. Benefits

A defensible, evidence-traced release sequence exists where none did
before. `FCR-0005`'s reprioritisation directly produces `WP 11.2A`'s
governance health-check tool three Work Packages later. The `v1.0`
definition this document proposes becomes, five releases later, the
literal text `D-021` (`WP 16.0A`) cites as the proposed governing scope
of `v1.0.0` — this roadmap's own §1 is not merely historical; it is
still load-bearing at the time of this retrospective.

## 10. Trade-offs

The roadmap deliberately commits to no calendar dates, which is honest
about this project having no velocity data to extrapolate from, but
also means no reader can answer "when" from this document alone — only
"in what order." The `v0.13.0` conditional branch adds real complexity
to the roadmap's own presentation (two paths, not one) in exchange for
not pre-empting a Product Owner decision (`WP 11.2A`, later folded into
`WP 11.3A`/`WP 11.3B`) that had not yet been made.

## 11. Common Mistakes

**Assuming the roadmap's own predicted Work Package numbering will hold
exactly.** It didn't: `WorkPackages.md`'s own Status section discloses a
double divergence — `WP 11.1B` and `WP 11.2A` were commissioned under
different scopes than this roadmap predicted for those exact slots. The
roadmap's own §7 had already named itself "a recommendation, not an
approval" — the divergence is that distinction being exercised, not a
defect in the roadmap.

## 12. Future Evolution

Realised roadmap items, in order: `WP 11.1A` (CI/CD, `R-1`); `WP 11.2A`
(governance tooling, in substance `FCR-0005`); `WP 11.3A`/`WP 11.3B`
(presentation strategy, `A-2`, commissioned two Work Package slots after
first predicted); `WP 12.0A`/`WP 12.0B` (composition-root decomposition,
`A-1`); `WP 12.1A`/`WP 12.1B` (vocabulary safety net, `A-6`). The
conditional `v0.13.0` branch was, in fact, opened later in the
project's real history for unrelated reasons (plugin trust hardening) —
outside this retrospective's own sourced evidence to characterise
further. This roadmap's own `v1.0` definition (§1) is, at the time of
this writing, `D-021` in `WP16.0A v0.16.0 Scope Decision.md` —
**Proposed**, awaiting Product Owner approval, not yet ratified into the
Decision Register.

## 13. Key Takeaways

- A roadmap's own predictions are recommendations, not commitments —
  name that explicitly, and a later divergence from them is not a
  defect.
- Reprioritise deferred work only on real, accumulating evidence (seven
  independent recurrences, not a hunch) — and hold every other deferred
  item to the identical bar, in both directions.
- A well-evidenced planning document can remain load-bearing for
  releases afterward — this one is still cited, verbatim, as a proposed
  governing decision five releases later.
