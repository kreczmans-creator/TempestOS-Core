# Quotations, Change Orders and the Project Lifecycle

**Release:** `v0.19.1` release candidate (`release/v0.19.1`, head `94998b9`)
and the `v0.20.0` release candidate (`release/v0.20.0`, head `3ce8f20`) —
neither merged to `main` · **Work Package(s):** `WP 19.5A`–`19.5D`, `WP
19.10H`, `WP 19.10R`, `WP 20.10E` · **Debt:** `TD-179` · **Decision:**
`ADR-0152` and its `WP 20.10E` addendum · **Code:** `Tempest.Core.Quotations`,
`Tempest.Core.Projects` (`ProjectLifecycleService`, `ProjectArchival`),
`Tempest.Core.Tasks`, `Tempest.Core.Commands` (`CommandBinding.Mutates`,
`ArchivedProjectCommandGuard`), `Tempest.Workspace.Quotations`,
`Tempest.Desktop.Views.ProjectQuoteView`/`QuotesView`/`ProjectSignOffView`,
`Tempest.Desktop.Quotations.QuotationSheetRenderer`

**In plain terms.** A quotation is the document a consultancy sends a client
before work starts: what will be done, in what pieces, and for what price.
Once accepted, that document should become the plan — not get re-typed as a
task list by whoever picks up the job. This release makes accepting a quote
*create* the project's own scope automatically, one deliverable and one
requirement per priced line. A change order is what you raise when the work
grows afterwards, tied back to the original quote rather than argued from
memory. And a project can be put on hold, formally signed off and closed, and
— after ninety days — locked as a permanent read-only record, with a short
window to reopen a mistake first.

## Comment 4: "a huge priority"

Testing the `v0.19.0` candidate, the Product Owner found the Deliverables
ribbon offered nothing but a disabled "Complete Deliverable" — no way to
create one at all, the only path being a milestone's own Timeline, which
nobody had found. The comment that followed named the whole shape this chapter
builds:

> a quote is opened with the project; the quote defines the initial
> requirement set and defines the deliverables

and, a line later: **"adding that quote section is a huge priority."** That
sentence is why `WP 19.5A`–`D` were worked ahead of every cosmetic item in the
same review. The spine it names — quote → requirements → deliverables →
completion → invoice request — was already half-built: `ADR-0150` gave a
project a client, a purchase order and a pinned rate card; `ADR-0151` had a
completed deliverable raise an invoice request. `ADR-0152` closes the missing
middle: what a client actually agreed to buy, before any of it exists to
complete.

## A quote that defines the work, not just prices it

`Quotation` (`Tempest.Core.Quotations`) is deliberately small: a reference
(`Q-<yyyy>-<nnn>`, generated by scanning every quotation the store already
holds for the highest suffix used that year, or given by hand), a date, a
client, a currency resolved from the project's own pinned rate card, a
validity period, terms, and a list of lines. Each line is priced one of two
ways — hours times a rate, or a fixed price — never both:

```csharp
if (hours is not null || rate is not null)
{
    return (null, QuotationRefusal.InvalidLine,
        "A line is either hours and a rate, or a fixed price — never both.");
}
```

Status is a closed, four-value vocabulary — Draft → Sent → Accepted | Declined
— smaller than `InvoiceRequestStatus`'s nine, since a quote has no connector
to reauthorise against. Both terminal states are final: **there is no revision
of an accepted quotation.** A change of mind about accepted work is a new
document, never an edit to this one — the rule a change order later hangs
from.

## Accept: one welded transaction pretending to be many

Accepting is the one act that reaches outside `Quotation` itself. For every
line, in order: find or create a Milestone named after the quotation's own
reference, then one Deliverable under it and one Requirement, both titled from
the line. Only once every line has produced its objects does the quotation
move to Accepted, recording every created id in that same transaction — what
makes a second Accept refused outright rather than quietly duplicating
everything.

That "only once" has a disclosed price: `AcceptAsync` is **not one atomic
transaction**. The platform's write primitive (`ADR-0145`) commits one object
at a time; widening it to span several was judged a substrate change outside
this Work Package's own files. A crash midway leaves a live, half-fulfilled
quotation, and retrying from there creates a second Deliverable per
already-fulfilled line and throws on the first re-created Requirement, since a
Requirement's identifier (`"<Reference>-<n>"`) is minted once — a real,
accepted gap, not a hidden one.

A Requirement has no parent-child link to join a project — it is a plain
document, not an `EngineeringObjectBase` — so `AcceptAsync` links each created
Requirement to the quotation itself instead, and the project's own requirement
register already treats anything allocated to a project member as belonging to
it. The Execution Plan's own fallback — a title-only association, if the
requirements service had needed changes its own tests forbid — was never
needed.

`WP 19.5D` then found a defect in the plumbing under all this:
`quotation.update-line`/`remove-line`'s line-id parameter, declared with no
default, could satisfy none of the invocation-contract test's generic probes —
so neither command was invokable from the Ribbon or the Palette, unnoticed
because the Quote tab's own buttons dispatch the command directly. The fix was
a default of `Guid.Empty`'s own string form, which the validator accepts and
the service then refuses cleanly. Alongside it, `InputDialog.PromptAsync`
gained `allowBlank`, so a generated reference or optional date can be accepted
with nothing typed, leaving the other twenty-eight prompts unchanged.

## A lifecycle with an expiry

A project's engineering objects already carry a generic `LifecycleState` — the
same eight-value vocabulary `41-project-tasks-and-delivery-workflow.md` found
the wrong fit for a task, for the identical reason: Hold and Resume are a
pause, not a status transition on a released artefact.
`ProjectLifecycleService` gives the project its own four acts instead — Hold,
Resume, Sign off, Reopen — each one transaction and audit row.

Whether a project is Open, Closed or Archive is never stored as a flag; it is
derived, every time, from one fact:

```csharp
public static bool IsArchived(Project project, DateTimeOffset asOf)
{
    ArgumentNullException.ThrowIfNull(project);
    return project.ClosedOn is { } closedOn && DateOnly.FromDateTime(asOf.UtcDateTime) >= closedOn.AddDays(ArchiveAfterDays);
}
```

Ninety days after `ClosedOn` a project becomes Archive: read-only, reference
data. Inside that window Reopen works; past it `ReopenAsync` refuses — "it is
Archive and read-only. It cannot be reopened." — with **the Reopen button left
enabled anyway**, one deliberate exception to an otherwise disabled-control
convention, so a person who tries is told why rather than finding the button
quietly gone.

## One guard, everywhere a write starts

A project past ninety days must genuinely be read-only, not merely labelled
so. `WP 19.5C` put the check into the commercial, quotation, deliverable,
timesheet and invoicing services; `WP 19.10H` closed the same gap in the
milestone, task, evidence and manual-task services. Two routes stayed open —
the Structure tab's Ribbon and the Command Palette — because
`CommandRegistry.Evaluate`, the one place both (and a macro replaying either)
already ask "can this run" (`43-one-way-to-run-a-command.md`), knew nothing
about a project's archived state.

`WP 19.10R` closed it there instead of a third time per surface: a new
`CommandBinding.Mutates` marker, defaulting `false` so no existing binding
changes by omission, and one `ArchivedProjectCommandGuard` that `Evaluate`
consults whenever a binding says it mutates:

```csharp
if (binding.Mutates
    && _archivedProjectGuard is not null
    && _archivedProjectGuard.FindReason(context) is { } archivedReason)
{
    return CommandAvailability.Blocked(archivedReason);
}
```

`mutates: true` was set across sixty binding sites, seventy-seven commands,
spanning the five engineering disciplines plus Quotations, Deliverables, Tasks
and Evidence — one class, one place, so a Ribbon button, a Palette row and a
macro step all see the identical refusal. **The marker is opt-in**, though: a
future mutating command nobody remembers to mark bypasses the guard silently,
and one residual already proves the pattern is not universal —
`IRequirementsService.CreateAsync` takes no project id at all, so it needs a
design step of its own (`TD-179`).

## Finding D18: sign off refused with the lights still on

The Product Owner's own manual test of `v0.19.1` found a hole the ADR had not
anticipated: a project could be signed off and closed while a deliverable it
quoted was still open. The finding named the fix itself — flag it, or let a
**change order** carry it — so `WP 20.10E` built exactly that against
`ADR-0152`'s own promise that a change to accepted work is "a new quotation,
never an edit to this one."

`Quotation` gained a closed `QuotationKind` — `Quotation` (unchanged) or
`ChangeOrder` — using the same Draft → Sent → Accepted lifecycle and its own
`CO-<yyyy>-<nnn>` reference from the identical scan that mints `Q-` numbers.
The difference is where a line's deliverable id comes from: an ordinary line
gets one at Accept; a change-order line carries an *existing* live
deliverable's id from the moment it is added, so `AcceptAsync` branches per
line:

```csharp
if (line.DeliverableId is { } carriedDeliverableId)
{
    deliverableId = carriedDeliverableId;
}
```

— else the ordinary create-a-Deliverable path from before runs unchanged.
`SignOffAsync` now refuses with `WorkStillOpen`, naming every live deliverable
with no completion, live `ManualTask` not done, or live calculation not
complete — unless a live change order's own line already names that
deliverable. A task or calculation can never be carried, since neither is ever
a quotation line; the only way out for them is to finish or close them. The
Sign off tab shows the same open-work snapshot before the statement box, each
item with an **Open** button, and a single **Raise change order…** that
creates a Draft `CO-` carrying every open deliverable at once and opens it on
the Quote tab for re-pricing.

## What was deliberately not built

No revision of an accepted quotation — a changed mind is a new document by
design, which is what makes the D18 fix a natural extension rather than a
special case. No atomic multi-object Accept — disclosed, not silently accepted
as fine. `ManualTask` is deliberately smaller than the existing
`EngineeringTask` the Tasks tab already uses
(`41-project-tasks-and-delivery-workflow.md`): a title, a due date, Done,
reachable through the ordinary discipline template rather than folded into a
type with its own work-state machine. And the quote export reuses the issue
sheet's own two-phase A4 layout
(`64-independent-check-and-the-issue-sheet.md`) at a disclosed cost: the PDF
runs to roughly 600 KB even for one page, since the embedded font subset is
the same size regardless of content — first stated wrongly in the release
notes as a fixed one-page limit, before the physical review corrected it
against the renderer's own tests.

## What to take away

- **Turning an accepted agreement into real objects automatically is worth
  an explicit, disclosed non-atomic step rather than a silent "mostly
  works."**
- **A test only proves what it actually tries to do** — a generic probe
  cannot invoke a parameter with no value that satisfies it.
- **One guard consulted from the single place availability is already
  decided reaches every surface for free; a per-binding opt-in marker
  reaches every surface except the one nobody remembered to mark.**
