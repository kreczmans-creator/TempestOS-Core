# Overview

Version **0.5.0** completes the Developer Experience phase of TempestOS.

This release delivers the capabilities that turn the Platform Foundation
(v0.4.0) — an extensible platform other things load into — into an
application a person can actually navigate, invoke logic in, and inspect:
Navigation, a Shell that finally runs `Tempest.App` through the real
platform, a Command Framework, Diagnostics, and a `dotnet new` module
template. It also delivered the platform's first comprehensive security
audit, establishing a standing Security Baseline.

The objective of this release, like v0.3.0 and v0.4.0 before it, was not
feature delivery for its own sake, but building capability on a governed,
deterministic platform surface without redesigning what already exists.
Every Work Package originally scoped for this release is now complete;
none was rescoped out.

This document, `docs/releases/v0.5.0/CHANGELOG.md`, and `docs/releases/
v0.5.0/Release Notes.md` together constitute the Release Candidate
produced by `WP 5.4` (v0.5.0 Release Candidate & Engineering Sign-Off) —
engineering verification and sign-off, not the release cut itself. Root
`VERSION` remains `0.4.0`; cutting and tagging `v0.5.0` is a separate,
explicit Product Approval decision (Engineering Governance §7).

# Developer Experience

Building on the Platform Foundation, v0.5.0 now provides:

- Navigation (`INavigationProvider`/`NavigationService`)
- The Shell & Composition Framework (`TempestShell`,
  `ITempestHost.Services`) — `Tempest.App` runs the real platform
- The Command Framework (`ICommandDispatcher`/`ICommandRegistry`)
- Diagnostics (`IDiagnosticsProvider`/`DiagnosticsProvider`)
- Composite Logging (`CompositeLogSink`)
- A `dotnet new` module-scaffolding template
- The v0.5.0 Security Baseline (`docs/security/`) — the platform's first
  comprehensive security audit

These components extend the Platform Foundation without modifying it —
every v0.4.0 platform-service contract is unchanged.

# Engineering Principles Demonstrated

The Developer Experience phase demonstrates the following engineering
principles, extending those v0.3.0 and v0.4.0 already established:

- Architecture before implementation — every implementation Work Package
  had a preceding design phase, except one (`WP 5.3`) whose own scope
  (scaffolding/tooling) was confirmed, before implementation began, not
  to require one
- Reuse before invention — the DI-public Platform Service pattern the
  Event Bus established was independently reached three more times
  (Navigation, the Command Framework, Diagnostics)
- Premise verification before implementation — a Work Package brief
  describing a non-existent architecture document was caught and
  redirected before any code was written (`WP 5.2`)
- Deterministic runtime behaviour, explicit ownership, and failure
  isolation, all unchanged from the Platform Foundation
- Governance made checkable, and actually checked — repeatedly, this
  release's own Work Packages found and corrected real, pre-existing
  drift left by their own predecessors

# Baseline Statement

**Version 0.5.0 completes the Developer Experience phase for TempestOS.**

Remaining Developer Experience Work: **NONE.**

Future capabilities shall build upon this platform rather than revisiting
the Platform Foundation or this release's own additions, unless a
genuine, documented engineering reason requires otherwise. Any change
affecting the Runtime Foundation, the Platform Foundation, or the
Developer Experience capabilities this release completes shall be
evaluated through the Architecture Decision Record process and
Engineering Governance before implementation.

# Historical Significance

Version 0.5.0 marks the completion of the TempestOS Developer Experience
phase — the platform gained its first real, human-facing surface
(Navigation, the Shell), its first uniform way to invoke application
logic (the Command Framework), its first visibility into its own runtime
state (Diagnostics), and its first comprehensive security audit.

This release concludes the developer-experience phase of development.
Subsequent releases are expected to focus on domain capability — a
Project Engine, a Requirements Engine, or whatever Product Approval
scopes next — built using the platform this release completes, not a
redesign of it.
