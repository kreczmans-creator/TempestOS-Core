## 2. Engineering Governance §5 — ADR Creation Rules (Verbatim Checklist)

Source: `docs/academy/06 Engineering Standards/Engineering
Governance.md`, lines 177–208, reproduced exactly (word-for-word, not
summarised):

> An Architecture Decision Record is **required** when a decision meets
> any one of the following criteria:

- [ ] "The decision was not the only reasonable choice available, and
  at least one genuine alternative was seriously considered and
  rejected (every ADR in `docs/adr/` today satisfies this)."
- [ ] "The decision would be expensive, risky, or disruptive to
  reverse later — particularly if reversing it would require breaking
  a public API or contradicting an established convention other code
  now depends on."
- [ ] "The decision establishes a convention future work packages are
  expected to follow (e.g., ADR-0003's constructor convention, which
  later work packages' correctness silently depends on)."
- [ ] "The decision resolves an explicit ambiguity or tension between
  two stated requirements (e.g., ADR-0008 resolving the tension
  between WP 2.4's literal wording and the 'do not redesign discovery'
  constraint)."
- [ ] "The decision was specifically challenged and defended under
  Technical Review (§2) — the outcome of that review, whichever way it
  concluded, is itself ADR-worthy."

> "An ADR is **not** required for implementation details with no
> genuine alternative, no future-convention implication, and no review
> challenge — routine code that simply does what the brief
> straightforwardly asked for does not need one merely because a
> decision, in the broadest sense, was technically made."

> "**Format**: `ADR-NNNN-kebab-case-title.md`, numbered sequentially,
> in `docs/adr/`, using the template already established: **Status**,
> **Context**, **Decision**, **Consequences**, **Future
> Considerations**. Numbers are never reused, even for a superseded or
> later-reversed decision — a superseded ADR is marked as such in its
> Status section and a new ADR is created referencing it, preserving
> the full history rather than overwriting it."

Every one of `ADR-0107`–`ADR-0112` the sibling agents propose must
satisfy at least one bullet above (checkable independently against the
new ADR's own Context/Decision text) and, if it revisits RD-0010 or
RD-0011, must follow the "superseded, not overwritten" numbering rule
for any ADR it modifies the practical effect of — not by editing
ADR-0025/ADR-0026 in place.

## 3. Existing ADRs a Plugin-Trust-Isolation Architecture Plausibly Interacts With

Named list, each with a one-line constraint a new ADR in this space
must not contradict without itself being an ADR that explicitly
supersedes the cited one (Engineering Governance §5's own supersession
mechanism):

| ADR | Must NOT — without explicit supersession |
|---|---|
| **ADR-0005** (Custom DI container) | Introduce a plugin-isolation mechanism that assumes a third-party DI container's scoping features (e.g., `IServiceScope`) — none exist; a per-plugin trust boundary must be built on TempestOS's own container primitives (`AddInstance`, reflection construction) or an explicitly new one. |
| **ADR-0009** (Composition root owns externally-created services) | Have a plugin-loaded service silently become container-constructed in a way that bypasses the "composition root owns what it externally creates" principle — any new construction path for isolated plugin services should extend this ADR's named future mechanisms (factory/singleton-factory/bootstrapped registrations), not invent an unrelated fifth one. |
| **ADR-0013** (Platform-service failures Host-fatal; module failures isolated) | Reclassify a plugin's *post-load* module failure as Host-fatal — ADR-0013's module-isolation half governs a plugin's module exactly like any other module once loaded (ADR-0025 says so explicitly), and that boundary is not this WP's to move. |
| **ADR-0015** (Runtime hosts are not restartable) | Require reversing the no-restart decision (e.g., "unload and reload a revoked plugin's `AssemblyLoadContext` without a process restart") without itself being an ADR that explicitly supersedes ADR-0015 — an `AssemblyLoadContext`-per-plugin design (Security Roadmap item 1's own first-named option) must state plainly whether *unloading* a context is in scope, since that is new restart-adjacent territory ADR-0015 never anticipated. |
| **ADR-0021** (Background service failure isolation, opt-in criticality) | Be treated as a template a plugin isolation ADR can just "reuse" for plugins — ADR-0025 already explicitly rejected this analogy (RD-0011) on the grounds that a plugin has no live component at failure time to declare criticality; a new ADR proposing per-plugin critical opt-in must engage RD-0011's reasoning directly, not silently re-run ADR-0021's pattern. |
| **ADR-0023** (Platform layering — dependencies flow downward only) | Introduce a mechanism where a Platform Service depends on, references, or holds a reference to a specific plugin/module — an enforcement point for plugin trust must sit in the Service layer and be called *by* module/plugin-loading code, not the reverse. |
| **ADR-0024** (Platform contracts packaged by capability) | Gather any new isolation-related contracts (a capability/permission-scope interface, a plugin identity type) into an undifferentiated shared "Contracts" namespace — new interfaces should land in a capability-named namespace, mirroring this ADR's established convention. |
| **ADR-0025** (Plugin failure classification) | Make a plugin's discovery/load-time failure Host-fatal, or add a manifest-level `IsCritical` opt-in, without explicitly reopening this ADR and its own RD-0010/RD-0011 rejections with new, cited evidence. |
| **ADR-0026** (Plugin discovery/loading lifecycle placement) | Require Module Discovery to change, or move Plugin Discovery/Loading out of Phases 3.1/3.2, without accounting for every downstream document that cites those phase numbers (`Host Lifecycle.md`, `Runtime State Machine.md`, `Startup Sequence.md`, `Failure Behaviour.md`) — an enforcement call inserted into these phases must state which phase's entry/exit criteria it changes, if any. |
| **ADR-0044** (`IPermissionEvaluator` is the single enforcement point; `CurrentPrincipalAccessor` is ambient) | Introduce a second, competing authorization-check mechanism for plugin trust rather than calling `IPermissionEvaluator.RequirePermission`/`HasPermission` — this ADR is `FCR-0001`'s own explicitly named "the enforcement mechanism itself already exists... this capability is applying it, not building it." A plugin-isolation ADR must not re-litigate whether `IPermissionEvaluator` is the right enforcement point; that question is already closed. It also must not silently assume request-scoped identity — `CurrentPrincipalAccessor` is ambient, process-wide, by this ADR's own explicit, tested decision. |
