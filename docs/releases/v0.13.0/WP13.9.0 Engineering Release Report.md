## Role and Standard Applied

This is the first execution of the Engineering Readiness Review (ERR)
`ADR-0106` defines, applied to `v0.13.0`. `ADR-0106` defines a
**five**-category model — Architecture, Implementation, Verification,
Governance, Release — executed by the proven six-discipline Programme
Review structure. This execution was explicitly commissioned with a
**sixth, additional** category, **Security/Trust**, specific to this
release: `v0.13.0`'s entire substantive content is a new plugin
trust/capability/signature enforcement platform (`ADR-0107`–`ADR-0112`),
a case `ADR-0106`'s own "Future Considerations" section explicitly
anticipates ("If a future release finds the six-discipline structure
genuinely insufficient... that is itself Technical Review material...
a candidate for revising this ADR directly, not a silent deviation from
it"). This report treats that addition as a deliberate, disclosed
methodology extension for this specific release — not a silent
deviation from the standard model, and not evidence the canonical
five-category model itself needs revising (that judgement is Product
Approval's own, informed by this report, not asserted here).

Six independent discipline reviews (Chief Architect, Principal Software
Engineer, joint QA Lead/Workflow Engineer, Technical Author,
Security/Trust, Product Manager), each performed **before seeing the
others' conclusions**, mapped onto Architecture/Implementation/
Verification/Governance/Security-Trust/Release readiness, reconciled
here into one Programme Review. Every claim in every discipline's own
report was independently re-verified from source this Work Package,
against `feature/v0.13.0`'s HEAD commit `88e41a2a48d1f89ea085b4817ee41b3ac0262a06`
— no prior Work Package's own report (`WP13.0A` through `WP13.3B`) was
assumed correct without a fresh check. Debug/Release build and full
regression evidence (0 Warnings/0 Errors both configurations;
2,519/2,519 tests passing both configurations — 2,298
`Tempest.Core.Tests` + 221 `Tempest.Desktop.Tests`) and
`governance-healthcheck.ps1` (7 passed, 1 warned, 0 failed) were
gathered once, fresh, by the orchestrating review itself at this exact
commit, and cited by the disciplines that required them rather than
independently re-run six times.

**No implementation defect is fixed by this Work Package.** Every
finding below is disclosed and classified, never corrected — including
governance/documentation gaps a prior sign-off's own precedent (`WP
11.9.0`'s Part C) might have corrected in-review; this execution's own
explicit brief is narrower: review, classify, report, stop.

## Release Decision

# **TempestOS v0.13.0 — NOT READY**

**Four of six disciplines independently reached Not Ready**, via
substantially non-overlapping evidence — the clearest possible
vindication of this project's own independent-before-reconciliation
discipline (`ADR-0106`'s own rationale, the `TD-42`/`TD-43` precedent):

1. **Verification readiness** — real, GitHub-hosted CI has never run
   against any commit of this release. `feature/v0.13.0` has no
   upstream tracking branch, does not exist on `origin` at all, and
   none of its seven commits have ever been merged into `main`.
2. **Release readiness** — independently, via its own
   branch/repository-state evidence, converged on the identical
   underlying fact.
3. **Implementation readiness** — three of its own findings: (a) the
   HEAD commit's own Work Package (`WP13.3B`) is undocumented anywhere
   in this release's governance record; (b) that same commit's own
   message claims a "20,000-trial differential fuzz harness"
   verification that does not correspond to any artefact in the
   repository; (c) `PluginManifest`'s public constructor gained five
   new **required** parameters this release — an undisclosed public
   API break, one of `ADR-0106`'s own three literally-named
   Release-Blocking examples.
4. **Security/Trust readiness** (the disclosed, additional sixth
   category) — a genuine, empirically-demonstrated trust-boundary
   bypass, newly found by this review, not previously tracked anywhere:
   plugin trust enforcement (`PluginAssemblyLoader.EnforceTrust`)
   scans only the one manifest-declared assembly, but Module Discovery
   (unmodified, per `ADR-0110`) scans the entire process `AppDomain` —
   so a second, wholly undeclared assembly present in a plugin's own
   folder is discovered and activated as an ordinary module, with
   **zero** trust checking of any kind, and is treated as
   indistinguishable from first-party code.

**Architecture and Governance readiness are both Pass, with
observations** — real, disclosed, non-blocking findings, none of which
independently produced a Not Ready category.

See Part E for the full mechanical derivation and Part A for each
discipline's own complete evidence.

### A5. Security/Trust — Security/Trust Readiness (disclosed, additional sixth category)

**Verdict: Not Ready.** One Release Blocking finding, newly found.

**Evidence:** `ADR-0110`/`0111`/`0112` confirmed honoured by shipped
code on every dimension checked except the one finding below — no ALC,
no process separation (`grep` for `AssemblyLoadContext`/`Process.Start`/
`AppDomain.CreateDomain` across `src/`: zero matches); trust tier table
implemented exactly; signature verification genuinely at Discovery,
strictly before `Assembly.LoadFrom`; `Plugins:AllowUnsignedLoad`
genuinely fail-closed at both the constructor-default and real
config-binding level. Both previously-fixed defects (`WP13.2B`'s
denylist, `WP13.3B`'s registry-spoofing fix) independently re-confirmed
present and correctly unconditional across every trust tier. Fail-closed
defaults independently verified across five distinct ambiguous-input
scenarios (unsigned+disallowed, malformed envelope, unrecognised
capability shape, expired/not-yet-valid certificate, untrusted
thumbprint) — every one denies/isolates, none silently permits.

**Finding — Release Blocking, empirically demonstrated, newly found by
this review, not previously tracked anywhere (not in the ADRs' own
Negative Consequences, not `TD-49`/`TD-50`, not `Plugin Trust &
Isolation Architecture.md`'s Risks section):**

`PluginAssemblyLoader.EnforceTrust` scans only the one manifest-declared
assembly's own types (`ADR-0111`'s own literal scope: "every discovered
`IModule` implementer **in the plugin's own assembly**"). Module
Discovery (`ReflectionFrameworkDiscoveryService`, deliberately left
"completely unchanged" per `ADR-0110`'s own Decision text) scans
`AppDomain.CurrentDomain.GetAssemblies()` — **every** assembly present
in the process, by any means. A live proof-of-concept, built against
this commit's actual compiled `Tempest.Core.dll` (not a hypothetical
reading of the code — a real, run, reproducible demonstration): a
plugin's one manifest-declared assembly (`AsmA.dll`, requesting zero
capabilities, `UnsignedLocal` tier — the *lowest* trust tier)
inherits a type from a second, wholly undeclared assembly
(`AsmB.dll`, sitting in the same plugin folder — an entirely ordinary
plugin-with-a-dependency-DLL layout). Resolving `AsmA`'s own base-type
chain during `EnforceTrust`'s own `assembly.GetTypes()` call loads
`AsmB.dll` into the `AppDomain` as an unavoidable CLR side effect —
`AsmB`'s own `EvilModule : IModule` type is never seen by
`EnforceTrust` (never trust-checked, never capability-checked, never
constructor-conformance-checked), yet is discovered and activated as
an ordinary module by the (correctly) plugin-unaware Module Discovery
pass. Because no principal was ever recorded for it, its ambient
component principal is `null` — and `PluginTrustPermission.IsFirstParty(null) == true`,
so **every dynamic capability check across `NavigationService`/
`CommandHandlerTable`/`CommandRegistry`/`EventBus` is skipped, not
merely satisfied**, for this module — and its constructor freely
receives the real, mutable `CurrentComponentAccessor` singleton
(exactly the type `WP13.2B`'s own denylist exists to forbid, for every
tier including FirstParty), fully reachable again through this
side-channel, at the lowest trust tier, requesting zero declared
capabilities.

This is categorically distinct from `ADR-0110`'s own disclosed "not a
hard sandbox" caveat (a trust-checked plugin using reflection to reach
past a `RequirePermission` call site from within its own already-scoped
code) — here, an entire second assembly receives zero trust checking of
any kind and is architecturally indistinguishable from first-party
code, via completely ordinary multi-assembly plugin packaging, no
unusual technique required. It is also distinct from `TD-49` (a timing
race on the *same* declared assembly's own bytes) and `TD-50`
(filename-based cert detection) — no race condition or trust-store
tampering is needed. This is a structural blind spot at the join
between `ADR-0110`'s own "Module Discovery unchanged" decision and
`ADR-0111`'s own "the plugin's own assembly" scope — not a coding
defect inside `EnforceTrust` itself, which does exactly what its
governing ADR describes.

**Methodology note, restated:** this finding is reported under the
disclosed, additional Security/Trust category this review was
commissioned with — it is not one of `ADR-0106`'s own five canonical
categories' findings, and its presence here is not itself evidence the
canonical model needs revising; that judgement belongs to Product
Approval, informed by this report.
