### A.2 Paragraphs — P1 and P2 rows (and the notable "closing tonight" findings)

**`TD-179` (P1, residual).** This is the one Live Backlog row where the shipped UI's own promise is contradicted by the code, and the sharpest finding of this audit. `ProjectArchival.IsArchived` is real and correctly enforced in the five Core services named in the Release Notes, but `ProjectWorkspaceView.RefreshAsync` (`src/Tempest.Desktop/Views/ProjectWorkspaceView.cs:454-455,469`) enabled Evidence's Create button, the Tasks area's New Task button, and the Timeline's Set Milestone/Edit/Add Deliverable buttons unconditionally on an archived project, showing only a passive "Reference data only; nothing here can be changed" banner that disabled nothing. None of `EvidenceWorkspaceView.cs`, `ProjectTasksView.cs`, or `ProjectTimelineView.cs` carried any archived check, and the write path through `ProjectDeliveryCoordinator.cs` to `IProjectTaskService`/`IProjectMilestoneService` had no guard either. Tonight's `WP 19.10H` closes the Milestone, Task and Evidence services (nine mutators) and the manual-task service, and disables every write control on an archived project's tabs with the tooltip "Archived project — read only." Two things still fall outside that fix: `IRequirementsService.CreateAsync` takes no `projectId` parameter at all, so guarding it needs a design step before a code change; and the Structure tab's ribbon-driven engineering commands carry no archived check anywhere in the command registry, so a user could still open Structure on an archived project and create or revise engineering objects through the ribbon with no refusal. This residual should be the first item any follow-on package closes.

**`TD-150` (P1, closing tonight).** `SqlitePersistenceStore.ExecuteInTransactionAsync` disposes its SQLite connection outside the try/catch that protects COMMIT (`src/Tempest.Core/Persistence/SqlitePersistenceStore.cs:468-509`); if that disposal throws after a successful COMMIT, the exception propagates uncaught and `EngineeringDomainContext.ExecuteWriteAsync`'s `afterCommit` callback — the one place the in-memory repository learns a write landed — never runs (`EngineeringDomainContext.cs:261-289`), directly contradicting that class's own documented "commit and apply are one critical section" invariant. This is exactly `TD-147`'s defect class (a durably-committed write the running application never learns about), reached from the opposite side of commit, and the platform's only fault-injection double for this scenario (`CommitFailingPersistenceStore.cs`) only ever fails *before* COMMIT — so 0 of the suite's 3,330 tests can catch a regression here. Closing tonight as `WP 19.10J`; carried here so the record survives if that closure slips.

**`TD-28` (P2).** `RequirementsService` writes bypass `EngineeringDomainContext.ExecuteWriteAsync` entirely (`RequirementsService.cs:90-256`) and so never publish to the `WorkspaceChanges` bus (`EngineeringDomainContext.cs:261-283`) — the row's own title undersells this as a bulk-command problem when it is in fact every Requirements write, single or bulk. A user with a Requirements Explorer tree or Cockpit docked while editing from a second tab or the bulk-status command sees stale data until they navigate away and back; no test anywhere asserts a Requirements write raises `WorkspaceChanged`. A real fix needs new sequence-number plumbing exposed to the service (3-4 days), since none exists there today.

**`TD-38` (P2).** `EngineeringObjectFactory<T>.CreateAsync`, the shared construction path for Calculations, Documents, Manufacturing, Mechanical/Parts, Verification and Evidence, enforces no business-identifier uniqueness at all; the one mitigating check (`DuplicateItemNumberValidationRule`) is advisory, BOM-scoped, and only surfaces on editor reopen. `BACKLOG.md`'s `WP 18.2B` owner is wrong — Evidence's own creation call passes `identifier: null` (`EvidenceService.cs:121`), so there was nothing for that package to have made unique. A consultant can create two Parts, Calculations or Documents sharing an identifier today with no warning outside the narrow BOM case, risking an ambiguous calc-sheet citation or drawing reference later.

**`TD-98`/`TD-99` (P2, Document viewer).** The single viewer every attachment "Open" button in the app funnels through (`AttachmentViewerLauncher`, wired once at composition root) supports paging and zoom only, no rotate/markup/annotation (`TD-98`, a deliberate `ADR-0115` scope cut), and reports DWG and SVG attachments "Unsupported" outright (`TD-99`, `ViewableDocument.cs:87-92`) — bytes are always stored safely, only the inline preview fails. Both are real, everyday friction on the one document surface Evidence (E2/E6/E9) and the Structure tab's attachments (D8) both use; SVG support is a moderate, self-contained addition, while DWG has no free rendering path and needs a licensed CAD SDK.

**`TD-92` (P2, in progress `WP 19.10N`).** Drag-to-dock already resolves and raises a live drop target (`WorkspaceLayoutController.cs:85-86,95-96,103`) but nothing subscribes to it, so a panel rearrangement in the Structure tab drags blind until release — a small, low-risk fix (`WorkspaceLayoutHost.cs`'s existing `_flyout` overlay, line 50, is a ready pattern to copy).
