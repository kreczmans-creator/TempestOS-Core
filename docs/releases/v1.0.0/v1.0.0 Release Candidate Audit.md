## 2. What "v1.0.0" means on record — three definitions, not one

This is the audit's first finding. The repository carries three distinct,
partially overlapping statements of what v1.0 is, and no document
reconciles them:

1. **`WP7.2A Recommended Programme.md` (`v0.7.0`)** — a *milestone
   marker*: "a real individual engineer or small professional practice
   could plausibly run real Systems Engineering work end-to-end: a
   requirement recorded, verified, and reported on." No scope.
2. **`WP11.0B Architecture Roadmap.md` §1 (`v0.11.0`) — the only
   scoped definition.** "A commercially credible, single-user (or
   small-trusted-team), locally-trusted desktop engineering platform,
   covering the six Engineering Disciplines already shipped through
   `v0.10.0`," on a CI-verified build, a decomposed Desktop composition
   root, one documented presentation surface, a compile-time vocabulary
   safety net, and an internally-consistent governance suite with drift
   closed by tooling. **Explicitly out of scope:** third-party plugins
   (`FCR-0002`) and REST beyond a trusted local network
   (`FCR-0003`/`0004`). Recommended path: `v0.11.0 → v0.12.0 → v1.0.0`.
3. **The 2026-08-28 product decision (`TD-84`, Product Compliance
   Audit)** — "TempestOS is a project-centric engineering operating
   environment: `TempestOS → Module → Project → Workspace → Engineering
   Object → Evidence`," measured against five mock-ups that include a
   ten-module global rail, Commercial/Resources/Knowledge/Admin modules,
   a drawing viewer, and a Companion mobile application. This decision
   post-dates and materially widens definition 2, and was never
   re-stated as a v1.0 scope.

`Product Roadmap.md` (last reviewed `WP 7.2A`, six releases ago) still
describes Phase 5 as "not yet scoped" and never gained the "Phase 5.5 —
v1.0 Readiness" entry `WP11.0B` §4 asked `WP 11.1B` to add. `VISION.md`
declines to assign v1.0 to any phase.

**This audit measures against definition 2 as the governing baseline**
(it is the only approved, scoped one) **and reports definition 3's
residuals separately** (§5.3), so that the Product Owner can choose the
v1.0 line rather than have this audit choose it. That choice is the
single decision that determines how long the remaining list in §5 is.

## 4. Findings about the plan, not just the code

1. **No approved v1.0 scope exists that reflects the current product.**
   §2. Until the Product Owner picks between definition 2 and definition
   3 (or a named subset of 3), the remaining-work list has two very
   different lengths.
2. **The release gate has never certified the product as it now
   stands.** `v0.12.0` was the last §9-certified release; `v0.13.x`,
   `v0.14.0`, `v0.15.0` carry engineering recommendations only. Three
   releases of un-certified change is itself a readiness gap for a
   release whose only Work Package is a re-certification.
3. **Two finished bodies of work sit outside `main`.** `WP 15.2A` is a
   trivial merge. The Companion branch is not: 64 commits behind, its
   own `TD-57`/`TD-58` numbering collides with `main`'s, and it carries
   a REST surface the current v1.0 definition excludes. `TD-82` (P0)
   asks for "merge or formally reject" and has had no decision for a
   week.
4. **Governance currency is still hand-maintained where it matters.**
   Six registers are known stale (`TD-57`); `Product Roadmap.md` and
   `Feature Register.md` were last reviewed at `WP 7.2A` and `WP 5.3`;
   the lower half of `PROJECT_STATUS.md` ("Current Repository Phase,"
   "Current Priorities," "Near-Term Roadmap") is frozen at `v0.8.0`–
   `v0.13.0` with layered "this field is stale" corrections (`DNB-7`).
   `PROJECT_STATUS.md` is 565 KB. The health-check passes because it
   checks what it checks.
5. **Retrospective coverage has a known hole the gate keeps waving
   through.** `v0.11.0`'s ten Work Packages, `WP 15.1A`/`15.1B`, and
   the ~34 pre-`v0.14.0` commits have no Academy retrospective; the
   Academy Register's per-article annotations are behind. Disclosed as
   non-blocking in three consecutive releases.
6. **Platform support is undecided.** The shipped Desktop cannot launch
   on Linux/X11 (`TD-116`, a deliberate security pin vs. an Avalonia
   binding). Windows/macOS work. A v1.0 needs either a fix or a stated
   support matrix.
7. **Durable data has no schema version.** `EngineeringObjectState` is
   versionless (`TD-87`). A v1.0 that writes user data without a
   migration seam commits every later release to reading it unchanged.
   This is the one Open item this audit rates as a hard v1.0 blocker
   that no existing document rates that way.
8. **Accessibility failed the product audit outright** (`TD-65`: non-
   modal dialogs, no `AutomationProperties`, pointer-only graph). Not
   named in definition 2, but "commercially credible desktop" is hard to
   defend without at least modal dialogs and accessible names.
9. **Security posture matches definition 2, not definition 3.** For a
   loopback-only, single-user product the open REST/licence items
   (`TD-13`/`14`/`16`/`62`) are acceptable declared debt. The moment
   Companion (mobile, over the network) is in v1.0, `FCR-0003`/`0004`
   and Security Roadmap items 6/7 become mandatory, and the never-run
   `WP 13.1A`/`13.1B` pair comes back. Third-party plugins are
   likewise "Identified, not started" (`FCR-0002`, `src/Plugins/`
   empty) with three mandatory-before-enablement items still Open
   (`TD-56` fail-open constructor scope, `TD-61`, `TD-64`).
10. **Test-suite determinism is close but not closed.** `TD-34`
    (`CompositeLogSinkTests` console-redirect race, seen again at
    `v0.13.0`'s failed publish), one retained fixed wait (`TD-119`),
    no real image-decode coverage (`TD-100`), no end-to-end resize or
    dialog-modality tests (`TD-83`). The `v0.13.0` publish failure was
    exactly this class.
11. **The good news is real.** Zero `TODO`/`FIXME`/`NotImplemented` in
    `src/` (re-verified here). Every placeholder is labelled in the UI.
    Five architectural invariants fail the build rather than living in
    prose. The registers disclose their own gaps. CI has been green on
    every `main` commit this release. This is a well-governed codebase
    whose plan has drifted, not a codebase hiding its state.
