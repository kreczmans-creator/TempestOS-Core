# WP 14.2.1 Completion Report — CI Pipeline Remediation

Per Engineering Governance §4 (nine mandatory sections).

## 1. Summary

Root-caused every recent red GitHub Actions run — on this branch and on
`main` — to a single condition that has nothing to do with the code:
this account's Actions **artifact storage quota is exhausted**, the two
diagnostic upload steps fail on it, and the required `CI Gate` keys off
a job conclusion that folds those steps in. Fixed at the gate's own
semantics (`ADR-0117`), removed the ~50 MB-per-push cause, and closed
the diagnosability gap the outage exposed, under which a real
intermittent failure on `main` could be counted but not named. Zero
`src/` and zero `tests/` files changed; no test weakened, retried,
skipped or quarantined.

## 5. Architectural Decisions & Reasoning

`ADR-0117` — the `CI Gate` reflects build and test outcome only.
Verification (build, test) decides whether a commit is sound and remains
fatal, `TreatWarningsAsErrors` included; diagnostics (artefact uploads)
carry evidence about a verdict already reached and must never be able to
reach it. Alternatives considered and rejected in the ADR: re-running
until quota clears (tried, three attempts, structurally cannot work);
deleting uploads; step-level gate inspection (GitHub exposes none to a
downstream job); in-workflow quota detection; retention reduction alone.

## 8. Assumptions

- The quota condition is account-level and outside this repository's
  control; this Work Package stops the pipeline *adding* to it and stops
  it *deciding the gate*, but cannot reset the counter. Upload steps may
  stay amber until GitHub recalculates usage — now against a green gate.
- `TD-60` (Node 20 action deprecation) is deliberately **not** fixed by
  guessing version tags: this environment is scoped to this repository
  and could not verify which major tags exist, and inventing one would
  have caused exactly the outage this Work Package ends.
- The `main` runs in the evidence table were `workflow_dispatch`
  re-runs of an unchanged commit, which is what makes them such clean
  controls.

## 9. Observations

- **A correction to this train's own prior reporting.** The completion
  reports for `WP 14.0A`, `WP 14.1A` and `WP 14.2A` each stated the
  suite passed and the build was clean. That was true *locally*, and it
  is what those reports said — but none of them checked the actual
  GitHub Actions result for the commit they described, and every one of
  those commits was red in CI at the time, for the reason established
  here. The claims were not false; the verification behind them was
  narrower than a reader would reasonably assume. Recorded plainly
  rather than left implied, and `WP 14.2.1` closes the gap by making the
  real CI result the thing that gets read.
- `release.yml` was reviewed and deliberately left unchanged: it
  publishes GitHub Release assets, not Actions artefacts, so the storage
  fault cannot reach it, and its own test step *should* remain able to
  stop a release. `TD-59` is therefore a live risk to the next release
  as well as to CI — it is the same class of failure that stopped
  `v0.13.0`'s release run at `Test (Release)`.
- Run `33129951166` shows `cancelled` rather than failed: `ci.yml`'s own
  `concurrency` group superseding an in-flight run. Benign.
