# WP 14.2A Completion Report — Companion Android & iOS Platform Heads

Per Engineering Governance §4 (nine mandatory sections).

## 1. Summary

Restructured the Companion into the official Avalonia cross-platform
shape — `Tempest.Companion` as the shared single-view application
library with thin heads — and authored the Android and iOS heads with
the brand pack's launcher icons. Heads live outside the gating solution
in `src/Tempest.Companion.Mobile.slnx` and build via the new
dispatch-only `mobile-heads.yml` workflow (`ADR-0116`). Android was
validated to this environment's hard edge (restore + Roslyn compile
against the workload's reference assemblies — which caught and fixed a
real AppCompat-theme launch crash before first run); iOS is authored to
the official template, validated by the workflow's macOS job on first
dispatch. `TD-57`: Open → Partially resolved.

## 4. Architectural Decisions & Reasoning

`ADR-0116`: heads outside the gating solution, built by a dedicated
non-gating dispatch workflow; the library/head split as the required
shape (`NETSDK1150` makes the old single-project shape structurally
unable to grow heads); heads are bootstrap, never behaviour; validation
claims graded and disclosed. Alternatives (gating workload installs,
conditional membership, auto-triggered workflow, reference tricks) in
the ADR.

## 7. Assumptions

- GitHub's `windows-2022` runner image ships an Android SDK + JDK, and
  `macos-15` ships Xcode — the documented basis of `mobile-heads.yml`;
  its first dispatch is the workflow's own validation (disclosed in the
  workflow header, `ADR-0116`, and `TD-57`).
- The simulator RID (`iossimulator-arm64`) builds without signing, so
  the workflow needs no secrets.
- `com.tempestengineering.tempestos.companion` is an acceptable
  application id pending a Product Owner-issued one.

## 8. Observations

- The .NET Android *workload* installs from NuGet alone on Linux; only
  the Google-hosted Android *SDK* is unreachable here — a distinction
  worth knowing for any future constrained-environment work.
- The reference-assembly compile check surfaced that
  `AvaloniaMainActivity` derives from AndroidX's `AppCompatActivity`:
  the initially chosen plain `@android:style` theme would have crashed
  at first launch; fixed (`styles.xml`, `Theme.AppCompat.DayNight.
  NoActionBar`, navy-800 first-frame window background) before the code
  ever ran anywhere.
