## 3. Installer (Velopack Setup.exe)

Read: `scripts/package-installer.ps1`, `.github/workflows/release.yml`'s "Package installer
(Velopack)" step, `tests/Tempest.Core.Tests/ReleaseEngineering/PackagingScriptTests.cs`, the
WP 21.5A row in `docs/releases/v0.21.0/Release Notes.md`, `src/Tempest.Desktop/Startup/*`, and
`tests/Tempest.Desktop.Tests/Startup/PersistenceRootResolverTests.cs`.

**What exists and is real:**
- `scripts/package-installer.ps1` is a genuine, complete script: `dotnet publish` (Release,
  win-x64, self-contained, `TreatWarningsAsErrors=true`) → `vpk pack` (installing the `vpk`
  1.2.0 dotnet tool locally if absent) → renames `TempestOS-win-Setup.exe` to
  `TempestOS-<Version>-Setup.exe`.
- `release.yml`'s "Package installer (Velopack)" step calls this exact script with the tag's
  semver, then renames the result to `TempestOS-<tag>-Setup.exe` to match every other asset.
- `PackagingScriptTests.cs` (8 tests) checks the script exists, is syntactically valid
  PowerShell (via the real `System.Management.Automation.Language.Parser`, out-of-process via
  `powershell` — Windows-only, and one of the 10 known Windows-only failures on Linux, see item
  7), and names the expected commands/assets as literal substrings. Its own doc comment is
  explicit that this is the limit of automated coverage: *"Running the script itself ... is
  exercised once, by hand, per this Work Package's own report — not on every `dotnet test`
  run."*

**What does not exist — the honest gap:**
- `release.yml` triggers only `on: push: tags: v*.*.*`. `git tag -l` in this repository lists
  16 tags, the newest being `v0.18.0`. **There is no `v0.19.0`, `v0.20.0`, `v0.21.0`, or any
  `-rc.` tag in this repository.** WP 21.5A (which added Velopack support) is dated after
  `v0.18.0`, so **`release.yml`'s "Package installer" step has never once actually run** on any
  tag that carries it. No `Setup.exe` has ever been produced by this pipeline, on CI or
  otherwise — this WP's own report (referenced by the test's doc comment) is the closest thing
  to that evidence, and it was not available to re-verify in this worktree.
- No Windows environment was available in this sandbox to run `vpk pack` directly and open the
  Setup.exe by hand, per the task's own instruction not to attempt that here.

**Persistence-root / first-run dialog (adjacent scope of the same WP):** verified thoroughly by
unit test, not by a real installed run (there is no installed Windows build to run):
`PersistenceRootResolverTests.cs` covers exactly the documented precedence — CLI argument
(`--persistence-root`, both space and `=` forms) wins outright even when installed and
configured; a configured `RootPathConfigurationKey` wins over the installed default and shows

Grepped `<root>/logs/tempest-*.log` across both launches (project creation, Settings, a real
backup, a refused restore, a close, and a relaunch — one continuous log file spanning ~430+
lines from the first run and growing to ~1,500+ lines total):

```
$ grep -c Exception logs/tempest-20260915.log

$ grep -c "\[Error\]" logs/tempest-20260915.log
0
$ grep -c "\[Warning\]" logs/tempest-20260915.log

```

Every `[Warning]` line falls into one of two known, non-novel categories, each occurring once
per module/service at startup:

1. **17 DI "registration slip, not an optional dependency" notices per launch**, e.g.
   `Constructing 'ProjectLifecycleService': parameter 'timeProvider' of type 'TimeProvider' has
   no registration; using its declared default.` (16 for `TimeProvider`, 1 for
   `IBusinessIdentifierIndex` on `EngineeringDomainContext`). These are the platform's own
   startup diagnostic for services that fall back to a declared default rather than a
   registered instance — present on both launches, not something introduced by this session's
   activity, and not accompanied by any functional symptom in this session (backup, restore
   guard, and persistence all worked correctly). This is a legitimate release-notes-worthy
   finding (a real warning surfaced on every ordinary launch) but not a defect this WP
   diagnosed further, since fixing it is product code and out of this WP's scope.
2. **1 secrets-storage notice per launch**: `Secrets are stored as plain, unencrypted files
   under '<root>/secrets' on this platform: no DPAPI or platform keychain binding exists yet
   (WP 19.1A, ADR-0151).` This is the expected, documented Linux fallback (see item 7) — the
   warning itself is the intended behaviour, correctly surfaced.

No new or unexpected warnings appeared during backup, restore-guard refusal, project creation,
or the restart cycle.

**Verdict:** Verified. **Blocks RC acceptance?** No (the 17-per-launch DI notice is worth a
follow-up ticket to either register the missing `TimeProvider`/`IBusinessIdentifierIndex` or
downgrade/annotate the log level, but it is cosmetic — every fallback used is the documented,
correct default).

## 7. Linux-only Core failures (the 10 Windows-only tests)

Reproduced locally rather than merely inferred:
```
dotnet test tests/Tempest.Core.Tests/Tempest.Core.Tests.csproj -c Debug --no-build \
  --filter "FullyQualifiedName~SecretStoreTests|FullyQualifiedName~CheckVulnerablePackagesScriptTests|FullyQualifiedName~PackagingScriptTests|FullyQualifiedName~OAuthAuthoriserTests.AStoredToken_IsNeverWrittenToTempestDb"
→ Failed: 10, Passed: 15, Skipped: 0, Total: 25
```
Exactly 10/10 failed, matching the lead's figure precisely:

**6 spawn `powershell` (a literal `ProcessStartInfo("powershell", ...)`, not `pwsh`; this box
only has `pwsh` installed, so `Process.Start` throws
`Win32Exception: ... No such file or directory`):**
- `Tempest.Core.Tests.Security.CheckVulnerablePackagesScriptTests.SelfTest_PassesItsOwnTwoFixtures`
- `...ACleanScan_ExitsZero`
- `...ASyntheticVulnerableLine_ExitsNonZero`
- `...AnUnparsableScan_ExitsNonZero_RatherThanSilentlyPassing`
- `...NeitherSelfTestNorInputPath_ExitsNonZero_WithAClearReason`
- `Tempest.Core.Tests.ReleaseEngineering.PackagingScriptTests.PackageInstallerScript_IsSyntacticallyValidPowerShell`

**4 DPAPI (`System.Security.Cryptography.ProtectedData.Protect` throws
`PlatformNotSupportedException` on Linux):**
- `Tempest.Core.Tests.Invoicing.SecretStoreTests.WindowsDpapiSecretStore_RoundTrips_GetSetRemove`
- `...WindowsDpapiSecretStore_EncryptsOnDisk_TheFileNeverCarriesThePlaintext`
- `...AStoredSecret_NeverAppearsInTempestDb`
- `Tempest.Core.Tests.Invoicing.Connectors.OAuthAuthoriserTests.AStoredToken_IsNeverWrittenToTempestDb`

**Guard status — confirmed unguarded on non-Windows:** `SecretStoreTests` carries a class-level
`[SupportedOSPlatform("windows")]`, and `OAuthAuthoriserTests.AStoredToken_IsNeverWrittenToTempestDb`
carries the same attribute at the method level. `[SupportedOSPlatform]` is a **static-analysis
attribute only** (feeds the CA1416 platform-compatibility analyzer); it has no effect on xUnit's
test discovery or execution at runtime, so these tests still run — and fail — on Linux. The
`CheckVulnerablePackagesScriptTests` and `PackagingScriptTests` classes carry no platform
attribute at all; their only nod to platform is a doc comment noting CI runs on Windows.

**Recommendation for the report (no code changed here):** give each of these four classes a
custom `[WindowsOnlyFact]`/`[WindowsOnlyTheory]` attribute pair that subclasses
`FactAttribute`/`TheoryAttribute` and sets `Skip` to a fixed reason string whenever
`!OperatingSystem.IsWindows()` at discovery time (the common, well-established xUnit v2/v3
pattern for this — cheaper and more explicit than pulling in `Xunit.SkippableFact`). This
converts these 10 from "fails everywhere except Windows CI" to "explicitly and visibly skipped
everywhere except Windows CI", which is both more honest about what was and wasn't run on a
given box and removes the need for anyone running `dotnet test` on Linux (as this WP just did)
to mentally subtract a known 10 from the failure count every time.

**Verdict:** Verified. **Blocks RC acceptance?** No — this is the already-known, already-
tracked gap the lead's brief names; it does not indicate a real product defect (the Windows
code paths are presumably still exercised in Windows CI). It should still be fixed before GA
for test-suite hygiene, per the recommendation above.

## 8. Release Notes figures cross-check

```
Tempest.Core.Tests:    [Fact] 4,009  +  [Theory] 215   = 4,224 test methods (lower bound)
Tempest.Desktop.Tests: [Fact] 161 + [Theory] 9 + [AvaloniaFact] 656 + [AvaloniaTheory] 10
```

Both lower bounds are comfortably below, and consistent with, the claimed totals (Core:
4,224 ≤ 5,317; Desktop: 836 ≤ 884) — the gap in each case is explained by Theory-family methods
each expanding into several cases, which is exactly the effect a lower bound is supposed to
absorb. Nothing here contradicts the Release Notes' own figures; the actual pass/fail totals
(5,317 and 884 respectively) remain the lead's own figures from the full runs, not
re-derived here.

**Verdict:** Verified (as a lower-bound sanity check, not a re-count). **Blocks RC
acceptance?** No.
