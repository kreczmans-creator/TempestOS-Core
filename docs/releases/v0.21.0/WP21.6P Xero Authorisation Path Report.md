## 1. Why this package exists

`WP 21.6` says the first live authorisation happens "with the lead on
hand; any mismatch fixed". Reading the path the Product Owner would take
in the morning — Settings → Connector *Xero* → Client Id → *Authorise* —
against the code found that the path did not exist. Three defects,
each **Verified** from the source before any change was made:

| # | Defect | Where | Effect on the Product Owner |
|---|---|---|---|
| X1 | The *Authorise* button only re-read the stored state. `OAuthAuthoriser.AuthoriseAsync` — the browser sign-in, loopback redirect, code exchange and token storage — had **no caller anywhere in `src/`**. | `SettingsView.OnAuthoriseInvoicingAsync` | Clicking Authorise could never open the browser; live Xero could not be authorised from the product at all. |
| X2 | Settings stored the typed client id and secret under `Invoicing:ClientId` / `Invoicing:ClientSecret`; the authoriser reads `Invoicing:<Provider>:ClientId` (`ADR-0151`), so a client id typed in the UI was never seen by the Xero or QuickBooks authoriser. Only a value placed in `appsettings.json` or the `TEMPEST_Invoicing__Xero__ClientId` environment variable worked. | `SettingsView` constants, `LoadInvoicingSectionAsync`, `SaveInvoicingSectionAsync`; `OAuthAuthoriser.Key()` | The connector would report "not configured" regardless of what was typed. |
| X3 | The connector selector saved to the persisted settings store (`ISettingsProvider`), but the host chose the connector at start-up from `IConfigurationProvider` only (appsettings/environment/command line), so choosing *Xero* in Settings never took effect at the next start. | `TempestHost` (connector selection), `SettingsView.SaveInvoicingSectionAsync` | The Fake connector kept running, and — because the Fake always answers "Authorised." — the status line read **Authorised.** for a Xero that had never been signed in to (evidence 01, captured before the fix). |

A fourth, found while writing the fix and not previously disclosed: `Process.Start(url)` inside the authoriser was unguarded, so a machine with no browser or URL handler would have thrown through the seam `ADR-0151` says never throws.

## 2. What changed

1. **`IAuthorisableConnector`** (Core, optional seam): `Task<OAuthResult> AuthoriseAsync(CancellationToken)`. `XeroConnector` and `QuickBooksOnlineConnector` implement it by delegating to their own `OAuthAuthoriser`. `FakeInvoicingConnector` deliberately does not (proven by a test). `IInvoicingConnector` itself is unchanged, so no test double changed.
2. **`TempestHost`**: when configuration is silent on `Invoicing:Connector`, the persisted setting (the `Settings` collection of the persistence store, the same key) is read before the connector is built. Configuration still wins when it says anything.
3. **`SettingsView`**: client id and secret are stored under the provider's own keys (`ClientIdSecretKeyFor(provider)` / `ClientSecretSecretKeyFor(provider)`); the legacy provider-less values are shown as a fallback and migrated onto the provider's key on Save, then removed. Switching the selector shows that provider's own credentials. *Authorise* now saves the section first, then: if the chosen connector is not the one this process is running, it says so in words (**"Saved. Restart TempestOS to use Xero — this session is running the Fake connector."**) and stops; otherwise, for a real provider that is not yet authorised, it runs the interactive sign-in (button disabled, status "Waiting for you to sign in to Xero in your browser (up to 5 minutes)…", a five-minute timeout), and shows the outcome in words. An already-authorised provider only refreshes. The Fake only refreshes, as before.
4. **`OAuthAuthoriser.AuthoriseAsync`**: a browser that cannot be opened is a `Failed` result naming the reason, never an exception; the loopback listener is disposed.

Nothing else moved. The loopback port default (49301, inside Windows' dynamic range — Release Notes warning) is unchanged: changing it changes the redirect URI registered in the Xero app, which is the Product Owner's decision.

## 5. What the Product Owner does in the morning (the `WP 21.6` script)

1. In the Xero developer console, the app's redirect URI must be exactly `http://127.0.0.1:49301/callback/` (ADR-0151 addendum). Copy the app's client id (and secret, if the app is not PKCE-only).
2. TempestOS → account chip (top right) → **Settings** → *Connector authorisation*: Connector **Xero**, paste the Client Id (and Secret), click **Authorise**. Expect: *"Saved. Restart TempestOS to use Xero — this session is running the Fake connector."*
3. Close and reopen TempestOS. Settings → *Connector authorisation*: expect Connector **Xero**, the Client Id shown, status **"Not authorised."**
4. Click **Authorise**. Expect the browser to open on Xero's consent page and the status to read *"Waiting for you to sign in to Xero in your browser (up to 5 minutes)…"*. Sign in, choose the organisation, allow access. The browser shows *"Authorisation complete. You can close this window and return to TempestOS."*; the status reads **"Authorised."**
5. If anything else appears, the status line says exactly what happened (port in use, consent denied, token endpoint refusal, browser could not open, five-minute timeout). Record it verbatim.
