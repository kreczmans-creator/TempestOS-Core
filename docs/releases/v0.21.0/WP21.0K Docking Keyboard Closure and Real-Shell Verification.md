## 1. What this Work Package was asked to do

Two things, and deliberately nothing else.

1. **Close `TD-133`'s own named residual** — `ADR-0153` decision 8. With a
   docked panel's tab header focused, `Ctrl+Shift+,` moves that tab one

## 3. Defects found

Driving the real application found two defects that the headless suite did
not. Both are reproduced by new headless tests that fail on the previous
code, and both are fixed here. A third finding is recorded, not fixed,
because it is about the shell's shutdown rather than the docking code, and
because this rig cannot tell a product defect from its own limitation.

### D1 — Closing a tab inside a floating window discarded every panel in every other window (critical, pre-existing, **fixed**)

*How it showed.* A floating window held Properties and the Project Explorer
(that is check K1's own end state). One click on that window's close
chrome — closing the Explorer tab, nothing more — and the floating window
vanished, the Project Explorer vanished, and the main window's **Documents**
panel was gone from the arrangement. Documents is registered
`CanClose: false`: no gesture in this product is supposed to be able to
close it. The main window went on *drawing* the old layout, so the loss was
invisible until the next thing that re-rendered — after which the workspace
held two panels where it had held four.

*Root cause.* A floating window's host renders a **synthetic single-window
tree**: `FloatingPanelWindow.Update` hands it
`new WorkspaceLayoutTree(model.Content, [], LayoutPanels)`, because one root
is all it needs in order to draw. Every gesture that host applied for itself
— close a tab, select one, collapse, pin, drag a splitter, the responsive
rule — therefore produced another single-window tree, and the controller
adopted that as the *whole* arrangement.

*Fix.* The subtree is spliced back into the one window entry it belongs to
(`WorkspaceLayoutController.AdoptSecondaryWindowSubtree`) instead of
replacing the forest. Exactly one window's content changes; the primary
window is not even re-rendered, so it cannot lose focus to someone else's
gesture.

*Age.* Present since floating windows became real windows (`WP 20.10D`),
carried through `WP 21.0A`. Not introduced by this package.

### D2 — The restored focus ring was never drawn (minor, **fixed**)

`PHYSICAL_REVIEW` §7j K3 asks for the focus *ring*, not merely focus.
Decision 7's restore called `Focus()`, whose `NavigationMethod.Unspecified`
deliberately does not set Avalonia's `:focus-visible` — the right choice for
a mouse drag, the wrong one for a key the user pressed. On the real
application the panel moved, the keyboard kept working, and a keyboard-only
user could no longer see where they were. A gesture that arrived from the
keyboard now restores focus *as keyboard focus*; every other operation
restores it silently, exactly as before.

### D3 — The application's own shutdown gate did not run on this rig, so nothing it saves was written (**open, and not attributable from here**)

*How it showed.* Closing the main window with a real
`WM_DELETE_WINDOW` client message (`xdotool windowclose`) removed the window
in under 0.2 s, and afterwards the database held **no**
`Workspace.Layout.Tree` row at all — nor `Desktop.WindowUiState`,
`Desktop.RecentObjects` or `Desktop.FavouriteObjects`, the other four saves
in `MainWindow.Closing`. Only `App.ShutdownRequested` →
`WorkspaceHost.ShutdownAsync` ran (`Workspace.CurrentProject`,
`Workspace.ShellLocation`, `Workspace.State`). Settings writing itself is
healthy: toggling the theme while running wrote `Desktop.Theme` immediately.
A temporary probe placed at the first line of the `Closing` handler printed
nothing at all — the handler is never entered.

*Why this rig cannot convict the product.* There is no window manager on
this display, and `xprop` reports that the `WM_PROTOCOLS` atom has never
been interned by any client on it — so these windows advertise no
`WM_DELETE_WINDOW` protocol, there is no title bar and no close button, and
`Alt+F4` has nobody to deliver it. The closest a review can get here is a
client message the application never agreed to receive, which takes the
window away underneath it. That is a property of the rig, not evidence
about Windows, where §7j is meant to be performed.

*What is worth the lead's attention anyway, from the code rather than the
rig:* `App.cs` sets `desktop.MainWindow` but never `ShutdownMode`, so
Avalonia's default `OnLastWindowClose` applies. Observed here: with the main
window gone, a floating panel window stayed open and the process kept
running. If a floating window can ever outlive the main window on Windows,
the application will appear closed while still running, and
`WorkspaceHost.ShutdownAsync` will not have run. Worth one check on
Windows; it is a shell-lifecycle question, not a docking one, so nothing was
changed here.

Two things a reviewer on real hardware should know before running §7j, both
found the hard way here:

- **A tab header does not take keyboard focus when clicked.** K3 says
  "focus a docked panel's tab": that means reaching it with `Tab`, not
  clicking it. Clicking selects the panel and leaves focus where it was, so
  the keyboard gestures appear to do nothing.
- **There is no "Float" command on a tab.** K1's "(its tab's Float)"
  describes an affordance this build does not have: a panel is floated by
  dragging its tab past the edge of the workspace area. The tab chrome
  offers Collapse, Pin/Auto-hide and Close only.
