# WP 21.5C (Linux variant) — Real-Shell Acceptance Journey

**Branch** `wp/21.5C-linux` · **Platform** Linux / X11 (Xvfb), Avalonia
11.3.20, .NET 10 · **Application under test** the built
`Tempest.Desktop.dll`, launched through its own
`Program.BuildAvaloniaApp().StartWithClassicDesktopLifetime(args)`.

---

## 1. What this is, and why it exists

The execution plan's `WP 21.5C` asked for "the built application launched
on the Windows runner and driven through a smoke journey by UI Automation,
mouse only". This is the Linux variant of that: **a real process, a real
renderer and real operating-system input**, because this repository has
already proved twice (`v0.20.0`, `v0.21.0`, and the `WP 21.7C`
follow-ups) that a headless suite can be entirely green while the real
application still has a defect a person would hit in the first minute.

Before this Work Package the only Linux CI evidence was
`linux-launch-smoke`: the application is started under Xvfb and two log
markers (`Host -> Running.`, `Desktop -> Composed.`) are grepped out of
its log. That proves the shell composes. It proves nothing about whether
a person can *use* it.

What this adds:

- The application is started **in-process, on the main thread, through its
  own entry point** — the real `App`, the real `WorkspaceHost`, the real
  X11 backend, the real Skia renderer, the real SQLite store.
- Every click, keystroke and typed character is delivered **through the X
  server** with `xdotool`. The application cannot tell the runner from a
  person at the keyboard. No Avalonia event is synthesised, and no
  service, view-model or command is ever called directly to make something
  happen.
- The visual tree is read **only** to find controls (by
  `AutomationProperties.Name`, by text) and to assert what is on screen.
- Every step is **screenshotted** from the framebuffer (`import -window
  root`).
- The application is then **closed through the window's own close
  message** and **relaunched on the same persistence root**, and everything
  created is read back twice — once off the running application's screen,
  once straight out of `tempest.db`.

It found four defects the headless suite cannot see, one of which
(`DEFECT-1`) blocks the product's own headline value chain on a clean
machine. One of them is fixed here, with a regression test.

## 3. Design

A new, **non-shipped** console project,
`tests/Tempest.Desktop.RealShell/`, added to `src/TempestOS.slnx` so the
ordinary warning-free build gate compiles it on Windows too. Everything
Linux-only in it is guarded **at runtime** (`OperatingSystem.IsLinux()`,
and the presence of the external tools), never with `#if`, so the Windows
build sees the identical source. It references `Tempest.Desktop` and
nothing else; it references no sample assembly, so
`SampleSeparationTests.TheSampleAssembly_IsDeletable…` is unaffected.

Six small files, no framework, no abstractions beyond a step list and a
few helpers:

| File | What it is |
|---|---|
| `Program.cs` | Starts the real application on the main thread; a background thread drives it. Modes: `journey`, `verify`, `drive`. |
| `OsInput.cs` | `xdotool` and `import`. Pointer moves, clicks, the wheel, key events, typed text, the X11 `WM_DELETE_WINDOW` close, and drivers for the **operating system's own GTK file and save dialogs**. |
| `Ui.cs` | Read-only introspection on the UI thread: every visible control in every window **and every open popup**, with its automation name, its text, its screen rectangle, whether it is enabled, what has keyboard focus, and a **hit test** at a screen point. |
| `Act.cs` | The four things a person does — point, click, type, pick from a drop-down — expressed against what is on screen. |
| `Journal.cs` | The step table, the screenshots, `journey.md` and `journey.tsv`. |
| `MainJourney.cs` / `VerifyJourney.cs` | The journey itself, and the second-launch verification (tree **and** `tempest.db`). |

### Three things the runner refuses to do

1. **It never clicks blind.** A control's own bounds are not enough to know
   a click will reach it: it can be clipped by the scroll viewport, covered
   by an overlay, or scrolled under the shell header while still reporting
   its full rectangle. Every candidate point is **hit-tested against the
   live tree** first, and the click is only sent to a point the control
   itself would receive. (The first run of this journey typed a beam span
   into the field *above* the one it meant, for exactly that reason.)
2. **It never types into a field it has not focused.** After clicking a
   field it waits for that field to actually hold keyboard focus, then
   types, then reads the value back and retries. A click that did not take
   focus otherwise silently overwrites the field that still had it.
3. **It never fakes a step.** Where the real UI blocks it, the step records
   what happened — `Failed`, or `Unknown`, or `not exercised (reason)` —
   and the exit code honours it. Nothing falls back to calling a service.

### Verdicts

- **Verified** — driven through real input and read back off the live
  visual tree (or, for the store step, out of SQLite).
- **Inferred** — driven, outcome follows from what was read, but the thing
  itself was not read. *(Not used in this run: every step is one or the
  other.)*
- **Unknown** — driven, could not be told either way. Never counted as a
  pass.
- **Failed** — driven, and the application did not do what it says it does.

Exit code 0 only if every **required** step passed. The two steps pinned
to open defects are marked not-required, so the runner stays usable as a
regression check while the defects are open; both are still counted and
printed.

## 5. Defects found

### DEFECT-1 — A rate card cannot be created anywhere in the shipped UI, and that blocks the whole commercial chain on a clean machine

**Severity: Major.** On a clean persistence root the **Rate cards library
is empty and nothing in the shipped user interface can add a record to
it**: `LibrariesView` offers an "Add a material" form and an "Add a
person" form and no other; the Reference data surface lists `Rate cards
(0)` with no Add action; the Command Palette offers only *Projects: Pin
Rate Card* (which pins an existing one); and there is no rate-card entry
in `src/Tempest.Core/ReferenceData/Seeding/Datasets/`.

Everything downstream of a rate-card pin is therefore unreachable on a
fresh install:

- **New Project…** shows *"Time cannot be recorded against this project
  until a rate card is pinned."* with **None** as the only choice
  (step 6).
- **Business → Timesheets → Record** disables Grade and Hours and states
  *"No rate card is pinned on Apollo Pump Redesign. Pin one on the
  project's Details tab first."* (step 27). No time can ever be recorded.
- **Business → Invoices → Raise invoice** is refused: *"Project '…' has no
  Released rate-card pin; an invoice request cannot be priced or
  currencied without one."* (step 26). No invoice request can ever be
  raised — not from a completion, and not by the automatic best-effort
  raise that `DeliverableService.CompleteAsync` attempts (which is why
  **New (0)** stays empty while **Available to invoice (1)** fills).

This makes `PHYSICAL_REVIEW.md` §7c C2/C3/C7, §7c D10–D12 and §7d T1 —
all of which assume a released rate card exists, C2 saying "release one
from Evidence → Libraries if none" — **not performable on a clean
machine**. It is also why this journey's own invoicing, timesheet and
finance steps stop where they do.

*Reproduce:* clean root → Engineering → Reference data → Rate cards reads
`(0)`; no Add control anywhere; Ctrl+K "rate" offers only *Pin Rate Card*.
Then Business → Invoices → Raise invoice → Continue.

*Root cause:* no creation surface (`src/Tempest.Desktop/Views/LibrariesView.cs`
has `_addMaterialButton` and `_addPersonButton` only) and no seed
(`RateCardCatalog` is never seeded). `Tempest.Core.BusinessGovernance.Pricing.RateCardCatalog`
itself is complete; only the way in is missing.

**Not fixed here** — it needs a new form with its own validation (a card
carries priced grades, a currency, an effective date and a pricing basis),
or a seeded card, plus tests. That is a product decision, not a one-file
correction. Two candidate fixes: an "Add a rate card" form beside "Add a
material", or a seeded sample card that ships Draft and must be released
like any other record.

### DEFECT-2 — Accepting a quotation leaves the project's own Requirements and Deliverables tabs showing their empty state

**Severity: Medium.** `PHYSICAL_REVIEW.md` §7c D7 says that after D6's
acceptance the Requirements tab lists the requirements and the
Deliverables tab lists the deliverables. It does not. Immediately after
**Accept** reports *"Accepted — 2 deliverable(s) and requirement(s)
created."* and the Quote tab grows its "Created on acceptance" section
with working **Open deliverable** / **Open requirement** buttons, the
Deliverables tab still reads **"No deliverables in this project yet."**
and Requirements reads **"No requirement is allocated to anything in
P-0001 …"**. Switching to another tab and back does **not** refresh them;
only leaving the project and reopening it does (step 15 then reads
*"2 deliverable(s), 0 completed."*).

The objects are real and correctly parented the whole time — the store
holds Project → Milestone `Q-2026-001` → two Deliverables from the moment
of acceptance, and **Open deliverable** opens one right up.

*Root cause:* `ProjectQuoteView.OnAcceptAsync`
(`src/Tempest.Desktop/Views/ProjectQuoteView.cs`) refreshes only itself
(`await RefreshAsync()`), and `Tempest.Core.Quotations.QuotationService`
publishes nothing on the change bus, so the sibling tabs — which are only
re-read by `ProjectWorkspaceView.RefreshAsync`, called on project open —
stay as they were. `PHYSICAL_REVIEW.md` §7d T4 lists exactly this shape
("the tree still shows the requirement's old title until the tab is left
and re-entered") as a **failure** condition elsewhere.

**Not fixed here** — the honest fix is either to publish the acceptance's
writes on the change bus in Core (touching `QuotationService`,
`DeliverableService` and `RequirementsService`) or to give
`ProjectQuoteView` a "the project changed" callback the workspace
subscribes to. Either is more than one file, and the change-bus route has
ordering implications this Work Package is not scoped to judge.

*Step 14 is pinned to this defect and is expected to fail until it is fixed.*

### DEFECT-3 — Raw GUIDs reach the operator in three places

**Severity: Low–Medium** (it is exactly what `PHYSICAL_REVIEW.md` §7a E7
and §7 step 7a count as failures elsewhere: "a GUID where a name should
be").

1. A deliverable completion's own content reads
   `Deliverable '094c92df-1c6a-40bd-8aed-530430ead56d' completed.`
   (step 24, and the editor that opens right up shows it).
2. The invoicing refusal reads `Project '8d70a987-…' has no Released
   rate-card pin …` (step 26) where every other refusal on this surface
   names the project (compare the timesheet refusal in step 27, which
   correctly says *"No rate card is pinned on Apollo Pump Redesign."*).
3. The status bar's own **Selected** segment reads `Selected: Calculation
   73e89395-85c7-46ff-bc96-697016e62752` after a calculation is selected.

**Not fixed here** — three different call sites in two layers.

### DEFECT-4 — Home's "Project status" panel counts 0 open projects while one is open

**Severity: Medium** — a lying zero on the cross-project cockpit, which is
the one thing `PHYSICAL_REVIEW.md` §7c D1 is written to forbid.

With exactly one open project, Home reads **"0 open project(s) in
total."** and all four bars at 0, while the *same dashboard's* Continue
panel names the project, Upcoming milestones lists `Q-2026-001`, and
Projects → Open lists it (step 29; reproduced in five consecutive runs).

*Root cause:* `ProjectHealthStatus`
(`src/Tempest.Workspace/Projects/ProjectStatusReadModel.cs`) has **six**
values — `OnHold`, `Blocked`, `Overdue`, `AtRisk`, `ReadyToInvoice`,
`OnTrack` — but `HomeDashboardView.RenderProjectStatus`
(`src/Tempest.Desktop/Views/Dashboards/HomeDashboardView.cs`, ~line 243)
draws only four bars and then computes the caption as
`bars.Sum(b => b.Value)`. A project classified `Blocked` ("an accepted
quote with no deliverable started" — precisely this journey's project
after step 12) or `ReadyToInvoice` (after step 24) is in neither the chart
nor the total. Before the quotation is accepted the same panel correctly
reads "1 open project(s) in total."

**Not fixed here** — the one-line caption fix (`snapshot.Counts.Values.Sum()`)
would leave a chart whose bars visibly do not add up to their own caption,
which is arguably worse; adding the two missing bars needs a label and a
palette token per bucket, which is a design decision.

### Cosmetic — developer markup shown to the operator

Business → Invoices renders the group heading *"Outstanding / Overdue (0)
— unpaid past its own due date (\`TD-180\`), or needing attention
(Reauthorise, Unknown)"* — a backlog id, in backticks, on a user-facing
surface (step 25, `src/Tempest.Desktop/Views/InvoicingView.cs`). Not
fixed; reported.

## 6. The defect that was fixed, with its regression test

### DEFECT-0 — The organisation picker opened *underneath* the New Project prompt that opened it

**Severity: Major** (a documented flow was unusable), **fixed here.**

`PHYSICAL_REVIEW.md` §7c D2 has the reviewer pick a client in **New
Project… → Client → Add organisation…**, which "opens the real
organisation picker in place — pick from list, or add a new one".

In the real renderer the picker opened **behind** the New Project prompt:
completely obscured, and unreachable by a real mouse click. Its controls
were present, visible and enabled in the tree — so a headless test that
raises the picker's own events directly passes — but the prompt was drawn
over them and swallowed every click. `evidence/realshell/defect-01-organisation-picker-behind-prompt.png`
is the screenshot: the picker's own panel edge is visible behind the
prompt, and nothing of it can be reached.

*Root cause:* the shell's overlays are siblings in one `Grid`
(`src/Tempest.Desktop/Composition/MainWindowComposer.Layout.cs`), and a
Grid's Z-order follows its `Children` order. `OrganisationPicker` is added
**before** `NewProjectPrompt`, so the prompt always won — and the same
geometry applies to any overlay opened from an overlay added later.

*Fix* (one file, `MainWindowComposer.Layout.cs`): the existing
`TrackModal` hook, which already watches each overlay's own `IsVisible`,
now also raises whichever overlay opens last —
`modal.ZIndex = ++topmostModalZIndex;` — so nesting depth decides what is
on top rather than construction order. `ToastHost.ZIndex` is set to
`int.MaxValue` so toasts keep the "above every overlay" position that
being added last used to give them.

*Regression test:*
`tests/Tempest.Desktop.Tests/NestedOverlayZOrderTests.cs` builds a real
`MainWindow` over a real `WorkspaceHost`, asserts the picker is still
constructed before the prompt (so the test stays meaningful), opens the
prompt and then the picker, and asserts the picker's Z-order is above the
prompt's and that it is the topmost visible overlay of them all. It
**fails** on the unfixed code (`picker ZIndex 0, prompt ZIndex 0`) and
passes on the fixed code — verified both ways.

*Verified in the real application afterwards:* step 7 of the journey now
registers a new client organisation through the picker's own fields and
hands it back — which is only possible because the picker is on top and
takes real clicks.

## 7. What was not exercised, and why

Nothing in the journey is recorded as "not exercised" — every step either
ran or is one of the two pinned failures. These are the surfaces the
journey deliberately does **not** reach, and the reason:

| Surface | Why |
|---|---|
| Timesheet entry, invoice **Send** through the Fake connector, **Reconcile now**, real finance figures on the Business/Home dashboards | Unreachable on a clean root — `DEFECT-1`. The journey drives each as far as the product allows and records the refusal verbatim. |
| Independent check by a second principal (§7h R4), evidence **Cite** / **Declare a figure** / **Check** / **Issue** / **Revise** | The evidence record is created with a real file through the real OS dialog and is verified to persist, but the Draft → Checked → Issued acts are reached from the engineering ribbon and the palette rather than the Evidence tab, and mapping that route was beyond this package's own time budget. The second principal *is* created and released (step 5), so the precondition for §7h R4 is in place. |

## 8. Two things worth knowing about the real application

Both were found by running it, and neither is a defect:

- **A release is four audited writes.** Releasing a Draft reference record
  from the Libraries tab takes it from `rev 1` to `rev 5`:
  Revise → Checked → Validated → Released, each its own stored revision
  (`ReferenceReviewService.VerifyAsync`/`ReleaseAsync`). It looks like a
  jump until you read the audit trail.
- **The OS file and save dialogs are drivable.** The evidence file picker
  and the quotation-sheet save picker are real GTK windows this
  application does not own. They are driven here with real keyboard input
  (Ctrl+L, type the path, Return; select-all, type the path, Return), so
  the evidence record really does carry the file's own 70 bytes and
  SHA-256 `c414cd0e…`, byte-identical to the file on disk, and
  `Q-2026-001-quote.pdf` really is written (497,253 bytes, `%PDF-` header).

### One intermittent abort on exit, seen once in nine runs

One run (of nine) ended with the process aborting (SIGABRT, exit 134)
**after** the journey had finished all 35 steps and after the platform
log had recorded an orderly shutdown down to *"Host lifecycle phase
completed: Module Disposal (Dispose)."* — no crash log was written and no
step failed. The two final back-to-back runs used for this report, and
six others, exited 0. It is recorded here rather than dismissed: an
abort on exit is worth knowing about, and one occurrence is not enough to
name a cause.

The runner was changed in response so that the report can never be lost
to it: `journey.md`/`journey.tsv` are written on the driver thread as
soon as the steps finish, **before** the process is asked to end, and
again when the loop returns. In the run above, the step screenshots
survived but the step table did not — that cannot happen now.

## 9. How to run it

```bash
# Everything: build, Xvfb, journey, close, relaunch, verify.
scripts/run-realshell-linux.sh                       # defaults to :102, Debug, artifacts/realshell
scripts/run-realshell-linux.sh --display :99 --configuration Release --out /tmp/realshell
scripts/run-realshell-linux.sh --no-build            # reuse the current build
```

Requires `Xvfb`, `xdotool`, ImageMagick (`import`) and the SDK in
`global.json`; the script checks for each and says which is missing.
Output: `journey/journey.md` (the step table), `journey/journey.tsv`
(one line per step, for diffing two runs), a PNG per step, and the same
again under `verify/`. Exit 0 only if every required step of both passes
passed. The default output directory is `artifacts/`, which `.gitignore`
already excludes, so raw output never reaches git.

To explore the running application by hand — which is how this journey's
own steps were discovered — there is a third mode:

```bash
mkfifo /tmp/drive.fifo
tail -f /tmp/drive.fifo | DISPLAY=:102 dotnet tests/Tempest.Desktop.RealShell/bin/Debug/net10.0/Tempest.Desktop.RealShell.dll \
  --display :102 --root /tmp/root --out /tmp/out --mode drive
# then: echo "names" > /tmp/drive.fifo ; echo "act New Project…" > /tmp/drive.fifo ; echo "into Name=Apollo" > /tmp/drive.fifo
```

`DISPLAY` must be exported before the runner starts: the X11 backend is
native code and reads it out of the real process environment, which a
managed `Environment.SetEnvironmentVariable` on Unix does not touch.
`--display` only names the same display for the input tools.

### CI

`linux-launch-smoke` in `.github/workflows/ci.yml` now runs the journey as
an **advisory** step after its existing launch smoke: `continue-on-error`
on the job *and* on each new step, still not in `gate`'s own `needs:`
list, with the step tables and screenshots uploaded as the
`realshell-journey` artifact. The job's timeout went from 15 to 25 minutes
to cover the extra build and run. `D-025`'s support boundary is unchanged
by this: Linux is still not CI-verified in the sense Windows is, and this
job passing does not make it so.
