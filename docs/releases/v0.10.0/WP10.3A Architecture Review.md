# WP 10.3A — Architecture Review

## Purpose

An independent architectural review — whether "one generic engine,
applied to six disciplines" is genuinely the correct design (not
merely the cheapest one), whether `ADR-0097` is a defensible third
`IWorkspaceManager` extension, and whether every new type was placed
in the correct layer.

## 1. Scope Constraints — Independently Confirmed

Re-read the controlling instruction's own five exclusions and
sixteen-item scope list directly against `git diff --stat`. Every
touched/added file falls under `src/Tempest.Desktop/`, one new file
plus six modified files under `src/Tempest.App/Workspace/`, and test
files. No file under `src/Tempest.Core/` appears anywhere in the diff.

## 2. Per-Contract Compatibility Table

| `IWorkspace` | No | Unchanged |

| `IWorkspaceView`/`IWorkspaceViewFactory` | No | `ObjectEditorView` consumes `IWorkspaceView.ObjectId`/`ObjectKind` read-only; contract itself untouched |

**11/12 unmodified, one additively extended** — the identical
compatibility posture `WP 10.2A` achieved with `ADR-0096`, applied a
second time for a genuinely new, distinct verb (Revise vs.
Rename/Delete).

## 3. "One Engine, Six Disciplines" — Independently Assessed as Correct

Considered the alternative directly: six separate `*EditorView`
classes, one per discipline, each hand-wired to its own Kind(s).
Rejected, independently confirmed correct to reject:

- Every discipline's own real object already composes the identical
  `EngineeringObjectBase` facet set (`ADR-0075`) — `Content`,
  `Status`/`History`, `GetRelationshipsAsync`, `ValidateAsync` all
  resolve identically regardless of discipline. Six separate classes
  would duplicate the identical field-population logic six times, the
  precise anti-pattern `ADR-0075`'s own composition-over-inheritance
  reasoning exists to prevent.
- The genuine per-discipline variation (which Kinds exist, which
  commands are registered) already lives entirely at the
  Workspace-layer registration boundary (`IWorkspaceManager.CanRename`/
  `CanRevise`), which `ObjectEditorView` already consults generically
  — a second, Desktop-layer per-discipline split would duplicate
  information the Workspace layer already owns.
- Genuine discipline-specific *presentation* differentiation (a
  bespoke BOM-fields section for Mechanical, an Execute button for
  Calculations) is real, disclosed future work (`FCR-0068`) — the
  generic engine's own layout (`BuildLayout`) is deliberately built as
  a sequence of independent `Expander` sections, a design that already
  supports a future Work Package inserting one more, discipline-gated
  section without restructuring the class.

## 4. `ADR-0097` — Independently Assessed as Correctly Scoped

Applying Engineering Governance §5's own ADR-creation criteria
directly, mirroring `WP10.2A Architecture Review.md` §4's own method:
Content-revise dispatch is a genuinely new *decision* (how does a View
mutate an object's own free-text content, given `ADR-0063`), with a
real alternative considered and rejected (direct `ReviseAsync` call —
`ADR-0097`'s own Alternatives Considered), and real, disclosed
consequences (a third `IWorkspaceManager` extension, worth naming
again per that same document). Independently concurred: a real ADR is
correct here, not over-formalising a small addition.

## 5. Layer Placement — Correct

`ObjectEditorView`/`DocumentAreaView`'s own content-builder extension
correctly live in `Tempest.Desktop` (presentation-only concepts —
Save/Cancel buttons, dirty-strip asterisks — with no meaning to a
hypothetical non-graphical presentation layer). `ReviseMechanicalObjectCommand`
correctly lives in `Tempest.App.Workspace.Mechanical`, alongside its
five siblings, not `Tempest.Desktop` — it is a real `IWorkspaceCommand`,
reachable from any presentation layer (console Command Palette
included), exactly like every other discipline command.

## 6. Recommendation

**Sound, complete.** Eleven of twelve frozen contracts fully
unmodified, the twelfth extended additively and precedentedly; "one
generic engine" independently assessed as the architecturally correct
choice, not merely the cheaper one; `ADR-0097` correctly scoped as a
real decision, not an over-formalised routine addition; every new type
correctly layered.
