# WP 10.0B — Desktop Application Framework — Implementation Report

## Purpose

The complete implementation record for `WP 10.0B` — the first real code
this project has written against the `WP 10.0A` UX architecture, and
this platform's first-ever graphical desktop application. Not named in
the controlling instruction's own deliverable list, produced anyway
(mirroring every prior implementation Work Package's own precedent) as
the anchor document the five required reviews below examine.

## 0. Scope Discipline

Honoured throughout, confirmed rather than merely asserted:

- **No engineering functionality changes** — zero behavioural change to
  any of the six Engineering Disciplines. Confirmed by `WP10.0B
  Engineering Review.md` §2's own direct test evidence.
- **No Engineering Domain changes** — zero files touched under
  `src/Tempest.Core/EngineeringDomain/` or any Engineering Core
  framework namespace.
- **No Workspace contract redesign** — `IWorkspaceView`,
  `IWorkspacePanel`, `IWorkspaceLayout`, `IWorkspaceManager`,
  `IProjectExplorer`, `IPropertyInspector`, `INavigationService`,
  `ISelectionService` are all consumed exactly as `WP 8.0B` shipped
  them, unmodified. Two small, disclosed, non-contract changes were
  made in `Tempest.App.Workspace` (§4) — neither touches an interface
  signature.
- **Reuse the existing Workspace architecture** — `Tempest.Desktop`
  introduces zero new Workspace concept; every capability it presents
  composes an existing service, exactly as `WP10.0A UX Architecture
  Document.md` §1 requires of every Workspace surface.

## 1. `ADR-0094` — Framework Selection

Avalonia 11.2.3 selected and justified — full reasoning in `ADR-0094`,
not repeated here. Three packages referenced: `Avalonia`,
`Avalonia.Desktop`, `Avalonia.Themes.Fluent`. A fourth,
`Tmds.DBus.Protocol`, is pinned directly to `0.94.2` to remediate a
known high-severity advisory (`GHSA-xrw6-gwf8-vvr9`) in the version
`Avalonia.Desktop` transitively pulls — disclosed, not suppressed, per
this Work Package's own "0 Warnings" requirement.

## 2. `Tempest.Desktop` — Project Structure

A new project, `src/Tempest.Desktop/`, referencing `Tempest.App`
(never `Tempest.Core` directly — every read/write goes through the
Workspace layer, never around it). No `.axaml` markup file exists
anywhere in this project — every View is constructed directly in C#, a
deliberate choice keeping this Work Package's own first Avalonia
integration on one build pipeline rather than two, while remaining a
fully idiomatic, first-class Avalonia authoring style, not a
workaround.

| Controlling Instruction Item | Realised As |
|---|---|
| Application bootstrap | `Program.cs`, `App.cs` |
| Main window | `MainWindow.cs` |
| Workspace host | `WorkspaceHost.cs` |
| Docking framework | `Docking/DockingGrid.cs` |
| Panel host | `Docking/PanelHostControl.cs` |
| Document host | `Views/DocumentAreaView.cs` |
| Status bar | `Views/StatusBarView.cs` |
| Toolbar | `MainWindow.BuildToolbar` |
| Menu system | `MainWindow.BuildMenuSystem` |
| Theme framework | `Theming/ThemeService.cs` |
| Icon framework | `Icons/IconRegistry.cs` |
| Navigation framework | `MainWindow.BuildNavigationFramework` |
| Command Palette host | `Views/CommandPaletteOverlay.cs` |
| Keyboard shortcut framework | `Input/KeyboardShortcuts.cs` |
| Session persistence | Reused unchanged — `WorkspaceHost.StartAsync`/`ShutdownAsync` call `WorkspaceManager.StartAsync`/`ShutdownAsync` directly (`ADR-0064`) |
| Window lifecycle | `App.OnFrameworkInitializationCompleted` + `IClassicDesktopStyleApplicationLifetime.ShutdownRequested` |

Toolbar, Menu System, and Navigation Framework are implemented as
`MainWindow`'s own private composition methods rather than separate
classes — each is a thin, 15–30 line factory over existing
`ICommandRegistry`/`INavigationService` data; extracting them into
their own types would fragment, not reduce, this Work Package's own
complexity.

## 3. Composition Reuse — `EngineeringWorkspaceComposer`

**The single most important design decision this Work Package makes.**
`Tempest.App`'s own console `Program.cs` (top-level statements)
previously performed the entire composition sequence — building
`ITempestHost`, wiring sample Explorer content, starting the
Workspace, and registering all six real disciplines — inline, once,
for the console presentation layer alone. This Work Package extracts
that exact sequence into `Tempest.App.Composition.EngineeringWorkspaceComposer`
(two methods: `Build()`, unstarted; `RegisterEngineeringDisciplines`,
called after start), and rewrites `Program.cs` to call it. Both
`Tempest.App`'s console and `Tempest.Desktop`'s graphical presentation
now call the **identical** code path — not two independently
maintained copies that could drift apart, which is what "must all load
without behavioural change" actually requires as a structural
guarantee, not only a tested-at-one-point-in-time claim.

`WorkspaceHost` (`Tempest.Desktop`) is the graphical presentation
layer's own thin wrapper around this shared composer — the direct
equivalent of what `Tempest.App.Shell.TempestShell` is for the console.

## 4. Two Disclosed, Non-Contract Changes to `Tempest.App.Workspace`

Both found during this Work Package's own real, live testing (§6), both
minimal, both confirmed by direct re-read to leave every public
interface signature untouched:

1. **`[assembly: InternalsVisibleTo("Tempest.Desktop")]`** added to
   `Tempest.App`'s `AssemblyInfo.cs` (alongside the pre-existing grant
   to `Tempest.Core.Tests`) — lets `Tempest.Desktop` reuse
   `WorkspaceManager.StatusBar` (`internal`, no dedicated public
   contract, `WP8.0A UI Architecture.md` §1) directly, rather than
   re-implementing its identical `WorkspaceSelectionChangedEvent`-driven
   logic a second time in a second assembly. A build-visibility grant
   only.
2. **`ProjectExplorer.Id`/`PropertyInspector.Id` changed from
   `Guid.NewGuid()` to a fixed, well-known `Guid` constant** — a
   genuine, disclosed, found-and-fixed pre-existing defect (`TD-26`'s
   own consequences, §6.4) that made cross-restart session persistence
   (`ADR-0064`) impossible to actually exercise correctly. `IWorkspacePanel.Id`'s
   own contract (`Guid Id { get; }`) is completely unchanged — only the
   concrete value-generation strategy.

## 5. What Was Deliberately Not Built

- **No third-party docking library.** `DockingGrid` is a hand-rolled
  `Grid`+`GridSplitter` host — `WorkspaceDockPosition` supports no
  `Floating` value today (`ADR-0095`, reserved), so a full docking
  framework's own floating-window capability would be unused surface.
- **No per-Kind rich Object Editors.** The Document Host renders every
  open `IWorkspaceView` generically (Title/ObjectKind/ObjectId/IsDirty)
  — `WP10.0A UX Architecture Document.md` §8's own bespoke, editable,
  per-discipline editor design remains genuinely future work, not this
  Work Package's own "Document host" framework requirement.
- **No lazy Project Explorer expansion.** The tree loads eagerly,
  one level at a time, appropriate to this project's own current
  sample-data scale — disclosed in `ProjectExplorerView`'s own XML
  documentation.
- **No graph-based Object Relationship View** (`ADR-0093`). Not named
  in this Work Package's own "Demonstrate" list; remains scoped to a
  future implementation Work Package.
- **No Notification Framework integration**, no floating/multi-monitor
  panel placement (`ADR-0095`) — both already reserved by `WP 10.0A`,
  neither in this Work Package's own scope.

## 6. Real Defects Found and Fixed During Implementation

Four genuine, disclosed implementation-time findings — one in this
Work Package's own test code, three in the Workspace/Desktop
presentation-integration layer, none a correctness defect in
already-shipped Engineering Domain/Discipline code, each caught by a
real, failing `Avalonia.Headless.XUnit` test before any commit, exactly
the discipline `WP 9.1A` first established for this project ("caught
by nine failing tests before any commit"). One of the four (§6.3) was
only caught by a full-solution `dotnet test src/TempestOS.slnx` run,
not `tests/Tempest.Desktop.Tests` alone — recorded as its own,
separate lesson (§7).

### 6.1 `ThemeService.Apply` Threw on a Non-UI Thread

`Tempest.Core`'s own async methods (`SettingsProvider` included)
`ConfigureAwait(false)` internally — a caller awaiting
`GetValueAsync`/`SetValueAsync` before applying a theme resumes on a
thread-pool thread, not necessarily the Avalonia UI thread.
`Application.RequestedThemeVariant`'s own setter requires the UI
thread and throws otherwise. **Fixed**: `ThemeService.Apply` now
checks `Dispatcher.UIThread.CheckAccess()` and marshals via
`Dispatcher.UIThread.Invoke` when not already on it — correct
regardless of calling thread, not only in the specific call shapes
this Work Package's own code happens to use today.

### 6.2 `CommandPaletteOverlay` — No Defect, Confirmed Correct

Named for completeness: no genuine defect was found in the Command
Palette itself; its own tests passed on first correct construction
once §6.1/§6.4 were fixed. Recorded here only to disclose that this
component was verified, not merely assumed correct because it built.

### 6.3 `ThemeServiceTests`'s Own Second Test Was Not Self-Contained

Found by a full-solution `dotnet test src/TempestOS.slnx` run (broader
parallelism than running `tests/Tempest.Desktop.Tests` alone) —
`LoadAsync_OnAFreshHost_ReadsThePreviouslyPersistedChoiceBack`
unconditionally asserted the second host's theme equalled `Dark`,
implicitly assuming its own first host started from `Light` and one
`ToggleAsync()` call would always land on `Dark`. Whenever a prior
test (or a prior run's own leftover `persistence-data`) had already
left the shared store on `Dark`, one toggle produced `Light`, and the
hard-coded assertion failed — a test-quality defect, not a production
one. **Fixed**: the test now captures the value its own first host
actually toggles *to*, and asserts the second host reads that same
value back, mirroring the self-contained pattern
`ToggleAsync_SwitchesBetweenLightAndDark_AndPersistsTheChoice` already
used. Re-run four consecutive times without cleaning
`persistence-data` between runs — stable throughout, confirming the
fix, not merely masking the symptom once.

### 6.5 `ProjectExplorer.Id`/`PropertyInspector.Id` Broke Cross-Restart Session Persistence — `TD-26`'s Own Predicted Consequence, Confirmed

**The most significant finding.** `WorkspaceState.LoadAsync` restores
`IWorkspaceLayout` from a persisted `WorkspacePanelPlacement` list
keyed by `PanelId`. `ProjectExplorer`/`PropertyInspector` originally
generated `Id` via `Guid.NewGuid()` — freshly random on every
`WorkspaceManager.StartAsync` call. A genuinely independent, second
process (this Work Package's own `PersistentLayouts_HidingAPanelAndRestarting_RestoresTheSameLayout`
test builds exactly one) would construct a *new* `ProjectExplorer`
with a *new* random `Id`, which could never match whatever `Id` an
*earlier* process had persisted — `IWorkspaceLayout.GetPlacement`
throws `ArgumentException`, "not a known panel," for the new instance's
own real Id. No prior test in this project's history ever exercised
two genuinely independent `WorkspaceManager` instances against the
same persisted session state to expose this. **This is `TD-26`'s own
disclosed "Revisit trigger" ("Any future Work Package building a
scripted, automation-driven, or latency-sensitive Workspace consumer
where a stale first read would be user-visible or consequential")
realised for the first time, confirmed empirically, not merely
predicted.** Fixed minimally: both panels' own `Id` is now a fixed,
well-known `Guid` constant (§4, Point 2) — cross-restart persistence
now round-trips correctly, proven by the same test that first exposed
the defect.

### 6.6 `TD-26` Itself, Reconfirmed Live for the First Time

Separately from §6.5: `WorkspaceManager.StartAsync` returning before
Runtime Host module `Discovery`/`Initialise` completes (`TD-26`'s own
root cause) was directly, reproducibly hit by this Work Package's own
tests — a `SwitchAreaAsync` call immediately after `StartAsync`
intermittently failed with `NavigationItemNotFoundException` before a
`Tempest.Samples` `*WorkspaceExplorerModule`'s own `InitialiseAsync`
had registered its `NavigationItem`. **Not fixed at the source**
(`WorkspaceManager` itself is unchanged, per this Work Package's own
"no contract redesign" scope) — mitigated entirely within
`Tempest.Desktop`: `WorkspaceHost.StartAsync` now polls, bounded to
3 seconds, until all six real discipline `NavigationItem`s are present,
degrading gracefully (no exception) on timeout rather than either
racing or hanging indefinitely.

## 7. Verification

- **Build**: `src/TempestOS.slnx`, Debug and Release, both 0
  Warnings/0 Errors, including `Tempest.Desktop` and
  `tests/Tempest.Desktop.Tests`.
- **Existing suite**: 2026/2026 passing, `tests/Tempest.Core.Tests`,
  unchanged — confirming §4's two `Tempest.App.Workspace` changes
  introduced zero regression.
- **New suite**: 10/10 passing, `tests/Tempest.Desktop.Tests`
  (`Avalonia.Headless.XUnit`), stable across three repeated runs —
  every one of this Work Package's own "Demonstrate" requirements
  proven as real, executable, `dotnet test`-verified behaviour.
- **Cross-test isolation**: `tests/Tempest.Desktop.Tests` share one
  file-based `persistence-data` Settings store by design (`ADR-0064`)
  — serialised via a new `[Collection("Tempest.Desktop WorkspaceHost
  persistence")]`, mirroring this project's own established
  `[Collection("Console output capture")]` precedent for exactly this
  class of shared-external-state contamination risk.
- **Combined suite**: `dotnet test src/TempestOS.slnx`, both projects
  together — **2036/2036 passing** (2026 + 10). One further, genuine
  test-quality finding (§6.3) surfaced only under this combined,
  broader-parallelism run, not when `tests/Tempest.Desktop.Tests` ran
  alone — fixed, then the combined run re-confirmed clean.
- **`TD-34` reconfirmed, not regressed**: one intermittent failure was
  observed in `tests/Tempest.Core.Tests` during combined-suite
  verification, consistent with `TD-34`'s own already-disclosed,
  cross-test-class `Console.Error` race (`WP 9.9.0` Second Pass) —
  re-run of `tests/Tempest.Core.Tests` alone, immediately after,
  passed 2026/2026 with zero failures, matching `TD-34`'s own
  documented "never reproduces in isolation" characteristic exactly.
  Not a regression this Work Package introduces.
