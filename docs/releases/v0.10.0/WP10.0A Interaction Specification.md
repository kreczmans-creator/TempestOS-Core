# WP 10.0A — Interaction Specification

## Purpose

Full interaction detail for Docking, Command Palette, Search, Context
Menus, Tab behaviour, and Keyboard Shortcuts — expanding `WP10.0A UX
Architecture Document.md` §4, §9, §12. Every interaction pattern
`WP8.0A UI Architecture.md` §4 already established (select-to-inspect,
open-to-edit, context menu, jump-to-relationship, keyboard navigation)
is retained in full below; each is re-stated only where a graphical
desktop paradigm changes its fidelity, not its meaning.

## 1. Docking and Panel Interactions

| Interaction | Behaviour |
|---|---|
| Drag panel edge | Live-resizes the panel; `WorkspacePanelPlacement.Size` updates continuously during drag, committed via `ISettingsProvider` on release (not on every intermediate frame — mirrors `ADR-0064`'s own existing write pattern, avoiding a write storm) |
| Drag panel header to another dock position | Redocks the panel (`Left`→`Right`/`Bottom`, or vice versa) — a genuinely new interaction relative to `WP8.0A`'s own terminal-era design, made possible only by pixel-precise drag; still expressed entirely through `WorkspaceDockPosition`'s own existing three values |
| Click panel collapse control | Sets `IsVisible = false`; the panel's own last `Size` is retained, not reset, so reopening restores the identical width (`WP8.0A UI Architecture.md` §2, unchanged) |
| Click "Reset Layout" | `IWorkspaceLayout.ResetToDefault()` — unchanged |
| Attempt to close Document Area | No-op; the Document Area is the one region that cannot be closed (`WP8.0A Workspace Architecture Document.md` §7, unchanged) |

**Not designed here** (`ADR-0095`, reserved): drag a panel header
entirely outside the main window to undock it into its own top-level
window. Named as the eventual interaction that capability will need, not
specified now.

## 2. Command Palette

Full data source: `WP10.0A UX Architecture Document.md` §3 (Command
Bar), `ADR-0070` (unchanged — "first-class global entry point").

| Interaction | Behaviour |
|---|---|
| Invoke (`Ctrl+K`/`Cmd+K` — platform-conventional, exact binding an implementation-phase choice) | Opens the overlay (`WP10.0A Wireframe Sketches.md` §4), focus in the query field |
| Type | Filters `ICommandRegistry.GetDescriptors()` by fuzzy/substring match against label and category, live, no explicit "search" action required |
| Selection exists in Workspace when invoked | Results additionally filtered to descriptors applicable to the selected object's own `Kind`/lifecycle state, exactly as context menus already filter (§4) — the Command Palette and context menu share one filtering rule, never two divergent ones |
| Arrow keys | Move selection within filtered results |
| Enter | Dispatches the selected command via `ICommandDispatcher`, closes the overlay |
| Escape | Closes the overlay, dispatches nothing |
| Empty query | Shows recently-invoked commands (presentation-local, session-scoped state — not persisted, not a new Platform Service) |

## 3. Search

Two distinct search surfaces, named separately because they search
different data and must not be conflated:

1. **Project Explorer filter** — `ProjectExplorer.FilterAsync`
   (`WP 8.1B`, unchanged), live-narrows the tree as the engineer types
   into the Explorer's own filter field. Zero new code path; this Work
   Package specifies only that the filter field is always visible atop
   the Project Explorer panel in the graphical layout (§Screen
   Catalogue §4), not hidden behind a separate "search mode" toggle the
   way a terminal's own constrained header row might have required.
2. **Command Palette query** — §2 above; searches commands, not
   engineering objects.

**No third, unified "search everything" surface is designed.**
Considered and explicitly declined: a single search box spanning both
objects and commands would require a new composed read over
`ICommandRegistry` and every discipline's own `ListAsync` at once — a
new aggregation capability with no real, demonstrated need behind it,
the same "do not build ahead of evidence" reasoning `ADR-0065`
originally applied to Digital Thread traversal.

## 4. Context Menus

Unchanged from `WP8.0A UI Architecture.md` §4: right-click (or its
platform-conventional keyboard equivalent) populates from
`ICommandRegistry`, filtered to descriptors whose `Category` and
applicability match the selected object's `Kind` and current lifecycle
state. **Multi-selection context menus** (`ISelectionService.SelectedItems`,
`WP 9.1A`) show only commands applicable to *every* selected object —
the identical intersection rule the Property Inspector's own
multi-selection state already applies (`WP10.0A Screen Catalogue.md`
§6), stated once here as the shared rule both surfaces follow.

## 5. Tab Interactions

| Interaction | Behaviour |
|---|---|
| Double-click object in Project Explorer | Opens (or focuses existing) tab, unchanged from `WP8.0A UI Architecture.md` §4 |
| Click open tab | Focuses it; updates Property Inspector/Object Relationship View to that tab's own object |
| Click tab close control | Closes only that tab; if dirty (§UX Architecture Document §8), prompts to Discard/Save/Cancel before closing — never a silent discard |
| Drag tab within strip | Reorders tabs; `WorkspaceStateDto.OpenViewIds`' own order updates and persists |
| Drag tab out of strip | **Not designed here** — would imply a second Document Area pane or a floating tab window, both explicitly out of scope (`WP8.0A Workspace Architecture Document.md` §"Deliberately Out of Scope", reaffirmed) |
| Tab strip overflow | Scrolls or reveals an overflow menu (implementation-phase choice); overflowed tabs remain in `OpenViewIds`, only their visual position changes |

## 6. Keyboard Shortcuts

No specific key bindings are fixed here — `WP8.0A UI Architecture.md`
§4 already established this as "an implementation-phase concern, not
fixed here," and this Work Package does not reverse that. What this
Work Package specifies, at the architecture level:

- **Every keyboard-accessible action is also reachable via the Command
  Palette or a visible control** — no keyboard-only capability is ever
  introduced, mirroring §Toolbar Philosophy's own "convenience, never
  capability" rule (`WP10.0A UX Architecture Document.md` §11) applied
  to keyboard shortcuts specifically.
- **Project Explorer and Document Area tabs remain keyboard-navigable**
  (arrow keys, Tab/Shift+Tab focus order) — unchanged from `WP8.0A`.
- **A future implementation Work Package owns the concrete binding
  table**, and should register it discoverably (e.g., surfaced directly
  in the Command Palette's own result rows, as sketched in `WP10.0A
  Wireframe Sketches.md` §4) rather than in a separate, easily-stale
  reference document — named here as a recommendation, not a
  requirement this Work Package can bind without implementation.

## 7. Mouse Interactions

| Interaction | Behaviour |
|---|---|
| Single click (Project Explorer node) | Select-to-inspect (`WP8.0A UI Architecture.md` §4, unchanged) |
| Double-click (Project Explorer node) | Open-to-edit (unchanged) |
| Right-click | Context menu (§4) |
| Ctrl/Cmd+click | Adds to multi-selection (`ISelectionService.ToggleSelectionAsync`, `WP 9.1A`, unchanged) |
| Shift+click | Range-selects between last-selected and clicked node — a genuinely new interaction this Work Package names, achievable with `ISelectionService`'s own existing `SelectedItems`/`ToggleSelectionAsync` shape (no contract change: range selection is a caller-side loop calling `ToggleSelectionAsync` per node in range, not a new service method) |
| Drag-and-drop | **Not designed** — `WP8.0A Workspace Architecture Document.md`'s own "no real demonstrated need" finding is reaffirmed unchanged; every interaction above already has a non-drag equivalent |
