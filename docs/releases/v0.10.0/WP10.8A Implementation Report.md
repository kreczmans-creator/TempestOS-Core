## Part 1 — Honest Ribbon Fallback Messaging

`RibbonView.OnCommandButtonClickAsync`'s final fallback (reached by
every command with no real dispatch route — e.g. Copy, for which no
destination-parent picker exists anywhere in this platform, `FCR-0073`)
previously read:

> "'{DisplayName}' needs a selected target or additional input this
> ribbon does not yet collect — available via Project Explorer's own
> context menu, or the Command Palette (Ctrl+K)."

Both named alternatives were checked directly and found false for every
command that can reach this branch:

- **The Command Palette** — `CommandPaletteOverlay` dispatches via
  `ICommandRegistry.InvokeAsync`, which requires `CommandDescriptor.
  CreateDefault`. A repository-wide `grep` (first performed `WP 10.3B`,
  re-confirmed here) found zero real discipline command registrations
  anywhere in this platform's history ever set that delegate. The
  Palette cannot invoke any real discipline command by Id at all.
- **The Project Explorer's own context menu** — offers exactly
  Open/Rename/Delete/Favourite; it has no Copy, no status-transition,
  and no Create entry.

Corrected to:

> "'{DisplayName}' isn't available yet — no destination picker or
> additional-input UI exists in this platform to collect what it
> needs."

This names no false alternative — a direct instance of the platform's
own "the UI must honestly communicate capability" discipline. No new
UI, no new dispatch path — a one-string correction to an already-real
code path.

## Part 2 — Real Property Inspector Validation

`PropertyInspectorView.AddValidationSection` previously rendered a
fixed message unconditionally, regardless of the selected object's own
Kind:

> "No automated validation is available for this object type yet."

`EngineeringDomainContext` is now a third, optional, additive
constructor parameter — mirroring exactly how `ObjectEditorView` gained
`ICommandDispatcher` the Work Package prior (`WP 10.7A`), the identical,
already-precedented "additive optional dependency" shape. When present,
the section:

1. Resolves the real target via `_domainContext.Repository.FindAsync(_currentId)`.
2. If the target implements `IValidatable`, calls `ValidateAsync()` and
   renders the real result — errors, warnings, or a real "No issues
   found" success row — reusing `ObjectEditorView.BuildSeverityRow`
   directly (changed from `private static` to `internal static`, not
   duplicated — the identical severity-row rendering the Object Editor's
   own Validation section already uses).
3. If the target resolves but does not implement `IValidatable`, or does
   not resolve at all (`domainContext` present but the object is a
   Requirement, `TD-41`), an honest, distinct message is shown instead
   of a fabricated result.
4. If no `EngineeringDomainContext` was supplied at all (defensive path,
   never hit in production), a distinct honest message is shown.

`MainWindow.cs` now passes its own already-resolved `domainContext`
into `PropertyInspectorView`'s constructor (previously omitted).

## Part 3 — Manufacturing "Record Inspection Result"

`"manufacturing.record-inspection-result"` had a real, working command
(`RecordVerificationResultCommand` — the identical command the Object
Editor's own Verification section already dispatches, `WP 10.7A`) but no
Ribbon dispatch route. Wired via the same `ObjectCreationHandlers` seam
every other Ribbon verb uses: an `InputDialog` prompt for Outcome, then
Method, then `commandDispatcher.DispatchAsync(new
RecordVerificationResultCommand(...))`. No new command, no new dialog
type — a disclosed cross-Work-Package reuse of an already-registered
command from a second entry point.

## Genuine Findings During Implementation

1. **`TD-41` gains a second, previously-undisclosed consumer.**
   `PropertyInspectorView.AddValidationSection` gates on the identical
   `EngineeringDomainContext.Repository.FindAsync` call `ObjectEditorView.
   TryCreate` already does — so a selected Requirement's own Validation
   section also cannot resolve a real target, and correctly reports the
   honest "not available for this object here" message rather than a
   fabricated result. Not a new defect — the same, already-registered
   gap, now known to affect a second surface. `TD-41`'s own Consequence
   text updated in the Technical Debt Register.
2. **Found and fixed in place, before any commit, not registered as
   debt** — the Ribbon's own false fallback-message claim (Part 1). A
   genuine, pre-existing defect (present since `WP 10.5B`, when the
   message was first written, true then, quietly become false as later
   Work Packages changed what the Palette/context menu could do), found
   by this Work Package's own direct-investigation discipline and fixed
   at its own source before commit.
