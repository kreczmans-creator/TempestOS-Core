# WP 10.1B — Technical Debt Review

## Purpose

The required, dedicated Technical Debt Review — the full disposition of
`TD-26` and `TD-37` (both this Work Package's own named subjects), plus
the one new item this Work Package's own investigation found and
disclosed, `TD-38`.

## 1. `TD-26` — Resolved

**Before:** `WorkspaceManager.StartAsync` returned as soon as
`ITempestHost.Services` was non-null — a Phase-6 event, several phases
before Module Initialisation/Start (Phase 7) completes. Open since `WP
9.0A`; its own real consequences directly, reproducibly hit by two
independent Work Packages (`WP 10.0B`, `WP 10.1A`), each mitigating one
layer up in `Tempest.Desktop` rather than at the source.

**After:** `WorkspaceManager.StartAsync` now also waits for
`IDiagnosticsProvider.HostState == HostState.Running` before returning
— fixed at its own source, for the first time. `Tempest.Desktop`'s own
now-redundant mitigation was removed. **Disposition: Resolved.**

## 2. `TD-37` — Resolved

**Before:** four `Tempest.Samples` modules
(`engineeringdomain`/`materials`/`requirements`/`requirementsworkspace`)
each failed their own `InitialiseAsync` with a duplicate-registration
error against their own literal Id, root cause not fully diagnosed,
consequence: `EngineeringDomainSampleModule`'s own Risk/Task/Milestone
data never seeded in any Workspace host.

**After:** root cause fully determined — a durable, cross-launch
persistence store (`ADR-0041`) colliding with each affected module's own
fixed, literal business identifiers, seeded by an earlier successful
launch from the same working directory (`WP10.1B Root Cause
Analysis.md` §2.2), never a double-invocation. Each affected module now
checks first and treats an already-registered identifier as its own
prior work; `Tempest.Desktop.Tests` now genuinely isolates its own
persisted state per test, mirroring `Tempest.Core.Tests`' own
established pattern. `EngineeringCockpitTests`' three previously
honest-empty assertions now read real, stable, live data.
**Disposition: Resolved.**

## 3. `TD-38` — New, Open

**`EngineeringObjectFactory<T>` enforces no business-identifier
uniqueness of its own.** Found while investigating `TD-37`:
`EngineeringDomainSampleModule` builds five objects
(`Portfolio`/`Programme`/`Project`/`Assembly`/`SubAssembly`) through
`EngineeringObjectFactory<T>` before reaching the Material registration
that (before this Work Package's own fix) crashed — each of those five
would otherwise have been silently duplicated, with the same displayed
identifier text but a fresh `Guid`, on every restart, never crashing and
never idempotent. Confirmed the identical pattern in
`MechanicalProductStructureSampleModule`, independent of the four
`TD-37`-affected modules. Compounded by a separate, deliberate `WP
8.2C` scope decision, re-confirmed here as context rather than a new
finding of its own: `IEngineeringObjectRepository`/
`IEngineeringRelationshipRepository` are in-memory-only, never rehydrated
from the durable document store on startup — so even a successfully-
created duplicate is invisible to any Workspace read once its own
process exits.

**Not fixed in this Work Package** — both candidate resolutions
(uniqueness enforcement on `EngineeringObjectFactory<T>`/
`EngineeringObjectBase`, or durable-store rehydration for
`IEngineeringObjectRepository`) are genuine Engineering Domain changes,
explicitly out of `WP 10.1B`'s own stated scope. Correctly disclosed
instead, mirroring this project's own established "disclose, don't
necessarily fix everything found in scope" precedent.

**Revisit trigger:** a future, dedicated Engineering Domain Work
Package considering either capability — or any Work Package that
depends on a sample/demonstration module's own object graph remaining
stable and singular across a real, multi-launch session.
