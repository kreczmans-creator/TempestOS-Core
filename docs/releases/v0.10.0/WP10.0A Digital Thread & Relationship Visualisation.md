# WP 10.0A — Digital Thread & Relationship Visualisation

## Purpose

Full detail for `ADR-0093`'s own decision: Object Relationship Views
render one-hop composed reads as a progressively-expandable node-link
graph. Architecture and specification only, expanding `WP10.0A UX
Architecture Document.md` §12.

## 1. Digital Thread Visualisation — What Stays the Same

**Zero change to how data is obtained.** `IRequirementsService
.GetEvidenceAsync` and each sibling framework's own composed read
(`Tempest.Core.Calculations`, `.Verification`, `.EngineeringDomain`
relationship reads) remain the sole data source, exactly as `ADR-0065`
originally established and `ADR-0093` explicitly reaffirms. No
`Tempest.Core` contract changes. No new traversal, index, or cache.

**What changes is rendering shape only** — from a flat, one-hop list
to a one-hop-per-expansion graph (§2).

## 2. Object Relationship Views — The New Rendering Shape

### 2.1 Graph Construction

1. The selected object becomes the graph's own **centre node**, styled
   distinctly from every other node (§Visual Design System §4 — the
   centre node's own Kind icon and lifecycle colour, at a visually
   larger size).
2. Its own direct relationships — exactly what `GetEvidenceAsync`
   already returns for it — become **edges**, each labelled with its
   own relationship kind (`RequirementRelationshipKinds` and each
   sibling framework's own vocabulary, unchanged), connecting to
   **neighbour nodes**.
3. Each neighbour node renders **collapsed** by default — visible, its
   own Kind icon and lifecycle colour shown, but its *own* relationships
   not yet fetched.
4. **Expanding** a neighbour node issues a fresh read (that node's own
   `GetEvidenceAsync`-equivalent), and the results become new edges/
   nodes attached to it — never merged into or replacing the existing
   graph, only added to it.
5. **Collapsing** an expanded node removes every node/edge that was
   added *only* because of that expansion (a subtree removal), unless
   one of those nodes is also independently reachable from a still-
   expanded path elsewhere in the graph, in which case it remains.

### 2.2 What Is Never Cached

Per `ADR-0093` and `WP8.0A UI Architecture.md` §3.3: the graph's own
in-memory node/edge set is **presentation-local, session-scoped
state**, discarded the moment the Object Relationship View closes.
Reopening the same object's Relationship View starts from a fresh
single centre node, re-reading `GetEvidenceAsync` again — identical to
how every other View in this Workspace already re-reads on open
(`WP8.0A UI Architecture.md` §5's own "current object data... not
cached" row, reaffirmed here for the graph specifically).

### 2.3 Layout

**No specific graph-layout algorithm is chosen here** — force-directed,
hierarchical, or radial layout are all implementation-phase choices;
none affects the data model above. The only architectural constraint
named: the centre node's own visual prominence (§2.1, Point 1) must be
preserved regardless of which layout algorithm a future implementation
Work Package selects, so the engineer never loses track of which object
the graph is actually centred on after several expansions.

## 3. Relationship to the Property Inspector

The Object Relationship View and the Property Inspector are two
independently dockable panels (`WP10.0A UX Architecture Document.md`
§6), no longer one combined panel with an internal mode switch. This
is a deliberate split, not an oversight: the Property Inspector answers
"what is true about this object"; the Object Relationship View answers
"what is this object connected to." Both may be open and visible
simultaneously, side by side, in a graphical layout with room for both
— the one improvement this split most directly depends on the desktop
paradigm (`ADR-0092`) to deliver, since a terminal's own limited screen
real estate was the original reason `WP8.0A` combined them into one
panel with a mode switch in the first place.

## 4. Cross-Discipline Behaviour

Every discipline's own composed read already participates identically:

| Discipline | Composed Read | Confirmed By |
|---|---|---|
| Requirements | `IRequirementsService.GetEvidenceAsync` | `WP 7.3A`/`WP 9.1A` |
| Calculations | `EngineeringDomainContext`/`CalculationRecordReader` relationship reads | `WP 9.2A` |
| Verification | `VerificationRecordReader` (direct `IEngineeringDocumentStore.GetReferencesAsync` read, not the permission-gated `GetVerificationHistoryAsync` — `TD-32`, unchanged) | `WP 9.3A` |

**Disclosed, per `WP10.0A Security Review.md` §3:** `TD-32`'s own
already-registered ungated-read characteristic now extends to any
Verification node reached inside this graph view — not a new
vulnerability, but a more visually prominent surface than the flat
list it replaces. `TD-32`'s own Technical Debt Register entry should be
revisited (disposition, not necessarily remediation) when a future
implementation Work Package actually builds this graph view.
| Documents | `EngineeringDomainContext` relationship reads | `WP 9.4A` |
| Manufacturing | `EngineeringDomainContext`/`ManufacturingObjectFactoryRegistry` relationship reads, plus reused Verification/Documents reads for `"Inspection"`/`"WorkInstruction"` Kinds | `WP 9.5A` |
| Mechanical | `EngineeringDomainContext` relationship reads (`groupedUnder`, BOM lines) | `WP 9.0A`/`WP 9.0B` |

**No new read is added for any discipline.** The graph construction
described in §2 is generic over whichever composed read a given
object's own `Kind` resolves to — the identical Kind-keyed dispatch
principle `ADR-0067` already established for Views and Explorer nodes,
applied here to relationship reads for the first time, with zero new
registration mechanism (the dispatch already exists implicitly, since
every discipline's own `IWorkspaceViewFactory` already knows which
service backs its own objects).

## 5. Known Limitation, Disclosed

A densely-connected object (e.g., a Routing with many sequenced
Operation steps, each itself linked to Work Instructions and
Inspections, `WP 9.5A`) can produce a large graph after only two or
three expansions. No automatic pruning, clustering, or "show only N
most relevant" heuristic is designed here — the engineer manages
graph size manually, by choosing what to expand and what to leave
collapsed. Named as a first-iteration, accepted limitation (`ADR-0093`
§Consequences), not a defect.
