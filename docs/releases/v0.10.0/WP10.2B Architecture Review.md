# WP 10.2B — Architecture Review

## Purpose

An independent architectural review — whether "maintain complete
compatibility with all twelve `WP8.0B` contracts" is genuinely true
(not merely "no member signatures changed" on paper), whether every
new type was placed in the correct layer, and whether zero new ADRs is
a defensible outcome rather than a missed decision.

## 1. Scope Constraints — Independently Confirmed

Re-read the controlling instruction's own six exclusions and
fourteen-item scope list directly against `git diff --stat`. Every
touched/added file falls under `src/Tempest.Desktop/` or one new file
under `src/Tempest.App/Workspace/` (`OutputPanel.cs`) plus
`tests/Tempest.Desktop.Tests/`. No file under
`src/Tempest.Core/`, `src/Tempest.App/Workspace/{Mechanical,
Requirements,Calculations,Verification,Documents,Manufacturing}/`, or
any Digital Thread/relationship namespace appears anywhere in the
diff.

## 3. Layer Placement — Correct

Every genuinely new concept (Collapse, Auto-Hide, predefined layouts,
`DesktopPanelUiState`) was placed at the Desktop presentation layer,
never the Workspace layer — the correct call, independently assessed:
none of the three has any meaning to a hypothetical non-graphical
presentation layer (a terminal UI, `ADR-0066`'s own pre-`ADR-0092`
world, would have no concept of a "collapsed strip" or a "flyout"),
exactly the same reasoning that already places `DockingGrid`/
`PanelHostControl`/`ThemeService`/`CommandPaletteOverlay` in
`Tempest.Desktop` rather than `Tempest.App.Workspace`. `OutputPanel`
itself is the one exception, correctly placed in
`Tempest.App.Workspace` alongside `ProjectExplorer`/`PropertyInspector`
— it genuinely does implement a Workspace-layer contract
(`IWorkspacePanel`), unlike its own view (`OutputPanelView`, correctly
Desktop-layer).

## 4. Zero New ADRs — Independently Assessed as Correct, Not a Miss

Applying Engineering Governance §5's own ADR-creation criteria
directly: an ADR records a genuinely new *decision* with real
alternatives considered, not every new class. Three candidate
decisions were considered and each found **not** to meet the bar:

- **Where to persist Collapse/Auto-Hide/Output state** — not a novel
  decision; `ADR-0064`'s own "persist via `ISettingsProvider`" decision
  already generalises to any Settings-shaped state, and
  `WorkspaceState`'s own concrete pattern is directly reused, not
  reinterpreted.
- **How to realise the Auto-Hide flyout without a floating window** —
  a genuinely new *technique* (reposition an already-parented control
  via `Grid` attached properties plus `ZIndex`), but confined entirely
  to one Desktop-local class (`DockingGrid`), with no cross-cutting
  consequence for any other part of the platform — below the bar
  `ADR-0086`/`ADR-0096` each cleared (both had real, disclosed
  consequences for other Work Packages' own future callers).
- **Click-to-dismiss vs. hover-to-peek** — a genuine interaction-design
  choice, but a UX decision, not an architectural one; recorded in
  `WP10.2B UX Review.md` §3, not here.

**Independently concurred: zero new ADRs is correct**, not a missed
opportunity.

## 5. `TD-39` — Correct Debt, Not a Missed ADR

The fixed-brush overlay background (§`WP10.2B Engineering Review.md`
§4) is a straightforward implementation gap, not a design decision —
correctly a Technical Debt entry, not an ADR.

## 6. Recommendation

**Sound, complete.** Twelve-contract compatibility independently
re-verified at the per-contract level, not merely asserted; every new
type correctly layered; zero new ADRs independently assessed as the
correct outcome against Engineering Governance §5's own criteria, not
an oversight.
