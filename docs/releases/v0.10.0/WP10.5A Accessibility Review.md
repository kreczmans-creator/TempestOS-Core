# WP 10.5A — Accessibility Review

## Purpose

This platform's own first dedicated Accessibility Review — assesses
keyboard navigation, focus visibility, colour/contrast, and scaling
across `Tempest.Desktop`, disclosing what was verified directly versus
what is inherited, unverified, from Avalonia's own FluentTheme.

## 1. Keyboard Navigation — Verified for Every New Control

`ToastNotification`'s own close button, `ConfirmationDialog`'s own
Confirm/Cancel buttons, and `EmptyStateView`'s own optional action
button are all ordinary `Button` controls — confirmed directly, each
reachable via Tab and activatable via Enter/Space through Avalonia's
own default `Button` keyboard handling, unmodified. No new control
introduces a custom, non-standard input handler that could break
keyboard reachability.

## 2. Tab Ordering — Inherited From Declaration Order, Spot-Checked, Not Exhaustively Re-Ordered

No `TabIndex` was set anywhere in this Work Package's own new code —
Avalonia's own default tab order (logical-tree declaration order)
governs every new control, matching every existing control in this
platform (none of which sets `TabIndex` either, confirmed by direct
`grep`, zero matches project-wide). `ConfirmationDialog`'s own internal
order (Cancel, then Confirm/Discard, matching its own declared child
order) was spot-checked directly against the source and assessed
correct — Cancel-before-destructive-action is the safer default tab
stop for a user tabbing quickly. A platform-wide tab-order audit across
every existing panel was not performed — genuinely out of this Work
Package's own realistic scope; disclosed as unverified, not claimed.

## 3. Keyboard Focus Visibility — A Real, Disclosed, Deliberately Deferred Decision

`Avalonia.Themes.Fluent.FluentTheme` provides real, working
`:focus-visible` indication for every stock control this platform uses
(`Button`/`TextBox`/`TreeView`/`ComboBox`/`CheckBox`) out of the box —
this is Avalonia's own documented behaviour, not something this Work
Package built or can independently re-verify visually in this
environment (no rendered screenshot capability). `ApplicationPalette.FocusRingBrushKey`
was added as a real, reserved token, explicitly **not** wired into a
global override style in this Work Package — overriding FluentTheme's
own already-correct default with an unverified colour choice was judged
a real risk of shipping something worse, not better, than what already
exists. This is a genuine, disclosed, deliberate deferral, not an
oversight: a future Work Package with access to real visual
verification (a running, visible instance) is the right place to make
this change.

## 4. Colour Contrast — Verified by Direct Value Inspection, Not an Automated Contrast Tool

No automated WCAG contrast-ratio checker was run (none exists in this
project's own toolchain, and adding one is out of this Work Package's
own scope). Every new colour value was instead checked by direct
inspection against its own background pairing:

| Foreground | Background | Pairing |
|---|---|---|
| `SeverityColors` (SteelBlue/SeaGreen/DarkOrange/Crimson) | `PanelBackgroundBrushKey` (Light `#FFFFFF` / Dark `#2A2A2E`) | All four assessed as sufficiently distinct from both panel backgrounds by direct colour-value comparison — none is a near-white-on-white or near-black-on-black pairing |
| `ApplicationPalette` Light palette | White/near-white panel backgrounds | `#0067C0` (focus ring, reserved), `#D0D0D0` (panel border) — the border colour is deliberately subtle (a hairline, not a high-contrast element) |
| `ApplicationPalette` Dark palette | `#2A2A2E` panel background | `#4CC2FF` (focus ring, reserved), `#454549` (panel border) |

Disclosed limitation: this is a direct-inspection pass, not a measured
luminance-ratio calculation — a real WCAG AA/AAA compliance audit
remains disclosed future work.

## 5. Colour Is Never the Only Signal — Verified Directly

Every `SeverityColors`/`LifecycleColors`/`HealthColors`/`CategoryColors`
consumer pairs its own colour with a glyph and/or text label — confirmed
directly by re-reading every call site added or changed in this Work
Package (`ToastNotification`, `ObjectEditorView.BuildSeverityRow`, the
lifecycle status badge). No new colour-only indicator was introduced.

## 6. Screen Scaling / High DPI / Font Scaling — Not Independently Verified, Disclosed Directly

No physical multi-resolution or High-DPI display is available in this
environment to test against. Every new control uses relative,
`DesignTokens`-derived sizing (no fixed pixel dimensions on text)
consistent with the platform's own existing controls, and Avalonia's
own rendering pipeline is DPI-aware by design (unchanged, inherited,
not re-verified here) — the identical trust boundary `WP 10.0B`/
`WP 10.2B` already accepted for this same reason. Not a new gap this
Work Package introduces; a pre-existing, disclosed limitation of this
project's own test environment, restated here because this is the
Work Package that names it as an explicit review category for the
first time.

## 7. Recommendation

**Accept**, with §3's own reserved-but-unwired `FocusRingBrushKey` and
§6's own environment limitation named as the two honest, load-bearing
disclosures of this review — neither blocks acceptance, both are
genuine, not hidden.
