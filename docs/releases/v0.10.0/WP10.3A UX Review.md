# WP 10.3A — UX Review

## Purpose

An independent UX review of the Object Editor Framework — whether one
generic editor genuinely reads as "the Requirements editor"/"the
Mechanical object editor"/etc. to a user rather than an undifferentiated
generic form, whether dirty-state/Save/Cancel/Read-only are coherent
and discoverable, and whether the Validation/Relationship/Lifecycle
sections are genuinely useful rather than merely present.

## 1. Discipline Differentiation — Assessed

Each open editor tab differs by real content, not merely a label:

- **Icon and Kind label** (`IconRegistry.Resolve(_objectKind)`) —
  already-established, discipline-distinct glyphs (`WP 10.0A`/`WP
  10.0B`'s own Visual Design System), reused here directly.
- **Real Identity data** — Identifier, DisplayName, current revision
  number, all genuinely different per object.
- **Real Content** — each discipline's own actual free-text, not a
  placeholder.
- **Real Lifecycle/Relationships/Validation** — genuinely different
  per object, reflecting that discipline's own real data graph.

**Assessed**: a user opening a Requirement vs. a Mechanical Component
sees a visually and substantively different editor, even though the
same C# class renders both — the differentiation lives in the data,
which is exactly correct for a "one engine" design (§`WP10.3A
Architecture Review.md` §3). The generic engine does **not** yet
differ in *layout* per discipline (no bespoke BOM-fields section for
Mechanical, no Execute button for Calculations) — disclosed honestly,
not hidden, as `FCR-0068`.

## 2. Dirty-State, Save/Cancel — Verified Discoverable

- The Save button is visibly disabled (not merely functionally
  inert) until a real edit exists — `_saveButton.IsEnabled = _isDirty
  && !readOnly`, confirmed by direct read.
- The tab header's own `" *"` suffix (`DocumentAreaView.MarkDirty`)
  gives a persistent, always-visible dirty indicator even when the
  editor itself is not the active tab — matching the same convention
  every mainstream text editor already uses, not a novel affordance a
  user would need to learn.
- Cancel is always reachable, regardless of dirty state, giving an
  unambiguous "discard and revert" action distinct from simply
  navigating away (which, disclosed honestly, does **not** prompt for
  unsaved changes — §5, below).

## 3. Read-Only Mode — Verified Coherent

The toggle's own label (`🔓 Editable` / `🔒 Read-Only`) states the
*current* mode, not the action the click will perform — assessed as
the clearer of the two conventions (avoids the classic "does this
button's label describe what IS or what WILL BE" ambiguity toggle
buttons are prone to). Auto-reverting a pending edit when Read-Only is
turned on (rather than leaving disabled fields showing an unsaved,
unreachable edit) is assessed as the correct, less-surprising choice —
the alternative (frozen, disabled, but still-edited fields) would look
like a bug.

## 4. Validation/Relationships/Lifecycle — Genuinely Useful, Not Decorative

- **Validation**: real Errors/Warnings, colour-coded (⛔ red / ⚠
  amber), with an honest "✅ No issues found" for a genuinely valid
  object — never a fabricated "coming soon" placeholder, the first
  section of its kind in this platform's own Desktop layer.
- **Relationships**: each row is independently actionable ("Open →"),
  not a static list — turns the summary into a genuine navigation
  surface, directly serving the "Navigation between related objects"
  scope item rather than treating it as a separate feature bolted on
  afterward.
- **Lifecycle**: real Status plus real recent History — gives a user
  an at-a-glance audit trail without needing to separately query
  revision history.

## 5. Disclosed UX Trade-offs

- **Closing a dirty tab does not prompt for confirmation.** `IWorkspaceView.CloseAsync`
  always returns `true` today (every concrete View's own `IsDirty` has
  been hard-coded `false` since `WP 8.1A`) — this Work Package's own
  new, real dirty state is not wired into that close-confirmation path,
  so an unsaved edit is silently discarded on tab close. A real,
  disclosed gap, not an oversight — building a proper confirmation
  dialog was judged disproportionate scope for this Work Package
  (`WP10.3A Implementation Report.md`'s own disclosed decision);
  named here as a candidate for a focused future enhancement.
- **No bespoke per-discipline layout yet** (§1) — `FCR-0068`.
- **Relationship rows show Kind-string labels for `RelationshipKind`**
  (e.g. `"groupedUnder"`, `"allocatedTo"`) rather than a
  human-friendly phrase — the same raw-string presentation this
  platform's own Property Inspector Relationship facets already use
  (`WP 10.2A`), not a new inconsistency.

## 6. Recommendation

**Sound.** Discipline differentiation genuinely present through real
data, honestly not yet through bespoke layout; Save/Cancel/dirty-state/
Read-only all discoverable through conventional, non-novel affordances;
Validation/Relationships/Lifecycle are all genuinely useful, live
sections, not decorative placeholders. Two disclosed UX gaps (no
close-confirmation on a dirty tab; no bespoke per-discipline layout),
neither release-blocking.
