# WP 10.0A — Architecture Review

## Purpose

An independent architecture review of `ADR-0092` and `ADR-0093` —
this project's first two ADR supersessions — and of the UX package's
own conformance to `FOUNDATION.md`'s non-negotiables and the existing
Workspace contract layer's own design integrity.

## 1. The Supersession Mechanism Itself

`Engineering Governance.md` §5 requires a superseded ADR be "marked as
such in its Status section," with "a new ADR... created referencing
it." This review independently re-read both amended files
(`ADR-0065`, `ADR-0066`) after `WP10.0A Engineering Review.md`'s own
F7 finding and confirms: both Status sections gained a superseded note
naming the superseding ADR and date, both original Context/Decision/
Consequences bodies are byte-identical to their pre-Work-Package
content (confirmed by reviewing the edits made, which touched only the
Status section of each file), and both new ADRs' own Status sections
state "Supersedes `ADR-00XX`" explicitly. This is the first time this
mechanism has been exercised in 93 ADRs — this review confirms it was
exercised correctly on the first attempt, not merely that a
"Superseded" word appears somewhere.

## 2. Is Superseding ADR-0066 Architecturally Justified?

**Yes, on the evidence, and this review independently re-derives the
same conclusion `ADR-0092` reaches, rather than merely accepting its
own stated reasoning.** `ADR-0066`'s own Consequences §Negative named
one, specific reversal condition: "a real, demonstrated need for a
graphical desktop experience." A Programme literally named "User
Experience & **Desktop Application**," commissioned by the Product
Owner, naming multi-monitor behaviour, theme architecture, and
iconography as *required* (not optional) topics, satisfies that
condition as directly as any future evidence plausibly could — this
review cannot construct a stronger form of "demonstrated need" than an
explicit Product Owner commissioning under that exact name. The
alternative — treating the Programme's own title as insufficient
evidence and continuing to satisfy the topic list within a terminal
paradigm — was independently considered by this review (not only by
`ADR-0092`'s own "Alternatives Considered") and rejected on the same
grounds: several named topics (true multi-monitor placement, pixel
iconography) are not achievable inside a terminal at all, regardless of
implementation effort, making a terminal-paradigm answer to this
specific controlling instruction incomplete by construction, not
merely a lesser design choice.

## 3. Is Superseding ADR-0065 Architecturally Justified?

**Yes, with a more precise scope than `ADR-0092`'s.** `ADR-0065` is not
fully reversed — its own core finding (no new traversal/query/
aggregation platform capability is needed) is *reaffirmed*, and this
review specifically checked that `ADR-0093`'s own Decision text does
not quietly reintroduce a new `Tempest.Core` capability under a
different name. It does not: §2 of `ADR-0093` states explicitly "zero
new `Tempest.Core` contract... every read this View performs already
exists, unchanged." This review independently confirms the graph
construction algorithm described (`WP10.0A Digital Thread &
Relationship Visualisation.md` §2.1) is expressible entirely as
repeated calls to the same one-hop composed read already in production
— no transitive closure, no new index. **This is the correct scope for
a supersession**: only the piece of the original decision the new
evidence actually invalidates (the rendering shape) is changed; the
piece the new evidence says nothing about (the traversal mechanism) is
carried forward.

## 4. FOUNDATION.md Conformance

Checked against all nine "What Is Non-Negotiable" principles:

| Principle | Conformance |
|---|---|
| 1. Architecture precedes implementation | Satisfied by construction — this Work Package *is* that architecture phase, explicitly forbidding implementation of its own scope |
| 2. One reason to change, structurally enforced | The Property Inspector/Object Relationship View split (§UX Architecture Document §6) is a direct application of this principle to presentation code — two panels, two reasons to change, where `WP8.0A` had combined them under space pressure a graphical canvas no longer imposes |
| 3. State has exactly one owner | Object Editor draft state (§8) is explicitly presentation-local and owned by the View instance alone, never written elsewhere until a Command commits it — the identical shape `RuntimeModule`'s own immutability established, applied to presentation state for the first time |
| 4. Platform-service vs. module failure distinction | Extended by this Work Package to presentation: Screen Catalogue §19 distinguishes Command rejection / Read failure / Platform-level fault as three categories with three different blast radii, mirroring the platform/module failure distinction structurally |
| 5. Cleanup always guaranteed | Object Relationship View's own collapse behaviour (§Digital Thread §2.1, Point 5) guarantees full subtree cleanup, never a partial or leaked graph state |
| 6. Interruption only at defined boundaries | Not directly exercised by this Work Package's own scope (no long-running operation is introduced) — not applicable, not violated |
| 7. Every non-obvious decision recorded in writing | Satisfied throughout — two full ADRs, plus every companion document's own explicit "Deliberately Out of Scope"/"Reserved" sections |
| 8. No tier of authority substitutes for another | This Work Package's own four independent reviews (Engineering, Security, Systems Engineering, this one) each reach their own verdict rather than deferring to the UX documents' own self-assessment — Technical Review exercised in fact, not only in name |
| 9. Dependencies flow downward only | Reconfirmed: every UX document composes existing `Tempest.Core`/`Tempest.App.Workspace` reads; none proposes a Workspace-layer capability that a Platform Service or Engineering Core framework would need to depend upward on |

**Zero non-conformance found.**

## 5. Architectural Risk Assessment

**Risk 1 — First-ever GUI dependency category, deferred but real.**
`ADR-0092` itself names this; this review adds no new information,
only confirms the risk is real and correctly not resolved prematurely
inside this Work Package (§ADR-0092 Decision, Point 1, `ADR-0094`
reserved).

**Risk 2 — Contract layer must actually remain unchanged once
implementation begins.** This review's own greatest architectural
concern, not fully retireable at the architecture stage: every claim
in this package that "zero contract change is needed" is a *prediction*
about what a future implementation Work Package will discover, not a
guarantee. `WP10.0A Engineering Review.md`'s own F2-F4 findings give
this prediction strong support (the contracts really are
rendering-agnostic today, confirmed by direct read) — but this review
recommends the first implementation Work Package explicitly re-confirm
"zero contract change" empirically once real rendering code exists,
rather than treating this package's own prediction as already proven.
Named as a recommendation for that future Work Package, not a defect in
this one.

**Risk 3 — Two supersessions in one Work Package is a new governance
pattern.** Not a technical risk, but a process one: this is the first
time this project has superseded even one ADR, and this Work Package
supersedes two simultaneously. This review recommends `PROJECT_STATUS.md`
and the ADR Register disclose this prominently (not merely as a routine
count update) precisely because it is a first, mirroring how `WP 9.9.0`
Second Pass's own `TD-34` finding — this project's first live
reproduction of a long-disclosed flake — was given prominent, dedicated
disclosure rather than folded quietly into a routine total-count
update.

## 6. Verdict

**Sound.** Both supersessions are independently re-justified by this
review, not merely accepted on the issuing documents' own say-so; the
package's own "zero contract change" claims are well-supported but
correctly flagged (Risk 2) as a prediction to be re-confirmed, not a
proof; `FOUNDATION.md` conformance is complete across all nine
non-negotiable principles. No architectural finding blocks this Work
Package's own closure.
