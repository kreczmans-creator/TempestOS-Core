# WP 10.0B — Security Review

## Purpose

An independent security review of `Tempest.Desktop`'s own real
implementation — whether the permission model, the two
`Tempest.App.Workspace` changes, and the new GUI dependency surface
preserve every guarantee `WP10.0A Security Review.md` required of the
architecture this code now realises.

## 1. Permission Model — Preserved

Every read/write `Tempest.Desktop` performs goes through the identical
Workspace service calls the console already uses:
`IProjectExplorer.GetRootNodesAsync`/`GetChildrenAsync`,
`IPropertyInspector.InspectAsync`, `INavigationService.OpenAsync`/
`SwitchAreaAsync`, `ISelectionService.SelectAsync`,
`ICommandRegistry.InvokeAsync`. None is wrapped, shortcutted, or
called with elevated context — confirmed by direct read of every
`Tempest.Desktop` source file that calls into `Tempest.App.Workspace`
or `Tempest.Core`. A principal without permission to read or mutate a
given object is denied identically whether the call originates from
`WorkspaceShell` (console) or `MainWindow` (graphical).

## 2. The Two `Tempest.App.Workspace` Changes — Reviewed for Security Impact

**`InternalsVisibleTo("Tempest.Desktop")`**: grants `Tempest.Desktop`
read access to `WorkspaceManager.StatusBar`/`WorkspaceStatusBar`
(current selection's Kind/Id, formatted as text) — the identical data
already exposed publicly via `IWorkspace.Selection.Current`
(`WorkspaceSelection`). No new data becomes reachable that was not
already reachable through the public contract; this grant only saves
`Tempest.Desktop` from re-deriving the same formatted string a second
time. **No security impact.**

**Well-known `ProjectExplorer.Id`/`PropertyInspector.Id`**: changes a
Guid from random-per-instance to fixed-per-type. This review considered
whether a predictable panel Id creates any new attack surface — it
does not: `WorkspacePanelPlacement`/`IWorkspaceLayout` govern only
docking geometry (position, size, visibility), never data access or
authorization; a panel's own `Id` was never a capability token or
credential of any kind, only a dictionary key. **No security impact.**

## 3. New GUI Dependency Surface — `Avalonia`/`Avalonia.Desktop`/`Avalonia.Themes.Fluent`

This platform's first-ever GUI framework dependency, per `ADR-0094`'s
own disclosed cost. This review specifically checked:

- **Known vulnerabilities**: `dotnet list package --include-transitive`
  (also re-run independently by this review) surfaces exactly one
  advisory (`Tmds.DBus.Protocol` 0.20.0, `GHSA-xrw6-gwf8-vvr9`, a Linux
  X11/DBus clipboard integration dependency), already remediated by a
  direct `PackageReference` pin to `0.94.2` (`WP10.0B Implementation
  Report.md` §1). Confirmed: `dotnet build` reports 0 Warnings after
  the pin, re-verified by this review's own clean rebuild.
- **License**: Avalonia is MIT-licensed — no commercial, per-seat, or
  copyleft obligation, consistent with this platform's own existing
  licensing posture (`ADR-0050`).
- **Attack surface**: a desktop GUI framework processes local window-
  manager/input events only in this Work Package's own scope — no
  network listener, no remote content rendering (no embedded browser/
  web view), no file-format parser beyond what the .NET base class
  library and Avalonia's own font/image loading already provide. This
  review found no new externally-reachable attack surface introduced
  by adopting Avalonia specifically, as distinct from the general risk
  any new dependency carries (already disclosed, `ADR-0094`).

## 4. Command Palette — No Authorization Bypass

Confirmed directly: `CommandPaletteOverlay.InvokeSelectedAsync` calls
`ICommandRegistry.InvokeAsync(descriptor.Id)` only when
`descriptor.CreateDefault is not null` — the identical `null`-check
`ICommandRegistry.InvokeAsync`'s own contract already documents as a
precondition (`CommandException` otherwise). No command becomes
invokable through the palette that was not already invokable through
any other caller holding only the command's Id.

## 5. Session Persistence — No New Data-at-Rest Risk

`WorkspaceHost` writes nothing new to disk — `WorkspaceManager.StartAsync`/
`ShutdownAsync` are called unmodified, persisting through the existing
`ISettingsProvider`/`IPersistenceStore` (`ADR-0064`). `ThemeService`
adds exactly one new Settings key (`Desktop.Theme`, a plain
"Light"/"Dark" string) — no sensitive data, confirmed by direct read
of `ThemeService.cs`.

## 6. Finding: Local Persistence Store Location Is Process-CWD-Relative

**Disclosed, pre-existing, not introduced by this Work Package.**
While verifying §5, this review directly observed
`PersistenceStore.DefaultRootPath` ("`persistence-data`") resolves
relative to the current working directory at process start, not a
fixed, per-user profile location (e.g., `%AppData%`/`~/.config`). For
a console tool launched from a terminal, this is a reasonable default.
For a graphical desktop application launched from a shortcut or file
manager (a materially more likely launch path for `Tempest.Desktop`
than for `TempestShell`), the effective working directory — and
therefore where session state and Settings persist — becomes
launcher-dependent and potentially unpredictable to the end user.
**Not a defect this Work Package introduces or is chartered to fix**
(the persistence mechanism itself is unchanged, `ADR-0064`), but a
genuinely new consideration this Work Package's own desktop launch
path surfaces for the first time — recorded here and in `WP10.0B
Technical Debt Review.md` for a future Work Package's own attention.

## 7. Verdict

**No release-blocking or Work-Package-blocking security finding.**
Permission model fully preserved; the one new dependency's own known
vulnerability is remediated and disclosed; one genuine, pre-existing,
non-blocking consideration is surfaced (§6) for future attention.
