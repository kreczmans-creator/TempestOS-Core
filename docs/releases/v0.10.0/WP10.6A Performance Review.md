# WP 10.6A — Performance Review

## Purpose

The required, dedicated Performance Review — verifying every new code
path this Work Package introduced against real algorithmic-complexity
analysis and real, measured `dotnet build`/`dotnet test` timings, never
fabricated profiler output.

## 1. Methodology, Disclosed

No dedicated profiling tool exists anywhere in this repository or its
own tooling — confirmed by direct search, mirroring every prior
Performance Review's own identical disclosure. Two real, honest
evidence sources are used instead: (1) direct algorithmic-complexity
analysis of every new or modified code path, against this platform's
own real, disclosed data-volume scale (single digits to low tens of
objects per discipline, per every prior Work Package's own established
finding); (2) real, measured `dotnet build`/`dotnet test` wall-clock
timings from this Work Package's own verification runs.

## 2. Startup — No Measurable Regression

`TempestHost.ExecuteStartupPhasesAsync` gains exactly two new
`services.Singleton<TInterface, TImpl>()` registration calls
(`IMacroManager`, `IInputBindingRegistry`) — registration itself is
`O(1)` (a dictionary insert into the DI container's own service map,
unchanged mechanism); neither service is constructed eagerly (this
platform's own container resolves lazily, confirmed by re-reading the
`Singleton<T>` implementation, unchanged this Work Package). The one
genuinely new startup-adjacent work is `MacroWorkspaceRegistration.
Register`'s own `macroManager.LoadAsync()` call — `O(m)` in the number
of previously-persisted macros (a JSON deserialize plus `m` descriptor
registrations); for zero-to-low-tens of macros (the only realistic
scale for a "foundation" capability with no authoring UI predating this
Work Package), this is imperceptible, well under one Settings-read's
own already-accepted cost.

## 3. Undo/Redo — `O(1)` Per Operation

`UndoRedoStack.Record`/`UndoAsync`/`RedoAsync` are all `O(1)` amortised
(a `List<T>` append/removal at the end, bounded by `Capacity = 50` —
the one `RemoveAt(0)` on overflow is `O(n)` in a 50-element list, i.e.
effectively constant). `ObjectEditorView`'s own new pre-commit-name
capture is a single field read, already-computed (`_originalName`),
adding zero new work to the Rename commit path beyond the
already-existing `RenameObjectAsync` dispatch itself.

## 4. Command History / Background Tasks — Bounded, `O(1)` Amortised

`CommandHistoryLog.Record`/`BackgroundTaskRunner`'s own task-tracking
are both bounded lists (`Capacity` 200/50 respectively) with the
identical `RemoveAt(0)`/oldest-eviction shape as Undo/Redo — `O(1)`
amortised, memory strictly bounded regardless of session length.
`OutputPanelView.RefreshHistory`/`RefreshBackgroundTasks` are each one
`O(n)` `Select`/`ToList` pass over an already-bounded (≤200/≤50) list,
called only on a real state change (`Changed` event) or an existing
`RefreshStatusBar` call site — never on a timer, never unconditionally
on every frame.

## 5. Recent/Favourite Objects — Bounded, Real Persistence Cost Disclosed

`RecentObjectsState.Record` is `O(n)` in current entry count for the
`RemoveAll` dedup check, bounded by `Capacity = 15` — negligible.
`FavouriteObjectsState.IsFavourite`/`Toggle` are `O(n)` linear scans
over the favourites list — no capacity bound exists on Favourites
(unlike Recent Objects), a deliberate choice (a user's own genuinely
favourited object count is expected to stay small in practice,
disclosed, not artificially capped) — `O(n)` remains imperceptible at
any realistic favourites-list size a single engineer would maintain.
Both `SaveAsync` calls write one JSON blob via the existing
`ISettingsProvider.SetValueAsync` — the identical, already-accepted
cost `UserSettings`/`WindowUiState` already impose on every save.

## 6. Macro Execution — `O(steps)`, No Hidden Cost

`RunMacroCommandHandler.HandleAsync` is a plain `foreach` over
`StepCommandIds`, each step an ordinary `ICommandRegistry.InvokeAsync`
call — the identical per-command cost any direct invocation already
has, multiplied by step count, with no additional overhead per step
beyond the loop itself. Routed through `IBackgroundTaskRunner.RunAsync`
from the Command Palette — confirmed `RunAsync` adds only `O(1)` list
bookkeeping around the `await`ed work itself, never a second thread
(§7, below) or any measurable dispatch overhead.

## 7. "Background" Is Non-Blocking, Never a New OS Thread — By Design

Confirmed by direct read: `BackgroundTaskRunner.RunAsync` never calls
`Task.Run` — the supplied work is `await`ed directly on the calling
(UI) `SynchronizationContext`. This is a deliberate, disclosed design
choice (`IBackgroundTaskRunner`'s own remarks): every command handler
in this platform is already `async`/non-CPU-bound (in-memory repository
reads/writes), so a dedicated background thread would add Avalonia
UI-thread-marshalling complexity and risk for zero real throughput
benefit — mirrors `BusyOverlay.RunAsync`'s own already-accepted,
already-shipped identical precedent. Confirmed no UI-thread blocking
call was introduced anywhere in this Work Package's own new code —
every new `ISettingsProvider`/`ICommandRegistry`/`IWorkspaceManager`
call is `await`ed, never `.GetAwaiter().GetResult()`'d from inside an
event handler that could be reached from a hot interaction path (the
handful of `.GetAwaiter().GetResult()` calls that do exist —
`MainWindow`'s own constructor-time `LoadAsync` calls for
`RecentObjectsState`/`FavouriteObjectsState` — run exactly once, at
startup, mirroring `UserSettings`/`WindowUiState`'s own identical,
already-accepted constructor-time-synchronous-load pattern).

## 8. `InputBindingRouter` — Negligible Per-Provider Overhead

`Register`/`Unregister` are `O(1)` dictionary operations; routing a
`CommandRequested` event is one `async void` method invocation plus one
`ICommandRegistry.InvokeAsync` call — no polling, no timer, purely
event-driven. `KeyboardCommandBindingProvider.HandleKeyDown` is one
`Dictionary<KeyGesture, string>` lookup per keystroke — `O(1)`, called
only from `MainWindow.KeyDown`, after the fixed `KeyboardShortcuts`
handler has already run (no duplicated dispatch work).

## 9. Measured Verification

Combined test suite (which constructs a real `WorkspaceHost`, and
therefore a real Runtime Host, dozens of times, including every new
test in this Work Package): **2238 tests, 2062 `Tempest.Core.Tests` in
~2m20s, 176 `Tempest.Desktop.Tests` in ~4m40s** — both materially in
line with this Work Package's own pre-change baseline (2201 tests,
comparable combined wall-clock range in the immediately-preceding full
run of the same suite before this Work Package's own new tests were
added). No test in this Work Package's own three new files took
measurably longer than any comparable existing `WorkspaceHost`-backed
test.

## 10. Conclusion

Every new code path is `O(1)` or bounded-`O(n)` against a small,
capped, or genuinely-small-in-practice input; no new blocking call
reaches the UI thread; "background" work is non-blocking by design,
never a new OS thread, a deliberate, disclosed choice matching this
platform's own established `BusyOverlay` precedent. No measurable
startup or runtime regression found.
