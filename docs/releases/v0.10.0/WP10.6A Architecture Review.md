# WP 10.6A — Architecture Review

## Purpose

The required, dedicated Architecture Review — verifying the three
genuine architectural decisions this Work Package made (Undo/Redo,
Macro-as-Command, External Controller abstraction) each meet Engineering
Governance §5's own ADR-creation criteria, are each correctly recorded,
and that every one of them is additive against the Command Framework
and the twelve frozen `WP8.0B` Workspace contracts — never a reopening.

## 1. Three New ADRs, Each Assessed Against §5

**`ADR-0098` (Undo/Redo)**: meets §5's criteria — a genuine choice
between a new Command Framework contract (`IUndoableCommand`) and a
Desktop-local delegate stack, with real, lasting consequences for how
every future reversible action is built. **`ADR-0099`** (Macro-as-
Command): meets §5 — the choice to route macro execution through the
existing `ICommandRegistry` rather than a parallel `IMacroManager.RunAsync`
entry point directly determines whether every future command-invoking
surface needs its own macro-aware branch. **`ADR-0100`** (External
Controller abstraction): meets §5 — establishes the shape every future
Stream Deck/MIDI/game-controller integration must implement against,
a genuine, lasting interface commitment.

All three verified Accepted, dated, cross-referenced to this Work
Package, and added to `ADR Register.md`'s own Entries table
(`ADR-0098`–`ADR-0100`, following `ADR-0097` — itself found missing
from the Register's own table during this review and fixed, §5 below).

## 2. Command Framework — Confirmed Zero Changes

Direct diff of `src/Tempest.Core/Commands/` against the pre-`WP 10.6A`
tree: zero files modified. `ICommand`, `ICommandDispatcher`,
`ICommandRegistry`, `CommandDescriptor`, `ICommandHandler<T>`,
`CommandResult` all byte-for-byte unchanged. `RunMacroCommandHandler` is
registered via the existing, unmodified `ICommandDispatcher.RegisterHandler<T>`;
every macro descriptor is registered via the existing, unmodified
`ICommandRegistry.RegisterDescriptor`. `ADR-0037`'s own "exactly one
handler per command type, resolved by concrete type" design is honoured
exactly — `RunMacroCommand` is one command type, one handler, carrying
`MacroId` as ordinary data, indistinguishable in shape from any other
command in this platform.

## 3. Workspace Contracts — Confirmed Zero Changes

None of the twelve frozen `WP8.0B` Workspace contracts
(`IWorkspaceManager` included) were touched. `IWorkspaceManager.
RenameObjectAsync` (`ADR-0096`) is called by `ObjectEditorView`'s own
Undo/Redo recording exactly as it already was for the forward Rename —
Undo/Redo's own real breadth across six disciplines is a direct,
verified consequence of `ADR-0096`'s own prior Kind-agnostic design
decision, not a new one.

## 4. Layering — Where Each New Type Lives, and Why

`Tempest.Core.Macros`/`Tempest.Core.Input`: Platform-Service-shaped,
zero UI dependency, usable identically by a future console or headless
host — the identical reasoning `ICommandRegistry` itself already
established for living in `Tempest.Core`. `Tempest.App.Workspace`
(`UndoableAction`/`IUndoRedoStack`/`MacroWorkspaceRegistration`):
needs `IWorkspaceManager`/`ICommandDispatcher`, App-layer-shaped,
mirroring where `WorkspaceManager` itself lives. `Tempest.Desktop`
(`RecentObjectsState`/`FavouriteObjectsState`/`CommandHistoryLog`/
`IBackgroundTaskRunner`/`KeyboardCommandBindingProvider`/
`MacroManagerDialog`): genuinely Desktop-local UI state and
presentation, mirroring `UserSettings`/`WindowUiState`/
`DesktopPanelUiState`'s own established placement precedent exactly.
Every placement decision traces to an existing precedent already in
this codebase — no new layering pattern was invented.

## 5. A Genuine, Disclosed Pre-Existing Drift, Found and Fixed

While cross-checking `ADR-0097`'s own file against `ADR Register.md`'s
own Entries table (a routine step before adding `ADR-0098`–`ADR-0100`
in sequence), this review found the table's own row for `ADR-0097` was
missing entirely — the file existed, `WP 10.3A`'s own narrative text in
the Register's `Last Reviewed` cell already named it as added, but no
table row had ever been created. The Register's own `Total`/`Related
ADRs` fields were correspondingly stale (`95`/`96` instead of the true
`96`). Both fixed directly in this Work Package's own governance pass —
the identical "found and fixed, disclosed, not silently backfilled"
discipline `WP 9.1A`/`WP 10.0A`/`WP 10.2B` each already established for
this same register.

## 6. Alternatives Rejected, and Why

See `ADR-0098`/`ADR-0099`/`ADR-0100`'s own Alternatives Considered
sections directly. Independently re-assessed here: an `IUndoableCommand`
contract was the strongest competing design for Undo/Redo, and was
rejected on a concrete, verifiable fact (no real command in this
platform carries prior-state data), not a stylistic preference — this
review re-confirmed that fact by direct inspection of every Rename/
Set-Status/Set-Priority/Set-Owner command's own constructor across all
six disciplines.

## 7. Conclusion

Three genuine architectural decisions, each meeting §5's own criteria,
each recorded, each verified additive against both the Command
Framework and every frozen Workspace contract. One genuine, pre-existing
governance-register drift found and fixed in the same pass. No further
architectural finding from this Work Package warrants its own ADR — the
remaining new types (`RecentObjectsState`, `CommandHistoryLog`,
`IBackgroundTaskRunner`, `MacroManagerDialog`) are each straightforward
applications of an already-established pattern (`UserSettings`'s own
persistence shape; `OutputPanel`'s own "extend an existing panel"
precedent), independently assessed against §5 and found not to meet it.
