# WP 10.3B — Ribbon, Toolbar & Command Experience — Implementation Report

## Purpose

The complete implementation record for `WP 10.3B` — a professional
command system for `Tempest.Desktop`: a real, tabbed Engineering
Ribbon, a Quick Access Toolbar, and command discoverability/context-
awareness features, built entirely as a view over the existing
`ICommandRegistry`/`Command Palette`, never a second registration
mechanism, never bypassing `ADR-0070`.

## 0. Scope Discipline

Direct `git status`/file-level review confirms every touched or added
file lives under `src/Tempest.Desktop/`. Zero files under
`src/Tempest.Core/`, `src/Tempest.App/Workspace/`, or any Engineering
Domain namespace. Zero floating windows, zero Digital Thread graph
code, zero new command framework — confirmed directly (§7).

## 1. The Ribbon — One Generic Engine Over `ICommandRegistry.Items`

`RibbonView` (`src/Tempest.Desktop/Views/RibbonView.cs`) groups
`ICommandRegistry.Items` by `CommandDescriptor.Category` into one tab
per discipline — six tabs today, matching the six real Engineering
Disciplines exactly, with zero hardcoded per-discipline knowledge.
Registers nothing of its own — exactly like `CommandPaletteOverlay`
(`ADR-0070`), it is a *view*.

**Context-sensitive ribbon tabs**: `RibbonView.SelectTabForArea`
matches the active Navigation area's own title against each tab's own
Category by substring (e.g. "Mechanical Product Structure" contains
"Mechanical") — a disclosed, deliberate heuristic requiring no
coupling to `Tempest.Samples`' own module Id constants. Wired from
`MainWindow.SetCurrentArea`, the single existing consolidation point
already called from every area-switch path (Ribbon tab click, the
Engineering Cockpit's own area cards, the default first-area selection
on startup) — one line added there keeps the Ribbon in sync with all
of them, not just the new one.

**Command grouping**: no descriptor sets a "group" field (none exists
in the frozen `CommandDescriptor` shape, unmodified). Every command Id
is classified by its own well-known verb suffix (`.create`, `.rename`,
`.delete`, ...) into one of four groups — Create, Organize, Lifecycle,
Actions — a real, deterministic, disclosed heuristic derived from data
every discipline's own registration already provides.

**Command icons**: the identical situation — `CommandDescriptor.Icon`
is `null` for every one of this platform's own ~80 registered
descriptors (confirmed by direct `grep`, zero results). A deterministic
glyph, derived from the same verb-suffix classification, stands in;
real, authored per-command icons remain disclosed future work
(`FCR-0069`).

**Large/small buttons**: Create-group commands render large (icon
above label, centred); every other command renders small (icon beside
label) — the conventional ribbon sizing convention, applied
deterministically.

## 2. Selection-Aware, Real Dispatch — Three Verbs, Honestly Scoped

`CommandDescriptor.CreateDefault` is `null` for every registered
command (confirmed by direct `grep` — zero call sites set it anywhere
in this platform's history), so `ICommandRegistry.InvokeAsync` cannot
invoke any of them by Id alone. Rather than inventing a generic
parameter-binding mechanism (explicitly out of scope — "No new command
framework"), the Ribbon reuses the three real, already-Kind-keyed
dispatch verbs `ADR-0096`/`ADR-0097` already built for exactly this
problem:

- **Delete** dispatches immediately (`IWorkspaceManager.DeleteObjectAsync`)
  — needs no input beyond the current selection.
- **Rename**/**Edit** (Revise) route to the real editing surface that
  already collects the required text input — the Object Editor tab
  (`WP 10.3A`), opened via the existing `INavigationService.OpenAsync`
  + `DocumentAreaView.ShowTab` — rather than duplicating a text box
  inside the ribbon.
- **Every other command** (Create, Move, Copy, Duplicate, Execute,
  Set Status, ...) is shown — per `ADR-0070`'s own "disabled, not
  hidden" discoverability principle — but honestly reports it needs
  more input than a button click supplies, never silently doing
  nothing.

## 3. A Genuine, Disclosed Pre-Existing Defect, Found and Fixed

Building the Ribbon's own honest "cannot invoke by Id alone" case
surfaced the identical problem already latent in
`CommandPaletteOverlay.InvokeSelectedAsync`: pressing `Enter` on a
selected command with no `CreateDefault` — every real discipline
command, ever, since `WP 8.1A` — closed the palette and did **nothing
else**, no error, no feedback, silently. Confirmed via direct `grep`
(zero `createDefault:` call sites anywhere) and a new, dedicated test.
Fixed in place, before this Work Package's own commit: a new
`CommandUnavailable` event, raised instead of the previous silent
no-op, wired in `MainWindow` to a real Status Bar message — the same
"found while building something else, fixed before sign-off"
discipline `WP 10.2A`'s own Property Inspector fix already established.

**A second, genuine, disclosed defect, found by this Work Package's
own tests, before commit**: `RibbonView.Rebuild()` never called
`RefreshEnablement()` after constructing every selection-aware button
— every Delete/Rename/Edit button defaulted to Avalonia's own
`Button.IsEnabled = true` regardless of whether a real selection
existed yet, dishonestly appearing available immediately on startup,
before the user had selected anything. Fixed in place — `Rebuild()`
now calls `RefreshEnablement()` unconditionally at its own end — caught
directly by `RibbonViewTests.RefreshEnablement_ReflectsTheRealCurrentSelectionsCapabilities`
before any commit.

## 4. Quick Access Toolbar and the Old Toolbar/Navigation Framework — Consolidated, Disclosed

The old, minimal two-button Toolbar (`WP 10.0B`) is subsumed into a new
Quick Access Toolbar (`BuildQuickAccessToolbar`) — Command Palette and
Theme unchanged, joined by Reset Layout (`WP 10.2B`, already real,
previously reachable only via the `_Layout` menu). The old Navigation
Framework's own standalone area-switch button row (`BuildNavigationFramework`)
is retired entirely — a Ribbon tab click now both switches the
Navigation area (`CategorySelected`) and shows that discipline's own
commands, so the two concerns need one control, not two. Both
consolidations are deliberate and disclosed, not silent removals —
every action remains reachable exactly as before, through one surface
instead of two.

## 5. Tooltips, Status-Bar Command Hints, Keyboard Shortcut Display

Every Ribbon button's own tooltip shows `CommandDescriptor.Description`
(falling back to `DisplayName`). `StatusBarView` gained a seventh
segment, Hint — `PointerEntered`/`PointerExited` on every Ribbon
button sets/clears it via a real, live interaction, never scripted.
Keyboard shortcut display is honestly scoped: no discipline command has
a real keyboard shortcut of its own today (only global UI actions —
`Ctrl+K`, `Ctrl+Tab`, ... — do, and none of those are
`CommandDescriptor`-registered) — a real, pre-existing, disclosed gap,
not fabricated here.

## 6. Recently-Used Commands and Command Search Integration

A bounded (5), in-memory, per-session most-recently-used list, updated
on every real dispatch (Delete succeeding, Rename/Edit opening an
editor, or a future `CreateDefault`-backed invocation), rendered as its
own section at the top of whichever tab the command belongs to.
Command search integration reuses `CommandPaletteOverlay` directly (the
Quick Access Toolbar's own Command Palette button) — zero duplicate
search implementation.
