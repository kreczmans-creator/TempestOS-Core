# WP 10.4A — Digital Thread Visualisation — Implementation Report

## Purpose

The complete implementation record for `WP 10.4A` — a graphical Digital
Thread viewer over the existing Engineering Domain: an interactive,
progressively-expandable node-link graph, realising `ADR-0093` and
`WP10.0A Digital Thread & Relationship Visualisation.md` as real,
working code for the first time. Every graph edge is a live read of an
already-existing composed relationship — never a new traversal
mechanism, never a cached transitive closure.

## 0. Scope Discipline

Direct `git status`/file-level review confirms every added file lives
under `src/Tempest.Desktop/DigitalThread/` (new) plus one integration
touch to `src/Tempest.Desktop/MainWindow.cs`. Zero files under
`src/Tempest.Core/` or `src/Tempest.App/Workspace/`. Zero floating
windows, zero multi-monitor code, zero automation framework, zero new
Workspace docking slot — confirmed directly (§7).

## 1. `DigitalThreadGraphModel` — The Graph's Own Pure State and Algorithms

`src/Tempest.Desktop/DigitalThread/DigitalThreadGraphModel.cs` holds
every named algorithmic scope item, entirely free of Avalonia rendering
concerns — the same "pure model, separate rendered view" split
`RibbonView`/`CommandPaletteOverlay` already established, here taken
one step further so the graph's own algorithms are directly, cheaply
unit-testable.

**Graph construction** (`Recentre`): the selected object becomes the
centre node, styled distinctly (`IsCentre`); its own direct
relationships are added immediately as collapsed neighbour nodes —
exactly `WP10.0A`'s own doc §2.1 steps 1-3, never eagerly expanded
further.

**The composed read — a deliberate, disclosed choice over
`IEvidenceComposer`**: every relationship read is
`IHasRelationships.GetRelationshipsAsync` (outgoing) +
`EngineeringDomainContext.RelationshipRepository.GetIncomingAsync`
(incoming) — the identical bidirectional pair `ObjectEditorView`
(`WP 10.3A`) already established and already tests, generic over every
Kind with zero per-discipline special-casing. `IEvidenceComposer`/
`IEvidence` was considered and rejected: it is outgoing-only, and its
own `VerificationResults`/`CalculationResults` resolve structurally
empty for every object today (`TD-30`) — strictly less complete than
the already-proven pair reused here. See `WP10.4A Architecture
Review.md` §2 for the full comparison.

**`TD-32`, closed for this view**: a Verification Activity's own
`"verifiedBy"` link to its recorded result is invisible to
`RelationshipRepository` entirely (confirmed: even `ObjectEditorView`'s
own Relationship summary already silently misses it — a pre-existing
gap this Work Package discloses but does not remediate, out of scope).
Expanding a `"VerificationActivity"` node additionally calls
`VerificationRecordReader.GetResultHistoryAsync` and adds each result
as a real, visible, non-expandable, non-editable leaf node — the first
place in the Workspace/Desktop layer this link is shown graphically.
See §6 and the Technical Debt Register's own updated `TD-32` entry.

**Expand/collapse with real reachability** (`ExpandNode`/`CollapseNode`/
`Prune`): expanding issues a fresh read of that node's own direct
relationships (never cached, never precomputed). Collapsing recomputes
reachability from the centre — a node/edge survives only if still
reachable through the centre itself or another currently-expanded node
— exactly `WP10.0A`'s own doc §2.1 step 5's "unless independently
reachable from another still-expanded path" rule, implemented as a
general fixpoint reachability sweep rather than fragile "added-by"
bookkeeping.

**Multiple layouts** (`SetLayout`): three real, distinct, deterministic
algorithms — `Hierarchical` (BFS depth from centre, rows spread
evenly), `Engineering` (concentric rings by BFS depth, angularly
spread — the radial "web" convention real traceability tools use),
`ForceDirected` (a seeded 80-iteration Fruchterman-Reingold-style
spring simulation: pairwise repulsion, edge attraction, weak centring,
damped). All three keep the centre node visually prominent
(`WP10.0A` doc §2.3's only layout constraint).

**Filtering, search, breadcrumb**: `SetCategoryVisible` hides edges of
one `RelationshipCategory` (nodes always remain visible — a disclosed
scoping choice, §5). `SetSearchText` matches node `DisplayName`
case-insensitively within the currently-loaded graph only. `Recentre`
pushes the prior centre onto `Breadcrumb`; `JumpToBreadcrumb` returns to
any prior centre, discarding forward history, without re-adding the
centre being left (a real, disclosed defect found and fixed before
commit — see §8).

**Zero caching beyond the session**: nothing here is persisted;
`DigitalThreadGraphModel` is a plain, transient object discarded when
its owning View closes and rebuilt from scratch next time
(`WP10.0A` doc §2.2, `ADR-0093`).

## 2. `DigitalThreadGraphView` — The Rendered Control

`src/Tempest.Desktop/DigitalThread/DigitalThreadGraphView.cs` — a
`UserControl` that also directly implements `IWorkspaceView`
(`TryCreate` mirrors `ObjectEditorView.TryCreate`'s own contract
exactly, returning `null` for a non-existent object). Every model
change triggers a full `Rebuild()` of the visual tree, the same
discipline `RibbonView.Rebuild()` already established — never
hand-patched incrementally.

- **Node visuals**: an expand/collapse toggle (hidden for the centre
  and for synthetic Verification-record leaves), `IconRegistry`'s own
  Kind icon, a lifecycle-status dot (`LifecycleColors`, new — see §4),
  and the display name. Search matches and the selected node are
  highlighted with a gold border.
- **Edge visuals**: an Avalonia `Line` per relationship, coloured by
  `CategoryColors.Resolve` (new — see §4), labelled with its own
  `RelationshipKind`, clickable to select it for the Relationship
  Inspector; highlighted (thicker, full opacity) when touching the
  selected node/edge.
- **Zoom/Pan**: `PointerWheelChanged` zooms; drag-on-empty-canvas pans,
  both also exposed as public `ZoomBy`/`PanBy` methods so tests never
  need to simulate real pointer gestures — the same "public method the
  test calls directly" pattern `WP 10.3B`'s own GridSplitter-adjacent
  tests already established.
- **Mini-map**: a real, proportionally-scaled dot-per-node rendering in
  the viewport's corner, with a click-to-pan affordance and a live
  viewport-outline rectangle.
- **Legend**: every `RelationshipCategory` (17 values) as a
  colour-swatched, checkable filter row (doubling as the filter UI —
  one panel, two purposes); every `LifecycleState` (8 values) as a
  status-colour key.
- **Search box, layout selector, breadcrumb bar, Relationship
  Inspector panel**: all real, wired directly to the model's own public
  surface.
- **Click-to-open vs. double-click navigation**: single click selects
  the node and opens its Object Editor tab (`_navigateToObject`,
  reusing `MainWindow`'s own existing `NavigateToObjectAsync`); double
  click re-centres the graph itself on that node — two distinct,
  named scope items, two distinct, unambiguous gestures.

## 3. `IWorkspaceView` — A Document Tab, Not a New Dock Slot

`DigitalThreadGraphView` implements `IWorkspaceView` directly rather
than a new `IWorkspacePanel`. `DockingGrid` has exactly three physical
dock slots, all already occupied (Explorer/Inspector/Output,
`WP 10.2B`) — adding a fourth would itself be a Workspace docking
change, out of this Work Package's own "No Workspace redesign" scope.
`MainWindow.BuildDocumentContent` gained one generic first branch —
`if (view is Control alreadyBuilt) return alreadyBuilt;` — since the
graph view already *is* its own rendered content, unlike every other
Kind's `IWorkspaceView`, which `ObjectEditorView.TryCreate` builds
separately. See `WP10.4A Architecture Review.md` §1.

## 4. New Colour Mappings — `CategoryColors`, `LifecycleColors`

Two small, deterministic, disclosed additions in
`DigitalThreadGraphView.cs`: `CategoryColors` (one brush per
`RelationshipCategory`, mirroring `HealthColors`' own "one value, one
colour, everywhere" rule, extended here for the first time to
relationship categories) and `LifecycleColors` (one brush per
`LifecycleState`, distinct from `HealthColors`, which is keyed on the
coarser `EngineeringHealthStatus`). Both are new, first-of-their-kind
mappings, not a reuse of an existing one — disclosed directly, not
silently introduced.

## 5. Disclosed Scoping Decisions

- **Filtering hides edges, never nodes.** Toggling a category off in
  the legend removes only that category's own edges/labels from the
  canvas; every node stays visible regardless, avoiding the surprise of
  nodes silently disappearing based on an unrelated toggle.
- **Verification-record leaf nodes cannot be expanded, opened, or
  double-click-recentred** — they have no live `IEngineeringObject`
  behind them (confirmed: `EngineeringDomainContext.Repository.FindAsync`
  resolves `null` for a raw record Id), so both gestures are guarded
  off (`if (node.IsRecord) return;`) rather than silently failing.
- **Re-centring rebuilds the graph fresh**, discarding whatever was
  separately expanded around the old centre — consistent with
  `WP10.0A`'s own "reopening starts fresh with one centre node"
  discipline, applied identically to in-place re-centring.
- **The Digital Thread graph tab is deduplicated per root object** — a
  `Dictionary<Guid, IWorkspaceView>` in `MainWindow`, purged on tab
  close — re-invoking "View Relationships" on the same object focuses
  its existing tab.

## 8. A Genuine, Disclosed Defect, Found and Fixed Before Commit

`DigitalThreadGraphModel.JumpToBreadcrumb`'s first implementation
cleared the target breadcrumb entries, then called the same `Recentre`
path ordinary forward navigation uses — which unconditionally re-pushed
the centre being navigated *away* from back onto the breadcrumb,
so jumping back to an earlier centre never actually emptied the trail.
Caught directly by
`DigitalThreadGraphModelTests.JumpToBreadcrumb_ReturnsToThePriorCentre_TruncatesForwardHistory`
before any commit. Fixed by splitting the shared graph-rebuild logic
into a private `BuildGraphAround` helper with an explicit
`pushCurrentCentreToBreadcrumb` flag — `Recentre` passes `true`
(forward-navigation semantics), `JumpToBreadcrumb` passes `false`
(standard "back" semantics, discarding the entry being left).
