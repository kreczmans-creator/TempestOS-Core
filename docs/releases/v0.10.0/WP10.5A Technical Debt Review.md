## 1. `TD-39` — Resolved

**Original finding**: `PanelHostControl`'s own Auto-Hide flyout
background and `CommandPaletteOverlay`'s own overlay background/border
were both fixed, non-theme-reactive brushes (`Brushes.White`/
`Brushes.Black`/`Brushes.Gray`) — visually wrong in the opposite theme
variant.

**Resolution**: both now bind through the new `ThemeReactiveBrush`
helper to `ApplicationPalette`'s own explicit Light/Dark resource keys
(`OverlayBackgroundBrushKey`/`PanelBorderBrushKey`). Proven by
`VisualPolishTests.PanelHostControl_Background_IsARealResolvedThemeBrush_ClosesTD39`/
`CommandPaletteOverlay_Background_IsARealResolvedThemeBrush_ClosesTD39`,
re-run five consecutive times, zero failures.

**Disposition**: **Resolved, `WP 10.5A`** — fixed at the exact
mechanism the register's own "Revisit trigger" column named ("a real
`DynamicResource`-bound background, resolved from the active
`ThemeVariant`, replacing both fixed brushes at once").

## 2. `TD-40` — Resolved

**Original finding**: `ObjectEditorView`'s own buffered dirty-state was
not wired into `DocumentAreaView`'s own tab-close path — closing a
dirty editor tab silently discarded unsaved edits, no confirmation.

**Resolution**: `DocumentAreaView.IsMarkedDirty(Guid)` (new) +
`MainWindow.CloseDocumentAsync`'s own new `ConfirmationDialog` gate —
a dirty tab now prompts "Discard unsaved changes?" before closing;
cancelling leaves the tab, and its edits, untouched. Reached from both
the tab close button and the keyboard-shortcut close path.

**Disposition**: **Resolved, `WP 10.5A`** — fixed at the exact
mechanism the register's own "Revisit trigger" column named ("wiring
`ObjectEditorView.IsDirty` into a real 'Discard unsaved changes?'
confirmation before `DocumentAreaView.RemoveTab`/`TabCloseRequested`
proceeds").

full-suite re-runs — its own assertion was too broad (matched *any*

disclosed.
