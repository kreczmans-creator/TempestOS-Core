# WP 10.4A — Security Review

## Purpose

A dedicated security assessment of `WP 10.4A`'s own new surface — the
Digital Thread graph reads Engineering Domain data no prior surface
read, so its own read-permission characteristics need direct,
independent verification, not an assumption of "it's just a view."

## 1. Scope

`src/Tempest.Desktop/DigitalThread/DigitalThreadGraphModel.cs`,
`DigitalThreadGraphView.cs`; the one integration touch to
`MainWindow.cs` (a new Quick Access Toolbar button, a new
`BuildDocumentContent` first branch). No Engineering Domain, Runtime,
or Workspace contract file is in scope — none was touched.

## 2. Read-Permission Characteristics — Unchanged From Already-Shipped Code

Every read `DigitalThreadGraphModel` performs
(`IEngineeringObjectRepository.FindAsync`,
`IHasRelationships.GetRelationshipsAsync`,
`EngineeringDomainContext.RelationshipRepository.GetIncomingAsync`,
`VerificationRecordReader.GetResultHistoryAsync`) is the identical read
already reachable from `ObjectEditorView` (`WP 10.3A`) — same
permission surface, same trust boundary, nothing new exposed to a
Workspace user who could not already reach the equivalent data via the
Object Editor's own Relationship summary one hop at a time. The graph
does not widen access; it changes *presentation* of already-reachable
data, exactly as `ADR-0093` frames it.

## 3. `VerificationRecordReader` — Re-Confirmed Deliberately Ungated

`VerificationRecordReader.GetResultHistoryAsync`'s own class remarks
disclose, explicitly, that it deliberately never calls the
permission-gated `IVerificationService.GetVerificationHistoryAsync` —
this was `WP 9.3A`'s own documented, deliberate avoidance of a passive-
surface availability defect class, not an oversight. `WP 10.4A` reuses
this exact same reader, unmodified, for exactly the same reason
`ObjectEditorView` and every other consumer already do. No new
ungated-read surface is introduced; an existing one gains a second,
more visually prominent consumer — disclosed directly in the Technical
Debt Register's own updated `TD-32` entry (Implementation Report §6),
not silently inherited.

## 4. Object-Editor Navigation — Same Dispatch Path, No New Route

Single-click "open object editor" reuses `MainWindow`'s own existing
`NavigateToObjectAsync` local function, unchanged — the identical route
`ObjectEditorView`'s own relationship rows already use (`WP 10.3A`).
Double-click "re-centre" never opens an editor or dispatches a mutation
of any kind — it only calls `DigitalThreadGraphModel.Recentre`, a pure,
local, read-only rebuild. No new mutation path exists anywhere in this
Work Package — confirmed directly: neither class calls
`ICommandDispatcher`/`IWorkspaceCommand` at all.

## 5. No New Attack Surface From Zoom/Pan/Search/Filter

Zoom, pan, category-filter-visibility, and search-text are all
presentation-local state (`ZoomLevel`, `PanOffset`, `HiddenCategories`,
`SearchText`) — never persisted, never sent anywhere, never influence
which reads occur (filtering hides rendering only, per Implementation
Report §5; it does not skip loading a category's own edges). Search
text is matched via `string.Contains`, never a regex or any other
construct with a plausible denial-of-service shape at the input sizes
involved (a Kind's own `DisplayName`, always short).

## 6. Honest, Disclosed Absences

- Verification-record leaf nodes carry no editor/navigation affinity —
  guarded off explicitly (`if (node.IsRecord) return;`), not silently
  broken.
- No new authorization check was added anywhere, because no new
  privilege boundary was crossed — every read was already reachable.

## 7. Recommendation

**Accept.** No new attack surface, no new ungated read (the one ungated
read reused is a pre-existing, disclosed, deliberate design already
independently justified in `WP 9.3A`), no new mutation path, and the
one genuinely new disclosure this Work Package makes (`TD-32`'s second
consumer) is registered, not hidden.
