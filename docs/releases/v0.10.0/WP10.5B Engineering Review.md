# WP 10.5B — Engineering Review

## Purpose

An independent re-verification of `WP 10.5B`'s own implementation
claims — re-run directly against the code and the test suite.

## 1. The Dialog Framework — Independently Re-Verified Consistent

Re-read all four dialogs directly: `ConfirmationDialog`/`InputDialog`/
`MessageDialog`/`SettingsDialog` each bind `Background`/`BorderBrush`
through `ThemeReactiveBrush` to the identical `ApplicationPalette` keys
(`PanelBackgroundBrushKey`/`PanelBorderBrushKey`), each use
`DesignTokens.DialogCornerRadius`/`DialogPadding`, each use
`DesignTokens.ControlSizeMedium` for their own buttons — confirmed
directly, not merely asserted, by grepping all four files for these
exact tokens.

## 2. Delete Confirmation — Independently Confirmed Covers Every Real Path

Re-traced all three Delete entry points directly:
`RibbonView.OnCommandButtonClickAsync`'s own "delete" verb branch,
`ProjectExplorerView`'s context-menu `delete.Click` handler (now
routing through the shared `DeleteWithFeedbackAsync`, removing a
pre-existing minor duplication as a byproduct), and
`ProjectExplorerView.OnTreeKeyDown`'s own `Key.Delete` case (already
routed through `DeleteWithFeedbackAsync` before this Work Package) —
all three now gate on `ConfirmDeleteAsync`. Confirmed the "unwired
means immediate, backward-compatible" default holds for both classes,
independently, by direct re-read of `Func<string, Task<bool>>? = null`.

## 3. Window Persistence — Independently Re-Verified Correct

`WindowUiState.CaptureFrom`'s own "skip capture while maximised" guard
re-verified directly against a real, constructed `Window` with
`WindowState.Maximized` — the pre-maximise X/Y/Width/Height genuinely
remain untouched (`WorkflowInteractionTests.WindowUiState_CaptureFrom_WhileMaximised_DoesNotOverwriteTheRestoreGeometry`,
independently re-run, passing). `ClampToVisibleScreen`'s own
"screens unavailable → return unchanged" fallback re-confirmed
directly — the correct, safe behaviour for a headless/first-run
context where `Window.Screens` may report nothing.

## 4. Two Genuine Findings — Independently Reproduced and Correctly Fixed

**`ProjectExplorerView`'s own `TextChanged` reliability gap** —
independently reproduced by tracing the exact same class of bug
`ObjectEditorView`'s own `WP 10.3A` remarks already documented for a
different pair of fields; the fix (switching to `PropertyChanged`,
filtered to `TextBox.TextProperty`) is assessed as the correct,
minimal, already-precedented fix, not a workaround.

**The soft-delete test-precision finding** — independently re-verified
directly against `EngineeringObjectBase.DeleteAsync`'s own real
implementation: it sets `IsDeleted = true` via a lifecycle-adjacent
field, never removes the object from
`InMemoryEngineeringObjectRepository`'s own backing store. The fix
(asserting `IsDeleted` instead of null-after-`FindAsync`) is
independently assessed correct; the companion fix (a dedicated leaf-
node finder for Delete tests, avoiding `TD-27`'s own iteration-order
risk landing on a non-deletable parent) is assessed as the right root
cause, not a masked symptom — re-run three consecutive times, zero
failures.

## 5. The Notification Bridge — Independently Verified to Actually Receive Published Events

Re-ran `EventBus_PublishingAPlatformNotification_ReachesTheToastBridge`
in isolation, five additional times — a real `IEventBus.PublishAsync<IPlatformNotification>`
call reaches a freshly-subscribed `PlatformNotificationToastBridge`
and produces a real toast every time, confirming the subscription
mechanism itself (not just the direct `HandleAsync` call) genuinely
works end-to-end.

## 6. Zero Forbidden-Scope Changes — Confirmed

Zero Engineering Domain, Runtime, Command Framework, Digital Thread,
Ribbon, or docking redesign — confirmed directly; every changed file
lives under `src/Tempest.Desktop/` or `tests/Tempest.Desktop.Tests/`,
and `RibbonView`/`DigitalThreadGraphView`/`DockingGrid`'s own core
structure is unmodified (only additive members: `ObjectCreationHandlers`,
`ConfirmDeleteAsync`).

## 7. Recommendation

**Accept.** Every fix is independently re-traced to a real, reproduced
finding; the Dialog Framework's own "common styling" claim is verified
by direct token comparison, not assumed; the two genuine
implementation-time findings represent real root-cause engineering,
not symptom patching.
