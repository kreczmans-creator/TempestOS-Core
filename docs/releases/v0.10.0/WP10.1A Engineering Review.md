# WP 10.1A — Engineering Review

## Purpose

An independent technical review of `WP 10.1A`'s own real implementation
— whether every upgraded Cockpit member is genuinely correct against
real data, whether every remaining placeholder is genuinely honest, and
whether the sample-module defect finding (`WP10.1A Implementation
Report.md` §4.2) is correctly diagnosed and correctly *not* attributed
to this Work Package's own code.

## 1. Scope Discipline — Verified

Direct `git status` re-check confirms zero files touched under
`src/Tempest.Core/EngineeringDomain/`. Every file this Work Package
touches is `src/Tempest.App/Workspace/EngineeringCockpit.cs`,
`src/Tempest.App/AssemblyInfo.cs`, and new/modified files entirely
under `src/Tempest.Desktop/`. `EngineeringCockpit` is independently
re-confirmed (by direct read of its own class-level XML documentation)
to be explicitly disclosed as "not one of the twelve `WP8.0B Workspace
Contracts.md` interfaces" — extending it is not a contract redesign,
consistent with every prior real-discipline Work Package's own
identical treatment.

## 2. Each Upgraded Member — Independently Re-Verified Correct

**`OpenDecisions`**: re-read directly. `IDecision` genuinely carries no
`IHasLifecycle` facet (confirmed against `Contracts/GovernanceRisk.cs`)
— the implementation's own claim that no "open vs. closed" state
exists to filter by is accurate, not a convenient excuse to skip
filtering logic.

**`BlockedItems`**: re-read directly. The Requirements portion
re-validates each live requirement individually
(`_requirementValidationService.ValidateAsync(requirement.Id)`, inside
its own `try`/`catch (PermissionDeniedException)`), rather than
correlating back from `LiveRequirementValidationResults`'s own
pre-aggregated list — this review confirms this was the correct choice:
`IValidationResult` carries no `ObjectId`, and that pre-aggregated
list can legitimately be shorter than `LiveRequirements` (a
permission-denied requirement is silently excluded) — a positional
correlation would have been a genuine, subtle defect. The Calculation/
Verification/Inspection portions correctly reuse already-computed
`LiveCalculationSnapshots`/`LiveVerificationSnapshots`/
`LiveInspectionSnapshots`, introducing no new read.

**`Health`/`HealthScoreDisplay`**: re-derived independently. This
review re-computed the rollup rule by hand against `RequirementsStatus`
through `ManufacturingStatus`'s own individually-documented behaviour
and confirms the priority order (Blocked > Attention > all-Unknown >
Healthy) is the only order consistent with every existing
per-discipline status's own established "Blocked is worse than
Attention" convention (`RequirementsStatus`'s own XML documentation,
unchanged, establishes this ordering first). `ReviewStatus`'s own
deliberate exclusion is independently justified: including a
permanently-`Unknown` status in the rollup could only ever pull a real
`Healthy` verdict down to `Unknown`, never contribute genuine signal —
confirmed by direct logical case analysis, not merely asserted.

**`RiskSummary`**: re-read directly. `IHazard : IRisk` (confirmed,
`Contracts/GovernanceRisk.cs`) — including both `"Risk"` and
`"Hazard"` Kinds in `LiveRisks` is correct, not double-counting (they
are disjoint Kind strings, confirmed by direct read of
`Implementation/GovernanceRisk.cs`: `Hazard : Risk` at the CLR level,
but registered under Kind `"Hazard"`, never also `"Risk"`, per the
`EngineeringObjectFactory<T>` pattern every other discipline already
establishes).

**`DigitalThreadSummary`**: re-read directly. Confirmed genuinely a
one-hop sum (`GetOutgoingAsync` per live object, never `GetIncomingAsync`
combined with `GetOutgoingAsync`, which this review notes would
double-count a link where both endpoints are live — the implementation
correctly counts each link exactly once, from its own source side
only). `WP 8.1C`'s own "never a live traversal" boundary is honoured:
no call chains from one object's own outgoing link into a *second*
`GetOutgoingAsync` call — confirmed by direct read, no recursion
present anywhere in this member.

**`UpcomingMilestones`**: re-read directly. `IMilestone.TargetDate` is
compared against `DateTimeOffset.UtcNow` at read time (never cached) —
correctly live, re-evaluated on every `Refresh()`.

## 3. Each Retained Placeholder — Independently Re-Confirmed Honest

**`FavouriteProjects`**: this review searched `Tempest.Core.EngineeringDomain`
directly for any "favourite"/"starred"/"pinned" concept on `IProject`
or `IHasMetadata` — none exists. Confirmed correctly unbuilt.

**`OverdueActions`**: this review searched `ITask`/`IAction`
(`Contracts/ProcessApproval.cs`) directly for any due-date field —
`AssignedToPrincipalId`/`RaisedByObjectId` are the only members either
interface adds beyond `IHasLifecycle`; no date field exists anywhere.
Confirmed "overdue" is genuinely uncomputable today, and `OpenTaskCount`
is a correctly-labelled, honestly-distinct substitute, never presented
as equivalent.

## 4. The Sample-Module Defect Finding — Independently Re-Diagnosed

This review independently re-ran the same `IDiagnosticsProvider.Modules`
diagnostic the Implementation Report describes, against a fresh
`WorkspaceHost`, and reproduces the identical four module failures
(`engineeringdomain`, `materials`, `requirements`, `requirementsworkspace`),
each against its own literal Id, on the very first host construction in
a fresh process — ruling out a "leftover state from a prior test in the
same process" explanation, which this review considered and rejected
for the same reason `WP10.1A Implementation Report.md` §4.2 gives. This
review confirms the finding is real, reproducible, and — critically —
**not caused by any file this Work Package modifies**: none of the
four failing modules, nor `IMaterialCatalog`/`IRequirementsService`
(the services they call), is touched anywhere in this Work Package's
own diff.

## 5. Verdict

**No release-blocking or Work-Package-blocking finding.** Every
upgraded Cockpit member is independently re-verified correct against
real data; every retained placeholder is independently re-confirmed to
have no real capability to draw from; the one significant, real defect
found (§4) is correctly diagnosed, correctly disclosed, and correctly
not attributed to this Work Package's own code.
