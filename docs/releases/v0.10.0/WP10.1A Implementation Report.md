# WP 10.1A — Engineering Cockpit Implementation — Implementation Report

## Purpose

The complete implementation record for `WP 10.1A` — the complete
graphical Engineering Cockpit, realised over the `Tempest.Desktop`
framework `WP 10.0B` built, and the first Work Package to systematically
audit and upgrade every disclosed Cockpit placeholder `WP 8.1C`–`WP
9.5A` left behind.

## 0. Scope Discipline

- **No Engineering Domain changes** — zero files touched under
  `src/Tempest.Core/EngineeringDomain/`. Every new Cockpit read composes
  `EngineeringDomainContext.Repository`/`.RelationshipRepository`,
  already-existing, already-public members, exactly as every prior
  discipline's own Cockpit KPI already does.
- **No Workspace contract redesign** — `EngineeringCockpit` is not one
  of the twelve `WP 8.0B` frozen contracts (its own class-level XML
  documentation states this explicitly, unchanged since `WP 8.1C`); it
  is a concrete, disclosed implementation-phase class every prior
  real-discipline Work Package has already extended. This Work Package
  extends it a seventh time, adding no new public interface anywhere.
- **Reuse existing services exclusively** — every new read uses
  `EngineeringDomainContext.Repository.ListByKindAsync`/`ListAllAsync`
  and `.RelationshipRepository.GetOutgoingAsync`, the identical
  Platform-Service-backed methods every existing Cockpit member already
  calls; `IDiagnosticsProvider` (`WP 6.x`) is the one additional
  existing service newly consumed, by `WorkspaceHost`, not the Cockpit
  itself.

## 1. `EngineeringCockpit` — Placeholder Audit and Upgrade

A full, direct read of every one of `EngineeringCockpit`'s own members
(1178 lines, `Tempest.App.Workspace`) was performed before writing any
graphical code — the class's own XML documentation already disclosed,
member by member, which were real and which remained fixed placeholder
content since `WP 8.1C`. Six were upgraded; two were reconfirmed
correctly still placeholder, with improved disclosure:

| Member | Before | After |
|---|---|---|
| `OpenDecisions` | One fixed editorial string | Real read of live `IDecision` objects |
| `BlockedItems` | Always empty | Real synthesis from already-computed Blocked signals (failed Requirement/Calculation/Verification/Inspection) |
| `Health` | Always `Unknown` | Real rollup across five discipline statuses |
| `HealthScoreDisplay` | Fixed "— (not yet available)" | Real "`X`/`Y` healthy (`Y`/5 disciplines reporting)" |
| `RiskSummary` | Fixed placeholder string | Real read of live `IRisk`/`IHazard` objects, bucketed by Severity |
| `DigitalThreadSummary` | Fixed placeholder string | Real one-hop relationship-link aggregate |
| `UpcomingMilestones` | Always empty | Real read of live `IMilestone` objects, sorted by `TargetDate` |
| `FavouriteProjects` | Always empty | **Unchanged** — reconfirmed no platform capability exists |
| `OverdueActions` | Always empty | **Unchanged** — reconfirmed no due-date field exists on `ITask`/`IAction`; a new, real `OpenTaskCount` added alongside it as the honest, clearly-distinguished substitute |

Full reasoning for each: `WP10.1A Engineering Review.md` §2.

### 1.1 A Previously Unread Domain Family

`IDecision`/`IRisk`/`IHazard`/`IMilestone`/`ITask`/`IAction` (the
Governance & Risk and Process & Approval families, `WP 8.2C`) were
real, compiled, concrete classes with real sample data already seeded
(`WP 7.x`/`WP 8.x` base sample modules) but had never been read by any
Workspace surface before this Work Package — the Cockpit's own
`RiskSummary`/`DigitalThreadSummary` XML documentation said so
explicitly ("no Risk service exists anywhere in this platform yet").
This was already false at the Domain layer (the classes existed and
compiled) and only true at the presentation layer (nothing read them)
— this Work Package closes that gap, reading the Domain data that was
already there.

## 3. Wiring — `MainWindow`/`DocumentAreaView`

`DocumentAreaView.SetHomeTab` (new) gives the Document Host a
permanent, non-closable first tab — the Engineering Cockpit,
`ADR-0069`'s own "default landing screen" now realised literally: the
Cockpit is the first thing a `Tempest.Desktop` user sees, and it is
never closable, distinct from every object tab. `MainWindow` reaches
`EngineeringCockpit` via `((Workspace)workspace).Cockpit` — the
identical, precedented `InternalsVisibleTo("Tempest.Desktop")` pattern
`WP 10.0B` already established for `WorkspaceManager.StatusBar`, applied
a second time. Every actionable Cockpit gesture (Continue, Open Recent,
Navigation Shortcuts, Command Palette) dispatches through the exact
same real Workspace methods the rest of `Tempest.Desktop` already uses
— `INavigationService.OpenAsync`/`SwitchAreaAsync`,
`CommandPaletteOverlay.Open` — never a new path.

## 4. Real Defects Found During Implementation

### 4.1 `WorkspaceHost`'s Own `TD-26` Mitigation Was Too Narrow

`WP 10.0B`'s own bounded poll waited only for six named
`NavigationItem`s. This Work Package's own new tests (reading
Governance & Risk/Process & Approval sample data, seeded by a
*different* module than any of the six disciplines) exposed that this
was an incomplete proxy for "the platform is actually ready." **Fixed**:
`WorkspaceHost.StartAsync` now polls `IDiagnosticsProvider.HostState ==
HostState.Running` — the Runtime Host's own authoritative "Module
Initialisation completed" signal — replacing the narrower,
six-item-specific heuristic entirely. Full reasoning: `WP10.1A
Architecture Review.md` §2.

### 4.2 A Genuine, Pre-Existing, Platform-Wide Sample-Module Registration Defect

**The most significant finding.** Using `IDiagnosticsProvider.Modules`
to diagnose §4.1, this Work Package found that four sample modules —
`tempest.samples.engineeringdomain`, `tempest.samples.materials`,
`tempest.samples.requirements`, `tempest.samples.requirementsworkspace`
— each fail their own `InitialiseAsync` with a duplicate-registration
error against **their own** literal Id (e.g.,
`EngineeringDomainSampleModule` fails "A material is already
registered with Id 'SAMPLE-MAT-001'" — a string that appears in no
other file in the entire `Tempest.Samples` project). This is not a
Cockpit defect, and this Work Package's own new `EngineeringCockpit`
reads are confirmed correct against it (§4.2.1) — full disclosure and
disposition: `WP10.1A Technical Debt Review.md` §1.

**§4.2.1 — Consequence for this Work Package's own Cockpit reads:**
`EngineeringDomainSampleModule`'s own failure means its own Risk/Task/
Milestone/Deliverable/Supplier/PurchaseItem sample data never seeds —
`RiskSummary`/`UpcomingMilestones`/`OpenTaskCount` therefore correctly,
honestly report empty/zero in every test run today, not because their
own real implementation is wrong (confirmed by direct test, §5), but
because the upstream sample data this Work Package expected to read is
itself never created. `OpenDecisions`/`BlockedItems` are unaffected —
seeded by different, unaffected sample modules (`WP 9.3A`/`WP 9.4A`).

## 6. What Was Deliberately Not Built

- **No per-Kind rich editing of Risk/Decision/Milestone objects** — the
  Cockpit only *reads* them; a full Governance & Risk Workspace
  discipline (Explorer area, commands, Property Inspector facets,
  `FCR-0056`) remains genuinely future work, not this Work Package's
  own "implement the Cockpit" scope.
- **No fix to the sample-module registration defect** (§4.2) — disclosed
  and registered as Technical Debt, not fixed; fixing `Tempest.Samples`
  content is outside this Work Package's own Cockpit-focused scope.
- **No live-refresh polling** — `CockpitView.Refresh()` is called after
  every real action taken from the Cockpit or the rest of the Workspace
  (object opened/closed, command invoked, area switched), never on a
  timer — consistent with `WP8.0A UI Architecture.md` §3.3's own "no
  View introduces its own... index" discipline; a timer-driven poll
  would introduce exactly that.
