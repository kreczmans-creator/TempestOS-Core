# WP 10.1B — Security Review

## Purpose

The required, dedicated Security Review this Work Package's own
controlling instruction names — a continuation of this project's own
run of dedicated Security Reviews performed for essentially every
Work Package since `v0.9.0`.

## 1. Scope

This Work Package touches the Runtime Host's own readiness signalling
(`WorkspaceManager`), sample-data seeding (`Tempest.Samples`), a
composition-root parameter (`EngineeringWorkspaceComposer`), and test
infrastructure (`Tempest.Desktop.Tests`). No Identity, Permission,
Audit, Licensing, or REST API surface is touched — confirmed by direct
`git diff --stat`.

## 2. New Findings

**None.** No new security-relevant defect was introduced or found.

## 3. Specific Checks

- **`ThrowIfHostRunFaulted()` (`WorkspaceManager.cs`):** rethrows a
  captured `Exception` via `task.GetAwaiter().GetResult()`. Confirmed
  this does not swallow, downgrade, or mask any fault classification —
  the exact same exception `RunAsync` itself would have thrown to a
  direct awaiter propagates unchanged, preserving `ADR-0013`'s existing
  platform-service-failure classification.
- **`EngineeringWorkspaceComposer.Build`'s new `configurationSources`
  parameter:** additive, optional, defaults to `null`. Confirmed the
  real console (`Program.cs`) and desktop (`Tempest.Desktop.App`) entry
  points both continue to call it with no argument — no production code
  path can have its own `Persistence:RootPath` (or any other
  configuration key) silently overridden by this change; only test code
  that explicitly opts in can.
- **`WorkspaceHost`'s new `persistenceRootPathOverride` constructor
  parameter:** same reasoning — optional, defaults to `null`, and the
  value, when supplied, flows only into a `MemoryConfigurationSource`
  keyed to `PersistenceStore.RootPathConfigurationKey`, never
  interpreted, executed, or passed to a shell — no injection surface is
  introduced. Test-only callers pass a `Guid`-derived path under
  `Path.GetTempPath()`, never caller-supplied or externally-influenced
  input.
- **Sample module idempotency checks (`FindAsync`/`FindByIdentifierAsync`):**
  each is a read-only lookup against an already-permission-neutral
  Platform Service (sample modules already operate as their own
  established sample principal, `WP 7.x`/`WP 8.x` precedent, unchanged
  here) — no new permission surface, no new principal, no change to
  either service's own existing access pattern.
- **Idempotent-skip branches never bypass a lifecycle transition or
  validation rule** — each skip is a complete no-op for the durable
  write path (no partial write, no state left inconsistent); the only
  behavioural difference is which properties end up populated, already
  covered as a disclosed, non-security trade-off (`WP10.1B Implementation
  Report.md` §2).

## 4. `TD-38` — Security Relevance

None. `TD-38` (silent Domain-object duplication for identifiers with no
uniqueness enforcement) is a data-integrity/determinism concern, not a
security one — no permission boundary, principal, or credential is
involved; the duplicated objects remain fictional, disclosed sample
data, never real engineering records.

## 5. Recommendation

**Sound, no security-relevant findings.** This Work Package's own
scope — Runtime Host readiness signalling and sample-data determinism —
carries no security surface of its own; every change was confirmed,
directly, to be additive and correctly defaulted.
