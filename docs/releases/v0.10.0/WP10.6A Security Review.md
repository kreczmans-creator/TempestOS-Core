# WP 10.6A — Security Review

## Purpose

A dedicated security assessment of `WP 10.6A`'s own new surface — a
Macro foundation that dispatches commands on the user's own behalf, an
Input Binding router that invokes commands from any registered
provider, and a Background Task Runner that executes work off the
initiating interaction — none of which should widen this platform's own
trust boundary, but verified directly rather than assumed.

## 1. Scope

`src/Tempest.Core/Macros/*.cs`, `src/Tempest.Core/Input/*.cs`,
`src/Tempest.App/Workspace/UndoableAction.cs`/`IUndoRedoStack.cs`/
`UndoRedoStack.cs`/`Macros/MacroWorkspaceRegistration.cs`,
`src/Tempest.Desktop/RecentObjectsState.cs`/`FavouriteObjectsState.cs`,
`src/Tempest.Desktop/History/*.cs`, `src/Tempest.Desktop/Tasks/*.cs`,
`src/Tempest.Desktop/Input/KeyboardCommandBindingProvider.cs`,
`src/Tempest.Desktop/Views/MacroManagerDialog.cs`, and every modified
file's own diff (`TempestHost.cs`, `EngineeringWorkspaceComposer.cs`,
`ObjectEditorView.cs`, `KeyboardShortcuts.cs`, `OutputPanelView.cs`,
`ProjectExplorerView.cs`, `CommandPaletteOverlay.cs`, `MainWindow.cs`).
No Engineering Domain, Runtime, or Workspace contract file is in scope
— none was touched.

## 2. A Macro Cannot Invoke Anything the User Could Not Already Invoke Directly

`RunMacroCommandHandler` invokes each step via `ICommandRegistry.
InvokeAsync` — the identical, already-permission-checked path the
Command Palette already uses for the exact same descriptor. Creating a
macro requires the descriptor already be registered and
`CreateDefault`-eligible (`IMacroManager.CreateAsync`'s own
`ArgumentException` guard, verified directly); a macro cannot reference
a command it did not already have standing to invoke through the
Palette. No privilege escalation: a macro is a convenience alias for a
sequence of actions already individually reachable, never a new
capability.

## 3. `RunMacroCommand` Carries No Injectable Data

`RunMacroCommand`'s only field is `MacroId` (a `Guid`) — no string
content is ever parsed, interpreted, or executed as code. `MacroManager`
persists `StepCommandIds` as an ordinary `List<string>` of Command Ids,
validated against `ICommandRegistry.Items` at creation time (rejecting
any unknown Id, verified directly) — never evaluated as an expression,
a shell command, or any other executable form. This is the direct
consequence of `ADR-0099`'s own explicit "no new scripting language"
decision — there is no expression evaluator anywhere in this Work
Package's own new code to exploit.

## 4. `InputBindingRouter` — A Bounded, Isolated Surface

Any code inside this process that holds an `IInputBindingRegistry`
reference can register a provider and, from then on, have that
provider's own `CommandRequested` event drive real command invocation
— the identical trust level the Command Palette (in-process,
UI-triggered) already carries; `IInputBindingRegistry` is not exposed
over any network boundary, IPC channel, or file-based configuration
this Work Package adds. `KeyboardCommandBindingProvider`'s own `Bind`
API is programmatic-only (no persisted, externally-editable binding
file exists yet — a real, disclosed absence, `AT-23`, not a security
gap: nothing reads an untrusted file to construct a binding today).

## 5. `MacroManagerDialog` — No New Input Surface Beyond Existing Dialogs

The macro Name field is used identically to `InputDialog`'s own
existing name-prompt pattern (Rename, `mechanical.create`) — passed
directly as a `CommandDescriptor.DisplayName`/`ICommandMacro.Name`
string, never parsed or interpreted. Step selection is constrained to
list-selection from an already-registered, already-trusted set
(`ICommandRegistry.Items`) — the user cannot type an arbitrary Command
Id string into a macro step at all, closing off even an accidental
typo-Id injection path.

## 6. Recent/Favourite Objects, Command History — No New Data Exposure

`RecentObjectsState`/`FavouriteObjectsState` persist only
`(Guid, string Kind, string DisplayName)` tuples — display metadata
already visible to the same user in the Project Explorer tree, never
Engineering content, never a credential, never anything not already
readable by the same user through the existing tree. `CommandHistoryLog`
persists nothing (session-only, in-memory) and records only the exact
human-readable strings the Status Bar/Toast already show the same user
in real time — no new information reaches any surface a user could not
already see.

## 7. `IBackgroundTaskRunner` — No New Execution Boundary

`RunAsync` executes the supplied delegate on the calling (UI) context,
`await`ed directly — never a new process, never a new AppDomain, never
elevated privileges of any kind. Cancellation is cooperative
(`CancellationTokenSource`, observed only if the running work checks
its own token) — identical to every other cancellable operation already
in this platform; a task that does not observe cancellation simply
keeps running, the same, already-accepted behaviour every `async`
method in this codebase already has.

## 8. `StubExternalControllerProvider` — Test-Only, Confirmed Never Reachable From Production

Confirmed by direct project-reference check: `StubExternalControllerProvider`
lives in `tests/Tempest.Core.Tests/Input/`, referenced by no production
project (`Tempest.Core`, `Tempest.App`, `Tempest.Desktop` all have zero
reference to `Tempest.Core.Tests`) — it cannot reach a running
TempestOS instance under any configuration.

## 9. Conclusion

No new trust boundary, no new injection surface, no new data exposure.
Every new invocation path (Macro, Input Binding) reuses the identical,
already-permission-checked `ICommandRegistry.InvokeAsync` entry point
every existing command-invoking surface already uses. `AT-23`'s own
disclosed absence (no persisted, user-editable keybinding file) is
correctly a Future Capability gap, not a present security concern —
nothing in this Work Package reads untrusted external configuration.
