# WP 10.6A — Command Execution & Productivity Experience — Implementation Report

## Purpose

The complete implementation record for `WP 10.6A` — the professional
engineering workflow layer sitting on top of `Tempest.Desktop`'s own
existing Command Framework and UI: a real Undo/Redo architecture, a
Background Task Framework, Command History, Recent/Favourite Objects, a
User Command Macro foundation, and a Macro & Controller Abstraction
(`ICommandMacro`/`IMacroManager`/`IInputBindingProvider`/
`IExternalControllerProvider`) — while changing zero Command Framework
or frozen `WP8.0B` Workspace-contract behaviour.

## 0. Scope Discipline, Honestly Bounded

This instruction names six independently large capabilities. As with

## 1. Undo/Redo — A Real, Working Architecture, Wired Broadly for Rename

`UndoableAction`/`IUndoRedoStack`/`UndoRedoStack` (new,
`Tempest.App.Workspace`) realise Undo/Redo as a plain Do/Undo delegate
pair recorded on two bounded (capacity 50), session-only stacks —
`ADR-0098` documents why this is a Desktop/App-layer mechanism, not a
new `ICommand`/`IUndoableCommand` contract: no real command in this
platform carries the "previous state" its own inversion would need.

`ObjectEditorView`'s own existing Rename commit path (already shared by
all six disciplines, calling the already-Kind-agnostic
`IWorkspaceManager.RenameObjectAsync`, `ADR-0096`) now captures the
pre-commit name and raises a new `UndoableActionRecorded` event —
`MainWindow` records it onto `IUndoRedoStack`. One call site, six
disciplines, real Undo/Redo for Rename with zero per-discipline code.
The new Favourite/Un-favourite toggle (§4) is the second real, wired
example — trivially self-inverting, since toggling twice is a no-op.

`Ctrl+Z`/`Ctrl+Y` (Keyboard Shortcut Framework) and two new Quick Access
Toolbar buttons (enablement/tooltip bound live to `CanUndo`/`CanRedo`/
`NextUndoDescription`/`NextRedoDescription`) are the real, working UI.

## 2. The Macro Foundation — A Macro *Is* a Registered Command

`ICommandMacro`/`CommandMacro`/`IMacroManager`/`MacroManager`/
`RunMacroCommand`/`RunMacroCommandHandler` (new,
`Tempest.Core.Macros`) realise `ADR-0099`'s own central decision: a
macro is registered as an ordinary `CommandDescriptor`
(`Id = "macro:{Guid}"`, `CreateDefault: () => new RunMacroCommand(macroId)`),
so the Command Palette invokes it through exactly the same
`ICommandRegistry.InvokeAsync` path as any other command — zero
macro-specific branching anywhere outside `Tempest.Core.Macros` itself.
`RunMacroCommandHandler` sequentially invokes each step, stopping at
the first failure, and fails gracefully (never throws) against a
deleted macro's own still-registered, stale descriptor
(`ICommandRegistry` exposes no unregister method, confirmed).

`MacroManagerDialog` (new) is the real, minimal "foundation" authoring
UI the brief asked for: browse existing macros (Run/Delete), and a
two-list-plus-buttons step editor for New Macro (name, then an ordered
pick from `ICommandRegistry.Items.Where(d => d.CreateDefault is not null)`
— today, honestly, the `Tempest.Samples` commands only; §8).
`MacroWorkspaceRegistration` (new, `Tempest.App.Workspace.Macros`)
registers `RunMacroCommandHandler` and loads every persisted macro once
the Host has started, alongside (not as) the six real Engineering
Disciplines.

## 3. External Controller / Input Binding Abstraction — No Vendor SDK

`IInputBindingProvider`/`IExternalControllerProvider`/
`IInputBindingRegistry`/`InputBindingRouter` (new, `Tempest.Core.Input`)
realise `ADR-0100` — mirroring `IEventBus`'s own established
subscriber-isolation shape (`ADR-0028`): any registered provider's own
`CommandRequested` event is routed to `ICommandRegistry.InvokeAsync`, a
throwing provider or failed invocation caught and logged, never
propagated back.

One real implementation: `KeyboardCommandBindingProvider`
(`Tempest.Desktop.Input`) — a genuine, working `KeyGesture → Command Id`
map (`Bind`/`Unbind`), wired into `MainWindow.KeyDown` after the fixed
`KeyboardShortcuts` bindings (which take priority). One test-only
implementation: `StubExternalControllerProvider`
(`Tempest.Core.Tests.Input`) — simulates a Stream-Deck-shaped device
(`IsConnected = true`, `SimulatePress(commandId)`), proving the
identical router drives a real device-shaped provider with zero Command
Framework changes. Neither is, or is intended to become, a real vendor
integration — explicitly matching this Work Package's own Out-of-Scope.

## 4. Recent/Favourite Objects, Command History, Background Tasks

`RecentObjectsState`/`FavouriteObjectsState` (new, `Tempest.Desktop`,
mirroring `UserSettings`'s own `ISettingsProvider`-JSON-DTO pattern)
surface as two new sections in `ProjectExplorerView`, mirroring its own
existing Recent Searches section exactly. Recent Objects records on
every real Open (tree double-click/Enter, or clicking a Recent/Favourite
flyout entry — all converge on the identical `ObjectOpened` event).
Favourites gains a "Toggle Favourite" context-menu item and `Ctrl+D`,
both routed through `MainWindow.ToggleFavourite` — the one real
implementation recording the Undo/Redo pair too (§1). **Deliberately
distinct from `EngineeringCockpit.FavouriteProjects`** — that member is
an unbuilt, Engineering-Domain-level "favourite Project" concept,
untouched by this Work Package; this is a separate, Desktop-local "any
open object" convenience list.

`CommandHistoryLog` (new, bounded 200, session-only) is appended to at
every existing `ActionCompleted`-shaped surface `MainWindow` already
has (Ribbon, Explorer, Inspector, Object Editor) plus Undo/Redo/Macro
outcomes — `succeeded` is a disclosed heuristic (§8), since these
surfaces carry only a string.

`IBackgroundTaskRunner`/`BackgroundTaskRunner` (new) tracks a title and
coarse state (Running/Succeeded/Failed/Cancelled) plus elapsed time —
never a percentage (§8). Real wired consumer: the Command Palette
routes a Macro's own multi-step invocation through it via the new
`CommandPaletteOverlay.InvokeOverride` hook — the one genuine "could
take a moment" case in this platform today.

Both `CommandHistoryLog` and `IBackgroundTaskRunner` surface as two new
sections in the already-existing `OutputPanelView` — no new dock panel,
no `DockingGrid` change.

## 8. Disclosed Scope Reductions — Named Directly, Not Hidden

- **Undo/Redo covers Rename (all six disciplines) and Favourite toggle
  only.** Create/Delete/Duplicate/Move/Status changes remain
  un-undoable; Delete specifically has no defined inverse (already a
  soft delete, no "restore" operation anywhere in this platform).
  `AT-18`, `FCR-0078`.
- **Background Task progress is coarse state only, never a percentage.**
  No `ICommandHandler<TCommand>` anywhere in this platform carries an
  `IProgress<T>` parameter — extending that frozen contract is a
  Command Framework-wide change, out of this Work Package's own scope.
  `AT-19`, `FCR-0079`.
- **Macro steps are limited to `CreateDefault`-eligible commands** —
  confirmed by repository-wide `grep`, only `Tempest.Samples` commands
  qualify today; no real Engineering discipline command is Id-invokable
  yet, the identical pre-existing limitation `CommandPaletteOverlay`'s
  own remarks already document. `AT-20`, `FCR-0080`.
- **Command History records only what reaches existing `ActionCompleted`
  UI surfaces**, with a disclosed "contains 'fail'" `succeeded`
  heuristic — never a global `ICommandDispatcher` interception.
  `AT-21`, `FCR-0081`.
- **Undo/Redo and Command History are both session-only** — neither is
  persisted across a restart, matching most desktop applications' own
  convention. `AT-22`, `FCR-0082`.
- **`KeyboardCommandBindingProvider` ships with zero default bindings
  and no remapping UI; no real external controller vendor integration
  exists.** `AT-23`, `FCR-0083`.
