# WP 10.6B — Prioritised Defect List

## Purpose

Every genuine gap found by `WP10.6B User Interface Reachability
Audit.md`, ranked, with direct evidence. **No fix is implemented here
— audit only, per this Work Package's own explicit instruction.**
Severity reflects real user impact, not code-change size. Items marked
"By Design" are informational, already disclosed by a prior Work
Package's own governance entry, and require no action — included here
only because the audit's own methodology explicitly asks about
placeholders.

## P0 — Ribbon Buttons Signal "Enabled" for Commands That Cannot Actually Execute

**Severity: High (misleading UI signal, newly quantified — not
previously disclosed at this precision by any prior Work Package).**

**Evidence.** `RibbonView.RefreshEnablement`:

```csharp
var enabled = selection is not null && verb switch
{
    "rename" => _manager.CanRename(selection.Kind),
    "edit" => _manager.CanRevise(selection.Kind),
    "delete" => _manager.CanDelete(selection.Kind),
    _ => true,
};
```

Every verb other than rename/edit/delete defaults to `enabled = true`
whenever *any* object is selected — including every Create (for 5 of 6
disciplines), Move, Copy, Duplicate (for 5 of 6 disciplines), Execute,
Recalculate, Lock, Unlock, Request Review, Approve, Archive, Release,
Set Status, Attach, Link, Record Result, and every other verb `WP10.6B
User Interface Reachability Audit.md` §5 lists. `RibbonView.OnCommandButtonClickAsync`
has exactly four real dispatch branches (delete; rename/edit; a
`CreateDefault`-gated branch that never fires for any real discipline
command, confirmed by `grep`; and `ObjectCreationHandlers`, containing
exactly two entries). Every other click, for a button the user just saw
rendered as fully enabled, produces only a status-bar/toast message —
never a visual "this isn't wired yet" signal *before* the click.

**Impact.** A user cannot visually distinguish a real, dispatchable
Ribbon button from one that will do nothing until after clicking it —
the opposite of `ADR-0070`'s own "disabled, not hidden" discoverability
principle, which this defect partially defeats: the button is neither
disabled nor hidden, it is *mis-enabled*.

**Root cause.** `RefreshEnablement`'s own `_ => true` fallback was
written for `WP 10.3B`, before any real dispatch existed for any verb
beyond rename/edit/delete — reasonable at the time, never revisited as
`WP 10.5B`/`WP 10.6A` added real dispatch for exactly two more verbs
(Mechanical Create/Duplicate) without narrowing the fallback for the
rest.

**Not fixed here, per this Work Package's own explicit instruction.**

## P1 — No UI Path Anywhere Can Change an Object's Lifecycle State

**Severity: High (core engineering workflow — Approve/Release/Archive
is a primary commercial-CAD-tool interaction).**

**Evidence.** `grep -rn "TransitionAsync" src/Tempest.Desktop` returns
zero matches. `ObjectEditorView.PopulateLifecycle` renders the current
`IHasLifecycle.Status` and `History` read-only (a `TextBlock`/`Border`
dot), never a transition control. `PropertyInspectorView`'s own
Lifecycle section is likewise read-only. The Ribbon's own entire
"Lifecycle" command group (Lock/Unlock/Request Review/Approve/Archive/
Release/Set Status, `RibbonView.ClassifyGroup`) is real, visible, and
grouped — but every button in it falls through to the same honest
fallback message as P0, for every one of the six disciplines. The
Command Palette cannot reach it either (§6 of the Traceability Matrix
— zero `CreateDefault`-eligible real discipline commands).

**Impact.** A user can create (Mechanical only), rename, edit content,
and delete an object — but cannot move it through its own lifecycle
(Draft → In Review → Approved → Released) anywhere in the running
application, despite `IHasLifecycle`/`LifecycleTransitionTable` being
real, complete, tested Domain-layer capability since `WP 7.x`/`WP 8.x`.

**Root cause.** The same root cause as P0 — no Ribbon/Palette dispatch
path exists for any Lifecycle verb, for any discipline; this item is
listed separately because it is also independently confirmed absent
from both the Object Editor and Property Inspector, not only the
Ribbon.

**Not fixed here.**

## P2 — Move / Copy Non-Functional for All Six Disciplines

**Severity: Medium (already named as a real, disclosed future-work
item — `FCR-0073` — but re-confirmed here with direct evidence rather
than restated from the prior document).**

**Evidence.** Identical trace as P0/P1 — Move/Copy verbs, all six
disciplines, fall through to the honest fallback message. No
destination-picker dialog exists anywhere (`WP10.6B User Interface
Reachability Audit.md` §13).

**Root cause.** `FCR-0073` (`WP 10.5B`) — a destination-picker dialog
shape does not yet exist; `InputDialog`'s own single-text-field shape
cannot collect a destination parent.

**Not fixed here.**

## P3 — Create / Duplicate Non-Functional for Five of Six Disciplines

**Severity: Medium (already disclosed, `FCR-0075`, `WP 10.5B`; listed
here for completeness against this audit's own explicit "Create" scope
line).**

**Evidence.** Only `mechanical.create`/`mechanical.duplicate` appear in
`RibbonView.ObjectCreationHandlers`. Requirements, Calculations,
Verification, Documents, and Manufacturing's own Create/Duplicate
buttons all fall through to the honest fallback message.

**Root cause.** `FCR-0075` — the other five disciplines' own Create
commands have genuinely different constructor shapes (Requirements
alone has three).

**Not fixed here.**

## P4 — Digital Thread Graph Has Exactly One Discovery Path

**Severity: Low-Medium (functional once found; a discoverability gap,
not a functional one).**

**Evidence.** `grep -n "DigitalThreadGraphView" src/Tempest.Desktop/MainWindow.cs`
shows exactly one construction site (`BuildQuickAccessToolbar`'s own
"🕸 View Relationships" button). No Ribbon command, no Project Explorer
context-menu item, no menu entry reaches it.

**Root cause.** Never named as a gap by any prior Work Package — `WP
10.4A` built the graph itself and wired one real entry point; no
subsequent Work Package added a second.

**Not fixed here.**

## P5 — Keyboard Rebinding Mechanism Is Fully Wired but Functionally Inert

**Severity: Low (infrastructure-only by explicit design, `FCR-0077`;
listed because this audit's own "actually instantiated / command
wired / end-to-end functional" questions apply cleanly to it and the
answer is genuinely nuanced).**

**Evidence.** `InputBindingRouter.Register(provider)` does correctly
subscribe `provider.CommandRequested` and route it to
`ICommandRegistry.InvokeAsync` — confirmed by direct read, this
mechanism is real, not dead code. `KeyboardCommandBindingProvider.Bind`
is a real, public, callable method. Re-verified precisely: `grep -rn
"_keyboardBindingProvider" src` returns exactly three lines, all in
`MainWindow.cs` — the field declaration (`= new()`), its own
registration (`inputBindingRegistry.Register(_keyboardBindingProvider)`),
and its own `KeyDown` wiring (`_keyboardBindingProvider.HandleKeyDown(e)`)
— never a single call to its own `.Bind(...)` method anywhere. Nothing
in the shipped application ever registers a single keyboard binding
through this mechanism, and no UI exists to let a user do so either.
The fixed, fully-functional
`KeyboardShortcuts` class (fewer than a dozen hard-coded gestures)
remains this platform's only real, reachable keyboard-productivity
surface.

**Root cause.** `FCR-0077` (`WP 10.5B`, reconfirmed `WP 10.6A`) — the
mechanism was built as disclosed foundation; no remapping UI was ever
in scope for any Work Package to date.

**Not fixed here.**

## Informational — By Design, No Action Needed

These were confirmed genuine placeholders during the audit, each
already disclosed by the Work Package that introduced it — listed here
only for this audit's own completeness against its "Placeholder?"
question, not as defects requiring attention:

- **Output Panel hidden by default** (`WP 10.2B`) — one click away via
  `View` menu or any Layout preset.
- **Property Inspector "Validation" section** (`WP 10.2A`) — no
  per-object validation read exists at the Workspace layer yet.
- **Cockpit "Favourite Projects"/"Overdue Actions" cards** (`WP
  10.1A`) — no platform capability (project favouriting, task due
  dates) exists to back either honestly.
- **Requirements' own Project Explorer nodes carry no lifecycle dot**
  (`WP 10.5C`) — `RequirementStatus` is a genuinely distinct taxonomy
  from `LifecycleState`, deliberately not force-mapped.
- **Project Explorer drag/drop is preparation architecture only, not
  full reparenting** (`WP 10.2A`, `FCR-0066`).
- **Copy/Move/Export/Import dialogs do not exist** (`WP 10.5B`,
  `FCR-0073`/`FCR-0074`).
- **`StubExternalControllerProvider` is test-only** — never intended
  to be reachable from the shipped application; proves the router
  pattern only, explicit Out-of-Scope since `WP 10.6A`.
