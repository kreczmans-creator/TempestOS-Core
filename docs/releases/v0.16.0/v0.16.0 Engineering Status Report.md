## 1. Executive status

v0.16.0 is "v1.0 Readiness Hygiene": every item the
`v1.0.0 Release Candidate Audit` rated mandatory, except the v1.0 gate
itself. **No new product capability, by design.**

The release plan defined 13 Work Packages in 5 waves. **All 13 are
complete.** A 9-perspective review board was then run against the
integrated tree; it produced **2 RED, 12 AMBER, 11 YELLOW** findings, and
every RED and every in-scope AMBER has been remediated in four additional
Work Packages the plan did not contain (`WP 16.1A-R1`, `16.2C`,
`16.4B-R1`, `16.4B-R2`, `16.5A-R1`).

**The two most important outcomes are both things the release board
caught rather than things the plan delivered:**

1. **A data-loss defect shipped inside `WP 16.4B` and is now closed.**
   The attachment reconciliation sweep could permanently delete a file a
   user was in the middle of attaching, while the metadata continued to
   claim the file existed. `TD-97` had already been marked **Resolved**
   against that code. Two reviewers found it independently; one
   reproduced it with probes against the real classes. It is fixed by the
   write-intent marker the release plan had specified in the first place
   and the implementing stream had substituted away.

2. **Two decisions shipped without the ADR the project's own governance
   requires**, and one register the health check does not derive had
   already drifted again one Work Package after `TD-57` closed. Both are
   now closed (`ADR-0121`, `ADR-0122`; DI Register corrected).

**Scale.** 64 commits, 22 merges since `v0.15.0`. 221 files changed
(+35,141 / −9,538). Production source: 50 files (+3,078 / −130). Tests:
64 files (+5,700 / −177).

**What is NOT done** — see §7. In short: no clean CI run on a final
commit; `WP 16.9.0` (readiness review, version bump, release notes, PR)
not started; no secondary review of the remediation diff; and
**`D-021`–`D-026` remain Proposed and unratified.** *(Superseded: all
six were ratified by the Product Owner on 2026-09-05. This sentence is

## 4. Review board — 9 perspectives

Each perspective ran against the integrated tree. The last four ran
against an **immutable pinned checkout** (tag `review-board-v0.16.0` at
`ac7daa6`) after an earlier reviewer had the repository move underneath
them mid-review, which invalidated their citations — itself a finding.

### RED (2) — both remediated

**R1. The attachment sweep can permanently delete a live file.**
`AttachContentAsync` writes content, then object state (`ADR-0114`
decision 4, deliberate). The sweep listed states, then content keys, and
deleted any content nothing referenced. A sweep between those two writes
deleted the bytes; the state write then recorded an attachment whose
hash pointed at content that no longer existed — **silent, permanent
loss, with metadata still claiming the file was there.** Reading states
first made the window *wider*, not narrower.

Found by the security perspective, independently reproduced by the
persistence perspective, which also found the same race in the
**Materials** sweep with a worse consequence: a fully-registered
material's index entry deleted, leaving the document intact but
unfindable — and because `RegisterAsync`'s duplicate check reads that
index, a later registration for the same id would not see a duplicate,
producing two conflicting documents under one identifier.

*Aggravating:* `TD-97` was already marked **Resolved** against this code,
and the release plan (line 241) had specified "a write-intent marker
before multi-file writes" — the implementing stream substituted a plain
comparison, and that substitution opened the race.

**Fix (`WP 16.4B-R2`)**: write-intent marker (`Mark → content → state →
Clear`), plus read reordering across all three sweeps. **The first
attempt was rejected** for sampling the marker *after* the state read,
which left a live window (state write lands after the state read, `Clear`
runs, marker read finds nothing). Correct order is
**content → markers → states**, which is provably airtight: to be
collected, content must be unmarked at the marker read; since the mark
precedes the content, that implies `Clear` already ran, which implies the
state write completed before the *later* state read — so it is
referenced. The corrected fix was verified by reverting to the broken
order and watching the new test fail.

**R2. A closed test race, reopened.** `RestartProofTests` redirects the
process-wide `Console.Out` without joining the collection that serialises
the 52 classes doing so — the exact defect `TD-34` closed in this same
release. It was the only such file outside the collection, and landed on
a parallel branch ~11 minutes after `WP 16.4A` merged the last
stragglers in. Fixed.

## 8. Questions worth an external architect's attention

1. **Is the write-intent marker the right closure**, or does the
   content-before-state ordering (`ADR-0114` decision 4) need revisiting
   now that a concurrent reader — not just a crash — can observe the
   window? The ADR's reasoning predates the existence of a sweep.
2. **Materials and Requirements sweeps have no marker** — only the read
   reordering. That is sound for their two-read shape, but has no runtime
   backstop if a future change breaks the document-before-index
   invariant. Is asymmetric protection acceptable?
3. **Should the three reconciliation services exist at all** in a release
   that forbids new capability, given nothing invokes them? The argument
   for: `TD-67` named "no reconcile path exists" as the defect. The
   argument against: unreachable code.
4. **`ADR-0122` changed the DI container from last-wins to
   first-wins-unless-opted-in** platform-wide. The audit found zero
   legitimate replacers among ~330 call sites. Is `allowReplace` the
   right escape hatch, or should there be none?
5. **`ADR-0121` documents a pattern that may already be obsolete** —
   `WP 16.4B`'s own `HasDefaultValue` support would now let a single
   public constructor do the same job. Recorded as such. Supersede now,
   or leave until a second consumer appears?
