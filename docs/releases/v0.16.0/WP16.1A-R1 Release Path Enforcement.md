# WP 16.1A-R1 — Release Path Enforcement

**Type.** CI and release-script configuration, plus two documentation
corrections. No production code or test.
**Branch.** `feature/v0.16.0` (integration line).
**Closes.** Nothing in the Technical Debt Register. `TD-45` stays Open —
its closing action is still the GitHub branch-protection setting, which
remains a Product Owner action.
**Cites.** The `v0.16.0` review board's Build, CI & Release Engineering
perspective, findings 3, 4, 5 and 8; `docs/releases/v0.16.0/WP16.1A
Enforce the Release Gate.md`; `FCR-0005`. `D-021`–`D-026` remain
**Proposed**; nothing here approves anything.

---

## Why this exists

`WP 16.1A` made `CI Gate` depend on the Governance Health Check, so no
branch reaches `main` carrying a governance register that has drifted
from source. The review board then asked the obvious next question — is
the *release* path as strong as the *merge* path? — and found it was
not. Three of the four findings below are about that gap; the fourth is
a documentation contradiction this release exists to end.

## What changed

**1. `release.yml` now runs the Governance Health Check, as a hard gate.**
The workflow that actually builds, verifies and publishes a tag never ran
the check at all. A tag could therefore be published carrying exactly the
drift `CI Gate` would have rejected on the way to `main` — and with
branch protection still unconfigured (`TD-45`), nothing else stood in the
way either. The step fails the publish, in the same shape as the existing
Build and Test steps.

**2. `scripts/new-release.ps1` now hard-fails when CI is not green.**
It previously queried `gh run list` and printed a **yellow warning** on
failure or absence, then continued — so a human who did not read the
warning could tag and push a commit whose `CI Gate` was red, or had never
run. It now reads the run's `conclusion` and throws unless it is exactly
`success`.

The specific hazard here was caught live rather than reasoned about: the
review board observed run `33950873014` complete as **`cancelled`**, not
`failure`, because a later push superseded it under
`concurrency: cancel-in-progress`. A check written as "block on failure"
would have waved that through. The check is written as "require
`success`", and the code comment says why.

A `-SkipCiCheck` switch exists for the one legitimate case — `gh` cannot
reach the run from where the operator is standing, and they have
confirmed the run on GitHub themselves. It does not make an un-green
commit taggable; it moves the check off the machine and onto the person,
who then owns it, and it says so on the console when used.

**3. `linux-launch-smoke` now requires a positive startup marker.**
The job treated exit code 124/137 — "still running when `timeout` fired"
— as success. That is not evidence of a successful launch: a process that
deadlocks *after* Avalonia platform initialisation (a stuck DI
resolution, a frozen dispatcher loop) is also still running at 25
seconds, and passed identically to a healthy one. The timeout branch now
additionally requires `Host -> Running.` in the captured log.

**The marker was verified empirically, not assumed.** A real
`xvfb-run` launch was run on this branch and its log inspected: the line
is `TempestHost.EnterRunning`'s own, appears exactly once, at
`07:03:21.139`, followed by real navigation activity. The job's own
`grep` was then run against that captured log to confirm it matches. A
marker taken from a source grep without a real launch behind it would
have risked a job that fails always — the exact class of unverified
claim this release exists to stop.

The job stays **advisory** and stays out of `gate`'s `needs:`. The
review board agreed that call is right; strengthening what the check
proves is a separate question from whether it should block, and only the
first is in scope here.

**4. `PHYSICAL_REVIEW.md` no longer contradicts itself about Linux.**
Its §1 table still read "**Linux cannot currently launch the desktop
application**" while §8 item 1, rewritten by `WP 16.5B`, said the
opposite; §9's troubleshooting row pointed a reader at a section
asserting the reverse of their symptom. The §1 row now states that Linux
launches, and — deliberately — that it does so on weaker evidence than
Windows: one local `xvfb-run` launch plus an advisory, non-required CI
job. The §9 row now says the symptom was `TD-116`, resolved, so seeing it
today is a new defect rather than the known one.

**5. `PDFtoImage` 4.1.1 carries a rationale.** It was the one
version-sensitive pin in `Tempest.Desktop.csproj` with no comment while
every other one has one. The comment records what it is (not a security
hold — the vulnerability scan is clean and NuGet shows no deprecation)
and what it is not (evaluated): 5.x changes the native SkiaSharp/PDFium
dependency set, which is the same class of change that produced
`TD-116`, so it wants its own timeboxed spike with a real Linux and
Windows launch behind it, not a version bump in a hygiene release.

## What did not change, and why

- **`TD-45` stays Open.** Everything above hardens the paths this
  session can reach. None of it configures GitHub branch protection,
  which is `TD-45`'s stated closing action and a repository-administrator
  act. Until it is set, "the gate exists" is still not "the gate is
  enforced", and the release board should read it that way.
- **`linux-launch-smoke` stays advisory.** Promoting it to a required
  check needs a track record it does not have yet, and a promotion
  criterion nobody has set. Named as an open question, not decided here.
- **The Digital Thread edge-keyboard gap, and the other review-board
  findings outside this perspective**, are handled in their own Work
  Packages (`WP 16.5A-R1`) or recorded as debt (`TD-123`–`TD-128`).

## Validation

All local, on the integration line:

- `dotnet build src/TempestOS.slnx -c Release -p:TreatWarningsAsErrors=true`
  — 0 warnings, 0 errors. Also Debug — 0 warnings, 0 errors.
- Both workflow files parse as valid YAML; `new-release.ps1` parses
  under the PowerShell parser.
- The `linux-launch-smoke` change was validated against a real captured
  launch log, as described above, rather than only by reading it.
- `scripts/governance-healthcheck.ps1` — 14 passed, 2 warned, 0 failed
  (of 16). Both warnings are informational and pre-existing.
- **A defect in this Work Package's own first attempt was caught by its
  own gate and is recorded rather than quietly fixed:** the `PDFtoImage`
  rationale comment initially contained a literal `--` inside an XML
  comment, which is illegal and broke `Tempest.Desktop.csproj`
  (`MSB4025`). The warnings-as-errors build failed immediately. Noted
  because a release whose subject is enforcement should show its own
  enforcement working on itself.
