# WP 16.9.0 — Engineering Release Report (v0.16.0)

**Type.** Verification and release preparation. The Engineering Readiness
Review required by `ADR-0106`, executed by the Programme Review structure
that ADR mandates.
**Release candidate.** `d7d3f3b`, frozen on `release/v0.16.0-rc`.
**Recommended verdict.** **ACCEPT WITH OBSERVATIONS** — derived below,
not chosen.

> **This document recommends. It does not certify.** Engineering
> Governance §9 reserves the verdict to Product Approval, and `ADR-0106`
> repeats it: "the Programme Review recommends, it never decides."
> `D-021`–`D-026` were **ratified by the Product Owner on 2026-09-05**
> (gate 1 of 4, scope only). `main` is untouched. Nothing is merged,
> tagged or published, and no Product Approval verdict is recorded.

---

## 1. How this review was conducted

`ADR-0106` requires five categories, independently reviewed by a
multi-discipline Programme Review, findings classified by a fixed
three-kind taxonomy, and a verdict derived by a single exclusive priority
order.

This release ran that structure **twice**, because the first pass found
defects in the release's own work and the remediation then needed
reviewing in its own right:

- **Board 1 — nine perspectives** against the integrated tree: governance,
  documentation/registers, build-CI-release, accessibility, product
  scope, architecture, security, persistence, test quality.
- **Board 2 — six fresh perspectives** against a pinned, immutable
  checkout, with an explicit mandate to assume board 1 had missed
  something and that **the remediation itself may have introduced
  defects**. No reviewer on board 2 had written the code it examined.

Board 2 was not a formality. It found the most serious defect of the
release, which board 1 had missed and which the remediation for board 1's
own finding did not close.

## 2. The five categories

### Architecture readiness — **Pass, with observations**

The two substantive mechanisms — schema-versioned durable state
(`ADR-0120`) and the DI registration contract (`ADR-0122`) — were
independently re-derived and hold. Layering is intact: `Tempest.Core`
carries zero project references, and ASP.NET Core remains confined to
`RestApiHostedService` per `ADR-0049`, verified by direct grep rather
than assumed. The composition-root carve-out (`ADR-0009`/`ADR-0017`) is
correctly applied.

Three decisions shipped without the ADR §5 requires. All three are now
written: `ADR-0121` (a test-only construction seam is an `internal`
constructor), `ADR-0122` (registering a service twice is an error), and
`ADR-0123` (a migration-chain collision is a registration error, with no
opt-out). `ADR-0123` was written only after board 2 rejected a Work
Package's own explicit "No ADR" judgement.

*Observations:* the migration-walk algorithm is duplicated across the two
migration seams rather than shared; the document-partition-by-Kind loop
now appears four times. Both recorded for a future release rather than
refactored — this release forbids scope creep, and neither is a defect.

### Implementation readiness — **Pass, with observations**

**One data-loss path was found and closed during this review, and it is
the most important fact in this report.** `EngineeringObjectBase.
PersistStateAsync` captured live state and then issued an unconditional
whole-record overwrite with nothing serialising the pair. Two concurrent
mutations on one object could land their saves in the opposite order to
their captures; the later-landing, earlier-captured snapshot silently
dropped the other's change from disk. Once that dropped an attachment
reference, the reconciliation sweep deleted its bytes as a genuine
orphan — while the caller who received a successful `IAttachment` still
believed the file existed.

Reproduced against the real classes on trial 323 of 500, with no
artificial delays. Closed by `WP 16.4B-R3` with an `AsyncKeyedLock` keyed
by object Id, held from before `CaptureState()` through `SaveAsync`, after
an exhaustive re-entrancy audit found no nested path. The lock is keyed
by Id rather than held per instance because `ReviseAsync` demonstrably
constructs a second live instance for the same Id — an instance lock would
have closed nothing. `TD-135`, Resolved.

The lineage matters for judging this release's process: `WP 16.4B` shipped
an attachment-sweep race → board 1 caught it → `WP 16.4B-R2`'s first fix
was **rejected** for narrowing rather than closing it → the corrected fix
landed → board 2 then found the marker's proof rested on a false
single-writer assumption → `WP 16.4B-R3` closed the real defect. Four
passes. Each found what the previous missed.

*Observations:* `PersistenceStore`'s atomic writes are crash-safe but not
power-loss durable (no `fsync`); recorded, not fixed, because changing the
most load-bearing write path in a hygiene release is the wrong trade.

### Verification readiness — **Pass, with observations**

The five-run CI determinism matrix required by `WP 16.4A`'s own acceptance
line was obtained on the frozen candidate — five for five, §4.1.

Board 2 proved, by mutation, that four tests guarding this release's
highest-risk code **could not fail**: two sweep race tests whose gates
paused on a collection name rather than call order (reverting the
production fix moved the watched collection to the first call, so the
interleaving never occurred), a double-dispose test with a measured 0.45%
detection rate, and a golden corpus whose "every field is compared" claim
omitted `Metadata`. All four are fixed and each fix is mutation-proven in
both directions — demonstrated failing against reverted code and passing
against restored code. `WP 16.4A-R1`.

*Observations:* the focus-ring contrast test cannot see any
`Flat`-treatment state (`TD-131`); the attachment sweep's own gates are
not yet timeout-bounded, disclosed rather than silently skipped.

### Governance readiness — **Pass, with observations**

`scripts/governance-healthcheck.ps1`: **14 passed, 2 warned, 0 failed**
of 16. Both warnings are informational and pre-existing.

Board 2's governance audit searched every citation of `D-021`–`D-026`
across the tree and found **no document claiming, implying or relying on
approval that has not been given**. The Decision Register genuinely stops
at `D-020`.

It also found four register/status falsehoods, all now corrected: the DI
and Platform Services registers each claimed complete coverage while
omitting `IAttachmentWriteIntentStore`; `WP 16.4A` was marked flatly
Complete despite its own acceptance being unmet; `WP 16.2C` was marked
Complete having left six Work Packages without retrospectives; and
`PROJECT_STATUS.md`'s headline metrics were stale by material margins.

**Register drift recurred three times inside this release**, each time in
one of the three registers no machine check derives. That is `TD-123`, and
it is the most important governance lesson here: the checks that were
extended caught things, and the registers left un-derived drifted again
within days.

*Observations:* `TD-123`, `TD-124`, `TD-125` remain open and are the
mechanism by which this class of drift will recur.

### Release readiness — **Pass, with observations**

`VERSION` is `0.16.0`. Release Notes are written, including the platform
matrix and the verified one-way downgrade door. All 18 Work Package rows
carry truthful status. The release path was itself hardened this release
(`WP 16.1A-R1`): `release.yml` now runs the governance check, and
`new-release.ps1` refuses to tag a commit whose CI did not conclude
`success` — a check that previously warned and continued, and which board
1 caught waving through a run that completed as `cancelled` rather than
`failure`.

*Observations, and these are Product Owner preconditions, not engineering
gaps:* `main` is untouched and §7.3's pre-tag Build/Test Gate run on
`main` has therefore not occurred; GitHub branch protection remains
unconfigured (`TD-45`), so the gate exists in the workflow but nothing on
GitHub enforces it; and `D-021`–`D-026` are unratified.

## 3. Findings by `ADR-0106`'s three-kind taxonomy

**Release Blocking — none remain.** Three existed and all three were
closed during this review: the lost-update data-loss path (`TD-135`), the
tests that could not fail, and — found by the third and final board, after
this report first claimed the count was two — the *second* lost update, on
`ReviseAsync`, the one durable-write path `TD-135`'s own fix never routed
through its lock (`TD-136`, `WP 16.4B-R4`). All three had real,
demonstrated evidence of harm: reproduced against the real classes, not
argued. The count in this paragraph read "two" until board 3 ran, and the
correction is left visible rather than smoothed over, because a readiness
review that quietly revises its own blocker count is worth nothing.

**Disclosed, Non-Blocking — 13.** `TD-45` (branch protection),
`TD-123`–`TD-134`. (`TD-136` is not among them: it was raised and closed
inside this review, like `TD-135` before it.) Each is real, tracked, newly raised or newly relevant,
and named rather than absorbed.

**Pre-Existing, Unaffected — the standing Open debt** this release neither
caused, worsened, nor re-raised, disclosed for completeness in the
Technical Debt Register's 70 Open rows.

### 4.1 CI evidence — the five-run determinism matrix

`WP 16.4A`'s acceptance line requires five consecutive clean CI runs, both
configurations, on one immutable commit. Local repetition does not satisfy
it and was not substituted for it. All five ran on GitHub-hosted runners
against SHA `d7d3f3b093061f177a37cd2bf17a06cb8e55dd94`, on branch
`release/v0.16.0-rc`, which exists solely to hold the candidate still.
The workflow's `concurrency` group is `ci-<workflow>-<ref>` with
`cancel-in-progress: true`: runs sharing a ref cancel each other, runs on
different refs do not. Had the matrix been dispatched on
`feature/v0.16.0`, every `WP 16.9.0` documentation commit pushed while it
ran would have killed the run in flight — which is not hypothetical, it is
what runs 191, 192 and 193 each did to their predecessor. Giving the
candidate a ref of its own is what made five *consecutive* runs obtainable
rather than merely five attempted.

| # | Run | ID | Started (UTC) | Duration | Conclusion |
|---|---|---|---|---|---|
| 1 | 195 | `33958003532` | 09:26:48 | 10m 55s | **success** |
| 2 | 197 | `33958632949` | 09:40:43 | 8m 44s | **success** |
| 3 | 199 | `33959162460` | 09:52:54 | 9m 18s | **success** |
| 4 | 201 | `33959683856` | 10:04:48 | 9m 47s | **success** |
| 5 | 202 | `33960215260` | 10:16:41 | 7m 59s | **success** |

Each run is five jobs, and in all five runs every one of the five
concluded `success` — no cancellation, no retry, no re-run of a failed
job, and no `continue-on-error` masking a failure:

| Job | Runner | Runs green |
|---|---|---|
| `Build & Test (Release)` | `windows-2022` | 5 / 5 |
| `Build & Test (Debug)` | `windows-2022` | 5 / 5 |
| `Governance Health Check` | `windows-2022` | 5 / 5 |
| `CI Gate` (needs both configurations + governance) | `windows-2022` | 5 / 5 |
| `Linux Launch Smoke` (advisory) | `ubuntu-latest` | 5 / 5 |

Two disclosures, so the record is not read as tidier than it is.

**The run numbers are not contiguous** (195, 197, 199, 201, 202), and it
is worth saying exactly what is in the gaps rather than waving at them.
`run_number` is per-workflow, so 196, 198 and 200 are `ci.yml` runs too —
each the automatic `push` run for one of the `WP 16.9.0` documentation
commits landing on `feature/v0.16.0` while the matrix was running on its
own frozen ref. That the two sequences interleave without interfering is
the separate-ref decision working as intended. All three concluded
`success`, and one of them matters to the question §4.1 closes on:
**run 200 (`33959195477`) is the branch tip `c6a16a5`**, the same commit
this evidence is being read against, and it passed a full CI run of its
own. The applicability argument below does not rest on that — it rests on
the diff — but the tip has independently been through CI, not merely
argued to be equivalent.

**Two runs at `d7d3f3b` were cancelled, and neither is counted here.**
Run 193 was the `push` run on `feature/v0.16.0`; run 194 was the `push`
run created seconds later when the same commit was pushed to
`release/v0.16.0-rc`. Both were cancelled by the `concurrency` rule as
designed — 194 three seconds after it started, by the dispatch of run 195.
They are excluded because neither executed a test, not because either
failed: a cancelled run is evidence of nothing, and is counted here as
neither a pass nor a failure. Every run in the matrix table is a
`workflow_dispatch`, every one is after both cancellations, and no run in
the table was re-run or retried.

**This evidence was invalidated, and re-obtained rather than argued
around.** The matrix above ran on `d7d3f3b`. For as long as every later
commit touched only `docs/`, it covered the tree being released, and this
section said so with a mechanical check behind it.

That stopped being true. The final release review (board 3, §5 of the
Review Board Disposition) found a data-loss defect and two further
findings whose remediation changes `src/`, `tests/`, `scripts/` and
`.github/`. The determinism acceptance is an acceptance on *a commit*, and
the commit changed. Nothing about a fix to `ReviseAsync` is likely to
perturb test determinism — and that reasoning is exactly what a
determinism gate exists to refuse. `WP 16.4A`'s own history is the
argument: an independent reviewer refused 16/16 clean local runs as
insufficient, citing `WP 13.12.9`, where a flake reproduced zero times in
25 local attempts and still failed a real release run.

So the matrix was re-run in full on the remediated candidate. Both results
are recorded below rather than the first being deleted, because the
superseded run is what makes the re-run's necessity legible.

The re-run's evidence is §4.2. It is not a tidier version of §4.1 — it
records a genuine failure before the five passes, because that failure is
the reason to trust the passes.

## 5. What this release did not verify

Stated plainly, because a readiness review that omits this is worthless:

- **macOS is not verified.** There is no macOS CI. It is expected to work
  and is untested.
- **No CI step on any platform launches the real windowed application** —
  the suites are Avalonia headless. Linux's launch is evidenced by an
  advisory smoke job asserting `Host -> Running.`; Windows's is asserted
  from development experience with no citation, which board 2 flagged and
  `PHYSICAL_REVIEW.md` now says outright.
- **Downgrade is a one-way door.** After running v0.16.0, any object it
  re-saves is unreadable to v0.15.0, whose read path logs a warning and
  returns `null` — so the object silently disappears from that workspace.
  Verified empirically. In the Release Notes.

## 6. Verdict derivation

`ADR-0106` §4's priority order, applied once over every finding:

1. Any category **Not Ready**? **No** — no Release Blocking finding
   remains; both that existed were closed and verified.
2. Any **Disclosed, Non-Blocking** finding anywhere? **Yes** — 13.

→ **ACCEPT WITH OBSERVATIONS.**

This is a recommendation to Product Approval. It is not certification, and
this document does not record a verdict in `Release Register.md` —
that field is Product Approval's to fill, and leaving it blank is
deliberate.
