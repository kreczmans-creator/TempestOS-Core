## 1. How this review was conducted

`ADR-0106` requires five categories, independently reviewed by a
multi-discipline Programme Review, findings classified by a fixed
three-kind taxonomy, and a verdict derived by a single exclusive priority
order.

This release ran that structure **twice**, because the first pass found
defects in the release's own work and the remediation then needed
reviewing in its own right:

- **Board 1 — nine perspectives** against the integrated tree: governance,
  documentation/registers, build-CI-release, accessibility, product
  scope, architecture, security, persistence, test quality.
- **Board 2 — six fresh perspectives** against a pinned, immutable
  checkout, with an explicit mandate to assume board 1 had missed
  something and that **the remediation itself may have introduced
  defects**. No reviewer on board 2 had written the code it examined.

Board 2 was not a formality. It found the most serious defect of the
release, which board 1 had missed and which the remediation for board 1's
own finding did not close.

### Implementation readiness — **Not Ready**

*(Re-derived `WP 16.4B-R6` round 2, 2026-09-06. This heading read

**One data-loss path was found and closed during this review, and it is
the most important fact in this report.** `EngineeringObjectBase.
PersistStateAsync` captured live state and then issued an unconditional
whole-record overwrite with nothing serialising the pair. Two concurrent
mutations on one object could land their saves in the opposite order to
their captures; the later-landing, earlier-captured snapshot silently
dropped the other's change from disk. Once that dropped an attachment
reference, the reconciliation sweep deleted its bytes as a genuine
orphan — while the caller who received a successful `IAttachment` still
believed the file existed.

Reproduced against the real classes on trial 323 of 500, with no
artificial delays. Closed by `WP 16.4B-R3` with an `AsyncKeyedLock` keyed
by object Id, held from before `CaptureState()` through `SaveAsync`, after
an exhaustive re-entrancy audit found no nested path. The lock is keyed
by Id rather than held per instance because `ReviseAsync` demonstrably
constructs a second live instance for the same Id — an instance lock would
have closed nothing. `TD-135`, Resolved.

The lineage matters for judging this release's process: `WP 16.4B` shipped
an attachment-sweep race → board 1 caught it → `WP 16.4B-R2`'s first fix
was **rejected** for narrowing rather than closing it → the corrected fix
landed → board 2 then found the marker's proof rested on a false
single-writer assumption → `WP 16.4B-R3` closed the real defect. Four
passes. Each found what the previous missed.

*Observations:* `PersistenceStore`'s atomic writes are crash-safe but not
power-loss durable (no `fsync`) — `TD-137`; recorded, not fixed, because
changing the most load-bearing write path in a hygiene release is the
wrong trade.

**What makes this category Not Ready, added `WP 16.4B-R6` round 2,

## 5. What this release did not verify

Stated plainly, because a readiness review that omits this is worthless:

- **macOS is not verified.** There is no macOS CI. It is expected to work
  and is untested.
- **No CI step on any platform launches the real windowed application** —
  the suites are Avalonia headless. Linux's launch is evidenced by an
  advisory smoke job asserting `Host -> Running.`; Windows's is asserted
  from development experience with no citation, which board 2 flagged and
  `PHYSICAL_REVIEW.md` now says outright.
- **Downgrade is a one-way door.** After running v0.16.0, any object it
  re-saves is unreadable to v0.15.0, whose read path logs a warning and
  returns `null` — so the object silently disappears from that workspace.
  Verified empirically. In the Release Notes.
