# WP 16.5B — Linux/X11 Avalonia Upgrade Spike — Implementation Report

**Type.** Timeboxed spike (one day) plus its resulting production, test,
CI and documentation changes. Governed by `D-025` (Proposed,
`docs/releases/v0.16.0/WP16.0A v0.16.0 Scope Decision.md`) and
`TD-116` (`docs/governance/Quality/Technical Debt Register.md`).
**Branch.** `feature/v0.16.0-wp16.5b-linux-spike`, cut from
`feature/v0.16.0`.
**Closes.** `TD-116` — resolved. Realises `docs/releases/v0.16.0/v0.16.0
Release Plan.md`'s "WP 16.5B" brief and `D-025`'s Linux clause.
**Status.** **Spike succeeded.** Avalonia upgraded to `11.3.20`,
`Tmds.DBus.Protocol` repinned to `0.21.3`, the solution builds
0 Warnings/0 Errors under `TreatWarningsAsErrors`, the full `Tempest
.Desktop.Tests` and `Tempest.Core.Tests` suites pass, and the built
application launches under `xvfb-run` with no exception and no crash
log. A `linux-launch-smoke` CI job is added, advisory for this release.

---

## 1. Objective

`TD-116` had a known cause and two remedies that trade against each
other — revert a deliberate security pin, or find a newer Avalonia that
binds against a patched `Tmds.DBus.Protocol` — and no decision. This
Work Package's only job was to spend one day finding out which remedy
actually works, apply it if it does, and either way turn `TD-116` from
"open, undecided" into a closed, evidenced answer.

## 2. Reproduction (before)

Built and launched the pre-upgrade tree exactly as `TD-116` describes:

```
dotnet build src/Tempest.Desktop/Tempest.Desktop.csproj -c Release
xvfb-run -a timeout 20 dotnet src/Tempest.Desktop/bin/Release/net10.0/Tempest.Desktop.dll
```

Build succeeded (0 Warnings, 0 Errors). The launch crashed immediately,
exit code 134 (`SIGABRT`), with this on stderr — verbatim:

```
Unhandled exception. System.TypeLoadException: Could not load type 'Tmds.DBus.Protocol.Connection' from assembly 'Tmds.DBus.Protocol, Version=0.94.2.0, Culture=neutral, PublicKeyToken=9abd76e9812c1bca'.
   at Avalonia.FreeDesktop.DBusIme.X11DBusImeHelper.DetectAndRegister()
   at Avalonia.X11.AvaloniaX11Platform.Initialize(X11PlatformOptions options)
   at Avalonia.AvaloniaX11PlatformExtensions.<>c.<UseX11>b__0_0()
   at Avalonia.AppBuilder.SetupUnsafe()
   at Avalonia.AppBuilder.Setup()
   at Avalonia.AppBuilder.SetupWithLifetime(IApplicationLifetime lifetime)
   at Avalonia.ClassicDesktopStyleApplicationLifetimeExtensions.StartWithClassicDesktopLifetime(AppBuilder builder, String[] args, Action`1 lifetimeBuilder)
   at Tempest.Desktop.Program.Main(String[] args) in .../src/Tempest.Desktop/Program.cs:line 21
Aborted
```

No crash log was written to `logs/tempestos-crash.log` — expected:
`CrashLog.Install()` (`src/Tempest.Desktop/Diagnostics/CrashLog.cs`) is
called from `App`'s construction, and this exception is thrown inside
`AppBuilder.Setup()`, before `App` is ever constructed. This matches
`TD-116`'s own recorded reproduction exactly.

## 3. The fix applied

`src/Tempest.Desktop/Tempest.Desktop.csproj`:

| Package | Before | After |
|---|---|---|
| `Avalonia` | `11.2.3` | `11.3.20` |
| `Avalonia.Desktop` | `11.2.3` | `11.3.20` |
| `Avalonia.Themes.Fluent` | `11.2.3` | `11.3.20` |
| `Avalonia.Fonts.Inter` | `11.2.3` | `11.3.20` |
| `Tmds.DBus.Protocol` | `0.94.2` | `0.21.3` |

`tests/Tempest.Desktop.Tests/Tempest.Desktop.Tests.csproj`:
`Avalonia.Headless.XUnit` `11.2.3` → `11.3.20` (the only other
`Avalonia.*` reference in that project). `Directory.Build.props` has no
Avalonia-related settings; nothing there needed a change.

**Why `0.21.3`, not the pre-upgrade `0.94.2`.** Research done ahead of
this spike (verified against the NuGet nuspecs and osv.dev) found:
`Avalonia.FreeDesktop 11.2.x` depends on `Tmds.DBus.Protocol >= 0.20.0`
— the version carrying the advisory. `Avalonia.FreeDesktop 11.3.14+`
raised that floor to `>= 0.21.3`. `0.21.3` and `0.92.0+` are both
listed as fixed versions for `GHSA-xrw6-gwf8-vvr9`, but they are two
different API lines: `0.21.3` is the advisory's fix backported onto the
pre-rewrite `0.2x` line — the same member layout `0.20.0` had — while
`0.92.0+` belongs to a `0.9x` line that rewrote the library's public
surface. `Avalonia.FreeDesktop`'s compiled IL binds `Tmds.DBus.Protocol`
by that member layout, not by semantic version: it is exactly this
mismatch that made `0.94.2` (patched, but on the rewritten line) throw
`TypeLoadException` against `Avalonia.FreeDesktop 11.2.3`, which is
`TD-116` in one sentence. `0.21.3` is the lowest version that is both
patched and binary-compatible with `Avalonia.FreeDesktop`'s current
build, so it is the direct pin. `Tempest.Desktop.csproj` carries the
full version of this reasoning in its own comment, next to the pin.

## 4. Build under the CI gate

```
dotnet build src/TempestOS.slnx -c Release -p:TreatWarningsAsErrors=true
```

Upgrading Avalonia surfaced one compile break unrelated to the
`Tmds.DBus.Protocol` fix: `src/Tempest.Desktop/Views/ProjectExplorerView.cs`
uses the drag/drop API (`DataObject`, `DragDrop.DoDragDrop`,
`DragEventArgs.Data`) that Avalonia 11.3 marks `[Obsolete]` in favour of
a new typed `DataTransfer`/`DataFormat<T>`/`DoDragDropAsync` API —
6 × `CS0618`, each a hard error under `TreatWarningsAsErrors`.

The new API is a real redesign, not a rename: `DataFormat<T>` has no
built-in `Guid` format (this code drags a node's `Guid` id), so adopting
it means designing a custom format/serializer for that id and rewriting
every read/write site — more than the "small, obvious edit" this spike
is timeboxed to make in `src/`. The old API is not removed, only
deprecated, and remains fully functional. Fixed by narrowly suppressing
`CS0618` around the four call sites that use it (`#pragma warning
disable/restore CS0618`, with a comment naming the reason and pointing
here), with **no behaviour change** to drag-and-drop. Migrating to the
new API is left as a disclosed follow-up, not this Work Package's job.

Result: **0 Warnings, 0 Errors.**

## 5. Full test suites (after the upgrade)

```
xvfb-run -a dotnet test tests/Tempest.Desktop.Tests -c Release --no-build
dotnet test tests/Tempest.Core.Tests -c Release --no-build
```

First run of `Tempest.Desktop.Tests`: **407 passed, 1 failed, 408
total.** The failure —
`WorkspaceLayoutControllerTests.EveryRenderedPane_IsADropCandidate_WithARealRectangle`
— asserted every rendered pane has a real (non-zero) on-screen rectangle
and got three zero-sized rectangles at the origin instead.

**Diagnosis.** Not a product regression: `WorkspaceLayoutController
.CurrentCandidates()` (`src/Tempest.Desktop/Docking
/WorkspaceLayoutController.cs`) reads `Visual.Bounds`, which the test's
own rig sets by calling `Measure`/`Arrange` directly on the host control
after `Window.Show()`. Under Avalonia 11.2.3's headless backend that
applied synchronously; under 11.3.20 part of the layout pass is now
queued onto the dispatcher, so reading `Bounds` immediately afterwards
observes it before that queued work runs. This is a genuine Avalonia
11.3 headless behaviour difference, not a bug in the test's assertions.
Fixed with the repository's own established drain for exactly this
situation — `Dispatcher.UIThread.RunJobs()`, the same pattern already
used in `ProjectTaskAcceptanceTests.LayOutAsync` and
`UndoRedoThreadingTests` — called once before and once after the
Measure/Arrange pair in `WorkspaceLayoutControllerTests.BuildRig`. No
assertion was weakened or removed.

Re-run after that one-line test fix:

| Suite | Result |
|---|---|
| `Tempest.Desktop.Tests` | **408 passed, 0 failed, 408 total** |
| `Tempest.Core.Tests` | **3,088 passed, 0 failed, 3,088 total** |

## 6. Launch evidence (after)

```
xvfb-run -a timeout --kill-after=10 25 dotnet src/Tempest.Desktop/bin/Release/net10.0/Tempest.Desktop.dll
```

Exit code **137** (killed — see the note below on why 137, not 124).
stderr: **empty**. No exception anywhere in stdout. No
`logs/tempestos-crash.log` was written. stdout shows a complete,
ordinary startup: host lifecycle phases (Configuration Built → License
Validated → Plugin/Framework/Module Discovery → Module Registration →
60 DI registrations → 6 workspace-explorer modules initialised),
`Now listening on: http://127.0.0.1:5080` / `REST API listening on
http://127.0.0.1:5080.` (`PHYSICAL_REVIEW.md` §8's own known port-bind
behaviour, working as documented), a navigation event to the default
workspace, and finally `Application is shutting down...` once the
timeout's `SIGTERM` arrived — i.e. the process was still up, running
normally, and responding to signals when the timeout fired; nothing
about the launch itself failed.

**Why 137 and not 124.** `timeout`'s plain `SIGTERM` did not end the
process within the run — it logged the shutdown message but did not
fully exit even ~3 minutes later in one earlier trial, so `timeout
--kill-after=10` was used to force a `SIGKILL` after a 10-second grace
period, which is what produced exit 137 (128+9) instead of `timeout`'s
own 124. This is disclosed as a separate, minor finding (§8 below); it
does not affect the `TD-116` verdict, since the failure `TD-116`
describes is an immediate crash during platform initialisation, and
none occurred — the process ran a full, ordinary session instead.

No screenshot was captured: `xwd`, `import` and `convert` are not
installed in this environment (`which` found none of the three), so a
visual capture was not possible. The exit-code plus full, exception-free
startup/shutdown log above is the evidence in its place.

## 7. CI: `linux-launch-smoke`

Added to `.github/workflows/ci.yml` as its own job, `runs-on:
ubuntu-latest`: `setup-dotnet` from `global.json`, restore, build
`Tempest.Desktop` Release, install `xvfb` via `apt-get`, then the same
`xvfb-run -a timeout --kill-after=10 25 dotnet
.../Tempest.Desktop.dll` launch, treating exit code 124 **or** 137 as
success (per §6's finding above) and any other exit — or a written
crash log — as failure. **Deliberately not added to `gate`'s `needs:`
list** — it is advisory for this release, per the Release Plan's own
"Linux `dotnet run` smoke step added to CI" language and this Work
Package's timebox; the Windows `build-and-test` and
`governance-health-check` jobs are unchanged. YAML validated with
`python3 -c "import yaml; yaml.safe_load(...)"` — parses cleanly, and
`gate`'s `needs` remains `build-and-test` only.

## 9. What was NOT done

- **`ProjectExplorerView`'s drag/drop was not migrated** to Avalonia
  11.3's new `DataTransfer`/`DataFormat<T>`/`DoDragDropAsync` API — see
  §4. The obsolete-but-functional old API is suppressed, not replaced.
  This is new, disclosed debt from this Work Package's own upgrade; it
  is not tracked as a register row here because the brief for this
  spike is `TD-116` alone and a one-day timebox — recommended as a
  follow-up item for whichever Work Package next touches
  `ProjectExplorerView` or does a general Avalonia API-currency pass.
- **`linux-launch-smoke` was not made a required check.** See §7/§8.
- **No screenshot was captured** — no `xwd`/`import`/`convert` available
  in this environment. See §6.
- **No real X11/Wayland desktop or macOS run was performed.** This
  spike's Linux evidence is `Xvfb`-only, exactly as `PHYSICAL_REVIEW.md`
  §1 and this Work Package's own brief scope it.
- **No other `Avalonia.*` package** (e.g. any DataGrid package) needed
  touching — `Avalonia.Headless` is not referenced directly by name in
  either csproj (pulled transitively via `Avalonia.Headless.XUnit`), and
  no `.axaml` files exist in the project (confirmed unchanged from
  `WP 10.0B`'s original disclosed choice).
- **`PROJECT_STATUS.md`, `WorkPackages.md`, any ADR, and Academy files**
  were not touched, per this Work Package's own commissioning brief.

## 11. Risks and observations for future Work Packages

- **The `SIGTERM`-doesn't-end-the-process behaviour (§6)** is worth its
  own look: something in this application's shutdown path (candidates:
  the `RestApiHostedService`'s own `StopAsync`, or the Avalonia
  dispatcher/X11 platform under `Xvfb`) does not complete promptly on a
  plain `SIGTERM`. Harmless for this spike's purpose and for
  `linux-launch-smoke` (both 124 and 137 are treated as "launched"), but
  worth a real fix if TempestOS is ever daemonised or run under a
  process manager on Linux that expects a clean `SIGTERM` exit.
  Suspected unrelated to the `TD-116` upgrade (it involves the ASP.NET
  Core generic host's shutdown handling, not `Avalonia.FreeDesktop`),
  but was not root-caused within this timebox.
- **Avalonia 11.3's headless layout is now partly dispatcher-deferred**
  (§5) — any future headless test that calls `Measure`/`Arrange`
  directly and reads geometry back immediately, without draining the
  dispatcher first, is at risk of the same zero-size-bounds symptom this
  spike found and fixed in one place.
- **The `DataObject`/`DoDragDrop` obsoletion (§4, §9)** is real,
  disclosed debt this upgrade introduced — not a regression in behaviour
  today, but a future Avalonia release could remove the old API outright
  rather than merely deprecating it.
