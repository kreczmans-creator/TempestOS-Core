# v0.16.0 — Consolidated Review Board Disposition

**Scope.** Every finding raised by the two review boards conducted on this
release, with its severity, evidence, disposition, remediation and
verification. This is the consolidated record `WP 16.9.0`'s Engineering
Readiness Review draws on; the ERR states verdicts, this states findings.

**Two boards, deliberately.** Board 1 ran nine perspectives against the
integrated tree. Board 2 ran six **fresh** perspectives against a pinned,
immutable checkout, mandated to assume board 1 had missed something and
that the remediation for board 1's findings might itself have introduced
defects. No board 2 reviewer had written the code it examined.

**Severity vocabulary.** RED — blocks the release. AMBER — must be
resolved before v1.0.0. YELLOW — worthwhile improvement or tracked debt.
GREEN — observation, no action.

---

## 1. RED findings — all four closed and verified

### R1. The attachment sweep could permanently delete a live file
*Board 1, security; independently reproduced by board 1, persistence.*

**Evidence.** `AttachContentAsync` wrote content then object state
(`ADR-0114` decision 4, deliberate). The sweep read states, then content
keys, and deleted any content nothing referenced. A sweep between those
two writes deleted the bytes; the state write then recorded an attachment
whose hash pointed at content that no longer existed. Reading states
*first* made the window wider, not narrower. The persistence reviewer
reproduced the same shape in the **Materials** sweep with a worse
consequence: a fully-registered material's index entry deleted, leaving
the document intact but unfindable, and its duplicate check then blind.

**Aggravating.** `TD-97` was already marked **Resolved** against this
code, and the release plan (§3) had specified "a write-intent marker
before multi-file writes" — the implementing stream substituted a simpler
comparison, and that substitution opened the race.

**Disposition.** Fix required, in scope.
**Remediation.** `WP 16.4B-R2` — write-intent marker plus read reordering
across all three sweeps. **The first attempt was rejected** for sampling
the marker *after* the state read, which narrowed the race rather than
closing it. Correct order is content keys → markers → states; the
*position* of the sample is what makes it airtight.
**Verification.** The corrected fix was proven by reverting to the broken
order and watching the new test fail, then restoring it.

### R2. A lost update let the sweep delete a live file anyway
*Board 2, persistence.*

**Evidence.** `PersistStateAsync` captured live state then issued an
unconditional whole-record overwrite, with nothing serialising the pair.
Two concurrent mutations could land their saves in the opposite order to
their captures; the later-landing, earlier-captured snapshot silently
dropped the other's change. The sweep then deleted the orphaned bytes,
behaving exactly as designed. **Reproduced against the real classes on
trial 323 of 500, no artificial delays.** The `WP 16.4B-R2` marker cannot
reach this — both writes complete and clear their markers correctly. Its
proof assumed a single writer per object, and that assumption is false.

**Disposition.** Fix required, in scope. The lost update predates
v0.16.0, but this release's sweep is what converts it from a dropped
reference into permanent deletion.
**Remediation.** `WP 16.4B-R3` — `AsyncKeyedLock` keyed by object Id,
owned by `EngineeringDomainContext`, held from before `CaptureState()`
through `SaveAsync`. Keyed by Id rather than per instance because
`ReviseAsync` demonstrably constructs a second live instance for one Id;
an instance lock would have closed nothing. An exhaustive re-entrancy
audit found no nested path. The same unprotected shape was found and
fixed in `EngineeringObjectFactory.CreateAsync`.
**Verification.** Deterministic test, verified by stashing the fix and
watching it fail immediately. `TD-135` Resolved. 3,204 tests.

### R3. Four tests guarding that code could not fail
*Board 2, testing — every finding proven by mutation.*

**Evidence.** The Materials and Requirements sweep race tests gated on a
collection *name* rather than call order, so reverting the production fix
moved the watched collection to the first call and the interleaving never
occurred — all nine tests passed against genuinely broken code. The
double-dispose test caught its bug in **0 of 20 runs** (0.45% per trial
over 2,000). The golden corpus's "every field is compared" docstring
omitted `Metadata`, so wiping it on every read passed all nine fixtures.

**Disposition.** Fix required, in scope. A test that cannot fail is worse
than none, because it buys false confidence in code that can destroy data.
**Remediation.** `WP 16.4A-R1` — a shared order-agnostic gate; the
double-dispose race looped 2,000× (arithmetic stated: p=0.0045 ⇒ N≥1021
for 99%); the corpus comparison extended to `Metadata`, `BomLine`,
`History` and `Attachments.ContentType`; gates bounded at 10s and
`--blame-hang-timeout` added to CI.
**Verification.** Every fix mutation-proven in both directions. Reverting
both sweeps failed all three race tests (24/24 restored); the looped
double-dispose test detected a reverted guard 10/10.

### R4. Governance documents claimed completeness they did not have
*Board 2, governance.*

**Evidence.** The DI and Platform Services registers both claimed
complete coverage while omitting `IAttachmentWriteIntentStore` — the
service that fixed R1 — left out by the very commit that added it to the
Interface Register. `WP 16.4A` was marked flatly Complete despite its own
5×CI acceptance never being met. `WP 16.2C` was marked Complete having
left six Work Packages without retrospectives, including `WP 16.4B`.
`PROJECT_STATUS.md`'s headline metrics were stale by material margins.

**Disposition.** Fix required, in scope.
**Remediation.** Both register rows added and totals re-derived from
source; both status rows corrected to state their shortfall; the six
retrospectives written (217 → 223); metrics re-derived. `TD-127` Resolved.
**Verification.** `governance-healthcheck.ps1` 14 passed, 2 warned,
0 failed; register totals re-derived by direct grep, not incremented.

## 3. One finding rejected, with reasoning

**`SettingsDocument` "ahead of target" discard** *(board 2, security —
graded YELLOW by its reporter).*

The reviewer proposed a symmetric "ahead" discard by analogy with
`EngineeringObjectStateStore`. **The analogy does not hold.** That store
has a fixed, platform-wide `CurrentSchemaVersion`, so "ahead" genuinely
means "written by a newer build". This seam derives its target from *the
calling consumer's own supplied chain*, which is not a build version at
all — a document past that target is not from the future, it merely sits
beyond what this caller claims to transform.

The change was written anyway, and it broke
`ADocumentAlreadyPastEveryRegisteredMigration_IsLeftAlone`, a pre-existing
test encoding the opposite intent. **Reverted**, the reasoning put in the
code so the next reader does not re-propose it, and the real residual risk
the reviewer correctly identified recorded as `TD-134` rather than
approximated with a target that means something else.

Recorded here because a review board that only ever agrees with its
reviewers is not a review board.

## 5. Board 3 — the final release review (2026-09-05, at `4e91ea8`)

Seven fresh reviewers, run against the release PR's own tree after gate 1
ratified `D-021`–`D-026`. None had written the code it examined. Their
mandate was the same as board 2's: assume the earlier boards missed
something.

They did.

### 5.1 RED — one, closed and mutation-proven

**`R5`. `ReviseAsync` was the one durable-write path `WP 16.4B-R3` never
routed through its own lock, and it lost data the same way.** Found by the
persistence reviewer, who built an executable reproduction against the
real classes rather than arguing from inspection.

`ReviseAsync` captured this object's state *outside* the write lock, handed
the snapshot to a newly constructed successor, and registered that
successor in place of its predecessor — two independently mutable
instances, one durable record. `WP 16.4B-R3` keyed the lock by `Id`
rather than by instance **because of this exact hazard**, and
`PersistStateAsync`'s own remarks named it. But ordering two writers is not
the same as preventing one from discarding the other: the successor's
snapshot was taken at revision time, so a predecessor write that lands
after it is invisible, and the successor's next mutation overwrites the
whole record.

The sequence, reproduced: attach on the predecessor lands durably; an
ordinary rename on the live successor follows; the attachment is gone from
disk. With real content attached, the predecessor's own persist has
already cleared the write-intent marker, so the reconciliation sweep then
sees content present, unmarked and unreferenced, and **deletes the file's
bytes as a genuine orphan.**

*Disposition:* fixed, `WP 16.4B-R4`. `ReviseAsync` performs its capture,
hand-off and registration inside the per-object write lock and retires the
predecessor there; a later durable write through a retired instance throws
`SupersededEngineeringObjectException`. The lock is the linearisation
point, so a predecessor write arriving *before* the revision is still
carried into the successor — which matters, because a fix that simply
stopped predecessors writing would have silently broken the
rename-then-revise sequence every `Revise*Command` in `Tempest.App`
performs, and two of the five new tests exist to catch exactly that
over-correction. `TD-136`.

*Verification:* mutation-proven in both directions. With the fix reverted,
**3 of 5 fail**, one reporting the on-disk attachment collection as `[]`
after the write was accepted without error. With it restored, **5 of 5
pass**.

*What this finding says about the process:* this is the second time a
board has found a data-loss defect inside the previous board's own
remediation, and the second time the remediation's own doc comment
correctly identified the hazard it then under-solved. That pattern is the
argument for running the board again rather than trusting the fix.

### 5.4 What board 3 confirmed sound

Recorded because a disposition listing only defects misrepresents the
tree. Independently re-derived, not taken from prior reports: `Tempest.Core`
has zero project references; `src/Plugins/` is empty, so `D-023` holds in
code; the REST enable key is evaluated before any `WebApplication` object

from scratch and is guarded by a test; `AsyncKeyedLock` has no lock-order
inversion, no re-entrancy and a sound double-dispose guard; the sweep's
content→markers→states read order is correct and its proof holds; all 16
new production files were individually judged for smuggled capability and
none is reachable from any command, route or UI; 123 ADRs match 123 rows;
26 decisions with no invented `D-027+`; 135 TD rows summing exactly to
their stated breakdown, with four "Resolved" rows spot-checked against
source; and **no live document anywhere claims v0.16.0 is approved,
certified, tagged or published.**

### 5.5 Not fixed, and why

`PersistenceStore` still has no `fsync` — process-crash-safe, not
power-loss-safe. The persistence reviewer confirmed the file is
**byte-for-byte unchanged by this release** (`git diff` empty), so it is
pre-existing rather than introduced, and changing the most load-bearing
write path in a hygiene release remains the wrong trade. `TD-129`,
`TD-130`, `TD-131`, `TD-132`, `TD-133`, `TD-134` all verified present in
code exactly as their register rows describe, and left as recorded debt.
