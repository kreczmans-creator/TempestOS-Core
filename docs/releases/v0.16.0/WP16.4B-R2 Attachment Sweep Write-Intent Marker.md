# WP 16.4B-R2 — Attachment Sweep Write-Intent Marker

**Type.** Implementation (Engineering Core) — data-loss remediation.
Production code, tests, and this report; no ADR, no register edit.
**Branch.** `feature/v0.16.0-sec-remediation`, cut from `feature/v0.16.0`
at `ac7daa6`.
**Closes.** A data-loss race in `AttachmentContentReconciliationService`
that shipped in `WP 16.4B` and was found by the v0.16.0 review board: a
sweep could permanently delete a live, in-flight attachment's bytes
while a user was uploading it. Widened, on a second reviewer's
independent reproduction, to the identical write-then-index race in
`MaterialCatalogReconciliationService` and `RequirementsReconciliationService`.
Also closes the `TD-62`-adjacent disclosure in `ApiRequestHandler`'s
`403` body (AMBER finding). Neither Technical Debt row this report
touches is marked Resolved here — that edit belongs to the integrator's
own register pass. `ADR-0114` decision 4 (content written before the
state that names it) is **unchanged**.
**Cites.** `docs/adr/ADR-0114-attachment-content-is-durable-bytes-in-the-same-store-addressed-by-attachment-id-and-verified-on-read.md`;
`docs/releases/v0.16.0/v0.16.0 Release Plan.md` §`WP 16.4B` ("a
write-intent marker before multi-file writes and a startup sweep that
reports orphans"); `docs/releases/v0.16.0/WP16.4B-3 Durability.md`
(`TD-67`/`TD-97`'s original sweep implementation, whose ordering this
report corrects); `docs/governance/Quality/Technical Debt Register.md`
(`TD-62`, `TD-97`).

## What changed

### 1. A durable write-intent marker for attachment content (the RED finding)

**New:** `src/Tempest.Core/EngineeringDomain/Contracts/IAttachmentWriteIntentStore.cs`,
`src/Tempest.Core/EngineeringDomain/Implementation/AttachmentWriteIntentStore.cs`.

A third store, sibling to `IAttachmentContentStore` and
`IEngineeringObjectStateStore`, following the exact same pattern: one
record per attachment, keyed by the attachment's own Id, in its own
`IPersistenceStore` collection (`EngineeringDomain.AttachmentWriteIntent`),
written through the platform's single persistence substrate with the
same atomic temp-file-then-rename discipline every other collection
gets for free from `PersistenceStore`. Three operations: `MarkAsync`,
`ClearAsync`, `ListMarkedAsync`.

**`EngineeringObjectBase.AttachContentAsync`** (`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs`)
now brackets its two existing writes with the marker, **without
reordering either of them**:

```
1. MarkAsync(attachmentId)         — new
2. contentStore.SaveAsync(...)     — unchanged, still first of the two real writes
3. PersistStateAsync(...)          — unchanged, still second
4. ClearAsync(attachmentId)        — new
```

**`AttachmentContentReconciliationService`** (`src/Tempest.Core/EngineeringDomain/Implementation/AttachmentContentReconciliationService.cs`)
takes a new optional `IAttachmentWriteIntentStore?` constructor
parameter and, before treating any content key as an orphan, checks it
against `ListMarkedAsync()`. A marked key is skipped outright —
regardless of what the state scan saw. Its own two reads are also
reversed: content keys first, object states second (see "Per-service
ordering analysis" below for why this alone was not enough).

**Wiring:** `EngineeringDomainContext` gained an optional
`AttachmentWriteIntentStore` property/constructor parameter (mirroring
`AttachmentContentStore`'s own optionality — every hand-assembled test
context that predates it keeps compiling unchanged). `TempestHost.cs`
registers `IAttachmentWriteIntentStore → AttachmentWriteIntentStore` as
a singleton alongside `IAttachmentContentStore`, so production always
composes both together.

**Why no failure mode of the marker can lose data:**

- The sweep's *only* use of a marker is to **skip** a content key. No
  code path reads a marker to decide *to* delete something — only ever
  not to. A marker that is wrongly present costs nothing but a delayed
  collection of bytes already tolerated as leaked (`TD-97`, pre-dating
  any sweep). A marker that is wrongly absent (never happens by
  construction here, but hypothetically) simply leaves the sweep exactly
  as exposed as it was in `WP 16.4B` — never worse.
- **Crash between steps 1 and 2** (marked, no content yet): the sweep
  never sees the content key at all (nothing was ever written), so the
  marker is moot; it is simply cleaned up by nothing, forever — inert.
- **Crash between steps 2 and 3** (the exact race the finding
  described): content exists, state does not yet reference it, marker
  is present. The sweep sees the content key, checks the marker, skips
  it. **This is the race closed.**
- **Crash between steps 3 and 4** (state landed, marker never cleared —
  exercised by `SweepAsync_AStaleMarker_LeavesContentUncollectedRatherThanErroring`):
  the attachment is fully live and referenced; the stale marker merely
  means this content is *also* never collected by the sweep, which is
  correct anyway since it is not an orphan. No error, no data loss —
  exactly `TD-97`'s pre-existing, disclosed tolerance for a leaked
  record, reached by one more path.
- **Success path**: the marker is cleared in step 4, so an attachment
  that later *does* become genuinely orphaned (e.g. its owning object is
  deleted) is collectable exactly as before
  (`SweepAsync_AfterAnOrdinaryAttach_TheMarkerIsClearedAndUnrelatedOrphansStillCollect`).

### 2. Read-order reversal in all three reconciliation sweeps (scope widened mid-task)

A second reviewer independently reproduced the identical class of race
in `MaterialCatalogReconciliationService` and
`RequirementsReconciliationService`: both scan the authoritative side
(documents) before the derived side (the `materialId` index; the
identifier index and the Collection/Group registries), which is exactly
backwards relative to how `MaterialCatalog.RegisterAsync`/
`RequirementsService.CreateAsync`/`CreateCollectionAsync`/
`CreateGroupAsync` write (document, then index/registry entry, always
in that order, within one uninterrupted async call). A sweep whose
document scan happens to run *before* a registration's document commits,
but whose index/registry scan happens to run *after* that same
registration's index/registry write commits, sees an index/registry
entry naming a document it does not know about — and deletes it. The
reviewer's own reproduction: a fully-registered `MaterialSpecification`
became unfindable by `FindAsync` after a concurrent sweep, with the
document intact on disk and the index entry destroyed.

**Fix, in all three services:** scan the derived side first, the
authoritative side second.

- `src/Tempest.Core/Materials/MaterialCatalogReconciliationService.cs` —
  index scan first, document scan second.
- `src/Tempest.Core/Requirements/RequirementsReconciliationService.cs` —
  the identifier index, the Collection registry, and the Group registry
  are all read before the one document scan
  (`PartitionDocumentsByKindAsync`) that feeds all three reconciliations.
  New helpers `ReadIndexEntriesAsync`/`ReadRegistryIdsAsync` pull the raw
  scans out of `ReconcileIdentifierIndexAsync`/`ReconcileRegistryAsync`
  so `RunAsync` can sequence every derived-side read ahead of the single
  authoritative-side one.
- `src/Tempest.Core/EngineeringDomain/Implementation/AttachmentContentReconciliationService.cs` —
  content keys first, object states second (already covered above).

#### Per-service ordering analysis — why the inversion is safe for each

**Materials and Requirements (the index/registry sweeps): the
inversion closes the race by construction, not merely narrows it.**
For both, the document write always strictly precedes its own
index/registry write, within one uninterrupted async call, and no
document is ever physically removed once created (`RequirementsService.DeleteAsync`
is a soft delete — it revises the document's own content, it never
touches the row or its Kind; `MaterialCatalog` has no delete path at
all). Therefore: if a sweep's derived-side read (index/registry, now
first) observes an entry, the document write that necessarily preceded
that entry's own write has already landed — strictly before the
derived-side read completed. Since the authoritative-side read (documents,
now second) runs *later* in wall-clock time than the derived-side read,
and the document set only ever grows, that document is *guaranteed* to
still be visible when the authoritative-side read runs. There is no
interleaving under which a live index/registry entry can any longer
look "stale" to this sweep. The two new race tests reproduce the
reviewer's own interleaving directly (`GatedListKeysPersistenceStore`
pauses the sweep's authoritative-side document scan while a registration
completes fully inside the pause) and assert the previously-destroyed
outcome (unfindable, unlisted) no longer occurs. A registration caught
only *partway* through this window (document visible, its own
index/registry write not yet landed because the sweep's derived-side
read simply ran first) now produces a false "missing index/registry
entry" finding instead — and the existing repair logic in both services
already re-reads the live value before ever writing (`existing is null`
guards in `MaterialCatalogReconciliationService`/
`RequirementsReconciliationService`), so it can never clobber the
in-flight registration's own write. Verified directly: my Materials race
test interleaves exactly this partial-window case and the resulting
report carries a `MissingIndexEntryCategory` finding with `Repaired:
false` (the fresh existing-check saw the value already there and
correctly declined to touch it) — a cosmetic mis-report, never data
loss.

**Attachments: the inversion narrows the window; it does not close it,
which is exactly why the marker exists.** Unlike the index/registry
pairs, an attachment's state write can land at *any* time after the
content write — there is no guaranteed "it must already have landed by
the time this scan started" relationship the way there is for
document-then-index, because `PersistStateAsync` is a second, unbounded
async operation, not a strictly-sequenced continuation of the same write
the way `RegisterAsync`'s two writes are (both still happen inside one
call, but nothing bounds how much *later* than the content write the
state write can complete relative to an external sweep's own two scans).
Reading content first narrows the window by giving the state write one
more moment to land before the sweep's own state read — but a state
write can always still land after that read, no matter how late it
runs. This is exactly the case the write-intent marker exists to close
outright, and is why this report leads with the marker rather than the
reorder for this one service.

### 3. Generic `403` body (the AMBER finding)

`src/Tempest.Core/Api/ApiRequestHandler.cs`, `AuthorizeAsync`: the `403`
response body no longer names the principal id or the required
permission key (`return new ApiResponse(403, "Forbidden.")`). Status
codes are unchanged (still `401`/`403`/`404` exactly as before).

**Why this closed the finding.** `IdentityService.GetPrincipal` never
rejects an unknown id — any non-empty `X-Identity-Id` header resolves to
a valid, zero-permission principal — so any unauthenticated caller could
previously read the exact required-permission key for any route straight
out of the `403` body, reconstructing the same route→permission map
`TD-62` closed a *different*, single-document disclosure of (the OpenAPI
route), just over two round-trips per route instead of one document.

**Where the detail went, verified:**
- **The log.** `AuthorizeAsync` now logs the full detail on denial —
  `_logger?.Information($"{method} {path} -> 403 (principal '{identityHeaderValue}' does not hold '{requiredPermission.Key}').")`
  — a strict *addition* over what existed before: the pre-existing code
  only logged the principal id via the shared `Log(...)` helper, never
  the permission key. An operator investigating a denied request now
  gets the complete picture from the log, which they did not before.
- **The audit record — checked, and deliberately left alone.** I
  verified directly that `AuthorizeAsync` never called
  `_auditRecorder.RecordAsync` on a denial (401 or 403) before this
  change, and does not now. This is not an oversight I found and left
  unfixed by accident — it is an existing, explicitly-tested contract:
  `tests/Tempest.Core.Tests/Api/ApiRequestHandlerTests.cs`'s
  `HandleAsync_UnauthorizedRequest_RecordsNoAuditEntry` asserts
  `Assert.Empty(auditRecorder.Recorded)` after a denied request, and
  passes both before and after this change. Recording every denied
  request in the Audit trail is therefore a deliberate, separately-owned
  design decision this finding's fix does not reopen — widening it would
  contradict an approved, tested contract for a reason outside this
  finding's own scope (likely: avoiding audit-log spam from routine
  permission checks or unauthenticated scans). **Reported as asked,
  rather than silently "fixed" past the existing contract.**
- **Status codes: unchanged**, as instructed.
- **The 404-vs-401 route oracle:** left untouched, as instructed — see
  Technical Debt Register rows below.

## What did not change, and why

- **`ADR-0114` decision 4 is unchanged.** Content is still written
  before the state that names it. The marker is additional, durable
  information a sweep can consult; it never alters *what* gets written
  *when*.
- **No permission check added to the sweeps (YELLOW finding, Finding
  3).** None of the three reconciliation services takes an
  `IIdentityService`/`IPermissionEvaluator`. Nothing wires any
  `SweepAsync` to a command or route today, so guessing at an
  authorization seam for a surface that does not exist yet would be a
  design decision, not a fix. Reported as a Technical Debt Register row
  below, per the brief.
- **The 404-vs-401 route oracle is unchanged.** A caller can still
  distinguish "route does not exist" (404) from "route exists, caller
  unauthenticated" (401), reconstructing route existence one probe at a
  time. Real, but explicitly out of this report's scope. Reported below.
- **No register, ADR, `PROJECT_STATUS.md`, or `WorkPackages.md` edit.**
  Per the governance rules, the integrator adds the rows this report
  names.
- **Existing orphan-collection tests are untouched in behaviour** — the
  pre-existing "plant an orphan, expect collection" tests in all three
  services still pass unmodified; the reordering and the marker check
  only ever add a *narrower* set of exclusions (marked-and-in-flight),
  never remove the ability to collect a genuine orphan.

## Tests

**Attachments** (`tests/Tempest.Core.Tests/EngineeringDomain/AttachmentContentReconciliationServiceTests.cs`):

- `SweepAsync_InterleavedBetweenContentWriteAndStateWrite_NeverCollectsTheLiveContent`
  — **the race itself.** A `GatedObjectStateStore` test double wraps the
  real `EngineeringObjectStateStore` and exposes `ArmNextSave()`
  (returns a `Task` that completes the instant the *next* `SaveAsync`
  call is reached) and `ReleaseSave()`. The test arms the gate
  immediately before calling `AttachContentAsync`, awaits the returned
  task (proving `AttachContentAsync` has reached its state write — by
  which point the content bytes and the marker are both already
  durable, but nothing yet references the attachment), runs a full
  `SweepAsync()` against the real, ungated stores entirely inside that
  window, then releases the gate and awaits the attachment. Purely
  `TaskCompletionSource`-driven — no `Task.Delay`, no timing assumption,
  fully deterministic.
- `SweepAsync_AStaleMarker_LeavesContentUncollectedRatherThanErroring` —
  simulates a crash between the state write landing and the marker
  clear (`ThrowAfterSave` on the same gate) and asserts the content
  survives a subsequent sweep with no error and the attachment is a
  genuinely live, referenced one.
- `SweepAsync_AfterAnOrdinaryAttach_TheMarkerIsClearedAndUnrelatedOrphansStillCollect` —
  the marker is gone after a normal `AttachContentAsync` completes, and
  an unrelated, genuine orphan planted alongside it is still collected.
- All eight pre-existing tests in this file (direct-delete half and the
  original sweep half) pass unmodified.

**Materials** (`tests/Tempest.Core.Tests/Materials/MaterialCatalogReconciliationServiceTests.cs`):

- `SweepAsync_InterleavedWithAnInFlightRegistration_NeverMakesTheMaterialUnfindable`
  — the reviewer's exact scenario. A `GatedListKeysPersistenceStore` test
  double pauses only the sweep's own `ListKeysAsync(EngineeringDocumentStore.DocumentsCollectionName)`
  call (the authoritative-side scan, now second). The test starts the
  sweep, awaits the gate being reached (proving the sweep's derived-side
  index scan already ran and saw nothing), runs `RegisterAsync` to full
  completion inside that pause, releases the gate, and asserts
  `catalog.FindAsync("AL-RACE-1")` still returns the just-registered
  material and no `StaleIndexEntryCategory` finding named its document.

**Requirements** (`tests/Tempest.Core.Tests/Requirements/RequirementsReconciliationServiceTests.cs`):

- `SweepAsync_InterleavedWithAnInFlightCreate_NeverMakesTheRequirementUnfindable`
  — the identical shape for `RequirementsService.CreateAsync`/the
  identifier index; asserts `FindByIdentifierAsync` still succeeds.
- `SweepAsync_InterleavedWithAnInFlightCollectionCreate_NeverMakesTheCollectionUnlisted`
  — the identical shape for `CreateCollectionAsync`/the Collection
  registry; asserts `ListCollectionsAsync` still lists it.

**Debugging note, for the record:** the first version of
`GatedObjectStateStore` had a genuine deadlock — `ReleaseSave()` read a
field that `SaveAsync` had already swapped to `null` via
`Interlocked.Exchange` before capturing it locally, so `ReleaseSave()`'s
`TrySetResult()` call landed on nothing and the awaited `Task` never
completed. Caught by the race test itself hanging (not by inspection),
diagnosed with `dotnet test --blame-hang-timeout` plus temporary trace
instrumentation, and fixed by leaving `_releaseSave` in the field for
`ReleaseSave()` to find, swapping out only `_reachedSave` (the
re-arming guard). All temporary instrumentation was removed before this
commit; none of it reached production code.
