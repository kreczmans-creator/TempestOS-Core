# WP 16.4B-R3 — Per-Object Write Serialisation

**Type.** Implementation (Engineering Core) — data-loss remediation.
Production code, tests, and this report; no ADR, no register edit.
**Branch.** `feature/v0.16.0-lost-update-fix`, cut from `feature/v0.16.0`
at its current head.
**Closes.** A lost update in `EngineeringObjectBase.PersistStateAsync`
that let `AttachmentContentReconciliationService.SweepAsync` permanently
delete a user's attachment while the in-memory object, and the caller who
received a successful `IAttachment`, still believed the file existed.
Found by an independent post-remediation review and reproduced against
the real classes (two concurrent `AttachContentAsync` calls on one
`Part`, no artificial delays, hit on trial 323 of 500). The underlying
lost update predates `v0.16.0` — every mutator on `EngineeringObjectBase`
has always captured then saved unserialised — but this release's
reconciliation sweep (`WP 16.4B`, `TD-97`) is what turns a silently
dropped in-memory-vs-disk disagreement into permanent, irreversible
deletion of the user's bytes. The `WP 16.4B-R2` write-intent marker does
**not** close this: both concurrent writers in the reproduction complete
correctly and clear their markers, because the marker only ever guards
the window while one write is in flight, not the ordering between two
separate writers' captures and saves. **Also closes** the
`StateMigrationRegistry.Register` phantom-chain-on-throw defect noted
alongside this Work Package.
**Cites.** `docs/releases/v0.16.0/WP16.4B-R2 Attachment Sweep
Write-Intent Marker.md` (the marker this report distinguishes itself
from); `docs/governance/Quality/Technical Debt Register.md` (`TD-85`,
`TD-97`); `src/Tempest.Core/Concurrency/AsyncKeyedLock.cs` (`TD-68`, the
lock this fix reuses); `tests/Tempest.Core.Tests/Concurrency/AsyncKeyedLockTests.cs`.

---

## What changed

### 1. The lost update — `EngineeringObjectBase.PersistStateAsync`

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs`

Before:

```csharp
protected Task PersistStateAsync(CancellationToken cancellationToken = default) =>
    _context.ObjectStateStore is { } store
        ? store.SaveAsync(CaptureState(), cancellationToken)
        : Task.CompletedTask;
```

After, the capture-then-save pair is wrapped in a per-object-Id lock,
acquired before `CaptureState()` and held through the `SaveAsync` call:

```csharp
protected async Task PersistStateAsync(CancellationToken cancellationToken = default)
{
    if (_context.ObjectStateStore is not { } store)
        return;

    using (await _context.AcquireObjectWriteLockAsync(Id, cancellationToken).ConfigureAwait(false))
    {
        await store.SaveAsync(CaptureState(), cancellationToken).ConfigureAwait(false);
    }
}
```

Every mutator on `EngineeringObjectBase` and its concrete descendants
(`AttachContentAsync`, `AttachAsync`, `TransitionAsync`, `RenameAsync`,
`MoveAsync`, `SetBomLineAsync`, `DeleteAsync`, `SetPriorityAsync`,
`AssignAsync`, `ChangeStatusAsync`/`ChangeWorkStateAsync`, `ScoreAsync`,
`AssignOwnerAsync`, `DecideAsync`, `SetRationaleAsync`, `SetDueDateAsync`
— the full list in the audit below) already funnelled through this one
method, so this single change closes the race for every one of them at
once, at its source, rather than adding a workaround per call site.

### 2. The design question — one instance per Id? No. Evidence, and the consequence.

**Finding: a second live instance for the same Id is not merely possible
in theory — it is a documented, deliberate feature of this codebase.**
`EngineeringObjectBase.ReviseAsync` constructs a new instance for the
*same* `Id` (the refreshed `IEngineeringDocument` it builds carries
`Document.Id` unchanged) and calls `_context.Repository.Register(revised)`,
which **replaces** the repository's entry for that Id. Nothing requires
every caller already holding a reference to the original instance to
notice the replacement — a caller that mutates the original after a
concurrent `ReviseAsync` is racing the revised successor for the
identical durable record, through two different `EngineeringObjectBase`
objects. `EngineeringObjectFactory<T>.CreateAsync` never produces a
second instance for an *existing* Id (each call mints a fresh `Guid` via
`_context.Store.CreateAsync`), and `EngineeringObjectRehydrationService`
explicitly refuses to construct a second instance for an Id already live
in the repository ("rehydration never overwrites a live object"). There
is no other caching or identity map. `ReviseAsync` is therefore the one
and only source of a second live instance per Id, but it is a real one.

**Consequence: an instance-level lock (e.g. a `SemaphoreSlim` field on
`EngineeringObjectBase`) would not have closed this.** It would only
serialise callers holding the *same* instance; the original and its
revised successor would still race each other freely. The lock has to be
**keyed by the object's `Id`**, not owned by any one instance. Every
instance for a given Id is guaranteed to share exactly one collaborator —
`EngineeringDomainContext` — because it is threaded through every
constructor and every `_selfFactory`/rehydrator closure. It is the
correct, and only, place to hold a shared keyed lock.

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringDomainContext.cs`
now owns a private `AsyncKeyedLock` (`src/Tempest.Core/Concurrency/AsyncKeyedLock.cs`
— already used by five other services; this is the sixth, so its own doc
comment lists the new consumer) and an internal
`AcquireObjectWriteLockAsync(Guid objectId, CancellationToken)` that keys
on `objectId.ToString("N")`.

### 3. The factory's own initial save — the same defect shape, found while auditing "any others"

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectFactory.cs`

`EngineeringObjectFactory<T>.CreateAsync` registered the freshly-created
instance in the repository, then captured and saved its initial state
**directly**, unprotected by any lock:

```csharp
_context.Repository.Register(instance);
if (_context.ObjectStateStore is { } stateStore)
    await stateStore.SaveAsync(instance.CaptureState(), cancellationToken).ConfigureAwait(false);
```

Registration happens *before* the initial save lands, so a concurrent
caller that finds the brand-new object through the repository (a
background sweep or listing enumerating `ListAllAsync`/`ListByKindAsync`,
for example — not the caller of `CreateAsync` itself, who does not have
the Id until it returns) could race this initial save exactly as two
mutators could race each other. This is the same capture-then-save shape
the task named explicitly ("and any others — find them all"), so it is
closed the same way: a new internal `EngineeringObjectBase.PersistInitialStateAsync`
forwards to the now-locked `PersistStateAsync` (exposed only because
`EngineeringObjectFactory<T>` is not part of the `EngineeringObjectBase`
hierarchy and cannot reach the `protected` method directly — the same
reason `CaptureState()` itself is `internal` rather than `protected`),
and the factory now calls it instead of capturing and saving inline.

### 4. The phantom migration chain — `StateMigrationRegistry.Register`

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectStateStore.cs`

`Register` built and wired a Kind's chain dictionary into `_byKind`
**before** running either collision check:

```csharp
var kindChain = _byKind.TryGetValue(kind, out var existingChain)
    ? existingChain
    : _byKind[kind] = new Dictionary<int, IStateMigration>();
// ...checks that can still throw...
```

For a genuinely new Kind, the only throw reachable here is
`ConflictingStateMigrationException` (a fresh, empty chain can never
itself hold a `DuplicateStateMigrationException`-triggering entry) — and
that throw left an empty chain behind in `_byKind` for a Kind whose
registration never actually completed, contradicting the type's own doc
comment, which promises a throwing registration "does not complete."
Fixed by deferring the `_byKind[kind] = kindChain` write until after both
checks pass:

```csharp
var kindChainAlreadyExists = _byKind.TryGetValue(kind, out var existingChain);
var kindChain = kindChainAlreadyExists ? existingChain! : new Dictionary<int, IStateMigration>();

if (kindChain.TryGetValue(fromVersion, out _))
    throw new DuplicateStateMigrationException(kind, fromVersion);
if (_common.TryGetValue(fromVersion, out _))
    throw new ConflictingStateMigrationException(kind, fromVersion);

kindChain[fromVersion] = migration;
if (!kindChainAlreadyExists)
    _byKind[kind] = kindChain;
```

A new internal `HasChainFor(string kind)` accessor (mirroring
`AsyncKeyedLock.TrackedKeyCount`'s own precedent — `internal`, reached
only by `Tempest.Core.Tests` via the project's existing
`InternalsVisibleTo`) makes the previously-unobservable `_byKind` key set
directly testable, since nothing in production ever reads it and the
doc comment itself says so.

## The complete re-entrancy audit

`AsyncKeyedLock` is not reentrant, so the lock had to be provably taken
at most once per object, per call, with nothing already holding it. Every
call path below was read in full for this Work Package:

- **Every method on `EngineeringObjectBase`** (`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs`):
  `CaptureState`, `RestoreState`, `PersistStateAsync` itself,
  `TransitionAsync`, `ReviseAsync`, `GetRevisionHistoryAsync`,
  `LinkAsync`, `GetRelationshipsAsync`, `GetEvidenceAsync`,
  `ValidateAsync`, `AttachAsync`, `GetAttachmentsAsync`,
  `AttachContentAsync`, `ReadAttachmentContentAsync`, `RenameAsync`,
  `MoveAsync` (and its private `GuardAgainstCircularParentAsync` helper),
  `DeleteAsync`, `SetBomLineAsync`. Result: each of the nine mutators
  (`TransitionAsync`, `AttachAsync`, `AttachContentAsync`, `RenameAsync`,
  `MoveAsync`, `DeleteAsync`, `SetBomLineAsync`, plus the two below)
  calls `PersistStateAsync` **exactly once**, as its last step, and never
  while any lock it took itself (`_lifecycleLock`, `_structuralLock`,
  or the plain `lock (_attachments)`) is still held — every one of those
  is a short, synchronous field-level lock released before
  `PersistStateAsync` is ever reached. `MoveAsync` calls `LinkAsync`
  before its own `PersistStateAsync` — `LinkAsync` never persists object
  state (it only writes to `_context.Store` and records into
  `RelationshipRepository`), so this is not a nested persist. `ReviseAsync`
  calls `CaptureState()` (field-locked, not the write lock) and
  `RestoreState` on a *different* instance, then registers it — it never
  calls `PersistStateAsync` at all (the values it carries are already
  durable on the original instance's own most recent save, so there is
  nothing new to persist here; confirmed, not modified — see "What did
  not change" below).
- **Every derived type with its own mutators**
  (`src/Tempest.Core/EngineeringDomain/Implementation/GovernanceRisk.cs`:
  `Issue.ChangeStatusAsync`/`SetPriorityAsync`/`AssignAsync`;
  `Risk.ChangeStatusAsync`/`ScoreAsync`/`AssignOwnerAsync`/`RealisedAsAsync`
  (the last delegates to `LinkAsync`, not a persist); `Decision.DecideAsync`/
  `SetRationaleAsync`/`AddressesAsync`/`SupersedesAsync` (the last two
  also delegate to `LinkAsync`); `src/Tempest.Core/EngineeringDomain/Implementation/ProcessApproval.cs`:
  `EngineeringTask.AssignAsync`/`ChangeWorkStateAsync`/`SetPriorityAsync`/
  `SetDueDateAsync`/`ContributeToAsync` (delegates to `LinkAsync`)).
  Every one of these calls `PersistStateAsync` exactly once, last, the
  same shape as the base class's own mutators. The remaining 22 concrete
  Kind types (`Calculations.cs`, `ChangeRelease.cs`,
  `DocumentationDesign.cs`, `PhysicalConfiguration.cs`,
  `ProgrammeHierarchy.cs`, `RequirementsVerification.cs`,
  `SupplyChain.cs`, `TestManufacturing.cs`) define no mutators of their
  own beyond `CaptureTypeState` overrides — grepped and read in full,
  confirmed.
- **`EngineeringObjectFactory<T>.CreateAsync`** — now calls
  `PersistInitialStateAsync` once, after registering the instance, never
  itself holding any lock beforehand (see item 3 above).
- **`EngineeringObjectRehydrationService`/`EngineeringObjectRehydrator<T>`** —
  read-and-register only; `RestoreState` is called directly (field locks
  only), never `PersistStateAsync`. No lock ever taken here.
- **Every composed caller in `Tempest.App`** that performs more than one
  mutation per logical operation — grepped for every call site of
  `RenameAsync`, `MoveAsync`, `SetBomLineAsync`, `DeleteAsync`,
  `TransitionAsync`, `AttachAsync`, `AttachContentAsync` across
  `src/Tempest.App`, then read the composing methods in full:
  `ProjectGovernanceService.EditAsync` (`RenameAsync` then `ReviseAsync`),
  `ProjectGovernanceService.CreateRiskAsync`/`CreateIssueAsync`/
  `CreateDecisionAsync` (`factory.CreateAsync` then `MoveAsync`),
  `ProjectTaskService.EditAsync` (`RenameAsync` then `ReviseAsync`),
  `ProjectTaskService.CreateAsync` (`factory.CreateAsync` then
  `MoveAsync`), `ProjectMilestoneService.EditAsync`/`CreateMilestoneAsync`/
  `CreateDeliverableAsync` (same two shapes). In every one of these,
  the two calls are **sequential `await`s** — the first mutator's whole
  call, including its own `PersistStateAsync` and lock release, completes
  before the second is even invoked. None of these nests a lock inside a
  lock; each acquires and releases the per-object lock twice, in series,
  never once while already holding it.
  `AttachDocumentCommandHandler.HandleAsync`
  (`src/Tempest.App/Workspace/Documents/AttachDocumentCommand.cs`) —
  the real product path the task names — calls exactly one mutator per
  invocation.

**No nested path was found**, so no restructuring toward "lock once at
the outermost point" or a non-locking private core was needed — the
existing shape, one call to `PersistStateAsync` at the end of each
mutator and never inside another lock, was already correct for a
non-reentrant lock; this Work Package only had to make sure it stayed
that way while adding the lock.

## What did not change, and why

- **`ADR-0113`/`ADR-0114`'s write ordering is untouched.** Content is
  still written before the state that names it (`ADR-0114` Decision 4);
  the sweep's own read ordering (content, marker, state — `WP 16.4B-R2`)
  is untouched. This fix serialises *within* one object's own
  capture-then-save pair; it does not reorder anything between objects
  or stores.
- **No optimistic concurrency, no version check, added to
  `EngineeringObjectStateStore`.** The task named this as the deliberately
  rejected alternative: a version check plus caller retry is a larger
  design change than this release should absorb, and the pessimistic
  per-object lock closes the same hole without it.
- **`EngineeringObjectBase.ReviseAsync` was read closely but not
  modified.** It never calls `PersistStateAsync`, and does not need to:
  the `EngineeringObjectState` fields it carries onto the revised
  instance (`RestoreState(CaptureState())`) are identical in content to
  what the original instance's own most recent successful
  `PersistStateAsync` already wrote to disk (same Id, same lifecycle,
  history, parent, deletion, BOM line, attachments — `ReviseAsync`
  changes only `Document`/`CurrentRevision`, which live in
  `IEngineeringDocumentStore`, not in `EngineeringObjectState`), so
  skipping a save here loses nothing. It **is** the source of the
  two-live-instances-per-Id fact this report's locking design rests on
  — noted, not touched, since restructuring it is outside this Work
  Package's scope.
- **The lock is held across the real `SaveAsync` call, including its
  disk I/O**, not merely across `CaptureState()`. Releasing it earlier
  would have narrowed the race window rather than closed it — exactly
  the kind of fix already rejected once this release. The trade-off is
  that two mutations on the *same* object can no longer execute their
  persist steps concurrently; two mutations on *different* objects are
  unaffected (the lock is keyed, per `AsyncKeyedLock`'s own established
  contract used by five other services already).
- **Nothing in `Tempest.App`, the Command Framework, or any discipline
  Kind type's own business logic was touched** beyond the two production
  files above (`EngineeringObjectBase.cs`, `EngineeringObjectFactory.cs`)
  plus the shared lock's new home (`EngineeringDomainContext.cs`) and the
  `AsyncKeyedLock.cs` doc-comment consumer list.

## Validation

- `dotnet build src/TempestOS.slnx -c Release -p:TreatWarningsAsErrors=true`
  — **0 warnings, 0 errors.**
- `dotnet test tests/Tempest.Core.Tests -c Release --blame-hang-timeout 300000`,
  run **twice**: **3,204 passed / 0 failed** both times, identical.
  Baseline was 3,199; delta **+5** — exactly the five new tests this
  report adds (two in the new `EngineeringObjectWriteSerializationTests.cs`,
  one in `AttachmentContentReconciliationServiceTests.cs`, two in
  `StateMigrationChainTests.cs`) — no other test count moved.
- `dotnet test tests/Tempest.Desktop.Tests -c Release --blame-hang-timeout 300000`,
  run **twice**: **474 passed / 0 failed** both times, identical to
  baseline — the Desktop composes through this code and is unaffected.
- **Directional verification that the reproduction is real** (not part
  of the "run twice" requirement, but load-bearing): with the fix
  temporarily reverted (`git stash`), both new tests in
  `EngineeringObjectWriteSerializationTests.cs` fail immediately and
  deterministically — no hang — with exactly the predicted loss
  (`TwoConcurrentAttachAsyncCalls_BothSurviveOnDisk` loses the second
  attachment; `ConcurrentRenameAndAttach_BothSurviveOnDisk` loses the
  rename entirely, confirming the *whole* later-landing snapshot wins,
  not just the attachment). With the fix restored, both pass, along with
  the rest of the suite. Run five additional times back-to-back with the
  fix in place to confirm no flake: 3/3 tests passed identically every
  time.
- **How each new test forces its interleaving deterministically**
  (`TaskCompletionSource` gating, no `Task.Delay`, no retry loop):
  - `EngineeringObjectWriteSerializationTests` (new file) uses a
    purpose-built, fully in-memory, single-slot gated
    `IEngineeringObjectStateStore` test double — deliberately *not* the
    existing file-backed `GatedObjectStateStore`, because forcing the
    bug's exact interleaving requires the second call's whole round trip
    (capture and land) to complete, deterministically, within the single
    statement that starts it, before the test ever releases the first —
    which is only guaranteed with **no other asynchrony underneath**
    (no real disk I/O, no second `AsyncKeyedLock` inside
    `PersistenceStore` to race for landing order). Combined with
    `IHasAttachments.AttachAsync` (metadata-only — no content-store or
    write-intent-store I/O), every step up to the gate is synchronous C#
    on both sides of the fix. The gate pauses the first call immediately
    after it captures state (holding the lock once the fix is applied);
    the second call is started but deliberately never awaited until
    after the first is released, so the test cannot hang under either
    version — pre-fix the second call's full round trip already
    completed by the time it is started (synchronous chain); post-fix it
    blocks on the lock and completes only once unblocked, which the test
    waits for at the end, not the middle.
  - The new `SweepAsync_AfterTwoConcurrentAttaches_CollectsNeitherAttachmentsContent`
    test in `AttachmentContentReconciliationServiceTests.cs` reuses the
    existing file-backed `GatedObjectStateStore`/`BuildGated` fixture and
    the real `AttachContentAsync`, for end-to-end fidelity to the
    reviewer's own repro (real content bytes, real marker, real sweep).
    It does not need to pin the exact landing order the lower-level test
    does: under the fix, whichever of the two calls the lock admits to
    its critical section *last* always captures the union of both
    attachments, because each call's own in-memory field write happens,
    in program order, before it ever requests the lock — so the
    assertion holds regardless of scheduling once serialised, which is
    what makes this test deterministic against the shipped (fixed) code
    without needing to force a specific winner.
  - The two new tests in `StateMigrationChainTests.cs` are ordinary,
    single-threaded assertions against `StateMigrationRegistry`'s new
    `HasChainFor` accessor — no concurrency, no gating needed.
