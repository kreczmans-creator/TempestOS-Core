Both are genuine, current defects in tracked governance-register
content — not artifacts of how the new checks are written, not
speculative, and each confirmed two ways below. Per this Work Package's
own file ownership, neither register was edited; each was instead

reported here as hard findings, per instruction.

### Finding 1 — Namespace Register: a BOM blind spot hides a real namespace

`src/Tempest.Core/Models/ProjectModel.cs` opens with a UTF-8 byte-order
mark (`EF BB BF`) before its `namespace Tempest.Core.Models;`
declaration — confirmed directly (`od -An -tx1` on the file's first 3
bytes). The register's own documented "Source of Truth" command,
`grep -rhoP "^namespace \K[\w.]+" src/...`, anchors on line start; the
BOM sits between the true line start and the literal text `namespace`,
so `grep`'s own anchored pattern silently never matches this one file.
`WP 16.2A`'s full re-derivation, built on that same grep, therefore
filed `ProjectModel.cs` under the register's `*(no namespace declared —
global namespace)*` row (stated as 4 files) instead of recognising it as
a first, genuine member of a namespace with no register row of its own.

This check's own source derivation uses PowerShell's `Get-Content -Raw`,
which strips a leading BOM automatically — the difference is not a
different rule, only a different tool's own default encoding handling,
and it is `Get-Content -Raw` that sees what the file actually declares.

**Exact fix the integrator needs (not made here):** add one row —
`Tempest.Core.Models | Tempest.Core | 1 | ProjectModel | ...` — to the
Namespace Register's Entries table, correct the `*(no namespace
declared — global namespace)*` row's own file list and count (4 → 3,
`ProjectModel.cs` removed), and correct the "Total: 46 namespaces" /
"713 files" summary line accordingly (47 namespaces once
`Tempest.Core.Models` is added; the global-namespace row's own file
count text needs matching correction, not counted toward the 47).

### Finding 2 — Technical Debt Register: a concurrent-merge artefact, not an arithmetic error

The register's own current summary line reads **"122 tracked — 39
Resolved (`TD-57` newly among them), 6 Closed, 72 Open, 4 Partially
resolved, 1 Deferred."** Direct re-derivation from the 122 `TD-nnn` rows
actually present (parsing each row's own Status cell's leading word,
bold or not) gives **40 Resolved, 71 Open** — every other figure
(Closed, Partially resolved, Deferred, and the 122 total itself)
matches exactly.

This is not `WP 16.2A`'s own arithmetic error at the time it wrote that
line — it is a real consequence of `v0.16.0`'s own branch topology,
confirmed directly against this repository's git history:

```
$ git merge-base --is-ancestor 1fc6954 40e267d ; echo $?
# (not an ancestor)
```

`40e267d` is `WP 16.2A`'s own commit — the one that wrote the current
summary line. `1fc6954` is the merge of `WP 16.5B` (which resolved
`TD-116`, changing its Status cell from Open to Resolved) into
`feature/v0.16.0`. The two are on independent, parallel branches; `WP
16.2A`'s own branch was cut, and its summary line authored, *before*
`WP 16.5B`'s merge existed for it to see. When both branches were later
merged into the same integration branch, git's own three-way merge of
`Technical Debt Register.md` correctly combined both sides' row edits
(`TD-116`'s Status cell now reads Resolved) — but a merge cannot also
re-run the prose arithmetic `WP 16.2A` had already written on its own
side, so the summary line still states the pre-merge count. The same
pattern most plausibly accounts for the identical `TD-121`/`TD-122`
"added retroactively" rows landing via a concurrent `WP 16.2B` backfill
branch.

**Exact fix the integrator needs (not made here):** re-run the
same re-derivation this check performs (`| TD-nnn |` rows, each row's
own Status cell's leading word) against the Technical Debt Register at
`HEAD`, and update the summary line's `Resolved`/`Open` figures (39 → 40,
72 → 71) to match. No row content changes; only the summary line's own
two numbers.
