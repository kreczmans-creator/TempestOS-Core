## 9. Amendment — the Engineering Calculation surface (2026-09-07)

The build above could be pulled and run, and the calculation could not be
reached from any screen. Two rows recorded that: `TD-159` (the Object
Editor offered five calculation templates and executing any of them threw)
and `TD-160` (the merged engineering capability had no Desktop surface at
all). This amendment closes the first and half of the second.

### 9.1 `TD-159` — Resolved, mutation-proven

The five definitions **already lived in `Tempest.Core.Calculations`**;
`TD-75` phase 1 moved them there on 2026-08-30 after the Product Gap
Reconciliation audit found they were "product content filed in the wrong
assembly". It moved the *declarations* and left the *registrations* in
`EngineeringCalculationsWorkspaceSampleModule` — an assembly neither
`Tempest.App` nor `Tempest.Desktop` references, and **both test projects
do**. That is why every test passed against a composition no user ever ran.

`SampleSeparationTests`, the standing guard `TD-75` left behind, asserted
only where each definition is *declared*. It never asserted where they are
*registered*, which is why the missing half stayed missing.

`ProductCalculationCatalogue.RegisterAll` now runs from `TempestHost`
during start-up, **before the first module initialises** — not from
`CalculationsWorkspaceRegistration`, the discipline's own composition root
and the natural home, because that runs after `manager.StartAsync()`
returns and a module may legitimately execute a calculation while
initialising. The sample module no longer registers product content.

Mutation-proven: replacing the `TempestHost` call with a comment fails
`ARealRunningHost_HoldsEveryProductCalculation_WithNoSampleModuleRegisteringThem`
— which starts a host with **no modules at all**, so only the host can have
registered anything — and fails **only** that test. Restoring it returns
29/29. A real Xvfb launch now logs `Product calculation catalogue
registered: 5 calculations.`

### 9.2 The surface

| Layer | What it holds |
|---|---|
| `Tempest.App/Engineering/BracketCalculationWorkbench.cs` + `BracketCalculationContracts.cs` | The application-side answer: composes populate / verify-and-release / check / recover, and formats every quantity with its unit before the Desktop sees it. Owns no rule of its own. |
| `Tempest.Desktop/Views/EngineeringCalculationView.cs` | Collects text, raises intent, renders what comes back. Parses no quantity, applies no rule, knows no formula. |
| `Tempest.Desktop/Composition/EngineeringCalculationCoordinator.cs` | An `ADR-0103` collaborator, the same shape as the two project coordinators. |
| `ShellArea.EngineeringCalculation` | **Appended**, never inserted — `ShellLocation` is persisted by ordinal. `Implemented`, so it carries no `TrackedBy` and must render a real surface, which `ProductGapReconciliationAuditTests` enforces at run time. |

**No approval is fabricated.** `ReferenceReviewService` is the single gate
to `Released` — three call sites in all of `src/`, all inside itself — and
was already composed in `WorkspaceHost`. The engineer performs the act:
they type the source they consulted and the release rationale, and the
platform stamps whoever is signed in, on its own clock, refusing outright
when nobody is. Seeding stays an **explicit user action**, honouring the
host's own recorded position that "deciding when a library gets populated
is a governance choice and not a side effect of booting."

### 9.3 What the behavioural tests prove, and what they cannot

Four tests in `EngineeringCalculationJourneyTests` drive the real
`MainWindow` — real rail navigation, real `Button` clicks, real `TextBox`
entry located by the name a screen reader would announce, real `ComboBox`
selection, and text asserted on screen at **non-zero laid-out bounds**
after a real `Measure`/`Arrange`:

- navigate, populate, **be refused on Draft data**, verify and release,
  calculate, read 200 MPa / 260 MPa / margin 0.30 / 24.3 g, inspect
  traceability, relaunch into a second host over one persistence root,
  recover the persisted result;
- superseding the reference afterwards leaves the historical result
  untouched, and the surface says the reference has moved on;
- invalid input rejected visibly, all four problems at once;
- a release with nobody signed in refused, record stays `Draft`.

**They cannot prove**, and are not claimed to: that a button is reachable
by a real pointer at a real coordinate (every click is a synthetic routed
event, the only mechanism this suite has, which bypasses hit-testing and
z-order); that real keystrokes work (`TextBox.Text = …` is assignment);
anything about pixels; or anything about **Windows** — this is headless
Linux.

### 9.4 Two defects the tests found, fixed in the product

1. **Re-entering the surface left the traceability stale** — it would have
   gone on calling a reference current after somebody superseded it. The
   stored calculation is now re-read from its record on every entry; the
   result cannot change, being immutable and pinned, so only the
   "reference now" fields refresh.
2. The first attempt **revised** a Released record; the lifecycle refused
   it correctly ("Register the corrected record and supersede this one
   instead"), so the test supersedes, as an engineer would have to.

Also corrected: an assertion that the library starts empty was asserting
the **harness**, not the product — this test process references
`Tempest.Samples`, whose `MaterialsSampleModule` registers its own alloys,
and the shipped Desktop does not.
