## What changed

### TD-67, item 1 — `EngineeringDocumentStore.CreateAsync` ordering

`src/Tempest.Core/EngineeringData/EngineeringDocumentStore.cs`

`CreateAsync` now writes revision 1 before the document record — the
exact inversion of its own original ordering, and exactly the ordering
`ReviseAsync` already used (write the new revision, then the document
record that names it). The document's own Id is minted locally
(`Guid.NewGuid()`) before either write, so nothing about revision 1's own
identity ever depended on the document record existing first; inverting
was straightforwardly safe. A crash between the two writes now leaves an
orphaned revision 1 with no document record — invisible to `FindAsync`/
`GetRevisionHistoryAsync` (both key off the document record and report
"not found"), never the "internally inconsistent" `EngineeringDataException`
the old ordering's own crash window produced.

### TD-67, item 2 — orphan detection and a sweep

Two new services, one per index the register names, mirroring each
other's shape and each namespace's own existing conventions
(constructor injection, `ILogger?` optional, `CancellationToken` on every
async method):

- `src/Tempest.Core/Requirements/IRequirementsReconciliationService.cs`,
  `RequirementsReconciliationService.cs`, `RequirementsReconciliationReport.cs`
  — covers `RequirementsService.CreateAsync`/`CreateCollectionAsync`/
  `CreateGroupAsync`'s own document-then-index/registry ordering, for all
  three: the identifier index, the collection registry, and the group
  registry. Forward orphans (a document with nothing indexing it) are
  repaired by re-writing the missing entry from the orphan's own recorded
  identity (read back from its stored content for the identifier index;
  the document's own Id for the two self-keyed registries) — never by
  guessing. A genuine identifier collision (the index already names a
  *different* document) is reported, never silently overwritten. Reverse,
  stale entries (an index/registry entry naming a document that no
  longer exists or is no longer the expected Kind — cheap to check once
  every document is already enumerated) are reported and, on sweep,
  removed.
- `src/Tempest.Core/Materials/IMaterialCatalogReconciliationService.cs`,
  `MaterialCatalogReconciliationService.cs`, `MaterialCatalogReconciliationReport.cs`
  — the identical shape for `MaterialCatalog.RegisterAsync`'s own
  `materialId` index, the second concrete example the register names.

Both are **explicit, operator-invoked operations** — `DetectAsync`
(read-only) and `SweepAsync` (detects and repairs). Neither runs at
startup or on any schedule; nothing in this Work Package wires either
into `TempestHost` or any other automatic path. This platform does not
repair a user's own data behind their back, and the register's own
complaint ("no reconcile/repair path") is a request for a path to exist,
not a request that it run unattended.

Both services enumerate the document store's own backing collection
directly through `IPersistenceStore.ListKeysAsync` — the identical,
already-established direct-`IPersistenceStore` dependency
`RequirementsService`/`MaterialCatalog` already carry for their own
indexes (`ADR-0059`, `ADR-0055` Decision 3) — because
`IEngineeringDocumentStore` has no "list documents of a Kind" capability,
a disclosed, deliberate limitation this Work Package does not reopen.

### TD-67, item 3 — `MoveToGroupAsync`/`MoveGroupAsync` append without removing

**Not changed — investigated and found not to be a live-state defect
against the current code.** See "What did not change, and why" below;
this is the one item where the register's own text and the code's own,
already-reviewed design disagree, and I did not resolve that
disagreement unilaterally.

### TD-67, item 4 — `MoveGroupAsync` Kind and ancestry-cycle checks

`src/Tempest.Core/Requirements/RequirementsService.cs`,
`IRequirementsService.cs`, and a new
`src/Tempest.Core/Requirements/RequirementGroupCycleException.cs`.

`MoveGroupAsync` now:

- Rejects a `newParentGroupId` that exists but is not itself a
  `RequirementGroup` document, via the same "wrong Kind reads as not
  found" idiom this service's own `FindGroupAsync`/`DeleteCollectionAsync`
  already use — `EngineeringDocumentNotFoundException`, not a new
  exception, since none was needed for this half.
- Rejects a move that would make the group its own ancestor, via a new
  `GuardAgainstGroupCycleAsync` helper that mirrors
  `EngineeringDomain.EngineeringObjectBase.GuardAgainstCircularParentAsync`'s
  own identical walk-the-chain algorithm, over
  `RequirementGroupDto.ParentGroupId` instead of `IHasParent.ParentId`.
  Throws the new `RequirementGroupCycleException : RequirementsException`
  — see below for why a new type, not a reused one.

### TD-67, item 5 — MaterialCatalog/RequirementsService ordering, and VerificationService's evidence graph

**Judged, not uniformly fixed — see "What did not change, and why."** The
document-then-index ordering is mitigated by item 2's sweep, not
inverted (inverting is not possible without a document-store contract
change — see below). `VerificationService.RecordAsync`'s partial
evidence graph is **not** mitigated by any sweep built in this Work
Package; it remains open, disclosed here rather than silently left.

### TD-97 — attachment content release and sweep

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs`
— `DeleteAsync` now releases every attachment's content
(`IAttachmentContentStore.DeleteAsync`) once `IsDeleted` is durably
persisted. Metadata (the `IAttachment` records themselves) is never
erased — deletion stays soft, matching this platform's own append-only,
nothing-silently-destroyed ethos for every other Domain mutation. The
release happens **after**, not before, the deletion write: a crash in
between leaves the object durably deleted with its content merely
unreleased yet — the pre-existing, disclosed `TD-97` state, closed the
rest of the way by the sweep below, never by reordering ahead of the
write it depends on. A domain with no `IAttachmentContentStore`
configured (the pre-`TD-31` default in every hand-assembled test context)
behaves exactly as before: `DeleteAsync` still succeeds, nothing is
released because there is nothing to release.

`src/Tempest.Core/EngineeringDomain/Contracts/AttachmentContentReconciliation.cs`
(`IAttachmentContentReconciliationService`, `OrphanedAttachmentContent`,
`AttachmentContentReconciliationReport`) and
`src/Tempest.Core/EngineeringDomain/Implementation/AttachmentContentReconciliationService.cs`
— the sweep the register names: every content key
`IAttachmentContentStore` holds is compared against every attachment Id
any currently-persisted `EngineeringObjectState` references (live or
soft-deleted alike, since a soft-deleted object's own attachment
*metadata* survives even after its content is released). A key nothing
references is reported, and, on sweep, deleted. Content listing goes
through `IPersistenceStore.ListKeysAsync` rather than a new member on
`IAttachmentContentStore`/`IBinaryPersistenceStore`: enumerating a
collection's own keys is encoding-agnostic (the same directory, the same
file-per-key store, differing only at the point a value is actually read
or written), so no new capability was needed on either interface.

**`ADR-0114` decision 4 (content written before metadata) is unchanged.**
This Work Package implements the sweep the ADR's own Consequences
section names as `TD-97`'s closure; it does not reverse the ordering the
ADR deliberately chose. No conflict was found with the ADR; none is
reported.

This sweep and TD-67's two sweeps are **three separate services**, not
one merged service — see "Design decision: one service or three?" below.

### Exception updated

`RequirementGroupCycleException` (new, `Tempest.Core.Requirements`) —
see item 4, and the dedicated note below on why a new type was added
rather than an existing one reused.

## Design decision: one service or three?

The three reconciliation services (`RequirementsReconciliationService`,
`MaterialCatalogReconciliationService`, `AttachmentContentReconciliationService`)
are **kept separate**, not merged into one service with several
operations, even though the prompt for this stream explicitly invited
merging TD-67's and TD-97's sweeps if that were a good outcome. Reason:
`RequirementDto`/`RequirementGroupDto`/`RequirementCollectionDto` and
`MaterialSpecificationDto` are `internal` types private to their own
namespaces, and every existing service in this pattern
(`RequirementsService`, `MaterialCatalog`, `RequirementValidationService`)
lives in the same namespace as the data it reconciles, depending only
*downward* on `EngineeringData`/`Persistence` — never the reverse. A
single merged service spanning `Requirements`, `Materials`, and
`EngineeringDomain` would need to depend *upward* into two sibling
disciplines' own internals, which is the one direction this codebase's
own layering never runs (confirmed by reading `RequirementsService`'s,
`MaterialCatalog`'s, and `AttachmentContentStore`'s own remarks, which
disclose exactly this kind of boundary repeatedly). Three small,
same-namespace services, each following its own namespace's existing
idiom exactly, keeps that layering intact. `RequirementsReconciliationService`
itself does merge three checks (Requirement/Collection/Group) into one
service, because all three already share `RequirementsService`'s own
namespace and index style.

## Why a new exception (`RequirementGroupCycleException`), not a reused one

The closest existing analogue, `Tempest.Core.EngineeringDomain.CircularParentAssignmentException`,
belongs to a different, architecturally separate implementation
(`EngineeringObjectBase`/`IHasParent`/`IEngineeringObjectRepository`) that
`RequirementsService` does not otherwise depend on — `RequirementsService`
is built directly on `IEngineeringDocumentStore` and has never imported
`Tempest.Core.EngineeringDomain` for anything but
`IValidationResult`/`ValidationDiagnostic` (in `RequirementValidationService`,
a different class). Reusing it here would be a new, one-off cross-layer
dependency introduced for a single exception type. This namespace's own
established idiom is one dedicated `RequirementsException` subtype per
invalid condition — `RequirementNotFoundException`,
`DuplicateRequirementIdentifierException`,
`InvalidRequirementStatusTransitionException`,
`RequirementGroupHasChildrenException` — so `RequirementGroupCycleException`
follows that pattern instead.

## What did not change, and why

Every one of `TD-67`'s five named defects, accounted for:

1. **`EngineeringDocumentStore.CreateAsync` ordering — closed.** Inverted
   exactly as instructed; see "What changed."
2. **No reconcile/repair path — closed** for the two concrete examples
   the register names (`MaterialCatalog.RegisterAsync`,
   `RequirementsService.Create*`, all three document/index pairs). See
   "What changed" and the note on item 5 below for what the sweep does
   and does not reach.
3. **`MoveToGroupAsync`/`MoveGroupAsync` append without removing — NOT
   changed. Investigated at length; the register's own characterization
   ("a 'move' that leaves the prior reference in place is a plain bug:
   the object ends up in two groups") does not hold against the current
   code, and I did not make a change that would reintroduce a bug this
   platform already fixed once.**

   `RequirementGroupDto.ParentGroupId` and `RequirementDto.GroupId` are
   each that record's own **live, current** value — not resolved from
   the relationship graph. This is a disclosed `WP 9.1A` correction,
   in `RequirementGroupDto`'s and `RequirementDto`'s own remarks: before
   it, group membership *was* resolved by `.FirstOrDefault()` over
   `GetReferencesAsync`'s returned list, and that resolution became
   genuinely ambiguous the moment `MoveGroupAsync` could record a second
   `groupedUnder` link for the same group — "the identical class of risk
   `TD-27` already found and fixed for a different repository." The fix
   was to stop resolving membership from the relationship graph at all;
   the `groupedUnder` link stays purely a permanent, historical Digital
   Thread record afterward, exactly mirroring
   `EngineeringDomain.EngineeringObjectBase.MoveAsync`'s own identical,
   already-shipped design ("the old 'groupedUnder' link \[...\] is never
   removed, so a full move history survives even though `ParentId`
   itself only ever reflects the latest move," `WP 9.0A`). Every live
   read this codebase has (`FindGroupAsync`, `ToRequirement`,
   `RequirementsPropertyFacetProvider`'s "Group" facet) reads the DTO
   field, never the relationship count — confirmed directly, including
   an already-passing test (`RequirementsLifecycleExtensionsTests.MoveGroupAsync_FindGroupAsync_ReflectsTheMove`)
   whose own comment states the invariant explicitly: "two groupedUnder
   links now exist for the same source, and `FindGroupAsync` must still
   resolve the correct, current parent." A requirement or group moved
   five times is not "in five groups" today; it is in exactly the group
   its own DTO field names, with four historical edges beside it.

   Removing the prior link would (a) reverse this already-reviewed,
   already-tested design and the platform-wide `groupedUnder` idiom it
   mirrors, and (b) require adding a destructive removal capability to
   `IEngineeringDocumentStore`'s reference store, which currently has
   none — every reference this store has ever recorded is permanent by
   design (`GetReferencesAsync`'s own remarks: "references are never
   deleted by this store"). I did not add one. **This is a genuine
   conflict between the register's own text and the code's own,
   previously-reviewed state, not a matter of my preference** — flagging
   it here rather than resolving it silently, exactly as this stream's
   own controlling instructions require for a comparable ADR conflict.
   I recommend the register row be corrected to drop this clause (or a
   Technical Review confirm the `WP 9.1A` design should be reopened) —
   that edit is the integrator's, not mine.

4. **`MoveGroupAsync` checks neither parent Kind nor ancestry cycles —
   closed.** Both guards added; see "What changed." (`CreateGroupAsync`
   has the identical unchecked-Kind gap on its own `parentGroupId`
   parameter — the register does not name it, and I left it alone
   rather than expanding scope; flagged under "Out of scope," below.)
5. **Document-then-index ordering (`MaterialCatalog`/`RequirementsService`)
   and `VerificationService.RecordAsync`'s partial evidence graph — mixed.**

   **The ordering cannot be cheaply inverted**, unlike item 1:
   `EngineeringDocumentStore.CreateAsync` could invert its two writes
   only because it mints the document's own Id itself, before either
   write. `MaterialCatalog.RegisterAsync`/`RequirementsService.Create*`/
   `VerificationService.RecordAsync` all call
   `IEngineeringDocumentStore.CreateAsync` to get a document Id back —
   they have no Id to index *before* that call returns, and
   `IEngineeringDocumentStore.CreateAsync` has no overload accepting a
   caller-supplied Id. Inverting here would mean changing that
   interface's own contract, a materially larger change this stream did
   not make. **The sweep built in item 2 is the mitigation for
   `MaterialCatalog`/`RequirementsService`, exactly as this stream's own
   controlling instruction anticipated** — it does not close the crash
   window, it closes the "no reconcile/repair path" complaint about it.

   **`VerificationService.RecordAsync`'s partial evidence graph is
   NOT mitigated by anything in this Work Package.** A crash after
   creating the `VerificationRecord` document but before the
   `verifiedBy` back-link (or any of the `references`/`basedOnCalculation`
   forward links) leaves the identical shape of orphan `RequirementsReconciliationService`
   closes for Requirements — but `VerificationService` was judged, on
   time and scope grounds, not to warrant a fourth reconciliation
   service in this stream. This is real, disclosed, unfixed debt: no
   sweep in this codebase today finds an un-linked `VerificationRecord`
   document. Recommended as direct follow-up, since the pattern (enumerate
   documents of a Kind via the same `IPersistenceStore.ListKeysAsync`
   idiom the three built services already use, check the subject's own
   `verifiedBy` back-reference) is now proven three times over and would
   be a small addition.

## Invocation — how an operator runs a sweep

None of the three reconciliation services is wired into `TempestHost`,
any command, or any scheduled path by this Work Package — see
"Registrations the integrator may add," below, for what exists to wire
if the integrator chooses to. Until wired, each is invoked exactly like
any other constructor-injected service: construct it with its declared
dependencies (all three already-registered platform services —
`IEngineeringDocumentStore`/`IPersistenceStore` for the two `TD-67`
services, `IPersistenceStore`/`IEngineeringObjectStateStore`/
`IAttachmentContentStore` for the `TD-97` one) and call `DetectAsync`
(read-only) or `SweepAsync` (repairs/collects) from whatever explicit,
operator-initiated surface the integrator chooses — a diagnostics
command, an admin CLI verb, a test. This is deliberate: a repair facility
this platform runs on a user's data must be something a person decided
to run, not something that ran while they were not looking.

## Whether an ADR is needed

**No new ADR proposed.** Nothing here is a new architectural decision:
the `CreateAsync` reorder mirrors an existing, already-decided pattern
(`ReviseAsync`'s own ordering); the three reconciliation services are a
new *operation*, not a new storage mechanism or a new authority, over
data these existing, already-approved designs (`ADR-0053`, `ADR-0055`,
`ADR-0058`, `ADR-0059`) already own; and the `TD-97` content release
implements `ADR-0114`'s own stated closure without touching any of its
five decisions. If the Product Owner or Technical Review disagrees about
item 3 (the `MoveToGroupAsync`/`MoveGroupAsync` conflict above) and
wants the `WP 9.1A` design formally reopened, that would be the one
candidate for a new ADR — but that is a decision for Technical Review,
not something I am proposing here.
