# WP 16.3B — Durable State Schema Versioning — Implementation Report

**Type.** Implementation. Realises `ADR-0120` (Decisions 1–6) exactly, per
`docs/architecture/State Schema Versioning Architecture.md`.
**Branch.** `feature/v0.16.0-wp16.3b-schema-versioning`, cut from
`origin/feature/v0.16.0` at `8b4c394` (the commit that lands `WP 16.3A` —
`ADR-0120` and the architecture document).
**Closes.** `TD-87` (Technical Debt Register). Cites `D-021` (Proposed,
`WP 16.0A`).

## 1. What changed, per file

### `src/Tempest.Core/EngineeringDomain/`

- **`Implementation/EngineeringObjectState.cs`** — `SchemaVersion` (an
  `int`) added as the record's first positional component, exactly as
  the architecture document's "after `WP 16.3B`" shape shows. Every other
  component is unchanged.
- **`Implementation/EngineeringObjectStateStore.cs`**:
  - `public const int CurrentSchemaVersion = 1`.
  - `private static readonly JsonSerializerOptions StateJsonOptions`
    carrying `JsonStringEnumConverter`, used by both `SaveAsync` and
    `Deserialise` (`ADR-0120` Decision 4).
  - `Deserialise` now: parses (unchanged `JsonException` → log, `null`);
    normalises `SchemaVersion <= 0` to `1` (Decision 1); rejects a record
    whose `SchemaVersion > CurrentSchemaVersion` as unbridgeable (a
    record from a newer build — logged, skipped, per Decision 5's
    "newer build" acceptance case); then repeatedly applies
    `_migrations?.Find(state.Kind, state.SchemaVersion)` — common chain
    first, then that Kind's own (Decision 2) — forcing the result's
    `SchemaVersion` to `migration.FromVersion + 1` regardless of what the
    migration itself returns, inside a `try/catch` that treats a
    throwing migration identically to a stuck one (Decision 5).
  - New optional constructor parameter `IStateMigrationRegistry? migrations
    = null` (default preserves every existing hand-assembled store's
    behaviour unchanged).
  - New concrete `StateMigrationRegistry : IStateMigrationRegistry`,
    added to this same file (mirroring how `EngineeringObjectRehydrator.cs`
    already holds both `EngineeringObjectRehydrator<T>` and its own
    concrete registry) — a common (`Kind: null`) dictionary and one
    dictionary per Kind, both keyed by `FromVersion`.
- **`Implementation/EngineeringObjectBase.cs`** — `CaptureState()` now
  stamps `EngineeringObjectStateStore.CurrentSchemaVersion` as the
  record's first argument.
- **`Contracts/StateMigration.cs`** (new sibling file, the architecture
  document's own "`WP 16.3B`'s own choice") — `IStateMigration`,
  `IStateMigrationRegistry`.

### `src/Tempest.Core/Runtime/TempestHost.cs`

- Registers `IStateMigrationRegistry → StateMigrationRegistry` as a
  singleton, immediately before `IEngineeringObjectStateStore`, mirroring
  exactly how `IEngineeringObjectRehydratorRegistry` is composed — empty
  until a Kind's own declaring class registers a migration onto it.

### `src/Tempest.Core/Settings/`

- **`ISettingsMigration.cs`** (new) — `ISettingsMigration<TDocument>`
  (`FromVersion`, `Migrate`), the per-`TDocument` mirror of
  `IStateMigration`.
- **`SettingsDocument.cs`** — new optional constructor parameter
  `IReadOnlyList<ISettingsMigration<TDocument>>? migrations = null`.
  `LoadAsync` now: deserialises exactly as before; **only** when a chain

  and walk the chain the same way `EngineeringObjectStateStore` does.
  With no `migrations` argument — every one of the six real object-shaped

## 2. Deviations from the governing documents, with reasons

**1. Migration ordering — followed `ADR-0120`'s Decision 2 prose, not
the architecture document's inline interface comment.** `ADR-0120`
states plainly: "repeatedly finds and applies the migration whose
`FromVersion` matches the record's current version (**common chain
first, then that Kind's own chain**)." The architecture document's own
`IStateMigrationRegistry.Find` snippet carries the comment "// **Kind-specific
first, then common**" — the opposite order. `StateMigrationRegistry.Find`
implements the ADR's stated Decision (common wins a `FromVersion` both
chains claim); `StateMigrationChainTests.WhenBothACommonAndAKindSpecificMigrationTargetTheSameVersion_TheCommonOneRunsFirst`
asserts this directly. Flagging rather than silently picking one: the
two governing documents disagree, and the ADR's own Decision text is the
authority I followed.

**2. The "stuck record" gate compares against `CurrentSchemaVersion`
before, not after, the migration loop — a necessary interpretive choice,
not a text conflict.** The read-path pseudocode has no explicit
post-loop version check; taken completely literally, a record with
`SchemaVersion 99` and no migration registered for `99` would just exit
the `while` loop immediately and be returned *as-is*, at `99` — not
"skipped", contradicting the explicit test-list requirement that such a
record is "treated identically" to a throwing migration (both `skipped,
not thrown`). I resolved this by gating **before** the loop
(`SchemaVersion > CurrentSchemaVersion` → immediately stuck, logged,
`null`) rather than after. This also makes `StateMigrationChainTests`'
multi-step `1 → 3` chain provable at all: `CurrentSchemaVersion` is a
fixed `const 1` this release (per the architecture document's own "What
this does not attempt" — no version bump ships in `WP 16.3B`), so a
post-loop `state.SchemaVersion == CurrentSchemaVersion` gate would reject
that test's own correctly-migrated `3`-versioned result. A pre-loop gate
that only catches "ahead of `CurrentSchemaVersion`" leaves the
chain-testing mechanism free to run past `CurrentSchemaVersion` for a
test-only Kind, while still catching every "record from the future"
case a real Kind can ever produce.

**3. `EngineeringRehydrationResult` was *not* extended with a new
"stuck" field, even though the architecture document's test-list entry
for `RehydrationSurvivesAStuckRecordTests` says the result "accounts for
the stuck one without `IsComplete` silently reading `true`".** Two
things pointed the same way here. First, the file boundary: neither
`EngineeringObjectRehydrationService.cs` (where `EngineeringRehydrationResult`
lives) nor `Contracts/IEngineeringObjectStateStore.cs` appears anywhere
in the architecture document's own "Files `WP 16.3B` touches" section —
the section this task's own governing instructions name as the file
boundary. Second, and more directly: `ADR-0120` Decision 5's own
Consequences say exactly where this distinction belongs — "actively
distinguished... **in the log line a caller reads**" — never mentioning
a result field. I implemented the log line (Id, Kind, stuck version, all
present, asserted by
`AStuckRecordEncounteredDuringRehydration_IsLoggedNamingItsIdKindAndStuckVersion`)
and proved every other object in the same batch still comes back
(`ARehydrationBatchContainingAStuckRecord_StillReturnsEveryOtherObject`),
which is everything the ADR's own Decision 5 actually promises.
`EngineeringRehydrationResult.IsComplete` genuinely does still read
`true` for a batch containing only a store-level-stuck record (the
identical, pre-existing gap `ACorruptedStateRecord_IsSkipped_AndEveryOtherObjectStillComesBack`
already exercises for malformed JSON, unchanged by this WP) — disclosed
here rather than silently left for someone to discover.

**4. `SettingsDocument<TDocument>`'s `SchemaVersion` detection is
reflection-based, not an interface constraint.** The architecture
document states `SettingsDocument<TDocument>` gains "no change... beyond
an optional constructor parameter" and its own read-path pseudocode
reads "if `TDocument` **declares** `SchemaVersion`" — a runtime,
duck-typed condition, not a compile-time one. A `where TDocument :
ISomething` constraint would have forced every one of the six real
consumers to change their DTO's declared type the moment
`SettingsDocument<T>` itself changed, which is exactly the "no change...
beyond an optional constructor parameter" promise being broken. Reflection
(one `PropertyInfo`, resolved once per closed generic type and cached in
a `static readonly` field, so the cost is paid once per `TDocument`, not
once per load) is the design that keeps every existing call site
untouched.

**5. Discipline `RegisterStateMigrations` methods were not added
anywhere.** The architecture document's file list names this as a
per-registry addition "populated only for a Kind that actually has one"
— and no Kind has one yet (`CurrentSchemaVersion` stays `1`; `WP 16.3B`
"ships the mechanism to move past it," per the architecture document's
own "What this does not attempt," "not itself a version bump"). The
concrete discipline registries the file list names
(`MechanicalObjectFactoryRegistry`, `DocumentObjectFactoryRegistry`, …)
all live in `src/Tempest.App/`, which this task's own governing
instructions explicitly forbid modifying. Adding a permanently-empty
`RegisterStateMigrations() { }` to five files in a directory I am
instructed not to touch, for a Kind vocabulary that has no migration to
register, would be pure ceremony with no behaviour behind it — the
"minimal form the doc allows" this task's own instructions invited me to
prefer when the alternative is empty methods everywhere. Nothing is lost:
the composed, empty `IStateMigrationRegistry` singleton
(`TempestHost.cs`) is exactly the "legal, zero-cost default" `ADR-0120`'s
own Consequences describe, and the very next Work Package that needs a
real migration adds its `RegisterStateMigrations` method(s) at that
point, with something real to put in them.

**6. One test file outside the stated boundary was touched:
`tests/Tempest.Core.Tests/Samples/EngineeringDomainSampleModuleIntegrationTests.cs`
gained one line.** This file hand-assembles a DI container that must
track every constructor-required collaborator
`EngineeringObjectStateStore` takes, by its own stated design (the
adjacent, pre-existing `IBinaryPersistenceStore` registration carries a
comment saying exactly this: "the container resolves every constructor
parameter whether or not it has a default"). Leaving this file's own registrations unchanged did not fail the build —
the new parameter is optional — but it left six existing tests in this
file throwing `ServiceNotRegisteredException` at run time, a real
regression `dotnet test` on the full Core suite caught immediately. One
line, in a file the
architecture document could not have named because it addresses a
DI-container detail specific to *this* test file's own composition
choice, not a design decision `WP 16.3B` makes.

**No other deviations.** The `EngineeringObjectState` record gained
`SchemaVersion` as its **first positional component**, exactly as the
architecture document's own "after `WP 16.3B`" code block shows (a
settable `[JsonPropertyOrder(-1)]` property was considered per this
task's own instructions, but the positional form's churn was four call
sites total — `EngineeringObjectBase.CaptureState()` plus three
directly-constructing tests — so the property form's extra indirection
bought nothing).

before the record was rewritten in the old format. This is the
architecture document's own "a v0 (unversioned) record loads identically"
acceptance, proven end-to-end through a real host rather than only

already proves as a committed, standing regression check). The
throwaway test itself was not committed — it exists only as the
one-time proof this report records; `GoldenCorpusTests` is the
repeatable version of the same claim, permanently in the suite.

## 5. Proposed `TD-87` closing text

`WP 16.2A` owns the Technical Debt Register's own `TD-87` row this wave;
the following is offered as the proposed **Resolution** column text, not
applied here:

> **Resolved** (`ADR-0120`, `WP 16.3B`) — `EngineeringObjectState` now
> carries `SchemaVersion` (first component; absent/`0` normalises to `1`
> explicitly, never left to a serialiser default). Every enum reachable
> from the record (`LifecycleState` included) now serialises as its
> member name (`JsonStringEnumConverter`), closing the exact risk this
> row named — a future `LifecycleState` reordering can no longer
> silently reinterpret a persisted status — with no migration required
> for that change specifically, since the converter reads both the old
> numeric and new named form. `IStateMigration`/`IStateMigrationRegistry`
> give `EngineeringObjectStateStore`'s read path an ordered,
> per-Kind-plus-common migration chain, applied once, only on read
> (never on write — an object in memory has exactly one shape, the
> current one); a record a migration cannot bridge is logged (Id, Kind,
> stuck version) and skipped, extending — not duplicating —
> `Deserialise`'s existing `JsonException` discipline (`TD-60`).
> `SettingsDocument<TDocument>` gained the identical optional chain for
> a document that is a JSON object (`ADR-0120` Decision 6); the three
> list-shaped `SettingsDocument<T>` consumers remain explicitly out of
> scope, per that Decision's own stated reasoning. A seven-file golden
> corpus of genuine pre-`ADR-0120` records (numeric enums, no
> `SchemaVersion`) is committed and loaded through the real read path on
> every test run, standing regression coverage for every future schema
> bump. 32 new tests; the full Core suite (3,120) and full Desktop suite
> (412) pass unchanged.
