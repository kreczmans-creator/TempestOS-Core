## 0. Technical Review history

Three commits on this branch; the first two were each reviewed and
returned with required changes before merge.

### Round 1 (commit `2e3ec8e`) — two required changes, addressed in commit `2225d2e`

**1. The "stuck record" gate did not check that a record actually
reached the store's target version after the migration loop ran** — a
record at `SchemaVersion 1`, read by a future build whose
`CurrentSchemaVersion` is `2` with no `1 → 2` migration registered,
would have passed through unmigrated and been silently misinterpreted:
exactly `ADR-0120` Decision 5's "no migration path to the store's
current version" case. Fixed by adding `int? targetSchemaVersion = null`
to `EngineeringObjectStateStore`'s constructor (resolved to
`CurrentSchemaVersion` when `null`, exposed as the read-only
`TargetSchemaVersion` property); the "ahead" gate now compares against
`TargetSchemaVersion`, the migration loop stops the moment
`state.SchemaVersion == TargetSchemaVersion`, and — the actual fix — a
new check immediately after the loop, `if (state.SchemaVersion !=
TargetSchemaVersion)`, logs the stuck `Warning` (`Id`, `Kind`, stuck
version, target version) and returns `null` whenever the loop stopped
short. `StateMigrationChainTests` now constructs its store with an
explicit `targetSchemaVersion` (`2` for a single-step case, `3` for the
multi-step chain); `GoldenCorpusTests`/`SchemaVersionDefaultingTests`/
`EnumSerialisesAsStringTests`/production composition all keep the
default. One new test,
`BrokenMigrationIsSkippedNotFatalTests.ARecordWithNoMigrationPathToItsTarget_IsSkipped_AndEveryOtherObjectStillComesBack`,
proves the new gate directly: a `v1` record with a target of `2` and no
migration registered is skipped with the `Warning`, and `ListAsync`
still returns the other record. The architecture document's own
contradicting inline comment ("Kind-specific first, then common") is
now corrected to match `ADR-0120`'s actual Decision 2 prose ("common
first, then that Kind's own"). See §2, Deviations 2 and 7 for the full
detail, including one further, unrequested but necessary consequence
this change forced (Deviation 7 — the DI-container registration needed
to keep `TempestHost.cs` and the Samples integration test compiling and
resolving).

**2. The restart proof is now a committed, permanent test**, not only a
manual validation this report recorded. `WorkspaceManager` is
`Tempest.App`-layer, but `Tempest.Core.Tests` already references
`Tempest.App` and already builds real
`TempestHostBuilder`/`WorkspaceManager` hosts directly (see
`Workspace/CommandDescriptorBindingTests.cs`, `Workspace/SampleSeparationTests.cs`)
— it did not need to move to `Tempest.Desktop.Tests`. It now lives at
`tests/Tempest.Core.Tests/EngineeringDomain/SchemaVersioning/RestartProofTests.cs`,
beside the other schema-versioning tests, using the isolation convention
those existing real-host tests already establish (an isolated
`TempDirectory` persistence root, an explicit module list rather than
`EngineeringWorkspaceComposer.Build`'s own reflective discovery).

### Round 2 (commit `2225d2e`) — one required change, addressed in this branch's third commit

**Round 1's own fix for requirement 1 introduced a new problem, correctly
caught:** the `services.AddInstance(typeof(int?), (object)(int?)EngineeringObjectStateStore.CurrentSchemaVersion);`
registration added to `TempestHost.cs` and the Samples integration test
registered a primitive nullable as a container-wide service to satisfy
one constructor's parameter — a hack that would silently collide with
any other, unrelated `int?` constructor parameter anywhere in the
platform, and that papered over the container's actual, disclosed gap
(no default-parameter-value support — `TD-69`'s second defect class,
`WP 16.4B`'s to fix properly) rather than working within it. Fixed by
using the container's own stated construction rule instead of fighting
it: `TempestServiceProvider.Construct` calls
`implementationType.GetConstructors()` — public instance constructors
only — and requires exactly one.
`EngineeringObjectStateStore` now has exactly one public constructor
again, `(IPersistenceStore, IStateMigrationRegistry? = null, ILogger? =
null)` — unchanged in shape from before `targetSchemaVersion` existed —
which chains to a second, `internal` constructor,
`(IPersistenceStore, IStateMigrationRegistry?, ILogger?, int
targetSchemaVersion)`, invisible to the container and visible only to
`Tempest.Core.Tests` via the pre-existing `InternalsVisibleTo("Tempest.Core.Tests")`
declaration in `src/Tempest.Core/AssemblyInfo.cs` (verified present
before relying on it). Both `AddInstance(typeof(int?), ...)`
registrations, and their comments, are removed; `TempestHost.cs` needs
no change at all to keep constructing the store with its own default
target, since the public constructor's shape is exactly what it already
satisfied. `TargetSchemaVersion` remains a public, read-only property.
`StateMigrationChainTests.cs` and `BrokenMigrationIsSkippedNotFatalTests.cs`
now call the internal, four-parameter constructor positionally wherever
they need an explicit target. See §2, Deviation 7 (fully rewritten to
describe this resolution).

## 2. Deviations from the governing documents, with reasons

**1. Migration ordering — followed `ADR-0120`'s Decision 2 prose, not
the architecture document's inline interface comment; the architecture
document is now corrected to agree (Technical Review requirement).**
`ADR-0120` states plainly: "repeatedly finds and applies the migration
whose `FromVersion` matches the record's current version (**common chain
first, then that Kind's own chain**)." The architecture document's own
`IStateMigrationRegistry.Find` snippet originally carried the comment
"// **Kind-specific first, then common**" — the opposite order.
`StateMigrationRegistry.Find` implements the ADR's stated Decision
(common wins a `FromVersion` both chains claim);
`StateMigrationChainTests.WhenBothACommonAndAKindSpecificMigrationTargetTheSameVersion_TheCommonOneRunsFirst`
asserts this directly. The two governing documents disagreed in the
first commit (`2e3ec8e`); the Technical Review directed the architecture
document's own inline comment be corrected to describe what was actually
implemented, which the ADR's own Decision text already governed — done
in the second commit (`docs/architecture/State Schema Versioning
Architecture.md`, one line: "Kind-specific first, then common" → "common
first, then that Kind's own").

**2. The "stuck record" gate now checks `TargetSchemaVersion` both
before and after the migration loop — corrected per Technical Review.**
The first commit (`2e3ec8e`) gated only "ahead of `CurrentSchemaVersion`"
*before* the loop, and let the loop's own natural exit (no migration
found) stand in for "stuck" — which is wrong for the specific case the
review named: a record at `SchemaVersion 1`, read by a build whose
`CurrentSchemaVersion` has moved to `2` with no `1 → 2` migration
registered, would pass the "ahead" check (`1` is not `> 2`), the loop
would find nothing and exit immediately, and the record would be
returned *unmigrated*, at `1` — silently misinterpreted as current,
exactly `ADR-0120` Decision 5's "no migration path to the store's
current version" case, un-caught. Fixed exactly as directed: an optional
`int? targetSchemaVersion = null` constructor parameter (defaulting to
`CurrentSchemaVersion`, exposed as the read-only `TargetSchemaVersion`
property); the "ahead" gate compares against `TargetSchemaVersion`; the
migration loop's own condition is now `while (state.SchemaVersion !=
TargetSchemaVersion)`, so it stops the instant the record reaches
target; and a new check immediately after the loop,
`if (state.SchemaVersion != TargetSchemaVersion)`, catches every case
the loop stopped short of target for any reason other than a migration
throwing (which its own `catch` already handles) — logging the
`Warning` (Id, Kind, stuck version, target version) and returning `null`.
`targetSchemaVersion` exists specifically so a test can exercise a
migration chain that runs past this build's fixed `CurrentSchemaVersion
= 1` (per the architecture document's own "What this does not attempt"
— `WP 16.3B` ships the mechanism, not a version bump) without needing to
bump that constant itself: `StateMigrationChainTests` now constructs its
stores with an explicit `targetSchemaVersion` (`2`, or `3` for the
multi-step chain), and every production/default-target test
(`GoldenCorpusTests`, `SchemaVersionDefaultingTests`,
`EnumSerialisesAsStringTests`, `TempestHost.cs`'s own composition) keeps
the implicit default unchanged.

**3. `EngineeringRehydrationResult` was *not* extended with a new
"stuck" field, even though the architecture document's test-list entry
for `RehydrationSurvivesAStuckRecordTests` says the result "accounts for
the stuck one without `IsComplete` silently reading `true`".** Two
things pointed the same way here. First, the file boundary: neither
`EngineeringObjectRehydrationService.cs` (where `EngineeringRehydrationResult`
lives) nor `Contracts/IEngineeringObjectStateStore.cs` appears anywhere
in the architecture document's own "Files `WP 16.3B` touches" section —
the section this task's own governing instructions name as the file
boundary. Second, and more directly: `ADR-0120` Decision 5's own
Consequences say exactly where this distinction belongs — "actively
distinguished... **in the log line a caller reads**" — never mentioning
a result field. I implemented the log line (Id, Kind, stuck version, all
present, asserted by
`AStuckRecordEncounteredDuringRehydration_IsLoggedNamingItsIdKindAndStuckVersion`)
and proved every other object in the same batch still comes back
(`ARehydrationBatchContainingAStuckRecord_StillReturnsEveryOtherObject`),
which is everything the ADR's own Decision 5 actually promises.
`EngineeringRehydrationResult.IsComplete` genuinely does still read
`true` for a batch containing only a store-level-stuck record (the
identical, pre-existing gap `ACorruptedStateRecord_IsSkipped_AndEveryOtherObjectStillComesBack`
already exercises for malformed JSON, unchanged by this WP) — disclosed
here rather than silently left for someone to discover.

**4. `SettingsDocument<TDocument>`'s `SchemaVersion` detection is
reflection-based, not an interface constraint.** The architecture
document states `SettingsDocument<TDocument>` gains "no change... beyond
an optional constructor parameter" and its own read-path pseudocode
reads "if `TDocument` **declares** `SchemaVersion`" — a runtime,
duck-typed condition, not a compile-time one. A `where TDocument :
ISomething` constraint would have forced every one of the six real
consumers to change their DTO's declared type the moment
`SettingsDocument<T>` itself changed, which is exactly the "no change...
beyond an optional constructor parameter" promise being broken. Reflection
(one `PropertyInfo`, resolved once per closed generic type and cached in
a `static readonly` field, so the cost is paid once per `TDocument`, not
once per load) is the design that keeps every existing call site
untouched.

**5. Discipline `RegisterStateMigrations` methods were not added
anywhere.** The architecture document's file list names this as a
per-registry addition "populated only for a Kind that actually has one"
— and no Kind has one yet (`CurrentSchemaVersion` stays `1`; `WP 16.3B`
"ships the mechanism to move past it," per the architecture document's
own "What this does not attempt," "not itself a version bump"). The
concrete discipline registries the file list names
(`MechanicalObjectFactoryRegistry`, `DocumentObjectFactoryRegistry`, …)
all live in `src/Tempest.App/`, which this task's own governing
instructions explicitly forbid modifying. Adding a permanently-empty
`RegisterStateMigrations() { }` to five files in a directory I am
instructed not to touch, for a Kind vocabulary that has no migration to
register, would be pure ceremony with no behaviour behind it — the
"minimal form the doc allows" this task's own instructions invited me to
prefer when the alternative is empty methods everywhere. Nothing is lost:
the composed, empty `IStateMigrationRegistry` singleton
(`TempestHost.cs`) is exactly the "legal, zero-cost default" `ADR-0120`'s
own Consequences describe, and the very next Work Package that needs a
real migration adds its `RegisterStateMigrations` method(s) at that
point, with something real to put in them.

**6. One test file outside the stated boundary was touched:
`tests/Tempest.Core.Tests/Samples/EngineeringDomainSampleModuleIntegrationTests.cs`
gained one line.** This file hand-assembles a DI container that must
track every constructor-required collaborator
`EngineeringObjectStateStore` takes, by its own stated design (the
adjacent, pre-existing `IBinaryPersistenceStore` registration carries a
comment saying exactly this: "the container resolves every constructor
parameter whether or not it has a default"). Leaving this file's own registrations unchanged did not fail the build —
the new parameter is optional — but it left six existing tests in this
file throwing `ServiceNotRegisteredException` at run time, a real
regression `dotnet test` on the full Core suite caught immediately. One
line, in a file the
architecture document could not have named because it addresses a
DI-container detail specific to *this* test file's own composition
choice, not a design decision `WP 16.3B` makes.

**7. `EngineeringObjectStateStore.TargetSchemaVersion` is reached
through an `internal` test-only constructor, not a raw `int?`/`int`
parameter on the container-facing public one — resolved per the second
Technical Review, after the first attempt (a global
`services.AddInstance(typeof(int?), ...)` registration in `TempestHost.cs`
and the Samples integration test) was correctly rejected as a hack.**
This platform's own DI container (`TempestServiceProvider.Construct`)
has no default-parameter-value support at all: every constructor
parameter is resolved through the same registry regardless of its C#
default, which is why `ILogger? logger = null` and `IStateMigrationRegistry?
migrations = null` already had to be backed by real registrations in
`TempestHost.cs`. Registering `Nullable<Int32>` itself as a container-wide
service to satisfy one constructor's fourth parameter was a real hazard,
correctly named: any *other* type that ever declared its own unrelated
`int?` constructor parameter would silently receive
`EngineeringObjectStateStore.CurrentSchemaVersion` too, and the
registration papered over the container's actual, disclosed gap
(`TD-69`'s second defect class, `WP 16.4B`'s to fix) rather than working
within it. Fixed by using the container's own stated construction rule
against the problem instead: `TempestServiceProvider.Construct` calls
`implementationType.GetConstructors()` — `Type.GetConstructors()` with
no arguments returns *public instance* constructors only — and requires
exactly one. `EngineeringObjectStateStore` now has exactly one public
constructor, `(IPersistenceStore persistenceStore, IStateMigrationRegistry?
migrations = null, ILogger? logger = null)`, unchanged in shape from
before `targetSchemaVersion` existed and fully satisfied by
`TempestHost.cs`'s existing, unmodified registrations — no `AddInstance(typeof(int?),
...)` needed anywhere any more. It chains to a second, `internal`
constructor, `(IPersistenceStore, IStateMigrationRegistry?, ILogger?, int
targetSchemaVersion)`, invisible to the container (which only ever calls
`GetConstructors()`, never sees it, and so never has cause to demand a
second public one and throw `AmbiguousConstructorException`) and visible
only to `Tempest.Core.Tests` via the `InternalsVisibleTo("Tempest.Core.Tests")`
declaration already present in `src/Tempest.Core/AssemblyInfo.cs`
(verified, not assumed, before relying on it). `TargetSchemaVersion`
remains a public, read-only property either way — the public constructor
sets it to `CurrentSchemaVersion`; the internal one accepts any value a
test needs. Every call site that previously passed `targetSchemaVersion:`
as a named argument on the (now-gone) four-parameter public constructor
now calls the internal one positionally
(`StateMigrationChainTests.cs`, `BrokenMigrationIsSkippedNotFatalTests.cs`).
The container's own lack of default-parameter-value support is not fixed
here, and should not be: it is `TD-69`'s second defect class, foundational
shared DI infrastructure outside this Work Package's scope, and is
