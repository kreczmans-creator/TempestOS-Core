# WP 16.4B-R1 — Migration Collision Guard and Platform Service Registration

**Type.** Architecture remediation. One production type's behaviour
changed (`StateMigrationRegistry.Register`), two new exception types
added, one test rewritten plus four added; three governance documents
updated (`docs/governance/Engineering/Platform Services Register.md`,
`docs/architecture/Platform Service Map.md`, one row of
`docs/governance/Quality/Technical Debt Register.md`), plus the
`Exception Register.md` row this new exception type requires. No ADR.
**Branch.** `feature/v0.16.0-arch-remediation`, cut from
`feature/v0.16.0` at `ac7daa6`.
**Closes.** Two independently-verified `v0.16.0` review board findings
(Architecture perspective): the `StateMigrationRegistry` collision
hazard, and the three unregistered `TD-67`/`TD-97` reconciliation
Platform Services. Also closes `TD-126`.
**Cites.** The `v0.16.0` review board's Architecture findings (source of
both remediations below); `docs/adr/ADR-0120-durable-state-carries-a-
schema-version-and-migrations-apply-only-on-read.md`; `TD-87`, `TD-69`,
`TD-67`, `TD-97`, `TD-126`; `docs/academy/06 Engineering Standards/
Engineering Governance.md` §6; `WP16.4B-2 Platform Hygiene.md` (the

## What changed

### Finding 1 — a migration could be silently skipped while the record was stamped as fully migrated

`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectStateStore.cs`,
`StateMigrationRegistry`:

- **`Register` now rejects two collisions it used to allow silently**,
  in the same idiom `WP 16.4B` established one file away for
  `IServiceCollection.Add` (`TD-69`):
  1. **Same-chain duplicate.** Registering a second migration for the
     identical `(chain, FromVersion)` pair — two common migrations at
     the same `FromVersion`, or two migrations for the same Kind at the
     same `FromVersion` — now throws `DuplicateStateMigrationException`
     instead of the second one silently overwriting the first
     (`chain[migration.FromVersion] = migration` used to be a plain,
     unconditional assignment).
  2. **Cross-chain collision.** Registering a common (Kind-less)
     migration and a Kind-specific migration at the **same**
     `FromVersion` now throws `ConflictingStateMigrationException`,
     **regardless of which of the two is registered first.** `Find`
     always prefers the common chain (`ADR-0120` Decision 2, unchanged
     by this fix — see "What did not change" below); before this fix,
     whichever of the two collided lost silently while the record still
     advanced to `FromVersion + 1` and looked fully migrated, exactly
     the "parses correctly but means something different" failure
     `ADR-0120` exists to prevent. The guard checks both directions
     explicitly: registering a common migration scans every existing
     Kind chain for an entry at that `FromVersion`; registering a
     Kind-specific migration checks the common chain for one. A guard
     that only caught one order would read as complete while still
     allowing the other — this was written and tested for both.
- **No opt-in replace escape hatch was added.** `IServiceCollection.Add`
  needed `allowReplace: true` because roughly 330 existing call sites
  had to keep working after that guard landed; here, zero real
  migrations are registered anywhere in `src/` today
  (`CurrentSchemaVersion` is `1`, confirmed by a repository-wide search
  for `IStateMigrationRegistry`/`StateMigrationRegistry` usage outside
  this file, `StateMigration.cs`, and `TempestHost.cs`'s own empty-
  registry registration) — nothing depends on replacing a migration
  once registered, so no escape hatch was added for a hazard that would
  only reopen it. If a future Work Package genuinely needs to replace a
  migration, that is a deliberate design conversation, not something
  this fix should pre-empt silently.
- **`Find`'s own ordering is unchanged** — common chain first, then
  that Kind's own, exactly `ADR-0120` Decision 2's stated behaviour.
  This fix removes the *ambiguous* case (two migrations that both want
  the same `FromVersion` step), not the *defined* one (a common
  migration and a later, different-`FromVersion` Kind-specific migration
  in the same chain walk, which still runs correctly — see the
  regression test below).
- Two new sealed exception types, both `EngineeringDomainException`
  subtypes (the existing root that fits — no new root was invented):
  `DuplicateStateMigrationException` and `ConflictingStateMigrationException`,
  mirroring `DuplicateRehydratorRegistrationException`'s own shape in the
  same file's sibling type one file up
  (`EngineeringObjectRehydrator.cs`) — sealed, a single constructor
  building a clear message, named properties for the contested `Kind`/
  `FromVersion`.
- `IStateMigrationRegistry.Register`'s XML doc updated to state both
  throw conditions.

`tests/Tempest.Core.Tests/EngineeringDomain/SchemaVersioning/StateMigrationChainTests.cs`:

- **Removed** `WhenBothACommonAndAKindSpecificMigrationTargetTheSameVersion_TheCommonOneRunsFirst`,
  which asserted the defect as correct (the Kind-specific migration
  never running, the record still advancing) — the same shape as
  `RestApiHostedServiceTests`' unauthenticated-200 assertion before
  `WP 16.4B`.
- **Added**, covering exactly what the finding and its remediation
  brief asked for:
  - `RegisteringTwoMigrationsForTheIdenticalChainAndFromVersion_Throws`
    — same-chain duplicate (Kind-specific).
  - `RegisteringTwoCommonMigrationsForTheIdenticalFromVersion_Throws` —
    same-chain duplicate (common).
  - `RegisteringACommonMigration_AfterAKindSpecificOneAtTheSameFromVersion_Throws`
    — cross-chain collision, Kind-specific-then-common order.
  - `RegisteringAKindSpecificMigration_AfterACommonOneAtTheSameFromVersion_Throws`
    — cross-chain collision, the reverse (common-then-Kind-specific)
    order.
  - `ANonCollidingCommonMigration_FollowedByThatKindsOwnLaterMigration_MigratesEndToEndInOrder`
    — the regression test: common at `FromVersion` 1, that Kind's own
    migration at `FromVersion` 2 (different versions, no collision) —
    proves `ADR-0120` Decision 2's real ordering still walks a record
    from 1 → 2 → 3 correctly, common first, after the guard above was
    added.

### Finding 2 — three new Platform Services had no register or map entry

`TempestHost.cs` Phase 6 registers `IRequirementsReconciliationService`,
`IMaterialCatalogReconciliationService` and
`IAttachmentContentReconciliationService` (`WP 16.4B`, `TD-67`/`TD-97`)
as ordinary singleton Platform Services. Neither governance document
had an entry for any of the three, and the Register's own Coverage
Status still claimed "35 of 35 known Platform Services" — no longer
true. Engineering Governance §6 states this update is part of the
adding Work Package's own Definition of Done, never a later pass; that
did not happen for `WP 16.4B`.

- **`docs/governance/Engineering/Platform Services Register.md`** —
  three new rows added (Requirements Reconciliation, Material Catalog
  Reconciliation, Attachment Content Reconciliation); Coverage Status
  and the Total line corrected to 38 of 38, and the Last Reviewed field
  states plainly that the review board found this, not `WP 16.4B`
  itself.
- **`docs/architecture/Platform Service Map.md`** — an "At a Glance"
  row and a full Responsibility/Key types/Dependencies/Consumers/
  Lifecycle/ADR-reference/Academy-reference section added for each of
  the three, following the shape the Map already uses. **Each entry
  states prominently that nothing invokes the service** — no startup
  hook, no command, no user-facing surface calls `DetectAsync` or
  `SweepAsync` — because this platform does not repair a user's data
  behind their back, so a reader a year from now does not mistake the
  absence of a caller for dead code.
- **`TD-126` closed in the same pass.** That row named a residual
  `WP 16.2A` disclosed but did not fix: `Platform Service Map.md` had
  register rows but no detail sections for three `v0.14.0` services
  (Plugin Trust & Capability Enforcement, Engineering Object Durability
  & Rehydration, Attachment Content Store). All three now have complete
  detail sections, and — found while doing this — none of the three had
  an "At a Glance" row either; those were added too, since a service
  entry without its summary row is not the shape the Map already uses
  for every other service. `docs/governance/Quality/Technical Debt
  Register.md`'s `TD-126` row is updated to Resolved with this evidence;
  no other TD row was touched.

### `docs/governance/Engineering/Exception Register.md`

`DuplicateStateMigrationException` and `ConflictingStateMigrationException`

Last Reviewed, the Total line (87 → 89), and the Distribution-by-Root-

in the table's own text rather than corrected silently.

## What did not change, and why

- **`Find`'s ordering is untouched.** `ADR-0120` Decision 2's "common
  chain first" behaviour is correct and is not what this fix addresses
  — only the ambiguous registration state that made that ordering
  matter destructively is removed.
- **No opt-in replace parameter.** See the reasoning above; this is a
  considered "no," not an oversight — happy to be argued out of it if a
  real need for it surfaces.
- **Nothing was made to invoke the three reconciliation services.**
  Adding a caller is product capability, explicitly out of `v0.16.0`'s
  scope per `TempestHost.cs`'s own comment above the registration —
  this Work Package documents the services accurately, it does not wire
  one up.
- **`docs/adr/**`, `PROJECT_STATUS.md`, `docs/releases/v0.16.0/
  WorkPackages.md`, and every governance register other than the two
  named plus the single `TD-126` row were left untouched**, per this
  Work Package's own scope boundary — including `Documentation
  Register.md`, `ADR Register.md`, and the Platform Services Register's
  own "At a Glance"-adjacent `Interface Register.md`/`Dependency
  Injection Register.md`/`Module Register.md`, none of which this
  Work Package's changes affect (no new public interface, no new DI
  lifetime pattern, no new module).
- **`User Command Macros` and `External Controller / Input Binding`
  (`WP 10.6A`) are also missing both an "At a Glance" row and a detail
  section in `Platform Service Map.md`**, found while adding the six
  rows above, though the Register's own Last Reviewed narrative for
  `WP 10.6A` had already disclosed the Map side as an unfinished
  follow-up. This is a real, pre-existing gap, distinct from `TD-126`
  (which names only the three `v0.14.0` services), and is left
  disclosed here rather than fixed — it is not one of the two verified
  findings this Work Package was commissioned to remediate, and folding
  an unrelated gap into this change would blur what each commit
  actually closes.
- **The Technical Debt Register's own topmost tracked-item tally** was
  updated only for the single count `TD-126`'s status change requires
  (51 Resolved / 65 Open, 128 tracked, unchanged) — no other row's
  status was touched or re-derived.
