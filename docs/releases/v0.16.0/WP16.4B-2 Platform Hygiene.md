## 1. `TD-68` — `AsyncKeyedLock` grows without bound

**File.** `src/Tempest.Core/Concurrency/AsyncKeyedLock.cs` (rewritten in
place; public shape — `Task<IDisposable> AcquireAsync(string key,
CancellationToken)` — unchanged, so none of its five callers
(`PersistenceStore`, `SettingsProvider`, `EngineeringDocumentStore`,
`MaterialCatalog`, `RequirementsService`) needed any edit).

### What changed

Each key's `SemaphoreSlim` is now held behind a private `Entry` (the
semaphore plus an `int RefCount` and a `bool IsRemoved`), reference-counted
across `AcquireAsync`/`Releaser.Dispose`, and removed from the backing
`ConcurrentDictionary<string, Entry>` — with its semaphore disposed — the
instant the count returns to zero. Keys no longer accumulate for process
life.

**The race closed, and how.** A naive "`GetOrAdd`; ...; `if (--RefCount ==
0) TryRemove(key)`" pair has a well-known TOCTOU window against a
`ConcurrentDictionary`: between one thread deciding the count has reached
zero and that thread actually removing the entry, a second thread's
`GetOrAdd` can observe the same about-to-be-removed entry, take a
reference on it, and start waiting on a `SemaphoreSlim` the first thread
is about to dispose out from under it.

This is closed with a **lock on the `Entry` object itself**, held across
both the refcount mutation *and* the dictionary removal:

- `AcquireAsync` only increments `RefCount` after confirming, under
  `lock (entry)`, that `IsRemoved` is not yet set.
- `ReleaseRef` (used by both `Releaser.Dispose` and the cancellation path
  below) decrements `RefCount` under the same lock, and — because the
  `ConcurrentDictionary.TryRemove` call itself happens while still holding
  that lock — by the time `IsRemoved` becomes visible to any other thread,
  the entry is already gone from the dictionary.

A concurrent acquirer can therefore never rediscover a retired entry and
wait on its disposed semaphore; at worst (if its `GetOrAdd` raced in just
before removal) it retries once with a fresh `GetOrAdd`, which is
guaranteed to either find a genuinely new entry or create one. This exact
reasoning is recorded as a code comment on `ReleaseRef` in the source, per
this stream's own instruction to say in-code which race was closed.

**A second, related leak this closed that wasn't explicitly named in the
register row:** if `WaitAsync(cancellationToken)` throws — cancellation,
most plausibly — *after* `AcquireAsync` has already reserved (incremented)
the entry, the original code had no equivalent state to leak, but a naive
refcounted rewrite would have leaked that reservation forever (the entry
never reaching zero, defeating the whole fix). `AcquireAsync` now wraps
`WaitAsync` in try/catch and calls `ReleaseRef` on any failure before
rethrowing.

**Double-dispose guard.** `Releaser`'s `bool _released` guard is replaced
with `Interlocked.Exchange(ref _entry, null)`: `Dispose()` hands the
`Entry` reference to at most one caller, even when two threads call
`Dispose()` on the same `Releaser` at the same instant, so the semaphore
is released and the reservation dropped exactly once.

### What did not change, and why

- **Public API.** `AcquireAsync`'s signature and `Releaser`'s `IDisposable`
  contract are identical to before. `AsyncKeyedLock` is `internal` and was
  never `IDisposable`/`IAsyncDisposable` itself (it has no unmanaged or
  disposable-typed state of its own beyond per-key semaphores it now
  manages entirely internally) — no disposal contract was added, per this
  stream's own instruction not to widen one.
- **`internal int TrackedKeyCount`** was added purely for test
  observability (guarded by the project's existing
  `InternalsVisibleTo("Tempest.Core.Tests")` in
  `src/Tempest.Core/AssemblyInfo.cs` — confirmed already present, no new
  grant added). It is not used by any production code path.

### Tests

`tests/Tempest.Core.Tests/Concurrency/AsyncKeyedLockTests.cs` (new folder,
new file):

| Test | Proves |
|---|---|
| `AcquireAsync_SameKey_SerializesConcurrentAccess` | A second acquirer cannot complete while the first still holds the same key — asserted as a correctness property (`IsCompleted` cannot legitimately flip before the release signal), not a timing race, so it cannot flake. |
| `AcquireAsync_AfterSoleHolderDisposes_RemovesTheEntry` | `TrackedKeyCount` goes `1 → 0` once the only holder disposes. |
| `AcquireAsync_WhileASecondHolderIsQueued_EntrySurvivesUntilBothRelease` | The entry is not torn down while a second reservation is still queued behind the first. |
| `AcquireAsync_ManyTasksFewKeysInterleaved_NoDoubleEntryAndCorrectFinalState` | 40 tasks × 50 iterations over 4 keys, interleaved acquire/release: no key is ever observed held twice at once, every reservation lands (`40×50` total), `TrackedKeyCount` is `0` at the end. Bounded entirely by fixed loop counts, no wall-clock waits — every assertion is an interleaving-independent invariant, so it cannot flake by machine speed (`WP 16.4A`'s own bar). |
| `Releaser_DoubleDisposedConcurrently_ReleasesExactlyOnce` | Two threads, released via a `Barrier`, call `Dispose()` on the same `Releaser` at the same instant: no `SemaphoreFullException`, `TrackedKeyCount` returns to `0`, and a fresh acquire on the same key succeeds immediately afterward (proving the semaphore's count was never corrupted by an over-release). |

All five pass; see §6 for the full-suite numbers.

## 2. `TD-69` — two latent DI container defects

**Files.** `src/Tempest.Core/DependencyInjection/ServiceCollection.cs`,
`IServiceCollection.cs`, `TempestServiceProvider.cs` (all edited); two new
files, `ServiceRegistrationException.cs` and
`DuplicateServiceRegistrationException.cs`.

### 2.1 Duplicate registration

`IServiceCollection.Add` and `AddInstance` both gained a trailing optional
`bool allowReplace = false` parameter. When `false` (the default, and
every existing call site's effective behaviour) and a registration for the
service type already exists, both now throw
`DuplicateServiceRegistrationException` naming the service type, instead
of silently replacing the registration. `allowReplace: true` opts in to
the deliberate-replace case explicitly.

**New exception shape.** `DuplicateApiRouteException`'s idiom (a
category-specific base, never thrown directly, plus a `sealed` subtype
carrying the identifying data) is followed, but *not* by hanging the new
exception off the DI category's existing base,
`ServiceResolutionException`. That type's own doc comment scopes it
specifically to failures *while an already-built `ITempestServiceProvider`
resolves a service* — a different lifecycle phase from *registering* with
an `IServiceCollection`, before any provider exists. A new base,
`ServiceRegistrationException : Exception` (never thrown directly), plus
`DuplicateServiceRegistrationException : ServiceRegistrationException`,
mirrors the same registration/resolution split the codebase already draws
for modules (`ModuleDiscoveryException` vs `ModuleRegistrationException`
are two separate root categories in the Exception Register, not one).
This is a deliberate, disclosed choice, not the only defensible one — the
alternative of hanging it off `ServiceResolutionException` directly was
considered and rejected as semantically wrong per that type's own stated
scope.

**Full duplicate-registration call-site audit.** Every call to `Add`,
`AddInstance`, and the `Singleton`/`Transient`/`AddInstance<T>` extension
methods across the entire `src/` and `tests/` trees (`Tempest.Core`,
`Tempest.Desktop`, `Tempest.App`, `Plugins`, `Samples`, `Templates`,
`Validation`, and both test projects) was enumerated by script, then every
case where the same service type was registered more than once against
the *same* `IServiceCollection` instance was traced by hand (method
boundaries, and, where registrations crossed method calls, actual
call-order tracing — e.g. `Tempest.Desktop`'s `DesktopCompositionRoot`,
confirmed to only ever call `GetService`, never `Add`/`AddInstance`, so it
cannot contribute a duplicate). This is the complete result:

| Call site | Service type | Disposition |
|---|---|---|
| `tests/Tempest.Core.Tests/DependencyInjection/ServiceCollectionTests.cs` — `Add_SameServiceTypeTwice_LastRegistrationWins` | `IGreeter` | **The one legitimate/deliberate case in the entire codebase, and it was testing the defect itself.** This unit test registered `IGreeter` as Singleton then as Transient on the same collection specifically to assert "last one wins" — i.e. it codified TD-69's own defect as a feature. Rewritten (see §2.3) to assert the new throw, plus a new, separate test that exercises the `allowReplace: true` opt-in explicitly. |
| `tests/Tempest.Core.Tests/Samples/AuditSampleModuleIntegrationTests.cs`, `IdentitySampleModuleIntegrationTests.cs`, `VerificationSampleModuleIntegrationTests.cs`, `ExportImportSampleModuleIntegrationTests.cs`, `LicensingSampleModuleIntegrationTests.cs`, `EngineeringDomainSampleModuleIntegrationTests.cs`, `RequirementsSampleModuleIntegrationTests.cs`, `ReportingSampleModuleIntegrationTests.cs` — each file's `BuildPipeline` helper | `Tempest.Core.Identity.IPermissionEvaluator` | **A real, previously-silent defect that TD-69's fix correctly caught.** Each of these eight helpers registered `IPermissionEvaluator` twice: once via `AddInstance(new PermissionEvaluator())` (a throwaway instance with no logger), then again a few lines later via `Singleton<IPermissionEvaluator, PermissionEvaluator>()` (container-constructed, so it receives the registered `ILogger`). Under last-wins, the `AddInstance` line was silently dead — every one of these pipelines was already only ever using the `Singleton` registration; the `AddInstance` call and its throwaway instance were doing nothing. Fixed by deleting the now-redundant `AddInstance` line from each file, which reproduces the exact effective behaviour these pipelines already had (verified: `PermissionEvaluator`'s only constructor parameter, `ILogger? logger = null`, means the two registrations were behaviourally interchangeable anyway; removing the shadowed one is a no-op on test outcomes — confirmed by the full suite re-run in §6). |
| Every other `Add`/`AddInstance`/`Singleton`/`Transient` call site found (≈330 call sites, spread across ~40 files) | various | No duplicate registration against the same collection instance found. Two extension points that register in a loop over caller-supplied collections — `ModuleServiceCollectionExtensions.AddDiscoveredModules` and `HostedServiceCollectionExtensions.AddDiscoveredHostedServices` — were checked specifically: each iterates a caller-supplied sequence and registers each entry's own concrete type as its own key; a genuine duplicate there (two descriptors sharing a `ModuleType`) would itself be a real defect worth surfacing, not a legitimate case to special-case around, so no `allowReplace` was threaded through them. |

No call site was silently changed in meaning: the one file relying on
replace semantics was rewritten to opt in explicitly (`allowReplace:
true`); the eight files with the latent double-registration had their
dead line removed, which changes zero test behaviour (confirmed by
re-run); every other call site is untouched.

### 2.2 Optional constructor parameters

`TempestServiceProvider.Construct` (constructor selection — `GetConstructors()`,
exactly one public constructor required — is completely unchanged) now
resolves each parameter as:

```csharp
if (!_descriptorsByType.ContainsKey(parameterType) && parameters[i].HasDefaultValue)
    arguments[i] = parameters[i].DefaultValue;
else
    arguments[i] = Resolve(parameterType, resolutionChain);
```

Only the exact case named in the register row — the parameter's type has
*no registration at all*, and the parameter itself declares a default —
falls back to that default. A registered type that fails for any other
reason (a circular dependency, a deeper missing dependency of its own)
still goes through the ordinary `Resolve` call and fails exactly as
before; a required parameter (`HasDefaultValue == false`) of an
unregistered type also still goes through `Resolve` and throws
`ServiceNotRegisteredException` with the same message quality as before —
this is a strict narrowing of when construction fails, not a general
"swallow resolution failures" fallback.

### What did not change, and why

  threaded through the `Singleton`/`Transient`/`AddInstance<T>` extension
  convenience methods, since the only caller needing it (a test) can call
  `Add`/`AddInstance` directly — threading it through every convenience
  overload as well was judged scope the register row did not ask for.
