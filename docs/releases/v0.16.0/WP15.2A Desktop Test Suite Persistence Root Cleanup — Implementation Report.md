## 3. The Fix

`WorkspacePersistenceCollection.NewIsolatedPersistenceRootPath()` now
returns a path under one shared, per-test-run parent directory
(`RunRootPath`, generated once when the class loads) instead of directly
under the OS temp folder. A new `PersistenceRootCleanupFixture`,
registered on the same collection via `ICollectionFixture<T>`, deletes
that entire parent directory — once — in its own `Dispose()`, which
xUnit calls only after every test in the "Tempest.Desktop WorkspaceHost
persistence" collection has finished.

**A design question the register's own `TD-120` entry left open**
("depends on whether a failed test's persistence root should survive for
diagnosis") **is resolved, not sidestepped**: an ordinary assertion
failure inside a test already carries its own message and stack trace in
the test-runner output, so it does not need its directory preserved.
xUnit v2 collection fixtures cannot observe individual test outcomes
directly, so this design does not try to special-case them — instead, the
one situation that genuinely still leaves a directory behind is exactly
the one this fixture's own `Dispose()` never reaches: a crash, a
disk-exhaustion kill, or a forced interrupt severe enough to end the
process before normal collection teardown runs. That is also precisely
the situation a real diagnosis would want evidence for, so the design
serves both goals without tracking pass/fail state at all.

**A second, adjacent gap found while implementing this, not assumed away:**
`ResponsiveWorkspaceTests` constructs three real `WorkspaceHost`
instances via the same `NewIsolatedPersistenceRootPath()` method but
carried no `[Collection(...)]` attribute — the only class among more than
forty call sites that did not. This meant it ran in its own,
unserialised xUnit collection, exposed to exactly the process-wide
headless-Avalonia-dispatcher hazard the collection exists to prevent, and
its own three directories would not have been covered by the new cleanup
fixture's lifetime (a collection fixture's `Dispose()` fires only when
its own collection's tests are done — a class outside the collection
gives no such guarantee). Fixed by adding the collection attribute; not a
separate Work Package, since leaving it out would have made this
Work Package's own "every isolated root gets cleaned up" claim false for
one file.

## 5. Why This Report Lives in `docs/releases/v0.15.1/`, Not `v0.15.0/`

`v0.15.0`'s own `WorkPackages.md` describes a closed, tagged, published
release — reopening its own accounting now would misrepresent that
release's own already-published history, the same reasoning `WP 11.5A`
applied to `v0.11.0`'s own closed record. No `v0.15.1` (or any later)
release has been approved, scoped, or cut. This folder is created
**only** to hold this Work Package's own documentation, not to declare a
release: **`VERSION` is deliberately left at `0.15.0`, no tag is created,
and no `Release Notes.md` is written here.** Assigning this work a real
version is a release-preparation decision for a future Work Package to
make — exactly the same relationship `WP 15.0A`–`D` had to `WP 15.1A`
before that Work Package formalised them.
