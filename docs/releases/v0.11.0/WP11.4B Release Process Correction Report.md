# WP 11.4B — Release Process Correction Report

## Role and Standard Applied

This report is written as Chief Release Engineer, in the format of a
genuine engineering Non-Conformance Report / Corrective and Preventive
Action (NCR/CAPA) record. It documents a **release-process defect** —
not a product defect, not an architecture defect, not a code defect —
found in `v0.11.0`'s own tag before that release's branch closed, the
one-time, Product-Owner-approved governance exception under which it
was corrected, the corrective sequence executed, and independent
verification of every claim below. Nothing in this report is assumed;
every figure was reproduced from source, from `git`, or from the
GitHub API during this Work Package itself.

## 2. Discovery

Discovered during `WP 11.4B`'s own required pre-merge verification —
specifically, checking where the `v0.11.0` tag actually resolved
relative to `main` before performing the merge, not assumed correct
because it had already been created:

```
$ git rev-parse "v0.11.0^{commit}"
fda4172689405fe7a8c3fd51a66fbd6b9276aca9
$ git rev-parse main
57601eb06a0bb10371997c6bd912b77556ce4ecb
$ git merge-base --is-ancestor v0.11.0 main; echo $?
1   # false — not an ancestor
$ git log main..feature/v0.11.0-v1-architecture --oneline | wc -l
10  # feature branch strictly ahead
$ git log feature/v0.11.0-v1-architecture..main --oneline | wc -l
0   # main has nothing feature doesn't
```

Per this task's own explicit instruction at the time ("if anything
unexpected is discovered during merge, stop immediately and report it
rather than correcting it"), no further repository action was taken
until this finding was reported and the Product Owner had explicitly
reviewed and authorised a correction.

## 3. Root Cause

`v0.11.0`'s tag was created (`WP 11.9.0`) by directly mirroring
`v0.10.0`'s own tag-creation *command shape* (`git tag -a v0.11.0 -F
<message>`, run against the feature branch's own tip commit) as a
mechanical template, without cross-checking `docs/releases/v0.11.0/
WP11.1B Engineering Workflow.md`'s own "Evidence & Findings" section —
written *during this same release*, before the tag was created — which
had already established that `v0.10.0`'s own tag-creation sequence
(tag before merge) was itself the defect, not a pattern to repeat.
Governance §7 items 1 and 3 (a release is only cut from `main`; Build
Gate/Test Gate must pass on `main` itself, immediately before tagging)
were both, as a direct consequence, not satisfied at the moment
`v0.11.0` was tagged — identically to how they were not satisfied for
`v0.10.0`.

## 4. Why the Error Occurred

- **A precedent was copied at the wrong level of abstraction.** `WP
  11.9.0`'s own tag-creation step correctly reproduced `v0.10.0`'s tag
  *format* (annotated, structured message, `git tag -a ... -F ...`) but
  did not re-derive *when* a tag should be created from Governance §7
  itself — it copied what `v0.10.0` did, not what `v0.10.0` was later
  found to have done wrong.
- **The two facts existed in different documents, both real, neither
  cross-referenced at the moment of action.** `WP11.1B Engineering
  Workflow.md`'s own disclosure of the `v0.10.0` defect, and the
  Governance §7 rule it was written to reinforce, were both already
  in the repository when `v0.11.0`'s tag was created — the error was
  not a missing fact, it was a missing cross-check between an
  available fact and an action about to be taken.
- **No mechanical gate existed to catch it.** Branch protection is not
  yet configured (`TD-45`); nothing in GitHub or in
  `scripts/governance-healthcheck.ps1` verifies that a newly-created
  tag is an ancestor of `main` before or after it is pushed. The
  correctness of a tag's own position depended entirely on the
  person or agent creating it remembering to check — exactly the
  failure mode `WP11.1B`'s own disclosure warned against in prose,
  without (at the time) adding an automated check to enforce it.

## 5. Why It Escaped Review

`WP 11.9.0` (the sign-off Work Package that created the tag) performed
extensive, genuinely rigorous verification — a six-discipline Programme
Review, independent build/test re-verification, governance-register
currency checks — but its own scope never included re-deriving the
release *process* itself from Governance §7's own numbered items; it
took the tag-creation step as a mechanical, low-risk formality similar
to `v0.10.0`'s own, not as a step with its own, independently-checkable
correctness condition (ancestry of `main`). The subsequent `WP 11.4A`
(release-engineering corrections) was scoped narrowly and explicitly to
three already-diagnosed CI defects — it had no reason to re-examine tag
placement, since nothing in its own brief pointed there. **This is a
real, second-order finding in its own right**: two prior review passes
(`WP 11.9.0`'s six-discipline Programme Review, `WP 11.4A`'s own
verification) each had genuine, real rigor, but neither one's own scope
included the specific check that would have caught this
(`git merge-base --is-ancestor`) — it was first performed only because
`WP 11.4B`'s own brief specifically required verifying the tag's
position as a precondition to merging.

## 6. Governance Exception

Per explicit Product Owner authorisation, Governance §7 item 4
(`docs/academy/06 Engineering Standards/Engineering Governance.md`) is
amended. The absolute wording:

> a tag, once created and pushed, is not moved or recreated

is now qualified by a narrow, explicitly-scoped exception:

> Published release tags are immutable except where a documented
> release-process defect is identified before closure of the release
> branch. Such corrections require explicit Product Owner approval, a
> documented Release Process Correction Report, and must preserve
> complete traceability.

Applied consistently in three places (each cross-referencing the
others, none contradicting): `Engineering Governance.md` §7 item 4 (the
canonical rule) and item 7 (the `v0.10.0`/`v0.11.0` disclosure, now
carrying a forward note); `WP11.1B Engineering Workflow.md` §10
(Rollback Procedure's own governing principle, now distinguishing
rollback — a defect in *content*, always forward, tag never touched —
from this exception — a defect in the tag's own *mechanical position*,
found before closure); `05-release-engineering.md` (the Academy
article, both citations updated to match).

**Explicitly bounded, not a general licence:**

- Applies only to a defect in the tag's own **position** — never to the
  release's own content, build, or test evidence.
- Applies only **before the release branch closes**. `v0.10.0`'s own
  case — found after its branch had long since merged and closed — is
  explicitly, textually **not reopened**; it remains permanent,
  disclosed history, exactly as `WP11.1B` originally recorded it. The
  distinction is not cosmetic: a release branch that has already closed
  has, by definition, already had its own tag durably referenced
  (downstream clones, external consumers, prior GitHub Release
  history) for however long it has been closed — correcting it
  retroactively would be a rewrite of already-relied-upon history, not
  a same-day correction of a defect no one outside this session has yet
  had reason to depend on. `v0.11.0`'s own correction was executed
  within the same working session the defect was created in, before
  the branch that produced it had merged anywhere.
- Requires explicit, per-occasion Product Owner approval — never
  standing, never assumed from this occasion forward.
- Requires a Release Process Correction Report (this document) with
  full traceability — the original tag's own commit, message, and
  timing are all preserved in this report and in `git reflog`/this
  document's own §1, even though the tag ref itself was recreated.

## 7. Corrective Action

Executed exactly per the Product-Owner-approved sequence, each step
independently verified before proceeding to the next:

1. Working tree confirmed clean; two outstanding commits
   (`0670843`, `9196aa6`) pushed to `feature/v0.11.0-v1-architecture`.
2. Local tag deleted: `git tag -d v0.11.0`.
3. Remote tag deleted: `git push origin :refs/tags/v0.11.0`.
4. `main` checked out and pulled (already up to date — no divergent
   commits existed on `main` since the branch was cut).
5. Merged: `git merge --no-ff feature/v0.11.0-v1-architecture` — clean,
   no conflicts, merge commit `4b1fb16918af4f9c53ed47a2182680a1ae0b8cb8`
   (parents `57601eb` — old `main` — and `9196aa6` — the feature
   branch's own final commit).
6. **Build Gate/Test Gate re-verified on `main` itself**, immediately
   before tagging — Governance §7.3, satisfied as literally written for
   the first time this release (see §8, below).
7. New annotated tag created on the merge commit, **reusing the
   original annotation verbatim** (captured via `git for-each-ref
   --format='%(contents)'` before deletion, applied via `git tag -a
   v0.11.0 -F <captured-file>`) — the tag's own text is therefore
   byte-identical to the one Product Approval originally reviewed;
   only its target commit changed.
8. `main` pushed, then the corrected tag pushed.

**Do not assume success — one claim required correction mid-verification**:
initially checking `GET /releases/tags/v0.11.0` immediately after tag
deletion returned **HTTP 404**, and the original Release object (`id
368605775`) was found — by its stable numeric ID, not by tag name — to
have been silently converted by GitHub into a **draft**, its URL
rewritten to a synthetic `untagged-9246469d05862713c1cc` placeholder.
This is disclosed as a genuine, observed GitHub platform behaviour, not
assumed or guessed: deleting a tag that has an associated Release
does not delete the Release, but does orphan it into a draft. Once the
corrected tag was pushed, `release.yml`'s own `gh release create`
**did not reattach this orphaned draft** — it created an entirely new,
correctly-published Release object. **The original orphaned draft
(`id 368605775`) still exists**, disclosed here explicitly, not
deleted: cleaning it up was outside `WP 11.4B`'s own explicitly
authorised sequence (which named only the git tag, not the GitHub
Release object), and deleting a GitHub Release — even a draft one — is
an outward-facing action this report defers to an explicit,
separate instruction rather than taking unilaterally.

## 11. Preventative Action

1. **A tag-ancestry check should be added to
   `scripts/governance-healthcheck.ps1`** (or a dedicated pre-tag
   script step): before or immediately after creating a `vX.Y.Z` tag,
   verify `git merge-base --is-ancestor <tag> main`. This converts the
   check that caught this defect from a human/agent-remembered
   cross-reference into a mechanical one — the same class of
   improvement `FCR-0005` already exists to generalise. Not
   implemented within this Work Package (`scripts/governance-
   healthcheck.ps1` code changes are outside `WP 11.4B`'s own
   "no production code changes" constraint) — recommended as a
   concrete `v0.12.0` candidate.
2. **A release checklist should explicitly separate "tag exists" from
   "tag is correctly positioned."** This defect occurred precisely
   because the former was verified (the tag existed, was annotated,
   was pushed, and a Release was published from it) while the latter
   was not — the two are easy to conflate when a release appears to
   have succeeded by every visible signal (a live GitHub Release, a
   working build) except the one this Work Package's own brief
   specifically asked to check.
3. **This report itself is the preventative record**: the next time a
   precedent is copied for a release action, `WP11.1B Engineering
   Workflow.md`'s own "Evidence & Findings" and this report both now
   exist as two, not one, concrete instances of the identical failure
   mode — a pattern strong enough that a future reviewer should treat
   "did the prior release do this correctly" as a question requiring
   its own explicit verification, not an assumption.
