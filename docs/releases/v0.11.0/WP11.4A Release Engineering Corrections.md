## Objective

Resolve the three release-engineering defects diagnosed in
`docs/releases/v0.11.0/Release Publication Report.md` — the first time

## Scope

Exactly the three diagnosed fixes. **No production code, Domain code,
or architecture changed; no feature work.** All three touched files
are test/tooling/CI-configuration only:

### 1. Stabilised the flaky `ObjectEditorView` test

**File**: `tests/Tempest.Desktop.Tests/ObjectEditorViewTests.cs`.

**Before**: `VerificationResultSection_RecordPass_ActuallyRecordsARealVerificationRecord`
used a fixed `await Task.Delay(50);` to wait for an async status-text
update before asserting on it.

**After**: replaced the fixed delay with a bounded (2-second) poll
against the real, live status text — re-read from the visual tree on
every iteration, not a reference captured once — that exits as soon as
the real condition is met. Test intent preserved exactly: the same
final assertion (`Assert.Contains("recorded", ...)`) still runs; the
test still genuinely fails if the operation never completes, just no
longer fails because it merely ran slower than an arbitrary guess.

### 2. Corrected `governance-healthcheck.ps1`'s absolute-path handling

**File**: `scripts/governance-healthcheck.ps1`.

**Before**: `-SummaryPath` resolution used PowerShell's `Join-Path`
unconditionally, which — unlike `[System.IO.Path]::Combine` — does not
discard an already-rooted child path. An absolute `-SummaryPath` (e.g.
`ci.yml`'s own `$env:RUNNER_TEMP`-based path) doubled into `RepoRoot`,
tripping the script's own "never write inside the repo" safety check
for the wrong underlying reason.

**After**: guarded with `[System.IO.Path]::IsPathRooted($SummaryPath)`
— an already-rooted path resolves directly via `GetFullPath`; a
relative path still joins against the current location exactly as
before. Existing behaviour preserved: relative-path resolution is
unchanged, and the genuine "path really is inside the repo" safety
check still fires correctly.

### 3. Corrected `ci.yml`'s tag-triggered checkout conflict

**File**: `.github/workflows/ci.yml` (`governance-health-check` job).

**Before**: the job's `Checkout` step set `fetch-tags: true` with no
pinned `ref:`. On a tag-triggered push, `actions/checkout@v4`'s own
default ref (the pushed tag itself) collided with `fetch-tags: true`'s
own fetch of that identical tag — both targeted the same local
`refs/tags/<name>` path, and git refused
(`fatal: Cannot fetch both <sha> and refs/tags/<name> to refs/tags/<name>`).

**After**: pinned `ref: ${{ github.sha }}` — checking out by commit SHA
removes the competing tag-ref write target. Verified valid on both a
branch push and a tag push (see Verification, below).

### Local — governance health check

Reproduced the exact CI failure scenario locally: an absolute,
`$env:RUNNER_TEMP`-shaped `-SummaryPath`, invoked with the repository
root as the current directory. **Before this fix** (per the CI logs
diagnosed in the Release Publication Report): uncaught exception,
non-zero exit, no report produced. **After this fix**: the script runs
to completion and writes its report to the correct absolute path (exit
code 1 — reflecting three genuine, pre-existing, already-disclosed
governance findings unrelated to this fix — Academy Index and
Documentation Register path gaps tracked since `WP 11.2A`/`WP 11.9.0`,
explicitly out of this Work Package's own scope to resolve).

Two regression checks also run and confirmed:
- **Relative `-SummaryPath`** (the pre-existing, documented behaviour):
  unchanged — still resolves next to the current directory.
- **A `-SummaryPath` genuinely inside `RepoRoot`**: the safety check
  still correctly throws, and no file is created inside the repository.
