# WP 11.1B — Engineering Workflow

**Type.** Implementation (GitHub configuration, release tooling,
documentation only). No production code behaviour changed.
**Branch.** `feature/v0.11.0-v1-architecture`.
**Builds on.** `.github/workflows/ci.yml` (`WP 11.1A`) — this document
defines the engineering workflow *around* that pipeline: what governs a
change from feature branch through release, now that a machine-verified
Build Gate and Test Gate exist.

---

## Preconditions

- **Active branch.** `feature/v0.11.0-v1-architecture` — confirmed via
  `git branch --show-current`.
- **Clean working tree.** Confirmed via `git status --porcelain`
  (empty) before any change was made — unlike `WP 11.1A`, no correction
  was required this time.

## 1. Branching Strategy

**`main` is the only permanent branch.** It always reflects the latest
released version, except momentarily during a release merge. Direct
commits to `main` outside a release merge or a hotfix merge are not part
of this workflow (see §9 for the one disclosed historical exception,
`v0.9.0`, which this document does not repeat as a model).

**One release branch per minor release**, `feature/vX.Y.0-<slug>`, cut
from `main` at the prior release's own tag — the exact, confirmed
pattern of `feature/v0.5.0-developer-experience` through
`feature/v0.10.0-user-experience`. Every Work Package for that release
lands as its own commit directly on this branch (the pattern this very
release's own history already demonstrates: `WP 11.0A`/`WP 11.0B` one
commit, `WP 11.1A` one commit).

**Hotfix branches**, `hotfix/vX.Y.Z-<slug>`, are the one other branch
type this workflow defines — see §7.

**Feature and hotfix branches are never deleted** after merging, matching
this project's own existing, confirmed convention.

**No permanent `develop`/`staging` branch.** Considered and rejected:
this project has never had one, nothing in `WP11.0A`/`WP11.0B`'s own
findings identifies a gap a permanent integration branch would close, and
adding one now would be a genuine process-architecture change this Work
Package's own brief did not ask for.

## 2. Pull Request Expectations

**From `WP 11.1B` onward, every merge into `main` — a release branch or
a hotfix branch — goes through a pull request.** This is a formal change
to how a branch reaches `main`: through `v0.10.0`, every merge was a
direct, local `git merge`/`git push` by Product Approval, with no GitHub
pull request involved at any point. That history is not invalidated by
this change — it predates the CI pipeline (`WP 11.1A`) a pull request's
own required status check depends on — but it does not continue as the
model either.

A pull request's own "unit" matches this project's existing branch
granularity: **one PR per release branch** (opened once the branch is
ready to merge, base `main`, compare the release branch), not one PR per
Work Package — Work Packages continue landing as individual commits on
the release branch exactly as today; only the final release-branch → `main`
step gains a pull request. A hotfix branch gets its own, separate,
smaller pull request.

**Every pull request:**

- Uses `.github/pull_request_template.md` (added this Work Package) —
  Work Package/change identification, a summary, the three review gates
  (§2 checklist), scope confirmation (no production code / architecture /
  ADR change, or an explicit justification), testing performed, and a
  Product Approval field left for that tier alone to complete.
- Has a green `CI Gate` check (`.github/workflows/ci.yml`, `WP 11.1A`) —
  the pull request's own required status check (§4).
- Is merged using **"Create a merge commit,"** never squash or rebase —
  preserves the Work-Package-by-Work-Package commit history a squashed
  merge would erase, the same granularity this project's own Academy and
  Technical Debt Register retrospectives already depend on for
  traceability.
- Is merged only on Product Approval's own explicit, per-occasion
  instruction (§6) — the pull request's own "Merge" action is that
  instruction's mechanical realisation, not a delegation of it.

---

## 3. Merge Requirements

A branch may be merged into `main` only when **all** of the following
hold, verified at the branch's own tip commit:

1. The `CI Gate` check (`.github/workflows/ci.yml`) is green.
2. The Build Gate and Test Gate (Engineering Governance §2) pass —
   mechanically identical to (1), restated because §2 predates CI and
   still governs in substance.
3. The Technical Review Gate (§2.3) is satisfied for any non-obvious
   decision the branch introduces — documented in the pull request or a
   linked Implementation Report.
4. The working tree that produced the branch tip was fully committed —
   no merge is ever performed against local, uncommitted state.
5. The merge is a non-fast-forward merge commit (§2, above).
6. Product Approval has given explicit, per-occasion instruction to
   merge (§6) — never assumed from an earlier, different approval.

## 4. Required CI Status Checks & Branch Protection (Recommended — Not Configured)

**This Work Package documents these settings; it does not enable them.**
Per this Work Package's own constraint, configuring GitHub repository
settings is left to a repository administrator. Recommended, for `main`:

| Setting | Recommended value | Why |
|---|---|---|
| Require a pull request before merging | On | Mechanically enforces §2. |
| Require status checks to pass before merging | On, required check: **`CI Gate`** | The single named check `.github/workflows/ci.yml`'s own `gate` job produces (`WP 11.1A`) — depends on both matrix legs (`Debug`, `Release`), so requiring it alone is sufficient; the two legs do not need to be named individually. |
| Require branches to be up to date before merging | On | Prevents merging a branch whose own CI run predates a since-merged change to `main`. |
| Require review from Code Owners | On | Pairs with `.github/CODEOWNERS` (added this Work Package) — makes Product Approval's existing, prose-only requirement (Governance §9) visible in GitHub's own review UI. |
| Allowed merge methods | **Merge commit only** — disable squash and rebase | Preserves Work-Package-level commit granularity (§2). |
| Require linear history | **Off — do not enable** | Directly incompatible with "merge commit only," above; enabling it would force squash/rebase and silently defeat §2's own requirement. Named explicitly so a future administrator does not enable it by reflex. |
| Restrict who can push to matching branches | On, Product Approval only | Mechanises Governance §9 — no tier merges or pushes to `main` except Product Approval. |

Recommended, for tags matching `v*`:

| Setting | Recommended value | Why |
|---|---|---|
| Tag protection rule, pattern `v*` | On | Mechanises Governance §7.4 ("a tag, once created and pushed, is not moved or recreated") — without this, the rule is discipline-only. |

## 5. Release Requirements

A version is releasable only when **all** of the following hold:

1. The release is cut from `main`, **after** the release branch has
   already been merged into it — never from the feature branch itself.
   (§9 discloses the one release this rule was not followed for.)
2. `VERSION` (repository root) matches the version being released
   exactly.
3. Release notes exist at `docs/releases/vX.Y.Z/Release Notes.md` —
   this project's actual, current convention (§9 discloses where the
   release script previously disagreed with it).
4. The `CI Gate` check is green on `main` itself, at the exact commit
   about to be tagged — not merely on the branch that fed into it.
5. A release-readiness review has been produced recommending **APPROVED**
   or **CERTIFIED** — the same pattern every release since `v0.6.0` has
   already followed (`WP 6.8`, `WP 7.4.0`, `WP 8.9.0`, `WP 9.9.0`,
   `WP 10.9A`), now named as a standing Release Requirement rather than
   an observed pattern. Proportionate for a hotfix — see §7.
6. An annotated tag (never lightweight) is created via
   `scripts/new-release.ps1` (or, exceptionally, the equivalent manual
   `git tag -a` command the script itself runs) — the script's own
   checks (branch, clean tree, `VERSION` match, release notes exist,
   Build Gate, Test Gate) must all pass; running it is not optional
   ceremony.
7. Product Approval gives separate, explicit, per-occasion instruction
   to push `main` and to push the tag (Governance §7.5) — restated, not
   changed.
8. Pushing the tag triggers `.github/workflows/release.yml` (added this
   Work Package, §6), which independently re-builds and re-tests Release
   configuration at the tagged commit and publishes a GitHub Release with
   the build output attached. **A tag that exists but whose `release.yml`
   run failed is not a shipped release** — see §8 (Rollback Procedure).

## 6. Release Sign-Off Responsibilities

Mapped directly onto Engineering Governance §9's existing three tiers —
this Work Package assigns no new authority, it binds the existing one to
concrete steps:

| Tier | Responsibility in this workflow |
|---|---|
| **Architecture** (the engineer/agent executing the release) | Prepares the release: runs the Build/Test Gates locally, writes release notes, produces the release-readiness review, sets `VERSION`, opens the pull request. |
| **Technical Review** | Reviews the release-readiness review and any non-obvious decision the release branch introduced; confirms or requires change, per §2.3's own established standard. |
| **Product Approval** | The only tier that may: approve and merge the pull request into `main`; push `main`; run `scripts/new-release.ps1` with `-Push`, which creates and pushes the annotated tag. Each of these three actions requires its own explicit, per-occasion instruction (Governance §7.5/§7.6) — an instruction covering one does not cover the others. |

## 7. Versioning Policy

`VERSION` (repository root) remains the single source of truth —
unchanged; `Directory.Build.props` still reads it once, as it always has.

- **Format:** `MAJOR.MINOR.PATCH`, with an optional `-rc.N` pre-release
  suffix during a release candidate (§8).
- **MAJOR** is reserved — every release through `v0.10.0` is `0.Y.0`;
  the first MAJOR bump is `v1.0.0`, per `WP11.0B Architecture
  Roadmap.md`'s own recommended definition, not incremented casually
  before then.
- **MINOR** is a regular, planned, Work-Package-driven release on its
  own `feature/vX.Y.0-*` branch — `v0.11.0`, `v0.12.0`, and so on.
  Always `.0` at first release.
- **PATCH** is a hotfix, and only a hotfix (§7 — Hotfix Workflow, below,
  reuses this same number in a different sense; context disambiguates).
  **This project has never cut a non-zero patch version** — every tag
  through `v0.10.0` is `X.Y.0`. This policy's PATCH semantics are a
  deliberate, disclosed new convention, not a retrofit of a pattern that
  already existed.
- **`-rc.N` pre-release suffix**: a release candidate (§8) — never a
  "real" release in its own right, always superseded by the final
  `vX.Y.Z` tag.

## 8. Release-Candidate Process

Optional, at Product Approval's own discretion, for a release carrying
material risk or scope — `WP11.0B Architecture Roadmap.md` already names
`v1.0.0` as an expected user of this process (its own `WP RC.0A`).

1. On the release branch, before merging to `main`: set `VERSION` to
   `X.Y.Z-rc.N`, commit.
2. Tag `vX.Y.Z-rc.N` **directly on the release branch** — the one
   deliberate, named exception to §5.1's "cut only from `main`, after
   merge" rule, since a release candidate by definition precedes the
   merge it is candidate *for*. Disclosed explicitly here so it is never
   mistaken for a second, silent violation alongside §9's.
3. Push the tag. `.github/workflows/release.yml` matches it (§1's tag
   pattern already covers `-rc.N`, no separate trigger needed), builds,
   tests, and publishes a GitHub Release marked **pre-release**
   (`--prerelease`) with the build attached — for stakeholder/user
   smoke-testing, without touching `main`.
4. Iterate (`rc.2`, `rc.3`, ...) as needed — each its own tag, never
   overwriting a prior one, per §7.4.
5. Once satisfied: set `VERSION` to the final `X.Y.Z` (no suffix),
   commit, and proceed through the ordinary Release Requirements (§5) —
   the RC tags remain in the repository's history and on GitHub as a
   permanent record of what was actually tested before release, never
   deleted.

## 9. Hotfix Workflow

**Trigger:** a confirmed defect in an already-released, already-tagged
version, severe enough not to wait for the next regular release (severity
triaged via `.github/ISSUE_TEMPLATE/bug_report.md` and Technical Review).

1. **Branch:** `hotfix/vX.Y.Z-<slug>`. Cut from `main` if patching the
   *latest* release (`main` sits at the latest release's own tag
   whenever no newer release has since merged — confirmed true of this
   repository today). Cut explicitly from the affected release's own tag
   (`git checkout -b hotfix/... vX.Y.Z`) if `main` has since moved past
   it.
2. **Scope discipline:** the branch contains only the minimal change the
   fix requires — no unrelated feature work, no opportunistic
   refactoring alongside it. The same "found and fixed only if it blocks
   completion" discipline this project already applies within a Work
   Package, applied here at branch scope.
3. **Gates:** identical to any other branch — Build Gate, Test Gate, `CI
   Gate`, Technical Review Gate — none is weakened or skipped for a
   hotfix. What is proportionate is the *documentation*: a short
   Implementation Report is sufficient; the full multi-document
   release-readiness package (§5.5) is not required for a
   single-purpose fix.
4. **Version:** bumps **PATCH only** — `vX.Y.(Z+1)`. Never MINOR, never
   MAJOR; a hotfix by definition adds no new capability.
5. **Merge:** a pull request from `hotfix/...` into `main`, the same
   Merge Requirements (§3) as any other branch.
6. **Tag:** cut on `main`, post-merge, exactly like a regular release —
   no shortcut, no exception (unlike the RC process's own single
   disclosed exception in §8).
7. **Forward-merge requirement — not optional.** After the hotfix ships,
   the identical fix is merged (or cherry-picked) into whatever release
   branch is currently active, so the next regular release does not
   silently reintroduce the defect the hotfix just closed. This is named
   explicitly because an omitted forward-merge is the single most common
   way a hotfix process quietly fails in practice, in any project, not
   only this one.

## 10. Rollback Procedure

**Governing principle**, already established (Governance §7.4): a
pushed tag is never moved, recreated, or deleted. Rollback in this
project is always forward — a new version, never a rewritten history.

| Scenario | Procedure |
|---|---|
| Defect found **before** the tag is pushed | Trivial: do not push. Fix on the release/hotfix branch and re-run the release process. Nothing was ever public; no rollback is needed. |
| Defect found **after** the tag is pushed, not severe enough to withdraw the release | The standing, default remedy: cut a hotfix (§9). |
| Defect severe enough that the tagged release should not be recommended for continued use | (a) The tag and its commit are never touched. (b) The **GitHub Release's own description** (published by `release.yml`) is edited to state the release is superseded and link the fix once available — the one narrow exception to "never alter," since it changes prose about the release, not the release's own content or tag. (c) An operator or user needing a known-good build always has one: every tagged release's build output is durably attached to its own GitHub Release (§5.8) — for this project's desktop-application shape, "rollback" means running the previous version's own published build, not a data migration or server redeploy. (d) The fix ships via the Hotfix Workflow (§9) as soon as possible. |

**What this procedure deliberately does not cover:** a user's own
locally-persisted project data (`IPersistenceStore`) is outside a
release-engineering procedure's scope entirely — nothing here claims to
roll back a user's own data to a pre-upgrade state.

## Evidence & Findings

Found while researching this Work Package's own branching/tagging
history — each disclosed here, not silently corrected, per this
project's own established convention:

1. **The `v0.10.0` tag deviates from Governance §7 as written.**
   `v0.10.0` resolves to commit `0f125a3` ("Release: TempestOS v0.10.0…"),
   the last commit **on the feature branch**, one commit *before* the
   merge into `main` (`57601eb`) — confirmed directly (`git rev-parse
   "v0.10.0^{commit}"` vs. `git rev-parse main` at the point this branch
   was cut). This contradicts §7.1 ("only cut from `main`, never from a
   feature branch") and §7.3 ("must pass on `main` itself… immediately
   before tagging") as literally written. Checked against every other
   release tag: `v0.4.0`–`v0.7.0` and `v0.8.0` all correctly resolve to a
   commit on `main` (the merge commit itself, or one after it); `v0.9.0`
   resolves to a direct `main` commit for the already-disclosed reason
   that no real feature branch existed that release (`PROJECT_STATUS.md`).
   **`v0.10.0` is the one genuine, previously-undisclosed instance.** Per
   §7.4, the tag itself is not moved — this finding is the direct reason
   §5.1 and §1 of this document state the "cut from `main`, post-merge"
   rule explicitly rather than assuming it was already being followed.
2. **`scripts/new-release.ps1`'s release-notes check was stale**, reading
   `docs/releases/v$Version.md` — a path convention every release from
   `v0.6.0` onward abandoned in favour of `docs/releases/v$Version/Release
   Notes.md`. Never actually exercised (no release since `v0.6.0` has
   been cut through this script), so it never surfaced. Found and fixed
   in place this Work Package, per this project's established "found and
   fixed, not merely disclosed" convention for a genuine pre-existing
   defect.
3. **`scripts/new-release.ps1` lacked `-p:TreatWarningsAsErrors=true`
   parity with `.github/workflows/ci.yml`** — a local release build could
   in principle succeed under a laxer check than the CI pipeline (`WP
   11.1A`) enforces. Fixed in place.
4. **No pull request template, branch protection, or `CODEOWNERS` ever
   existed.** Not a defect — pull requests were never part of this
   project's workflow before `.github/workflows/ci.yml` gave a pull
   request's own required status check somewhere to attach to (`WP
   11.1A`). Closed by this Work Package's own deliverables (§2, §4).

## Verification

**Internally consistent.** Every job name, file path, branch pattern,
and version convention this document cites was cross-checked directly
against the file that defines it, not assumed:

| Claim | Verified against |
|---|---|
| Required status check is named `CI Gate` | `.github/workflows/ci.yml`, `jobs.gate.name` |
| `TreatWarningsAsErrors=true` used identically in CI, release publishing, and the release script | `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `scripts/new-release.ps1` — all three, `-p:TreatWarningsAsErrors=true` |
| Release notes path `docs/releases/vX.Y.Z/Release Notes.md` | Confirmed against the real, current repository layout (`docs/releases/v0.10.0/Release Notes.md`) and matched in `scripts/new-release.ps1` and `.github/workflows/release.yml` |
| Tag pattern `v*.*.*` covers final, hotfix, and RC tags in one pattern | Traced through GitHub's own tag-filter glob semantics (§8/§9 examples: `v0.11.0`, `v0.10.1`, `v0.11.0-rc.1`, all matched) in `.github/workflows/release.yml` |
| Feature-branch naming `feature/vX.Y.0-<slug>`, cut from `main` at the prior tag | Confirmed against `git log --all --graph` for `v0.5.0` through `v0.10.0` |
| Three-tier sign-off (Architecture / Technical Review / Product Approval) | Matched exactly against Engineering Governance §9, no new tier introduced |

**Aligns with the `WP 11.1A` CI pipeline.** Every gate this document
defines resolves to `.github/workflows/ci.yml`'s own `CI Gate` check;
`.github/workflows/release.yml` reuses the identical SDK-pinning
(`global-json-file`), runner-pinning (`windows-2022`), and
warnings-as-errors approach `WP 11.1A` already established, rather than
introducing a second, inconsistent build convention.

**Supports reproducible releases.** Every release's own evidence is
reconstructible from the repository alone: `VERSION` and Release Notes
are committed; the `CI Gate` run is tied to a specific commit; the tag
itself triggers an *independent second* Build Gate/Test Gate run
(`release.yml`), against the tagged commit, not merely trusting whatever
CI run happened earlier on the branch. A release is not "shipped" on a
human's word that a script printed "RELEASE SUCCESSFUL" — it is shipped
once `release.yml` has itself passed against the pushed tag.

**Requires no manual step that could invalidate release evidence.** The
one irreducibly manual step is the go/no-go decision itself — Product
Approval choosing to merge, push, and tag — and Governance §9 already
assigns that decision to a human tier deliberately, not as a gap to
close. Every *technical* claim behind that decision (build succeeded,
tests passed) is machine-verified twice, independently, by two separate
workflow runs (`ci.yml` on the branch, `release.yml` on the tag) — no
single local run, and no human transcription of a local run's output,
is ever the sole evidence for a release.

## What This Work Package Deliberately Did Not Do

- Did not configure any GitHub repository setting — §4's table is a
  recommendation for a repository administrator, per this Work
  Package's own explicit constraint.
- Did not extend `scripts/new-release.ps1` to automate hotfix or
  release-candidate tagging — both remain documented `git`/script-hybrid
  procedures (§8, §9), not scripted end-to-end, since both are
  exceptional paths this project has not yet exercised even once; adding
  automation for a procedure with zero real usage would be building
  ahead of demonstrated need, the same discipline this project already
  applies elsewhere (Security Principle 7).
- Did not retroactively correct the `v0.10.0` tag — cannot, per
  Governance §7.4, and would not if it could; disclosed instead (Evidence
  & Findings, above).
- Did not modify any ADR — none of this Work Package's decisions meets
  Engineering Governance §5's ADR criteria; this is engineering-process
  tooling, not a platform architectural decision.
- Did not begin any Work Package beyond `WP 11.1B`.
