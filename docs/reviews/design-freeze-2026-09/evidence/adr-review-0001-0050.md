# ADR Review — ADR-0001 through ADR-0050 (Design-Freeze Evidence)

Review date: 2026-09-08
Scope: `docs/adr/ADR-0001-*.md` through `docs/adr/ADR-0050-*.md` (50 ADRs), cross-checked against `docs/governance/Architecture/ADR Register.md` and source under `src/`.
Method: each ADR's own file was read for its Decision/Status/Consequences text; "Implemented in code?" was checked by grepping `src/` for the key type or term the ADR names, citing one representative `file:line`. Verdicts are this reviewer's judgment for a design freeze of a **single-user, locally-trusted engineering-consultancy desktop system of record** (per the `v1.0.0` re-scope referenced in `ADR-0146`), not a re-statement of the ADR's own claimed status.

Verdict key:
- **STRUCTURAL COLUMN** — a decision any re-implementation must keep; it defines the product.
- **KEEP** — sound and cheap; keep as is.
- **KEEP-BUT-SIMPLIFY** — sound intent, over-built implementation.
- **REVISIT** — questionable for a single-user consultancy desktop, or contradicted by later ADRs/code.
- **DROP** — speculative or superseded; no longer serves the product.

## Patterns across 0001-0050

1. **The platform-service-fatal / module-isolated failure split (ADR-0013) is reused verbatim, twice.** Background services (ADR-0021) and plugins (ADR-0025) both extend ADR-0013's exact reasoning to a new component category, rather than inventing a new failure policy each time — one rule, three applications, no drift found in code.
2. **"Reuse the Event Bus, don't build a second pub/sub" is stated three times.** ADR-0022 (Navigation), ADR-0032 (Navigation registration), and ADR-0046 (Notifications) all deliberately route through the existing `IEventBus` rather than invent a new dispatch mechanism — though ADR-0046 ends up re-implementing `EventBus`'s own dispatch loop internally because C# generic constraints block literal delegation.
3. **The composition-root "construct it directly, register via `AddInstance`" idiom (ADR-0009) is reused repeatedly.** First for Configuration/Logging, then Diagnostics (ADR-0039), then again for ADR-0146's `Microsoft.Extensions.Logging` bridge — a stable, validated idiom rather than a one-off.
4. **Three ADRs in this range are stale relative to current code with no amendment recorded on the ADR itself.** ADR-0016 claims `Tempest.Core.Hosting` is "retained" — it no longer exists anywhere in `src/`. ADR-0033/ADR-0035 (`TempestShell`, `IPage`) were concretely deleted by ADR-0101 and superseded in substance by the Workspace/Desktop architecture (ADR-0062, ADR-0092, the ADR-0067 kind-keyed registration family), but their own Status sections still just say "Accepted." ADR-0043's identity mechanism was gutted by ADR-0146 without a reciprocal amendment note on ADR-0043 itself.
5. **REST API (ADR-0047–0049) and Licensing (ADR-0050) were built for a distribution model the product never had, and are now frozen.** ADR-0146 states plainly: "nobody calls its REST API from outside the sample harness... nobody has ever been handed a licence file." Both moved wholesale to `src/Frozen`, unbuilt and unshipped as of this freeze, kept only so the design isn't lost if a paying client ever asks.
6. **Every real caller of the frozen REST/Licensing layers was that layer's own sample module.** `ApiSampleModule` and `LicensingSampleModule` were deleted in the same Work Package as the freeze — the only evidence either capability ever worked was self-referential.
7. **The plugin platform (ADR-0025, ADR-0026, and the later trust model ADR-0107–0112) was built for a third-party plugin marketplace that never materialized.** ADR-0146 froze the loading/trust half but deliberately kept manifest discovery live, reasoning that reading the plugin drop folder "has no attack surface of its own" and is what a real future plugin capability would be rebuilt on.
8. **Identity narrowed toward the product's real shape while authorization stayed fixed.** ADR-0043 went from "local, extensible, config-sourced multi-role identity" to "one OS-derived session principal, two roles" (ADR-0146) — correcting toward a genuinely single-user product — while ADR-0044's single-enforcement-point authorization design was left completely untouched through that same change, evidence it was scoped correctly the first time.
9. **Two otherwise-sound decisions disclose their own incompleteness in their own text or in code comments.** ADR-0040's promised Reporting→permission/audit/notification integration has only ever been shown in a sample module, never a production caller. ADR-0046's Notification dispatcher duplicates the Event Bus's dispatch loop rather than thinly wrapping it.
10. **Persistence, audit, and authorization (ADR-0041, ADR-0044, ADR-0045) are the most durable stratum in this range.** None of it was touched by the platform-trim freeze, and ADR-0041's backend swap (file-per-key → SQLite/WAL, ADR-0144) proves the shared abstraction — not any specific storage engine — is the real structural decision.
11. **The v0.4.0 release-planning block (ADR-0020–0030, all dated 2026-07-23 to 2026-07-25) is almost entirely "architecture only, decided before code" by its own Status text**, and every one of the ten was later implemented with zero deviation found in this review — deciding in writing ahead of code is itself a recurring, apparently effective, pattern in this range, not just an individual ADR's choice.
12. **ADR-0005 (custom DI container) is the weakest cost/benefit case among the early infrastructure decisions.** It was reaffirmed once already, in ADR-0146, on an inertia rationale ("nothing here has found a reason to replace") rather than a demonstrated gap in `Microsoft.Extensions.DependencyInjection` — notable because that same ADR adopts Microsoft's own abstractions for Configuration and Logging in the same breath.
