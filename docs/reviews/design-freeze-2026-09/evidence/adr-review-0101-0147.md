# ADR Review: ADR-0101 through ADR-0147

Design-freeze review, 2026-09. Evidence-gathering pass over docs/adr/ADR-0101 .. ADR-0147.

No dedicated register/index file was found directly under docs/adr/ (checked README/index/register variants). A repository-wide search did find `docs/governance/Architecture/ADR Register.md`, which carries a Status/Notes/Date/Verified table for every ADR. It was consulted as a cross-check, with two findings recorded in "Patterns" below: (1) its own "Last Reviewed" metadata narrative stops at ADR-0144 ("144 ADRs, 144 register rows, no gaps") even though the table itself has been extended to 147 rows including ADR-0145/0146/0147; (2) the table rows for ADR-0143 and ADR-0147 are missing their trailing Date and Verified columns (4 pipe-delimited fields instead of the 6 every other row has), so neither carries an explicit "Verified" attestation in the register as it stands. Status per ADR text below is drawn primarily from each ADR file's own Status section, not the register.

Caution on stray copies: this working tree contains a nested legacy copy of much of `docs/` and `tests/` under `TempestOS-Core/`, an `archive/docs-2026-09/` snapshot, and at least one stray agent worktree under `.claude/worktrees/`. None of these count as the live/shipped tree. Two evidence rows below (ADR-0105) were corrected after an initial grep hit turned out to resolve only to one of these stray copies, not the live path — a caution worth restating: "Implemented in code?" below cites only files under the live `src/`/`tests/`/`docs/` trees at the repository root.

Method: for each ADR, the key type/term it names was grepped across `src/` to determine implementation status; one representative file:line is cited per row. This is a terseness-first evidence table, not a full code review — absence of a hit is reported as such rather than assumed. Two independent passes were made over ADR-0101–ADR-0110 (one by the lead reviewer, one by a delegated sub-review) and reconciled where they disagreed; the table below reflects the reconciled, more thoroughly-verified version.

## v0.17.0 substrate ADRs — detail

**ADR-0144 (SQLite persistence store).** (a) The ADR's own Related Documents section states it "Supersedes ADR-0041 in part (the storage backend it chose; the `IPersistenceStore` shape it drafted stands unchanged) and ADR-0053 in part (its premise that the one persistence abstraction has no query and no transaction, which the Engineering Data Model was built to work around)." It retires the file-per-key `PersistenceStore` (in place since WP 6.4) as the *default* backend, citing five defects: no fsync, O(N) directory scans, no query, no multi-key transaction, and no cross-process lock. (b) The replacement is complete in code today. `SqlitePersistenceStore.cs` implements `IPersistenceStore`/`IBinaryPersistenceStore`/`IQueryablePersistenceStore`, and its pragma-application method issues, in the load-bearing order the ADR specifies, `PRAGMA busy_timeout=5000; journal_mode=WAL; synchronous=FULL; foreign_keys=ON`. `IPersistenceStore.cs` is confirmed unchanged in shape. The old file-per-key class, `PersistenceStore.cs`, still exists in `src/` — exactly as the ADR itself specifies: deliberately retained for one release as the `files` backend (selectable via `Persistence:Backend`) before deletion in v0.18.0; its continued presence is evidence of a correctly-scoped, not incomplete, migration. (c) Assessment: **complete** — pragmas, interfaces, and the deliberate one-release retention of the old backend all match the ADR's text exactly.

**ADR-0145 (one transactional store; in-memory repositories are caches).** (a) The ADR states it "Supersedes ADR-0113 in part (its four-writer decomposition of an engineering object's durable state; the state record's own shape and its migration rules stand unchanged) and ADR-0116 in part (its write ordering — memory first, then disk, with a compensating undo; everything else ADR-0116 decides about the boundary and the acting principal stands)." It replaces the multi-writer compensation apparatus (`MutationRollbackPoint`, `AttachmentWriteIntentStore`, `AttachmentContentReconciliationService`, `InMemoryEngineeringDocumentStore`) with one transaction, built directly on ADR-0144's SQLite store. (b) Verified as complete. `EngineeringDomainContext.ExecuteWriteAsync` is the single write path: it takes the domain write lock, runs `ExecuteInTransactionAsync`, and only after that commits invokes `afterCommit` — still inside the lock hold — matching the "project, commit, apply" ordering the ADR mandates. `EngineeringObjectFactory.cs` shows the repository is populated strictly after commit (the `TD-147` fix). A grep for `InMemoryEngineeringDocumentStore` across `src/` returns no matches, confirming it was deleted rather than kept alongside the fix; `InMemoryEngineeringObjectRepository`/`InMemoryEngineeringRelationshipRepository` still exist as the cache types the ADR names, and direct inspection of `EngineeringObjectBase.cs`/`EngineeringObjectBase.State.cs` shows the rollback machinery (`MutationRollbackPoint`, `RollBackOnFailureAsync`, `AttachmentWriteIntentStore`) survives only in XML-doc commentary explaining the old design, not as live classes — `EngineeringObjectBase.cs` is 821 lines against the ADR's own claimed 817 (negligible drift), and `EngineeringObjectBase.State.cs` is exactly the claimed 203. (c) Assessment: **complete** — the write path, the after-commit registration pattern, and the deletion of the fourth writer are all directly visible in the current tree.

**ADR-0146 (Configuration/Logging on Microsoft.Extensions; plugin trust/REST/licensing frozen; one session principal).** (a) This ADR does not supersede a numbered ADR in the usual sense — instead it explicitly "Marks Frozen: ADR-0047, ADR-0048, ADR-0049, ADR-0050, ADR-0107–ADR-0112" (REST API, Kestrel adoption, and licence-validation-as-host-gate ADRs, plus the plugin dependency/signing ADRs), moving their subject code out of the build rather than rewriting it in place. It also narrows ADR-0043's identity model from "local, extensible" to "one session, OS-derived," and leaves ADR-0044/ADR-0045 standing. (b) Both halves are verifiably complete in the current tree — not just Decision A (the freeze, described as implemented "in this commit") but also Decision B (Configuration/Logging/Identity/Audit, described in the ADR's own text as merely "decided here... implemented by WP 17.2A part 2" as a *future* work package). `src/Frozen/` contains exactly the three folders named — `Tempest.Core.Api` (incl. `RestApiHostedService.cs`, `ApiEndpointRegistry.cs`), `Tempest.Core.Licensing` (incl. `LicenseValidator.cs`, `LicenseProvider.cs`), and `Tempest.Core.Plugins` (trust store, signature verifier, trust tiers, component-principal/denied-type registries, assembly loader — no manifest-discovery types, matching the ADR's carve-out) — and none of the three are referenced from `src/TempestOS.slnx`. Separately, live `src/Tempest.Core/Configuration/MicrosoftExtensionsConfigurationSource.cs`, `Logging/RollingFileLogSink.cs`/`TempestLoggerProvider.cs`, and `Identity/SessionPrincipal.cs` (defining `ISessionPrincipal`/`SessionPrincipal` with `IdentityId`/`DisplayName`/`SessionRole Role` exactly as specified) are all present, meaning Decision B has also already landed, ahead of what the ADR's own text implies about sequencing. Live `src/Tempest.Core/Plugins/` retains exactly the carve-out the ADR promises: `PluginManifest.cs`, `PluginDependency.cs`, `PluginRegistryState.cs` (whose own remarks explicitly cite being "Frozen by ADR-0146" for the states it no longer produces) and `PluginManifestDiscoveryService.cs`, with none of the loading/trust/signing types. (c) Assessment: **complete** (both Decision A and Decision B, the latter apparently landed already despite the ADR text framing it as a separate future work package).

**ADR-0147 (dimension-vector units; generic `Quantity` as typed facade).** (a) The ADR states in its Related Documents that "ADR-0054 (superseded in part by this decision — see its own Status line)" — specifically ADR-0054's exact-same-unit arithmetic/comparison rule is reversed for `Quantity<TDimension>` — while explicitly *extending, not superseding*, ADR-0125 (affine units) via the new `TemperatureDelta` dimension, and leaving ADR-0143's `ReferencePin` requirement as the reason `UnitsNet` was rejected as an alternative. (b) Verified as complete. The runtime dimension vector is `public readonly record struct Dimension` in `Dimension.cs`, with the named vector catalogue in `Dimensions.cs` as the ADR specifies. The non-generic runtime-dimensioned quantity is `public readonly struct Quantity` in `QuantityVector.cs` (not `Quantity.cs`, which instead holds the generic facade `Quantity<TDimension>` with `ToQuantity()` and static `FromQuantity(Quantity)` — the two-directional bridge the ADR calls "Decision 4"). `UnitDefinition.cs` defines the runtime counterpart to `Unit<TDimension>`. A typed facade example, `Force.cs`, shows `public sealed class Force : IDimension` exposing `public static Dimension Vector => Dimensions.Force;` — confirming individual quantity types are thin marker types over the vector, exactly as claimed. All eight new dimensions the ADR lists (`SecondMomentOfArea`, `SectionModulus`, `Frequency`, `TemperatureDelta`, `ElectricCurrent`, `Voltage`, `Resistance`, `ElectricCharge`) have corresponding files present in `src/Tempest.Core/UnitsAndQuantities/`. (c) Assessment: **complete** — dimension-vector struct, non-generic `Quantity`, `UnitDefinition`, the generic facade's bridging methods, and a concrete typed-facade example are all directly verified.

## Patterns across 0101-0147

- **The v0.17.0 substrate rewrite (ADR-0144–0147) is real and complete, not aspirational.** All four are verified directly against `src/Tempest.Core/Persistence`, `src/Tempest.Core/EngineeringDomain`, `src/Frozen`, and `src/Tempest.Core/UnitsAndQuantities` — pragmas, transaction ordering, frozen-folder contents, and the dimension-vector types all match what each ADR claims, with no gap found. These four are the ADRs a re-implementation must treat as ground truth for the current substrate.
- **A recurring reversal chain runs through the whole range**: ADR-0041/0053 (file-per-key persistence, no query/transaction) → superseded in part by ADR-0144 → whose transaction is then spent by ADR-0145, which itself supersedes ADR-0113 (four-writer decomposition) and ADR-0116 (write-before-commit ordering) in part. Separately, ADR-0054 (exact-same-unit arithmetic) → extended by ADR-0125 (affine units/temperature) → both partly reversed/extended again by ADR-0147 (same-dimension auto-conversion, `TemperatureDelta`). Each link in both chains explicitly names what it keeps and what it changes — the discipline of partial, cited supersession (not silent rewrite) holds throughout.
- **A whole speculative plugin-marketplace substrate (ADR-0107–ADR-0112) was built, then frozen wholesale by ADR-0146** once the product's actual scope (a single-user consultancy desktop tool) was named plainly. `src/Plugins/` (the runtime drop folder) still holds only a README; ADR-0146's own text states the ~13K lines of production/test code "adjudicate trust for plugins that do not exist." This is the single largest "built ahead of demonstrated need" episode in the whole 0101-0147 range, and the project's own later ADR reached the same DROP verdict this review reaches for ADR-0107–0112.
- **ADR-0116 is a live documentation-drift case**: its own Status section discloses only the ADR-0145 write-ordering supersession, but ADR-0146 (same day, 2026-09-08) has already replaced its concrete `ISessionPrincipalSource`/`LocalSessionPrincipalSource` mechanism in code with `ISessionPrincipal`/`SessionPrincipalSource`/`SessionRole`. ADR-0116's text has not been updated to say so — worth a retroactive amendment note.
- **ADR-0124 has the same kind of drift, one ADR later**: its own storage envelope (`BearingDocumentDto`) no longer exists in code, superseded in effect by ADR-0126's shared reference-data layer the very next day, but ADR-0124's own Status section carries no note of it.
- **The `docs/governance/Architecture/ADR Register.md` file itself shows drift at exactly this range's most active edge**: its "Last Reviewed" narrative metadata stops at "144 ADRs... WP 17.1A" even though its own table was later extended to 147 rows, and the table rows for ADR-0143 and ADR-0147 are missing their Date/Verified columns that every other row (including ADR-0144/0145/0146) carries — the register's own bookkeeping fell slightly behind at the same moment the substrate itself was being rewritten fastest.
- **A recurring, load-bearing idiom across the Group A-F "P0x" business/engineering programmes (ADR-0126, 0128, 0129, 0132, 0136) is one shared `ReferenceDataCatalog<TDefinition>` lifecycle reused rather than re-invented per domain** — cheap to extend, consistently verified in code (Bearings, Rules, Decision Trees, Business Governance, Commercial Intelligence, Engineering Assets all sit on the identical base type).
- **A second recurring idiom is enforcement-by-reflection-test over a namespace** (ADR-0135, 0137, 0138, 0140, 0142) — banning forbidden verbs/authority-sounding names or foreign-namespace property types. All five are genuinely implemented as tests, not merely documented aspirations, but this is real ongoing machinery (and, per ADR-0135's row, arguably disproportionate machinery) for a single-developer, single-user product.
- **P03 (Commercial Intelligence) and P06 (Knowledge) are fully built and tested but functionally invisible**: `Tempest.Core.CommercialIntelligence` and `Tempest.Core.Knowledge` have zero references anywhere under `src/Tempest.Workspace` or `src/Tempest.Desktop` — registered in the DI host and covered by unit tests, but unreachable from the UI a single user would actually touch. P05 (Engineering Assets, ADR-0136-0138) is the one exception in this cluster with real desktop/workspace wiring.
- **Two governance/process ADRs in the 0101-0110 range (ADR-0105's Vocabulary Register, ADR-0106's Engineering Readiness Review) named companion artifacts that do not exist, or no longer exist, in the live tracked tree** — the register and its consistency test are found only in an archived snapshot or a stray worktree copy, and the Readiness Review's own cited Architecture document is absent entirely, with no visible repeat sign-off after an early release. Both are process debt: promised once, not visibly maintained since.
- **ADR-0103/0104 (composition-root decomposition, delegate-only Desktop wiring) are sound, cheap "don't over-engineer" decisions that mostly held**, but ADR-0103's own `MainWindow` motivating example regrew past its post-decomposition size per the v1.0.0 Release Candidate Audit (`TD-109`, open) — the pattern didn't structurally prevent the regression it was created to stop.
- **Money (ADR-0130), lead times (ADR-0133), and units (ADR-0125/0147) all share one refusal discipline**: never silently convert or default across a boundary that isn't actually equivalent (currency, working-day vs. elapsed time, affine vs. non-affine units) — throw instead. This is the single most consistent, cheapest-to-keep cross-cutting design principle found across the whole 0101-0147 range and the strongest STRUCTURAL COLUMN candidate that isn't already a storage/identity decision.
- **The plugin-trust freeze (ADR-0146) and the Business-Authorisation ceremony (ADR-0130) sit at opposite ends of the same lesson**: the project has already demonstrated, once, that it will retroactively strip out over-built machinery for a capability nobody uses (plugins) — the same lens applied to `BusinessAuthorisation`'s multi-stakeholder ceremony, or to the P06 knowledge layer with no UI surface, would likely reach the same conclusion the project already reached for plugins.
