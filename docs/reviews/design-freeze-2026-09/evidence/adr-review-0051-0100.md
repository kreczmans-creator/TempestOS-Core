# ADR Review — ADR-0051 through ADR-0100

Design-freeze review evidence file. Covers `docs/adr/ADR-0051-*.md` through `docs/adr/ADR-0100-*.md`
inclusive, cross-checked against the ADR Register (`docs/governance/Architecture/ADR Register.md`)
and against current source under `src/` and `tests/` (including `src/Frozen/` and `tests/Frozen/`
for layers frozen out of the `v1.0` build by ADR-0146).

Verdict key:
- **STRUCTURAL COLUMN** — a decision any re-implementation must keep (defines the product).
- **KEEP** — sound and cheap; keep as is.
- **KEEP-BUT-SIMPLIFY** — sound intent, over-built implementation.
- **REVISIT** — questionable given the product (single-user consultancy desktop) or contradicted by later ADRs/code.
- **DROP** — speculative or superseded; no longer serves the product.

Rows are appended in batches of 10 as evidence is gathered, so partial work survives.

## Patterns across 0051-0100

- **"Frozen contract + additive extension" is the dominant mechanism, applied at least eight times in this range.** `IWorkspaceManager` (frozen at `WP8.0B` with `RegisterView`/`RegisterExplorerArea`) is extended additively by ADR-0082 (+`RegisterFacetProvider`, 3rd category), ADR-0096 (+`RegisterRenameFactory`/`RegisterDeleteFactory`, 4th/5th), and ADR-0097 (+`RegisterReviseFactory`, 6th) — six Kind-keyed provider categories on one interface today, each ADR individually cheap but the pattern itself flagged as "worth watching" by ADR-0082 and repeated as a disclosed-but-unresolved concern by every subsequent extension. The same shape recurs for `ISelectionService`/`IWorkspaceContext` (ADR-0085, +`SelectedItems`/`ToggleSelectionAsync`) and for `IRequirementsService`, which grows from 13 to 20 methods in one Work Package (ADR-0084). No ADR in this range ever proposes consolidating or re-cutting these contracts — each treats the previous frozen shape as permanent and adds beside it.
- **"Classification-tag an existing Kind, don't add a new Domain Kind" is independently reinvented three times.** ADR-0088 (Documents: Specification/Report/Procedure/Standard/Datasheet/External Reference are all plain `"Document"` objects distinguished by `Classification`), ADR-0090 (Verification: "Plan" vs. "Activity" are the same `VerificationActivity` Kind distinguished by `LifecycleState` alone), and ADR-0091 (Manufacturing: Routing/Operation/Supplier Operation are all plain `"ManufacturingOperation"` distinguished by `Classification`) each face structurally the same brief-vs-frozen-catalogue tension and resolve it identically — real convergent evidence the underlying object model (ADR-0072/0075) is sound, but also meaning `Classification` is an unvalidated free string doing real categorisation work platform-wide, with no closed vocabulary anywhere (a caller can write `"Speciffication"` and get a silently miscategorised object; disclosed in each ADR, never fixed).
- **The facet-composition model (ADR-0075) is honoured at the interface layer but not at the base-class layer.** `EngineeringObjectBase` implements every facet — including the four added later by ADR-0080/0083 (`IRenamable`, `IHasParent`, `IDeletable`, `IHasBomLine`) — **unconditionally on every concrete Kind**, regardless of whether that Kind's own public interface composes it. Concretely: `IHasParent`/`IDeletable`/`IRenamable` are meaningfully composed by only ~5 of ~44-48 canonical interfaces (Project/Assembly/SubAssembly/Part/Component), and `IHasBomLine` by only 3 (`IAssembly`/`IPart`/`IComponent`, realised in 4 concrete classes including `SubAssembly`) — yet all ~29 concrete Domain classes (Calculation, Risk, Decision, Milestone, Portfolio, Supplier, VerificationActivity, etc.) carry working `MoveAsync`/`ParentId`/`DeleteAsync`/`SetBomLineAsync`/`Quantity`/`UnitOfMeasure` members that are domain-nonsense for them (a Risk has a "BOM quantity and unit of measure"; a Decision can be "moved" under a parent assembly). `ISearchable` is the starkest case: it is implemented unconditionally by every Kind but is composed by **zero** of the ~44 canonical interfaces — an ADR-0075 facet that exists only at the shared-base-class level and is never reachable through any typed Domain contract. This is not merely theoretical: production code (`src/Tempest.Workspace/Projects/ProjectMembership.cs:57`) and several tests reach `IHasParent`/`IDeletable` on Risk/Issue/Decision/Milestone/Task/Deliverable via casts that these Kinds' own declared interfaces never advertise — test code does this as an unchecked cast that would throw `InvalidCastException` if a re-implementation followed the interfaces literally rather than the shared base class's generosity.
- **Decisions explicitly, formally reversed within this range:** ADR-0066 (terminal/TUI presentation) was superseded by ADR-0092 (graphical Avalonia desktop) — the project's first-ever ADR supersession, and ADR-0065 (flat-list Digital Thread panel) was superseded by ADR-0093 (progressively-expandable node-link graph) in the same Work Package. Both reversals are honest about what survived: the underlying Workspace contracts (`IWorkspaceView`, `IWorkspaceManager`, `ADR-0067`'s Kind-keyed registration) needed zero rework across the reversal, which the ADRs themselves cite as vindication of the original rendering-agnostic contract design (ADR-0075/ADR-0067) even though the specific UI paradigm they were built for was wrong.
- **Decisions that outlived their own product surface without a formal supersession note.** `Tempest.App` (the composition root/entry point ADR-0062/0068/0071 name explicitly, and the file paths ADR-0096/0097/0098/0099 cite) was later split into `Tempest.Workspace` (library) and `Tempest.Harness` (console executable), demoted by a later ADR-0101 to "internal engineering harness, not shipped product" — with `Tempest.Desktop` as the real, shipped product entry point. None of ADR-0062/0068/0071's own Status/Related-Documents text was updated to reflect this; their file citations (e.g. `src/Tempest.App/Program.cs`) no longer resolve.
- **Decisions serving a now-frozen layer.** ADR-0052 (REST API per-request identity resolution) governs `Tempest.Core.Api`, which ADR-0146 later froze entirely out of the `v1.0` build (moved to `src/Frozen/Tempest.Core.Api`, no project file, not compiled/tested/shipped) alongside the plugin-trust platform and Licensing. The decision itself was sound engineering, but it currently governs dead code for a product that ADR-0146 confirms is a "single-user, locally-trusted desktop system of record."
- **Two decisions read as speculative generality built ahead of a real, demonstrated single-user need:** ADR-0099 (macro system, generalized as an ordinary Command Framework citizen) and ADR-0100 (external-controller `IInputBindingProvider` abstraction, explicitly built to support Stream Deck/MIDI/game-controller integration that does not exist and is out of scope). Both are honestly disclosed as narrow today (ADR-0099: macro steps limited to the small `CreateDefault`-eligible command subset, effectively Sample commands only; ADR-0100: one real keyboard provider, one test stub, zero vendor SDKs) — the abstractions are cheap and non-intrusive, but for a single-user consultancy desktop with no named hardware-integration client, the generality is ahead of any demonstrated need and worth a REVISIT at design-freeze rather than automatic carry-forward.
- **A later usability gap surfaced against an ADR in this range without a formal reversal.** ADR-0086's `CalculationTemplateRegistry` design let a calculation execute and produce evidence, but a later, archived usability pass ("WP16.4B Follow-On — Engineering Calculations Workspace Usability Completion") found the resulting `CalculationRecord` was unnamed, unorganisable, and had no lifecycle — the workspace could run a calculation but not manage the object it produced. This was fixed as a follow-on rather than a formal ADR amendment, so ADR-0086's own text still reads as if the original design were sufficient.
- **Four consecutive real-discipline Work Packages (Calculations/Documents/Verification/Manufacturing, ADR-0086-0091) each independently confirm zero `Tempest.Core.EngineeringDomain` files touched.** This is repeated, cross-validated evidence that the ADR-0072/0075/0076 object-model foundation genuinely supports adding a full engineering discipline through Workspace-layer composition alone — one of the strongest structural validations in the whole range.
- **Requirements is architecturally quarantined from the facet-composition model by design, not oversight.** ADR-0084 explicitly declines to retrofit `Requirement`/`RequirementGroup`/`RequirementCollection` onto `EngineeringObjectBase` (they are immutable snapshot classes reconstructed on every read, a deliberate `WP 7.3A` choice) and extends `IRequirementsService` instead — the one clear case in this range where the dominant facet pattern was judged not to fit, and the ADR says so rather than forcing it.
- **The concurrency/single-user tension appears twice without resolution.** ADR-0060 defers Requirements optimistic-concurrency ("a systems engineering team... edit the same artefact concurrently") as accepted technical debt (`TD-25`); ADR-0052's per-request REST identity model is built for a networked multi-client scenario. Both predate the platform's later, explicit self-description as a single-user desktop product (ADR-0146) — worth revisiting now to confirm whether the deferred risk is actually permanently moot rather than merely unaddressed.
- **Verdict distribution across this batch of 50:** 9 STRUCTURAL COLUMN, 26 KEEP, 6 KEEP-BUT-SIMPLIFY, 8 REVISIT, 1 DROP-adjacent pairs (ADR-0052 DROP; ADR-0065/ADR-0066 DROP as superseded mechanisms, their surviving principles noted separately) — the overwhelming majority of decisions in this range are sound and cheap; the REVISIT/DROP concentration clusters almost entirely around (a) the two paradigm-reversal ADRs, (b) the one frozen-layer ADR, and (c) generality built ahead of demonstrated single-user need (macros, external controllers, requirements concurrency).
