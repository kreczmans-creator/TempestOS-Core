# TempestOS Substrate Audit — Design Freeze Review 2026-09

Scope: non-UI substrate layers only. Read-only audit; no build/test execution performed. Evidence is cited as file:line against the working tree at the time of this audit.

## 1. Persistence

### What exists

Three narrow contracts in `src/Tempest.Core/Persistence`, each kept deliberately small because roughly 20 test doubles across the repository implement `IPersistenceStore` alone:

- `IPersistenceStore` (`src/Tempest.Core/Persistence/IPersistenceStore.cs:8`) — `ReadAsync`/`WriteAsync`/`DeleteAsync`/`ListKeysAsync` over `(collection, key)` string values.
- `IBinaryPersistenceStore` (`src/Tempest.Core/Persistence/IBinaryPersistenceStore.cs:45`) — the byte-valued sibling, sharing collections/keys with the text store but never the same record (a key written as text reads null as bytes, and vice versa).
- `IQueryablePersistenceStore` (`src/Tempest.Core/Persistence/IQueryablePersistenceStore.cs:37`) — `ListKeysAsync(prefix)`, `ReadAllAsync`, `ReadManyAsync`, and `ExecuteInTransactionAsync` returning an `IPersistenceTransaction` (`IQueryablePersistenceStore.cs:130`) that mirrors the other two interfaces member-for-member.

Two implementations:

- `SqlitePersistenceStore` (`src/Tempest.Core/Persistence/SqlitePersistenceStore.cs:91`, 863 lines) — the default backend (`ADR-0144`). One SQLite file `tempest.db` under the configured root, one table `records(collection, key, text_value, blob_value, updated_utc, PRIMARY KEY(collection,key))` plus a `schema_info(version)` table (DDL at `SqlitePersistenceStore.cs:570-585`, `SchemaVersion = 1` at line 117). Every connection applies `busy_timeout=5000; journal_mode=WAL; synchronous=FULL; foreign_keys=ON` (`SqlitePersistenceStore.cs:630-639`); the ordering (`busy_timeout` first) is called out as load-bearing in a code comment (lines 619-629). Cross-process safety is a `tempest.lock` file held open with `FileShare.None` for the store's lifetime (`AcquireInstanceLock`, lines 519-540); a second instance over the same root is refused at construction. Transactions use `BEGIN IMMEDIATE` (line 460) so a contending writer fails at the start of a transaction rather than partway through. `Dispose()` clears only this store's own connection pool rather than `SqliteConnection.ClearAllPools()`, called out (lines 493-500) as a fix for an `ObjectDisposedException: SQLitePCL.sqlite3` race seen in ~1 of every 4 parallel test runs when two hosts shared a process.
- `PersistenceStore` (`src/Tempest.Core/Persistence/PersistenceStore.cs:114`, 772 lines) — the file-per-key predecessor, superseded but retained behind `Persistence:Backend=files` (`SqlitePersistenceStore.BackendConfigurationKey`/`FileBackendValue`, `SqlitePersistenceStore.cs:98-108`) for exactly one release, documented for deletion in `v0.18.0` (`ADR-0144`). One file per `(collection,key)`, with percent-encoding for reserved Win32 device names/trailing dots (`EncodeSegment`, `PersistenceStore.cs:701-714`), a per-key `AsyncKeyedLock`, and write-then-atomic-rename with `FileOptions.WriteThrough` and `Flush(flushToDisk: true)` for power-loss safety (`WriteThroughAsync`, lines 528-543). `ExecuteInTransactionAsync` is explicitly not atomic on this backend — documented in capitals at lines 359-374 and enforced by a named test (below).

Backend selection is via the `Persistence:Backend` configuration key (`SqlitePersistenceStore.BackendConfigurationKey`, `SqlitePersistenceStore.cs:98`), default `"sqlite"`.

Documents/revisions are layered on top, not new storage: `EngineeringDocumentStore` (`src/Tempest.Core/EngineeringData/EngineeringDocumentStore.cs:35`, 431 lines) uses three `IPersistenceStore` collections — `EngineeringData.Documents` keyed by document Id (line 50), `EngineeringData.Revisions` keyed by `"{documentId:N}_{revisionNumber:D10}"` (doc comment near line 19; constant at line 56) so revision history is read by direct key rather than scanned, and a per-source-document references collection named `EngineeringData.References.{sourceDocumentId:N}` (`GetReferencesCollectionName`, line 93). A per-document `AsyncKeyedLock` (line 42, `_documentLock`) serialises the read-current-then-write-next sequence in `ReviseAsync` so two concurrent revises can't claim the same revision number. `CreateAsync` writes revision 1 before the document record (lines 116-136), a deliberately chosen ordering documented as closing `TD-67` — a crash between the two writes leaves an orphaned revision invisible to lookups rather than an internally-inconsistent record.

### Soundness — evidence

Tests live in `tests/Tempest.Core.Tests/Persistence` (2,810 lines across 10 files) plus fault-injection/concurrency tests that live under `tests/Tempest.Core.Tests/EngineeringDomain` because they exercise the transaction boundary through the domain layer:

- Shared-contract tests run against both backends. `QueryablePersistenceStoreTests<TBackend>` (`tests/Tempest.Core.Tests/Persistence/QueryablePersistenceStoreTests.cs:19`) is instantiated once per backend (`FileBackedQueryablePersistenceStoreTests` / `SqliteBackedQueryablePersistenceStoreTests`, lines 232/235) via `IPersistenceStoreBackend`/`PersistenceStoreBackendFixture` (`PersistenceStoreBackendFixture.cs`), so prefix listing, whole-collection reads, batched multi-key reads (>1 batch, `ReadManyAsync_BeyondOneBatch_ReadsEveryKey`, line 148), and transaction visibility are asserted identically for both stores.
- Crash-consistency / fault injection. `TransactionalWriteFaultInjectionTests` (`tests/Tempest.Core.Tests/EngineeringDomain/TransactionalWriteFaultInjectionTests.cs`, 279 lines) uses `CommitFailingPersistenceStore` (`tests/Tempest.Core.Tests/Persistence/CommitFailingPersistenceStore.cs:28`) to fail a transaction's commit after its body has run to completion — explicitly framed (lines 10-22) as the deterministic equivalent of the Work Package's stated acceptance test ("process kill between the BLOB write and the commit"). `AFailedCreation_IsNotInTheRepository_AndNothingIsOnDisk` (line 51) asserts the repository is empty and every durable collection (`EngineeringData.Documents`, `.Revisions`, and the audit collection) has zero committed keys after an injected commit failure, reading the raw store directly rather than through the domain (rationale at lines 30-33: "a repository or a rehydration pass could agree with a mutation that never landed; the raw collections cannot"). `AFailedAttachContent_LeavesNoRow_AndNoBytes` (line 85) and `ASuccessfulAttachContent_LeavesBothTheRowAndTheBytes` (line 117) cover the same property for binary attachments.
- SQLite-specific transaction tests. `SqlitePersistenceStoreTests.cs` (566 lines): `AThrowInsideATransaction_RollsBackEveryWriteItHadMade` (line 265), `AThrowInsideATransaction_LeavesTheStateBeforeItExactlyAsItWas` (line 289), `ACancelledTransaction_RollsBack` (line 311), `ReadAllAsync_ReturnsEverythingOneTransactionWrote_OrNothingOfIt` (line 330), `ATransactionHandle_IsUnusableAfterItsUnitOfWorkReturns` (line 377), `ATransactionsWrites_AreVisibleToEveryLaterReaderOnceItCommits` (line 393).
- Cross-process lock. `ASecondStoreOverTheSameRoot_IsRefusedByNameRatherThanAllowedToShare` (line 414), `AStoreOverADifferentRoot_IsNotAffectedByAnotherStoresLock` (line 426).
- Disposal / pool hygiene. `AfterDisposal_TheRootDirectoryCanBeDeleted` (line 439), `AfterDisposal_TheRootCanBeOpenedByAFreshStore_AndStillHoldsItsRecords` (line 461), `Disposal_IsIdempotent_AndEveryOperationAfterItIsRefused` (line 473).
- Concurrency at the domain boundary. `TwoHundredConcurrentMoveRaces_NeverFormAParentCycle` (`TransactionalWriteFaultInjectionTests.cs:169`) and `ADeleteCannotCommitWhileAConcurrentMoveGivesItALiveChild` (line 236) use `GatedPersistenceStore` (`tests/Tempest.Core.Tests/Persistence/GatedPersistenceStore.cs:27`) to deterministically park one transaction mid-flight and force a second writer to observe committed state rather than a stale snapshot.
- Scale/perf budget. `TenThousandKeysInOneCollection_ListAndReadAllWellInsideTheBudget` (`SqlitePersistenceStoreTests.cs:493`) seeds 10,000 keys in one transaction and asserts `ListKeysAsync` + `ReadAllAsync` together complete inside a loose 10-second budget, explicitly framed as a budget rather than a benchmark — the claim under test is "one indexed query, not 10,000 file opens" (comment, lines 494-499).
- The file backend's non-atomicity is asserted, not merely documented. `TheFileBackend_DoesNotRollBackAUnitOfWork_AndThisIsDocumentedNotAccidental` (`SqlitePersistenceStoreTests.cs:544`) writes inside a unit of work, throws, and asserts the write survived anyway.
- Hostile names. `PersistenceStoreHostileNameTests.cs` (522 lines) covers reserved Win32 device stems, trailing dots, and legacy-encoding migration for the file backend only (n/a to SQLite, which stores names verbatim per `SqlitePersistenceStore.cs:48-57`).

### Hazards observed in code

- File backend delete-ordering defect, self-documented as unresolved. `PersistenceStore.DeleteAsync` (`PersistenceStore.cs:228-253`) removes the current-encoding file before the legacy-encoding file; if the second removal fails, the stale legacy value becomes the live record again for that key. This is called out at length in the `MigrateLegacyRecordAfterCommit` remarks (`PersistenceStore.cs:601-624`) as "a defect of this store's delete ordering, pre-existing... and it is recorded rather than quietly fixed here." Only reachable on the file backend, which is scheduled for deletion in `v0.18.0`.
- File backend has no real transactions at all. `PersistenceStore.ExecuteInTransactionAsync` (`PersistenceStore.cs:376-390`) runs the unit of work directly against the store with no rollback; a mid-work failure leaves partial writes standing. This is intentional and documented, but any code path still configured with `Persistence:Backend=files` has no crash-consistency guarantee at all for multi-key writes — including the engineering-domain transactional writes exercised in section 2.
- SQLite single-writer serialization is global, not per-collection. `BEGIN IMMEDIATE` (`SqlitePersistenceStore.cs:455-460`) takes SQLite's one database-wide write lock; a long-running transaction (e.g. the 10k-key bulk seed) blocks all other writers for its duration, bounded only by the 5-second busy timeout. There is no per-collection or per-document write concurrency in the persistence layer itself — that concurrency (see section 2) is implemented one layer up as a single domain-wide write lock.
- Two backends can silently diverge in production if `Persistence:Backend=files` is left set past `v0.18.0`'s removal; no code was found in this audit that enforces or warns about that removal beyond the doc comments.

### Reusability estimate: Reusable as-is

The SQLite backend is well-isolated behind two narrow interfaces, has direct fault-injection coverage of its core durability claim (a failed commit leaves nothing), and its schema is trivial (one table, composite primary key). The file-backed `PersistenceStore` should be dropped rather than carried forward into a fresh build — it exists only as a one-release migration shim and its own code documents an unresolved defect. A fresh implementation could keep `SqlitePersistenceStore` and the three interfaces essentially unchanged; the only interface-trim candidate is `IBinaryPersistenceStore`, which exists mainly to avoid retrofitting ~20 legacy test doubles — a concern that would not apply to a fresh codebase, so it could be folded into `IPersistenceStore` directly, or kept as-is for BLOB clarity (not a soundness issue either way).

## 2. Engineering domain object model

### What exists

`src/Tempest.Core/EngineeringDomain` totals 6,766 lines: 1,270 in `Contracts/` (interfaces only) and 4,867 in `Implementation/`.

- `EngineeringObjectBase` (`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs:38`, split across `EngineeringObjectBase.cs` (821 lines) and the `EngineeringObjectBase.State.cs` partial (203 lines) — only two files, not a wide partial spread) is the single shared base every concrete Kind derives from. It implements **14 interfaces**: `IEngineeringObject` plus 13 facet interfaces — `IHasBusinessIdentifier, IHasMetadata, IHasLifecycle, IHasRevisions, IHasRelationships, ITraceable, IValidatable, IHasAttachments, ISearchable, IRenamable, IHasParent, IDeletable, IHasBomLine` (declaration at `EngineeringObjectBase.cs:38-41`). The doc comment (lines 7-12) states the design intent directly: "A concrete Kind class only ever declares the specific facets its own interface actually composes — inheriting the rest here costs nothing extra."
- **31 concrete Kind classes** derive from `EngineeringObjectBase` (28 directly; `SubAssembly : Assembly`, `Baseline : Configuration`, `Release : Baseline` derive transitively), spanning every discipline folder under `Implementation/`: `ProgrammeHierarchy.cs` (Portfolio, Programme, Project), `PhysicalConfiguration.cs` (Assembly, SubAssembly, Part, Component, Configuration), `ChangeRelease.cs` (ChangeRequest, EngineeringChange, Baseline, Release), `Calculations.cs` (Calculation, CalculationSet), `GovernanceRisk.cs` (Issue, Risk, Decision, Assumption), `ProcessApproval.cs` (EngineeringTask, Review, Approval, Milestone, Deliverable), `RequirementsVerification.cs` (Verification, VerificationActivity), `SupplyChain.cs` (Supplier, PurchaseItem), `TestManufacturing.cs` (ManufacturingOperation), `DocumentationDesign.cs` (Document, Simulation), `EvidenceReference.cs` (ExternalSystemLink).
- **Every one of the 31 Kinds overrides exactly one method: `CaptureTypeState(IDictionary<string,string?> state)`** — grep for `override` across `Implementation/*.cs` finds it in every Kind file and nowhere else Kind-specific (e.g. `PhysicalConfiguration.cs:18,39,63,97`; `ProcessApproval.cs:142,188,215,237,261,281`; `GovernanceRisk.cs:118,276,481`; `ProgrammeHierarchy.cs:18,41,65`). No Kind overrides a mutator, a lifecycle rule, a validation method, or anything relationship-related — all of that behavior lives once, in the base class. This is a strong, uniform template-method pattern: Kinds are data-shape declarations, not behavior variations.
- `EngineeringObjectFactory<T>` (`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectFactory.cs:11`) is one generic factory type serving every Kind, one instance per Kind (comment, lines 6-9). `CreateAsync` (line 51) mints a document Id, runs the whole creation (document + revision 1 + object state + audit row) through `EngineeringDomainContext.ExecuteWriteAsync`, and only registers the instance in the in-memory repository after that transaction commits (remarks, lines 33-49) — closing `TD-147`, where a failed creation used to leave a live, mutable instance registered anyway.
- `EngineeringDomainContext.ExecuteWriteAsync` (`src/Tempest.Core/EngineeringDomain/Implementation/EngineeringDomainContext.cs:233-253`) is the single write path for every durable engineering change. It is built around **one domain-wide, non-reentrant write lock** — a `SemaphoreSlim(1,1)` (`_domainWriteLock`, line 69) — taken outside the persistence transaction, then one `PersistenceStore.ExecuteInTransactionAsync` transaction runs the caller's `work`, and only on successful commit does `afterCommit` mutate in-memory state, still under the lock (lines 245-247). The class-level remarks (lines 40-58) explicitly justify the coarse-grained lock: "TempestOS is a single-user desktop system of record... A finer-grained lock... would buy concurrency nobody is waiting for and cost a lock-ordering discipline that the cycle check makes genuinely hard." This is `ADR-0145`.
- Repositories are caches, not sources of truth. `IEngineeringObjectRepository` (`src/Tempest.Core/EngineeringDomain/Implementation/IEngineeringObjectRepository.cs:4-10`) is documented at the interface as "populated from committed state only; never a co-equal writer" and never a replacement for `IEngineeringDocumentStore`, "which remains the sole source of durable document/revision/relationship truth per ADR-0072." `InMemoryEngineeringObjectRepository` (`InMemoryEngineeringObjectRepository.cs:5-37`, 37 lines) is a `ConcurrentDictionary<Guid, IEngineeringObject>` with `Register`, `FindAsync` (dictionary lookup), `ListByKindAsync` (linear scan + filter), and `ListAllAsync` (returns a full copy of every live object, line 32-36). **There is no parent/child index** — no by-parent dictionary anywhere in the repository.
- Audit rows: `AuditRecorder` (`src/Tempest.Core/Audit/AuditRecorder.cs:47`, collection `"Audit"` at line 53) — `Audit/` totals 623 lines across the namespace.

### Children lookups and their cost at scale

Every discipline's tree/node provider computes "children of X" by calling `ListAllAsync()` (a full copy of every live engineering object in the domain) and then LINQ-filtering by `ParentId == X` in memory. Confirmed call sites:

- `src/Tempest.Workspace/Workspace/Mechanical/MechanicalProductStructureNodeProvider.cs:146` (`GetOrphansAsync`) and `:157` (`GetLiveChildrenAsync`) — the latter is called once per rendered node from `ToNodeAsync` (`MechanicalProductStructureNodeProvider.cs:157-166`), so building a tree view over the whole object graph issues one `ListAllAsync` scan per node rendered.
- `src/Tempest.Workspace/Workspace/Calculations/CalculationsNodeProvider.cs:96,143`
- `src/Tempest.Workspace/Workspace/Documents/DocumentsNodeProvider.cs:107,157`
- `src/Tempest.Workspace/Workspace/Manufacturing/ManufacturingNodeProvider.cs:84,127`
- `src/Tempest.Workspace/Workspace/Verification/VerificationActivityNodeProvider.cs:81,120`
- `src/Tempest.Workspace/Projects/ProjectMembership.cs:88`
- `src/Tempest.Core/EngineeringDomain/Implementation/BillOfMaterialsValidationRules.cs:129,157`
- `src/Tempest.Core/EngineeringDomain/Implementation/EngineeringObjectBase.cs:750` — `DeleteAsync`'s live-children guard (`liveChildren > 0` check, lines 745-753) itself does a full `ListAllAsync` scan *inside the domain write transaction*, i.e. while holding the single global write lock (see `TD-146` remarks at lines 718-732: the check was moved inside the transaction specifically to close a race with a concurrent `MoveAsync`).

**Cost at 10,000 objects**: `ListAllAsync` is an O(n) copy-and-return of the whole live-object set (`InMemoryEngineeringObjectRepository.cs:34`, `_objectsById.Values.ToList()`). A node provider building a tree calls it once per rendered node (`GetLiveChildrenAsync` inside `ToNodeAsync`), so rendering a subtree of k visible nodes over a 10,000-object domain costs on the order of `k × 10,000` object-reference copies and LINQ predicate evaluations — quadratic in the number of nodes rendered, not linear. No caching, memoization, or by-parent index mitigates this anywhere in the reviewed code. This is an in-memory, non-durability hazard (nothing is at risk of corruption), but it is the clearest scaling cliff found in the domain layer.

### Soundness — evidence

- **Fault injection / transactional integrity**: `TransactionalWriteFaultInjectionTests.cs` (see section 1) proves creation, attach-content, and structural mutation all roll back cleanly on a failed commit, and that concurrent structural races are ordered rather than corrupting (`TwoHundredConcurrentMoveRaces_NeverFormAParentCycle`, line 169; `ADeleteCannotCommitWhileAConcurrentMoveGivesItALiveChild`, line 236).
- **Adversarial mutator tests**: `MutatorRefusalAdversarialTests.cs` (1,384 lines, the largest test file in the suite) and `RefusedMutationSuccessorLeakageTests.cs` (632 lines) probe what happens when a mutator's precondition is violated or when a refused mutation might otherwise leak a successor object into the repository.
- **Revision/rehydration correctness**: `RevisionRehydrationEquivalenceTests.cs` (580 lines), `EngineeringObjectRehydrationTests.cs` (718 lines), `RevisionAttachmentInterleavingTests.cs` (883 lines), `RevisionStatePreservationTests.cs` (329 lines), `RevisionSuccessorUniquenessTests.cs` (214 lines) — together the largest concentration of tests in the domain, consistent with revision/rehydration being the highest-risk area (the `CaptureTypeState`/`Rehydrate` template-method pair every one of the 31 Kinds participates in).
- **Regression-specific suites**: `R7FalsificationTests.cs` (320 lines) and `R7RegressionProofTests.cs` (588 lines) are named for a specific Work Package round (`WP 16.4B-R7`, the same round referenced in the persistence-layer commit-boundary fix in section 1), i.e. tests written to falsify and then prove a specific prior defect fix.
- **Canonical shape coverage**: `CanonicalKindRoundTripTests.cs` (317 lines) round-trips presumably all/most of the 31 Kinds through create/persist/rehydrate.
- Total: 28 test files, 8,977 lines under `tests/Tempest.Core.Tests/EngineeringDomain`.

### Hazards observed in code

- **Quadratic children-lookup cost with no index**, detailed above — every node provider and `BillOfMaterialsValidationRules` pays an O(n) scan per lookup; a full tree render is effectively O(nodes × objects). At 10,000 objects this is a plausible interactive-latency problem, not merely an asymptotic curiosity.
- **The live-children scan on `DeleteAsync` runs inside the single global write transaction** (`EngineeringObjectBase.cs:745-753`), so a delete on a large domain holds the one domain-wide write lock for the duration of an O(n) scan, serializing every other writer behind it.
- **Single domain-wide write lock is a deliberate, documented single-point serialization** (`EngineeringDomainContext.cs:40-58`) — reasonable for the stated single-user-desktop scope, but it is a hazard specifically *if* the product's scope changes (multi-user, background batch import, etc.), since the code states outright that no per-object or per-project lock granularity exists.
- **No by-parent or by-relationship index in `InMemoryEngineeringObjectRepository`** — confirmed by reading the full 37-line file; this is the direct cause of the quadratic cost above and would be the natural place to fix it (a `ConcurrentDictionary<Guid, List<Guid>>` keyed by parent) without touching the durable schema.

### Reusability estimate: Reusable with interface trim

The mutator discipline (project → commit → apply, `ADR-0145`), the single-writer-transaction model, and the uniform Kind/`CaptureTypeState` template-method pattern are sound architectural decisions with strong fault-injection and adversarial test coverage, and should be kept in a fresh build. The facet-interface composition (14 interfaces on one base class, 31 Kinds each composing a subset via their own interface) is more interface surface than a fresh build strictly needs — a fresh implementation could keep the composition *contracts* (`ADR-0075`'s rule) but would benefit from re-deriving which facet combinations actually recur across the 31 Kinds before re-cutting the interfaces, since some (e.g. `ISearchable`, `ITraceable`) are implemented identically by the shared base regardless of Kind and add little beyond documentation value. The in-memory repository should not be carried forward unchanged — it should gain a parent index before or as part of any fresh build, since the current shape is the direct cause of the quadratic children-lookup cost.

## 3. Units and quantities

### What exists

`src/Tempest.Core/UnitsAndQuantities` totals 2,352 lines across 65 files: 26 physical-quantity dimensions (Length, Mass, Duration, Force, Pressure, Area, Volume, Velocity, Acceleration, MassDensity, Stiffness, TorsionalStiffness, Torque, Energy, Power, RotationalSpeed, PlaneAngle, SpecificHeatCapacity, ThermalConductivity, ThermalExpansion, Dimensionless, SecondMomentOfArea, SectionModulus, Frequency, ElectricCurrent, Voltage, Resistance, ElectricCharge, TemperatureDelta, Temperature), each a compile-time marker type paired with a `<Type>Units.cs` catalogue of `Unit<TDimension>` instances.

Core types:

- `Dimension` (`src/Tempest.Core/UnitsAndQuantities/Dimension.cs:46`, 171 lines) — a `readonly record struct` carrying the seven SI base-quantity exponents (L, M, T, Θ, I, N, J) as `sbyte` fields (7 bytes total), with `*`/`/` operators that add/subtract exponents and a `Pow` method, all `checked` (overflow-safe, lines 105-137). Documented (`ADR-0147`) as the runtime counterpart to the compile-time marker types, letting `Quantity` arithmetic discover e.g. that newtons/m² is pascals without a pre-declared catalogue entry.
- `UnitDefinition` (`src/Tempest.Core/UnitsAndQuantities/UnitDefinition.cs:20`, 69 lines) — `{Symbol, Dimension, ToBaseFactor, ToBaseOffset}`, validated at construction (`ToBaseFactor` must be positive and finite, `ToBaseOffset` finite; lines 37-41). `IsAffine => ToBaseOffset != 0.0` (line 62) is the single flag distinguishing an affine scale (Celsius, Fahrenheit) from an ordinary multiplicative unit.
- `Quantity<TDimension>` (`src/Tempest.Core/UnitsAndQuantities/Quantity.cs:47`, 259 lines) — the compile-time-checked facade: `{Value, Unit}`, arithmetic operators that auto-convert between units of the same `TDimension` through the dimension's base unit (`ADR-0147`, widening the original `ADR-0054` exact-unit-match rule; remarks lines 17-35), affine arithmetic refused via `RequireNotAffine` (lines 222-234, throws `IncompatibleUnitsException`), `Parse`/`TryParse` for `"<number> <symbol>"` text (lines 181-220), and `ToQuantity()`/`FromQuantity()` bridging to the non-generic runtime type (lines 236-258).
- The non-generic runtime `Quantity` (despite the file name, defined in `src/Tempest.Core/UnitsAndQuantities/QuantityVector.cs:67`) pairs a value with a `UnitDefinition` rather than a compile-time type parameter, so cross-dimension arithmetic (force ÷ area → pressure) can be discovered at run time. Its remarks (lines 22-31) disclose a deliberate contract deviation: `==` between quantities of *different* dimensions throws `IncompatibleUnitsException` rather than returning `false` — "not the ordinary `object.Equals` contract... at the cost of this type being unsafe as a `Dictionary`/`HashSet` key across mixed dimensions," stated as a conscious trade continuing the framework's "fail loudly" convention.

### Soundness — evidence

- **Property-based round-trip tests (CsCheck)**: `tests/Tempest.Core.Tests/UnitsAndQuantities/PropertyTests.cs` (156 lines) runs one property per dimension — a value converted from a randomly chosen unit to another randomly chosen unit of the same dimension and back recovers the original to within `1e-12` relative tolerance — via `Gen.Double[-1_000_000, 1_000_000]` and `Gen.Int` unit-index selection (`AssertRoundTrips<TDimension>`, lines 132-146). Every one of the 26 dimensions has its own named `[Fact]` invoking this (e.g. `Length_EveryUnitPair_RoundTripsWithinRelativeTolerance`, line 24, through `Temperature_EveryUnitPair_RoundTripsWithinRelativeTolerance`, line 111, which uses a narrower `Gen.Double[-200, 2000]` range and its own inline property to keep intermediate Kelvin values physically sensible for affine source units, lines 110-129).
- **Affine-unit correctness and refusal**: `AffineUnitTests.cs` (260 lines) covers default-zero-offset behaviour, Celsius↔Kelvin and Fahrenheit↔Celsius conversion, that addition/subtraction/scaling on an affine unit throws (`AddingTwoAffineQuantities_Throws` line 98, `SubtractingTwoAffineQuantities_Throws` line 109, `ScalingAnAffineQuantity_Throws` line 118), that non-finite offsets are refused at construction (`AUnit_RefusesANonFiniteOffset`, line 155), JSON round-trip including backward compatibility with units serialized before the offset field existed (`AUnitSerialisedBeforeOffsetsExisted_DeserialisesWithZeroOffset`, line 180), and internal consistency of several unit catalogues against their own base unit (lines 198-207 and beyond).
- **Compile-time dimension safety**: `CompileTimeDimensionSafetyTests.cs` (68 lines) exercises that same-dimension `ConvertTo`/arithmetic compiles and executes (line 47) — the flip side of the guarantee being that a cross-dimension `Quantity<TDimension>` combination simply does not compile, so it cannot be tested by execution, only by the type system itself.
- **Example-based coverage**: `QuantityTests.cs` (265 lines), `DimensionCatalogueTests.cs` (51 lines, base-unit-only round trip, the fast check `PropertyTests.cs`'s own remarks say it subsumes), `QuantityParsingTests.cs` (63 lines), `QuantitySerializationTests.cs` (29 lines), `RotationalSpeedAndPlaneAngleTests.cs` (90 lines), `UnitConverterTests.cs` (18 lines), `UnitTests.cs` (58 lines), `ExceptionTests.cs` (14 lines). Total: 1,152 lines across 12 files in `tests/Tempest.Core.Tests/UnitsAndQuantities`.

### Hazards observed in code

- **The non-generic `Quantity`'s `==` operator can throw** across mismatched dimensions (`QuantityVector.cs:22-31`, self-disclosed as violating the ordinary `Equals` contract) — a caller that puts a `Quantity` into a `Dictionary`/`HashSet`/LINQ `Distinct` alongside quantities of another dimension will get an exception instead of `false`, from code that looks like an ordinary equality check. This is documented but not defended against by any static analyzer rule found in this audit.
- **`sbyte` exponent overflow is possible in principle** (`Dimension.cs:104-137`, `checked` arithmetic throws `OverflowException` rather than silently wrapping) — a safe failure mode, but means an extreme derived-dimension composition (unlikely in practice, per the code's own comment) throws a generic `OverflowException` rather than a domain-specific one.

### Reusability estimate: Reusable as-is

This is the most self-contained and best-tested substrate reviewed: small (2,352 lines), immutable value types, no I/O, no dependency on persistence or the domain layer, and its central numerical claim (round-trip conversion accuracy) is property-tested across all 26 dimensions and every unit pair rather than a handful of hand-picked examples. A fresh implementation could take this namespace essentially unchanged.

## 4. Reference data governance

### What exists

`src/Tempest.Core/ReferenceData` totals 5,916 lines (including `Review/` and `Seeding/` subfolders); `src/Tempest.Core/Materials` totals 1,232 lines.

- **State model.** `ReferenceValidationState` (`src/Tempest.Core/ReferenceData/ReferenceValidationState.cs:19`) is a 5-value enum: `Draft → Checked → Validated → Released → Superseded` — not the three-state "Draft→Verified→Released" the review brief names, but a finer-grained model with an extra intermediate `Validated` state and a terminal `Superseded` state. It is explicitly documented (lines 9-17) as a family-specific specialisation of the platform's own canonical `LifecycleState` vocabulary (`ADR-0074`), with `CanonicalEquivalent` (lines 78-86) mapping each state onto it. `ReferenceValidationStates.Permitted` (lines 45-61) is a static transition table: down-transitions are deliberately allowed (`Checked → Draft`, `Validated → Checked`) so a failed check can send a record back rather than forcing abandonment; `Released` only transitions to `Superseded`; `Superseded` is terminal. `IsPermitted`/`GetPermittedTargets` (lines 70-75) are the sole gate — no same-to-same transition is ever permitted (line 66-68 comment).
- **Provenance-gated transitions.** `ReferenceValidationStates.DescribeProvenanceShortfall` (lines 102-116) is "the single enforcement point for P01's own central rule: reference data earns its status from its provenance, never from a caller asserting one" (doc comment, lines 96-101): reaching `Released` specifically requires `provenance.IsVerified` (line 112), and any non-Draft state requires `provenance.IdentifiesASource` (line 109).
- **`ReferenceReviewService`** (`src/Tempest.Core/ReferenceData/Review/ReferenceReviewService.cs:62`, 282 lines) is the sole path by which a record earns verified/released provenance. `VerifyAsync` (line 113) takes the reviewer's principal id from `ICurrentPrincipalAccessor` and the date from an injected `TimeProvider` — neither is a caller-supplied parameter, so "a caller can no longer name somebody else as the reviewer, and cannot backdate the review" (remarks, lines 33-41); with nobody signed in, the act is refused outright (`RequireReviewer`, lines 260-274) rather than attributed to an "unknown" principal. `ReleaseAsync` (line 201) is a deliberately separate act from `VerifyAsync`, walking `Checked → Validated → Released` in sequence (lines 226-241) and refusing outright if `record.Provenance.IsVerified` is false (lines 217-224). Both actions write an audit row when an `IAuditRecorder` is supplied (`reference.verified` / `reference.released`, constants at lines 65/68; recorded at lines 173-183 and 245-255).
- **Who can release**: **no role or permission check exists anywhere in `src/Tempest.Core/ReferenceData`** (confirmed by grep for `Permission`/`IsAuthorized`/`Role` across the namespace — zero matches). `RequireReviewer` only checks that *some* principal is signed in; any authenticated user can call both `VerifyAsync` and `ReleaseAsync` on any record. The two-act split (verify, then separately release) is a workflow nudge toward two-person review, not an enforced control — nothing stops the same principal from calling both in succession.
- **Immutability of released records.** `ReferenceDataCatalog<TDefinition>.ReviseAsync` (`src/Tempest.Core/ReferenceData/ReferenceDataCatalog.cs:222-266`) checks `ReferenceValidationStates.IsRevisable(current.ValidationState)` (line 240) and throws `ReleasedReferenceImmutableException` if the record is `Released` or `Superseded` — a released record's own engineering content cannot be edited in place, only revised via `SupersedeAsync` (referenced but not the record's own content mutated). `SetValidationStateAsync` (lines 273-306) is the sole path to change validation state and separately guards against being used to reach `Superseded` (must use `SupersedeAsync`, lines 279-283).
- **Common machinery, not per-library reinvention.** `ReferenceDataCatalog<TDefinition>` (`ReferenceDataCatalog.cs:51`, 496 lines) is documented (lines 9-13) as "the storage, revision, lifecycle and supersession machinery every Group A reference library shares" — a thin typed index over `IEngineeringDocumentStore`, the same pattern `Materials.MaterialCatalog` established (`ADR-0055`) and `Requirements.RequirementsService` repeated (`ADR-0058`) before being extracted here (`ADR-0126`). A per-record lock (`_recordLock.AcquireAsync(recordId, ...)`, e.g. line 234) and an optional secondary-key lock (`AcquireSecondaryLockAsync`, line 233) serialise concurrent revisions to the same record and protect a caller-declared secondary uniqueness key (e.g. a material grade designation).
- **Seeding.** `src/Tempest.Core/ReferenceData/Seeding` holds one dataset file per discipline (`BearingSeed`, `CommercialSeed`, `ConstantSeed`, `EngineeringAssetSeed`, `FastenerSeed`, `KnowledgeSeed`, `MaterialSeed`, `ProcessSeed`, `RuleSeed`, `StandardSeed`) plus `ReferenceSeedService` and `IReferenceSeed` — a uniform mechanism for loading built-in reference data at startup.
- **Materials** (`src/Tempest.Core/Materials`, 1,232 lines): `MaterialCatalog` derives from `ReferenceDataCatalog<MaterialDefinition>`, inheriting the same Draft→Checked→Validated→Released→Superseded governance rather than a parallel one. `MaterialCatalogReconciliationService`/`MaterialCatalogReconciliationReport` exist specifically to reconcile catalog state (e.g. after a seed update).

### Soundness — evidence

### Hazards observed in code

- **No authorization gate on release.** Any signed-in principal can verify and release any reference record; the review brief's implicit assumption of a distinct "who can release" answer is, in the code today, "anyone with a session." This is a governance-process gap, not a data-integrity one (provenance and audit trail are sound), but it means the two-person-review intent is procedural convention rather than an enforced platform rule.
- **`Superseded` records are permanently terminal** (`ReferenceValidationStates.cs:60`, empty permitted-target set) — there is no path to un-supersede a record if a supersession is later found to be in error; a new record must be created and the chain re-pointed, which is not itself demonstrated as tested in the files reviewed here.

### Reusability estimate: Reusable as-is

The state machine, provenance-gating rule, and the review/release split are small, cleanly separated from storage mechanics (built on the same `IEngineeringDocumentStore`/`IPersistenceStore` primitives as sections 1 and 2), and have direct test coverage of the governance rule itself (not just the storage plumbing). The authorization gap is a genuine finding but is an *addition* to make (wire a permission check into `RequireReviewer`), not a redesign — the state machine and provenance model do not need to change to fix it.

## 6. Identity, configuration, logging, and the custom host

### What exists

- **Identity** (`src/Tempest.Core/Identity`, 890 lines across 13 files): `IPrincipal` (`IPrincipal.cs:15`) carries an `IIdentity` and a set of `Permission` values; `ISessionPrincipal : IPrincipal` (`SessionPrincipal.cs:95`) is the signed-in session's own principal, produced by `ISessionPrincipalSource`/`SessionPrincipalSource` (lines 188, 235); `ICurrentPrincipalAccessor` is the ambient accessor every other substrate in this audit resolves the acting principal from (used in sections 1, 2, 4, 5). `Permission` (`Permission.cs:13`) is a minimal value-equal record wrapping a string `Key` (e.g. `"reports.generate"`), "expected to be extended additively." `PermissionEvaluator` (`PermissionEvaluator.cs:18`) is the sole `IPermissionEvaluator` implementation: `HasPermission` checks `principal.Permissions.Contains(permission)` directly (line 37); `RequirePermission` (lines 41-58) logs a `Warning` with principal Id and permission key only (never a credential, per the code's own citation of `Platform Service Contracts.md`'s Logging Requirements) and throws `PermissionDeniedException`. `PrincipalDirectory` (`PrincipalDirectory.cs:27`, 90 lines) resolves a stored identity id to a human-readable display name (session principal first, then the OS, then the id verbatim) — built specifically because "the first Windows review of `v0.17.0` saw `S-1-5-21-…` under 'Last Revised By'" (doc comment, lines 5-11).

The gap identified there is an omission against an existing platform convention, not a missing capability.
- **Configuration** (`src/Tempest.Core/Configuration`, 509 lines across 10 files): `IConfigurationProvider`/`ConfigurationProvider`/`ConfigurationBuilder` are TempestOS's own thin key-value configuration surface, fed by `IConfigurationSource` implementations — `MemoryConfigurationSource` for tests/defaults and `MicrosoftExtensionsConfigurationSource` (`MicrosoftExtensionsConfigurationSource.cs`), which explicitly wraps a real `Microsoft.Extensions.Configuration.ConfigurationBuilder` (line 113) to read `appsettings.json`/environment/command-line sources and flattens the result into TempestOS's own flat key space (`:`/`_` section separators, matching `Microsoft.Extensions.Configuration.CommandLine`'s convention per the doc comment at line 30). **Configuration is not reimplemented from scratch — it is a thin custom facade over the real Microsoft library for file/env/CLI parsing.**
- **Logging** (`src/Tempest.Core/Logging`, 1,051 lines across 12 files): `ILogger`/`ILoggerFactory`/`ILogSink` are TempestOS's own abstraction, with `ConsoleLogSink`, `RollingFileLogSink`, and `CompositeLogSink` as concrete sinks, plus `TempestLoggerProvider` (`TempestLoggerProvider.cs:1,22`) which forwards `Microsoft.Extensions.Logging` messages (from any third-party library that logs via `MEL`) into TempestOS's own sinks — the same "own abstraction, bridge to the standard one at the edges" pattern as Configuration.
- **The custom DI container** (`src/Tempest.Core/DependencyInjection`, 843 lines across 13 files, no dependency on `Microsoft.Extensions.DependencyInjection` anywhere in this folder): `IServiceCollection`/`ServiceCollection` (`ServiceCollection.cs`, 80 lines) is deliberately minimal — one `Add(Type, Type, ServiceLifetime, allowReplace)` method plus `AddInstance`, with `Singleton<T>()`/`Transient<T>()` generic sugar as extension methods (per the interface's own doc comment, `IServiceCollection.cs:8-15`). `TempestServiceProvider` (`TempestServiceProvider.cs:42`, 210 lines) does constructor-injection resolution: exactly one public constructor is required per implementation type (zero or multiple both throw a descriptive exception, lines 17-21); circular dependencies throw `CircularServiceDependencyException` carrying the full chain (lines 107-113); a missing registration falls back to a constructor parameter's own declared default **only** when the parameter's own nullability annotation says absence is legitimate (`IsAbsenceLegitimate`, lines 202-209) — a deliberate closure of `TD-64`, where a non-nullable parameter with a default value used to silently disarm what should have been a hard-required permission-gate dependency (comment, lines 165-186). **Only two lifetimes exist: Singleton and Transient** — `ServiceLifetime.cs:8-11` states outright "there is deliberately no 'Scoped' lifetime — TempestOS has no notion of a request or unit-of-work scope today, and adding one without a concrete consumer would be speculative." There is also no multiple-registration/`IEnumerable<T>` resolution support, no open-generic support, and no automatic `IDisposable` tracking/disposal of container-created instances (not found in this file).
- **The custom host** (`src/Tempest.Core/Runtime`, 1,895 lines across 7 files): `TempestHost` (`TempestHost.cs:114`, 1,335 lines — by far the largest single file examined in this audit) is built by `TempestHostBuilder` (`TempestHostBuilder.cs`, 223 lines) and constructs Configuration, Logging, module Discovery, Registration, and the DI container itself, in that order, during `RunAsync` (doc comment, lines 74-79). It implements an explicit state machine (`HostState`: `Created → Starting → Running → Stopped`/`Faulted → Disposed`) with documented semantics deliberately matched to ".NET generic-host convention" for cancellation-vs-graceful-stop (doc comment, lines 91-99) and idempotent disposal (lines 101-106, `ADR-0019`). `TempestHost.cs`'s import list alone spans roughly 65 `using Tempest.Core.*` namespaces — it is the single composition root for every module in the entire platform (Bearings, Calculations, Commands, BusinessGovernance, BusinessOperations, CommercialIntelligence, EngineeringAssets, Knowledge, Manufacturing, Materials, ReferenceData, Requirements, Standards, Verification, and more), registering each module's services directly. The doc comment (lines 108-119) states plainly that a large portion of what this class used to do — constructing plugin trust, component-principal, licence validation, and the REST API's endpoint registry — is now frozen at `src/Frozen/` (section 8): "Plugin Discovery... stays live: the Host still discovers and records what is in the plugin drop folder, and goes no further."

### Is the custom DI/host a liability versus `Microsoft.Extensions.Hosting`?

Sizing the substitution: `Microsoft.Extensions.DependencyInjection` (abstractions + implementation) and `Microsoft.Extensions.Hosting` together are mature, widely-used, heavily-tested libraries offering scoped lifetimes, keyed services, `IEnumerable<T>` multi-registration, open generics, automatic disposal tracking, and a large hosted-service/background-task ecosystem — none of which TempestOS's custom container provides. Against that, TempestOS's own DI container is small (843 lines) and its **feature gaps are explicitly disclosed as deliberate scope decisions** (no Scoped lifetime, stated directly in `ServiceLifetime.cs`) rather than accidental omissions, and its constructor-selection/circular-dependency/nullability-driven-fallback behavior is more strictly checked than the .NET default container in at least one respect (`TD-64`'s fix: a non-nullable dependency with a declared default is refused, not silently satisfied by the default — the .NET built-in container has no equivalent guard). The host lifecycle (`TempestHost`) is a bigger and more debatable case: it reimplements a state machine and cancellation semantics that `Microsoft.Extensions.Hosting.IHost`/`IHostedService` already provide, at real cost (1,335 lines in one file, plus the whole `TempestHostBuilder`), and its main non-generic-host-shaped responsibility — module discovery/registration across ~30+ business and engineering domains — is coupled directly into it as one large composition root rather than factored into smaller per-module registration units that a generic host's own `IServiceCollection` extension-method convention would naturally support. The generic-host substitution would not be a small change (module discovery, the plugin-trust boundary now in `src/Frozen`, and the audit/logging bridges all currently assume this specific host shape), but the size and single-file concentration of `TempestHost.cs` is itself a maintainability concern independent of which host abstraction is chosen.

### Soundness — evidence

- `tests/Tempest.Core.Tests/Runtime` totals 3,411 lines — the largest test surface of any substrate examined in this section, consistent with the host's own size and its state-machine/cancellation semantics being the highest-risk part of this substrate.
- `tests/Tempest.Core.Tests/DependencyInjection` (598 lines), `tests/Tempest.Core.Tests/Identity` (627 lines), `tests/Tempest.Core.Tests/Configuration` (537 lines), `tests/Tempest.Core.Tests/Logging` (1,253 lines).

### Hazards observed in code

- **`TempestHost.cs` at 1,335 lines in one file is a single, large composition root** coupling module registration for the entire platform to host lifecycle management — a change to either concern risks touching the other.
- **No permission check on reference-data release** (repeated from section 4) is specifically an inconsistency against this substrate's own established convention — `IPermissionEvaluator`/`RequirePermission` is live, tested infrastructure used in half a dozen other substrates.
- **No Scoped DI lifetime and no automatic disposal tracking** are stated as deliberate for the product's current shape; both would need to be added (not merely re-enabled) if a future requirement introduced request/unit-of-work scoping or many container-created `IDisposable` services.

### Reusability estimate: Reusable with interface trim

Identity, Configuration, and Logging are small, each already brokers to a real Microsoft library where one is genuinely useful (Configuration's file/env parsing, Logging's third-party bridge) rather than reinventing that part, and are reasonably well-tested — keep as-is. The custom DI container is defensible at its current, deliberately narrow scope, but a fresh build should re-examine whether `Microsoft.Extensions.DependencyInjection` now covers the scenario better, since the custom container's chief advantage (`TD-64`'s stricter nullability-driven fallback check) is a narrow, specific fix that could plausibly be replicated as a startup-time registration-validation pass over the standard container instead of justifying an entire hand-rolled one. `TempestHost` is the part most worth reconsidering in a fresh build — not because its lifecycle semantics are unsound (they are carefully thought through and deliberately mirror the generic-host convention), but because its size and the concentration of whole-platform module registration into one file is a standing maintenance cost that a fresh build has the opportunity to avoid by adopting `Microsoft.Extensions.Hosting` directly or by splitting registration into per-module units regardless of host choice.

## 7. Commands and events

### What exists

- `src/Tempest.Core/Commands` totals 1,763 lines across 20 files. `ICommand`/`ICommandHandler<T>` is the typed dispatch path: `CommandDispatcher` (`CommandDispatcher.cs`, 81 lines) implements `ICommandDispatcher.DispatchAsync<TCommand>`, delegating to the shared `CommandHandlerTable`. `CommandRegistry` (`CommandRegistry.cs:24`, 419 lines) is the Id-based path for callers with only a string (a menu, a toolbar, a keyboard shortcut, "or a future AI service" per `CommandDescriptor`'s own doc comment, `CommandDescriptor.cs:5`) — a single lock-guarded dictionary keyed by `CommandDescriptor.Id`, "mirroring `Navigation.NavigationService`'s own pattern exactly" (doc comment, lines 9-12).
- **Invocation tracking**: `CommandInvocation` (`CommandInvocation.cs:36`, 83 lines) is the result of `ICommandRegistry.InvokeAsync` and models three distinct outcomes — `Executed` (with the handler's `CommandResult`), `Cancelled` (a person declined a prompt; not a failure), and `Unavailable` (with a stated reason) — explicitly designed so a declined confirmation or an unavailable command is never reported as an error to a user who did nothing wrong (doc comment, lines 20-29).
- **The "prompt"**: `CommandParameterPrompt` (`CommandParameter.cs:95-99`) is a delegate — `Task<IReadOnlyDictionary<string,string>?> (CommandDescriptor, IReadOnlyList<CommandParameter>, string? confirmationMessage, CancellationToken)` — supplied by whichever surface invokes a command, so "Core never renders anything: it hands over a descriptor, a list of parameters and an optional confirmation message, and takes back values or a refusal" (doc comment, lines 70-74). `CommandParameter` (line 36) declares one required value a `CommandBinding` needs beyond what `CommandContext` supplies — every parameter is required by design (there is no optional parameter; a binding that can proceed without one simply omits it, doc comment lines 11-14), with `AllowedValues` and an optional `Validate` callback. `CommandBinding` (`CommandBinding.cs`, 225 lines) is the explicit, hand-written, non-reflective mapping from `CommandContext` + collected parameter values to a concrete `ICommand` — "nothing here inspects a constructor, scans an attribute, or resolves a service" (doc comment, lines 10-16), a deliberate rejection of convention-based/reflective command construction (`ADR-0037`).
- **Plugin-trust complexity has already been removed, not merely deferred.** Both `CommandRegistry` (doc comment, lines 15-21) and `EventBus` (below) explicitly document that they used to carry a second dictionary of owning component principals, an optional component-scope accessor, and an optional permission evaluator so a higher-trust-tier plugin could evict a lower one's descriptor — "Nothing third-party ever loaded, so registration is unconditional duplicate rejection again... and the trust platform is frozen at `src/Frozen/Tempest.Core.Plugins`." What remains in `src/Tempest.Core/Commands` today is the single-user-desktop-shaped subset.
- `src/Tempest.Core/Events` totals 272 lines across 4 files. `EventBus` (`EventBus.cs:42`, 154 lines) is a lock-guarded `Dictionary<Type, List<object>>` of subscribers; `PublishAsync` takes an immutable snapshot under the lock then dispatches sequentially outside it (so a handler that subscribes/unsubscribes or re-enters `PublishAsync` during its own `HandleAsync` cannot corrupt the in-flight dispatch, doc comment lines 9-19); dispatch is sequential and awaited one subscriber at a time in subscription order; a subscriber's exception is caught, logged at `Error`, and never rethrown (`OperationCanceledException` is the sole exception propagated directly to the publisher) per `ADR-0028`. The same "used to carry a permission evaluator and component scope for plugins that never shipped, now frozen" story applies here too (doc comment, lines 32-40): "Subscribers are bare handler references again."

### Is the command framework proportionate to a single-user desktop?

Largely yes, and the code's own commit history (visible in the doc comments) shows the framework being actively *right-sized down* rather than left over-built: both `CommandRegistry` and `EventBus` had plugin-trust/permission-evaluation machinery added for a plugin ecosystem that never shipped, and that machinery has since been stripped back out to `src/Frozen` (`ADR-0146`, `WP 17.2A`), leaving genuinely small classes (419 and 154 lines respectively) doing one job each. The dual dispatch paths (typed `ICommandDispatcher` for code that already has strongly-typed data, and Id-based `ICommandRegistry` for callers with only a string) are each independently justified by a real, distinct caller shape rather than being two ways to do the same thing. The `CommandParameterPrompt` delegate is a clean way to keep Core UI-agnostic without inventing a UI abstraction of its own. The one area that might be more machinery than a single-user desktop strictly needs is the parameter/binding/prompt/confirmation apparatus (`CommandParameter`, `CommandBinding`, `CommandParameterPrompt`, `CommandContextRequirement`, `CommandAvailability` — five additional files/concepts) for what is, per-command, usually a handful of fields — but this is a reasonable, bounded amount of ceremony for a framework whose explicit purpose (per `CommandDescriptor`'s own doc comment) is to let a command be invoked uniformly from a menu, a toolbar, a keyboard shortcut, or "a future AI service," which a single hard-coded UI callback per command would not support as cleanly.

### Soundness — evidence

- `tests/Tempest.Core.Tests/Commands` totals 3,319 lines — nearly double the size of the 1,763-line substrate itself, the highest test-to-source ratio observed in this audit.
- `tests/Tempest.Core.Tests/Events` totals 549 lines, covering the substantially smaller 272-line `Events` namespace at a similarly high ratio, including (per `EventBus`'s own doc comment) the concurrent-mutation-during-dispatch and re-entrant-publish scenarios its snapshot-then-dispatch design exists to handle.

### Hazards observed in code

- No specific defects were found in this substrate during this audit; the main design question is proportionality (addressed above) rather than correctness. The heavy test investment relative to code size suggests the team already treats this as a substrate worth guarding carefully, which is consistent with commands being the platform's primary mutation entry point.

### Reusability estimate: Reusable as-is

Small, already right-sized after the plugin-trust rollback, cleanly separated dispatch paths for genuinely different caller shapes, and disproportionately well-tested relative to its size. A fresh build could carry this forward with little to no change.

## 8. Frozen platform

### What exists

`src/Frozen` holds three sub-projects, 3,120 lines of C# total: `Tempest.Core.Plugins` (2,045 lines — plugin signing, the trust store, trust tiers, capability enforcement, component principals, the denied-type registry, and assembly loading), `Tempest.Core.Api` (724 lines — the inbound REST API), and `Tempest.Core.Licensing` (351 lines). `src/Frozen/README.md` states the governing fact directly: "there is no project file here, no folder here is referenced by `src/TempestOS.slnx`, and nothing here compiles, is tested, or is shipped." Confirmed independently: `find src/Frozen -iname "*.csproj"` returns nothing, and the solution file (`src/TempestOS.slnx`) has no reference to `Frozen`. The matching tests are frozen alongside at `tests/Frozen/Tempest.Core.Tests` (also with no `.csproj`), 12,603 lines across subfolders mirroring the frozen namespaces plus `Commands`, `Events`, `Identity`, `Modules`, `Navigation`, `Runtime`, `Samples` — i.e. the tests for the plugin-trust/permission-evaluation behavior that used to be woven into those live substrates before `ADR-0146` stripped it back out (consistent with the "used to carry a permission evaluator" doc comments found in `CommandRegistry.cs` and `EventBus.cs` in section 7).

The README states the intent plainly: this code is kept rather than deleted "because deleting it would throw away working design that a paying client may one day ask for," and explicitly documents that it will drift from `Tempest.Core` over time and that returning it to the build means re-pointing it at whatever `Tempest.Core` has become and re-reviewing it, not merely re-enabling a flag. Plugin *manifest discovery* is deliberately kept live (not frozen) in `src/Tempest.Core/Plugins` — the host still discovers and records what is in the plugin drop folder without loading, signing, verifying, scoping, or enforcing any of it.

### Whether anything live still depends on Frozen namespaces

**No.** This required care to verify because the frozen `Tempest.Core.Plugins` project deliberately shares its C# namespace (`Tempest.Core.Plugins`) with the live, still-shipped `src/Tempest.Core/Plugins` folder (manifest discovery). A naive grep for the namespace string therefore returns many false positives from unrelated, genuinely live files. Verification instead enumerated every public type declared under `src/Frozen` (e.g. `IPluginAssemblyLoader`, `PluginTrustStore`, `PluginTrustTier`, `IApiEndpointRegistry`, `ApiRequestHandler`, `RestApiHostedService`, `ILicense`, `LicenseValidator`, `LicenseProvider`, `LicenseValidationResult`, and others) and searched for each by exact name across `src/` excluding `src/Frozen`. The only hits were doc-comment mentions inside `<c>...</c>` tags — e.g. `TempestHost.cs:118` ("...it registered the REST API's own `IApiEndpointRegistry` singleton") and `Quantity.cs:13` (comparing `Quantity`'s own no-DI-container design to `LicenseValidationResult`'s) — never an actual `using`, field, parameter, or call site. Combined with the absence of any `.csproj` for the frozen projects and their absence from the solution file, there is no way for the current build to reference this code even accidentally.

### Reusability estimate: Reusable as-is (as a frozen artifact; not part of the live build)

This is not a "substrate" in the same sense as sections 1–7 — it is deliberately inert, versioned-and-parked design. Its size (3,120 lines of source, 12,603 lines of matching tests — roughly a 4:1 test-to-code ratio, unusually high even by this codebase's own well-tested standards) suggests it was a mature, seriously-built subsystem before being frozen, not an abandoned prototype. For a fresh implementation that keeps the same architectural decisions, this code is a reference design to consult if/when plugin trust, an inbound API, or licensing is actually needed, but should not be un-frozen speculatively — the README's own stated re-activation path (re-point, re-review against the platform's current shape) is the right one to follow rather than merging it back wholesale.

## 9. Verification models

### What the review brief expects

A planning document found at `docs/releases/v1.0.0/WorkPackages.md:88` describes `WP 17.1B` as intending to, among other things, "collapse the three verification models (`Core/Verification`, `EngineeringDomain/RequirementsVerification`, `EngineeringAssets/Verification`) to the one `VerificationArtefact` model that the calc-sheet chain uses." That document also states (line 22) "Nothing below has begun. `VERSION` is `0.16.0`" as of when it was written; the tree's current `VERSION` file reads `0.17.0`, and the transactional-store half of `WP 17.1B` (`ADR-0145`, audited directly in sections 1 and 2 of this report, with its own dedicated fault-injection test suite) has demonstrably landed. This section checks the other half — the verification-model collapse — independently against the current code.

### What exists today: three separate, independently-wired models, not one

Grepping `Verification` folders under `src/Tempest.Core` and `src/Tempest.Workspace` finds exactly the three locations the planning document named, all still present:

1. **`src/Tempest.Core/Verification`** (453 lines: `IVerificationRecord`, `IVerificationService`, `VerificationService`, `VerificationContext`, `VerificationCriterion`, `VerificationEvidenceEntry`, `VerificationOutcome`, `VerificationRecord`, `VerificationRecordDto`). `VerificationService` (`VerificationService.cs:8-45` doc comment) records a verification as a brand-new `IEngineeringDocument` of `Kind = "VerificationRecord"` and links it to *any* subject document via `IEngineeringDocumentStore.LinkAsync` (`VerifiedByRelationshipKind`) — a lightweight, document-relationship-based event log usable against any document in the platform, with permission-gated reads (`IPermissionEvaluator.RequirePermission` on `GetVerificationHistoryAsync`, mirroring `Audit.AuditQuery`'s pattern) but ungated writes.
2. **`EngineeringDomain`'s `Verification`/`VerificationActivity` Kinds** (contracts in `src/Tempest.Core/EngineeringDomain/Contracts/RequirementsVerification.cs`: `IVerification`, `IVerificationActivity`, `IVerificationResult`; implementation in `src/Tempest.Core/EngineeringDomain/Implementation/RequirementsVerification.cs:5,18`) are full engineering-domain object Kinds (section 2) — `EngineeringObjectBase`-derived, with `SubjectId`/`Method` as bare fields (`Method` is a plain `string`, not a closed enum), participating in the domain's own lifecycle, relationships, and children/parent machinery like every other Kind. No comment in this file references either of the other two models.
3. **`src/Tempest.Core/EngineeringAssets/Verification`** (864 lines: `VerificationArtefact`, `VerificationArtefactCatalog`, `VerificationTraceService`) — the newest of the three, and architecturally distinct from *both* others: `VerificationArtefact` is a governed **reference-data record** (`IVerificationArtefactCatalog : IReferenceDataCatalog<VerificationArtefact>`, `VerificationArtefactCatalog.cs:30`), inheriting the same Draft→Checked→Validated→Released→Superseded governance audited in section 4, with a closed `VerificationMethod` enum (`VerificationArtefact.cs:12`) and a six-value `VerificationStanding` (line 36) explicitly designed so "missing evidence is never a pass" (doc comment, lines 44-50). Its own doc comment (lines 5-11) explicitly contrasts itself with model 1: "A closed vocabulary here, unlike `Core.Verification.IVerificationRecord.Method`'s open string, because `E3` plans verification as well as recording it and a plan needs a countable method" — i.e., the newest model is aware of the oldest one and deliberately diverges from it rather than replacing it.

### Whether the collapse happened: no

All three are simultaneously live and wired into the composition root. `src/Tempest.Core/Runtime/TempestHost.cs` registers `IVerificationService`/`VerificationService` (line 871), `IVerificationArtefactCatalog`/`VerificationArtefactCatalog` (line 787), and `IVerificationTraceService`/`VerificationTraceService` (line 789) — all three as singletons in the same host, none conditional on the other, none a delegating shim over another. Separately, `src/Tempest.Workspace/Workspace/Verification/VerificationActivityFactoryRegistry.cs:49` constructs `EngineeringObjectFactory<VerificationActivity>`, keeping the second (domain-Kind) model live and reachable through the workspace's own command/node-provider surface (`CreateVerificationActivityCommand`, `VerificationActivityNodeProvider`, and 16 other files under `src/Tempest.Workspace/Workspace/Verification`, 1,774 lines). Each model has its own test coverage confirming it is actively exercised, not dead code awaiting deletion: `tests/Tempest.Core.Tests/Verification` (598 lines) for model 1; `tests/Tempest.Core.Tests/Workspace/VerificationActivityCommandsTests.cs` and `VerificationActivityNodeProviderAndFacetsTests.cs` for model 2; `tests/Tempest.Core.Tests/EngineeringAssets/EngineeringAssetBehaviourTests.cs` (6 references to `VerificationArtefact`) and `AssetFixtures.cs` for model 3.

**Conclusion: the collapse described in `WP 17.1B`'s own stated scope has not occurred.** The transactional-store portion of that Work Package shipped (audited in sections 1–2); the verification-model-collapse portion did not. This is stated by the planning document itself as part of the same Work Package's scope, so its absence from the code is a scope item still outstanding against the plan, not a silent regression — but a design-freeze review should record it as unresolved rather than assume `WP 17.1B`'s completion covered it.

### Reusability estimate: Rewrite (consolidate)

None of the three models is unsound in isolation — each has its own test coverage and a defensible reason for its own shape (model 1 is a cheap generic event log for any document; model 2 gives verification activities full domain-object standing, useful if verification work itself needs to be scheduled/assigned/tracked like a task; model 3 is governed reference data with a closed vocabulary suited to planning). But carrying three parallel representations of "verification" into either continued development or a fresh implementation is the wrong shape for a single-user desktop engineering tool: a caller (or a future AI service, per the command framework's own stated ambition in section 7) has no principled way to know which "verification" a given document, requirement, or calculation is expressed against. A fresh build should decide which one shape survives — `VerificationArtefact`'s governed reference-data model looks best-fitted to the calc-sheet/reference-governance direction the rest of this audit's evidence points toward — and fold the other two into it, rather than keeping all three.
