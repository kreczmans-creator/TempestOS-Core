# ADR-0176: The Demo Project Is Flagged on the Project, Installed and Removed Only by a Person, and Its Removal Is the One Delete the Calculation Store Makes

## Status

Accepted (v0.26.0, Addendum C, C-6). Builds on `ADR-0165` (Evidence governs a calculation), `ADR-0168` (links pin a revision and staleness is gated), `ADR-0172` (scan profiles are versioned and immutable) and `ADR-0074` (an engineering object is deleted by a flag, never erased). Adds no table, no collection and no migration: every row it writes is a row of an existing collection, written by the existing services.

## Context

Addendum C §C6 C-6 asks for one realistic fictional project holding every built chain, uses only invented data, marked DEMO on its project, its calculations and its exported sheets, installable and removable from a menu action and never installed into a real database by itself. Four questions follow.

1. Where does the DEMO mark live, so that no calculation's text carries it and a real calculation cannot?
2. How is the project made, and what stops an install from touching a project that is not the demonstration?
3. What does removal delete, given that issued records are immutable and an engineering object is never erased?
4. What does the person see, and when does anything run?

## Decision

1. **The flag is the project's own tag, and the sheet reads it.** The project is made through the same `EngineeringObjectFactory<Project>` the Projects area uses, with the tag `demo-project` in its metadata and the number `DEMO0-PRESS1`. `CalcDemoProject.IsDemo` is the one test of the flag; `CalcInstanceService` asks it when it builds a header and sets `CalcSheetHeader.Watermark` (a new optional last parameter, `null` on every real sheet). The text renderer prints it as the second line; the PDF prints it in the header band, as a notice line, in the footer of every page and in the file's title and subject. No template, input or assumption holds the word, so every sheet of a flagged project carries it, the issued sheet of a demo pack too, and no sheet of any other project does unless someone tags a project by hand (which only adds a mark). Every calculation, pack and Evidence record is also named "DEMO — …", so the lists say it.

2. **The demonstration is the project that carries the flag and the number.** Install refuses while a live project holds the number, whether it is the demonstration or a real project that took the number. Removal acts only on a live project that carries the flag *and* the number; one with either alone is "not the demo project" and is never touched. A project's id cannot be chosen (the factory mints it), so the number and the flag are the fixed identity.

3. **The install is the services, not a script.** Each pack is made by `InstantiatePackTemplateAsync` from its template, seeded from the template's own example inputs (`ExampleInputs`) with the specification the story names, the two synthetic cable tables given to the cable steps as plain, labelled inputs (no reference record is stored, so none can be licensed), and the scan-to-seal pair made by `CreateAsync`, `BindAsync`, `ApplyScanImportAsync` and `UpdateLinksAsync` from a 30-part synthetic table through two stored scan profiles whose ids start `demo-press-`. Nothing is checked or issued: a check names an independent second person. A failure part-way runs the removal on what was made; when that clean-up fails as well the message says so ("part of it is left; use Remove demo project to clear it") instead of claiming nothing was kept. The section dimensions of the published UC 203×203×46 (the steel-support column and the two base plates) are given their own provenance by the demonstration, "published UC 203×203×46 dimensions (indicative)", and are not cited to the invented specification the story's chosen figures cite (the pack templates' own example inputs, which every user sees, are unchanged).

4. **Removal is the one delete the calculation store makes, and it is narrow.** `CalcInstanceStore.DeleteDemonstrationRowsAsync` deletes in one transaction the instance and pack rows under the project's own key prefix and the exact scan-profile versions the install wrote (`demo-press-seal-stack@1` and `demo-press-seal-gland@1`; a later version a person saved is theirs and stays), with their search-index rows; a profile id without the prefix is refused, and an issued or superseded row stops the transaction (nothing is deleted). The service refuses first, naming the issued calculation, pack or Evidence record under the project, so an issued demonstration record is never deleted. The removal is two steps, the row transaction and then the soft delete, so the audit row is written between them: `Demo.Removed`, with the counts the transaction really deleted, is recorded the moment it commits, and a removal that finds no rows (a retry after the second step failed) records nothing again. If the soft delete fails the person is told "The demo's calculations were removed; finishing the removal failed — press Remove demo project again.", the project stays live and flagged, and pressing again finishes it; any other store failure is a one-sentence refusal, never an exception at the screen. The project and everything under it (the register entries and the Evidence) are then marked deleted with the platform's own soft delete, deepest first: the platform never erases an engineering object, its history stays, and the audit trail, which a removal never touches, gets one row for the install and one for the removal (`Demo.Installed`, `Demo.Removed`, with the counts). Rows of any other project are never read for deletion.

5. **A person asks, in the application's own dialog.** Settings → Demo project holds the two menu actions. Each asks in `ConfirmationDialog` and waits for the answer; a refusal or a No changes nothing; a removal is refused while the demonstration is the open project. `WorkspaceHost` builds the service and never runs it: nothing at start-up, on an empty database or on opening Settings installs anything.

## Consequences

- No new package, assembly, table, collection or migration. `CalcSheetHeader` gains one optional member (the golden sheets are unchanged: a null watermark prints nothing).
- A removed demonstration leaves its engineering objects as deleted tombstones (project, register entries, Evidence) and its audit rows; its calculation, pack and scan-profile rows are gone. Installing again makes a new project with new ids.
- A demonstration pack that has been issued cannot be removed; the message says which. The person can issue a copy in a project of their own instead.
- The synthetic cable tables and the published section dimensions of the steel-support example are the only figures not invented from nothing; the user page says so, and the sheets cite the section as published and indicative rather than as an invented specification's figure.
- `CalcInstanceStore.WriteGuardedAsync` now refuses a write that expects the stored calculation to be as the caller read it when the row is gone (a calculation deleted since), so a stale update cannot bring a removed demonstration calculation back. Writes that expect nothing (a new calculation) are unchanged.

## Follow-ups

- The soft delete leaves the project in `IProjectDirectory.ListAsync` (it does not filter deleted projects, for projects the person deletes from the explorer too); surfaces that list projects from it should filter deleted ones.

## Changes after the Addendum C security review

SEC-C-03 (`docs/reviews/security-review.md`, Addendum C). Decision 4 deleted the two scan-profile keys whatever they held. A person who had saved their own profile under `demo-press-seal-stack@1` or `demo-press-seal-gland@1` before the install (from a profile file) had it used by the install, which cannot overwrite a version, and then deleted by Remove. `DeleteDemonstrationRowsAsync` now deletes a profile version only when the stored text is the shipped profile word for word (`CalcDemoProject.ShippedProfile`); any other is kept. Test: `AddendumCSecurityRegressionTests.SEC_C_03_Remove_Keeps_A_Scan_Profile_The_Person_Saved_Under_The_Demonstrations_Id`.

SEC-C-05. After a removal, a window that still showed the demonstration could make a calculation in it: `CreateAsync` did not refuse a deleted project, and the row was then out of reach of Remove, which looks only for a live demonstration. `CreateAsync`, `CreatePackAsync` and `InstantiatePackTemplateAsync` now refuse a deleted project with one sentence (`CalcProjectDeletedException`, or the refusal string). A row that still lands there (a create that passed its check while the removal ran) is reported by `StatusAsync` as `LeftOver`; Settings then offers Remove demo project, which clears it through the same removal. Tests: `SEC_C_05_Nothing_New_Can_Be_Made_In_A_Deleted_Project`, `SEC_C_05_Remove_Clears_Rows_Left_In_A_Removed_Demo_Project`.

## Changes after the Addendum C colour-team reviews

B-C-02 (`docs/reviews/black-team.md`, Addendum C). A demo scan-profile version that a calculation of another project cites in its scan imports is kept, so that import can be repeated, and Remove names it (`CalcInstanceStore.DeleteDemonstrationAsync`, which returns the kept versions; `DeleteDemonstrationRowsAsync` stays as a wrapper). With SEC-C-03 the rule is both: a version is deleted only when it is stored word for word as the install writes it **and** no other project cites it. Only a shipped version spared by a citation is reported as kept. Test: `AddendumCColourRegressionTests.Integration_SEC_C_03_And_B_C_02_Remove_Deletes_Only_A_Shipped_Demo_Profile_No_Other_Project_Cites`.

B-C-03 settles the follow-up above: `IProjectDirectory.ListAsync` leaves deleted projects out, and `ListIncludingDeletedAsync` (which a project number stays unique against) keeps them. The demonstration's own status and left-over checks (SEC-C-05) read the engineering domain directly, so they still see a removed demonstration.
