# ADR-0177: A Superseded Template Version Stays Resolvable Through the Version Manifest, and a Calculation Made on It Re-Runs Only Where the Installed Formulas Reproduce It Exactly

## Status

Accepted (v0.26.0, owner decision DC-14, confirmed in DC-21). Builds on `ADR-0165` (the issued record is the Evidence: a sheet, outputs and a template content hash, byte-stable), `ADR-0166` (a checked calculation is never a dead end) and `ADR-0168` (a stale calculation is revised before it is checked or issued again). Adds no table, no collection and no migration: every document keeps the shape it has.

## Context

A worksheet template is C# code with an `id@version` reference; `CalcCatalogue` registered the current version of each template, and a calculation stores the reference it was made on, the content hash of that version and, once issued, its sheet, outputs and checks. When a template's version rose (42 of the 54 templates were bumped during this release, 30 of them more than once: 160 `id@version` lines in `TemplateVersionManifest.json` for 54 templates, 106 of them superseded), a calculation on the earlier version kept its stored sheet but its reference no longer found a calculator: the worksheet said "not registered in this build", a draft could not be edited and, since Grey GR-B-01, opened as a new sheet on the current version, and an issued or checked calculation could not be opened in the form at all. DC-14 asked the owner to choose between keeping superseded versions resolvable and taking display-only text out of the content hash; the owner chose the first: an issued calculation re-runs on the version it was issued on.

Three ways of keeping an old version's behaviour were weighed.

1. **A frozen definition per version.** Keep a copy of every superseded calculator class (160 today, growing with every bump) beside the current one, each registered under its own `id@version`. It is the only approach under which "re-run on its own version" is literally true for every past version. But the templates are code: a frozen copy is a second class with the same formulas, clause references, known-answer cases and golden sheets, which the common Definition-of-Done theories would then run and the engine, the units library and the shared modules would have to keep behaving identically for, for ever. Every fix to a shared module (a unit, a section property, a material rule) would change what a "frozen" copy computes while its hash claims it did not; and a defect found in an old version could be neither fixed (it is frozen) nor removed (it is resolvable). The maintenance cost is one more calculator per bump, for ever, with no one responsible for the copies.
2. **Version branches inside each calculator.** One class per template with `if (version < x)` around the formulas that changed. Every formula on a transparent sheet would then be a conditional, the content hash of one version would depend on the code of every later one, and the builders who change templates in parallel would edit the same branches; the review burden moves from a reviewed manifest diff into every calculator.
3. **Reproduce or read-only.** Keep one current calculator per template; make every version the product has ever recorded resolvable by `id@version` (what it was, what its content hash was, what it became); and, for a calculation whose own version is not installed, re-run it on the current version and compare, output by output and check by check, with what the calculation stored. Where every stored value comes out exactly as stored, the re-run is reported as reproducing the record; where anything differs, the calculation stays as stored, read-only, and one sentence says what differs and what to do. The stored record is never replaced by a re-run, so a version whose formulas moved cannot change an issued number.

The third is chosen, with the catalogue still allowing a frozen copy to be registered beside the current version for any specific version that ever needs it (a regulatory hold, for example): such a copy resolves as installed and a calculation made on it runs on its own formulas, which a test proves. That is a deliberate exception for a named version, not the rule for every bump.

## Decision

1. **The manifest is the list of resolvable versions.** `tests/Tempest.Calc.Tests.Library/TemplateVersionManifest.json`, the add-only record of the content hash of every shipped `id@version` (merge review finding 1), is embedded in `Tempest.Calc.Library` (the csproj links it) and read as `TemplateVersionHistory`. It stays where `TemplateVersionManifestTests` writes it, so the test that keeps it complete and the builders who add lines to it are unchanged; the file is never moved and never edited by hand. A line is a version the product knows; a version with no line is "unrecorded" (made on a build this one has no record of) and is treated as superseded without a recorded hash.
2. **`CalcCatalogue.Resolve(reference)` says what a reference is**, never throwing and never running anything: `Installed` (that version's own formulas are registered: the current version, or a frozen copy), `Superseded` (recorded, not installed, the current version is), `Unrecorded`, `Newer` (a version above the installed one: made by a newer build), `Withheld` (a feature flag, `ADR-0173`) or `Gone`. `Find` never returns another version's formulas for a versioned reference: nothing is silently run on code it was not made on. `Get` on a superseded version throws `CalcVersionNotInstalledException` (a `KeyNotFoundException`) whose message names the version it became.
3. **`CalcInstanceService.Rerun(instance)` writes nothing.** It runs the calculation's own inputs on its own version where that is installed, otherwise on the template's current version, and reports `Reproduced` only when every stored output (the SI number to the last digit, or the text where there is no number: the same value the outputs hash covers) and every stored check (verdict and utilisation) comes out exactly as stored, and the installed version adds no check the calculation fails. A stored output the version no longer gives, a changed value, a changed verdict, a run the version blocks or refuses, all give `Differs`, with the first three differences in the sentence and at most 20 symbols listed. A legacy archive, a withheld or gone template, a newer version or a calculation with nothing stored to compare gives `Unavailable` with the reason.
4. **`OpenOlderVersion(instance)` is what the worksheet shows** when the calculation's own version is not installed. A draft whose template has a current version is offered as a new, unsaved sheet on it with its inputs (the existing GR-B-01 upgrade, with C-2 aliases carrying renamed inputs under their new names, dropped inputs named), the draft left unchanged. A checked, issued or superseded calculation (or a draft that has nowhere to go: its version is newer than this build, or its template is gone) is shown as it was stored, read-only: the sheet as issued, or for a calculation that was never issued a capped summary of its stored results (500 rows a section), under one sentence that names the version it was made on, what that version became, the re-run's verdict and the way forward ("Revise it to carry its inputs to `id@new`"; for a checked one, "then check and issue it again"). Where the calculation's stored template fingerprint is not the hash the manifest records for its version, the sentence says it was made on a build of that version before its content was final.
5. **Revise is the way forward, and it already carries the inputs to the current version.** `ReviseAsync` reads the current version by template id; an issued calculation, or a checked one that is stale because its template moved on, revises to a draft on the current version with its inputs, the old record marked Superseded and nothing else about it changed. The worksheet's stored-record view offers Revise for an issued and for a checked calculation, and never Save, Check, Issue or an import.
6. **Every refusal names the version and the way forward.** Editing, checking, issuing, attesting, countersigning, linking, importing into or issuing a pack with a calculation whose version is superseded is refused with "was made on `id@old`, which has been revised to `id@new`" and what to do, instead of "no longer registered"; a version newer than the build says to open it in a build that has that version; a gone template keeps the old sentence.
7. **A new sheet is made on the current version**, whatever older versions are installed beside it: `Find(id)` and `Current()` are unchanged, and the catalogue tree lists only current versions.
8. **A symbol that came to mean something else is declared, and a value stored under it before the change is never carried, linked or bound** (review of this ADR). A version bump that keeps a symbol but changes what it stands for (an axis swapped, a width that became a depth) would otherwise carry an old number into a new meaning, and no re-run could tell. `CalcInputSpec` and `CalcOutputPort` carry `MeaningChangedAt` (the template version the meaning changed at, dotted digits), `MeaningWas` and `MeaningNow` (plain words); the catalogue refuses a change declared at a version the template has not reached or without both meanings, and a declared change is part of the version's content hash. A value stored under that symbol by a calculation made on an earlier version is not carried by the draft upgrade (named in `Dropped` and in the sentence), refuses Revise, refuses a new link by symbol or public name, is reported stale and is never moved to a later revision by "update links"; a pack binding or example saved from such a version is refused (`CalcPackStep` records the version a chain was saved from). A value stored under an alias keeps its meaning, since an alias is declared precisely because the old symbol is this input; and an old record holding one input under two of its names with different values carries neither, both named. A template declares it on the input it renamed the meaning of, for example `struct.section-properties` 1.2.0 if `W_el_y` came to mean the modulus about the major axis: `new CalcInputSpec("W_el_y", "Elastic modulus about y-y", CalcInputKind.Quantity, "mm^3", MeaningChangedAt: "1.2.0", MeaningWas: "the elastic modulus about the minor axis", MeaningNow: "the elastic modulus about the major axis")`; the sentence then reads "W_el_y meant the elastic modulus about the minor axis on struct.section-properties@1.1.0; since struct.section-properties@1.2.0 it means the elastic modulus about the major axis".
9. **A default unit that changed is declared, and a bare stored number is read in the unit of its own version** (review of this ADR). A stored value may carry no unit of its own (a bare number read in the input's default unit); when a version changes the default unit, that number would be read in the new unit, a hundred times out for bar→kPa and still within the hard range. `CalcInputSpec` and `CalcColumnSpec` carry `UnitChangedAt` (the version) and `UnitWas` (the unit before it, another unit of the same dimension); the catalogue refuses anything else, and a declared change is part of the content hash. `CalcInputUnits` is the one place a unit is resolved, used by the binder, the validator, the runner, the CSV and JSON readers, the sheet builder, the draft upgrade and Revise: a value with a unit of its own is read in it; a bare number is read in the default unit of the template version the values were recorded on (`CalcInputSet.MadeOn`, which a stored calculation gives from its reference through `CalcInstance.InputSet()`); a new sheet reads a bare number in the new unit; a bare number on a record that carries no version (an inputs file, a CSV, a legacy record) is refused with one sentence naming the symbol and both units. The draft upgrade and Revise carry a bare number with the unit it was recorded in made explicit, so the carried value means what it meant; the runner does the same before a calculator reads its table cells. A template declares it on the input whose default unit it changed, for example `bs.sealed-system` if `p_margin` moved from bar to kPa at 1.3.0: `new CalcInputSpec("p_margin", "Pre-charge margin over static head", CalcInputKind.Quantity, "kPa", Default: 30, Min: 0, Max: 100, HardMin: 0, HardMax: 200, Group: "Pressures", UnitChangedAt: "1.3.0", UnitWas: "bar")`; a bare 0.3 stored on 1.2.0 is then 0.3 bar (30 kPa) wherever it is read, and a column does the same with `new CalcColumnSpec("p", "Pressure", CalcInputKind.Quantity, "kPa", UnitChangedAt: "1.3.0", UnitWas: "bar")`.

## Consequences

- No new package, assembly, table, collection or migration; the Library gains one embedded resource (about 12 KB), linked from the tests folder. An installed build therefore carries the manifest, and `SupersededVersionTests.The_Embedded_Manifest_Is_The_Committed_Manifest` fails if the two ever differ.
- "Re-run on its own version" is literal where the version is installed (the current one or a kept frozen copy) and is otherwise a verified reproduction on the current version: the sentence always says which. A re-run that does not reproduce the record changes nothing and says why; an engineer who needs the old numbers has the issued sheet, which is the Evidence.
- A version bump that changes only wording or a display-only field reproduces every record made on the earlier version, so the owner's common case (a template reworded, an older issued sheet opened) re-runs cleanly. A bump that changes a formula shows the stored sheet read-only with the differing symbols named, which is the honest outcome: the record was issued on formulas this build no longer has.
- The manifest is now product data read at run time as well as a test fixture. The parse refuses a line that is not `id@version` with a 64-character lower-case hex hash and a file over 4 MB, and the shipped file is read once per process.
- A re-run on the current version is a verified replay, and a replay of the manifest's 106 superseded versions on the current one reproduces about 55 % of them for any record, about 25 % for some records only (where a changed check or limit catches particular inputs) and about 20 % not at all (a changed formula: those open read-only with Revise). A frozen copy per released version (Follow-ups) remains the way to make "re-run on its own version" literal after the first release; nothing has been released yet, so no version in the manifest has an issued record behind it.
- Tests: `SupersededVersionTests` (Library: manifest-driven resolution of every recorded version, the six states, a frozen copy re-running on its own version, reproduction, difference, revise forward, the draft upgrade, a newer build's calculation, gone and unrecorded, the caps), `MeaningChangeTests` (a declared change of meaning: the catalogue's refusals and hash, the draft upgrade, Revise, links, "update links", pack bindings, two old names of one input), `UnitChangeTests` (a declared change of unit: the catalogue's refusals and hash; a bare number read, re-run, shown and carried in its own version's unit; a value with its own unit; a new sheet; a record with no version refused on the run, the validator, the binder, a CSV and an inputs file) and `WorksheetSupersededVersionTests` (Desktop, headless: an issued calculation opens as its stored sheet read-only with the sentence and Revise carries it to the current version; a changed formula opens read-only saying why; a checked one shows its stored results and offers Revise not Issue; an old draft opens as a new sheet with its inputs under their new names; a new sheet is offered on the current version only and a kept older version still opens its own calculations).

## Follow-ups

- Where a specific version must stay literally re-runnable (a client or regulatory hold), register a frozen copy of that calculator under its own `id@version` beside the current one and add a known-answer case to it; the catalogue, `Resolve`, `Rerun` and the worksheet already treat it as installed.
- A calculation's `TemplateHash` could be shown against the manifest's recorded hash in the register, so a record made on a pre-release build of a version is visible without opening it.
