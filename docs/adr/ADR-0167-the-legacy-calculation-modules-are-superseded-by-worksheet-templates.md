# ADR-0167: The Legacy Calculation Modules Are Superseded by Worksheet Templates

## Status

Accepted (v0.27.0, Phase 0). Owner request of 2026-10-23, recorded as D-38 and D-39; the comparison is `docs/reviews/legacy-calculators-review.md`.

## Context

Two calculation surfaces exist after v0.26.0. The legacy one (`Tempest.Core.Calculations`: five original definitions, eleven `WP 21.7A` modules, the v0.16.0 tolerance stack and two thermal modules; `CalculationModulesView` with Re-run and Compare) records named intermediates, never reaches Evidence, throws on invalid input and carries no clause references. The new one (`Tempest.Calc.*`, ADR-0165) shows every step as formula → substitution → result, carries provenance on every input, cites clauses, refuses instead of throwing, and issues through the Evidence lifecycle in one transaction. The owner asked that the lower-quality surface be replaced and the higher one raised where the other was better.

## Decision

1. **Every legacy module becomes a `Tempest.Calc` template** (mapping in the review): six are already covered by shipped templates and gain the legacy outputs they lack; nine are ported; two are retired as covered. Each port carries the legacy module's test vectors as known-answer cases with the same figures and the same five-significant-figure tolerance, so no expected value is lost.
2. **Stored legacy runs stay readable.** A migration reads every `CalculationRecord` (through `CalculationEngine.ListRecordsAsync` and the untyped record document) and writes a `CalcInstance` snapshot: status Draft, inputs with Manual provenance, the intermediates as recorded outputs, the original `ExecutedAt`, principal and revision kept in the snapshot's name and notes. The legacy engine, its persistence and its read-back, retention and corruption tests are kept until the migration passes the Grey upgrade test on real v0.25 and v0.26 databases; only then are the legacy definitions, descriptors, diagrams, the Desktop surface and their tests removed (non-negotiable #3: nothing is deleted to make something pass; the records are migrated, not dropped).
3. **The new surface is raised** where the legacy one was better: every template spec gains an "In plain terms" paragraph and the hand arithmetic of one worked example; the worksheet form fills material, fastener and bearing inputs from released reference records with a `FromReference` pin (the legacy descriptor's `Library` / `SourceProperty` pattern, carried over).
4. **Compare** (two runs side by side) is reimplemented over calc instances of one template before the legacy surface goes.

## Consequences

- The Desktop ends with one calculation surface (Worksheets) and one lifecycle (Evidence); the legacy "Engineering Calculators" node disappears in Phase 4.
- Phase 1 adds a migration step to the upgrade path; a database that holds legacy records opens with the same records as draft worksheets.
- The lean-Markdown rule (D-04, CONTRIBUTING) is kept: the spec prose is counted against the examples' README lines already in the tree.
- Until Phase 4, both surfaces ship; the release notes say which to use (Worksheets).

## Amendment 1 (2026-10-23, v0.27.0 Phase 4): the Calculators surface is retired

Preconditions met: every legacy module has a worksheet template (Phases 1–3); the record migration passes the Grey test on real v0.25.3 and v0.26.0-rc1 databases (`GreyLegacyDatabaseTests`, 46 records of all 19 calculations); Compare is reimplemented over calc instances (`CalcInstanceComparer`); and every template draws its reference diagram in the worksheet form (D-41, `CalcDiagrams`).

Retired: the Desktop `CalculationModulesView` and its coordinator, the Engineering → Calculators node (Worksheets takes its place), `CalculationModuleWorkbench` and `CalculationModuleService`. Kept: the legacy engine, its persistence and read-back tests (the migration reads through them); the fourteen module definitions, their descriptors and vector tests until Phase 5 Green confirms each vector is carried; the form record and the diagram model (`CalculationModuleForm`, `Diagrams/*`), which the reference diagrams and `ModuleGuards` still use.

Tests superseded, each by the test named:

| Retired test(s) | Superseded by |
|---|---|
| `CalculationModulesViewTests` (10: catalogue, generated form, record pickers, calculate, re-run, compare, status) | `CalcSheetViewTests` (catalogue, form, reference pickers, live run, archives, compare), `CompareTests`, `ReferenceFillTests` |
| `CalculationModuleServiceTests` (20: governed run on pinned records, refusals, fills) | `ReferenceFillTests` (released records only, pins, refusals) and each template's known-answer cases |
| `CalculationModuleWorkbenchTests` (7: named runs, re-run, compare) | `CompareTests`, `CalcInstanceServiceTests` (create, revise, register entry) |

## Amendment 2 (2026-10-25, integration into v0.26.0): the legacy replacement ships in v0.26.0

The owner decided that all work on `release/v0.27.0` is brought into the v0.26.0 release line and that nothing ships as 0.27.0. The decisions D-39…D-47 keep their numbers (D-38 was already in the v0.26.0 decisions); the CHANGELOG, release notes and handover carry the work as a marked section of v0.26.0. Three overlaps with Addendum A and Addendum B were settled when the lines met:

1. **`mech.bearing-life`.** Addendum A's M5 (`mech.bearing-life`, ISO 281:2007 with a duty cycle, a₁ derived from a stated reliability, a_ISO and the static safety factor) keeps the id. The port of the legacy `calc.bearing-rating-life` used the same id and path; it was checked against M5 and **does not reproduce every legacy vector**, so it is kept under a new id, **`mech.bearing-life-basic`** (`BearingLifeBasicCalculator.cs`, spec `docs/calcs/mechanical/mech.bearing-life-basic.md`): (a) the legacy third example enters the reliability factor a₁ = 0.64 directly, and M5 has no a₁ input (it derives 0.6379 from 95 %), so L_nm 164.75 and L_nmh 2745.8 h cannot be reproduced; (b) the legacy outputs include the load ratio `k_P`, which M5 does not report; (c) the legacy module blocks at P > 0.5·C and below a millionth of C, where M5 only warns or caps. Examples 1 and 2 (a₁ = 1) do agree with M5 to five significant figures for P, L₁₀ and L₁₀h, and a test (`BearingLifeBasicTests`) pins that agreement and the three differences. The legacy-module mapping is therefore: `calc.bearing-rating-life` and `calc.bearing-load-capacity` → `mech.bearing-life-basic` (same symbols); a person who wants the full ISO 281 sheet re-enters the inputs in `mech.bearing-life` with `type`, `C`, `F_r`, `F_a`, `n`, `L_req` carried over, the legacy `X`/`Y` as `X_1`/`Y_1` (radial-only) and `X`/`Y` with `e_lim`, and `a_1` replaced by the reliability `R`. All the port's tests are kept, re-targeted at the new id.
2. **`mech.lifting-lug` is gated like the rest of lifting (`ADR-0173`).** Addendum B put lifting behind the `lifting` feature flag, including the legacy `calc.lifting-lug-pin-joint`. The port is a lifting design calculation, so it is gated the same way and, like S8, demands what ADR-0173 §2 demands: `FeatureFlag = CalcFeatures.Lifting`, `RequiresAttestation` (with the three attestation inputs), `IndependentCheck` and `RequiresSecondCheck`; its id is in `CalculationFeatureGate` so the engine refuses it while the feature is off; its sheet prints the design-calculation and unauthenticated-signature notices. Version 1.1.0 (from 1.0.1) adds only this governance; the arithmetic and the two legacy known-answer cases are unchanged. A migrated legacy lifting record opens as a read-only archive sheet whatever the flag says (reading is not running), and the legacy definition is refused by id while the flag is off.
3. **The Calculators surface stays retired; the gate stays where the legacy definition is reachable.** Amendment 1's retirement of `CalculationModulesView`, `CalculationModuleWorkbench` and `CalculationModuleService` is kept. The gate that the service and the workbench applied to the legacy lifting module (`ModuleSwitchedOff`, `AvailableCatalogue`) went with them; the engine's own gate (`CalculationFeatureGate`, consulted at `CalculationEngine.ExecuteAsync` and so at both `ReRunAsync` overloads) remains, and the tests that exercised the service gate are re-targeted at it (`GatedLiftingModuleTests`, `GatedEngineExecutionTests`). The two surface tests that offered or withheld the module (`TheLiftingModule_IsOfferedOnlyWhileTheLiftingFeatureIsOn`, `WithTheLiftingFeatureOff_TheSurfaceOffersEveryCalculationButTheLiftingLug`) tested a surface that no longer exists and are superseded by the catalogue tests in `LiftingGovernanceTests`, which now cover both lifting worksheets.

Other overlaps are different templates and are all kept: `mech.shaft-stress` (legacy shaft module) beside Addendum A's `mech.shaft`; `struct.fillet-weld` (legacy simplified method) beside S4 `struct.connection-ec3` and M6 `mech.weld-group`; `bs.plane-wall` beside B4 `bs.room-heat-loss`. Where both lines changed one template (`bs.pipe-pump`, `bs.psychrometrics`, `elec.enclosure-heat`, `elec.motor-sizing`, `mech.bolt-group`, `mech.iso286-fit`, `mech.tolerance-stack`, `struct.frame-2d`) both sets of changes are merged and the template moves up one minor version; `mech.bolt-group` keeps Addendum A's unsymmetric-bending kernel and its `collinear` rule in place of the port's `unresisted-moment`. The method-narrative rule (D-46) now applies to every template, so 22 templates of Addenda A and B had method labels reworded and moved up one patch version, and 29 specs gained the "In plain terms" paragraph.

Reference diagrams (D-41, Principle 33) exist for the 27 templates of this line only; the templates added by Addenda A and B have none yet. `CalcDiagramsTests` lists them as an explicit exemption (it fails if a listed template gains a diagram without leaving the list, or an unlisted template has none), and drawing them is a follow-up (TASKS).
