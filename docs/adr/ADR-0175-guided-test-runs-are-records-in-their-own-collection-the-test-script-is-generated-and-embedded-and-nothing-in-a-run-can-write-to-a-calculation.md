# ADR-0175: Guided Test Runs Are Records in Their Own Collection, the Test Script Is Generated and Embedded, and Nothing in a Run Can Write to a Calculation

## Status

Accepted (v0.26.0, Addendum C, Track S, C-5). Builds on `ADR-0144` and `ADR-0145` (one SQLite store of collections of JSON documents), `ADR-0120` (durable state carries a version, additions only), `ADR-0165` (the worksheet engine, whose "Import inputs (CSV/JSON)" path the guided test reuses) and `ADR-0173` (the Lifting feature flag, which the lifting steps of the script are about).

## Context

Addendum C §C6 C-5 asks for a guided test mode: the app walks the owner through the owner test pack, shows each step, opens the worksheet with the example's inputs loaded, shows the expected outputs and the tolerance, and lets the tester mark Pass, Fail, Blocked or Skipped with a note. The results are kept as a test-run record with the date, the build commit and the tester, and the dashboard (C-4, built at the same time) wants to show "manual test status" per calculator. It must never alter a calculation or an Evidence status.

Five questions follow.

1. Where do the steps come from, given that `docs/` is not in an installed build?
2. What does "compare to the digits shown" mean when the form rounds to five figures and the printed expected value has up to six?
3. Where is a run stored, and how does adding it stay additive?
4. How does the dashboard read the latest manual result without being able to write one?
5. How is "a guided run changes no calculation" made true rather than promised?

## Decision

1. **The script is generated from the docs and embedded.** `scripts/generate-guided-test-script.py` reads each worked example (`inputs.json`, the inputs table of `sheet.txt`, the README "Output | Expected | Computed" table and its governing-check line) and the manual sections of `docs/testing/v0.26.0-runbook.md` (smoke test, linked packs, imports, lifting, legacy records), and writes `src/Tempest.Calc/Tempest.Calc.Library/ManualTesting/guided-test-script.json`, which the library embeds as a resource. The script has a format number and a version (`<release>+<8 hex of a hash of the steps>`), so a run knows which script it was started on. A test (`GuidedTestScriptStalenessTests`) re-reads the docs with its own parsers and fails when the shipped script differs from them; it also runs the generator's `--check` where Python is present. Every size in the script is capped and `GuidedTestScript.Parse` refuses a script over a cap with a one-sentence reason.

2. **One tolerance rule, stated on screen.** A number passes when it differs from the expected value by no more than half a unit in the last digit of the less precise of the two, the digits counted as written; the form shows five significant figures with trailing zeros dropped, so a shown value is taken at its five-figure place whatever zeros were dropped. This is exactly the difference two roundings of one true value can reach, so a correct result never fails and a wrong one that differs in a digit both show does. A text (a governing PASS or FAIL) must be identical. The arithmetic is exact (integers scaled by powers of ten). A different unit is not decided by rule; it is left to the tester. The rule is `GuidedTolerance`; it is not a looser tolerance than the brief's, it is the brief's applied to a form that rounds.

   **A finding the rule exposed.** The expected values in the worked-example READMEs are hand calculations or published figures held to each example's own verification tolerance (`CalcExpectedValue.RelativeTolerance`, 1 % by default, and in one case a placeholder `0 Pa` at 1e9), not to the digits printed. In 12 of the 87 examples one or more outputs differ from the printed expected value by more than half a unit in its last digit although the engine is right (it equals the README's own "Computed" column). The auto-compare therefore puts such a line to the tester ("decide by hand") instead of calling it a fail, and records the rule it applied; it never passes it silently and never fails it. The 12 are listed in a closed list in the tests, so a thirteenth is noticed. Tightening the printed expected values, or adding a tolerance column to the READMEs, is a decision for the owner (it touches all 87 READMEs and every regeneration of them).

3. **A run is a document in a new collection, `Manual.TestRuns`.** The persistence store is a set of collections of JSON documents (`ADR-0144`); a collection comes into being on its first write, so there is no DDL and no change to the store's `SchemaVersion`, and nothing existing is read, rewritten or dropped (the "additive migration" is that: the migration is the absence of one). A run carries its own `Schema` (1): a reader that finds a newer schema, or a document it cannot parse, leaves it out of every list rather than failing, so a database written by a later build still opens. A run holds the run id, started and finished (UTC), the build as the title bar shows it and its short commit, the tester (the person the app signs work off as: display name and sign-in id), the script version and one result per step (outcome, note capped at 2,000 characters and refused, never cut, when longer; values shown capped at 4,000 characters; recorded time). A run is unfinished until it is finished; an unfinished run can be resumed, only by the person who started it and only on the script it was started on; a finished run is never changed. The store keeps at most 1,000 runs and refuses to start another.

4. **The dashboard reads through `IManualTestStatusSource`**, in `Tempest.Calc.Library.ManualTesting` (the non-UI project the Desktop and the tests already reference): one method, `LatestByTemplateAsync`, returning template id to `ManualTestStatus` (outcome, date, build commit, tester, run, examples recorded of examples in the script). A template's status is the worst (Fail, then Blocked, then Pass) of the latest non-skipped result of each of its worked examples, dated by the most recent of them. `ManualTestRunService` implements it; a dashboard that holds the interface cannot write a run.

5. **A guided run cannot write to a calculation.** `ManualTestRunService` is given the persistence store and writes only `Manual.TestRuns`; it holds no calculation service, no Evidence service and no issue state. The worksheet is opened for a step as a scratch, unsaved form (the same path as "Import inputs", which seeds the form and saves nothing); a form with unsaved edits is not replaced without a second press. `GuidedRunNoSideEffectsTests` runs a full guided run over the shipped script beside a draft and an issued calculation and asserts that every other collection, text and byte, is identical afterwards.

## Consequences

- The owner can run the whole pack inside the app and get the results sheet (the runbook's section 11 table, plus the commit, tester and dates) as markdown.
- A change to a worked example, its expected table or the runbook makes `GuidedTestScriptStalenessTests` fail until `python3 scripts/generate-guided-test-script.py` is run. The same command belongs after any regeneration of the worked examples.
- The script adds about 0.5 MB to the library.
- A tester who presses Save on the scratch worksheet creates a calculation as any worksheet user would; that is the worksheet's own act, not the guided test's, and the panel says the form is a scratch.
- Followed up: the dashboard (C-4) can show manual status per template with no further work in this project; a tolerance column for the READMEs would make the 12 examples auto-comparable.

## Changes after review

The review of the first build found twelve things to change. None alters the five decisions above; each is a tightening of them. The decisions that were a choice between options are marked and are listed for the owner in DECISIONS.

1. **Compare reads only the step the worksheet was opened for (M1).** The view model remembers the example it last opened the form for and refuses Compare for any other step with a sentence (opening one example of a template, then selecting a sibling example and pressing Compare used to compare the sibling's expected values with the first example's run). The host hands out the form's run only while the form is exactly what `Prepare` left: the template, no calculation behind it (a scratch sheet), not marked stale, and its inputs the very text that was loaded.
2. **A comparison goes stale with the form (M2).** The host raises `FormChanged` when the form's inputs or its run change after `Prepare` (and only when what the form shows really differs, because the form raises its change events for work that leaves the inputs alone). The view model then takes back the comparison, the tick it made and the values it filled in; a result the tester ticked or values they typed are theirs and stay. `RecordAsync` also reads the form again when the tick or the values came from a Compare, and refuses (clearing them) when the form no longer gives the same values and result. A Compare-ticked Pass could be recorded with the old values after the form had been edited; it cannot now.
3. **No unguarded I/O in a button handler (M3).** Every handler that reaches the store, the clipboard or a file goes through `GuidedTestViewModel.RunGuardedAsync` (the same shape as `CalcSheetCoordinator.GuardedAsync`): a refusal is its own sentence, any other failure is "Could not <what>: <reason>" in the status line, and an exception is never left for a handler nobody awaits. The synchronous handlers (open worksheet, compare) are guarded too.
4. **A run needs a signed-in person (L4).** `StartAsync` refuses with a sentence naming the sign-in when the person has no id, and every change compares ids: a run kept under no id (an earlier build, nobody signed in) can no longer be added to by anyone. It can be finished by whoever is signed in, so that it can be cleared away (nothing is added by finishing).
5. **A long note is counted, not cut (L5).** The note box no longer stops at 2,000 characters (it holds 20,000, a cap that only keeps the box usable; the view model says so when it leaves text out). A counter shows `n of 2,000 characters`, or by how many it is over; the service still refuses a longer note when it is recorded, naming the step, and never cuts it.
6. **The allowance applied is shown (L6).** The expected line states the allowance of the expected value as written; after a compare it also says "allowance applied ±x", the coarser of the expected value's last place and the form's displayed last place, which is what the verdict used.
7. **A draft survives leaving the screen (L7).** Showing the Guided test node again re-reads the runs but keeps the tick, note and values for the same step; only a different step, or a run started or resumed, starts from what is recorded. Moving to the step already shown (Next on the last step) changes nothing.
8. **The results sheet (L8).** `<`, `>` and `&` are HTML-encoded in every cell and header line (the sheet's own `<br>` for a line break is the one tag left), the file is written to a temporary file in the same folder and moved over the target (`ManualTestMarkdown.WriteFileAsync`), and the "known defects" file named at the foot follows the script's release instead of a fixed `v0.26.0`.
9. **The governing check's name, and "none" (L9).** The compare reads the name with the outcome (`PASS — <name>`), so a worksheet whose governing check is another one is a difference although both pass. An example whose README says `Governing check: none` now asserts that the form has none (a line `governing check`, expected `none`).
10. **A pressure basis is part of the unit (L10).** `bar`, `bar a` (absolute) and `bar g` (gauge) are no longer taken for one another; any pair of them that differ is left to the tester with the existing "compare them by hand". One worked example (`fp.accumulator/clamp-circuit-bladder-accumulator`, p0 printed in a bare bar, shown by the form in bar a) is therefore put to the tester instead of passing; it joins the closed list of examples that need a look, now 13 (12 differ in the digits, one in the basis of a pressure).
11. **Clearing the run store is in the app (L11). A choice: delete, not reword.** The platform's deletion rules are about engineering objects (soft delete, the append-only audit and revision histories); a test-run record is none of those, it is not Evidence, and it is exported as the results sheet that is sent back. So the cap message ("ask for the old ones to be cleared") now points at a real action: **Delete older finished runs…** on the Guided test screen. It deletes only finished runs beyond the newest 50 (`ManualTestRunService.DefaultKeepFinished`), only from `Manual.TestRuns`, never an unfinished run, and never a finished run that still holds the latest counted result of a worked example (the dashboard's status is worked out from the runs on file, so deleting such a run would change what it shows); it asks through the app's confirmation dialog first, naming the count, and needs a signed-in person. The screen no longer deserialises every run each time it is shown: it counts the finished ones from the stored text (a finished run carries a `FinishedUtc` property, and no note can contain that name as such because its quotes are escaped) and reads only the unfinished ones, and it now finds an unfinished run behind any number of newer finished ones (the earlier listing looked only at the newest 100).
12. **What counts as a template's manual status (L12). A choice: count final results only.** `LatestByTemplateAsync` now counts only results from **finished** runs made on the **current script version**. A result in a run still being worked on may yet change, and one made against an earlier script was made against worked examples that may since have changed. The alternative (exposing the script version and a finished flag in `ManualTestStatus` and leaving the dashboard to choose) would put a rule that belongs to the test in every reader. The consequence is that a tester has to finish a run for its results to reach the dashboard, which the panel already asks for; `ManualTestStatus` and `IManualTestStatusSource` are unchanged.
13. **The generator and its test (L13).** The generator stops, naming the example, on a `Governing check:` line it cannot read, or a README without one, unless the line says `none` (so a typing slip can no longer turn "must show this check" into "must show none"); the runbook is named from `VERSION` (`docs/testing/v<VERSION>-runbook.md`) instead of a fixed release; and the staleness test that runs the generator is an xUnit skip with the reason "skipped: Python not available" where there is no Python (`PythonFactAttribute`), not a silent pass. Three tests drive the generator against a scratch copy (a bad line, a missing line, `none`, another release).

The tests are `ManualTestRunServiceReviewTests`, `GuidedToleranceTests`, `GuidedAutoCompareTests` and `GuidedTestScriptStalenessTests` in `Tempest.Calc.Tests.Library`, and `GuidedTestReviewTests`, `GuidedTestWorksheetTests` and `GuidedTestViewTests` in `Tempest.Desktop.Tests`.

## Changes after the Addendum C security review

SEC-C-02 (`docs/reviews/security-review.md`, Addendum C). The half-unit rule of decision 2 took an expected value written as an exact `1`, `5` or `0.6` as rounded to that digit, so it allowed ±0.5 (50 %), ±0.5 (10 %) or ±0.05 (8 %): a utilisation of 1.4 against an expected 1, or 4.55 A against 5 A, was a Match and the auto-compare suggested Pass. In the auto-compare (`CompareShown`) the allowance is now also capped at 1 % of the expected value (`GuidedTolerance.ShownRelativeCapPercent`, the worked examples' own default verification tolerance), and never below half of the form's own last displayed place, so a correct value as the form shows it still agrees. The rule text and the expected line say so (`±1 % of 5`). Values the tester types (`CompareNumbers`) keep the half-unit rule. One example joins the closed list of examples that need a look, now 14: `mech.iso286-fit/h7-g6-25mm`, whose README prints the standard's rounded es = −7 µm and c_min = 7 µm where the engine gives 7.2853 µm. The tests are `AddendumCSecurityRegressionTests` (`SEC_C_02_*`) and the updated `GuidedToleranceTests` and `GuidedAutoCompareTests`.
