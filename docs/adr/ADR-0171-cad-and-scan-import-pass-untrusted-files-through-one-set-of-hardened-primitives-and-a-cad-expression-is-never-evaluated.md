# ADR-0171: CAD and Scan Import Pass Untrusted Files Through One Set of Hardened Primitives, and a CAD Expression Is Never Evaluated

## Status

Accepted (v0.26.0, Addendum B, B-4, W1). Extends `ADR-0165` (the worksheet engine and Evidence), `ADR-0168` (linking and staleness) and `ADR-0170` (the M1 stack engine W1 feeds). W2 (scan deviation import) reuses the primitives decided here.

## Context

Addendum B §B6 W1 reads parameters out of CAD files — NX `.exp` and `.xlsx`, Creo relations and parameters, SolidWorks design tables and equations, Onshape variables, a generic CSV/JSON schema — and puts them into worksheet inputs (the CAD-driven tolerance chain: W1 → M1 → M2/M8). W2 will read scan deviation tables the same way. These files come from outside the trust boundary: anyone can send an engineer an `.exp` or an `.xlsx`. §B8 puts both parsers in the Security and Red-team scope: zip bombs, XXE, oversized rows, decimal-comma confusion, CSV injection, path traversal.

Three design questions had to be settled once, for both importers:

1. How is an untrusted file read — and in particular how is a workbook read (a package, or hand-written)?
2. What is done with a CAD *expression* (`edge = (plate_w - hole_d)/2`, `"Flange_W" = "Plate_W" * 2`)?
3. How does an imported value keep its origin, and what happens when the same file is imported again after the CAD model changed?

## Decision

1. **One assembly of hardened primitives, `Tempest.Calc.Import`** (depends on Engine and Sheets only; tests in `Tempest.Calc.Tests.Import`, in the solution and both CI Calc legs):
   - `BoundedInputReader`: streaming read with a hard 5 MB cap enforced while reading (a stream that lies about its length or never ends stops at the cap), a time limit and the caller's `CancellationToken`, strict UTF-8 (a BOM is dropped; UTF-16/32 and invalid sequences are refused), and refusal of every control character other than tab, CR and LF. The SHA-256 of the bytes is taken at the same point.
   - `LocaleNumber` / `NumberProfile`: numbers are read as the file's *declared* format says (decimal point or decimal comma, optional grouping character, strict groups of three); a number in the other notation is refused with a message, never reinterpreted; nothing is taken from the machine's culture. `.xlsx` stores numbers with a point and is read that way.
   - `ImportPath`: refuses traversal (`..`), network shares and device prefixes, alternate data streams, drive-relative forms, Windows reserved names, trailing dots and spaces, control and invisible characters, anything outside a required root, and a file that is a link.
   - `CsvReader` (RFC 4180, strict quoting, row/column/field caps) and `CsvSafeWriter` (a text whose first visible character is `=`, `+`, `-`, `@`, tab or CR — or the full-width forms — is written with a leading apostrophe; numbers go through a separate invariant path).
   - `XlsxReader`: see 2.
   - One documented exception, `ImportRefusedException` with a stable `ImportRefusalCode`; the fuzz/property tests (CsCheck) assert that no other exception escapes and that the importer's own defect code (`Internal`) never occurs.

2. **`.xlsx` is read by a hand-written reader over `System.IO.Compression` and `XmlReader`, not ClosedXML.** Addendum B §B5 allows ClosedXML (MIT), and the brief offers either. The choice is the hand-written reader because the import needs *less* than a workbook library offers: cell values only — shared strings, inline strings, numbers, booleans, error codes and, for a formula cell, the cached value; no styles, no formula engine, no object model. A library that opens a package and can evaluate formulas is the larger attack surface for that need, and a new package means a new supply-chain entry, lock-file churn in every dependent project and a third-party-notices line, for code that is about 650 lines here and is fully covered by the hardening tests. The reader: checks the archive's entries before opening anything (entry count, names, declared sizes, per-part and total expanded size, expanded:compressed ratio once a part passes 1 MB); counts the bytes a part actually produces against the same caps while reading, so an archive whose directory lies is stopped as well; refuses a workbook with macros (`vbaProject.bin`, macro-enabled content type, macro sheets); reads XML with DTDs prohibited and no resolver, so no entity or external reference is ever expanded; never follows an external link; ignores embedded objects; never reads, keeps or evaluates a formula. If a later need is beyond this (styles, dates as dates, writing workbooks), ClosedXML is the approved package and the reader's interface (`XlsxWorkbook` of sheets of rows of cells) is the seam to swap behind.

3. **A CAD expression is read-only text.** A right-hand side is a *literal* only when it is exactly a number (in the declared format) optionally followed by a unit, a boolean word, or a quoted string; everything else — a reference, a function, an operator — is an `Expression` parameter, kept as text and never evaluated, and a mapping that points an input at one is refused with a message. A formula cell in a workbook gives its saved result, never a re-evaluation, and the result is flagged as coming from a formula. Units are parsed by the engine's own `UnitCatalog` (with a short alias table for CAD spellings such as NX's `MilliMeter`); a unit the engine does not know leaves the value unmappable. The engine's `UnitCatalog.TryParse` is not total on hostile text (a huge exponent in a unit raises `OverflowException`, not a unit error), so every call from an importer is contained in `CadUnits.TryParseEngine`; the engine itself is untouched.

4. **Mapping profiles are named, versioned, typed and immutable.** A profile maps CAD names to template input symbols (or to a cell of an existing table row, `contributors[2].nominal`), with an optional assumed unit for a value the file states without one. Mapping checks the *dimension* against the input's own unit — a length into a force input is refused — and keeps angles, ratios and counts apart although the engine treats all three as dimensionless. A name in the file that the profile does not list is reported (unmapped, or read-only expression), a name the profile lists that the file lacks is reported (and refused when marked required), a name assigned twice has no single value and is refused, and while anything is refused nothing is applied. A stored profile version is never overwritten; a change is a new version (`Calc.ImportProfiles` collection, like reference records).

5. **Provenance is a new kind, `CalcProvenanceKind.CadImport`, appended at the end of the enum.** None of the existing kinds fits: `Drawing` and `Specification` carry a number and a revision, `Evidence` must resolve to an attachment, `Reference` is a record pin and `calc:` links are checked as such. The reference carries the CAD system and version, part, part revision, the full file SHA-256, the import time and the CAD parameter's name; the revision carries the profile `id@version`. The reference is held to the existing 200-character cap by shortening the part and parameter names, never the hash. Nothing in a template hash reads the kind, so no template hash changes. The worksheet form keeps the provenance of a CAD-imported input on save exactly as it does for a link pin. The full facts of the import — file name, hash, every parameter of the file as it was — are kept on the instance (`CalcInstance.CadImports`, one record per source), and carried into a revision.

6. **A re-import is an ordinary input update.** `CalcInstanceService.ApplyCadImportAsync` maps the file, compares it with the instance's previous import record (added, removed and changed parameters, and which of them move an input), and updates the draft through the same `UpdateInputsCoreAsync` path as any edit, with the import record committing in the same write. No staleness path is added: a calculation linked to the draft goes stale because the draft's outputs changed, through the machinery of `ADR-0168`. A checked, issued or superseded calculation is never changed in place; it is revised first. A parameter that disappeared from the file leaves its input at the last imported value, and the diff says so.

## Consequences

- W2 starts from tested primitives (bounded reader, strict numbers, CSV in and out, the workbook reader, paths, limits with a `Scan` preset of 1e6 rows) and only adds scan statistics and its own profile type.
- `CalcInstance` gains an optional `CadImports` list (omitted from stored JSON when empty); `CalcProvenanceKind` gains `CadImport`; `CalcInstanceStore` gains the profile collection. Stored instances and template hashes are unchanged.
- The hand-written reader reads what Excel writes and what the generators write; an exotic workbook feature it does not read (a cell in a table part, a value only in a drawing) is simply absent, never wrong. The cost of that choice is that the reader is ours to keep correct; the fuzz suite and the ratio/directory tests are the guard.
- An imported number is as trustworthy as the CAD file's author and the profile's author: the provenance says which file and which profile, and the preview says what each name became; it does not say the CAD model is right.
- Staleness on a re-import is as coarse as the existing machinery: a downstream calculation goes stale when *any* output of the draft changes, not only the one it is linked to.
