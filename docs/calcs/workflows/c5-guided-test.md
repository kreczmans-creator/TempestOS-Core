# C-5 — Guided test (`Tempest.Calc.Library.ManualTesting`, `Tempest.Desktop.GuidedTest`, ADR-0175)

**In plain terms.** The owner test pack asks you to open each worksheet, type or import a set of inputs, run it and compare the outputs with a table. The Guided test does the opening, loading and showing in the app, and keeps your Pass, Fail, Blocked or Skipped (with a note) in a test run you can export. It never saves, checks or issues a calculation and never changes Evidence.

**Where it is.** Engineering → Modules → Calculations → **Guided test**. The panel sits to the left of the worksheet form; the form is the same one as under Worksheets.

**How a run goes.**

1. **Start a new run** (or **Resume the unfinished run**, offered when an earlier run on this machine was not finished). A run is yours: it records the person the app signs work off as, the build (the title bar's version and commit), the start time and the script version. Only that person can add to it, and nobody can start or add to a run while nobody is signed in.
2. Pick a step from the list (filter by runbook section, or search by title, template or discipline). A worked example shows its expected outputs, each with its allowance, and its governing check. A manual step (smoke test, linked chains, imports, lifting, legacy records) shows the runbook's instructions and what must be seen.
3. **Open worksheet with these inputs** opens the template as a scratch sheet and loads the example's inputs through the form's own "Import inputs (CSV/JSON)" path. The sheet is not saved. If the form holds changes you have not saved, the first press says so and the second press for the same step discards them; a form that still holds exactly the loaded example asks nothing.
4. Run it, then compare. Either read the form against the expected outputs yourself, or press **Compare with the form**: it reads the form's current outputs, fills "Values shown", and ticks the result it would give. Nothing is recorded by that. You confirm or change the tick and press **Record result**.
   - Compare reads **only the example the worksheet was opened for**, and only while the form still holds that example's inputs. Selecting another step without opening its worksheet, editing an input, or showing a saved calculation in the form makes Compare say so; press **Open worksheet with these inputs** again.
   - If you change the form after comparing, the comparison, the result it ticked and the values it filled in are taken back (a result you ticked yourself, or values you typed, stay). Pressing **Record result** on a ticked result that came from Compare reads the form again first and refuses if it no longer gives the same values.
   - After a compare each expected line says which allowance was applied ("allowance applied ±0.005"): the coarser of the expected value's last digit and the form's displayed last digit. The governing check is compared by name as well as PASS or FAIL; for an example that has no governing check, the form must show none.
5. Tick **Pass**, **Fail**, **Blocked** or **Skipped**, write a note and press **Record result**. A recorded note holds up to 2,000 characters: a longer pasted note is kept whole in the box, counted under it ("2,600 characters: 600 over the 2,000 a note can hold"), and refused when you record it until you shorten it; it is never cut. A result and note you have not recorded stay on the screen when you go to another part of the app and come back to the same step. Record again on the same step to replace the result. **Finish the run** when you are done: it is dated and read-only from then on.
6. **Copy results sheet** or **Save results sheet…** gives the run as markdown in the runbook's section 11 table (Step, Item, Result, Value shown, Expected, Note), headed with the build, the commit, the tester and the dates. Text from the run (a build name, a note) has `<`, `>` and `&` encoded so that it shows as written in a viewer; a saved file is written whole or not at all. Send it back with the commit.
7. If something cannot be done (the test runs cannot be read or written, the sheet cannot be saved) the status line under the panel says "Could not …" and why; the app carries on.

**The tolerance rule** (shown on the panel). A number passes when it differs from the expected value by no more than half a unit in the last digit of the less precise of the two, counting the digits as written (the form shows 5 significant figures). A text, such as a governing PASS or FAIL, must be identical. A different unit is left to you, and so is a different pressure basis: `bar`, `bar a` (absolute) and `bar g` (gauge) are not taken for one another.

Some worked examples (12 of 87) print an expected value that is a hand calculation held to the example's own verification tolerance, so a line can differ from the printed digits although the form shows what the engine computed when the example was made. One more (the bladder accumulator, 1 of 87) prints its pre-charge in a bare `bar` where the form shows `bar a`. Compare marks such a line **your call** and ticks nothing; it never calls it a fail on its own. They are listed in `GuidedAutoCompareTests` (`ForReview`).

**What is kept.** A test run is a record in the `Manual.TestRuns` collection (ADR-0175): run id, started and finished (UTC), build, build commit, tester, script version and one result per step (step id, outcome, note, values shown, time). Nothing else is written.

**Clearing old runs.** The store keeps at most 1,000 runs. **Delete older finished runs…** (shown when more than 50 finished runs are on file) deletes the finished runs beyond the newest 50 after the app's confirmation dialog tells you how many; it cannot be undone, so save the results sheets you need first. It never deletes a run that is not finished, never a run that still holds the latest result of a worked example (so the dashboard's status does not change), and nothing outside the test-run records. A run with no tester id (made by an earlier build while nobody was signed in) cannot be added to; finish it, then it can be cleared like any other.

**For the verification dashboard.** `IManualTestStatusSource.LatestByTemplateAsync()` (in `Tempest.Calc.Library.ManualTesting`) returns, per worksheet template, the worst of the latest result of each of its worked examples (Fail, then Blocked, then Pass), the date, the commit and the tester of the most recent, and how many of the template's examples have a result. Only results in a **finished** run made on the **current script** count: finish a run for its results to reach the dashboard. It is read-only. `WorkspaceHost.ManualTests` implements it.

**Keeping the script current.** The steps come from `scripts/generate-guided-test-script.py`, which reads the worked examples and `docs/testing/v0.26.0-runbook.md` and writes `src/Tempest.Calc/Tempest.Calc.Library/ManualTesting/guided-test-script.json` (embedded in the library, because `docs/` is not in an installed build). The runbook is the one named by the `VERSION` file (`docs/testing/v<VERSION>-runbook.md`). After a change to a worked example or the runbook, run `python3 scripts/generate-guided-test-script.py`; `python3 scripts/generate-guided-test-script.py --check` says whether the shipped script is stale, and `GuidedTestScriptStalenessTests` fails when it is (on a machine without Python 3.10 or later the check that runs the generator is reported **skipped**, not passed). The generator stops with the example's name when a README's `Governing check:` line is neither `<name> — PASS|FAIL (utilisation <n>)` nor `none`.

**Limits.** The script: 400 steps, 200 expected outputs, 400 input rows, 60 instruction lines and 2,000 characters a field, 200,000 characters of inputs, 4 MB. A run: a 2,000-character note (longer is refused, not cut; the box holds 20,000 characters while you write), 4,000 characters of values shown (longer is cut with a mark), 1,000 results, 200 characters for the tester, build and script version; the store keeps 1,000 runs. The search box takes 100 characters.
